### 从源码到正在运行的实例

### 从源码到正在运行的实例

对 Go 初学者而言，`check -file history-c-a.json` 看似只是“运行一段代码”，但操作系统实际面对的是多个不同层次的对象。

- **Go 源码**：如 `main.go`、检查消息历史的函数、读取 JSON 的逻辑。它们是开发者编辑的文本，本身不能被操作系统直接执行。
- **编译产物**：执行 `go build` 后得到的 `check` 可执行文件。它包含机器可执行指令，以及 Go 运行时所需的内容；这是可被操作系统装载的“程序文件”。
- **进程实例**：在命令行输入 `check -file history-c-a.json` 后，操作系统依据 `check` 文件创建的一次运行实体。此时，代码真正开始执行，参数 `-file` 也成为这次运行的输入。
- **线程与 goroutine**：线程是操作系统为进程提供的执行单位；goroutine 是 Go 在运行时中管理的轻量并发任务。它们都不是源码文件，也不等同于进程。

可以把关系概括为：

`main.go` 等源码 → `go build` → `check` 可执行文件 → 启动命令 → 一个 `check` 进程实例

同一个 `check` 文件可以被启动多次。例如，两个终端分别检查不同历史文件时，得到的是两个独立进程，而不是“同一个程序运行了两遍”这么简单。它们各自拥有独立的地址空间、变量状态和内核资源句柄；一边读取 `history-c-a.json` 失败，不会直接改写另一边的内存或读取位置。

因此，分析本地 IM 的文件检查错误时，应先问清对象：是源码逻辑有问题、构建出的 `check` 文件不对，还是某一次具体进程在读取文件时失败？这条边界会贯穿后续的系统调用与错误分析。

### 同一可执行文件为何能运行多次

### 同一可执行文件为何能运行多次

`check` 是经 `go build` 得到的**可执行文件**：它是一份存放在磁盘上的程序代码与数据。它本身不会“自动检查文件”，只有操作系统把它启动起来，才会产生正在执行的**进程**。

例如，先后多次输入：

`check -file history-c-a.json`

每一次启动请求，操作系统都可以创建一个新的 `check` 进程。它们都来自同一份可执行文件，却不是同一个运行实体。可以把关系理解为：

- 可执行文件：同一张菜谱；
- 进程：按菜谱实际开火做出的一次菜；
- 多次执行：可以同时做多份菜，彼此过程独立。

因此，即使三次命令的参数完全相同，也可能对应三个独立进程。每个进程都有自己的地址空间：自己的变量、堆、栈以及 Go 运行时状态；也各自持有操作系统分配的资源句柄，例如打开的文件、标准输入输出等。

一个进程检查 JSON 时读到的位置、解析出的内容、发生的错误，不会直接改写另一个 `check` 进程中的变量。它们可能读取同一个 `history-c-a.json`，但“共享同一文件”不等于“共享同一进程内存”。

还要区分三个层次：

- **程序/可执行文件**：磁盘上的 `check`；
- **进程实例**：某一次被操作系统启动的 `check`；
- **线程与 goroutine**：进程内部可用于并发执行的单位。

这里的重点是：多次运行命令首先意味着可创建多个进程；是否使用线程或 goroutine，是每个 `check` 进程内部的实现问题。

### 进程、线程与 goroutine 的层次

### 进程、线程与 goroutine 的层次

执行 `check -file history-c-a.json` 时，容易把“Go 程序”“进程”“线程”“goroutine”说成同一件事；它们其实处在不同层次。

- **程序（可执行文件）**：`go build` 产出的文件，是静态的指令与数据集合。它躺在磁盘上，本身不会读取 JSON，也不会占用运行中的内存。
- **进程**：操作系统启动该可执行文件后创建的运行实例。进程拥有相对独立的**地址空间**，并持有内核分配的资源，例如当前工作目录、打开文件的句柄、网络连接等。  
  同一个 `check` 文件可以同时启动多次，形成多个进程实例；它们即使都检查同一个文件，也各自保存自己的变量、打开状态和错误结果。
- **线程**：进程内部实际执行指令的执行流。一个进程至少需要一个线程来开始运行；多个线程通常共享该进程的地址空间和大部分资源。
- **goroutine**：Go 运行时管理的轻量级并发任务，不是操作系统直接等同对待的线程。一个 Go 进程可以创建很多 goroutine；Go 运行时会把它们安排到较少数量的操作系统线程上执行。

可用层次关系记忆：

`可执行文件 → 进程（资源容器） → 线程（执行者） → goroutine（Go 的并发任务）`

例如，`check` 的主 goroutine 可能负责解析命令行参数，另一个 goroutine 负责读取文件；但它们仍属于同一个进程，因而共享该进程打开的文件资源。讨论“文件打不开”时，先问“哪个进程持有并操作该资源”；讨论“哪段代码正在做事”时，再区分线程或 goroutine。

### 进程私有的地址空间与资源句柄

### 进程私有的地址空间与资源句柄

`check -file history-c-a.json` 不是“文件自己被 Go 程序读取”，而是某个**正在运行的进程实例**提出读取请求。要理解这件事，先把进程拥有的两类东西分开：用户态可访问的内存，以及内核代管的资源引用。

当系统启动一次 `check` 时，会为该进程准备独立的**虚拟地址空间**。其中可包含：

- 可执行代码与只读数据；
- `main`、解析参数、校验历史记录时使用的变量；
- Go 运行时分配的堆、栈，以及 goroutine 需要的运行时数据；
- 映射进来的库或文件页面。

“虚拟”表示程序看到的是自己的地址编号，而不是直接操作物理内存。即使两个终端都运行同一份 `check` 可执行文件，两个进程中都可能有一个名为 `history` 的变量；它们只是恰好同名，实际位于彼此隔离的地址空间。一个进程修改自己读入的 JSON 内容，不会改写另一个进程内存中的副本。

但文件不属于进程私有内存。`history-c-a.json` 位于文件系统中，打开它需要内核参与。进程向内核请求打开文件后，内核返回一个小整数形式的**文件描述符**；它可以理解为“本进程持有的某个内核资源引用”。后续读取并非反复按路径寻找文件，而是通过该描述符说明：“读取我刚才打开的那个对象”。

因此可以形成一条基本链路：

`check` 进程 → 私有内存中的解析与缓冲数据 → 文件描述符 → 内核维护的文件对象 → `history-c-a.json`

描述符不等于文件内容，也不等于文件路径；它是进程与内核资源之间的连接标记。若打开失败，进程就没有得到可用于读取的描述符，后续错误分析也应沿着这条边界展开。

### 一次 check 命令的概念生命周期

### 一次 `check` 命令的概念生命周期

设想你已经执行过构建，得到本地 IM 工具的可执行文件。现在输入：

`check -file history-c-a.json`

这不是“源码直接在终端里跑”，而是一条从**可执行文件**到**进程实例**的生命周期。

1. **启动**：操作系统根据命令找到可执行文件，并创建一个新的进程来运行它。可执行文件是静态产物；进程是一次正在进行的运行。即使再次输入同一条命令，操作系统也会创建另一个独立进程。

2. **执行 Go 代码**：新进程从程序入口开始执行，Go 运行时完成必要初始化，再进入 `main` 及其调用链。命令行参数中的 `-file history-c-a.json` 被解析为程序需要检查的文件路径。

3. **打开与读取文件**：程序请求访问该路径。若文件可访问，操作系统为这次打开操作建立资源关联，程序随后读取字节内容，并将 JSON 解析、校验或统计。这里的“请求操作系统帮忙打开文件”正是后续要学习的系统调用边界。

4. **报告结果**：检查成功时，程序把结果写到终端；发生错误时，例如路径不存在、权限不足或 JSON 格式不合法，则输出相应错误信息。文件错误不等于进程本身消失，而是程序根据错误决定如何结束。

5. **关闭与退出**：不再需要文件后，程序关闭相关资源；`main` 返回后，进程退出。它的地址空间、打开文件等内核资源会随退出被回收。

因此，`check` 的一次执行可以概括为：**创建进程 → 执行代码 → 请求文件操作 → 输出结果 → 释放资源并退出**。下一节将把“请求打开、读取、关闭文件”进一步拆到系统调用层面。

> **要点** — 可执行文件是静态产物；进程是其一次运行实例，拥有独立地址空间和资源，并通过线程与运行时完成执行。

一次本地命令的执行，不是从 main 函数突然开始，而是经历 shell、操作系统、Go 运行时与程序自身协作的完整生命周期。

### 从命令行文本到进程映像

### 从命令行文本到进程映像

在终端输入：

`imtool check ./message.json`

这首先只是一行文本。Shell 会按规则解析它：`imtool` 是要执行的命令，`check` 是子命令，`./message.json` 是路径参数。引号、空格、通配符和变量展开也由 Shell 处理；例如 `$HOME/a.json` 会先展开为实际路径。程序通常接收到的是已经整理好的参数列表，而不是原始命令行字符串。

随后，Shell 根据 `PATH` 查找 `imtool` 对应的可执行文件，并请求操作系统创建新进程。新进程不是“复制一份终端”，而是拥有独立的进程标识、虚拟地址空间、文件描述符表和执行上下文。它通常继承当前工作目录、环境变量以及标准输入/输出/错误流；路径如何受工作目录和环境影响，将在后续深入讨论。

操作系统把可执行文件装载为该进程的映像：代码段、只读数据、可读写数据、堆、栈等被映射到新进程的虚拟内存中，并设置入口地址。对 Go 程序而言，这个入口先进入 Go runtime：运行时完成必要初始化，建立调度所需资源，然后才调用 `main.main`。

因此，`main` 不是进程的真正起点，而是语言运行时交给应用代码的起点。Go 运行时可能创建多个操作系统线程以支持调度、垃圾回收或系统调用，但这不意味着“一进程等于一线程”：一个进程可以包含多个线程，而本例仍只是 Shell 启动的一个独立进程。

### Go 运行时、main 与线程边界

### Go 运行时、`main` 与线程边界

操作系统装载可执行文件后，并不会直接跳到你写的 `main`。对 Go 程序而言，入口代码会先进入 Go runtime：它完成必要的运行时初始化，例如建立调度器、准备垃圾回收相关状态、初始化主 goroutine，随后才调用包级初始化函数与 `main.main`。

一个教学型 CLI 的控制流可概括为：

`shell` → `OS 创建进程并装载映像` → `Go runtime 初始化` → `main` → `run` → `os.Exit`

例如：

`main` 负责把错误分类映射为退出码；`run` 负责实际业务流程，如打开文件、读取内容、校验格式，并在函数返回前关闭已打开的资源。

```text
main()
  └─ err := run(args)
       ├─ 打开
       ├─ 读取
       ├─ 校验
       └─ 关闭
  └─ os.Exit(退出码)
```

这里要区分两层“结果”：

- `run` 返回 `error`，表示程序内部控制流中的成功或失败；
- `main` 将错误转换为进程退出码，例如 `0` 表示成功，`2/3/4/5` 表示不同教学约定的失败类别；
- shell 最终只能取得进程退出状态，而不能直接取得 Go 的 `error` 值。

还要注意，`os.Exit(n)` 会立刻终止整个进程，**不会执行尚未运行的 `defer`**。因此，文件关闭等资源清理应放在 `run` 内完成；`main` 只在所有正常返回路径都结束后调用 `os.Exit`。

最后，进程不等于线程。一次命令执行通常对应一个 Go **进程**，但 Go runtime 可能为调度、垃圾回收或阻塞系统调用创建多个操作系统线程；goroutine 更不是线程，而是由 runtime 调度的轻量级执行单元。

### 打开、读取、校验与关闭文件

### 打开、读取、校验与关闭文件

设想用户在终端执行：

`im check ./messages.log`

`main` 通常只负责组织流程：解析命令后调用 `run`，由 `run` 完成资源操作并返回错误或结果。对 `check` 而言，最小路径可写成：

`os.Open` → 读取内容 → 校验格式/签名 → `Close` → 返回状态

```go
func runCheck(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close()

    data, err := io.ReadAll(f)
    if err != nil {
        return err
    }
    return verifyMessages(data)
}
```

`os.Open(path)` 并不是 Go 直接“拿到文件内容”。它会请求操作系统的文件服务：内核依据当前进程的工作目录解释相对路径，检查路径是否存在、是否为目录、当前用户是否有读取权限；成功后，内核返回一个可供该进程使用的文件句柄。Go 将其包装为 `*os.File`。

随后 `io.ReadAll(f)` 反复发起读取请求。数据可能已在内核缓存中，也可能需要从磁盘、网络文件系统等底层设备取得；无论来源如何，程序看到的是一串字节。`verifyMessages` 再把字节按 IM 日志协议解析，例如检查每条消息的字段、长度、时间顺序或校验值。注意：“成功读到文件”不等于“内容有效”；前者是 I/O 成功，后者是业务校验成功。

`defer f.Close()` 保证 `runCheck` 返回时归还文件描述符等内核资源。这里应在 `run` 内完成清理：若外层直接调用 `os.Exit`，Go 不会执行尚未运行的 `defer`。因此常见设计是 `run` 返回错误，由 `main` 映射为教学约定的退出码：成功为 `0`，路径或打开失败可为 `2`，读取失败为 `3`，内容校验失败为 `4`，关闭失败为 `5`；最后才由 `main` 调用 `os.Exit`。

### 错误返回与教学退出码

### 错误返回与教学退出码

函数的“返回错误”和进程的“退出码”属于不同层次：

- `error` 是程序内部控制流：`open`、`read`、校验等步骤失败后，把原因交给调用者处理。
- 退出码是程序对 shell 的最终回答：命令是否成功、失败大致属于哪一类。shell 可通过 `$?` 取得它。

可为教学 CLI 约定如下：

| 退出码 | 含义 | 典型场景 |
|---:|---|---|
| `0` | 成功 | 文件已读取并通过校验 |
| `2` | 参数错误 | 缺少路径、选项格式错误 |
| `3` | 打开失败 | 文件不存在、权限不足、路径指向目录 |
| `4` | 读取失败 | 读取过程中发生 I/O 错误 |
| `5` | 校验失败 | 内容格式不合法、摘要不匹配 |

例如，`run(args) error` 可以保留底层错误；`main` 再根据错误类别映射为退出码：

`参数错误 → 2`，`打开错误 → 3`，`读取错误 → 4`，`校验错误 → 5`。

这避免让每个底层函数都直接调用 `os.Exit`。底层函数只报告失败，上层统一决定命令行语义、打印诊断并退出。正常路径应显式关闭文件；异常路径也应在 `run` 内通过 `defer` 等机制完成清理，因为 `os.Exit(code)` 会立即结束进程，**不会执行尚未运行的 `defer`**。

因此，`error` 追踪“为什么失败”，退出码表达“shell 应如何理解这次命令”。

### 退出进程与 shell 获取结果

### 退出进程与 shell 获取结果

`run` 的职责是完成业务流程：打开文件、读取内容、校验消息，并在返回前关闭已打开的资源。它通常返回一个错误或结果，而不应直接随处终止进程：

```go
func main() {
    if err := run(os.Args[1:]); err != nil {
        fmt.Fprintln(os.Stderr, err)
        os.Exit(2)
    }
    os.Exit(0)
}
```

这里的分工很重要：

- `run` 负责“做事”和清理，例如 `defer file.Close()`；
- `main` 负责把业务结果翻译为进程退出码；
- `os.Exit(code)` 立即结束整个 Go 进程，并把 `code` 交给操作系统。

尤其要注意：`os.Exit` **不会执行当前进程中尚未运行的 `defer`**。因此，若在 `run` 内打开文件后直接调用 `os.Exit`，原本依赖 `defer` 的关闭逻辑可能来不及执行。更稳妥的结构是让 `run` 返回，待其栈帧正常退出、清理完成后，再由 `main` 调用 `os.Exit`。

教学 CLI 可以约定：

- `0`：成功；
- `2`：命令参数错误；
- `3`：文件打开或读取失败；
- `4`：消息格式或校验失败；
- `5`：其他内部错误。

shell 启动程序后会等待其结束，并保存退出状态。用户可用 `$?` 查看最近一条命令的结果：

```sh
imtool verify message.txt
echo $?
```

退出码表达的是“进程最终结果”，不等同于 Go 的 `error`；一个错误如何映射为 `2`、`3` 或 `4`，是该命令行工具自己的约定。

> **要点** — CLI 的结果由进程生命周期串联：系统装载、运行时启动、文件处理、错误映射、退出并交还状态。

03.01中的地址、字节与缓存进入进程后，不再是“文件中的一串位置”：操作系统为每个运行中的程序建立独立的虚拟地址空间，Go运行时再在其中管理堆与goroutine栈。

### 从可执行文件到独立进程地址空间

### 从可执行文件到独立进程地址空间

磁盘上的可执行文件只是一个静态文件：其中包含机器指令、只读常量、初始全局数据，以及供装载器使用的段和元数据。它尚未拥有“正在执行”的栈、堆、打开的网络连接或聊天窗口状态。

用户启动本地 IM 工具时，操作系统创建一个进程，并由装载器依据可执行文件描述建立虚拟内存映射。随后，CPU 以该进程的虚拟地址执行代码；内核还为它关联进程号、文件描述符、权限凭据、信号状态等运行时资源。Go 程序启动后，Go 运行时会在这片地址空间中进一步管理 Go 堆、goroutine 栈和垃圾回收所需的数据结构。

可以把关系区分为：

- **可执行文件**：磁盘上的可复制、可保存对象。
- **进程**：一次正在运行的实例，拥有独立的运行状态。
- **虚拟地址空间**：该进程可见的地址范围及其映射规则。
- **物理内存页**：由内核按需分配、回收或换出的实际存储资源。

同一个 IM 可执行文件可以被启动两次，形成两个进程。它们或许共享部分只读代码页，但各自的全局可写数据、堆、栈和连接状态仍应隔离：一个实例中收到的消息不能因普通内存写入而改写另一个实例的会话。

这种隔离首先来自虚拟地址：两个进程都可能使用看似相同的地址，如 `0x...`，但内核为它们维护不同的映射与访问权限。某个虚拟地址是否有效、可读、可写或可执行，取决于当前进程，而不是地址数字本身。地址也不是文件偏移；内存中的切片更不是磁盘文件的原件。页表与 TLB 如何让 CPU 落实这些映射，将在 03.05 展开。

### 概念图中的代码、数据、栈与堆

### 概念图中的代码、数据、栈与堆

把一个本地 IM 工具启动后的进程画成“代码、数据、栈、堆”几块区域，目的是说明**职责与访问方式**，不是声称内存真的按图中顺序占据一段连续物理内存。

- **代码区域**：保存已加载的机器指令，例如登录、收发消息、界面刷新等函数编译后的结果。它通常可执行、通常不允许随意写入；多个进程运行同一程序时，底层代码页还可能被共享。
- **全局数据区域**：保存生命周期接近整个进程的状态，例如全局配置、初始化表、包级变量。已初始化数据与未初始化数据在装载时的来源不同，但概念上都属于长期存在的数据。
- **栈**：保存函数调用现场，如参数、局部变量、返回地址。函数调用深入时栈帧增加，返回时相应释放。Go 的每个 `goroutine` 有自己的可增长栈，因此不能把“栈”简单理解为唯一、固定大小的一条内存带。
- **堆**：保存需要跨函数继续存活、大小或生命周期不易在编译期确定的对象，例如消息列表、聊天记录缓存、图片元数据。Go 运行时负责分配、垃圾回收与部分内存复用。

这些区域首先是**虚拟地址空间中的映射和范围**。内核决定某段虚拟地址当前映射到哪些物理页，未被访问的页未必已驻留内存；同一概念区域也可能由许多离散物理页组成，或在需要时再扩展。

因此，变量的地址不是它在可执行文件或聊天数据库中的文件偏移；一个内存切片也不是磁盘文件本体。文件、匿名内存与共享库都可通过映射进入进程地址空间，而其具体页表与 TLB 如何完成转换，将在后续讨论。

### Go堆与goroutine栈：运行时的管理层

### Go堆与goroutine栈：运行时的管理层

进程拿到的是一片由操作系统映射和保护的**虚拟地址空间**；Go 程序在这片空间之上，还运行着一层 Go 运行时。它负责分配对象、调度 goroutine、扩展栈、回收不再使用的内存。因此，图中的“堆”和“栈”应理解为**运行时管理的逻辑区域**，而不是磁盘文件中的连续片段，更不是固定对应某段物理内存。

- **Go 堆**存放通过逃逸分析或显式分配产生、生命周期可能超出当前函数调用的对象，例如聊天消息结构、连接状态、切片底层数组等。运行时会按大小类别、页和跨度等组织分配，并由垃圾回收器追踪可达对象。
- **goroutine 栈**属于单个 goroutine 的调用现场，保存局部变量、返回地址和函数调用帧。它通常从较小容量开始；调用变深、空间不足时，运行时可为其扩展并调整相关引用。它不同于“每个线程一块固定的大栈”。
- **系统线程栈**仍由操作系统或线程库提供，用于执行 Go 调度器和当前运行中的 goroutine；不要把它与每个 goroutine 的逻辑栈混为一谈。

例如，`sendMessage` 中的短暂整型变量可能留在某个 goroutine 的栈帧；被多个会话共享、在函数返回后仍需存在的消息对象，则可能进入 Go 堆。二者最终都位于该进程的虚拟地址空间中，但其具体地址、连续性和实际驻留的物理页都可随运行时与内核策略变化。

所以，内存预算中的“堆占用”或“栈占用”是容量与生命周期的概念估算，不应据此推断固定地址、固定物理内存，或把内存切片当作磁盘上原始文件的直接视图。

### 地址、切片与文件偏移不能混为一谈

### 地址、切片与文件偏移不能混为一谈

本地 IM 工具读取配置、加载联系人缓存或发送消息时，常同时出现“地址”“切片”“偏移”三个词；它们都能定位字节，却属于不同层次。

| 概念 | 它定位什么 | 典型形式 | 关键限制 |
|---|---|---|---|
| 虚拟内存地址 | 当前进程地址空间中的某个字节 | `0x...`、指针 | 只在该进程的当前映射下有意义 |
| 切片 | 一段内存的视图 | Go 的 `[]byte` | 包含指向底层数组的位置、长度和容量，不等于独立文件 |
| 文件偏移 | 文件字节流中的位置 | `offset=1024` | 相对文件开头计数，需经读写系统调用或映射才接触内存 |

例如，`buf := make([]byte, 4096)` 创建的是 Go 运行时管理的一段堆内存；`buf[0]` 的位置可由某个虚拟地址访问，但它没有天然对应某个磁盘文件偏移。执行读取后：

`n, err := file.ReadAt(buf, 1024)`

含义是：请求内核把文件中从偏移 `1024` 开始的字节复制到 `buf` 所表示的内存区域。文件偏移描述**来源**，切片描述**接收视图**，虚拟地址描述**进程如何访问该视图中的字节**。

即使使用内存映射，文件页被映射进地址空间后，也不能简单说“内存地址就是文件偏移”。映射还涉及映射起点、页边界、权限、共享或私有写入等条件；同一文件区域也可被映射到不同虚拟地址。内核维护这些对应关系，后续再讨论页表与 TLB 如何参与地址转换。

### IM检查命令的内存预算与内核映射

### IM检查命令的内存预算与内核映射

设本地 IM 工具执行：

`im check --input messages.json --output report.txt`

它不会把 `messages.json` 的“文件偏移”直接当作内存地址。进程启动后，内核为它建立独立的虚拟地址空间；当程序通过系统调用读取文件时，内核负责把文件数据经页缓存、缓冲区或映射机制交给进程可访问的内存区域。

可以先做一份**概念性**预算，而非承诺固定字节数：

- **输入数据**：读取中的 JSON 字节、缓冲区，以及可能保留的原始文本。
- **解析结果**：消息、用户、时间戳等结构；字段中的字符串通常还会引用或复制相应字节。
- **检查过程临时对象**：去重集合、错误列表、排序索引、统计计数器。
- **输出数据**：报告文本的拼接缓冲、格式化临时字符串，以及写入前尚未交给内核的字节。
- **运行时开销**：Go 堆对象、垃圾回收元数据、goroutine 栈和运行时自身结构。

若输入大小为 $N$，解析后对象与索引额外占用约 $P$，输出与临时工作区为 $W$，可用

$$M_{\text{概念}} \approx N + P + W + M_{\text{运行时}}$$

帮助判断风险：一次性读入并完整解析通常使峰值随 $N$ 增长；流式读取、边解析边检查、分批写出，则能降低同时存活的数据量。

这里的“堆”“goroutine 栈”是 Go 运行时在虚拟地址空间中管理的对象，不应画成固定、真实连续的物理内存块。内核维护虚拟页到物理页及文件页的映射关系；具体页表与 TLB 如何让地址访问落到实际存储位置，将在 03.05 展开。

> **要点** — 进程看到的是内核维护的虚拟地址空间；Go运行时在其中管理堆和goroutine栈，地址、切片与文件偏移各属不同层次。

本节建立用户态与内核态的保护边界：本地 IM 检查命令为何必须通过系统调用，才能请求文件等操作系统服务。

### 特权边界为何存在

### 特权边界为何存在

本地 IM 工具虽然能显示消息、读写配置、建立连接，却不能直接操纵磁盘控制器、网卡寄存器、页表或其他进程的内存。它通常运行在**用户态**：CPU 对可执行指令和可访问资源施加限制，普通代码不能随意关闭中断、修改内存映射或抢占设备。

这些高权限能力集中在**内核态**。内核负责管理：

- 进程与线程的创建、调度和退出；
- 虚拟内存、页表与地址空间隔离；
- 文件系统、磁盘、网络和终端等设备；
- 多个进程竞争的共享资源与权限检查。

这样设计的首要目标是隔离与稳定性。若 IM 客户端因 bug 写错地址，通常只会导致自身崩溃，而不应直接覆写另一个应用的数据；若某个程序请求删除文件，内核可依据身份、路径和权限决定是否允许。

因此，用户态程序必须经由系统调用请求内核服务，例如打开文件、发送网络数据或创建进程。系统调用不是普通函数调用：它会触发受控的特权切换，内核检查参数和权限后执行，再返回结果或错误。该边界能显著缩小故障与攻击影响范围，但并不意味着绝对安全；内核漏洞、错误配置或被授予的过高权限仍可能破坏隔离。

### 系统调用：受控的服务入口

### 系统调用：受控的服务入口

本地 IM 工具想读取配置、打开聊天记录文件、创建网络连接或等待键盘输入时，不能直接操纵磁盘控制器、网卡寄存器或内核维护的文件表。这些资源属于内核保护的范围；普通进程只能通过**系统调用**提交受控请求。

可以把一次读取文件抽象为：

\[
\texttt{read(fd, buf, n)} \rightarrow (\texttt{count}, \texttt{error})
\]

其中，`fd` 是已打开文件的标识，`buf` 指向用于接收数据的用户态缓冲区，`n` 是期望读取的字节数。程序发起调用后，处理器执行一种受控的陷入（trap）机制：从用户态切换到内核态，内核检查参数和权限，定位对应资源，执行读取；完成后再返回用户态，并给出结果。

返回并不总是“成功数据”。常见结果包括：

- 返回实际读取的字节数：可能小于请求的 `n`；
- 返回 `0`：例如读到文件末尾；
- 返回错误：如文件描述符无效、权限不足、资源暂时不可用。

在 Go 中，开发者通常使用 `os.Open`、`File.Read`、`net.Dial` 等标准库接口，而非手写系统调用；这些接口会在需要时封装并调用底层 OS 服务。Linux 可通过 `man syscalls` 查看系统调用总览。

系统调用不是普通函数调用：它涉及特权级切换和内核验证；也不是网络 RPC：请求不会经由网络到远端服务。它同样不同于 goroutine 调度：前者跨越用户态与内核态边界，后者主要决定用户程序中的并发任务何时运行。保护边界能限制进程任意越权，但并不意味着系统自动消除所有漏洞或错误。

### 从 check 启动到读取本地消息

### 从 check 启动到读取本地消息

设想本地 IM 工具提供命令：

`im check`

它的目标是读取当前用户的消息缓存文件，例如 `~/.local/share/im/messages.json`，筛选未读消息并输出摘要。这个过程看似只是“调用几个函数”，实际跨越了用户态与内核态的保护边界。

1. **启动进程**  
   Shell 解析命令后，请求操作系统创建并装载 `im` 进程。Go 程序开始执行 `main`，解析 `check` 子命令；这些 Go 函数仍运行在**用户态**，不能直接操作磁盘设备或任意内存页。

2. **打开文件**  
   程序通过标准库调用，例如 `os.Open(path)`。它不是普通的磁盘读取函数：标准库最终会封装 Linux 的 `openat` 等系统调用，提交路径、打开标志和权限参数。CPU 经由 trap 进入内核态，内核检查路径、文件权限、挂载状态等，再返回文件描述符，例如 `fd=3`。

3. **读取内容**  
   后续 `file.Read(buf)` 通常会进一步触发 `read` 系统调用。内核根据文件描述符定位文件，将数据复制到该进程提供的用户态缓冲区，并返回实际读取字节数 `n`。若返回错误，如权限不足、文件不存在或 I/O 故障，Go 会将其表现为 `error`。

4. **关闭与输出**  
   程序解析 JSON、计算未读数、调用 `file.Close()` 释放描述符；关闭通常对应 `close` 系统调用。最后 `fmt.Println` 把结果写到终端，底层又可能通过 `write` 请求内核服务。

可将关键边界概括为：

`Go 用户代码 → 标准库封装 → 系统调用 → 内核检查与执行 → 返回值/错误 → Go 用户代码`

系统调用不是每个 Go 函数都会发生，也不等同于网络 RPC：前者是同一台机器上从用户态请求内核服务的受控入口。它服务于进程隔离和资源保护，但并不意味着应用天然绝对安全；错误处理、权限设计与输入校验仍不可省略。它也不同于 goroutine 调度，后者主要是运行时对用户态并发任务的安排。

### Go 标准库与系统调用不是一一对应

### Go 标准库与系统调用不是一一对应

调用 Go 函数，并不意味着发生了一次系统调用。二者处在不同层次：

- **普通 Go 函数调用**：如 `strings.TrimSpace`、业务中的 `检查命令()`，通常只在当前进程用户态执行，主要是栈帧、参数和返回值的变化。
- **标准库封装**：如 `os.ReadFile`、`net.Dial`、`time.Sleep`，提供跨平台、易使用的接口；一次调用可能触发零次、一次或多次系统调用，也可能先命中缓存、复用连接或经过运行时处理。
- **实际系统调用**：例如 Linux 的 `openat`、`read`、`write`、`socket`、`epoll_wait`。只有这类受控入口才会请求内核操作文件、套接字、进程或时间等资源。其参数、返回值和错误可参考 Linux `man 2 syscalls`，Go 通常通过 `os`、`net`、`syscall` 或 `x/sys/unix` 等封装访问。
- **网络 RPC**：RPC 是向另一台机器或另一服务发请求。它通常会经过本地的 `send`、`recv` 等系统调用，但“调用远端方法”本身不是系统调用。
- **goroutine 调度**：调度器负责把多个 goroutine 安排到线程上运行；它不是每次函数调用都进入内核。阻塞 I/O、创建线程或等待事件时，运行时才可能借助系统调用协调执行。

例如：

`os.ReadFile("config.json")` → Go 封装与运行时处理 → 可能执行 `openat`、`read`、`close` → 返回 `[]byte` 或错误。

因此，应从“是否请求内核服务”而非“是否调用了 Go 函数”判断系统调用。goroutine 的并发调度与用户态—内核态的保护边界相关但不同：前者解决任务如何运行，后者限制程序能直接做什么。

### 错误边界与命令退出状态

### 错误边界与命令退出状态

本地 IM 工具执行“读取配置”“加载历史消息”等命令时，失败并不只有一种含义。应先区分错误发生的边界，再决定提示文本与退出状态。

- **操作系统错误**：系统调用请求未完成。例如打开文件时得到“文件不存在”、读取目录时得到“权限不足”、磁盘或设备读取失败。Go 标准库通常把这类结果包装为 `error`；可用 `errors.Is(err, os.ErrNotExist)`、`errors.Is(err, os.ErrPermission)` 判断语义，而不要只比较错误字符串。
- **应用校验错误**：文件能被打开和读取，不代表内容可用。例如 JSON 格式损坏、必填字段缺失、消息时间戳非法。这不是内核拒绝请求，而是应用对字节内容解释后的结论。
- **命令行退出状态**：这是 CLI 向调用者报告最终结果的协议。通常 `0` 表示成功，非 `0` 表示失败；脚本、CI 或其他程序据此判断命令是否继续执行。退出状态不等同于某个系统调用的错误码。

可以形成清晰的分层流程：

`open/read 失败 → 保留并说明操作系统原因`  
`open/read 成功但解析失败 → 报告内容无效`  
`任一无法完成命令目标的错误 → 命令以非零状态退出`

例如，配置文件不存在时，可以提示“未找到配置文件，请先初始化”；权限不足时提示“当前用户无权读取”；JSON 损坏时提示“配置内容无效”。三者对用户的修复动作不同，却都可能让 CLI 返回非零状态。

不要把“失败”简单吞掉后返回空结果：那会把真实的系统边界错误伪装成“没有消息”。同时，退出状态只是进程结束时的摘要；详细诊断应写入错误输出，而正常结果应保留给标准输出。

> **要点** — 系统调用是用户程序请求内核服务的受控边界；Go 封装、文件错误与命令退出状态需分层理解。

以本地 IM 的 v1 配置检查命令为线索，沿着“打开、限长读取、解析校验、输出、退出”理解文件 I/O 的权限边界与错误边界。

### 从命令启动到验证结果

### 从命令启动到验证结果

用户执行 `imctl check ./config.json` 后，操作系统先创建一个新进程，并把命令行参数交给它。Go 程序从参数中取得路径，随后完成一条清晰的用户空间流程：

1. **打开文件**：调用 `os.Open(path)`。成功时得到 `*os.File`，其内部关联一个由进程持有的文件描述符；它是内核授予的整数句柄，不是文件内容本身。
2. **限制读取量**：对文件使用 `io.LimitReader(f, 1<<20+1)`，再 `io.ReadAll`。多读出的 1 字节专门用于判断：文件是否超过 `1 MiB`。
3. **及时关闭**：无论后续解析是否成功，都应执行 `f.Close()`，归还描述符这一有限资源。
4. **解析与领域校验**：将字节交给 JSON 解码器，再检查例如版本必须为 `v1`、必填字段存在、字段组合合法等规则。
5. **输出并退出**：只有全部验证通过，才向标准输出写入成功结果；任一步失败则向标准错误输出原因，并以非零状态码退出。

可将主干理解为：

`启动进程 → 接收路径 → 打开 → 限长读取 → 关闭 → JSON 解码 → v1 规则校验 → 输出结果 → 退出`

这里有两条不能混淆的边界。`os.Open` 成功，仅表示内核允许该进程按请求方式访问该路径；它不表示文件一定存在有效 JSON，更不表示其内容符合本地 IM 的 `v1` 配置规则。相反，JSON 解码和领域校验发生在用户空间，属于程序自己的判断。

“打开、读取、关闭”在概念上对应文件 I/O 操作，但 Go 的实现可能因平台和版本不同而涉及多个具体系统调用；此处不承诺 API 与某个 syscall 一一对应。文件描述符如何关联 inode、如何维护读写 offset，将在 03.07 再展开。

### 打开文件：对象、描述符与访问权

### 打开文件：对象、描述符与访问权

执行 `os.Open("v1.json")` 成功，并不意味着 Go 已把配置文件全部读入内存。它首先向操作系统请求“以只读方式访问这个路径所指向的对象”；若路径解析、文件存在性与访问权限都通过，Go 会返回一个 `*os.File`：

`f, err := os.Open("v1.json")`

`*os.File` 是用户空间中的 Go 对象，负责提供 `Read`、`Close` 等方法；它通常关联着该进程持有的一个**文件描述符**。文件描述符可理解为进程表中的整数句柄：内核借此知道“这个进程正在访问哪个已打开对象、采用什么访问模式、读写位置处于何处”等状态。

因此应区分三层：

- **文件字节本体**：存储在文件系统中的内容，例如 JSON 文本。
- **文件描述符**：进程持有的访问凭证和索引，不等于文件内容。
- **`*os.File`**：Go 对描述符的封装，使程序能以方法调用方式读、关闭文件。

`os.Open` 的成功只说明内核允许当前进程按只读方式打开该对象；它不说明文件是 JSON，更不说明其字段、版本号或业务语义合法。后续 `io.LimitReader`、读取、解码和领域校验都仍在用户空间完成。

最后必须调用 `f.Close()` 归还打开资源。概念上的“打开、读取、关闭”在不同平台、Go 版本下可能对应多个具体系统调用或运行时步骤，不应机械地建立一一对应关系。

### 受限读取：先守住 1MiB 边界

### 受限读取：先守住 1MiB 边界

本地 IM 的 v1 配置约定“文件不得超过 1MiB”时，不能先把整个文件读入内存、再检查长度。文件可能远大于约定，甚至来自意外路径；读取阶段就应设置上限：

`r := io.LimitReader(f, max+1)`

随后执行 `data, err := io.ReadAll(r)`。这里故意使用 `max+1`，而不是 `max`：

- 若读到的 `len(data) <= max`，文件在大小边界内；
- 若 `len(data) == max+1`，即可判定原文件至少超过 1MiB，立即报“文件过大”；
- `LimitReader` 只允许本次读取最多取得 `max+1` 字节，因此不会因超大文件而无界占用内存。

`io.LimitReader` 并不会修改文件，也不会保证文件恰好只有这些字节；它只是给读取者加了一道上限。即使底层文件实际有 2GiB，`ReadAll` 在这里也至多收集 `1MiB+1` 字节。

打开成功得到的 `*os.File` 持有底层文件描述符。描述符是进程用于引用已打开文件的整数句柄，不是文件内容本身；无论读取、解析还是校验成功与否，都应及时：

`defer f.Close()`

这样函数返回时会释放该打开资源，避免反复检查配置时耗尽描述符。`Close` 的意义是结束进程对该打开对象的使用；其具体可能涉及哪些系统调用，取决于平台和 Go 版本，不应机械地与某一个调用一一对应。

大小合格只说明“读取量未超限”。之后的 JSON 解码与领域校验仍在用户空间完成：内核允许打开、读取某文件，不等于文件内容就是合法的 v1 配置。

### 内核准入不等于内容正确

### 内核准入不等于内容正确

`os.Open` 成功只说明：操作系统允许该进程以请求的方式打开这个路径，并返回一个 `*os.File`；它**不**说明文件一定能读完，更不说明其中是合法 JSON 或符合本地 IM 的 v1 配置规则。

可将检查过程分成几层错误边界：

| 情况 | 发生层次 | 含义 | 处理方式 |
|---|---|---|---|
| 文件不存在 | 路径解析/打开阶段 | 指定路径没有可打开的对象 | 报告“配置文件不存在” |
| 权限拒绝 | 内核访问控制 | 文件存在，但当前进程无权访问 | 报告“无读取权限”，不要误称为 JSON 错误 |
| 读取失败 | 已打开后的 I/O 阶段 | 设备、网络文件系统、介质或其他 I/O 条件出错 | 保留读取错误；不能把部分内容当完整配置 |
| JSON 无效 | 用户空间解码阶段 | 字节序列不符合 JSON 语法或目标结构 | 报告格式错误 |
| 领域校验失败 | 用户空间业务规则阶段 | JSON 可解析，但字段值不满足 v1 约束 | 报告配置语义错误 |

典型流程是先 `os.Open`，再用 `io.LimitReader(file, max+1)` 限制读取量，并在 `ReadAll` 后立即安排 `Close`。若读到的长度超过 `max`，应拒绝该文件，而不是继续解码。只有“读取完整、未超限、JSON 解码成功、领域校验通过”后，才向标准输出给出验证成功结果。

这里的文件描述符本质上是进程持有的整数句柄，指向内核维护的打开文件状态，不是文件字节本身。打开、读取和关闭在不同平台或 Go 版本中可能涉及不同的具体系统调用；理解其职责边界即可，不必把每个 Go 方法机械对应为唯一 syscall。

### 系统调用边界与稳定的程序约定

### 系统调用边界与稳定的程序约定

对本地 IM 的 `v1` 配置检查器而言，程序可写成一条清晰的数据路径：

`os.Open` → `io.LimitReader(max+1)` → `io.ReadAll` → `Close` → JSON 解码与领域校验 → `stdout` → 退出。

`os.Open(path)` 成功后得到的是 `*os.File`。它在概念上代表进程向内核申请到的“已打开文件”访问能力；底层可关联一个文件描述符，即进程持有的整数句柄。描述符不是文件内容，也不等同于路径；文件的 inode、共享偏移等细节留待后续讨论。

可以把上述调用理解为经过内核文件服务的路径：

- 打开阶段：内核检查路径、文件是否存在及当前进程是否有权限。
- 读取阶段：程序通过已打开对象请求字节；`LimitReader(max+1)` 使程序最多读取 `max+1` 字节，从而能区分“未超过 `max`”与“文件过大”。
- 关闭阶段：`Close` 释放该打开对象占用的资源，应尽早执行，通常在成功打开后立刻安排 `defer f.Close()`。

但不要把 Go 函数机械地等同于某一个系统调用。一次 `Open`、读取或关闭在不同操作系统、Go 版本和文件类型上，可能涉及不同的具体系统调用、运行时逻辑或缓存行为。稳定的程序约定应建立在标准库语义上，而非某个 syscall 的逐一映射。

内核允许读取，只说明访问控制通过；它不保证内容是合法 JSON，更不保证满足 `v1` 的领域规则。解码、字段必填、版本匹配等验证都在用户空间完成。只有完整验证成功，才向标准输出写入成功结果；任何打开、读取、超限、解码或领域校验失败都应写入标准错误，并以非零退出状态结束。

> **要点** — 文件描述符连接进程与内核文件服务；访问获准后，内容解析和领域校验仍由用户空间负责。

本地 check 命令不仅要判断消息内容，还必须把参数、文件访问与内容校验的失败边界清楚地交给调用者。

### 先划清命令的失败边界

### 先划清命令的失败边界

`check` 命令的退出码是它与 shell、自动化脚本之间的稳定合同。不要把所有失败都压成“非零退出”，而应先按责任边界分类：

| 退出码 | 含义 | 典型情况 |
|---:|---|---|
| `0` | 成功或帮助 | 校验通过；显示 `--help` |
| `2` | 参数错误 | 缺少文件参数、未知选项、参数组合非法 |
| `3` | 本地内容错误 | JSON 无效、版本不支持、消息重复、字段违反规则 |
| `4` | I/O 错误 | 路径不存在、无读取权限、读取中断、关闭或写出失败 |
| `5` | 未知错误 | 未预期的内部状态、未分类的依赖故障 |

文件不存在不能靠错误文本中是否包含“no such file”判断，应使用错误身份：

`os.IsNotExist(err)` 或 `errors.Is(err, fs.ErrNotExist)`

同理，权限拒绝、设备故障等也应保留底层错误链，再映射到 `4`。这里的“权限”是操作系统内核对文件、目录的许可；它不等于 IM 会话是否有权查看某条消息，后者属于内容或业务规则。

参数在打开文件前检查，打开成功后再解析内容：前者失败返回 `2`，后者语法或语义失败返回 `3`。`defer file.Close()` 只在当前函数返回时执行；若命令正在导出结果，`Close` 失败意味着数据未必完整，不能仍报告成功，应转为 I/O 退出 `4`。

调用者既看退出码，也应按合同处理标准输出与标准错误：成功结果写入 stdout，诊断信息写入 stderr。这样脚本能可靠分支，而人也能读懂失败原因。

### 文件错误应按身份识别

### 文件错误应按身份识别

`check` 命令读取本地消息文件时，首先面对的是操作系统层面的 I/O 边界：路径不存在、目录不可访问、文件权限不足、设备故障、读取中断等。它们的共同点不是“报错文字相似”，而是工具尚未获得可供校验的完整输入。因此，无论后续本可进行 JSON、版本或去重检查，都应归入 I/O 错误并退出 `4`。

典型流程可写成：

1. 参数已解析后，尝试打开或读取文件；
2. 若打开、读取或关闭阶段失败，向 `stderr` 输出诊断信息；
3. 返回退出码 `4`，而不是把它误判为内容无效。

错误分类必须依据错误身份，而非文本匹配。例如，不应写成“错误信息包含 `no such file` 就是文件不存在”：错误文本可能随操作系统、语言版本、包装层而变化，也可能被其他错误碰巧包含相同片段。

应使用标准库提供的身份判断：

- `os.IsNotExist(err)`：判断错误是否表示目标不存在；
- `errors.Is(err, fs.ErrNotExist)`：适合错误经过 `%w` 包装后继续追溯；
- 对权限类错误，可用 `errors.Is(err, fs.ErrPermission)` 或相应平台错误进一步诊断。

```go
data, err := os.ReadFile(path)
if err != nil {
    if errors.Is(err, fs.ErrNotExist) {
        fmt.Fprintln(os.Stderr, "输入文件不存在:", path)
    } else if errors.Is(err, fs.ErrPermission) {
        fmt.Fprintln(os.Stderr, "无权读取输入文件:", path)
    } else {
        fmt.Fprintln(os.Stderr, "读取输入文件失败:", err)
    }
    return 4
}
```

三种情况的提示可以不同，但对 shell 而言，它们都表示“工具无法可靠取得本地输入”。尤其要区分：文件权限是内核对进程的访问许可；IM 会话授权则是消息内容或远端身份规则。前者失败时文件甚至不能读，属于 I/O；后者只有在成功读入并解析内容后才可能判断。

### 内容有效不等于文件可读

### 内容有效不等于文件可读

`check` 命令应先区分“能否取得字节”与“字节是否构成有效内容”。文件根本读不到时，尚无从判断 JSON、版本或消息标识，因此不能把它误报为内容错误。

| 失败情形 | 典型原因 | 分类 | 退出码 |
|---|---|---:|---:|
| 路径不存在 | 文件被删除、参数指向错误路径 | I/O 错误 | 4 |
| 无读取权限、目录不可遍历 | 内核拒绝打开文件 | I/O 错误 | 4 |
| 读取中断、设备故障 | `Read` 返回错误 | I/O 错误 | 4 |
| JSON 语法无效 | 字节存在但无法解析 | 本地内容错误 | 3 |
| 版本不支持 | 结构可解析但协议不兼容 | 本地内容错误 | 3 |
| 消息重复 | 内容合法但违反本地状态规则 | 本地内容错误 | 3 |

推荐顺序是：解析参数 → 打开并读取文件 → 解析 JSON → 校验版本与字段 → 检查重复消息。打开或读取阶段应使用 `os.IsNotExist(err)`、`errors.Is(err, fs.ErrPermission)` 等识别错误身份，而非匹配“没有那个文件”之类的文本；错误文本会随系统、语言和包装方式变化。

```go
data, err := os.ReadFile(path)
if err != nil {
    return 4
}
msg, err := parseJSON(data)
if err != nil {
    return 3
}
```

注意：操作系统允许读取，只表示内核权限通过，不代表当前 IM 会话已获授权；会话、令牌或业务身份校验仍属于后续内容/业务规则。若导出时 `Close` 失败，也不能报告成功：内层 `defer` 只在其所在函数返回时执行，应将关闭失败纳入最终结果。

### 关闭文件也是结果的一部分

### 关闭文件也是结果的一部分

`defer f.Close()` 很适合“打开后读取、解析后返回”的局部资源管理：`defer` 绑定的是**当前函数返回时**执行，而不是某个 `if`、`for` 或 `{}` 代码块结束时执行。因此，若在循环中反复打开文件却把 `defer Close` 写在外层函数，所有文件会一直占用到函数结束，可能耗尽文件描述符。

应把单次资源生命周期收进内层函数：

```go
for _, path := range paths {
    if err := func() error {
        f, err := os.Open(path)
        if err != nil { return err }
        defer f.Close()

        // 读取并校验 f
        return nil
    }(); err != nil {
        return err
    }
}
```

读取场景中，`Close` 通常只是释放资源；但导出、写回、生成附件等写入场景不同。缓冲区中的数据可能在 `Close` 时才真正刷新到内核或远端文件系统，因此“`Write` 返回成功”不等于“文件已成功完成”。磁盘空间不足、网络文件系统中断等错误，可能延迟到 `Close` 才出现。

因此写入函数不能无条件 `defer f.Close()` 后直接 `return nil`。应把关闭错误纳入最终结果；若写入、`Sync` 或关闭任一步失败，就返回 I/O 错误并使用退出码 `4`，不得向 shell 或脚本报告成功。资源释放是操作的一部分，而不是成功之后可忽略的清理细节。

### 让脚本可靠理解命令结果

### 让脚本可靠理解命令结果

虚构的 `im check --file message.json` 不应只“打印一句报错”，而应提供稳定的三部分合同：`stdout` 输出成功结果，`stderr` 输出诊断信息，退出码供 shell、CI 与上层脚本分支处理。

| 退出码 | 含义 | 示例 |
|---:|---|---|
| 0 | 成功、显示帮助 | 校验通过；`--help` |
| 2 | 参数错误 | 缺少 `--file`，未知参数 |
| 3 | 本地内容错误 | JSON 无效、版本不支持、消息重复 |
| 4 | I/O 错误 | 文件不存在、无读取权限、读取中断 |
| 5 | 未知或未分类错误 | 未预期的内部失败 |

成功时可向 `stdout` 输出机器可读结果，例如 `{"ok":true,"message_id":"m-42"}`；失败诊断写入 `stderr`，例如 `im check: 读取 message.json: 权限不足`。脚本不能只看文字，而应优先检查退出码：

`im check --file message.json >/tmp/result.json 2>/tmp/check.err`

随后依据 `$?` 判断是重试 I/O、修正参数，还是要求用户修复消息内容。`stdout`/`stderr` 的格式也应保持兼容，不能把调试日志混入成功 JSON。

识别文件不存在不能匹配“no such file”文本，应使用 `os.IsNotExist(err)` 或 `errors.Is(err, fs.ErrNotExist)`；权限、读取失败同理应按错误身份归类。文件打开后，`defer f.Close()` 只在当前函数返回时执行；导出或写入场景还必须检查 `Close` 错误，否则缓冲区落盘失败却错误报告成功。

最后，操作系统文件权限与 IM 会话授权是两层概念：前者决定进程能否读取本地 JSON，后者决定该消息是否允许发送到某个会话。前者失败通常退出 `4`，后者若属于消息语义或本地校验失败则归入 `3`；不要因为“文件可读”就假定“消息可发送”。

> **要点** — 以错误身份和稳定合同分类失败：退出码表达结果，标准输出与错误输出补充可读信息。

本节用本地 IM 的 check 命令拆解五个常见误解，建立进程、系统调用、地址、文件与退出状态之间的正确边界。

### 先拆开：程序、进程、线程与 goroutine

### 先拆开：程序、进程、线程与 goroutine

同一份 Go 可执行文件，例如 `im-check`，可以被连续启动两次：

`./im-check check alice`  
`./im-check check bob`

磁盘上仍只有一份程序文件；但操作系统会创建两个彼此独立的**进程**。每个进程都有自己的进程号、虚拟地址空间、打开文件表、环境变量和退出状态。一个进程崩溃或退出，通常不会直接清空另一个进程的内存。

层级可这样理解：

| 层级 | 是什么 | 本地 IM 中的例子 |
|---|---|---|
| 程序 | 静态的可执行文件或源代码构建产物 | 磁盘上的 `im-check` |
| 进程 | 一次运行中的程序实例 | 一次命令行启动产生的 PID |
| 操作系统线程 | 进程内部可被内核调度的执行单元 | Go 运行时使用的工作线程 |
| goroutine | Go 运行时管理的轻量并发任务 | 并发检查多个用户或消息 |

因此，`goroutine` 不等于进程。它通常没有独立 PID，也不拥有独立地址空间；多个 goroutine 共享所属进程的堆、全局变量和打开的文件描述符。Go 运行时会把大量 goroutine 调度到较少的操作系统线程上执行，关系不是“一条 goroutine 对应一条线程”，更不是“一条 goroutine 对应一个进程”。

例如 `check` 同时读取配置、校验 JSON、查询本地索引时，可以启动多个 goroutine；它们仍属于同一个 `im-check` 进程。若该进程退出，所有 goroutine 都会停止，其内存中的会话、缓存和待处理任务也随之消失。至于已写入文件的数据是否真正持久，则还要区分缓冲、内核页缓存与设备落盘，不能仅凭“进程退出”下结论。

### 一次函数调用不等于一次内核调用

### 一次函数调用不等于一次内核调用

以 `im check --config ./config.json` 为例，命令启动后并不会“每执行一个 Go 函数就进入一次内核”。

1. **启动与参数处理主要在用户态完成**  
   操作系统创建进程、装载可执行文件时会发生内核参与；但进入 Go 的 `main` 后，诸如解析 `os.Args`、匹配 `check` 子命令、拼接字符串、校验参数等，通常只是读取进程启动时已准备好的内存并执行普通指令。函数调用是栈帧、寄存器和跳转的变化，不等于系统调用。

2. **goroutine 不是进程，也不必一一对应内核线程**  
   `check` 可能启动 goroutine 做配置检查、日志收集或超时控制。goroutine 由 Go 运行时调度到少量操作系统线程上运行；一次 goroutine 切换常完全发生在用户态。只有运行时需要创建线程、等待内核对象、唤醒线程等，才可能请求内核。

3. **读取配置不等于只发生一次 `read`**  
   `os.Open` 可能触发打开文件的系统调用，返回文件描述符；随后 `json.Decoder` 的多次读取可能经由缓冲区完成。缓冲区已有数据时，`Decode` 可以不进入内核；反之，一次高层 `Read` 也可能因重试、分段读取或运行时调度对应多次底层操作。JSON 解析、字段校验则是纯用户态计算。

4. **退出路径也不是“函数返回一次，内核退出一次”**  
   `check` 返回错误、执行 `defer`、刷新用户态缓冲、打印诊断，都可能先在用户态进行；最终进程终止通常才由运行时发起退出系统调用。`Exit(0)` 仅表示本进程报告成功退出，不证明配置已持久落盘，更不证明未来网络网关或设备已收到消息。

因此，观察“函数调用次数”不能推导“系统调用次数”。同理，阻塞 I/O 常意味着线程在等待、CPU 占用可能很低；高 CPU 则可能来自 JSON 解析、循环重试或加密计算，即使几乎没有 I/O。后续分析文件持久性与网络 socket 时，也应分别追踪用户态逻辑、运行时调度和内核资源状态。

### 地址、偏移与文件描述符各管什么

### 地址、偏移与文件描述符各管什么

本地 IM 的 `check` 命令读取 `config.json` 时，常会同时出现“地址”“偏移”“描述符”三个词；它们都像数字，但描述的对象完全不同，不能互换。

| 概念 | 它回答的问题 | 所属空间 | 典型含义 |
|---|---|---|---|
| 虚拟内存地址 | 数据当前放在进程内存的哪里？ | 当前进程的虚拟地址空间 | `0x...`、指针、切片底层数组位置 |
| 文件偏移 | 下一次从文件的哪个字节开始读或写？ | 内核维护的打开文件状态 | 第 `0`、`128`、`4096` 字节 |
| 文件描述符 | 要操作的是哪一个已打开的内核资源？ | 进程的描述符表 | `3`、`4`，可能指向文件、管道或 socket |

例如：

`os.Open("config.json")` 返回的文件对象底层持有一个文件描述符。`Read` 系统调用把“描述符指向文件、从当前偏移读取若干字节”这一请求交给内核；内核再把读到的数据复制到 Go 提供的内存缓冲区地址。于是：

- 缓冲区地址改变，不代表文件读取位置改变；
- 调用 `Seek(0, 0)` 改变的是文件偏移，不会把内存指针移回起点；
- 两个不同描述符即使打开同一文件，也通常各有独立的打开状态与偏移；
- 同一描述符被复制或继承时，相关操作可能共享底层打开文件状态，读写会相互影响。

因此，“内存地址就是文件偏移”是错误的：前者是进程访问 RAM 的坐标，后者是文件内容的逻辑字节位置；一个往往是十六进制指针，一个通常是从文件开头计数的整数。文件描述符则更像进入内核资源的门牌号，本身既不是数据地址，也不是文件位置。

`Open` 成功只说明路径解析、权限检查和打开资源等步骤成功；它不保证随后读出的字节一定是有效 JSON。`Read` 得到的内容仍须由 `json.Unmarshal` 验证，空文件、截断文件和格式错误文件都可能“打开成功、解析失败”。

### 从 Open 到 Close：成功打开不代表内容可用

### 从 Open 到 Close：成功打开不代表内容可用

本地 IM 的 `check` 命令若要读取配置或消息索引，常见路径是：

`os.Open(path)` → `Read` → JSON 解析 → `Close`

这里每一步成功的含义都不同。`os.Open` 成功，只说明操作系统已为当前进程建立一个可读文件描述符；它不保证文件非空、不保证内容是 JSON，更不保证读取过程不会在随后失败。

```go
f, err := os.Open(path)
if err != nil { /* 打开失败 */ }
defer f.Close()

data, err := io.ReadAll(f)
if err != nil { /* 读取失败 */ }

var cfg Config
if err := json.Unmarshal(data, &cfg); err != nil { /* 内容无效 */ }
```

`f` 不是文件内容本身，而是进程持有的一个操作系统资源句柄。`Read` 才会把文件当前内容复制到用户态缓冲区；JSON 解析则只检查这段字节是否符合预期结构。即使 `Open` 和 `Read` 都成功，`json.Unmarshal` 仍可能因截断、手工编辑、字段类型错误或旧版本格式而失败。

| 故障类别 | 常见表现 | `check` 的处理重点 |
|---|---|---|
| 文件不存在 | `os.IsNotExist(err)` 为真 | 提示尚未初始化或路径错误 |
| 无权限 | `os.IsPermission(err)` 为真 | 提示检查权限、属主或运行账户 |
| 内容无效 | JSON 解析失败 | 报告配置损坏或格式不兼容，不应伪装成“不存在” |
| 其他 I/O 失败 | 设备错误、目录被当作文件、读取中断等 | 保留原始错误并标明读文件失败 |

`Close` 表示释放该文件描述符；应尽快执行，通常用 `defer f.Close()` 保证异常路径也会释放。关闭成功不等于此前读到的数据“正确”，打开成功也不等于业务状态“可用”。进程退出时，操作系统通常会回收尚未关闭的描述符和进程内存；但文件写入是否已经可靠持久化是另一层问题，不能仅由 `Close` 或 `Exit(0)` 推断。

### 退出、阻塞与持久性不能望文生义

### 退出、阻塞与持久性不能望文生义

`Exit(0)` 只表示：该进程主动以状态码 `0` 结束，操作系统认为它“正常退出”。它**不**自动证明：

- 服务端已经收到并处理了消息；
- JSON 内容符合业务约束；
- 文件数据已经真正落到物理介质；
- 其他 goroutine 都完成了清理工作。

进程退出时，操作系统会回收其虚拟内存、关闭仍打开的文件描述符，并撤销大部分进程级资源；因此内存中的联系人列表、未发送消息队列、缓存对象都会消失。若要跨重启保留，必须显式写入文件、数据库或远端服务。至于“写入”后数据何时真正持久化，仍要区分用户缓冲、内核页缓存、`fsync` 与设备落盘，后续在 03.08 深入讨论。

阻塞 I/O 也不能直接等同于“CPU 很忙”。例如：

```text
读取本地文件 / 等待终端输入 / 等待 socket 数据
```

goroutine 发起 I/O 后，若数据尚未就绪，运行时或内核可使其等待；此时它通常不持续消耗 CPU。反过来，CPU 占用高也未必在做 I/O：死循环、频繁 JSON 编解码、排序或忙等都会消耗 CPU，却可能没有任何系统调用。

| 现象 | 常见误判 | 更合理的排查方向 |
|---|---|---|
| `Exit(0)` | 消息已送达且已保存 | 看返回值、服务端确认、持久化策略 |
| 命令卡住 | CPU 一定满载 | 看是否在等待输入、文件或网络 I/O |
| CPU 很高 | 磁盘或网络阻塞 | 查循环、计算热点、锁竞争 |
| 重启后数据丢失 | 退出时内存会保留 | 检查写文件与同步语义 |
| 文件打开成功 | 内容必然是有效 JSON | 单独读取、解析并校验字段 |

未来网关连接使用的网络 socket 同样是操作系统资源；先掌握文件描述符、阻塞与资源回收，再在 03.03、03.04 及网络章节中分析其生命周期。

> **要点** — 进程、内核资源、内存地址、文件内容与退出状态属于不同层次，不能依据单一成功信号互相推断。

以本地 IM 的 check 命令为线索，沿着 shell 输入、进程启动、文件读取、结果输出到退出的路径，建立用户态、内核态与错误边界的整体图景。

### 从命令行到进程：12步主路径总览

### 从命令行到进程：12步主路径总览

设在隔离环境输入本地检查命令：`im check c-a/u-a/m-a`。其中三段标识分别定位配置、用户与消息相关的本地数据；它们只是参数，尚未被内核解释。

1. **用户态：Shell 读取输入**，按空白分词，识别命令名与三个参数。  
2. **用户态：Shell 查找命令**，依照 `PATH` 或显式路径定位可执行文件。  
3. **内核态：创建子进程**，Shell 请求派生执行上下文；可观察到新的进程标识。  
4. **内核态：装载程序**，内核读取可执行文件、建立地址空间并转入入口点。  
5. **用户态：Go 运行时启动**，初始化栈、调度器、垃圾回收等运行环境。  
6. **用户态：参数解析**，程序确认子命令为 `check`，收集 `c-a/u-a/m-a`。  
7. **用户态：业务层组织检查计划**，确定需要读取的本地配置、账户和消息描述。  
8. **内核态：打开文件**，程序经系统调用请求文件；内核执行路径解析与权限检查。  
9. **内核态：读取字节**，内核将文件内容复制给进程；用户态获得字节流。  
10. **用户态：解析 JSON**，数据层将字节解码为结构；语义层检查字段关系。  
11. **用户态：输出结果**，正常时写入标准输出，例如“检查通过”；诊断信息通常写入标准错误。  
12. **内核态→用户态：退出**，程序返回退出状态；Shell 记录并可通过 `$?` 观察。  

这条路径的关键边界是：Shell、Go 运行时、JSON 解析和业务校验主要在用户态；进程创建、程序装载、文件访问、权限判定与字节读取由内核参与。实际观察到的进程号、输出和退出状态应记录为“真实记录”，不要与本节的静态预期混写。

### 每一步在哪运行：用户态、内核态与资源角色

### 每一步在哪运行：用户态、内核态与资源角色

把 `im check <文件>` 想成一条跨越边界的链路：命令逻辑主要在**用户态**执行；创建进程、打开文件、读取字节、写终端等受保护操作由**内核态**服务完成。一次系统调用不是“程序搬到内核中运行”，而是当前线程短暂切换到内核执行受控入口，完成后返回原用户态指令。

1. **Shell 接收输入**：Shell 进程的用户态线程解析 `check`、参数和重定向符号。  
2. **解析命令**：Shell 在自己的虚拟地址空间中查找命令路径、准备参数与环境变量。  
3. **请求创建程序**：Shell 的用户态代码发起创建/执行相关系统调用；内核检查权限并建立新进程。  
4. **装载映像**：内核为新程序建立或替换虚拟地址空间，映射代码、数据、栈及动态库页面。  
5. **开始执行 `check`**：新进程回到用户态，从程序入口开始；初始通常只有一个主线程。  
6. **解析参数**：`check` 在用户态读取参数，决定待检查的配置文件路径。  
7. **打开文件**：用户态库调用 `open`；内核检查路径、目录可搜索性和读取权限，成功后返回文件描述符，如 `3`。  
8. **读取内容**：程序以文件描述符请求 `read`；内核从页缓存或文件系统取得字节，再复制或映射给用户态缓冲区。  
9. **解析 JSON**：JSON 解码完全属于用户态计算；它操作本进程内存，不必进入内核。  
10. **形成检查结果**：业务规则在用户态判断字段、账号或会话状态，构造成功或失败消息。  
11. **输出结果**：程序对标准输出或标准错误调用 `write`；内核依据描述符指向终端、管道或文件交付数据。  
12. **退出并回收**：程序调用退出接口；内核记录退出状态、关闭描述符、释放资源，Shell 随后观察并报告退出码。

文件描述符是用户态整数与内核对象之间的“句柄”：`0/1/2` 常对应标准输入、标准输出、标准错误。虚拟地址空间隔离不同进程；线程是实际执行系统调用和用户代码的主体。可静态预期“坏 JSON”发生在第 9 步，而“不存在文件”或“无权限”通常在第 7 步由内核拒绝；在隔离环境中只读观察时，应把真实进程状态与这张概念路径分开记录。

### 读取配置的概念链：Open、Read、Close并非一一对应

### 读取配置的概念链：`Open`、`Read`、`Close`并非一一对应

本地 IM 的 `check` 命令读取配置时，源码可能只呈现为：

`os.Open(path)` → 读取内容 → `Close()`

但这不是“三次函数调用恰好对应三次系统调用”。应把它理解为跨层协作链，而非逐行直通内核的映射。

- **用户态：应用与标准库。** `os.Open` 接收路径，返回一个 `*os.File`；读取方法可能是 `File.Read`，也可能经由缓冲读取器、JSON 解码器间接触发；`Close` 表示应用不再需要该文件对象。
- **用户态：Go 运行时。** 运行时负责调度、阻塞处理及文件描述符相关协作。一次高层读取可能被拆成多次底层读取；反之，预读缓冲可能让后续“读取”完全不进入内核。
- **内核态：文件服务。** 内核解析路径、检查权限、定位文件，并维护打开文件状态。成功打开后，进程获得文件描述符；读取从该描述符当前偏移处取字节；关闭则释放该进程持有的描述符引用。

因此，“配置读取成功”至少包含三个不同事实：

1. 路径可被打开；
2. 文件字节可被读到；
3. 字节能被解析为合法配置。

它们不能互相替代。文件存在但无读权限时，失败通常发生在打开阶段；文件可读但内容是坏 JSON 时，打开和读取已成功，失败属于用户态解析层；`Close` 失败也不必然否定此前已读到的数据，但工程上仍应记录或处理其错误。

在隔离环境中只读观察进程时，应将“静态预期”与“真实记录”分开：静态上可预期出现打开、读取、关闭等内核交互；真实进程中，缓冲、缓存、运行时实现和具体代码路径都可能改变次数与顺序。观察到的系统调用轨迹是某次执行的证据，不是标准库接口的一对一说明书。

### 三类失败变式：找不到、无权限与坏JSON

### 三类失败变式：找不到、无权限与坏JSON

设想 `im check --config ./account.json`：三种失败都可能让命令以非零状态退出，但失败位置、责任层与可观察证据不同。不要只看“失败了”，而要问：**哪个阶段首次无法继续？**

| 变式 | 首次失败动作 | 主要责任层 | 常见可观察结果 |
|---|---|---|---|
| 文件不存在 | `open` 查找路径失败 | 内核返回错误；用户态呈现 | “没有那个文件或目录”、非零退出 |
| 权限不足 | `open` 进行访问检查失败 | 内核依据权限/凭据拒绝；用户态呈现 | “权限不够”、非零退出 |
| 坏 JSON | 已成功读取字节，解析失败 | 用户态程序/JSON 解析器 | “JSON 格式无效”、非零退出 |

**找不到**时，shell 已经成功启动了 `im` 进程；程序在用户态请求打开文件，内核遍历路径并发现目标不存在，向程序报告 `ENOENT`。因此，“命令不存在”和“配置文件不存在”不可混为一谈：前者通常发生在 shell 查找可执行文件时，后者发生在 `im` 已运行之后。

**无权限**时，路径可能完全存在。内核检查进程的有效用户、组身份及文件/目录权限；即使文件本身可读，父目录不可搜索也可能导致访问失败。程序得到如 `EACCES` 的失败结果，通常尚未读取任何配置内容。

**坏 JSON**则相反：打开与读取均已成功，内核的文件访问职责已经完成；程序在用户态把字节解释为 JSON 时发现缺逗号、引号未闭合或字段类型不符。此时错误信息往往可附带行列位置，例如“第 4 行附近语法错误”。

退出状态是 shell 可观察的总结信号：`0` 通常表示检查通过，非零表示失败；具体数值由程序约定，不能仅凭数值推断一定是哪类错误。

<details>
<summary>练习：基础（1—6）</summary>

1. “配置文件不存在”时，`im` 进程是否一定已启动？  
   **反馈：**若错误来自程序打开配置文件，则已启动；若是 shell 找不到 `im`，则未启动。

2. 三类错误中，哪类最可能来自 JSON 解析器？  
   **反馈：**坏 JSON。

3. 权限不足是否说明文件一定不存在？  
   **反馈：**不说明；它通常说明对象存在但访问被拒绝。

4. 非零退出状态是否自动说明内核崩溃？  
   **反馈：**不是；这是普通程序失败的常规表达。

5. 坏 JSON 前，文件读取是否可能已经成功？  
   **反馈：**是，解析需要先获得内容。

6. `ENOENT` 更接近哪一类？  
   **反馈：**找不到文件或路径组成部分。  
</details>

<details>
<summary>练习：机制（7—12）</summary>

7. `open` 的成功返回主要说明什么？  
   **反馈：**内核允许打开该对象；不保证 JSON 内容有效。

8. 哪类失败最直接涉及内核的访问控制检查？  
   **反馈：**无权限。

9. 父目录缺少搜索权限，可能表现为何种结果？  
   **反馈：**访问路径失败，常呈现权限相关错误。

10. 解析器报告“第 8 行第 3 列”说明什么？  
   **反馈：**程序已拿到文本，并在用户态定位语法问题。

11. shell 与 `im` 分别可能报告什么错误？  
   **反馈：**shell 可报告命令找不到；`im` 可报告配置打开或解析失败。

12. 为什么不能只依据终端的一句错误文本判断底层原因？  
   **反馈：**文本是用户态包装；应结合发生阶段、路径和退出状态。  
</details>

<details>
<summary>练习：工程（13—17）</summary>

13. 错误信息应包含配置路径吗？  
   **反馈：**应包含，便于定位；但避免泄露敏感内容。

14. 程序应把原始系统错误完全吞掉吗？  
   **反馈：**不应；应保留可诊断原因并给出上下文。

15. 对坏 JSON，除了“格式错误”还应报告什么？  
   **反馈：**可报告位置或字段上下文，但不要回显秘密字段。

16. 三种错误是否应共享同一个模糊提示？  
   **反馈：**不宜；分类清晰能减少误修复。

17. 在隔离环境中只读观察时，应记录哪些事实？  
   **反馈：**命令文本、终端输出、退出状态、是否出现目标进程；与静态预期分栏记录。  
</details>

<summary>练习：业务（18—20）</summary>

18. 用户说“登录检查失败”，客服首先应区分什么？  
   **反馈：**配置是否找不到、不可读，还是内容不合法。

19. 为什么权限错误可能影响团队部署？  
   **反馈：**不同账户、挂载方式或目录权限会使同一配置在不同机器上表现不同。

20. 为什么坏 JSON 不应被误报为“账号失效”？

### 静态追踪与分层练习：把预期和观察分开

### 静态追踪与分层练习：把预期和观察分开

先在纸面完成“静态预期”，再在**隔离环境**中进行只读观察；两者必须分栏记录，不能让观察结果倒推修改原先判断。

| 项目 | 静态预期 | 真实记录 |
|---|---|---|
| `check` 的执行者 | shell 创建的子进程 | 进程名、父进程、退出状态 |
| 配置文件读取 | 用户态请求，内核完成打开与读取 | 是否出现目标文件、权限与错误文本 |
| 成功输出 | 标准输出输出检查结果 | 实际输出位置与内容 |
| 失败输出 | 标准错误输出诊断 | 错误类型、退出码、是否含路径 |

折叠练习可按四层完成；每题先写预期，再补观察与反馈。

<details><summary>基础练习（1—6）</summary>

1. `check` 由谁解析输入？**反馈：**shell。  
2. 谁创建新进程？**反馈：**shell 发起请求，内核创建。  
3. 程序代码主要运行在哪里？**反馈：**用户态。  
4. 打开文件的最终裁决者是谁？**反馈：**内核。  
5. 正常结果通常写向哪里？**反馈：**标准输出。  
6. 错误诊断通常写向哪里？**反馈：**标准错误。  

</details>

<details><summary>机制练习（7—12）</summary>

7. 文件不存在时，失败发生在 JSON 解析前还是后？**反馈：**打开阶段，解析前。  
8. 无权限是应用自行决定的吗？**反馈：**通常由内核权限检查拒绝。  
9. 坏 JSON 能否说明文件已成功读取？**反馈：**通常能，至少已得到待解析内容。  
10. 系统调用失败后，应用层还应做什么？**反馈：**翻译错误、输出诊断并退出。  
11. 退出码属于内核态还是用户态协议？**反馈：**程序设定，shell 读取其状态。  
12. 父进程为何能得知子进程结束？**反馈：**内核保存终止状态供父进程获取。  

</details>

<details><summary>工程练习（13—17）</summary>

13. 为三种失败分别写出最早责任层。**反馈：**不存在/无权限：文件访问链路；坏 JSON：应用解析层。  
14. 错误信息应包含什么？**反馈：**操作、目标路径或逻辑资源、原因。  
15. 是否应把解析错误伪装成“文件不存在”？**反馈：**不应，错误语义会误导排障。  
16. 观察进程时可记录哪些只读信息？**反馈：**进程标识、父子关系、状态、打开资源的可见线索。  
17. 为什么不以单次观察证明全部实现细节？**反馈：**调度、缓存、实现版本均会改变表象。  

</details>

<details><summary>业务折叠练习（18—22）</summary>

18. 正常 `check` 对用户承诺什么？**反馈：**给出可理解的检查结论。  
19. 配置缺失应如何引导用户？**反馈：**说明缺少何物及下一步，而非只报告底层编号。  
20. 无权限与不存在为何必须区分？**反馈：**前者可能是授权或部署问题，后者是资源定位问题。  
21. 坏 JSON 的业务风险是什么？**反馈：**配置语义不可信，不能继续按默认成功处理。  
22. 哪些记录可进入故障单？**反馈：**命令意图、预期、可见输出、退出状态、环境边界；避免记录敏感内容。  

</details>

最终检查：每条真实记录都标注“观察到”而非“必然如此”；每条静态结论都标注其依据层次：shell、应用、内核或业务约定。

> **要点** — check 命令是用户态进程借系统调用使用内核资源的生命周期；失败位置决定错误信息与退出状态。
