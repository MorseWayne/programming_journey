### 先把三种“成功”拆开

### 先把三种“成功”拆开

面对“网关有 3 个副本”，先不要立刻得出“用户能用、消息可靠”的结论。至少要分开看三件事：

1. **副本数达标**：控制器观察到期望副本数为 3，并创建、替换 Pod；调度成功后，可能有 3 个进程正在运行。它回答的是：**是否有足够多的工作负载实例？**

2. **用户请求可用**：用户经由 Service、Ingress 或负载均衡访问时，流量必须实际落到健康且已就绪的副本。若某 Pod 虽在运行但未通过就绪探针，或路由、端口、依赖服务异常，用户仍可能无法请求。它回答的是：**请求现在能否被正确处理？**

3. **消息可靠送达**：即使请求返回 `200`，在本例中也只表示该网关进程已在**内存中受理**消息；不表示消息已持久化、不表示 S3 提议已从 6B 变更，也不表示 R9 审核完成，更不表示目标设备已经收到。

因此，不能作如下推导：

- `3 个运行副本` $\Rightarrow$ `3 个用户可用入口`；
- `HTTP 200` $\Rightarrow$ `消息已持久化`；
- `消息已持久化` $\Rightarrow$ `设备已收到`。

静态合同仍要逐项执行：正文超过 `4096B` 拒绝，重复请求返回 `409`，非成员返回 `404`，有效 UTF-8 的 `6B` 正文才可能获得 `200`。Kubernetes 维持的是副本趋近目标；业务协议、存储确认、重试与设备回执，仍由网关系统自行保证。

### 期望状态与观测状态

### 期望状态与观测状态

在 Deployment 中写下 `replicas: 3`，表达的是**期望状态**：集群希望持续拥有 3 个满足条件的网关 Pod。它不是“立刻启动 3 个进程”，更不是“已有 3 个用户可用的 IM 网关”。

```yaml
spec:
  replicas: 3
```

对应地，API 返回的 `status` 是控制面目前观察到的**观测状态**，例如：

- `status.replicas`：已被控制器统计到的 Pod 数；
- `status.readyReplicas`：通过就绪检查、可进入 Service 后端的 Pod 数；
- `status.availableReplicas`：持续就绪达到要求的 Pod 数；
- `status.updatedReplicas`：使用当前模板版本创建的 Pod 数。

控制器不断执行近似的比较：

$$\text{差距}=\text{spec.replicas}-\text{status.availableReplicas}$$

若期望为 3、当前可用为 2，Deployment 控制器会创建或推动一个新的 ReplicaSet Pod；若有 4 个，则会缩容。调度器再为新 Pod 选择节点，kubelet 拉取镜像并启动容器。Pod 崩溃、节点失联或被删除后，这条控制回路仍会继续尝试补足副本。

但 `readyReplicas: 3` 只说明三个网关实例通过了你的就绪判定。例如 `/readyz` 返回成功，最多表示它们可接收 HTTP 请求。它不自动证明：S2 的 6 UTF-8 字节合同已被持久化、重复请求一定返回 `409`、非成员一定返回 `404`，也不证明 S3 的 6 字节提议已提交，或 R9 已完成审核。

因此应区分三层事实：`spec=3` 是声明，`status` 是 Kubernetes 的观察，业务可用性则仍要由应用的存储、幂等、成员校验、消息投递与审核状态共同定义。

### 从 Deployment 到运行中的 Pod

### 从 Deployment 到运行中的 Pod

先把 `Deployment` 看成“声明期望”：教学 IM 网关要求维持 `replicas: 3`，并使用当前 S2/v1 静态合同。它不直接启动进程，而是创建或管理一个 `ReplicaSet`；ReplicaSet 再不断比较“期望 3 个”与“当前可计数的 Pod”，缺少就创建 Pod 对象，多了就删除。

新 Pod 起初通常是 `Pending`：这只说明它已被 API 服务器记录，却尚未完成可运行条件。调度器负责从候选节点中挑选一个合适节点，考虑资源请求、污点容忍、亲和性等；如果没有节点满足条件，Pod 会持续 Pending，即使 Deployment 仍显示期望副本数为 3。

Pod 被绑定节点后，责任交给该节点的 `kubelet`：拉取镜像、创建容器、挂载卷、启动网关进程，并持续上报状态。进程启动不等于可接流量。只有就绪探针成功，Pod 才进入 `Ready=True`，对应的 Service 才通常把它加入后端端点。

因此应分别读三个数字：

- `replicas=3`：声明想要三个副本；
- `Running=3`：三个容器进程正在运行；
- `Ready=3`：三个副本通过就绪检查，可被 Service 选中。

即便 `Ready=3`，也只能说明三个进程当前可受理 HTTP 请求。某次 `200` 若仅表示消息进入进程内存，S3 的提议仍只有 6B、R9 仍待审，那么它既不代表消息已持久化，也不代表目标设备已收到。反过来，重复请求返回 `409`、非成员返回 `404`，属于网关合同与业务判定，不能由 Deployment 副本数替代。

### 一副本故障后的替换账本

### 一副本故障后的替换账本

设教学 IM 网关原本有 `gw-a`、`gw-b`、`gw-c` 三个运行中的 Pod。某时 `gw-b` 所在节点故障，或其进程退出。应把恢复过程记成一笔“替换账”，而不是理解为原 Pod 被修好：

| 时刻 | 集群控制面观察到的事实 | 业务可据此断言的事实 |
|---|---|---|
| 故障前 | 期望副本数为 3，三个 Pod 曾处于运行状态 | 不代表三位用户都能连接，也不代表消息已落盘或送达设备 |
| `gw-b` 失联 | 旧 Pod 不再可用，端点可能被移除 | 该 Pod 的进程内存、长连接、未发送响应都会丢失 |
| 控制器补位 | 创建一个新的 Pod 对象 | 新对象具有新的 `UID`；它不是旧 `gw-b` 的“续命” |
| 新 Pod 就绪 | 调度完成、容器启动，并通过就绪检查后加入流量入口 | 至多说明它可以开始接收请求；不说明恢复了旧会话或旧内存 |
| 稳态恢复 | 可运行副本重新达到 3 | 仅表示副本数量回到目标值 |

例如，旧 `gw-b` 已对某请求返回 `200`，但该 `200` 的含义仅是“本进程内存受理”。随后 `gw-b` 故障，该内存记录消失；新 Pod 即使副本数恢复为 3，也不能证明该消息已持久化、已复制，或客户端设备已收到。

当前静态合同中的“正文为 6 个 UTF-8 字节”“原始 HTTP 请求正文最多 4096 字节”“重复请求返回 `409`”“非成员返回 `404`”仍是接口规则，但若重复判定状态只在旧进程内存中，替换后新 Pod 未必认识旧请求。`S3` 的提议仍只是 6 字节，`R9` 仍待审；Pod 重建不会自动推进提议，也不会自动完成审核。

因此，Kubernetes 负责朝“3 个运行副本”收敛；业务若要跨替换仍能判重、保留会话、持久消息并确认送达，必须把这些状态放到 Pod 生命周期之外。

### v1 合同与 S3 承诺边界

### v1 合同与 S3 承诺边界

S2 的 `v1` 静态合同先规定“网关此刻接受什么”，而不是“消息最终到达哪里”。纸上三副本网关中，每个 Pod 都执行同一规则：

- 原始 HTTP 请求正文最多 `4096B`；超限应拒绝，不能因副本数量变成更大的可发送消息。
- 业务消息文本按 UTF-8 编码后最多 `6B`。例如 `abc` 是 `3B`，`你好` 通常是 `6B`；超过限制返回 `409`。
- 目标用户不属于当前教学成员集合时返回 `404`；这表示“资源或成员不存在”，不是“暂时没有可用副本”。
- 返回 `200` 只表示**当前处理该请求的进程**已在内存中受理。它不等于写入数据库、不等于复制到另外两个副本，也不等于设备已经显示消息。

因此，Deployment 维持“期望 3 个运行副本”时，控制器可能创建、重建或替换 Pod；但每个 Pod 的内存彼此独立。请求落到 A 后，即使 A 返回 `200`，A 随后崩溃，消息仍可能消失；B、C 运行正常也不会自动知道这条消息。

S3 的“提议仍为 6B”只说明下一版候选合同没有放宽消息长度，尚未构成已发布、已部署或已兼容的承诺。R9 仍待审，意味着其涉及的路由、重试、存储或回执语义不能假定已生效。

要把“受理”升级为“可靠发送”，还需显式建立持久化写入、跨副本一致性或队列投递、失败重试，以及设备确认回执。集群副本数解决的是进程存活与替换，不自动提供消息持久化和端到端送达。

> **要点** — Kubernetes 维持的是期望副本与运行条件，不自动证明请求持久化、消息送达或设备确认。

以三副本 IM 网关为纸上集群，先读懂对象声明与实际回报，再理解控制器为何持续把 Ready 数量拉回 3。

### 对象三层：身份、期望与观测

### 对象三层：身份、期望与观测

Kubernetes 中看到的 Deployment、Pod、Service 都是 **API 对象**。阅读对象时，先不要把它当成“立即执行的一条命令”，而应分成三层：

- `metadata`：对象是谁、在哪里、如何被唯一识别。
- `spec`：用户声明希望它最终变成什么样。
- `status`：集群控制器和节点当前观察到什么。

以 IM 网关的 Deployment 为例：

```yaml
metadata:
  name: im-gateway
  namespace: production
spec:
  replicas: 3
status:
  readyReplicas: 2
```

`metadata.name` 是对象在其命名空间中的名字；`metadata.namespace` 划定对象所属的逻辑隔离范围。不同 namespace 可以都有名为 `im-gateway` 的 Deployment。`metadata.uid` 则是 API 服务器分配的全局唯一身份：即使旧对象删除后又创建了同名对象，两者的 UID 也不同。

`spec.replicas: 3` 表示期望：该 Deployment 应维持 3 个可用副本。它不是“现在立刻启动 3 个 Pod”的同步命令，而是一条持续有效的目标状态声明。

`status.readyReplicas: 2` 表示观测：此刻只有 2 个副本通过了就绪条件。控制器会持续比较期望值 $3$ 与观测值 $2$，发现差距后创建、替换或等待 Pod，直到 Ready 数量逼近 3。若某个已就绪 Pod 随后故障，观测值又降为 2，控制循环仍会再次尝试恢复。

因此，`spec` 回答“想要什么”，`status` 回答“目前看到了什么”，两者不一致正是控制器需要工作的信号。读取真实对象及其更新需要访问 Kubernetes API；本课程中的纸上集群仅用于推演，不会创建实际集群。

### 三副本网关的期望状态

### 三副本网关的期望状态

设想要运行一个 IM 网关，目标不是“现在启动三个进程”，而是声明：**任何时刻都应有 3 个满足模板要求的网关副本可用**。这份声明首先写入 Deployment：

`spec.replicas: 3`

Deployment 的 `spec` 描述较高层的期望：副本数、Pod 模板、镜像、端口、环境变量，以及更新策略等。它并不亲自创建每个 Pod，而是将“应运行 3 个符合该模板的副本”这一目标向下落实。

Deployment 通常管理一个 ReplicaSet。ReplicaSet 的期望更直接：维护指定数量、带有特定标签的 Pod。例如它的 `spec.replicas` 同样为 3，并通过选择器确认哪些 Pod 属于自己。若当前只找到 2 个匹配 Pod，它就会请求创建第 3 个；若意外存在 4 个，则会减少一个。

每个 Pod 也有自己的 `spec`：应使用哪些容器、容器应运行什么镜像、挂载什么卷、采用何种网络与资源配置。Pod 不是“3 个副本”这一数量目标的主要持有者；它保存的是**单个副本应长成什么样**。

因此，这条期望链可写为：

`Deployment：网关整体应有 3 副本`  
$\rightarrow$ `ReplicaSet：应维持 3 个匹配 Pod`  
$\rightarrow$ `Pod：每个副本应按模板运行容器`

这里的 `3` 是存储在 API 对象中的持续目标，不是一条执行一次就结束的命令。后续即使某个 Pod 消失，ReplicaSet 仍会根据其 `spec.replicas=3` 发现数量不足，并继续尝试补齐。

### 纸上推演：Ready 从 3 降到 2

### 纸上推演：Ready 从 3 降到 2

设 `Deployment` 声明：

`metadata.name: im-gateway`，`metadata.namespace: prod`，`spec.replicas: 3`。

它的身份不仅是名字：API 还会为对象分配不可复用的 `UID`。名字便于人和程序查询，`UID` 用于区分“同名但已重建”的对象；`namespace` 则把 `prod` 中的网关与其他环境隔离开。

初始时，Deployment 的期望是 3，而状态回报可概念化为：

- `spec.replicas = 3`：希望有 3 个副本；
- `status.readyReplicas = 3`：当前有 3 个通过就绪检查；
- 3 个 Pod 分布在若干节点上，均能接收流量。

现在其中一个 Pod 所在节点异常，或容器崩溃且无法恢复。该 Pod 不再 Ready，于是观测状态变为：

`status.readyReplicas: 3 → 2`

这不是 Deployment “执行了一条重启命令”，而是控制循环重新比较期望与观测：

$$\text{期望副本}=3,\quad \text{已就绪副本}=2,\quad \text{差额}=1$$

接力过程可纸上推演为：

1. Deployment 控制器发现副本数不足，调整其 ReplicaSet，使其创建一个替代 Pod。
2. 新 Pod 刚出现时通常处于 `Pending`，尚未绑定节点，也不能算 Ready。
3. 调度器根据资源请求、节点可用容量、亲和性或污点等条件，为该 Pod 选择合适节点。
4. 目标节点上的 kubelet 看到已分配给自己的 Pod，拉取镜像、创建容器、挂载网络与存储。
5. 容器启动后，通过存活与就绪检查；只有就绪检查成功，Pod 才计入 `readyReplicas`。
6. 状态最终回到 `status.readyReplicas = 3`，控制器不再需要补充副本。

整个过程中，控制器、调度器和 kubelet 都通过 API 读取对象并更新状态。这里的“创建”“调度”“启动”是纸上模型；课程静态环境不会真的创建集群或运行 Pod。

### Pending 不等于 Ready

### Pending 不等于 Ready

对 IM 网关而言，“有 3 个 Pod”不等于“有 3 个可接收用户消息的网关”。应至少区分两个层次：

- **已创建/期望副本数**：Deployment 的 `spec.replicas: 3` 表示控制器希望最终维持 3 个副本。
- **可用副本数**：只有 Pod 完成启动，并通过就绪检查（readiness probe）后，才会被视为 `Ready`，通常才会加入 Service 的流量端点。

Pod 处于 `Pending` 时，说明对象已经存在，但尚未真正具备服务能力。常见原因包括：

- 调度器还未为它找到合适节点；
- 节点 CPU、内存、端口或其他资源不足；
- 镜像仍在拉取，或容器启动条件尚未满足；
- 存储卷、网络等依赖尚未就绪。

即使 Pod 已从 `Pending` 进入 `Running`，也仍可能不是 `Ready`。例如网关进程已启动，但尚未连上配置中心、数据库连接未建立，或健康检查接口尚未返回成功。此时把流量导入该 Pod，用户请求仍可能失败。

可以把状态写成：

\[
\text{创建} \rightarrow \text{Pending} \rightarrow \text{Running} \rightarrow \text{Ready}
\]

这不是所有 Pod 都严格经历的唯一状态图，但它强调了关键事实：`Ready` 是“可承接流量”的判断，不是“对象已存在”的同义词。

纸面观察中，若 Deployment 期望为 3，而 Ready 数先为 3、后降为 2，控制器看到的是“实际可用能力偏离期望”。它会持续尝试让系统回到 3 个 Ready 副本；但新建出的 Pod 可能暂时仍是 `Pending`，因此“副本数达到 3”与“可用副本恢复到 3”可以在时间上分离。

### 替换而非复活：UID、内存与连接边界

### 替换而非复活：UID、内存与连接边界

设 IM 网关的 `Deployment.spec.replicas=3`。某个 Pod 故障后，控制器发现可用副本少于目标，通常会删除失效 Pod，并创建一个新 Pod 补足数量；这叫**替换**，不是把原进程“复活”。

- `metadata.name` 是对象名称，可能仍遵循相似规则，如 `im-gateway-7c8d9-xxxxx`；名称可帮助人识别，但不是身份的永久凭据。
- `metadata.uid` 才是该对象在 API 中的唯一身份。旧 Pod 被删除后，即使后来出现同名对象，新对象也有新的 UID，应视为不同实例。
- `metadata.namespace` 划定对象所属的逻辑边界；同名 Pod 位于不同命名空间仍是不同对象。

旧 Pod 的进程退出，其内存中的会话表、缓存、未落盘消息、临时计数器都会消失。新 Pod 从镜像和配置重新启动，除非应用主动从数据库、消息系统或共享存储恢复状态，否则它不继承旧 Pod 的内存。

客户端连接也跨不过替换边界：旧 TCP/WebSocket 连接会断开，客户端需要重连、重新鉴权，并可能补拉遗漏消息。`Ready` 只表示 Kubernetes 认为该 Pod 当前可以接收流量，不表示所有客户端已经连回，也不表示业务状态已完全恢复。

因此，控制器保证的是某个时刻尽力逼近“有 3 个符合条件的副本”这一 S2 目标；它不承诺未来任意时刻都始终是 3 个，更不替应用保证设备已确认收到消息。要确认这些变化，需通过 API 读取对象的 `metadata`、`spec` 与 `status`；纸上课程不实际创建集群。

> **要点** — Kubernetes 持续比较 spec 与 status；三副本被维持是多组件接力逼近期望，而非一次同步命令。

三副本网关并非由某台固定机器守护，而是由一组对象分工把“应有三个”持续逼近为现实。

### 从模板到副本数：Deployment的声明职责

### 从模板到副本数：Deployment的声明职责

Deployment 不是直接逐个启动、看守某三个网关 Pod；它保存的是**期望状态**：应运行多少副本，以及每个副本应按什么模板创建。对网关而言，核心声明通常包括：

- `replicas: 3`：目标是同时存在三个符合条件的网关 Pod；
- `template`：Pod 模板，规定标签、容器镜像、端口、环境变量、资源请求等；
- `selector`：Deployment 认定“属于自己”的 Pod 标签范围。

可将其理解为一份持续生效的规格：

```yaml
spec:
  replicas: 3
  selector:
    matchLabels:
      app: gateway
  template:
    metadata:
      labels:
        app: gateway
    spec:
      containers:
      - name: gateway
        image: example/gateway:v1
```

其中，`selector.matchLabels` 必须能匹配 `template.metadata.labels`。否则，Deployment 创建出的 Pod 都无法被其后续控制链正确归属，集群会拒绝这类不一致的配置。

Deployment 进一步创建并管理 ReplicaSet；ReplicaSet 才负责持续观察：实际匹配的 Pod 数量是否等于目标值 $3$。少一个就补建，多一个则缩减。这里的“相同副本”来自同一模板，而不是三台固定机器：Pod 被删除、节点故障或容器无法恢复时，替代 Pod 会拥有新的 UID、IP 和进程内存。

当镜像从 `v1` 改为 `v2`，Deployment 的职责也不是原地修改旧 Pod，而是声明新的模板版本，并驱动新的 ReplicaSet 逐步扩容、旧 ReplicaSet 逐步缩容。因而 Deployment 关心的是“最终三份网关应长成什么样”，而非“某个旧 Pod 必须永远存活”。

### ReplicaSet：按选择器维持三个Pod

### ReplicaSet：按选择器维持三个Pod

ReplicaSet 不关心“原来的那三个 Pod 是否还活着”，只持续比较两件事：

- 期望副本数：`replicas: 3`
- 实际副本数：集群中**标签匹配 selector** 的 Pod 数量

例如，ReplicaSet 的选择器为：

`app: gateway`

控制器会不断统计带有 `app=gateway` 标签的 Pod。若当前只剩 2 个匹配 Pod，就得到缺额：

`缺额 = 期望数 3 - 实际数 2 = 1`

于是 ReplicaSet 依据自己的 Pod 模板创建 1 个新 Pod。调度器随后为它选择节点，容器运行时启动其中的进程。这个新 Pod 即使承担了旧副本的业务角色，也拥有新的 UID、IP、进程与内存状态；它是替代品，不是旧 Pod 的复活。

模板标签必须能被本 ReplicaSet 的 selector 选中。例如：

- selector：`app: gateway`
- 模板标签：`app: gateway`

这样新建 Pod 才会被计入实际副本数。若模板误写为 `app: gw`，ReplicaSet 创建出的 Pod 不匹配自己的选择器，统计结果仍可能是 0；控制器会持续认为存在缺额并反复创建 Pod。反过来，selector 过宽时，其他偶然匹配的 Pod 也可能被计数，使 ReplicaSet 少建甚至删除本不该管理的副本。

因此，副本数并不是“记住三台机器”，而是“让 selector 匹配的 Pod 数始终逼近三”。

### Pod不是主机：调度与运行的基本单位

### Pod不是主机：调度与运行的基本单位

Pod 是 Kubernetes 调度、部署和运行应用的最小单位，不是某台可长期依赖的“服务器”。调度器把 **Pod** 分配到某个节点；节点上的 kubelet 再创建并管理 Pod 内的一个或多个容器。容器共享同一 Pod 的网络命名空间、IP 地址、端口空间，以及可声明共享的存储卷，因此它们适合承载紧密协作的主进程与辅助进程。

层级关系可以概括为：

- **节点**：提供 CPU、内存、网络和运行时的宿主资源；一个节点可运行多个 Pod。
- **Pod**：一次调度和生命周期管理的边界；一个 Pod 可包含一个或多个容器。
- **容器**：实际执行进程的隔离环境；容器通常不是独立被调度的对象。
- **ReplicaSet / Deployment**：不直接代表某个固定进程，而是声明“应持续存在多少个符合模板的 Pod”。

因此，“有三副本网关”并不意味着固定保留三台机器，更不意味着某三个 Pod 永远不变。节点故障、驱逐、滚动更新或人工删除后，Deployment 经由 ReplicaSet 创建替代 Pod。替代者拥有新的 UID，通常也会获得新的 IP；其容器进程、内存状态和本地临时文件都不会自动继承旧 Pod。

这要求应用把可恢复状态放到合适的外部位置，例如持久卷、数据库、对象存储或消息系统；客户端则应通过 Service 等稳定入口访问副本，而非记住某个 Pod IP。Pod 是可替换的运行实例，节点只是其暂时落脚的位置。

### 故障替换追踪：新UID、新IP与新内存

### 故障替换追踪：新UID、新IP与新内存

设想网关 `gw-7c9d` 所在节点宕机，或该 Pod 被删除。ReplicaSet 不会寻找并“修复”这一个旧 Pod；它只重新观察当前状态：匹配其 `selector` 的存活 Pod 少于期望值 `3`，于是依据 `template` 创建一个新的 Pod 对象。

这一步可按链路理解：

1. **ReplicaSet 补建**：控制器发现副本数从 `3` 变为 `2`，提交一份按模板生成的新 Pod。
2. **调度器绑定**：新 Pod 起初尚未分配节点；调度器根据资源请求、污点容忍、亲和性等条件，为它选择某个可用节点并写入绑定结果。
3. **kubelet 启动**：目标节点上的 kubelet 看到已绑定的 Pod，拉取镜像、创建容器、挂载卷和网络，并上报运行状态。

新 Pod 可能仍带有 `app=gateway` 等相同标签，因此继续被 Service、ReplicaSet 或 NetworkPolicy 选中；但“标签相同”不等于“身份相同”。它具有新的 `UID`，通常也获得新的 Pod IP；容器进程重新启动，进程内存、未持久化缓存、连接状态都会消失。

因此，Pod 应被看作可替换的运行实例，而非永久主机。若网关需要跨替换保留会话、配置或数据，必须把状态放到外部系统或持久卷中，而不能依赖某个 Pod 的 IP、内存或名字。

### 三副本维持的边界：对象存在不等于业务可用

### 三副本维持的边界：对象存在不等于业务可用

`replicas: 3`表达的是控制器的目标，而不是“已有三条可用业务连接”。Deployment 创建或调整 ReplicaSet，ReplicaSet 再持续比较“期望 3 个”与“当前选中的 Pod 数量”；缺少时创建，多余时删除。但这一链路中的每一步都代表不同层次的事实：

- **对象已创建**：API 中存在 Deployment、ReplicaSet 或 Pod 记录，只能说明控制面接受了声明。
- **副本数满足**：ReplicaSet 选中了 3 个 Pod，可能仍有 Pod 尚未被调度、正在拉取镜像或反复重启。
- **Pod 为 Pending**：Pod 已被创建，却还没有成功绑定节点；常见原因是资源不足、节点约束不满足或卷无法挂载。
- **Pod 为 Ready**：容器通过就绪探针，Kubernetes 才通常将其加入 Service 后端；这表示它具备接收流量的条件，不等于下游设备、认证服务或长连接已经恢复。
- **业务连接恢复**：网关已实际连通目标设备或上游系统，并能完成所需协议交互。这是应用语义，不能仅由 Pod 数量推断。

因此，当前 **S2** 的确认边界应停在集群可观察的状态：模板匹配、Pod 是否被创建、调度状态、Ready 数量及容器事件。即使看到 `3/3 Ready`，也不能据此宣称三台设备已经确认在线。未来 **S3** 若需要确认设备侧状态，应通过明确的业务探测、握手结果或设备回执建立证据链；它是在 Kubernetes 副本维持之上的确认，而不是 ReplicaSet 自动提供的能力。

> **要点** — Deployment声明模板，ReplicaSet维持数量；Pod被替换即是新身份，三副本不自动等于业务已恢复。

控制器创建Pod后并不等于实例已运行：调度器、kubelet与节点条件共同决定它能否从Pending走向Ready。

### 未绑定Pod：调度器接过接力棒

### 未绑定Pod：调度器接过接力棒

控制器创建 Pod 后，通常只写入期望状态：容器镜像、`resources.requests`、标签、亲和性等；此时 `.spec.nodeName` 为空，Pod 仍处于 `Pending`。调度器持续监听这类“未绑定 Pod”，将其放入待调度队列，并执行一次典型的两阶段决策。

1. **筛选可行节点**：先排除不满足硬约束的 Node，例如：
   - 节点可分配 CPU、内存不足以容纳 `requests`；
   - `nodeSelector`、节点亲和性、污点与容忍不匹配；
   - Pod 反亲和性、拓扑分布约束或端口冲突不满足；
   - 节点处于不可调度状态，或受节点条件限制。

2. **评分并选择节点**：对剩余节点按资源均衡、镜像本地性、亲和性偏好、拓扑分布等策略打分，选择得分更合适的节点。

最终调度器不是“启动”Pod，而是通过绑定操作写入 `.spec.nodeName`，例如将 Pod 绑定到 `worker-2`。这一步相当于分配责任：从此该节点上的 kubelet 负责观察并运行它。

若所有节点都被筛掉，Pod 会继续保持 `Pending`，事件中常见 `FailedScheduling`。它不会因为等待一段时间就自动变为 `Ready`；只有资源释放、节点加入、约束修改或条件恢复后，调度器重新尝试才可能完成绑定。

### 先过滤再评分：节点为何被选中

### 先过滤再评分：节点为何被选中

调度器面对一个未绑定的 Pod，不是“找一台负载最低的机器”这么简单，而是先回答：**哪些节点绝对能放？** 再回答：**能放的节点里，哪台更合适？**

先进入过滤阶段。对每个节点，调度器检查 Pod 的 `requests` 是否能被满足。若节点可分配 CPU 为 `2` 核、已被其他 Pod 请求 `1.6` 核，而新 Pod 请求 `600m`，则：

$$1.6 + 0.6 > 2.0$$

该节点即使当前实际 CPU 使用率很低，也会因“请求量”超额而被排除。内存、扩展资源、GPU 等同样按 `requests` 计算；`limits` 通常不直接决定能否调度。

资源只是第一层约束。节点还必须满足：

- `nodeSelector`、节点亲和性：Pod 例如要求 `disk=ssd` 或指定可用区；
- 污点与容忍：节点有未被 Pod 容忍的污点时不可选；
- Pod 反亲和性、拓扑分布约束：副本不能过度集中在同一主机、机架或可用区；
- 端口占用、卷绑定、节点不可调度状态等条件。

例如 3 个副本要求跨两个可用区均匀分布：即使 A 区节点资源最多，若前两个副本已落在 A，第三个副本也可能被过滤掉 A 区，或在评分中强烈偏向 B 区。

通过过滤的节点构成候选集。随后调度器按多种策略评分，如资源均衡程度、镜像本地性、亲和偏好与拓扑分布；总分更高者被选中并写入 Pod 的 `nodeName`。因此，“被选中”表示它同时满足硬约束，并在当前候选节点中更优，不表示容器已经启动。

### 无可行节点时：Pending不是故障修复

### 无可行节点时：Pending不是故障修复

调度器只为**尚未绑定节点**的 Pod 寻找落点。它先过滤不满足条件的 Node，再对剩余节点评分；若过滤后集合为空，Pod 会继续处于 `Pending`，通常可在事件中看到 `FailedScheduling`。

常见的“无可行节点”原因包括：

- **资源请求放不下**：Pod 的 `requests.cpu`、`requests.memory`，以及扩展资源、端口、可分配 Pod 数超过任一节点剩余可分配量。调度依据是请求值，不是当前瞬时使用率。
- **污点未被容忍**：节点带有 `NoSchedule` 污点，而 Pod 没有匹配的 toleration。
- **节点选择条件冲突**：`nodeSelector`、节点亲和性、Pod 反亲和性、拓扑分布约束等共同筛掉了所有节点。
- **节点不可调度或状态异常**：节点被 cordon、未就绪，或带有无法容忍的条件污点。

这里的 `Pending` 是一种**等待状态**，不是自动修复机制。调度器会在节点资源释放、节点标签变化、污点移除或 Pod 约束修改后重新尝试；但它不会自行扩容节点、降低 requests、删除污点，也不会篡改亲和性规则。

控制器的边界同样明确：Deployment、StatefulSet 等负责维持副本数，会发现 Pod 存在，却通常不会因为它调度失败而“修好集群”。因此，副本数已经满足但全部 Pending 时，控制器未必会新建替代 Pod。应优先检查 `kubectl describe pod` 中的调度事件，再决定是扩容、释放资源，还是修正约束。

### 绑定之后：kubelet把声明变成进程

### 绑定之后：kubelet把声明变成进程

调度器的核心产物不是容器，而是一次绑定：它为 Pod 写入 `spec.nodeName`。这表示“该 Pod 应由此节点负责”，并不表示应用已经启动。目标节点上的 kubelet 持续监听 API Server，发现分配给自己的 Pod 后，开始把声明式规格落实为本机运行时对象。

典型链路是：

1. **准备运行环境**：kubelet 检查 Pod 配置、卷挂载、ServiceAccount 凭据、Secret 与 ConfigMap，并通过容器运行时创建 Pod 沙箱和网络命名空间。
2. **拉取镜像**：运行时按 `imagePullPolicy` 获取镜像；若镜像仓库不可达、认证 Secret 错误、镜像标签不存在或节点磁盘不足，Pod 仍会停留在 `Pending`，常见状态为 `ImagePullBackOff` 或 `ErrImagePull`。
3. **创建并启动容器**：kubelet 将 `containers` 中的命令、环境变量、资源限制和挂载信息交给运行时。容器成功启动后，Pod 通常进入 `Running`，但这仍不等于可接收流量。
4. **持续汇报状态**：kubelet 将 `status.phase`、容器退出码、重启次数、节点 IP 及各类 Conditions 写回 API Server。`Ready` 条件还要通过就绪探针；探针失败时，Pod 可以是 `Running`，却仍为 `Ready=False`。

因此，`spec.nodeName` 是调度完成的证据，而 `status` 才描述实际执行结果。绑定后的失败多发生在节点侧：镜像、网络、存储、运行时、探针或节点资源都可能阻止 Pod 真正变为 Ready。

### 从Pending到Ready：两道不同的门

### 从Pending到Ready：两道不同的门

Pod 的生命周期至少要跨过两道门：**被调度到节点**，以及**在该节点上真正可用**。二者都不是自动保证的。

1. **第一道门：调度器为未绑定 Pod 选择节点**  
   scheduler 先过滤不满足条件的 Node：例如 `requests.cpu`、`requests.memory` 超过节点可分配资源，`nodeSelector`、亲和/反亲和规则、污点与容忍度不匹配，或节点处于不可调度状态。再对剩余节点评分并绑定 Pod。  
   若没有可行节点，Pod 通常保持 `Pending`，事件可能显示“资源不足”或“没有匹配的节点”。此时扩容节点、降低 requests 或修正约束后，才可能再次被调度。

2. **第二道门：kubelet 让已绑定 Pod 变得可用**  
   绑定成功仅表示 Pod 已有 `spec.nodeName`；目标节点上的 kubelet 才负责拉取镜像、创建沙箱、挂载卷、启动容器，并持续上报状态。镜像不存在、仓库认证失败、网络不可达时，Pod 即使已调度，仍可能停留在 `Pending`，并出现 `ImagePullBackOff` 或 `ErrImagePull`。

即便容器进入 `Running`，也不等于 `Ready=True`。若配置了就绪探针，探针失败会使 Pod 保持未就绪；Service 通常不会把流量转发给它。可以概括为：

`已调度` → `容器运行` → `就绪探针成功` → `Ready`

因此，排障时应先看 Pod 是否绑定节点，再看容器状态与 Events，最后检查就绪探针和应用自身健康状态。

> **要点** — 调度成功只为Pod选定节点；kubelet成功运行容器且业务通过就绪检查，Pod才可能Ready。

以三副本 IM 网关从故障到恢复的时间线为主线，拆解声明、创建、调度、启动与就绪确认各自提供的证据。

### 从三副本健康到单副本退出

### 从三副本健康到单副本退出

设 IM 网关的 `Deployment` 声明期望副本数为 3。理解恢复过程前，必须先在 `t0` 建立三层状态基线：

| 观察层 | `t0` 的证据 | 能说明什么 |
|---|---|---|
| 声明层 | `spec.replicas=3` | 控制器目标是维持 3 个副本 |
| 实例层 | 存在 3 个网关 Pod，均未终止 | 当前有 3 个可被管理的实例 |
| 流量层 | 3 个 Pod 都通过 `readinessProbe`，Service 后端有 3 个 Ready Endpoint | 当前可向 3 个实例转发请求 |

因此，`spec=3` 不等于“已有 3 个 Pod”，Pod 处于 `Running` 也不等于“已经可接流量”。对网关而言，真正决定负载均衡后端集合的是就绪状态：通常可通过 Pod 的 `Ready=True` 条件、EndpointSlice 中的 `ready=true`，或 Service 后端列表交叉确认。

到 `t1`，假设 Pod `P1` 开始退出，例如进程收到终止信号、节点故障，或 Pod 被删除。此时应将状态描述为：

- 期望副本仍为 3：`spec.replicas=3` 没有改变；
- 可存活实例可能暂时只剩 2 个，或 `P1` 仍显示为 `Terminating`；
- 可接流量实例应降为 2 个：`P1` 一旦失去 `Ready`，应从 Service 的有效后端中移除。

这里最容易产生误判：看到 Deployment 仍写着 3，不能宣布三副本网关健康；看到 `P1` 尚未完全消失，也不能把它算作可用容量。`t1` 的正确结论是：系统的**目标**仍是 3，但当前已确认可安全承接流量的网关只有 2 个，控制器需要开始弥补这一缺口。

### 控制器为何只负责补出 P4

### 控制器为何只负责补出 P4

设 Deployment 期望副本数为 $3$。在 $t_0$，其 ReplicaSet 已拥有 `P1、P2、P3` 三个 Pod，且三者均通过就绪检查：

\[
\text{spec.replicas}=3,\quad \text{Ready}=3
\]

到 $t_1$，`P1` 因进程退出、节点问题或主动终止而失去 `Ready`。这里必须区分两类计数：`Ready` 降为 2，说明可接流量的网关只剩两副本；但控制器是否创建 `P4`，主要依据的是 ReplicaSet 对“当前受管 Pod 数量”与目标副本数的比较，而不是直接以 `Ready=2` 为触发条件。

责任链如下：

- **Deployment**：保存期望状态，例如副本数为 3、镜像版本、滚动更新策略；它通常不逐个创建 Pod，而是管理对应的 ReplicaSet。
- **ReplicaSet**：持续观察带有匹配标签的 Pod，维持 `spec.replicas=3`。当 `P1` 已被删除，或不再计入该 ReplicaSet 的有效受管实例时，观察到实际数少于 3。
- **ReplicaSet 控制器**：执行补差计算：

\[
\Delta = 3-\text{currentPods}
\]

若 $\Delta=1$，便依据 Pod 模板创建一个新的 Pod 对象，即 `P4`。
- **Pod**：`P4` 被创建只意味着 API 中出现了新的声明对象；其 `nodeName` 尚为空时，仍没有任何节点真正承诺运行它。

因此，控制器在这一阶段的职责是“补出一个符合模板的候选副本”，而非保证网关已恢复服务能力。`P4` 即使已存在，也可能处于 `Pending`：等待调度、资源、镜像或卷挂载。此时可以证明的是“期望副本正在被补齐”，不能证明 A/B 流量已恢复到三路可用。只有后续调度绑定、kubelet 启动容器，并使 `P4` 的 readiness 变为真后，`Ready` 才会重新达到 3。

### Pending：P4 已存在但尚未可用

### Pending：P4 已存在但尚未可用

在 $t_2$，控制器发现可用副本从 3 降到 2，于是创建替代 Pod `P4`。此时最容易产生误判：`spec.replicas=3` 已满足，集群中也确实能查到 3 个 Pod 对象，但 A/B 网关的三副本服务能力尚未恢复。

可将几个状态区分为不同层次的证据：

| 观察结果 | 能证明什么 | 不能证明什么 |
|---|---|---|
| `spec=3` | 控制器期望维持 3 个副本 | 已创建、已调度、可接流量 |
| 已看到 `P4` 对象 | 控制器已执行补副本动作 | `P4` 有节点可运行 |
| `P4` 为 `Pending` | Pod 尚未完成可运行前置条件 | 已绑定节点、进程已启动、网关已恢复 |
| 已调度 | scheduler 已为 Pod 选定节点并绑定 | 容器已成功启动或通过探针 |
| `Running` | 容器已被 kubelet 启动 | 已通过 readiness、已加入服务端点 |

`Pending` 常见于调度器尚未找到满足条件的节点，例如 CPU、内存不足，节点带有污点，Pod 的亲和性、反亲和性或卷挂载条件未满足。此时 `P4` 虽然“存在”，却没有承担任何网关请求。

因此，$t_2$ 的正确结论是：**声明副本数已补齐，实际可用副本仍为 2。** 排查证据应查看 `P4` 的 `status.phase`、`PodScheduled` 条件和事件，而不是只核对 Deployment 的期望副本数。只有后续完成调度、启动并通过 readiness，`P4` 才可能成为第三个可服务副本。

### 调度与 kubelet 的接力证据

### 调度与 kubelet 的接力证据

$t2$ 时，控制器虽已创建替补 Pod `P4`，但它仍是 `Pending`：这只证明“期望副本已被补齐为对象”，并不证明网关已有第三个可服务实例。接下来必须区分调度器与节点侧 kubelet 所提供的证据。

到 $t3$，scheduler 为 `P4` 选择合适节点并写入：

`spec.nodeName: node-x`

这一步是**绑定证据**。调度器已综合资源请求、污点与容忍、亲和性、端口冲突、拓扑约束等条件，确认 `P4` 应落在 `node-x`。因此 Pod 不再是“无处安放的 Pending”；但绑定并不等于容器已经存在，更不等于流量可进入。

随后 kubelet 观察到本节点新增的 `P4`，在 $t4$ 接力执行：

1. 拉取镜像、创建 sandbox 与容器；
2. 启动网关进程，状态可逐步表现为 `Running`；
3. 按 `readinessProbe` 周期探测，例如 HTTP 健康接口、TCP 端口或命令检查；
4. 仅当探针连续满足阈值，写入 Pod 条件 `Ready=True`。

这里 `Running` 的证据仅表示主进程已启动；它可能仍在加载配置、连接 IM 后端、同步会话路由，或尚未监听业务端口。只有 `Ready=True` 才表示 kubelet 已确认该实例满足服务入口定义的就绪条件，EndpointSlice 才会将 `P4` 纳入可转发后端。

因此恢复链条应手推为：

`P4 Pending` → `已绑定 node-x` → `容器 Running` → `readiness 成功` → `Ready=3`

在最后一步之前，不能因为 `spec.replicas=3` 或看到三个 `Running` Pod，就宣布 A/B 网关能力恢复。

### Ready3 才是接流量恢复的证据

### Ready3 才是接流量恢复的证据

设初始时刻三副本网关均已就绪：`P1`、`P2`、`P3`，对应 `Ready=3`。`P1` 失去就绪状态后，即使其容器仍显示 `Running`，它也应从 Service 的可用后端中移除；此时真正可接收新流量的是当前集合：

\[
S_2=\{P2,P3\}
\]

控制器随后创建替代 Pod `P4`，但“替代”并不表示 `P1` 原地复活。应以 Pod UID 区分实例身份：

- `P1.uid \ne P4.uid`：`P4` 是新对象，不是 `P1` 的状态回升。
- `P4` 默认不继承 `P1` 的进程内存、长连接、连接池或本地临时状态。
- 若客户端曾连接到 `P1`，该连接可能已断开或正在排空；`P4` 的启动不能自动证明这些旧会话已经迁移。

因此，`P4` 处于 `Pending` 时，声明层面可能已满足“期望三副本”，但数据面仍只有 `S2`。scheduler 将 `P4` 绑定到某个 Node，只能证明它获得了放置位置；kubelet 拉镜像、创建容器并看到 `Running`，也只能证明进程已启动。此时进程可能仍在恢复配置、预热缓存、建立上游连接或加载会话状态。

只有 readiness 探针通过，`P4` 被写入 Service 后端集合，才得到未来可用集合：

\[
S_3=\{P2,P3,P4\}
\]

`Ready=3` 的含义是：三个被标记为就绪的端点可以承接**新的**负载均衡流量。它不等于设备已经确认重新建立连接，也不等于原先连接在 `P1` 上的用户已无感恢复。排障时应分别核对：Pod UID、EndpointSlice/Service 后端、`P4` 的 readiness 事件，以及设备或客户端的重连确认。

> **要点** — 期望三副本不等于可用三副本；只有新 Pod 被调度、启动并通过就绪检查后，才能确认网关接流量能力恢复。

三副本只能维持网关进程存活，不能替代业务协议对消息状态、重试和设备确认的约定。

### 从旧P1断开到替代P4

### 从旧P1断开到替代P4

设网关旧副本 `P1` 与设备维持一条 WebSocket 连接，且已在进程内状态 `S2` 记录消息 `m-a`：可能是“已接收、待转发”，也可能是“已发送、等待设备确认”。此时 `P1` 崩溃或被驱逐，首先消失的是连接本身：TCP/WebSocket 会断开，设备必须重新连接；其次消失的是 `S2`：内存中的 `m-a`、计时器、待确认表和局部会话上下文均不再可靠。

控制面发现副本数不足后创建替代副本 `P4`。`P4` 继承的是“需要一个可运行网关副本”这一目标，而不是 `P1` 的进程记忆：

- `P4` 不知道 `m-a` 是否已送到设备；
- `P4` 不知道设备是否已处理、但确认包尚未来得及返回；
- `P4` 无法恢复 `P1` 的 WebSocket 会话，更不能继续其未完成的发送；
- 即使设备重连到 `P4`，也只是建立新连接，不等于恢复旧连接中的消息状态。

因此，三副本部署可降低“没有网关可连”的概率，却不能把进程内状态变成跨重启的可靠状态。若 `m-a` 的投递结果必须可追踪，消息状态、序号或设备确认必须存在于进程外的持久协议边界；否则故障后的正确结论只能是：`m-a` 状态未知，不能仅凭 `P4` 已启动就宣称其已送达或可安全重发。

### 替代Pod为何不继承内存

### 替代Pod为何不继承内存

`Deployment` 声明的是“期望有 3 个可用副本”，并不声明“某个副本死后必须由带着原内存的新进程继续执行”。因此，P1 失联后的接力链路只保证副本数量回补：

1. P1 所在节点故障、进程退出，或 kubelet 判定容器不健康后，P1 的 Pod 状态进入失败、删除或长期不可用。
2. `ReplicaSet` 观察到实际可用 Pod 数少于期望值 3，于是创建新的 Pod 对象，例如 P4。
3. 调度器只根据资源、污点、亲和性等条件，为 P4 选择可运行的节点；它不会读取 P1 的堆内存，也不知道 P1 曾维护哪些 WebSocket。
4. 目标节点上的 kubelet 拉取镜像、创建容器并启动网关进程。P4 从镜像、配置、挂载卷及显式外部依赖中初始化，而非从 P1 的进程快照恢复。

所以，P1 中的连接表、会话对象、未完成请求、已发送但未确认的消息，以及 `m-a` 的“正在等待设备响应”状态，都会随 P1 的进程消失。即使 P4 恰好调度到同一节点，甚至使用相同镜像、相同环境变量，也只是启动了一个新的进程实例：

\[
\text{P4 是副本数量的替代} \neq \text{P1 内存状态的继承}
\]

若客户端 A 因超时以同一请求标识重试，P4 至多能重新接收该请求；它无法仅凭 Kubernetes 得知 P1 是否已向设备发送过 `m-a`、设备是否已执行、响应是否曾到达但尚未来得及返回。此类判定必须由业务合同、持久化消息状态或设备确认协议承担，而不能归因于 Deployment 的三副本机制。

### Pending、运行与Ready的差别

### Pending、运行与Ready的差别

P4 被创建出来，并不表示它已经接替了故障的 P1。控制面观察的是副本数与 Pod 生命周期；业务侧真正关心的则是：是否有可用网关、旧会话是否仍存在、消息状态能否继续确认。

- **Pending**：P4 已被期望创建，但尚未成功调度或完成资源、镜像、卷、网络等前置条件。此时“期望副本数=3”，却可能只有 2 个实际进程；P1 的 WebSocket 已断开，进程内 S2 中的状态也不会因 P4 处于 Pending 而被保存或迁移。

- **运行中**：P4 的容器进程已经启动，说明节点上有了新的网关进程。但它可能仍在加载配置、建立上游连接、恢复缓存，或者尚未监听服务端口。更重要的是，P4 是新进程，不会继承 P1 的内存会话、未确认消息、连接上下文或进程内去重记录。

- **Ready**：P4 通过就绪检查，才表示它应当能够接收流量。负载均衡器随后才会把新请求导向它。然而 Ready 通常只证明“进程可服务”，不证明“旧业务会话已恢复”。原 WebSocket 需要客户端重新连接；同一 `ID` 的超时重试是否返回 `409`、接受还是状态未知，仍必须按业务合同处理。

因此，控制面从 2 个副本恢复到 3 个副本，只完成了**进程可用性的修复**。它不会自动提供跨重启的消息去重、顺序保证或设备 ACK 追踪；这些能力应由后续持久化状态与业务协议单独定义。

### 同ID重试必须回到合同

### 同ID重试必须回到合同

客户端 A 发送消息 `m-a` 后发生超时，并不等于网关没有收到、没有转发，或设备没有执行。超时只说明：A 在约定时间内未获得可用响应。此时若 A 以相同消息 ID 重试，结果取决于接口合同，而不是由三副本、负载均衡或替代 Pod 自动保证。

常见结果至少包括：

- 返回成功：服务端识别到同一请求已被接受，返回此前的结果或等价确认。
- 返回 `409`：服务端认为该 ID 已存在、请求冲突，拒绝再次创建。
- 返回“状态未知”或可查询令牌：服务端无法在当前调用中证明最终结果，要求客户端后续查询。
- 再次受理：若合同未规定幂等语义，同 ID 也可能被当作新请求；这会带来重复下发风险。

因此，A 收到 `409` 时不能简单判定“失败后重发”，也不能直接认定“设备已执行”。正确动作是按合同中的查询接口、状态机和终态定义处理，例如查询 `m-a` 的受理状态、下发状态或设备确认状态。只有合同明确规定“`409` 表示此前请求已成功受理”时，客户端才能将其视为等价成功。

进程内的旧状态 `S2(m-a)` 会随 Pod 重启消失；替代 Pod `P4` 不会天然继承它。集群控制面最多尽力维持网关副本可用，不能替客户端补全消息去重、结果恢复或设备确认。重试策略必须以接口合同为准：何时重试、是否复用 ID、冲突后查什么、未知状态如何收敛，都属于业务协议的一部分。

### 控制面与未来S3的责任边界

### 控制面与未来 S3 的责任边界

Kubernetes 的职责是尽力维持期望副本数：某个网关 Pod 崩溃、被驱逐或节点故障后，控制器会创建替代 Pod，使服务端点逐步恢复可用。它并不理解 `m-9` 是哪条业务消息，也不知道 `seq9` 是否已被设备处理，更无法判断设备 ACK 是否真实到达。

因此，未来的 S3 必须作为独立的业务可靠性设计：由数据库持久化消息标识 `m-9`、设备序号 `seq9`、投递状态、重试次数以及设备 ACK。例如可将状态建模为：

`待发送 → 已投递 → 已确认`

其中“已投递”只能表示网关或连接层曾尝试发送；只有收到并持久化设备 ACK 后，才能进入“已确认”。网关重启、连接迁移和 Pod 替换均不得抹去这些记录。

需要特别区分两类“重试”：

- **控制面重试**：Kubernetes 重建 Pod，目标是恢复进程和网络服务。
- **业务重试**：S3 根据持久化状态重新投递 `m-9`，目标是最终获得与 `seq9` 对应的确认。

即使新 Pod 恰好接到同一设备连接，它也不能仅凭“这是替代副本”推断旧消息是否已处理；设备可能已执行但 ACK 丢失，也可能根本未收到。业务侧应以稳定消息标识、序号规则和 ACK 协议实现幂等与去重。换言之，Kubernetes 负责“网关还在”，S3 才负责“这条消息是否已被确认”。

> **要点** — Kubernetes尽力补齐Pod副本；跨重启消息状态、幂等重试与设备确认必须由业务合同和持久化机制承担。

三副本并非由某个组件“一次性创建”后永久不变，而是由声明、观测与多段控制接力持续维持。

### 从期望三副本到观测两就绪

### 从期望三副本到观测两就绪

在 Kubernetes 中，“三副本网关”首先不是三个已经稳定运行的进程，而是一份**期望状态**。例如 Deployment 声明 `replicas: 3`，其含义是：系统应持续努力让对应工作负载拥有 3 个满足条件的副本。

需要先区分两类信息：

- `spec`：用户提交的目标，例如“期望 3 个副本”。
- `status`：控制面根据当前观测写回的事实，例如“当前 3 个 Pod 已创建，但只有 2 个 Ready”。

因此，`spec.replicas = 3` 且 `status.readyReplicas = 2` 并不等于 Kubernetes 已经“失效”。它描述的是一个尚未收敛的状态：控制器已知目标为 3，而集群当前只能确认 2 个副本通过就绪判定。

这里的“就绪”尤其重要。Pod 被创建、被调度到节点、容器已启动，都不必然意味着它可以接收网关流量；只有 readiness probe 或相应就绪条件成立，Pod 才会计入 `readyReplicas`，并通常成为 Service 的可用后端。

从“期望 3、就绪 2”出发，后续要问的不是笼统的“为什么少一个”，而是该副本停在哪一段：尚未创建、处于 Pending、镜像拉取失败、节点资源不足，还是容器运行但未通过 readiness。不同现象对应不同控制环节与排查入口。

### 四类组件的接力职责

### 四类组件的接力职责

设网关工作负载期望副本数为 `spec.replicas=3`，当前只有两个可用副本，即 `status.readyReplicas=2`。这里的“补齐”不是某个组件单独完成的动作，而是一条按职责分段的控制链。

1. **API server：保存声明与事实入口**  
   用户或控制器提交的 Deployment、ReplicaSet、Pod 等对象都经由 API server 校验、持久化并提供读取接口。它不亲自创建容器，也不选择节点；它维护的是集群共享的期望状态与观测状态。控制循环可据此发现：期望为 3，而已就绪仅为 2。

2. **控制器：把副本差额变成新 Pod**  
   Deployment 控制器先确保对应 ReplicaSet 存在；ReplicaSet 控制器再比较 `spec.replicas=3` 与当前受其管理的 Pod 数量。若少了一个，就创建一个新的 Pod 对象。此时 Pod 通常仍处于 `Pending`：对象已经被声明出来，但尚未被分配节点。

3. **scheduler：为未绑定 Pod 选择节点**  
   调度器观察到 `spec.nodeName` 为空的 Pod，依据 CPU、内存、污点与容忍、亲和性、端口、卷等约束筛选节点并打分，然后写入目标节点名。若没有满足条件的节点，Pod 会持续 Pending，原因与事件通常指向资源不足或调度约束不满足，而不是“控制器没有补副本”。

4. **kubelet：在目标节点兑现 Pod**  
   目标节点上的 kubelet 发现已绑定给自己的 Pod 后，拉取镜像、创建沙箱、挂载存储并启动容器，再持续回报状态。镜像拉取失败、容器退出等问题发生在这一段；容器即使已运行，也还要通过 readiness 探针，才计入 `readyReplicas`。因此“有 3 个 Pod”不等于“有 3 个可服务副本”。

这条链解释了副本恢复的顺序：控制器补对象，调度器补位置，kubelet补运行实例，readiness 补可用性。`Pending` 原因、Events、节点资源、镜像拉取和就绪检查分别属于不同环节，不能混为同一种故障。

### Pending、容器运行与Ready不能混为一谈

### Pending、容器运行与Ready不能混为一谈

排障时应把 Pod 的“被调度”“容器已启动”“已可接收流量”分开看。它们对应不同控制阶段，不能仅凭“副本数不足 3”就归因于应用故障。

| 场景 | 常见 Pod 状态 | 主要定位字段 | 典型事件/现象 |
|---|---|---|---|
| 节点资源不足 | `Pending`，尚未绑定节点 | `PodScheduled=False`、`reason=Unschedulable` | 调度器提示 CPU、内存、Pod 数或污点容忍条件不满足 |
| 镜像拉取失败 | 通常仍显示 `Pending`，但已分配节点 | `containerStatuses[*].state.waiting` | `ErrImagePull`、`ImagePullBackOff`、认证失败、镜像不存在或网络不可达 |
| 就绪探针未通过 | Pod 可能为 `Running`，但 `Ready=False` | `conditions.Ready=False`、`readinessProbe` | 容器已运行，却未进入 Service 可用后端；事件可见探针超时、连接拒绝或返回码异常 |

资源不足发生在 scheduler 选择节点之前：Pod 没有合适 Node，重点检查请求值 `resources.requests`、节点可分配资源、污点与亲和规则。此时不是 kubelet 未启动容器，而是 kubelet 尚未接手该 Pod。

镜像拉取失败发生在调度完成之后。Pod 已有 `nodeName`，kubelet 正尝试创建容器，但镜像尚不可用；应沿镜像名、仓库凭据、`imagePullSecrets`、节点到仓库网络路径排查。

就绪失败则更靠后：进程可能正常存活，因此不能把 `Running` 当作服务可用。`readinessProbe` 不通过时，Deployment 的 `status.readyReplicas` 不会增长，对应 Pod 通常也不会加入 Service 的 EndpointSlice。`Pending`、容器运行、`Ready` 分别回答“能否调度”“能否启动”“能否提供流量”，是三条不同的诊断线索。

### Pod替换后哪些东西会消失

### Pod替换后哪些东西会消失

设某个 Deployment 声明 `spec.replicas: 3`，其中一个 Pod 因节点故障、进程退出或被删除而消失。控制器关注的是“可用副本数量”，不是“让原来的那个 Pod 复活”：它会创建一个**新的 Pod 对象**补足副本，新旧 Pod 即使名称相似，也不是同一实例。

最直接的边界是 UID。旧 Pod 的 `metadata.uid` 唯一标识其生命周期；替代 Pod 会获得新的 UID、新的容器实例、新的沙箱和新的网络命名空间。副本数恢复到 3，不表示任何实例身份被继承。

因此，下列状态通常会随旧 Pod 一起消失：

- **进程内存**：缓存、会话、未落盘任务、队列消费位置等，除非应用主动写入外部持久化系统。
- **本地临时数据**：容器可写层、`emptyDir` 内容、临时文件及本机日志缓冲都不应假定保留。
- **客户端连接**：TCP/WebSocket/gRPC 长连接终止；客户端需要超时、重连和必要的幂等重试。
- **节点相关条件**：新 Pod 可能被 scheduler 分配到另一 Node，再由该节点 kubelet 拉取镜像、启动容器并上报状态。

替代 Pod 还要重新经历 `Pending`、镜像拉取、容器启动和 readiness 探针检查。`spec.replicas: 3` 只保证控制器持续尝试维持期望数量；`status.readyReplicas: 2` 则表示当前只有两个副本真正通过就绪检查、可被 Service 作为后端使用。副本“存在”不等于连接、内存状态和服务能力自动无缝继承。

### 集群自愈不等于业务自愈

### 集群自愈不等于业务自愈

Kubernetes 能维持的是**声明层面的可用性**：例如 Deployment 声明 `replicas: 3`，控制器持续比较期望副本数与实际副本数；某个 Pod 消失、节点故障或进程退出后，会创建替代 Pod。`readiness` 探针决定 Pod 是否进入 Service 后端，从而避免“进程存在但尚不能接流量”的实例被过早使用。

但这不等于 OpenIM 或网关业务已经自愈。集群通常只能确认：

- Pod 是否被调度、容器是否启动、镜像是否拉取成功；
- 容器是否存活，是否通过就绪检查；
- Service 是否还有足够的 Ready 后端。

它不能自动判断业务语义。例如 S2 当前是否已持久化成功、响应是否已返回、消息是否重复投递；未来 S3 设备是否真正收到指令、是否离线、是否需要重试或人工确认，都属于应用协议、状态机与设备侧确认机制的责任。

因此，“三个 Pod 都是 Ready”最多说明三个副本满足预设健康门槛，不证明请求一定完成，更不证明外部设备状态正确。业务应自行设计幂等键、事务/补偿、消息确认、超时重试、死信处理与状态对账。

同样，仓库中固定存在两份 OpenIM 源码，只能证明源码被保存或引用；它不能证明这些源码已构建为镜像、已提交 Kubernetes 清单、已被 API server 接受，更不能证明 scheduler 已调度且 kubelet 正在运行对应容器。部署事实必须由实际集群对象、事件、Pod 状态与运行证据确认。

> **要点** — Kubernetes通过持续对齐期望与观测维持副本；Pod可被替换，但业务状态、连接与设备确认必须另行设计。

以三副本 IM 网关为线索，拆解 Kubernetes 如何把声明的副本数持续拉回现实，并明确平台控制与业务恢复的边界。

### 期望状态与观测状态：控制循环的起点

### 期望状态与观测状态：控制循环的起点

Kubernetes 不要求管理员逐台启动三台 IM 网关，而是先在 API 对象中声明目标。例如 Deployment 的 `spec.replicas: 3` 表示“期望最终有 3 个可用副本”。`spec` 是用户提交的意图：镜像、端口、资源请求、更新策略，以及期望副本数；它不是某一刻的机器运行清单。

与之对应，`status` 记录集群当前观测到的事实。例如 Deployment 会报告已创建副本、可用副本和不可用副本数；ReplicaSet 报告实际管理的 Pod 数；Pod 则记录 `Pending`、`Running`、`Ready` 等阶段与条件。控制器不断比较两者：

$$
\text{偏差}=\text{spec 中的目标}-\text{status 中的事实}
$$

若 Deployment 期望 3 个副本，而当前只有 2 个可用副本，Deployment 控制器会调整 ReplicaSet；ReplicaSet 再创建缺少的 Pod。新 Pod 起初可能是 `Pending`：它已被声明，却尚未被 scheduler 找到合适节点。scheduler 经过过滤与评分后绑定节点，kubelet 才拉取镜像并启动容器。

但“容器正在运行”不等于“网关已满足业务合同”。Pod 的 `Ready` 条件通常来自 Readiness 探针；只有就绪后，它才应进入 Service 的后端端点。若 IM 网关进程虽存活，却无法连接 S2/S3 或设备侧依赖，应保持未就绪，而非过早接流量。

因此，控制循环是：

1. 用户写入 `spec`，声明三副本网关；
2. 控制面持续观测并更新 `status`；
3. 控制器针对偏差创建、删除或替换对象；
4. 业务通过 Readiness 表达“可服务”的额外事实。

注意，Pod 的 UID 对应一次具体实例；重建出来的是新 Pod，不是把旧 Pod “搬到”另一台机器。Kubernetes 可以补足副本，却不能自动迁移旧 WebSocket 会话、恢复客户端连接，或替设备与外部系统完成业务重试。平台纠正的是对象数量与调度状态；会话断开及其恢复，仍是网关应用与客户端协议的边界。

### Deployment、ReplicaSet 与 Pod 的责任接力

### Deployment、ReplicaSet 与 Pod 的责任接力

对三副本 IM 网关，可以先写出期望状态：`replicas: 3`。但“保持三个”并不是某个对象独自完成的，而是一条逐层下沉的控制链：

- **Deployment 管版本与发布策略**：它声明网关应使用哪个镜像、环境变量、标签，以及期望运行几份。更新镜像时，Deployment 不会直接逐个重建容器，而是创建新的 ReplicaSet，并按滚动更新策略逐步扩大新版本、缩小旧版本。
- **ReplicaSet 管副本数收敛**：ReplicaSet 的任务更单纯：让匹配其标签选择器的 Pod 数量趋近目标值。若目标为 3 而当前只剩 2 个，它创建 1 个 Pod；若多出 1 个，则删除 1 个。它不决定 Pod 落在哪台节点，也不理解 IM 会话是否恢复。
- **Pod 承载一次具体运行实例**：Pod 是调度和运行的最小单位，包含网关容器及其网络、卷等运行上下文。Pod 被调度到节点后，其生命周期绑定该实例；节点失效或 Pod 被删除时，控制器通常创建的是**新 Pod**，具有新的 Pod UID，而不是把旧 Pod “搬迁”到别处。

因此，三副本的真实推导是：

`Deployment 声明版本与 3 份期望`  
$\rightarrow$ `ReplicaSet 维持 3 个 Pod 对象`  
$\rightarrow$ `scheduler 为每个待调度 Pod 选择节点`  
$\rightarrow$ `kubelet 在节点启动容器`

其中，ReplicaSet 看到的是“Pod 数量”，而非“可用网关数量”。新 Pod 可能处于 `Pending`：对象已被创建，但尚未通过调度过滤、评分并绑定节点；也可能容器已经运行，却尚未通过 `Readiness`。所以 `3 个 Pod`、`3 个 Running 容器` 与 `3 个可接收 IM 流量的网关` 是三个不同层次的事实。

### 从待调度到就绪：调度器与 kubelet 的接力

### 从待调度到就绪：调度器与 kubelet 的接力

假设 Deployment 发现实际可用副本不足，ReplicaSet 便创建一个新的 Pod 对象。此时 API 中已有 Pod UID，但尚未绑定节点：`spec.nodeName` 为空，状态通常表现为 `Pending`。这个 UID 标识的是一次具体实例生命，不是“可随意搬运的容器”；已绑定的 Pod 不能被调度器整体迁移，只能删除后再由控制器创建新 Pod。

调度器持续观察未绑定节点的 Pod，并分两步选择落点：

1. **过滤**：剔除不满足硬约束的节点，例如 CPU/内存可分配量不足、节点污点未被容忍、节点选择器或亲和性不匹配、端口冲突、卷无法挂载。
2. **评分**：对剩余节点按偏好排序，例如资源均衡、镜像局部性、Pod 反亲和性分散程度。最高分节点被选中。

随后调度器向 API 写入绑定结果，即设置 `spec.nodeName`。这不是把运行中的 Pod 搬到节点，而是为这个尚未启动的 UID 指定唯一宿主。若所有节点都被过滤，Pod 会持续处于 `Pending`；问题在于资源、约束或容量，而非 kubelet 尚未“启动得够快”。

目标节点上的 kubelet 观察到这个绑定 Pod 后，才接手执行：拉取镜像、准备网络与卷、调用容器运行时创建容器，并持续回报 `status`。容器进程启动只说明“进程在运行”，并不说明 IM 网关已满足业务合同：配置可能未加载、依赖未连通、会话状态未恢复、监听端口虽开但无法处理请求。

因此 kubelet 或应用通过 Readiness Probe 报告就绪前，Pod 不应进入 Service 的可转发端点集合。对外表现上，旧连接的 WebSocket 仍可能因旧 Pod 消失而断开；新 Pod 的 Readiness 只能允许新流量进入，不能恢复既有连接。至此，平台完成 S2/S3 层的实例补位与流量收敛；设备侧重连、鉴权、会话续接仍属于业务边界。

### 故障替换：新 UID、不可搬迁与连接代价

### 故障替换：新 UID、不可搬迁与连接代价

设三副本 IM 网关由 `Deployment` 声明：

`spec.replicas: 3`

正常时，`Deployment` 通过 `ReplicaSet` 维持三个 Pod。若其中一个网关 Pod 进程崩溃、Pod 被删除，或所在节点失联，控制面不会“修复原 Pod”，而是观察到实际副本数低于期望值，在别处创建一个**新的 Pod**。

这个过程的关键是：新旧 Pod 不是同一个实体。

- 旧 Pod 有 UID `A`，其容器、网络命名空间、内存、临时文件和进程全部随之消失。
- 新 Pod 即使名称相似，也会获得 UID `B`。
- Kubernetes 不会把 UID `A` 的内存直接迁移到 UID `B`；Pod 不是可在线搬迁的虚拟机。

若节点故障，`scheduler` 会为替换 Pod 寻找可用节点：先过滤不满足资源、污点、亲和性等约束的节点，再对剩余节点评分并绑定。新 Pod 在镜像拉取、容器启动、探针通过前可能处于 `Pending` 或未就绪状态。此时“已创建”不等于“可接流量”；只有 `Readiness` 成功，Service 才会将它加入后端端点。

对 IM 网关而言，代价不止一次容器重启。旧 Pod 内存中的登录会话、房间订阅、限流计数、未发送消息缓存和 WebSocket 连接状态都会丢失。客户端与旧实例之间的 TCP/WebSocket 连接断开，必须经历重连、鉴权、恢复订阅或补拉消息。

因此，Kubernetes 保证的是副本数量最终回到 3，而不是保证连接无感、会话不丢。容器“正在运行”只说明进程存在；应用合同还应覆盖重连策略、状态外置、消息幂等与断线恢复。S2/S3 等持久化系统可保存消息或会话数据，但不能保存某个 Pod 的内存连接；设备侧更不能被视为可由集群迁移的运行环境。

### 平台自愈与业务合同：S2、S3、设备确认边界

### 平台自愈与业务合同：S2、S3、设备确认边界

Kubernetes 的“自愈”首先是**声明状态的回归**：Deployment 在 `spec.replicas: 3` 中声明三副本网关，控制器经由 ReplicaSet 观察实际 Pod 数量；Pod 消失、节点失联或容器退出后，新的 Pod 会被创建，scheduler 经过过滤与评分选择节点，最终使 `status` 再次趋近三副本。

但这不等于业务状态自动恢复。原 Pod 的 UID 已经消失；新 Pod 是一个新的实例，不能被当作旧进程“搬家”或原地续命。若旧 Pod 上承载了 WebSocket 连接，其进程、内存会话、未发送缓冲和本地去重窗口都会随故障消失。客户端看到的通常是连接断开，而不是一次无感迁移。

需要区分三个层次：

- **S2：容器/进程层恢复**  
  kubelet 重启容器，或控制器补建 Pod。它解决“网关进程是否重新运行”，不保证进程内会话仍存在。
- **S3：服务可用层恢复**  
  新 Pod 被调度、拉取镜像、启动后，只有 Readiness 通过才会进入 Service 后端。Pod 处于 `Pending` 时尚未获得可运行资源；容器运行也不表示已具备接流量条件。
- **设备与协议层恢复**  
  设备发现 WebSocket 断开后重连、重新认证、恢复订阅；服务端从持久化存储恢复必要状态，并依靠消息 ID、序列号、确认记录实现幂等投递与去重。

因此，Readiness 表达的是“该实例现在可以接受请求”的平台信号，而不是“所有设备已重连、所有离线消息已补偿”的业务承诺。Kubernetes 可以维持三副本的容量目标；会话续接、消息至少一次或恰好一次语义、S3 持久化、设备确认与重试窗口，必须由 IM 协议和应用状态模型明确规定。

> **要点** — Kubernetes 维持的是声明副本与可用实例，不自动维持 Pod 内存、连接和业务确认语义。
