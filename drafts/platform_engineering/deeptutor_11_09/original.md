### 从慢查询到级联失稳

### 从慢查询到级联失稳

B 离线恢复后执行历史 `GET`，本应是“读取旧消息”的低风险路径，却可能成为级联故障的起点。设数据库一次历史查询耗时为 $s$，到达速率为 $\lambda$，服务并发能力为 $c$。当查询变慢时，单个请求占用连接、线程和数据库会话的时间上升，系统可承载的有效吞吐下降；一旦 $\lambda$ 接近或超过该吞吐，请求便开始排队。

失稳链路通常如下：

1. **数据库变慢**：索引失效、热点会话、磁盘抖动或大范围历史扫描，使 $s$ 增大。
2. **请求占用变长**：每个 `GET` 更久才释放应用工作线程、连接池槽位和数据库连接。
3. **排队放大尾延迟**：新请求不仅等待查询本身，还要等待前面积压请求完成；平均延迟与尤其是 P99 延迟迅速恶化。
4. **客户端超时重试**：客户端未在超时窗口内收到响应，便重发同一历史拉取请求。此时原请求往往仍在执行，重试不是替代，而是叠加。
5. **额外流量继续压慢数据库**：重试提高实际到达率 $\lambda'=\lambda+\lambda_{\text{retry}}$，队列更长、超时更多，形成正反馈。

可用简化关系理解风险：当利用率 $\rho \approx \lambda s/c$ 接近 $1$ 时，排队等待会非线性增长；重试使 $\lambda$ 上升，而慢查询使 $s$ 上升，两者共同把 $\rho$ 推向饱和。此时，即使单次慢查询只多出数秒，也可能演化为全体恢复客户端同时失败。

处置重点不是修改既有消息合同：`m-9`、`c-a`、`seq9` 保持固定，UTF-8 正文上限仍为 `4096B`，重复同 ID 仍为 `409`，非成员仍为 `404`，`200` 仍只表示服务端内存受理成功。尤其不能把一次历史请求或消息提交得到的 HTTP `200` 解释为 B 已收到设备侧送达。

要切断正反馈，应限制恢复并发与分页范围，为重试设置退避、抖动和总次数上限，并对数据库查询设置明确超时与隔离。目标是让超时请求停止继续制造负载，而不是让更多请求在已经拥塞的队列中等待。

### 区分意图、尝试与受理

### 区分意图、尝试与受理

设设备 B 离线后恢复，用户发起一次“补拉会话 `c-a` 中 `seq9` 附近历史”的**意图**。这一次意图应由稳定标识关联，例如消息 `m-9`、会话 `c-a`、序号 `seq9`；它不应因网络超时而变成多次业务操作。

但在慢数据库场景中，同一意图可能产生多次**请求尝试**：

1. 第一次 `GET` 查询历史，数据库变慢，请求长期占用连接或工作线程。
2. 客户端在超时阈值到达后并不知道服务端是否仍在处理，于是再次发起相同补拉。
3. 第二、第三次尝试又排队等待同一慢查询资源，积压进一步拉长超时。
4. 更多超时触发更多重试，形成“慢 → 堆积 → 超时 → 重试 → 更慢”的反馈环。

因此，应明确区分计数对象：

- **意图数**：用户希望补拉 `m-9/c-a/seq9` 的一次业务动作；
- **尝试数**：为完成该动作发出的第 $1,2,\ldots,n$ 次 HTTP 请求；
- **受理数**：服务端返回 `200` 并将请求或结果放入内存处理路径的次数。

`200` 只表示该次 HTTP 请求已被当前服务实例**内存受理**，并不证明设备 B 已收到历史，也不证明客户端已成功消费响应。设备可能仍断线、响应可能在链路上丢失、进程重启也可能丢失未持久化状态。

故重试必须围绕同一补拉意图做去重、限次与退避；不能把多个 `200` 误读为多次送达，更不能把一次 `200` 当作 `m-9` 已送达设备 B。

### 手算重试放大与积压

### 手算重试放大与积压

设 B 重连后需补拉固定历史批次 `m-9/c-a/seq9`，初始请求数为 $m=9$；每个请求超时后最多重试 $r$ 次，服务端可同时处理的历史查询槽位为 $C$。若数据库已变慢到每次查询都在客户端超时前未返回，则一次补拉的最坏尝试总数为：

$$
N_{\max}=m(1+r)
$$

例如固定“首次请求 + 2 次重试”，即 $r=2$：

$$
N_{\max}=9\times3=27
$$

这 27 次并不代表 27 条新消息：它们是对同一历史范围的重复读取。若客户端超时阈值为 $T$，而数据库实际响应时间为 $L>T$，则旧请求在客户端发起重试时往往仍占着服务端连接、数据库查询或线程槽位。单个原始请求最多可形成近似：

$$
I_{\text{单}} \le 1+r
$$

个同时在途尝试；9 个补拉并发启动时，最坏在途占用可逼近 $27$。当 $27>C$，超出的请求进入队列，初始积压约为：

$$
Q_0=\max(0,27-C)
$$

更危险的是，排队会继续拉长响应时间。设重试到达速率为 $\lambda$、慢数据库实际完成速率为 $\mu$，只要 $\lambda>\mu$，积压按近似速度增长：

$$
Q(t)\approx Q_0+(\lambda-\mu)t
$$

因此，“200 已内存受理”只说明本次 HTTP 写入被接受；它不等于 B 已送达，更不能据此无限缩短超时或追加重试。重复同 ID 仍应返回 `409`，非成员返回 `404`，而历史 GET 的慢响应必须通过限并发、退避和停止条件隔离，避免补拉把数据库拖入级联故障。

### 用截止时间守住身份合同

### 用截止时间守住身份合同

B 离线恢复时，历史 `GET` 可能因慢数据库长期占用连接与工作协程。应用层应为每次补拉设置明确截止时间，并将同一个 `context.Context` 传递到鉴权、成员校验和数据库查询；请求一旦超时，取消尚未完成的数据库操作，避免“客户端已放弃，服务端仍在排队”。

```go
ctx, cancel := context.WithTimeout(r.Context(), 800*time.Millisecond)
defer cancel()

if !isMember(ctx, roomID, userID) {
    write404(w)
    return
}
msgs, err := repo.ListHistory(ctx, roomID, beforeSeq, limit)
```

传播路径应是：

`HTTP 请求上下文 → 应用服务 → 成员关系查询 → 历史消息查询 → 数据库驱动`

不能在仓储层改用 `context.Background()`，否则 HTTP 超时仅停止响应写回，慢查询仍会继续占用数据库连接；也不要为每层各自叠加无关的长超时，最终截止时间应受入口请求预算约束。

截止时间只限制执行时长，不改变身份与消息合同：

- 固定会话 `m-9`、设备 `c-a`、序号 `seq9` 的鉴别规则不变。
- 非成员仍返回 `404`，不能因查询慢而泄露房间存在性。
- 重复同一消息 ID 仍返回 `409`，不能把超时后的重试误判为新消息。
- `S2/v1` 的 UTF-8 正文上限仍为每请求原始正文 `4096B`。
- `200` 仅表示服务端已在内存中受理，不表示设备 `c-a` 已送达。

对历史 `GET`，超时应成为可重试的暂时失败信号，并配合退避、抖动和并发限制；若每个超时请求立即重试，只会重新制造数据库积压。截止时间的目标不是“尽量等到成功”，而是在资源耗尽前终止无望工作，守住成员身份判定、幂等语义与受理边界。

### 恢复门与过载防线

### 恢复门与过载防线

B 离线恢复时，历史 `GET` 的慢查询不能靠“多重试几次”解决。它会把数据库延迟放大为连接占用、队列积压和超时风暴；因此各机制应分工，而非互相替代：

- **限流**：限制进入系统的恢复请求速率，例如按用户、会话或设备限制并发历史拉取数。它保护入口，避免瞬时重连潮直接打满数据库。
- **背压**：当历史查询队列、连接池或响应延迟超过阈值时，明确拒绝或延后新的补拉，并给出可重试时间。它把系统当前承载能力反馈给客户端。
- **隔离**：将在线发消息、历史补拉、推送追平使用不同的队列、连接池或并发额度。否则 B 的恢复流量会拖慢正常 IM 写入与实时收消息。
- **熔断**：数据库连续慢响应或错误率升高时，暂时停止向其发起昂贵的历史查询，快速返回“稍后恢复”，避免所有请求都等待超时。
- **退避**：客户端重试必须采用指数退避加随机抖动，例如 $1,2,4,8\text{s}$ 并加随机偏移；不能在超时后立即并发重发。

恢复流程应设置“恢复门”：B 先按游标拉取**权威历史**，确认已获得截至某一稳定位置的记录；再以该位置为起点订阅或查询增量，直到追平服务器当前高水位；最后才允许设备进入实时接收状态。固定消息 `m-9/c-a/seq9` 的重复提交仍返回 `409`，非成员仍为 `404`，原始正文仍受 `4096B` 限制，这些静态合同不因过载改变。

尤其要区分：`200` 仅表示服务端已在内存中受理该请求，不表示 B 已收到、更不表示已完成历史追平。恢复门关闭前，设备送达状态必须保持“未确认”。

> **要点** — 慢依赖下重试会放大负载；以截止时间、退避和恢复门保护权威历史，不能把受理成功误当送达成功。

当慢数据库遇上双层重试，新增的并非用户需求，而是被放大的请求尝试；先用可计算的上界看清队列为何会失控。

### 从用户意图拆分请求生命周期

### 从用户意图拆分请求生命周期

分析过载时，先固定统计单位：**用户意图**不等于**请求尝试**，更不等于**下游已完成请求**。

- **用户意图**：用户发起一次“补拉未来历史”的业务目标。即使客户端、网关多次重发，仍是同一个意图。设到达率为 $\lambda_I=100$ 意图/s。
- **请求尝试**：为完成该意图发出的某一次网络请求。客户端最多重试 2 次，即最多 3 次尝试；每次到网关后，网关又最多 3 次尝试。故一个意图在最坏情况下可变成 $3\times3=9$ 个下游请求。
- **成功结果**：下游真正处理完成并返回的结果。它应按完成量统计，而非按发起量统计；同一意图可能有多个重复尝试到达下游，但业务上通常只需要一个结果。
- **超时**：调用方在等待期限内未收到响应，并不证明下游没有执行。超时请求可能仍在数据库排队、执行或返回途中。
- **在途请求**：已经发送但尚未得到最终确认的尝试，包括网络传输、网关排队、数据库排队和执行中的请求。

因此，重试的触发条件往往是“未观察到成功”，而不是“确认失败”。若把超时误记为新业务需求，就会把 $100$ 意图/s 错看成 $900$ 个独立查询/s。正确表述应是：业务需求仍为 $100$ 意图/s，但在双层重试的上界假设下，下游**尝试到达率**可被放大至 $900$ 请求/s。

### 双层重试的九倍放大

### 双层重试的九倍放大

设用户每秒发起 $I=100$ 个“查询未来历史消息”的**意图**。意图表示用户真正想完成的一次业务操作；网络超时、服务端慢响应导致的再次发送，都不应被误认为新增需求。

客户端最多尝试 3 次，网关收到每一次客户端请求后，又最多向下游尝试 3 次。若所有尝试都因超时而触发完整重试链，单个意图对应的下游请求上界为：

$$
A_{\text{downstream/intent}}
= A_{\text{client}}\times A_{\text{gateway}}
=3\times3=9
$$

因此，下游数据库或历史服务实际看到的请求到达率上界为：

$$
\lambda_{\text{downstream}}
= I\times9
=100\times9
=900\ \text{请求/秒}
$$

这不是“900 个用户每秒都要查历史”，而是 100 个用户意图在两层独立重试策略下被放大后的**请求尝试数**。其中可能有请求已成功但响应尚未返回，也可能仍在数据库执行；客户端或网关仅因等待超时而又发起副本。

应明确区分四个量：

- **意图**：$100$ 次/秒，代表真实业务需求；
- **尝试**：最坏 $900$ 次/秒，代表下游收到的工作量；
- **成功**：真正完成并被上游确认的结果数；
- **超时或在途**：未及时得到响应的请求，不等于已经失败或已被取消。

九倍是一个最坏上界：它假设每层都耗尽三次尝试，且下游重复请求没有被去重、拒绝或取消。即使真实比例低于九倍，只要慢响应触发重试，额外尝试仍会继续占用本已紧张的下游容量。

### 慢数据库如何制造积压

### 慢数据库如何制造积压

设未来历史查询的用户意图到达率为 $100$ 次/秒。客户端最多重试 $2$ 次，因此一次意图最多产生 $3$ 次客户端尝试；每次尝试又经由网关，网关同样最多重试 $2$ 次，即最多向数据库发出 $3$ 个下游请求。于是最坏情况下：

\[
100 \times 3 \times 3 = 900\ \text{个数据库请求/秒}
\]

这里的 $900$ 是**请求尝试率**，不是新增的用户需求；用户仍然只有 $100$ 个意图/秒。慢数据库只能稳定处理：

\[
\mu=120\ \text{请求/秒}
\]

若系统没有限流拒绝、超时取消或主动丢弃，请求会持续进入数据库等待队列。每秒进入量与完成量之差，就是净积压速度：

\[
\Delta Q = 900-120=780\ \text{请求/秒}
\]

因此，哪怕该峰值只持续 $5$ 秒，队列也会额外堆积：

\[
Q(5)=780\times5=3900\ \text{个请求}
\]

这 $3900$ 个请求中，可能包含同一用户意图的多次重复尝试，以及已经对用户失去价值、却仍在数据库排队或执行的在途请求。数据库越慢，超时越多；超时越多，重试越密集，进入队列的尝试率越高，最终形成放大式积压。

### 超时未必等于请求消失

### 超时未必等于请求消失

客户端收到超时，并不表示这次历史查询已经从系统中消失。它通常只表示：客户端在自己的等待窗口内没有拿到响应。此时请求可能正处于不同阶段：

- 仍在网关排队，尚未转发；
- 已被网关转给下游，数据库连接正在等待；
- 数据库已经开始扫描消息记录、排序或分页；
- 数据库已完成计算，但响应正在网络链路上返回。

若客户端超时后立即重试，网关又有自己的超时与重试策略，就会出现时间错位：旧尝试仍在数据库执行，新尝试已经抵达数据库。对用户而言仍是同一个“补拉历史”的意图；对数据库而言，却是多个并发在途请求。

设一次查询的客户端等待上限为 $T_c$，而数据库实际执行时间为 $T_d$。当 $T_d>T_c$ 且取消信号未传播时，客户端在 $T_c$ 时刻放弃等待，但数据库仍可能继续工作到 $T_d$。这段 $T_d-T_c$ 的“无人等待执行”依然占用：

- 数据库连接与工作线程；
- CPU、磁盘读取和缓存；
- 排序、分页等查询算子资源；
- 下游队列中的服务能力。

因此，超时是观察者的结论，不是下游工作的终止命令。只有将取消信号沿客户端、网关、数据库驱动一直传播，并让数据库能够中断查询，超时后的旧尝试才会真正释放容量。否则，重试会与未取消的旧请求重叠，使在途量持续攀升。

### 用可观测指标识别放大起点

### 用可观测指标识别放大起点

先把“用户想查一次历史”与“系统实际发了多少次请求”分开统计。过载时，流量图上的陡增未必意味着用户需求增长，往往是超时触发的重试在放大。

建议按同一查询链路持续观测：

- **意图数**：进入客户端或业务层的原始查询数，例如 $100$ 个用户意图/s。它是需求基线，应使用稳定的 `intent_id` 去重。
- **尝试数**：每次实际发出的下游调用都计数，包括首次与重试。计算放大倍数  
  $$A=\frac{\text{尝试数}}{\text{意图数}}$$  
  若双层各最多 3 次尝试，理论上界为 $A=9$。
- **重试层级与原因**：分别记录客户端重试、网关重试、服务端内部重试，以及超时、连接失败、限流、5xx 等触发原因。否则只能看到“请求变多”，却不知道放大从哪一层开始。
- **成功率与超时率**：成功应区分“最终意图成功”和“单次尝试成功”。最终成功率可能暂时很高，但尝试超时率已上升，正是重试风暴的早期信号。
- **在途量与队列长度**：记录各层并发在途请求、数据库连接池占用、消息/任务队列长度及其增长斜率。若下游能力 $120$/s、实际到达 $900$/s，则队列净增长约 $780$/s；在途量持续不回落说明旧请求尚未取消，新重试又不断叠加。

定位时沿链路比较相邻层的“尝试数/意图数”。某层该比值先升高，同时超时率、在途量和队列长度上升，该层通常就是正反馈的放大起点。

> **要点** — 重试只会增加尝试，不会增加用户意图；双层三次尝试可将100意图/秒放大为900下游请求/秒，并迅速形成积压。

端到端截止时间不是“超时后报错”而已：它要沿调用链约束工作预算，并在失败后守住消息身份与恢复边界。

### 从用户等待预算到统一截止时间

### 从用户等待预算到统一截止时间

一次历史补拉的时间预算应从用户可接受的等待上限出发，而不是由设备、接口、数据库分别设置“各等一会儿”。例如客户端最多等待 $8\text{s}$，则请求进入服务时就应携带一个绝对截止时间；鉴权、消息范围计算、数据库分页查询、下游存储访问都只能消耗这同一预算。

在 Go 中，可将入口请求的 deadline 传入 `context.Context`，并继续向所有依赖调用传播：

- 入口若没有截止时间，服务可按合同补充一个默认上限；
- 子调用使用父 `context`，不得脱离它改用 `context.Background()`；
- 可为子步骤预留回包、序列化和降级空间，因此数据库查询的实际超时应早于总截止时间；
- 调用前检查剩余时间；若预算已不足以完成一次查询，应立即返回，而非启动注定无用的工作。

```go
ctx, cancel := context.WithTimeout(req.Context(), 8*time.Second)
defer cancel()

rows, err := repo.LoadHistory(ctx, stableUserID, cursor)
```

`ctx.Done()` 能让仍在等待锁、连接池、数据库响应或下游 RPC 的工作尽快停止，避免用户早已放弃后，补拉请求仍持续占用连接、CPU 与热点分区。但取消不是“时光倒流”：已经发往消息队列、已提交到数据库、或已被依赖接收的操作不会因 deadline 自动撤销。

因此，截止时间解决的是**继续投入资源**的问题，不解决已提交操作的幂等与状态确认问题。后续重试必须带同一稳定身份，并先依据状态判断此前请求是否已经生效；不能因为等待超时就换一个新 ID 再提交一次。

### 在Go调用链传播context

### 在 Go 调用链传播 `context`

端到端 `deadline` 必须进入请求根 `context`，再由处理函数逐层传递，而不是在每一层重新随意设置超时。入口可从 HTTP 请求取得：

`ctx := r.Context()`

若网关已把剩余预算转换为请求截止时间，`ctx.Deadline()` 即可成为本次历史补拉的统一停止边界。业务层应显式接收 `ctx`：

`func PullHistory(ctx context.Context, req PullRequest) error`

调用数据库、缓存、RPC、对象存储时，将同一个 `ctx` 传入支持取消的接口，例如 `QueryContext`、`ExecContext`、`http.NewRequestWithContext`。这样客户端断开、上游超时或预算耗尽时，`ctx.Done()` 会关闭；等待数据库连接、执行查询、读取下游响应等可中止工作应尽快返回 `context.Canceled` 或 `context.DeadlineExceeded`。

局部操作确有更小预算时，只能从父 `ctx` 派生：

`dbCtx, cancel := context.WithTimeout(ctx, 800*time.Millisecond)`

并立即 `defer cancel()`。子截止时间不得晚于父截止时间；更不能使用 `context.Background()` 脱离请求链，否则历史补拉即使已无用户等待，仍可能继续占用连接、扫描大量消息并放大过载。

处理函数还应在昂贵循环、分页和批量写入间检查取消信号：

`select { case <-ctx.Done(): return ctx.Err(); default: }`

但取消只会请求停止，不能自动撤销已经提交的副作用。若 S2 `POST` 已把消息写入服务端、响应却丢失，客户端即使因 deadline 退出，也必须以原稳定消息 ID 重试；收到 `409` 后查询状态确认结果，而不是换新 ID 再发一次。

### 截止时间停止无用工作而非撤销提交

### 截止时间停止无用工作而非撤销提交

端到端截止时间应通过 Go 的 `context.Context` 沿调用链传播：网关、业务逻辑、数据库查询、历史补拉和下游 RPC 都应检查 `ctx.Done()`。当预算耗尽时，服务应尽快停止尚未开始或仍可中断的工作，释放连接、协程、查询槽位与队列容量，避免重试流量继续放大过载。

但必须区分三个彼此独立的状态：

- **客户端超时**：客户端没有在自己的等待窗口内收到响应，只能说明“结果未知”。
- **服务端取消**：服务端观察到 `context` 已取消，可能停止后续计算；也可能请求已越过不可中断边界。
- **存储已提交**：消息写入、事务提交或事件发布已经成功。此后即使响应在网络中丢失，取消也不能自动回滚该提交。

例如，客户端发送 `POST /messages`，服务端以消息 ID `m-123` 完成写入，但响应包丢失。客户端看到超时，不应推断“消息未写入”，更不能换一个新 ID 再发，否则可能制造两条语义相同但身份不同的消息。

正确恢复方式是使用同一稳定消息 ID 重试。若合同规定重复提交返回 `409` 且不覆盖原消息，则 `409` 表示该身份已被占用，而非可随意覆盖的失败；客户端应进一步查询该 ID 的状态、内容摘要或版本，确认已提交结果。`400`、`404`、`409` 都不是盲目重试信号：它们分别可能意味着请求无效、资源不存在或身份冲突，必须按明确的恢复分支处理。

### 响应丢失后的同ID安全重试

### 响应丢失后的同ID安全重试

设客户端向历史服务提交补拉任务：

`POST /messages/{messageID}`

请求已到达服务端，服务端也可能已经成功持久化消息；但在响应返回途中，客户端连接因截止时间到期、网关断连或网络抖动而失败。此时客户端看到的是“没有响应”，而不是“服务端没有执行”。

正确恢复方式是使用**同一个稳定消息 ID**重试，而不是生成新 ID：

1. 首次请求：`POST /messages/m-123`，客户端未收到响应。
2. 重试请求：仍发送 `POST /messages/m-123`。
3. 若首次已成功，当前合同返回 `409 Conflict`，并且**不得覆盖**已有消息。
4. 客户端随后查询 `GET /messages/m-123`，根据状态确认消息是否已创建、是否仍在处理、是否已完成或失败。

这里的 `409` 不是“再试一次就会成功”的瞬时错误，而是身份冲突信号：该 ID 已经代表一条既有业务事实。把它当作成功的替代响应之前，仍应查状态，因为冲突对象可能是已完成消息，也可能是先前创建但尚未处理完的消息。

```text
POST m-123 → 响应丢失
POST m-123 → 409，不覆盖
GET  m-123 → 确认真实状态
```

不要因响应丢失而换用 `m-124`。新 ID 会绕开幂等边界，可能把同一段历史补拉写入两次；在过载期间，这类重复任务还会放大队列、重试和下游读取压力。对于 `400`、`404`、`409` 等明确的合同性响应，也不应盲目重试；应先依据稳定身份查询状态，再决定恢复动作。

### 按错误语义停止重试并进入恢复门

### 按错误语义停止重试并进入恢复门

重试不是默认动作，而是对错误语义的判断。客户端收到响应或本地截止时间到达后，必须先区分“请求是否可能已被服务端接受”与“继续发送是否会改变状态”。

- `400` 表示请求不符合合同：字段、签名、游标、消息格式或状态前置条件错误。原样重试只会重复无效负载；应记录可诊断信息，修正请求或升级客户端版本。
- `404` 表示目标资源、会话或历史锚点不存在。不要立刻改用新消息 ID 再发；应进入恢复门，核验该资源是否已过期、被迁移，或本地状态是否落后。
- `409` 表示稳定身份下的冲突，例如同一消息 ID 已存在、版本不匹配或幂等键对应的请求摘要不同。按当前合同，`S2 POST` 响应丢失后以**同一 ID**重试，服务端返回 `409` 时不得覆盖已有消息，也不得改造为新 ID 重新提交。

此时恢复门的职责是“查明事实”，而不是“尽快再试”：以消息 ID、会话 ID 和可信游标查询权威历史，确认远端是否已持久化该消息；随后按权威顺序补拉缺口，并让设备从已确认位置追平。只有恢复策略明确判定原请求未被接受，才允许在既定身份规则下重新投递。

过载拒绝、限流后的退避参数，以及大规模历史核验与设备追平的调度，属于后续恢复策略的评审范围；本层先保证：`400/404/409` 不触发盲目重试，不用新 ID 制造重复，更不以覆盖冲突来伪造成功。

> **要点** — 截止时间约束工作预算；稳定消息ID守住幂等边界；超时后查状态，不以新ID重发制造重复。

以千台设备同时重连补拉历史为病例，分析突刺如何经重试放大，并建立可恢复、可控量的追平机制。

### 重连突刺与排队起点

### 重连突刺与排队起点

设有 1000 台设备因网络切换、服务重启或令牌刷新而在同一时刻重连。每台设备都立即发起一次“补拉历史”`GET`，则入口面对的不是“未来十秒平均每秒 100 个请求”，而是近似同时到达的 1000 个请求。

平均到达率只是事后统计量：

\[
\bar{\lambda}_{10s}=\frac{1000}{10}=100\ \text{请求/秒}
\]

它不能约束任意短时间窗内的峰值。若请求集中在首个 100 ms 到达，则瞬时等效到达率约为：

\[
\lambda_{0.1s}=\frac{1000}{0.1}=10000\ \text{请求/秒}
\]

这正是排队的起点。假设网关、历史查询服务或数据库在该路径上的稳定处理能力为 $\mu=300$ 请求/秒，那么即使后续没有新增流量，首批请求也会形成约 700 个请求的积压；若单次历史拉取还要读取多页消息、访问索引和消息存储，实际消耗的并非一个轻量 `GET`，而是一串下游工作。

因此，容量评估不能只问“1000 个请求能否在 10 秒内处理完”，还必须问：

- 同一毫秒内可能有多少设备开始补拉；
- 入口并发、连接池、线程池和下游查询槽位各能吸收多少；
- 排队等待是否会先触发客户端超时；
- 超时后的重试是否会在队列尚未排空时再次注入流量。

“十秒内均匀分散”只能作为理想情形，不能作为系统前提。重连事件天然具有相关性：同一机房断网、同一版本发布、同一推送通道故障，都会让设备在相近时刻恢复。若不主动打散到达时间，系统看到的首先是突刺，其后才是平均值。

### 重试为何形成正反馈

### 重试为何形成正反馈

设 1000 台设备断线后同时补拉历史。若每台仅发起一次 `GET /history`，后端瞬时面对 1000 个请求；即使理想地在 10 秒内均匀分散，平均也只是 $100\ \text{req/s}$，但“同时重连”并不保证这种均匀性。

过载闭环通常从一次变慢开始：

1. 数据库连接、磁盘或索引查询变慢，单请求服务时间从 $s$ 增长到 $s'$。
2. 到达率 $\lambda$ 不变而服务率 $\mu=1/s'$$ 下降；当 $\lambda>\mu$ 时，请求队列持续积压。
3. 排队时间加入数据库处理时间，使端到端延迟超过客户端超时阈值。
4. 客户端将“未及时响应”视为失败，发起重试；原请求可能仍在数据库执行，于是重试并非替代，而是新增负载。
5. 新增负载进一步降低 $\mu$、拉长队列，触发更多超时，形成正反馈。

若初始有 1000 个请求，超时后全部重试 3 次，则最多尝试数为：

$$
N_{\text{attempt}}=1000\times(1+3)=4000
$$

若每轮仅有 $50\%$ 请求超时并重试，连续 3 轮仍会产生：

$$
1000+500+250+125=1875
$$

这 875 个额外尝试没有带来新的历史数据需求，却竞争同一组网关连接、线程池、数据库连接和消费者吞吐。更危险的是，多层同时重试：客户端重试、网关转发重试、消费者拉取重试若各做 2 次，理论放大可达 $2^3=8$ 倍。

因此，超时不应直接等价于“请求没有执行”。在拥塞期间，它更常表示“结果尚未返回”；盲目重试会把等待中的工作复制成更多工作，使原本可恢复的慢查询演变为级联故障。

### 意图、尝试与消息身份

### 意图、尝试与消息身份

一次“设备追平”是**业务意图**：设备从本地游标 `cursor` 补到服务端最新历史；而一次 `GET /history` 只是该意图下的一次**请求尝试**。网络超时、网关 `502/503/504`、限流 `429` 都可能让同一意图产生多次尝试。若把每次尝试都当成新任务，重连风暴会同时制造重复拉取、重复投递和重复消费。

应为追平意图分配稳定的 `sync_intent_id`，并在所有重试中保持不变；每次请求另带递增的 `attempt_no`。服务端据此区分“同一意图重发”与“新的补拉任务”，日志、限额和重试预算也应按意图聚合，而非按请求计数。

是否重试取决于错误语义：

- `429`、`503`、连接失败、可确认的超时：通常可在退避与抖动后重试，并遵守 `Retry-After`。
- `400`、鉴权失败、游标格式错误、权限拒绝：重试无效，应终止并刷新身份或修复状态。
- 超时但服务端可能已成功响应：不能假设失败；应以稳定游标、请求身份或幂等读取结果确认进度。

消息也必须有稳定身份，如 `message_id` 或单调递增的 `sequence`。消费者以“已处理的最大连续序号”或去重表提交进度，而不是按收到次数计数。这样即使历史页重复返回、网关重复转发，客户端仍可安全丢弃已消费消息；续传依据最后确认的消息身份，而非不可靠的本地时间。

### 退避、抖动与全局预算

### 退避、抖动与全局预算

重连后的历史补拉不能简单地“失败就立即再试”。若 1000 台设备同刻发起 `GET /history`，即使设计为 10 秒内均匀分散、平均仅 $100/s$，同步定时器、相同超时和相同退避序列仍会让请求在某几个时刻重新对齐，形成尖峰。

对一次补拉意图，采用带抖动的指数退避：

$$
d_n=\min(d_{\max},d_0\cdot 2^n),\qquad
w_n\sim U(0,d_n)
$$

其中 $d_0$ 可取 200～500 ms，$d_{\max}$ 取数秒；第 $n$ 次失败后等待随机的 $w_n$，而非固定等待 $d_n$。全随机抖动能打散“第 1 次一起失败、第 2 次一起重试”的波峰。服务端返回 `Retry-After` 时，应优先遵从该值，并在其附近再加入小幅随机量。

更重要的是限制**一次意图**，而不是只限制单个网络请求。例如“补齐设备 A 的某段历史”最多尝试 3～5 次，超过上限即记录可恢复游标，转入延迟队列或等待下一轮同步；不能因分页、连接重建或 SDK 自动重试而重新获得完整次数。

还要设置**进程级重试预算**：例如每个进程每秒最多允许 20 次额外重试，或仅允许失败请求中的 10% 消耗重试令牌。预算耗尽时快速失败、排队或降级，避免故障期间重试流量反而超过正常业务流量。

多层链路必须明确“谁负责重试”：

- 客户端重试连接或低成本、幂等的历史读取；
- 网关只在明确可重放且未透传重试的场景重试；
- 消费者对消息处理重试，但不应反向触发同一历史拉取；
- 下游已返回 `429`、过载、熔断或身份失效时，上层不得继续叠加重试。

`超时`、连接中断等结果不代表请求未执行；只有带稳定请求身份、幂等键或可比较游标的 `GET` 补拉才适合自动重试。认证失败、权限拒绝、参数错误应立即停止；`429` 和 `503` 则应进入受预算约束的延迟重试。

### 分层保护与恢复门

### 分层保护与恢复门

面对同刻重连的历史补拉，四种机制解决的是不同位置的问题，不能互相替代：

| 机制 | 保护位置 | 主要作用 | 不足 |
|---|---|---|---|
| 限流 | 网关、历史服务入口 | 将历史 `GET` 限为每设备、每租户、全局配额 | 只削峰，不能阻止下游积压 |
| 背压 | 消费者、队列、数据库写入端 | 以积压、延迟、并发槽位反向压低拉取速度 | 必须让客户端接受“稍后再拉” |
| 隔离 | 租户、设备组、历史读取池 | 防止补拉流量挤占实时消息、关键租户资源 | 资源池过小会延长恢复时间 |
| 熔断 | 历史库、依赖服务调用侧 | 错误率或延迟越阈值时快速拒绝，避免无效重试 | 熔断后必须有受控恢复路径 |

恢复门应以**权威历史存储**为准，而非设备本地“我已恢复”的声明。设备重连后先提交身份、租户、最后确认游标和待补区间；服务端校验游标连续性，并按当前全局负载发放短期“追平令牌”。令牌规定最大时间窗、分页大小、并发数与下次允许请求时间。

可将设备按一致性哈希或租户分桶，分批放行：例如每秒仅准入 $N$ 个设备，每台最多并发 1 个历史页；实时通道优先，补拉仅消费剩余容量。若历史库延迟升高、消费者积压扩大或错误率超阈值，恢复门立即收紧：暂停新准入、缩小页大小、延长令牌间隔；已获准设备完成当前页后退避。这样恢复过程由“千台同时抢救”转为可观测、可暂停、可逐批追平的队列。

> **要点** — 重试不是免费恢复手段；必须以身份、预算、抖动和分层准入约束追平流量。

当慢数据库触发历史补拉重试时，系统必须先保护权威写入，再让设备以可控速度追平，避免队列、连接和工作协程共同失控。

### 两类流量与两套资源边界

### 两类流量与两套资源边界

不要把所有消息都送进同一条队列、同一组连接和同一批工作协程。IM 在故障期至少应区分三种可靠性等级：

- **权威写入**：例如消息 `m-9` 的落库、顺序号分配、会话游标推进。这是事实来源，必须先持久化再确认；不能因下游慢、通知失败或补拉积压而被丢弃。
- **历史补拉**：设备按游标请求缺失消息，可重试但天然具有放大效应。一台设备反复请求会同时占用数据库连接、查询槽位、序列化 CPU 和网络带宽。
- **可丢通知**：如“有新消息”“会话更新”推送，只是唤醒信号。投递失败可合并、延迟或丢弃，前提是客户端仍能凭游标从权威历史补齐。

因此应建立两套主要资源边界：

1. **写入资源池**：独立的入口配额、持久化队列、数据库连接池与工作协程；队列必须有界，接近上限时优先入口拒绝或短暂限流，而非无限堆积。
2. **补拉资源池**：独立的查询并发、每用户/设备速率限制、分页上限和响应带宽；补拉耗尽自身预算时，只延迟该设备追平，不能挤占写入资源。

通知最好再使用独立的低优先级队列：满了就丢旧通知、做去重或合并。例如同一会话连续产生十条“有更新”事件，保留一次唤醒即可。关键不在于“通知必达”，而在于客户端可验证地获得权威历史；反之，若 `m-9` 尚未成为可补拉的权威记录，就绝不能把它当作可丢通知处理。

### 有界队列与入口拒绝

### 有界队列与入口拒绝

设历史补拉任务以速率 $\lambda$ 到达，后端以速率 $\mu$ 完成处理，队列容量为 $K$。队列长度 $Q(t)$ 的基本演化为：

$$
Q(t+\Delta t)\approx \min\{K,\;Q(t)+(\lambda-\mu)\Delta t\}
$$

当 $\lambda<\mu$ 时，系统有机会消化积压；当数据库变慢、连接池收缩或重试放大使 $\lambda\ge\mu$ 时，积压会持续增长，并在约

$$
T_{\text{满}}\approx \frac{K-Q(0)}{\lambda-\mu}
$$

后填满队列。无界队列并未解决过载，只是把失败从“立即拒绝”延后为内存膨胀、排队超时、协程堆积和全局雪崩。

因此，补拉队列必须有容量上限，并与权威写入使用独立的队列、连接池和工作协程。即使补拉洪峰填满其队列，也不能挤占权威消息 `m-9` 的写入资源。

队列满时，正确动作是快速返回“稍后重试”或下发带退避时间的延期结果，而不是：

- 无限阻塞入口线程，导致连接与协程耗尽；
- 接收请求后静默排队，制造不可观测的长尾；
- 盲目扩容消费者，把慢数据库进一步压垮；
- 丢弃权威写入，只为保留历史补拉请求。

入口拒绝应携带可执行的恢复语义：例如 `retry_after=30s`、分段游标或较小批量上限。这样设备以受控速率重试；服务端则将可接受到达率限制在 $\lambda_{\text{admit}}\le\mu_{\text{safe}}$，把过载从内部资源竞争转化为显式、可退避的边界协议。

### 慢消费者的隔离与背压

### 慢消费者的隔离与背压

慢消费者不是“处理得慢”这么简单：若其持续占用补拉连接、解码协程和内存队列，就会把本应服务于权威写入与正常设备追平的共享资源耗尽。隔离的目标是让某台设备落后，而不是让全体设备一起不可用。

- **每设备有界队列**：为设备 `d` 维护独立待发送队列 `Q_d`，设置消息数和字节数上限，例如 `maxMsgs=500`、`maxBytes=4MB`。入队前检查容量；达到上限时，不再无限堆积实时通知，而是记录该设备的最高已见游标 `cursor_d`，将其标记为“需要补拉”。
- **共享资源配额**：补拉任务不能按设备数无限并发。使用全局信号量限制总补拉数 `G`，再设置租户、连接或设备级配额 `g_t`、`g_d`。典型约束为  
  $$
  \sum_d \mathrm{inflightPull}_d \le G,\qquad \mathrm{inflightPull}_d\le1
  $$
  同一设备通常只允许一个补拉执行，避免多个重试并发读取同一段历史。
- **公平调度而非先到先得**：从“待补拉设备集合”轮询取任务，每轮只发放有限令牌。大批积压设备不能长期霸占队列，使刚落后的设备也有机会恢复；对反复超时的设备增加退避时间，而非提高优先级。
- **取消必须向下传播**：用户离线、连接替换、请求超时或熔断打开时，应取消该设备的补拉上下文。取消信号需传到数据库查询、分页读取、网络发送和排队等待处；否则表面任务已结束，后台仍持有连接与协程。

队列满时可丢弃**可再生通知**，例如“有新消息”“未读数变化”，随后由设备按游标补拉；但不能丢弃权威消息 `m-9`，也不能伪造“已送达”。正确语义是：通知可能缺失，权威历史仍完整，且客户端拥有经过授权的补拉路径。这样，慢消费者只承担自己的追平成本，不会把共享补拉资源拖入级联过载。

### 熔断状态与小量探测

### 熔断状态与小量探测

熔断器不是“出错就重启”的开关，而是根据下游健康度改变请求准入策略，避免历史补拉把已经变慢的数据库、缓存或消息服务彻底压垮。

| 状态 | 请求策略 | 适用含义 |
|---|---|---|
| 关闭（closed） | 正常转发请求，但持续统计超时率、错误率与排队时长 | 下游基本健康；权威写入与历史读取仍应使用独立连接池、并发额度和队列 |
| 打开（open） | 快速拒绝或走降级，不再向故障下游发送常规请求 | 下游已明显失效；补拉请求应返回“稍后重试”并携带退避时间，不能无限阻塞工作协程 |
| 半开（half-open） | 仅放行极少量、受控的探测请求 | 用真实结果验证恢复情况；探测成功才逐步恢复，失败则立即回到打开状态 |

半开状态最危险的误用是“一次成功即全量放开”。例如数据库刚恢复一个连接，若立即释放积压的数万条历史补拉，连接池、磁盘和查询队列会再次饱和，形成二次熔断。应限制探测并发，例如仅允许 $1\sim 5$ 个请求，优先选择小范围、可取消的历史查询，并设置严格超时。

探测连续成功后，也应采用阶梯式扩容：`1 → 5 → 20 → 正常额度`，每一级观察延迟、错误率和队列增长。探测失败、超时或延迟重新恶化时，立即重新打开熔断器并延长冷却时间。

打开期间允许丢弃可再生成的降级通知；但不得丢弃权威消息 `m-9`。权威写入应继续进入其受保护的持久化路径，而历史补拉仅在权限校验通过、权威历史仍可取得时延后执行。

### 恢复门与不可丢消息

### 恢复门与不可丢消息

设消息 `m-9` 已被权威写入历史库，但实时通知因队列拥塞无法立即送达设备。此时可以降级“通知”，却不能降级 `m-9` 的权威存在性与可恢复性：

- **权威写先提交**：`m-9` 必须先获得持久化序号、会话归属和提交确认；只有提交成功，才允许返回“已发送”或进入后续通知流程。
- **通知允许丢弃或合并**：拥塞时可丢弃“有新消息”推送、合并多个未读提醒，甚至只保留最新水位；但不能把通知失败解释为消息写入失败，更不能删除 `m-9`。
- **恢复门控制补拉**：设备携带已确认游标 `cursor=8` 请求补拉时，系统验证其会话成员资格、访问权限与游标范围，再返回 `(8, current]` 中包含 `m-9` 的分页结果。无权限设备只能得到拒绝，不能借恢复接口枚举历史。
- **可续传而非无限重试**：返回结果带连续序号或不可变消息 ID；客户端仅在成功落盘后推进确认游标。若网络在收到 `m-9` 后中断，下一次仍从旧游标补拉，重复项按 ID 幂等去重。
- **恢复门限流**：补拉使用独立的有界队列、连接池和并发配额。队列满时返回“稍后重试”及建议退避，而非阻塞权威写协程；`half-open` 状态只放行少量补拉探测，确认存储恢复后再逐步扩大额度。

因此，降级的对象是“提醒路径的及时性”，不是消息事实本身。只要 `m-9` 已进入权威历史，且合法设备始终能依据游标验证、分页、续传地取回它，实时通知暂时缺失就不会演变为不可恢复的数据丢失。

> **要点** — 用有界入口、流量隔离和半开探测限制故障扩散；宁可延后补拉，也不能牺牲权威消息与写入能力。

以一次设备重连补拉为时间线，追踪慢数据库如何经等待、超时与重试演化为全链路级联故障，并建立先止血、后恢复的处置框架。

### 从慢查询到排队：故障时间线

### 从慢查询到排队：故障时间线

设备重连后的历史补拉通常不是单点请求，而是“会话恢复 → 消息索引查询 → 分页读取 → 下发历史”的链路。故障初期应按时间站点记录每层的到达、完成、拒绝、等待与重试，而非只看平均延迟。

- **T0：数据库查询变慢。** 索引缺失、热点分区、锁等待或存储抖动使单次查询耗时从 $L_0$ 升至 $L_1$。若服务并发槽位为 $c$，其近似处理能力从 $\mu_0=c/L_0$ 降为 $\mu_1=c/L_1$；即使请求到达率 $\lambda$ 未变，也可能出现 $\lambda>\mu_1$。
- **T1：应用层开始等待。** 新到补拉请求进入连接池、线程池或数据库连接池队列。此时“到达量”仍高、“完成量”下降、“拒绝量”可能仍为零，但排队长度和等待时间持续上升。最危险的信号是运行中请求数长期贴近并发上限。
- **T2：服务能力被慢请求占满。** 每个未完成查询持续占用工作线程、连接及内存；短请求也被迫排在长请求后。平均延迟上升只是表象，关键是分位延迟、队列等待和连接池占用率同步恶化。
- **T3：入口开始拒绝或超时。** 队列达到上限后出现限流、连接获取失败或网关超时。若仅因拒绝增多而使已完成请求的延迟下降，并不表示恢复：用户成功率与有效完成量仍可能下降。
- **T4：慢端扩大影响面。** 客户端收到超时后重连或重复补拉，形成新的到达峰值；慢设备长期占用会话和下行资源，使数据库侧的初始变慢演化为全链路排队。

因此，每站至少对照记录：`到达率、完成率、拒绝率、队列等待、在途数、依赖耗时`。当完成率低于到达率时，积压已在生成；等待比拒绝更早揭示服务能力正在耗尽。

### 重试正反馈与放大倍数

### 重试正反馈与放大倍数

一次“补拉历史”的**用户意图**，不等于一次后端请求。设用户意图到达率为 $\lambda_0$，客户端最多尝试 $c$ 次；每次客户端请求进入服务端后，服务端又最多尝试访问数据库 $s$ 次。若所有尝试都因超时而未被及时确认，则最坏情况下：

- 网关/服务端入口请求率：$\lambda_{\text{入口}}=\lambda_0 c$
- 数据库尝试率：$\lambda_{\text{DB}}=\lambda_0 c s$
- 相对原始意图的最大放大倍数：$A=c s$

例如，设备每秒发起 $100$ 个补拉意图，客户端“首次+重试两次”，即 $c=3$；服务端“首次+重试一次”，即 $s=2$。数据库看到的并非 $100$ 次，而可能是：

$$100\times 3\times 2=600\ \text{次/秒}$$

这里的关键不是“重试次数多”，而是**超时不等于请求未执行**。DB 变慢后，原请求可能仍在排队、持锁或执行；客户端因等待超过超时阈值再发一次，服务端也可能对同一逻辑查询重试。于是同一用户意图对应多个并发中的副本，旧请求尚未结束，新请求已继续占用连接、线程和 DB 容量。

若数据库实际完成能力为 $\mu$，而重试后的到达率 $\lambda_{\text{DB}}>\mu$，积压以近似速度增长：

$$\frac{dQ}{dt}\approx \lambda_{\text{DB}}-\mu$$

积压增大又会拉长等待时间，使更多请求跨过超时线；更多超时触发更多重试，形成正反馈。应逐站分别记录“意图数、请求尝试数、完成数、超时数、拒绝数、重试数”，避免只看成功请求延迟。若延迟下降只是因为大量请求被拒绝，用户补拉成功率和端到端 SLI 仍可能继续恶化。

### 指标不能只看延迟下降

### 指标不能只看延迟下降

过载期间，延迟下降可能是“请求不再被处理”，而非系统恢复。例如限流、连接耗尽或队列丢弃后，留在系统中的少量请求更快完成，$p99$ 延迟下降；但更多用户得到超时、拒绝或空结果。

因此，SLI 应按**用户结果**而非单一服务耗时定义，并同时观察：

- **结果分布**：成功、业务失败、超时、被拒绝、取消、降级响应的比例。成功率应以入口总请求为分母，而不是以“进入数据库的请求”为分母。
- **拒绝与丢弃**：网关限流、线程池拒绝、队列满、连接池获取失败分别计数。若延迟下降同时拒绝率上升，属于止血，不是恢复。
- **排队时长**：记录请求在网关、任务队列、连接池、数据库执行前的等待。执行耗时稳定而端到端耗时恶化，通常说明瓶颈在等待与资源争用。
- **连接占用**：连接池使用率、等待者数量、长连接比例、重连速率。连接接近满载时，小幅慢查询即可放大为全局阻塞。
- **依赖健康度**：数据库的执行延迟、锁等待、活跃连接、错误码，以及下游调用的超时和重试率；还要区分“依赖变快”与“调用量被拒绝后下降”。

可将恢复判定写成联合条件：入口成功率回升、拒绝率回落、排队时长缩短、连接占用脱离饱和，且依赖在正常负载下稳定。只有这些指标同时改善，才能说明补拉链路真正恢复，而不是通过牺牲用户请求换来了更低延迟。

### 先阻断生成器：限额、退避与隔离

### 先阻断生成器：限额、退避与隔离

故障扩散时，首要目标不是“尽快补完历史”，而是停止把已拥塞的依赖继续推向超载。应将补拉、实时收发、登录重连等流量分开计量，并对每类流量设置独立预算。

- **限流**限制请求进入速率，适合控制设备重连后瞬时发起的大量历史查询。限的是“到达量”，但无法避免已进入系统的请求长期占用连接。
- **背压**把下游容量不足显式反馈给上游：队列满、令牌耗尽或依赖变慢时，暂停继续生成补拉任务。背压应落在任务生成处，而非仅在数据库前拒绝。
- **并发隔离**为补拉设置独立 worker 池、连接池和队列上限，避免其耗尽实时消息的 goroutine、DB 连接与带宽。实时链路可降级，权威写入链路必须保留容量。
- **熔断**用于依赖已明显失效时快速失败；它不是永久拒绝，而是以半开探测恢复。熔断打开后应停止重试生成，不能让“快速失败”反而变成更高频重试。

Go 调用链必须传播同一个截止时间，而非每层重新给完整超时：

`ctx, cancel := context.WithTimeout(parent, budget)`

下游仅使用该 `ctx`；若剩余时间不足以完成一次查询，就直接返回可重试或降级结果。重试应限制为有限次数，并采用指数退避加随机抖动；仅对网络瞬断、明确的过载响应等可恢复错误重试，不能对超时、取消、参数错误盲目重放。

补拉任务需保留稳定的 `message_id`、会话/设备标识、历史游标和尝试次数。重试只重放同一身份的任务，服务端据此去重并推进游标，避免超时后生成新的补拉请求而重复扫描同段历史。监控中同时看拒绝率、重试生成率、队列长度和最终用户成功率：若延迟下降只是因为拒绝增多，系统并未恢复。

### 恢复权威历史与设备追平

### 恢复权威历史与设备追平

止血后不能立即放开全量重连。恢复门应以**权威历史**为唯一真相：设备本地缓存、推送序号和临时消息队列只能用于定位缺口，不能据此直接判定“已追平”。服务端先确认会话的权威水位，例如每个会话的最大连续消息序号 $H$；客户端提交已确认游标 $C$，仅补拉区间 $(C,H]$。

补拉接口应具备以下约束：

- **可恢复游标**：响应返回 `next_cursor`，游标绑定会话、历史版本和过期时间；客户端崩溃、切网或限流后可从该点继续，而非重拉整段。
- **小页分批**：按条数与字节数双重截断，如每页最多 100 条或 256 KiB。客户端完成一页、持久化并确认后，才申请下一页。
- **服务端配额**：对用户、设备、租户分别限制并发补拉数、页速率和总字节预算；超额返回明确的“稍后继续”结果，而不是让请求在连接池中等待超时。
- **渐进放量**：先恢复少量设备或较短缺口，再按数据库完成率、拒绝率、连接占用和历史读取延迟扩大令牌池。慢端重连必须经过同一限额器。
- **幂等追平**：消息以稳定消息标识去重；客户端仅在连续区间落盘后推进 $C$。收到重复页可安全覆盖或跳过，不能把“收到”误作“确认”。

“追平”应定义为：客户端确认游标连续达到当前权威水位，而非接口返回成功、页面加载完成或延迟下降。恢复期间同时记录补拉到达、完成、限额拒绝、游标重复、重试及用户可见结果；若延迟降低只是因为拒绝率上升，说明系统仍在止血，尚未恢复。

> **要点** — 慢依赖不可怕，失控重试才会制造级联；先限制请求生成，再以权威历史和受控追平恢复。

恢复阶段的风险不在于“数据库已恢复”，而在于积压客户端同时补拉、重试与队列回灌是否再次耗尽数据库和连接池余量。本节用可验证的恢复门，界定何时可逐步撤销保护措施。

### 恢复不是开关：先验证可用余量

### 恢复不是开关：先验证可用余量

“数据库恢复”只说明实例可响应，不说明系统能承受历史补拉、在线消息、重试回灌同时发生。进入恢复期前，应把余量定义为一组**共同成立**的条件，而非单项监控转绿。

- **数据库余量**：主库读写延迟、慢查询、锁等待、复制延迟均稳定低于保护阈值；容量应按峰值补拉读、正常写入和失败重试后的放大系数估算。若当前负载已接近常态上限，开放历史补拉只会把恢复变成第二次过载。
- **连接池余量**：数据库连接池、Redis/Mongo 客户端池及 HTTP 出站池必须保留可用连接；持续出现“池耗尽、等待获取连接、请求排队”时，即使数据库 CPU 不高，也不能放开入口。
- **消费队列可控**：MQ 积压深度、最老消息年龄、消费者吞吐和失败重投率应呈持续改善趋势。关键不是“消费者在线”，而是净清空速率  
  $r_{\text{drain}}=r_{\text{consume}}-r_{\text{produce}}>0$，且足以在目标时间内消化存量。
- **入口负载有界**：补拉接口、登录重连、发送重试必须有并发、速率和分页上限；客户端应采用慢放、指数退避和抖动，避免同一时刻重试。入口放量应小于当前可验证的净余量，而不是等于理论峰值。

因此，恢复门可表述为：在固定限流下，数据库与连接池存在稳定余量，队列连续下降，错误率未侵蚀错误预算，且入口负载受控，才允许小步提高配额。仅查看 OpenIM `send.go` 的 `MsgToMQ` 或 Mongo 消费代码，最多证明消息路径存在；它不能证明生产速率、重试放大、池等待与历史补拉是否共同构成真实故障机制。

### 有界入站：让慢客户端停在系统外

### 有界入站：让慢客户端停在系统外

历史补拉不能以“请求来了就查库”为入口模型。设授权历史库恢复后可用连接池余量为 $P_{\text{free}}$，单次补拉平均持池时间为 $t_q$，为在线写入、后台任务和抖动预留比例 $\rho$，则补拉并发上限应满足：

$$
C_{\text{pull}}\le \left\lfloor P_{\text{free}}(1-\rho)\right\rfloor
$$

并以实际池等待、慢查询分位数动态收紧，而非按应用线程数放大。B 离线 $25h$ 超过 broker 的 $24h$ 保留期后，确需从授权 DB 补历史；但 B 的慢网络、反复重连或大页请求不应占住 DB 连接。

入口应设置容量为 $Q$ 的有界队列，且 $Q$ 不是“越大越安全”：它只允许吸收短暂突发。若可接受排队时间为 $T_{\text{queue}}$，完成率为 $\mu$，则应满足 $Q/\mu\le T_{\text{queue}}$。队列满时立即返回“稍后重试”及带抖动的退避提示，不把请求阻塞在网关、协程或连接池等待队列中。

超时必须沿链路递减传播：客户端截止时间 $\rightarrow$ 网关排队预算 $\rightarrow$ 历史服务执行预算 $\rightarrow$ Mongo 查询截止时间。剩余预算不足以完成查询时直接拒绝；查询超时或客户端断连应取消下游操作、归还连接。每个设备同时只允许一个补拉会话，并限制页大小、连续页数与每设备速率；已确认权威 `seq9`、写入 outbox/E9 且设备状态可追平后，才允许继续下一页。

撤销临时限流前，应同时看到队列持续下降、池等待与超时回落、错误预算消耗速率受控，以及离线设备追平比例上升。仅观察 OpenIM `send.go` 的 `MsgToMQ` 和 Mongo 消费路径，不能证明补拉入站是否已被真正约束。

### 以权威序列确认消息真实状态

### 以权威序列确认消息真实状态

以消息 `m-9` 为例，恢复期间不能因为某个客户端“看到了消息”就认定系统已恢复一致。应以会话的权威序列 `seq=9` 为锚点，沿写入、投递、消费和设备游标逐层核验：

- **已权威落库**：授权消息数据库中存在 `m-9`，其所属会话序列为 `seq9`，内容、发送者、时间戳及去重键一致。`seq9` 是历史补拉的依据；仅在 Mongo 消费日志或缓存中见到消息不足以证明此状态。
- **已产生投递意图**：事务性 outbox 中存在事件 `E9`，并与 `m-9/seq9` 一一关联。若消息落库而无 `E9`，则应按 outbox 补偿流程重放事件，而非让客户端盲目重试发送。
- **已投递**：`E9` 已被投递链路确认接收，例如进入 MQ、推送服务或离线消息通道。此处表示服务端已尝试分发，不等于目标设备已经收到。
- **已追平**：设备状态记录的已确认游标达到 `seq9`，例如设备 A 的 `ack_seq=9`。只有该证据出现，才能说 A 已追平；若 A 显示消息但确认游标仍为 `8`，它仍可能在重连后重复补拉。
- **仅客户端可见**：界面展示、内存缓存或本地 SQLite 有 `m-9`，但服务端无 `seq9`、无 `E9` 或设备游标未推进。这可能是乐观回显、旧缓存或重复投递，不能作为恢复判据。

因此，`send.go` 中 `MsgToMQ` 调用成功、Mongo 消费成功，都只能说明局部链路经过；必须将 `m-9 → seq9 → E9 → 投递记录 → 设备确认游标` 串成可审计证据链，才能决定是否允许 B 从授权 DB 补齐历史。

### 超出保留期后的历史补拉恢复门

### 超出保留期后的历史补拉恢复门

B 离线 $25\text{h}$，已超过 broker 的 $24\text{h}$ 保留期，不能把“从 MQ 找不到消息”误判为消息丢失。恢复路径应切换为：以服务端授权数据库中的会话消息历史为准，按设备游标补拉；broker 仅承担保留期内的实时投递与短期追赶。

补拉前先确认权威边界：会话 `m-9` 的权威序列为 `seq=9`，对应业务事件为 `E9`，且该事件已完成 outbox 落库、Mongo 消费及设备状态更新。客户端 B 上报的最后确认序列记为 `ackSeq`，服务端仅返回 `(ackSeq, 9]` 范围内、且 B 仍有权限读取的消息；不得用客户端本地时间、broker offset 或“最新消息 ID”替代权威序列。

恢复门应是有界的，而非一次性全量放开：

- **分页有界**：每次补拉限制消息数与字节数，例如 `limit=100`、`maxBytes=1MB`；响应附带 `nextSeq`，由客户端显式续拉。
- **并发有界**：按设备、用户和租户设置并发槽位；同一设备仅允许一个历史补拉流，避免多端重连重复扫库。
- **速率有界**：依据 DB 连接池余量、慢查询、读取延迟和队列深度动态发放令牌。池等待上升或 P99 查询延迟越线时，立即降低补拉速率。
- **追平有证据**：B 连续确认至 `seq=9`，服务端记录 `deviceSeq=9`，且后续实时消息可从该游标衔接，才可标记设备追平。

不能仅凭 OpenIM `send.go` 中 `MsgToMQ` 的发送逻辑，或 Mongo 消费成功，就断言补拉链路可靠。真实恢复还需证明：E9 在授权历史库可查询、权限过滤正确、B 的确认游标持久化成功，以及限流撤销后 DB、连接池和入站队列仍保持稳定。

### 撤销临时限流的证据与顺序

### 撤销临时限流的证据与顺序

恢复期不能因“数据库可用”就一次性解除所有保护。限流、背压、隔离与熔断约束的是不同风险面，撤销条件也不同；共同前提是监控窗口内同时看到：入站与补拉队列持续下降、错误预算消耗速率稳定、活跃设备的历史追平比例上升，且数据库与连接池保有明确余量。

| 机制 | 保护对象 | 可撤销证据 | 撤销方式 |
|---|---|---|---|
| 限流 | API、补拉接口、发送入口 | 请求成功率稳定，限流队列下降，DB CPU、慢查询、连接池未逼近阈值 | 分批提高配额，先低风险租户或新请求，再放开历史补拉 |
| 背压 | MQ、消费者、写库链路 | 生产速率持续低于消费速率，积压下降而非仅短暂波动 | 逐级提高消费者并发；每级观察一个完整峰谷周期 |
| 隔离 | 正常实时消息与历史补拉 | 实时链路延迟、失败率已恢复目标，补拉不再抢占共享池 | 最后才扩大补拉份额，保留独立连接池和并发上限 |
| 熔断 | 故障依赖、授权 DB、Mongo 等 | 依赖健康检查、超时率和错误预算速率连续稳定 | 半开探测，小流量成功后逐步闭合，不直接全量恢复 |

设备追平必须可验证：例如 B 离线 `25h` 超过 broker 保留 `24h`，应确认其从授权 DB 补得权威 `seq=9`，收到 `outbox/E9`，并上报设备状态已推进到 `seq=9`。仅看到 OpenIM `send.go` 的 `MsgToMQ` 或 Mongo 消费恢复，并不能证明历史补拉、去重、状态确认和重试回路已脱离过载。

建议撤销顺序为：先保持熔断与隔离，恢复有限入站；再扩消费者以消化积压；随后缓慢提高实时流量；最后按设备追平率放开历史补拉。任一阶段若队列反弹、错误预算消耗加速或连接池余量缩小，应立即退回上一档，而不是继续“观察”。

> **要点** — 恢复应以数据库余量、队列趋势、错误预算和设备追平共同验收，不能因服务进程恢复便解除保护。

以设备B重连补拉历史为病例，分析慢数据库如何经由超时、重试与重连演变为级联故障，并建立止损与恢复路径。

### 慢依赖为何形成重试正反馈

### 慢依赖为何形成重试正反馈

数据库变慢时，最先变化的往往不是错误率，而是单个查询的服务时间。请求到达速率为 $\lambda$、依赖实际处理能力为 $\mu$；当 $\lambda$ 接近或超过 $\mu$ 时，队列开始累积，排队时间叠加到数据库执行时间上，使端到端延迟迅速越过客户端 deadline。

此时若客户端把“超时”直接视为“未执行”，便会发起重试。原本每秒 100 个历史补拉请求，若平均每个请求触发多次重试，入站请求可膨胀到 900/s。更糟的是，超时请求未必已停止：它可能仍在数据库连接池中排队，或已经占用锁、扫描和 I/O。于是系统同时处理“旧请求”和“其重试副本”。

闭环因此形成：

1. 数据库变慢，完成率下降；
2. 请求在网关、线程池、连接池和数据库前排队；
3. 排队使更多请求超时；
4. 超时触发重试、断线重连和重复补拉；
5. 新增流量进一步挤占依赖能力，使延迟继续上升。

当有效到达率持续大于完成率时，积压以 $\lambda-\mu$ 的速度增长；例如每秒多出约 3900 个未完成请求，短暂抖动也会迅速变成难以清空的堆积。关键误区是：重试看似在提高单个请求成功率，实际却可能降低全局成功率。

因此，deadline 必须与取消联动：客户端超时后应传播取消信号，服务端、连接池和数据库查询也要尽可能停止无价值工作。否则 deadline 只是“客户端放弃等待”，并不等于“系统停止消耗资源”。

### 区分意图、尝试与积压

### 区分意图、尝试与积压

一次“补拉历史”是一个**用户意图**：设备 B 希望得到某段历史记录。它不应因为网络超时而被统计成九次独立业务需求。若系统每秒产生 $I=100$ 个补拉意图，且每个意图在截止时间内最多发起 $A=9$ 次尝试，则最坏情况下到下游的请求到达率为：

$$
\lambda_{\text{try}}=I\times A=100\times9=900\ \text{次/秒}
$$

这里的“100→900/s”不是用户突然增加，而是同一批意图因超时、重试或重连被重复投递。若旧尝试未在新尝试发出时取消，它们还可能同时占用数据库连接、线程和队列。

积压取决于尝试到达率与下游实际完成率 $\mu$ 的差：

$$
B(t)=(\lambda_{\text{try}}-\mu)\times t
$$

例如慢数据库只能完成 $120$ 次/秒，而重试已把流量推至 $900$ 次/秒，则每秒净新增：

$$
900-120=780\ \text{条}
$$

仅持续 $5$ 秒，积压便达到：

$$
780\times5=3900\ \text{条}
$$

因此，`3900` 不是“数据库里有 3900 条历史消息”，而是等待处理的**尝试请求**；其中可能包含同一补拉意图的多个副本。监控也应分开记录：意图速率、实际尝试速率、成功率、取消率与队列积压。只看“请求量”会把重试放大误判为真实需求增长，从而错过级联故障的起点。

### 用截止时间守住请求边界

### 用截止时间守住请求边界

重连后的历史补拉不能只有“尽力而为”，而必须有明确的时间边界。客户端应为一次补拉会话设置总 `deadline`，再为单页查询、单条发送分配更短的子截止时间；任一上游变慢，都不能无限占用数据库连接、发送协程和重试配额。

在 Go 中，将根上下文贯穿重连、查询与发送链路：

- 重连建立 `ctx`，携带本轮补拉的总截止时间；
- 查询使用 `context.WithTimeout(ctx, queryTimeout)`，数据库驱动应响应 `ctx.Done()`；
- 发送使用独立短超时；若父上下文取消，立即停止排队、查询和网络写入；
- 不要在循环中使用 `context.Background()`，否则补拉已止损，后台请求仍会继续压库。

```go
ctx, cancel := context.WithTimeout(parent, 30*time.Second)
defer cancel()

for hasMore {
    page, err := repo.LoadHistory(ctx, cursor)
    if err != nil { return err }

    for _, msg := range page {
        if err := sender.Send(ctx, msg); err != nil { return err }
    }
    cursor = page.Next
}
```

取消不是失败后才处理的补救措施，而是过载控制信号：达到截止时间、用户离线、熔断打开或服务进入降级时，都应取消该链路。调用方还应区分“请求尚未提交”和“结果未知”：网络超时后直接重发可能造成重复写入。

因此发送 S2 时必须携带稳定的消息身份，例如 `message_id`。服务端若已持久化同一身份，应返回 `409`，表示“该消息已存在”，客户端将其视为幂等成功并推进游标，而非再次重试。这样，即使响应在途中丢失，重连后的补拉也不会把同一条历史消息反复写入、反复通知。

### 止损策略的选择与组合

### 止损策略的选择与组合

止损不是单一“少重试”，而是切断不同环节的正反馈：慢查询使请求超时，客户端重试与重连又放大到更多并发，队列积压进一步拉长延迟。策略应按故障性质分层：

| 策略 | 阻断环节 | 关键规则 |
|---|---|---|
| 拒绝分类 | 无效流量进入系统 | 参数错、权限错、同一请求 ID 已完成等返回不可重试错误；S2 收到同 ID 的 `409` 时必须视为幂等冲突/已有执行结果，而非立即再发。仅 `429`、部分 `503` 等可被有限重试。 |
| 带抖动的退避与重连 | 同步重试尖峰 | 使用指数退避加随机抖动，如 $t=\min(t_{\max},t_0 2^k)+jitter$；重连也必须退避，禁止大量设备在网络恢复瞬间同时补拉。 |
| 限流 | 入口过载 | 对用户、设备、租户及历史补拉分别设配额；新消息与 25 小时历史补拉不可共用无限额通道。 |
| 背压 | 中间队列失控 | 当积压、延迟或数据库连接池超过阈值时，向上游返回“稍后再试”或暂停拉取，而非继续接收并把 3900 条积压扩大。 |
| 资源隔离 | 争抢关键资源 | 将实时收发、补拉、索引和通知拆分线程池、连接池、队列及数据库副本；补拉变慢不能耗尽实时请求的容量。 |
| 熔断 | 持续访问故障依赖 | 熔断器在错误率或慢调用率超限后进入开启态，快速失败；冷却后进入半开态，仅放少量探测请求，成功达标才关闭。 |

组合顺序通常是：入口先分类拒绝，再按配额限流；可重试请求采用带抖动退避；服务端以背压保护队列，以隔离保护关键路径；依赖持续失效时由熔断器阻止无意义访问。恢复门不能只看“数据库已恢复”，还应确认积压下降、成功率稳定、半开探测通过，并渐进提高补拉额度，避免恢复期再次形成重连风暴。

### 从权威历史到设备追平

### 从权威历史到设备追平

设备 B 重连后不能把“收到一条新消息通知”当作历史已完整恢复的证据。通知可能丢失、乱序、重复或在服务端限流期间延迟；**权威历史**应来自可分页、可校验、带单调游标的消息存储。通知只承担“可能有新数据，请触发检查”的提示职责。

25 小时离线补拉应按时间窗或游标分段，例如每段 5～15 分钟，并记录持久化检查点：

1. 请求携带 `cursor`、段范围和固定请求标识；同一标识重复提交时，服务端返回已有结果或 `409`，避免重连后制造并发补拉。
2. 每段只在本地完成去重、落盘和游标提交后，才推进下一段；收到乱序通知时仍以权威游标扫描，而非直接插入通知中的消息。
3. 每段设置 deadline，并将取消信号向数据库查询、网络请求和任务队列传播。超时不应立即无限重试，而应释放并发槽位，等待带 jitter 的退避后重新准入。
4. 对补拉流量设置独立配额：限制单设备并发段数、单租户速率和全局补拉预算。实时写入与在线查询必须优先于历史恢复。

恢复门不是“连接建立成功”，而是同时满足：已追到服务端声明的稳定水位；最后一段校验通过；积压队列低于安全阈值；错误率、延迟和数据库负载连续观察窗口内恢复正常。若熔断器仍处于打开或半开状态，只允许少量探测段，禁止全部设备同时恢复 25 小时补拉。这样，通知负责唤醒，权威历史负责纠正，恢复门负责防止追平过程再次压垮系统。

> **要点** — 重试不是免费可靠性：必须以截止时间、幂等身份、准入止损和可验证恢复门约束补拉。
