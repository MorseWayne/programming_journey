### 建立四层内存责任模型

### 建立四层内存责任模型

分析 Go 服务内存时，必须把“对象还在不在”“堆是否变大”“地址空间是否保留”“RSS 是否下降”拆成四层问题：

1. **业务对象层**：例如 IM 的一批消息临时缓冲、连接读缓冲、切片及其底层数组。这里关心业务代码是否仍保留引用：消息处理完成后，队列、缓存、闭包或全局表是否还指向它。

2. **Go 堆层**：对象可达时占用堆；引用撤销后，对象只是“可回收”。GC 真正扫描到它，才会把相应 span 中的槽位标记为空闲。此时内存通常已可供 Go 运行时再次分配，但未必立刻还给操作系统。

3. **进程虚拟地址空间层**：运行时为了后续分配，可能继续保留已经申请的虚拟页区间。地址范围仍存在，不等于其中每页都有物理内存，也不等于其中仍有存活对象。

4. **RSS 层**：RSS 统计当前驻留在物理内存中的页。只有运行时对空闲页执行归还、解除驻留或内核回收后，RSS 才可能下降；其变化还受页访问、回收时机和内核策略影响。

因此，`buf = nil` 只说明业务引用可能撤销；一次 GC 说明对象可能变成堆空闲空间；堆可复用也不意味着虚拟地址范围缩小；虚拟范围保留更不意味着 RSS 必然高。排查“内存没降”时，应先问：是哪一层没有释放，还是只是尚未反映到下一层？

### 从消息批次看内存生命周期

### 从消息批次看内存生命周期

设 c-a 批次到达后，连接协程先把消息读入临时 `[]byte`，再按协议切分、解码并投递给下游。它看似只是“一次分配”，实际跨越多层生命周期：

1. **Go 对象层：建立引用**  
   `make([]byte, n)` 产生切片头和底层数组；切片变量、消息结构体字段、队列元素都可能持有指向该数组的引用。只要仍有可达引用，GC 就不能回收该对象。

2. **运行时分配层：取得槽位**  
   Go 分配器通常从已有 span 中取一块合适大小的槽位，而非每次向操作系统申请新内存。此时进程的虚拟地址空间可能早已存在，对 RSS 未必立刻有影响。

3. **写入层：促使物理页驻留**  
   仅拿到地址不等于占用物理内存。连接协程把网络数据写入缓冲区时，触及的虚拟页发生缺页并映射物理页；这些驻留页才会计入 RSS。批次越大、实际写入页越多，RSS 越可能上升。

4. **业务层：撤销引用**  
   c-a 批次处理完成后，消息从队列删除，临时切片离开作用域，或字段被置为 `nil`。这只是让对象变得“可能不可达”；它既不等于 GC 已执行，也不等于 RSS 已下降。

5. **GC 层：确认对象死亡**  
   下一轮 GC 扫描后，若找不到该底层数组的任何引用，数组占用的槽位可被标记为空闲。但空闲槽位通常仍属于 Go 堆。

6. **复用与归还层：决定 RSS 何时变化**  
   后续批次可能直接复用该槽位，因此无需再次分配或触发新的物理页驻留。即使运行时将空闲页标记为可回收，操作系统也可能延后回收其物理页。故应区分：

   `业务引用撤销 → GC 回收对象 → 分配器复用/释放页 → 操作系统回收物理页 → RSS 下降`

长连接读缓冲尤其容易打破直觉：一次峰值消息把缓冲扩容到较大容量后，即使后续流量很小，只要连接仍持有该切片，底层数组始终可达；GC 无法回收，相关页也不会因“当前没装消息”自动离开 RSS。

### 切片引用决定对象是否可达

### 切片引用决定对象是否可达

长连接常用一个较大的读缓冲承接网络数据：

`buf := make([]byte, 64<<10)`

一次读取后，解析器从中切出一条消息：

`msg := buf[start:end]`

这里 `msg` 虽然长度可能只有几十字节，但它仍是一个切片描述符：包含指向底层数组某处的指针、长度和容量。只要 `msg` 仍被某个对象、队列、闭包或协程栈引用，GC 就能沿引用链找到它；进而认定整块 `buf` 的底层数组仍可达。

关键不在于子切片“看见”了多少字节，而在于它的指针仍落在同一底层数组中。例如，64 KiB 缓冲中仅保留 100 B 的 `msg`：

`pending = append(pending, msg)`

即使随后覆盖 `buf` 变量、消息主体已经处理完毕，这 100 B 的子切片仍可能让整块 64 KiB 数组不能被回收。若批量消息都从多个大读缓冲切片并长期排队，小对象引用会意外延长大量大块内存的寿命。

需要脱离原缓冲时，应复制有效数据：

`stable := append([]byte(nil), msg...)`

此后撤销对 `msg` 的引用，原读缓冲才可能在未来 GC 中变为不可达。注意：不可达只意味着 Go 对象可回收；运行时可能复用其 span，物理页也未必立刻归还系统，因此 RSS 的下降还要看后续分配器与页回收行为。

### 用玩具span理解复用与滞留

### 用玩具 span 理解复用与滞留

把运行时管理的一块连续堆空间想成一个玩具 `span`：它包含若干页，每页又切成固定大小的对象槽位。例如，某个 `span` 有 4 页，每页可放 4 个 `64B` 对象：

| 页 | 存活对象数 | 状态 |
|---|---:|---|
| 第 1 页 | 4 | 已满 |
| 第 2 页 | 2 | 部分使用 |
| 第 3 页 | 1 | 部分使用 |
| 第 4 页 | 0 | 全空 |

IM 的 c-a 批次消息临时缓冲消失后，业务代码虽然撤销了切片、指针或 map 中的引用，GC 也已经确认其中对象不可达，但这首先只意味着：这些槽位可以重新分配。它不等于运行时立刻缩小堆，更不等于操作系统立刻回收物理页。

关键在于“空闲槽”和“空闲页”不同：

- 第 2、3 页中的死亡对象留下的是空闲槽，但页内仍有存活对象；运行时不能归还整页。
- 第 4 页全空，理论上可成为归还候选；但分配器也可能暂时保留它，等待下一批同尺寸对象快速复用。
- 即使运行时决定把某些全空页交还给操作系统，内核对 RSS 的统计变化仍取决于解除映射、回收物理页或后续页面访问等机制。

因此可区分三件事：

1. **对象死亡**：GC 后槽位不再承担业务数据责任。  
2. **堆可复用**：`HeapAlloc` 可能下降，但 `HeapSys` 仍保留已申请的堆地址空间。  
3. **物理页可回收**：只有整页空闲且运行时、内核都完成相应处理时，RSS 才可能下降。

长连接读缓冲尤其容易制造这种现象：高峰期扩大的缓冲曾触及许多页；请求结束后对象虽死，但这些页可能仍被 `span` 保留、被其他对象部分占用，或等待后续分配复用。于是“GC 已回收”与“进程 RSS 未降”并不矛盾：前者描述对象可达性，后者描述物理页驻留。

### 把运行时统计放回Linux视角

### 把运行时统计放回 Linux 视角

Go 的堆通常来自匿名私有映射：运行时向内核申请一段虚拟地址，再按需触发缺页分配物理页。因此，`HeapAlloc`、`HeapSys` 与进程 RSS 不能直接画等号。

- `HeapAlloc`：仍被 Go 对象占用的堆字节数。消息临时缓冲的切片、连接读缓冲及其底层数组，只要仍可达，通常计入这里；但它描述的是运行时对象责任，不表示这些字节都恰好驻留在物理内存中。
- `HeapSys`：Go 已向操作系统取得的堆地址空间，包含已分配对象、空闲 span 和可复用空间。对象被 GC 回收后，`HeapAlloc` 可下降，而这部分地址往往仍保留在 `HeapSys` 中，等待后续分配复用。
- `HeapReleased`：`HeapSys` 中运行时已通知内核可回收、归还物理页的一部分。它意味着 Go 不再需要这些页的驻留资源，但 RSS 的观察值还会受内核回收时机、统计采样和页是否再次触碰影响。

与之对照，文件 `mmap` 映射的页通常来自页缓存。`MAP_SHARED` 的修改可见于其他映射者，并可能回写文件；`MAP_PRIVATE` 初始可共享文件页，但写入时通过写时复制得到匿名页。两者的已驻留页面都可能计入进程 RSS；不过文件页缓存可被多个进程共享，单看 RSS 会重复计数，不能把它当作“该进程独占内存”。

因此，批次消息引用撤销后，变化顺序可能是：`HeapAlloc` 先因 GC 下降；空闲堆被分配器保留，`HeapSys` 不变；运行时释放页后 `HeapReleased` 上升；最终 Linux 回收或解除驻留，RSS 才下降。RSS 是映射页的进程视角结果，不是 Go 对象存活量的直接读数。

> **要点** — 对象死亡、堆可复用、物理页归还和RSS下降是四个可能相隔很久的事件。

### 四个“堆”与内存层次

### 四个“堆”与内存层次

“堆”在排查 Go 内存问题时至少可能指四种不同概念，不能混为一谈。

- **goroutine 栈**：每个 goroutine 都有自己的调用栈，存放调用帧、部分局部变量、返回地址等。它会按需增长和收缩；“局部变量”不等于一定在栈上，是否逃逸到 Go 堆由编译器根据生命周期和使用方式决定。
- **Go 的 GC 堆**：由运行时分配并由垃圾回收器管理的对象区域。跨函数、跨 goroutine 存活，或大小、引用关系不适合放栈上的对象，通常会在这里分配。
- **进程虚拟地址空间**：操作系统给进程提供的逻辑地址范围，除 Go 堆外还包括代码段、全局数据、goroutine 栈、运行时元数据、动态库、内存映射文件等。
- **RSS**：常驻内存集，即上述虚拟地址中当前真正驻留在物理内存里的页。它是操作系统观察指标，不等于 Go 堆大小；Go 堆对象被回收后，RSS 也未必立刻下降。

还有一种完全不同的含义：**二叉堆**。它是优先队列常用的数据结构，通常由数组或 slice 实现；名称中的“堆”描述元素的顺序性质，如父节点不大于子节点，并不表示这些元素一定分配在 Go GC 堆上。

因此，看到“堆增长”时，先问清楚：是二叉堆中的元素变多、Go 堆的存活对象变多、虚拟地址空间扩大，还是 RSS 上升。不同层次对应不同原因与排查工具。

### 局部变量为何未必在栈上

### 局部变量为何未必在栈上

“局部变量”只描述**作用域**：它只能在某个函数或代码块内通过名字访问；它并不承诺对象一定分配在 goroutine 栈上。Go 编译器会进行**逃逸分析**：若编译器无法证明对象的引用不会在当前函数返回后继续存活，就会把对象安排到 Go 堆上，由 GC 管理。

以 IM 消息为例：

`func build() *Message { m := Message{Text: "hi"}; return &m }`

`m` 的名字是 `build` 的局部变量，但 `&m` 被返回。调用者在 `build` 返回后仍要访问该消息，因此 `m` 不能随该函数栈帧销毁，通常会逃逸到堆。

跨函数保存也是同样的逻辑：

`func save(m Message) { pending = append(pending, &m) }`

这里 `m` 虽是 `save` 的形参，却被放入更长寿命的 `pending` 中；只要该切片或其中元素仍可达，消息对象就必须继续存在，因而可能堆分配。

反过来，**取地址不等于必然逃逸**：

`func handle() { m := Message{}; use(&m) }`

若编译器能证明 `use` 不会保存这个指针，且 `handle` 返回后无人可达 `m`，那么 `m` 仍可放在栈上。是否逃逸取决于指针是否被返回、写入堆对象、交给未知调用、被闭包或 goroutine 延后使用等具体情境，而非“它是局部变量”或“代码里出现了 `&`”。

### 切片头、底层数组与可达性

### 切片头、底层数组与可达性

切片不是数组本身，而是一个很小的描述符，通常可理解为：

`指向底层数组的指针 + 长度 len + 容量 cap`

因此，切出一小段数据并不等于复制数据：

```go
buf := make([]byte, 10<<20) // 10 MiB
part := buf[:100]
buf = nil
```

此时 `part` 的长度只有 100 字节，但它的切片头仍指向原来的 10 MiB 底层数组。只要 `part` 仍可达，GC 就必须保留整块数组；原变量 `buf = nil` 并不能改变这一点。

这种保留常隐藏在更长的引用链中：

- 子切片被放入缓存字段；
- 消息对象保存了原始数据的一段视图；
- 全局变量、队列或 map 仍保存该切片；
- 某个 goroutine 的局部变量尚未结束使用。

例如解析网络包时，若把 `packet[:32]` 存入长期会话状态，可能无意间让整个 `packet` 长期存活。若只需要那 32 字节，应显式复制：

`header := append([]byte(nil), packet[:32]...)`

GC 判断的是对象是否仍可从根对象经引用链到达，而不是切片的 `len` 看起来有多小。只有所有指向该底层数组的切片、指针和容器引用都消失后，数组才具备回收资格；即使随后被回收，也不能据此承诺进程 RSS 会立刻下降。

### GC回收的是不可达对象

### GC回收的是不可达对象

一次请求结束、局部变量离开作用域，并不等于其指向的 Go 堆对象立刻消失。关键不在“变量名还在不在”，而在对象是否仍能从 **根对象** 到达：例如 goroutine 栈中的指针、全局变量、运行时结构以及仍存活对象中的引用。

典型顺序是：

1. 某个引用被覆盖、置为 `nil`，或所属栈帧退出；
2. 若不存在任何其他可达路径，对象才成为不可达对象；
3. GC 在后续标记阶段识别它不可达，并在清扫阶段将其空间归还给 Go 分配器；
4. 分配器可优先复用这块空间服务后续 `new`、切片扩容等分配。

因此，`x = nil` 只是**可能减少一条引用边**，不是“立即释放内存”命令。尤其是切片场景：

```go
small := big[:10]
```

即使 `big` 变量消失，`small` 的 slice header 仍指向同一底层数组；数组仍可达，整块数组都不能被 GC 回收。需要时应复制所需元素到新切片，而非只缩短长度或容量。

即便 GC 已回收对象，进程 RSS 也未必立刻下降：Go 分配器可能保留已清扫的页以便复用，运行时何时将空闲页归还操作系统还受内存压力、页状态和运行时策略影响。程序能保证的是“不再持有不必要引用”，不能承诺“某行代码后 RSS 立即降低”。

### 从对象生命周期到RSS变化

### 从对象生命周期到 RSS 变化

同一段代码里的“内存还在”，至少可能指四种不同事实，不能混为一谈：

| 口径 | 关心的问题 | 何时减少 |
|---|---|---|
| 对象存活 | 是否仍能从根对象、栈、全局变量等路径访问 | 引用消失后，下一次 GC 才可能确认不可达 |
| Go 堆已分配 | 程序当前逻辑上持有多少堆对象 | GC 清扫不可达对象后下降 |
| 运行时保留页 | Go 运行时向操作系统申请并缓存了多少页 | 运行时认为页可归还时才可能下降 |
| RSS | 操作系统当前认为该进程驻留在物理内存中的页数 | 页被回收、换出或解除映射后才变化 |

例如，请求处理中创建一个 `[]byte`。请求结束后，若没有任何引用保留其底层数组，该数组可能在下一轮 GC 中成为垃圾；但这只意味着“对象不可达”。运行时往往会把清扫后的页留作后续分配复用，因此 Go 堆对象减少，不代表保留页立刻减少，更不代表 RSS 同步下降。

反过来，RSS 上升也不必表示 Go 堆泄漏：goroutine 栈增长、运行时元数据、`mmap`、cgo 分配、文件页缓存或刚被触碰的匿名页，都可能进入进程 RSS。解释监控数据时，应先问“测量的是哪一层”，再判断是否存在真正的对象长期存活。

> **要点** — 对象是否可达决定GC能否回收；对象回收、页复用与RSS下降属于不同层次、不同时间点的事件。

对象释放后，为什么进程RSS常常不降？关键在于对象、槽位、页与操作系统归还之间存在多层时间差。

### 从对象到页：四层概念不可混同

### 从对象到页：四层概念不可混同

解释内存现象时，先把四层实体分开：

1. **Go 对象**：程序语义上的值，如 `&T{...}`、切片底层数组或 map 的部分存储。对象死亡只表示垃圾回收器确认其不再可达。
2. **分配槽**：分配器实际交付对象的容器。小对象通常落入某个大小类别对应的槽；对象释放后，槽可标记为空并供后续同类分配复用。
3. **Go 堆页**：多个槽组织在堆页及更高层的 span 中。一个页内只要仍有存活对象，或分配器仍希望保留其容量，该页通常不能作为“整页空闲”处理。
4. **进程 RSS**：操作系统视角中当前驻留在物理内存里的虚拟页集合。它反映页是否驻留，而非某个 Go 对象是否存活。

玩具模型中，一个 `4KiB` 页含四个 `1KiB` 槽。若只剩一个对象存活，其余三个槽虽可复用，却仍与该存活槽共享同一页；程序无法仅归还页中的三个 `1KiB` 空洞。因此，“对象已释放”不等于“堆页可归还”，更不等于“RSS 立即下降”。

这里的空槽可视为页内的**内部空洞**；空闲槽分散在许多不同页、导致难以腾空完整页，则是**外部碎片**。这是概念模型，不能直接等同于 Go 真实的 size class、`mspan` 和页管理细节。

还要注意：物理页帧可以不连续，但程序看到的 Go 堆虚拟地址仍可能连续；物理不连续并不意味着程序地址空间不连续。分配器保留已提交容量以便复用时，后续分配可能无需重新向系统申请页，所以 RSS 会在一段时间内保持稳定。

### 玩具span：一页四槽与一个存活对象

### 玩具span：一页四槽与一个存活对象

设想运行时向操作系统取得一个连续的 $4\text{KiB}$ 页，并把它作为同一类小对象的容器，切成 $4$ 个 $1\text{KiB}$ 槽位：

| 槽位 | 初始状态 | 一轮 GC 后 |
|---|---|---|
| 槽 0 | 对象 A | 存活 |
| 槽 1 | 对象 B | 空闲 |
| 槽 2 | 对象 C | 空闲 |
| 槽 3 | 对象 D | 空闲 |

对象 B、C、D 已不可达时，GC 会把对应槽位标记为空闲；之后新建一个不超过 $1\text{KiB}$ 的对象，运行时通常可直接复用槽 1、2 或 3，无须再次向操作系统申请页。于是，从“对象分配”角度看，$3\text{KiB}$ 已经可以再利用。

但从“归还整页”角度看，这一页仍包含存活的对象 A。运行时不能只把槽 1～3 对应的物理内存独立交还操作系统：它们属于同一个页，而页中仍有有效数据。因此，该页通常仍保留在运行时管理的 span 中，进程 RSS 也未必下降。

这里的空闲是**页内空洞**：槽位可复用，却不足以释放整个页。若许多页都各自只剩一个存活对象，空闲空间总量可能很大，但分散在不同页中；除非对象随后全部死亡，或运行时能够把完全空闲的页回收，否则这些页仍会继续支撑已提交的内存规模。

### 清扫、复用与归还：不同步的生命周期

### 清扫、复用与归还：不同步的生命周期

设一个玩具页大小为 $4\text{ KiB}$，其中有 4 个 $1\text{ KiB}$ 槽位。开始时，页内放入对象 $A,B,C,D$；随后只有 $A$ 仍被根对象引用。

生命周期并不是“引用消失，RSS立刻下降”，而更接近下面的顺序：

1. **引用消失**：程序不再持有 $B,C,D$ 的引用。此时它们在语义上已经不可达，但其内存位仍可能保留原数据；槽位也尚未立刻变成可分配空间。
2. **GC 标记**：垃圾收集器从根集合遍历，只标记仍可达的 $A$。$B,C,D$ 未被标记，因而被判定为垃圾。
3. **清扫形成空槽**：清扫阶段把 $B,C,D$ 所占槽位登记为空闲。现在该页有 3 个可复用槽位，但 $A$ 仍占据第 4 个槽位。
4. **后续分配复用**：新对象到来时，分配器通常优先使用这些空槽，而不是立刻向操作系统申请新页。于是堆的“已使用对象量”曾下降，但进程保留的页数和 RSS 可以保持不变。
5. **整页空闲后才可能归还**：只有当 $A$ 也死亡并完成清扫，这个页才可能整体空闲；随后运行时还要决定是否把它保留为缓存、交给堆的空闲页管理，或最终通知操作系统回收。即使通知了，RSS 的下降也可能滞后。

这里的“页”只是推导模型。真实 Go 运行时按 `size class` 管理对象槽位，并以 `mspan` 等结构组织分配；不要把玩具槽位直接等同于真实布局。也不要把物理页可能不连续误解为程序虚拟地址不连续：虚拟地址空间可连续映射，而其背后的物理页由操作系统分别管理。

因此，内部空洞是“同一页内仍有活对象，空槽不能整页归还”；外部碎片则是空闲容量散落在多个 span 或页中。容量被保留以供复用，正是对象已释放而 RSS 暂时稳定的常见原因。

### 内部空洞、外部碎片与容量保留

### 内部空洞、外部碎片与容量保留

设一个玩具页大小为 `4 KiB`，每页切成 4 个 `1 KiB` 槽。若其中仅 1 个对象仍存活，其余 3 个槽已经释放，那么这 3 个槽可立即被后续同类分配复用；但该页仍被那个存活对象占住，分配器通常不能把整页归还给操作系统。这是**页内空闲槽形成的内部空洞**：从对象视角看有大量空闲空间，从页回收视角看却仍是“不可整页释放”。

与之相对，**外部碎片**强调空闲空间分散在多个页或 span 周围。例如许多页都只残留一个长寿命对象，每页都有大量空槽，却没有足够多的“全空页”可回收。这里的“分散”指分配与存活布局，不应简单理解为物理页不连续，更不能据此断言程序虚拟地址不连续。

真实 Go 运行时不会机械地按 `1 KiB` 切槽，而是按 size class 管理对象，并以 span 等结构批量服务分配；但核心约束相同：只有满足相应粒度的完整空闲单元，才可能进入进一步的归还流程。

此外，切片的 `len` 变小不等于其底层数组立刻消失；只要 `cap` 对应的数组仍被引用，容量仍被保留。即使数组已不可达，运行时也往往优先复用已获得的槽、span 和页。因而“对象释放了”常先表现为可复用容量增加，而不是 RSS 立刻下降。

### 从玩具模型回到Go统计与RSS

### 从玩具模型回到 Go 统计与 RSS

玩具模型中，$4\text{ KiB}$ 页有 4 个 $1\text{ KiB}$ 槽：即使只剩 1 个对象存活，其余 3 个槽虽然可复用，该页仍不能作为完整页归还。这解释了“逻辑上释放”不必立刻变成“操作系统少占内存”。

但不要把它机械等同于 Go 运行时。实际 Go 分配器按 `size class` 管理小对象；一组相近大小的对象槽位由 `mspan` 承载，`mspan` 又从运行时管理的堆空间取得页。对象死亡后，槽位可能先留在对应 `mspan` 中等待同类分配复用；只有满足更严格条件时，相关页才可能被回收或标记为可归还。

观察时可将几个指标分层理解：

- `HeapAlloc`：当前仍被存活对象占用的堆字节，GC 后通常会下降。
- `HeapSys`：Go 向操作系统申请并纳入堆管理的地址空间/内存范围，往往不会随一次 GC 立即下降。
- `HeapReleased`：Go 已通知操作系统“这部分物理页可回收”的字节数；它增加才意味着运行时主动释放了部分页。
- RSS：操作系统当前认为该进程驻留在物理内存中的页数，受延迟回收、页重新访问、采样时刻和操作系统策略影响，不必与上述任一指标一一对应。

因此，若 GC 后 `HeapAlloc` 明显下降而 RSS 暂稳，常见含义是：对象确实已死，但空槽仍在 `mspan` 中复用，或空闲页尚未被运行时归还、尚未被内核从驻留集移除。这里的“页不连续”也不能直接推出程序虚拟地址不连续：物理页可以离散映射到连续的虚拟地址区间。

> **要点** — 对象死亡只会先产生可复用空间；只有相关页整体可释放并被归还时，RSS才可能下降。

通过两个固定的 4KiB 消息缓冲，沿着 t0 到 t3 推演：对象消失、堆统计变化、页复用与 RSS 回落为何不是同一时刻发生。

### 先分清四个层次

### 先分清四个层次

讨论“分配了一个 4KiB 缓冲，内存为什么没降”之前，先把观察对象分开。它们相关，却不是同一个量：

1. **Go 对象层**  
   例如 `B := make([]byte, 4<<10)` 产生一个切片及其背后的数组对象。这里关心的是：程序中是否还存在从根对象可达的引用。`B` 失去最后引用，只表示它**可被 GC 回收**，不表示内存立刻归还。

2. **Go 堆层**  
   对象通常从运行时管理的堆中取得空间。GC 标记、清扫后，不可达对象所占槽位可重新用于后续 Go 分配；`HeapAlloc` 因此可能下降。但这通常只是“堆内空间可复用”，不是“进程少占了一页物理内存”。

3. **进程虚拟地址空间层**  
   运行时会向操作系统申请并保留一批地址范围，再切分为 span、页和对象槽位。某个对象消失，甚至某个 span 变空，也不要求这段虚拟地址马上取消映射；保留地址可降低下一次分配的成本。

4. **RSS（常驻集）层**  
   RSS 是当前实际驻留在物理内存中的页面总量。它受页访问、内核回收、运行时向 OS 释放页、计量时点等共同影响。即使运行时统计中的 `HeapReleased` 增加，RSS 也未必立刻同步下降；反过来，RSS 波动也不能单独证明 Go 对象仍存活。

因此，“`B` 不可达”“`HeapAlloc` 下降”“span 可复用”“RSS 回落”是可能发生在不同时间点的四件事。把一次 Go 分配直接等同为一次物理页占用，或把 GC 触发等同为立即还给操作系统，都会误判暂存、缓存与真正泄漏。

### t0：两个缓冲仍被切片引用

### t0：两个缓冲仍被切片引用

先固定一个最小场景：进程已经分配了两个 `4KiB` 消息缓冲 `A`、`B`。它们通常不是“切片对象本身”占了 `4KiB`，而是两个底层字节数组各占约 `4KiB`；切片变量只是一个切片头，包含指向数组的指针、长度和容量。

```go
a := make([]byte, 4<<10) // 缓冲 A
b := make([]byte, 4<<10) // 缓冲 B

queue = append(queue, a)
stash = b[:128]
```

此刻 `A`、`B` 都是可达对象：

- `A` 被 `queue` 中的切片头指向。即使当前函数不再使用局部变量 `a`，队列仍构成一条从根对象到 A 底层数组的引用链。
- `B` 虽然只保留了 `b[:128]`，但这个短切片的底层数组仍是原来的 `4KiB` 数组。长度变短不等于数组变小；只要切片头仍指向该数组，GC 就不能回收整块数组。
- 局部变量、全局变量、goroutine 栈、接口值、闭包捕获变量、缓存、队列、重试暂存区等，都可能成为保活引用。

因此，`t0` 时两个缓冲的逻辑存活量约为：

$$
\text{live bytes} \approx 4\text{KiB}(A)+4\text{KiB}(B)
$$

若它们已进入 Go 堆，`HeapAlloc` 会包含相应分配；但这并不意味着 RSS 恰好只增加 `8KiB`。运行时按 span、页和更大的堆区间管理内存，映射及实际驻留也有自己的粒度。

一个常见误判是：“消息已发送，所以 B 应当释放。”发送完成只说明业务上不再需要消息；若 `stash`、队列槽位或某个局部暂存切片仍保留指针，B 对 GC 仍然可达。这是**引用残留**，未必是真泄漏：后续清空 `stash`、覆盖队列元素或函数返回后，B 可能自然变为不可达。

### t1 到 t2：不可达不等于立刻归还

### t1 到 t2：不可达不等于立刻归还

设 t0 时有两个分别为 4KiB 的对象缓冲 `A`、`B`，它们都已分配在某个 Go 堆 span 中。t1 时，程序清除了指向 `B` 的最后一条强引用：

```go
b = nil // 假设不存在其他指针、接口值、闭包或暂存引用指向 B
```

此刻 `B` 的语义状态是“不可达”，但它通常仍占着原来的堆槽位。原因是 Go 的垃圾回收并不会在每次赋值为 `nil` 后立即扫描全堆；在下一轮 GC 真正发现它之前，运行时尚未把该槽位登记为空闲。

可将状态区分为：

- **t1：逻辑不可达**  
  从根对象出发已无法到达 `B`；但 GC 尚未完成标记与清扫，`HeapAlloc` 可能仍包含 `B`，span 的已分配页数和进程 RSS 通常不变。

- **标记完成后：确认垃圾**  
  并发标记确认 `B` 不存活。此时“不可达”成为运行时已知事实，但其内存槽位还未必立刻可供分配器使用。

- **t2：清扫完成后：槽位可复用**  
  sweep 将 `B` 所在对象槽位归入该 span 的空闲集合。`HeapAlloc` 可能减少约 4KiB，因为它统计的是仍被认为存活、已分配的堆对象；但 span 仍可能同时容纳 `A`，因此不能整体归还。

关键推论是：

\[
\text{B 不可达} \ne \text{span 空闲} \ne \text{物理页归还 OS}
\]

即使 `HeapAlloc` 在 t2 下降，运行时仍可保留该 span 及其页，供后续同规格对象快速复用；这些页仍可能映射在进程地址空间中，RSS 因而没有同步下降。把一次 GC 后 RSS 未降直接判为泄漏，忽略了“已清扫但等待复用”的正常中间状态。

### t3：空闲槽、span 复用与页归还

### t3：空闲槽、span 复用与页归还

设玩具 `span` 含有若干个 4KiB 槽位。到 `t2`，B 已被标记为不可达并在 sweep 中清扫：

```text
span S: [ A:存活 ][ B:空闲 ][ 空闲 ][ 空闲 ]
```

此时 `HeapAlloc` 可以因 B 被回收而下降；但 B 原先所在的物理页通常仍由运行时持有。原因是“槽位空闲”首先意味着可再次分配，而非必须立刻交还操作系统。

若随后分配新的 4KiB 对象 C，运行时通常优先从 S 的空闲槽取得空间：

```text
span S: [ A:存活 ][ C:复用B的槽 ][ 空闲 ][ 空闲 ]
```

这一步不需要向 OS 申请新页，因而既可能降低后续分配成本，也不要求 RSS 下降。只有当 span 中所有对象槽都空闲，且该 span 所在页暂时没有更合适的用途时，运行时才可能将其放回更大的空闲页集合，或通过 scavenger 建议/释放其中的物理页：

```text
span S: [ 空闲 ][ 空闲 ][ 空闲 ][ 空闲 ]
        ↓
runtime 空闲页池 → 可复用，或尝试归还 OS
```

`HeapReleased` 记录的是运行时已向系统归还、或声明不再需要的堆页量；它不是“RSS 已同步减少”的保证。内核何时实际回收物理页、进程 RSS 何时被采样到下降，受页回收策略、内存压力和平台接口影响。因此常见时间线是：

- `t2`：B 被 sweep，`HeapAlloc` 下降；
- `t3`：span 空闲，可被后续 Go 分配复用；
- 更晚：部分页被 scavenger 释放，`HeapReleased` 上升；
- 仍可能更晚：RSS 才下降，或在低内存压力下暂不明显下降。

所以，看到 RSS 暂时不回落不能单独证明泄漏；关键还要看存活对象、可复用空闲 span，以及 `HeapAlloc` 的长期趋势。

### 识别残留引用与真泄漏

### 识别残留引用与真泄漏

两个 4KiB 缓冲中，`B` 在 `t1` 看似“用完”，却未必已消失。首先应问：**是否仍存在从根对象可达的引用？**

- **切片截短不是释放底层数组。**  
  `buf = buf[:0]` 只把长度变为零，`cap(buf)` 仍可能是 4096；底层数组继续被 `buf` 持有。即使写成 `buf = buf[:0:0]`，旧数组仍由该切片的数据指针引用。要断开关系，应令 `buf = nil`，或复制所需小片段到新数组。

- **临时缓存是延迟释放，不一定是泄漏。**  
  连接池、`sync.Pool`、批处理队列、全局复用缓冲可暂存 `B`。此时 GC 后 `HeapAlloc` 未必下降，因为对象仍可达；但若缓存有容量上限、可淘汰策略，峰值后趋于稳定，它是有意保留的工作集。

- **运行时保留空闲页也不是泄漏。**  
  `t2` sweep 后，`B` 不可达，`HeapAlloc` 可以下降；但其 span 可能仍留在 `HeapSys` 中供后续分配复用。直到 `t3` 空闲 span 被归还，`HeapReleased` 才可能上升；即便如此，操作系统 RSS 的回落仍可能滞后。

真正的泄漏特征是：请求持续进行时，可达对象、缓存键或队列元素**无上限增长**，多轮 GC 后 `HeapAlloc` 仍呈长期上升趋势。阅读指标宜按顺序进行：

1. 看 `HeapAlloc`：活对象是否持续增长；
2. 看 `HeapSys`：运行时是否扩张了堆地址空间；
3. 看 `HeapReleased`：其中多少页已声明可归还；
4. 最后看 RSS：实际驻留页受内核回收、页触碰和采样时机影响，不能单独判定泄漏。

因此，“GC 触发了但 RSS 没降”通常只能说明页尚可复用或尚未被内核回收；只有持续可达增长，才是更接近真泄漏的证据。

> **要点** — GC 让对象可复用，不保证立即还给操作系统；Go 堆统计、已保留页与 RSS 必须按时间和层次分别解读。

mmap 不是“把文件读进内存”，而是在进程地址空间建立映射；页的来源、共享方式与写入后的行为决定了 RSS 和文件内容如何变化。

### mmap：建立地址到页的映射

### mmap：建立地址到页的映射

`mmap` 的核心动作不是复制数据，而是向内核申请一段虚拟地址区间，并规定这段地址将来应如何取得页内容：可以来自文件，也可以是匿名零页。此时进程得到的是“地址到页”的映射规则，而不必立即拥有对应数量的物理内存。

例如，程序把一份很大的聊天日志以只读方式映射：

`日志文件偏移 0 ~ 1 GiB → 进程虚拟地址 A ~ A+1 GiB`

映射成功后，`A` 附近的地址已经合法，但程序尚未读取日志时，多数页面通常并未进入该进程的 RSS。只有 CPU 实际访问某个页，触发缺页异常后，内核才会按映射规则取得该页：文件映射通常关联页缓存中的文件页；匿名映射则通常提供初始为零、随后可被写入的匿名页。

因此，映射长度很大不等于 RSS 立刻同样大。一个 `1 GiB` 的只读日志映射，若只查看开头几页，RSS 的增长可能很小；反复扫描整份日志，才可能逐步触及更多页。相似地，消息缓冲区可用匿名映射预留较大空间，但未读写的区域不应简单视为已经占用等量物理内存。

还要区分地址空间与资源生命周期：关闭文件描述符只是不再保留该文件句柄；已建立的映射通常仍可继续访问。要撤销这段虚拟地址区间，应调用 `munmap`。

### 两类来源：匿名页与文件页

### 两类来源：匿名页与文件页

匿名映射与文件映射都只是在虚拟地址空间中预留一段区间；刚建立映射时，通常并没有立刻为每个虚拟页分配实际物理页。真正访问时触发缺页，内核才决定该页从哪里来。

- **消息缓冲：匿名映射**  
  设聊天程序为待发送消息建立一块匿名缓冲区。读取尚未写入的页时，内核可提供逻辑上的零页；首次写入时，才分配新的物理页并将其计入进程 RSS。该页没有对应普通文件的磁盘位置，内容主要由匿名内存、交换空间或内存回收机制管理。

- **聊天日志：只读文件映射**  
  设程序用 `mmap` 只读映射聊天日志。访问某个偏移量时，缺页处理会按文件偏移查找页缓存：若缓存中已有该文件页，可直接建立映射；若没有，内核从文件系统读取数据填充页缓存，再映射给进程。因而文件映射页的“来源”是文件内容，其常驻副本通常由页缓存承载。

同一日志页还可能被多个进程映射，或被普通 `read` 读取；它们可以复用同一页缓存页。RSS 表示该进程当前映射并驻留的页，不应据此误认为进程独占了这些物理内存。相对地，匿名消息缓冲在首次写入后通常更接近该进程私有的工作集。

### 私有映射：写入触发写时复制

### 私有映射：写入触发写时复制

设聊天日志文件 `chat.log` 被以只读方式映射：

`mmap(..., PROT_READ | PROT_WRITE, MAP_PRIVATE, fd, 0)`

这里的“可写”只表示该进程允许写映射区，并不表示允许修改文件。初始阶段，映射页仍以文件页为来源：访问某段日志时发生缺页，内核把对应文件页放入页缓存，再将其映射到该进程页表。多个进程即使各自建立 `MAP_PRIVATE` 映射，在**只读**时也通常可以指向同一份文件页。

当程序首次写入某个页，例如把映射中的一个字节改为 `X`，流程发生分叉：

1. CPU 发现该页实际被设为只读，触发保护异常；
2. 内核为当前进程分配新的匿名页；
3. 将原文件页内容复制到该匿名页；
4. 当前进程的页表改指向匿名页，并允许写入；
5. 其他进程及原文件仍继续看到旧的文件页内容。

这就是写时复制（Copy-On-Write，COW）。因此，私有映射的 RSS 不能只理解为“文件占了多少内存”：未修改部分可能仍是可共享的文件页；被写过的页则成为该进程独占的匿名页，计入其私有内存压力。

若消息缓冲区采用匿名私有映射，例如：

`mmap(..., MAP_PRIVATE | MAP_ANONYMOUS, -1, 0)`

它本来就没有文件来源，首次实际访问时才获得匿名物理页；写入不会产生“回写文件”这一问题。

关键结论是：`MAP_PRIVATE` 的修改通常只存在于当前进程的匿名副本中，`munmap` 后即失去这份映射视图，原始 `chat.log` 不会因此被改写。即使修改在同一进程内立即可见，也不能据此推断文件内容已更新，更不能推断数据已经持久落盘。

### 共享映射：共享可见不等于耐久

### 共享映射：共享可见不等于耐久

`MAP_SHARED` 与 `MAP_PRIVATE` 的关键差别不在于“是否能写”，而在于写入后的页如何被其他映射和底层文件观察到。

| 映射方式 | 写入后的可见性 | 对底层文件的关系 |
|---|---|---|
| `MAP_SHARED` | 对同一文件同一区间的其他共享映射通常可见 | 修改的是文件页缓存中的相应页，之后可能回写文件 |
| `MAP_PRIVATE` | 仅当前进程的私有副本可见 | 首次写入触发写时复制，不改动底层文件内容 |

例如，聊天日志文件可被多个进程以只读方式映射；若某个写入者以 `MAP_SHARED` 映射日志区并修改字节，另一个映射同一页的读取者可能很快看到新内容。这里的“共享”描述的是内存页内容的可见性，而不是磁盘写入已经完成。

相反，消息缓冲区若用匿名 `MAP_PRIVATE` 映射建立，初始页可按需分配；某线程写入后获得自己的可写页，这些数据既不会进入文件，也不会自动被另一独立私有映射看到。

必须区分两个问题：

- **可见性**：其他共享映射、后续文件读取何时观察到修改，受页缓存、同步与并发协议影响。
- **耐久性**：修改何时真正抵达稳定存储，需讨论 `msync`、`fsync`、文件系统及设备缓存语义。

因此，看到 `MAP_SHARED` 中的新消息，只能说明相关内存内容已经可观察；不能据此宣称“聊天日志已经落盘”。

### fd、映射、页缓存与 RSS 的独立生命周期

### fd、映射、页缓存与 RSS 的独立生命周期

文件描述符、虚拟映射、页缓存和 RSS 彼此关联，却不共享同一个生命周期。`mmap` 成功后，内核已在该进程的虚拟地址空间登记一段映射；此后访问该地址不再依赖原来的 `fd` 仍然打开。

设聊天日志文件 `chat.log` 被只读映射：

`p = mmap(..., PROT_READ, MAP_PRIVATE, fd, 0)`

随后应用执行 `close(fd)`，再从 `p` 读取历史消息。这个纸上案例仍可正常工作：`close` 只释放该进程持有的文件描述符表项，减少一个打开引用；它**不会**撤销已有映射，也不会立刻丢弃映射所关联的文件对象和页缓存。

应分开理解四件事：

- `close(fd)`：不能再通过该整数进行 `read`、`write`、再次 `mmap` 等操作；已有映射通常继续有效。
- `munmap(p, len)`：删除该进程地址空间中的映射区间。之后访问 `p` 属于非法访问，而不是“重新从文件读取”。
- 页缓存：文件页的内核缓存，可被多个进程映射或普通 `read` 共享；即使某个进程 `munmap`，缓存页也可能因缓存策略、其他引用而继续存在。
- RSS：某进程当前驻留在物理内存中的映射页统计。映射存在不等于立刻计入 RSS；只有实际访问触发缺页、页面驻留后才可能计入。`munmap` 会使该进程不再把这段页计入 RSS，但不必然立即释放对应物理页。

因此，“关闭日志 fd 后仍能读映射”说明映射独立于描述符；“RSS 下降”也只说明该进程不再驻留或映射这些页，不能据此断言页缓存已经消失。

> **要点** — mmap 管理的是地址映射；页来源、共享标志和访问写入决定 RSS、可见性与文件关系，关闭 fd 不会解除映射。

文件被读取或映射后，内核页缓存、进程RSS与系统内存压力会呈现不同视角；先厘清“文件页归谁统计”，才能避免误判内存泄漏。

### 页缓存：文件内容的内核复用层

### 页缓存：文件内容的内核复用层

Linux 读取普通文件时，通常不会把磁盘数据直接交给调用者后立刻丢弃。内核会先将文件内容按页装入**页缓存**（page cache）：同一文件的同一偏移量，后续 `read`、预读或其他进程访问时都可复用已在内存中的页，避免再次进行磁盘 I/O。

例如，Go 程序执行：

`os.ReadFile("config.json")`

其中一部分数据会短暂进入 Go 堆中的 `[]byte`；但文件内容本身也可能继续保留在内核页缓存中。前者可随对象不可达、垃圾回收而释放；后者并不隶属于这个 `[]byte`、`os.File` 或任何 Go 对象。即使进程退出，若该文件页仍有缓存价值，页缓存仍可暂留并服务其他进程。

页缓存的关键属性是：

- **按文件与页偏移复用**：多个进程读取同一文件，通常共享同一批缓存页。
- **可回收**：发生内存压力时，干净的文件缓存可被内核回收；需要时再从磁盘读取。
- **不等于进程堆**：普通 `read` 产生的页缓存通常不必计入该进程 RSS；进程 RSS 增长更直接反映其地址空间中实际驻留的页。
- **写入也会经过它**：常规文件写入往往先修改页缓存中的脏页，再由回写机制落盘。

因此，看到系统“缓存”升高，不能直接推断 Go 堆泄漏，更不能把全部缓存归因给最近读取文件的进程。页缓存是内核管理的共享复用层；它会增加系统已用内存的表象，但其中相当一部分是可按需让出的文件数据缓存。

### 普通读取与文件映射的RSS差异

### 普通读取与文件映射的RSS差异

`read` 与 `mmap` 都可能让文件内容进入 Linux 页缓存，但它们把数据交给进程的方式不同，因而 RSS 变化也不同。

- **普通 `read`**：内核先从磁盘读取文件页，或直接命中已有页缓存；随后将数据复制到 Go 的用户缓冲区，例如 `[]byte`。页缓存本身通常不计入该进程 RSS，但这份用户缓冲区属于匿名内存，实际访问后会表现为 `RssAnon` 增长。  
  即使文件随后被关闭，页缓存仍可保留，供其他进程或后续读取复用；它是系统可回收缓存，不等于“该 Go 进程持有的 RSS”。

- **文件 `mmap`**：映射建立时通常只创建虚拟地址范围，不立即读入全部文件。进程首次访问某页时发生缺页，内核将对应页缓存页映射到该进程页表。此时该页可计入进程的 `RssFile`，而不是 `RssAnon`；通常无需再复制一份到 Go 堆缓冲区。

- **共享的统计陷阱**：同一文件页被多个进程映射时，每个进程的 RSS 都可能包含该页，因此 RSS 直接求和会重复计算。`Pss` 会按共享进程数分摊，更适合估计实际占用责任。

因此，`read` 常见模式是“页缓存 + 一份匿名用户缓冲区”，而 `mmap` 更接近“页缓存直接映射为文件 RSS”。前者更容易抬高 Go 进程匿名 RSS；后者则可能抬高 `RssFile`，但两者都可能给系统页缓存和容器内存压力带来影响。

### RssFile、共享页与Pss分摊

### RssFile、共享页与 Pss 分摊

设文件页 $F$ 已进入页缓存，并被进程 A、B 通过 `mmap` 映射。只有当某进程实际访问该页、产生缺页并建立页表映射后，$F$ 才会进入该进程的文件型驻留集合，通常反映为 `RssFile`。

若 $F$ 大小为 4 KiB，且 A、B 都已映射并访问它：

- A 的 `RssFile` 增加 4 KiB；
- B 的 `RssFile` 也增加 4 KiB；
- 两进程 RSS 相加为 8 KiB；
- 物理内存中实际仍只有一份 4 KiB 文件页。

这不是重复占用了两份页缓存，而是 RSS 的设计口径：它回答“该进程当前页表可访问多少驻留页”，不负责消除跨进程共享。因而把多个进程的 RSS 直接求和，常会高估系统实际使用的物理页，尤其是共享库、容器基础镜像和大量共同映射的数据文件。

Pss（比例集大小）改用分摊规则。若一页被 $n$ 个进程共享，则每个进程记为：

$$
\operatorname{Pss}(F)=\frac{4\text{ KiB}}{n}
$$

上例中 A、B 各获得 2 KiB Pss；两者相加恰为该页实际占用的 4 KiB。`smaps` 中的 `Shared_Clean`、`Shared_Dirty` 描述共享页的 RSS 分类，而 `Pss` 更适合估算“若按共享责任分账，该进程应承担多少内存”。不过，Pss 是归因视角，不表示进程退出时一定能立刻释放同等数量的物理内存：文件页仍可能作为页缓存保留，等待后续读取或在内存压力下回收。

### 匿名映射、私有写入与共享写入

### 匿名映射、私有写入与共享写入

三类映射都能形成虚拟地址区，但其“初始内容来自哪里、写入后归谁、能否回写文件”完全不同。

| 类型 | 首次读 | 首次写 | 写入结果 | 常见 RSS 口径 |
|---|---|---|---|---|
| 匿名映射 | 缺页后得到零页或匿名页 | 分配真实匿名页 | 无文件可回写 | `RssAnon` |
| `MAP_PRIVATE` 文件映射 | 通常从页缓存建立映射 | 写时复制（COW）出私有匿名页 | 私有副本不回写原文件 | 读前为 `RssFile`，写后新增/转为 `RssAnon` |
| `MAP_SHARED` 文件映射 | 映射文件页缓存页 | 直接修改共享页缓存页 | 脏页后续回写文件 | `RssFile` |

匿名 `mmap` 没有后备文件；即使申请了很大的地址范围，也通常要到首次访问才缺页。只读访问可能暂时映射内核的共享零页；真正写入时才需要独立的物理匿名页。因此，`mmap` 成功不等于 RSS 立刻增长。

`MAP_PRIVATE` 的关键是“读共享、写私有”。多个进程可读取同一文件页缓存页，物理页相同，但每个进程的 RSS 都可能计入该页；`Pss` 则按映射进程数分摊。某进程写入后，内核为该进程复制匿名页，原文件页保持不变：这部分私有副本通常表现为 `RssAnon`，也不会因文件回写而释放。

`MAP_SHARED` 则让写入落到共享的页缓存页。多个映射者随后可见修改；页面被标为脏页，内核在适当时机回写到底层文件。它在进程中通常仍属于 `RssFile`，但不能据此断言“该进程独占了这些内存”：同一页可被其他进程共享，也可被文件读取路径复用。

### 从smaps到容器压力的读数边界

### 从 smaps 到容器压力的读数边界

排查“内存上涨”时，应按由进程到系统的顺序阅读指标，而不要把任何单个数字直接等同于 Go 堆或泄漏。

1. **先看 `/proc/<pid>/status`：快速分类 RSS**
   - `VmRSS`：该进程当前驻留的总物理页视图。
   - `RssAnon`：匿名页，通常最接近 Go 堆、goroutine 栈、运行时元数据、匿名 `mmap` 等。
   - `RssFile`：文件映射驻留页，例如动态库、可执行文件、`mmap` 文件；它不等于“进程读过的文件总量”。
   - `RssShmem`：共享内存、tmpfs 等页。

   若 `VmRSS` 上升而 `RssAnon` 稳定，应优先怀疑映射文件或共享内存，而非 Go 对象未释放。

2. **再看 `/proc/<pid>/smaps`：定位到映射区间**
   `smaps` 按 VMA 展示 `Rss`、`Pss`、`Private_*`、`Shared_*`。`Pss` 将一张被 $n$ 个进程共享的物理页按约 $1/n$ 分摊，适合估算“该进程可归因的内存”，但不代表实际独占占用。多个进程的 `RssFile` 可以重复包含同一共享页，不能直接相加。

3. **最后看容器或系统指标：判断整体压力**
   容器的 memory usage 往往同时包含匿名页、文件页缓存、共享内存及部分内核记账。普通 `read` 填入页缓存后，文件内容可留在系统页缓存中，却未必出现在读取进程的 RSS；但它仍可能抬高容器使用量并参与内存回收压力。

因此，`status` 用于粗分类型，`smaps` 用于归因映射，容器指标用于判断资源边界是否承压。它们是不同统计口径，不应要求数值严格相加或相等。

> **要点** — 页缓存是系统复用文件页的机制；RSS记录映射驻留，Pss用于分摊共享页，二者都不等同于Go堆。

本节建立统一统计口径：Go 运行时指标描述堆状态，RSS 描述进程驻留页；两者相关，却不能互相替代。

### 先分清指标在测什么

### 先分清指标在测什么

以消息缓冲对象为例：服务持续接收消息、创建 `[]byte` 或结构体缓冲，处理后大部分对象变得不可达。此时不能把所有“内存指标”都理解为“当前仍被消息占用的内存”。

| 指标 | 测量对象 | 对消息缓冲的含义 |
|---|---|---|
| `HeapAlloc` | 当前已分配堆对象的估计大小 | 包含仍存活的缓冲，也可能包含**已不可达但尚未被 GC 清扫**的缓冲 |
| `TotalAlloc` | 进程启动以来累计分配的字节数 | 每次创建缓冲都会增加；即使随后释放，也不会回落 |
| `HeapSys` | runtime 向系统取得的堆虚拟地址空间 | 是堆可管理范围，不等于其中每页都已实际驻留 |
| RSS | 进程当前驻留在物理内存中的页 | 除 Go 堆外，还含 goroutine 栈、运行时元数据、代码/映射页、C 分配等 |

因此，消息高峰后 `HeapAlloc` 下降而 `TotalAlloc` 继续上升是正常现象：前者描述当前堆状态，后者描述历史分配流量。`HeapSys` 较大也不必然意味着 RSS 同样大；它首先表示地址空间预留。

进一步地，`HeapIdle - HeapReleased` 可视为 runtime 已空闲、但仍保留而未归还系统的 span；`HeapInuse - HeapAlloc` 则近似反映 size class 分配页中尚未装入对象的空间上界。它们适合提出“缓存了多少空闲堆空间”的假设，不能替代对 RSS、页回收或容器限制的实测。

### HeapAlloc 与 TotalAlloc 的时间含义

### HeapAlloc 与 TotalAlloc 的时间含义

`HeapAlloc`回答的是“运行时当前认为堆上有多少已分配字节”，但这里的“当前”并不等于“所有对象都仍可达”。垃圾回收采用并发标记—清扫：对象在标记结束后若不可达，逻辑上已死；但其所在 span 可能尚未完成清扫，字节仍可能暂时计入 `HeapAlloc`。因此它更接近**最近一次 GC 状态与后续分配活动共同形成的堆分配量**，不是精确的存活对象总和。

`TotalAlloc`则是进程启动以来累计向堆申请过的字节数：

\[
\text{TotalAlloc}(t+\Delta t)\ge \text{TotalAlloc}(t)
\]

它只增不减。即使对象很快死亡、GC 已回收其空间，历史分配仍保留在累计值中。两次采样的差值

\[
\Delta\text{TotalAlloc}
\]

可用于估计该时间窗内的分配吞吐或分配压力；若除以时间间隔，可得到近似分配速率。

诊断时应区分假设：

| 观察 | 可支持的假设 | 不能直接推出 |
|---|---|---|
| `TotalAlloc`快速增长，`HeapAlloc`平稳 | 分配频繁且对象较短命 | 当前堆泄漏 |
| `HeapAlloc`持续抬升，跨多个 GC 仍不回落 | 存活集可能增长 | 一定是泄漏 |
| `HeapAlloc`在 GC 后下降 | 部分此前分配已不可达并被回收 | RSS 会同步下降 |

因此，用 `TotalAlloc`看“累计做过多少分配”，用 `HeapAlloc`观察“当前堆状态的近似量”；两者都不是进程 RSS 的直接替代。

### 用玩具 span 推演堆的空闲状态

### 用玩具 span 推演堆的空闲状态

设运行时曾向操作系统预留了 `100` 页堆地址空间，即：

\[
\text{HeapSys}=100\text{ 页}
\]

这些页按 span 管理。下面的状态表是**推演模型**，用于建立口径，不代表某次真实采样。

| span 状态 | 页数 | 是否计入 `HeapInuse` | 是否计入 `HeapIdle` | 是否计入 `HeapReleased` |
|---|---:|---:|---:|---:|
| 正在分配对象的 span | 40 | 是 | 否 | 否 |
| 已分配 span 中的空闲槽 | 10 | 是 | 否 | 否 |
| 完全空闲但仍由运行时保留的 span | 30 | 否 | 是 | 否 |
| 完全空闲且已通知系统归还物理页的 span | 20 | 否 | 是 | 是 |

因此：

\[
\text{HeapInuse}=40+10=50\text{ 页}
\]

这里的 `10` 页不是独立空闲 span，而是混在仍在使用的 span 内部的空闲槽。它们不能立即整体归还给系统，所以仍计入 `HeapInuse`。这也是为什么 `HeapInuse` 往往大于实际存活对象占用的 `HeapAlloc`。

\[
\text{HeapIdle}=30+20=50\text{ 页}
\]

空闲 span 已不含已分配对象，运行时可以日后复用它们；其中只有一部分真正执行了归还：

\[
\text{HeapReleased}=20\text{ 页}
\]

于是始终满足：

\[
\text{HeapSys}=\text{HeapInuse}+\text{HeapIdle}=50+50=100\text{ 页}
\]

而：

\[
\text{HeapIdle}-\text{HeapReleased}=30\text{ 页}
\]

表示“逻辑上空闲、可能可归还、但当前仍保留”的堆页。它们可能仍对应 RSS，也可能因系统回收、延迟提交等原因与 RSS 不严格相等。

若进一步假设存活对象实际仅占 `35` 页，则：

\[
\text{HeapAlloc}=35,\qquad
\text{HeapInuse}-\text{HeapAlloc}=15
\]

这 `15` 页可视为 size class、span 对齐及空闲槽导致的未充分利用空间的估计上界；它不是泄漏证据，而是分配粒度与碎片化的成本。

### 从堆统计走向 RSS 的边界

### 从堆统计走向 RSS 的边界

`HeapAlloc`、`HeapSys`回答的是 Go 运行时堆的状态；RSS 回答的是“此进程当前实际驻留在物理内存中的页”。二者不能按一条固定公式换算。可先用下表建立诊断假设：

| 来源 | 与 Go 堆统计的关系 | 对 RSS 的典型影响 |
|---|---|---|
| Go 活对象与尚未清扫的死对象 | 主要体现在 `HeapAlloc` | 已触碰的堆页通常计入 RSS |
| 堆空闲 span | 可位于 `HeapIdle-HeapReleased` | 未释放给内核时，可能仍驻留；释放后 RSS 可下降 |
| size-class 内部碎片 | 上界可由 `HeapInuse-HeapAlloc` 估计 | 所在页仍可能驻留，故 RSS 高于活对象大小 |
| goroutine 栈 | 不属于 `HeapAlloc` | 栈增长、缩容滞后或大量 goroutine 都会推高 RSS |
| 运行时元数据 | 不等同于用户堆对象 | `mspan`、位图、调度与 GC 辅助结构会占页 |
| 匿名映射 | 常不在堆统计中 | `mmap`、分配器映射、原生库缓冲区可直接增加 RSS |
| 文件映射与页缓存 | 不属于 Go 堆 | 访问映射文件后页面可驻留；是否计入 RSS取决于映射和统计口径 |

因此，`RSS - HeapAlloc` 并不自动等于“内存泄漏”。它可能是栈、堆碎片、未归还的空闲页、运行时开销，或 Go 之外的映射与库分配。反过来，`HeapSys` 很大也不必然意味着 RSS 很大：它首先表示堆虚拟地址空间的预留，未触碰或已 `Released` 的页未必驻留。

`GOMEMLIMIT`限制的是运行时愿意管理的内存目标，并非 cgroup 限额，更不是 RSS 硬上限。诊断时应并列观察堆指标、`Stack*`、映射信息与 cgroup/进程 RSS；状态表用于提出可验证的解释，不能替代实际测量。

### 用假设诊断异常内存曲线

### 用假设诊断异常内存曲线

不要只看某一条曲线是否“高”，而要观察 `HeapAlloc`、`HeapSys`、`HeapReleased` 与 RSS 的组合关系，形成可验证的诊断假设：

| 观察组合 | 初步假设 | 下一步验证 |
|---|---|---|
| `HeapAlloc` 持续上涨，RSS 同步上涨 | 对象确实仍被引用，可能存在 Go 堆泄漏或缓存无界增长 | 对比 heap profile、对象类型与引用链 |
| `HeapAlloc` 回落，但 RSS 不回落 | GC 已识别不可达对象，但页仍在 Go 堆中保留，或存在碎片、页未归还 | 看 `HeapSys-HeapReleased`、触发 GC 后复测 |
| `HeapSys` 上涨，`HeapAlloc` 平稳 | 运行时扩堆、span 空闲或 size-class 碎片增加 | 估计 `HeapInuse-HeapAlloc`，检查分配尺寸分布 |
| `HeapReleased` 上涨，RSS 仍高 | Go 已建议内核回收部分空闲页；高 RSS 可能来自尚未回收的页、栈、映射或 C 分配 | 检查 `/proc` 映射、匿名页及 cgo 库 |
| RSS 上涨而 Go 堆指标平稳 | 增长主要不在 Go 托管堆 | 排查 goroutine 栈、`mmap`、文件页缓存、cgo/系统库内存 |

这里的差值只能帮助定位：`HeapSys` 是 Go 堆预留的虚拟地址范围，不等于物理驻留；`HeapIdle-HeapReleased` 表示可能归还但仍保留的空闲 span；`HeapInuse-HeapAlloc` 可近似视为 size-class 等造成的未用空间上界。并且 `HeapAlloc` 可能暂含尚未清扫的不可达对象，`TotalAlloc` 则是累计分配量，不能用于判断当前占用。

`GOMEMLIMIT` 约束的是运行时管理内存的目标与 GC 节奏，不是 RSS 上限，更不是 cgroup 的硬限制。若进程还有栈、映射、cgo 或内核计费页，即使 Go 堆努力受限，RSS 仍可能超过该值；最终是否被限制或杀死，应以 cgroup 配额与实际 RSS 为准。

> **要点** — Heap 指标反映运行时堆状态，RSS反映进程驻留页；必须结合时间差、映射类型和非 Go 内存解释。

以一条虚构 IM 消息的生命周期为线索，建立从 Go 引用、堆对象到 Linux RSS 的分层心智模型，并用图表辨析各统计口径。

### 四层对象视图：引用、堆、地址空间与 RSS

### 四层对象视图：引用、堆、地址空间与 RSS

分析内存前，先把“对象占了多少内存”拆成四层；它们相关，但绝不能互相替代：

1. **引用层**：变量、字段、切片头、映射桶等保存指针或间接索引，决定对象是否仍可达。  
   `msg := &Message{...}` 中，`msg` 本身只是一个引用；它指向的 `Message`、其字符串数据、切片底层数组可能是多个独立对象。

2. **Go 堆层**：运行时为对象分配的堆空间。一个逻辑消息通常对应对象图，而非一块连续内存：  
   `Message → []byte 底层数组 → 子对象`。垃圾回收依据引用可达性回收这里的对象。

3. **进程虚拟地址空间层**：Go 堆只是进程地址空间中的一部分。地址空间还可包含 goroutine 栈、运行时元数据、共享库、代码段、文件映射、匿名映射及预留但未使用的区域。它描述“可寻址范围”，不等于已使用物理内存。

4. **RSS 层**：Resident Set Size，即当前实际驻留在物理内存中的页。虚拟页只有被访问后才可能进入 RSS；已映射的页也可能尚未驻留，或之后被内核换出、回收。

可用包含关系理解：

`引用图` → 决定 `Go 堆对象存活` → 位于 `虚拟地址空间的一部分` → 其中部分页当前计入 `RSS`

但箭头不是等号。例如：

- 对象已不可达，短时间内仍可能占据堆页和 RSS，直到 GC 与页回收发生。
- `HeapAlloc` 增长通常表示存活堆对象增多，却不能直接推出 RSS 等量增长。
- 一块已保留的堆地址空间可计入 `HeapSys`，但其中未触碰的页未必进入 RSS。
- RSS 还可能包含非 Go 堆内容，因此 RSS 高不必然说明 Go 对象泄漏。

排查时应先问：增长发生在“引用、堆、地址空间、还是驻留页”中的哪一层；跨层直接下结论，往往会误判。

### 消息切片的引用图与 t0—t3 生命周期

### 消息切片的引用图与 t0—t3 生命周期

设接收缓冲区 `buf` 读入一条 64 KiB 的网络数据，其中前 200 B 是一条 IM 消息：

```go
msg := buf[:200]
queue = append(queue, msg)
```

切片并不复制字节。`msg` 只是一个三元描述符：`{数据指针, 长度, 容量}`；其数据指针仍指向同一块 64 KiB 底层数组。因此引用关系是：

`queue → msg 切片头 → 64 KiB 底层数组`

即使业务只需 200 B，只要 `queue` 中的 `msg` 存活，整块数组都不能被 GC 回收。若改为：

```go
msg := append([]byte(nil), buf[:200]...)
```

则形成新关系：

`queue → 200 B 新数组`，而原 64 KiB 缓冲若无其他引用即可被回收。

| 时刻 | 程序事件 | 原 64 KiB 数组的可达性 | 物理页与 RSS 的可能表现 |
|---|---|---|---|
| t0 | `buf` 读入数据 | 被 `buf` 引用 | 页已被触碰，可能计入 RSS |
| t1 | `msg := buf[:200]` 并入队 | 仍被 `buf`、`msg` 引用 | 不能释放；“只留小消息”不等于只占小内存 |
| t2 | `buf = nil`，消息仍在队列 | 仍被 `msg` 引用 | 数组继续存活 |
| t3 | 队列删除消息，GC 标记清扫 | 变为不可达 | 对象可进入空闲空间；页未必立刻归还系统，RSS 未必同步下降 |

关键时间差有两层。第一层是“引用消失”到“GC 发现不可达”：对象不会因执行 `queue = queue[1:]` 而立即释放。第二层是“对象已清扫”到“RSS 下降”：运行时可能复用这块空间，而非立刻将其对应页交还内核。

还要警惕截短后的残留引用。若队列元素是指针或切片，单纯缩短长度可能使底层数组中旧元素仍保留指针；应在必要时置零：

```go
queue[0] = nil
queue = queue[1:]
```

这里置零切断的是 Go 引用图；GC、运行时页管理与 RSS 统计何时响应，仍是后续阶段的问题。

### 玩具 span：空闲槽、碎片与未归还页面

### 玩具 span：空闲槽、碎片与未归还页面

设一个 span 恰好占用一个 `4KiB` 页，被切成 8 个、每个 `512B` 的槽位。某时其中 6 个槽位存放仍被引用的 Go 对象：

```text
4KiB 页 / span
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ A  │ B  │ C  │ D  │ E  │ F  │ 空 │ 空 │
└────┴────┴────┴────┴────┴────┴────┴────┘
 512B × 8，已分配 3072B，空闲 1024B
```

当 `B`、`D`、`F` 失去所有引用，垃圾回收后，它们对应的对象可以被回收：

```text
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ A  │ 空 │ C  │ 空 │ E  │ 空 │ 空 │ 空 │
└────┴────┴────┴────┴────┴────┴────┴────┘
```

此时，存活对象从 `3072B` 降到 `1536B`，因此 `HeapAlloc` 应下降。但这个页仍含有 `A`、`C`、`E`；运行时不能把整页交还给操作系统，否则会丢失存活对象。页仍属于 Go 堆的保留空间，故 `HeapSys` 通常不变；该页此前已被访问并驻留物理内存时，进程 `RSS` 也通常不变。

关键不在“对象已释放”，而在“页是否完全空闲”：

| 状态 | HeapAlloc | HeapSys | RSS |
|---|---:|---:|---:|
| 释放部分槽位 | 下降 | 通常不变 | 未必下降 |
| span 全部槽位空闲 | 下降 | 可暂不变 | 可能仍不变 |
| 空闲页被运行时归还或解除驻留 | 不变 | 可能下降 | 可能下降 |

碎片就是这种“空闲槽散落在仍有存活对象的页中”的现象。它会让逻辑上的对象内存已经减少，却暂时无法转换成可释放的整页；因此不能仅凭 `HeapAlloc` 下降，就断言进程 RSS 会立刻下降。

### 匿名映射与文件映射的私有共享差异

### 匿名映射与文件映射的私有共享差异

`mmap` 的关键不是“是否占用地址”，而是页面的**来源、写入后的归属，以及修改能否被其他映射者或文件看到**。同一段虚拟地址，在 RSS、页缓存和文件持久化中的意义可能完全不同。

| 映射类型 | 初始页面来源 | 写入后的页面归属 | 其他进程可见 | 回写文件 | 常见用途 |
|---|---|---|---|---|---|
| 匿名私有映射 | 无文件；按需分配匿名页 | 进程私有匿名页 | 不可见 | 不适用 | Go 堆、栈、运行时元数据 |
| 文件私有映射 `MAP_PRIVATE` | 文件页缓存 | 首次写入触发写时复制，变为私有匿名页 | 原始文件页可共享；私有修改不可见 | 不回写原文件 | 读取文件并局部修改、装载程序段 |
| 文件共享映射 `MAP_SHARED` | 文件页缓存 | 仍关联共享文件页 | 可见，映射同一文件页者可观察修改 | 可回写文件 | 共享数据文件、进程间通信 |
| 匿名共享映射 | 无文件；共享匿名页或共享内存对象 | 共享页 | 可见 | 不适用 | 共享内存、部分运行时协作结构 |

可以把 `MAP_PRIVATE` 理解为“先共享、写时分叉”。例如两个进程都私有映射同一个文件的某个 4KiB 页：未写入时，它们可能共同引用同一页缓存页；进程 A 写入 1 字节后，内核为 A 复制出一个匿名页。于是：

- A 的 RSS 可能增加一个私有页；
- 原文件内容不变；
- B 仍读到原始页缓存内容；
- 该页的物理内存不再能简单按“文件大小”或“映射长度”估算。

相对地，`MAP_SHARED` 的写入修改共享文件页：A 写入后，B 的同一映射通常可见该变化；脏页随后可能由内核回写到底层文件。这里“共享”描述的是页面语义，不表示每个进程的 RSS 都为零：每个进程都可能在自身 RSS 统计中显示该驻留页，跨进程求和会重复计数共享物理页。

因此，分析 RSS 时应先问：该页是匿名页、文件页缓存，还是私有写时复制后的匿名副本？仅看到“某进程 RSS 增长”，不能直接推出文件变大、Go 堆增长，或系统新增了等量独占物理内存。

### 统计口径矩阵与综合判读练习

### 统计口径矩阵与综合判读练习

先区分“Go 仍认为在用”“Go 向操作系统保留”“Go 已归还但地址空间可能仍在”“物理页驻留”：

| 指标 | 表示什么 | 不直接表示什么 |
|---|---|---|
| `HeapAlloc` | 当前存活堆对象占用 | 堆向系统申请的总量、进程 RSS |
| `HeapSys` | Go 堆已保留的地址空间规模 | 全部已驻留物理页 |
| `HeapReleased` | Go 已建议系统回收的堆页 | RSS 必然立刻下降 |
| RSS | 当前驻留物理内存页，含堆、栈、代码、运行时、映射等 | 仅 Go 堆对象大小 |

可用近似关系建立直觉：  
`HeapAlloc ≤ HeapSys`；可供 Go 复用的堆空间大致为 `HeapSys - HeapAlloc - HeapReleased`。RSS 还会受 goroutine 栈、运行时元数据、文件映射、共享页计账方式影响。

#### 纸上判读：22 题

1. `HeapAlloc` 上升，说明？  
   **答：**存活 Go 堆对象增加；不等于 RSS 必涨同量。

2. `HeapAlloc` 下降而 RSS 不变？  
   **答：**对象已死，但页可能仍由 Go 保留或仍驻留。

3. `HeapSys` 很大、`HeapAlloc` 很小？  
   **答：**堆曾扩张，现有大量保留或空闲页。

4. `HeapReleased` 上升意味着泄漏消失？  
   **答：**不一定；只说明部分堆页已交还策略处理。

5. RSS 大于 `HeapSys` 是否异常？  
   **答：**不异常；RSS 包含非堆内存与映射。

6. RSS 增长、`HeapAlloc` 平稳？  
   **答：**检查栈、运行时、`mmap`、文件页或 C 分配。

7. `HeapAlloc` 增长后 GC 回落？  
   **答：**常见短生命周期分配，不足以证明泄漏。

8. 多轮 GC 后 `HeapAlloc` 单调增长？  
   **答：**优先怀疑仍被引用的对象图。

9. RSS 下降慢于 `HeapAlloc`？  
   **答：**正常可能性高：页回收与驻留并非同步。

10. 私有匿名映射写入一页会怎样？  
    **答：**该页通常计入本进程 RSS。

11. 共享文件映射的页只属于一个进程吗？  
    **答：**物理页可共享；各工具的进程归属口径需谨慎。

12. 读取映射文件会立刻让整个文件进 RSS 吗？  
    **答：**通常按实际触及页面驻留。

13. `HeapReleased` 增、RSS 不降的合理解释？  
    **答：**回收延迟、其他区域增长或统计时点不同。

14. `HeapSys` 下降一定代表 RSS 下降？  
    **答：**不一定；两者对象范围不同。

15. 一个 4KiB 页内只剩 1 字节存活对象，页能立刻归还吗？  
    **答：**通常不能；该页仍含存活引用。

16. 碎片主要影响哪一层？  
    **答：**堆页复用与归还效率，可间接抬高 RSS。

17. 删除 map 条目后内存为何未马上降？  
    **答：**对象可达性、桶容量、GC 时机和页碎片都可能影响。

18. 缓存保留对象属于泄漏吗？  
    **答：**语义上未必；若无上界或超出预算，运营上仍是问题。

19. 判断“泄漏”最有力的观察？  
    **答：**稳定负载下，经 GC 后存活对象及其引用链持续增长。

20. 仅凭 RSS 曲线能定位 Go 泄漏吗？  
    **答：**不能；必须与堆指标、对象类型和引用关系交叉验证。

21. `HeapAlloc` 小但 RSS 高，第一结论应是什么？  
    **答：**“存在非存活堆对象因素”，而非立即认定泄漏。

22. 综合判读顺序？  
    **答：**先看存活对象（`HeapAlloc`），再看堆保留/归还（`HeapSys`、`HeapReleased`），最后解释 RSS 中的非堆与映射部分。

> **要点** — 对象是否可达决定可回收性；页是否复用或归还决定堆统计与 RSS 是否变化。
