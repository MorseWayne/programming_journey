## 教学重组

- 先补路径名、目录项、inode、硬链接与设备号，再讲进程 FD 表到打开文件描述的第二级引用；名称查找与已打开对象分开。
- 初始日志固定 `m-a\nm-b\n` 共 8 字节。`fd7` 从偏移 0 读 4，`dup` 得 `fd8` 并共享 O1 读后偏移 8；独立 `open` 得 `fd9→O2`，从偏移 0 读后关闭，保证后续删除案例只有 fd7/fd8 继续引用旧 inode。
- 顺序固定为 `rename` 旧路径、创建新路径 I2、旧 fd7 继续写 I1、删除 `.1`、逐一关闭 fd7/fd8；每个时刻用表格列明路径与 FD 目标。
- 22 道自检题从名字与 inode、偏移、轮转空档、已删除仍打开，到短读写和持久性边界逐步推进。

## 技术修订

- 原稿反复切换 `fd3/fd4`、`app.log` 等图例，且有一段写“fd7、fd8 可能是两次独立 open”，与固定 `dup(fd7)` 案例的共享偏移矛盾。正式页仅保留一条一致的引用链与操作顺序。
- 原稿有“`rename(chat.log,chat.log.1)` 后 `chat.log` 不经历消失”的措辞，混淆**单次 rename 对目标名的原子可见性**和**rename 后再创建原名的两步流程**。正式页明确两步之间原路径暂不存在；两步不是一个事务。
- 原稿对 `unlink` 后的数据回收有多种重复表述，正式页标清最后硬链接、最后打开引用及其他映射等条件；`fd9` 在删除前已关闭，避免遗漏引用。
- `read/write` 的返回值是实际处理字节数；4 字节整行和旧 fd 写入都是明确的纸上成功假设，不被当作通用 API 保证。
- `O_APPEND` 的单次写入末尾定位不等于多次写组成的业务消息原子性；`rename` 可见性也不等于崩溃耐久性。`fsync` 与目录同步留给 03.08。
- inode 数字只在所属文件系统内有标识意义；比较不同文件身份应考虑设备号。Go `os.Rename` 的跨平台行为没有从 Linux 手册直接推广。
