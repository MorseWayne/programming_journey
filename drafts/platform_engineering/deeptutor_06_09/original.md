消息发送后界面显示成功，并不等于消息已具备可恢复性。本节以PostgreSQL为教学路径，拆解从写入到对端收到之间的持久化边界。

### 一条消息的四个完成时刻

### 一条消息的四个完成时刻

“发送成功”至少可能指四个不同事件，不能混为一谈。以下以 PostgreSQL 中保存消息记录、服务端再向 B 设备投递为教学路径：

1. **`INSERT` 返回**：数据库已接受插入语句，并可能已生成消息 ID；但若仍在事务中，这条记录尚未对其他事务正式可见。此时进程崩溃、事务回滚或连接异常，都可能使记录消失。

2. **`COMMIT` 完成**：事务提交成功，消息记录成为数据库的一致性结果。若 PostgreSQL 已按持久化语义确认提交，崩溃恢复后应能从数据库找回该消息；但这只证明“服务端已记账”，不证明已投递。

3. **HTTP `200` 返回**：接口服务已经把“成功”告知发送方。它通常应建立在 `COMMIT` 成功之后，否则会出现“客户端看到成功、消息却未入库”的风险。`200` 仍只是发送端与服务端之间的确认。

4. **B 设备实际收到**：消息已到达 B 的某个客户端实例，并被其接收层处理。这要求服务端在提交后完成路由、连接推送或离线同步；网络中断、设备离线、应用被杀死都可能使其晚于 HTTP `200` 很久。

因此，责任边界应写清：`COMMIT` 解决“能否恢复”，HTTP `200` 表示“服务端是否已接受”，而 B 收到才对应“是否完成送达”。若还要证明用户看见或阅读，则需要额外的客户端回执，不能从前述任一时刻推断。

### WAL为何必须先于数据页

### WAL为何必须先于数据页

PostgreSQL 中，消息行被 `INSERT` 后通常先进入共享缓冲区，所在数据页成为脏页；它不必立刻写回表文件。延迟写页能合并随机写、提高吞吐，但也引入崩溃窗口：内存中的修改可能尚未落盘，而磁盘上的数据页又可能只写到一半。

因此必须满足**预写式日志**规则：

$$\text{数据页写入磁盘之前} \Rightarrow \text{描述该修改的 WAL 已持久化}$$

一次消息写入可抽象为以下顺序：

1. `INSERT` 修改缓冲池中的数据页，并生成对应的 WAL 记录；
2. WAL 先写入日志缓冲区，数据页继续作为脏页留在内存；
3. `COMMIT` 再生成一条提交记录；
4. 当事务需要被确认提交时，系统将至少刷到该提交记录对应位置的 WAL；
5. 此后，即使数据页尚未落盘，也可以向调用方报告事务已提交；
6. 后台写入器可在更晚时候把脏页写回数据文件，但写页前仍须保证相关 WAL 已刷盘。

若在第 4 步之后、第 6 步之前宕机，表文件可能还看不到那条消息；恢复时 PostgreSQL 从 WAL 重放已提交事务，重新得到该行。反过来，若数据页先于 WAL 落盘，宕机后磁盘可能留下无法解释的半条修改，恢复既无法可靠重做，也难以判断其是否属于已提交事务。

所以，`INSERT` 返回通常只说明语句执行成功；`COMMIT` 完成并不自动等于客户端已收到结果；而只有提交记录按配置完成所需的 WAL 持久化后，数据库才能把该消息视为可通过崩溃恢复找回。HTTP 200 与 B 设备收到消息，则仍是数据库边界之外的后续事实。

### 沿C0—C5时间线手算结果

### 沿 C0—C5 时间线手算结果

设服务端执行一条消息写入事务：`INSERT message(...)`，随后 `COMMIT`，再向客户端返回 HTTP `200`。以下假设 PostgreSQL 默认开启 `fsync`，并以 WAL 作为崩溃恢复依据。

- **C0：收到发送请求，尚未执行 `INSERT`**  
  此时崩溃，数据库没有该消息；重试可能安全，但应由业务幂等键避免重复发送。

- **C1：`INSERT` 已执行，数据页成为脏页，但事务未提交**  
  行记录可能已在共享缓冲区，甚至产生了对应 WAL；但未提交事务对其他会话不可见。崩溃恢复会回滚它，因此消息不可恢复为“已发送”。

- **C2：执行 `COMMIT`，提交记录已写入 WAL 缓冲区，尚未刷盘**  
  服务进程内可能认为已提交，但机器断电时 WAL 可能丢失。重启后该事务不保证存在，不能据此返回成功。

- **C3：提交记录及此前 WAL 已刷入持久介质，`COMMIT` 成功返回**  
  即使消息所在的数据页尚未回写，崩溃恢复也会通过 WAL 重放已提交事务。消息在数据库意义上可恢复、可查询；这才是服务端“已持久提交”的关键边界。

- **C4：服务端已提交，但 HTTP `200` 尚未到达发送方**  
  崩溃或网络中断后，发送方会看到超时或失败；但数据库中消息可能已存在。这是“提交未知”场景，必须用客户端消息标识查询或幂等重试，不能直接再次插入。

- **C5：HTTP `200` 已返回，随后数据页回写完成或未完成**  
  数据页是否已经落盘不改变 C3 的可恢复性：只要 WAL 提交已持久化，恢复时仍可重放。HTTP 成功仅说明服务端已确认提交，不自动证明 B 设备已经收到。

因此，`INSERT` 成功、`COMMIT` 返回、HTTP `200`、B 设备收到分别对应不同边界；本时间线仅用于理解 PostgreSQL 持久化，不代表任何具体即时通信系统的实现。

### REDO、检查点与恢复起点

### REDO、检查点与恢复起点

PostgreSQL 不会在崩溃后从数据库创建时的第一条日志开始恢复。它利用**检查点**缩短恢复范围：检查点时，系统尽量将此前已修改的脏页写回数据文件，并记录一个检查点 WAL 位置。此后若发生宕机，恢复通常从该检查点附近的 WAL 开始扫描。

可将过程理解为：

1. 事务修改页面时，先生成 WAL 记录，再允许相应脏页落盘；这就是预写日志规则。
2. 检查点推进时，部分或全部旧脏页被刷入表、索引等数据文件。
3. 崩溃后，数据文件可能只包含一部分较新的修改，但 WAL 中保留了更完整的历史。
4. 恢复进程读取检查点信息，重放其后的 WAL，使页面达到崩溃前可确认的一致状态。

这里的“重放”常被称为 **REDO**：把日志中已经记录、但可能尚未进入数据页文件的变化重新施加。即使某些页面其实已经写入，重放也必须保持幂等性，不能把同一修改重复造成错误。

但不要把 PostgreSQL 的恢复机械地理解为“REDO 加通用 UNDO”。许多数据库教材中的 UNDO 指回滚未提交事务的页级改动；PostgreSQL 主要依赖 MVCC 元组版本、事务状态与 WAL 恢复规则处理可见性和异常事务，并非简单地对每条未提交更新做通用反向页修改。

因此，`COMMIT` 对应的 WAL 已安全持久化，才是崩溃后可恢复提交的关键边界；`INSERT` 返回、脏页存在内存，甚至数据页已偶然落盘，都不能单独证明该消息一定能恢复。

### 同步提交并非跨设备承诺

### 同步提交并非跨设备承诺

以 PostgreSQL 为例，`COMMIT` 成功通常表示：事务产生的 WAL 已按当前配置达到可承诺的持久化边界。默认的 `synchronous_commit=on` 会在返回前等待本机 WAL 刷入稳定介质；`fsync=on` 则要求数据库使用操作系统提供的刷盘语义，而不是只停留在页缓存中。

但“已刷盘”仍不是绝对的物理承诺。写入路径大致是：

`事务记录 → WAL 缓冲区 → 内核页缓存 → 磁盘控制器缓存 → 稳定介质`

若磁盘、控制器或虚拟化平台谎报写入完成，突然断电时仍可能丢失最近的提交。因此，PostgreSQL 的同步提交是在其存储与 `fsync` 假设成立时，承诺**本机可通过 WAL 崩溃恢复**，并不承诺：

- 业务已向用户返回 HTTP 200；
- 消息已被推送服务取走；
- B 设备已收到、展示或确认；
- 异地副本已经存在。

` synchronous_commit=off` 会让 `COMMIT` 先返回、WAL 稍后刷盘；进程崩溃通常可恢复，但断电可能丢失一小段已向业务报告成功的事务。它适合可重试、可容忍少量尾部丢失的记录，不适合作为消息“绝不丢失”的唯一依据。

不同数据库的措辞相近，边界却必须分别核对：

| 系统 | 提交/日志语义 | 主要恢复范围 |
|---|---|---|
| PostgreSQL | WAL、`fsync`、可选同步复制 | 本机崩溃恢复；同步备库可扩展到副本确认 |
| SQLite | 回滚日志或 WAL，`synchronous` 控制同步强度 | 单文件数据库的一致性恢复，不代表文件已异地复制 |
| MongoDB | journal 与写关注级别 `writeConcern` | 可要求主节点日志确认，或多数副本确认 |

备份也不是实时副本：它通常只能恢复到备份点，或结合归档日志恢复到某个时间点。故“INSERT 已返回”“COMMIT 已完成”应被记录为数据库状态；只有投递记录、设备回执等独立证据，才能分别说明 HTTP 返回与 B 设备收到。

> **要点** — 数据库提交可保证已确认日志的恢复，却不等同于HTTP成功、消息投递成功或对端设备已收到。

消息提交后的可恢复性，取决于修改是否先被可靠地写入预写日志，而非数据页是否已立即落盘。

### 从一条消息拆分四个确认时刻

### 从一条消息拆分四个确认时刻

一次“发送消息”看似只有一个成功结果，实际上至少经历四个不同的确认时刻：

1. **执行 `INSERT`**：数据库在事务中生成一条新记录，修改通常先落在内存中的共享缓冲区。对应的数据页变为 `dirty`（脏页）：内存版本已经更新，但数据文件中的页面未必变化。

2. **执行 `COMMIT`**：事务提交时，PostgreSQL 需要确保描述这次修改的 WAL 记录已达到配置要求的持久化边界。同步提交通常意味着：提交记录及此前相关 WAL 已经写出，并完成必要的 `flush`，然后事务才被视为成功。这里持久化的是**日志**，不是刚才那张数据页。

3. **服务返回 HTTP 成功响应**：应用只有在拿到数据库提交成功后，才应向客户端返回“消息已发送”。此时即使机器突然崩溃，恢复过程也能从 WAL 重做这条 `INSERT`；因此“已提交”不等于“数据页已经落盘”。

4. **设备确认持久化**：WAL 的 `write` 可能只是进入操作系统缓存；`flush`/`fsync` 才是在要求操作系统和存储设备把数据推进到稳定介质。数据库的可靠性还依赖一个前提：设备对持久化完成的响应必须诚实，不能在实际未持久化时提前确认。

之后，后台写进程会在合适时机把脏数据页写回数据文件。只要遵守 WAL 规则：**相关 WAL 必须先于数据页持久化**，崩溃恢复就能用日志补回已提交但尚未写入数据页的修改。

### 预写日志为何必须先于数据页

### 预写日志为何必须先于数据页

一次更新并不会直接改写磁盘中的表页。典型顺序是：

1. 为修改生成一条 WAL（预写日志）记录，例如“事务 `T` 将页 `P` 中的某行从 `a` 改为 `b`”；
2. 在共享缓冲区中修改数据页，数据页成为 `dirty`（脏页），并标记其对应的日志序号 `pageLSN`；
3. 日志先写入 WAL 缓冲区，再按需要写入操作系统缓存与持久存储；
4. 只有当 WAL 已经持久到覆盖该页 `pageLSN` 的位置后，脏页才允许被写回数据文件。

核心约束可写成：

$$\operatorname{flush}(P)\Rightarrow \operatorname{flush}(\mathrm{WAL}_{\le pageLSN(P)})$$

原因在于：若数据页先落盘、日志尚未可靠持久，机器随后崩溃，就会出现“磁盘上已有部分修改，但恢复时没有足够日志解释、重做或回滚它”的状态。反之，日志先持久，即使脏页尚留在内存，崩溃后也可根据 WAL 重做已提交修改，或撤销未提交修改。

因此，提交时通常需要等待 WAL 达到配置要求的持久化边界；但不必等待每个被修改的数据页刷盘。数据页可由后台写入器稍后批量回写，甚至在提交后很久才落盘。恢复能力依赖的是“日志先行”，不是“数据页立即落盘”。

### 缓冲区、操作系统缓存与存储刷新

### 缓冲区、操作系统缓存与存储刷新

一次“写数据”通常要穿过多层缓冲，不能把 `write()` 成功直接理解为“已经安全落盘”。

- **数据库缓冲区**：数据库先在内存中的共享缓冲区修改数据页，并将其标记为脏页（`dirty page`）。此时修改仅存在于数据库进程内存；进程崩溃或机器断电都可能丢失。
- **操作系统页缓存**：数据库调用 `write()` 写 WAL 或数据页后，内核往往只是把内容放入 OS cache，并在稍后异步回写设备。`write()` 返回通常只表示“内核接受了数据”，不表示介质已持久化。
- **设备缓存**：内核将数据交给磁盘、SSD 或存储控制器后，设备也可能暂存在自身缓存中。若缓存尚未受断电保护，突然掉电仍可能丢失已经“写成功”的内容。
- **存储刷新**：`fsync()`、`fdatasync()` 或等价的刷新请求，要求操作系统推动此前写入的数据到达配置所承诺的持久化边界；设备需要执行相应的缓存刷新或写屏障。

因此，WAL 的关键顺序不是“先把数据页写盘”，而是：

1. 先生成并写入描述修改的 WAL 记录；
2. 在允许相关脏数据页持久化前，确保其对应 WAL 已经被刷新；
3. 对同步提交，提交记录还必须被刷新到配置要求的 WAL 持久边界，才能向客户端确认成功。

数据页可以晚得多才刷出；崩溃后，PostgreSQL 可依据已持久化的 WAL 重放这些修改。反过来，若数据页先落盘而 WAL 尚未持久化，恢复时便可能看到无法解释或无法修复的页面状态，这正是 WAL 规则要避免的情况。

这里还隐含一个工程前提：操作系统、驱动和存储设备必须诚实地执行并确认刷新语义。若设备谎报 `flush` 已完成，或关闭了无断电保护的写缓存，那么即使 PostgreSQL 调用了 `fsync()`，断电恢复保证也会被底层硬件破坏。

### 同步提交承诺的真实边界

### 同步提交承诺的真实边界

同步提交承诺的不是“提交后数据页已经写入表文件”，而是：在客户端收到成功响应前，该事务的提交记录及其所需的 WAL 已跨过配置要求的持久化边界。崩溃后，即使相关数据页尚未落盘，恢复过程仍可重放 WAL，重新得到已提交的修改。

可将几种情形区分为：

- **同步提交**：提交会等待 WAL `flush`。通常这意味着日志已由数据库写入操作系统，并要求操作系统与存储设备确认其达到稳定介质；是否还要等待复制节点确认，取决于同步复制配置。客户端收到成功后，系统承诺该提交可在崩溃恢复中找回。
- **异步提交**：事务提交记录可能只停留在 WAL 缓冲区、操作系统页缓存，或已写出但尚未 `flush`。客户端可先收到成功；若主机断电或系统崩溃，最近一小段时间内已确认的事务可能丢失，直到后台 WAL 刷盘器完成持久化。
- **仅写入 WAL 不等于持久化**：`write` 常只是把 WAL 从数据库缓冲区交给操作系统缓存；`flush` 才是请求将此前日志稳定化。前者提高吞吐，后者建立提交的崩溃恢复边界。
- **数据页可延后刷新**：被修改的缓冲页先标记为 dirty，之后由后台写入器或检查点批量写回。WAL 规则只要求：某个 dirty 数据页真正落盘前，描述该页修改的 WAL 必须已先持久化；它不要求每次 `COMMIT` 都刷新该事务的数据页。

因此，同步提交的关键等待对象是 WAL，而非表、索引等数据文件。该承诺还隐含“设备诚实响应”假设：当存储设备报告 flush 完成时，数据确已具备断电后可读取的持久性；若控制器、磁盘缓存或虚拟化层虚报完成，数据库无法仅靠 WAL 自行弥补这一硬件违约。

### 诚实设备假设下的恢复保证

### 诚实设备假设下的恢复保证

PostgreSQL 的崩溃恢复建立在一个关键前提上：存储系统对“已完成持久化”的确认必须可信。一次事务修改先生成 WAL 记录；相关数据页只是在共享缓冲区中变为脏页，稍后才由后台写入、检查点等机制刷回数据文件。只要数据页落盘前，其对应 WAL 已经持久化，就满足预写日志规则。

对同步提交事务，`synchronous_commit=on` 时，提交成功意味着提交记录及此前必要的 WAL 已跨越配置的持久化边界：PostgreSQL 已请求将 WAL 从内存写入内核缓存，并通过 `fsync`、`fdatasync` 等操作请求稳定存储。断电重启后，恢复过程从最近检查点开始扫描 WAL，对其中已持久化的修改执行 REDO；即使目标数据页尚未写回，或只写入了一半，也可用日志将其重建到正确状态。

这里“不必每笔提交刷数据页”正是 WAL 的性能价值：提交路径主要等待日志持久化，数据页可批量、延后写入。`full_page_writes` 还会在检查点后的首次修改中记录完整页面映像，以处理页写入中断造成的撕裂页。

但保证不等于“任何硬件下都不会丢数据”。若操作系统、磁盘控制器、SSD 固件或虚拟化层把仍在易失缓存中的数据谎称为已 flush，断电后 WAL 本身可能消失，REDO 无从进行。未配备断电保护的写缓存、错误的挂载或 `fsync` 配置、介质损坏，以及整机或多副本同时失效，都超出该语义的保证范围。PostgreSQL 能恢复的是设备诚实确认后实际持久化的 WAL，而非被错误确认的写入。

> **要点** — WAL保证先持久化恢复依据，再延后写数据页；提交可靠性最终受刷盘配置与设备诚实性约束。

一条消息从提交到送达，会经历多个可见性边界；崩溃恢复的关键，是沿时间线判断哪些事实已被可靠保存。

### 先拆开四种“成功”

### 先拆开四种“成功”

“消息发成功了”至少可能指四件不同的事，不能混为一谈：

1. **`INSERT` 执行成功**：数据库进程已经执行了插入语句，内存中的事务状态或数据页可能看得到 `m-a`。但若尚未完成提交，崩溃后该修改可以被回滚；这不是持久成功。

2. **`COMMIT` 完成**：提交记录已按所需的同步语义写入可靠存储。对采用同步 WAL 与 `fsync` 的系统，恢复时可通过 REDO 重建 `m-a`，即使数据页还没有落盘。这里才是数据库意义上的“已提交”。

3. **HTTP 响应送达客户端**：服务端可能已经提交，却在返回 `HTTP 200` 前、发送途中或客户端接收前崩溃/断网。于是服务端事实是成功，客户端认知却是未知。客户端应以稳定的 `message_id` 查询或幂等重试，而不是把超时直接当成失败。

4. **设备实际确认**：消息已提交到服务端，也不等于设备已收到、更不等于设备已展示或确认。离线设备、推送通道、设备端去重与确认回执都属于后续交付链路。

因此，`WAL record` 已出现不必然表示已提交：它可能只是未持久化的事务记录；数据页已写回也不表示客户端已经知道结果。数据库提交、客户端获知与设备交付，是三个独立边界。

### 用C0—C5标记崩溃时间线

### 用 C0—C5 标记崩溃时间线

把一次“发送消息”拆成六个崩溃切点，才能区分**数据库事实**、**恢复后可见性**与**客户端认知**：

- **C0：`BEGIN` 前**  
  尚未开始事务，也没有消息记录；崩溃后不存在 `m-a`。

- **C1：执行 `INSERT` 后、`COMMIT` 前**  
  `m-a` 可能已出现在内存页、缓冲区或未提交的日志中，但事务尚未提交。崩溃恢复必须撤销或忽略它，**不能保证消息存在**。

- **C2：生成 `COMMIT` 日志后、尚未持久化**  
  即使内存里已有提交记录，或日志文件曾被写入操作系统页缓存，也不等于可靠落盘。断电可能丢失该记录；恢复时仍可能把事务视为未提交。故 **C1、C2 都不能宣称提交成功**。

- **C3：同步 WAL 已 `flush` 且 `fsync` 成功，事务提交成功；数据页尚未写回**  
  此时日志先于数据页持久化，满足预写日志规则。若可靠存储确实兑现 `fsync` 语义，崩溃恢复可通过 **REDO** 重放 `m-a`，因此消息在数据库语义上已提交。注意：`WAL record` 存在本身不等于提交，关键是包含有效 `COMMIT` 的日志已可靠持久。

- **C4：数据页已写回**  
  `m-a` 已直接存在于持久数据页；恢复仍可能检查并重放日志。这只是存储形态更靠后，**不代表客户端已经知道成功**。

- **C5：服务端返回 HTTP 200，且 A 已收到**  
  此时数据库已提交，客户端也获得成功确认。若崩溃发生在 C3—C5 之间，服务端可能已成功而响应丢失，A 的正确状态是“未知”，应按稳定的 `message_id` 查询或幂等重试，而不是盲目再次插入。

上述结论只覆盖数据库提交与可恢复性；消息是否已被设备接收、展示或确认，需要另一条交付时间线判断。

### WAL为何先于数据页

### WAL为何先于数据页

预写日志（WAL，Write-Ahead Logging）的核心约束是：**任何被修改的数据页写回磁盘前，描述该修改的日志必须先持久化**。因此，插入消息 `m-a` 时，系统可先在内存中修改索引、消息表等数据页，同时追加日志；真正提交时，再写入一条 `COMMIT` 日志并执行同步持久化：

`BEGIN → INSERT(m-a)日志/页缓存 → COMMIT日志 → fsync(日志) → 以后再写数据页`

这样设计的原因是：数据页可以延迟、合并、乱序写回，以提高吞吐；但一旦崩溃，恢复程序必须有可靠依据重建已提交修改。持久化的提交日志正是这项依据。恢复时：

- 对有完整且已持久化 `COMMIT` 记录的事务执行 **REDO**，即使 `m-a` 所在数据页从未写回，也能由日志重放出 `m-a`。
- 对没有持久化 `COMMIT` 记录的事务，不应视为提交；其可能留在内存、日志缓冲或部分页面中的影响，需要通过撤销或恢复规则排除。

据此看时间点：

- **C1：`INSERT` 已执行但未 `COMMIT`**。只有“做过插入”的事实，没有“提交成功”的可靠证据；崩溃后不能保证 `m-a` 存在。
- **C2：`COMMIT` 日志已生成但未持久化**。日志记录存在于内存或操作系统缓存，并不等于掉电后仍存在；仍不能保证提交。
- **C3：同步 WAL 已 `flush` 且 `COMMIT` 成功**。在 `fsync` 语义可信、底层存储可靠的前提下，提交记录可在崩溃后读取，恢复过程可 REDO 出 `m-a`；即使数据页尚未落盘，`m-a` 也可恢复。

因此，不能把“某条 WAL 记录已经生成”误读为“事务已提交”，也不能把“数据页已经写回”当作“客户端已经知道成功”。WAL首先保证的是**可恢复的提交事实**，而不是 HTTP 响应或设备交付事实。

### 从崩溃点手算REDO结果

### 从崩溃点手算 REDO 结果

设消息 `m-a` 的稳定标识为 `message_id=K`。下面的“存在”指数据库重启恢复后可查询到该消息，不等同于设备已经收到，也不等同于客户端已经知道成功。

| 崩溃点 | 崩溃时状态 | 重启后的 `m-a` | 客户端是否已知成功 | 是否应按 `message_id=K` 查询 |
|---|---|---|---|---|
| C0 | 尚未 `BEGIN` | 不存在 | 否 | 通常不必；请求根本未进入事务 |
| C1 | 已执行 `INSERT`，未 `COMMIT` | 不存在 | 否 | 可安全重试；未提交修改应被撤销 |
| C2 | 已生成提交日志，但尚未可靠持久化 | 不保证存在 | 否 | 必须查询或重试；不能把“有日志记录”当作已提交 |
| C3 | 同步 WAL 已 `flush`、`fsync`，提交成功；数据页未回写 | 存在；恢复时 REDO 得到 `m-a` | 可能未知 | 必须按 `K` 查询，避免重复插入 |
| C4 | 数据页已写回 | 存在 | 可能未知 | 仍应查询；数据页落盘不代表响应已送达 |
| C5 | HTTP 200 已被 A 收到 | 存在 | 是 | 通常不需要恢复性查询，但幂等设计仍应保留 |

关键分界在 C3：在同步 WAL 与可靠存储前提下，提交记录已经持久化，即使 `m-a` 所在数据页尚未写回，重启也会通过 REDO 重建它。相反，C1 与 C2 都不能承诺提交成功。

C3 到 C5 常出现“服务端已提交、客户端未收到响应”的窗口。客户端超时后不应盲目再次发送新消息，而应携带同一个稳定 `message_id=K` 查询；查到即确认原请求成功，查不到才按幂等规则重试。数据库中的 `m-a` 存在，仅说明消息已被持久接收；后续设备投递、设备确认属于另一条状态线。

### 恢复承诺的配置与边界

### 恢复承诺的配置与边界

“可恢复”不是单指看到一条日志记录，而是配置、存储介质与恢复协议共同给出的承诺。评审时应先确认提交路径：

- **同步提交**：事务提交前，WAL 中的 `COMMIT` 及其此前必要记录已 `fsync` 到可靠存储。若崩溃发生在 C3 之后，恢复可通过 **REDO** 重放得到 `m-a`，即使数据页尚未在 C4 写回。
- **异步提交或未可靠落盘**：C1 的 `INSERT`、C2 的提交日志生成，都可能仅在进程内存、页缓存或易失写缓存中；断电后不能保证提交成立。`WAL record 存在`不等于`事务已提交`。
- **可靠存储前提**：`fsync` 的意义依赖文件系统、磁盘控制器与硬件确实兑现持久化屏障。若设备谎报刷盘、关闭写缓存保护，或副本尚未满足确认策略，则 C3 的承诺会被削弱。

REDO 的任务是把“已确认但数据页未落盘”的更新补齐；它不意味着任意未完成操作都能撤销。**UNDO** 是否存在、如何做，是具体数据库的并发控制与日志设计问题，不能把 WAL 一概理解为通用撤销日志。

检查点只是缩短恢复扫描范围、推进已安全写回的数据页位置，不改变提交语义：C4 数据页写回也不等于客户端已经知道成功。SQLite 的日志模式与同步级别、MongoDB 的 journal 与写关注级别，均需按各自文档确认“确认”是否已覆盖持久化及副本条件。

备份恢复解决的是更大范围的介质损坏或误操作，通常需要备份加日志链，不能替代单机崩溃时的 WAL 恢复。至于设备交付、推送或消费确认，则属于数据库提交之后的外部协议；C3 至 C5 间响应丢失时，客户端应按稳定 `message_id` 查询状态，而非盲目重发。

> **要点** — WAL已可靠落盘才构成可REDO的提交；数据页写回与客户端得知、设备送达都不是同一件事。

消息显示“已发送”并不等于数据页已落盘。理解 PostgreSQL 的恢复机制，要沿着 WAL、事务状态与数据页写回的时间线判断结果。

### 从消息提交拆解持久性边界

### 从消息提交拆解持久性边界

一次“发送消息”的 SQL 执行成功，不等于消息已经可在崩溃后找回。应区分以下时间点：

1. **SQL 执行**：`INSERT` 创建新行版本、修改缓冲池中的数据页，并生成相应 WAL 记录。此时事务仍可能回滚，其他事务通常也不能把它当作已提交结果。
2. **事务提交**：执行 `COMMIT` 后，PostgreSQL 需要记录该事务的提交状态；只有提交状态成立，新行版本才对后续事务可见。
3. **WAL 刷盘**：在通常的同步提交配置下，提交相关 WAL 必须先被刷到持久化存储，`fsync` 成功后才形成崩溃恢复依据。这是“可恢复提交”的核心边界。
4. **客户端收到成功响应**：服务器通常在提交 WAL 持久化后才返回“提交成功”。因此，应用收到成功响应，可将消息视为已提交业务结果。
5. **数据页落盘**：包含消息行的数据页可以晚得多才写回磁盘。即使此时机器断电，恢复过程仍会从 WAL 重做已提交修改。

因此，关键顺序是：

`修改数据页 → 生成 WAL → WAL 持久化 → 返回提交成功 → 数据页随后落盘`

若客户端尚未收到成功响应就发生故障，结果可能是不确定的：事务也许已提交但响应丢失，应用应通过消息唯一标识查询确认，而不是盲目重复插入。未提交事务即使留下了 WAL 或页内版本，也不构成已提交消息；恢复后其版本会依据事务状态与 MVCC 可见性规则被忽略或清理。

### WAL 先行：先保证可重做

### WAL 先行：先保证可重做

PostgreSQL 不要求“提交时数据页已经写回磁盘”，但要求：**在任何可能携带该修改的数据页落盘前，描述该修改的 WAL 必须先持久化**。这就是预写式日志（Write-Ahead Logging，WAL）的核心顺序：

1. 事务修改某行、索引或元组时，先在共享缓冲区中修改数据页；该页成为脏页。
2. 同时生成相应的 WAL 记录，记录“如何重做这项修改”。
3. `COMMIT` 时写入提交记录；只有包含该提交记录的 WAL 已经通过 `fsync` 等方式持久化，客户端才会收到“提交成功”。
4. 脏数据页不必立即落盘，可由后台写入器、检查点或缓冲区淘汰在之后异步写回。

因此，客户端看到“已提交”时，关键承诺不是“表文件已经更新”，而是“即使此刻宕机，也存在足够持久的信息把已提交修改恢复出来”。

设某已提交修改的 WAL 位置为 $L$。恢复时，PostgreSQL 从最近检查点开始扫描 WAL；若磁盘上的数据页尚未包含位置 $L$ 对应的变化，就执行 redo，将修改重新应用到页中。即使崩溃发生在数据页写回之前，提交结果仍可重建。

反过来，若先写数据页、后持久化 WAL，就可能出现页已带有新内容而日志丢失的状态；崩溃后系统无法可靠判断或重现该变化。WAL 先行正是为了避免这种不可恢复的顺序错误。

### 崩溃后 REDO 如何补齐数据页

### 崩溃后 REDO 如何补齐数据页

数据库崩溃时，内存中的共享缓冲区会丢失，但已刷入 WAL 的记录仍在磁盘上。恢复的核心工作是 **REDO（重做）**：从最近一次有效检查点附近开始读取 WAL，把其中描述的页修改再次应用到数据文件，使数据页追上日志已经确认的状态。

典型时间线如下：

1. 事务修改某个数据页，先在缓冲区中产生新版本；
2. 对应的 WAL 记录被写入并持久化；
3. 事务提交时，提交记录及此前 WAL 已落盘，于是客户端可收到“提交成功”；
4. 但脏数据页可能尚未来得及写回表或索引文件；
5. 若此时断电，重启后 PostgreSQL 扫描 WAL，将缺失的页修改重放。

因此，`COMMIT` 的持久性首先由 WAL 保证，而不是要求每个被修改的数据页立即落盘。恢复期间，系统会检查 WAL 记录对应的数据页 `LSN`：若页上的 `LSN` 已不小于该日志记录的 `LSN`，说明修改已经写入数据页，无须重复执行；否则执行重做。这个判断使 WAL 重放具有幂等性。

检查点缩短了恢复范围：检查点之前的脏页理论上已被写回，恢复通常只需从检查点记录指定的位置向后扫描。不过，崩溃可能发生在单个数据页只写入一部分时。为防止“半页写入”导致页内容损坏，PostgreSQL 启用 `full_page_writes` 时，会在检查点后的某页首次修改中记录完整页镜像；恢复时可先用该镜像重建页面，再继续重放后续修改。

REDO 补齐的是“日志已持久化但数据页尚未完成写回”的物理修改。至于某事务最终是否属于已提交业务结果，还要结合 WAL 中的事务提交状态和 MVCC 可见性判断，而不能仅凭某条页修改记录是否被重放。

### 未提交事务为何不算业务成功

### 未提交事务为何不算业务成功

可将恢复问题先分成两个通用概念：

- **REDO（重做）**：把“已经记入日志、但数据页可能尚未完整写入”的修改重新应用，保证页结构和已提交结果可恢复。
- **UNDO（撤销）**：把未完成事务的影响回退，使其不再可见。许多传统数据库会把它理解为“每个事务保存一套反向操作日志”。

PostgreSQL 不宜被简化为后一种模型。它的核心是 **WAL + MVCC 版本 + 事务状态**：

1. 事务修改行时，可能产生带有该事务 `xmin`/`xmax` 标记的元组版本；这些页面甚至可能在崩溃前已被写出。
2. 崩溃恢复会按 WAL 执行必要的 REDO。这里的“重做”是恢复数据库物理一致性，不等于宣布所有被重做的行都提交成功。
3. 只有事务提交记录持久化后，其事务状态才是已提交；未见提交记录的事务会被视为未提交或中止。
4. 查询依据 MVCC 可见性规则过滤这些版本：来自中止事务的新增版本不可见，被其删除或更新影响的旧版本仍可按规则继续可见。
5. 后续 `VACUUM` 再清理已经确定无用的死版本，而不是在崩溃时逐条执行传统意义上的事务 UNDO 日志。

因此，“数据页上曾出现过修改”与“业务上修改成功”是两件事。WAL 重做保证恢复后页面正确；事务提交状态与 MVCC 可见性才决定订单、消息或余额是否应被业务读取。

### 页部分写入与 full_page_writes 防护

### 页部分写入与 `full_page_writes` 防护

数据库页通常远大于一次底层扇区写入。崩溃、断电或存储设备异常若发生在页面写回中途，磁盘上可能留下“半新半旧”的页：页头、行数据、索引指针或校验信息彼此不一致。这类**页部分写入**即使 WAL 已记录了修改，也可能使恢复时无法在一个结构已损坏的页面上可靠地重做。

PostgreSQL 的 `full_page_writes=on` 用于降低此风险。其核心做法是：

- 在一次检查点之后，某个数据页**第一次被修改**时；
- PostgreSQL 将该页修改前的完整页面镜像写入 WAL；
- 随后的普通修改仍以增量 WAL 记录；
- 崩溃恢复时，若发现磁盘页因部分写入而不可信，可先用 WAL 中的整页镜像重建该页，再重做后续 WAL 修改。

因此，整页镜像不是“每次更新都复制整页”，而是通常每页每检查点周期至少记录一次。代价是 WAL 量增加，尤其是频繁修改大量不同页面时；收益是普通存储栈发生部分页写入时，恢复路径更可靠。

但它不是万能的数据安全承诺。`full_page_writes` 不能修复 WAL 本身丢失、磁盘静默篡改、控制器错误写入、文件系统违背持久化语义等问题；它也不替代可靠硬件、`fsync`、校验和、备份与持续归档。关闭它只应建立在存储系统明确保证原子页面写入、且已理解恢复风险的前提上。

> **要点** — PostgreSQL 以 WAL 保证已持久提交可重做；未提交结果由事务状态与 MVCC 排除，整页写入防护页半写风险。

检查点不是业务提交，也不是备份；它通过推进可恢复起点，在恢复时间、运行时写入压力与WAL保留之间做权衡。

### 检查点解决什么问题

### 检查点解决什么问题

检查点的核心任务是：**把“从很久以前开始重放 WAL 才能恢复”的范围，推进到一个较新的位置**。

PostgreSQL 中，事务执行 `COMMIT` 时，首先要保证其提交状态等关键 WAL 已持久化；这说明事务在崩溃后可以被判定为已提交，并不表示该事务修改过的所有数据页已经写回数据文件。实际数据页可继续留在共享缓冲区中，成为脏页，之后由后台写入或检查点逐步落盘。

一次检查点大致会：

- 将检查点之前需要持久化的脏页刷入数据文件；
- 写入并持久化一条 checkpoint WAL 记录；
- 记录恢复应从哪个 redo 位置开始。

因此，数据库异常重启时，不必从最早的 WAL 开始扫描，而是从该 redo 位置起重放必要的 WAL，使数据文件恢复到一致状态。检查点越久未完成，可能需要重放的 WAL 越多，崩溃恢复越慢；检查点越频繁，则会带来更多数据页写入、WAL 压力和运行时 I/O 抖动。

检查点也不是备份。它只保证现有数据文件与 WAL 能支持崩溃恢复，不能替代可独立保存、可跨故障恢复的备份。即使某些 WAL 已早于检查点，仍可能因归档、流复制或复制槽而必须保留。

### 从脏页到检查点记录

### 从脏页到检查点记录

检查点的核心不是“把内存全部清空”，而是建立一个新的、可信的恢复起点。其推导依赖 WAL（预写式日志）规则：**描述某次页面修改的 WAL 必须先持久化，随后该修改后的数据页才能安全写入数据文件**。

一次典型检查点可理解为以下顺序：

1. **确定检查点边界**：系统选定一个检查点位置，并记录此时需要纳入检查点处理的脏页范围。
2. **推进 WAL 持久化位置**：对于准备写回的数据页，先确保其对应修改的 WAL 已经刷入持久化存储；否则宕机后可能看到“数据页已更新、日志却丢失”的不一致状态。
3. **将检查点前的脏页写回数据文件**：后台写入器逐步把缓冲区中的脏页落盘。这里写的是页面物理状态，不是逐条重放 SQL，也不意味着这些页面上的事务刚刚提交。
4. **写入并持久化检查点记录**：当要求的脏页已经满足落盘条件后，WAL 中写入 checkpoint record，并将其持久化。该记录声明：恢复时无需再从更早的 WAL 位置扫描。

因此，崩溃恢复可以从检查点记录指定的 redo 位置开始，而不必回放此前所有 WAL。

要区分“页面变脏”和“事务提交”：事务执行 `UPDATE` 时，缓冲页可能立刻变脏；即使事务尚未 `COMMIT`，检查点也可能将该页写入数据文件。若随后事务未提交并在崩溃后被判定为中止，恢复仍会借助 WAL、提交状态与必要的回滚机制恢复正确结果。检查点保证的是**物理可恢复性**，不是新的业务提交点。

### 恢复为何从重做位置开始

### 恢复为何从重做位置开始

检查点完成时，PostgreSQL 会在 WAL 中写入一条检查点记录，其中包含一个关键边界：**重做位置**（redo position）。它表示：恢复时，数据文件不能假定比这个位置更新，因此必须从这里开始检查并重放 WAL。

推导逻辑是：

1. 检查点要求把其开始前已脏的缓冲页尽量写回数据文件；
2. 但数据页写入与 WAL 持续追加可并行进行，检查点执行期间仍会产生新的修改；
3. 因而，数据文件至多反映检查点附近的某个状态，不能简单认为“检查点记录之后才需要恢复”。

恢复时先读取最近有效检查点记录，再从其 `redo` 位置顺序扫描 WAL。对于每条修改记录，系统依据页的 LSN 判断是否已落盘：若页上的 LSN 已不小于该记录 LSN，说明该修改已经在数据文件中，无须重复执行；否则重放该记录。

因此，重做位置不是“所有更早 WAL 都永久无用”的业务边界，而是**崩溃恢复所需 WAL 的最早起点**。检查点之后的 WAL 仍可能包含尚未刷入数据文件的已提交修改；即使某次 `COMMIT` 已向客户端成功返回，崩溃后也仍要依靠这些 WAL 将数据页推进到一致状态。

### 频率、写入峰值与恢复时间

### 频率、写入峰值与恢复时间

检查点越频繁，崩溃恢复时需要从最近一次检查点的 `redo` 位置重放的 WAL 通常越少，因此恢复更快、恢复时间更可预测。但代价不是“多写一条检查点记录”，而是必须在检查点完成期限内将相应脏页逐步刷入数据文件。

| 策略 | 崩溃后的恢复工作量 | 在线写入压力 | WAL 与延迟影响 |
|---|---|---|---|
| 更频繁检查点 | 较小，重放区间较短 | 更持续地刷脏页，后台写入更忙 | 检查点相关全页写入可能更频繁；存储紧张时业务写入延迟上升 |
| 更稀疏检查点 | 较大，可能需重放更长 WAL 区间 | 平时可积累更多脏页 | 单次检查点要处理更多页面，容易形成写入峰值；故障后恢复更久 |

这里的核心矛盾是：把写盘工作分散到运行期间，还是把更多工作留给未来恢复与检查点窗口。稀疏检查点并不意味着完全不写脏页，后台写入器仍会工作；但脏页积累更多时，检查点更容易遭遇 I/O 饱和，进而拖慢前台写入。

更频繁也不等于更安全。已提交事务的持久性依赖 WAL 的提交与刷盘规则，而非检查点是否刚完成；检查点只是缩短“需要从 WAL 重建多少数据页”的范围。并且 WAL 不能仅因检查点推进就任意删除：归档、流复制和复制槽仍可能要求保留它。合理频率应结合可接受恢复时间、磁盘吞吐、写入波动和 WAL 保留需求共同确定。

### 不能随检查点丢弃的WAL

### 不能随检查点丢弃的 WAL

检查点完成后，数据库恢复通常可以从新的 `redo` 位置开始，不必重放更早的大量 WAL；但这只说明**实例崩溃恢复的起点前移**，并不表示旧 WAL 已经可以立即删除。

WAL 是否必须保留，还取决于其他消费者：

- **归档与时间点恢复**：启用归档后，已切换出的 WAL 要先安全归档。做时间点恢复时，先还原一份基础备份，再连续重放备份后的归档 WAL，直到目标时间、事务或 LSN。若中间某段 WAL 被丢弃，恢复链条就会断裂。
- **物理复制**：备用库可能仍在重放较旧的位置。主库删除了它尚未接收的 WAL，备用库便无法继续追赶，只能重新建立。
- **复制槽**：物理复制槽会记录消费者所需的最早 WAL 位置；只要槽未推进，主库就必须保留相应 WAL。槽长期失效会导致 `pg_wal` 持续膨胀，甚至耗尽磁盘。
- **逻辑解码与逻辑复制**：逻辑槽同样依赖 WAL；订阅端积压、消费程序停止或槽遗忘清理，都会阻止 WAL 回收。

因此，检查点是“缩短本机崩溃恢复”的机制，不是 `COMMIT`，不产生业务级可回退副本，也不是备份成功的证明。可靠恢复至少需要：可验证的基础备份、连续且可用的 WAL 归档、受监控的复制状态，以及定期的恢复演练。尤其要监控归档失败、复制延迟、复制槽滞后和 `pg_wal` 目录增长；这些问题不会因检查点成功而自动消失。

> **要点** — 检查点推进恢复起点而非确认业务；它缩短重做范围，却不能取消WAL、备份和复制所需的保留责任。

消息接口返回成功并不等于数据已跨越所有崩溃边界。理解 PostgreSQL 的提交确认、刷盘链路与硬件承诺，才能准确回答“消息还能否找回”。

### 先拆开：成功响应究竟确认了什么

### 先拆开：成功响应究竟确认了什么

一次“发送消息成功”至少跨越五个彼此独立的确认层次：

1. **`INSERT` 成功**：SQL 语句已被 PostgreSQL 接受并执行；新行可能仍只在当前事务上下文、共享缓冲区或 WAL 缓冲中，尚未对其他事务可见，更谈不上可抗崩溃。
2. **`COMMIT` 成功**：事务的逻辑提交已完成，之后的查询通常能看到该消息。但“逻辑可见”不天然等于“掉电后仍存在”。
3. **WAL 刷盘确认**：提交所需的 WAL 已经通过 `fsync`/`fdatasync` 等路径，请求写入持久化介质。这是 PostgreSQL 默认本地崩溃恢复承诺的关键边界；若 `synchronous_commit=off`，服务端可先返回提交成功，再异步刷 WAL，留下短暂丢失窗。
4. **HTTP 响应成功**：应用向客户端返回 `200`、`201` 或业务成功码。它只说明应用选择在当前时点报告成功；它可能对应已刷盘的提交，也可能仅对应已执行、已入队，甚至仅进入应用内存。
5. **设备持久化确认**：存储设备真正将数据放入断电后仍可保留的介质。操作系统页缓存、磁盘写缓存、RAID 控制器的易失缓存都可能使“写入完成”与“物理持久”之间仍有差距。

因此，不能把“设备 ACK”直接翻译为“客户端 200”，也不能把 `COMMIT` 与“远端副本已收到”混为一谈。普通 `synchronous_commit=on` 主要约束本地 WAL 持久化；是否等待同步备库、等待到何种复制阶段，还取决于同步复制配置及故障模型。若 `fsync=off`，即使数据库报告提交成功，也不再保证崩溃后的数据一致性。

### synchronous_commit=off 的短暂丢失窗

### synchronous_commit=off 的短暂丢失窗

设事务 $T$ 写入一条消息。PostgreSQL 提交时，先把变更写入共享缓冲区与 WAL 缓冲区，再由 WAL 写入进程把日志交给内核页缓存；关键区别在于，何时等待持久化确认。

当 `synchronous_commit=on` 时，提交路径近似为：

`写 WAL → 请求 flush → 存储设备确认持久化 → 向客户端返回成功`

而 `synchronous_commit=off` 允许路径变成：

`写 WAL → 事务标记提交 → 向客户端返回成功 → 后台稍后 flush WAL`

因此，客户端收到“消息已提交”后，WAL 可能仍只在 PostgreSQL 内存、操作系统页缓存，或尚未真正稳定的设备缓存中。若此时主机掉电、内核崩溃或进程所在节点失效，恢复时找不到该提交记录，则该事务会被视为未提交；对应的已确认消息可能消失。

可将时间线写为：

1. $t_0$：事务写入消息及其 WAL。
2. $t_1$：PostgreSQL 向客户端返回成功。
3. $t_2$：后台执行 WAL flush，持久化边界被跨越。

在区间 $(t_1,t_2)$ 内发生主机崩溃，消息存在丢失可能；$t_2$ 之后，才具备本地 WAL 崩溃恢复所依赖的持久化基础。这个窗口通常很短，受 `wal_writer_delay`、写入负载、调度和存储延迟影响，但它不是零，也不能由接口的 `200` 响应掩盖。

这里的“丢失”并非数据库逻辑主动删除，而是**已向客户端确认的提交尚未拥有可恢复的 WAL 证据**。应用若以成功响应立即投递下游、扣减库存或确认外部请求，就必须接受重复投递、状态回退或消息找回失败的补偿需求。

还要明确故障模型：该结论针对本机崩溃恢复。`synchronous_commit=off` 不等于“异步复制”，也不意味着远端副本已收到数据；即使启用同步复制，也必须说明提交等待的是本地刷盘、远端写入，还是远端刷盘。客户端成功只能证明 PostgreSQL 已按当前确认策略应答，不能自动证明数据已跨越主机、操作系统、控制器和远端节点的全部崩溃边界。

### fsync=off：不是更快的可靠提交

### fsync=off：不是更快的可靠提交

`同步提交关闭`与`fsync=off`都会降低提交路径上的等待，但它们削诺的边界完全不同：

| 配置 | 主要省去什么 | 崩溃后的典型结果 | 是否仍保留 WAL 恢复模型 |
|---|---|---|---|
| `synchronous_commit=off` | 本次提交等待 WAL 刷到稳定介质的时间 | 已返回成功的最近一小段事务可能丢失 | 是；已真正落盘的 WAL 仍可用于恢复 |
| `fsync=off` | 所有要求操作系统将数据可靠落盘的同步屏障 | WAL、数据页、检查点状态可能彼此矛盾 | 否；恢复正确性的基本前提被移除 |

当 `synchronous_commit=off` 时，PostgreSQL 仍会生成 WAL，也仍会由后台刷写器最终执行持久化。若主机突然断电，恢复过程通常能回放已经持久化的 WAL；代价是客户端已经收到成功响应、但 WAL 尚未到达稳定介质的事务可能消失。因此它形成的是**短暂且明确的确认—持久化缺口**。

而 `fsync=off` 不只是扩大这个缺口。它允许 WAL、数据文件和控制文件的写入在未建立可靠落盘顺序时继续进行，可能破坏 WAL 先行原则：数据页先于对应 WAL 落盘，或检查点记录声称某些页已安全、实际却没有。断电后，数据库不一定仅仅“少几条消息”，还可能无法完成一致恢复，甚至需要从备份、归档 WAL 或副本重建。

还要注意，`fsync=on` 依赖存储栈兑现刷盘语义。若操作系统缓存、磁盘控制器的易失缓存或虚拟化层错误地把“已写入缓存”报告为稳定写入，PostgreSQL 的 `flush` 假设仍会失效。因而设备 ACK 不是客户端 `200`，客户端成功更不等于数据已跨越断电、主机重启和存储掉电等全部故障边界。

### 从 WAL 到设备：确认链路的硬件边界

### 从 WAL 到设备：确认链路的硬件边界

PostgreSQL 所谓“WAL 已刷盘”，并不是一个脱离硬件的绝对事实，而是一条确认链路上的承诺：

`事务提交 → WAL 写入内核页缓存 → flush/fsync 请求 → 设备控制器 → 持久介质`

`fsync=on` 时，PostgreSQL 会在提交路径上要求操作系统将 WAL 的相关写入同步落盘；这比仅写入 PostgreSQL 进程缓冲区或操作系统页缓存可靠得多。但 `fsync` 成功通常表示：操作系统和设备驱动已接受并完成了其定义的持久化请求，而非应用程序能够直接证明每个比特已写入闪存单元或磁盘磁介质。

关键风险在于写缓存：

- **操作系统页缓存**：普通 `write()` 返回，只说明数据进入内核缓存；断电前尚未执行有效 flush，数据可全部丢失。
- **磁盘自身写缓存**：设备可能先对写入或 flush 给出 ACK，再把数据延后写入介质。若该缓存易失且断电保护失效，已确认的 WAL 仍可能消失。
- **RAID/HBA/存储控制器缓存**：控制器若使用易失内存缓存，或错误配置了“忽略写屏障”“强制写回”，会破坏 PostgreSQL 对 flush 的前提。
- **虚拟化与云存储层**：来宾机看到的虚拟磁盘 flush，还依赖宿主机、网络存储及底层设备正确传递并兑现该语义。

因此，`fsync=on` 的含义应理解为“在软硬件正确实现持久化屏障、缓存受可靠掉电保护的故障模型下，提交 WAL 可跨进程、操作系统和主机崩溃恢复”。它不等于“任何断电、任何固件缺陷、任何存储设备下都绝不丢失”。

实践上应确认设备与控制器启用了可靠的掉电保护，例如带电池/电容保护的写缓存，且 flush、FUA 等语义未被虚拟化或存储层吞掉。更重要的是，不要把“设备已 ACK”误读为“客户端应得到 200”：客户端成功响应应建立在数据库提交语义、复制策略和实际硬件持久化保障共同成立之上。

### 同步提交不等于远端副本已保存

### 同步提交不等于远端副本已保存

` synchronous_commit=on ` 的核心含义是：PostgreSQL 在向客户端报告提交成功前，会等待本地 WAL 提交记录达到其要求的持久化边界；通常是已执行 WAL 刷新，而不是“远端副本已经保存”。因此，单机实例的本地同步提交只能覆盖本机进程崩溃、操作系统崩溃后由 WAL 恢复等模型，不能覆盖整机损毁、磁盘不可读或机房级故障。

远端确认需要单独配置同步复制，例如设置 `synchronous_standby_names`，并使备库实际处于可被选为同步候选者的状态。此时还要区分确认级别：

- `synchronous_commit=on`：等待本地 WAL 持久化；不要求备库确认。
- `remote_write`：等待备库已接收并写入其操作系统缓存；备库掉电时仍可能丢失。
- `on`：等待备库报告 WAL 已刷入持久存储，才返回成功。
- `remote_apply`：进一步等待备库已回放事务，适合要求故障切换后立即可读的场景。

消息服务不能只写“已同步提交”，而应写清承诺边界。例如：“成功响应表示消息已在主库本地持久化”；或“成功响应表示消息已在主库及至少一个指定同步备库持久化”。还应说明同步备库不可用时的策略：阻塞、超时失败、自动降级为异步，还是通过 `ANY 1` 在多个候选备库中任选一个确认。

尤其不能把数据库协议确认、磁盘设备 ACK 与客户端 `200` 混为一谈。即使 PostgreSQL 已完成刷盘调用，若操作系统缓存、磁盘控制器的易失缓存或虚假的 flush 承诺未受断电保护，实际掉电恢复仍可能违背预期。客户端看到的“发送成功”，只应被解释为系统文档明确写出的那一级持久性承诺。

> **要点** — HTTP 200 只证明系统已作出当前配置下的确认；能否抗崩溃取决于提交模式、fsync、复制级别及完整存储链路。

同样是“已提交”，SQLite 与 MongoDB 对日志、刷盘、复制和恢复的承诺并不相同；必须先辨认各自的持久化边界。

### 先划清两类存储引擎的承诺边界

### 先划清两类存储引擎的承诺边界

“客户端收到成功”不能直接等同于“所有副本都有数据”或“主数据文件已经更新”。比较 SQLite 与 MongoDB 时，应把一次写入拆成彼此独立的事件：

- **客户端成功**：接口已返回成功；其含义取决于所选事务、确认级别及错误处理路径。
- **日志持久**：写入先进入可恢复日志，并按引擎与配置决定何时同步到稳定介质。
- **数据文件更新**：日志中的变更被合并进主数据文件；这通常是后续整理过程，不必发生在请求返回前。
- **副本可见**：其他节点已接收、应用或确认该写入；单机 SQLite 不存在这一层，MongoDB 则由复制与写关注控制。

SQLite 的 WAL 模式中，提交后的新页面先记录在 WAL 文件；读取者可在其快照范围内并发读取，随后 `checkpoint` 才将 WAL 内容合并回主数据库文件。这里的“已提交”不应表述为“数据库主文件已刷新”，且 SQLite 仍遵循单写者模型。

MongoDB 的 WiredTiger journaling 关注本地节点崩溃恢复；`j:true` 表示请求与日志持久化相关，但它不自动等价于多数副本确认。副本层面的承诺应另看 `writeConcern`，例如多数确认及其超时设置；具体 `j:true`、默认日志策略和版本行为必须核对所部署版本的官方文档。

因此，不应把同一套持久化等级逐项套到两种引擎上：SQLite 的重点是 WAL、同步与检查点，MongoDB 还必须分开讨论本地日志、复制确认和读可见性。

### SQLite：WAL 先记录，检查点再合并

### SQLite：WAL 先记录，检查点再合并

启用预写日志（WAL）模式后，SQLite 不会在每次事务提交时立即改写主数据库文件。其基本路径是：

1. 事务把变更后的页面追加写入 `-wal` 文件；同一页面可在 WAL 中出现多个版本。
2. 提交时写入提交标记；在满足当前同步设置所要求的刷盘条件后，该事务才对随后启动的读者可见。
3. 读者通常读取“主数据库文件 + WAL 中截至其读取快照的页面版本”。因此，读操作不必等待写者把页面合并回主文件。
4. 后台或显式执行的检查点（checkpoint）把已提交 WAL 页面复制回主数据库文件；当旧读快照不再需要相应 WAL 内容后，日志空间才可回收或重用。

可将可见数据抽象为：

\[
\text{读取结果}=\text{主库页} \oplus \text{WAL 中快照边界之前的最新页版本}
\]

因此，“已提交”不等于“主数据库文件已经更新”：崩溃恢复时，SQLite 可根据 WAL 中有效且已提交的记录重建应有状态；而尚未形成有效提交标记的尾部写入不应视为已提交事务。

WAL 的并发优势在于读者可与写者并行：写者持续追加日志，读者维持各自快照。但它不是多写者并行提交模型；同一时刻仍通常只有一个写事务写入 WAL。长时间运行的读事务还会阻碍检查点推进，使 WAL 文件增长。检查点是“合并与回收”步骤，不应被误解为事务提交本身。

### SQLite 并发：多读者与单写者的官方范围

### SQLite 并发：多读者与单写者的官方范围

SQLite 的 WAL（预写式日志）模式允许“读主数据库快照、写入 WAL 文件”同时发生，因此常见表述是：**多个读者可以与一个写者并发**。但这不等于多个写事务能够并行提交。

- **读者不阻塞写者**：读事务启动时记录其可见的 WAL 末尾位置；之后即使写者继续追加新页面，读者仍按原快照读取主数据库文件与对应 WAL 页面。
- **写者通常不阻塞读者**：写者先取得写入相关锁，将修改追加到 WAL；已有读者无需等待这些新修改完成。
- **同一时刻只有一个写者**：SQLite 仍是单写者模型。两个连接若都要开始写事务，后者必须等待前者结束，或在忙碌超时后收到 `SQLITE_BUSY` 等结果。WAL 改善的是读写重叠，不是把写入扩展为多写者并行。

checkpoint 是把 WAL 中已提交页面合并回主数据库文件的过程。它也不能任意越过仍在使用旧快照的读者：若某个长读事务的快照仍需要 WAL 前段页面，checkpoint 只能合并其安全范围之前的内容，不能删除该读者仍可能读取的 WAL 内容。

因此，长时间未结束的读事务会使 WAL 文件持续增长，并可能让自动 checkpoint 反复只能部分完成。应用层应避免把网络等待、人工交互或耗时计算包在读事务中；需要稳定读取时，也应理解其代价是延后 WAL 回收，而非获得无限制的并发写能力。

### MongoDB：journal、writeConcern 与复制确认

### MongoDB：journal、writeConcern 与复制确认

MongoDB 中“写成功”至少涉及三个不同边界，不能把它们混成一个承诺。

- **WiredTiger journal**：副本节点先将变更记录到日志，再由检查点将数据页稳定写入数据文件。发生异常时，服务器可利用 journal 恢复已记录但尚未完成检查点的数据。它描述的是**单个节点的崩溃恢复路径**。
- **`j: true`**：这是写关注中的 journal 要求。服务端仅在该节点确认相应写入已提交到 journal 后才返回成功；因此它强调本地日志持久化，而不是“数据页已经写回集合文件”，更不等于其他副本已经收到该写入。是否允许、默认如何处理以及与存储引擎的具体关系，应以所用 MongoDB 版本的官方文档为准。
- **`w` 与复制确认**：`w: "majority"` 要求多数投票数据承载节点确认该写入；它解决的是副本集层面的复制确认与故障切换可见性问题。`w: 1` 通常只表示主节点已接受写入，未要求从节点确认。

常见配置可写为：

`{ w: "majority", j: true }`

其含义是：请求既要满足多数副本确认，也要求 journal 确认；但应避免将其机械表述为绝对不会丢失。实际保证还受副本集拓扑、故障时机、选举、写关注超时、节点存储状态及版本行为影响。

因此，分析 MongoDB 提交语义时应分别问：**主节点是否已写入本地 journal？多少副本已确认？客户端是在确认前还是确认后失联？** 只有这些边界明确后，才能讨论消息提交后能否重试、查询或恢复。

### 恢复与备份：不能把同一时间线硬套两者

### 恢复与备份：不能把同一时间线硬套两者

SQLite 的 WAL 恢复首先处理的是“数据库文件与同目录 WAL 文件是否仍可被识别”。发生异常后，SQLite 会利用 WAL 中已提交的事务恢复可见状态；尚未提交、或提交标记未完成的内容不会成为数据库状态。`checkpoint` 的作用是把已提交页逐步合并回主数据库文件，而不是额外制造一次业务级备份。因此，复制或备份 SQLite 数据库时，不能只拿走 `.db` 文件：在 WAL 模式下，`-wal` 与 `-shm` 文件及其一致性同样重要。应使用 SQLite 官方推荐的备份接口、`VACUUM INTO`，或在确保一致性边界下完成文件级快照。

MongoDB 的 WiredTiger journal 则服务于实例崩溃后的恢复：启用 journaling 时，重启会依据 journal 将数据文件恢复到某个可恢复的一致状态。`writeConcern: { j: true }` 表示该次写入等待 journal 持久化确认，但它不等于已复制到其他节点，也不等于已有可离线保存的备份；复制层面的承诺应另看 `w`、`majority`、副本集状态及部署版本。

备份恢复又是另一条时间线。SQLite 的备份通常恢复到一次备份或快照时刻；MongoDB 的逻辑备份、文件系统快照、持续归档或时间点恢复，分别具有不同的恢复粒度与前置条件。不要把“journal/WAL 可崩溃恢复”误写成“可回到任意历史时刻”，也不要把 MongoDB 的副本集多数确认套到 SQLite。实际结论必须核对运行版本、journal/WAL 配置、存储卷刷盘语义、备份工具及演练结果。

> **要点** — SQLite 的 WAL/checkpoint 与 MongoDB 的 journal/复制确认分别定义恢复边界，不能用一套崩溃时间线直接互相套用。

从消息提交后的每个时间点追踪证据：先判定权威状态，再说明崩溃恢复、可接受丢失窗口与备份边界。

### 用C0—C5时间线判定消息去向

### 用 C0—C5 时间线判定消息去向

一次“发送成功”不是单一事件，而是多个可独立发生的证据点：应用执行 `INSERT`、数据库接受 `COMMIT`、日志写入操作系统缓存、日志真正刷到稳定介质、客户端收到 HTTP 响应、存储设备确认持久化。崩溃后不能只看“用户是否看到成功”，应从最后可确认的持久化证据反推权威状态。

| 时点 | 已发生的事件 | 崩溃后判定 | 对调用方的处理 |
|---|---|---|---|
| C0 | 请求尚未到达数据库，或尚未执行 `INSERT` | 一定不存在 | 可安全重试 |
| C1 | `INSERT` 已执行，但未提交事务 | 通常回滚，不应可见 | 重试；依赖幂等键防重复 |
| C2 | 已请求 `COMMIT`，但日志未确认刷盘 | 状态不确定 | 查询业务键；不可盲目重发 |
| C3 | 提交日志已刷到稳定介质，尚未返回响应 | 崩溃恢复后应存在 | 视为“可能成功”，执行查证 |
| C4 | HTTP 成功响应已发出，但设备持久化语义不可靠 | 可能出现“已答复但丢失” | 依赖存储承诺、备份与恢复策略 |
| C5 | 设备已确认持久化，提交记录可由 REDO 重放 | 应存在且可恢复 | 可返回确定成功 |

关键分界是稳定介质上的提交日志，而不是内存中的事务状态，也不是 HTTP `200`。恢复时，数据库从最近检查点开始扫描日志：已提交但数据页未落盘的修改通过 **REDO** 重放；未提交事务则撤销或忽略。因此，C3 之后即使数据页尚未写回，也不等于消息丢失。

对外接口应把 C2—C4 统一建模为“结果未知”：客户端携带消息唯一标识，服务端按该标识查询权威记录，再决定返回已成功、继续处理或允许补偿。这样“超时重试”不会把一次未知提交变成两条消息。

### WAL、REDO与检查点如何衔接

### WAL、REDO与检查点如何衔接

WAL（预写式日志）的核心约束是：**任何脏数据页写回磁盘前，描述该修改的日志必须先稳定落盘**。若事务修改页 $P$ 并生成日志记录 $L$，则必须满足：

$$\operatorname{LSN}_{stable}(L)\ge \operatorname{pageLSN}(P)$$

因此，提交时通常先强制写入该事务的 REDO 日志与提交标记；数据页可以稍后、乱序地刷盘。即使提交后立刻宕机，也能依据稳定日志重做尚未落盘的更新。

恢复流程可由此推导：

1. **定位恢复起点**：读取最近完成检查点的位置，而非从日志开头扫描。
2. **分析阶段**：识别检查点后哪些事务已提交、哪些页可能仍是脏页。
3. **REDO 阶段**：按日志 LSN 正向扫描；若目标页的 `pageLSN` 小于日志记录 LSN，说明该修改未持久化，执行重做；否则跳过，保证幂等。
4. **撤销阶段**：对未提交事务回滚，避免其部分修改作为有效结果留下。

检查点不是“立刻把所有数据页刷盘”，而是保存恢复所需的边界证据，例如检查点 LSN、活动事务表、脏页表及各脏页最早修改的 LSN。之后后台可继续按合适顺序刷写页面；只要每页遵守 WAL 约束，刷盘顺序无需与事务顺序一致。

可将它理解为两条不同的持久化路径：日志决定“已提交修改能否找回”，数据页决定“正常读取时是否已直接看到修改”。检查点缩短 REDO 扫描范围，却不替代日志，也不等同于备份。备份用于跨介质损坏或误操作恢复；检查点主要服务于本机崩溃后的快速恢复。

### 以稳定m-a查询确认权威状态

### 以稳定 `m-a` 查询确认权威状态

应用不应把“客户端收到成功响应”当作唯一事实。网络中断、进程崩溃或响应丢失后，客户端看到的往往是**未知结果**：请求可能未到达、已到达但未提交，或已提交而响应未送达。

因此，每条业务消息应携带稳定且可重试复用的消息标识，例如 `m-a`。重试前先查询权威存储：

| 查询结果 | 权威含义 | 应用动作 |
|---|---|---|
| 不存在 `m-a` | 尚无可见提交证据 | 可提交或重新投递 |
| 存在且状态为已提交 | 业务事实已落库 | 不重复写入，返回原结果 |
| 存在但处理中 | 结果尚未确定 | 等待、轮询或交由恢复流程裁决 |
| 存在但失败/撤销 | 未形成有效业务提交 | 按业务规则重试或补偿 |

关键是让 `m-a` 与业务操作绑定，并在权威存储上设置唯一约束或幂等记录。这样“重复提交”不会产生两笔订单、两次扣款或两条同义消息；它只是对同一 `m-a` 的再次确认。

还要区分三个不同证据层次：

- **已提交未送达**：权威库已见 `m-a`，但调用方未收到响应；应查后确认，而非盲目重发。
- **设备确认**：设备、客户端或下游消费者确认收到，只证明交付到该环节，不自动等于源端业务提交。
- **未知结果**：任何一方缺少可查询证据时，都不能推断成功或失败；应以恢复后的权威查询为准。

`m-a` 的价值不在于“保证网络不丢包”，而在于把不确定的瞬时通信结果，转换为可重复查询、可审计、可恢复裁决的持久事实。

### 同步提交、硬件边界与恢复目标

### 同步提交、硬件边界与恢复目标

“同步提交”并不等于“永不丢失”。它通常表示：事务成功返回前，日志已按配置写入持久化路径；但“持久化”依赖从进程缓存到硬件介质的整条链路。

| 层次 | 已完成的动作 | 断电后保证 |
|---|---|---|
| 应用/数据库缓存 | 日志留在内存 | 不保证，直接丢失 |
| 操作系统页缓存 | 已调用写入，但未刷盘 | 不保证 |
| 数据库刷盘 | 请求 `fsync`/等价屏障 | 取决于文件系统、驱动与设备是否诚实执行 |
| 带掉电保护的控制器/存储 | 写入受保护缓存或稳定介质 | 通常可恢复 |
| 远端同步确认 | 本地与远端均达到约定稳定点 | 可抵抗单站点故障，不天然抵抗错误复制 |

评审时应明确区分三类承诺：

- **同步提交**：提交确认等待本地日志稳定，主要降低主机崩溃、进程异常造成的已确认事务丢失。
- **同步复制提交**：确认还等待副本达到指定状态，降低主机或存储节点故障的丢失风险，但增加提交延迟。
- **硬件持久化保证**：若磁盘缓存、阵列缓存或虚拟化层谎报刷盘完成，数据库即使正确调用刷盘，也无法兑现同步提交语义。应核验掉电保护、写缓存策略、屏障支持及故障注入记录。

恢复目标应写成可验收指标，而非“尽量不丢”：

- **RPO（恢复点目标）**：最多允许丢失多久的数据。例如 RPO 为 5 分钟，灾难恢复后允许缺少最近 5 分钟的已提交变更；同步且可信的稳定存储可将本地故障场景的 RPO 接近 0。
- **RTO（恢复时间目标）**：从故障发生到服务恢复可用的最长时间。它包含故障识别、切换或重启、日志重放、校验、业务放流，不只是数据库启动时间。

因此，配置“每次提交刷盘”回答的是“已确认提交在断电后是否可找回”；RPO回答“业务允许缺多少”；RTO回答“多久必须恢复”。三者必须结合实际硬件边界和定期恢复演练验证。

### 备份、日志、复制与恢复演练

### 备份、日志、复制与恢复演练

SQLite 的 WAL/回滚日志主要服务于**本地崩溃后的原子性与一致性恢复**：提交前后由日志与检查点决定哪些页可重做或回滚。MongoDB 的 journal 也用于实例崩溃恢复；若启用副本集，还需区分“已写入主节点”“已写入日志”“多数确认”三种口径。日志不是长期备份：日志可能被截断、覆盖或随磁盘故障一同丢失。

| 手段 | 主要解决的问题 | 不能单独保证 |
|---|---|---|
| 备份+日志 | 删除、损坏、历史时点恢复 | 极低数据丢失窗口、即时接管 |
| 复制 | 节点故障后的可用性与副本冗余 | 误删、逻辑损坏不会同步扩散 |
| 恢复演练 | 证明备份可读、日志链完整、流程可执行 | 自动产生备份或副本 |

恢复时先选定稳定的 $m-a$ 时刻，依据该时刻前最后可信的备份、连续日志和确认语义判定权威状态。RPO 问“最多允许丢多少数据”，例如 15 分钟；RTO 问“多久必须恢复服务”，例如 1 小时。二者必须通过演练验证，而非仅凭“已有备份”声明。

**分层自检（答案见括号）：**

1. WAL 是否等于备份？（否）  
2. journal 的首要用途？（崩溃恢复）  
3. 复制能否阻止误删传播？（不能）  
4. RPO 衡量什么？（可接受数据丢失量）  
5. RTO 衡量什么？（恢复服务时间）  
6. SQLite 单机磁盘损坏靠 WAL 能否恢复？（通常不能）  
7. MongoDB 多数确认意味着什么？（多数节点确认该写入）  
8. “写入返回成功”必然永久保存吗？（不必然）  
9. 检查点的作用？（将日志相关修改推进到数据文件）  
10. 日志截断后还能依赖其恢复历史吗？（不能假定）  
11. 备份是否应验证可还原？（必须）  
12. 演练应测什么？（数据、步骤、耗时、权限）  
13. 副本集是否替代离线备份？（否）  
14. 逻辑损坏会复制吗？（可能）  
15. 恢复前先确定什么？（权威状态与目标时点）  
16. 日志链缺段能否声称精确时点恢复？（不能）  
17. RPO 为零意味着什么？（不允许确认数据丢失）  
18. RTO 很短只靠人工恢复可行吗？（通常不可行）  
19. 备份成功日志是否足够？（不够，须恢复验证）  
20. 主节点故障后副本是否天然最新？（不一定）  
21. 备份应防范哪类风险？（介质、误删、勒索、逻辑损坏）  
22. 本节最重要的证据链？（确认语义、备份、连续日志、演练记录）

> **要点** — 消息能否找回取决于持久化证据、恢复链路与既定RPO/RTO，响应或设备确认都不是唯一依据。
