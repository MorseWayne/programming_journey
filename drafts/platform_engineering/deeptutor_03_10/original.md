### 先把症状定义成可测事实

### 先把症状定义成可测事实

“历史查询变慢”不是可诊断的结论，只是用户感受。先把它压缩为可重复验证的事实：

- **对象**：IM 服务 `c-a` 的“历史消息查询”用户可见端点；不要混入发消息、会话列表或后台索引任务。
- **窗口**：连续 **5 分钟**，例如 `10:00:00–10:05:00`；所有延迟、吞吐和资源指标必须使用同一时间窗。
- **负载**：约 **100 rps**。同时记录请求数、成功数、错误数与超时数，避免低流量或失败请求被排除后造成 p95 失真。
- **延迟**：端到端 p95 由历史基线约 **60 ms** 升至 **240 ms**。需明确计时边界：从网关收到请求到向客户端返回响应，还是仅服务进程内部耗时。
- **范围**：确认受影响的是全部用户、某个地域、某类会话，还是仅命中某些实例；也要记录 p50、p99，判断是整体变慢还是尾部恶化。
- **版本与实例**：记录部署版本、配置版本、实例清单及其启动时间。例如只有新版本实例 p95 升高，才值得优先怀疑发布差异。

可写成一条症状陈述：在 `10:00–10:05`、约 `100 rps` 下，`c-a` 版本 `V` 的历史查询端到端 p95 为 `240 ms`，高于基线 `60 ms`，影响范围为 `X`。这仍不说明是 CPU、内存、文件系统还是 I/O 导致；它只是后续证据链必须解释、也可能被推翻的观测事实。

### 从症状到竞争假设

### 从症状到竞争假设

已知某 IM 服务的“历史消息查询”用户可见端点，在同一服务版本、同一实例集合下，最近 `5 min`、约 `100 rps` 的 `p95` 时延由 `60 ms` 升至 `240 ms`。这首先是**端到端症状**，而不是“CPU 高”“磁盘慢”或“内存泄漏”的结论。

将一次请求近似拆解为：

$$
T_{\text{请求}}=T_{\text{排队}}+T_{\text{运行}}+T_{\text{等待CPU}}+T_{\text{内存回收}}+T_{\text{磁盘I/O}}+T_{\text{网络}}+T_{\text{应用等待}}
$$

其中各项可以同时上升；`p95` 恶化尤其可能意味着少量请求落入拥塞、长尾 I/O 或锁竞争路径。应保留彼此竞争、可被数据推翻的假设：

- **CPU 争用**：可运行任务增多、线程被抢占，或单核热点使请求获得 CPU 的等待时间增加；总 CPU 利用率不高也不能排除核间不均衡。
- **内存回收**：匿名页或页缓存压力触发直接回收、换页、频繁缺页，应用线程在分配或访问数据时停顿。
- **磁盘等待**：历史查询涉及索引、消息文件或数据库页，队列深度、设备服务时间或同步写入抬高尾部等待。
- **网络排队**：连接池耗尽、发送/接收队列积压、重传，或下游存储与远程服务变慢，使本机请求卡在网络路径。
- **进程与应用内部等待**：线程池排队、互斥锁竞争、数据库连接等待、垃圾回收、慢查询或依赖调用，均可能在资源指标平稳时制造高时延。

因此，诊断的下一步不是挑选“最像”的原因，而是为每个假设寻找时间对齐的只读证据：它是否只影响异常实例、是否随 `p95` 同步变化、是否能解释约 `180 ms` 的增量，以及是否存在反证。

### 建立利用率、饱和与错误检查表

### 建立利用率、饱和与错误检查表

对“历史查询 p95 在 5 分钟窗口内由 60ms 升至 240ms、约 100 rps”的排查，先固定服务版本、实例集合、用户可见端点与时间边界；随后以只读命令持续采样。每项指标都必须同时写下“支持何种假设”和“什么结果会推翻它”，避免把高利用率直接当成根因。

| 维度与采样项 | 只读观察 | 可支持的证据 | 关键反例 |
|---|---|---|---|
| 进程 | `ps -eo pid,ppid,stat,%cpu,%mem,etime,cmd --sort=-%cpu` | 查询进程长期占满核心、出现异常子进程或大量 `D` 状态任务，支持计算阻塞、等待 I/O 或进程堆积 | CPU 低、进程数稳定、无 `D` 状态，不能归因于本进程忙碌 |
| CPU | `vmstat 1`、`/proc/stat` | `r` 持续高于可运行 CPU 数，`us`/`sy` 高且 `id` 很低，支持 CPU 饱和；`sy` 异常高还提示系统调用、网络或锁开销 | `id` 充足且 `r` 很小，240ms 不能用“CPU 不够”解释 |
| 内存 | `free -h`、`vmstat 1`、`/proc/meminfo` | `si/so` 持续非零、可用内存紧张、主缺页上升，支持回收或换页拖慢请求 | 缓存下降本身不是故障；无交换活动且可用内存充足，排除明显内存压力 |
| 磁盘 I/O | `iostat -xz 1` | 相关设备 `%util` 接近饱和、`await`/队列深度上升，且查询期间读写量同步增加，支持存储排队 | 设备空闲、延迟平稳，或高 I/O 来自无关批任务，不能指向历史查询 |
| 文件与内核对象 | `/proc/<pid>/fd`、`/proc/<pid>/limits` | 文件描述符接近上限、连接或日志文件异常增长，支持资源泄漏或打开失败风险 | 描述符余量大、数量稳定，排除该类耗尽 |
| 网络连接 | `ss -s`、`ss -tanp` | `SYN-RECV`、`TIME-WAIT`、发送队列或重传相关现象增长，支持连接建立、下游慢读或网络拥塞 | 连接状态稳定、队列为空，不应凭“网络调用存在”断言网络是瓶颈 |

采样应至少覆盖异常前、异常中和恢复后，并将指标与同一实例的请求率、p50/p95/p99 对齐。利用率回答“忙不忙”，饱和回答“是否排队”，错误回答“是否失败”；只有三者与时延变化共同出现，资源假设才具备较强解释力。

### 正确解读跨层指标边界

### 正确解读跨层指标边界

同一时刻的“资源指标”并不处于同一层，也未必描述同一种时间尺度。对 `c-a` 而言，5 分钟内约 `100 rps` 的历史查询 p95 从 `60 ms` 升至 `240 ms`，首先确认比较的是同一服务版本、同类实例与同一用户可见端点；随后才讨论资源。任何单项指标都只能支持或推翻某个假设，不能直接宣告根因。

- **`vmstat`：瞬时状态与累计计数不可混读。** `r`、`b` 是采样时刻的可运行或不可中断任务数，反映当下排队；`si`、`so`、`bi`、`bo`、`in`、`cs` 常表示采样间隔内的速率；`cpu` 中的 `wa` 是 CPU 时间归因，并非“磁盘慢”的证明。若 p95 持续恶化，而 `r` 偶发升高一次，不能据此认定 CPU 排队；应观察其是否在整个异常窗口持续高于 CPU 可服务能力。

- **RSS 不等于 Go 堆，也不等于泄漏。** RSS 包含 Go 堆、运行时元数据、栈、共享库及可能驻留的文件页。Go 堆增长应结合 `runtime` 指标、GC 周期与暂停时间判断；RSS 增长但 Go 堆稳定，可能是文件映射、页缓存关联或原生分配。文件描述符数则是另一条证据：它升高可能导致连接、文件或 socket 耗尽，却不能从 RSS 曲线推出。

- **`iostat await` 不是设备“忙碌率”。** `await` 是请求从提交到完成的平均等待加服务时间，受排队、合并、读写混合影响；高 `await` 可由设备饱和、下游抖动或少量长请求拉高。并行设备上 `%util` 接近 `100%` 只说明设备持续有工作，并不自动等于吞吐封顶。应同时看请求速率、队列深度、读写延迟与应用侧 I/O 等待。

- **`ss` 队列不是业务队列。** `Recv-Q`、`Send-Q` 描述内核 socket 缓冲中的未处理数据或待发送数据；它们增长可提示应用读写不及时、对端慢或网络受阻。业务线程池、数据库连接池、RPC 等待队列则位于应用层。二者可能相关，但不能把 `Send-Q` 堆积直接解释为“历史查询排队”。

因此，只有当用户 p95、应用阶段耗时与相应资源队列在同一 5 分钟窗口内共同变化，并且替代解释被排除时，跨层关联才构成可信证据链。

### 用合成证据决定下一次观察

### 用合成证据决定下一次观察

将历史查询的 `p95=240ms` 与基线 `60ms` 放入同一 `5min` 窗口，并固定对象：已发布的服务版本、异常实例集合、用户实际访问的历史消息端点。约 `100 rps` 下，不能因为“变慢”就直接归因于 CPU、内存、文件或磁盘；每个资源只能形成待检验的竞争假设。

可将观察结果汇总为一张证据表：

| 假设 | 同窗证据 | 当前结论 | 下一步 |
|---|---|---|---|
| CPU 竞争导致排队 | CPU 使用率高，但运行队列未增、限额节流为零 | 削弱：忙不等于排队 | 查线程态、热点方法或下游等待 |
| 内存回收导致暂停 | p95 抬升时，堆使用平稳、无长暂停、无频繁缺页 | 暂不支持 | 保留为低优先级，继续看分配率与回收事件 |
| 文件/页缓存失效 | 读请求增多，缓存命中下降，页面回收与主缺页上升 | 保留 | 对比异常实例的工作集、缓存命中和读延迟 |
| 存储 I/O 排队 | 设备利用率接近饱和、队列深度与读等待同步升高 | 强化 | 按设备、卷和请求类型拆分 I/O 延迟 |
| 下游依赖变慢 | 应用处理时间稳定，但客户端端到端与依赖调用同时升高 | 强化 | 采集依赖端点的时延、错误率和连接池等待 |

判断应以“预测是否被观测推翻”为准。例如，若 CPU 假设预测运行队列、节流或可运行线程会随 p95 上升，而这些指标均稳定，则应削弱它；即使 CPU 平均值为 `85%`，也不能把它当作根因。反之，若仅异常实例出现 I/O 等待与查询时延同步，且正常实例没有该模式，I/O 假设得到更强支持，但仍未证明具体是设备、文件系统还是远端存储。

下一项观测应低风险且能最大区分剩余假设：在不改流量、不重启实例的前提下，按实例采集请求分段耗时（应用计算、数据库/存储等待、网络等待）及对应的设备队列、主缺页、依赖调用时延。优先选择能让两个假设给出不同预测的指标，而不是继续堆积相关性图表。

> **要点** — 时延是症状而非原因；统一时间窗，以只读数据和反例逐步收敛资源诊断结论。

面对IM历史消息查询变慢，先固定症状与时间窗，再用只读证据检验CPU、内存、磁盘和网络假设，避免凭单项指标仓促归因。

### 从业务症状建立可检验假设

### 从业务症状建立可检验假设

“历史消息查询慢”不是可直接诊断的结论，而是需要拆解的症状。先将描述转为可比较、可复现的观测对象：

- **延迟**：记录客户端总耗时、服务端处理耗时、下游调用耗时；区分平均值与分位数，如 `$P50$、$P95$、$P99$`，避免平均值掩盖尾延迟。
- **范围**：明确是单个会话、特定租户、某类查询条件、某台实例，还是全量请求均受影响；同时确认分页大小、时间跨度、消息量与冷热数据差异。
- **时间窗**：标注开始、结束、持续时间及是否周期性出现，并与发布、流量峰值、批处理任务、备份或索引任务对齐。
- **影响面**：区分“请求变慢”“请求超时”“错误率上升”“连接失败”。同一用户感知可能对应完全不同的服务端状态。

随后建立待证伪的假设，而非直接认定某项资源“有问题”：

1. **CPU 竞争**：查询进程或同机其他进程消耗 CPU，导致运行队列增长、调度等待增加。
2. **内存压力**：工作集无法驻留内存，发生频繁回收、换页或缓存命中下降，间接拉长查询路径。
3. **磁盘瓶颈**：历史消息查询触发随机读、日志写入或存储设备排队，表现为 I/O 等待和请求延迟升高。
4. **网络或 socket 阻塞**：连接积压、重传、端口耗尽，或客户端读取慢，使服务端连接长期占用。
5. **下游依赖变慢**：数据库、搜索、对象存储、鉴权等调用耗时增加；本服务 CPU 可能并不高，却在等待外部响应。

每个假设都应附带预期证据、观察时间窗和作用域。USE（利用率、饱和度、错误）用于提醒“该查什么”，不是看到单项利用率高就自动得出根因。

### 用USE检查表组织证据

### 用 USE 检查表组织证据

USE 将资源现象拆成三个可验证维度：**利用率**、**饱和度**、**错误**。它适合把“历史消息查询慢”的模糊症状转化为检查清单，但不能把任一指标异常直接等同于根因。

- **利用率**：资源在观察窗内实际忙碌的比例。例如用 `ps` 或 `/proc/<PID>/status` 观察进程 CPU 与内存，用 `iostat` 查看磁盘忙碌率，用 `ss` 统计连接与 socket 状态。高利用率说明资源可能成为瓶颈候选，仍需结合请求量、限额和基线判断。
- **饱和度**：工作是否在等待资源服务，即排队或积压。`vmstat` 中持续增长的运行队列、`iostat` 中较高的请求队列与等待时间、`ss` 中大量 `SYN-RECV`、发送队列或接收队列堆积，通常比单纯“利用率高”更接近时延来源。
- **错误**：资源请求是否失败、超时、重传或被拒绝。关注进程异常退出、内存分配失败、磁盘 I/O 错误、连接重置、超时和下游返回的失败码；错误应与 IM 查询失败率、慢请求样本对应。

每条证据都应记录：采集起止时间与时区、单位、PID、主机及容器作用域、采样频率、命令版本或参数，并对账号、会话标识、消息内容等敏感字段脱敏。随后按时间窗关联：若慢查询期间磁盘队列上升且 I/O 等待增加，再检查是否伴随数据库或下游响应变慢；若仅见 CPU 利用率升高而无排队、无错误，则只能说明负载增加，不能据此断言 CPU 是根因。

### 进程与内存证据的作用域

### 进程与内存证据的作用域

进程证据首先要回答“谁在变慢、占了什么、数据属于哪一层”。对 IM 查询服务，可在症状时间窗内以只读方式采集 `ps` 与 `/proc/<PID>/status`，并将每条记录绑定主机名、容器/Pod 标识、PID、采样时刻、单位和采样频率；PID 在容器重启后可能复用，不能脱离时间与实例身份解释。

建议优先规划以下字段：

- `ps`：PID、PPID、启动时间、命令行、`%CPU`、`%MEM`、RSS、VSZ、线程数。命令行可能含令牌、连接串或用户参数，应先脱敏。
- `/proc/<PID>/status`：`VmRSS`、`VmHWM`、`VmSize`、`Threads`、`FDSize`、`voluntary_ctxt_switches` 与 `nonvoluntary_ctxt_switches`。其中 `VmRSS` 是当前驻留物理内存，`VmHWM` 是历史峰值，不能把虚拟地址空间 `VmSize` 当作实际内存占用。
- 文件描述符：`FDSize` 反映描述符表容量，不等于已打开数量；必要时只统计 `/proc/<PID>/fd` 的条目数，并避免记录链接目标中的敏感路径或连接信息。

还应明确 RSS 不等于 Go 堆对象大小。Go 对象、运行时保留空间、栈、共享库映射及页缓存影响会共同进入进程内存视图；若有应用指标，可并列记录 Go 堆在用量、堆保留量与 GC 暂停，但不要用其替代操作系统 RSS。

最后区分作用域：容器内看到的是该命名空间中的进程与限制，主机侧看到的是宿主机总资源及可能的跨容器竞争。`%MEM` 的分母尤其需注明是主机内存还是容器 cgroup 限额。线程数、RSS 或描述符上升只是待检验线索；只有与查询延迟时间窗一致，并结合 CPU、回收、磁盘或下游证据，才可推进归因。

### CPU、内存与磁盘采样判读

### CPU、内存与磁盘采样判读

`vmstat` 与 `iostat` 的价值不在单次快照，而在同一症状时间窗内的连续趋势。先记录主机、容器或宿主机作用域、采样起止时间、间隔与单位；例如 `vmstat 1 60`、`iostat -x 1 60`，并将首行“自系统启动以来的平均值”与后续区间样本分开。

对 `vmstat`，可按因果链阅读：

- `r`：可运行或正在运行的任务数。持续高于可用逻辑 CPU 数，才支持“CPU 排队”假设；容器受配额限制时，应以其实际可用 CPU 而非宿主机总核数比较。
- `b`：不可中断睡眠任务数，常见于块设备或部分内核等待。它升高不能单独证明磁盘慢，需与 `wa`、`iostat` 交叉验证。
- `wa`：CPU 空闲但等待 I/O 的比例。持续升高且伴随磁盘延迟上升，才构成较强证据；若 CPU 已忙于用户态或系统态，`wa` 可能并不高。
- `si`、`so`：每秒换入、换出量。持续非零，尤其 `so` 连续出现并伴随查询变慢，提示内存压力和换页；一次短暂峰值可能只是批处理或页回收。
- 还应结合 `free`、`/proc/<PID>/status` 区分进程常驻内存增长、文件缓存与宿主机整体压力。

对 `iostat -x`，重点观察 `await`：它是 I/O 从提交到完成的平均等待时间，包含排队和设备服务时间。`await` 升高且请求量、队列或吞吐同步变化，说明该设备路径存在延迟；但平均值会掩盖长尾，也不能直接归因于物理盘。

`%util` 仅表示设备在采样期内忙碌的时间比例。对单队列、低并发设备，接近 `100%` 常意味着饱和；对 NVMe、阵列、虚拟块设备等可并行处理请求的设备，高 `%util` 不必然是瓶颈，低 `%util` 也不能排除上游队列、网络存储或限流。USE 的利用率、饱和度、错误率应作为检查表：只有当 IM 慢请求时间窗与 `r/b/wa/si/so/await` 的连续异常在同一作用域内对齐，才应推进相应资源假设。

### Socket证据与反例闭环

### Socket证据与反例闭环

`ss` 看到的是内核 socket 状态与队列，不等于 IM 应用的待发消息数。排查历史消息查询或确认变慢时，应在故障时间窗内按固定频率采样，并记录主机/容器作用域、网络命名空间、PID、端口、单位及脱敏后的对端信息。

- `ss -tanp`：关注连接状态、`Recv-Q`、`Send-Q` 与所属进程。`Recv-Q` 持续增长，表示内核已收数据但应用读取不及时；`Send-Q` 持续增长，表示应用写入后尚未被内核发送或对端窗口、链路存在阻塞。
- `ss -s`：观察 `TIME-WAIT`、孤儿 socket、重传等汇总趋势。短时间大量建连、连接回收异常，可能使查询或确认请求排队。
- 必须区分三层队列：内核 socket 收发队列、IM 服务内部任务/消息队列、确认链路中的未确认消息集合。三者可能相关，但不能互相替代。

每个假设都要有反例。例如，若怀疑“下游确认慢导致 `Send-Q` 堆积”，但多个采样点 `Send-Q=0`、重传未升高，而业务未确认数仍增加，则应转查应用确认回调、消费者线程或下游业务队列。若 `Recv-Q` 高但进程 CPU 空闲，也不能直接断言网络故障；下一观察应是应用线程是否阻塞于磁盘、锁或连接池。反之，socket 队列正常且连接状态稳定，是排除网络传输瓶颈的证据，不是“系统无问题”的结论。

> **要点** — 诊断应以时间对齐的只读证据检验假设；指标必须连同单位、作用域、采样方式与反例一起解释。

诊断时延不能只看“CPU低不低”或“磁盘忙不忙”，而要将事故时间窗内的进程快照与系统间隔样本对应起来，识别资源等待和反例。

### 先定义症状与观测窗口

### 先定义症状与观测窗口

以“IM 历史消息查询变慢”为例，先把模糊反馈转成可验证的症状：用户点击会话后，历史消息首屏返回耗时从正常的数百毫秒上升到数秒，还是请求超时、空白重试，或仅附件、搜索结果变慢？优先记录用户可感知指标，如请求延迟的中位数、P95/P99、超时率与错误率；平均值可能仍正常，却掩盖少量严重卡顿。

随后界定影响范围：

- 是否只影响某个机房、节点、租户或群聊；
- 是否只发生在高峰时段，还是持续存在；
- 新消息收发、未读数同步、媒体下载是否也受影响；
- 慢请求是否集中于特定接口、数据库分片或后端进程。

观测窗口必须包含事故前的正常基线、事故期间和恢复后的对照。例如用户在 `10:15` 首次投诉，`10:18` 至 `10:32` 延迟显著升高，则不能只在 `10:40` 登录机器查看一次 `ps`；应尽量取得覆盖 `10:10`—`10:35` 的间隔样本，并将请求日志按分钟或更细粒度聚合。

采样粒度由症状持续时间决定：持续数十分钟的退化可用 `vmstat 1` 或 `vmstat 5` 观察趋势；仅持续数秒到数十秒的尖峰，则需要更短间隔，并结合应用请求时间戳。进程 `ps`、`cwd`、`fd` 是某一刻的快照，适合确认“当时谁在运行、等待什么、打开了什么”；`vmstat` 的后续行才反映事故窗口内的变化。先固定时间边界，后续 CPU、I/O 与交换证据才有可比性。

### 用ps建立进程快照

### 用 `ps` 建立进程快照

`ps` 是事故现场的“进程身份证照片”：它不能直接证明某次消息为何变慢，却能在同一时间点固定住**是谁在运行、处于何种状态、从哪里启动、持有哪些资源**。先记录时间戳，再采集：

`ps -eo pid,ppid,stat,rss,etime,args`

- **PID**：进程唯一标识，用于把 `ps`、`/proc/<PID>`、日志、连接和火焰图关联起来。不要只按进程名判断；同名 worker 可能有多个实例，某一个 PID 才是异常者。
- **STAT**：调度状态及附加标记。`R` 表示正在运行或等待 CPU，`S` 为可中断睡眠，`D` 为不可中断睡眠，常见于磁盘、网络文件系统等内核 I/O 等待；`Z` 是僵尸进程。若事故窗口中大量关键进程持续为 `D`，应沿 I/O 路径继续取证；单个 `S` 并不等于异常。
- **cwd**：当前工作目录，可由 `readlink /proc/<PID>/cwd` 查看。它能发现进程是否运行在意外的发布目录、挂载点或已删除目录中；后者可能导致磁盘空间“已删除但未释放”。
- **fd**：文件描述符可通过 `ls -l /proc/<PID>/fd` 或 `lsof -p <PID>` 检查。异常增长可能是套接字、日志文件、管道或文件句柄泄漏；关注总量，也要看类型和指向。

三类指标不能混为一谈：

1. **RSS** 是进程当前驻留物理内存，反映实际占用页，增长可提示内存压力，但不等于应用堆大小。
2. **Go 堆对象数量**来自运行时指标，如 `heap_objects`，描述堆中存活对象规模；对象多未必 RSS 高，RSS 高也可能来自 goroutine 栈、映射文件或非 Go 分配。
3. **文件描述符数**是内核资源占用，与内存泄漏是不同证据链；即使 RSS 稳定，fd 耗尽仍会导致新连接、打开文件或写日志失败。

快照应在延迟窗口内重复采集。一次 `ps` 只能说明当时状态；连续样本中的 RSS、fd、`D` 状态变化，才更接近故障演化过程。

### 用vmstat读取事故窗口

### 用 `vmstat` 读取事故窗口

`vmstat 1 10` 的价值不在于某个数字“高不高”，而在于连续样本能否还原事故窗口中的资源竞争链。首行通常是开机以来的累计平均值，不能直接代表当前故障；应重点比较后续按间隔采集的行，并与消息延迟发生时刻对齐。

- `r` 表示等待 CPU 调度的可运行任务数。若 `r` 持续大于逻辑 CPU 数，同时 `us` 或 `sy` 较高、`id` 接近零，说明请求可能在运行队列中排队：前者偏用户态计算，后者偏内核调用、网络协议栈、上下文切换等开销。
- `b` 表示不可中断睡眠中的任务，常见于块设备 I/O 等待。`b` 上升且 `wa` 上升，才构成较强的“存储或 I/O 路径拖慢”证据；仅凭高 `wa` 不能断言某一条磁盘查询变慢，它反映的是 CPU 在该采样间隔内无可运行工作、同时存在 I/O 等待的时间比例。
- `id` 高并不等于资源充裕。若同时 `b` 高、`wa` 高，CPU 虽空闲，业务线程却可能被 I/O 卡住；若 `r` 很低而延迟仍高，应继续检查锁等待、网络等待、下游服务和应用线程池。
- `si`、`so` 分别是换入、换出活动。持续非零，尤其伴随 `r` 增大、`sy` 升高或延迟抖动，提示内存压力导致页面换入换出；`so` 持续出现通常比瞬时峰值更值得警惕。

因此，可将事故样本归纳为：`r↑ + us/sy↑` 指向 CPU 争用，`b↑ + wa↑` 指向 I/O 等待，`si/so↑` 指向交换压力；若这些组合均不成立，就不应把“CPU 低”误判为系统无资源问题。

### 避开累计行与单指标结论

### 避开累计行与单指标结论

`vmstat 1 5` 的第一行不是“刚刚这一秒”的状态，而是自开机以来的累计平均值；后续各行才表示相邻采样间隔内的变化。因此，若 IM 消息在 `10:03` 出现时延，应优先对齐 `10:03` 附近的间隔样本，而不能用首行的 `wa`、`id` 为事故下结论。

例如，首行显示 `wa=2`，可能掩盖了刚发生的短时 I/O 堵塞；反过来，某个间隔 `wa=40` 也不等于“某一条磁盘查询耗时 40%”。`wa` 表示采样期内 CPU 有可运行之外的时间在等待 I/O 完成，它可能来自日志刷盘、网络块设备、文件系统回写、容器卷、内存回收触发的换页等。还应同时检查：

- `b` 是否上升：是否有不可中断睡眠的任务堆积；
- `r` 是否持续大于 CPU 核数：是否同时存在运行队列竞争；
- `si/so` 是否非零：是否发生换入、换出，I/O 等待可能由交换而非业务磁盘查询引起；
- `ps` 中目标进程的 `STAT`、`cwd`、`fd`：确认其处于运行、可中断睡眠还是 `D` 状态，以及是否持有异常目录或大量文件描述符。

同样，`CPU` 利用率低不能推出“资源充裕”。若 `id` 高但关键进程处于 `D` 状态、`b` 增长，CPU 只是空闲地等待外部资源；若 `id` 高而 `r` 突发升高，则可能是短任务排队被采样平均值稀释。诊断应以事故窗口内的连续样本和进程快照构成证据链，而非依赖单个百分比。

### 从快照形成竞争假设

### 从快照形成竞争假设

以 IM 消息“发送成功但接收回执延迟”这一合成事故为例：10:03—10:05 的延迟从 $80\text{ms}$ 升至 $4\text{s}$。先在窗口内保存 `ps -eo pid,stat,pcpu,pmem,etime,cmd`，并检查关键进程的 `/proc/PID/cwd`、`/proc/PID/fd`；再对照 `vmstat 1` 的间隔样本。注意：`vmstat` 第一行是开机以来汇总，不能直接解释本次事故；`ps`、内存字段则只是当前快照。

可形成若干可竞争的解释：

- **CPU 争用**：`r` 持续高于 CPU 核数，`us+sy` 接近饱和，IM 进程为 `R` 或频繁切换状态。反例是 `r` 很低且 `id` 很高；此时“CPU 低”不等于健康，线程仍可能在锁、网络或磁盘上等待。下一步观察线程栈、运行队列及请求处理线程数。
- **I/O 等待**：`b` 增长、`wa` 升高，进程常为不可中断睡眠 `D`，其 `cwd` 或已打开的 `fd` 指向日志、附件、队列挂载目录。反例是高 `wa` 但关键进程并未访问该设备，或延迟与该目录无时间相关性；`wa` 本身也不是某一条磁盘查询的延迟。下一步只读检查挂载点、设备统计和慢请求对应文件。
- **交换抖动**：`si/so` 在事故窗口持续非零，`r`、`b` 波动，关键进程 RSS 或可用内存异常收缩。反例是仅偶发一次 `si/so`、随后归零且延迟未改善。下一步检查内存压力、容器限制与大进程增长轨迹。

`fd` 数量异常还可提出“描述符泄漏或连接堆积”假设；但必须确认其类型和增长趋势，不能只凭单次快照定责。

> **要点** — 以事故窗口内的间隔样本串联进程快照；资源指标必须结合定义、时间尺度和反例解释。

进程内存与文件描述符是关键证据，但单一数值变化不能直接等同于内存泄漏或连接泄漏。

### 先界定进程证据的观察边界

### 先界定进程证据的观察边界

分析“历史消息查询变慢”时，先固定证据的时间窗与对象范围，而不是看到某个进程 `VmRSS` 或文件描述符数偏高就下结论。

- **时间窗**：以慢查询发生前、发生中、恢复后为连续窗口。至少记录请求量、查询耗时分位数、错误率、GC 停顿、`/proc` 指标与磁盘换页指标；单次采样只能说明瞬时状态。
- **实例范围**：区分慢请求命中的具体实例、同一服务的健康实例，以及承载数据库、缓存或代理的相关进程。若只有少数实例变慢，优先比较实例间差异；若全量变慢，再检查共享依赖与主机资源。
- **基线**：选取相同业务时段、相近连接数和请求量下的正常样本。高峰期 `VmRSS`、`HeapAlloc`、连接数和 FD 数共同上升，可能只是容量随负载扩张。

读取 `/proc/PID/status` 时，`VmSize` 是虚拟地址空间，不等于实际占用；`VmRSS` 是当前驻留物理内存，还应拆分 `RssAnon`、`RssFile`、`RssShmem`。例如 RSS 从 200 MiB 到 220 MiB，只能证明多了约 20 MiB 驻留页；它可能来自 Go 堆、文件页、共享内存或映射变化。

文件描述符同理：先记录总数，再按套接字、普通文件、管道、匿名对象和映射来源分类。排查时仅保留类型、数量与必要的脱敏标识，避免在诊断记录中暴露用户目录、令牌或敏感路径。

### 读懂 status 中的地址空间与常驻集

### 读懂 status 中的地址空间与常驻集

`/proc/<PID>/status` 将进程内存拆成“已映射的虚拟地址”和“当前驻留在物理内存中的页”两层：

- `VmSize`：进程占用的**虚拟地址空间总量**。它包含尚未实际分配物理页的匿名映射、共享库、文件映射、线程栈、保留地址区等；数值大并不等于真实耗费同等 RAM。
- `VmRSS`：当前驻留在 RAM 中的总页数，即常驻集。通常可近似理解为  
  $VmRSS \approx RssAnon + RssFile + RssShmem$，  
  但这是内核统计快照，可能有页表更新与采样误差。
- `RssAnon`：匿名页的常驻部分，如 Go 堆、goroutine 栈、`malloc` 分配、匿名 `mmap`。它增长值得重点关注，但仍不能直接证明泄漏：GC 尚未归还页面、短时流量峰值或缓存扩张都可能造成增长。
- `RssFile`：文件支持页的常驻部分，如可执行文件、动态库、内存映射文件及页缓存相关映射。这类页通常可被内核回收，且可能与其他进程共享，不能简单视为进程独占内存。
- `RssShmem`：共享内存页的常驻部分，例如 tmpfs、共享内存段或某些容器运行时映射；同一物理页也可能被多个进程计入各自 RSS。

因此，`VmRSS` 从 200 MiB 升到 220 MiB，只说明该进程当前多驻留约 20 MiB 页面，不能说明增长来自 Go 堆、文件映射还是共享内存，更不能单凭一次变化判定泄漏。应结合 `HeapAlloc`、`HeapReleased`、GC 次数、连接数及系统 `si/so`（换入/换出）趋势，确认增长是否持续、是否可回落，以及是否伴随内存回收压力。

### 将 RSS 变化映射到 Go 运行时证据

### 将 RSS 变化映射到 Go 运行时证据

`VmRSS` 从 `200MiB` 升至 `220MiB`，只能说明该进程当前驻留在物理内存中的页面增加了约 `20MiB`；它不是“Go 堆泄漏”的直接证据。RSS 同时包含匿名页、文件映射页、共享内存页以及运行时、线程栈等开销，应先拆看：

- `RssAnon`：通常更接近 Go 堆、goroutine 栈、C 分配等匿名内存；
- `RssFile`：可执行文件、动态库、`mmap` 文件及页缓存映射；
- `RssShmem`：共享内存、某些 IPC 或临时共享映射。

再将其与 Go 指标按时间对齐：

- `HeapAlloc` 持续上涨，业务低峰后不回落，且 GC 后仍逐步抬升：更像存活对象累积；
- `HeapAlloc` 回落而 `HeapReleased` 很低：Go 已回收对象，但保留了堆页，RSS 暂不下降未必异常；
- `HeapAlloc` 平稳、RSS 上涨而 `RssFile` 增加：优先检查文件映射、二进制库或读取模式；
- 连接数、活跃会话数、goroutine 数同步增长：RSS 增长可能是正常容量扩张，而非泄漏；
- GC 次数和暂停明显增加，同时 `HeapAlloc` 高位运行：说明分配压力增大，需继续看分配热点与对象生命周期。

还应查看系统换页证据：`/proc/vmstat` 中 `si/so` 持续非零，表示发生换入/换出；此时 RSS 的短期波动可能受内存回收和竞争影响。只有当业务负载、连接数下降后，`HeapAlloc`、匿名 RSS 仍长期单调上升，并能在堆剖析中找到未释放引用，才能较有把握地定性为 Go 内存泄漏。

### 以合成样本区分缓存、堆增长与换页

### 以合成样本区分缓存、堆增长与换页

设某 IM 进程的 `VmRSS` 在 10 分钟内从 `200MiB` 升至 `220MiB`。这只说明当前驻留页增加了 `20MiB`，不能直接判定泄漏。可构造竞争假设：

- **缓存预热或文件映射增长**：`RssFile` 增加约 `18MiB`，`RssAnon` 基本不变；请求量、活跃会话数同步上升，文件描述符数也可能随连接或日志文件正常增长。  
  **只读验证**：连续采集 `/proc/PID/status`、`/proc/PID/smaps_rollup` 的匿名/文件页，以及 fd 数与连接数；观察流量回落后 `RssFile` 是否稳定或回落。  
  **反例**：若 `RssAnon` 持续单调增长而 `RssFile` 不变，则“文件缓存主导”不成立。

- **Go 堆扩张但可回收**：`RssAnon` 上升，`HeapAlloc` 随消息积压或在线用户增长，GC 后下降；`HeapReleased` 可能滞后，故 RSS 未立即下降。  
  **只读验证**：按 GC 周期对齐采集 `HeapAlloc`、`HeapInuse`、`HeapReleased`、GC 次数和 goroutine 数。  
  **反例**：负载下降、GC 多轮完成后 `HeapAlloc` 仍持续增长，才更接近对象滞留或泄漏。

- **内存压力与换页**：RSS 变化不大甚至下降，但系统 `si/so` 持续非零、延迟升高；此时问题可能是页被换出后重新换入，而非进程“占用更多”。  
  **只读验证**：关联 `/proc/vmstat` 的 `pswpin/pswpout`、内存可用量与时延分位数。  
  **反例**：`si/so=0` 且可用内存充足，换页不应作为首要解释。

fd 数应与连接数、监听套接字、日志轮转共同观察；只报告类型和计数，避免暴露具体文件路径、用户标识或套接字端点。

### 审查文件描述符增长而不误判泄漏

### 审查文件描述符增长而不误判泄漏

`/proc/<PID>/fd` 中每个条目对应一个仍被进程持有的文件描述符，但“总数上升”不等于泄漏。应先记录基线、请求量、在线连接数和部署时间，再按类型拆分：

- `socket:[inode]`：通常对应客户端连接、服务端接受的连接、上游连接或监听套接字；
- 普通文件：日志、配置、证书、临时文件、数据库文件等；
- `pipe:[inode]`、`eventfd`、`epoll`：常见于子进程通信、运行时事件循环和并发框架；
- 匿名映射或设备文件：需结合具体组件判断，不能按“文件泄漏”处理。

可用 `ls -l /proc/<PID>/fd`、`lsof -p <PID>` 或按链接类型聚合计数；对外输出时应隐藏真实目录、用户名、租户标识、令牌文件名和内部地址。更稳妥的证据是趋势而非单点：若 FD 随并发连接上升，并在连接关闭、流量回落或 GC/空闲回收后下降，通常是正常容量增长；若请求已结束、连接数已回落而 FD 持续单调增加，则重点检查连接是否未关闭、响应体是否未释放、文件句柄是否遗漏 `Close`、子进程管道是否残留。

还要与生命周期指标交叉验证：比较“新建连接数—关闭连接数”、连接池活跃/空闲数、超时数量及错误重试率。若套接字 FD 增长同时出现大量 `CLOSE_WAIT`，常提示本端未完成关闭；若普通文件 FD 增长且路径模式重复，才更像文件句柄泄漏。最后检查 `ulimit -n` 与进程限制：接近上限说明存在可用性风险，但仍不能仅凭 FD 总数断言根因。

> **要点** — RSS 与 FD 都是线索而非结论；必须用时间窗、映射分类和 Go 运行时指标交叉验证。

当历史消息查询变慢时，磁盘指标能提供方向，却不能直接证明根因。先确认请求实际经过的主机与设备，再用时间窗内的证据建立可证伪的竞争假设。

### 先界定症状与观测边界

### 先界定症状与观测边界

“历史消息查询变慢”首先应被定义为可对齐的症状，而非笼统的“磁盘慢”。例如：在 `10:05–10:15`，历史查询端到端延迟的 `p95` 从基线 `120 ms` 升至 `480 ms`，同时错误率、超时率或查询量是否变化？若只看到平均耗时上升，可能是少量长尾请求；若 `p95`、`p99` 同时恶化，才更像共享资源竞争或下游抖动。

观测边界至少包含四项：

- **时间窗**：应用延迟、`iostat`、`vmstat` 必须覆盖同一窗口。不要把上午的 `await` 与下午的接口慢查询直接关联。
- **请求路径**：确认历史查询是本机读库、本机读索引，还是经由 RPC 访问远端数据库、对象存储或搜索集群。
- **目标主机**：应用实例变慢，不等于应用所在机器磁盘变慢。若数据实际在远端 DB，应优先采集 DB 主机及其存储设备的证据。
- **实际设备**：识别承载数据目录的挂载点、逻辑卷、底层块设备与 RAID/云盘映射；`sda` 的指标不能自动代表 `/data` 所在设备。

可先形成一条待验证链路：`历史查询 p95 上升 → 请求命中某数据库/索引节点 → 该节点的数据设备在相同时间窗出现排队或服务延迟异常`。其中任一环无法确认，都只能称为相关线索，不能归因。

### 读懂扩展磁盘指标

### 读懂扩展磁盘指标

`iostat -x -y 1` 常用于观察块设备的短时间行为，但三个核心指标回答的是不同问题，不能互相替代。

- `await`：一次 I/O 从提交到完成的平均等待时间，单位为毫秒（ms）。它同时包含**队列等待**与**设备服务**：
  $$
  await \approx 排队时间 + 服务时间
  $$
  因而 `await` 从 `4ms` 升至 `38ms`，只能说明 I/O 完成变慢；不能仅凭此断言“磁盘坏了”。可能是请求排队、底层存储变慢、读写模式改变，或虚拟化/网络存储链路抖动。

- `aqu-sz`：统计窗口内的平均未完成 I/O 数，即平均队列长度。它不是某一瞬间看到的队列深度。`aqu-sz` 升高通常意味着积压增加；结合 Little 定律，可粗略理解为：
  $$
  平均队列长度 \approx IOPS \times 平均响应时间
  $$
  但它不能单独证明设备已饱和：高并发应用本身就可能维持较长队列，而较低的队列也可能因单个慢 I/O 导致高 `await`。

- `%util`：统计窗口内设备至少有一个 I/O 在处理的时间比例。传统单队列磁盘接近 `100%` 往往值得警惕；但对 NVMe、RAID、云盘等可并行处理多个请求的设备，`100%` 只表示“持续忙碌”，不等于吞吐已到上限，更不等于性能必然恶化。

应把三者放在同一时间窗解释：`await` 上升、`aqu-sz` 增大、`%util` 持续高位，才较支持 I/O 竞争或容量压力假设；若 `await` 高而 `%util` 不高，应继续检查远端存储、虚拟化宿主机或请求路径。`-y` 会跳过开机以来的累计首屏，避免把历史平均值误当作当前一分钟的证据。

### 排除首行累计值误读

### 排除首行累计值误读

`iostat -x interval` 的第一组输出不是“刚过去 interval 秒”的状态，而是**自开机以来的累计平均值**。它会把启动初期的空闲、历史高峰、设备重置前后的行为混在一起，因此不能直接与当前慢查询时间窗对应。

例如，刚收到“历史消息查询变慢”的告警后执行：

`iostat -x 1`

首行显示 `await=4ms`，随后各行显示 `await=38ms`。这里的 `4ms` 只说明机器开机至今的总体平均延迟较低；真正反映当前一分钟压力的是后续按 1 秒间隔计算的样本。若误读首行，可能得出“磁盘延迟正常”的错误结论。

推荐使用：

`iostat -x -y 1`

其中：

- `-x`：输出扩展指标，如 `await`、`aqu-sz`、`%util`；
- `-y`：跳过自开机累计的首行；
- `1`：每秒输出一次增量样本。

采样不应只看单行。应至少连续观察数十秒，并与应用慢请求发生时段对齐，记录 `await` 是否持续升高、`aqu-sz` 是否累积、`%util` 是否变化。对短暂尖峰，可缩短间隔；对周期性任务，则应覆盖一个完整周期。

还要明确：这些样本只描述**本机该块设备**的增量 I/O 行为。若应用实际读取的是远端数据库、网络文件系统或另一台存储节点，本机 `iostat` 即使平稳，也不能排除远端存储排队；应先核实请求路径，再到实际承载数据的主机和设备上执行同样的连续采样。

### 用合成数据形成竞争假设

### 用合成数据形成竞争假设

设历史消息查询的 `p95` 在 10:05 后由 `180ms` 升至 `920ms`。同一时间窗采样显示：

| 指标 | 基线 | 异常期 |
|---|---:|---:|
| 目标设备 `await` | `4ms` | `38ms` |
| `vmstat` 的 `b` | `0` | `4` |
| `vmstat` 的 `wa` | `2%` | `22%` |

这组数据说明：更多进程处于不可中断 I/O 等待，且该设备一次 I/O 的平均完成时间显著变长。`await` 包含排队时间与服务时间，因此 `4→38ms` 既可能是设备本身变慢，也可能是并发请求增多造成排队；`aqu-sz` 若同步升高，会进一步支持“队列堆积”。

可形成三组竞争假设：

1. **本机磁盘竞争**：查询实际在本机读取索引、消息分片或缓存文件；异常窗口内 `await`、`aqu-sz`、`wa` 与查询 `p95` 同升。继续检查谁在读写：数据库进程、备份任务、日志压缩、邻居容器或宿主机其他租户。
2. **远端依赖变慢**：应用节点虽出现高 `wa`，但查询实际访问远端数据库、网络块存储或对象存储。本机设备指标只能说明本机也有 I/O 压力，不能证明它是查询根因；必须在远端数据库主机、存储卷和网络链路取得同窗证据。
3. **错误归因**：若慢查询流量被路由到另一台机器，或实际数据落在另一块设备，则本机 `iostat` 的异常只是巧合。先从连接串、服务发现、查询日志、挂载路径和 `lsblk` 映射确认请求路径。

注意 `iostat -x -y 1`：`-y` 会跳过开机以来的累计首屏，只保留按秒增量。对于并行 SSD，`%util` 高不必然表示饱和；应结合 `await`、`aqu-sz`、吞吐量及应用延迟判断。

### 从本机线索走向证据链

### 从本机线索走向证据链

`iostat -x -y 1` 与 `vmstat 1` 只能说明“本机可能存在存储等待”，不能自动证明历史消息查询慢由本机磁盘造成。应先把观测串成可反驳的链路：

1. **确认请求落点**：查应用配置、连接池、服务发现与追踪记录，确认查询是在本机访问本地盘，还是经网络访问远端数据库。若数据库地址、读副本或对象存储在远端，本机 `await` 升高最多是并发症状，必须转向远端主机、数据库慢查询、存储卷与网络时延取证。

2. **正确读取本机窗口指标**：`iostat -x -y 1` 跳过开机以来累计的首行。若某设备 `await` 从约 `$4\,ms$` 升至 `$38\,ms$`，同时 `aqu-sz` 增大，表示一次 I/O 的排队加服务时间明显变长；它不等于纯设备服务时间。`%util` 对并行 SSD 不能简单按“接近 100% 即饱和”解释，需结合队列长度、吞吐、延迟基线判断。

3. **与调度状态交叉验证**：若同一时间窗 `vmstat` 中 `b` 从 `0` 升至 `4`、`wa` 从 `2%` 升至 `22%`，且查询时延超过历史 `p95`，则“本机 I/O 竞争影响请求”的假设增强。再用 `pidstat -d 1`、`iotop -o` 或进程级指标确认是数据库、日志、备份还是其他进程在读写该设备。

下一项只读验证应是：将慢请求的追踪时间戳与目标数据库节点的慢查询、连接等待、磁盘延迟对齐。反例是：应用实际读远端数据库，且远端查询/网络时延升高而本机进程无显著 I/O；此时本机磁盘不是首要根因。

> **要点** — await 升高是排队加服务变慢的信号；先证实请求使用本机设备，SSD 的 %util 不能单独证明饱和。

以历史消息查询变慢为场景，学习用 ss 将连接状态与收发队列转化为可验证的网络证据，而非直接推断业务结论。

### 先界定症状、主机与观测窗口

### 先界定症状、主机与观测窗口

排查“历史消息查询变慢”前，先把一句模糊投诉拆成可观测的边界。`ss` 看到的是**执行命令这一台主机、这一瞬间、这一组网络命名空间中的 TCP 套接字**；它不是全站在线用户表，也不是消息系统的全局健康度。

至少记录以下事实：

- **症状时间窗**：慢查询从何时开始、持续多久、是否与发布、扩缩容、流量峰值或网络告警重合。不要只在故障结束后执行一次 `ss`，再将快照解释为故障现场。
- **受影响范围**：是全部客户端、某地域、某运营商、某类版本，还是仅少数会话？同时区分“请求发不出去”“服务端响应慢”“响应已到但客户端处理慢”。
- **观测主机与角色**：命令运行在客户端、接入层、查询服务实例、代理节点还是数据库侧？同一条连接在不同主机上会呈现不同的本地端口、队列和状态。
- **实例集合**：若服务有多个副本，单机 `ESTAB` 约为 2000，只能说明该实例当前约有 2000 个已建立 TCP 连接；不能推出全系统有 2000 个用户，更不能推出有 2000 条活跃消息请求。
- **采样方式**：在异常窗口内按固定间隔连续采样，例如每 10 秒记录一次状态、`Recv-Q`、`Send-Q` 与五元组摘要。趋势比单点更有证据力。

地址、端口和连接标识应脱敏保存，但要保留其可关联性，例如将同一客户端地址稳定映射为同一匿名标识。随后再结合半帧、收发队列与流控证据判断：本机 `Send-Q` 有字节不等于应用仍有“未发送消息”，`Recv-Q` 非零也不等于已经收到完整业务帧；远端是否拥塞、是否已读取数据，不能仅凭本机快照直接断言。

### 用 ss -s 建立连接状态基线

### 用 `ss -s` 建立连接状态基线

执行 `ss -s` 可先获得本机网络栈的连接状态摘要，例如：

`TCP:   2148 (estab 2003, closed 71, orphaned 0, timewait 64)`

其中最容易被误读的是 `estab 2003`。它表示**当前由本机 TCP 协议栈维护、处于 `ESTABLISHED` 状态的 TCP 套接字数量**；在常见的一对一连接中，可近似理解为约两千条已完成握手且尚未关闭的连接。

但它不能直接推出：

- 有两千名在线用户：一个用户可能有多条连接，或多端登录；反向代理、服务间调用、健康检查也会计入。
- 有两千条活跃消息会话：`ESTABLISHED` 只说明 TCP 连接存在，不说明近期有 IM 消息收发。
- 远端也有相同数量的连接：该值是**本机视角**。NAT、负载均衡、代理转发都会改变不同节点看到的连接数。
- 服务器承受两千个客户端：监听端、客户端、代理端看到的 `ESTABLISHED` 都是各自本机的套接字统计。

其他状态同样应按协议语义解读：`timewait` 常反映近期主动关闭连接后的残留；`orphaned` 表示脱离进程文件描述符引用、仍由内核处理的套接字；`closed` 等汇总项的具体含义还会受 `ss` 版本和内核统计口径影响。

因此，`ss -s` 的价值是建立“连接状态基线”：平时记录 `estab`、`timewait` 等数量及其波动，故障时比较是否出现异常增长。若历史消息查询变慢，而 `estab` 长期稳定在约两千，只能初步排除“连接数突然暴涨”这一线索；还必须继续检查特定连接的 `Send-Q`、`Recv-Q`、半帧积压及应用层流控，才能形成完整证据链。

### 读懂特定连接的 Recv-Q 与 Send-Q

### 读懂特定连接的 Recv-Q 与 Send-Q

对单条 TCP 连接执行 `ss -tn` 时，`Recv-Q` 与 `Send-Q` 展示的是**本机内核套接字视角下的字节量**，不是 IM 业务消息数量。

- `Recv-Q`：已经到达本机、进入 TCP 接收缓冲区，但尚未被本机应用通过 `read()`、`recv()` 等调用取走的字节。
- `Send-Q`：本机应用已经写入内核发送路径、但尚未被对端确认完成的字节；其中可能包含尚未实际发出的数据，也可能是已发出但仍在等待 ACK 的数据。

因此，看到：

`Recv-Q = 8192`

只能说明该连接有约 8192 字节等待本机应用读取，不能推出“有一条 8 KB 消息未处理”。TCP 是字节流：一个 IM 帧可能只到达帧头，多个小帧也可能连续堆积在同一缓冲区；还可能存在压缩、加密、长度字段和粘包后的残余字节。完整帧应由应用层协议解析器依据边界判断。

同理：

`Send-Q = 65536`

不等于“应用还有 65536 字节没发送”，更不等于“积压了若干条待发送消息”。应用层待发送队列通常位于进程内存、消息中间件或异步运行时；只有应用调用写操作后，数据才可能进入内核发送缓冲。`Send-Q` 增长应结合拥塞窗口、对端接收窗口、重传、网络 RTT 及本机写入速率分析。

诊断时还要明确地址方向：`ss` 中本地地址对应本机套接字，队列数值描述本机状态；不能把本机 `Recv-Q` 直接解释为“远端处理慢”，也不能把本机 `Send-Q` 直接解释为“本机业务未消费”。应再结合应用半帧日志、写入/读取速率与流控指标，形成完整证据链。

### 合成快照：提出竞争假设与反例

### 合成快照：提出竞争假设与反例

设消息服务端执行 `ss -tanp` 后得到脱敏快照：

- `ESTAB 0 262144 10.2.1.8:443 10.2.7.31:51820`
- `ESTAB 8192 0 10.2.1.8:443 10.2.7.32:51821`
- `CLOSE-WAIT 0 0 10.2.1.8:443 10.2.7.40:52001`
- 汇总：`estab 2000`，少量 `SYN-RECV` 与 `TIME-WAIT`。

这只能说明**本机 TCP 视角**下的连接状态和内核队列，不能直接称为“2 000 在线用户”或“消息堆积”。

可提出相互竞争的假设：

1. **服务端读取不足**：第二条的 `Recv-Q=8192` 表示字节已到达本机内核、尚未被应用读走。反例是：若应用线程正常持续 `read`，且多个采样周期内 `Recv-Q` 很快回落，则不能据此认定服务端消费卡住；它也可能只是半帧暂存。

2. **客户端接收变慢**：第一条的 `Send-Q=262144` 表示服务端内核仍有待发送字节，不等于应用层“尚未发送的消息队列”。若该值持续增长，并结合重传、拥塞窗口或客户端侧读速率下降，才支持对端接收慢；反例是队列迅速清空，说明只是瞬时流量峰值。

3. **网络异常**：若大量连接同时出现发送队列滞留、重传升高或连接状态频繁切换，可怀疑链路问题。反例是仅少数地址异常且集中于同一客户端网段，应优先排查该客户端或其出口，而非宣布服务端网络故障。

4. **业务队列积压**：`ss` 看不到应用消息队列。即使 TCP 队列均很小，业务投递、序列化、持久化或消费者队列仍可能积压；必须以应用指标佐证。

地址应脱敏，且要明确采样位置：服务端的 `Send-Q` 对应服务端本机待发字节，不能混同为客户端的接收队列。连续快照、应用读写指标与流控信号，才构成可验证证据链。

### 连接证据链的边界与下一观察

### 连接证据链的边界与下一观察

`ss -s` 或 `ss -tan` 提供的是某一时刻的本机 TCP 视角，适合提出假设，不足以直接宣判业务故障。证据链至少要区分四层：

- `ESTAB≈2000`：表示本机当前处于 Established 状态的套接字数量，可能包含空闲长连接、重复登录终端、代理连接或即将释放的连接；它不等于在线用户数，更不等于正在发送消息的用户数。
- `Send-Q>0`：表示内核发送队列中仍有待处理字节，原因可能是对端窗口变小、链路拥塞、对端读取慢，或短暂调度延迟；它不是“应用还有消息没调用发送”的证据。应用未发送的数据可能仍在用户态缓冲区、批处理队列或半帧组装区。
- `Recv-Q>0`：表示数据已到达本机内核、尚未被应用读取；它不能说明已收到完整 IM 帧。若协议帧跨多个 TCP 段，队列中的字节可能只是长度字段、半个消息体，或多个粘连帧。
- 应用确认：TCP 已确认只说明字节被对端 TCP 栈接收，不说明对端 IM 服务已解析、落库或向用户展示。业务确认必须由应用日志、消息状态或协议回执证明。

地址也必须脱敏：记录时使用哈希、网段归类或角色标签，如“接入节点→消息节点”，避免暴露用户 IP、端口和会话标识。并明确 `ss` 中本地地址是**本机监听/连接端点**，对端地址只是该连接可见的远端端点；不能据此推断整个远端集群、用户真实位置或中间代理后的原始来源。

下一项只读证据应按假设选择：怀疑半帧或解析停滞，查看应用的收包长度、解帧失败和确认日志；怀疑流控，观察发送队列、对端窗口与写阻塞指标；只有日志和指标无法解释字节级时序时，才在合规前提下进行限时、过滤后的抓包。

> **要点** — ss 展示的是本机内核 TCP 视角；状态与队列是诊断线索，必须结合协议分帧、业务确认和后续证据验证。

以历史消息查询 p95 从60ms升至240ms为起点，用同一时间窗的基线与事故数据建立证据链，避免把资源异常直接等同于根因。

### 先固定症状、时间窗与对照基线

### 先固定症状、时间窗与对照基线

先把“慢”定义为可复现的业务症状，而不是某台机器的资源告警：本次对象是**历史消息查询**的端到端时延，统计口径为同一接口、同一请求类型、相近租户/会话规模下的 `p95`。基线期为事故前稳定运行窗口，`p95≈60ms`；事故期选择告警开始后、流量形态未明显变化的连续窗口，`p95≈240ms`。两者相差 $4\times$，才是后续证据链需要解释的现象。

对照表必须统一聚合维度与采样窗口，至少同时保留应用、主机和依赖侧指标：

| 维度 | 基线 | 事故期 | 初步含义 |
|---|---:|---:|---|
| 历史查询 `p95` | 60ms | 240ms | 已确认的业务退化 |
| 运行队列 `r2` | 2 | 2 | 暂无明显 CPU 排队证据 |
| 阻塞任务 `b0` | 4 | 4 | 未显示新增不可中断阻塞 |
| `wa` | 2% | 22% | 存在 I/O 等待信号 |
| `iostat await` | 4ms | 38ms | 本地块设备时延恶化 |
| RSS | 200MiB | 220MiB | 内存增长有限 |
| socket 队列 | 接近 0 | 接近 0 | 未见显著本机收发积压 |

这里的关键约束是：`await` 升高只能说明本机观测到 I/O 变慢，尚不能证明历史查询确实走了该读路径，更不能直接排除数据库、远端依赖或慢接收方。下一步应以同一批慢请求的端到端 Trace 为主线，对照数据库查询耗时、连接池等待、远端调用与应用内处理分段；只有资源异常与 Trace 中对应阶段同步变长，才能将相关性推进为可检验的因果假设。

### 把纸上表拆成资源信号

### 把纸上表拆成资源信号

同一事故窗内，`p95: 60→240ms` 是结果；`r、b、wa、await、RSS、socket queue` 是解释结果的候选证据，不能直接互相替代。

- `r: 2→2`：可运行队列未增长，反例是 CPU 排队并不明显；但这不证明 CPU 无影响，单核热点、软中断或应用线程锁竞争仍可能存在。下一步只读查看各核利用率、上下文切换、热点栈和线程状态。
- `b: 0→4` 与 `wa: 2%→22%`：出现更多不可中断等待，且 CPU 大量时间在等 I/O，支持“本机存储路径变慢”。其反例是等待的 I/O 未必属于消息查询，也可能是日志、刷盘、文件缓存回收。下一步按进程、文件描述符和块设备读取 `iostat`、`pidstat -d`、页缓存指标。
- `await: 4→38ms`：块设备请求端到端平均等待显著上升，是饱和或后端盘延迟的强信号；但 `await` 混合读写，且不能证明业务请求真的读到了该盘。应在 Trace 中对照查询跨度、文件读取跨度与数据库调用跨度。
- `RSS: 200→220MiB`：仅小幅上涨，不足以单独支持内存泄漏或 OOM；仍需检查缺页、回收、交换和 GC 暂停，排除内存压力间接放大 I/O。
- 套接字队列接近零：缺少本机发送或接收缓冲积压，反驳“网络队列堆积”这一解释；但慢接收方、远端网络和应用层等待仍未排除。

因此可暂列“本地 I/O 影响查询”为高优先级候选，影响是拉长读路径或数据库等待；最终须将端到端 Trace 的慢段与数据库慢查询、连接池等待、存储读延迟按同一请求和时间窗对齐。

### 评估本地I/O竞争假设

### 评估本地 I/O 竞争假设

同一事故时间窗内，阻塞任务数 `b` 从 `0` 升至 `4`，`iowait`（`wa`）从 `2%` 升至 `22%`，设备平均等待时间 `await` 从 `4ms` 升至 `38ms`。三项指标方向一致：请求进入块设备后排队或服务时间显著变长，部分线程因等待 I/O 而不可运行。本地存储竞争因此是解释历史消息查询 p95 由 `60ms` 升至 `240ms` 的强候选。

| 假设 | 支持证据 | 反例与缺口 | 下一步只读观测 | 可能影响 |
|---|---|---|---|---|
| 本地 I/O 竞争拖慢历史查询 | `b↑`、`wa↑`、`await↑` 同窗出现 | RSS 仅 `200→220MiB`，socket 队列近零；尚未证明历史查询实际读取本地盘 | 对端到端 Trace 按 span 分解：应用、数据库、文件系统与下游等待；对照数据库查询耗时、磁盘读写量、缓存命中率、日志刷盘延迟 | 若查询或日志与其他工作负载争用同一设备，可放大尾延迟 |
| I/O 异常只是伴随现象 | `await=38ms` 足以影响依赖磁盘的请求 | CPU 饱和、线程池排队、慢接收方仍未排除；若 Trace 中 DB/文件 span 未变慢，则 I/O 非主因 | 查看 CPU 使用率与运行队列、请求处理队列、每接收方发送/确认时延；将 Trace 中慢请求与设备延迟逐请求关联 | 避免将系统级 `wa` 直接归因于业务读路径 |

关键判据不是“机器发生了 I/O 等待”，而是慢请求的关键路径是否包含同步本地读、数据库落盘或日志刷盘，并且该 span 的增长与 `await` 同时发生。若 Trace 显示 `DB` 或文件读取阶段由约 `4ms` 扩大到数十毫秒，且数据库磁盘指标同步恶化，I/O 假设增强；若主要耗时位于应用排队、序列化或下游发送，则应降级该假设。

### 保留CPU与慢接收方反例

### 保留 CPU 与慢接收方反例

事故窗口中，历史查询 `p95` 由 `60ms` 升至 `240ms`，但运行队列 `r` 仍约为 `2`，与基线持平；套接字发送、接收队列也接近零。这两项反例削弱了“CPU 饱和”与“客户端慢接收”作为**当前主要解释**的力度：

| 假设 | 现有支持 | 关键反例 | 下一步只读观测 | 若成立的影响 |
|---|---|---|---|---|
| CPU 竞争 | `wa` 由 `2%` 升至 `22%`，请求变慢时线程可能等待调度 | `r=2→2`，没有持续排队；RSS 仅 `200→220MiB`，未见明显回收压力 | 按进程/线程看 CPU 使用率、上下文切换、运行延迟；在 Trace 中拆分排队时间与执行时间 | CPU 不是总量耗尽，也可能是少数工作线程、锁竞争或调度抖动导致尾延迟 |
| 慢接收方 | IM 响应慢可能发生在服务端写回阶段 | socket 队列近零，未见大量待发送字节积压 | Trace 记录服务端完成业务处理、开始写响应、连接真正关闭的时间；按客户端统计响应写耗时、重传和 RTT | 可能是少量客户端、网络路径或代理层慢，而非全局 socket 堵塞 |

因此，不能仅凭 `r` 低就宣布 CPU 无关：`r` 是采样时刻的可运行任务数，可能漏掉短促尖峰、线程池饥饿或锁等待。同样，近零 socket 队列只能说明内核缓冲未持续堆积，不能证明客户端已及时消费完整响应。

端到端 Trace 应与数据库指标同窗对照：若 Trace 显示耗时主要落在数据库调用前后，且 DB 慢查询、连接等待或读延迟同步上升，则优先沿业务读路径验证；若 DB 段稳定而应用内部排队、执行或响应写回拉长，再回查 CPU 与慢接收方。

### 用只读观测闭合端到端证据链

### 用只读观测闭合端到端证据链

历史消息查询 `p95` 由 `60ms` 升至 `240ms`，首先说明“用户可见时延变差”，并不自动证明某项资源就是根因。应把同一时间窗内的端到端 Trace、数据库指标与主机观测并列，逐一收缩假设。

| 假设 | 支持证据 | 反例与未证部分 | 影响范围 | 下一步只读观测 |
|---|---|---|---|---|
| 本地 I/O 拖慢查询 | `iostat await` 从 `4ms` 升至 `38ms`；重试 `r2→2`、退避 `b0→4`，可能放大读路径等待 | RSS 仅 `200→220MiB`，socket 队列近零；尚未证明业务查询实际发生本地磁盘读 | 使用该节点、该存储卷，且命中冷数据或索引页未命中的请求 | Trace 中拆分应用、DB、存储等待；对照 DB 的读 IOPS、缓存命中率、慢查询、单查询读页数与 `await` 同窗变化 |
| 数据库查询或连接等待 | 历史消息查询整体变慢，可与重试、退避共同表现为 DB 端排队 | 当前只有主机 I/O 异常，没有 SQL 执行时间、锁等待或连接池耗尽证据 | 依赖同一 DB 实例、分片或热点会话的请求 | 按 Trace 的 `trace_id` 对照 SQL 耗时、排队时间、锁等待、活跃连接、连接池等待及副本延迟 |
| CPU 调度或运行时暂停 | 时延上升可能来自应用排队、GC 或 CPU 抢占，而非磁盘 | 未给出 CPU 利用率、负载、运行队列、GC 暂停；RSS 小幅增长不能替代这些指标 | 同机所有应用请求，或特定进程/线程池 | 采集 CPU 使用率、`load`、运行队列、上下文切换、GC 暂停、线程池队列，并映射到 Trace 的应用 span |
| 慢接收方或网络发送受阻 | 重试与退避可能由下游响应慢触发 | socket 队列接近零，不支持本机发送堆积；仍不能排除远端处理慢或链路抖动 | 指向特定下游、地域、客户端或连接类型的请求 | Trace 比较客户端、网关、服务端 span；查看下游 `p95`、超时率、TCP 重传、握手与响应体传输时间 |

判定时以 Trace 的关键分段为准：若 DB span 与 DB 读等待、慢查询同步抬升，I/O 才从“候选”升级为业务读路径证据；若应用 span 增长而 DB span 稳定，应转查 CPU、GC、线程池或下游；若服务端完成时间正常而客户端总时延升高，则重点检查慢接收方和网络。

> **要点** — 资源异常只能生成竞争假设；必须以同窗追踪、数据库指标和反例验证业务慢点所在。

以 IM 历史消息查询变慢为统一线索，先界定症状与作用域，再用两时间窗和只读证据链排除错因。

### 先把“慢”定义为可验证症状

### 先把“慢”定义为可验证症状

“历史消息查询变慢”不是诊断结论，只是用户体感。排障前应将其改写为可测量、可复核的症状陈述，例如：

> 10:05—10:25，私聊会话的历史消息分页查询，服务端 `P95` 耗时由基线 `180 ms` 升至 `1.8 s`；超时率由 `0.1%` 升至 `3.2%`，主要影响华东区域的活跃用户。

一条合格症状至少包含以下元素：

- **请求类型**：区分历史消息查询、实时收消息、搜索、群聊加载、附件下载等。即使都表现为“聊天慢”，调用链和资源依赖也可能不同。
- **延迟指标**：明确观察的是客户端总耗时、网关耗时、服务端处理耗时、数据库查询耗时，还是下游调用耗时。优先使用分位数，如 `P50/P95/P99`，不要只看平均值。
- **基线与阈值**：说明“正常时是多少”和“何时算异常”。例如过去 7 天同一时段 `P95 < 250 ms`，本次连续 5 分钟 `P95 > 1 s`。
- **影响范围**：限定用户、地域、机房、版本、租户、会话类型、分页参数或特定接口。全量慢与单区域慢的排查方向不同。
- **事件时间窗**：同时记录异常窗与对照窗。异常窗用于找变化，对照窗用于确认哪些指标原本就高，避免把常态误判为故障。

可先填写两行最小事实表：

| 时间窗 | 请求量 | `P95` | 错误/超时率 | 影响范围 |
|---|---:|---:|---:|---|
| 对照窗 |  |  |  |  |
| 异常窗 |  |  |  |  |

若无法回答“哪类请求、从何时开始、慢到什么程度、影响谁”，就还不能进入 CPU、内存、磁盘或网络的资源归因。

### 两时间窗与作用域对照表

### 两时间窗与作用域对照表

单点采样只能说明“此刻看到什么”，不能证明“为何变慢”。应先固定两个可比较的时间窗：

| 时间窗 | 目的 | 选择原则 |
|---|---|---|
| 异常窗 | 捕获消息查询慢时的资源状态 | 与用户报障、慢查询日志或延迟峰值重叠 |
| 健康基线窗 | 描述正常状态 | 同一业务高峰类型、相近工作日与相近数据量 |

时间窗至少记录起止时间、时区、采样间隔、请求量和版本/发布状态。例如，周一 10:00 的异常不能直接同凌晨低负载数据比较；发布后异常也不能与发布前基线简单归因。

对照必须逐层限定作用域：

| 作用域 | 应对照的证据 | 常见不可比情形 |
|---|---|---|
| 主机 | CPU、内存、负载、网络错误计数 | 异常窗与基线窗不是同一台或同规格机器 |
| 进程 | IM 服务进程 CPU、RSS、线程、文件描述符 | PID 已重启，或采样对象实际是代理进程 |
| 磁盘 | 查询所在挂载点的容量、延迟、队列、错误 | 比较了根盘，但数据实际位于独立数据盘 |
| 连接 | 数据库连接池、TCP 状态、重传、等待连接数 | 连接统计包含无关服务或不同端口 |
| 业务请求 | 历史消息接口的 p50/p95/p99、QPS、错误率、慢查询 | 请求参数、时间范围、租户或缓存命中率不同 |

建议将每条证据写成“窗口—对象—指标—单位—来源”的形式，如“异常窗 10:05–10:15，`im-api`，p99=2.4 s，访问日志”。若单位、采样周期、实例集合或请求筛选条件不一致，只能视为线索，不能作为趋势结论。先确认作用域一致，再判断资源指标是否随异常窗同步恶化。

### 用 USE 矩阵生成竞争假设

### 用 USE 矩阵生成竞争假设

USE 指每类资源的**利用率**（Utilization）、**饱和度**（Saturation）与**错误**（Errors）。它不是直接下结论的清单，而是把“IM 历史消息查询慢”拆成可竞争、可证伪的解释：同一症状可能来自 CPU 争用，也可能是数据库磁盘等待或连接排队。

| 资源 | 利用率：是否繁忙 | 饱和度：是否排队/等待 | 错误：是否失败或重试 | 候选解释 |
|---|---|---|---|---|
| CPU | 用户态、内核态、空闲比例 | 运行队列、上下文切换压力 | 通常无直接错误项 | 查询线程与其他任务争用 CPU |
| 内存 | 已用内存、缓存占比 | 换页、回收、内存压力 | 分配失败、进程被终止 | 工作集超出可用内存，查询受换页拖慢 |
| 磁盘 | 设备忙碌比例、读写吞吐 | 请求队列、I/O 等待、延迟 | I/O 错误、文件系统错误 | 索引或历史消息读取受磁盘等待限制 |
| 网络 | 网卡收发速率、连接使用量 | 发送/接收队列、连接等待 | 重传、丢包、连接失败 | 应用到数据库或 IM 服务的连接排队 |

填写时必须绑定两个时间窗：**慢查询窗**与**正常对照窗**。只有慢窗中某指标显著恶化、正常窗未出现同样现象，才值得提升为优先假设。例如慢窗 CPU 利用率高但运行队列不高，不能仅凭“CPU 很忙”认定 CPU 饱和；慢窗有较高 I/O 等待且磁盘队列、读延迟同步升高，磁盘等待的解释才更强。

静态证据只能形成候选矩阵，不能宣称已观察到实时队列、换页或重传。报告应写成“需在慢窗采集相应只读指标验证”，并按影响范围与证据强度排序：先检查共享资源造成的广泛变慢，再检查数据库查询路径，最后才考虑单个客户端或网络链路。

### 按证据边界解读系统字段

### 按证据边界解读系统字段

系统字段首先是**内核或工具的观测结果**，不是业务结论。诊断 IM 历史消息变慢时，应先明确每类证据回答的问题：

| 来源 | 主要观测对象 | 常见字段与单位 | 首行/累计值边界 |
|---|---|---|---|
| `ps` | 进程快照 | `%CPU`、`RSS`（通常为 KiB）、`VSZ` | `RSS` 是驻留页集合，含共享页影响，不等于 Go 堆或“真实独占内存” |
| `/proc` | 内核原始状态 | `stat`、`status`、`smaps`、`net/*` | 字段版本与口径可能变化；许多值自启动以来累计 |
| `vmstat` | 全机 CPU、内存、调度 | `r`、`b`、`si/so`、`cs`、`wa` | 第一行通常是启动以来平均值；后续行才是采样区间值 |
| `iostat` | 块设备 I/O | `r/s`、`w/s`、`await`（ms）、`%util` | `await` 是设备请求平均等待加服务时间，不是单条 SQL 或消息请求时延 |
| `ss` | 套接字与 TCP 状态 | `Recv-Q`、`Send-Q`、`rtt`、连接状态 | 队列表示内核套接字缓冲中的字节或待处理量，不能直接推成“应用消费慢” |

解释时遵守三个限制。第一，**对象不可偷换**：进程 RSS 上升只能说明驻留内存变化，须结合 PSS、匿名页、文件页或 Go 运行时指标，才可讨论泄漏。第二，**时间不可偷换**：累计计数应以两时间窗差值计算速率；不能拿 `vmstat` 首行或设备累计读写量解释某一分钟的慢查询。第三，**层次不可偷换**：高 `await` 可支持“块设备路径存在等待”，却不能证明数据库查询慢由磁盘导致；`Send-Q` 堆积可提示发送受阻，仍需结合连接状态、对端窗口和应用写入速率。

因此，字段应写成限定性证据：`iostat` 在慢窗内 `await` 高于基线，且读写量同步增加；而不是“磁盘导致 IM 变慢”。

### 从反例收束为诊断报告

### 从反例收束为诊断报告

设定症状：用户查询某会话近 30 天历史消息时，接口耗时从常态 `180 ms` 升至 `2.8 s`；发送消息、在线状态和其他会话查询正常。先写清作用域：仅历史查询接口、仅部分长会话、仅高峰窗口，不能把“IM 很慢”直接归因为整机资源不足。

| 假设 | 支持证据 | 反例/限制 | 当前结论 | 下一只读观察 |
|---|---|---|---|---|
| 数据库慢查询 | 查询日志中同一 SQL 的总耗时升高 | 不能仅看平均耗时；可能是锁等待或返回行数增加 | 优先级最高 | 比较两时间窗的 `rows_examined`、`rows_sent`、等待时间 |
| 索引失效 | 扫描行数由 `2,000` 升至 `2,000,000` | 扫描行数单位是“行”，不是字节或毫秒 | 强支持 | 查看执行计划是否从索引范围扫描变为全表扫描 |
| 应用端序列化慢 | 数据库耗时正常而接口总耗时高 | 单次慢请求不能代表全量 | 待证 | 对齐网关、应用、数据库时间戳 |
| 主机 CPU 饱和 | CPU 使用率升高 | 静态材料未给出按进程、核或时间窗拆分，不能下结论 | 证据不足 | 补充同窗 CPU 利用率与运行队列证据 |
| 网络抖动 | 客户端观测变慢 | 同机房其他接口正常，且数据库日志已显示服务端慢 | 低优先级 | 比较服务端处理时长与端到端时长 |

两时间窗必须同口径：基线窗与异常窗使用相同查询条件、相同单位和相近负载。若字段 `duration_us` 的单位为微秒，则 `2,800,000` 表示 `2.8 s`，不能误读为 `2800 s`；若首行是表头，也不能计入样本。

报告结论应保留边界：异常集中于长会话历史查询，慢查询扫描行数显著扩大，当前最符合索引未命中或谓词变化；尚无证据证明 CPU、内存、网络或容器限制是主因。下一步仅观察执行计划、慢查询字段及时间戳链路，不运行 `ps`、`vmstat`、`iostat`、`ss`，也不重启服务。

> **要点** — 可靠诊断不是寻找单个高指标，而是在明确时间窗和作用域后，用可证伪的资源证据链收束假设。
