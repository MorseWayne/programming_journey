## 11.03 日志、指标与 Trace：沿 IM 请求链留下有限证据

- 区分单次事件日志、聚合指标和一次请求追踪
- 为本章POST定义脱敏结构化日志字段
- 选择Counter/Gauge/Histogram并标单位与统计窗口
- 限制route/result等低基数标签避免user/message ID爆炸
- 画出handler/app/memorystore父子span与trace上下文
- 说明trace采样不能替代完整失败计数
- 关联请求ID、消息ID和traceID但不混为同一身份
- 根据症状提出黑盒与白盒证据计划并标未覆盖阶段

当u-a向m-a提交消息后，若u-b未见回应，需要用有限而互补的证据回答：发生了什么、总体是否异常、时间耗在哪里。

### 先划定证据边界与问题

### 先划定证据边界与问题

设 09.04，`u-a` 通过客户端 `c-a` 向 `m-a` 发起一次内存 `POST`，目标是 `u-b`；`u-a` 随后称“没有收到回应”。在尚无在线服务、持久化存储或真实推送通道的虚构场景中，先不要把“未见回应”误读为“`u-b` 没收到消息”。

应将问题拆成不同证据层：

- **黑盒客户端观察**：`c-a` 是否发出了请求、收到了何种 HTTP 状态或超时、界面是否显示提交成功。这只能说明客户端可见的请求—响应结果。
- **白盒进程内部证据**：`m-a` 的日志可说明请求是否进入进程、通过了哪些校验、是否写入内存队列、是否生成响应；指标可显示同时段 `POST` 成功率、错误比例、队列长度；Trace 可定位本次调用在解析、校验、入队、返回等阶段各耗时多少。
- **不可跨越的边界**：即使日志写有“已入队”、指标显示成功率 100%、Trace 显示调用完成，也只能证明 `m-a` 已处理到其可观测边界。它们不能证明 `u-b` 的设备已在线、已接收、已展示，更不能证明用户已阅读。

因此，本节要回答的不是笼统的“消息去哪了”，而是：`c-a` 看到了什么？`m-a` 实际做了什么？异常是单次事件还是总体趋势？这次调用的时间耗在哪里？

### 结构化日志还原单次事件

### 结构化日志还原单次事件

09.04 `u-a → m-a` 的 `POST` 已提交、但 `u-a` 未收到回应时，`m-a` 应记录可检索的结构化事件，而不是只写“发送失败”。日志首先回答：进程是否收到请求、是否完成校验与持久化、是否尝试投递、在哪一步返回或超时。

建议以一条“受理完成”日志为核心，字段包括：

- `时间`、`级别`、`事件名`：如 `message.accepted`、`delivery.attempted`、`request.timeout`。
- `请求ID`：本次 HTTP 请求的唯一标识，用于串起网关接收、鉴权、响应写回等同一次请求内的事件。
- `消息ID`：业务消息的稳定标识，用于关联重试、入队、投递尝试及后续回执；一次请求通常创建一条消息，但重试请求可能对应同一消息。
- `追踪ID`：跨组件调用链标识，用于把 `u-a`、`m-a` 及未来队列服务的同一链路拼接到 Trace 中。
- `发送方/接收方`：记录脱敏后的主体标识，例如内部编号、哈希或截断值，不记录完整账号、手机号、正文。
- `结果与原因码`：如 `accepted`、`rejected`、`timeout`，并附 `validation_failed`、`queue_unavailable` 等机器可聚合原因。
- `耗时与状态`：`http_status`、`queue_latency_ms`、`response_write_ms`。

例如：`事件=message.accepted, 请求ID=r17, 消息ID=m91, 追踪ID=t42, 发送方=u-a, 接收方=u-b, 结果=queued`。这说明 `m-a` 已受理并入队；它不能证明 `u-b` 的设备已经收到消息。客户端黑盒日志只能说明“请求方未见回应”，而 `m-a` 的白盒日志才能定位其内部处理阶段。

### 用指标判断总体比例与队列

### 用指标判断总体比例与队列

指标不解释某一条 `09.04 POST` 的完整经过，而是回答一段时间内“成功、失败、积压和变慢是否成比例异常”。对当前仅有内存提交、尚无在线服务的场景，可保留三类低成本指标：

- **Counter：提交结果累计数。**  
  `im_submit_total{result="accepted|rejected|timeout"}` 在入口完成校验或返回结果时递增。以 5 分钟窗口计算  
  $\text{失败率}=\frac{\Delta rejected+\Delta timeout}{\Delta total}$。  
  不要把 `user_id`、消息内容、请求 ID 放入标签；可使用固定枚举的 `result`、`endpoint="submit"`。

- **Gauge：内存队列当前深度。**  
  `im_memory_queue_depth{queue="outbound"}` 表示尚待处理的消息数；入队后上升，成功取走或丢弃后下降。它适合发现持续积压，但瞬时值不能代表吞吐，也不能证明消息已送达 u-b。若进程重启，Gauge 可归零，因此应结合重启指标或日志理解。

- **Histogram：处理阶段时延。**  
  `im_submit_duration_seconds` 记录从收到 POST 到完成内存入队、形成响应的耗时，统一使用秒。通过 `p50`、`p95`、`p99` 观察尾延迟，并固定桶边界，例如 `0.001、0.005、0.01、0.05、0.1、0.5、1、5` 秒。标签只保留有限的 `stage="validate|enqueue|respond"`，避免按用户、消息或动态错误文本拆分。

观察时应明确窗口：例如“过去 5 分钟提交失败率升至 12%，队列深度持续上升，`enqueue` 的 p95 为 0.8 秒”。这说明服务总体可能阻塞或处理不足；它仍不能替代日志对单次请求的解释，也不能证明 u-b 的设备收到回应。

### 用Trace定位请求耗时阶段

### 用 Trace 定位请求耗时阶段

对 `09.04 POST /messages`，Trace 不回答“是否每次都失败”，而回答“这一次为何慢、慢在何处”。可将一次内存提交建模为父子 Span：

- `handler POST /messages`：接收 `u-a` 请求、校验参数、组装响应。
  - `app.submitMessage`：生成消息对象、执行业务规则、决定写入目标。
    - `memorystore.append`：取得锁、写入内存队列、更新索引或计数。
      - `memorystore.notify`：尝试唤醒等待 `u-b` 的本地读取流程。

父 Span 的 `trace_id` 标识整次请求；每个子 Span 继承该上下文并拥有自己的 `span_id`。因此可比较：

\[
T_{\text{handler}}
\approx T_{\text{app}} + T_{\text{等待/序列化}} + T_{\text{响应写回}}
\]

若 `memorystore.append` 很短而 `handler` 很长，应继续检查锁等待、响应写回或客户端提前断开；若 `append` 自身长，则检查队列竞争、容量扫描或内存复制。Span 应附带有限属性，如 `request_id`、消息大小分桶、队列长度分桶、结果码；避免记录正文、令牌或可识别内容。

上下文必须跨 handler、应用层与存储层显式传播，否则会出现多个孤立 Trace，无法归因于同一提交。对于 `u-b` 的长轮询或后续拉取，应创建新的根 Trace，并仅通过 `request_id` 或消息标识建立关联；它不是同一同步调用链。

Trace 通常采样：一次未被采到的失败不等于未发生，采到的慢请求也不能推出失败比例。完整的 `POST` 成功、拒绝、超时和客户端断开计数仍应由指标承担；日志补充该事件的离散原因。即使 Trace 显示写入和通知完成，也只能证明服务进程内部路径完成，不能证明 `u-b` 的设备已经收到或展示回应。

### 从症状组织互补证据计划

### 从症状组织互补证据计划

症状是：`u-a` 向 `m-a` 发起 `POST`，客户端显示提交成功，但 `u-b` 未见回应。此时应先区分“服务器接受了请求”与“对端设备收到了消息”：前者只覆盖请求进入 `m-a` 的有限阶段，不能推出设备送达。

| 证据 | 最适合回答 | 本例应记录或观察 | 不能回答 |
|---|---|---|---|
| 日志 | 这一次事件发生了什么 | `request_id`、`u-a/u-b`、提交结果、消息标识、状态迁移、错误码 | 同类请求失败比例、各阶段耗时分布 |
| 指标 | 总体是否异常、队列是否积压 | `POST` 成功/失败计数、待投递队列长度、重试数、延迟分位数 | 某个具体请求为何未到达 |
| Trace | 这次调用时间耗在哪里 | 接入、鉴权、持久化、入队等 span 的开始/结束时间 | 没有埋点的后续链路，更不能证明设备展示 |

可将观测边界写成：

`客户端 POST → m-a 接收 → 持久化/入队 → S2 后续投递 → 设备接收/展示`

当前系统没有在线服务，且 **S2 之后不可观测**。因此，日志最多证明 `m-a` 是否接受并处理到已知状态；指标最多显示此类请求或队列是否整体异常；Trace 最多定位已埋点阶段的耗时。即使三者都显示 `POST` 成功，也只能说明服务端前段未见异常，不能证明 `u-b` 的设备已收到、通知已弹出或用户已看到回应。

> **要点** — 日志解释一件事，指标衡量总体，Trace分解一次调用；三者均不能证明设备已送达或已读。

本节为虚构 m-a 的 POST 内存受理路径设计有限、可检索且不泄露隐私的结构化日志证据。

### 日志在请求链中的证据职责

### 日志在请求链中的证据职责

日志记录的是**某一次请求链上已经发生的离散事件**：何时进入、经过哪个阶段、以何种结果结束、失败发生在响应提交之前还是之后。它适合回答“这一个请求为什么失败”“哪个操作返回了什么错误码”“某次异常由哪一阶段触发”等追责与诊断问题。

对虚构的 m-a `POST` 内存受理路径，可围绕稳定字段输出结构化事件：

- `event_time`、`level`：发生时间与严重级别；
- `op_id`、`request_id`：操作与单次请求关联标识；
- `route_template`：如 `/v1/memories`，不用原始路径参数；
- `stage`：如 `authenticate`、`validate`、`persist`、`respond`；
- `result`、`error_code`、`duration_ms`：结果、可枚举错误与耗时；
- `response_committed`：响应是否已写入客户端。

`request_id` 应由受信任网关透传，或由服务端生成；客户端自带的请求头只能视为不可信输入，不能直接作为证据主键。日志不得写入原始请求体、令牌、真实用户标识或其他敏感载荷。

尤其要区分两类失败：提交响应前失败可改变 HTTP 状态并记录 `response_committed=false`；提交后才失败时，客户端可能已收到成功或部分响应，只能记录 `response_committed=true` 并触发告警，不能假装能够撤回结果。

日志不是指标：指标聚合计数、错误率与分位耗时，回答“是否普遍变差”；日志保留单例上下文，回答“这一例发生了什么”。日志也不是 Trace：Trace 表示跨服务的时序与因果路径；日志可携带 `trace_id` 作为跳转证据，但不应复制每个跨度的全部细节。

字段值必须受控以避免高基数和成本失控：`route_template` 不能使用完整 URL，`error_code` 采用有限枚举，禁止把错误文本、用户输入或随机标识作为标签。按故障排查与合规需要设定保留期，并让调试日志比审计级结果日志更短期、访问更受限。

### 面向 POST 受理的脱敏日志字段

### 面向 POST 受理的脱敏日志字段

POST 受理日志的目标不是复述请求内容，而是为一次处理链留下可聚合、可关联、可告警的有限证据。用 `slog` 记录稳定键值，避免把路径参数、原始请求体或临时调试文本变成检索维度。

一次事件至少包含：

- `time`：事件发生时间；由日志处理器统一输出。
- `level`：`INFO` 表示正常阶段或成功，`WARN` 表示可预期拒绝、限流等，`ERROR` 表示内部失败。
- `op_id`：本次受理操作标识，用于串联入口、校验、持久化与响应事件。
- `route`：路由模板，如 `POST /v1/messages`，不能记录展开后的真实路径。
- `stage`：有限枚举，如 `request_received`、`validated`、`stored`、`responded`。
- `result`：有限枚举，如 `accepted`、`rejected`、`failed`。
- `error_code`：稳定业务或内部错误码；成功时省略，不能直接写底层错误文本。
- `duration_ms`：从可信入口计时到当前事件的耗时。
- `response_committed`：响应头或响应体是否已提交，决定失败是否还能转换为标准错误响应。

例如，受理成功可记录为：

`INFO op_id=... route="POST /v1/messages" stage=responded result=accepted duration_ms=18 response_committed=true`

若错误发生在提交前，记录 `result=failed`、`error_code=storage_unavailable` 与 `response_committed=false`，调用方仍可收到规范的 `5xx`。若提交后才失败，则必须保留 `response_committed=true`；此时日志说明服务端后续处理失败，但不能假称响应已被改写。

`request_id` 应由受信任网关传入或服务端生成。客户端自带请求头只能作为不可信候选值，必须校验格式、长度与来源后才可采用。严禁记录原始正文、令牌、真实用户标识或任意错误对象；这些字段既泄露隐私，也会造成日志基数、存储成本和保留风险失控。对 `route`、`stage`、`result`、`error_code` 保持小集合，并设置与审计需求匹配的保留期。

### 提交前后失败的记录语义

### 提交前后失败的记录语义

HTTP 响应一旦写出状态码或首段响应体，即视为 `response_committed=true`。此后即使业务仍发生错误，也不能可靠地改写客户端已收到的结果；日志必须明确区分“可返回失败”和“仅能补记异常”。

```go
logger.Error("im_request_failed",
    "event_time", now,
    "level", "ERROR",
    "op_id", opID,
    "route", "/v1/memories",
    "stage", "persist",
    "result", "failed",
    "error_code", "STORE_UNAVAILABLE",
    "duration_ms", elapsed.Milliseconds(),
    "response_committed", false,
)
```

提交前失败表示处理链尚有控制权：处理器可停止后续步骤，返回统一错误响应，例如 `503` 与稳定的 `error_code`。此时日志中的 `result=failed`、`stage=persist` 和 `response_committed=false` 共同说明：客户端应当看到了失败，重试策略可据此设计。

若已先写入 `202 Accepted`，随后在异步登记、审计补写或连接收尾阶段失败，则只能记录服务端异常：

```go
logger.Error("post_commit_failure",
    "op_id", opID,
    "route", "/v1/memories",
    "stage", "audit_finalize",
    "result", "failed",
    "error_code", "AUDIT_WRITE_FAILED",
    "duration_ms", elapsed.Milliseconds(),
    "response_committed", true,
)
```

这类记录不应再伪装成客户端请求失败：客户端可能已获得成功响应。应配合告警、补偿任务或死信队列处理。`op_id` 应来自受信任的请求生成器或经校验的链路上下文；外部传入的 `Request-ID` 只能作为受限关联字段，不能直接信任。日志不记录原始请求体、令牌或真实用户标识，以避免将排障证据变成隐私副本。

### 请求身份、关联标识与信任边界

### 请求身份、关联标识与信任边界

同一条 IM 请求通常需要三类标识，但它们回答的问题不同，不应混用：

| 标识 | 关联对象 | 主要用途 | 典型来源 |
|---|---|---|---|
| `request_id` | 一次 HTTP 入站请求 | 串联网关、处理器、响应与错误日志 | 服务端生成，或仅接受受信代理注入值 |
| `message_id` | 一条被受理的消息实体 | 查询消息生命周期、投递结果、幂等处理 | 服务端生成或由协议字段经校验后确定 |
| `trace_id` | 一次跨服务调用链 | 将日志、指标与 Trace 中的多个 span 关联 | Trace 上下文传播或根 span 生成 |

`request_id` 的边界是“这一次请求”；重试会产生新的 `request_id`，却可能指向同一个 `message_id`。`message_id` 的边界是“这条消息”；它适合回答“消息是否已落库、是否已投递”。`trace_id` 的边界是“这次分布式执行”；一次请求触发异步任务时，后续任务可继续携带或链接该追踪上下文。

外部客户端提交的 `X-Request-ID`、`traceparent` 等头部默认不可信：可能缺失、过长、格式非法，甚至被攻击者刻意构造以污染检索结果。应用不应直接把原值当作内部身份标识。较稳妥的规则是：

- 仅当请求来自已认证的网关、负载均衡器或服务网格时，接受其注入的关联头；
- 对接受的值执行长度、字符集和格式校验；
- 非受信来源的头要么忽略并生成新值，要么记录为受限诊断字段，不能覆盖内部 `request_id`；
- 每个入站请求保证存在服务端可控的 `request_id`，并在该请求的所有 `slog` 事件中复用。

例如，受理成功可记录 `request_id`、`trace_id`、`message_id`、`stage="accepted"` 与 `result="ok"`；鉴权失败通常只有 `request_id` 和 `trace_id`，不应伪造尚未产生的 `message_id`。这些标识用于关联，不承载真实用户 ID、令牌、消息正文或原始请求头。

### 控制日志基数、成本与留存

### 控制日志基数、成本与留存

结构化日志不是“字段越多越好”。对 m-a 的请求链，应以可定位一次失败、可统计一类失败、可审计关键阶段为目标，控制字段数量与动态值范围。

建议每条请求级事件保留稳定字段：`event_time`、`level`、`op_id`、`request_id`、路由模板、`stage`、`result`、`error_code`、`duration_ms`、`response_committed`。其中路由必须写模板，如 `/v1/memories/{memory_id}`，不能写实际路径；`op_id` 应来自有限操作集合，如 `memory.create`、`memory.delete`，不能把客户端输入拼入操作名。

避免将高基数字段作为常规索引或指标标签：

- 不记录原始请求体、响应体、`Authorization`、Cookie、令牌、真实用户标识、邮箱、手机号及客户端自由文本。
- 不把 `request_id`、资源 ID、完整错误文本、动态 URL、远端地址作为指标标签；它们仅适合出现在受控日志字段中。
- `error_code` 使用有限枚举，例如 `invalid_input`、`store_unavailable`、`timeout`、`internal`；保留原始错误仅限服务端受保护错误链。
- `duration_ms` 是数值字段，可用于查询与分位数分析；不要把每个毫秒值转换成标签。

`request_id` 必须由受信任的入口层生成，或仅接受经过验证的上游传递值。客户端自带的请求头不能直接信任；若需关联，可记录为受限的 `client_request_id`，并限制长度与字符集。

日志等级也影响成本。正常成功请求可采样记录或仅写摘要；参数校验失败通常为 `info`/`warn`；依赖故障、提交前内部错误为 `error`。若响应已经提交，后续失败必须记录 `response_committed=true`，但不能伪造为可向客户端返回的新错误响应。

留存策略应分层：短期保留可检索明细以支持排障，中期保留聚合统计与脱敏审计证据，期满自动删除。留存期限、访问权限和导出能力都应受合规要求约束；调试便利不能成为长期保存敏感关联数据的理由。

> **要点** — 结构化日志应记录可关联的受理事实，而非原始载荷、令牌或真实用户身份。

指标把大量请求压缩为可计算的趋势证据：先分清计数器、仪表盘与直方图的语义，再避免把受理误当成交付。

### 指标是聚合证据，不是单次请求记录

### 指标是聚合证据，不是单次请求记录

指标回答的是“系统整体在一段时间内怎样”，而不是“某个请求后来发生了什么”。同一条 IM 请求链应当分工明确：

- **日志**保留可检索的离散事件，例如请求被拒绝的原因、解析失败字段、关联标识。
- **Trace**连接一次请求跨越的步骤，用于定位它经过了哪些组件、在哪一步耗时或失败。
- **指标**将大量事件压缩为少量可计算的时间序列，用于观察趋势、容量和异常比例。

本节只度量**进程内存中的受理阶段**：请求是否到达入口、是否被校验并受理、当前积压多少、受理耗时如何。`accepted` 表示服务已接受并进入后续处理，不表示消息已经写入存储、送达对端或被用户阅读；这些是不同阶段的事实，不能用一个“成功”指标混写。

指标标签必须有限且稳定。例如可记录 `attempts_total{route="send",result="accepted|duplicate|invalid"}`，而不要把 `user_id`、`message_id`、完整错误文本放入标签。前者形成固定数量的序列，后者会造成基数爆炸，也会把本应由日志或 Trace 承担的单请求细节塞进指标系统。

因此，指标是面向聚合判断的有限证据：它能提示“无效请求比例上升”“队列持续堆积”“尾延迟变差”，但不能替代日志中的具体原因，更不能单独证明某一条消息已经完成最终交付。

### 用计数器记录有界结果的尝试量

### 用计数器记录有界结果的尝试量

计数器适合回答“累计发生了多少次”。例如为 IM 写入：

`attempts_total{route="send", result="accepted"}`

每次请求完成一次可判定的受理流程，就按**有限、稳定**的标签组合加一。`route` 可取 `send`、`recall` 等少数入口；`result` 可取 `accepted`、`duplicate`、`invalid` 等有限结果。不要把用户 ID、消息 ID、错误详情放进标签，否则时间序列会随请求数量膨胀。

一次观察窗口内，`route="send"` 的结果可能是：

- `accepted`：92
- `duplicate`：5
- `invalid`：3

因此共有 $92+5+3=100$ 次发送尝试，受理比例为 $92/100=92\%$。这里的 `accepted` 只表示服务已接受该请求，例如已完成幂等判断、参数校验或写入待处理状态；它**不等于消息已经送达对端**。送达应由独立的确认、回执或状态流转指标证明。

计数器在同一进程生命周期内应单调递增：

$$C(t_2)\ge C(t_1)$$

吞吐量不能直接读取 $C(t)$，而应在窗口 $\Delta t$ 上求增量速率：

$$r \approx \frac{C(t)-C(t-\Delta t)}{\Delta t}$$

例如 5 分钟内 `attempts_total` 从 12,000 增至 12,600，则平均尝试速率为 $600/300=2$ 次/秒。

进程重启后，内存中的计数器通常从零开始；若把重置后的值直接与旧值相减，会得到负数并误判流量下降。计算窗口增量时应识别重置：出现下降可视为新进程从零重新累计，或由采集侧使用重置感知的速率计算。多实例时，也不能先把各实例的原始累计值随意相减；应先对每个实例计算窗口增量或速率，再求和，避免实例重启掩盖其他实例的真实流量。

### 用仪表盘观察当前积压与并发

### 用仪表盘观察当前积压与并发

仪表盘（gauge）记录的是**某一时刻的当前状态**，数值可以上升，也可以下降，适合回答“现在是否堵住了”。

例如：

- `im_in_flight`：已开始处理、但尚未完成的请求数。请求进入处理阶段时加一，完成、失败或超时清理时减一。
- `im_queue_length`：等待消费者处理的队列长度。生产者入队时增加，消费者取走或丢弃消息时减少。
- `im_active_connections`：当前存活的长连接数；连接建立增加，断开减少。

若某时刻 `queue_length=80`，它表示当前约有 80 条消息尚在排队，并不表示系统历史上只收到过 80 条请求。相反，`attempts_total=100` 表示从进程启动以来累计观测到 100 次尝试；即使队列已经清空，累计值通常仍是 100。

因此，不能用累计请求量替代积压，也不能把仪表盘值当作吞吐量。吞吐量应从一段窗口内的计数器增量推导，例如：

$$
\text{处理速率} \approx \frac{\Delta attempts\_total}{\Delta t}
$$

观察时应组合判断：`in_flight` 持续升高，可能意味着下游变慢；`queue_length` 持续升高而处理速率不变，说明入队速度超过消费速度；两者短暂波动则可能只是正常并发。多实例部署时，应先分别观察每个实例的积压，再按需要求和；但“最大队列长度”与“队列长度之和”回答的是不同问题。

### 用直方图近似延迟分布与 p99

### 用直方图近似延迟分布与 p99

`latency_seconds` 用直方图记录请求延迟的**分布轮廓**，而非只记录平均值。预先设置边界，例如 `0.01、0.05、0.1、0.5、1、+∞` 秒；每次请求完成后，延迟会落入相应范围。对 `route=send`，可观察三类值：

- `latency_seconds_bucket{le="0.1"}`：延迟不超过 `0.1` 秒的**累计**请求数；
- `latency_seconds_count`：已观察到的请求总数；
- `latency_seconds_sum`：所有延迟秒数之和，可估计均值：`sum / count`。

“累计”是关键：若 `le="0.1"` 为 `92`，`le="0.5"` 为 `98`，则 `0.1~0.5` 秒内的请求数是 `98-92=6`，不是 `98`。最后的 `le="+∞"` 应等于 `count`。

在一个时间窗口内，应先对各桶计数求增量或速率，再按 11.02 的方法寻找第一个累计比例达到目标分位的位置。若窗口内共有 `100` 个请求，`p99` 的目标秩约为 `99`；累计到 `0.5` 秒为 `98`，累计到 `1` 秒为 `100`，则可报告 `p99` 位于 `0.5~1` 秒，并在桶内作近似插值得到估计值。桶越粗，p99 越只能表示范围；因此应在延迟目标附近布置更密的秒级边界。

始终把单位写入指标名：`latency_seconds` 明确是秒，避免将毫秒数误读为秒。多实例汇总时，先对同一桶边界的窗口增量求和，再计算分位数；不要分别计算各实例 p99 后再平均。进程重启会使桶、`count` 与 `sum` 归零，也应按窗口增量处理，而不是把重置后的原始累计值当作延迟趋势。

### 纸面读数：100 次尝试不等于 100 次送达

### 纸面读数：100 次尝试不等于 100 次送达

设某时间窗内，`route=send` 共发生 100 次发送尝试，可设计单调递增计数器：

- `attempts_total{route="send",result="accepted"} = 92`
- `attempts_total{route="send",result="duplicate"} = 5`
- `attempts_total{route="send",result="invalid"} = 3`

这里的 100 是“进入发送处理并得到结果分类”的尝试数，$92/100=92\%$ 是**受理率**：系统认为请求格式、鉴权、幂等条件等满足要求，于是接受其进入后续流程。`duplicate` 表示重复请求被识别；`invalid` 表示请求在本地校验阶段失败。三类结果应互斥，且标签取值必须有限，不能把用户 ID、消息 ID 放进标签。

不要把计数器原值 `92` 当作吞吐量。计数器只会递增，直到进程重启或被重置；应比较窗口增量，例如 5 分钟内 `accepted` 增加 92、总尝试增加 100，才能得到该窗口的受理速率和受理率。多实例时先按相同 `route/result` 汇总各实例的增量；若某实例重启，不能把重置后的较小值误读为负吞吐。

更重要的是，`accepted` 不是 `delivered`。受理后消息可能仍在队列中等待、被下游拒绝、网络超时、重试耗尽，或最终到达但尚无回执。因而这组纸面读数最多证明“92 次被本服务受理”，不能证明“92 次送达”。要缩小这段不可观测区间，还需沿后续队列、下游调用与回执链路留下独立证据。

> **要点** — 计数器看窗口增量，仪表盘看当前状态，直方图看分布；受理成功只能证明当前 S2，不能证明已持久、已送达或已读。

指标标签决定监控系统能否长期可用：应让聚合维度有限、可解释，并把精细关联留给日志与追踪。

### 标签是聚合维度，不是请求明细

### 标签是聚合维度，不是请求明细

指标的职责是回答“哪一类请求变慢、失败或堆积了”，因此标签必须支持**有限集合上的分组比较**。判断一个标签是否合格，可问两个问题：

1. 它是否对应稳定、可解释的业务或系统维度，如路由、结果、处理阶段？
2. 它的可能取值是否有明确上限，并能在较长时间内保持可控？

例如将 IM 请求标为：

`route=send_message|pull_history|ack`  
`result=success|invalid|timeout|internal_error`

仅按 `3 条路由 × 4 种结果` 就是 12 条时间序列，尚未叠加机房、版本等维度，仍可预测、可聚合。`stage=decode|authorize|persist` 也通常适合作为有限标签。

相反，`user_id=100000`、`message_id=1000000`、原始 URL 路径 `/users/123/messages/456` 都会让每个新请求产生新序列。它们不仅抬高存储、索引、查询和告警成本，还会拖慢监控系统；对标识符做哈希并未解决问题，因为哈希后的取值基数仍然很高。原始路径应归并为路由模板，如 `/users/:id/messages/:message_id`。

指标直方图的单位应统一为秒，即使界面展示为毫秒也应在展示层换算。请求体、令牌、完整身份信息不应进入指标标签；需要精细关联时，应在日志或 Trace 中按脱敏、保留期和访问控制保存关联信息。

### 用路由、结果与阶段构造有限序列

### 用路由、结果与阶段构造有限序列

指标的标签应描述**有限且稳定的聚合维度**。对一次 IM 请求，可先定义：

- `route`：`send_message`、`pull_messages`、`ack_message`
- `result`：`success`、`invalid_request`、`rate_limited`、`internal_error`

则一个计数器可写为：

`im_request_total{route="send_message", result="success"}`

仅这两个维度就形成：

$$3\text{ 条路由}\times4\text{ 种结果}=12\text{ 条基础时间序列}$$

这 12 条序列足以回答多数运行问题：哪条接口失败增多、限流是否集中、内部错误是否影响某个操作。若再加入有限的 `stage`，例如 `validate`、`persist`、`dispatch`，序列数变为：

$$3\times4\times3=36$$

新增标签不是“多写一个字段”那么简单，而是与已有维度相乘。继续加入 `region`、`client_type`、`status_code` 后，系列规模会快速膨胀；因此每个标签都应先问：它的取值集合是否可枚举、是否有上限、是否值得长期聚合？

路由应使用模板名，而非原始 URL。`/messages/:message_id` 是一个有限路由；`/messages/8f3...` 会因每个消息标识不同而持续产生新序列。`user_id`、`message_id` 即使哈希后也仍有近乎无限的不同值：哈希隐藏内容，却不降低基数，也不能消除关联与泄露风险。

精细定位应放入日志或 Trace，并受脱敏、留存期和访问控制约束；指标只保留可长期运行的汇总证据。计时直方图建议统一以秒记录，如 `0.125`，展示层再换算为毫秒。

### 原始路径与业务标识为何不可作标签

### 原始路径与业务标识为何不可作标签

指标系统擅长回答“这一类请求是否变慢、失败是否增加”，不擅长保存“某个具体用户、某条具体消息发生了什么”。因此，标签必须是**有限且稳定的分类值**，而不是请求中的原始细节。

| 标签选择 | 取值规模 | 典型后果 |
|---|---:|---|
| `route=/v1/messages/{id}` | 路由数有限 | 可按接口稳定聚合 |
| `result=success\|timeout\|reject\|error` | 例如 4 种 | 可比较失败结构 |
| `stage=validate\|dispatch\|deliver` | 流程阶段有限 | 可定位阶段瓶颈 |
| `path=/v1/messages/8f2...` | 随请求增长 | 几乎每次请求新建序列 |
| `user_id=...` | 可达 10 万以上 | 用户数直接转化为序列数 |
| `message_id=...` | 可达百万甚至无限 | 每条消息都成为独立时间序列 |

例如只有 `3` 条路由和 `4` 种结果时，`route × result = 12` 条序列，尚未计入实例、区域等其他维度，规模仍可预测。若再加入 `user_id=100000`，理论组合立刻膨胀至 $12\times100000$；加入近乎唯一的 `message_id`，序列会持续产生且难以回收。其代价是采集端内存、索引、存储、查询延迟和监控账单同步上升。

原始 URL 路径尤其危险：`/v1/users/42/messages/abc` 与 `/v1/users/43/messages/def` 业务上同属一条路由，却在标签层面被视为不同值。应记录为 `route=/v1/users/{user_id}/messages/{message_id}`，而非原始 `path`。

不要以为对 ID 哈希就安全：哈希后的 `user_id` 仍有近似相同的唯一性，基数问题没有消失；若输入空间较小，还可能被反查。请求体、令牌、邮箱、手机号等也不应进入指标标签。

需要关联具体请求时，将受控的 `trace_id`、脱敏后的业务标识放入日志或 Trace，并配置脱敏、保留期限和访问权限。指标直方图的单位通常用秒，如 `0.25`、`1`；界面展示时再换算为毫秒，避免标签与单位同时失去一致性。

### 单位、窗口与直方图展示

### 单位、窗口与直方图展示

延迟指标应统一以**秒**记录，即使业务界面通常展示为毫秒。这样可避免不同采集端混用 `ms`、`s`、`μs`，也与多数指标系统的直方图惯例一致。界面层可将 `0.125 s` 格式化为 `125 ms`，但不要改变底层指标单位。

直方图必须同时说明三个语义：

- **观测对象**：例如 `im_request_duration_seconds` 表示一次 IM 请求从服务端收到请求到返回响应的总耗时。
- **阶段含义**：若记录 `stage="dispatch"`，应明确其范围，如“路由完成后到消息投递调用返回”；不要把排队、重试、网络等待混入未说明的阶段。
- **统计窗口**：分位数、平均值和错误率都基于查询窗口计算。`P99=0.8 s` 若未说明是最近 5 分钟、1 小时还是按日汇总，几乎无法用于告警或排障。

例如，对最近 5 分钟的成功请求，可展示：

`P50 18 ms，P95 120 ms，P99 480 ms`

直方图桶仍保存为秒，如 `le="0.05"`、`le="0.1"`、`le="0.5"`、`le="1"`。桶边界应覆盖正常波动与告警阈值：若 SLO 是 `99%` 请求低于 `300 ms`，则应设置接近 `0.3 s` 的桶，而非只依赖粗粒度的 `0.5 s` 桶。指标用于有限维度的趋势与聚合；单个慢请求的具体上下文，应转入经过脱敏和访问控制的日志或 Trace。

### 把关联信息放入受控证据通道

### 把关联信息放入受控证据通道

一次 IM 请求可能经过网关、鉴权、会话服务、消息队列、投递服务与客户端回执。排障时确实需要回答“这条消息后来怎样了”，但这不意味着应把 `request_id`、`message_id` 或 `trace_id` 写成指标标签。

指标用于持续聚合，应只保留有限维度，例如：

`im_request_total{route="send_message",result="success",stage="persist"}`

若有 3 条路由、4 种结果，初始仅为 $3\times4=12$ 条时间序列；而将百万级 `message_id` 加入标签，会近似制造百万倍的序列分裂。即使对 ID 做哈希，也没有降低基数：哈希后的值仍几乎逐条不同，同时还可能让原本可审计的关联变得困难。

关联信息应进入受控证据通道：

- **脱敏日志**：记录 `request_id`、`trace_id`、必要时记录经过权限评估的 `message_id`；不得记录消息正文、登录令牌、完整用户隐私字段。
- **分布式追踪**：以 `trace_id` 串联跨服务 span，展示耗时、重试、错误与队列等待；业务消息标识仅作为受控属性或链接。
- **访问与留存**：日志和追踪应设置保留期限、查询权限、审计记录及导出限制。不是所有值“能查到”就应长期保存。

典型流程是：先通过指标发现 `send_message` 的失败率或延迟异常，再从对应时间窗的日志或 Trace 中，使用请求标识定位少量样本。这样既保留了聚合监控的性能与成本边界，也让精细排障具有可控的隐私和权限边界。

> **要点** — 指标标签必须低基数且有限；高基数关联信息应脱敏后交给日志与追踪，哈希标识并不能消除成本与隐私风险。

以一次 m-a 的 POST 内存受理请求为主线，建立可关联、可采样且不误作业务账本的追踪证据。

### 一次请求对应一棵追踪树

### 一次请求对应一棵追踪树

对一次 `POST /messages` 内存受理请求，最直观的证据结构是一棵 Trace：HTTP 处理器创建根 span，随后每个有独立耗时、失败语义或关键边界的步骤创建子 span。

- 根 span：`HTTP POST /messages`，覆盖请求进入到响应写完的完整生命周期。
- 子 span：`auth`，验证调用方身份、权限或签名。
- 子 span：`app.Send`，执行应用层编排、校验与业务决定。
- 子 span：`memorystore.Append`，将消息追加到内存存储；它应记录存储结果，而非把整段业务逻辑塞入属性。
- 子 span：`encode response`，序列化成功或错误响应并写回客户端。

子 span 必须在其真实工作开始时启动、结束时立即关闭，并以当前上下文作为父级来源：

`ctx, span := tracer.Start(r.Context(), "app.Send")`

因此它自动继承同一 `traceID`，但拥有新的 `spanID`；`parentSpanID` 指向调用它的 span。根 span 的 `traceID` 可关联整次请求，不能替代业务 `messageID`：同一消息重试时，通常可产生新的 Trace。

在 span 属性中记录低基数、可筛选的事实，如 HTTP 方法、路由、结果码、消息类型；对校验失败、存储拒绝等瞬时节点使用事件或错误状态。不要把请求正文、令牌等敏感且高基数数据写入属性。这样，追踪树既说明“请求经过了哪里”，也保留每一步的局部耗时与失败边界。

### Span 生命周期与上下文字段

### Span 生命周期与上下文字段

一次 `POST /im` 进入服务时，应从 `r.Context()` 创建或继续一个根服务端 Span；随后认证、`app.Send`、`memorystore.Append`、响应编码分别创建子 Span。Span 的生命周期对应可观测操作边界：

- 开始：记录单调计时起点，并确定父 Span；
- 运行：补充稳定属性，如 `http.request.method`、路由、用户类型、存储结果；
- 事件：在某一瞬间留下事实，如“鉴权失败”“消息已写入内存”“重试第 2 次”；
- 结束：无论成功、错误还是提前返回，都必须 `End()`，通常用 `defer span.End()` 保证闭合。

父子关系形成一条 Trace：根 Span 与所有后代共享同一 `traceID`，每个 Span 自有唯一 `spanID`；子 Span 还携带父 `spanID`。因此，`traceID` 回答“这次请求链路是什么”，`spanID` 回答“链路中的哪一步是什么”。

不要混淆几个身份字段：

- `traceID`：一次观测链路的标识，可随上下文跨组件传播；
- `spanID`：链路内单个操作的标识；
- 请求 ID：面向网关、日志或客户端的请求关联键，可与 Trace 并存；
- 消息 ID：业务消息实体的身份，用于幂等、去重和状态查询。

同一条业务消息重试时，可能产生新的 HTTP 请求和新的 `traceID`，但仍应保有同一个消息 ID。反过来，一个 Trace 也不应被当作消息账本。跨进程传播只有在发送方注入、接收方正确提取上下文时才成立；仅把 `traceID` 写进消息字段，并不会自动恢复父子关系。

### 沿 Go Context 传播追踪

### 沿 Go Context 传播追踪

入口处理器应以 `r.Context()` 作为本次 HTTP `POST` 的根上下文：HTTP 中间件已从入站请求头提取远端追踪信息，随后创建服务端根 Span；业务函数只接收并继续传递该 `ctx`。

```go
ctx, span := tracer.Start(r.Context(), "app.Send")
defer span.End()

if err := store.Append(ctx, msg); err != nil {
    span.RecordError(err)
    return err
}
```

`ctx` 同时携带取消信号、截止时间和当前 Span。`auth`、`app.Send`、`memorystore.Append`、响应编码等操作以该上下文创建子 Span，因而共享同一 `traceID`，各自拥有不同 `spanID`，父子关系可还原请求路径。Span 必须在操作开始时创建、结束时关闭；错误、重试原因或关键状态变化宜记为属性或事件，而非把完整消息正文写入追踪。

启动 goroutine 时不能改用 `context.Background()`；应显式传入当前 `ctx`，并在异步任务的生命周期确实属于本请求时使用它：

`go func(ctx context.Context) { ... }(ctx)`

若任务应脱离客户端取消而持续执行，应建立新的业务边界，并审慎保留必要的关联信息，而不是无条件继承请求上下文。

跨进程传播不是“传了 `ctx` 就自动发生”。发送 HTTP、RPC 或消息前，必须由 OpenTelemetry 注入器将上下文写入载体头；接收端必须从相同载体提取后，再创建本地 Span。缺少注入、提取或中间层丢弃追踪头时，下游会形成新的 Trace。注意：`traceID` 标识一次追踪，不是业务 `messageID`；同一消息重试可产生新的 Trace。

### 用静态时序阅读追踪证据

### 用静态时序阅读追踪证据

先把一次 `POST /messages` 的受理过程画成纸面时序。假设同一进程内各 span 使用单调时钟计时，客户端请求在 `0ms` 到达：

| 时刻 | 追踪证据 | 含义 |
|---|---|---|
| `0ms` | 根 span：`HTTP POST /messages` 开始 | 创建或继续一个 `traceID`，记录方法、路由、请求大小等属性。 |
| `0–12ms` | 子 span：`auth` | 鉴权、解析身份；失败时在 span 上记录错误状态与事件。 |
| `12–25ms` | 子 span：`app.Send` | 校验消息、生成业务处理结果；这里可记录 `messageID`，但它不等于 `traceID`。 |
| `25–40ms` | 子 span：`memorystore.Append`、`encode response` | 前者表示写入内存存储，后者表示序列化 HTTP 响应。 |
| `40ms` | 根 span 结束 | 响应已写出，根 span 的总耗时约为 `40ms`。 |

因此，阅读一条 trace 时，先确认所有 span 是否共享同一个 `traceID`，再按 `parent spanID` 恢复树形关系：

`HTTP POST /messages`  
├─ `auth`  
├─ `app.Send`  
├─ `memorystore.Append`  
└─ `encode response`

这张图是解释延迟归属的“纸面模型”：若 `memorystore.Append` 持续 `15ms`，它解释的是根请求中 `25–40ms` 的一段；若子 span 重叠，则不能简单把所有子 span 时长相加。

注意，`0/12/25/40ms` 只适合表达同一进程或可靠单调计时下的相对顺序。跨机器 span 即使属于同一条 trace，也不能直接用墙上时钟的绝对开始时间断言先后：机器时钟偏移会制造看似“子 span 早于父 span”的现象。跨进程关联依赖正确注入与提取上下文，而不是比较时间戳。

### 采样边界与失败计数责任

### 采样边界与失败计数责任

一次业务消息不等于一条 Trace。客户端因超时、连接断开或收到可重试状态而再次提交同一 `messageID` 时，新的 HTTP 请求通常会创建新的根 Span，因此拥有新的 `traceID`；但它们仍应携带同一个业务消息标识。可将关系理解为：

- `messageID`：业务幂等、去重与投递语义的主键；
- `traceID`：某一次请求执行路径的诊断关联键；
- `spanID`：该次路径中某个具体操作的局部标识。

因此，排查“消息为何重复投递”时，应先按 `messageID` 聚合，再查看其关联的多个 `traceID`；不能看到两个 Trace 就断言产生了两条不同业务消息。反过来，同一 Trace 内的 `memorystore.Append` 重试也仍属于一次请求链，只是应以事件或子 Span 记录重试次数、错误原因和退避时间。

采样进一步限定了 Trace 能说明什么。若采用概率采样，未被采样的请求根本不会出现在追踪后端；即使采用尾部采样，规则配置不当也可能遗漏罕见错误、短请求或异常中断链路。故“检索到 3 条失败 Trace”只能证明至少观察到 3 次失败，不能推出失败总数为 3，更不能用 `失败 Trace 数 / 总 Trace 数` 计算错误率。

完整失败计数应由指标承担：在服务端按实际处理结果累加请求总数、成功数、认证拒绝数、存储失败数及重试次数，并以稳定标签区分结果类别。日志和 Trace 用于回答“这一次为何失败、经过了哪些 Span”；指标用于回答“失败发生了多少次、占全部请求的比例是多少”。采样 Trace 是有限证据，不是业务账本，也不是统计分母。

> **要点** — Trace 解释单次请求路径；正确传播上下文并关联多种标识，但失败分母必须由完整指标承担。

以“服务已受理、内存已写入、响应却丢失”的时间线为主线，建立日志、指标与追踪各自能证明什么、不能证明什么的证据边界。

### 先拆开：受理、提交与客户端可见结果

### 先拆开：受理、提交与客户端可见结果

设用户 `u-a` 向服务 `m-a` 发起一次 `POST`，携带操作关联键 `op_id`。一次看似简单的“发送成功”，至少包含彼此独立的检查点：

1. **服务受理**：`m-a` 完成鉴权、格式校验，并记录 `stage=accepted`。这只能证明请求已被服务入口接受，不证明业务状态已经改变。
2. **内存提交**：处理器将消息追加到内存队列或会话状态，记录 `stage=memory_appended`。这证明该进程当时观察到一次内存写入；若进程崩溃、未持久化或后续回滚，它不等于可靠提交。
3. **响应发送**：服务尝试写出 `200` 响应。网络连接、代理或客户端超时都可能使该响应在途中丢失。
4. **客户端可见结果**：`u-a` 最终看到的是超时。超时只证明客户端未在期限内收到可确认的响应，不能反推“服务未受理”或“内存未写入”。

因此，时间线可能是：

`POST(op_id)` → `accepted` → `memory_appended` → `200` 写出或待写出 → 响应丢失 → 客户端超时

日志中的 `accepted`、指标中的受理计数增加、被采样 Trace 中的 `memory_appended`，共同支持“服务端可能已处理到内存提交”。但它们都**不能证明 `u-a` 收到了 200**；客户端超时也**不能证明操作没有发生**。

对照地，格式非法或正文过长的请求可在入口留下拒绝记录而没有提交检查点；队列拥塞则可能已受理却迟迟未到内存提交。排障应始终分别询问：服务是否受理？状态是否提交？客户端究竟看到了什么？

### 日志记录可审计的单次受理事件

### 日志记录可审计的单次受理事件

对一次 `u-a POST m-a`，日志应记录“服务端完成受理”这一独立检查点，而不是把“客户端收到成功响应”混写为同一事实。典型时间线是：请求通过校验 → 写入内存 → 写入 `accepted` 日志 → 递增受理计数器 → 响应在网络中丢失。此时日志可以证明服务端曾受理，不能证明 A 已收到 `200`。

建议在内存提交成功后追加一条结构化、脱敏的受理日志：

`stage=accepted op_id=... trace_id=... message_ref=... payload_bytes=... queue_depth=...`

其中：

- `stage=accepted`：仅表示业务校验完成且消息已进入本服务的受理状态；不能表示下游已消费、持久化完成或客户端确认。
- `op_id`：单次操作的服务端关联键，用于连接入口日志、校验结果、内存提交和响应写出等阶段；应随机生成且不可由用户猜测。
- `trace_id`：用于跨服务追踪。同一请求未被采样时，不能据此否定其发生；被采样的 Trace 可补充“曾执行到 memory append”，但仍不能证明响应送达。
- `message_id`：业务消息标识通常具有更高敏感性，日志中应使用不可逆的 `message_ref`、截断值或受控映射，避免直接暴露用户关联信息与消息内容。

`op_id ↔ trace_id ↔ message_id` 的完整映射不应默认出现在普通日志平台。只有具备明确排障或审计授权的人员，才能通过受控查询关联它们；常规指标则只记录 `accepted_total` 等有界聚合值，绝不附带标识符。

对比而言，`body_too_long` 应记录拒绝阶段和长度区间，不能写成受理；队列变慢则应记录等待时长、深度或拥塞状态。它们分别证明“被拒绝”和“受理后变慢”，与“客户端是否收到响应”是不同命题。

### 指标只保留有界的聚合信号

### 指标只保留有界的聚合信号

指标回答的是“系统整体发生了什么”，而不是“某个 `op_id` 最终是否拿到 `200`”。因此，`u-a POST m-a → 内存提交 → 响应丢失`这类链路中，指标可以证明受理量、积压和时延变化，却不能替代日志或 Trace 证明客户端 A 的具体结果。

- **Counter：累计发生次数。**  
  对已完成基本校验并进入受理路径的请求增加 `im_requests_total{route="message",result="accepted"}`；无效请求可记为 `result="invalid"`，正文超长记为 `result="body_too_long"`。若 A 超时后重试，计数可能增加多次；它只能说明服务端受理次数，不说明 A 收到了多少个成功响应。

- **Gauge：某时刻的存量。**  
  使用 `im_queue_depth{queue="delivery"}` 表示待处理队列长度。队列持续升高说明下游消费慢、投递受阻或生产快于消费；但它不能指出哪条消息堵塞，也不能据此断言某个请求已落入队列。

- **Histogram：一次操作的分布。**  
  用 `im_request_duration_seconds{route="message",stage="accepted"}` 观察受理耗时，用队列等待耗时直方图观察“已入队但未处理”的延迟。相比平均值，分位数更容易暴露少量慢请求；但采样窗口内的高延迟仍不能证明 A 的响应是否丢失。

标签必须低基数且可枚举，例如 `route`、`result`、`stage`、`queue`、状态类别。不要把 `op_id`、`message_id`、用户标识、完整错误文本放进标签：它们会制造近乎无限的时序，增加存储与查询压力，并可能泄露业务关联信息。需要定位个案时，应在受授权条件下通过日志与 Trace 的关联键查证；指标只保留无身份、可聚合、可长期保留的信号。

### 追踪还原一次请求的内部路径

### 追踪还原一次请求的内部路径

一次 `POST /messages` 可被建模为一棵 span 树：入口 `handler` span 接收请求上下文，创建子 span `app.accept` 完成校验、幂等判断与业务受理；随后 `memorystore.append` 记录内存写入。若写入成功，控制权回到 `handler`，尝试发送 `200` 响应：

`handler → app.accept → memorystore.append → handler.response`

父子关系必须依赖上下文传播，而非仅靠时间戳猜测。入口从请求头提取 `traceparent`；应用层在异步任务、队列投递或存储调用时显式携带该上下文，否则“写入 span”会成为孤立轨迹，无法证明它属于哪次受理。

在被采样的轨迹中，若看到：

- `app.accept` 状态成功；
- `memorystore.append` 成功并带有提交事件；
- 最后的响应发送 span 缺失、超时或连接断开；

可还原“服务已受理且已写入，但响应可能在返回途中丢失”的内部路径。它不能推出客户端实际收到 `200`：客户端超时也可能发生在服务端已成功写响应之后。

追踪尤其适合比较分支：非法请求或正文过长应止于校验 span，不应出现存储子 span；队列缓慢则表现为投递、等待或消费 span 的持续时间增长。`op_id` 可作为受控关联键写入 span；业务 `message_id` 仅在授权条件下关联，避免泄露内容或身份。指标则只保留有界计数，如“已受理数”“校验拒绝数”“响应失败数”，不携带这些标识。

采样轨迹是解释单次路径的白盒证据，不是完整总体事实。未采到某次失败不等于失败未发生；完整失败率、超时数仍须由独立日志与计数器检查点承担。

### 按症状组合黑盒与白盒证据

### 按症状组合黑盒与白盒证据

同一条“客户端失败”并不对应同一种服务端状态。证据计划应先区分黑盒症状，再用白盒检查点缩小范围；两者都不能越过自身观测边界。

- **响应丢失：**客户端以 `op_id` 发起 `POST`，等待超时，黑盒只能证明“客户端未收到成功响应”，不能证明服务未执行。白盒可见日志 `stage=accepted`、`accepted_total` 递增，以及被采样的 Trace 显示内存追加已完成。这些证据共同支持“请求已受理且可能已提交内存”，但**不能证明客户端 A 收到 200**；响应写入、网络传输和客户端接收是后续独立检查点。尤其在 S2 之后，若系统未记录响应发送或确认阶段，则该阶段尚不可观测。

- **非法请求或正文过长：**黑盒通常得到 `4xx`、连接关闭或明确拒绝结果。白盒应记录有限的拒绝原因，如 `invalid_request_total{reason="format"}`、`rejected_body_too_large_total`，并在日志中保留校验阶段与长度区间，而非原始正文。此类证据应显示请求在受理或解析前被拦截；不能仅因 Trace 缺少“内存追加”就断言不存在执行，采样缺失与异步路径都可能造成空白。

- **队列变慢：**黑盒表现为延迟升高、超时增多或重试增加。白盒优先组合队列深度、排队等待时间分位数、消费者处理速率与超时计数；Trace 可定位一次请求停在入队前、队列中还是消费阶段。指标只能证明总体拥塞趋势，不能携带 `op_id`；单条请求归因需在授权条件下用 Trace 关联 `op_id`，业务 `message_id` 仅用于受控关联，避免写入高基数指标或明文日志。

因此，应把“已受理”“已入队”“已提交”“已发送响应”“客户端已收到”视为彼此独立的断言，而不是由某一个日志、计数器或 Trace 自动推出的结论。

> **要点** — 日志、指标和追踪分别证明事件、总体趋势与路径；独立检查点不能推出客户端一定收到 200。

本节为 S2 内存受理链设计有限、可关联且不过度承诺的观测证据，明确当前看得见什么，以及未来阶段尚未覆盖什么。

### 先界定 S2 的可观测边界

### 先界定 S2 的可观测边界

S2 只能为当前的 `POST` 请求建立一条**内存受理链**：请求进入服务、完成基础校验、进入应用处理、得到“已受理”或“被拒绝”的结果。这里的证据回答的是：

- 请求是否到达当前进程；
- 输入是否通过校验；
- 应用逻辑是否尝试受理该请求；
- 受理结果、失败原因与关联标识是什么。

它**不**证明消息已经持久化，不证明设备已经收到推送或在线投递，也不证明用户已读。尚未实现的持久化写入、跨进程恢复、离线补偿、设备回执与已读语义，不能被记为“成功”，更不能因为没有观测到错误就被解释为“零故障”。

因此，S2 的状态应保持克制，例如：

`received → validated → accepted_in_memory`

而不是：

`sent → delivered → read`

日志、指标与 Trace 也都是有限证据。错误 Trace 可能未被采样，日志可能因限流或缓冲失败而丢失，进程重启会使内存计数器归零；单条 Trace 只能说明一个请求的路径，不能代表总体用户体验。尤其不能从某次慢请求直接推断根因，也不能用 p99 指标替代诊断结论。

当前应优先保留最小关联字段：请求标识、Trace 标识、时间、接口、校验结果、内存受理结果、错误类别与有限的耗时阶段；同时规定保留期限和访问权限，避免把正文、令牌或不必要的用户数据写入观测系统。后续诊断、SLO 与 CI 中的验证将分别在 11.04、11.08 与 10.09 展开。

### 三类证据各自回答什么

### 三类证据各自回答什么

结构化事件日志、聚合指标与 Trace 都是在请求链上留下证据，但回答的问题不同，不能互相替代。S2 目前只能为内存中的受理与处理流程规划这些证据；未来持久化、设备侧行为、读回链路尚未覆盖，缺失并不等于数值为零。

| 证据类型 | 观察粒度 | 主要回答的问题 | 不能替代什么 |
|---|---|---|---|
| 结构化事件日志 | 单个关键事件 | “某次请求走到了哪里、为何被拒绝或失败？” | 不能稳定描述总体比例；日志可能被采样、限流或丢弃。 |
| 聚合指标 | 时间窗内的总体计数、比例与分布 | “错误是否上升、吞吐是否变化、延迟处于什么范围？” | 不能还原某个请求的完整上下文；计数器重置会影响连续性。 |
| Trace | 单个请求的跨步骤因果路径 | “这次请求经过哪些步骤、耗时主要落在哪里？” | 单条 Trace 不代表总体；错误 Trace 也可能因采样而缺失。 |

结构化日志宜包含请求关联标识、事件名、结果码、阶段、耗时及必要的脱敏上下文，使后续诊断能解释“发生了什么”。指标宜保留请求总数、成功/失败数、按结果码分类的计数和延迟直方图，用于观察趋势与 SLO；仅有 `p99` 升高并不能直接定位根因。Trace 则以同一请求的关联标识串联受理、校验、路由等内存步骤，适合检查局部时序与因果关系。

因此，日志负责可解释的事件细节，指标负责群体信号，Trace 负责请求路径。字段应最小化，并预先规定保留期、访问权限与脱敏边界；更完整的诊断、SLO 评估和 CI 验证将在后续章节展开。

### 为内存受理链设计最小证据

### 为内存受理链设计最小证据

以虚构的 `POST /m-a` 为例，S2 只能为“请求进入 handler、经 app 校验、写入 memorystore”的内存受理链规划证据；它不证明真实指标已上报，也不覆盖未来持久化、设备侧处理或读回路径。

日志应围绕一次请求能否被关联和审计，而非记录完整载荷。建议最小字段为：

- `timestamp`、`level`、`request_id`、`trace_id`：用于时序与跨层关联；
- `route=POST /m-a`、`method`、`status_code`、`outcome`：描述结果；
- `latency_ms`、`error_code`：保留诊断所需的结果与耗时；
- `subject_hash`、`payload_size_bytes`、`schema_version`：用不可逆摘要、大小和版本替代身份信息及原文载荷。

不得记录令牌、手机号、消息正文或完整设备标识。日志应设定有限保留期，并按排障职责授予访问权限；日志可能因采样、限流或投递失败而缺失，不能将“未见日志”等同于“未发生请求”。

指标按语义区分：

- Counter：`ma_requests_total`、`ma_failures_total`，单位为“请求数”，仅递增；重启后的归零应被查询端识别。
- Gauge：`memorystore_items`，单位为“条目数”，表示某一时刻内存存量，不代表持久化数量。
- Histogram：`ma_request_duration_ms`，单位为毫秒，按固定桶聚合；例如以 1 分钟窗口观察吞吐和错误率，以 5 分钟滚动窗口观察延迟分布。

Trace 可建立父子关系：`handler POST /m-a` 为根 Span，`app.validate_and_accept` 为子 Span，`memorystore.put` 再作为其子 Span。每个 Span 至少携带 `trace_id`、耗时、结果和脱敏后的错误类别。错误请求应提高采样优先级，但仍可能漏采；单条 Trace 只能解释个例，不能代表总体，`p99` 也只能指出尾延迟现象，不能单独确定根因。后续诊断、SLO 与 CI 验证将分别扩展这些证据的使用边界。

### 控制标签、身份与数据风险

### 控制标签、身份与数据风险

指标标签应服务于聚合，而非携带逐请求细节。S2 可优先使用低基数标签：`route`（如发送、拉取）、`result`（成功、拒绝、内部错误）、`operation`、`error_class`。避免将用户 ID、会话 ID、请求 ID、消息 ID、完整错误文本或动态群组名作为标签；这些值近乎无界，会造成时间序列膨胀、查询变慢，并可能泄露业务身份。

三类标识承担不同职责：

- `request_id`：一次入口请求的关联键，用于把该请求的日志串联起来。
- `message_id`：一条消息的业务实体标识；一次请求可能没有消息，也可能涉及多条消息。
- `trace_id`：一次调用链的追踪标识；未来跨服务或异步传播时才有更完整价值，S2 仅可为内存受理链预留字段。

日志中优先记录必要上下文：时间、级别、`route`、`result`、`request_id`、可选 `trace_id`、错误类别和耗时桶。正文、令牌、密码、设备标识、完整 IP、手机号等不得直接写入；确需关联时，应采用截断、哈希或受控替代标识，并确认哈希不会因低熵输入而可逆。

还应在设计时写明边界：短期诊断日志保留较短期限，聚合指标保留较长期限；原始日志仅向值班、排障和审计所需角色开放，按最小权限访问并记录查询审计。采样、丢日志和计数器重置会留下证据缺口，因此这些字段支持后续诊断，不构成完整事实或总体统计结论。

### 从症状制定有限证据计划

### 从症状制定有限证据计划

先按症状而非组件堆砌数据源：S2 只能为内存受理链规划请求级证据，不能据此宣称已有真实指标系统、持久化链路或设备侧观测。

- **失败增多**：黑盒侧记录请求总量、成功/失败分类与可见错误码；白盒侧关联`request_id`、入口时间、处理阶段、拒绝原因和异常摘要。重点回答“失败发生在哪一阶段、属于哪一类”，而非仅给出一个失败率。
- **响应变慢**：黑盒侧保留端到端耗时的分桶计数与慢请求阈值事件；白盒侧记录各内存处理阶段的开始/结束或耗时。单次 Trace 只能解释该请求路径，不能代表总体；`p99`即使未来可计算，也只能定位尾部现象，不能单独证明根因。
- **个别请求异常**：用`request_id`串联结构化日志、错误事件与可选 Trace，最小字段可包括时间、请求类型、结果、阶段、耗时、错误类别和脱敏后的关联标识。

证据本身也有失真边界：错误请求可能因采样策略未进入 Trace；高压下日志可能丢弃或截断；进程重启会使内存计数器重置，不能与长期趋势直接拼接。因此应同时记录采样率、日志丢弃状态、计数器启动时间与版本信息，并把“未观察到”表述为“在当前保留证据中未观察到”。

字段应遵循最小化与脱敏原则，明确短期保留期限、按故障排查角色授权访问。持久化、设备、读取等未来阶段尚未覆盖；后续诊断方法见 11.04，服务目标见 11.08，自动化验证接入见 10.09。

> **要点** — S2 只能证明请求被内存受理；日志、指标与追踪互补，且必须诚实标注采样、丢失和未来阶段边界。

本节为虚构 m-a POST 内存受理链设计有限、可关联且不过度暴露隐私的可观测证据。

### 三类证据与请求链边界

### 三类证据与请求链边界

事件日志、聚合指标与 Trace 不是同一份数据的三种格式，而是回答不同问题的证据：

- **事件日志**回答“这一次发生了什么”。例如记录 `request_id`、受理阶段、结果码与失败原因，适合定位单个异常请求；不得写入 IM 正文、联系人、令牌等敏感内容。
- **聚合指标**回答“总体表现如何”。例如 `im_accept_requests_total{result="accepted"}` 统计已受理请求数，单位为“次”；标签只能描述有限维度，如 `result`、`stage`，不能使用 `request_id` 这类高基数字段。
- **Trace**回答“这一次请求经过了哪些边界、各阶段耗时多少”。它将同一请求的 span 组织为树，并用 `trace_id` 关联跨阶段证据。

当前 S2 仅讨论虚构的内存受理路径：

`POST /m-a` → 请求解析 → 基本校验 → 内存写入 → 响应

可对应为 Trace 树：

- `POST /m-a`
  - `parse_request`
  - `validate_input`
  - `store_in_memory`
  - `build_response`

这里的边界必须明确：没有真实网络下游、数据库、消息队列、重试器或持久化存储；因此不能从本节证据推断外部服务延迟、跨进程传播、数据落盘成功或最终送达。`store_in_memory` 成功仅证明当前进程中的受理状态改变。

| 阶段 | 成功证据 | 典型错误证据 |
|---|---|---|
| 解析 | 日志事件、解析耗时 span | 请求格式无效 |
| 校验 | `accepted` 指标增长 | 字段缺失、值不合法 |
| 内存写入 | 写入 span 成功结束 | 容量限制、内部状态错误 |
| 响应 | 响应状态日志 | 未分类内部错误 |

关联时，日志可带 `trace_id` 与 `request_id`；指标通常只保留低基数标签。Trace 可采样，未被采样的请求仍应由指标保留总体计数。

### POST 受理的日志与指标规格

### POST 受理的日志与指标规格

一次 `POST` 内存受理至少应留下可由 `request_id` 关联的日志与指标；日志解释“发生了什么”，指标回答“发生多少、当前多少、耗时如何”。两者都不得记录请求正文、令牌、邮箱或原始用户标识。

**脱敏结构化日志事件**（在请求完成时写一条）：

`time`、`level`、`event="im_accept_completed"`、`request_id`、`trace_id`、`stage`、`result`、`error_code`、`duration_ms`、`payload_bytes`、`subject_hash`

其中 `subject_hash` 是带密钥的不可逆摘要，仅用于同一受理窗口内关联；`result` 只能为 `accepted`、`rejected`、`failed`；`error_code` 为空或受控枚举，如 `invalid_input`、`capacity_exceeded`、`internal_error`。禁止把动态错误文本作为标签或字段主键。

**指标规格：**

| 类型 | 名称与单位 | 标签 | 窗口与解释 |
|---|---|---|---|
| Counter | `im_accept_requests_total`，请求数 | `result`、`stage`、`error_code` | 以 5 分钟增量观察吞吐与失败率：`failed / total`。成功不应携带错误码。 |
| Gauge | `im_accept_inflight`，个 | `stage` | 瞬时正在受理的请求数；持续升高而完成速率不变，提示阻塞或容量不足。 |
| Histogram | `im_accept_duration_seconds`，秒 | `result`、`stage` | 以 5 分钟窗口计算分位数和桶计数；用于观察端到端及阶段耗时，不以毫秒命名却上报秒值。 |

`stage` 应是有限枚举，例如 `validate`、`admit`、`persist`；不得使用请求路径、用户标识、错误详情或 `request_id` 作为标签，否则会产生无界基数。`error_code` 仅在 `result="failed"` 或 `rejected` 时出现；若错误码过多，应归并为稳定类别。

指标不能替代单请求证据：某次失败先用 `request_id` 查日志，再沿 `trace_id` 查看阶段跨度；指标则用于判断该失败是否属于窗口内的系统性变化。对于高流量链路，可保留全部错误 Trace、对成功 Trace 进行概率采样，但 Counter、Gauge 与 Histogram 必须持续记录，避免采样扭曲总体率与延迟分布。

### 上下文传播与 Span 树

### 上下文传播与 Span 树

一次 `m-a POST` 的 Trace 不应只是“耗时列表”，而应表达受理链的因果结构。可将入口 `handler` 设为根 Span，业务编排 `app` 与内存写入 `memorystore` 作为其子代：

- `POST /messages`（根 Span）
  - `app.accept_message`
    - `memorystore.put`

父 Span 在创建子 Span 时传播 Trace 上下文；因此三者共享同一 `traceID`，但各自拥有不同 `spanID`。`parentSpanID` 指向直接调用者，便于回答“慢发生在哪一层”：

| Span | 父级 | 主要证据 | 失败示例 |
|---|---|---|---|
| `POST /messages` | 无 | 路由、HTTP 状态、总时长 | 请求格式无效 |
| `app.accept_message` | handler | 校验、受理决策 | 业务规则拒绝 |
| `memorystore.put` | app | 写入结果、存储耗时 | 容量不足、写入失败 |

三类标识不可混用。`traceID` 标识一次跨层执行路径，应进入 Span、结构化日志，并可作为日志查询键；`requestID` 标识外部请求边界，可由入口生成或接收，适合返回给调用方；`messageID` 标识被受理的消息实体，可在重试、异步处理或多个请求中持续存在。

因此可建立关联：一次请求通常对应一个 `requestID`、一个根 `traceID`；一次成功受理产生一个 `messageID`。但身份边界必须清晰：`requestID` 与 `traceID` 是运行证据，不是用户身份；`messageID` 也不应编码用户名、正文或令牌。跨进程传播时仅传递受控上下文，不把完整请求体、认证凭据或用户可识别信息写入 Span 属性。

### 标签、采样与隐私约束

### 标签、采样与隐私约束

指标标签应服务于聚合，而不是保存逐请求细节。低基数标签的取值集合有限，适合建立稳定时间序列；高基数标签会使序列数近似按标签取值组合相乘，抬高存储、索引、查询和告警成本。

| 标签示例 | 基数 | 是否适合指标标签 | 原因 |
|---|---:|---|---|
| `stage=validate/accept/reject` | 低 | 是 | 可按处理阶段聚合 |
| `error_class=timeout/schema/conflict` | 低 | 是 | 支持失败趋势与告警 |
| `result=success/failure` | 低 | 是 | 支持成功率计算 |
| `request_id` | 极高 | 否 | 几乎每次请求唯一 |
| `user_id`、邮箱、手机号 | 高且敏感 | 否 | 既膨胀基数又泄露隐私 |
| 原始错误文本、完整请求体 | 高且敏感 | 否 | 内容不稳定，可能含秘密信息 |

脱敏的默认原则是：**不记录不需要的数据；不能识别则不记录；必须关联时使用受控摘要。** 例如日志和 Trace 可保留 `request_id`，但不应出现身份证号、令牌、完整地址或原始 IM 内容；如确需关联用户，可使用加盐后的稳定摘要，并限制访问与保留期限。错误应记录分类后的 `error_class`，而非直接复制底层异常和输入内容。

Trace 采样用于控制链路明细成本，不用于替代失败计数。若仅保留 $10\%$ Trace，观察到 3 条失败链路只能说明“样本中有失败”，不能可靠表示总失败数为 30，更不能作为告警分母。完整请求量、完整失败量和阶段拒绝量应由未采样指标记录；Trace 则回答“这次失败经过了哪些阶段、耗时在哪里、关联日志是什么”。

可采用分层策略：成功请求概率采样，失败请求优先保留，关键拒绝阶段提高采样率；但即使“失败全采样”，失败总数仍应以计数器为准，以避免采样器、导出器或 Trace 后端丢失造成证据缺口。

### 症状驱动的证据计划与自测

### 症状驱动的证据计划与自测

先从症状反推证据：用户说“发送慢”，要区分受理慢、后续持久化慢、设备投递慢，还是已读回执缺失。虚构 `m-a POST` 当前仅保证内存受理，因此不能把“接口成功”误写为“消息已送达”。

**指标规格**：`im_accept_duration_seconds` 为直方图，单位秒，记录请求进入至内存受理完成的耗时；标签仅含 `result`（`ok`、`reject`）与 `route`（规范化路由）。不使用 `user_id`、消息内容或请求标识作标签。

**日志事件**：`im.accepted`：`request_id`、`trace_id`、`message_id`、`stage=accept`、`result=ok`、`duration_ms`。`message_id` 用于关联，不应记录正文、收件人明文或令牌。

**Span 树**：

- `POST /messages`
  - `authenticate`
  - `validate`
  - `accept_in_memory`
  - `persist_message`（未来）
  - `deliver_device`（未来）
  - `record_read`（未来）

| 阶段 | 成功证据 | 失败/缺口 |
|---|---|---|
| 受理 | 指标、日志、根 Span | 仅表示内存接受 |
| 持久化 | 未来 Span/错误码 | 当前未覆盖 |
| 设备投递 | 未来投递事件 | 当前不能证明送达 |
| 已读 | 未来回执事件 | 当前不能证明已读 |
