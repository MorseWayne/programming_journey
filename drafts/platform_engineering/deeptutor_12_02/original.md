从镜像摘要 D1 到一次运行中的 IM 网关，关键变化不在镜像内容，而在运行时为它组合出的进程、配置、挂载与隔离环境。

### D1 只是镜像身份，不是运行实例

### D1 只是镜像身份，不是运行实例

`D1` 是镜像内容的摘要，可把它理解为“某份镜像文件系统与元数据的身份标签”。只要镜像内容不变，摘要就不变；它回答的是“运行时依据了哪份镜像”，而不是“当前有哪个服务正在运行”。

需要分开看四个对象：

- **镜像摘要 D1**：不可变身份，例如 `sha256:...`。
- **镜像层**：镜像中可复用的只读文件层，如 Go 编译出的二进制、证书、基础系统文件。
- **容器实例**：一次运行时创建的实例，拥有自己的可写层、环境变量、网络、挂载、namespace 与 cgroup 限制。
- **容器内 Go 进程**：真正执行入口命令的操作系统进程，例如 `/app/gateway`；它处理请求、维护内存中的连接和状态。

同一个 `D1` 可以同时启动多个实例：

`D1 → 容器 A → gateway 进程 101`  
`D1 → 容器 B → gateway 进程 208`

二者虽来自同一镜像，却可以使用不同的端口、配置文件、数据库地址、挂载目录和资源限制。因此，“部署的是 D1”不等于“只有一个运行中的服务”。

容器停止或被重建时，进程内存会消失；容器可写层中的临时修改也未必保留。镜像能重建程序环境，但不能自动恢复未持久化的数据、内存会话或长连接。

### 运行时如何组装一次容器启动

### 运行时如何组装一次容器启动

镜像摘要 `D1` 只标识一份只读文件系统与默认元数据；运行时启动容器时，才把它组装为一个可执行的 IM 网关进程。可将实际运行状态抽象为：

\[
\text{容器实例}=D1+\text{可写层}+\text{启动配置}+\text{挂载}+\text{隔离与资源限制}
\]

入口命令是首要线索。镜像可声明默认 `ENTRYPOINT` 与 `CMD`，例如执行 `./im-gateway`；运行时也可覆盖为 `./im-gateway --port=8080`。最终命令决定 PID 1 是什么进程、接收哪些参数，以及退出码如何反映服务终止原因。

但同一命令未必产生同一行为，因为运行时还会注入：

- **环境变量**：如 `PORT`、日志级别、数据库地址、密钥引用。镜像内没有生产环境密码，并不表示进程启动后拿不到密码。
- **工作目录与用户**：`WORKDIR` 决定相对路径解析；`USER` 决定进程 UID/GID，从而影响读取配置、写入缓存和访问挂载目录的权限。
- **网络**：网络 namespace 提供独立的网卡、IP、路由和端口空间。进程监听的是容器内 `:8080`，是否能被外部访问还取决于端口发布、服务发现与网络策略。
- **挂载**：卷、宿主机目录或临时文件系统会覆盖镜像中的目标路径。挂载 `/data` 后，真正持久的数据可能不在 `D1`，而在外部卷中。
- **namespace 与 cgroup**：前者隔离进程、网络、挂载等视图；后者限制 CPU、内存和进程数。网关因内存上限触发 OOM 退出，是运行配置的结果，不是镜像内容发生变化。

因此，“用 `D1` 重建容器”只能重建基础程序环境。是否恢复原有连接状态、内存中的静态 `6B` 正文或原始请求体，以及挂载中的业务数据，取决于当次运行时配置和外部持久化资源。

### 只读层、可写层与持久卷的边界

### 只读层、可写层与持久卷的边界

镜像摘要 `D1` 标识的是一组只读镜像层：应用二进制、依赖库、默认配置模板等。启动容器时，运行时会在这些只读层之上叠加一层新的**可写层**，于是进程看到的是一个仿佛可读可写的文件系统。

容器内写文件时，去向取决于路径是否被挂载覆盖：

- 写入未挂载路径，如 `/tmp/a.log`、`/app/cache/x`，通常进入该容器的可写层。
- 修改镜像原有文件时，底层文件不会被直接改写；存储驱动会先复制到可写层，再修改这份副本。
- 写入挂载的 `volume`，如 `/var/lib/im/data`，数据进入独立持久卷，而非容器可写层。
- 写入宿主机绑定目录时，数据直接落在宿主机指定路径，生命周期也由该目录管理。

因此，“删除再重建容器”有两种完全不同的结果：

1. 用同一镜像 `D1` 可以重新得到相同的程序文件和默认环境；
2. 原容器可写层中的上传文件、SQLite 数据库、运行期生成配置和缓存会随容器删除而消失；
3. 已正确放入持久卷或外部数据库的数据，才能在新容器重新挂载后继续使用。

例如，IM 网关的静态 `6B` 正文、原始请求体上限 `4096B`、以及 `409/404/200` 的内存受理逻辑属于镜像中的程序行为；但消息记录若仅写入 `/app/data` 的可写层，容器重建后并不会自动回来。镜像可重建，进程可重启，不等于业务数据可恢复。

### S2 当前状态与 S3 未来数据逐项核对

### S2 当前状态与 S3 未来数据逐项核对

S2/v1 的目标是提供**当前容器进程内可见的即时受理结果**，而不是建立可在容器销毁后恢复的业务事实库。核对时应把“响应约定”“进程内存”和“未来持久化数据”分开看。

| 项目 | S2/v1 当前含义 | 容器重启或重建后 | S3 未来可能承担的职责 |
|---|---|---|---|
| 静态正文 `6B` | 固定响应正文，例如 `已受理`一类的短文本 | 可随镜像和代码再次出现 | 通常无需持久化 |
| 原始请求体 `4096B` | 单次请求允许进入处理逻辑的最大原始体积 | 未写入外部存储即丢失 | 保存完整载荷、摘要或审计副本 |
| `200` | 当前请求被正常接收并得到成功响应 | 不证明历史记录仍存在 | 可对应已持久化的受理记录 |
| `404` | 当前进程内找不到指定对象或状态 | 重启后可能因内存清空而增多 | 基于权威数据查询真实不存在 |
| `409` | 当前进程内判定请求与已有状态冲突 | 重启后冲突依据可能消失 | 依据持久化唯一键、版本或幂等记录判定 |

尤其要警惕：`200`、`404`、`409` 在 S2 中都可能只由内存中的映射、集合或计数器得出。它们描述的是“**这一个运行中的进程目前怎么判断**”，不是“系统已经永久记住了什么”。

因此，镜像摘要 D1 不变、入口命令不变，并不能保证 S2 内存仍在。运行时创建新容器后，会得到新的进程、新的地址空间，并重新组合配置、挂载、namespace 与 cgroup。若没有卷、数据库或消息系统等外部权威存储，旧容器中的受理状态不会自动迁移到新容器。

S3 的关键增量不是把响应文本写得更长，而是为请求标识、载荷、处理结果和冲突依据建立可恢复的权威记录。容器可重建，表示程序可再次启动；数据可恢复，则要求业务状态已脱离该容器的易失内存。

### 同一 D1 为何表现不同

### 同一 D1 为何表现不同

镜像摘要 `D1` 只标识一组只读镜像层内容相同；它不等于某次容器，也不保证两个容器对外行为一致。运行时会以 `D1` 为基础，额外组合入口命令、环境变量、可写层、挂载、网络 namespace 与 cgroup 限制，最终启动具体进程。

例如，两个容器都来自 `D1`，却可能出现：

- 容器 A 挂载了新的 `config.yaml`，容器 B 使用镜像内默认配置；A 允许静态文件 `6B`，B 的路由规则可能直接返回 `404`。
- A 以可读写权限挂载日志目录，B 挂载为只读；同一程序在 B 中写文件会失败。
- A 设置了请求体上限 `4096B`，并启用 `409`、`404`、`200` 的内存受理逻辑；B 的环境变量缺失或被覆盖，可能采用另一套限制。
- A 与后端服务位于可互通的网络 namespace，B 的 DNS、端口或路由不同，表现为连接失败或超时。
- A 获得足够内存和 CPU，B 受更严格 cgroup 限制，可能频繁 GC、被 OOM 终止，或无法及时处理长连接退出。

排查“同一 D1 行为不同”时，按以下顺序比较通常最高效：

1. 确认实际镜像摘要确为 `D1`，并记录入口命令与启动参数。
2. 比较环境变量、配置文件及其挂载来源。
3. 检查挂载点、覆盖关系与读写权限，尤其是数据和日志目录。
4. 对照网络 namespace、DNS、暴露端口及后端连通性。
5. 最后检查 cgroup 的内存、CPU、进程数限制和退出事件。

容器可以从 `D1` 快速重建，但挂载中的数据、运行时注入的配置以及可写层内容未必随之恢复；“能重建容器”不能推导出“能恢复数据”。

> **要点** — D1 固定的是镜像内容；容器行为由运行时配置决定，内存数据与可写层都不能替代持久化设计。

先把镜像、容器与文件变化拆开看：同一镜像摘要可以启动多个彼此隔离的容器，而每个容器都拥有独立的临时写入视图。

### 镜像摘要不是正在运行的容器

### 镜像摘要不是正在运行的容器

镜像是用于创建容器的**只读文件系统模板与配置描述**。镜像摘要通常形如 `sha256:...`，是对特定镜像内容的内容寻址标识：摘要相同，表示所指向的镜像内容相同；它不等于某个容器，也不表示其中一定有进程正在运行。

从同一个镜像摘要可以创建多个容器实例。每个容器都会组合：

- 镜像提供的不可变层；
- 该容器独有的可写层；
- 独立的配置、网络命名空间、进程视图和生命周期状态。

因此，两个容器即使都由同一 `D1` 镜像启动，也不是“同一个运行环境”。容器甲在 `/tmp/a` 写入内容，通常不会让容器乙在自己的 `/tmp/a` 中看到该文件；两者共享的是底层只读镜像内容，而不是彼此的写入结果。

还要区分容器与进程：容器是隔离与资源管理的实例边界，容器内进程才是真正执行命令的主体。主进程退出后，容器通常随之停止，但镜像摘要仍可存在，也可据此再次创建新容器。反过来，一个已停止容器仍保留其自身的可写层和配置，直到被删除。

可将关系概括为：

`镜像摘要 → 镜像只读层 → 创建多个容器实例 → 每个容器运行自己的进程`

不要把“同一镜像”“同一容器”和“同一进程”混为一谈：它们分别回答“从什么构建”“是哪一次实例化”“当前谁在执行”。

### 只读镜像层与独立可写层

### 只读镜像层与独立可写层

镜像不是一份会被容器“直接改写”的目录，而是由若干**只读层**组成的文件系统快照。启动容器时，运行时将这些层按顺序联合挂载：上层中同路径的文件可覆盖下层版本，于是进程看到的是一棵完整目录树。

多个容器可以复用同一镜像的只读层，避免为每个容器复制 `/usr`、运行库和应用初始文件。与此同时，每个容器都会获得自己的**可写层**。当进程第一次修改来自只读层的文件时，运行时采用写时复制：先将该文件复制到本容器的可写层，再修改副本；未被修改的文件仍直接复用只读层。

因此，基于同一 `D1` 镜像启动的两个容器，即使都写入 `/tmp/result.txt`，彼此也不会看见对方内容：

- 容器 A 的修改位于 A 的可写层；
- 容器 B 的修改位于 B 的可写层；
- 镜像 `D1` 的只读层不因任何一个容器的写入而改变。

可以把容器视为“镜像只读基底 + 独立短暂增量”。重启**同一个**容器通常仍会使用原有可写层，因此其层内文件可能保留；删除该容器再按同一镜像新建，则会得到新的可写层，旧层中的改动随容器移除而销毁。故容器层适合运行时临时状态，不应作为权威历史或持久数据的唯一载体；需要保留的数据应交给卷、宿主机挂载或外部存储。

### 同一 D1 的两次写入为何互不可见

### 同一 D1 的两次写入为何互不可见

设镜像 `D1` 含有只读的应用文件。基于它同时启动两个 IM 网关容器：

- 容器 `gateway-a`：向 `/tmp/session.token` 写入 `A-123`
- 容器 `gateway-b`：向同一路径写入 `B-456`

随后分别读取：

| 容器 | 读取 `/tmp/session.token` 的结果 |
|---|---|
| `gateway-a` | `A-123` |
| `gateway-b` | `B-456` |

路径相同、基础镜像相同，并不意味着它们在写同一份文件。`D1` 提供的是共享的不可变只读层；每个容器启动时还会获得自己的可写容器层。首次写入 `/tmp/session.token` 时，运行时会在该容器自己的可写视图中创建或覆盖该文件，这就是 copy-on-write（写时复制）的核心效果：读取可复用底层镜像内容，写入则落到各自独立的上层。

因此，`gateway-a` 的文件变化不会回写到 `D1`，也不会出现在 `gateway-b` 中。即使 `gateway-a` 重启，只要仍是同一个容器，其容器层通常仍会保留；但若删除 `gateway-a` 后再用 `D1` 新建容器，原容器层会随容器移除，新的 `/tmp/session.token` 不会自动存在。

所以，容器层适合临时运行状态，不应作为消息、会话或审计记录的权威历史；需要跨容器或跨重建保存的数据，应写入挂载卷、数据库或外部存储。

### 重启、删除与重建的状态边界

### 重启、删除与重建的状态边界

应把“重启”和“重建”视为两种完全不同的状态操作。关键不在于是否仍使用同一个镜像，而在于**原容器对象及其独立可写层是否仍然存在**。

- **重启同一容器**：容器只是停止后再次启动，容器身份、配置以及该容器的可写层通常仍被保留。此前写入 `/tmp/report.txt`、安装的临时工具或程序生成的非挂载目录文件，仍可在该容器中看到。进程会重新创建，但文件系统的容器可写视图并未因重启自动清空。

- **删除容器后重建**：删除会移除该容器对象，同时销毁与之关联的容器可写层。随后即使用完全相同的镜像摘要、相同命令和环境变量创建新容器，得到的也是一个新的可写层；旧容器在 `/tmp`、应用目录等位置写入的内容不会出现。

可将其概括为：

`镜像层 + 容器甲可写层 ≠ 镜像层 + 新容器乙可写层`

同一镜像只提供共同的只读起点，不提供共享的运行时历史。因此，容器可写层适合承载短暂运行状态，却不能作为权威数据、审计记录或需要跨重建保存的业务历史。需要保留的数据应显式写入卷、宿主机挂载目录或外部持久化服务，而不是依赖“容器下次还能回来”。

### 把临时层与权威历史分离

### 把临时层与权威历史分离

IM 网关容器的可写层适合承载“可丢失、可重建、仅服务当前进程”的数据，例如：

- 进程运行时生成的日志缓冲、临时解压文件、请求追踪片段；
- 当前连接的内存索引落盘副本、短期限流计数缓存；
- 排空期间的本地标记文件，如`/tmp/draining`，用于让该实例停止接收新会话；
- 可由配置、注册中心或权威数据重新生成的派生状态。

这些文件属于单个容器的临时视图。即使两个网关由同一镜像启动，容器 A 写入`/tmp/draining`，容器 B 也不会看见；A 重启后是否仍能看到该文件，取决于该容器是否仍被保留。若 A 被删除再重建，即使镜像相同，也会得到新的可写层，旧文件不应被假定存在。

相反，会话归属、用户已读位置、消息投递状态、去重键、离线消息、排空决策等，都属于业务事实。它们不能只写入容器层，应进入持久卷、数据库、对象存储或消息系统等权威存储。例如，消息附件可写入 S3，消息状态写入数据库；网关本地仅缓存“该会话当前由谁处理”。

一个实用判断是：若容器被删除、迁移或扩容后，数据丢失会导致重复投递、消息错序、会话错误迁移或无法审计，那么它就不是临时层数据。容器可写层不是权威历史，也不应承担跨实例协调职责；具体底层存储驱动可能不同，但这一边界不变。

> **要点** — 镜像层可复用且不可变；容器写层彼此隔离、随容器删除而消失，不能承担权威历史。

命名卷能跨容器保留数据，但它不是数据库、备份系统或自动持久化开关；关键在于程序实际写入了什么，以及未来权威状态由谁定义。

### 命名卷的生命周期与重新挂载

### 命名卷的生命周期与重新挂载

容器、命名卷与卷内数据是三个不同层次：

- **容器生命周期**：`docker rm` 删除容器后，容器的可写层随之消失；未挂载到卷中的文件改动通常不可恢复。
- **命名卷生命周期**：如 `docker volume create app-data` 创建的卷独立于容器存在。删除使用它的容器，并不会自动删除该卷；只有显式执行卷删除，或使用会一并清理卷的操作时，数据才可能被移除。
- **数据可见性条件**：数据仍在卷中，不等于新容器自动能看到。新容器必须再次将**同一个卷名**挂载到程序实际读取的**同一个容器内路径**。

例如：

`docker run -v app-data:/var/lib/app ...`

容器删除后，重建时仍需挂载：

`docker run -v app-data:/var/lib/app ...`

若改挂到 `/data`，而程序仍只读取 `/var/lib/app`，它看到的可能是镜像自带目录，而非旧卷数据。反过来，卷挂载到某个镜像已有内容的目录时，会覆盖该目录在容器中的可见内容；镜像里的文件没有消失，但在该挂载点下暂时不可见。

因此，命名卷解决的是“宿主机管理的文件目录可跨容器保留”，不是“进程状态自动落盘”。若 S2 的 `m-a` 仅存在内存，即使挂载了卷，只要程序从未将其写入挂载路径，卷中仍没有对应数据。未来若以 S3、`m-9` 或 `seq9` 为权威状态，也必须由明确的数据库事实、写入流程与恢复规则定义，不能仅凭“曾经挂过 volume”推断其存在或有效。

### 三类挂载的语义边界

### 三类挂载的语义边界

容器的可写层会随容器删除而消失；挂载的作用，是把某个路径的存储来源改为容器外部或内存中的另一套语义。三者都能“让目录可写”，但并不等价。

| 类型 | 数据来源与生命周期 | 权限/管理主体 | 典型场景 |
|---|---|---|---|
| 命名卷（named volume） | 由容器运行时管理；删除容器后通常仍保留，删除卷才消失 | 运行时与管理员管理；可重新挂载到新容器 | 数据库数据目录、需要跨容器延续的应用状态 |
| 绑定挂载（bind mount） | 直接映射宿主机指定路径；生命周期由宿主机文件系统决定 | 宿主机用户、权限、SELinux/ACL 等直接生效 | 源码开发、导入导出文件、由主机统一管理的目录 |
| 内存临时挂载（tmpfs） | 存在主机内存中；容器停止、卸载或主机重启后通常丢失 | 由运行时创建，受内存与挂载选项约束 | 密钥短暂落地、缓存、临时计算文件 |

挂载到某路径会**覆盖镜像中该路径原有内容的可见性**。例如镜像在 `/var/lib/app` 预置了初始化文件，空命名卷首次挂入后，程序看到的可能是卷内容而非镜像目录内容；初始化逻辑必须明确处理这一点。

命名卷的“持久”仅表示字节可在容器删除后保留，不表示数据库事务已提交、数据可恢复、备份已完成，或访问授权正确。数据库仍需自身的日志、刷盘、一致性与备份机制；卷也需显式检查、备份、迁移和权限治理。

尤其不能把挂载误解为自动捕获进程内存。S2 若将 `m-a` 仅保存在内存结构中，即使挂载了卷，也不会自动写入卷。未来若 S3 要读取权威的 `m-9/seq9` 并上传至 S3，则必须先定义明确的数据库事实：何时提交、由哪个表或记录表示、如何按序读取；卷只是承载该数据库文件或数据目录的介质。

### 挂载覆盖与应用实际写入路径

### 挂载覆盖与应用实际写入路径

将卷挂到容器路径后，挂载点会**覆盖镜像中该路径原有内容**。例如镜像构建时已包含：

`/app/data/config.json`

但运行时使用命名卷挂载：

`/app/data`

容器内看到的是卷根目录，而不是镜像层里的 `/app/data`。若该卷为空，`config.json` 也会“消失”；它仍在镜像层中，只是被挂载遮蔽。删除或取消挂载后，镜像原有文件才会再次可见。

因此，必须从应用的实际写入路径推导持久化结果，而不能只看“是否挂了卷”。对 Go 服务而言，可区分三类状态：

- **纯内存状态**：如 `map`、缓存、会话、队列中的未落盘对象。S2 若只把 `m-a` 保存在进程内存，即使容器挂载了 volume，也不会自动写入卷；进程退出、重启或迁移后该状态消失。
- **容器可写层文件**：例如程序写入 `/tmp/result`，而该路径没有挂载。文件随容器存在，但删除容器通常即丢失。
- **挂载路径中的文件**：例如程序明确将快照写到 `/var/lib/app/state.json`，且 volume 挂载到 `/var/lib/app`。此时文件进入卷，可在容器删除后由新容器重新挂载读取。

可将判断写成：

$$
\text{可保留数据}=\text{应用实际写入的路径}\cap\text{持久挂载覆盖的路径}
$$

若交集为空，卷的存在没有意义；若写入发生在被挂载目录下，则还要确认写入是否成功完成、何时刷新，以及新实例是否会把该文件视为权威事实。卷只能保存字节，不能替应用把内存中的 `m-a` 变成可恢复状态，更不能自动规定未来 S3、`m-9/seq9` 或 S2 应以哪些数据库记录、日志或对象存储结果为准。

### S2 内存消息为何不会自动持久化

### S2 内存消息为何不会自动持久化

设 IM 网关收到消息 `m-a` 后，仅执行：

`连接读包 → 校验 → 放入进程内存队列 → 转发给在线用户`

此时 `m-a` 存在于堆、队列或会话对象中，而不在文件系统中。即使容器启动时挂载了命名卷：

`/var/lib/im-data ← named volume`

也不会改变上述事实：卷只提供一个可写的文件系统路径，不能监听进程内存，更不会把对象、队列元素或网络缓冲区自动序列化为文件。

因此，容器被删除、进程崩溃或宿主机重启后，内存中的 `m-a` 消失；命名卷仍保留，但其中可能根本没有与 `m-a` 对应的记录。重新创建容器并挂回同一卷，只能看到此前**实际写入该卷**的文件。

要让 `m-a` 可恢复，程序必须显式完成持久化，例如：

- 将消息编码后写入卷内日志文件；
- 写入外部数据库或消息队列，并等待确认；
- 在数据库事务提交成功后，再把该记录声明为可查询事实。

挂载卷解决的是“写入文件后，文件放在哪里、容器删除后是否保留”；它不解决“消息何时落盘、是否提交成功、能否去重、如何恢复、谁是权威状态”。若未来 S3、`m-9` 或 `seq9` 需要作为可追溯消息，必须由明确的数据库事实或持久日志定义，而不能依据某次纯内存转发推断。

### S3 权威事实、事务与恢复核对

### S3 权威事实、事务与恢复核对

S3 的关键不是“数据有没有放进卷”，而是故障、重启或迁移后，系统能否依据**唯一、可验证的权威事实**恢复一致状态。若 `m-9` 表示消息标识、`seq9` 表示已确认的递增序号，则应由数据库事务明确记录其含义、归属与状态，例如：

- `message_id = m-9` 是否已接收、已处理、已投递或已撤销；
- `seq = 9` 属于哪个流、租户或消费者，是否允许跳号、重放；
- 消息内容、游标、去重键与授权主体之间是否处于同一事务边界。

命名卷只提供“容器删除后目录内容仍可保留”的存储位置。它不保证应用已将内存状态刷入文件，更不保证多个文件与数据库记录原子一致。S2 若仅把 `m-a` 保存在进程内存，哪怕挂载了 volume，退出后也不会自动出现可恢复记录。

恢复时应以数据库中的事务提交结果为准：先读取已提交的 `m-9`、`seq9` 和状态版本，再重建缓存、连接会话及派生索引；卷中的文件只能作为明确设计的日志、附件或快照输入，并须校验版本、校验和及对应事务位置。挂载到镜像原有目录还会覆盖镜像内文件，因此不能把“目录存在”误判为“初始数据仍可用”。

备份负责保留可恢复副本，事务负责原子提交与一致性，授权负责判断谁能读取、修改或重放事实；volume 只负责承载数据。未来若迁移到 S3，对象存储也只能保存已定义的数据库事实或其可验证快照，不能替代数据库对 `m-9`、`seq9` 的语义裁决。

> **要点** — 卷只保存实际写入其中的数据；容器删除后须重新挂载，业务权威性仍需由数据库事实、事务、备份与授权共同保证。

容器不是轻量虚拟机，而是由镜像、隔离视图、资源限制与进程共同构成的运行边界。理解这些边界，才能正确诊断IM网关的真实行为。

### 容器的本体：进程加运行约束

### 容器的本体：进程加运行约束

镜像不是容器本身，而是一份通常只读的文件系统模板：包含应用二进制、依赖库、默认配置和启动命令。由镜像启动后，运行时为它准备可写层、网络与挂载等环境，并在宿主机上创建一个或多个真实进程；这组进程连同其运行约束，才是容器。

可以将其抽象为：

$$
\text{容器}=\text{宿主机进程}+\text{隔离视图}+\text{资源限制}+\text{文件系统可写层}
$$

因此，容器内看到的 `PID 1`，在宿主机上往往只是某个普通 PID；容器内的 `/` 可能由镜像层和可写层叠加而成；容器内的 `127.0.0.1` 只指向该网络命名空间自己的回环接口，并不自动等于宿主机回环地址。

容器不是虚拟机：它通常不模拟独立硬件，也不运行独立内核，而是与宿主机共享同一个内核。namespace 决定进程“看见什么”，例如进程号、挂载点、网络接口和用户映射；cgroup 则决定进程“最多能用多少”，例如 CPU、内存和进程数。即使宿主机 CPU 空闲，限制为 `0.5` 核的容器仍可能因配额耗尽而被节流。

此外，是否能执行特权操作还取决于 capabilities、安全策略及用户映射，而不只取决于“是否在容器里”。诊断容器问题时，应始终回到宿主机进程、其 namespace 与 cgroup，而不要把容器当作一台独立机器。

### namespace：进程看到的独立世界

### namespace：进程看到的独立世界

namespace 不会“虚拟出一台机器”，而是让同一内核上的进程获得不同的观察视图。容器启动时，运行时根据配置为进程创建或加入某些 namespace；因此，“是否隔离”不是容器天然属性，而是具体 namespace 的组合结果。

- **PID namespace**：容器进程看到独立的进程号空间。容器内的主进程通常是 `PID 1`，但宿主机仍能看到它对应的真实 PID。`PID 1` 还承担信号处理与孤儿进程回收责任；若它不正确转发 `SIGTERM`，长连接服务可能无法优雅退出。
- **mount namespace**：决定进程看到哪套挂载表与根文件系统。镜像层、容器可写层、挂载卷共同形成容器内的 `/`；容器修改文件，通常写入可写层或显式挂载的卷，而非直接改宿主机同路径。
- **net namespace**：拥有独立的网卡、路由表、iptables 规则和端口空间。因此容器里的 `127.0.0.1` 指向该容器自身，不是宿主机，也不是其他容器。若网关监听 `127.0.0.1:8080`，外部流量即使映射端口也未必能到达。
- **user namespace**：映射用户与组 ID。容器内看似 `root` 的 `UID 0`，可映射为宿主机上的非特权 UID，从而缩小文件权限和内核操作的影响范围。

配置也可以选择继承而非新建视图，例如 `hostNetwork` 使进程共享宿主机网络 namespace，`hostPID` 共享宿主机进程视图。此时容器获得便利，也失去相应隔离边界。namespace 只回答“看见什么”；能做什么还取决于 capabilities、安全策略与 cgroup 资源限制。

### cgroup v2：看似空闲仍会被节流

### cgroup v2：看似空闲仍会被节流

cgroup v2 不改变进程“看见”的 CPU 数量，却会限制它实际能使用的计算时间。容器即使运行在 16 核主机上，也可能被配置为最多使用 `0.5` 个 CPU：

`cpu.max = 50000 100000`

含义是在每个 `100ms` 周期内，该 cgroup 只能累计运行 `50ms`。如果容器内多个线程同时抢占 CPU，它们的运行时间会合并计入这 `50ms`；额度耗尽后，内核将其暂停到下一个周期。这就是 **CPU 节流**。因此主机 `top` 显示大量空闲 CPU，并不表示该容器还能继续提速：空闲的是宿主机可调度能力，容器已经触及自己的配额边界。

可从 cgroup 统计中确认：

- `cpu.stat` 中 `nr_throttled`、`throttled_usec` 持续增长，说明发生节流。
- `memory.max` 是内存硬上限；达到上限后，分配可能失败，严重时触发 cgroup 内存回收或 OOM 杀进程。
- `pids.max` 限制进程与线程总数；线程池膨胀、频繁 `fork` 或连接处理模型失控时，会出现“无法创建新线程/进程”。

对 IM 网关而言，CPU 配额不足会放大加解密、序列化、心跳处理和事件循环延迟；内存或 pids 限制则可能表现为连接建立失败。诊断时应同时看容器内负载、`cpu.stat`、内存事件和 `pids.current`，不能只看宿主机是否空闲。

### IM网关实例：127.0.0.1与权限边界

### IM网关实例：127.0.0.1与权限边界

设想同一份 IM 网关镜像摘要 `sha256:...` 被启动为两个实例：`gateway-a` 与 `gateway-b`。镜像相同，只说明初始根文件系统内容相同；运行时行为仍由 namespace、挂载、资源限制与能力集决定。

- `gateway-a` 使用独立网络 namespace。它监听 `127.0.0.1:8080`，该地址只存在于自己的网络视图中；宿主机或 `gateway-b` 不能直接访问它。若要对外提供服务，必须监听容器网卡地址，或由端口映射、代理转发进入。
- `gateway-b` 使用宿主网络 namespace。此时它的 `127.0.0.1` 就是宿主机回环地址。若宿主机已有服务占用 `127.0.0.1:8080`，网关会绑定失败；反之，网关也可能意外接触宿主机仅打算本地开放的服务。

挂载配置同样会改变结果。`gateway-a` 将日志目录挂载到独立卷，写入不会改变镜像层；`gateway-b` 若绑定挂载宿主机 `/etc/im-gateway`，则容器内该路径会覆盖镜像原有文件，配置更新可立即影响进程。

权限并不由“是否在容器中”自动决定。即使进程是容器内的 `root`，若删除 `NET_ADMIN`，它仍不能配置路由或创建网卡；若额外授予 `SYS_ADMIN`、挂入宿主机敏感目录，隔离边界便显著缩小。故排查连接失败或权限拒绝时，应同时核对网络视图、挂载来源与 capabilities，而非只比较镜像版本。

### 排障核对：从S2进程状态走向S3权威数据

### 排障核对：从 S2 进程状态走向 S3 权威数据

看到容器“运行中”、镜像摘要正确，只能说明 **S2：进程存在**；它并不能证明服务已具备正确的隔离视图、资源条件和外部可达性。排障应把运行时元数据、宿主机内核视角和实际探测结果提升为 **S3：权威数据**。

按以下顺序核对：

1. **先锁定真实进程**：确认容器主进程及其子进程，而非仅看编排平台状态。检查退出码、重启次数、僵尸进程与信号处理；长连接网关尤其要确认收到 `SIGTERM` 后是否停止接入、等待连接排空，并在宽限期内退出。

2. **核对 namespace 归属**：从 `/proc/<pid>/ns/` 比较 `pid`、`mnt`、`net`、`user` 等链接。若使用 host 网络，容器的 `127.0.0.1` 实际指向宿主机；若新建 net namespace，则它只指向容器自身。不要把“能访问 localhost”直接推断为“服务监听正确”。

3. **读取 cgroup v2 实际值**：检查 `cpu.max`、`memory.max`、`memory.current`、`pids.max` 及事件计数。宿主机 CPU 空闲不代表容器可用：`cpu.max` 若限制为 0.5 核，持续负载仍会发生节流；内存问题应同时看 `memory.events` 中的 OOM、`oom_kill`。

4. **确认挂载与可写层**：查看 `/proc/<pid>/mountinfo`，确认配置文件、证书、日志目录和数据卷是否确实挂入预期路径。镜像内文件可能被 bind mount 覆盖；可写层中的临时修复也会随容器重建消失。

5. **最后验证网络与权限**：在该进程所在 net namespace 内检查监听地址、路由、DNS 与防火墙规则；再核对 UID/GID、Linux capabilities、只读根文件系统及安全策略。端口未监听、证书不可读和缺少绑定低端口权限，表象都可能是“应用启动失败”。

结论应基于 PID、`/proc`、cgroup 文件、挂载表和命名空间内探测，而不是基于镜像标签或控制台的“健康”标记。

> **要点** — 镜像相同不代表运行行为相同；namespace决定视图，cgroup决定资源边界，挂载、网络与权限共同决定容器实际能力。

容器退出不是“进程结束”这么简单：入口形式、PID1、信号转发与长连接排空共同决定服务能否平稳下线。

### 容器主进程与入口命令

### 容器主进程与入口命令

容器并不是一台独立虚拟机；对运行时而言，它首先是一组受隔离约束的进程，其中最关键的是容器的**主进程**，通常也是容器内的 `PID 1`。主进程仍在运行，容器通常显示为运行中；主进程退出，容器即使还有其他后台子进程，也会进入退出状态。

入口命令决定谁成为这个主进程。理想情况是应用程序直接作为主进程启动，例如：

`ENTRYPOINT ["./server"]`

这类 exec 形式会直接执行 `server`，应用成为 `PID 1`，容器运行时发送的停止信号可直接到达应用。

但若使用 shell 形式：

`ENTRYPOINT ./server`

运行时通常会先启动类似 `/bin/sh -c "./server"` 的 shell。此时 shell 可能是 `PID 1`，真正的应用只是其子进程。于是“容器在跑”不等于应用就是主进程；信号先到 shell，而 shell 未必会正确转发、等待或回收子进程。

因此，应优先让服务进程直接成为入口。确有启动脚本需求时，脚本最后应使用 `exec ./server` 替换自身，而不是以后台方式启动服务后自行退出。这样既避免包装层干扰信号处理，也使容器生命周期与应用生命周期保持一致。

### exec 形式与 shell 形式的信号路径

### exec 形式与 shell 形式的信号路径

`ENTRYPOINT` 的写法决定了容器内谁成为 PID 1，以及停止信号能否直接到达业务进程。

- **exec 形式**使用 JSON 数组：
  `ENTRYPOINT ["./server", "--port", "8080"]`

  Docker 直接执行 `./server`，它通常就是容器的 PID 1。执行文件、参数边界都明确，不经过 shell 的字符串解析；当 `docker stop` 向容器发送停止信号时，业务程序可直接收到 `SIGTERM`（或配置的停止信号），因此 Go 程序能据此调用 `Server.Shutdown`、停止接收新请求并开始排空。

- **shell 形式**使用字符串：
  `ENTRYPOINT ./server --port 8080`

  Docker 实际会启动类似 `/bin/sh -c " ./server --port 8080"` 的 shell。此时 shell 往往是 PID 1，业务程序成为其子进程。停止信号先到 shell；shell 是否向子进程转发、何时等待子进程退出，取决于 shell 行为和脚本写法，不能假定会自动可靠转发。结果可能是 shell 退出而子进程仍在运行，或业务程序根本未收到优雅退出信号。

若必须使用启动脚本，应在脚本末尾使用：

`exec ./server --port 8080`

`exec` 会用业务进程替换当前 shell，使业务程序接管 PID 1，恢复与 exec 形式相近的信号路径。还应避免把参数拼接成未经引用的字符串；exec 形式及脚本中的 `"$@"` 更能保留参数边界，减少空格、通配符展开和注入式歧义。

### PID1 的信号与子进程回收责任

### PID1 的信号与子进程回收责任

容器并不等同于一台完整虚拟机；通常，容器入口进程就是该 PID 命名空间中的 `PID 1`。它既是服务生命周期的第一接收者，也天然承担“孤儿子进程最终监护人”的角色。

首先看信号路径。若镜像采用 exec 形式：

`ENTRYPOINT ["./server"]`

则 Go 程序直接成为 `PID 1`，`docker stop` 发送的停止信号可以直接到达程序，`signal.NotifyContext`、`http.Server.Shutdown` 等退出逻辑才有机会执行。若采用 shell 形式：

`ENTRYPOINT ./server`

实际的 `PID 1` 往往是 `/bin/sh -c`；停止信号先到 shell，shell 未必会正确转发给其子进程。结果是：外层看似收到停止请求，真正的 Go 服务仍在运行，直至宽限期结束后被强制杀死。必要时可在脚本末尾使用 `exec ./server`，以 shell 替换自身。

其次，服务若启动了辅助子进程，例如调用转码器、备份命令或 worker，退出时不能只关闭 HTTP 监听：

1. 停止接收新任务；
2. 取消子任务的 `context`，或向子进程发送终止信号；
3. 调用 `Wait()` 等待子进程退出；
4. 在超时边界内完成收尾，再让主进程退出。

原因在于子进程退出后，父进程若未调用 `wait` 系列操作读取退出状态，就会留下僵尸进程。普通进程退出后，其孤儿通常会被 `PID 1` 接管；但若 Go 服务本身就是 `PID 1`，又没有可靠回收逻辑，容器内可能持续积累僵尸条目，最终耗尽进程表。

因此，PID1 的正确职责可概括为：**接收并响应停止信号、协调子任务退出、回收所有已结束子进程，并在有界时间内完成自身退出。**

### docker stop 的两阶段停止过程

### docker stop 的两阶段停止过程

`docker stop` 不是立即“拔电源”，而是一个先请求、后兜底的两阶段流程：

1. **发送停止信号**：Docker 先向容器的 `PID 1` 发送停止信号，默认通常为 `SIGTERM`。镜像可通过 `STOPSIGNAL` 指定其他信号，命令也可覆盖该设置。此时容器仍在运行，应用应开始自主退出。
2. **等待宽限期**：Docker 等待一段可配置的时间；常见默认值为 10 秒，可用 `docker stop -t 秒数 容器名` 调整。宽限期的意义是让服务停止接流量、完成必要清理，而非无限等待。
3. **强制终止**：若期限届满进程仍未退出，Docker 发送不可捕获、不可忽略的 `SIGKILL`，容器随即结束。`SIGKILL` 不会触发 Go 的延迟清理逻辑，因此未完成的请求、日志刷新或状态写入都可能中断。

对 Go 的 HTTP 服务，收到停止信号后应尽快执行有界退出流程：

- 停止接受新请求，例如关闭监听器或从负载均衡摘除；
- 调用 `http.Server.Shutdown(ctx)`，并给 `ctx` 设置小于 Docker 宽限期的超时；
- 主动通知并关闭 WebSocket 等 hijacked 连接；`Shutdown` 不会替应用管理它们；
- 等待后台 goroutine、任务队列和日志写入在限定时间内收尾，再退出主进程。

例如 Docker 宽限期为 30 秒时，应用内部排空预算可设为 25 秒，保留余量处理信号、退出和调度延迟。否则应用即使已收到 `SIGTERM`，仍可能在排空尚未完成时被 `SIGKILL` 截断。

### IM 长连接的有界排空方案

### IM 长连接的有界排空方案

以 IM 网关为例：HTTP 登录、鉴权后升级为 WebSocket，连接常被 `Hijack` 或由 WebSocket 库接管。此后它不再是普通 HTTP 请求；调用 `http.Server.Shutdown(ctx)` 会停止监听、等待普通请求返回，却**不会自动关闭已劫持的 WebSocket**。若只依赖 `Shutdown`，容器可能一直等到 Docker 宽限期结束，再被强制杀死。

收到停止信号后，可按以下顺序执行：

1. **进入 draining 状态**：原子标记 `draining=true`，健康检查返回不就绪，使负载均衡摘除实例。
2. **拒绝新会话**：关闭或停止接收端口；对尚未升级的请求返回“服务维护中”；鉴权、重连接口也不再分配新连接。
3. **通知存量客户端**：遍历连接注册表，发送业务消息，如 `server_draining`，携带重连地址或预计截止时间；必要时再发送 WebSocket Close 控制帧。
4. **限时排空**：允许客户端主动完成确认、消息提交与迁移，但排空必须有上限，例如 `20s`。连接断开时从注册表删除。
5. **到期强制收口**：截止时间到达后，逐个关闭剩余 WebSocket，再调用 `Shutdown` 等待普通 HTTP 请求结束；总时限应小于容器停止宽限期。
6. **最终退出**：取消后台任务、等待 goroutine 结束，并确保 PID 1 正确退出；若启动了子进程，还应负责回收。

核心不是“等待所有用户下线”，而是在确定窗口内尽量完成迁移。可将总预算拆为：$T_{\text{notify}} + T_{\text{drain}} + T_{\text{http}} < T_{\text{docker}}$。所有关闭路径应幂等，因为停止信号、连接异常和超时可能并发发生。

> **要点** — 平稳退出依赖正确的 PID1 与信号路径；Go 长连接必须由应用主动、有界地通知和排空。

以停机重建中的虚构 IM 网关为纸上案例，分清当前内存事实、容器临时状态、持久数据证据与连接排空边界。

### 从镜像摘要到正在运行的 D1

### 从镜像摘要到正在运行的 D1

镜像摘要标识的是一份不可变的文件系统与配置模板，例如 `sha256:...`。它说明 D1 可以基于“同一份程序镜像”启动，却不说明旧容器当时仍保有什么运行事实。不要把镜像理解为进程快照、内存转储或连接存档。

纸上可将对象分为四层：

- **镜像摘要**：提供网关二进制、依赖和默认配置；同一摘要可创建多个容器。
- **旧容器实例**：曾承载 S2 中已受理的 `m-a`、在线 B 连接、环境变量及其可写层。
- **旧容器内进程**：实际占有内存、文件描述符、套接字和请求上下文；停止后这些运行态消失。
- **重建后的 D1**：由镜像与启动参数创建的新容器，其内部是新的进程、PID、内存空间和监听套接字。

因此，即使 D1 使用与旧容器完全相同的镜像摘要，也只能推出“程序版本可能相同”，不能推出它恢复了旧进程的 S2 内存、B 的长连接或 `m-a` 的受理上下文。`docker running` 最多证明 D1 当前有容器在运行；它不是“旧业务状态已恢复”的证据。

若执行的是同一容器的 `restart`，其可写层中的临时文件通常仍可能存在，但进程内存与网络连接仍须重建。若旧容器被删除后再创建 D1，则旧可写层不应视为可用来源。未来 DB volume 中的 `m-9/seq9` 是否保留，要依据卷管理策略与数据库提交证据判断，而不是依据镜像摘要或 D1 的运行状态判断。

### 旧容器 S2 的状态分层清单

### 旧容器 S2 的状态分层清单

面对旧容器 `S2`，先不要把“`docker running`”误读为“业务状态已恢复”。应将纸面事实按归属分层，并为每项指定可验证证据。

- **进程内存：当前受理 `m-a`**  
  若 `m-a` 已被网关进程接收、尚未完成数据库提交或下游确认，它存在于 `S2` 进程地址空间、线程队列或运行时缓冲区中。停止并重建为 `D1` 后，该内存必然消失；即使镜像、环境变量和启动命令相同，也不会自动重现。可检查旧进程日志、内存转储或应用级投递记录，但不能由新容器启动成功反推其已处理。

- **进程内存：在线连接 `B`**  
  在线 `B` 是 TCP/WebSocket 等连接及其会话状态，归属于旧进程和旧网络命名空间。停机时连接会断开，客户端是否重连、是否重复发送 `m-a`，取决于协议、会话令牌和客户端重试逻辑。应以连接排空记录、关闭原因、客户端确认或服务端会话日志验证，而非把“端口重新监听”当作旧连接仍在。

- **容器可写层：临时文件**  
  临时上传片段、缓存、队列落盘文件若写在容器根文件系统可写层，只是 `S2` 的临时状态。对**同一容器执行 restart**，该层通常仍在；删除 `S2` 后再创建 `D1`，该层不应假定保留。验证方式是检查原容器文件系统或导出其层，不是检查新容器内同路径是否存在。

- **命名卷：未来数据库 `m-9` 与 `seq9`**  
  `m-9` 及序号 `seq9` 若写入命名卷中的数据库文件，其保留性由卷的生命周期和部署操作决定，而非镜像决定。应核对卷名、挂载点、卷是否复用，以及数据库恢复后的实际查询结果。卷仍存在不等于事务已提交；`seq9` 也不当然证明消息内容、顺序约束和索引均一致。

- **外部系统：提交与设备确认**  
  数据库提交证据应来自事务日志、提交位点或可重复查询；设备 ACK 应来自协议记录、回执标识或对端状态。它们属于容器外部或独立持久化系统，必须分别核验。仅凭 `docker running`，不能宣称 `m-a` 已恢复、`m-9` 已提交，或设备已经收到并确认。

### 重启、删除与重建的状态后果

### 重启、删除与重建的状态后果

不要把“服务又起来了”误读为“状态恢复了”。对旧容器执行 `restart`，与删除后创建新容器 `D1`，边界完全不同：

| 状态对象 | 同一容器 `restart` | 删除旧容器并创建 `D1` |
|---|---|---|
| S2 内存中的受理 `m-a`、会话表、队列指针 | 进程终止即消失；重启后只能由程序重新初始化或外部恢复 | 消失；`D1` 是新进程，不能继承旧进程地址空间 |
| 在线 B 连接、TCP 长连接 | 停机时连接断开；客户端需重连，应用需重新鉴权、订阅或补偿 | 同样断开；新容器网络身份也可能变化 |
| 容器可写层中的临时文件 | 同一容器通常仍在，因其可写层未被删除；但不能据此假定应用状态一致 | 随旧容器删除而消失；`D1` 获得新的可写层 |
| 命名卷中的数据，如 DB volume `m-9/seq9` | 通常继续挂载，数据是否可用取决于卷、文件系统与数据库恢复 | 若删除容器时未删除命名卷，`D1` 可重新挂载；若卷被删除、替换或未挂载，则不能继承 |

因此，`restart` 仅可能保留“同一容器的磁盘式临时层”，绝不保留进程内存和既有连接；删除再创建则连该临时层也失去。命名卷是独立管理对象，不能由 `docker running` 推导其内容已恢复，更不能据此断言数据库提交完成或设备已收到 ACK。对此仍须分别检查数据库提交证据、卷挂载与一致性，以及设备侧确认记录。

### PID1 停止信号与长连接排空

### PID1 停止信号与长连接排空

Go 网关若作为容器的 PID1，不能只依赖默认行为：它应直接接收 `SIGTERM`，把“容器将停止”转换为应用级排空流程。`docker stop` 通常先发送 `SIGTERM`，超出宽限期后才发送不可处理的 `SIGKILL`；因此真正的退出窗口由网关主动管理，而非看到进程仍在就宣称连接已安全恢复。

推荐将状态从当前 `S2` 切换为“排空中”：

1. **停止接收新工作**：关闭监听器，或使健康检查返回不就绪，让负载均衡不再导入新 HTTP、WebSocket 或 IM 长连接。
2. **拒绝新连接**：新到达的连接明确返回维护中；不要让其继续进入内存受理表 `m-a`。
3. **通知在线 B**：对已在线的 B 发送“服务重启、请重连”控制消息，给客户端留出迁移或重连时间。
4. **排空存量请求**：允许已开始的请求在截止时间前完成；长连接不应无限等待，可按连接、会话或消息确认状态逐步关闭。
5. **超时收尾**：到达应用截止时间后取消 `context`、关闭剩余连接、停止后台协程，再退出 PID1；该截止时间必须小于容器停止宽限期。

可将退出逻辑表达为：

`SIGTERM → draining=true → 关闭入口 → 通知B → 等待inflight=0或deadline → 强制关闭 → exit`

重建 `D1` 后，`m-a` 中的受理状态、在线 B 的连接对象及其排空进度都必须重新建立。即使同一容器仅 `restart` 而可写层临时文件仍在，也不能把文件或 `docker running` 当作连接恢复、消息提交或设备 ACK 已完成的证据。

### 恢复判断必须回到权威证据

### 恢复判断必须回到权威证据

`docker running` 只证明容器进程尚在运行；它不能证明旧容器中的业务状态、持久数据和客户端连接已经恢复。对纸上 IM 网关而言，重建后的 D1 即使成功启动，也必须逐项回到各自的权威证据核对：

- **内存受理状态**：旧 S2 中的 `m-a`、在线 B 连接属于进程内存。D1 启动后只能重新加载或重新受理，不能因新进程存在而推定其仍然有效。
- **数据库提交**：未来消息 `m-9/seq9` 是否恢复，应查询数据库事务提交记录、复制状态或审计日志；“应用日志打印成功”不等于已提交。
- **设备送达**：B 是否实际收到消息，应检查设备 ACK、会话确认或可验证的回执记录。服务端仍显示“在线”不能替代 ACK。
- **卷与文件**：先确认 named volume 是否仍存在、是否挂载到正确路径、容器内运行用户是否有读写权限。卷存在不代表应用实际读到了正确数据。
- **网络与身份**：端口监听、DNS 名称、网络命名空间、证书与服务发现注册都应单独检查。新 D1 可能使用了不同 IP、不同网络或失效凭据。
- **临时可写层**：同一容器执行 `restart` 时，未删除的可写层文件可能仍在；若删除旧容器再创建 D1，则不能把这些文件当作恢复依据。

因此，恢复结论应写成“DB 已确认提交、卷已正确挂载、D1 已重新建立会话、设备 ACK 已收到”等可验证事实，而不是笼统地说“容器已经起来，所以业务已恢复”。

> **要点** — 镜像不保存运行现场；重建必失内存与连接，数据恢复须以卷、数据库提交和设备确认等权威证据判定。

相同镜像摘要只说明起点一致，容器的挂载、权限、网络与资源配置才决定IM网关实际如何运行。

### 从摘要到实例：相同D1不等于相同行为

### 从摘要到实例：相同 D1 不等于相同行为

`D1` 是镜像内容的摘要，通常只能证明两次部署使用了同一份镜像文件系统与镜像配置；它不能证明运行时拿到了同一份配置、数据、网络或资源。因此，“两台机器都是 D1”只能说明起点相同，不能推出 OpenIM 网关的连接、鉴权、退出行为必然一致。

应区分四个层次：

1. **源提交**：某个 Git 提交只描述源码版本。即使提交相同，构建参数、依赖下载、构建时间和是否重新打标都可能不同。
2. **镜像摘要**：`D1` 固化构建后的镜像产物，但不包含容器启动时追加的卷、环境变量、端口映射和资源限制。
3. **容器实例**：同一 `D1` 可启动多个容器；每个实例拥有独立的环境变量、命令行、`volume` 挂载、用户身份、只读根文件系统及重启策略。
4. **宿主进程**：最终是宿主机上的进程在监听端口、读取文件、建立长连接。它实际受网络命名空间、DNS、iptables、cgroup CPU/内存限额、文件权限及宿主机负载影响。

例如，两个实例均来自 `D1`：A 挂载了正确的配置和证书，映射 `10002:10002`，并获得足够 CPU；B 挂载空目录覆盖默认配置，证书权限不足，或仅限 `0.1` 核 CPU。二者镜像相同，却可能分别表现为正常建连与启动失败、健康检查超时或长连接频繁断开。

因此，固定展示两段 OpenIM 源码或同一个摘要，不能证明真实运行配置。结论必须落到具体容器实例：检查其启动参数、挂载内容、网络路径、cgroup 限额、健康状态，并以业务连接成功与失败的正反证据验证。

### 挂载与权限：可写层之外的数据变量

### 挂载与权限：可写层之外的数据变量

同一镜像摘要 `D1` 只保证镜像的只读层相同；容器启动后，挂载会覆盖镜像内原有路径，而权限决定进程能否读取、写入或创建文件。因此，两个基于 `D1` 的 OpenIM 容器可能代码完全一致，却得到相反的启动与运行结果。

| 对比项 | 容器 A | 容器 B | 可能结果 |
|---|---|---|---|
| 配置挂载 | 挂载正确的生产配置到 `/app/config` | 挂载空目录或旧配置覆盖该路径 | A 连接正确数据库；B 使用默认值、旧地址或因缺少配置退出 |
| 日志挂载 | 宿主目录对运行用户可写 | 目录属主为 `root`，容器以普通用户运行 | A 持续输出日志；B 创建日志失败，部分程序直接启动失败 |
| 数据目录 | 挂载持久卷 `/data` | 未挂载，数据写入可写层 | A 重启后保留状态；B 重建容器后数据丢失 |
| 只读挂载 | 配置以只读方式挂载 | 程序尝试改写该配置 | B 可能因“只读文件系统”报错或无法热更新 |

应区分镜像内文件与实际可见文件：若宿主机将目录挂载到 `/app/config`，镜像在该路径预置的配置即被遮蔽，不能再据镜像内容推断运行配置。类似地，容器内显示的 UID/GID、`umask`、宿主目录属主、访问控制列表以及安全策略，都会影响写入结果。

检查时应静态核对容器实例的挂载源、目标路径、读写模式、宿主目录权限，以及容器实际运行用户；再结合启动日志判断是否出现配置缺失、权限拒绝或数据初始化失败。仅展示 OpenIM 固定两段源码，不能证明真实容器挂载了什么配置，也不能证明其对日志和数据目录具有写权限。

### 端口与网络：同一服务的可达性分叉

### 端口与网络：同一服务的可达性分叉

设两个 IM 网关容器都由镜像摘要 `D1` 创建，应用二进制、依赖和默认配置完全相同；“能否连接”仍可能截然不同。

- 容器 A 发布端口：`-p 8080:8080`，网关监听 `0.0.0.0:8080`。宿主机访问 `宿主机IP:8080` 可进入容器，反向代理也可将流量转发到该端口。
- 容器 B 未发布端口，或误配为 `-p 8081:8080`。即使容器内执行 `curl 127.0.0.1:8080` 成功，外部访问 `宿主机IP:8080` 仍会失败。
- 若进程仅监听 `127.0.0.1:8080`，端口发布规则也无法使其他容器或宿主网络正确访问；它只接受该容器网络命名空间内的回环流量。
- A 接入业务网络，能通过 DNS 名称解析并连接 Redis、消息队列和 OpenIM 服务；B 位于隔离网络、DNS 配置不同，或解析到错误地址，可能表现为“端口已通但登录、消息转发失败”。

检查应落到运行实例：查看端口发布、所属网络、容器 IP、DNS 解析结果与实际监听地址，例如核对 `ss -lntp`、容器网络配置及服务发现记录。源码中固定的 OpenIM 两段配置只能说明镜像或提交曾包含该逻辑，不能证明当前容器发布了正确端口、加入了正确网络，更不能证明依赖服务实际可达。

### cgroup限额与健康状态：资源条件塑造结果

### cgroup限额与健康状态：资源条件塑造结果

同一镜像摘要 `D1` 启动的程序代码相同，但容器并不共享相同的资源条件。`cgroup` 对 CPU、内存、进程数等施加的限制，会直接改变 OpenIM 网关处理连接、心跳、鉴权和消息转发时的可观测结果。

- **CPU 限额导致“能运行但变慢”**：例如容器仅获得 `0.2` 核 CPU，而高峰期需要处理大量 WebSocket 心跳、序列化和日志写入。进程不会立即退出，却可能出现请求排队、心跳超时、健康检查响应慢、客户端误判断线。另一实例若分配 `2` 核，即使镜像仍为 `D1`，延迟和在线稳定性也会不同。
- **内存上限导致“突然失败”**：设置 `memory=512MiB` 时，连接缓存、消息队列或 Go/Java 运行时堆增长可能触及上限。内核可触发 OOM kill，表现为主进程被杀死、容器退出码异常；设置更高内存上限的同镜像实例则可能持续正常服务。
- **重启策略掩盖一次性崩溃**：`restart: always` 或编排系统的自动重启会让容器在 OOM、配置读取失败或依赖连接失败后反复拉起。外部看到的不是“已停止”，而是“间歇可用、频繁断连”。应检查重启次数、最近退出码、OOM 标记及事件时间线。
- **健康检查决定流量是否进入**：健康检查可能执行 HTTP 探针、TCP 连接或命令检测。程序端口已监听不等于健康：若探针路径错误、启动宽限期过短、依赖服务尚未就绪，实例会被标为不健康并从负载均衡摘除。反之，过于宽松的 TCP 检查也可能把业务已卡死的实例误判为健康。

因此，`D1` 只能证明镜像起点一致，不能推出实际运行结果一致。静态检查应同时记录 CPU/内存/pids 限额、OOM 与退出状态、重启策略、健康检查命令与阈值，并将其与业务日志、请求延迟、连接断开和负载均衡摘除记录交叉验证。

### 静态核对清单：从S2现象走向S3证据

### 静态核对清单：从S2现象走向S3证据

S2 只能描述“某容器看起来异常或与预期不同”；要形成 S3 级证据，必须把镜像之外的运行条件逐项固定。相同摘要 `D1` 只证明镜像字节一致，不能证明同一份配置、同一挂载内容或同一资源约束。

按以下顺序静态核对：

1. **源提交**：记录 OpenIM 使用的仓库、分支、提交号与构建参数。确认构建 `D1` 的源码是否确为目标提交，而非本地未提交修改、不同子模块版本或缓存产物。
2. **镜像**：核对镜像摘要、入口命令、环境变量默认值、镜像内配置文件及暴露端口；标签如 `latest` 不能替代摘要。
3. **容器实例**：比较实际容器的 `command`、`entrypoint`、环境变量、用户、工作目录、重启策略与启动时间。两个容器都基于 `D1`，仍可能因启动参数不同而执行不同角色。
4. **挂载与权限**：核对 `volume`、绑定目录、配置映射、证书、日志目录及读写权限。宿主机上不同的 `config.yaml`、数据库地址或密钥文件会直接改变网关行为。
5. **网络与端口**：确认网络命名空间、服务发现地址、DNS、端口映射、防火墙及监听地址。容器内监听 `0.0.0.0:10001` 不等于宿主机端口已正确发布。
6. **cgroup 资源**：比较 CPU 配额、内存上限、`pids` 限制、文件描述符限制及 OOM 记录。限额不同可造成超时、频繁重启或长连接被动断开。
7. **健康与业务正反例**：同时保留健康检查成功/失败、端口连通/不通、登录成功/失败、消息收发成功/失败等对照；单条成功日志不能证明整条链路正常。

OpenIM 的两段固定源码至多说明“代码中存在某逻辑”或“理论上会读取某配置”。它们不能证明生产容器实际运行了该提交、加载了该文件、获得了该环境变量，或在当前网络与资源条件下执行到了该路径。静态核对应明确这些证据边界，避免以源码片段替代运行实例证据。

> **要点** — 摘要D1只能标识镜像内容；真实行为必须由容器实例配置、运行状态与后续权威证据共同确认。

从同一份镜像启动两个IM网关，为何它们的文件、网络、权限和退出行为仍可能完全不同？本节以故障恢复场景拆解容器运行时边界。

### 镜像摘要、容器与进程的三层身份

### 镜像摘要、容器与进程的三层身份

镜像、容器、进程不是同一个对象，应分别回答“代码从哪来”“运行实例是谁”“此刻谁在执行”。

- **镜像摘要 `D1`**：镜像内容的不可变标识，通常指镜像清单或内容摘要，如 `sha256:...`。它固定了应用二进制、基础系统文件、默认环境与镜像配置。若两个网关都来自 `D1`，只能说明它们的**镜像文件系统基线相同**。
- **容器实例**：运行时基于 `D1` 创建的具体实例。每个容器有独立的可写层、挂载卷、网络命名空间、环境变量、启动命令和资源限制。因此，同一 `D1` 可以启动容器 A、B，而 A 写入 `/tmp` 的文件通常不会出现在 B 中。
- **进程**：容器内实际执行的操作系统进程，例如 Go 网关主进程。容器并非轻量虚拟机；它本质上是被 `namespace` 隔离、被 `cgroup` 限制的一组进程。该组的首进程通常是 `PID 1`，其信号处理和子进程回收行为会直接影响退出与恢复。

可将关系记为：

`镜像 D1` → 创建 `容器 A / 容器 B` → 各自运行 `Go 进程`

因此，“两个实例都使用 `D1`”不能推出它们运行状态一致。容器 A 可能挂载生产卷、连接旧数据库、收到 `SIGTERM` 后优雅关闭；容器 B 则可能使用空卷、不同配置或因 `PID 1` 未转发信号而被强制终止。排障时应同时记录镜像摘要、容器配置与进程/日志证据，而不能只凭 `D1` 判断故障是否可复现。

### 只读层、可写层、卷与临时文件

### 只读层、可写层、卷与临时文件

镜像由多层只读文件系统组成：启动容器时，运行时在其上叠加一层容器专属的可写层。对镜像文件的“修改”实际写入可写层；删除下层文件通常只是写入白化标记。因此，同一镜像启动的两个 IM 网关，初始内容相同，但各自写入的日志、缓存和临时配置彼此不可见。

可写层的生命周期绑定容器：`docker rm`、重建或调度到新节点后，其中数据通常消失，且写入性能、容量和备份策略受运行时驱动影响，不能承担恢复依据。

应按数据语义选择位置：

- **镜像只读层**：程序、依赖、默认配置模板；发布即版本化，不写运行态数据。
- **容器可写层**：短暂调试文件、可丢弃缓存；不放会话、上传文件或关键日志。
- **volume**：跨容器重建保留的数据，如持久日志、SQLite 数据、上传附件；但高可用场景仍需外部存储、备份与一致性方案。
- **tmpfs**：仅驻留内存，容器停止或主机重启即消失；适合令牌解密后的短期材料、临时消息缓冲，避免落盘泄露。

IM 的在线会话状态若只在进程内或 `tmpfs`，属于 S2 内存状态，重启后必须允许重连与恢复；消息事实、设备确认记录等 S3 数据库状态应写入数据库，而非可写层。配置也应区分：默认值随镜像发布，环境差异通过挂载配置或环境变量注入；同一镜像因 volume 内容、挂载配置不同，运行行为可以完全不同。

### 隔离视图与资源边界：namespace和cgroup

### 隔离视图与资源边界：namespace和cgroup

容器不是“轻量虚拟机”，而是宿主机上的一组进程；其隔离主要来自 `namespace`，资源约束主要来自 `cgroup`。同一 `image` 启动的两个网关容器，代码和初始文件可相同，但运行视图与可用资源可以完全不同。

`namespace` 为进程提供彼此独立的“看到什么”：

- **PID namespace**：容器内通常只看到自己的进程树，应用主进程可见为 PID 1；它对信号处理、僵尸进程回收负有特殊责任。
- **network namespace**：每个容器可拥有独立网卡、IP、路由表、端口空间。两个容器都监听 `8080` 并不冲突；只有映射到同一宿主机端口时才会冲突。
- **mount namespace**：容器看到自己的挂载树。镜像只读层之上叠加各自的 writable layer；挂载的 `volume`、`tmpfs` 又可改变可见文件及其持久性。
- **user namespace**：容器内的用户 ID 可映射为宿主机上的非特权 ID，影响文件权限与越权边界。

`cgroup` 不改变“能看见什么”，而限制“最多能用多少”。常见约束包括 CPU 配额/权重、内存上限、进程数上限（`pids`）与块设备 I/O。网关在 CPU 被限流时，心跳、WebSocket 读写和 Shutdown 回调可能延迟；内存触顶时可能被 OOM kill，连接来不及优雅关闭；进程数耗尽时则无法创建工作线程或子进程。

因此，排查“同 D1、同镜像却行为不同”时，不能只比对镜像摘要，还应保存证据：容器启动参数、环境变量、挂载、网络模式、资源限制与事件记录。回退到旧镜像也未必恢复服务；若新旧实例的 `volume`、`tmpfs`、端口映射或 cgroup 配置不同，故障根因仍可能存在。

### PID1、停止信号与WebSocket排空

### PID1、停止信号与 WebSocket 排空

容器停止不是“杀掉一个进程”那么简单：运行时通常先向容器的 `PID 1` 发送 `SIGTERM`，等待宽限期；超时后再发送不可捕获、不可忽略的 `SIGKILL`。因此应用应尽量直接成为 `PID 1`，或确保启动脚本使用 `exec` 转交进程，避免 shell 吞掉信号、子进程未被回收。

Go 服务收到终止信号后，应立即进入“拒绝新流量、排空旧连接、到期强杀”的状态：

1. 停止健康检查或将就绪探针置为失败，使负载均衡不再分配新请求。
2. 调用 `http.Server.Shutdown(ctx)`，等待普通 HTTP 请求完成。
3. WebSocket 不会因 `Shutdown` 自动结束；必须自行维护连接集合，向客户端发送“服务维护/重连”消息或关闭帧，例如关闭码 `1001`，随后等待短暂排空。
4. 排空上下文必须小于编排平台的终止宽限期；若仍有连接未退出，主动关闭底层连接，避免最终由 `SIGKILL` 截断。
5. 记录收到信号时间、剩余连接数、关闭原因和超时连接，作为恢复与回退证据。

典型骨架是以 `signal.NotifyContext` 监听 `SIGTERM`、`SIGINT`，在 goroutine 中先摘流量，再依次执行 HTTP 关闭与 WebSocket 广播。注意：`SIGKILL` 没有处理机会；任何未刷新的内存状态都不应依赖退出钩子保存。会话状态、消息确认等关键事实应在运行期间写入外部存储，而不是寄望容器停止时补写。

### S2恢复核对：内存状态、权威数据与同D1差异

### S2恢复核对：内存状态、权威数据与同D1差异

S2故障后，首先要避免把“恢复了容器”误判为“恢复了会话”。容器重启通常只会重新创建进程与其内存：原先的在线会话表、WebSocket连接、未刷盘队列、限流计数和临时鉴权上下文都已丢失。它们属于易失内存状态，不是恢复依据。

应逐项判定权威来源：

| 对象 | 常见位置 | 是否权威 | 恢复含义 |
|---|---|---:|---|
| S2内存会话、连接映射 | 进程内存 | 否 | 允许丢失，客户端应重连 |
| S3用户、消息、会话版本 | 数据库/持久日志 | 是 | 以事务、版本号、提交时间为准 |
| 设备ACK | 设备侧或其持久回执记录 | 条件性权威 | 证明设备已收到，不等于S2仍保存连接 |

设备ACK回答的是“设备是否确认收到某消息”；S3记录回答的是“服务端权威状态是什么”；S2内存只回答“故障前该进程暂时记得什么”。若ACK已到但S3未提交，应优先检查投递协议与幂等键，不能仅凭内存日志补写数据库。

同一份D1镜像启动的S2实例仍可能不同：挂载的`volume`决定读取哪个配置或证书；`tmpfs`中的密钥、缓存会随重启消失；环境变量与权限决定能否访问数据库；网络命名空间、DNS、路由和安全组决定能否连到S3或设备网关。因此应采集证据：镜像摘要、容器启动参数、挂载列表、环境变量摘要、网络地址与路由、数据库连接结果、权限检查及关键日志时间线。

回退前先冻结写入或切换流量，确认目标版本兼容S3模式；恢复后以S3重建可派生状态，要求客户端重连，并按消息ID去重重投。若证据不足，应保持降级而非强行宣称会话连续。

> **要点** — 镜像只定义起点；容器配置决定运行边界，恢复必须以S3权威数据和设备ACK为证据。
