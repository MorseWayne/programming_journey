## 04.09 代理与负载均衡：逐跳追踪请求和超时

反向代理不是“透明管道”：请求经过 A→P→N1/N2 时，连接、TLS、确认与超时都必须按逐跳关系理解。

### 拆开 A→P→N 的两段连接

### 拆开 A→P→N 的两段连接

设客户端 A 请求服务，反向代理 P 将其转发到后端 N1。应把路径明确拆成两条独立连接：

`A ──连接①：TLS/HTTP──> P ──连接②：TLS/HTTP──> N1`

请求流与响应流也分别经过两跳：

`A 发请求 → P 收到并解析 → P 选择 N1、重建或转发上游请求 → N1 受理`  
`N1 产出响应 → P 收到上游响应 → P 转发或改写响应 → A 收到响应`

每一跳能观察到的事实不同：

- A 可确认自己是否连到 P、是否收到 P 返回的 HTTP 响应；A 收到 TCP ACK，只说明 P 所在连接栈确认了字节，不能说明 N1 已收到请求，更不能说明业务已提交数据。
- P 可记录连接①上的客户端地址、TLS 协商、请求头和请求体读取情况；也可独立记录连接②是否建立、何时向 N1 写入请求、何时读到响应首部。
- N1 的“请求已受理”是另一件事：它至少意味着请求到达 N1 的进程边界，不自动等价于数据库写入、消息持久化或异步任务完成。

若 P 终止客户端 TLS，则 TLS 会话终点是 A 与 P；P 若再以 TLS 访问 N1，会新建另一套握手、证书验证和加密上下文。因而“客户端已建立 HTTPS”不能推出“P 到 N1 也加密”。

排障日志应携带同一请求 ID，并分别标注 `A→P`、`P→N1`、`N1处理` 与 `N1→P→A` 的时间点。这样才能区分：请求未到 P、P 未连上 N1、N1 未及时响应，还是 P 已收到响应却未能交付给 A。

### TLS 终止与身份边界

### TLS 终止与身份边界

设客户端 A 与代理 P 建立 TLS 连接。TLS 在 P 终止意味着：P 持有该连接对应的证书与私钥，完成握手、验证（若配置了客户端证书）并解密 HTTP 或 WebSocket 字节流。因此，A 发出的请求到达 P 后，P 可以读取方法、路径、头部、Cookie、请求体和应用令牌，也可以改写、删除或新增头部后再转发。

但这只说明 A→P 被保护；它不自动说明 P→N1/N2 的安全性。代理转发时通常另建上游连接：

\[
A \xrightarrow{\text{TLS}_1} P \xrightarrow{\text{TLS}_2\text{ 或明文}} N_i
\]

是否启用 $\text{TLS}_2$ 是独立决策：

- **重新加密**：P 作为客户端连接 N1/N2，验证上游证书的名称、有效期和签发链；适合跨网段、不完全可信网络或需要端到端传输保密的场景。
- **不重新加密**：P→N1/N2 使用受控内网明文连接。此时不能宣称请求“端到端 TLS 加密”，只能说客户端到代理使用 TLS。
- **双向 TLS**：N1/N2 除了向 P 出示服务证书，还要求 P 出示客户端证书，以识别连接发起方的工作负载身份。

证书验证回答的是“**这条连接对端是谁**”：A 验证 P，P 验证 N1/N2；它不自动回答“此请求中的用户能否操作该资源”。后端仍应校验应用身份与授权，例如验证由 P 转发的用户令牌、会话成员关系、租户边界和操作权限。

尤其不要仅因请求来自 P 就默认用户已获授权。P 可以是可信身份传递者，但应明确约定哪些头部由 P 生成、哪些来自客户端且必须剥离或重建，例如 `X-Forwarded-For`、用户标识和权限声明。

### 代理如何选择后端并转发

### 代理如何选择后端并转发

P 接到 A 的请求后，先在**本跳**完成 TLS、HTTP 解析与基础校验，再依据路由规则选择上游：例如按 `Host`、路径、方法、租户、灰度标记或健康状态，将 `/api/orders` 发往 N1/N2 所在的服务池。选定后端后，P 以自己的上游连接发送新请求；这不是把 A→P 的 TCP 字节、确认或 TLS 会话原样“穿透”到 N1。

负载均衡策略主要决定**新请求**落到哪个可用后端：

- **轮询**：依次分配给 N1、N2，简单且适合实例能力相近的短请求。
- **加权轮询**：性能更高或容量更大的实例获得更多请求。
- **最少连接**：优先选择当前活跃上游连接较少的实例，适合请求耗时差异大、长连接较多的场景；但“连接少”不必然表示 CPU、队列或数据库压力低。
- **粘性策略**：按会话 Cookie、用户标识或一致性哈希让同一类请求尽量回到同一后端，可降低会话迁移成本；代价是流量可能不均衡，实例故障时仍须重新映射。

转发时，P 通常会重写或补充请求头：保留原始 `Host` 或改为上游期望的主机名，加入 `X-Forwarded-For`、`X-Forwarded-Proto` 或标准 `Forwarded` 来记录来源链路，并传播请求 ID、追踪上下文和剩余超时预算。后端不能盲信这些头：只有来自受信任代理的字段才可用于审计、限流或生成外部跳转链接。

P 还负责读取 N 的响应并转发给 A，必要时修改响应头、压缩策略或错误页。若 N1 返回 `503`，这是后端产生的响应；若 P 根本无法连上 N1，或等待上游超时后自行返回 `502`、`504`，则响应产生者是 P。

### 逐跳确认不能证明业务完成

### 逐跳确认不能证明业务完成

同一条“请求已成功”的说法，可能指完全不同的事实。设客户端为 A，代理为 P，后端为 N1：

| 观察到的信号 | 实际能证明什么 | 不能证明什么 |
|---|---|---|
| A 收到 P 的 TCP ACK | P 的 TCP 栈已收到 A 发出的字节 | P 已解析完整 HTTP 请求，更不代表 N1 收到请求 |
| P 收到 N1 的 TCP ACK | N1 的 TCP 栈已收到 P 发出的字节 | N1 的 HTTP 服务已受理、已执行业务逻辑 |
| P 成功写完上游请求 | P 已将请求字节交给本机内核，或在一定程度上交给上游连接 | N1 已完整读取请求；连接中断时仍可能结果未知 |
| N1 返回 HTTP `200` | N1 或其前方组件生成了成功响应 | 响应所代表的数据已在所有副本、消息队列或外部系统中持久化 |
| P 向 A 转发 `200` | P 已收到并开始/完成转发该响应 | A 已完整收到响应；A 断开时业务可能其实已经完成 |
| N1 写入数据库成功 | 该数据库写入点已确认持久化 | 后续发消息、扣库存、通知其他系统也已完成 |

尤其要区分两个方向的确认：A→P 的 ACK 属于客户端连接，P→N1 的 ACK 属于上游连接；它们不是同一个确认链。P 即使已经向 A 确认收到数据，也可能尚未选择后端、尚未建立上游连接，或因 N1 超时而最终返回 `504`。

超时会进一步制造“结果未知”状态。例如 P 已把请求转发给 N1，但在收到响应前上游超时：P 可以向 A 产生 `504`，却不能据此断言 N1 未执行。若该请求会创建订单、扣款或提交任务，A 直接重试可能造成重复执行。

因此，端到端业务确认应由应用协议明确表达：使用请求 ID、幂等键、可查询的任务状态，或由后端在必要的持久化与副作用完成后再返回成功。日志也应分别记录 `A→P` 接收、`P→N1` 转发、N1 受理、持久化完成及响应产生者，而不是用一次“已发送”替代完整事实链。

### 追踪 502、504 与超时来源

### 追踪 502、504 与超时来源

排查 `502 Bad Gateway`、`504 Gateway Timeout` 时，第一问题不是“服务是否报错”，而是：**哪一跳、哪个组件、在什么阶段生成了该响应**。同一个客户端请求至少应关联下列记录：

- 请求标识：入口生成的 `request_id`，并向上游透传；必要时另有 `trace_id`、`span_id`。
- 代理身份：代理实例、可用区、监听器与路由规则版本。
- 后端选择：目标池、被选中的 `N1/N2`、重试次数与每次尝试的结果。
- 分段耗时：`A→P` 接收时间、P 排队时间、连接上游时间、TLS 握手时间、首字节时间、响应传输时间。
- 响应产生者：`proxy`、`N1` 或其他网关；不要只记录最终状态码。

例如，P 记录：

`request_id=r7 proxy=P3 upstream=N1 connect=12ms first_byte=— timeout=2s status=504 responder=proxy`

这表示 P 已选中 N1，但在自己的上游等待预算内没有收到响应首字节，因此由 **P 生成 504**；它不能证明 N1 从未执行，也不能证明 N1 没有稍后写入数据库。

相反，若日志为：

`request_id=r7 proxy=P3 upstream=N1 upstream_status=502 status=502 responder=N1`

则是 N1 已经通过 `P→N1` 连接返回了 502，P 只是转发。客户端看到的状态码相同，修复责任却可能完全不同。

常见判读是：

- P 无法连接 N1、上游 TLS 验证失败、连接被提前关闭：通常由 P 生成 `502`。
- P 已连上 N1，但在读取响应前超过上游等待期限：通常由 P 生成 `504`。
- N1 自己的应用超时处理器返回 `504`：响应产生者是 N1，不应误称为“代理超时”。
- A 在等待 P 时断开：P 可能继续执行上游请求；这与 P 是否收到 N1 响应是两条独立事实。

因此，状态码之外还应记录“已连接上游”“是否写入请求体”“是否收到上游首字节”“客户端是否取消”等事件。只有把每一跳的观察结果按同一请求标识串起来，才能避免把 P 的超时误诊为 N1 必然失败。

> **要点** — 代理负责逐跳转发与分配；连接、TLS、超时和确认都只说明对应一跳，必须记录响应与失败的实际产生者。

代理转发不是透明管道：目标地址、Host、路径和来源头都可能被改写，安全关键在于逐跳厘清“谁能声明什么”。

### 画出逐跳连接与改写边界

### 画出逐跳连接与改写边界

先把一次“客户端访问后端”拆成两条独立连接，而不是想象成一条端到端的 HTTP 管道：

`客户端 A ──(连接 ①，TLS?)──> 代理 P ──(连接 ②，TLS?)──> 后端 N1 / N2`

A 与 P 协商的 TLS、证书、HTTP 版本和超时，只约束连接①；P 与 N1/N2 重新建连，连接②可使用另一套 TLS、证书、协议和超时。若 TLS 在 P 终止，N 并未直接看见 A 的 TLS 会话；它只能相信 P 转交的、且经过约束的请求信息。

P 通常可改写以下字段：

- 目标：根据负载均衡策略把请求送往 N1 或 N2，并通过 `SetURL` 设置上游 scheme、host、端口。
- `Host`：外部 `api.example` 可被改为内部服务名；后端不能据此断言原始访问域名。
- 路径与查询串：`/gateway/v1/send` 可能去掉前缀后转成 `/v1/send`。一处错误改写就可能把请求送到错误的版本或资源。
- 转发线索：P 可添加或覆盖 `Forwarded`、`X-Forwarded-For`、`X-Forwarded-Proto` 等头，描述它观察到的连接①信息。

因此，应在图上明确每个字段的“最后可信写入者”。外网进入 P 时，先清洗客户端自带的同名转发头；P 再按配置生成逐跳信息；N 仅接受来自已认证、受网络限制的 P 的连接。`X-Forwarded-For: 127.0.0.1` 只是未验证的文本，不能使 A 获得“本机请求”的含义，更不能替代对用户身份及 `doc-private` 权限的授权判断。

### 用 ReverseProxy 显式重写请求

### 用 ReverseProxy 显式重写请求

`httputil.ReverseProxy` 的 `Rewrite` 是把“入口请求”推导为“上游请求”的显式边界：不要假定它会按业务意图自动保留 URL、`Host` 或来源头。代理应先确定上游地址、路径合同和可传递的逐跳信息，再构造请求。

```go
proxy := &httputil.ReverseProxy{
    Rewrite: func(pr *httputil.ProxyRequest) {
        pr.SetURL(&url.URL{
            Scheme: "http",
            Host:   "send.internal:8080",
        })
        pr.Out.URL.Path = "/v2/send"
        pr.Out.URL.RawQuery = pr.In.URL.RawQuery
        pr.Out.Host = "send.internal"
        pr.SetXForwarded()
    },
}
```

这里有三个彼此独立的决策：

- `SetURL` 设置上游的 `Scheme`、`Host` 和请求目标；它还会默认把出站 `Host` 改为上游主机。若上游按虚拟主机路由，必须显式检查或设置 `pr.Out.Host`。
- `pr.Out.URL.Path` 决定实际调用的路径。入口 `/v1/send` 是否映射为 `/v2/send`，应是可测试的合同；漏掉前缀、重复拼接或错误版本都可能把请求送到另一项能力。
- `SetXForwarded` 依据当前连接信息补充 `X-Forwarded-For`、`X-Forwarded-Host`、`X-Forwarded-Proto`。它是“代理声明本跳观察结果”的工具，不是“相信客户端自称来源”的工具。

尤其要注意，外部客户端可以自行发送 `X-Forwarded-For: 127.0.0.1`。入口代理应按配置删除、覆盖或仅在受信上游链中保留这些头；后端也只能在确认直连者是受信代理、且每一跳都执行了清洗与追加规则后，才解释其含义。即使得到真实源 IP，也只能作为审计或风控线索，不能替代对用户身份、会话和 `doc-private` 权限的授权判断。

### 转发头的信任链而非字符串

### 转发头的信任链而非字符串

`Forwarded` 与 `X-Forwarded-For` 的价值是记录请求经过的代理链，而不是证明客户端身份。典型地，`X-Forwarded-For` 是逗号分隔的地址序列；每个受信代理在转发时追加自己观察到的上一跳地址。`Forwarded` 使用更结构化的参数，例如 `for=`, `by=`, `host=`, `proto=`，但安全前提相同：字段内容只有在写入它的那一跳可信时才有意义。

外部客户端可以直接发送：

`X-Forwarded-For: 127.0.0.1`

若入口代理原样保留该值，后端又把最左侧地址解释为“真实客户端”，攻击者便可能伪装成本机来源。把“地址字符串看起来像内网”当成授权条件，是信任边界错位。

职责应明确分层：

- **公网入口 P**：丢弃或覆盖来自外部的 `Forwarded`、`X-Forwarded-*`；按自身实际观察到的对端地址重新生成，或在受控规则下追加。
- **内部代理**：仅接受配置清单中的上游代理；转发时保护已有链，不能让普通客户端插入任意节点。
- **后端应用**：只在直接对端属于受信代理集合时解析转发头，并按配置从右向左剥离受信代理，得到可用的来源线索。
- **授权层**：使用登录身份、会话和资源权限判断访问权，而非用来源 IP 放行 `doc-private` 或 `c-a`。

Go 的 `ReverseProxy` 可通过 `Rewrite`、`SetURL`、`SetXForwarded` 写入转发信息，但这些接口不会替系统建立信任链。是否清洗入站头、哪些代理可信、后端如何验证，仍必须由部署拓扑和显式配置共同定义。

### 反例：伪造本机来源越权

### 反例：伪造本机来源越权

用户 `u-b` 直接向公网入口 P 发送请求，并自行附带：

`X-Forwarded-For: 127.0.0.1`

目标资源是仅允许内部维护者访问的 `doc-private`。若后端应用采用如下错误规则：

> 只要 `X-Forwarded-For` 显示为本机地址，就允许读取 `doc-private`。

那么 P 若原样转发该头，应用就会把 `u-b` 伪装成“来自本机”的请求，造成越权。问题不在于头的语法，而在于应用把**客户端可声明的数据**误当成了**可信代理证明**。

安全边界应分层处理：

- 公网入口 P 必须清洗外部请求携带的 `X-Forwarded-For`、`Forwarded` 等来源头；不能让客户端预先写入链路记录。
- P 仅在确认直接对端后，按部署配置重新生成或追加逐跳信息；后端只接受来自明确受信代理链的此类头。
- 后端即使可靠地得知真实源 IP，也只能将其作为网络线索，例如审计、限流或异常检测。

来源 IP 不能替代登录身份、会话验证和资源授权。确认请求确实来自 `u-b` 后，仍应依据其认证主体及权限策略判断：`u-b` 是否有读取 `doc-private` 的权限，或是否可操作 `c-a` 的资源。把“像本机”直接等同于“已授权”，本质上是把网络位置错误提升为身份与权限。

### 路径与 Host 改写的合同校验

### 路径与 Host 改写的合同校验

代理配置应被视为一份“转发合同”：外部请求的路径、查询参数、`Host`、协议及认证语义，经过每一跳后都必须仍符合后端接口约定。否则，请求虽然到达了服务，实际执行的却可能是另一项操作。

典型故障是外部 `POST /v1/send` 被路径前缀规则错误改写为后端的 `/v2/send`。若两个版本的字段含义、幂等键、权限范围或状态机不同，可能出现“客户端以为创建草稿，后端却提交发送”的合同破坏。对高风险路由，应显式校验：

- 代理规则：记录“入站路径 → 出站路径”的确定映射，避免宽泛的前缀替换。
- 后端路由：仅接受其声明支持的版本与方法；未知路径返回明确错误，而非回退到默认处理器。
- 认证上下文：令牌中的受众、权限和资源范围应与**最终路由**匹配，不能只因入口是 `/v1/send` 就沿用该判断。
- `Host`：后端若按 `Host` 选择租户、站点或回调域名，代理必须设置预期目标主机，且后端只接受配置中的可信主机名。

日志至少应同时记录原始请求目标、代理后的目标 URL、入站与出站 `Host`、路由名、认证主体和请求标识。例如：

`request_id=r1 in=/v1/send out=/v2/send host_in=api.example host_out=send-v2.internal route=submit principal=u-b`

部署前可用表驱动测试覆盖路径、`Host`、方法和认证组合；一旦映射发生变化，必须同时复核路由合同与授权策略，而不是只确认返回了 `200`。

> **要点** — 代理可改写请求，但只有经过清洗与验证的受信逐跳信息才可解释；IP 线索永远不能替代应用授权。

沿着 A→P→N1/N2 的请求路径，厘清负载均衡只能选择后端，不能替代状态复制、持久化与容量验证。

### 逐跳还原状态所在位置

### 逐跳还原状态所在位置

设客户端 A 经代理 P 发送消息 `m-1`：

1. A 与 P 之间存在一条客户端连接；P 将该请求选择性转发给 N1。
2. N1 在本进程中处理 `m-1`，并把结果写入自己的内存状态，例如消息列表、会话缓存或未落盘队列。
3. N1 返回 `200 accepted_in_memory`，其含义至多是“**N1 已接受并暂存于内存**”；它不表示 N2、P 或其他实例已经获得该状态。
4. P 将响应回传给 A。P 若未显式实现缓存、日志或复制，也只知道本次转发与响应，不拥有 N1 的业务内存。

随后 A 发起“查询历史消息”请求。即使它仍通过同一个 P，P 也可能按轮询等策略将请求转发给 N2：

\[
A \rightarrow P \rightarrow N2
\]

此时 N2 只拥有自己的进程内存。除非查询读取了真实存在的共享存储、复制日志或持久数据库，否则 N2 看不到 N1 中的 `m-1`，结果可能为空、过旧，或与刚才的写入不一致。

| 位置 | 可自然拥有的状态 | 不会自动拥有的状态 |
|---|---|---|
| A | 本地连接、已发送内容、界面缓存 | N1/N2 的服务端内存 |
| P | 连接与路由信息、可能的代理级缓存 | 后端实例的业务状态 |
| N1 | `m-1` 的本进程内存状态 | N2 的内存状态 |
| N2 | 本进程处理过的数据 | N1 中仅内存保存的 `m-1` |

粘性会话只能提高 A 再次被送往 N1 的概率，不能把 N1 的内存复制到 N2；N1 重启、失效或被摘除后，`m-1` 仍可能消失。轮询同样只是“下一跳选谁”的规则，不是状态传播协议。要改变这一边界，必须有已实现且可验证的共享或持久数据路径。

### 轮询为何不能复制状态

### 轮询为何不能复制状态

设客户端 A 先经代理 P 向后端 N1 发送消息 `m-1`：

`A → P → N1`

N1 将其仅写入本进程内存，并返回：

`200 accepted_in_memory`

这句话只说明 **N1 已在其当前内存空间中接受该消息**。它并不等价于：

- 已写入共享数据库；
- 已复制到 N2；
- 已持久化到磁盘；
- 已广播给所有后端；
- 即使 N1 重启也能恢复。

随后 A 发起历史查询。若 P 按轮询策略选择下一个后端，请求路径可能变为：

`A → P → N2`

轮询的输入通常只是“下一个可选后端是谁”。它至多维护代理侧的选择游标，例如：

`N1 → N2 → N1 → N2`

该游标不包含业务状态，更不会把 N1 的堆内存对象、会话缓存或消息列表搬运到 N2。于是 N2 只能查询自己可见的数据边界：自己的内存、已连接的共享存储，或明确实现的复制日志。若 `m-1` 只存在于 N1 内存，N2 的可见集合中就没有它，查询结果自然可能缺失。

可将这一点写成：

$$
m\in Memory(N1),\quad m\notin SharedStore,\quad m\notin Memory(N2)
$$

当请求被转发到 N2 时：

$$
Query(N2,m)=\varnothing
$$

即使采用粘性会话，使 A 暂时持续回到 N1，也只是提高“读到 N1 内存”的概率；它仍不是复制机制。N1 重启、失效、扩缩容迁移或粘性映射过期后，这份仅存于 N1 的状态仍可能消失。

因此，负载均衡解决的是“本次请求交给谁处理”，状态复制解决的是“多个节点能否看到同一份数据”。只有真实部署共享存储、持久化日志或复制协议后，N2 才可能读取 `m-1`；未来 S3 方案若获批并实现，才会改变这一数据边界。

### 粘性会话的短期收益与失效边界

### 粘性会话的短期收益与失效边界

轮询通常按请求依次选择后端：A 的一次历史查询可能到 N1，下一次则到 N2。若 `m-1` 仅存在 N1 的进程内存，N2 并不知道它；即使 N1 已返回 `200 accepted_in_memory`，该响应也只说明 N1 当前接受了数据，并不表示数据已复制。

粘性会话会尝试让同一客户端 A 在一段时间内继续命中同一实例。例如 A 先经 P 到达 N1，后续查询仍被路由到 N1，便可能直接读取 N1 的热内存状态。相较轮询，其短期收益是：

- 减少跨实例状态缺失造成的查询不一致；
- 提高本地缓存、会话上下文和长连接关联状态的命中率；
- 避免每次请求都重新装载或重建短生命周期状态。

但粘性只改变“本次优先选谁”，并未改变数据边界。N1 重启、崩溃、被摘除健康检查、扩缩容迁移，或粘性标识过期后，A 仍可能被送往 N2；此时 N1 的内存状态不可用，`m-1` 仍会丢失或不可见。更重要的是，粘性可能形成热会话集中：少数实例承载大量长连接、CPU 密集请求或下游数据库压力，而连接数较少的实例未必更健康。

因此，轮询适合无状态或状态已共享的请求分散；粘性适合把本地热状态当作性能优化。二者都不能替代共享存储、复制、持久化、故障切换和容量验证。只有未来 S3 共享/持久数据被真实实现后，实例切换时的状态可见性边界才会改变。

### 负载策略应均衡什么

### 负载策略应均衡什么

负载均衡首先要回答的不是“如何把请求平均分开”，而是“要均衡哪一种稀缺资源、隔离哪一种失败域”。不同策略观察到的信号不同，能解决的问题也不同：

- **轮询**：按顺序把新请求依次交给 N1、N2……适合实例规格接近、请求成本接近、处理时间短且状态可独立恢复的场景。它只负责选择后端；P 把后续查询发往 N2，并不会使 N2 获得 N1 内存中的 `m-1`。
- **最少连接**：优先选择当前活动连接数较少的实例，适合连接持续时间差异较大的服务。但两条 WebSocket 长连接未必只消耗“两份工作量”：一个连接可能持续空闲，另一个可能高频发送、占用 CPU、积压消息或触发下游查询。
- **加权策略**：根据实例 CPU、内存、配额、地域成本或实测吞吐设置权重，让性能更强的节点承担更多流量。权重应来自容量测试和运行数据，而不是仅凭机器规格推测。
- **健康状态选择**：避开不可达、错误率高或探测失败的节点，是可用性保护而非负载证明。某实例连接数少，可能是它刚重启、路由未命中，也可能是队列、CPU 或下游数据库已经异常。

因此，“连接数少”不等于“更空闲”，“轮询均匀”不等于“延迟均匀”。应先定义目标指标，例如并发连接、请求速率、CPU 时间、队列长度、数据库连接、尾延迟或错误率；再定义失败域，例如单进程、单机、单可用区或下游依赖。没有压测与观测数据时，任何策略都只是待验证的选择规则，而不是已证明的调度效果。

### 用实验验证调度与故障假设

### 用实验验证调度与故障假设

不要仅凭“轮询均匀”或“连接数较少”推断系统已均衡。应先写出可证伪的假设，再沿请求链路记录 `A → P → N1/N2 → 下游服务` 的证据。

- **建立逐跳观测**：为每次 HTTP 请求、WebSocket 建连、消息 `m-k` 生成关联标识；记录 P 选择的实例、连接建立与断开时间、消息处理耗时、实例队列长度、CPU、内存、错误码及下游 DB/服务延迟。日志应能回答：“A 的这条消息到了哪台实例，是否读到了预期状态，为何超时？”
- **区分连接与工作量**：分别压测短请求、少量高频 WebSocket、海量低频 WebSocket，以及单个 A 持续发送昂贵查询的热会话。比较轮询、最少连接、加权和健康检查策略下的 `p50/p95/p99` 延迟、队列深度、拒绝率与实例负载偏斜。两条长连接相同，并不意味着消息速率、查询成本或下游压力相同。
- **验证状态边界**：让 A 经 P 向 N1 写入仅存内存的 `m-1`，再使后续历史查询明确路由到 N2。预期 N2 无法自动读取 N1 的内存状态；若短暂粘回 N1 可以读取，也只能证明粘性路由生效，不能证明状态已复制。
- **注入故障**：在 A 保持连接或重连期间重启 N1、摘除 N1、使 N1 健康检查失败，并分别模拟 DB 变慢、连接耗尽和返回错误。观察 P 的摘流时间、在途请求结果、重试放大、A 的恢复行为，以及 N2 是否错误地被期待拥有 N1 的内存。
- **设定验收标准**：例如实例失效后新请求在规定时间内不再进入故障实例，关键请求在超时预算内失败或恢复，且无测试声称“状态仍在”却无法从持久或共享存储验证。

实验结果只能说明当前实现与当前负载下的行为；在真正实现并验证 S3 共享或持久数据前，不能把它当作故障恢复前提。

> **要点** — 负载均衡决定请求去向；只有真实共享或持久化的数据层，才能跨实例保留状态。

健康探测回答的是“此刻能否承接某类请求”，而非“用户操作是否已成功”。应先定义探测语义，再据此决定摘除、恢复与观测策略。

### 先定义“健康”对应的请求能力

### 先定义“健康”对应的请求能力

“健康”不是单一布尔值，而是实例对某类请求的承接能力。负载均衡器据此决定是否继续路由，因此探测语义必须比“进程还活着”更具体，又不能把一次完整用户操作误当作探测。

可将能力分层：

- **端口可达**：TCP 握手成功，只说明网络路径、监听套接字和进程基本存在；应用可能卡在初始化、线程池耗尽，或尚未取得成员资格。
- **HTTP 就绪**：如 `/ready` 返回 `200`，表示实例愿意接收预定义范围内的流量。应明确它覆盖哪些路由、是否允许只读请求、是否排除写入请求。
- **依赖可用**：实例能否访问数据库、认证服务、队列或配置中心。但“依赖可连”不等于权限、配额、事务状态和数据一致性都正确。
- **业务操作成功**：例如 B 已收到 `m-1`、写入已提交、授权已生效。这是特定请求的端到端结果，不能由端口或普通就绪探测推出。

因此，可让只读路由使用较浅的就绪条件，而写入路由额外要求主库可写、租约有效或成员已同步。不要让 `/ready` 为验证这些条件真的创建消息、扣减额度或写入状态；探测应使用无副作用的检查、隔离测试资源或只读验证。

记录时也应区分“探测失败导致摘除”和“用户请求失败”。前者说明路由决策的输入变化，后者才说明实际业务体验；两者混在一起会掩盖发布、过载或依赖故障的真实边界。

### 主动探测如何驱动摘除与恢复

### 主动探测如何驱动摘除与恢复

主动探测通常按间隔 $I$ 向实例发送检查；若单次响应超过超时 $T$，或返回不符合预期的结果，就记为一次失败。负载均衡器不会因一次偶发超时立刻摘除，而是维护连续失败计数：

- 连续失败达到阈值 $F$：实例从可选端点集中摘除，新请求不再路由到它；
- 摘除后继续探测，连续成功达到恢复阈值 $R$：实例重新加入端点集；
- 已在实例上的连接、长请求或重试是否终止，取决于代理的连接排空与重试策略，不能由“摘除”一词推断。

因此，最快摘除时间近似为 $F \times I + T$；最快恢复时间近似为 $R \times I$。例如每 $5$ 秒探测一次、超时 $1$ 秒、连续失败 $3$ 次，则故障实例可能仍接收约十余秒流量。若将 $F$ 设得过小，短暂 GC、网络抖动或依赖瞬断会造成流量来回切换；设得过大，则真实故障会持续暴露给用户。

恢复阈值通常应避免过于激进：实例刚能返回 `/ready`，不代表缓存已预热、连接池已重建或积压任务已消化。可用较低的失败阈值保护用户、较高的恢复阈值抑制抖动，并记录探测失败、摘除、恢复与真实用户请求结果。这样才能区分“探测判定不可接流量”与“业务操作实际失败”。

### 为不同路由匹配不同就绪条件

### 为不同路由匹配不同就绪条件

“就绪”不应是实例的单一布尔值，而应回答：**它现在能否安全承接这条路由的这类操作？** 可按任务风险拆分探测语义：

- **只读路由**：如查询状态、读取缓存，可用 TCP 连通性加轻量 HTTP `/ready/read`。检查进程、监听端口、必要的只读存储连接；不必因异步写入队列积压而摘除。
- **写入路由**：如创建订单、提交消息，应使用 `/ready/write`，确认身份凭据有效、主库或日志可写、幂等存储可用、剩余容量未越过保护阈值。不能只因端口可连就继续分发写请求。
- **成员授权或一致性路由**：如核验集群成员、领取分区、写入共识状态，应检查当前节点角色、租约或证书、授权数据版本及必要依赖；但不要在探测中实际申请锁、消费消息或写入状态。
- **降级可用路由**：若下游推荐、通知服务失效但核心读取仍可完成，可让 `/ready/read` 保持成功，同时使依赖该下游的路由返回不可就绪或走降级策略。

HTTP 探测应仅执行确定、快速、无副作用的判定，返回码表达路由承接能力；TCP 探测只适合作为“进程大致可达”的底线信号。将探测结果按路由类别记录，并与真实用户请求的成功率、延迟分开统计，才能避免把“探测通过”误读为“写入已成功”。

### 反例：200 就绪不等于消息已送达

### 反例：200 就绪不等于消息已送达

设负载均衡器把请求路由到实例 B，B 的 `/ready` 返回 `200`。这最多说明：按该就绪探测的定义，B 当前被允许接收某类流量。它不能推出用户消息 `m-1` 已经送达后端，更不能推出用户已经得到可靠确认。

一次“发送 `m-1`”至少可拆成不同状态：

1. **实例健康**：B 的进程、端口、基础依赖满足 `/ready` 的判定条件，因此探测得到 `200`。
2. **请求受理**：B 已收到客户端请求，完成鉴权、参数校验，并决定尝试处理 `m-1`。
3. **持久化完成**：B 已将 `m-1` 写入消息库、队列或下游服务，并获得该系统的成功响应。
4. **用户确认**：B 的成功响应已穿过代理、网络并被客户端收到；若响应丢失，客户端仍可能重试。

例如，B 在 `/ready` 中只检查“数据库连接池可取连接”，但处理 `m-1` 时需要成员授权服务和消息写入权限。此时端口可连、`/ready=200`，而授权超时或写入被拒绝，用户操作仍失败。反过来，B 的某个非关键下游只影响附件预览，不影响文本消息持久化；若探测把它纳入硬失败条件，可能无谓摘除本可处理 `m-1` 的实例。

因此，应把探测日志与业务结果分开记录：探测记录“B 是否可承接消息写入路由”，业务链路记录 `m-1` 的受理、写入结果、确认发送与客户端确认。只有持久化语义明确后，`200` 才能表示相应层次的成功。

### 发布与过载期间分离探测和用户结果

### 发布与过载期间分离探测和用户结果

健康探测日志回答“代理是否应继续路由”，用户请求指标回答“业务是否真的成功”；两者不能互相替代。发布、扩容或过载时，实例短暂启动、连接池预热、缓存未就绪都可能使探测失败，但用户请求尚未大量受损；反之，`/ready` 持续返回 `200`，也可能只有写入、成员校验或特定租户路由失败。

| 维度 | 健康探测 | 用户请求 |
|---|---|---|
| 触发者 | 代理或编排系统 | 真实客户端 |
| 目的 | 决定摘除、恢复、权重 | 衡量成功率、延迟、业务结果 |
| 标签 | 实例、探测类型、失败原因、状态迁移 | 路由、操作类型、状态码、错误码、租户/消息标识 |
| 告警含义 | 容量或可路由性风险 | 用户影响与 SLO 风险 |

实践上应分别记录：探测失败率、连续失败次数、摘除实例数、恢复次数，以及用户的 `$5xx$`、超时率、分位延迟和业务拒绝率。仪表盘中将“实例不健康”与“用户失败”并列展示，避免把发布期的预期重启误报为业务事故，也避免健康端点正常掩盖真实写入失败。

防抖应作用于状态迁移，而非伪造成功：连续 $N$ 次失败后摘除，连续 $M$ 次成功后恢复，并设置启动宽限期与最小摘除时长。过载时可让轻量探测验证监听端口和本地接入能力；若路由承接写请求，再使用只读、无副作用的就绪检查验证关键依赖。不要让“深度健康”发送消息、创建记录或更新成员状态，否则探测本身会污染链路并放大压力。

> **要点** — 健康是面向特定路由能力的判定；探测可摘除实例，却不能替代用户消息成功确认。

WebSocket 经代理并非一次请求的简单转发：先完成升级握手，再维持两段独立的长寿命字节流，必须逐跳观察其边界、资源与超时。

### 升级握手与逐跳连接边界

### 升级握手与逐跳连接边界

设客户端为 $C$、代理为 $P$、后端节点为 $N1$。在 HTTP/1.1 WebSocket 路径中，实际存在两条独立连接，而不是一条被“穿透”的 TCP 连接：

`C ⇄ P ⇄ N1`

升级前，$C \to P$ 是普通 HTTP 请求；$P$ 再向 $N1$ 发起另一条 HTTP 请求。客户端请求通常携带 `Upgrade: websocket` 与 `Connection: Upgrade`，后端若接受升级，返回状态码 `101` 及相应协商头。由于 `Upgrade` 是逐跳头部，$P$ 必须明确向上游转发升级意图；不能假设普通 HTTP 反向代理会自动完成这件事。

升级成功后，边界变为：

- $C \leftrightarrow P$：一段已升级的 WebSocket 字节流；
- $P \leftrightarrow N1$：另一段已升级的 WebSocket 字节流；
- $P$ 在中间读取、转发、缓冲或限速；两段连接的建立时间、拥塞状态、超时和关闭原因均可不同。

若 TLS 在 $P$ 终止，则客户端侧是 `wss://`：

`C == TLS/WebSocket ==> P == HTTP 或 TLS/WebSocket ==> N1`

此时 $P$ 能看到 HTTP 头、WebSocket 帧及应用数据；若 $P$ 到 $N1$ 也使用 TLS，则那是重新建立的独立 TLS 会话，不是客户端 TLS 的延续。证书校验、SNI、加密边界和观测日志也应分别归属两跳。

因此，看到“$P$ 已收到客户端消息”只能证明第一跳写入到达代理附近；看到“$P$ 向 $N1$ 写入成功”也未证明应用已处理。应分别记录升级结果、两跳连接标识、关闭码、超时触发点和字节方向，避免把代理存活、后端健康与用户会话状态混为一谈。

### 从 HTTP 转发到双向字节传输

### 从 HTTP 转发到双向字节传输

WebSocket 起点仍是 HTTP/1.1 请求，但 `Upgrade` 与 `Connection` 是**逐跳头**：它们描述的是“客户端—代理”这一跳是否请求切换协议，不能被当作普通端到端业务头原样穿过多个中间节点。

设客户端为 C、代理为 P、节点为 N1。过程可拆成两次独立协商：

1. C 向 P 发送 HTTP 请求，声明希望升级到 WebSocket。
2. P 验证并转发必要的升级语义，向 N1 发起自己的升级请求。
3. N1 返回成功响应后，P 才分别完成 C↔P 与 P↔N1 两段连接的协议切换。

因此，不能只看到 C 收到升级成功就认定 N1 已可通信；也不能仅把普通 HTTP 请求转发给上游，期待 WebSocket 自动建立。代理必须显式处理升级相关头，并在握手完成后改变转发模式。

升级成功前，P 处理的是有请求头、响应头和边界的 HTTP 交换；升级成功后，P 不再按“一问一答”的短请求模型工作，而是维持两条可长期存在的双向字节流：

\[
\text{C} \leftrightarrow \text{P} \leftrightarrow \text{N1}
\]

P 从客户端读到的数据要写往上游，从上游读到的数据也要写回客户端；两个方向都可能在任意时刻发送，且两侧读取、写入速率并不相同。于是 P 同时占有下游连接、上游连接、缓冲区和事件循环/工作线程等资源。

排障时应分别问：升级在哪一跳失败？C↔P 与 P↔N1 哪一段仍可读写？哪一侧先触发空闲或读超时？“请求已到代理”只说明字节进入 P，不等于 N1 已读取、更不等于业务已经处理。

### 长连接空闲超时的断线含义

### 长连接空闲超时的断线含义

WebSocket 升级成功后，代理 P 不再按“一个请求、一个响应”处理，而是维护两段独立连接：客户端 $C \leftrightarrow P$ 与 $P \leftrightarrow N1$。因此，“空闲超时”必须先问清楚：**哪一跳、哪个方向、由谁关闭**。

例如，P 发现上游 $P \leftrightarrow N1$ 在配置窗口内没有可读数据，便关闭该上游连接。此时可能发生：

1. P 向客户端发送关闭帧或直接断开，$C$ 感知 WebSocket 已断；
2. 客户端网络仍正常，用户页面也仍打开；
3. 用户的登录凭证、服务端会话、已提交消息并不会因此自动失效或撤销。

故障链应写成：

`上游空闲超时` → `P 关闭 P—N1` → `C 的 WebSocket 断线` → `客户端重连/恢复逻辑执行`

其中不能擅自补成：

`WebSocket 断线` → `用户登出`，或  
`WebSocket 断线` → `此前业务消息未生效/已撤销`。

消息是否生效取决于独立的应用确认点。`C 写入 P 成功` 只说明字节已被本地协议栈或代理接受；即使 P 已转发，也未必表示 N1 已解析、持久化或完成业务处理。反过来，断线前已被 N1 提交的消息，仍可能在客户端尚未来得及收到确认时生效。

排查时应同时记录关闭发起方、关闭时间、关闭码、两跳读写活动、心跳结果及业务确认标识。这样才能把“连接失活”限定为传输事件，而非误判为身份或业务状态变化。

### N1 重启、N2 健康与会话恢复

### N1 重启、N2 健康与会话恢复

设客户端经代理 `P` 建立了路径 `C—P—N1`。即使负载均衡器发现 `N1` 重启、健康检查转而选中 `N2`，它通常也只影响**后续新建连接或新请求**：

| 现象 | 能否由“`N2` 健康”自动保证 |
|---|---|
| 新客户端连接被分配到 `N2` | 可以，取决于健康检查与调度策略 |
| 旧的 `C—P—N1` WebSocket 无感切到 `C—P—N2` | 不可以 |
| 用户恢复原会话、未确认消息、订阅和房间状态 | 不可以，需应用协议支持 |

旧 WebSocket 的上游字节流终止于 `N1`；`N1` 进程退出、机器故障或其连接被关闭后，`P` 不能仅凭 `N2` 可用，就把已有 TCP/WebSocket 连接“接到”`N2`。TCP 状态、WebSocket 帧边界、认证上下文及 `N1` 内存中的会话状态都未必存在于 `N2`。

正确的恢复链路通常是：客户端发现断线或心跳超时 → 重连到 `P` → `P` 按当前策略选到 `N2` → 客户端携带身份、会话标识及最后确认的位置 → 应用决定恢复订阅、补发缺口或要求重新同步。这里“已连到 `N2`”只说明新传输路径建立，不等于此前业务消息已经处理，更不等于用户在线、已读状态已恢复。

因此排障时应分别记录：旧连接在哪一跳断开、新连接落到哪个节点，以及恢复协议从哪个应用确认点继续。不要把健康检查成功误读为连接迁移或会话恢复成功。

### 连接资源、慢消费者与确认观测

### 连接资源、慢消费者与确认观测

代理 `P` 终止或转发 WebSocket 时，应把客户端侧连接 `C↔P` 与上游侧连接 `P↔N1` 分别计数、限额和观测。一次业务会话通常占用两段文件描述符、读写缓冲区、定时器及可能的应用状态；因此“在线连接数”不能只看后端 `N1`，也不能只看代理入口。

重点监控以下边界：

- **连接资源**：当前连接数、建连/断连速率、连接年龄分布、拒绝连接数、每连接内存，以及按租户或用户的配额命中率。
- **空闲与心跳**：分别记录客户端方向和上游方向的最后读写时间、心跳发送数、心跳响应延迟、超时关闭原因。心跳超时只说明某段路径在窗口内未获响应，不足以证明用户已登出、未在线或未读消息。
- **慢消费者积压**：代理向客户端、向上游的待发送字节数和消息数，写阻塞持续时间、缓冲区占用、因积压丢弃或断开的连接数。缓冲增长意味着接收端或网络慢；若不设上限，少量慢连接即可耗尽内存。
- **逐级确认**：`客户端写入 P 成功` 仅表示字节进入客户端到代理这一段；`P 写入 N1 成功` 仍不等于 `N1 已处理`；只有业务确认，例如“消息已持久化”或“已投递”，才对应业务语义。

可将一条消息的时间线记为：

`客户端发送 → P 接收 → P 转发 → N1 处理 → 业务确认返回`

分别测量各阶段耗时与失败数。这样，当客户端断线或确认迟到时，才能区分是代理超时清理、上游拥塞、后端处理慢，还是业务确认链路缺失，而不会把连接存活误判为业务完成。

> **要点** — WebSocket 经过代理后仍是两段独立长连接；断线、健康、在线与业务确认必须逐跳观测，不能互相推断。

以1000毫秒纸上预算逐跳拆解请求，识别单次尝试、整体截止时间与写操作未知结果之间的风险边界。

### 先画逐跳链路与时间账本

### 先画逐跳链路与时间账本

先把一次请求画成可计时的链路，而不是只盯着代理返回的状态码：

`客户端 → 名称解析/建连/TLS → 代理 P 入站与排队 → 上游 N1（或 N2）→ P 回传 → 客户端校验`

设用户可感知的总预算为 **1000 ms**，可先做一份纯加法的纸上账本：

| 阶段 | 预算 | 可能包含 |
|---|---:|---|
| 到达代理前 | 100 ms | 名称解析、TCP 建连、TLS 握手、客户端排队 |
| 上游处理 | 700 ms | P 选点、连接上游、N1/N2 排队与业务执行、响应首字节 |
| 回传与校验 | 200 ms | P 转发响应、网络回程、客户端解析与校验 |
| 合计 | 1000 ms | 用户请求的整体截止时间 |

这里的 `700 ms` 不是建议配置，更不是实测结论；它只是提醒我们：上游可用时间必须从总账本中扣除其他逐跳成本。P 即使“刚把请求发给 N1”，也可能已经消耗了入站排队、连接复用检查或取消传播所需的时间。

尤其要区分两类计时器：

- **每次尝试超时**：某次 P→N1 或 P→N2 上游尝试最多可等多久。
- **整个请求超时**：从客户端发起到最终得到响应或失败，所有排队、尝试、重试和回传合计最多多久。

若整体仍是 `1000 ms`，但 P 允许两次串行上游尝试、每次均可耗满 `700 ms`，则仅上游等待就可能达到 `1400 ms`；再加其他开销，必然穿透用户预算。因此，画图时应给每一跳标注开始时间、截止时间和取消点，并明确：第二次尝试只能使用**剩余**时间，而不能重新获得完整的 `700 ms`。

### 区分单次超时和整体截止时间

### 区分单次超时和整体截止时间

先把 `1000 ms` 当作一次纸上加法预算：名称解析、TLS、代理入站等已用 `100 ms`；上游处理计划最多 `700 ms`；响应传回、取消传播与校验预留 `200 ms`。

关键在于：`700 ms` 若只是“**单次尝试**的上游超时”，并不等于“**整个用户请求**必须在 1000 ms 内结束”。

设代理 P 对上游请求允许两次串行尝试：

- 第一次发往 N1，单次超时为 `700 ms`；
- N1 未在期限内返回，P 再发往 N2；
- 第二次同样允许 `700 ms`。

即使忽略重试调度、连接建立、排队和取消传播，时间也已是：

$$100 + 700 + 700 = 1500\text{ ms}$$

再加上原本预留的返回与校验 `200 ms`，总路径可能接近：

$$100 + 700 + 700 + 200 = 1700\text{ ms}$$

因此，逐次超时只限制“某一次调用最多等多久”；整体截止时间才限制“这个用户请求从进入系统到必须结束，最多活多久”。

应同时审查两类约束：

- **每次尝试超时**：限制单个上游实例拖慢代理的时间。
- **整体请求截止时间**：覆盖排队、所有尝试、重试间隔、取消传播以及响应回传。

整体剩余时间不足以再容纳一次尝试时，代理应停止重试，而不是重新给予完整的 `700 ms`。尤其对写消息，超时后的 `504` 表示结果未知：N1 可能已受理，不能因“未收到响应”就把它视为未执行。

### 把排队、取消与回传纳入预算

### 把排队、取消与回传纳入预算

设总预算为 $1000\text{ ms}$，前置名称解析、TLS、代理入站已消耗 $100\text{ ms}$；即使纸面上为上游处理预留 $700\text{ ms}$、回传与校验预留 $200\text{ ms}$，也不能把这 $700\text{ ms}$ 全部解释为“业务代码可运行时间”。

代理向上游发起一次尝试前，常先经历连接池等待、负载均衡选点、排队、建连或复用连接。上游响应后，还要有响应头传回、响应体传输、代理缓冲、客户端接收与状态校验。取消同样不是零成本：P 到期后发出取消，不代表 N1 立刻停止；取消信号可能排队、在网络中传播，或到达时写操作已经提交。

可将一次尝试粗略拆成：

$$
T_{\text{尝试}}=
T_{\text{排队}}+
T_{\text{连接}}+
T_{\text{上游}}+
T_{\text{回传}}+
T_{\text{校验/取消}}
$$

因此，若“单次上游超时”设为 $700\text{ ms}$，而整体请求截止时间也是或接近 $1000\text{ ms}$，剩余空间可能不足以完成回传；客户端看到的 504 仍可能对应上游已受理或已写入。更稳妥的审查方式是同时标出：

- **整体截止时间**：从请求进入 P 起统一倒计时，覆盖排队、全部尝试和回传。
- **单次尝试超时**：必须小于整体剩余时间，并为取消与响应传输留余量。
- **排队上限**：队列等待不应悄悄吞掉后续处理时间。
- **取消后的语义**：取消只表示“不再等待”，不证明写操作未发生。

对 S2 写消息，预算耗尽后的 504 应记录为“结果未知”；在没有权威结果查询或持久去重前，不能因代理超时而安全重试。

### 504后的写消息为何不可盲重试

### 504后的写消息为何不可盲重试

设客户端经代理 P 向实例 N1 发送写消息 `message_id=m-42`。N1 已返回或即将返回 `accepted_in_memory`，表示它已在内存中受理并可能继续异步落库、投递；但 P 的本次尝试计时器先到期，未收到响应便向客户端返回 **504**。

此时 504 的含义是：**P 未在截止时间内确认结果**，而不是“N1 一定没有执行”。后续至少存在三种状态：

- N1 尚未真正处理，写操作可能未发生；
- N1 已受理，正在处理，结果稍后可见；
- N1 已完成写入，但响应在网络链路、排队或取消过程中丢失。

因此，P 自动将同一消息转发至 N2，会让 N2 也可能受理 `m-42`。若去重仅存在于各实例内存而非共享持久层，就可能形成两份写入、两次投递或两次扣费。

重发到 N1 也不能消除不确定性：若 N1 发现同一 `message_id` 已受理并返回 **409**，这只证明“当前请求与已有记录冲突”，并不能证明前一次操作已成功完成、其业务结果正确，或客户端可将其视为本次成功。

安全边界应是：

1. 将 504 记录为“结果未知”，保留 `message_id`、尝试次数和路由实例；
2. 不对当前 S2 写消息进行透明跨实例重试；
3. 只有具备权威操作结果查询，或持久化、可验证的去重与结果复用机制后，才讨论有界重试；
4. 同时审查每次尝试超时与整个请求截止时间，避免两次各耗尽 `700 ms`，突破 `1000 ms` 总预算。

### 按操作语义设计有界重试

### 按操作语义设计有界重试

重试不是“超时后再发一次”，而是依据操作语义、剩余截止时间与可验证结果决定是否允许继续。

- **可验证幂等的只读请求**：例如查询状态、读取配置。若请求带有整体截止时间，且首次失败后仍有足够余量，可允许有限次数重试。每次尝试都应受独立的单次超时约束，同时不得越过请求整体截止时间；还要把排队、连接、取消传播和响应返回时间计入预算。
- **当前 S2 写消息**：不能仅凭 `message_id` 相同就默认可安全重试。N1 可能已经返回或处于 `accepted_in_memory`，但响应在到达 P 前超时；P 向客户端返回 `504` 时，含义是**结果未知**，不是“该写入必定没有执行”。

设总预算为 `1000 ms`，前置链路已消耗 `100 ms`，上游及回传还需共享余量。即使单次上游尝试限制为 `700 ms`，两次串行尝试也可能消耗 `1400 ms`，更不用说代理排队、建连、取消和回传开销。因此应同时配置：

1. **每次尝试截止时间**：限制单个上游实例占用；
2. **整个请求截止时间**：限制所有尝试、排队与返回的总和；
3. **最大尝试次数**：避免在剩余时间不足时机械重发；
4. **取消传播**：整体请求结束后，停止仍在执行或排队的后续尝试。

对写操作，安全边界还依赖服务端能力。重试前应优先执行权威的操作结果查询，例如按稳定操作标识查询“已提交、处理中、未找到、失败”。同时，接收端需要以持久化去重记录绑定 `message_id` 与操作结果，而非仅用内存状态。否则 P 将同一消息改发至 N2，N2 可能再次受理；重发 N1 得到 `409` 也只能说明该实例观察到重复，不能证明本次操作已安全完成。

> **要点** — 总截止时间约束所有尝试；504表示结果未知，未具备权威查询与持久去重前不得自动重试写操作。

以逐跳视角理解 Go 反向代理：标准库解决转发机制，可靠多实例仍取决于边界、状态与可观测性设计。

### 逐跳连接与代理职责边界

### 逐跳连接与代理职责边界

一次经代理的请求不是一条“端到端连接”，而是至少两跳独立链路：

`客户端 A ──连接①──> 代理 P ──连接②──> 后端 N1/N2`

P 接受 A 的请求后，按路由、健康状态或负载策略选择 N1 或 N2；随后使用自己的上游连接向被选后端发起请求。连接①与连接②的建立、复用、超时、TLS 状态和失败原因都应分别记录，不能把“客户端已连到 P”误当成“请求已到达 N”。

若 TLS 在 P 终止，则：

`A --HTTPS--> P --HTTP 或 HTTPS--> N`

P 能读取并改写 HTTP 头、路径及必要的转发信息，也因此承担保护私有正文、校验身份边界、限制请求体和防止伪造转发头的责任。若 P 到 N 仍使用 HTTPS，还必须独立验证上游证书；客户端侧 TLS 成功不证明上游 TLS 成功。

`ReverseProxy` 提供转发、改写请求、选择 `Transport`、修改响应和错误处理的机制；`http.Transport` 则负责上游连接池、空闲连接复用及握手等。它们不替应用决定哪些后端可被访问、何时可重试，或某个写操作是否安全重放。

响应责任也要逐层区分：N 正常返回时，P 是转发者；P 无法连接 N、收到无效上游响应或自身超时时，P 可能是 502、503、504 的产生者。此时状态码仅说明该跳失败，不能证明 IM 写操作在 N “一定未执行”。排障应关联外部请求 ID、P 选中的后端、两跳连接阶段、TLS/升级结果、逐跳超时、重试次数，以及后端业务确认点。

### ReverseProxy 与 Transport 的机制边界

### ReverseProxy 与 Transport 的机制边界

`httputil.ReverseProxy` 是“把一跳 HTTP 请求转到另一跳”的机制，不是多实例架构开关。其典型处理链为：

1. 接收下游请求；
2. 通过 `Rewrite`（或旧式 `Director`）改写目标 `URL`、`Host`、路径与查询参数；
3. 由 `Transport` 向选定上游发起请求；
4. 可用 `ModifyResponse` 检查或改写上游响应；
5. 上游拨号、TLS、读写或响应处理失败时，交给 `ErrorHandler` 产生错误响应。

目标选择可以来自固定地址、服务发现或负载均衡器 `P`，但应用必须限制可代理的主机、端口和路径；绝不能把客户端给出的地址直接当上游目标。转发头如 `Forwarded`、`X-Forwarded-For`、`X-Forwarded-Proto` 也应只在可信边界补写或覆盖，而非盲目信任下游传入值。

`http.Transport` 则负责上游连接生命周期：DNS、拨号、TLS 握手、HTTP/1.1 keep-alive、HTTP/2 连接与空闲连接池复用。共享并复用同一个已配置 `Transport`，通常才能避免每个请求重新建连；但连接复用不等于请求可安全重试，更不等于 IM 写操作幂等。

因此应把职责分开：`ReverseProxy` 决定“如何转发和处理代理结果”，`Transport` 决定“如何建立与复用上游连接”，业务层仍须决定“谁可访问、可转到哪里、正文多大、何时超时、何时重试，以及后端何时真正确认写入”。

### 转发头信任与安全转发策略

### 转发头信任与安全转发策略

`Forwarded`、`X-Forwarded-For`、`X-Forwarded-Proto`、`X-Forwarded-Host` 不是天然可信的身份事实：客户端可以自行构造它们。代理若直接把入站头原样交给后端，攻击者可能伪造来源地址、协议或主机名，绕过仅允许内网、仅 HTTPS、按 IP 限流等策略。

安全策略应先定义信任边界：

- **边缘代理**：删除客户端携带的转发头，再写入自己观察到的客户端地址、协议和主机信息。
- **内部代理**：仅当直接对端 IP、mTLS 身份或受控网络证明其是可信代理时，才解析并追加既有链路；否则视为客户端输入并覆盖。
- **后端服务**：只接受来自指定代理网段或已认证代理的请求；业务身份应来自签名令牌、会话或服务间认证，不能仅凭 `X-Forwarded-For` 授权。

在 Go 中，`httputil.ReverseProxy` 的改写逻辑应明确设置目标地址与允许的路径、方法、主机范围，避免请求借代理访问任意内网地址，即 SSRF。还应限制请求体大小、上传时长和可升级协议；IM 的 WebSocket 升级只允许预期路径，并验证用户身份与会话权限。

转发时记录“谁写入了哪个转发头”，但普通日志只保留请求 ID、选定后端、脱敏后的客户端标识和结果。消息正文、令牌、Cookie 及完整私有头不应进入日志。代理负责安全地传递上下文；认证、授权、幂等与业务确认仍必须由后端明确执行。

### 状态、健康检查与长连接误区

### 状态、健康检查与长连接误区

轮询、粘性会话与进程内存解决的是不同问题，不能互相替代：

| 机制 | 解决的问题 | 不能证明什么 |
|---|---|---|
| 轮询 | 将新请求分散到多个健康后端 | 同一用户后续仍会到同一实例 |
| 粘性会话 | 让某客户端尽量持续命中同一后端 | 后端重启、扩容或故障后状态仍存在 |
| S2 进程内存 | 单个实例内保存连接、会话或待确认消息 | 多实例共享状态、故障恢复与全局一致性 |

健康检查成功通常只表示探测请求得到了预期响应，例如 `/healthz` 返回 `200`。它不等于 WebSocket 仍可收发：代理与后端之间、客户端与代理之间的任一连接都可能已断开；更不等于后端已经把某条 IM 消息写入数据库、投递队列或确认给目标用户。

长连接尤其容易放大误判。负载均衡器在升级 WebSocket 后，连接通常固定落在已选后端；轮询只影响新的连接。若 S2 把用户在线表、房间成员或未确认消息仅存进程内存，则一次重新连接、实例漂移或滚动发布都可能暴露状态缺口。粘性会话只能降低漂移概率，不能成为状态存储方案。

排障时应分别记录：探测结果、连接升级结果、连接关闭方与原因、P 选定的后端、后端业务确认点。看到 `502`、`503` 或 `504`，只能先说明某层转发失败或超时；必须继续确认消息是否到达后端、是否持久化、是否已投递，才能判断是否需要安全重试。

### 超时预算、5xx 归因与追踪字段

### 超时预算、5xx 归因与追踪字段

代理不能只设置一个“请求超时”。应先给客户端请求分配总预算，例如 $T=5\text{s}$，再拆分为：入口读取、鉴权与路由、连接上游、TLS 握手、等待首字节、响应传输及必要重试。各阶段之和必须小于总预算，并留出取消、记录日志和向客户端返回错误的余量。上游 `http.Transport` 的连接、握手、首响应字节等超时，应与代理的 `Context` 截止时间一致；客户端已取消时，代理也必须取消上游请求。

重试会消耗预算，且不能默认安全。仅对幂等请求，或具有幂等键且尚无“后端业务确认”的写请求，才可在明确条件下重试。不要因连接断开就断言消息未写入：后端可能已持久化，只是确认响应未能返回。

看到 5xx 时，先确定**响应产生层**：

- `502`：代理收到了无效上游响应，例如协议损坏、错误的升级握手；不等于业务未执行。
- `503`：某层明确表示暂不可服务，例如无健康后端、限流或维护；检查是负载均衡器还是后端生成。
- `504`：代理等待上游超时；它只能证明代理未在预算内获得可用响应，不能证明后端没有继续执行。
- 后端自行返回的 `5xx` 应保留其来源标记，不能统称为“代理故障”。

每次请求至少关联外部请求 ID、代理选中的后端、下游与上游连接阶段、TLS/协议升级结果、各逐跳截止时间、重试次数和原因、最终响应产生者，以及后端业务确认点（如“消息已提交并获得消息 ID”）。正文、令牌和私有消息内容不进入普通日志；排障应依赖结构化字段、指标与追踪，而非复制用户数据。

> **要点** — 代理库提供转发能力；安全、状态一致性、超时重试和故障归因必须由应用逐跳设计与验证。

以虚构链路 A→P→N1/N2 为唯一场景，逐跳识别连接、信任、状态与超时，避免把代理能力误当作业务保证。

### 逐跳画出请求、响应与 TLS 边界

### 逐跳画出请求、响应与 TLS 边界

只讨论虚构链路：客户端 **A** 经代理 **P** 访问后端实例 **N1/N2**。首先把它拆成两条独立连接，而不是一条“穿透”全链路：

`A ──连接①──> P ──连接②──> N1 或 N2`

P 按配置、健康状态或负载策略选择 N1/N2；它转发请求与响应，但不会因此同步实例内存、持久化业务数据，或替代应用层授权。

- **连接①：A ↔ P**
  - 若使用 TLS，通常在 P 终止：A 验证 P 的证书，P 负责这一段握手、加密、空闲超时、读写超时与客户端身份材料的处理。
  - A 收到的传输层 ACK，只表示数据到达该段对端协议栈；不等于 N1/N2 已执行业务，更不等于设备或即时通信应用已确认。

- **连接②：P ↔ N1/N2**
  - P 另行建立或复用到被选实例的连接，并独立承担上游连接、上游响应和上游超时。
  - 若要求端到端均加密，应定义“P 终止后再加密”：P 验证 N1/N2 的证书，N1/N2 也可验证 P 的客户端证书。前一段 TLS 的信任不会自动延伸到后一段。

响应方向同样逐跳返回：

`N1/N2 ──响应②──> P ──响应①──> A`

因此，A 看到 `200` 至多说明 P 已在连接①返回成功；还必须明确该状态对应的是 P 已收到上游响应、N1/N2 已受理，还是业务已持久化。每一跳都应分别记录请求标识、选中的实例、TLS 验证结果、连接事件与超时原因，才能定位失败发生在入口、代理还是上游。

### 代理转发不等于身份与头部可信

### 代理转发不等于身份与头部可信

在虚构链路 `A → P → N1/N2` 中，P 的基本职责是按配置选择一个上游、建立或复用到该上游的连接，并转发请求与响应。即使 P 记录了客户端地址、补充了 `Forwarded` 或 `X-Forwarded-For`，这些头部也只是**请求路径信息**，不能自动推出“这是谁”或“允许做什么”。

设 A 到 P 的实际对端地址为 `ip_A`。若 P 直接把 A 传来的头部原样交给 N1/N2：

`A: X-Forwarded-For: 203.0.113.9`

则 A 可以伪造任意来源。此时 N1 看到的值不具备可信性；它至多是客户端声称的值，而非 P 观测到的网络事实。

更稳妥的推演是：

1. P 仅从其**实际入站连接**取得对端地址 `ip_A`。
2. P 对不受信任客户端提交的 `Forwarded`、`X-Forwarded-For` 进行删除或覆盖。
3. P 按明确规则重建头部，例如添加 `Forwarded: for=ip_A;proto=https`，再转发给所选的 N1 或 N2。
4. N1/N2 只在“请求确实来自受信任 P 网络身份”的条件下，才把这些头部当作 P 提供的路径证据。

即便如此，`ip_A` 仍不等于用户身份。地址可能对应 NAT、企业出口、共享设备或另一层代理；它不能替代登录会话、令牌签名或客户端证书。更不能由“请求来自某 IP”直接得出“该用户有写入权限”。

可将三类结论分开：

- **来源地址**：P 在当前一跳观测到的网络对端，或 P 重建后传递的链路信息。
- **用户身份**：应用依据凭证验证得到的主体，例如令牌中的用户标识。
- **授权结论**：N1/N2 依据已验证身份、目标资源和权限策略作出的允许或拒绝决定。

因此，P 选择 N1 还是 N2，不会使地址头变成身份，也不会替业务服务完成授权。只有清晰定义“谁可以写入这些头部、N1/N2 信任哪些代理、身份如何验证”，逐跳转发才不会变成可伪造的信任链。

### 轮询、粘性与 N1/N2 的状态分裂

### 轮询、粘性与 N1/N2 的状态分裂

在虚构链路 `A → P → N1/N2` 中，`P` 的负载均衡策略只决定**本次请求被转发给哪个上游实例**；它不负责同步 N1、N2 的进程内存，更不会自动把一次 `200` 变成可恢复、可查询的业务持久化结果。

- **轮询**：P 依次把请求分给 N1、N2。若 A 的第一次请求到 N1，第二次请求可能到 N2。若 S2 仅保存在 N1 内存，N2 对该状态天然未知。
- **粘性会话**：P 尽量让同一会话持续到同一实例，例如持续转给 N1。这能降低“后续请求落到另一实例”的概率，却仍只是选路规则，不是状态复制协议。
- **故障切换**：N1 不可用、连接断开、健康检查失败或粘性标识失效时，P 可能将 A 转发至 N2。此时即使 A 先前获得过 N1 返回的 `200`，也只能说明 N1 当时已受理其本进程内的 S2；不能推出 N2 也拥有该状态。

因此，以下推理不成立：

> “A 收到 S2 的 200，随后 P 改发 N2；N2 应当知道 S2。”

若 S2 没有写入共享数据库、复制状态服务或其他权威持久化系统，N1/N2 可能形成状态分裂：N1 认为已受理，N2 认为从未见过。轮询会暴露这一差异；粘性会话只能暂时掩盖它，不能消除它。

对需要跨实例恢复的操作，应将权威状态放在进程外，并用操作标识、幂等键或可查询结果判断“是否已完成”。不要把负载均衡粘性当作存储保证，也不要因一次 `200` 就假定故障切换后状态仍然存在。

### 健康探测与 WebSocket 的两类证据

### 健康探测与 WebSocket 的两类证据

在虚构链路 `A → P → N1/N2` 中，P 的健康探测回答的是“某个节点是否适合被继续选作上游”，不是“用户消息是否已被业务成功处理”。

- **健康探测证据**：P 按配置向 N1、N2 发起探测，例如请求 `/health` 并收到 `200`。这通常只能证明该节点在该探测路径、该时刻能够响应；其范围取决于探测内容。若探测只检查进程存活，则不能推出数据库可写、消息已持久化、权限校验正确或所有业务接口正常。
- **应用确认**：A 发出一条用户消息后，N1 返回的应用级确认才可表示该消息已被 N1 按定义受理。即便如此，`200` 的语义仍必须明确：它可能仅代表“写入 N1 本进程内存”，不必然代表已持久化、已复制到 N2，或已被目标设备确认。
- **WebSocket 连接证据**：A 与 P、P 与 N1 是两段独立的长寿命双向连接。P 选择 N1 后不会退出路径；它仍持续占用逐跳连接、文件描述符、缓冲区和并发配额。A 到 P 连通，不等于 P 到 N1 仍连通。

对 WebSocket，应分别观测三类信号：

1. **空闲时间**：连接长期无业务帧，可能被 P、上游、网络设备或 N1 的空闲策略关闭；“没有报错”不能证明连接仍可用。  
2. **心跳结果**：心跳应定义发送方、接收方、确认期限及失败后的关闭/重连动作。传输层 ACK 只说明字节被对端协议栈接收，不等于应用心跳已处理。  
3. **资源指标**：分别记录 P→N1、P→N2 的活跃连接数、空闲连接数、心跳超时、关闭码、重连次数及上游连接耗尽情况。

因此，N1 健康探测为 `200` 而某条 WebSocket 消息超时并不矛盾：前者是探测条件下的节点可达证据，后者需要沿 A、P、N1 各跳的连接状态、心跳和应用确认记录继续定位。

### 从 504 到重试的超时证据决策

### 从 504 到重试的超时证据决策

在虚构链路 `A→P→N1/N2` 中，超时不是“请求必然失败”的证据，而是某一跳在期限内未获得所需响应。尤其是 A 收到 `504` 时，只能确认：P 未能及时向 A 返回成功结果；不能推出 N1/N2 未执行，也不能推出写入一定未发生。

先分配总预算。若 A 的端到端等待上限为 $T_A$，则 P 的上游等待时间必须小于它，并为入口排队、转发、回传和 A 的核验保留余量：

$$T_{\text{connect}}+T_{\text{request}}+T_{\text{return}} < T_P < T_A$$

例如 $T_A=300\text{ ms}$、$T_P=200\text{ ms}$ 只是预算示意，不是通用阈值。P 还应把连接超时、首字节超时、响应读取超时分开记录；否则“超时”无法定位为未连上 N1/N2、已发送未首包，还是响应回程过慢。

收到 504 后按执行证据决策：

- **请求未离开 A 或 P 未成功转发**：可选择另一上游或重试，风险较低。
- **P 已转发，但未收到 N1/N2 响应**：执行状态未知。对读请求可重试；对创建、扣款、发送等写请求，应先以请求标识查询权威结果。
- **查询确认未执行**：在剩余总预算内重试，并沿用同一幂等键；每次重试应有独立、递减的超时预算。
- **查询确认已执行**：返回既有结果，停止重试。
- **结果仍不可判定**：停止盲目自动重试，保留 `请求标识、A/P/N1/N2 时间戳、上游选择、状态码与超时阶段`，转入人工或异步对账。

负载均衡只决定 P 此次选 N1 还是 N2；它不会同步两者的进程内存。因此，即使后续重试被转发到 N2，也不能把 N1 上的“可能已受理”当作已知失败。重试策略必须建立在共享的权威状态与可查询证据上，而非 `504` 本身。

> **要点** — 代理只逐跳转发；状态、确认与重试安全性必须由明确边界、观测证据和业务机制保证。
