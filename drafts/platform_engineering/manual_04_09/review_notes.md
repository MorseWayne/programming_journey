## 单章覆盖与教学审阅

- 以 A→P→N1/N2 两段连接分离反向代理/负载均衡、逐跳 TLS/HTTP 与应用确认；受信 `Forwarded/X-Forwarded-For` 不能替用户身份/权限。
- N1 `200 accepted_in_memory` 后 N2 不自动有其进程内消息；轮询只选路，粘性也不使 N1 重启后持久。未来 S3 DB 仍只是提议。
- 健康探测定义 TCP/HTTP 路径的可用性，不证明某 IM 写入、历史查询或 B 设备 ACK；探测不得制造用户消息。
- HTTP/1.1 WebSocket 代理升级、双跳连接、空闲读超时/心跳和资源上限按 NGINX 官方机制说明，不给可直接部署配置。
- 纸上 1000 ms 预算拆 100+700+200，两个 700 ms 上游尝试会超预算；P 504 不能证明 N1 未受理，当前同 ID 再试得 409 也非幂等成功，改投 N2 可能双实例受理。
- RFC 502/503/504 分层与请求 ID/后端/超时/确认点证据，22 题按逐跳基础、多实例推演、重试决策分层。

## 原稿对账与修订

- 原稿正确复算 **1000 ms = 100+700+200**，并指出两次各 700 ms 上游尝试会越过总预算；后段又引入 **5 s** 与 **300/200 ms** 等另一套示意数字，未贯穿同一图。正式页只用 1000 ms 一套纸上账本，避免把不同配置误拼成可执行建议。
- 原稿以 N1 内存保存 `m-1`、随后对 N1/N2 发“历史查询”作推演；这只能说明多实例内存不可自动共享，不证明当前 S2 已有跨请求或跨重启的权威历史接口。正式页明确当前 `accepted_in_memory` 只到受理进程，未来 S3 存库仍是提议。
- 原稿一处说 N1 `accepted_in_memory` 后“可能继续异步落库、投递”，这不是当前 S2 已承诺的动作；正式页只陈述已观察到的内存受理确认点，不从代理 504、健康探测或重试推得持久与设备 ACK。
- 原稿后段泛称“具有幂等键且尚无后端确认的写请求可在明确条件下重试”；对当前 S2 同 ID 重复 **409**，不能凭键存在、代理 504 或切换 N2 自动重试。正式页要求先有权威操作结果/持久去重证据，避免跨实例双受理。
- 原稿对 TLS 逐跳、受信代理头、WebSocket 长连接及 502/503/504 的响应来源解释基本正确；正式页保留这些内容，按入口→状态→探测→长连接→预算→诊断递进。
