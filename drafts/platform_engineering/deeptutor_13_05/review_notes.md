# 13.05 审阅记录：容量与数据设计

DeepTutor BookEngine 八节初稿均 ready、无失败块；本地 HTTP Markdown 导出与归档的 `original.md` SHA256 一致。正式页沿 11.12 同一组虚构容量基线，用四本账解释连接、权威历史、E9 事件、设备任务，再推访问模式、热群、增长和积压恢复，附 22 道分层练习。

## 教学重组

- 先固定当前 S2 `/v1` 的 6 B/4096 B/409/404/`accepted_in_memory` 与未来 S3/R9 边界，再按用户确认点定义资源单位。
- 使用与 11.12 一致的条件算式：10,000 连接、200 活跃、20 入站/s、未来 2,000 设备任务/s、312.5 MiB 连接分量、0.977 MiB/s 纯任务封装载荷。
- 按未来访问模式列稳定消息 ID 判重、`(conversation,seq)` 有权历史分页、每设备连续游标与 E9 发布状态；表、索引和分片保留为待验证候选。
- 将未来权威原始记录 1.648 GiB/天、待批 30 天 49.44 GiB 与 E9 在 broker 24h 约 0.824 GiB 分账，强调元数据大小和物理存储放大。
- 用只改连接数/只改群规模的单变量场景识别热群，再算停消费 10 分钟积压 12,000 条、净清 10/s 时理想 20 分钟，区分 RTO/RPO 和业务补拉。

## 技术修订

- 初稿导出有重复 `###` 小节标题及大量同义重述；正式页重排为需求单位→访问模式→四本账→热键增长→恢复→验证。
- 初稿将 S2 `/v1` 同 ID 重复 409 直接推成“消息写入需要唯一 DB 约束”，忽略当前只有本进程内存受理。正式页把持久唯一性限定为未来权威写入的设计问题，当前 409 仍按现合同解释。
- 初稿局部用 6 B 正文估逻辑正文总量，可能让初学者把它当权威记录大小；正式页按与 11.12 相同的**未来每记录含元数据 1 KiB**假设计权威历史，6 B/4096 B 各自限定为正文/原始 HTTP 请求体。
- 初稿把 R9 6→9 B 的 3 B 差额扩展为对群扇出容量的确定性影响；正式页只标 R9 待审，不据此改变 512 B 设备任务封装或既有算式。
- 初稿一处用 B 离线 25h 与 broker 24h 来设 RTO，不符定义。正式页分别解释离线覆盖/数据保留、服务恢复目标、可接受数据损失窗口及积压清空时间，不把它们合并。
- 固定 OpenIM 两处源码只支持所读发送与 Mongo 消费异步边界，不能证明真实吞吐、单连接内存、权威记录字节、保留或清空时间。
