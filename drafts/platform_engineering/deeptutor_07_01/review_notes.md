# 07.01 审阅记录：访问模式与状态角色

DeepTutor BookEngine 八节初稿均 ready，HTTP Markdown 导出与本地渲染 SHA256 一致。完整原稿保存在 `original.md`；正式页先定义消息/权限/预览/在线/计数的损失角色，再讲访问模式、局部性、命中/陈旧、TTL/逐出与缓存重启，附 22 道练习。

## 教学重组

- 严格分开当前 S2 v1 `accepted_in_memory` 与未来 S3 v2 `stored_in_teaching_db` 提议。S2 进程内消息易失、没有数据库历史可回源；S3 的权威消息才在所选数据库合同下可恢复。
- `members.left_at` 是当前发送/读取资格权威；会话预览可重建但必须有完整消息和编辑/撤回/可见规则；在线 presence 依赖新连接/心跳，缓存缺键时应标未知或按合同降级，不从旧历史推断在线。
- 06.12 的 `conversation_counters.next_seq` 是**提议的事务序号权威**，不能与允许重置的短期限流 counter 同列为“临时”。精确业务配额若有不可逆后果也需另设持久边界。
- 固定 10 次预览读 7 hit、3 miss，命中率 70%；在每 miss 一次回源的无并发模型下有 3 次预览回源。缓存仍可命中 seq8 而权威已到 seq9，所以 hit 不证明新鲜/授权/正确。

## 技术修订

- 原稿某段直接把 **S2 定义为 Redis 内存服务、S3 定义为数据库**，与本项目阶段合同不一致；正式页不擅自给 S2 指定 Redis 组件，也不把未来 S3 的数据库当现有实现。
- 原稿把 S2 消息预览称作可重建派生值，却同时承认内存历史在重启后可能丢失；正式页说明“派生”必须有完整权威重建来源，S2 一旦连源消息也丢失就不能凭空重建预览。
- 原稿用虚构的 30 ms 全回源基线推出“平均延迟显著降低”，缺少实际成本、并发与旧值证据；正式页只保留可核算的 7/10 与 3 次玩具回源，不编造性能收益。
- 原稿在线缺键时有“未知或离线”两种表达，容易被读成缺键证明真实离线；正式页要求先按合同标未知/保守降级，再等心跳或连接重新确认。
- TTL 到期、主动失效、内存逐出和节点故障各有不同触发原因；TTL 只是缓存键生命周期，不自动保证剩余时间内值最新。权限旧许可不得因为缓存 hit 而放行。
- Redis 只是存储技术，可否逐出取决于业务角色；若真承载唯一权威事实，就须满足持久、复制和恢复要求，不能套普通缓存的损失政策。
