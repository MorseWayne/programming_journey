先分清三条设计轴：HTTP版本管传输，RPC管服务调用，IM合同管业务语义；它们不能互相替代。

### 三类版本与合同边界

### 三类版本与合同边界

先分清三条设计轴：HTTP 版本管**连接上的传输与帧格式**，RPC 管**服务如何调用方法**，IM 合同管**消息业务语义**；它们可以组合使用，但不能彼此替代。

- **HTTP/1.1、HTTP/2、HTTP/3**：决定请求和响应怎样在网络上传输。HTTP/1.1 常按文本报文与连接顺序工作；HTTP/2 支持二进制分帧、多路复用和流级控制；HTTP/3 基于 QUIC。启用 HTTP/2 不会自动新增任何业务字段、消息状态或存库步骤。
- **路径版本 `/v1`、`/v2`**：是应用资源或业务合同版本。例如 `POST /v1/messages` 表示当前对外消息接口，不是“使用 HTTP/1.1”；将来出现 `/v2/messages`，也不意味着底层必须使用 HTTP/2。
- **RPC 接口版本**：内部服务可用普通 HTTP，也可用 gRPC 的“服务 + 方法 + 类型化请求/响应”模型，例如 `MessageService/AcceptMessage`。RPC 版本演进关注方法、字段兼容性和错误码，不等同于外部路径是否升级。
- **IM 业务合同**：规定身份如何认证、`message_id` 是否可重复、正文格式、确认是否仅表示内存受理，以及失败如何分层。`200 accepted_in_memory` 只说明当前 S2 进程已受理，不能推导为已持久化、已投递或已读。

因此，A 客户端仍可经 HTTP/1.1、HTTP/2 或 WebSocket 调用现行 `/v1`；网关内部也可选择 HTTP 或 RPC 调用处理组件。即使 HTTP/2 已启用，R9 的业务结果、幂等判断和存库状态仍必须按 IM 合同单独实现与记录。

### HTTP/2：多路复用与流控

### HTTP/2：多路复用与流控

HTTP/2 将一条连接拆成多个逻辑**流**（stream）。每个请求—响应通常对应一个流；同一 TCP 连接内可同时传输多个流的帧，因此不必像 HTTP/1.1 那样依赖多个连接或按请求顺序等待响应：

- 流 1：发送消息；
- 流 3：拉取会话列表；
- 流 5：上传附件；
- 各流的 `HEADERS`、`DATA` 等帧可以交错发送，并由流 ID 重新归属。

这叫**多路复用**。它改善的是应用层请求之间的串行等待，不改变 `/v1`、`/v2` 的业务合同，也不意味着接口自动变成 RPC。

HTTP/2 还有逐跳流控：接收方通过窗口限制发送方可继续发送的 `DATA` 字节数。窗口分为连接级和流级；发送方必须同时满足两者：

$$
\text{可发送字节} \le \min(\text{连接窗口},\text{该流窗口})
$$

接收方消费数据后发送 `WINDOW_UPDATE` 增加窗口。这样，慢速接收者或大附件流不会无限占用内存；但如果连接级窗口耗尽，即使另一个流本身很轻，也可能暂时不能继续发送。

注意 HTTP/2 仍运行在 TCP 之上。TCP 按字节序可靠交付：某个底层报文丢失时，后续字节即使已经到达，也要等待缺失部分重传后才能交付。于是，一个流中的丢包可能阻塞同一连接上其他流的后续数据，这就是仍然存在的**TCP 队头阻塞**。

因此，“HTTP/2 已启用”通常只表示该链路可并发复用流、使用帧和流控；它不表示 `/v2` 已发布，不改变 `200 accepted_in_memory` 仅代表当前 S2 进程已受理的业务含义。

### HTTP/3与QUIC的收益边界

### HTTP/3 与 QUIC 的收益边界

HTTP/2 建立在单条 TCP 连接之上，可在协议层复用多个请求流；但 TCP 丢失一个报文段时，后续数据即使属于其他 HTTP 流，也可能等待缺失数据重传。这是**传输层队头阻塞**。

HTTP/3 则运行在 QUIC 之上。QUIC 基于 UDP 实现可靠传输、加密和多路流，每个流具有独立的有序交付范围。某个流的分片丢失时，通常只阻塞该流，其他流仍可继续交付，因此在高丢包、移动网络或网络切换场景中可能改善并发请求体验；连接迁移也比 TCP 重建连接更自然。

但这不意味着“启用 HTTP/3，IM 就更可靠或更快”：

- QUIC 流独立，不能消除网关、S2 进程、数据库或消息处理队列中的排队与慢处理。
- 所有流仍共享连接的拥塞控制与带宽；网络拥塞时，整体吞吐仍会下降。
- `200 accepted_in_memory` 仍仅表示当前 S2 进程已受理，不因 HTTP/3 自动变成已持久化、已投递或已确认。
- HTTP/3 需要客户端、负载均衡、证书与 UDP 网络路径支持；某些环境可能回退到 HTTP/2 或 HTTP/1.1。

因此，HTTP/3 是外部传输能力的可选升级，不等于 `/v2` 业务合同上线，也不要求内部服务必须改用 gRPC 或 QUIC。

### 内部RPC与Protobuf演进

### 内部RPC与Protobuf演进

gRPC 可作为 IM 服务内部调用的一种实现：它通常运行在 HTTP/2 之上，用 `.proto` 描述方法与类型化消息；但这不意味着外部 `/v1` 接口改为 RPC，更不意味着必须放弃普通 HTTP。

例如，网关将已完成鉴权的发送请求交给消息处理组件：

`MessageService.SendMessage(SendMessageRequest) returns (SendMessageResponse)`

请求应携带业务所需的稳定语义，而非复制 HTTP 细节：

- `sender_id`：已认证用户身份；内部服务仍应校验调用方是否可信。
- `conversation_id`、`client_message_id`、`body`：会话、客户端去重标识与消息正文。
- `request_id`：链路追踪与审计关联，不应替代幂等键。
- 响应可返回 `message_id`、`accepted_in_memory` 与拒绝原因。

```protobuf
message SendMessageRequest {
  string sender_id = 1;
  string conversation_id = 2;
  string client_message_id = 3;
  string body = 4;
  string request_id = 5;
}
```

Protobuf 演进遵循“字段编号永久稳定”原则：新增字段使用新的编号并保持可选；删除字段后必须 `reserved` 原编号和名称；绝不能把编号 `3` 从 `client_message_id` 改作其他含义。旧服务会忽略未知字段，新服务则必须为缺失的旧字段提供兼容处理。

```protobuf
message SendMessageRequest {
  string sender_id = 1;
  string conversation_id = 2;
  reserved 3;
  reserved "client_message_id";
  string body = 4;
}
```

错误也要分层：网络或 gRPC 状态码说明调用是否成功到达；业务响应说明消息是否被当前 S2 进程内受理。即使返回 `200 accepted_in_memory` 或对应的 RPC 成功结果，也不能推导消息已经持久化、投递或被对方确认。普通内部 HTTP 同样可以表达这套合同；选择 gRPC 是调用形态与工程权衡，不是业务版本升级。

### 分层确认、超时与重复消息

### 分层确认、超时与重复消息

一次“成功”必须说明成功发生在哪一层，不能把传输成功误写成消息已持久化或已投递。

- **HTTP 层**：外部 `POST /v1/messages` 返回 `200`，仅表示该 HTTP 请求得到正常响应。响应体中的 `accepted_in_memory` 表示当前 S2 进程已在内存中受理，不等于已写库、已进入队列，更不等于对方已收到。
- **RPC 层**：内部 gRPC 的 `grpc-status=OK` 表示该方法调用按协议成功结束；业务拒绝、参数错误或重复 ID 可映射为明确状态，不能只看 HTTP 网关是否返回 200。
- **业务层**：消息是否持久化、是否可查询、是否已投递，需要由业务结果字段、消息状态或后续查询合同定义。

超时也必须分层处理。HTTP 客户端断开或 gRPC deadline 到期时，调用方应取消等待；服务端收到取消信号后，应尽量停止尚未开始的工作。但若消息已经写入存储，取消并不能“撤销”该写入。此时调用方看到超时，服务端却可能已完成，因此超时后的重试天然会遇到重复请求。

为安全重试，客户端应为同一逻辑消息稳定生成 `message_id`，并在每次重试中保持不变。服务端以该 ID 做幂等判定：

- 首次成功受理：返回业务成功，例如 `200` 与 `accepted_in_memory`；
- 相同 ID、相同内容再次提交：可返回原结果，或按合同返回 `409` 表示重复；
- 相同 ID、不同内容：必须拒绝，常用 `409`，避免调用方借重复 ID 覆盖既有消息。

因此，只有请求具备稳定消息 ID、服务端实施幂等检查、调用方能接受“超时但可能已成功”时，自动重试才是安全的。HTTP/2、HTTP/3 或 gRPC 都不会自动提供这项业务保证。

> **要点** — 传输版本、服务调用方式和IM受理语义是独立设计轴；成功响应不等于消息已持久化或已送达。

HTTP 版本决定一次请求如何在链路中传输，却不等同于接口版本或消息业务状态。理解连接、流与流控边界，才能正确诊断并发与延迟问题。

### 先分清接口版本与传输版本

### 先分清接口版本与传输版本

一次调用里常同时出现三种“版本”，但它们回答的是不同问题：

- **应用路径版本**：如 `/api/v1/orders`、`/v2/users`，表示接口契约的演进：字段、认证方式、分页规则或行为是否兼容。它由服务端路由和业务代码决定。
- **HTTP 协议版本**：如 `HTTP/1.1`、`HTTP/2`，表示客户端与某个逐跳对端如何传输请求和响应：连接是否复用、是否多路复用、头字段如何编码、流控如何工作。
- **业务语义版本或状态**：如消息协议版本、订单状态机版本、事件 schema 版本，表示负载内容应如何解释；它不由 HTTP 帧或 URL 自动决定。

因此，访问 `/v1/chat/send` 并不意味着使用 HTTP/1.1；同一个 `/v1` 接口可经 HTTP/2 传输，也可因代理降级为 HTTP/1.1。反过来，HTTP/2 也不会让旧接口自动兼容新字段。

还要注意 HTTP 版本是**逐跳**属性：

`客户端 --HTTP/2--> 网关 --HTTP/1.1--> 后端`

客户端日志中的 `h2`，只能说明客户端到网关这一跳协商成功，不能推出网关到后端也使用 HTTP/2。排查并发、队头阻塞或流控时，应分别记录接口路径、实际协议版本、代理链路和业务请求结果，避免把传输现象误判为接口版本问题。

### HTTP/1.1：复用连接不等于并发无阻

### HTTP/1.1：复用连接不等于并发无阻

HTTP/1.1 的持久连接允许多个请求复用同一条 TCP 连接，避免每次请求都重新进行 TCP（以及 HTTPS 场景中的 TLS）握手。这降低了连接建立成本，但“连接可复用”不意味着请求能够完全独立、无阻塞地并发完成。

客户端可以在尚未收到前一个响应时继续发送后续请求，这称为**管线化**。但服务端必须按请求顺序返回响应：若第一个请求处理慢、响应体很大，后面的响应即使早已计算完成，也不能先发送。这就是 HTTP/1.1 应用层的**队头阻塞**：

`请求 A（慢） → 请求 B（快） → 请求 C（快）`  
`响应 A 未完成时，响应 B、C 只能等待`

因此，浏览器和许多客户端通常会针对同一目标建立多条 TCP 连接，把不同请求分配到不同连接上，以获得实际并发度。一条连接被慢响应占住时，其他连接仍可传输请求；代价则是更多握手、更多套接字与拥塞控制状态，也可能加重服务端资源压力。

还要区分两层含义：持久连接解决的是“能否继续使用同一连接”，管线化试图提高“同一连接上的请求发送并发”；但由于响应顺序约束，后者并未消除队头阻塞。实践中 HTTP/1.1 管线化兼容性有限，客户端更常以多连接并发作为折中方案。

### HTTP/2：以流和帧实现多路复用

### HTTP/2：以流和帧实现多路复用

HTTP/1.1 虽可复用同一条 TCP 连接，但管线化请求的响应仍必须按顺序返回：若前一个响应很慢，后面即使已准备好也难以先交付，形成应用层队头阻塞。实践中，浏览器和客户端常通过建立多条 TCP 连接换取并发。

HTTP/2 将一条连接中的通信拆成多个独立的 **stream（流）**。一次请求及其响应通常对应一个流；流具有唯一编号和各自状态。请求头、响应头与正文不再作为连续的整块文本发送，而是编码为带有流标识的 **frame（帧）**：

- `HEADERS` 帧承载压缩后的头字段；
- `DATA` 帧承载正文数据；
- 控制帧用于建立、关闭流或更新窗口等。

因此，同一 TCP 连接上的字节序列可以交错排列：

`流 1 的头 → 流 3 的头 → 流 1 的部分正文 → 流 3 的正文 → 流 1 的剩余正文`

接收方依据帧中的流标识，将内容重新归入对应请求。这样，某个大响应或慢处理请求不必在 HTTP 语义上阻止其他流的帧先发送、先完成；一个连接即可承载多个并发请求。

HTTP/2 还使用 HPACK 压缩头字段。重复出现的 `Cookie`、`User-Agent`、认证信息等可被索引或增量编码，减少大量请求重复携带文本头部的开销。

但“多路复用”不等于完全隔离。所有流仍共享同一条 TCP 连接；一旦底层 TCP 某个报文丢失，后续字节无法按序交付，多个流的帧都可能等待缺失数据。这是传输层队头阻塞，也是 HTTP/3 改用 QUIC 试图进一步改善的问题。

### 逐跳流控与共享 TCP 的限制

### 逐跳流控与共享 TCP 的限制

HTTP/2 将请求拆成独立的 `stream`，发送端能交错发送不同流的帧；但“可交错”不等于“无限并发”。接收方通过窗口声明尚可接收的字节数，发送量同时受两层约束：

$$
\text{可发送量} \le \min(\text{stream 窗口},\ \text{connection 窗口})
$$

- **流级窗口**：限制某一个 `stream` 尚可发送多少响应或请求体数据。某流的消费者读取缓慢、迟迟不更新窗口时，该流应被抑制，避免其无限占用接收端缓冲。
- **连接级窗口**：限制整条 HTTP/2 连接中所有流合计可发送的数据。即使某个流自己的窗口充足，只要连接窗口耗尽，它也必须等待窗口更新。

因此，流控是两个端点之间的**逐跳字节传输协商**：客户端与代理之间、代理与源站之间各自独立。它不表示用户权限、消息是否已送达，也不等同于业务层的限流配额。

更深的一层限制来自共享 TCP。HTTP/2 的帧虽可交错，但它们最终仍编码进同一条有序 TCP 字节流。若其中一个 TCP 报文丢失，后续字节即使已到达也通常不能交给 HTTP/2 解析；于是多个 `stream` 都可能停顿。这是传输层队头阻塞，而非 HTTP/1.1 管线化的响应排序问题。

慢读取还可能通过连接窗口、服务端写缓冲、内存和调度资源外溢到其他流。故应用层仍应限制单连接并发流数、请求体大小、排队长度与缓冲内存；HTTP/2 改善了复用方式，并未取消资源边界。

### Go 中确认实际协商协议

### Go 中确认实际协商协议

`http.Client` 是请求抽象，不是“必定使用 HTTP/2”的承诺。一次外部 HTTP 调用实际使用 `HTTP/1.1`、`h2` 还是其他协议，取决于目标地址、TLS 的 ALPN 协商、`Transport` 配置、中间代理以及服务端能力。尤其在 IM 的推送、鉴权、媒体下载等链路中，不能只根据“代码复用了同一个 `http.Client`”推断多路复用是否生效。

最直接的证据在响应中：

```go
resp, err := client.Do(req)
if err != nil {
    return err
}
defer resp.Body.Close()

log.Printf("status=%s proto=%s major=%d",
    resp.Status, resp.Proto, resp.ProtoMajor)
```

若 `resp.Proto` 为 `HTTP/2.0`，才说明**客户端到当前对端这一跳**使用了 HTTP/2；它不证明后续代理到源站仍是 HTTP/2。经过网关、反向代理或企业代理时，应同时记录：

- 目标主机、最终 URL、重定向次数；
- `resp.Proto`、状态码、请求耗时；
- 代理地址与是否使用 `CONNECT` 隧道；
- 连接复用信息，例如 `httptrace.GotConnInfo.Reused`；
- 请求标识、上游返回的追踪标识，以及网关日志中的协议字段。

可用 `httptrace` 区分“新建连接”与“复用连接”，但不要把连接复用等同于 stream 并发。若诊断到实际是 HTTP/1.1，则多个并发 IM 请求可能依赖多个 TCP 连接；若为 HTTP/2，也仍要关注单条 TCP 连接丢包、连接级窗口、慢响应流和客户端队列造成的整体延迟。

> **要点** — HTTP/2 用流改善并发，但流控是逐跳能力，且所有流仍可能受共享 TCP 与连接资源限制。

HTTP/3 以 QUIC 承载既有 HTTP 语义，改变的是传输复用与丢包恢复边界，而非业务受理和消息持久化的含义。

### HTTP语义与传输版本的边界

### HTTP语义与传输版本的边界

先区分三个容易混淆的“版本”：

- **应用接口版本**：如 `/v1/orders`、`Accept: application/vnd.example.v2+json`、JSON 字段是否兼容。这决定请求和响应的业务契约，与底层使用 h1、h2 还是 h3 无必然关系。
- **HTTP 协议版本**：HTTP/1.1、HTTP/2、HTTP/3 保持方法、状态码、头字段和资源语义的基本含义；`POST` 仍不天然幂等，`200` 仍只表示该 HTTP 响应的成功语义。
- **实际链路版本**：客户端到边缘代理可能是 h3，代理到服务网格是 h2，网格到后端则可能是 HTTP/1.1。代理通常逐跳终止连接，再按下一跳能力重新发起请求。

因此，看到客户端协商到 `h3`，只能说明**客户端—第一跳**使用 HTTP/3；不能推出后端也使用 QUIC，更不能推出整条调用链没有 TCP 队头阻塞。排障和性能观测应逐跳记录协议、连接复用、重试、超时与流控状态。

HTTP/3 改变的是 HTTP 语义在 QUIC stream 上的承载方式：不同请求通常可位于不同 stream，一条 stream 的丢包不必等待另一条 stream 的字节补齐。但连接级拥塞控制、流控额度、握手延迟、服务端处理排队及网络路径仍会影响整体延迟。

更重要的是，传输升级不提升业务确认等级：

`200 accepted_in_memory` ≠ 数据库已持久化 ≠ 下游服务已完成 ≠ 设备 B 已 ACK。

协议版本回答“消息如何传输”；接口契约与业务状态机才回答“操作完成到什么程度”。

### QUIC多流如何缓解跨流阻塞

### QUIC多流如何缓解跨流阻塞

HTTP/2 可在一条 TCP 连接中并发多个请求，但所有 HTTP/2 帧最终都写入同一条 **TCP 字节流**。TCP 交付给上层时必须保持全局字节序：若较早序号的数据包丢失，即使后续数据包中装着另一个请求的完整响应，接收端也不能越过缺口交付这些字节。于是，流 A 的一个丢包可能使流 B 暂时停顿，这就是传输层的跨流队头阻塞。

可将其抽象为：

- TCP：连接只有一条有序字节序列 `$b_1,b_2,\ldots$`
- HTTP/2：多个 HTTP 流的帧复用到这条序列
- 缺失 `$b_i$`：后续 `$b_{i+1},b_{i+2},\ldots$` 均须等待重传补齐

HTTP/3 改用 QUIC。QUIC 在一个连接内提供多个 stream，每条 stream 都有自己的偏移量、可靠性和有序交付边界。若流 A 的某个数据包丢失，接收端只需等待流 A 对应偏移的数据恢复；流 B 已完整到达的数据通常仍可交付给 HTTP/3 层并继续处理。

因此，阻塞边界从“整条连接的字节序列”缩小为“发生缺口的那条 stream”。这尤其有利于页面资源、并发 RPC 等场景：大响应或丢包请求不必因 TCP 顺序语义直接卡住无关的小请求。

但“独立流”不等于完全互不影响。各流仍共享连接拥塞控制、连接级流控、网络带宽与 CPU；丢包也可能降低整体拥塞窗口。若流控额度耗尽、路径抖动严重或服务端排队，其他请求仍会变慢。QUIC 缓解的是**可靠有序交付造成的跨流阻塞**，不是消除所有延迟与竞争。

### 流控、拥塞与丢包仍是共同约束

### 流控、拥塞与丢包仍是共同约束

QUIC 消除了 HTTP/2 在单条 TCP 字节流上的跨 stream 队头阻塞：某个 stream 丢包后，其他 stream 若数据已到达，通常可以继续交付。但“可以继续”仍受共享资源约束。

- **流级流控**限制单个 stream 可发送、可缓存的字节数；接收方未及时读取或未更新额度时，该 stream 仍会停顿。
- **连接级流控**限制整个 QUIC 连接的在途与未消费数据总量。一个大响应持续占用窗口，可能压缩其他请求的可用发送额度。
- **拥塞控制**通常以连接和网络路径为单位工作。发生丢包、时延上升或带宽竞争时，发送方会降低发送速率；即使其他 stream 没有丢包，也会共享这次降速。
- **丢包恢复**仍要重传受影响 stream 的数据。小对象可能先完成，但依赖缺失字节的响应、请求体上传或服务端处理仍会延迟。
- **握手与路径条件**也很关键。首次 QUIC 建连需要握手；`0-RTT` 只适用于满足条件的可重放请求，且可能被拒绝。UDP 被限速、丢弃或中间设备兼容性较差时，HTTP/3 甚至可能不如 h2/h1 稳定。

因此，HTTP/3 改善的是“一个 stream 的可靠交付等待不必阻塞另一个 stream”的边界，不是取消流控、拥塞、握手和网络路径成本。性能判断应按真实链路、请求并发与丢包特征测量，而非假定 h3 总会更快。

### IM发送请求的逐跳版本示例

### IM发送请求的逐跳版本示例

设客户端向 IM 网关发送消息：

`客户端 → 边缘代理 → IM 网关 → 消息服务 → 数据库/设备投递`

一次实际部署可能是：

| 跳段 | 协议版本 | 含义 |
|---|---|---|
| 客户端 → 边缘代理 | HTTP/3 over QUIC | 移动端与公网边缘协商 `h3`，多个请求可映射到独立 QUIC stream。 |
| 边缘代理 → IM 网关 | HTTP/2 over TCP | 代理终止 QUIC，验证、限流后，以新的 TCP 连接和 HTTP/2 转发。 |
| IM 网关 → 消息服务 | HTTP/1.1 | 网关调用遗留内部服务，可能使用连接池上的串行请求或有限并发连接。 |

因此，客户端看到的响应头即使包含 `:status 200`，并且其连接是 HTTP/3，也只能说明**客户端到边缘代理这一跳**使用了 h3；它不能推出网关到后端同样使用 QUIC，更不能推出消息已经持久化或设备已经收到。

例如代理收到：

`POST /messages {"to":"B","text":"你好"}`

它可以在 h3 请求 stream 上读取完整请求，再创建一个 h2 stream 调用网关。若内部 h2 连接拥塞、网关排队，或遗留 h1 服务连接耗尽，外部 h3 仍会变慢。反过来，客户端侧某个 QUIC stream 的丢包通常不要求另一个请求等待其字节补齐，但连接级拥塞窗口、流控额度和代理资源仍会共同限制吞吐。

排障时应记录每一跳的协议、连接标识、stream 标识和耗时：`client_h3`、`proxy_upstream_h2`、`gateway_backend_h1`。不要把入口协议版本当作整条调用链的性质。

### 传输成功不等于消息已送达

### 传输成功不等于消息已送达

HTTP/3 改善的是 HTTP 请求在 QUIC 上的传输方式，不改变“成功”的业务边界。收到 HTTP 响应、看到 gRPC `OK`，通常只能证明某一层已经处理到某个阶段，不能自动推出消息已落库、已被下游消费，更不能推出设备已经执行。

可将结果分为三层：

- **传输与协议层**：客户端收到了可解析的 HTTP 响应，或收到了 gRPC trailers。HTTP/3 的 QUIC stream 已可靠有序地交付该响应字节；这不表示服务端的后续异步工作完成。
- **服务接口层**：HTTP `2xx` 或 gRPC `OK` 表示该接口按其约定成功。若接口语义是“接受任务”，成功可能仅表示任务进入内存队列。
- **业务完成层**：消息已写入数据库、已提交消息队列、已被 B 设备确认，或业务动作已产生可验证结果。这些都需要显式状态、回执或查询接口证明。

例如：

`200 accepted_in_memory`

应理解为“服务进程当前内存中接受了该消息”。进程崩溃、重启、队列未刷盘、异步消费者失败时，消息仍可能丢失。即使响应经 HTTP/3 成功返回，也不能将其升级解释为：

`200 persisted_to_db`  
`200 published_durably`  
`200 device_B_acknowledged`

同理，gRPC `OK` 是 RPC 方法的状态，不是端到端投递证明。若方法名为“提交命令”，`OK` 可能表示命令格式合法并已受理；若要求设备确认，应返回明确的确认标识，或提供按 `request_id` 查询的最终状态。

设计接口时，应把受理、持久化、投递和执行分别建模，并为异步链路提供幂等键、状态机与可重试查询。HTTP/3 能降低部分跨流队头阻塞，但不能替代持久化协议、消息确认和业务回执。

> **要点** — HTTP/3 减少跨流传输阻塞，但仍受流控和网络约束；每跳版本与业务受理状态必须分别观察。

本节从内部 IM 调用出发，厘清 gRPC 的服务建模、流式模式与受理语义，避免把协议、序列化和授权混为一谈。

### 以服务和方法表达内部操作

### 以服务和方法表达内部操作

gRPC 将内部能力组织为“服务中的方法”：服务表示一组相关操作，方法表示一次可调用的业务动作；请求与响应则由结构化消息明确字段、类型和语义。它不是“把任意函数暴露到网络上”，而是先定义稳定的调用契约。

纸上可将 IM 内核提案写成：

- `GetCurrentRule(actor, question) → rule, source_version`：查询当前适用资料及其来源版本，属于只读操作。
- `SubmitMessage(actor, conversation_id, message_id, body) → acceptance_status`：提交一条消息，返回业务是否已受理，而不应仅以“网络包已到达”冒充成功。

可用 Protocol Buffers 描述这类契约，例如请求中的 `conversation_id`、`message_id` 与 `body` 都是独立字段，而不是拼接在一段文本里。这样调用方、网关和服务端能围绕字段进行校验、演进与审计。

但字段类型不是完整业务规则。即使接口写作 `body string`，应用核仍必须验证：内容非空、其 UTF-8 编码字节数不超过 `6`、调用者具有该会话成员权限；若 `message_id` 已被使用，应返回重复标识的 `409` 语义结果。`actor` 也不能因客户端自行声明便成为身份依据：metadata 可传递调用相关信息，但网关与内部服务都要独立验证信任来源及对象范围。

这些方法只是教学中的内部接口提案，并不表示当前 S2 已有对应 RPC。Protocol Buffers 用于定义消息也不自动意味着采用 gRPC、HTTP/2，或已经具备安全与授权机制。

### 请求响应与四类流式模式

### 请求响应与四类流式模式

gRPC 的一个服务可定义多个方法；方法的差异不只在消息字段，还在于请求与响应能否连续发送。四种基本模式可按数据流方向比较：

| 模式 | 请求方向 | 响应方向 | 典型用途 |
|---|---|---|---|
| 一元调用 | 1 条请求 | 1 条响应 | `GetCurrentRule` 查询、`SubmitMessage` 受理 |
| 服务端流 | 1 条请求 | 多条响应 | 订阅规则变更、分批导出、持续推送进度 |
| 客户端流 | 多条请求 | 1 条响应 | 批量上传事件、分片提交文件后汇总确认 |
| 双向流 | 多条请求 | 多条响应 | 实时协作、长连接消息转发、交互式数据处理 |

一元调用最接近传统 HTTP 请求/响应：调用方给出完整参数，服务返回结果或错误。纸上接口中，`GetCurrentRule(actor, question)` 应返回现行资料及来源版本；`SubmitMessage(actor, conversation_id, message_id, body)` 则返回“已受理”“重复”或“无权限”等业务结果。即使模式写作 `body string`，服务仍须验证非空、UTF-8 字节数不超过 6、成员资格及重复 `message_id`；模式描述字段形状，不自动表达业务约束。

流式调用适合数据持续产生、结果无法一次装入或需降低等待时间的情形。HTTP/2 提供多路复用与流级控制，但“使用流”不意味着可以无限发送：服务应规定单条消息大小、总量、超时、取消、背压与完成条件。

双向流尤其容易被误解为“永久聊天通道”。它允许双方独立地读写，响应不必严格对应某一条请求；但每条消息仍要关联会话、验证对象范围并处理顺序、断线重连和幂等性。客户端在 metadata 或消息中自称的 `actor` 不能构成授权依据；网关与内部服务都必须各自验证其信任来源。

### Protobuf、HTTP/2 与 gRPC 的边界

### Protobuf、HTTP/2 与 gRPC 的边界

这三个概念经常同时出现，却分别解决不同问题，不能由其中一个自动推出另一个。

- **Protocol Buffers（protobuf）**解决“数据长什么样”：用消息模式描述字段、类型和编号，并可生成多语言代码。例如 `SubmitMessageRequest` 可包含 `conversation_id`、`message_id` 与 `body`。它是常用序列化与接口描述工具，但使用 protobuf 不等于已经提供了远程调用、HTTP/2、加密或权限控制。
- **gRPC**解决“如何调用服务”：以“服务/方法”定义操作及其请求、响应模式，例如 `GetCurrentRule` 是只读调用，`SubmitMessage` 是写入受理调用。gRPC 可表达一问一答、客户端流、服务端流和双向流；protobuf 是其常见默认搭配，但二者在概念上不是同一层。
- **HTTP/2**解决“怎样承载和复用传输”：常见 gRPC 实现把调用映射到 HTTP/2 的流，利用多路复用、头部压缩和流级控制。HTTP/2 本身不知道 `SubmitMessage` 的业务含义，也不保证消息字段有效。
- **安全授权**解决“谁能对哪个对象做什么”：TLS 可保护传输，metadata 可携带令牌、追踪标识等调用信息；但客户端声称的 `actor`、转发头或普通 metadata 都不能直接视为授权结论。网关与内部服务都应验证信任来源、调用者身份及其对 `conversation_id` 的对象范围。

因此，即使接口写作 `body string`，应用核仍须检查 UTF-8 字节数不超过 6、内容非空、成员权限以及重复 `message_id`；重复 ID 应返回业务可识别的 `409` 类冲突语义。纸面上的 `GetCurrentRule` 与 `SubmitMessage` 只是教学提案，不表示当前 S2 已有这些 RPC。

### 写接口的业务校验与受理状态

### 写接口的业务校验与受理状态

以教学接口 `SubmitMessage(actor, conversation_id, message_id, body)` 为例，字段能否被编码、请求能否到达服务，并不等于消息已被业务受理。应从输入语义逐层推出校验规则：

1. `body` 是字符串，不代表任意内容都合格。应用核应先要求非空，再按 UTF-8 **编码后的字节数**计量：
   \[
   1 \le |\operatorname{UTF8}(body)| \le 6
   \]
   不能按字符个数替代字节数；一个汉字通常占多个字节，`"你好"` 可能字符数很短，却超过 6 字节。

2. `conversation_id` 决定对象范围。调用者必须是该会话成员，且具备发送权限；仅凭请求中自称的 `actor` 不能建立身份。网关可验证外部凭据，内部服务仍应验证传入身份的可信来源及其对该会话的权限。

3. `message_id` 用于幂等与去重。若同一会话中该标识已存在，不能悄悄覆盖旧消息，也不应重复创建；应返回冲突语义，例如 HTTP 映射中的 `409`。这表示请求格式正确，但当前资源状态不允许该创建操作。

校验通过后，响应应表达“业务已受理”，例如已记录待处理消息、已分配服务端状态，而非宣称所有后续投递、通知或持久化副作用都已完成。因而可区分三层：传输成功、请求通过业务校验、消息被业务受理。前两层失败时，客户端应依据明确错误修正输入或权限；受理成功后，则以业务状态查询或后续事件确认最终进展。

### 元数据、身份信任与教学接口边界

### 元数据、身份信任与教学接口边界

gRPC metadata 是随调用携带的附加键值信息，适合传递追踪标识、截止时间、认证凭据、租户上下文或链路观测信息。它不是业务请求体，也不应因为客户端提交了 `actor`、`x-forwarded-user` 一类字段，就被直接当作可信身份。

以教学接口为例：

- `GetCurrentRule(actor, question)`：返回现行资料及其来源版本；
- `SubmitMessage(actor, conversation_id, message_id, body)`：返回业务受理状态。

这里的 `actor` 只能视为调用者声明或业务参数；真正的身份应来自经验证的凭据，例如网关验证后的访问令牌、服务间 mTLS 身份或签名令牌。网关负责确认外部请求的认证状态、令牌有效期和基础入口策略；内部服务仍须验证调用方是否来自受信任链路，并检查该身份是否有权访问指定的 `conversation_id`、执行写入操作。

因此，不能把“请求已通过网关”简化为“内部服务无需鉴权”。网关可能被绕过、配置可能漂移，且网关知道“谁在调用”，不必然完整表达“谁可操作哪个对象”。内部服务至少应落实成员权限、对象归属和操作范围等授权判断。

同样，`body string` 只是模式层类型，应用核仍要验证：内容非空、UTF-8 字节数不超过 `6`、发送者具备会话成员资格；若 `message_id` 已处理，则返回冲突语义，如 `409`。这些接口仅是纸上教学提案，不表示当前 S2 已存在对应 RPC、protobuf 定义或 HTTP/2 部署。

> **要点** — gRPC 定义服务与结构化调用；传输、序列化、授权和业务受理必须分层判断。

本节厘清 gRPC over HTTP/2 中传输成功、RPC 结果与 IM 业务受理三层含义，避免将 HTTP 200 误判为消息已可靠送达。

### 三层结果：HTTP、RPC与业务受理

### 三层结果：HTTP、RPC 与业务受理

一次 gRPC 调用至少要分别判断三层结果，不能用任一层替代另一层：

| 层次 | 典型信号 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| HTTP/2 传输层 | `:status 200`、流是否正常结束 | 请求已按 gRPC 协议获得 HTTP 响应 | RPC 业务逻辑成功 |
| RPC 协议层 | 尾部元数据 `grpc-status=0`、`grpc-message` | 该 RPC 方法按其合同成功返回 | 下游已持久化、消息已送达 |
| 业务受理层 | `accepted_in_memory`、事件 ID、持久化状态 | 某个明确业务动作已达到约定阶段 | 更晚阶段必然完成 |

正常的 gRPC 协议响应通常使用 HTTP `:status 200`，即使服务端最终在 trailers 中返回：

`grpc-status: 7`（权限不足）或 `grpc-status: 14`（暂不可用）。

因此，客户端若只检查 HTTP 200，会把 RPC 失败误判为成功；必须在读取响应消息后继续读取尾部元数据，并以 `grpc-status` 作为 RPC 成败依据。

反过来，`grpc-status=OK` 也不是“消息一定送达”的承诺。设发送方法返回：

`{ accepted_in_memory: true, message_id: "m-42" }`

它最多表示服务 B 已在内存中接受该任务；若进程随后崩溃、异步写入 S3 失败或下游投递失败，RPC 仍可完全符合合同并返回 `OK`。只有方法合同明确返回 `persisted=true`、`delivered=true` 或可查询的最终状态，客户端才能对相应阶段作出判断。

日志与指标应同时记录 HTTP/2 流错误、原始 `grpc-status`、业务字段及发生节点。对外 HTTP 映射则另行显式定义：内部权限错误不应泄露会话存在性，外部重复 ID 仍应保持 `409`，不能因某次 gRPC 调用得到 HTTP 200 而一律映射为外部成功。

### 为何 HTTP 200 不等于 RPC 成功

### 为何 HTTP 200 不等于 RPC 成功

在 gRPC over HTTP/2 中，HTTP `:status 200` 通常只表示：服务器接受了这条 HTTP/2 请求，并以符合 gRPC 协议的方式开始或完成响应。它不是某个 RPC 方法的最终业务结论。

原因在于，gRPC 的响应可能是流式的：服务端需要先发送响应头和若干消息，直到流结束时才能确定方法最终是成功、超时、被取消还是内部失败。因此，最终状态放在 HTTP/2 尾部元数据（trailers）中，例如：

- `grpc-status: 0`：RPC 按 gRPC 语义成功结束；
- `grpc-status: 5`：`NOT_FOUND`；
- `grpc-status: 7`：`PERMISSION_DENIED`；
- `grpc-message`：可选的状态说明，需按协议解码。

典型响应可理解为：

`HTTP :status 200` → 响应消息（可为零条或多条）→ trailers 中的 `grpc-status`

因此客户端的读取规则是：**必须等待流结束并读取 trailers，依据 `grpc-status` 判断 RPC 成败**。只检查 HTTP 200，会把“协议响应正常、但 RPC 执行失败”的情况误判为成功。

反过来，非 200 的 HTTP 状态、HTTP/2 `RST_STREAM`、连接断开等，通常意味着客户端未能获得一个可被正常解释的 gRPC 最终状态；它们属于传输或协议层异常，不应伪装成某个确定的业务结果。客户端应分别记录 HTTP 状态、流错误、是否收到 trailers，以及其中的原始 `grpc-status`。

### grpc-status=OK 的合同边界

### grpc-status=OK 的合同边界

`grpc-status=OK` 表示：该次 RPC 已按**该方法声明的合同**正常结束。它首先不是“HTTP 请求成功”的同义词，更不是“业务目标已经实现”的总证明。

例如 `SendMessage` 的合同若定义为“完成鉴权、校验基本结构，并将消息放入本进程内存队列”，则返回 `OK` 只能推出：

- 服务端已处理到合同承诺的边界；
- 本次调用未以 gRPC 错误状态结束；
- 调用方可取得该方法定义的响应字段。

它不能自动推出以下结论：

- 消息正文满足全部业务语义，例如附件类型、引用关系或内容审核均有效；
- 附件已写入 S3、数据库事务已提交、索引已建立；
- 后台任务已成功执行；
- B 已上线、已收到推送，或已经阅读消息。

因此，响应应明确暴露业务阶段，而非借用 `OK` 表达超出合同的承诺。例如：

`{ "result": "accepted_in_memory", "message_id": "m_123" }`

这里 `OK` 表示“受理接口正常完成”，`accepted_in_memory` 则明确持久化尚未被证明。若产品需要“已持久化”或“对方已送达”，应定义不同的状态、查询接口或异步事件；只有在方法合同明确包含相应保证，`OK` 才能代表该保证已达成。

### IM发送链路的分层响应示例

### IM发送链路的分层响应示例

设外部客户端调用 `POST /messages`，网关鉴权、校验后调用内部 `SendMessage`。一次响应至少应区分：HTTP/2 流是否完成、gRPC 方法是否完成、消息业务推进到哪一步。

| 场景 | 外部 HTTP 响应 | 内部 gRPC 结果 | 正确含义 |
|---|---|---|---|
| `content` 为空、长度超限 | `400` | 可不发起 RPC；若已调用则 `grpc-status=INVALID_ARGUMENT` | 请求不符合接口合同，未受理消息。 |
| 消息写入进程内队列 | `202`，如 `{"status":"accepted_in_memory","message_id":"m1"}` | HTTP `:status 200`，尾部 `grpc-status=OK` | 仅说明 `SendMessage` 已按“内存受理”合同结束；不证明已存储或已送达。 |
| 同步写 S3/数据库失败 | `503` 或 `500` | `grpc-status=UNAVAILABLE` 或 `INTERNAL` | 若方法合同要求“持久化后成功”，则本次不能报告受理成功；保留原始存储错误与失败节点。 |
| 已入队，但 B 离线、推送失败 | 通常仍为 `202` | `grpc-status=OK`，业务字段可标注 `delivery_pending` | 发送服务完成受理，不代表 B 已收到；后续由投递、重试和回执更新状态。 |

gRPC 的正常协议响应常带 HTTP `:status 200`；最终 RPC 成败应读取尾部的 `grpc-status`、`grpc-message`。因此网关不能只因 HTTP 200 就向外宣称“发送成功”，也不能把一次内部重试失败机械映射为外部 200。

外部状态码还应按公开合同转换：重复客户端消息 ID 仍可返回 `409`；无权访问会话时可统一返回隐藏语义的 `404`，不能直接透传内部 `PermissionDenied`。日志至少关联 `request_id`、`message_id`、HTTP/2 流错误、原始 gRPC 状态、业务受理状态及发生节点。

### 错误映射、重试与可观测性

### 错误映射、重试与可观测性

外部 HTTP 契约与内部 gRPC 状态必须分层映射，而非机械透传。内部服务返回 `PermissionDenied`、`Unavailable` 或流被重置，并不直接决定对外状态码：例如非成员查询会话时，为避免泄露会话是否存在，网关可统一返回 `404`；创建消息时客户端提交已存在的幂等 ID，应稳定返回 `409`，不能因内部某次重试得到 `OK` 或 `Unavailable` 而改写语义。

建议为每个边界明确映射表，并保留未映射状态的安全兜底：

- 身份、成员资格或资源可见性不能向外暴露：按资源隐藏策略映射为 `404`。
- 重复业务 ID、版本冲突、状态机不允许转换：映射为 `409`，响应中携带可安全公开的冲突原因。
- 参数格式或业务字段不合法：映射为 `400` 或 `422`；不能仅因 gRPC 的 `grpc-status=OK` 就认为正文有效。
- `DeadlineExceeded`、`Unavailable` 等可恢复内部故障：通常映射为 `503` 或 `504`，并给出受控的重试提示；未知提交结果应标记为“结果待查询”，而不是声称失败或成功。

重试以前必须判断方法合同。只有服务端以去重键、消息 ID 或条件写入保证幂等时，客户端才可安全重试；`accepted_in_memory` 即使伴随 `grpc-status=OK`，也只证明该节点受理到内存，不证明 S3 已落库、下游 B 已收到。deadline 到期或客户端取消后，服务端可能仍在执行，因此调用方应通过同一幂等键查询最终结果，而非生成新 ID 再次提交。

可观测性应同时记录请求 ID、幂等键、HTTP 状态、`grpc-status`、`grpc-message`、HTTP/2 流错误、deadline、重试次数及错误发生节点。日志中保留原始内部错误供排障，但对外响应只暴露经过脱敏和映射后的原因；这样既能区分“传输中断”“RPC 失败”“业务冲突”，也不会把内部拓扑或资源存在性泄露给调用方。

> **要点** — HTTP 200、grpc-status=OK 与消息业务成功分别描述不同层次，必须按方法合同显式映射、判断和记录。

Deadline、取消与流控解决的是“何时停止等待、何处减速”，并不能证明写操作未发生；超时后的首要任务是核证结果。

### Deadline定义等待边界

### Deadline定义等待边界

`deadline` 是客户端为一次 RPC 设定的**最晚等待时刻**，也可理解为“从现在起最多等多久”。例如客户端设置 `3s` deadline，表示它最多等待约 3 秒获得 RPC 结果；这不是在要求服务端“必须在 3 秒内完成业务”，更不是事务回滚边界。

需要区分三个时间概念：

- **Deadline**：客户端定义的等待上限，通常随 RPC 元数据传播给服务端，并会扣除网络与中间处理已经消耗的时间。
- **超时结果**：deadline 到达而客户端尚未获得成功终态时，客户端通常得到 `DEADLINE_EXCEEDED`。这只说明“客户端没有及时确认结果”，不说明请求未到达、服务端未执行或写入未完成。
- **服务端实际执行时长**：服务端从收到请求到完成业务处理的时间。它可能短于 deadline，也可能在客户端放弃等待前后仍已产生外部改动；服务端收到取消信号后也需要主动停止后续工作。

例如：

`客户端发送写请求 → 服务端写入数据库 → 响应在网络中延迟 → 客户端 deadline 到达`

此时客户端看到 `DEADLINE_EXCEEDED`，而服务端可能已成功写入。反过来，服务端可能认为“响应已交给传输层”，客户端却因未及时收到响应而判定超时。双方对本次调用的观察并不天然一致。

因此，deadline 的作用是限制资源占用、避免无限等待，并促使调用方进入补偿或核证流程；它不是“超时即可安全重试”的依据。对写操作，应使用请求标识、状态查询或幂等语义确认结果，而不是把 `DEADLINE_EXCEEDED` 解释为“没有发生”。

### 超时取消不等于回滚

### 超时取消不等于回滚

设客户端为一次写操作设置截止时间 $T$。当本地时钟到达 $T$ 而尚未收到完整响应时，客户端即可结束等待并得到 `DEADLINE_EXCEEDED`。这只说明：

> 客户端在期限内**没有确认结果**，并不说明服务端没有执行。

一次调用可能按如下顺序发生：

1. 客户端发送请求；
2. 服务端已接收请求，并写入数据库、扣减库存或向设备下发命令；
3. 服务端准备返回成功响应时，网络拥塞、连接中断或客户端 deadline 到期；
4. 客户端报告 `DEADLINE_EXCEEDED`，同时服务端收到取消信号。

这几个事实并不矛盾。取消是一个“请停止后续工作”的协作信号，不是可跨数据库、消息队列、第三方支付和设备系统自动执行的事务回滚命令。服务端即使检测到取消，也无法抹去已经提交的外部副作用；若它尚未检查取消状态，也可能继续运行一段时间。

因此，客户端的“我超时了”和服务端的“我已发送完响应”也可同时成立：响应可能已从服务端发出，却在到达客户端前丢失、延迟，或因客户端已放弃接收而无效。

对非幂等写操作，`DEADLINE_EXCEEDED` 应归类为**结果未知**。正确后续动作是按操作 ID 查询状态、读取资源版本或使用幂等键核证；不能把超时当作“未执行”的证明后直接重试。服务端则应在副作用前后检查取消，并记录可查询的操作结果，而不是承诺“收到取消就一定没有改动”。

### 结果未知后的核证路径

### 结果未知后的核证路径

以即时消息“向用户发送一条消息”为例，客户端在发起写请求前生成全局唯一的 `message_id`，并将其作为业务幂等键随请求提交。`message_id` 应稳定地标识“这一次发送意图”，而不是某次网络尝试；超时后重连、切换网络或更换 gRPC 通道，都必须复用同一个 ID。

一次调用得到 `DEADLINE_EXCEEDED`、连接断开或代理 `504` 时，客户端只能得出：

> 请求结果未知：服务端可能未收到、已接收未完成、已持久化但响应丢失，或已投递到下游。

因此不应直接再发一条新消息，而应进入核证流程：

1. **查询状态**：调用 `GetMessageStatus(message_id)`，返回“不存在、处理中、已接受、已投递、失败”等明确状态。
2. **等待或轮询处理中状态**：服务端可能已落库并正在异步投递；客户端可按退避策略查询，或订阅状态事件。
3. **以同一 ID 重提，而非新建**：若状态确为“不存在”，可携带原 `message_id` 重试。服务端对该 ID 建立唯一约束或幂等记录：
   - 首次请求：创建消息记录并开始投递；
   - 重复请求：返回已存在记录的当前结果；
   - 同一 ID 但内容、接收者不同：返回 `409`，拒绝把冲突意图伪装成重试。
4. **记录可审计结果**：幂等记录至少保存请求摘要、处理状态、下游投递标识、最终错误及过期策略，使人工排障也能按 ID 核证。

`grpc-status=OK` 只说明该 RPC 在协议层成功结束；若一个流中承载多条设备指令或消息，它不能证明每条都已被目标设备接收。应为每条消息保留独立 ID、独立状态和应用确认，并在取消或 deadline 到期后继续让服务端按幂等记录收敛结果。

### 流式写入的阶段性确认

### 流式写入的阶段性确认

在流式 RPC 中，客户端一次 `Send` 或写入返回成功，通常只说明消息**已被本地 gRPC 运行时接受**；它可能仍在用户态缓冲、等待 HTTP/2 流窗口、等待连接窗口，甚至尚未离开进程。慢消费者、拥塞控制、服务端未及时读取都会使后续写入被流控阻塞。

应把“写入成功”拆成至少四个阶段：

1. **本地接收**：客户端库接收消息，可能仅进入本地队列。
2. **网络发送**：消息被编码为帧，并在连接与 stream 窗口允许时发出；这不等于对端应用已读取。
3. **服务端处理**：服务端 gRPC 运行时收到并交给业务处理器；deadline 或取消可能恰在此前后发生。
4. **应用持久化**：业务完成数据库提交、设备下发或外部系统调用。这才是写操作可核证的业务结果。

因此，不能把“客户端循环发送完 N 条消息”理解为“服务端已处理 N 条”，也不能把最终 `grpc-status=OK` 推断为每条消息、每台设备都成功。`OK` 只描述这次 RPC 的整体终态，不能替代逐条业务回执。

若一个 stream 承载多条命令，应为每条消息携带稳定的操作 ID，并由服务端返回应用级确认，例如“已接收”“已持久化”“已执行”及失败原因。客户端超时、取消或断连后，应按操作 ID 查询这些确认记录，而不是直接重发。对于同一 ID 的重复写入，当前语义应明确为 **409**；这表示请求冲突，不能把它当作可安全重试的信号。

### 多消息流的确认与取消

### 多消息流的确认与取消

设客户端在一个双向流中连续推送 100 条即时消息。最终收到 `grpc-status=OK`，最多只能说明：该次 RPC 在 gRPC 协议层正常结束；它**不能逐条证明** 100 条消息都已到达目标设备、更不能证明都已持久化或展示。

流中应为每条消息携带稳定的 `message_id`，并由服务端返回逐条应用确认，例如：

- `accepted`：服务端已校验并接受该消息；
- `persisted`：消息已写入业务存储或可靠队列；
- `delivered`：目标设备已收到；
- `displayed`：用户侧已展示，若业务确实需要该语义。

确认必须关联 `message_id`，而非只报告“已处理到第 80 条”。因为流可能出现重连、重复发送、乱序处理或部分失败；同一 ID 的重复写入还应按既定规则返回 `409`，不能把“重试”默认为安全覆盖。

取消同样是逐条问题。客户端 deadline 到期后取消流，服务端可能已经接收第 1～60 条，正在处理第 61 条，其余消息则尚未读取。服务端应停止接收后续数据，并为已接受但未完成的消息定义策略：继续可靠投递、标记取消，或交由后台任务完成；不能把取消误解为自动回滚。

建议按阶段记录 `stream_id`、`message_id`、入流、框架写入、服务端接收、业务持久化、设备确认、取消原因和 deadline 耗尽时间。遇到超时或连接断开时，客户端据此查询未确认消息的真实状态，而不是根据最终缺失的 `OK` 盲目重发。

> **要点** — DEADLINE_EXCEEDED与取消只说明等待或传输中断；写操作是否生效必须依靠幂等ID与状态核证。

协议选择应从用户需求、既有合同与运行约束出发，而非从“更高版本”或“单连接”标签出发。

### 先画出通信约束图

### 先画出通信约束图

协议选择前，先把通信路径上的约束写成一张图，而不是直接比较 HTTP/2、HTTP/3、WebSocket 或 gRPC 的“性能”。至少标出：

- **用户端**：是浏览器、移动端、桌面端还是服务器？浏览器可稳定使用的 API 是普通 `fetch`、流式响应、WebSocket，还是受限于特定运行环境；旧客户端能否升级。
- **入口代理与网络**：CDN、负载均衡、反向代理分别终止什么协议，是否支持连接升级、长连接、HTTP/2 转发、HTTP/3，企业代理或弱网是否会阻断新能力。
- **服务边界**：外部 `/v1` 已承诺的请求、响应、鉴权和错误合同是什么；内部调用是否真的需要跨语言的类型化接口，还是普通 HTTP 已足够。
- **连接规模**：在线用户数、每用户连接数、连接存活时间、重连峰值，以及代理和服务实例可承受的文件描述符、内存与端口压力。
- **流量形状**：请求是短小读写、批量上传、持续推送，还是双向实时交互；是否存在慢消费者、突发广播、严格顺序或取消需求。
- **失败路径**：断网、代理超时、版本不支持、限流、上游失败分别如何暴露给客户端；哪些错误可重试，哪些必须转换为既有 `/v1` 错误语义。

例如，可先提出候选：外部 `/v1` 保持现有 HTTP 合同；实时通知评估 WebSocket；内部只读查询在确认存在类型化跨服务需求后再评估 gRPC。图中还应注明旧端回退路径、协议版本观测字段和错误转换表；它们与“能否连通”同样属于协议设计的一部分。

### 外部HTTP合同与实时通道

### 外部HTTP合同与实时通道

外部 `/v1` 首先是面向浏览器、移动端、代理和网关的**稳定合同**；HTTP 版本是承载方式，不应自动改变资源路径、认证、幂等语义、状态码或错误体。

| 方式 | 浏览器与代理适配 | 请求—响应 | 持续推送 | 适用判断 |
|---|---|---|---|---|
| HTTP/1.1 | 最广泛，基础设施成熟 | 一请求一响应；可复用连接但并发受限 | 轮询、长轮询或事件流 | 兼容优先、普通接口流量 |
| HTTP/2 | 浏览器普遍支持，但需确认代理终止与转发能力 | 单连接多路复用，适合并发请求 | 仍可用事件流；不等同双向实时通道 | 页面或客户端存在大量并发 API 请求 |
| HTTP/3 | 浏览器支持逐步完善，网络、负载均衡和观测链路需验证 | 基于 QUIC，弱网切换时可能更有利 | 可承载事件流，但部署复杂度更高 | 有明确网络收益证据后再试点 |
| WebSocket | 浏览器 API 成熟；代理、超时和连接治理要专项确认 | 不以单次请求响应为中心 | 全双工、低延迟持续消息 | IM 消息、在线状态、输入状态等实时交互 |

IM 不应因“需要实时”而把全部 API 改成 WebSocket。登录、拉会话列表、历史消息分页、上传附件等仍适合维持 HTTP 合同；WebSocket 只承接连接建立后的增量事件与客户端上行指令。这样断线后可用 HTTP 补拉，且缓存、审计、重试和错误处理更清晰。

协议演进须准备回退：客户端可协商或降级至 HTTP/1.1，实时通道不可用时转长轮询或提示重连；服务端应记录协商出的版本、连接时长、关闭码、握手失败原因，并把 WebSocket 关闭原因转换为客户端可理解的业务错误。HTTP/2、HTTP/3 或 WebSocket 的收益必须以用户时延、失败率和资源占用验证，而非仅凭“多路复用”或“单连接”判断。

### HTTP/2与HTTP/3的收益边界

### HTTP/2与HTTP/3的收益边界

HTTP/2 的核心变化是：在一条连接上并发传输多个流，并以逐跳流控限制每个流及整条连接的发送量。它能减少 HTTP/1.1 多连接、排队建连和应用层队头等待，尤其适合浏览器同时请求较多小资源、代理与服务端均已正确支持的场景。

但 HTTP/2 的多路复用运行在 TCP 之上。若某个 TCP 分组丢失，TCP 必须先补齐该位置的数据；即使其他 HTTP/2 流的数据已到达，也可能受运输层队头阻塞影响而暂时不能交付。因此，“单连接多路复用”不等于所有请求都独立降低尾时延。拥塞、丢包率、服务端排队、代理缓冲，以及错误重试策略，仍可能主导用户感知。

HTTP/3 将流承载于 QUIC：一个流的丢包通常不阻塞其他流的有序交付，因而在移动网络、网络切换或存在较明显丢包时，可能改善并发请求的相互牵连。不过它仍受共享拥塞控制、连接级流控和服务端资源限制约束；大流量下载也可能挤占小消息的发送机会。

因此，升级应验证实际流量形状：并发流数、消息大小、丢包与切网比例、代理链路支持度，以及首字节、完成时延和失败率。若瓶颈是后端慢查询或连接级限额，换成 HTTP/2 或 HTTP/3 不会自动消除它。

### 内部gRPC的候选条件

### 内部 gRPC 的候选条件

gRPC 适合被评估为**内部服务间**的候选方案，而非因为“性能更高”就替换现有 HTTP 接口。一个较窄且可验证的起点是：多个服务之间存在稳定的、频繁的**只读查询**，调用方需要明确的请求/响应类型、字段校验、代码生成与跨语言一致性，例如“按用户标识批量查询会话摘要”。

方法边界应按业务能力划分，而不是直接暴露数据库表或通用 CRUD：

- 合适：`GetConversationSummary`、`BatchGetUserPresence`；
- 不合适：`Query(sql)`、`GetById(table, id)`；
- 读取接口应声明分页、批量上限、超时和“未找到”的语义，避免调用方依赖底层存储细节。

`protobuf` 演进必须默认兼容旧调用方：

- 字段编号一经发布不得复用；删除字段后应保留编号并标记为 `reserved`。
- 新增字段应是可选增量，旧客户端必须能忽略它；不要把新增字段立即当作必填前提。
- 枚举值只能追加，调用方需能处理未知枚举值。
- 不要改变既有字段的编号、含义或线格式；“名称相近”不代表语义兼容。

例如，可先定义：

`rpc BatchGetUserPresence(BatchGetUserPresenceRequest) returns (BatchGetUserPresenceResponse)`

并明确空结果、部分命中、权限不足、限流与上游超时分别映射为何种状态。若未来采用 gRPC，还需保留现有外部 `/v1` HTTP 合同，并建立 HTTP 错误与内部状态码的转换表、版本观测和回退路径。这里仅是设计候选，是否部署仍应以兼容回归、用户时延、失败率和资源消耗测量为准。

### 兼容回退与验证闭环

### 兼容回退与验证闭环

协议升级不能只验证“新链路可用”，还必须证明旧端、旧代理和失败路径仍按既有合同工作。先把外部 `/v1` 的请求格式、状态码、错误体、幂等语义和超时约定固定下来；内部即使试用 HTTP/2、HTTP/3 或 gRPC，也不应把传输层错误直接泄漏给用户端。

兼容与回退至少明确以下内容：

- **旧端范围**：列出仍可能使用 HTTP/1.1、旧版 WebSocket 实现或不支持新认证字段的客户端版本，并定义支持截止时间。
- **协商与降级**：新协议握手、代理转发或连接建立失败时，是否自动回退至 HTTP/1.1；回退次数、超时预算和重试边界必须有限，避免“升级失败—重试—降级”放大流量。
- **错误转换表**：将内部的超时、限流、上游不可用、协议协商失败等，稳定转换为外部约定的状态码与业务错误码。例如内部 `UNAVAILABLE` 不应原样暴露，而应映射为既有的“服务暂不可用”错误。
- **版本可观测性**：日志、指标和追踪中记录客户端版本、协商协议、代理路径、回退原因及最终错误码。否则只能看到失败率，无法判断是某个旧端、某层代理还是新协议实现造成问题。

上线验证以合同和业务结果为准，而非以连接数下降为准。先用固定合同回归覆盖正常响应、超时、取消、重复请求、限流和降级；再灰度比较新旧路径的用户时延、消息送达失败、重连率、服务端连接与资源消耗。若核心业务指标恶化，能够按用户群、入口或协议版本快速切回旧路径，才构成完整的验证闭环。

> **要点** — 先明确合同、路径与流量约束，再选择协议；升级必须可回退、可观测并以业务结果验证。

本节以虚构 IM 的外部 HTTP 与内部 RPC 为线索，辨清协议层、流控边界、状态含义及兼容重试决策。

### 应用路径不等于 HTTP 版本

### 应用路径不等于 HTTP 版本

`POST /v1/messages`、`GET /users/{id}` 这类路径属于**应用接口设计**：它表达资源或操作入口，并约定认证、参数、响应体、业务错误等合同。路径中出现 `/v1` 通常只是应用自己的版本策略，不表示底层必然使用 HTTP/1.1、HTTP/2 或 HTTP/3。

应分四层理解：

- **应用路径与方法**：如 `POST /v1/messages`，说明客户端要调用“发送消息”这一应用操作。
- **HTTP 语义**：方法、状态码、首部、缓存语义等。例如 `POST` 不天然可安全重试，`401` 表示认证问题，`429` 表示请求过多。
- **HTTP 版本**：HTTP/1.1、HTTP/2、HTTP/3 定义报文交换及复用方式。HTTP/2 可让多个 stream 的帧交错；HTTP/3 建立在 QUIC 上，减少传输层队头阻塞影响。
- **内部 RPC 合同**：如 `SendMessage(request) -> response` 的方法名、字段、错误码与流式规则。它定义可调用操作及请求/响应结构，但不会自动完成授权、幂等、业务批准或结果确认。

因此，同一个 `/v1/messages` 可通过 HTTP/1.1、HTTP/2 或 HTTP/3 对外提供；网关也可将其转换为内部 gRPC 的 `SendMessage`。反过来，内部 RPC 方法名并不能推出外部 URL，更不能据此判断使用了哪一代 HTTP。

一个常见误判是：“路径含 `/v1`，所以客户端使用 HTTP/1。”正确结论应是：前者是**应用合同版本**，后者是**传输协议版本**；二者可独立演进。

### HTTP/2 多路复用与逐跳流控

### HTTP/2 多路复用与逐跳流控

HTTP/2 将一条 TCP 连接划分为多个逻辑 `stream`。每个请求或响应不再必须连续占用连接，而是被拆成帧；发送端可以交错发送不同流的帧：

`流 1：HEADERS → DATA(部分)`  
`流 3：HEADERS → DATA(部分)`  
`流 1：DATA(剩余)`

因此，多路复用解决的是**应用层请求彼此排队**的问题：慢响应不必阻止其他流的帧被调度。但它不意味着各流拥有完全独立的传输命运。

流控至少有两层窗口：

- **流级窗口**：限制某一 `stream` 尚未被接收方确认消费的数据量；
- **连接级窗口**：限制整条 HTTP/2 连接上所有流合计的未消费数据量。

若连接级剩余窗口为 `W_c`，各流可发送额度为 `W_1,W_2,\ldots`，则总发送量还必须满足：

$$\sum_i \text{未确认数据}_i \le W_c$$

即使流 7 自己的窗口充足，只要其他流已耗尽连接级窗口，流 7 也必须等待 `WINDOW_UPDATE`。这说明流控是**逐跳**的：客户端到代理、代理到服务端各自维护窗口；某一跳的窗口更新不能直接推断另一跳的消费状态。

更重要的是，HTTP/2 通常运行在 TCP 之上。TCP 提供的是单一有序字节流：若某个较早的 TCP 报文丢失，后续已到达的数据即便属于另一 HTTP/2 流，也可能因等待缺失字节而不能交付给 HTTP/2 解析器。这就是传输层队头阻塞。HTTP/2 能避免“一个 HTTP 请求占满应用连接”，却不能消除“一个 TCP 丢包拖住多个流”。

因此，观察到某个流变慢时，不能立刻归因于该流的业务处理；它也可能受连接级窗口、同连接大流量竞争，或 TCP 丢包恢复影响。

### HTTP/3 的 QUIC 流：收益与边界

### HTTP/3 的 QUIC 流：收益与边界

HTTP/2 通常运行在 TCP 之上：多个 HTTP stream 虽可在应用层交错发送帧，但底层共用一条 TCP 字节流。若某个 TCP 报文丢失，TCP 必须先补齐缺失字节；其后到达的数据即使属于其他 HTTP stream，也可能等待交付。这是**传输层队头阻塞**。

HTTP/3 改用 QUIC。QUIC 在 UDP 之上提供多个独立的可靠、有序 stream：某一 stream 的数据包丢失时，其他 stream 中已完整的数据通常仍可交付。因此，它改善的是“一个流丢包拖住其他流”的问题，而不是让网络不再丢包或无限快。

| 维度 | HTTP/2 over TCP | HTTP/3 over QUIC |
|---|---|---|
| 多路复用 | HTTP 帧可交错 | HTTP 帧可交错 |
| 丢包影响 | TCP 字节流可能阻塞多个 stream | 通常主要阻塞对应 QUIC stream |
| 可靠性与顺序 | TCP 提供 | QUIC 各 stream 提供 |
| 拥塞控制 | 连接级 | QUIC 连接级 |
| 流量控制 | 连接及 HTTP/2 stream 相关限制 | QUIC 连接级与 stream 级限制 |

因此，“HTTP/3 没有队头阻塞”并不准确；更准确地说，它避免了 **TCP 层跨 stream 的队头阻塞**。若网络整体拥塞、连接级流控窗口耗尽、服务端处理慢、CPU 加密开销高，所有流仍可能变慢。

纸上判断时应区分两类结论：

- 某个流丢包，不能直接推出其他 QUIC 流也必须等待。
- 某条连接拥塞或连接级额度不足，可以同时限制多个流。
- HTTP/3 是否一定比 HTTP/2 更快，不能静态断言；需结合丢包率、往返时延、实现质量、负载与连接复用情况测量。

### gRPC 合同、状态与业务受理

### gRPC 合同、状态与业务受理

内部 RPC 合同应明确“可调用什么”和“每次调用交换什么”，而不能把传输成功误写成业务完成。例如 IM 可定义：

- `SendMessage(request) returns (SendMessageReply)`
- 请求含 `conversation_id`、`client_message_id`、`body`；
- 响应含 `message_id`、`accepted_in_memory`，必要时含拒绝原因或当前限制。

`protobuf` 的字段号是线格式的一部分：已发布字段不得随意改号、删除后重用，也不应把原字段号赋给不同语义。新增字段通常可保持旧客户端兼容；旧客户端忽略未知字段，新服务端则应为缺失字段定义安全默认值。枚举值、`oneof` 分支和必填业务语义也要考虑旧版本无法理解时的降级策略。

一次调用至少有三层结果，必须分开判断：

1. **HTTP 200**：HTTP/gRPC 承载层成功建立并完成了本次响应交换；它不等于 RPC 一定成功，更不等于消息已持久化或已送达。
2. **`grpc-status` 为 `OK`**：该 RPC 按 gRPC 语义正常结束。若状态位于 trailers，不能只看响应头或 HTTP 状态码；`UNAVAILABLE`、`DEADLINE_EXCEEDED` 等则表示 RPC 结果未可靠取得。
3. **`accepted_in_memory=true`**：服务端已把提案放入当前内存队列或缓冲区。这仍不等于已写入数据库、已获会话成员批准、已广播，更不等于对方已读。

因此，若客户端超时后未看到最终 `grpc-status`，不能据此断言“未发送”：服务端可能已执行。应依靠 `client_message_id` 幂等去重，并按业务确认点查询消息是否已持久化、批准或投递。取消 RPC 也只是停止等待或请求终止，不能自动回滚已经发生的业务动作。

### 截止时间、取消与重复提交决策

### 截止时间、取消与重复提交决策

截止时间与取消首先约束的是**调用等待**，不是业务动作的原子回滚承诺。客户端在截止时间到达后收到超时、主动取消请求，均不能推出“服务端未执行”：

- 请求可能尚未到达服务端，此时可安全按未执行处理；
- 服务端可能已接收并开始执行，但响应尚未返回；
- 服务端可能已完成写入，只是响应帧、状态或 trailers 在链路中丢失。

因此，取消只能表达“客户端不再等待结果”。除非 RPC 方法明确提供撤销语义，并以业务状态确认撤销成功，否则不能把取消当作删除、退款或消息未发送的依据。

遇到 `409` 也不能机械重试。若其表示重复提交 ID 冲突，应先区分：

1. **同一请求 ID、同一业务载荷**：查询该 ID 对应的既有结果；若服务端返回已完成结果，可将其视为幂等重放，而非重新创建。
2. **同一请求 ID、不同业务载荷**：这是调用方生成或复用 ID 的错误，重试会扩大歧义，应停止并人工或业务侧修复。
3. **服务端尚未形成最终结果**：只能依据接口定义轮询、查询或等待，不能改用新 ID 再提交，否则可能产生重复业务对象。

安全的确认点应是业务合同规定的状态，例如“消息已被服务端持久化并分配消息 ID”，而非“HTTP 已发出”“客户端取消成功”或“框架已接收字节”。为支持这种判断，请求应携带稳定的幂等键；其字段号一旦投入使用便不可重用或改号。字段号标识线上的编码含义，未来即使删除字段，也应保留其编号，避免旧客户端的数据被新版本误解释。

> **要点** — 协议版本、RPC 状态和业务受理是不同层；流控逐跳生效，重试必须依赖幂等与明确确认点。
