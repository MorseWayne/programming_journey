# 07.04 审阅记录：缓存过载与热点

## 教学重组

- 一个热键在首个回填前有 1000 个同时 miss，朴素路径产生 1000 次回源；权威 DB 本题安全能力 200/s。若无拒绝、第一秒最多完成 200，至少 800 未完成；**只一批**的理想排空约 5 秒，**持续 1000/s** 则积压每秒净增 800，两类条件分开。
- 四个独立网关各收 250 次 miss，进程内同键 singleflight 理想各回源一次，共 4 次而非全局 1 次。leader 超时/崩溃和不同键并发仍需有界等待与回源预算。
- 100 个键同刻失效、各 10 次同时 miss 得 1000 次；均匀错开至 10 秒的理想量级为 100/s，但随机 TTL 不保证均匀，也不解决单热键击穿或缓存整体清空。
- 1000 个各不相同且真不存在的 ID，逐 ID 负缓存对**第一批**仍需 1000 次权威查询；重复同一 ID 才可能复用。私有隐藏 404 不可按 ID 全局负缓存。
- 热键每秒 1000 次 hit 可压 Redis，不必回源；10000 成员 Set 一次 `SMEMBERS` 全取属于大键操作。两者不同，也不能拿候选成员 Set 直接授权。

## 技术修订

- 原稿不同段落把“1000 次同刻突发”和“持续 1000/s”都写成同一积压公式，容易误认一次突发会永远净增 800/s。正式页把第一秒剩余量、一次性批次排空和持续到达增长率分别列条件。
- 原稿给出了虚构的固定等待 80 ms、预览陈旧 30 s 等工程参数；正式页只讲**有界**等待/陈旧及业务合同，避免把未经负载验证的示意值误当推荐配置。
- 原稿部分 singleflight 段落倾向把跨进程 Redis 锁当“接近全局一次加载”；正式页强调分布式锁有租约、迟到写和失败回退问题，不能凭加锁宣称跨进程正确或恰好一次。
- TTL 抖动只缓解多键同刻过期；负缓存对随机新 ID 首查无效；缓存 hot hit 与大键全取的压力来自缓存层，不是同一个数据库击穿原因。
- 缓存故障时旧预览只在产品容许且权限安全时可降级，退群后的旧成员许可绝不可为保障可用性放行发送。容量和 P95 不能由纸上倍率直接推出。
