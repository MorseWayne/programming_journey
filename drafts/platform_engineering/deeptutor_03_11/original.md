排查容器超时时，先界定观察范围：主机空闲不等于网关进程拥有足够的可运行资源。

### 先确定指标属于谁

### 先确定指标属于谁

排查超时时，第一步不是看“机器忙不忙”，而是问：**这个指标描述的是谁的资源？**

- **主机层**：8 核宿主机总 CPU 使用率 10%，只说明整台机器大部分计算能力未被所有进程用掉。
- **容器层**：网关若被 cgroup 限制为 `0.5` 核，它在一个周期内可获得的 CPU 配额远小于主机总量。
- **进程层**：真正处理 HTTP 请求、校验静态合同、写入内存状态的是网关进程及其 Go 运行时线程；它们是否能及时被调度，取决于容器配额、节流、队列和自身并发。

例如，网关在 1 秒内累计使用约 `0.48` 核秒。相对于宿主机 8 核，这只占约 `6%`；但相对于容器的 `0.5` 核额度，已接近：

$$0.48 / 0.5 = 96\%$$

因此，即使宿主机仍显示空闲，容器也可能频繁接近配额并出现 CPU 节流；请求 A 的处理时间随之拉长，客户端便可能先看到超时。这里的数字用于说明观察作用域，并非某个实际运行环境的监控结论。

同样，协议语义也必须归属到网关实例：当前 S2/v1 的静态合同正文为 6 UTF8B，原始 HTTP 请求正文上限为 4096B；同一 ID 返回 `409`，非成员返回 `404`，`200 accepted_in_memory` 仅表示已在内存中受理，并不表示已持久化或跨实例可见。未来 S3 的提议不能倒灌为当前行为。

### 命名空间改变你看到的世界

### 命名空间改变你看到的世界

容器并不是一台真正独立的机器；它本质上仍由宿主机内核调度。但 Linux 命名空间会给进程提供不同的“视图”，因此同一时刻，宿主机与容器内看到的世界可以明显不同。

- **PID 命名空间**隔离进程编号与进程列表。容器中的应用常把自己看到为 `PID 1`，只能枚举本命名空间及其子空间中的进程；宿主机却能看到该容器进程以及其他容器、系统服务。于是，容器内执行 `ps` 看不到大量宿主进程，不代表它们没有竞争 CPU。

- **挂载命名空间**隔离文件系统挂载视图。容器看到的是镜像层、卷挂载和自己的根目录；宿主机可看到实际的容器存储路径、其他磁盘与挂载点。容器内“磁盘还有空间”的判断，也只是在其可见文件系统范围内成立。

- **网络命名空间**隔离网络栈。每个容器可拥有独立的网卡、路由表、端口、iptables 规则和 `localhost`。网关容器访问 `127.0.0.1:8080` 时，通常访问的是容器自身，而不是宿主机上的服务；宿主机端口空闲，也不能直接推出容器内网络路径正常。

- **用户命名空间**隔离身份映射。容器内的 `root` 可以映射为宿主机上的普通或受限 UID。因而“容器内是 root”不必然拥有宿主机 root 的文件、设备或管理权限。

这些隔离改变的是**可观察对象与身份解释**，不是资源凭空独占。网关容器虽然看不见宿主机上的其他进程，仍可能受到 cgroup 的 CPU 配额限制：例如宿主机 8 核总使用率仅 10%，而网关被限为 `0.5` 核；若 1 秒已使用 `0.48` 核秒，约达到额度的 `$96\%$`，后续请求仍可能因节流而变慢。这里是推导示例，不表示实际运行状态。

### 半核配额下的超时推演

### 半核配额下的超时推演

设想一台宿主机有 8 个逻辑核，监控显示总 CPU 使用率约为 10%。这只说明整机平均大约使用了：

\[
8 \times 10\%=0.8\text{ 核}
\]

从主机视角看，仍有大量空闲算力；但网关容器若被 cgroup 限制为 `0.5` 核，它在一个调度周期内可获得的 CPU 时间并不会因为宿主机空闲而自动增加。

假设该网关在 1 秒内实际消耗了 `0.48` 核秒，则相对于自身配额的使用率为：

\[
\frac{0.48}{0.5}\times100\%=96\%
\]

`96%` 不一定立即意味着请求失败，却表示容器已非常接近配额边界。若同一秒又出现 JSON 编解码、日志写入、连接处理、垃圾回收或突发并发请求，容器可能用尽可分配的 CPU 时间，随后被节流。此时请求 A 即使没有阻塞在网络或数据库上，也可能只是迟迟得不到继续运行的机会，最终表现为响应变慢或超时。

因此应分别观察：

- 宿主机：整体 CPU 是否繁忙；
- 进程：网关自身实际消耗了多少 CPU；
- 容器：`0.5` 核配额、配额使用率与节流次数是否上升。

上述数字仅用于推演观察作用域，不表示某个实际网关正在以该方式运行。

### 内存、进程数与连接不是一回事

### 内存、进程数与连接不是一回事

“容器资源不足”不能只理解为内存不足。cgroup、Go 运行时和操作系统分别统计不同对象，排查时必须先问：**到底是哪一种额度触顶了？**

- **cgroup 内存**约束容器整体可计费内存，通常包括匿名页、页缓存等；超过 `memory.max` 可能触发 OOM。OOM 事件说明内核因内存限制参与了处置，但不等价于“Go 堆太大”。
- **Go 堆**是 Go 运行时管理的对象内存。堆增长会提高垃圾回收压力，却只是进程内存的一部分；`GOMEMLIMIT` 是运行时的软目标，并不能替代 cgroup 硬上限。
- **RSS**（常驻集）表示当前驻留物理内存的页面，除 Go 堆外还可能含 goroutine 栈、运行时元数据、动态库、`mmap` 区域等。因此，`HeapAlloc` 较小而 RSS 较高并不矛盾。

进程数也不是连接数。`pids.max` 限制的是 cgroup 可创建的任务数；在 Go 中，一个 goroutine 不是一个内核进程，通常也不是一个独立线程，所以“连接很多”不必然首先撞到 `pids.max`。但阻塞调用、线程扩张或子进程创建仍可能消耗该额度。

文件描述符上限限制的是套接字、文件、管道等打开句柄。一个长期 HTTP 连接通常至少占用一个套接字描述符；大量未关闭连接可能先导致“打开文件过多”，即使内存和进程数仍有余量。

因此，连接超时应分别查看：内存当前值与 OOM 计数、Go 堆与 RSS、`pids.current`、文件描述符使用量，以及活动连接数。它们相关，但没有一一对应关系。

### 用 S2 受理合同审查恢复结论

### 用 S2 受理合同审查恢复结论

S2/v1 的结论必须限定在“**当前进程存活期间的内存受理**”，不能从一次 `200` 推导出重启后仍可查询、可去重或可恢复。

- 静态合同正文为 **6 UTF8B**；这是合同规定的响应正文，不应擅自附加诊断信息。
- 原始 HTTP 请求正文最大为 **4096 B**。超过该边界应在进入业务受理前拒绝，避免网关在受限 CPU 下为超大正文持续分配、解析和排队。
- 对同一成员重复提交同一 ID，返回 **409**：它表达当前内存中的 ID 冲突，而非“历史上曾经成功持久化”。
- 非成员访问返回 **404**：该结果优先说明调用方不具备成员可见性，不能据此判断目标 ID 是否存在。
- 新请求成功进入内存状态后返回 **200**，其语义仅为 `accepted_in_memory`，即本进程已受理；它不承诺磁盘落盘、跨副本同步或重启恢复。

因此，网关即使在主机总体 CPU 使用率较低时发生超时，也不能通过“客户端已得到 `200`”否定资源隔离或节流的影响；`200` 只证明当时受理路径完成。若容器重启，内存中的成员关系、已受理 ID 与去重状态都可能消失，随后同一请求可能不再得到原先的 `409`，非成员也仍可能得到 `404`。

“重启后恢复受理记录、保持跨重启幂等性、查询历史状态”应明确标注为**未来 S3 提议**，需要引入持久化存储、恢复顺序与一致性规则；这些能力不属于 S2/v1 当前合同。

> **要点** — 主机空闲只能说明宿主机视角；网关超时应优先按容器配额、隔离视图和进程实际资源逐层判断。

主机看似空闲时，容器内的 IM 网关仍可能超时；先要厘清：namespace 改变的是“看见什么”，并不直接分配 CPU、内存或安全保证。

### 先分清三种观察范围

### 先分清三种观察范围

排查容器超时时，至少要同时区分三层观察范围：**宿主机视图、容器视图、进程所在 namespace 视图**。它们由同一个宿主内核驱动，却不必看到同一组对象。

- **进程号视图**：容器中的 `PID 1` 通常只是该 PID namespace 的第一个进程；在宿主机上，它可能是 `PID 24873`。因此，容器内执行 `ps` 看不到宿主机全部进程，宿主机却能看到该容器进程。
- **网络视图**：容器的 `127.0.0.1` 指向本容器网络 namespace 内的回环接口，不是宿主机回环，也不是另一个容器。网关连 `127.0.0.1:8080` 超时，可能只是容器自身没有服务监听该端口。
- **文件系统视图**：容器看到的是自己的 mount namespace。容器内的 `/etc/hosts`、`/var/log`、`/tmp` 或挂载卷，可能与宿主同路径完全不同；宿主存在某个证书或套接字文件，不代表容器也能访问。

还要注意：同一容器内的进程通常共享这些视图，但也可以被单独放入新的 network、mount 等 namespace。于是“主机端口正常”“主机文件存在”“主机进程仍在”都只是宿主侧事实，不能直接推出 IM 网关所在进程也能看见、连通或使用它们。

### PID 与 UTS：容器内的“一号进程”

### PID 与 UTS：容器内的“一号进程”

PID namespace 为同一进程提供不同的编号视图。容器启动的入口进程通常在容器内显示为 `PID 1`，但在宿主机上它往往对应另一个普通 PID，例如：

- 容器内：`nginx` 是 `PID 1`
- 宿主机：同一 `nginx` 可能是 `PID 24873`

因此，容器里的 `ps` 看不到宿主机其他进程；宿主机却能看到该容器进程及其真实宿主 PID。父 namespace 可以观察子 namespace，反向通常不成立。

`PID 1` 还具有特殊语义：它应负责回收孤儿子进程，并正确处理终止信号。若入口脚本只是简单启动应用、未转发 `SIGTERM` 或未执行 `wait`，可能出现停止容器缓慢、僵尸进程积累等问题。它不是“宿主 init”，只是该 PID 视图中的一号进程。

UTS namespace 则隔离主机名与域名。容器内执行 `hostname`，看到的是容器自己的名称；修改它通常不影响宿主机或其他容器。于是日志中的主机名、监控标签和服务自报身份可能彼此不同。

但要注意：PID 与 UTS 隔离只改变进程编号和机器身份的观察结果，既不保证应用获得更多 CPU，也不意味着 `PID 1` 卡住时网关请求就不会超时。

### mount 与 net：目录和本地地址并非主机全貌

### mount 与 net：目录和本地地址并非主机全貌

排查 IM 网关超时时，最容易犯的错误是把容器中的“本地”直接等同于主机本地。`mount namespace` 与 `net namespace` 分别改变目录树和网络栈的观察视图。

例如，网关容器内配置：

`/var/log/im-gateway/access.log`

该路径可能来自镜像层、匿名卷，或被单独挂载到容器内；主机上的同名路径未必存在，也未必是同一份文件。容器内看到磁盘写满、日志无法追加时，应检查容器实际挂载：

`/proc/self/mountinfo`

以及运行时声明的卷、绑定挂载。不能仅凭主机 `/var/log` 尚有空间，就断言容器日志写入正常；容器可能写到容量受限的卷、只读挂载，或已经失效的网络文件系统。

网络视图同样如此。容器内连接：

`127.0.0.1:8080`

默认连接的是**该容器网络命名空间内**的回环地址，而不是主机上的 `127.0.0.1:8080`，也不是另一个容器的本地端口。若 IM 网关把 Redis、认证服务或本地代理写成 `127.0.0.1`，而目标服务实际运行在主机或其他容器中，连接通常表现为拒绝、超时或不断重试。

因此应分别确认：服务监听在哪个网络命名空间、端口是否发布、容器应通过服务名或宿主网关地址访问。只有使用主机网络模式时，容器的网络视图才会更接近主机；这仍不意味着目录挂载视图也相同。

### user namespace：映射后的身份不是无限权限

### user namespace：映射后的身份不是无限权限

`user namespace` 将“身份编号”和“权限判断范围”分开。容器内看到的 `root` 通常是 `UID 0/GID 0`，但它不必等于宿主机上的 `UID 0`。例如可配置映射：

| 容器内身份 | 宿主对应身份 |
|---|---|
| `UID 0` | `UID 100000` |
| `UID 1` | `UID 100001` |

于是，进程在容器内可以以 `root` 身份安装软件、修改容器文件系统中归其映射范围所有的文件、管理其子进程；但宿主内核在检查宿主资源时，会按映射后的 `UID 100000` 判断，而不是把它当作宿主超级用户。

这解释了两个常见现象：

- 容器内 `id` 显示 `uid=0(root)`，却无法读取宿主 `/root`、修改宿主敏感文件或加载内核模块。
- 挂载进容器的宿主目录若属宿主 `UID 0`，而容器 root 映射为 `UID 100000`，容器内 root 仍可能遇到“权限被拒绝”。

权限还取决于 capability、挂载选项、LSM 策略及运行时配置。即使进程在某个 user namespace 中拥有较多 capability，也通常只在该命名空间及其可管理对象上有效；跨到初始 user namespace 的宿主全局资源时，权限并不会自动升级。

因此，应区分三句话：容器内是 root、映射到宿主的哪个 UID/GID、该进程对目标内核对象是否真正具备权限。前两者成立，不推出第三者成立；反过来，错误地以特权模式运行、共享宿主命名空间或授予高危 capability，又可能削弱这种隔离。

### 隔离视图不能解释资源额度

### 隔离视图不能解释资源额度

namespace 的职责是改变进程的“观察坐标系”，不是授予资源配额。IM 网关容器中的 `127.0.0.1` 指向自身网络命名空间，容器 PID 1 也只是该 PID namespace 的 1 号进程；它们都不能说明该进程实际获得了多少 CPU、内存、文件描述符或网络带宽。

因此，主机负载低而网关超时，不能仅凭“容器隔离”解释。应优先区分以下问题：

- **CPU 与内存额度**：由 cgroup 控制。容器可能被设置了很低的 CPU quota、CPU weight、内存上限或 `pids.max`；宿主总体空闲，不代表该 cgroup 尚有可用额度。
- **Go 运行时行为**：Go 可能依据 cgroup 感知到的 CPU 数调整并发度；`GOMAXPROCS`、GC、连接池、goroutine 堆积也会使请求排队，即使宿主还有大量空闲核。
- **网络视图与网络质量**：net namespace 决定路由、接口和本地回环的可见性；但超时还可能来自 conntrack、DNS、代理、队列、丢包或远端依赖，而非 namespace 本身。
- **安全边界**：user namespace 中的“root”通常只是映射后的身份；再叠加 capability、seccomp、LSM 等限制。namespace 不是完整安全边界，也不自动阻止资源争用。

排障时应同时在两侧观察：容器内看 `GOMAXPROCS`、请求队列、连接状态和 DNS；宿主侧看该容器 cgroup 的 CPU throttling、内存事件、OOM、进程数与网络统计。先确认“看见什么”，再确认“实际能用多少”。

> **要点** — namespace 决定进程看见的世界；资源配额由 cgroup 管理，权限边界还需结合能力、策略与配置判断。

主机看似空闲时，容器仍可能因自身及祖先 cgroup 的 CPU 带宽限制被节流，最终表现为网关请求排队与超时。

### 先锁定资源观察的作用域

### 先锁定资源观察的作用域

排查“主机 CPU 很空闲，但 IM 网关容器请求超时”时，第一步不是看宿主机总 CPU 百分比，而是确认每个指标属于哪个资源作用域：

- **宿主机作用域**：`top`、`mpstat` 看到的是全机 CPU 使用情况。即使整机仅使用 10%，也只能说明其他 CPU 容量尚未被消耗，不能证明某个容器被允许使用这些容量。
- **进程作用域**：容器内进程的 CPU 时间反映它实际获得并执行的 CPU；若线程因调度等待或被限额节流，进程并不会“补用”宿主机剩余核心。
- **cgroup 作用域**：容器进程通常归属某个 cgroup，其 `cpu.max`、`cpu.stat` 决定该组可获得的 CPU 带宽；还必须检查父 cgroup，因为祖先限制同样会向下生效。

例如 `cpu.max` 为 `50000 100000`，表示每个 100 ms 周期最多运行 50 ms，即平均约 `0.5` 个 CPU 核的带宽。网关即使运行在 32 核宿主机上，也可能在一个周期内迅速耗尽这 50 ms，随后等待下一个周期恢复配额。

因此，“宿主空闲”与“容器有可用 CPU”是两个不同结论。应把宿主机 CPU 视为全局供给，把 cgroup 配额视为该容器可领取的上限；后续分析要围绕容器及其祖先 cgroup 的 `usage_usec`、节流次数和节流时长增量展开。

### 读懂 cpu.max 的配额与周期

### 读懂 cpu.max 的配额与周期

`cpu.max` 通常写作：

`$quota\ period$`

例如：

`50000 100000`

两个数的单位都是微秒，因此可直接推导：

- 周期 $period=100000\ \mu s=100\ ms$
- 配额 $quota=50000\ \mu s=50\ ms$
- 在每个 100ms 窗口内，该 cgroup 最多累计使用 50ms 的 CPU 执行时间

其持续可获得的 CPU 带宽为：

$$
\frac{quota}{period}=\frac{50000}{100000}=0.5
$$

也就是说，该容器平均最多相当于 **0.5 个逻辑核**。若宿主有 32 个逻辑核，主机监控可能显示整体 CPU 仅使用几个百分点；但对这个容器而言，它的 0.5 核预算仍可能已经耗尽。

这里的“50ms CPU 时间”是所有可运行任务的累计时间，而不是墙上时钟。若容器内只有一个忙碌线程，它大约可连续运行 50ms，随后在本周期剩余约 50ms 内被限制；若有两个线程同时在不同核上运行，它们会更快共同耗尽这 50ms，例如各运行约 25ms 就可能触顶。

因此，`cpu.max=50000 100000` 不表示“每秒只能运行 50ms”，而是表示“每 100ms 都重新发放 50ms 预算”。负载持续超过 0.5 核时，请求处理会在周期边界附近反复排队；短请求也可能恰好到达预算耗尽后，只能等待下一周期恢复，进而放大为网关超时。

### 用 cpu.stat 识别节流增量

### 用 `cpu.stat` 识别节流增量

`cpu.stat` 记录的是当前 cgroup 自创建以来的累计 CPU 统计值。判断网关是否因 CPU 配额受限，关键不是看某一刻的绝对值，而是在固定观测窗口内计算增量。

常见字段含义如下：

- `usage_usec`：该 cgroup 实际获得并消耗的 CPU 时间，单位为微秒。多核并行时可累计超过墙钟时间；例如 10 秒内增长 `20000000`，表示累计使用了 20 个 CPU 秒，平均约 2 核。
- `nr_periods`：经历过的 CPU 带宽周期数。若 `cpu.max` 的周期为 `100000` 微秒，通常约每 100 ms 增加一次。
- `nr_throttled`：发生过节流的周期数。它增长说明该周期内 cgroup 曾用尽可分配的 CPU 带宽。
- `throttled_usec`：因节流而无法运行的累计时间，单位为微秒。增长越快，说明可运行任务等待 CPU 的时间越多。

可间隔 10 秒采样两次：

`Δusage_usec = 4,800,000`  
`Δthrottled_usec = 3,200,000`  
`Δnr_periods = 100`  
`Δnr_throttled = 76`

这表示该窗口中容器实际只获得约 4.8 个 CPU 秒，却有明显节流等待；100 个带宽周期中有 76 个触发节流。即使宿主机总体 CPU 使用率很低，容器内的网关 goroutine 仍会因本 cgroup 或祖先 cgroup 的配额耗尽而排队，进而放大请求延迟。

`nr_throttled` 只表明“发生次数”，`throttled_usec` 才更接近节流造成的等待规模；两者应结合 `usage_usec` 的窗口增量一起判断。

### 为什么宿主 CPU 百分比会误导排障

### 为什么宿主 CPU 百分比会误导排障

宿主机“CPU 使用率只有 20%”回答的是：**整台机器所有逻辑核平均下来还剩多少算力**；它并不回答某个网关容器是否还能继续获得 CPU 时间。排障时至少要区分三种指标：

| 观察对象 | 它说明什么 | 常见误判 |
|---|---|---|
| 宿主总体 CPU 使用率 | 全机各核的平均忙碌程度 | 机器空闲，所以容器不可能缺 CPU |
| 容器进程 CPU 使用率 | 进程实际已运行并消耗的 CPU 时间 | 使用率不高，所以应用没有 CPU 压力 |
| cgroup 配额消耗与节流 | 在限定周期内是否已用尽允许的 CPU 带宽 | 忽略配额上限与父 cgroup 限制 |

例如 `cpu.max` 为 `50000 100000`，表示每个 $100\text{ ms}$ 周期最多运行 $50\text{ ms}$，等价于约 $0.5$ 个 CPU 核的平均带宽。即使宿主有 32 核、总体只使用了 10%，该容器在某个周期内一旦累计运行满 50 ms，剩余约 50 ms 仍会被强制等待下一周期。

因此，容器进程可能只显示“约 0.5 核”的稳定使用率；这不是它只需要 0.5 核，而可能是它**最多只能拿到** 0.5 核。突发请求到来时，工作线程、加密、序列化、日志等竞争这部分预算，未获调度的 goroutine 会堆积，请求延迟跨越超时阈值。

应结合 `cpu.stat` 看增量：`usage_usec` 表示实际获得的运行时间；`nr_throttled`、`throttled_usec` 持续增长，则直接表明配额耗尽后的等待。还要沿 cgroup 层级检查祖先限制：子容器配额未满，也可能被父 cgroup 的更小总预算节流。

### 网关超时案例与 GOMAXPROCS 边界

### 网关超时案例与 GOMAXPROCS 边界

设想 IM 网关容器配置了：

`cpu.max = 50000 100000`

这表示每个 `100ms` 周期最多获得 `50ms` 的累计 CPU 时间，即约 `0.5` 个逻辑核的平均带宽。若突发期间需要同时解析大量消息、执行鉴权、序列化响应，多个 Go 线程可在多核上并行运行，却会更快耗尽这 `50ms` 配额。

例如，4 个可运行线程同时占用 CPU，约 `12.5ms` 墙钟时间就可能消耗完一个周期的 `50ms` CPU 预算。随后，该 cgroup 中的任务会被节流，直到下一个周期补充配额。此时宿主机可能仍有大量空闲核，但容器内请求已无法继续推进：

1. 新连接进入后被 goroutine 接收；
2. 已就绪 goroutine 因节流无法及时执行；
3. 运行队列、连接队列和下游调用等待逐步累积；
4. 请求超过网关读写、鉴权或整体截止时间，最终报超时。

诊断时应看增量而非单点值：`cpu.stat` 中 `usage_usec` 增长有限，而 `nr_throttled`、`throttled_usec` 持续增长，说明瓶颈是 CPU 带宽配额，不是主机总 CPU 不足。还要检查该容器所属 cgroup 及其祖先；任一层配额收紧都可能形成实际限制。

`GOMAXPROCS` 只控制 Go 运行时可同时执行 Go 代码的并行度。把它调大可以增加竞争 CPU 的线程数，却不能突破 `cpu.max`；在严格配额下，过大的值甚至可能更快耗尽周期预算。应先按实际 quota 设置合理的 `GOMAXPROCS`，再结合削峰、限流和减少单请求 CPU 开销处理突发。

> **要点** — cpu.max 限制的是 cgroup 在周期内可获得的 CPU 时间；宿主空闲与容器未被节流是两件事。

主机看似空闲时，容器仍可能因自身内存边界触发超时或重启；关键在于辨认不同统计口径与事件证据。

### 从主机空闲到容器受限

### 从主机空闲到容器受限

“主机还有很多内存”描述的是**整机**视角；容器是否能继续分配内存，则先受其所属 **cgroup** 视角约束。两者不是同一个资源池。

可以按三层观察：

- **主机层**：`free`、`MemAvailable`、节点监控反映全机可回收和可分配的内存。主机空闲，只说明其他 cgroup 或宿主机仍有余量。
- **cgroup 层**：若容器所在 cgroup 配置 `memory.max=512MiB`，则该范围内累计内存不能稳定越过 512MiB。即使主机还剩几十 GiB，也不能把这些余量“借”给该容器。
- **进程层**：进程的 RSS、Go heap、线程栈、内存映射等只是组成部分；它们不能直接替代 cgroup 的总量判断。

`memory.current=500MiB` 表示该 cgroup **及其后代 cgroup** 当前计入的内存约为 500MiB，通常包括匿名页、页缓存、部分内核内存等。因此它既不等于某个 Go 进程的 heap，也不等于单个进程 RSS。网关即使堆内存看似不高，也可能因缓存文件、连接缓冲、子进程或内核记账接近上限。

当请求高峰需要更多内存时，内核会先尝试在该 cgroup 范围内回收；回收不足而又触及 `memory.max`，分配可能阻塞、失败，甚至触发该范围内的 OOM 处理。于是表现为请求超时、进程重启，而主机监控仍显示“内存充足”。

排障时应先并列读取：

`memory.max`、`memory.current`、`memory.events`

其中主机可用内存只能解释节点是否整体紧张；是否发生容器内存限制，必须以 cgroup 的上限、当前用量和事件证据为准。

### 读懂 memory.current 的构成

### 读懂 `memory.current` 的构成

设容器的 `memory.max=512MiB`，而 `memory.current=500MiB`。这并不表示“Go 堆已经用了 500MiB”，也不等于“某个进程的 RSS 恰好是 500MiB”。`memory.current` 是该内存 cgroup **及其所有后代 cgroup** 当前被计费的总内存，常见组成包括：

- **匿名内存**：进程堆、栈、`mmap` 的匿名页等。Go 的堆对象最终大多落在这里，但匿名内存还包含运行时元数据、goroutine 栈、C/C++ 分配及其他进程的内存。
- **页缓存**：容器读写文件、日志、数据库文件、镜像层文件时，文件页可能进入缓存；即使应用“没有显式申请大块内存”，缓存也会推高 `memory.current`。
- **内核计费内存**：例如 slab、页表、socket 缓冲区等与该 cgroup 工作负载相关的内核内存。
- **子进程与旁车**：网关主进程、shell、日志代理、探针或子 cgroup 中的进程，都会共同消耗该限额。

因此，500MiB 可以是如下结构：

\[
350\text{MiB 匿名内存}+110\text{MiB 页缓存}+40\text{MiB 内核计费}=500\text{MiB}
\]

而 Go 指标中的 heap 可能仅为 280MiB。`HeapAlloc` 描述 Go 仍在使用的堆对象；Go 进程 RSS 描述其驻留物理页；`memory.current` 则是 cgroup 范围内、按内核规则计费的总量。三者相关，但不能直接互相替代。

排查时可结合 `memory.stat` 观察 `anon`、`file`、`slab`、`kernel_stack`、`sock` 等字段。若 `file` 很高，应考虑缓存和 I/O 模式；若 `anon` 很高，再进一步对照 Go 堆、RSS 与同一 cgroup 内其他进程。

### max、oom 与 oom_kill 的证据链

### max、oom 与 oom_kill 的证据链

`memory.events` 记录的是该 cgroup 内存控制器的事件计数，通常应同时观察 `max`、`oom` 与 `oom_kill`，而不是看到内存接近上限就直接断言“进程被杀”。

- `max`：该 cgroup 的内存使用尝试越过 `memory.max` 时递增。内核会尝试回收本范围内可回收页，例如页缓存；因此它表示“撞到硬上限并发生限制/回收”，**不表示一定有进程死亡**。高频增长还可能带来回收、分配阻塞和延迟抖动，表现为网关请求超时。
- `oom`：到达上限后，内核无法获得足够内存以满足一次分配请求时递增，表示该 cgroup 发生了内存不足条件。它说明压力已从“触顶后回收”升级为“分配无法满足”，但仍不单独证明某个进程已经退出。
- `oom_kill`：内核最终选择并杀死该 cgroup 范围内某个进程时递增。这是“容器内进程因该 cgroup 的 OOM 被杀”的直接证据；若网关主进程被杀，编排器可能随后重启容器，外部看到的则是连接中断、`502/504` 或短暂不可用。

可用前后差分建立证据链：

`memory.current` 持续贴近 `memory.max` → `memory.events:max` 增长 → `oom` 增长 → `oom_kill` 增长且容器重启/进程退出。

其中最后一步最关键。仅有 `max` 增长，可能只是内存回收导致的性能退化；`oom` 增长说明分配失败风险；只有 `oom_kill` 增长，才能确认该 cgroup 内确有进程被 OOM 机制杀死。

### GOMEMLIMIT 不是容器内存上限

### GOMEMLIMIT 不是容器内存上限

`GOMEMLIMIT` 是 Go 运行时的**软内存目标**：它促使垃圾回收器更积极地回收、降低 Go 管理内存的增长速度，但不构成内核强制边界。运行时为了维持吞吐、处理瞬时分配或满足最小堆目标，实际 Go 内存仍可能短暂超过该值。

应区分三种口径：

- `GOMEMLIMIT`：主要约束 Go 运行时可管理的内存预算，如堆、部分运行时元数据；不直接覆盖所有进程内存。
- `memory.max=512MiB`：cgroup 的**硬限制**。该 cgroup 及其后代的匿名页、页缓存、部分内核内存等计入 `memory.current`；无法继续回收或压缩时，内核可能在该范围内触发 OOM。
- 进程 RSS：某个进程当前驻留在物理内存中的页面，通常包含 Go 堆、栈、共享库映射等，但不等于整个 cgroup 的计费内存。

因此，不能认为：

`512MiB - GOMEMLIMIT = 可供页缓存或其他进程使用的内存`

也不能用 RSS 判断距离 cgroup 上限还有多少。多个子进程、文件页缓存、网络缓冲和内核记账都可能推高 `memory.current`；反过来，较低的 Go 堆也不保证容器不会碰到 `memory.max`。

排障时，`GOMEMLIMIT` 用于调节 Go 的回收行为，`memory.max` 用于确认硬边界，`memory.current` 用于观察实际 cgroup 占用。若 `memory.events` 的 `oom_kill` 增加，才说明该 cgroup 范围内确有进程因 OOM 被杀；仅达到或接近 `memory.max` 并不意味着每次都会立刻杀进程。

### 网关重启恢复的受理评审

### 网关重启恢复的受理评审

某 IM 网关出现大量请求超时，重启容器后立即恢复。S2 受理不能仅记录“主机内存空闲、重启有效”，而应形成可复核的内存合同，证明故障是否发生在该容器的 cgroup 边界内。

- **限制证据**：采集 `memory.max`，例如 `512MiB`；同时记录是否配置 `memory.high`、交换空间限制及容器实际所属 cgroup 路径。`memory.max` 是硬上限，不是告警阈值。
- **用量证据**：故障前后连续采集 `memory.current`。若其接近 `500MiB`，表示该 cgroup 及其后代的总内存占用，可能包含匿名内存、页缓存、内核记账等；它既不等于 Go heap，也不等于单个进程 RSS。
- **事件证据**：保存 `memory.events` 快照及增量：
  - `max` 增加：内存分配曾触及 `memory.max` 并被限制或回收尝试；
  - `oom` 增加：该 cgroup 内发生 OOM 条件；
  - `oom_kill` 增加：内核确实杀死了该范围内的进程。  
  只有 `oom_kill` 增加，才能将“重启恢复”与 cgroup 内 OOM 杀进程建立强证据链；达到 `memory.max` 并不意味着每次都会被杀。
- **退出证据**：关联容器退出码、编排平台终止原因、内核日志与进程重启时间。若存在 `OOMKilled` 或对应 SIGKILL，需与 `oom_kill` 的时间窗口一致。
- **恢复验证**：重启后确认就绪探针恢复、超时率回落、连接数和消息处理延迟正常；并再次读取 `memory.current` 与 `memory.events`，确认事件未持续增长。

若应用设置 `GOMEMLIMIT=400MiB`，它仅约束 Go 运行时管理内存的软目标，不能覆盖 cgo、页缓存、内核记账等，也不能替代 `memory.max=512MiB`。受理结论应明确：这是 Go 堆压力、容器 cgroup OOM，还是两者尚未证实。

> **要点** — 容器 OOM 要以 cgroup 用量、限制和 events 联合判断；Go heap 与 GOMEMLIMIT 都不能代表真实硬边界。

主机看似空闲时，网关容器仍可能因任务数、文件描述符或网络视图隔离而超时；排障必须先确认观察对象与限制边界。

### 先辨对象：连接、描述符与内核任务不是一回事

### 先辨对象：连接、描述符与内核任务不是一回事

排查“连接一多就超时”时，不能把几个计数器当作同一件事。它们相关，却受不同内核对象、不同限制和不同命名空间约束。

- **连接数**：通常指 TCP/UDP socket 所处的会话或监听状态数量，如 `ESTABLISHED`、`SYN-SENT`、`TIME-WAIT`。一条客户端连接通常对应服务端的一个已连接 socket，但短连接积累的 `TIME-WAIT` 不等于正在处理请求的连接。
- **文件描述符数（FD）**：进程用整数句柄引用资源；socket 只是 FD 可指向的一类对象，另有文件、管道、事件通知、日志等。一个连接常会占用一个或多个 FD，但 FD 增长也可能完全与网络无关。其上限优先检查进程的 `RLIMIT_NOFILE`。
- **进程数**：应用进程、工作进程、辅助进程等用户态执行实体的数量。多进程模型中，连接数上升可能触发更多 worker，但并非必然。
- **线程任务数**：内核将进程和线程都表示为 task；线程有各自的 TID。因此 cgroup 的 `pids.max` 限制的是可创建的 task 总数，而不是“最多 10000 条连接”。线程池扩容、fork worker 或运行时创建后台线程，都可能先撞上该限制。

可用关系式作粗略理解：

$任务数 \neq FD数 \neq socket数 \neq 连接数$

例如，单进程事件驱动网关可维持大量连接而仅有少量线程；反之，线程一连接模型可能在连接数尚低时就耗尽 `pids.max`。因此应分别在容器作用域内核对 task、FD 与 socket，再判断真正的瓶颈。

### pids.max限制的是task与TID创建

### pids.max限制的是task与TID创建

`pids` cgroup 控制器限制的不是“容器内可建立多少条网络连接”，而是该 cgroup 中可存在多少个内核 `task`。一个普通进程至少对应一个 `task`；多线程程序中，每个线程也有独立的 TID，并同样计入额度。因此，设定：

`pids.max = 512`

含义是该 cgroup 最多容纳 512 个进程与线程任务的总和，而不是最多 512 个进程，更不是最多 512 或 10000 条 TCP 连接。

当应用调用 `fork()`、`clone()`，或运行时为请求创建工作线程时，内核会检查当前计数：

`pids.current < pids.max`

若配额已满，新的 `task` 创建被拒绝，常见表现为 `fork/clone` 返回 `EAGAIN`，日志中可能出现“资源暂时不可用”、无法创建线程、无法启动子进程。对 IM 网关而言，连接本身通常不会直接消耗 PID 配额，但连接高峰可能触发线程池扩张、每连接处理线程、DNS 或 TLS 辅助进程，从而间接耗尽 `pids.max`，最终表现为握手超时、请求排队或健康检查失败。

只读检查应在容器对应的 cgroup 路径中进行：

- `pids.current`：当前已使用的任务数；
- `pids.max`：允许的上限，`max` 表示不设此控制器上限；
- `pids.events`：重点查看 `max`，其递增说明曾因达到上限而拒绝创建任务。

若 `pids.current` 持续贴近 `pids.max`，且 `pids.events` 的 `max` 增长，可将故障方向收敛到任务额度耗尽。随后再查看容器内线程数，例如 `/proc/<PID>/status` 的 `Threads`，识别是少量多线程进程膨胀，还是大量子进程累积；不要把它与 `RLIMIT_NOFILE`、套接字数量或主机 `ss` 输出混为同一类限制。

### 十万连接为何不等于触发pids上限

### 十万连接为何不等于触发 pids 上限

以 Go 编写的 IM 网关为例，`pids.max` 限制的是 cgroup 中可创建的内核任务（task），通常可理解为进程与线程对应的 PID/TID 总数；它**不限制 TCP 连接条数**。

一个采用事件循环或 `epoll`/`netpoll` 模型的网关，可以让少量 OS 线程管理大量 socket：

- 10 万个客户端连接，对应约 10 万个 socket 与文件描述符；
- Go 的 goroutine 是用户态调度单元，不会与内核线程一一对应；
- 数十万 goroutine 也可能由几十个 `M`（内核线程）复用执行；
- 因而“连接数很高”并不自动意味着 `pids.current` 很高。

风险出现在阻塞或线程膨胀设计中。例如 goroutine 大量进入无法被运行时有效复用的阻塞路径，运行时可能为了维持调度而创建更多 OS 线程；某些 cgo 调用、同步阻塞 I/O、失控的线程池，或每个连接都启动外部子进程，也会使 TID/PID 快速增长。此时即使主机 CPU 仍空闲，容器也可能因达到 `pids.max` 而无法创建新线程、执行辅助进程，甚至导致请求超时。

调查时应在容器对应 cgroup 的只读视图中对比：

- `pids.current` 与 `pids.max`：确认任务配额是否逼近；
- 进程的线程数：判断是否存在 OS 线程膨胀；
- `RLIMIT_NOFILE`、`/proc/<pid>/fd`：确认是否其实是 FD/socket 耗尽。

不要把 `ss` 中的连接总数直接当作 pids 证据：连接、FD、goroutine、内核任务属于不同计数层次。

### FD限制、socket统计与网络命名空间

### FD限制、socket统计与网络命名空间

`RLIMIT_NOFILE`限制的是**单个进程可持有的文件描述符数量**，并不直接等于连接数。一个 TCP 连接通常占用一个 socket FD，但日志文件、配置文件、管道、事件通知 FD 也会计入，因此应先查看目标网关进程，而非只看容器总连接数：

- 查看限制：`cat /proc/<PID>/limits | grep -i 'open files'`
- 统计已打开 FD：`ls /proc/<PID>/fd | wc -l`
- 查看具体类型：`ls -l /proc/<PID>/fd`
- 在进程权限允许时：`lsof -p <PID>`

若日志出现 `Too many open files`，重点比较“当前 FD 数”与 `Max open files` 的软、硬限制；不要把它误判为 `pids.max` 耗尽。`pids.max`限制的是 task/TID 创建，线程暴涨也会触发；`RLIMIT_NOFILE`则常表现为新建 socket、打开日志或接受连接失败。

socket 统计还必须说明观察作用域。宿主机执行 `ss -s`、`ss -lntp` 看到的是**宿主网络命名空间**中的 socket；容器使用独立网络命名空间时，容器内监听的 `0.0.0.0:8080` 未必直接出现在宿主同名监听列表中。应进入目标容器的网络视图，例如：

`nsenter -t <容器主进程PID> -n ss -s`

或在容器内执行 `ss -lntp`、`ss -tan`。其中 `ss -tan` 的连接状态可帮助区分：大量 `ESTAB` 可能是并发连接压力，大量 `TIME-WAIT` 可能是短连接回收问题，大量 `SYN-RECV` 则更接近握手或上游异常。

端口映射是另一层概念。宿主 `宿主端口 -> 容器IP:容器端口` 往往由 NAT、代理或运行时规则实现；宿主看到端口已发布，不代表容器进程实际成功监听。排查顺序应为：先在容器网络命名空间确认服务监听，再检查宿主端口映射与转发规则，最后从客户端验证连通性。全程优先使用 `/proc`、`ss` 等只读查询，避免为“查看网络”而修改防火墙、重启容器或进入特权调试环境。

### 最小权限下完成容器超时调查

### 最小权限下完成容器超时调查

超时调查应遵循“先定位作用域，再读取指标，最后核验网络”的顺序。避免在主机上直接看到大量空闲资源后，误判容器内部不存在限制。

1. **确认容器对应的 cgroup 路径**  
   从容器运行时或 `/proc/<容器主进程PID>/cgroup` 获取实际路径，再读取该路径下的 `pids.current`、`pids.max`。关注的是内核 task 数：一个多线程进程会占用多个 task/TID，因此 `pids.current` 接近 `pids.max` 时，即使进程数不多，新线程、子进程或辅助任务仍可能创建失败。

   可只读检查：
   `cat /sys/fs/cgroup/<路径>/pids.current`  
   `cat /sys/fs/cgroup/<路径>/pids.max`

2. **将 task 数与容器内线程数对应**  
   对容器主进程及其子进程读取 `/proc/<PID>/status` 中的 `Threads`，或枚举 `/proc/<PID>/task/`。这用于确认增长来自工作线程、运行时线程池还是短生命周期子进程。不要把 `pids.max` 理解为“最多一万个客户端连接”：连接通常首先消耗 socket 文件描述符，而非每连接一个 task。

3. **独立检查文件描述符限制与 socket 占用**  
   查看目标进程的 `/proc/<PID>/limits` 中 `Max open files`，并对照 `/proc/<PID>/fd/` 数量。若 FD 接近 `RLIMIT_NOFILE`，新 socket、日志文件或 DNS 相关文件都可能打开失败，表现为连接超时或间歇性拒绝。

4. **进入正确的网络命名空间核验**  
   主机执行 `ss` 看到的是主机网络命名空间；容器使用独立网络命名空间时，应以只读方式在目标命名空间执行 `ss -lntp`、`ss -nt`，确认服务是否实际监听、连接是否堆积，以及状态是否存在大量 `SYN-RECV`、`TIME-WAIT` 或 `CLOSE-WAIT`。

端口映射是宿主机端口到容器地址的转发规则，不等于容器进程在宿主机地址上监听。调查记录应明确每项数据来自“宿主机、目标进程、cgroup 路径或容器网络命名空间”，避免混用不同作用域的观察结果。

> **要点** — pids.max管的是内核task创建，不是连接数；FD、socket和网络状态必须在对应进程或命名空间内分别核验。

主机看似空闲，不代表网关容器未被配额节流；一次超时与重启背后，可能同时存在调度受限、内存淘汰和状态丢失。

### 从主机空闲到容器饥饿

### 从主机空闲到容器饥饿

“主机 CPU 只有 20%、内存还有很多”只能描述**整机平均余量**，不能推出某个 IM 网关容器获得了足够资源。排障时应同时建立三层观察范围：

- **主机层**：总 CPU、可用内存、磁盘与网络负载。它回答“机器整体是否饱和”，但会掩盖容器之间的不均衡。
- **容器层**：`CPU limit/request`、CFS 配额节流、内存上限、`OOMKilled`、重启次数、网络与文件描述符限制。它回答“该工作负载被允许使用多少”。
- **进程层**：事件循环延迟、线程池排队、GC 停顿、连接数、请求超时、进程内待确认消息。它回答“网关实际为何来不及处理”。

例如，主机有 16 核，但网关容器被限制为 1 核；突发消息到来时，进程可能持续可运行，却因 CPU 配额用尽而被节流。此时主机其余核心仍空闲，S2 的 `200` 响应却会因签名校验、序列化、下游调用或事件循环排队而变慢。

反证很直接：若降低容器 CPU 限额后，主机总体利用率仍低，而容器的节流时间、请求延迟和超时同步上升，则“主机空闲所以不是资源问题”不成立。类似地，主机尚有可用内存也不能排除容器触及自身内存上限并被 OOM 重启；重启会清空进程内受理状态并断开连接，不能再把此前的 S2 `200` 当作后续 DB 落库或设备确认的证据。

### 纸上计算CPU节流证据

### 纸上计算 CPU 节流证据

读取容器 cgroup v2 的 `cpu.max`：`quota period`。若为 `200000 100000`，表示每 $100\,ms$ 最多获得 $200\,ms$ CPU 时间，即理论上限为

$$
N_{\text{可用核}}=\frac{quota}{period}=\frac{200000}{100000}=2
$$

这不是“主机有多少空闲核”，而是该容器在每个调度周期内可消费的 CPU 预算。即使宿主机 32 核整体空闲，网关也不能持续使用超过约 2 个核的算力。

再取同一观察窗 $\Delta t$ 内 `cpu.stat` 的 `usage_usec`：

$$
U=\frac{\Delta usage\_usec}{\Delta t_{\mu s}}
$$

若 10 秒内容器累计使用 `19000000` 微秒，则 $U=1.9$ 核，已接近 2 核配额；此时突发的签名校验、序列化、压缩或大量并发连接，会迅速耗尽本周期余额。内核随后将 cgroup 中可运行任务暂停至下一周期，表现为请求排队，而非主机 CPU 忙碌。

节流证据应同时核对：

- `nr_throttled` 在超时窗口持续增长；
- `throttled_usec` 增量与 S2 延迟尖峰同向；
- `usage_usec` 接近配额上限，且容器内运行队列或请求队列上升；
- 降低并发、提高 `cpu.max` 配额后，A 当前的 S2 `200` 延迟明显回落。

例如一次 S2 请求本需 $25\,ms$ CPU；若到达时本周期预算已耗尽，最坏可先等待接近一个 `period=100\,ms`，再竞争后续预算。因此“已返回 200”仍可能从几十毫秒变为数百毫秒。

反证也必须保留：若 `nr_throttled` 不增、`throttled_usec` 平稳，或提高配额后延迟不变，则不能把慢 S2 归因于 CPU 节流；应转查下游依赖、网络阻塞、锁竞争或应用事件循环饱和。

### OOM重启为何造成业务假象

### OOM重启为何造成业务假象

容器发生 OOM 后，最容易被误判为“偶发网络超时”或“下游接口不稳定”。实际上，内存指标描述的是不同层次，不能互相替代：

- `memory.current`：cgroup 当前计费内存，通常包含匿名页、页缓存、内核记账等；它接近容器是否撞上 `memory.max` 的事实。
- Go heap：Go 运行时管理的对象堆，只反映 Go 可见的部分内存；即使 heap 平稳，goroutine 栈、运行时元数据、`mmap`、网络缓冲及非 Go 分配仍可增长。
- RSS：进程当前驻留物理页，适合观察进程占用，但不等于 cgroup 的完整计费值，也不能单独证明 OOM 原因。
- OOM 事件：应以 cgroup 的 `memory.events` 中 `oom`、`oom_kill` 增长，以及容器退出码、内核日志为证据。仅看到内存“后来降下来了”，往往恰恰是进程已被杀死并重启。

业务假象来自重启的破坏性：进程内“已受理、待投递、等待设备确认”的状态会被清空；现有长连接、WebSocket 或 TCP 连接被内核关闭；客户端可能未收到响应而重试，服务端日志却只留下重启后的新实例。于是同一消息可能呈现为“用户看到超时，但服务似乎处理过”，或“返回过 S2 200，之后仍未送达”。

反证也很重要：若 `memory.current` 始终明显低于限制、`oom_kill` 未增长、容器没有退出和重建记录，则不能把超时归因于 OOM，应继续检查 CPU 节流、连接池耗尽或下游依赖延迟。即使确认发生 OOM，S2 的 `200` 也只能说明当次请求被当前实例接受，不能推断未来 S3 已落库，更不能推断设备已经确认。

### S2成功不等于S3已确认

### S2成功不等于S3已确认

`S2 200`通常只表示：网关进程**已经在当前内存中受理**了请求，例如完成鉴权、解析参数，并把待发送任务放入内存队列或交给异步线程。它是“入口受理成功”，不是“数据库已落盘”，更不是“设备已收到并确认”。

三类边界应明确区分：

| 边界 | 成功含义 | 失败后果 |
|---|---|---|
| S2：内存受理 | 当前进程接受了命令 | 进程重启、OOM、队列丢失后任务可能消失 |
| S3：数据库持久化 | 命令、状态或投递记录已提交到数据库 | 可恢复、可重试，但仍未证明设备执行 |
| 设备确认 | 设备返回匹配的确认或业务回执 | 才能证明命令到达并被设备接受 |

反证很直接：网关返回 `200` 后，在异步写库前被 OOM 杀死；调用方看见的是成功，数据库中却没有命令记录。或者记录已写入数据库，但发送线程受 CPU 配额节流、连接池耗尽或下游网络阻塞，设备始终未收到命令。即使设备连接已建立，也可能在发送后断开，导致“已提交发送”不等于“已确认执行”。

因此，不能从 S2 的 `200` 推断“S3 已持久化”或“设备已完成”。若业务要求可追溯与可靠投递，应让响应语义对应明确合同：S2 返回“已受理”，S3 返回“已持久化”，设备确认则通过状态查询、回调或带幂等键的投递记录单独证明。监控也应分别统计受理数、落库数、发送数、确认数及其差值；只监控 HTTP 成功率，会掩盖重启后的内存状态丢失和后续积压。

### 补齐限制、依赖与监控链路

### 补齐限制、依赖与监控链路

排查 IM 网关“主机空闲但请求超时”时，不能只看节点总 CPU、总内存。应把容器内的限制、调度等待、下游阻塞与可观测性缺口拆开验证：

- **CPU 限额与节流**：容器即使只申请较少 CPU，也可能因 `cpu limit` 被 CFS 节流。此时宿主机仍有空闲核，但网关处理线程拿不到连续运行时间，S2 当前请求的 `200` 响应会变慢。应关联 `cpu throttled` 时间、节流次数、请求延迟分位数和运行队列长度，而非仅看 CPU 使用率。
- **内存限制与重启**：内存接近 `limit` 时，内核可能触发 OOM kill；进程重启后，进程内的会话、去重键、已受理但未持久化的消息状态都会丢失，现有长连接也会断开。反证是：若重启前后没有 OOM 事件、退出码异常或内存逼近限额，则不能把超时归因于 OOM。
- **pids、描述符与连接数**：线程池扩张可能先撞上 `pids limit`；连接泄漏会耗尽文件描述符；入口、代理、应用或数据库各层都可能有连接上限。表现通常是建连失败、排队增加或间歇性 `5xx`，不一定伴随高 CPU。
- **下游依赖**：数据库连接池耗尽、缓存慢查询、鉴权服务抖动、DNS 解析延迟，都会让网关工作线程阻塞。网关返回 S2 `200` 仅表示当前层已接受，不证明未来 S3 已写入 DB，更不证明设备已确认。
- **监控闭环**：恢复评审至少应覆盖容器重启次数与原因、OOM 事件、节流指标、FD/pids 使用率、活跃连接、线程池与连接池等待、下游超时、S3 落库结果及设备确认率。没有这些证据，“扩容后恢复”只是相关性，不能证明故障链路已消除。

> **要点** — 容器超时不等于主机繁忙；S2 200仅表示内存受理，不能证明状态已持久化或设备已确认。

网关容器超时或重启时，先界定观察范围并保全事件增量；修复须经权限流程验证，不能把主机空闲或两处源码直接当作容器配置结论。

### 先建立可复核的故障时间线

### 先建立可复核的故障时间线

“主机空闲”只描述宿主机整体视角，不能证明网关容器未触及自身的 `CPU`、内存、连接数或运行时限制。故障发生后先冻结证据，再讨论调参；时间线应覆盖故障前、故障窗口、恢复后三段，并统一使用同一时区与时间源。

建议按时间顺序记录以下增量：

- **资源范围**：宿主机、目标容器、同节点其他容器的 CPU、内存、网络与磁盘状态；明确采样对象是容器 cgroup 指标还是主机汇总指标。
- **版本身份**：镜像摘要或镜像标签、容器创建时间、OpenIM 网关版本、运行时与编排平台版本。不要仅凭源码目录中出现两处 OpenIM 配置，就推断线上容器实际加载了其中之一。
- **负载变化**：请求量、活跃连接数、新建连接、消息投递速率、队列积压、下游依赖耗时。重点标出突增、发布、流量切换和批量任务开始的时刻。
- **限制值**：容器的内存上限、CPU 配额/权重、进程数、文件描述符、探针阈值及重启策略；同时记录实际使用量和距上限的余量。
- **事件证据**：网关超时日志、`OOMKilled`、退出码、容器重启、探针失败、节点驱逐、连接断开与重连事件。记录“首次出现—持续—恢复”的精确时间，而非只保留最终状态。

可用表格将事件串联：

| 时间 | 负载/资源变化 | 限制与实际值 | 可见症状 | 关联事件 |
|---|---|---|---|---|
| $t_0$ | 连接数上升 | 内存接近上限 | 请求延迟增加 | 探针开始失败 |
| $t_1$ | 峰值持续 | 容器触限 | 网关超时 | 重启或 OOM |
| $t_2$ | 流量回落 | 使用量下降 | 连接重连 | 旧消息待确认 |

这样才能判断超时是容量限制、负载尖峰、下游阻塞还是重启后的连接恢复问题，并为后续镜像与容器环境核验提供输入。

### 按观察范围解释“主机空闲”

### 按观察范围解释“主机空闲”

“主机空闲”通常只说明宿主机整体视图中的 CPU、内存或磁盘尚有余量，不能推出某个 IM 网关容器、容器内进程或其请求路径没有受限。排障时应先写清观察对象：

- **主机视图**：`top`、`free`、`iostat`、节点监控反映全部进程汇总。例如主机有 32 核，但容器可能仅被分配 `cpu.max=200000 100000`，即约 2 个 CPU 的配额。
- **容器视图**：cgroup 限制决定容器可实际使用的 CPU、内存、进程数及 I/O 配额。主机尚有 20 GiB 可用内存时，容器仍可能因 `memory.max`、`memory.high` 或 OOM kill 退出。
- **进程视图**：单个网关进程还受运行时、文件描述符、连接池、线程数和 `pids.max` 影响。容器不满载，不代表 Go 进程没有暂停、GC 压力或连接积压。

同一 PID 在不同 namespace 中也可能呈现不同结论。容器内看到的 PID `1`，在宿主机上可能是 PID `18427`；应通过 `/proc/<宿主机PID>/cgroup` 对应其 cgroup，而非仅看主机总负载。`mount namespace` 会使容器看到独立的挂载点与磁盘容量；`net namespace` 会隔离网卡、路由、端口、conntrack 与 DNS 路径；`user namespace` 则会映射 UID/GID，使“容器内 root”未必拥有宿主机权限。

因此，超时应关联同一时间窗内的容器 CPU 节流、内存事件、进程退出码、网络重传和连接重连，而不是据“主机空闲”直接修改 `GOMEMLIMIT`、增加 CPU 或重启。后续镜像与容器运行环境的核对见 12.01。

### 核对CPU、内存与进程限制证据

### 核对 CPU、内存与进程限制证据

主机整体空闲并不等于容器未被限流。应在同一故障时间窗内采集容器或其 cgroup 的限额、实际使用量与事件计数，避免把不同负载阶段的数据拼接为结论。

- **CPU：`cpu.max` 与同窗使用率**  
  `cpu.max` 通常形如 `quota period`；例如 `100000 100000` 约等于一个 CPU 核，`max 100000` 表示不设 CFS 配额。结合容器 CPU 使用率、`cpu.stat` 中的 `nr_throttled`、`throttled_usec` 判断：使用率未高也可能频繁被配额节流，表现为请求排队、心跳延迟、网关超时。只看主机 CPU 空闲不能排除该问题。

- **内存：`memory.current`、限额与 OOM 事件**  
  将 `memory.current` 与 `memory.max`、`memory.high` 对照，观察是否持续贴近上限或被高水位回收。读取 `memory.events` 的 `oom`、`oom_kill` 增量；`oom_kill` 增加可直接解释进程被杀和容器重启，`oom` 增加但未杀进程则仍说明分配失败风险存在。

- **Go 运行时：堆不等于进程总内存**  
  Go heap 反映托管堆压力，应与 RSS 一起看。若 heap 尚低而 RSS 接近容器限额，可能是 goroutine 栈、网络缓冲、mmap、cgo 或页缓存等占用；若 heap 与 RSS 同步上涨，则需关联连接数、消息积压和请求负载。不能仅凭源码中出现 `GOMEMLIMIT` 就断言容器已配置该值。

- **进程数：`pids.max`**  
  对照 `pids.current`、`pids.max` 及 `pids.events` 的 `max` 增量。达到 PID 上限时，线程或子进程创建失败，可能表现为连接处理异常、日志报错或服务无响应，而非明显的内存 OOM。

记录限额原值、采样时刻、事件计数前后差值及对应超时请求。两处 OpenIM 源码、镜像默认值只能说明程序能力，不能证明运行中容器限制；镜像与容器环境的核验留待 12.01。

### 按受理合同评审恢复动作

### 按受理合同评审恢复动作

将 S2 内存问题视为一份“恢复动作受理合同”，而不是看到主机仍有空闲就立即增大容器限制。申请应先写清对象：集群、命名空间、工作负载、容器名、镜像版本、当前 `requests/limits`、实际负载窗口，以及超时、重启、OOMKilled 等事件的新增量。

受理人需确认以下边界：

- **权限**：谁有权修改 Deployment、StatefulSet、Helm values 或平台配额；应用排障人员只能提交证据，不应绕过变更流程直接调参。
- **动作**：优先比较两条路径：临时提高内存限制，或通过限流、缩短队列、降低并发、暂停非关键任务降载。不得仅凭 OpenIM 两处源码固定值推断运行中容器限制。
- **风险**：调高 `limits.memory` 可能挤压节点可调度空间；盲增 CPU 不能解决内存上限触发；随意修改 `GOMEMLIMIT` 可能掩盖泄漏、改变 GC 延迟与吞吐。
- **回滚条件**：若变更后仍出现 OOM、延迟恶化、节点内存压力、驱逐事件或错误率超过约定阈值，应恢复原配置或继续降载，而非连续加码。

执行结果必须记录接口或平台响应：`A成功` 表示目标版本已受理并生效；`409` 通常表示资源版本冲突，应重新读取对象后按流程合并；`404` 则先核对集群、命名空间与工作负载名称，不能把“未找到”当作已更新。

若动作包含滚动重启，恢复证据不能停留在 Pod 变为 `Running`。还要核验网关连接是否重新建立、鉴权与心跳是否恢复、旧消息的投递/消费状态是否连续，并对比重启前后的超时率、内存峰值和重启计数。镜像、容器运行时及环境差异的后续核对，转入 12.01。

### 验证接口结果与业务状态恢复

### 验证接口结果与业务状态恢复

调整限制或降低负载后，不应只看容器“仍在运行”，而要把接口返回与业务恢复分开验收。优先记录调整前后的请求时间、实例标识、响应码、连接日志及消息状态变化，避免把短暂恢复误判为根因已消除。

- **A 类成功响应**：表示本次请求已被目标服务正常受理或完成。还需确认响应中的会话、用户、消息标识与预期一致，并观察一段负载窗口内超时率、重试率和容器重启次数是否下降。
- **`409`**：通常表示资源状态冲突，例如重复创建、版本不一致、同一请求已被并发处理。它不等于网络故障；应核对幂等键、资源当前状态及客户端重试逻辑，避免重试放大负载。
- **`404`**：表示目标路由或资源不存在，可能是旧实例、已删除会话、错误版本路径或数据已清理。应区分“接口路径不存在”和“业务对象不存在”，不能仅靠重启容器掩盖问题。

连接恢复应验证客户端是否收到断开事件、是否按退避策略重连、重连后认证与订阅是否恢复；同时抽查断连前的旧消息：已确认消息不得重复投递，未确认消息应符合系统的补偿、失败或重试语义。若状态仍不一致，应保留请求标识和时间线继续定位。

固定 OpenIM 的两处源码只能说明镜像中存在相应实现，不能证明运行中的容器采用了何种 CPU、内存、`GOMEMLIMIT`、环境变量或编排限制；这些必须以实际容器检查结果和后续镜像容器环境核对为准。

> **要点** — 先用范围、版本、负载和事件证据定位限制，再经审批调限或降载，并以接口、重连和消息状态确认恢复。

主机看似空闲时，网关容器仍可能因隔离视图、资源配额或运行时限制而超时、OOM并重启；排障必须回到容器实际可见与可用的边界。

### 先校准观察范围：主机空闲不等于容器有余量

### 先校准观察范围：主机空闲不等于容器有余量

排障的第一步不是看宿主机是否“很闲”，而是确认指标属于哪一层。网关进程实际受限于容器的 `namespace` 与 `cgroup`；因此，宿主机剩余 CPU、内存和端口，并不自动成为该容器可用资源。

- **主机层**：看到整机的 CPU 利用率、可用内存、网卡流量和进程总数。此处“空闲”只能说明全局资源未耗尽。
- **容器层**：看到该容器的 CPU 配额、内存上限、进程数上限及网络命名空间。容器可能仅获分配 `0.5` 核，即使宿主机还有几十个空闲核心。
- **进程层**：看到网关自身的 RSS、线程、文件描述符、连接队列、GC 和请求延迟；这是超时直接发生的位置。

`namespace` 改变“看见什么”：容器中的 `localhost` 指向容器自己的网络命名空间，不是宿主机，也不是其他容器；容器内的进程列表、网卡、路由表、挂载点同样是隔离视图。于是“宿主机能访问 `127.0.0.1:8080`”不能证明网关容器能访问同一地址。

`cgroup` 决定“能用多少”：容器即使只消耗了很少的宿主机总资源，也可能已经碰到自身 CPU throttling、内存上限或 PID 上限。后续判断应优先在容器 cgroup 范围内取证，而非用主机平均负载替代容器可用余量。

### 用 cpu.max 还原半核容器的 96% 繁忙

### 用 `cpu.max` 还原半核容器的 96% 繁忙

`cpu.max` 的格式是 `配额 周期`。例如：

`50000 100000`

表示每个 100 ms 周期最多获得 50 ms CPU 时间，即容器可持续使用的上限为：

$$\frac{50000}{100000}=0.5\text{ 核}$$

若在 10 秒观测窗口内，容器累计消耗 CPU 时间为 4.8 秒，则相对其**可用配额**的利用率为：

$$\frac{4.8}{10\times0.5}\times100\%=96\%$$

此时主机即使有 16 核、整体 CPU 利用率只有 10%，也不能说明该容器空闲：它已经接近自己的 0.5 核边界。请求到达速度一旦略高于该配额能处理的速度，goroutine、连接处理或上游调用后的继续执行都会排队，最终表现为 P99 延迟升高和请求超时。

不要用主机 `top` 的百分比替代容器视角；应同时检查 cgroup 的 `cpu.stat`：

- `nr_throttled` 持续增长：周期内曾因配额耗尽被限流；
- `throttled_usec` 快速累积：实际被剥夺的可运行时间较多；
- CPU 使用接近 $0.5$ 核且限流计数增长：可将超时优先归因于 CPU 配额，而非主机总算力不足。

验证后可先将配额提高到 1 核或临时取消限制，比较限流计数、队列长度与超时率是否同步回落；若无改善，再回退配置并转查锁竞争、下游阻塞或连接池等待。

### 从 memory.current 到 oom_kill：定位内存重启链路

### 从 `memory.current` 到 `oom_kill`：定位内存重启链路

容器内存问题不能只看应用日志中的“堆使用量”。在 cgroup v2 中，`memory.current` 表示该容器 cgroup 当前被计费的内存，通常包括匿名页、页缓存及部分内核内存；它不是 Go heap，也不等同于进程 RSS。

可按层次建立判断：

- Go heap：Go 运行时管理的对象堆，可通过运行时指标或 `pprof` 查看；
- RSS：进程驻留物理内存，除 heap 外还可能包含 goroutine 栈、运行时元数据、`mmap`、动态库等；
- `memory.current`：cgroup 视角的实际计费用量，可能高于单进程 RSS 之和，因为页缓存和内核分配也会被计入；
- 可回收空间：接近 `memory.max` 时，内核会先回收文件页等可回收内存；若回收后仍无法满足分配，才可能触发 OOM。

关键证据是：

`memory.events` 中 `oom` 增长表示发生了 cgroup 内存不足事件，`oom_kill` 增长才表示内核实际杀死了该 cgroup 内的任务。应同时核对容器退出时间、重启次数、内核日志及网关请求错误时间线；仅看到“连接重置”不能直接断言 OOM。

若 `memory.current / memory.max` 长期接近 96%，即使主机整体空闲，容器仍可能在一次短暂分配峰值中被杀。Go 服务可设置 `GOMEMLIMIT`，为运行时留出 RSS、栈和非堆分配余量，而不是把它设为容器硬上限。

恢复阶段先确认重启后 `memory.current` 回落、`oom_kill` 不再递增，再逐步恢复流量受理；若提高限额或调整 `GOMEMLIMIT` 后延迟恶化，应回退配置并保留事件计数、内存曲线和退出码作为证据。

### 软硬限制不能混为一谈：GOMEMLIMIT、pids 与连接

### 软硬限制不能混为一谈：GOMEMLIMIT、pids 与连接

`GOMEMLIMIT` 是 Go 运行时的**软内存目标**：运行时会更积极地执行 GC、归还空闲页，尽量让 Go 堆及其相关运行时内存不越过该目标；它不是内核强制上限，也不能覆盖所有进程内存。cgroup 的 `memory.max` 才是**硬限制**：容器总内存达到边界后，内核可能触发回收、拒绝分配，最终记录 `memory.events` 中的 `oom`、`oom_kill` 并杀死进程。

因此应同时看：

- `memory.current`：cgroup 当前计费内存，包含 Go 堆之外的栈、匿名页、页缓存等。
- 进程 `RSS`：进程驻留物理页，适合定位主要内存消费者，但不等同于 cgroup 计费。
- `memory.events`：若 `oom_kill` 增加，说明问题是硬限制下的实际杀进程，不能仅靠调大 GC 频率解释。

经验上可令 `GOMEMLIMIT` 低于 `memory.max`，为非堆内存保留余量。例如容器限制 `512MiB`，若预留约 `96MiB` 给栈、网络缓冲、代码页和波动，可设：

\[
GOMEMLIMIT \approx 512MiB-96MiB=416MiB
\]

但这只是受理恢复中的保护线；若 `memory.current` 仍持续逼近 `memory.max`，应回退并限制并发、请求体或缓存，而非盲目继续提高限制。

`pids.max` 也常被误解。它限制的是 cgroup 内的**进程和线程数**；Go 的 goroutine、TCP 连接都不是 PID。连接暴涨通常先消耗文件描述符：检查进程 `nofile` 限制、已打开描述符数及 socket 状态。只有连接处理导致大量线程创建、子进程派生，才会间接撞上 `pids.max`。因此，“连接超时”不能直接归因于 PID 限制；应分别取得 `pids.current`、`pids.max`、文件描述符使用量和 `memory.events` 作为证据。

### 以 S2 内存受理合同评审恢复与回退

### 以 S2 内存受理合同评审恢复与回退

IM 网关重启恢复前，S2 应签署可验证的内存受理合同，而非仅确认主机“还有空闲内存”。容器看到的是自身 `namespace` 与 `cgroup` 边界：宿主机的 `localhost` 不等于容器的 `localhost`，主机 RSS、端口探测和空闲率也不能替代容器内证据。

受理条件可定义为：

- CPU 限额为 `0.5` 核时，持续使用率不应超过 `0.5×96%=0.48` 核；超过该线说明扩容内存也未必消除排队超时。
- 采集 `memory.current`、容器 RSS、`memory.max` 与工作负载峰值；以 `memory.current/memory.max < 80%` 作为恢复门槛，并保留突发余量。
- 检查 `memory.events`：`oom_kill>0` 表示已发生 cgroup 级杀进程，必须先解释增长来源，再恢复流量。
- Go 网关应设置 `GOMEMLIMIT`，使其低于容器限额并预留运行时、内核页缓存和 sidecar 空间；不能把限额全部交给堆使用。
- `pids.max` 限制的是进程/线程数量，不是 IM 连接数；连接上限应由文件描述符、事件循环、内存模型独立核算。

恢复时先在容器内执行 `curl 127.0.0.1`、健康检查和本地依赖连通性校验，再按小比例放量。证据应包含重启时间线、`memory.current` 曲线、`memory.events`、RSS、限额配置及 OOM 日志。若放量后内存斜率持续上升、再次出现 `oom_kill` 或延迟恶化，应立即回退流量与副本版本；仅在证据表明容量不足且无泄漏迹象时，才谨慎提高 `memory.max`。

> **要点** — 容器故障应以 namespace 视图和 cgroup 证据判断；主机余量不能否定容器 CPU 限流、内存 OOM 或 PID/描述符风险。
