### 从程序文件到一次进程实例

### 从程序文件到一次进程实例

磁盘上的 `imhistory` 是**程序文件**：它保存可执行指令、依赖信息和默认行为，本身并不等于“正在运行”。当你在 shell 中输入：

`imhistory check -file history-c-a.json`

操作系统会依据该程序文件创建一次**进程实例**。这次实例拥有独立的运行现场，例如：

- `PID`：此刻分配给它的进程标识；
- `PPID`：启动它的父进程标识；
- 命令行参数：`check -file history-c-a.json`；
- 当前工作目录、环境变量、打开的文件；
- 内存、CPU 时间及退出状态。

可将关系简化为：

`终端 → shell 进程 → imhistory 进程`

其中 shell 通常是 `imhistory` 的父进程，但具体父子关系会随图形终端、脚本、任务调度器或容器环境而变化，不能把示意图当作固定结构。

`PID` 不是程序文件名，也不是用户 ID；它只是内核在某段时间内用于识别该进程的编号。进程退出后，观察窗口随之消失，之后该编号还可能被新进程复用。因此，记录“曾见到 PID 1234”不能单独证明它始终对应某个 `imhistory` 实例。

`imhistory check` 这类命令通常很短命：检查完成便退出。教学中若需观察进程状态，应使用长时间运行的示例进程或纸上样本；本项目不为此额外启动服务。

### PID 与 PPID：定位而非身份认证

### PID 与 PPID：定位而非身份认证

设你在终端执行一次虚构检查命令：

`imhistory check -file history-c-a.json`

Shell 会先找到 `imhistory` 程序文件，再创建一个运行中的进程。该进程在某一时刻可能显示为：

- `PID=4821`：当前这次运行的进程标识；
- `PPID=3170`：创建它的父进程标识，通常是当前 Shell；
- 命令参数：`check -file history-c-a.json`，说明它正在检查哪个文件。

可将启动关系抽象为：

`终端模拟器 → Shell(PID 3170) → imhistory(PID 4821)`

这里的箭头表示“由谁启动”，不是永久不变的组织结构。不同终端、脚本、任务调度器或容器环境中，`imhistory` 的父进程都可能不同；Shell 也可能再经由脚本、`sudo` 等环节启动它。

PID 的用途是**在某个观察时刻定位一个进程**，而不是认证身份：

- 它不是 `imhistory` 程序文件本身；同一程序可同时有多个 PID。
- 它不是用户 ID；用户身份应看 UID、GID 等信息。
- 它不是永久编号；进程退出后，操作系统可把该 PID 分配给后续新进程。

尤其这类检查命令往往很短命：命令完成后，PID 4821 对应的观察窗口就消失了。此时再按旧 PID 查询，可能得到“进程不存在”，也可能在较晚时刻看到一个无关的新进程。因此，排查记录应同时保存命令、时间、PID、PPID 与关键输出，而不能只写“PID 4821 出错”。

为便于练习，可使用教学用长进程或纸上样本观察父子关系；本项目不需要为此启动任何服务。

### Shell 启动链与短命命令的观察窗口

### Shell 启动链与短命命令的观察窗口

在终端输入虚构命令：

`imhistory check -file history-c-a.json`

Shell 会先解析命令、查找可执行文件，并创建一个子进程来运行它。一次常见的关系可以示意为：

`终端模拟器 → Shell（如 bash/zsh）→ imhistory check`

其中，`imhistory` 运行时拥有自己的 PID；启动它的 Shell 通常是它的 PPID 所指向的父进程。命令完成后，子进程退出，Shell 回到提示符。

但这不是固定结构：命令可能由脚本、IDE、任务调度器、管道中的其他程序或服务管理器启动。例如 `cat history-c-a.json | imhistory check` 中，父进程仍可能是 Shell；而在脚本或自动化任务中，父进程则可能完全不同。因此，PPID 说明的是“这一次由谁创建”，不是程序永久属性。

`imhistory check` 这类 CLI 往往很短命：检查结束后进程立即退出，`ps`、`top` 等工具的观察窗口也随之消失。退出后其 PID 未来还可能被系统复用，不能把旧 PID 当作持续有效的身份标记。教学中可使用人为延长运行时间的示例或纸上进程样本观察字段；本项目不需要为此启动任何常驻服务。

### 纸上样本中的进程现场证据

### 纸上样本中的进程现场证据

`imhistory check -file history-c-a.json` 是一次短命令行任务：shell 创建子进程，子进程读取文件、输出检查结果并退出。若在它结束后才查看进程列表，通常已经找不到对应条目；进程退出时，其 PID、内存映射、打开文件和调度状态等“现场”也随之从常规观察窗口消失。

因此，学习进程概念时可采用两类证据：

- **教学长进程**：人为让示例程序暂时运行，以便观察其 PID、PPID、状态与资源信息。
- **静态纸上样本**：把某一时刻的 `ps`、进程树或资源快照写入教材，分析其中的父子关系和字段含义。

例如可将 shell 启动命令的关系概括为：

`终端 → shell（父进程）→ imhistory（子进程）`

其中 PID 是该次运行中的进程标识，PPID 是其父进程标识；二者都不是程序文件名，也不是用户 ID。进程结束后，操作系统可能在未来复用旧 PID，所以“PID=某个固定程序”并不成立。不同终端、脚本、容器或后台启动方式下，父子关系也可能不同，上图只是常见示意。

本章仅借助教学样本理解观察方法，不实际启动服务，也不要求执行命令。

### 事实、假设与业务结论的边界

### 事实、假设与业务结论的边界

执行虚构命令 `imhistory check -file history-c-a.json` 时，系统工具可能显示：

- `PID=18420`：该次运行中的进程标识；
- `PPID=17206`：创建它的父进程标识，常见为当前 shell；
- 命令行：`imhistory check -file history-c-a.json`；
- 可执行文件路径、启动用户、工作目录与启动时间等。

这些是**进程现场事实**：它们描述“哪个进程以什么参数运行、由谁启动”。但 PID 不是程序文件名，也不是 IM 用户 ID；进程退出后 PID 还可能被系统复用。因而“PID 曾为 18420”不等于“某个固定身份永远对应 18420”。

更重要的是，命令行中的文件名也不能单独推出业务结论。例如：

| 可观察信息 | 可以合理说明 | 不能直接断定 |
|---|---|---|
| `PID`、`PPID` | 某次进程及其父子启动关系 | IM 账号身份、操作者意图 |
| `-file history-c-a.json` | 进程尝试读取该路径 | 文件真实归属、内容可信 |
| 启动用户 | 操作系统层面的账户 | IM 中的登录用户或授权范围 |
| 命令执行成功 | 工具返回成功状态 | 消息已送达、已读或已被对方接收 |

shell 启动工具时，关系通常可示意为 `终端 → shell → imhistory`；但具体父进程会随 IDE、脚本、容器或服务管理器而变化。短命 CLI 退出后，观察窗口随即消失；教学中可借助长进程或纸上样本理解字段，但不应据此在项目中额外启动服务。

业务结论必须补充对应证据：身份看认证记录，授权看权限策略与审计日志，送达看服务端回执或消息状态，而不是把一条进程信息解释成完整业务事实。

> **要点** — PID 和 PPID 只描述某时刻的进程关系；先保存现场事实，再提出可验证的故障假设。

本地 IM CLI 找不到历史文件时，先确认进程实际从哪里看见路径，再判断文件是否存在或可读。

### 相对路径的唯一参照：进程工作目录

### 相对路径的唯一参照：进程工作目录

`-file history-c-a.json`并不表示“源码目录下的 `history-c-a.json`”，也不表示“可执行文件旁边的文件”。对 Linux 进程而言，它通常按**当前工作目录**（current working directory，cwd）解析：

`history-c-a.json` → `cwd/history-c-a.json`

例如，程序位于 `/opt/im/bin/imcli`，源码位于 `/home/dev/im`；如果 shell 当前位于 `/tmp/test` 后执行：

`/opt/im/bin/imcli -file history-c-a.json`

程序实际尝试访问的是：

`/tmp/test/history-c-a.json`

而不是 `/opt/im/bin/history-c-a.json`，也不是 `/home/dev/im/history-c-a.json`。因此，排查“找不到文件”时，先查看启动命令所在 shell 的位置：`pwd`；再检查规范化后的目标：`realpath -m history-c-a.json`，以及文件是否存在、是否可读：`ls -l history-c-a.json`。

运行中的进程可通过 `/proc/PID/cwd`观察其工作目录：

`readlink /proc/1234/cwd`

这是一个只读符号链接；进程退出后，对应的 `/proc/1234` 会消失，不能再据此追溯。若报错是“没有那个文件或目录”，重点检查 cwd 与文件名；若是“权限不够”，则检查目录的搜索权限和文件读取权限，而不只是文件是否存在。

Go 中可用 `os.Getwd()`记录当前 cwd，`os.Chdir()`可以改变它，但不应把全局 `Chdir` 当作修复业务相对路径的手段：它会影响后续所有相对路径访问。CLI 更稳妥的做法是让用户传入明确的 `-file` 绝对路径，或在启动日志中记录 cwd 与最终解析出的文件路径。

### 从 Shell 启动位置还原路径现场

### 从 Shell 启动位置还原路径现场

在 Shell 中执行：

`im-cli -file history-c-a.json`

时，`history-c-a.json`并不默认相对于源码目录、`im-cli`可执行文件所在目录，或配置文件目录；它相对于启动该命令的 Shell 当前工作目录（current working directory，cwd）。Shell 创建子进程后，子进程会继承这一 cwd，因此实际访问目标可写为：

`实际路径 = 启动时 cwd + 相对文件路径`

例如：

```text
/home/alice/project$ /usr/local/bin/im-cli -file history-c-a.json
```

程序尝试打开的是：

`/home/alice/project/history-c-a.json`

而不是：

`/usr/local/bin/history-c-a.json`

先在同一终端确认现场：

- 用 `pwd -P` 查看规范化后的物理 cwd；`pwd` 有时会保留符号链接形式。
- 用 `readlink -f history-c-a.json` 推导规范化后的目标路径；若文件不存在，可改为检查其父目录。
- 用 `ls -l history-c-a.json` 区分“文件不存在”和“存在但不可读”。前者常报 `no such file or directory`，后者常报 `permission denied`。
- 若进程仍在运行，可查看 `readlink /proc/<PID>/cwd`。这是指向该进程 cwd 的只读链接；进程退出后，`/proc/<PID>`通常会随之消失。

Go 中可通过 `os.Getwd()`读取当前工作目录，`os.Chdir()`可以改变它；但不要用全局 `Chdir`“修复”业务相对路径：它会影响同一进程内后续所有相对文件访问，并可能造成并发任务互相干扰。更稳妥的 CLI 约定是让用户传入明确的 `-file` 绝对路径，或在启动日志中记录 `cwd` 与最终解析出的文件路径。

### 文件不存在与权限拒绝的证据边界

### 文件不存在与权限拒绝的证据边界

对 `-file history-c-a.json` 而言，先将参数按进程的当前工作目录解析为绝对路径，再讨论“找不到”还是“没权限”。例如进程 `cwd` 为 `/srv/im/run`，则实际目标是：

`/srv/im/run/history-c-a.json`

几类现象的证据含义不同：

- **路径解析失败**：参数为空、包含非法形式，或程序自行拼接了错误路径；应记录原始参数、规范化后的路径与 `cwd`。
- **目标不存在**：`stat`/`open` 返回 `ENOENT`。也可能不是最终文件缺失，而是其任一父目录不存在，或符号链接指向不存在的目标。
- **目录不可遍历**：返回 `EACCES` 不必表示文件本身不可读。访问 `/a/b/file` 时，执行用户必须对 `/a`、`/a/b` 均有“执行/搜索”权限；缺少任一级目录的 `x` 权限，就无法抵达文件。
- **文件不可读**：已能定位文件，但打开时因文件权限、属主属组、ACL、挂载策略等被拒绝。此时才能说“操作系统拒绝该进程读取此文件”。

因此，`permission denied` 首先是文件系统访问控制证据，不应直接解释为 IM 的业务授权、账号角色或会话权限失败。排查时应分别确认：进程身份、`cwd`、规范化绝对路径、各级目录权限、目标文件权限。

Go 中可用 `os.Getwd()` 获取当前工作目录；`os.Chdir()` 能改变它，但不应把全局 `Chdir` 当作修复业务相对路径的手段，因为它会影响同一进程后续所有相对路径。CLI 更稳妥的做法是要求或记录 `-file` 的绝对路径与启动时 `cwd`。运行中的进程可查看 `/proc/PID/cwd` 这一只读链接；进程退出后，该证据可能随 `/proc/PID` 消失。

### 用 Go 明确管理 CLI 的路径条件

### 用 Go 明确管理 CLI 的路径条件

`-file history-c-a.json`不是“相对源码目录”或“相对可执行文件目录”，而是相对**进程当前工作目录**（current working directory，cwd）。用户在不同 shell 目录启动同一 CLI，`history-c-a.json`会解析为不同位置；因此排查前应先确认启动位置，而不是先怀疑文件名。

Go 中，`os.Getwd()`返回当前进程 cwd 的规范化路径（可能受符号链接、目录权限等影响而返回错误）。CLI 可在启动时记录它，用于诊断：

- 输出“当前工作目录：`/path/to/dir`”；
- 将用户传入的相对路径与该 cwd 一并写入日志；
- 在报错时区分“文件不存在”和“文件存在但不可读”。

`os.Chdir(dir)`会修改**整个进程**的 cwd；之后所有未解析的相对路径，包括配置、日志、子模块文件访问，都可能改变含义。它适合少数明确的启动环境切换，但不应作为“让业务文件找得到”的全局补丁，否则测试、并发任务和后续维护都难以判断路径基准。

更稳妥的 CLI 约定是：优先要求或建议 `-file` 使用绝对路径；若接受相对路径，则在参数解析后立即基于启动时 cwd 将其规范化为绝对路径，并持续使用该结果。这样即使后续代码调用 `Chdir`，历史文件的目标也不会漂移。

Linux 上还可查看运行中进程的 `/proc/PID/cwd`，它是指向该进程 cwd 的只读链接；进程退出后该入口可能消失。若报错为“没有那个文件或目录”，先核对解析后的完整路径；若为“权限不够”，再检查目录的执行权限与文件的读取权限。

### 借助 procfs 只读验证运行现场

### 借助 procfs 只读验证运行现场

当 CLI 报告找不到 `history-c-a.json` 时，不要先假定文件位于源码目录或可执行文件旁。相对路径的基准是**该进程的当前工作目录**（cwd）。对仍在运行的进程，可只读查看 procfs：

```text
$ readlink /proc/24871/cwd
/home/alice/im-test
$ ls -l /proc/24871/cwd
lrwxrwxrwx ... /proc/24871/cwd -> /home/alice/im-test
```

若程序参数为 `-file history-c-a.json`，可复核其实际目标：

```text
/home/alice/im-test/history-c-a.json
```

建议在故障记录中同时保存：

- PID、启动命令与启动用户；
- `/proc/PID/cwd` 的链接目标；
- 原始 `-file` 参数及规范化后的候选路径；
- `stat` 或 `ls -l` 的结果，区分“不存在”和“无读取权限”；
- 采集时间。

例如，文件存在但目录缺少执行权限、文件缺少读取权限，都会表现为打开失败；不能仅凭“路径看起来正确”下结论。

Go 程序可用 `os.Getwd()` 记录启动时 cwd，也可通过 `os.Chdir()` 改变它；但不应以全局 `Chdir` 修补业务相对路径，因为它会影响同一进程后续所有相对文件访问。更稳妥的是让 CLI 接受明确的 `-file` 绝对路径，或在日志中记录 cwd 与最终解析路径。

`/proc/PID/cwd` 是内核暴露的只读现场链接，不是持久日志。进程退出后，对应的 `/proc/PID` 目录通常立即消失；因此应在问题发生时采集，或由程序主动记录 cwd，避免事后只能猜测启动位置。

> **要点** — 相对文件名由进程 cwd 决定；先记录并验证路径现场，再区分不存在、权限与业务结论。

本节聚焦本地 IM CLI 的环境配置：厘清启动时继承、参数覆盖与安全观察，避免把环境变量误当作认证或业务状态。

### 环境是进程启动现场的一部分

### 环境是进程启动现场的一部分

Linux 进程启动时，除了获得可执行文件代码、工作目录和文件描述符，还会获得一份**环境变量副本**。这份环境是启动现场的一部分：它描述“该进程被谁、以什么配置启动”，而不是一个会自动同步的全局配置中心。

环境通常由父进程提供。例如，Shell 中执行：

`export IMHISTORY_FILE=$HOME/.local/share/im/history`

随后从该 Shell 启动 IM CLI，子进程就能通过 `os.Getenv("IMHISTORY_FILE")` 读取该值。父进程可以是交互式 Shell，也可以是 `systemd`、桌面启动器、脚本或其他程序。

关键关系是：

- 父进程创建子进程时，子进程继承当时的环境副本。
- Shell 在子进程启动后再执行 `export IMHISTORY_FILE=...`，已经运行的 IM CLI 不会自动改变。
- 程序自身可在运行期间修改环境，但这通常只影响它后续创建的子进程，不会反向修改父 Shell。
- 不同启动入口可能提供不同环境：终端中正常、桌面图标启动失败，常常就是启动现场不同。

因此，排查配置时应先确认“这个进程实际从哪里启动、启动时拿到了什么变量”，而非只查看当前终端。观察时只输出必要变量及其是否为空，避免打印整个 `environ`：其中可能包含令牌、代理凭据或其他敏感信息。环境变量用于传递配置，不是认证机制，也不应被当作可信身份来源。

### 历史文件路径的三层优先级

### 历史文件路径的三层优先级

本地 IM CLI 需要决定历史记录写到哪里时，可把配置来源按“越明确，优先级越高”排序：

1. 显式参数：`-file /tmp/im.log`
2. 环境变量：`IMHISTORY_FILE=/tmp/im.log`
3. 教学默认路径：例如 `./imhistory.log`

可将最终路径写成：

$$
P=
\begin{cases}
P_{\text{file}}, & \text{若 }-file\text{ 已提供且有效}\\
P_{\text{env}}, & \text{否则若 }IMHISTORY\_FILE\text{ 非空}\\
P_{\text{default}}, & \text{否则}
\end{cases}
$$

Go 中读取环境变量可使用：

`envPath := os.Getenv("IMHISTORY_FILE")`

但 `os.Getenv` 对“未设置”和“设置为空字符串”都返回 `""`。若需求必须区分两者，应使用 `os.LookupEnv`：它额外返回变量是否存在。常见约定是将空值视为“未配置”，继续回退到默认路径；若产品要求空值表示“显式禁用历史”，则必须单独定义并实现，不能靠猜测。

环境通常由父进程在创建子进程时提供。例如 shell 中先执行 `export IMHISTORY_FILE=/tmp/a.log`，再启动 CLI，程序可继承该值；但 CLI 已经运行后，另一个 shell 再 `export`，不会自动改变该进程的环境。配置应在启动前确定，或通过程序自己的重载机制更新。

参数解析失败应以退出码 `2` 结束；路径创建、打开或写入失败应以退出码 `4` 结束。诊断时只记录“配置来自参数、环境或默认值”及必要的脱敏路径，不要打印整个 `environ`：其中可能含有令牌、代理凭据等敏感信息。环境变量只是配置传递渠道，不是认证机制。

### 未设置与空值不是同一种事实

### 未设置与空值不是同一种事实

`os.Getenv("IMHISTORY_FILE")` 只能返回字符串：变量不存在与变量存在但值为 `""` 时，结果同为 `""`。若产品需要区分两者，应使用 `os.LookupEnv`：

```go
v, ok := os.LookupEnv("IMHISTORY_FILE")
```

可将现场归为三类，并先定义需求而非猜测用户意图：

| 状态 | `LookupEnv` 结果 | 建议产品语义 |
|---|---|---|
| 未设置 | `ok == false` | 使用教学默认路径，或提示用户配置 |
| 已设置为空 | `ok == true && v == ""` | 视为显式禁用默认值，报参数错误 `2`，或按文档约定回退 |
| 已设置为路径 | `ok == true && v != ""` | 尝试打开；路径不存在、无权限或不可读时返回 `4` |

显式 `-file` 的优先级最高：即使环境变量为空或指向坏路径，只要 `-file` 合法，就应使用它。没有 `-file` 时才读取 `IMHISTORY_FILE`；环境变量未设置才使用教学默认值。

“空值”的含义必须写入接口约定。例如 `IMHISTORY_FILE=` 可能表示“我明确不想使用默认历史文件”，此时静默回退会掩盖配置错误；若需求规定空值等同未设置，也应明确实现并测试。不要打印完整环境或真实路径中的敏感信息；诊断时仅说明变量状态与打开失败类别。环境变量只是启动配置，不是认证机制。

### 从现场事实到可验证假设

### 从现场事实到可验证假设

排查本地 IM CLI 时，先记录可复现的现场事实，再提出假设；不要凭“我刚刚 `export` 过”推断已运行进程的配置。进程创建时继承父进程环境，之后 shell 新增或修改环境变量，不会自动更新已有进程。

先定位进程及其启动参数：

```sh
ps -o pid,ppid,user,etime,args -p "$pid"
```

这里可确认：

- `pid`：目标进程；
- `ppid`：父进程，帮助判断它来自终端、脚本、服务管理器还是 IDE；
- `args`：是否显式传入 `-file`。显式参数应优先于 `IMHISTORY_FILE`。

再读取 procfs 中的只读现场信息：

```sh
readlink "/proc/$pid/cwd"
tr '\0' ' ' < "/proc/$pid/cmdline"; echo
```

工作目录尤其重要：相对路径的打开结果依赖它。若程序报路径打开失败，应记录实际 `cwd`、`-file` 值或经脱敏后的环境线索，并检查文件是否存在、权限是否允许。

环境只观察必要键，不输出完整 `environ`，更不要记录令牌、密码或会话凭据。例如：

```sh
tr '\0' '\n' < "/proc/$pid/environ" |
  grep '^IMHISTORY_FILE='
```

据此形成可验证假设：若命令行含 `-file`，应使用该路径；否则检查 `IMHISTORY_FILE` 是否存在及是否为空；两者都未提供时才回退教学默认值。注意“未设置”和“设置为空”是否等价，必须由需求明确。环境用于配置而非认证；参数格式错误应返回状态码 `2`，路径打开失败返回 `4`。

### 错误码与安全边界

### 错误码与安全边界

本地 IM CLI 应把“用户输入不合法”和“资源不可用”区分为稳定、可脚本化的退出状态：

- 返回码 `2`：参数错误。例如 `-file` 缺少值、出现未知选项，或给出了不符合约定的路径参数。此时应输出简短用法提示，不应继续尝试读取历史文件。
- 返回码 `4`：路径打开失败。例如最终选定的历史文件不存在、权限不足、路径指向目录，或文件系统暂时不可访问。诊断信息应说明失败的操作和路径；若路径可能含敏感目录信息，应按产品约定脱敏。

最终路径仍遵循优先级：

`显式 -file` ＞ `IMHISTORY_FILE` 环境变量 ＞ 教学默认路径。

环境变量只是进程启动或运行期间可读取的配置输入，通常由父进程继承；它不是认证机制。即使 `IMHISTORY_FILE` 存在，也不能据此推断用户已获 IM 授权、身份可信，或消息一定能够送达。认证、会话有效性和投递结果必须由独立的凭据校验、服务端响应或可靠的本地状态确认。

排查时避免打印完整环境或真实令牌、密码、会话标识。只记录必要事实，例如“是否设置”“是否为空”“最终采用哪一层来源”，不要把环境内容本身写入日志。

> **要点** — 环境属于进程启动现场；先参数、后环境、再默认值，并以最小暴露原则记录可验证事实。

本节从本地 IM CLI 的文件与输出现场出发，建立“文件、路径与文件描述符并非同一对象”的进程资源视角。

### 文件描述符：进程持有的整数资源表项

### 文件描述符：进程持有的整数资源表项

在 Linux 中，文件描述符（FD）不是“文件本身”，而是**某个进程资源表中的整数索引**。进程调用 `open`、创建管道或连接套接字后，内核在该进程的描述符表中分配一个可用编号，例如 `3`、`4`；进程随后用这个整数读、写或关闭资源。

惯例上：

- `0`：标准输入 `stdin`
- `1`：标准输出 `stdout`
- `2`：标准错误 `stderr`

但这只是启动时常见约定。重定向、管道或父进程安排都可能让 `1` 指向文件、管道而非终端，让 `2` 指向另一处日志；这不会改变命令行错误的类别，只会改变输出去了哪里。

Go 中的 `*os.File` 是对这类底层资源句柄的封装。它可能表示普通文件，也可能表示终端、管道或其他可按文件接口操作的对象；可通过 `f.Fd()` 取得对应的整数句柄。不要把 `*os.File`、路径字符串和磁盘文件内容混为一谈：

- 路径是查找资源的名字；
- FD 是当前进程持有的访问入口；
- 内容是资源中实际存储的数据。

`close` 会释放该进程表项，之后该编号可能被下一次 `open` 复用。因此日志中“FD 3”并不能永久指向同一个文件。若长期打开却不关闭，描述符表最终可能耗尽配额，导致后续打开文件、建立连接等操作失败。

### 0、1、2：标准流约定与重定向现场

### 0、1、2：标准流约定与重定向现场

Linux 进程启动时通常已占用三个文件描述符：

- `0`：标准输入（`stdin`），默认来自终端键盘；
- `1`：标准输出（`stdout`），默认写到终端；
- `2`：标准错误（`stderr`），默认也写到终端。

它们是**编号约定**，不是“永远连接终端”的保证。以本地 IM CLI 为例：

`im send alice "你好" >send.log`

这里正常结果写入 `stdout`，因此进入 `send.log`；若认证失败、参数非法或网络不可用，错误信息通常仍写入 `stderr`，所以仍显示在终端。若希望分别保存：

`im send alice "你好" >send.log 2>send.err`

管道也主要连接标准输出：

`im history | grep alice`

前一个命令的 `1` 不再指向终端，而是指向管道写端；后一个命令的 `0` 指向管道读端。`stderr` 默认不会进入管道，除非显式合并，例如 `im history 2>&1 | grep 错误`。

因此，输出“看不见”不等于程序没有输出：它可能被重定向到文件、管道或其他设备。更重要的是，重定向只改变数据流向，不改变 CLI 错误的类别；参数错误仍是参数错误，权限失败仍是权限失败。

### 路径、文件内容与描述符：三个不同层次

### 路径、文件内容与描述符：三个不同层次

排查本地 IM CLI 时，先把“文件”拆成三个层次：

- **路径名**：如`./config.json`、`/tmp/im.log`，是目录中指向文件对象的名字。路径可以改名、删除，也可能是符号链接；同一路径在不同工作目录下含义不同。
- **文件内容**：真正存放配置、消息缓存或日志字节的数据。内容是否变化，应通过读取结果、校验值或时间戳判断，而不能只看路径“看起来存在”。
- **已打开描述符**：进程通过`open`得到的整数句柄，如`3`、`4`。它记录在该进程的资源表中，供后续`read`、`write`、`close`使用。

例如，CLI 打开`/tmp/im.log`后得到`fd=3`。即使随后该路径被删除或改名，进程通常仍可经由`fd=3`继续写入原先打开的内容；反过来，重新创建同名`/tmp/im.log`，新打开的路径也可能对应另一份内容。因此，“日志路径不存在”不等于“进程没有写日志”。

`0`、`1`、`2`通常分别表示标准输入、标准输出和标准错误，但它们只是描述符约定：启动脚本可将`1`重定向到文件、管道或`/dev/null`，也可让`2`指向另一位置。错误信息出现在终端、日志文件还是管道消费者处，改变的是**输出去向**，不会改变命令本身的错误类别。

可从进程视角只读检查自己打开的描述符：

`/proc/$$/fd/`

这里看到的是“该进程当前持有的资源入口”，不是业务文件清单；不要据此推断敏感路径或跨进程内容。`close(fd)`后编号可被后续`open`复用，所以`fd=3`不是永久身份。

### 打开、关闭与复用：资源泄漏的形成机制

### 打开、关闭与复用：资源泄漏的形成机制

对一个本地 IM CLI 而言，`os.Open`、创建日志文件、连接附件缓存等操作，都会请求内核为**当前进程**分配一个可用的文件描述符编号：

```go
f, err := os.Open(path)
if err != nil { /* 处理打开失败 */ }
defer f.Close()
```

打开成功不等于“只得到了文件内容”。进程实际得到的是一个整数句柄，如 `3`、`4`、`5`；`0/1/2`通常分别约定为标准输入、标准输出、标准错误，但它们可能已被管道或重定向。该编号可在 `/proc/<PID>/fd/` 中观察；检查时应只查看自己有权限的进程样本，避免输出或暴露敏感路径。

资源泄漏的因果链通常是：

1. 某次打开、创建或接受连接成功；
2. 程序在某条返回、异常或循环分支上遗漏 `Close`；
3. 该描述符持续占用进程的资源表项；
4. 重复执行后，已打开描述符数量不断增长；
5. 达到进程或系统配额，新的 `open` 失败，常见现象是“打开文件过多”。

编号本身不能用来判断是否泄漏。`Close` 会释放编号；下一次 `Open` 可以复用刚释放的 `3` 或 `4`。因此，“FD 号反复出现”通常是正常复用；“同时存活的 FD 数持续增长”才支持泄漏假设。

可验证的排查方式是：让 CLI 重复执行同一打开路径，分别在前后查看 `/proc/self/fd` 的条目数量。若操作结束后数量回落，说明关闭链路大致完整；若每轮稳定增加，则应检查错误分支、循环体以及所有权转移处是否遗漏关闭。文件路径、文件内容和 FD 句柄是不同层次：路径相同不代表同一打开实例，FD 相同也不代表仍指向先前资源。

### 只读查看描述符现场：为 CLI 故障记录证据

### 只读查看描述符现场：为 CLI 故障记录证据

本地 IM CLI 出现“附件打不开”“日志没输出”“命令卡住”时，先记录进程当前持有的描述符现场，而不是立即修改配置或反复重试。描述符表属于**进程视角**：同一路径可被不同进程分别打开，`0/1/2`通常对应标准输入、标准输出、标准错误，但它们可能已被终端、文件或管道重定向。

先定位目标进程：

```text
ps -ef | grep '[i]m-cli'
```

确认 `PID` 后，只做只读枚举：

```text
ls -l /proc/PID/fd
```

记录时应保留：采集时间、命令行、`PID`、描述符编号，以及其可见类型。例如：

- `0 -> /dev/null`：该 CLI 不会从交互终端读取输入；
- `1 -> pipe:[...]`：标准输出被管道接收；
- `2 -> /tmp/im-cli.err`：错误信息被重定向到文件；
- 某编号指向 `socket:[...]`：进程持有套接字，但不能仅据此判断网络故障；
- 多个编号指向同一文件：可能是重复打开，也可能是复制描述符，需避免武断归因为泄漏。

不要把 `/proc/PID/fd` 的链接目标直接贴入工单、聊天记录或截图：其中可能含用户名、项目目录、挂载路径、临时文件名或附件位置。对外证据宜脱敏为“普通文件”“管道”“终端”“已隐藏路径”，仅在受控环境保存原始记录。

这类观察只能说明“采样瞬间该进程持有哪些编号及其指向”，不能证明文件内容正确、路径仍可访问、编号永不变化，或 CLI 错误类别已经确定。`close` 后编号可被复用；标准输出与标准错误是否被重定向，也不会改变命令本身成功或失败的语义。

> **要点** — 文件描述符是进程资源，不等同于路径或文件内容；应以只读现场证据验证 CLI 资源故障。

停止本地 IM CLI 并不等于“进程立刻安全结束”。应先区分信号请求、程序响应、资源清理与业务恢复这些不同层次的事实。

### 信号是进程间的通知机制

### 信号是进程间的通知机制

信号是操作系统向进程发送的一类异步通知：它表达“发生了某种事件”或“外部提出了某种请求”，但**不直接等于业务结果**。例如，对本地 IM CLI 发送终止信号，只能说明系统请求它结束；并不能自动证明消息已落盘、网络连接已关闭，或在途任务已经恢复。

常见的终止相关信号包括：

- `SIGINT`：通常由终端中的 `Ctrl+C` 触发，语义接近“请中断当前运行”。
- `SIGTERM`：常用于脚本、进程管理工具或用户主动请求停止，语义接近“请正常终止”。

它们都属于可请求处理的终止通知。程序若未专门处理，往往会按默认行为退出；若程序通过 Go 的 `os/signal` 等机制监听它们，则可以在收到通知后选择停止接收新工作、关闭连接、写入状态，再自行返回或退出。这里的“可以”不等于“必然”：处理逻辑可能未注册、阻塞、超时或发生错误。

因此，观察到“已发送 `SIGTERM`”只能确认操作已发出，不能推导出“IM 网关安全停止”。应继续检查进程是否仍存在、日志是否记录退出路径，以及资源是否按预期释放。信号是通知协议，不是对业务一致性或清理完成的承诺。

### 可协作终止与不可拦截终止

### 可协作终止与不可拦截终止

终止进程不是单一动作，而是内核向进程传递不同强度的信号。对本地 IM CLI 这类受控个人进程，最重要的区别是：`SIGINT`、`SIGTERM` 提供“协商退出”的机会；`SIGKILL` 则是立即强制终止。

| 信号 | 常见来源 | 程序能否处理 | 含义 |
|---|---|---|---|
| `SIGINT` | 终端按下 `Ctrl+C` | 可以 | 请求中断当前运行 |
| `SIGTERM` | `kill <pid>`、服务管理器停止请求 | 可以 | 请求进程正常结束 |
| `SIGKILL` | `kill -9 <pid>` | 不可以 | 内核立即终止进程 |

程序可以用 Go 的 `os/signal` 订阅部分信号，例如收到 `SIGINT` 或 `SIGTERM` 后停止循环、关闭监听套接字、刷新必要状态，再从主流程返回。这里的“可以处理”不表示必须退出：程序也可以记录日志、拒绝当前操作或选择延后退出；具体策略取决于代码。

但 `SIGKILL` 不能被捕获、忽略或延后。内核会直接结束目标进程，程序没有机会执行信号处理函数，也不能依赖 `defer` 完成清理。类似地，若代码调用 `os.Exit`，Go 也会跳过尚未执行的 `defer`。

因此，排查时应优先尝试可协作的终止请求；只有在进程无响应且确认风险后，才考虑强制终止。强制结束能释放进程占用，却不承诺连接关闭、消息处理或本地状态写入已经完成；终端中显示的退出结果及是否标记为“被信号终止”，也应以实际 shell 和运行环境为准。

### Go 清理逻辑的适用边界

### Go 清理逻辑的适用边界

Go 程序可以通过 `os/signal` 订阅部分可捕获信号，例如 `SIGINT`（常见于按下 `Ctrl+C`）和 `SIGTERM`（常见于外部请求进程结束）。收到这类信号后，主协程可进入受控退出路径：停止后台任务、关闭监听器或文件句柄、等待必要的 goroutine 收尾，并让已注册的 `defer` 按正常返回路径执行。

典型思路是：信号到达后不立刻强制退出，而是通知程序“开始结束”；清理完成后再从 `main` 返回。这里的关键不是“捕获信号”本身，而是程序是否把它转换为可控的退出流程。

但这种机制有明确边界：

- `SIGKILL` 不能被程序捕获、阻塞或忽略。系统会直接终止目标进程，尚未执行的 `defer`、关闭逻辑和日志刷盘都不保证发生。
- `os.Exit(...)` 会直接结束进程，同样不会执行当前 goroutine 或其他 goroutine 中尚未运行的 `defer`。因此，若希望依赖 `defer` 释放资源，应避免在清理路径中过早调用它。
- 信号处理也不等于业务完整恢复。例如停止网关时，是否继续接受新连接、如何处理在途消息、如何恢复会话状态，仍需由后续协议与服务设计定义。

因此，在个人本地调试中，可把 `SIGINT`、`SIGTERM` 看作“给予程序清理机会的请求”，而不能把任何进程终止都视为“清理必然完成”。命令行最终显示的退出状态或“被信号终止”提示还会随 shell 与运行环境而变化，不应据此臆造固定含义。

### 退出现场不能替代业务结论

### 退出现场不能替代业务结论

在受控的个人 IM CLI 中，按下 `Ctrl+C`、发送 `SIGTERM`，或观察到进程从 `ps` 列表消失，只能说明“退出流程可能发生了”，不能直接推出“消息已送达”“对端已收到”或“下次连接一定能恢复”。

应把现场分成几层看：

- **进程退出**：程序主动返回、收到可处理的终止请求后收尾，或被强制结束，都会使进程最终消失；但退出路径不同。
- **文件描述符关闭**：进程退出时，内核会回收其打开的套接字、文件等描述符。这能结束本地资源占用，却不等于应用层已完成协议中的确认、注销或消息刷盘。
- **日志残留**：看到“正在关闭”“已断开”等日志，只是程序曾执行到该处；日志缓冲是否落盘、最后一条消息是否真正发出，仍需结合实现和现场判断。
- **业务状态**：消息送达、重复投递规避、未确认消息重试、断线重连后的会话恢复，都依赖协议和持久化设计，属于后续业务机制，不应由“进程已经退出”替代证明。

例如，CLI 在处理 `SIGINT` 后可以停止接收新输入、关闭连接并返回；但若此时仍有在途消息，关闭套接字可能使其成功、失败或处于未知状态。相反，`SIGKILL` 无法被程序捕获或忽略，不能保证 `defer` 执行；Go 中调用 `os.Exit` 也会跳过尚未执行的 `defer`。因此，退出码或 shell 对“被信号终止”的显示只能作为环境相关线索，不能编造成固定业务结论。

### 记录可验证的停止故障假设

### 记录可验证的停止故障假设

遇到“本地 IM CLI 停不掉”时，先写出可证伪的假设，而不是直接假定“信号失效”或“退出码异常”。一次受控个人进程的记录可围绕以下证据展开：

- **目标是否正确**：记录 `PID`、命令行、启动时间与父进程。`ps -o pid,ppid,stat,lstart,args -p <PID>` 可避免误杀由守护脚本、终端或其他工具拉起的同名进程。
- **信号从何而来**：明确是终端 `Ctrl+C` 产生的 `SIGINT`、`kill -TERM <PID>` 发出的 `SIGTERM`，还是外部工具发送了 `SIGKILL`。前两者是可请求程序自行收尾的终止信号；`SIGKILL` 不能被捕获、忽略或延后处理，不能据此期待 `defer` 执行。
- **进程现场是什么**：保存工作目录、环境和打开资源的只读线索，例如  
  `readlink /proc/<PID>/cwd`、`tr '\0' '\n' < /proc/<PID>/environ`、`ls -l /proc/<PID>/fd`。环境中可能包含配置路径、代理设置或日志级别；注意其中也可能有敏感值，不应原样上传。
- **状态是否支持假设**：`/proc/<PID>/status` 中的状态、线程数和信号相关字段，可辅助判断进程仍在运行、睡眠，还是已经不存在。它们是观察证据，不等同于业务已完成清理。

记录应使用条件句：例如“若 `SIGTERM` 已发送且进程仍存活，检查其是否有阻塞操作或未处理的终止路径”；不要编造固定退出码。`os.Exit` 也会跳过尚未执行的 `defer`；而 shell 如何表示“被信号终止”取决于具体环境，应以实际命令输出和进程现场为准。

> **要点** — SIGTERM 和 SIGINT 可请求协作退出；SIGKILL 与 os.Exit 不保证 defer 执行，进程停止也不能直接推出 IM 业务结果。

定位本地 IM CLI 的路径或资源故障，应先固定进程现场证据，再提出可验证假设，避免把内核观察直接等同于业务结论。

### 以 PID 与 PPID 锁定观察对象

### 以 PID 与 PPID 锁定观察对象

先从已知的进程号开始，而不是按名称模糊猜测。可用教学命令：

`ps -o pid,ppid,stat,comm -p PID`

其中：

- `PID` 是当前进程实例的标识；记录它时应同时记录观察时刻，因为进程退出后，内核可能复用同一 PID。
- `PPID` 是父进程号，可用于判断该 IM CLI 是由终端、脚本、服务管理器还是另一层启动器拉起。若 `PPID` 为 `1`，通常表示原父进程已退出、该进程被重新托管；这不是“服务一定正常”的证明。
- `STAT` 是内核调度状态及附加标记的摘要，只能提供初步线索。例如 `R` 表示可运行，`S` 表示可中断睡眠，`D` 常与不可中断等待有关，`Z` 表示僵尸进程。它不能直接证明 CPU 饱和、网络阻塞或业务死锁。
- `COMM` 是短命令名，便于区分同名父子进程或包装器，但可能被截断，也不等同于完整启动参数。

例如，若目标 `PID` 的 `PPID` 指向 shell，而 shell 又由终端启动，可先建立“交互终端启动”的假设；若其父进程是 supervisor，则应把服务配置和重启策略纳入后续检查。观察记录至少应包含时间、PID、PPID、`COMM`、所在主机或容器范围；在容器、PID namespace 或 `hidepid` 配置下，看到的父子关系与可见进程集合可能并非宿主机全貌。

### 从工作目录解释相对路径

### 从工作目录解释相对路径

进程解析相对路径时，基准通常不是可执行文件所在目录，而是其**当前工作目录**。对目标进程可教学性地观察：

`readlink /proc/PID/cwd`

该符号链接指向进程此刻的工作目录。若 IM CLI 以工作目录 `/srv/im-client` 启动，则代码中的 `./config.json`、`logs/client.log` 分别会解析为：

- `/srv/im-client/config.json`
- `/srv/im-client/logs/client.log`

因此，“找不到配置文件”并不必然表示文件缺失；也可能是启动器、服务管理器、容器入口脚本或调用者改变了工作目录。例如程序文件位于 `/opt/im/bin/client`，但进程的 `cwd` 是 `/tmp`，则 `./plugins` 指向 `/tmp/plugins`，而非 `/opt/im/bin/plugins`。

需要明确区分三件事：

- **程序文件位置**：可执行文件本身所在路径；
- **启动位置**：启动命令执行时的目录，常是初始工作目录；
- **当前工作目录**：进程现在用于解析相对路径的目录，程序可在运行中通过 `chdir` 改变它。

所以证据链应写成：“在时刻 $t$，PID 为 `PID` 的进程工作目录为 `X`；其访问相对路径 `R` 时，预期解析为 `X/R`。”这只是路径推导，尚不能证明程序确实访问过该文件。还应注意进程可能已退出、PID 被复用，且容器、权限或 `hidepid` 设置可能使 `/proc/PID/cwd` 不可见；观察时应同时记录 PID、命令和环境范围。

### 用描述符还原资源连接现场

### 用描述符还原资源连接现场

每个进程都通过文件描述符访问资源：`0` 是标准输入，`1` 是标准输出，`2` 是标准错误。它们未必连接终端：本地 IM CLI 可能从管道读取消息，将正常结果重定向到文件，而把报错写入另一份日志。

可先在记录观察时刻、PID 与命令后，教学性地查看：

`ls -l /proc/PID/fd`

输出中的符号链接可初步还原连接关系，例如：

- `0 -> /dev/pts/3`：输入来自当前终端；
- `1 -> pipe:[12345]`：输出交给下游进程；
- `2 -> /tmp/im-cli.err`：错误信息被重定向到文件；
- `3 -> socket:[...]`：进程持有套接字，但仍需结合网络信息确认对端；
- `4 -> /path/config.json`：配置或数据文件仍处于打开状态；
- `5 -> anon_inode:[eventpoll]`：内核事件机制，不是普通磁盘文件。

描述符是“进程当前持有什么”的快照，不直接说明“为什么失败”。例如，看到 `pipe` 只能提出“是否因下游退出而写入失败”的假设；看到日志文件也不能证明该文件就是本次错误来源。短命进程可能已退出，PID 还可能复用；权限、`hidepid` 或容器命名空间也会使部分描述符不可见。因此应将 `PID`、时间、命令及所在宿主机/容器范围一并记录，再用可复现操作验证。避免读取或打印 `/proc/PID/environ` 全文，其中可能包含令牌、密码等秘密。

### 识别 procfs 观察的权限与时效边界

### 识别 procfs 观察的权限与时效边界

`/proc` 是内核按当前时刻生成的伪文件系统，不是进程启动时留下的静态档案。观察本地 IM CLI 时，可将接口分为三类：

| 类型 | 例子 | 能回答的问题 | 边界 |
|---|---|---|---|
| 普通只读观察 | `ps -o pid,ppid,stat,comm -p PID`、`readlink /proc/PID/cwd`、`ls -l /proc/PID/fd` | 进程标识、父子关系、工作目录、已打开描述符的名称线索 | 结果仅对应采样瞬间 |
| 受限可见性 | `/proc/PID/*`、其他用户的进程目录 | 是否能看见或读取目标进程 | 受 UID、能力、`hidepid`、安全策略影响 |
| 可写控制接口 | `/proc/sys/*` 等 | 部分内核参数可被调整 | 不是“观察数据”，修改会影响系统行为 |

看不到进程不等于进程不存在：挂载时启用 `hidepid`、目标属于另一用户、容器与宿主机处于不同 PID 命名空间，都可能使目录缺失、内容被拒绝读取，或只看到命名空间内的 PID。应先记录观察位置（宿主机或容器）、执行用户、时间点、PID 与命令。

还要防范时效偏差：短命子进程可能在两次读取之间退出；原 PID 退出后，内核可能复用该数字给新进程。因此不要把单个 PID 当作永久身份，应结合采样时刻、`comm`、PPID 和环境范围交叉确认。`STAT` 只能作为初步线索，不能据此断言 CPU 占用高或具体阻塞原因。另避免读取或打印 `/proc/PID/environ` 全量内容，其中可能含令牌、密码或代理凭据。

### 形成可复核的故障排查记录

### 形成可复核的故障排查记录

一次有效排查不应只留下“看过了、没发现问题”，而应形成可由他人复查的现场快照。建议每条记录固定包含：

- **观察时刻**：记录带时区的时间，如 `2025-03-08 14:32:05 +08:00`；短命进程可能已退出，PID 也可能被复用。
- **对象与范围**：PID、执行账户、主机或容器标识、命名空间/运行环境；`hidepid`、容器 PID namespace 会影响可见结果。
- **进程身份**：用 `ps -o pid,ppid,stat,comm -p PID` 记录 PID、父 PID、`STAT` 与命令名。`STAT` 仅是初步线索，不能据此断言 CPU 饱和或具体阻塞原因。
- **工作目录**：通过 `readlink /proc/PID/cwd` 记录实际工作目录，核对相对路径配置、日志目录或套接字路径。
- **描述符摘要**：用 `ls -l /proc/PID/fd` 记录关键文件、管道、套接字或已删除文件的链接目标；避免无差别传播敏感路径。
- **假设与验证**：明确写成“现象—假设—下一步验证”。例如：“工作目录指向旧发布目录；假设 CLI 读取了旧配置；待核对启动脚本与配置加载日志。”

可采用如下模板：

`时刻｜环境范围｜PID/PPID/命令/STAT｜cwd｜关键 fd 摘要｜观察｜假设｜验证结果`

不要读取或打印 `/proc/PID/environ` 全量内容，其中可能含令牌、密码和业务密钥。更重要的是，将**系统观察**与**业务结论**分开：`procfs` 显示的是某一时刻的内核视角，不直接证明“消息发送失败”或“服务不可用”。

> **要点** — procfs 与 ps 提供的是带时效和权限边界的进程事实；记录证据后再验证路径、资源与业务假设。

通过同一款本地 IM CLI 在不同启动条件下的现场差异，建立“观察事实、提出假设、验证边界”的资源故障排查框架。

### 案例现场与排查边界

### 案例现场与排查边界

设想本地 IM 命令行工具 `imcli` 出现以下现场：同一条 `send` 命令在终端中可用，经由服务脚本启动却报“配置不存在”；显式传入 `--file` 后行为改变；环境变量指向另一份配置；进程的文件描述符数量持续上升；某些附件读取失败；收到 `SIGTERM` 后进程退出。

这些是待解释的现象，不等于“消息未送达”“会话失效”或“发生泄漏”。

| 现象 | 假设 | 只读证据 | 下一验证 | 仍未知 |
|---|---|---|---|---|
| 相对 `file` 找不到 | 当前工作目录不同 | `/proc/<pid>/cwd`、启动命令 | 在两种目录下解析同一路径 | 实际使用哪份配置 |
| `--file` 后恢复 | 显式参数覆盖环境 | `/proc/<pid>/cmdline`、`environ` | 比较参数、环境与加载日志 | 覆盖优先级细节 |
| 环境变量指错文件 | 服务继承了旧环境 | `systemctl show`、`/proc/<pid>/environ` | 读取目标文件内容与权限 | 是否已重新加载服务 |
| `fd` 数上升 | 连接或文件未关闭 | `/proc/<pid>/fd` 快照、`lsof` | 比较 fd 类型及增长速率 | 是否构成泄漏 |
| 附件读取失败 | Linux 文件许可不足 | `stat`、目录逐级权限、进程身份 | 以同一 UID 只读访问 | 是否还有安全模块限制 |
| `SIGTERM` 后退出 | 正常响应终止信号 | `journalctl`、退出码、信号记录 | 检查是否有优雅清理日志 | 是否影响未发送任务 |

必须分层判断：文件访问许可属于 Linux 身份与路径问题；IM 会话权限属于认证授权问题；JSON 无效是输入解析问题；服务端送达需要服务端回执或消息状态证据。`ps` 显示进程存活，只能证明进程尚在；`fd` 较多，也只能说明当前持有资源，不能直接证明泄漏。

### 工作目录改变相对路径含义

### 工作目录改变相对路径含义

命令中的 `file` 若写为相对路径，其含义不由脚本所在目录决定，而由进程的当前工作目录（cwd）决定。即使启动的是同一个 IM CLI，交互终端、`systemd` 服务、定时任务或父进程拉起的子进程，也可能拥有不同 cwd。

| 现象 | 假设 | 只读证据 | 下一验证 | 仍未知 |
|---|---|---|---|---|
| `file=config.json` 在终端可用，服务中报“文件不存在” | 两次启动的 cwd 不同，解析到了不同对象 | `ps -o pid,ppid,args -p $PID`；`readlink /proc/$PID/cwd`；`readlink /proc/$PID/exe` | 对 cwd 与 `file` 拼接后的绝对路径执行 `ls -l`、`stat` | 目标文件内容是否为预期配置 |
| 进程存活但消息未发出 | CLI 读取了 cwd 中另一个同名 JSON | `readlink /proc/$PID/cwd`；`cat /proc/$PID/cmdline`；比较两个候选文件的 `sha256sum` | 使用显式绝对路径重跑，或检查日志中的实际配置路径 | JSON 是否有效、会话是否有发送权限 |
| 子进程行为与手工启动不同 | 父进程继承或设置了不同 cwd | 记录 PID、PPID：`ps -o pid,ppid,lstart,args -p $PID`；沿 PPID 查看启动链 | 检查父进程启动位置、服务单元的 `WorkingDirectory=` | 是否还有 `--file`、环境变量覆盖该路径 |

可将相对路径解析写成：

$实际文件 = cwd / file$

例如终端位于 `/home/u/project` 时，`file=conf/im.json` 指向 `/home/u/project/conf/im.json`；服务 cwd 若为 `/`，则指向 `/conf/im.json`。因此，看到 PID 存活只能证明进程尚未退出，不能证明它读到了正确文件，更不能证明 IM 会话、JSON 内容或服务端送达状态健康。最稳妥的下一步是记录 PID、PPID、cwd 与最终绝对路径，再分别验证文件存在性、访问许可和配置语义。

### 启动条件的优先级与错误配置

### 启动条件的优先级与错误配置

本地 IM CLI 常按“命令行显式参数 → 环境变量 → 内置默认值”选择配置路径。例如：

`imcli -file ./prod.json`  
`IM_CONFIG=/etc/im/dev.json imcli`

可将最终配置来源视为：

$$
C=\operatorname{first}(-file,\ IM\_CONFIG,\ default)
$$

其中，`-file` 的优先级最高；即使环境变量指向另一份文件，显式参数仍会覆盖它。但“覆盖成功”只说明程序选择了该路径，**不说明该文件存在、可读、JSON 有效，或其中的服务器与会话凭据正确**。

| 现象 | 假设 | 只读证据 | 下一验证 | 仍未知 |
|---|---|---|---|---|
| 同一命令在终端 A、B 行为不同 | 两处 `cwd` 不同，`./prod.json` 解析到不同文件 | `pwd`；`readlink -f ./prod.json`；检查启动命令 | 改用绝对路径重新启动 | 文件内容是否可用 |
| 已设置 `IM_CONFIG` 仍连接到意外服务器 | `-file` 显式覆盖环境变量 | `ps -ef` 或 `/proc/<pid>/cmdline`；`/proc/<pid>/environ` | 比较最终选中的配置文件及其字段 | 服务端是否接受凭据 |
| 报“配置加载失败” | 路径错误、权限不足或 JSON 无效 | `stat`、`namei -l`、`cat`/校验工具的报错 | 分别确认目录可搜索、文件可读、JSON 可解析 | 配置语义是否正确 |
| 进程仍存活但 IM 不可用 | 配置仅使进程启动，未建立健康会话 | 日志中的连接、认证、心跳记录 | 查询会话状态或发送测试消息 | 服务端是否实际送达 |

尤其要区分四层结论：Linux 文件访问许可决定能否读取；IM 会话权限决定能否认证；JSON 有效性决定能否解析；服务端送达决定消息是否真正到达。看到 `ps` 中进程存活，只能证明进程尚未退出，不能证明 IM 健康。

### 描述符、权限与退出现场

### 描述符、权限与退出现场

Linux 进程默认继承标准输入 `0`、标准输出 `1`、标准错误 `2`。本地 IM CLI 的日志、管道输入、配置文件、套接字都会对应打开文件描述符（fd）。可用 `/proc/<pid>/fd` 只读观察其当前引用对象，用 `ls -l` 区分普通文件、管道、套接字与匿名对象。

| 现象 | 假设 | 只读证据 | 下一验证 | 仍未知 |
|---|---|---|---|---|
| fd 数量持续上升 | 存在描述符泄漏 | 多次记录 `/proc/<pid>/fd` 数量及新增链接目标 | 比较新增 fd 是否为同类文件或 socket，结合请求量观察 | 新增是否是正常并发、重连或日志轮转 |
| 配置读取失败：`Permission denied` | Linux 文件访问许可不足 | `stat` 查看属主、组、模式；`namei -l` 查看路径各级目录搜索权限 | 以实际运行用户检查可读性，而非仅看自己的权限 | 是否还有 ACL、挂载选项或安全模块限制 |
| 登录后仍无法发消息 | IM 会话权限或服务端授权失败 | 客户端日志中的会话状态、请求响应码、账号与目标会话信息 | 用同一已认证会话查询权限或发送测试消息 | 服务端是否实际接收、排队或送达 |
| 启动即解析失败 | JSON 无效或读到了错误文件 | 日志中的解析位置；检查实际打开路径及文件内容 | 对该文件执行 JSON 校验，并核对 `cwd`、`-file`、环境变量优先级 | 配置语义是否满足工具要求 |
| 收到 `SIGTERM` 后退出 | 外部发出了终止请求 | 日志中的信号记录、退出码、父进程与服务管理器事件 | 查找谁发送信号：shell、systemd、容器或脚本 | 终止是预期发布动作还是健康检查误杀 |

`ps` 显示进程存活，只能证明其尚未退出；它不能证明配置正确、IM 已登录或消息已送达。同样，fd 多也只是资源占用快照：若数量随负载上升后回落，可能正常；若在稳定负载下单调增长，才值得继续追踪。SIGTERM 后的有序退出则应与崩溃区分：前者通常有信号、清理与明确退出链，后者更可能伴随异常日志、核心转储或非预期状态。

### 现象证据表与下一步验证

### 现象证据表与下一步验证

排查时先记录可复现事实，再让证据缩小假设；`ps` 中进程仍存活只说明它尚未退出，不能证明 IM 已认证、请求有效或消息已送达。

| 现象 | 假设 | 只读证据 | 下一验证 | 仍未知 |
|---|---|---|---|---|
| 同一 `file` 参数在不同终端读取不同配置 | 相对路径受当前工作目录 `cwd` 影响 | `pwd`、`readlink /proc/$pid/cwd`、`strace -e openat` | 改用绝对路径后比较行为 | 配置内容是否正确 |
| 设置环境变量后仍读取旧文件 | 显式 `-file` 覆盖环境变量 | `ps eww -p $pid`、启动日志、`/proc/$pid/cmdline` | 分别去掉 `-file` 或环境变量重启 | 程序实际优先级规则 |
| `env` 指向不存在或错误文件 | 变量值拼写、继承或加载顺序错误 | `tr '\0' '\n' </proc/$pid/environ`、`ls -l "$FILE"` | 在同一启动上下文打印并校验路径 | 是否还有默认配置兜底 |
| 文件打开数持续上升 | 可能泄漏，也可能是并发连接、日志轮转 | `ls /proc/$pid/fd | wc -l`、`lsof -p $pid` 的类型与时间序列 | 固定负载采样，观察停止请求后是否回落 | 哪段代码未关闭描述符 |
| 读取配置报拒绝访问 | Linux 文件许可、属主或目录执行权限不足 | `id`、`namei -l 文件路径`、`getfacl` | 用运行用户只读测试目标文件 | 是否受 SELinux/AppArmor 限制 |
| 请求返回未授权 | IM 会话令牌过期或账号无会话权限 | 客户端响应码、令牌过期时间、只读会话查询 | 重新认证并发送测试请求 | 服务端是否已接收消息 |
| 本地 JSON 解析失败 | 文件内容无效，与权限无关 | `jq . 配置文件`、错误行列 | 修正格式后重新解析 | 字段语义是否符合接口 |
| 收到成功响应但对方未见消息 | 服务端受理不等于最终送达 | 请求标识、服务端回执、投递状态查询 | 按消息标识查询投递链路 | 对端离线、策略拦截或客户端展示问题 |
| 收到 `SIGTERM` 后退出 | 被服务管理器、脚本或人工终止 | 日志、`journalctl`、退出码、审计记录 | 核对父进程与停止策略 | 终止信号最初来源 |

Linux 文件许可决定“能否访问本地文件”；IM 会话权限决定“能否调用接口”；JSON 有效性决定“请求能否构造”；服务端送达决定“消息是否抵达目标”。四者属于不同层次，证据不可互相替代。

> **要点** — 进程现场只能支持可验证假设；路径、配置、描述符与存活状态都不能直接证明 IM 业务健康或消息送达。

以本地 IM CLI 的完整 check 失败为现场，在不执行命令的前提下读取静态进程证据，建立可验证的路径与资源故障判断。

### 先固定现场：进程实例与证据边界

### 先固定现场：进程实例与证据边界

排查本地 IM CLI 的完整 `check` 失败时，第一步不是解释“为什么失败”，而是锁定**哪一个进程实例**值得解释。预设观察参数为：

- `c-a`：命令行参数，确认实际启动的是哪个可执行文件，以及传入的配置、工作目录或子命令。
- `u-a`：用户与权限属性，确认进程以谁的身份运行，避免把权限差异误判为路径问题。
- `m-a`：内存映射与装载信息，确认进程实际装入的程序、动态库或映射文件。
- `PID`：当前被观察的进程实例标识。
- `PPID`：父进程标识，用于还原它由终端、脚本、守护进程还是其他 CLI 拉起。
- 启动条件：启动位置、启动用户、继承环境、是否经由包装脚本，以及预期工作目录。

记录时应把“事实”与“结论”分栏，禁止让结论伪装成证据：

| 项目 | 事实记录 | 业务结论 |
|---|---|---|
| 进程身份 | `PID=...`，`PPID=...`，用户为 `...` | 是否属于本次 `check` |
| 启动命令 | `c-a` 显示的原始参数 | 参数是否指向预期配置 |
| 启动上下文 | 父进程、启动目录、继承环境 | 相对路径是否可能失效 |
| 文件资源 | 打开的配置、日志、套接字、FD | 失败是否与资源定位相关 |

例如，事实可以是：“该实例的 `PPID` 对应包装脚本，工作目录为 `/tmp`，参数中出现 `config/app.yaml`。”业务结论才是：“`config/app.yaml` 作为相对路径，可能未指向项目配置。”前者可由静态证据复核；后者仍需等待 `cwd`、环境变量、打开文件和错误输出相互印证。

证据边界同样重要：`PID` 只能说明一个瞬时实例，不能自动代表所有同名进程；命令行中的路径只是输入，不能证明文件已成功打开；父进程关系能够解释启动链，却不能单独证明业务规则错误。先固定实例、保留原始观察值，再进入路径、环境变量与文件描述符分析，才能避免把另一进程的现场误归因给本次失败。

### 相对路径为何在 check 中失效

### 相对路径为何在 check 中失效

`check` 读取的不是“你以为的项目目录”，而是进程实际工作目录（`cwd`）下解析出的路径。若参数为：

`--config configs/im.yaml`

其目标可写为：

$P=\operatorname{clean}(\mathrm{cwd}/\texttt{configs/im.yaml})$

因此，CLI 参数本身正确，并不保证目标文件正确。静态观察应把预期与真实证据分开记录：

| 证据项 | 预期 | 个人真实观察 | 推论 |
|---|---|---|---|
| 参数 | `configs/im.yaml` | 待填写 | 是否为相对路径 |
| `cwd` | 项目根目录 | 待填写 | 相对路径起点 |
| 环境变量 | 如 `IM_CONFIG` 未覆盖 | 待填写 | 是否改写配置来源 |
| 目标文件 | `$cwd/configs/im.yaml` 存在且可读 | 待填写 | 最终解析是否成立 |
| 文件描述符 | 已打开目标配置或日志 | 待填写 | 进程实际使用的资源 |

例如进程从 `/srv/im/bin` 启动，却传入 `configs/im.yaml`，实际寻找的是 `/srv/im/bin/configs/im.yaml`，而非源码目录 `/srv/im/configs/im.yaml`。环境变量可能进一步覆盖参数默认值；已打开的文件描述符则只能证明进程曾成功打开某个文件，不能证明当前相对路径仍指向它。

按 01.12 的 `0/2/3/4/5` 分类，可形成故障链：

- **0：参数缺失或空值**：未提供配置参数，默认相对路径生效。
- **2：路径解析错误**：`cwd` 与预期不同，或环境变量覆盖后仍是相对路径。
- **3：目标不存在**：拼接后的实际路径没有该文件。
- **4：资源不可用**：文件存在但权限、挂载状态或目录访问条件不满足。
- **5：业务校验失败**：文件已读到，但内容、令牌、地址等不符合 `check` 规则。

修复应保持业务规则不变，只消除解析歧义：将参数或环境变量改为明确绝对路径，如 `/srv/im/configs/im.yaml`；或在启动定义中明确工作目录。不要把“找不到文件”改写成跳过校验，也不要依赖调用者恰好位于项目根目录。

### 从描述符读取资源现场

### 从描述符读取资源现场

进程的文件描述符（FD）是“已打开资源”的静态证据。除 `cwd`、`argv`、环境变量外，应同时观察标准流与其他 FD，避免把“路径存在”误判为“进程实际可用”。

- `0`：标准输入。它可能连接终端、管道、文件或空设备；可证明配置、消息或凭据是否可能由输入流提供。
- `1`：标准输出。若重定向到日志文件、管道或已关闭目标，CLI 的成功提示未必显示在当前终端。
- `2`：标准错误。错误信息常在此输出；`1` 与 `2` 指向不同位置时，“没有输出”不能证明“没有失败”。
- 其他 FD：可指向配置文件、数据库、套接字、日志、临时文件或目录。已打开的文件证明进程曾成功完成打开操作，但不证明后续读写一定成功。

目录 FD 尤其重要：进程可通过目录句柄配合相对路径访问资源，因此仅比较 `cwd` 与配置中的相对路径仍不充分。反之，若证据显示程序只依赖 `cwd`，则 `config/token.json` 的实际解析结果是：

$$\operatorname{clean}(\text{cwd}/\text{config/token.json})$$

此时从不同工作目录启动，得到的就是不同资源现场；业务规则没有变化，失败来自启动上下文。修复应将部署入口、配置位置或重定向目标改为明确绝对路径，而非随意修改认证、消息或重试逻辑。

还要区分“打开”与“可访问”：FD 可证明对象已被内核接受为打开目标；文件权限、目录搜索权限、挂载状态及重定向链则解释为何打开失败、输出丢失或资源不可达。记录时应分栏写下“预期 FD 指向”和“个人真实观察”，不可用预期替代证据。

### 只读检查的推理模板与改法

### 只读检查的推理模板与改法

对本地 IM CLI 的完整 `check` 失败，先区分**预期**与**真实观察**：预期是程序应读取项目配置、连接本地服务并写入约定日志；真实观察只能来自预设的 `ps`、`/proc/<pid>/cwd`、`/proc/<pid>/environ`、`/proc/<pid>/fd` 与文件元数据，不能用猜测补全现场。

可按“假设—证据—反证—结论”记录：

- **假设**：程序以相对路径读取 `config/check.yaml`。
- **证据**：`ps` 显示参数为 `--config config/check.yaml`；`cwd` 指向 `/tmp`；环境中没有覆盖配置目录的变量。
- **反证**：若 `cwd` 已是项目根目录，或参数实际为绝对路径，则“工作目录错误”不成立。
- **结论**：相对路径由进程工作目录解释，而非由可执行文件所在目录解释；启动位置变化即可使同一业务规则失败。

按 01.12 的 `0/2/3/4/5` 分类，可将观察落为：`0` 成功；`2` 参数或调用方式错误；`3` 路径、权限、文件不存在等环境错误；`4` 资源暂不可用，如 FD 指向的套接字已关闭；`5` 程序内部或未分类失败。分类依据应来自退出状态、参数、文件状态与 FD 指向，不能仅凭错误文案。

改法不改变“读取该配置、访问该日志、连接该服务”的业务规则，只消除路径解释歧义：

- 将 `config/check.yaml` 改为明确的绝对路径；
- 将日志目录、Unix socket、附件目录统一由受控配置给出明确路径；
- 若必须保留相对参数，则在启动定义中明确工作目录，并把它作为部署契约；
- Go 中优先以配置的明确路径调用 `os.Open`、`os.Stat`，不要隐式依赖当前工作目录。

FD 还能补强判断：`fd` 指向常规文件说明已打开对象未必等于目标路径；指向 `socket:[…]` 只能证明套接字存在，不能证明对端服务可用；指向 `/dev/null` 则提示输出可能被丢弃。记录时应写“预期 FD 结构”和“实际 FD 结构”，再给出可被后续验证推翻的结论。

### 练习：记录预期与真实观察

### 练习：记录预期与真实观察

对每题建立两栏：**预期**写依据与推断，**真实观察**只记录已给定的 `ps`、`cwd`、`env`、文件参数及 FD 证据；不得把猜测写成事实。可按 01.12 的 `0/2/3/4/5` 分类记录：`0` 正常、`2` 路径、`3` 权限或资源、`4` 环境或依赖、`5` 业务规则。

1. **起步**：PID 是否属于目标 IM CLI？反馈：核对命令行与父 PID，不以进程名缩写定案。  
2. **起步**：`cwd` 是哪个目录？反馈：相对 `config.json` 必须相对此目录解释。  
3. **起步**：参数给出 `./data/a.db` 时实际目标是什么？反馈：写出规范化后的绝对路径。  
4. **起步**：参数本身是绝对路径吗？反馈：绝对路径不受 `cwd` 改变影响。  
5. **起步**：`PATH` 缺少目录会影响已打开文件吗？反馈：只影响后续命令查找，通常归 `4`。  
6. **原理**：`HOME` 与 `cwd` 不同，默认配置应推断在哪里？反馈：仅在程序规则已知时推断。  
7. **原理**：FD `3 -> /tmp/im.sock` 表示连接成功吗？反馈：仅证明该描述符指向该对象。  
8. **原理**：FD 指向 `(deleted)` 能否说明立即故障？反馈：不能；记录风险与继续可读的可能。  
9. **原理**：缺少目标文件应归哪类？反馈：通常为 `2`，除非业务规则定义为其他状态。  
10. **原理**：权限位不可读能否断言访问失败？反馈：还需进程身份、ACL 等证据，暂记边界。  
11. **工程**：PID 已变更，旧观察还能用于新进程吗？反馈：不可混用，按 PID 分组。  
12. **工程**：配置参数为相对路径而启动目录错误，如何修复？反馈：改为明确绝对路径，不改业务规则。  
13. **工程**：日志文件 FD 已打开但参数路径不存在？反馈：区分“启动时已打开”与“后续重新打开”。  
14. **工程**：环境变量含密钥怎么办？反馈：记录变量名、是否存在和脱敏摘要，不抄录值。  
15. **工程**：标准输出重定向至文件说明什么？反馈：说明 FD 去向，不说明日志内容完整。  
16. **工程**：`cwd` 不可访问时如何写结论？反馈：记录观察受限，不虚构目录内容。  
17. **业务**：本地 socket 存在却无法登录，能归因网络吗？反馈：不能；socket 只是局部资源证据。  
18. **业务**：数据库路径正确但租户不匹配，分类为何？反馈：`5`，路径正常而业务约束失败。  
19. **业务**：令牌环境变量缺失属于什么？反馈：通常 `4`；是否必须由业务规则确认。  
20. **业务**：收到 `SIGTERM` 能说明异常崩溃吗？反馈：不能；它表示终止请求，不等同原因。  
21. **业务**：收到 `SIGKILL` 能说明谁发出吗？反馈：不能从信号本身识别发送者。  
22. **综合**：`cwd=/srv/app`、参数 `./conf/im.yaml`、实际文件在 `/etc/im/im.yaml`。反馈：预期为 `2`；修复是将参数改为 `/etc/im/im.yaml`，不迁移文件、不修改校验规则。  

每题结尾补写“**证据不足项**”：例如“尚未观察到退出码、文件权限、信号来源或程序配置搜索顺序”。这能防止把静态现场误写成确定的业务因果。

> **要点** — 路径故障应由进程现场证据验证；权限、信号和状态不能直接证明 IM 授权或送达。
