## 本章的入口：进程存在，却找不到历史文件

03.02 已解释：磁盘上的程序文件可以启动一个进程，Go 的 `os.Open` 通过操作系统文件服务取得资源，JSON 是否有效则由程序继续判断。现在假设虚构的本地历史工具 `imhistory` 在一个终端里能 `check`，换到另一个启动方式却报“打开历史文件失败”。代码和 `history-c-a.json` 都没有改。**应该先观察进程的哪些条件，才能区分相对路径、环境、权限与文件内容？**

本章用 Linux 作为学习平台。所有 `c-a/u-a/m-a` 都是教学身份，目录与 PID 也是示意值；不要求在课程仓库或真实服务上运行命令。先学进程身份与路径，再学环境和描述符，最后用信号及只读观察组成排障证据。03.04 才讲 CPU 调度，03.07 才深入打开文件内部状态，03.12 再讨论资源故障和恢复。

|---|---|---|
| PID、父子关系、cwd、参数与环境 | 描述符、标准流、信号、procfs 观察边界 | 一份“现象→假设→只读证据→下一步”的记录 |

## 一、PID 标识这一次运行，不标识业务用户

Linux 为正在运行的进程提供**进程 ID**（PID），观察时可用它在进程表和 `/proc/<PID>/` 中定位一份运行现场。它标识的是某个时间窗口内的进程实例，**不是可执行文件的永久编号，也不是 IM 用户 ID**。同一份 `imhistory` 程序先后运行两次通常对应不同实例；旧进程退出后，PID 数值以后还可能被复用，所以仅保存一个数字而不记录观察时刻和程序身份，不能保证日后指向同一进程。

**父进程 ID**（PPID）帮助描述创建或管理关系。交互式 shell 启动外部命令时，命令通常成为与该 shell 有父子关系的进程；由服务管理器、容器入口或其他程序启动时，关系可能不同。不要把教材图固定为所有 Linux 环境的唯一启动路径，也不要用“PPID 是某个值”直接判断进程业务健康。

```text
示意时刻 t0：shell（PID 24000）
                       └── imhistory check（PID 24100，PPID 24000）

示意时刻 t1：imhistory 已退出；24100 这个数不能当永久身份。
```

03.02 还区分了线程和 goroutine。`ps` 看到一行主进程，不表示只存在一条执行线程；goroutine 也不会自动获得一个新的进程 PID。理解 `PID` 后再看线程 ID 和调度细节会更容易，留给 03.04 与 05 卷。

短命 CLI 可能在你准备查看 `/proc/24100` 时已经结束。这是**观察窗口问题**，不等于它从未运行过。个人练习可以在自己隔离环境安排一个受控的长生命周期样本，或先在纸上推演本章的虚构快照；本章不要求为了观察而启动项目里的任何服务。

## 二、工作目录决定相对路径从哪里开始

一个进程有**当前工作目录**（current working directory，cwd）。当 `-file` 给出 `history-c-a.json` 这样的相对路径，文件访问要以该进程当时的 cwd 为起点。相对路径不是“相对 Go 源码目录”，也不是必然“相对可执行文件目录”。交互式 shell 通常把自己的工作目录传给启动的命令；其他启动方式可以设置不同目录，运行中的程序也可能改变自己的 cwd。实际值要观察，不能只凭写代码时的目录猜。

```text
示意文件实际位置：/tmp/imlesson/history-c-a.json

cwd = /tmp/imlesson，-file history-c-a.json
→ 候选路径为 /tmp/imlesson/history-c-a.json

cwd = /tmp/elsewhere，-file history-c-a.json
→ 候选路径为 /tmp/elsewhere/history-c-a.json
```

第二次报“文件不存在”时，文件也许还在原目录，只是**相同的相对路径在不同 cwd 下指向不同位置**。排查时同时记录命令参数、进程 cwd、路径是否存在以及错误身份；不能只问“我在编辑器里看得到文件吗”。`os.Getwd()` 可在 Go 代码中取得当前工作目录，但本章不修改课程工具实现；Linux 的 `/proc/<PID>/cwd` 也能提供该进程 cwd 的只读视角，前提是进程还在且你有相应访问权限。

把程序内部到处调用 `os.Chdir` 当“修复路径”的通用办法并不好：它会改变同一进程后续相对路径的含义，其他部分可能受影响。对于 01.12 的 CLI，更直接的做法是使用明确的 `-file` 路径，或把启动工作目录写进运行说明。若配置合同需要支持相对路径，还应约定它相对哪个基准目录；不能暗中随部署环境变化。

即使 cwd 正确，`os.Open` 仍可能因目录不可遍历、文件访问被拒或资源问题失败；“文件存在”与“本进程能读到”不是同一个判断。03.02 的错误链仍应保留 `os.ErrNotExist`、`os.ErrPermission` 等身份，CLI 将这类文件 I/O 失败映射到课程退出码 4，而非无效 JSON 的退出码 3。

## 三、参数、环境与默认值：同一个进程的三个来源

01.12 的本地工具约定了 `-file` 的优先级：**显式 `-file` > 非空 `IMHISTORY_FILE` > 教学默认 `history-c-a.json`**。它们都决定输入路径，但来源不同。命令行选项由这次调用提供；环境变量是进程运行条件的一部分，通常由启动它的环境提供；默认值写在程序合同中。改变上限或参数格式需要另立规则，不能由本章排障自行改动。

| 条件 | 最终输入路径 | 为什么 |
|---|---|---|
| `-file=/tmp/imlesson/a.json`，环境指向 `b.json` | `/tmp/imlesson/a.json` | 显式选项优先 |
| 没有 `-file`，`IMHISTORY_FILE=/tmp/imlesson/b.json` | `/tmp/imlesson/b.json` | 非空环境默认 |
| 两者都没有或环境为空 | `history-c-a.json` | 教学默认，仍相对进程 cwd |

`os.Getenv("IMHISTORY_FILE")` 返回字符串；若要区分“未设置”和“设置为空”，Go 还提供 `os.LookupEnv`。本课程 01.12 的**现有**优先级将空值当作没有可用的环境路径，所以退回教学默认；这不是所有程序的通用环境变量规则。一个进程已经启动后，在别的 shell 中执行新的 `export`，不会神奇地更新该进程先前拿到的环境。若程序自己修改环境，则要按它自己的调用路径另行分析。

环境可包含秘密或个人数据。排查 `IMHISTORY_FILE` 只需记录“是否设置、是否为空、脱敏后的目标类别”，不应把整个 `/proc/<PID>/environ` 或所有环境变量复制进课程记录、日志或评论。尤其不要把环境变量存在当成用户已登录或已获 IM 会话授权的证据；身份与权限将在 09 卷处理。

**先后次序也重要。** `-file` 明确为空、无效 flag 或非法 `-max-bytes` 属于命令用法问题，应在读文件前按退出码 2 拒绝；路径选好了却打不开是文件 I/O 问题，退出 4；能读到字节但 JSON v1 不合法，退出 3。把三者全部写成“输入文件坏了”，会让使用者到错误层次排查。

## 四、文件描述符与标准流：进程怎样握住资源

在 03.02，`os.Open` 返回 `*os.File`；Linux 下它可关联一个**文件描述符**（file descriptor，FD）。把 FD 想成进程用于请求内核操作某项已打开资源的**整数句柄**。它不是文件字节，也不是业务消息 ID。`open` 成功会占用一个可用描述符，`Close` 结束该打开关系；以后这个整数编号可以再次分配给别的资源，所以“FD=7”脱离进程和时间没有永久含义。一个路径也可以被不同进程或同一进程多次打开，不能用路径名代替已打开资源的全部状态。

| 常见编号 | 约定用途 | 可能连接到什么 |
|---:|---|---|
| 0 | 标准输入 `stdin` | 终端、文件或管道 |
| 1 | 标准输出 `stdout` | 终端、文件或管道 |
| 2 | 标准错误 `stderr` | 终端、文件或管道 |
| 其他编号 | 打开的本地文件、套接字等 | 由具体进程与操作决定 |

0/1/2 是常见的进程启动约定，不能由“编号 1”推出它此刻一定连着你的屏幕：shell 可以重定向到文件，管道也可接到另一个进程。01.12 让成功摘要走 `stdout`，失败诊断走 `stderr`；重定向改变输出**去向**，不改变 `check/list/export` 的成功或错误分类。若把诊断错写到 `stdout`，脚本可能把错误行当成成功数据。

```text
imhistory check 进程（示意）
FD 0 → 本次标准输入
FD 1 → 本次标准输出
FD 2 → 本次标准错误
FD 3 → 打开的 history-c-a.json（示意编号，不保证总是 3）
```

一次 CLI 若不断打开文件而不关闭，描述符使用量可能增长，最终触及进程可用资源的限制。**观察到 FD 多不等于已证明泄漏**：它们也可能是当前确实需要的文件或套接字；还要结合时间变化、打开/关闭路径和负载。03.07 会详细区分 FD、内核打开文件状态、inode 与偏移，03.09 再把句柄扩展到网络 socket 和事件通知。

Linux 的 `/proc/<PID>/fd` 可提供这个进程描述符的只读观察入口，但目录项可能指向敏感路径，权限和 procfs 挂载选项也可能限制访问。学习者只应在自己的隔离样本中查看需要的编号与类别，记录必要的计数和现象，不把真实用户路径或令牌复制到教材。进程一退出，这份现场也可能消失。

## 五、信号是请求或通知，不是业务提交保证

Linux **信号**给进程传递一种异步事件通知。比如终端上的中断通常关联 `SIGINT`，常规终止请求可用 `SIGTERM`；程序可以为某些信号安排处理方式。`SIGKILL` 则不能由目标进程捕获或忽略，操作系统会强制终止。不同信号默认动作、可处理性和产生方式各不相同，不能把“发送了信号”写成“程序已经完成清理”。

对本地 `imhistory check`，你应区分三条路径：

```text
正常完成：run 返回 → 内层 defer 有机会执行 → main 决定退出状态
收到可处理的终止请求：是否清理，取决于程序如何处理该信号
被不可处理的终止强制结束：不能指望 Go defer 或写入回调执行
```

`os.Exit` 也不会运行尚未执行的 `defer`。如果未来服务需要在 `SIGTERM` 后停止接收新连接、给在途操作一个期限、关闭资源，必须**显式设计、实现并验证**信号处理路径；不由“写了 `defer`”或“系统会发 SIGTERM”自动实现。长连接网关停机时消息是否仍可恢复，是 S5–S6 的可靠性设计，不属于本章本地 CLI 已有能力。

shell 看到“由信号终止”的状态表示可能受 shell 和环境影响，本章不为所有系统编造一个固定退出码。课程 CLI 的 0/2/3/4/5 用于它自己**正常返回并主动给出**的类别；被强制终止不等于“按课程约定返回 4”。在个人练习中也不要向真实工作进程发送信号来验证教材；先用虚构时间线推演，若以后做实验，应在自己明确启动的受控样本上执行。

## 六、`ps` 与 `/proc`：只读观察也要知道视角

Linux 的 `/proc` 通常挂载为**伪文件系统**，为内核与进程信息提供文件式接口。它并非普通磁盘上的历史记录；进程状态变化时，里面能看到的内容也会变化。`/proc/<PID>/` 可暴露某次进程的若干信息；访问受权限、挂载选项（例如 `hidepid`）以及容器/命名空间视角影响。`/proc` 中**并非所有文件都只读**，所以本章只选择明确的只读观察路径，不把“浏览 `/proc`”理解为可随意修改它。

以下命令是学习者未来在**自己的隔离 Linux 练习进程**上可选择的只读观察示意；`24100` 是虚构 PID，本次编写没有执行：

```bash
ps -o pid,ppid,stat,comm -p 24100
readlink /proc/24100/cwd
ls -l /proc/24100/fd
```

第一条请求 `ps` 显示 PID、PPID、状态缩写和命令名，帮助确认正在看哪份进程；第二条读该进程的工作目录链接；第三条列出它当前可见的描述符入口。它们不保证所有环境都能成功：进程可能在两条命令之间退出，PID 以后可能复用，权限或 procfs 挂载策略可能隐藏目录，容器内部视角也可能与主机不同。若观察失败，先记录“观察不到”及原因，不填造一个 cwd 或 FD 数量。

`ps` 的 `STAT` 是一个**快照线索**，用于区别某一刻的可运行、等待等状态；它并不能单独解释为什么 CPU 高或低，也不能证明业务请求成功。具体状态码、调度和等待在 03.04 讲。`comm` 是命令名线索，不是完整身份凭据；相同名字可对应不同进程。观察时记录时间、PID、可识别的程序来源和所处环境，必要时重新确认进程仍是同一实例。

环境变量可以在 `/proc` 的其他接口出现，也可能含令牌、密码或真实路径。本章**不建议读取或展示整个进程环境**；验证 01.12 的 `IMHISTORY_FILE` 优先级时，用自己构造的虚构值与脱敏记录即可。描述符链接也可能显示隐私路径；课程笔记只保留“有一个打开的输入文件”这类足够回答问题的事实。

## 七、把观察写成因果链，而不是见到一个症状就下结论

假设有人报告：“相同的 `history-c-a.json`，手工运行 `check` 成功，从另一种启动方式运行却退出 4。”把这个观察直接解释成“Go 的 JSON 解码不稳定”并不合逻辑：退出 4 属于文件 I/O 类别，JSON 解码失败按课程合同是 3。更合适的步骤是提出几个可区分的假设，并选择最小只读证据。

| 现象 | 假设 | 要看什么 | 仍未得到的结论 |
|---|---|---|---|
| 相同相对 `-file` 一处成功、一处不存在 | 两次进程 cwd 不同 | 参数和各自的 cwd | 不代表文件内容有问题 |
| 未给 `-file` 时读错文件 | 环境默认值或教学默认指向别处 | 是否显式 flag、`IMHISTORY_FILE` 是否非空、cwd | 不代表某用户已获会话权限 |
| 路径正确但打开被拒 | 当前进程缺少文件或目录许可 | 错误身份、路径和权限条件 | 不代表 JSON 校验规则错 |
| 描述符数量随请求增长 | 某路径未关闭资源 | 自己样本的前后数量、打开/关闭代码 | 单次 FD 多不能证明泄漏 |
| 收到 SIGTERM 后迅速退出 | 未设计清理或程序按默认动作终止 | 信号处理设计和可观察退出过程 | 不代表消息已持久化 |

这里的证据强度有层次。看到 `cwd=/tmp/elsewhere` 和参数 `-file history-c-a.json`，能说明候选路径从 `/tmp/elsewhere` 开始；仍需确认文件是否在那里、访问是否许可。看到 `os.ErrPermission`，能说明文件访问被拒，但不能由此推出是哪项 IM 业务授权未通过。看到进程“还活着”，只能说明它在该时刻存在，不能推出本地 CLI 的文件内容正确、未来网关可接受连接或消息最终送达。

**修正动作也要对应原因。** 对 cwd 不一致，可在个人练习中改用显式绝对 `-file`，或明确启动目录；对配置优先级误判，按 flag > 环境 > 默认复核；对权限错误，先核对是否访问了正确的虚构练习文件。不要为了让 `check` 通过而把 JSON 校验关掉、把所有错误改成退出 0，或给进程不必要的高权限。

## 八、完整排障记录与分层练习

下面是一份**纯静态**的虚构运行现场，不是从当前机器读取的真实进程数据：

```text
文件：/tmp/imlesson/history-c-a.json（合法 v1，含 c-a/u-a/m-a）
手工运行进程 A：cwd=/tmp/imlesson，参数=-file history-c-a.json
另一启动方式的进程 B：cwd=/tmp/elsewhere，参数=-file history-c-a.json
两者都未设置可用的 IMHISTORY_FILE；文件本身未改变。

预期 A：候选 /tmp/imlesson/history-c-a.json；若可读且合法，check 退出 0。
预期 B：候选 /tmp/elsewhere/history-c-a.json；若不存在，打开错误退出 4。
```

排查记录应先写：**现象**是 A 成功、B 失败；**假设**是相对路径基准不同；**证据**是两次 cwd、同一相对 flag 和 B 的 `os.ErrNotExist` 类别；**修正**是让 B 显式使用 `/tmp/imlesson/history-c-a.json` 或约定正确工作目录；**复核**是学习者在自己隔离环境记录新进程的实际退出码、`stdout/stderr` 与文件前后字节。课程静态预期不能填进“实际运行结果”栏。即使 B 改为退出 0，也只证明本地文件被接受，不能推断线上 IM 历史完整。

### 分层练习：先回答，再核对反馈

<details><summary>1. PID 是程序文件的永久 ID 吗？</summary>

不是。它标识某个时间窗口里的进程实例，数值日后可能复用。</details>

<details><summary>2. PPID 表示什么？</summary>

表示观察时进程的父进程标识；父子关系应结合具体启动方式解释。</details>

<details><summary>3. `u-a` 与 Linux PID 是同一种身份吗？</summary>

不是。`u-a` 是虚构 IM 用户 ID，PID 是 Linux 进程实例标识。</details>

<details><summary>4. 在编辑器里看到文件，能保证任意进程用相对路径打开它吗？</summary>

不能。要看该进程的 cwd、参数和访问许可。</details>

<details><summary>5. `-file history-c-a.json` 相对哪个目录？</summary>

相对进程当时的工作目录，不必是源码或可执行文件所在目录。</details>

<details><summary>6. shell 后来改了环境变量，已启动进程一定随之改变吗？</summary>

不会自动改变。已启动进程有自己的环境状态，除非程序自身另行修改。</details>

<details><summary>7. 显式 `-file` 与 `IMHISTORY_FILE` 同时给出时用谁？</summary>

按 01.12 合同，显式 flag 优先。</details>

<details><summary>8. 环境变量为空时，本课程用哪个路径？</summary>

若没有显式 flag，退回教学默认 `history-c-a.json`，它仍是相对路径。</details>

<details><summary>9. `-max-bytes=0` 是文件打不开还是用法错误？</summary>

用法错误，读取前拒绝，退出 2。</details>

<details><summary>10. 路径存在但进程没权限读取，退出哪类？</summary>

文件 I/O 类别 4；不能报告成 JSON 无效 3。</details>

<details><summary>11. FD=3 会永久指向同一份 JSON 文件吗？</summary>

不会。描述符编号相对进程和时间，关闭后可被复用。</details>

<details><summary>12. 标准输出编号 1 一定连着屏幕吗？</summary>

不一定。shell 可以把它重定向到文件或管道。</details>

<details><summary>13. 诊断写入 stdout 与 stderr 对脚本一样吗？</summary>

不一样。01.12 约定成功结果走 stdout，错误诊断走 stderr。</details>

<details><summary>14. 看到 40 个 FD 就能判定泄漏吗？</summary>

不能。先了解正常负载与用途，再看数量是否异常增长及关闭路径。</details>

<details><summary>15. `SIGTERM` 到达后 `defer` 一定执行吗？</summary>

不保证。是否处理信号并走正常清理路径由程序实现决定。</details>

<details><summary>16. `SIGKILL` 能被 Go 程序捕获并完成优雅退出吗？</summary>

不能。不能以它作为依赖程序清理和保存的机制。</details>

<details><summary>17. `os.Exit` 会运行当前尚未执行的 `defer` 吗？</summary>

不会。资源清理应在内层函数正常返回前完成。</details>

<details><summary>18. `/proc` 的所有文件都只读吗？</summary>

不是。它是伪文件系统，其中有可写接口；本章只选择只读观察路径。</details>

<details><summary>19. `/proc/24100/cwd` 读不到，能证明 24100 从未存在吗？</summary>

不能。进程可能已退出、PID 被复用、权限或挂载策略限制可见性。</details>

<details><summary>20. 记录整个 `/proc/<PID>/environ` 适合作为公开排障证据吗？</summary>

不适合。它可能包含敏感信息；只记录与假设相关的虚构或脱敏配置事实。</details>

<details><summary>21. 文件许可通过等于有 IM 会话查看权限吗？</summary>

不等于。内核访问许可与业务身份授权属于不同层次。</details>

<details><summary>22. 进程在 `ps` 中出现能证明消息已送达吗？</summary>

不能。它只证明该时刻可观察到进程，远端受理和接收端状态需其他证据。</details>
