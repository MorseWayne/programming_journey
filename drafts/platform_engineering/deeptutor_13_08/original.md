从S2内存受理走向S3教学数据库，不是给旧结果补一层存储，而是先划清历史事实、兼容承诺与新权威的边界。

### 先分三类任务：保留、迁移与建权威

### 先分三类任务：保留、迁移与建权威

从 S2 内存受理走向 S3 教学数据库，不是“给旧结果补一层存储”，而要先把三类任务分开：

1. **保留旧合同**：S2/v1 继续按既有规则工作：正文非空、最多 `6 UTF-8 字节`、原始 HTTP 请求体最多 `4096B`；同一消息 ID 重复提交返回 `409`，非成员返回 `404`，成功返回 `200 accepted_in_memory`。这里的“accepted”只表示**当前进程内存已受理**，不等于已经写入权威历史。

2. **迁移真实存在的数据**：迁移的前提是源数据确实存在且可读取，例如已有数据库表、日志归档或可靠快照。迁移程序只能复制、校验、转换这些事实记录；它不能根据接口调用痕迹、客户端重试或推测规则，补造一条从未被持久保存的消息。

3. **建立新的权威**：S3/v2 提议将新消息写入教学数据库，并返回 `stored_in_teaching_db`。这意味着从 S3 开始，数据库成为可查询、可恢复、可审计的权威来源；它不是对 S2 内存状态的追认。

尤其不能把“旧接口仍可调用”误解为“旧历史可以恢复”。若某个 S2 进程退出，内存中的消息随之消失；没有持久源，就没有可迁移事实。回填脚本若凭空生成记录，会制造看似完整、实则不可信的历史。

S3/v2 当前仍沿用 `6B` 正文限制，以降低合同变化风险；R9 中 `6→9B` 的调整尚待审批，应作为未来版本变更处理，而不应混入存储迁移或历史回填。

### 旧内存不是可回填的历史

### 旧内存不是可回填的历史

S2/v1 返回 `200 accepted_in_memory`，只说明**当时那个进程**已在内存中接受该消息；它不是“已经进入可审计历史”的承诺。进程重启、崩溃、扩缩容或内存被释放后，若消息从未写入任何持久介质，系统便不再拥有该消息的可靠事实来源。

因此，不能把迁移理解为：

- 扫描旧日志、缓存或监控记录；
- 推测哪些请求可能曾返回 `200`；
- 用脚本向教学数据库补插一批消息；
- 再把这些补插结果标记为 S2 的权威历史。

问题不在于脚本能否写入数据库，而在于它无法证明被写入的内容就是当时被受理的原始消息。原始 HTTP 体可能未保存、日志可能截断或脱敏、重试请求可能重复、`409` 与 `200` 的时序也可能无法还原。即使补出的记录“看起来合理”，它仍是迁移时生成的推测，不是 S2 当时持久化的事实。

应明确区分三件事：

1. **保留旧合同**：S2/v1 仍按既有规则处理，如正文非空、最多 `6` UTF-8 字节、原始 HTTP 体最多 `4096` 字节、同 ID 重复为 `409`、非成员为 `404`。
2. **迁移现有数据**：仅迁移已经存在于可信持久存储中的数据，并保留来源、时间和完整性证据。
3. **建立新权威**：S3/v2 从启用持久写入开始，才可声明 `stored_in_teaching_db`；这建立的是新边界后的权威记录，而非追认旧内存。

所以，旧 S2 消息的正确状态不是“等待回填”，而是“若未持久化，则不可恢复、不可证明、不可伪装为历史”。

### 按扩展、迁移、收缩设置阶段门

### 按扩展、迁移、收缩设置阶段门

S2/v1 与 S3/v2 并存时，发布顺序应是“扩展—迁移—收缩”，但每一步都必须有可检查的准入证据，而不是只看代码是否上线。

- **扩展阶段：不改变旧合同。**  
  S2/v1 仍保持原语义：正文非空、最多 `6` 个 UTF-8 字节、原始 HTTP 体最多 `4096` 字节；同一消息 ID 重复提交返回 `409`，非成员返回 `404`，成功仅返回 `200 accepted_in_memory`。这表示结果只在当前进程内受理，不能被解释为可查询、可恢复的历史记录。  
  同时增加 S3/v2 的教学数据库写入路径与 `stored_in_teaching_db` 状态，但其当前正文上限也仍是 `6` 字节。R9 将 `6→9` 字节只是待审提议，不能悄悄借 v2 发布生效。

- **迁移阶段：只迁移存在的数据。**  
  对已经进入教学数据库的数据，可执行校验、索引补建、格式转换和回读验证；验证至少覆盖成员判定、消息 ID 去重、字节长度、原始请求体边界及写后可读性。  
  但旧 S2 进程从未持久化的内存消息，没有可迁移的源数据。回填脚本不能根据日志、猜测或“曾返回 200”凭空制造权威历史；那是在建立新记录，不是在恢复旧事实。

- **收缩阶段：以证据关闭旧路径。**  
  只有当 v2 写入稳定、读回一致、失败可观测、重复请求语义明确，并确认仍需支持的客户端已完成兼容验证后，才可停止新流量进入 v1。随后再移除旧内存受理路径、相关监控和临时代码。  

因此，兼容旧合同、迁移已有数据、建立新的权威存储是三项不同任务：前者保护调用方，第二项搬运事实，第三项从启用时刻开始产生事实。

### 双写与影读只能服从一个权威

### 双写与影读只能服从一个权威

双写不是“同时相信两个库”，影读也不是“发现不同就自动修复”。迁移期间必须明确：每个阶段只有一个写入权威、一个读取权威；另一个系统仅承担复制、验证或观测职责。

| 阶段 | 写入权威 | 读取权威 | 另一侧职责 |
|---|---|---|---|
| S2/v1 | 本进程内存 | 本进程内存 | 无法补建历史 |
| 切换前双写 | 旧内存受理结果 | 旧内存响应结果 | 教学数据库记录候选副本 |
| 影读验证 | 教学数据库或旧内存之一，须明确切换点 | 仍保持原读权威 | 对同一键查询并比较 |
| S3/v2 切换后 | 教学数据库 | 教学数据库 | 旧路径仅兼容或下线 |

对账键不能只用消息内容，应至少使用稳定的 `(成员ID, 消息ID)`；若消息ID仅在进程内生成，则不能跨进程证明同一事实。比较内容包括：是否存在、成员归属、原始体长度、正文长度上限（当前仍为 `6 UTF-8 字节`）、重复提交结果及状态语义。特别是：S2 的 `200 accepted_in_memory` 只说明该进程曾接受，不能被影读结果改写为“历史已持久”。

差异应分类处理：

- **预期差异**：旧内存因重启丢失，而新库无记录；这是不可恢复历史，不是回填失败。
- **复制差异**：双写漏写、字段截断、事务失败；由迁移实现负责人修复，并保留失败证据。
- **合同差异**：例如同 ID 重复请求未返回 `409`，或非成员未返回 `404`；由接口负责人阻断切换。
- **规则差异**：未来 R9 从 `6` 调整到 `9` 字节；在待审期间不得让影读把新规则结果当作旧合同错误。

影读只产生告警、指标和人工复核队列，不应反向写入旧内存，更不能用数据库记录“补回”从未保存过的 S2 消息。新权威只能从明确启用 S3/v2 的时刻开始建立。

### 兼容旧端，并限制确认后的回滚

### 兼容旧端，并限制确认后的回滚

`/v1` 是既有合同，不应因引入 S3 教学数据库而悄悄改变含义。旧客户端仍应看到原有规则：正文非空、最多 `6` 个 UTF-8 字节、原始 HTTP 请求体最多 `4096` 字节；同一消息 ID 重复提交返回 `409`，非成员返回 `404`。成功响应仍可保持 `200 accepted_in_memory`，但其含义必须明确：它只说明当前 S2 进程已受理，不能伪装成可跨进程查询的历史事实。

S3 可新增 `/v2` 或显式版本协商，使成功结果表达为 `stored_in_teaching_db`。这不是给 `/v1` 的旧成功补写一个新语义，而是建立新的、可查询且可恢复的权威记录。若 S3 同时接受 `/v1`，也应按旧限制校验后再落库；存储成功不反向证明旧 S2 曾保存过同 ID 消息。

R9 的长度上限从 `6` 增至 `9` 字节仍待审，因此不能提前让 `/v1` 接受 `7~9` 字节。较稳妥的演进方式是：

- `/v1` 固定 `6` 字节，直到正式废弃；
- `/v2` 在 R9 获批后才采用 `9` 字节；
- 响应、文档和测试均标明适用版本，避免客户端把“新服务器”误解为“旧规则已放宽”。

回滚也必须分阶段。尚未确认写入教学数据库时，可以停止 S3 写入并退回 S2 内存受理；但一旦已向客户端确认 `stored_in_teaching_db`，就不得回滚到“仅内存”的路径，否则已确认的记录会在重启后消失。此时只能保留数据库读取能力、修复新版本，或进行可验证的数据迁移。原则是：可以回滚代码，不能回滚已经对外确认的权威事实。

> **要点** — 旧内存结果不能补造成历史；迁移必须以唯一权威、可审计对账和不可丢失回退为边界。

迁移不是“新表已建成”就算切换，而是以兼容、证据、唯一权威和可逆边界逐步完成合同演进。

### 并行变更的三阶段与启用门

### 并行变更的三阶段与启用门

Fowler 的并行变更可概括为“扩展—迁移—收缩”：先让新旧合同能够共存，再把经批准的流量逐步迁入，最后删除已无消费者的旧路径。Evolutionary Database Design 的关键也在于：数据库模式的出现只是**能力已具备**，不是业务状态已经切换。

- **扩展（expand）**：新增可空列、新表、索引、读取兼容逻辑或事件版本解析器；旧客户端仍可写旧格式，新客户端也暂不必立刻成为唯一写入者。此时可以部署 D1/D2 代码、K1/K2 配置和新数据模式，但它们各自有独立版本轴。
- **迁移（migrate）**：仅让小范围、明确获批的 `v2` 写入教学数据库。每次写入产生可核验的证据，例如 `m-9`、`seq=9`、`E9`，并与旧路径结果对账。回填数据应标明来源、时间和转换规则，不能伪装成当时已经发生的权威事件。
- **收缩（contract）**：确认旧读写路径、旧事件消费者和旧客户端均已退出，且对账、回滚窗口、审计留存满足要求后，才删除旧列、旧表、双写逻辑或兼容解析器。

因此，“新 schema 已建”“D2 已发布”或“K2 已配置”只能证明系统**具备 S3 的候选能力**；只有启用门明确放行、目标流量实际经过批准路径、证据链完整且对账通过，才能声明 **S3 已启用**。客户端版本、事件版本、数据模式与部署版本不得互相代言；涉及 R9 的受理与权威性，还必须另行审查。

### 旧合同、回填数据与新权威

### 旧合同、回填数据与新权威

旧合同下的内存受理记录只能说明：某次请求曾按旧规则被处理，或某个进程曾暂存其结果。它不是可跨进程验证、可重放审计的历史账本。进程重启、并发覆盖、旧代码缺少事件字段，都可能使这类记录失去完整上下文；因此不能把它回填到教学数据库后，倒推出“当时已经形成权威历史”。

应区分三类证据：

| 来源 | 证据等级 | 可证明内容 | 不可证明内容 |
|---|---:|---|---|
| 旧合同内存记录 | 低 | 旧端曾受理或暂存 | 形成了持久、唯一、可审计的事件 |
| 教学数据库回填行 | 中低 | 在迁移时写入了衍生数据 | 原始发生时间、原始顺序、旧业务已启用新语义 |
| 经批准的 `/v2` 新写入 | 高 | 新合同下产生了可审计事实 | 其他版本轴已同步完成迁移 |

例如，回填可生成 `m-9 / seq=9 / E9`，但其语义应明确为“迁移生成的基线”或“回填投影”，并保存来源、回填批次、执行时间及可追溯标记。`seq=9` 是新库中的排序或版本结果，不自动等价于旧内存中第九个真实发生的业务事件。

只有在批准范围内，`/v2` 写入经由新模式、持久化约束和事件记录共同落地后，才可成为新权威的增量来源。此时仍应先对账：比较回填基线、`/v2` 增量、重复键、缺失事件与读模型结果；确认旧读写路径不再承担权威职责，才收缩旧合同。

尤其不要因为模式已扩展、表已存在或回填已完成，就宣称 `S3` 已启用。数据模式、D1/D2 代码、K1/K2 配置、事件格式和客户端版本是独立版本轴；`R9` 的审查也应独立记录。新结构可以先“可读、可写受限”，但只有批准的新写入和可核验对账，才能改变权威边界。

### 双写影读中的单一裁决口径

### 双写影读中的单一裁决口径

双写与影读的目的，是验证迁移链路，而不是制造两个“都可能正确”的历史。每个业务实体必须预先指定唯一主数据源：迁移期间仍以旧权威库为裁决源；只有经批准的 `v2` 写入教学数据库、形成连续的 `m-9 / seq9 / E9` 证据链，并完成对账后，才可显式切换权威。新 schema 已存在、影子表已有数据，均不等于 `S3` 已启用。

双写应由同一受理结果驱动。一次已批准写入生成稳定的业务键、幂等键、`seq` 与事件标识；旧路径写入产生旧记录，新路径写入产生映射后的记录或事件。对账不以“行数大致相同”为准，而按以下顺序核验：

1. **身份对应**：业务键、租户、对象类型及版本映射唯一，禁止一条旧记录被静默拆分或合并。
2. **顺序连续**：同一聚合内比较序号单调性、缺口与重复；`seq9` 必须能追溯到其来源受理或迁移批次 `m-9`。
3. **语义等价**：比较归一化后的状态、金额、时间边界、删除标记与事件类型；允许字段重命名，不允许状态含义漂移。
4. **事件闭环**：每个 `E9` 应有可定位的触发原因、写入结果和消费可见性；缺事件、重事件、乱序事件分别记录。

影读只读取候选路径并与主源结果比对，返回给客户端的仍是主源裁决值。差异首先归责于明确层次：受理判定错误、双写投递失败、模式转换错误、读取投影错误或客户端解释差异；不得用人工回填掩盖来源。回填只能修复候选副本，并保留原始差异、操作者、时间和重放依据，不能把旧内存受理追认成权威历史。

当差异率、未闭环事件与回放结果均满足门槛，且 `R9` 风险审查独立通过后，才可切换裁决源并收缩旧路径。

### 多版本轴与旧端兼容策略

### 多版本轴与旧端兼容策略

迁移期间不能用一个“版本号”概括系统状态。代码、配置、数据模式、事件格式与客户端发布节奏不同，必须分别记录其兼容关系：

- **D1/D2 代码轴**：D1 只能读取旧字段并走旧写入路径；D2 可同时读取新旧结构，但新增写入能力必须受开关约束。
- **K1/K2 配置轴**：K1 保持旧行为，K2 才允许经批准的 D2 实例写入教学数据库。配置发布不等于功能启用，更不等于历史权威已迁移。
- **数据模式轴**：先扩展 schema，例如新增可空列、新表、兼容索引或映射表；旧端仍可正常读写。schema 出现只能证明“可承载”，不能证明 S3 已启用。
- **事件格式轴**：消费者应先做到“读新也读旧”，生产者再小范围发出 v2 事件。事件需带 `schemaVersion`、幂等键与来源，避免旧消费者把 v2 误解为旧语义。
- **客户端轴**：`/v1` 保持原合同，`/v2` 才暴露新字段、新约束或新流程；不要因服务端升级而迫使未升级客户端承担迁移风险。

按 Parallel Change 的 expand/migrate/contract 推进：先扩展兼容读写能力，再仅让获批的 `/v2`、D2+K2 写入形成 `m-9 / seq9 / E9`，随后对账新旧数据、事件与审计证据；确认旧路径无调用且可回滚后，才收缩字段、接口和开关。

`R9` 不属于上述任一版本轴：它应作为独立风险审查，确认授权范围、写入对象、回填边界与证据链，而不能被“代码已上线”或“表已建好”自动放行。

### 确认新数据后的收缩与回退

### 确认新数据后的收缩与回退

当教学数据库已出现经批准的 `m-9`，并形成事件 `E9`、序列位置 `seq9` 时，回退不再等于“把代码切回旧版”。新数据已经成为需要保存、解释和审计的事实；旧路径若无法表达它，就不能被当作完整回退目标。

| 阶段 | 可做操作 | 必需证据 | 责任方 |
|---|---|---|---|
| 扩展 | 增加新 schema、读取兼容、双向解析能力 | `D1/D2` 迁移脚本已验证；旧客户端仍可读旧数据 | 数据库负责人、客户端负责人 |
| 小范围迁移 | 仅允许获批的 v2 写入 `m-9`，产生 `seq9/E9` | 写入审批、调用方版本、事件幂等键、审计日志 | 发布负责人、业务负责人 |
| 对账确认 | 比对新旧投影、事件顺序和聚合结果 | `m-9 → seq9 → E9` 可追溯；差异清单为零或已签收 | 数据治理、审计人 |
| 收缩 | 删除废弃写路径或旧字段，但保留解释与导出能力 | 旧路径无生产写入；回放、备份恢复和降级演练通过 | 架构负责人、运维负责人 |

若 v1 不能读取 `m-9` 的语义，回退应限制为：停止新增 v2 写入、将流量切回兼容读取层、冻结相关业务，或将新事实投影为旧端可见的只读摘要。不得删除 `E9`、重置 `seq9`，也不得用回填把旧记录伪造成先前就存在的权威历史。

收缩前应明确边界：`D1/D2` 代码、`K1/K2` 配置、数据模式、事件格式与客户端版本分别核验；其中 `R9` 的审查结论独立记录。schema 已扩展只说明“可承载”，不说明 `S3` 已启用；只有批准写入、证据链完整且对账通过，才可宣布新路径生效。

> **要点** — 先扩展兼容，再以受控新写入和对账建立权威；回填只能辅助迁移，不能追认历史。

迁移期间最危险的误判，是把旧内存中的缺失或回填结果当成历史真相。v2数据库一旦承担新写入，就必须被明确设为唯一权威。

### 先划清旧合同、可回填数据与新权威

### 先划清旧合同、可回填数据与新权威

迁移不是把数据“补齐”就完成，而是先声明每个存储对什么事实负责。设：

- $S2$：旧内存实现，服务于旧合同；它可能只保留进程生命周期内的数据、有限窗口的数据，或根本不具备完整持久化能力。
- $S3$：候选 v2 数据库；一旦开始承接新写入，应被明确指定为新合同下的唯一权威。
- $R$：可靠来源，例如不可变业务事件、已确认的历史数据库、带校验的导出快照；只有 $R$ 中可验证的数据才可用于回填。

关键边界是：$S2$ 中“没有”某条记录，只能说明旧内存当前不可见，不能证明历史上未发生；$S2$ 中“有”某条记录，也未必覆盖完整历史。因此，不能将 $S2$ 与 $S3$ 做“全部历史应当相等”的比较，更不能依据旧读空结果否定已经成功写入 $S3$ 的事实。

回填的语义应是：

$$R \rightarrow S3$$

而不是：

$$S2 \rightarrow S3 \rightarrow \text{重新认定 } S2 \text{ 为历史权威}$$

例如，旧内存可被临时填入数据以维持旧接口可用，但该副本只是兼容性投影；即使它随后可读，也不改变 $S3$ 的权威地位。回填任务必须记录来源、覆盖范围、校验结果与失败状态；来源不可靠、范围不明或无法去重的数据，应宁可不回填，也不能伪造“完整历史”。

### 以message_id和E9建立写入边界

### 以 `message_id` 和 E9 建立写入边界

每条消息必须拥有跨重试、跨双写链路均不变化的稳定 `message_id`。它不是“本次请求编号”，而是该业务消息的身份：同一消息因超时、进程重启或消费者重复投递而再次处理时，仍必须携带同一个 `message_id`。v2 数据库应对此建立唯一约束，例如 `(message_id)` 唯一；重复写入只能得到既有记录或幂等更新，不能生成第二条权威历史。

E9 是“v2 已确认”的明确边界，可定义为以下原子结果之一：

- v2 主记录及其必要状态已在同一事务中提交；
- 或 v2 主记录提交后，可靠事件表中已落入 `E9(message_id, ...)`，由后续发布器投递；
- `E9` 一旦可被可靠地观察，即表示该消息的权威写入已完成。

因此，判定不应依赖旧内存 S2 是否存在副本，也不应依赖影子写是否成功。若 v2 已提交而旧副本写入失败，结果仍是“v2 成功、旧副本失败待补偿”；旧读返回空，只能说明旧副本不可用或未同步，不能否定 E9 之后的权威记录。

失败状态也必须归属于 `message_id` 与 E9 边界：事务未提交时，可标记为待重试；事务已提交但事件尚未发布时，应由可靠事件表重试发布；旧副本失败则单独记录补偿状态。重试只能围绕同一 `message_id` 执行，并以 v2 的已提交记录为准。这样，“是否已受理”由 v2 与 E9 决定，“是否完成兼容副本”只是附属迁移状态，二者不可混淆。

### 双写与影子写只能服从一个权威

### 双写与影子写只能服从一个权威

当 v2 数据库开始承接新写入时，应明确规定：**v2 是唯一权威，`message_id` 是稳定业务标识，E9 是提交语义的边界**。旧内存 S2 即使仍被写入、读取或用于兼容，也只是副本或观测对象，不能反向裁决 v2 的事实。

- **双写**：一次业务写入先以事务或可靠事件方式确认 v2；随后写 S2 的成功、失败、延迟均不改变 v2 结果。若 S2 写失败，应记录副本失败状态并按 `message_id` 幂等重试，而不是撤销或怀疑 v2。
- **影子写**：可将同一变更异步投递到旧路径，以验证兼容性、容量或行为差异；但影子写不得参与用户可见结果判定，更不得成为确认写入成功的前提。
- **影读**：旧读可用于比较字段、延迟和命中率，但“旧读为空”只说明 S2 未命中，可能是未写入、写入失败、淘汰或历史本就不存在；它不能否定 v2 中已确认的记录。
- **对账**：只能以 v2 已提交记录为基线，检查旧副本是否漏写、延迟或内容不一致。对账发现差异后，修复目标是副本，而不是删除、覆盖或回滚 v2。

不要假设 S2 与 S3 能比较“全部历史”：S2 可能只保留有限窗口，且旧数据缺少可靠来源与完整事件边界。回填仅可处理能够从可靠日志、事件流或已验证存储中重建的数据；不能把旧内存残留、读空结果或猜测性补写包装成权威历史。

### 用不对称写入案例识别错误回滚

### 用不对称写入案例识别错误回滚

设事件 `E9` 携带稳定的 `message_id=m42`。迁移期写路径先提交 v2 数据库事务，随后尝试写入旧内存副本：

1. v2 事务成功：`m42` 已持久化，状态为“已受理”；
2. 旧副本写入因进程重启、容量限制或网络错误失败；
3. 某读请求查询旧副本，得到“无记录”。

此时“旧读无结果”只能说明旧副本未同步成功，不能说明 `m42` 从未发生，更不能据此删除 v2 中的数据。v2 既然被指定为新权威，读路径应优先读取 v2；旧副本最多作为兼容性视图或降级来源，并须标明其可能陈旧、不完整。

错误回滚通常表现为：旧写失败后，补偿逻辑执行“删除 v2 记录”，试图恢复双边一致。这样会把已经完成的权威提交改写为丢失，且若 `E9` 已对外产生响应，重试又可能形成“同一 `message_id` 曾成功、后来消失”的矛盾历史。

正确补偿是**补旧，不回退新**：

- 记录旧副本失败状态、失败原因和待重试任务；
- 以 `message_id` 作为幂等键重试旧侧写入；
- 重试只补齐兼容副本，不重新生成业务事件；
- 若旧侧永久不可用，保留失败审计，并允许其视图缺失。

只有当 v2 事务本身未提交，或能证明该数据来自不可靠来源且尚未构成权威事件时，才讨论撤销。旧 S2 的缺失没有这种证明力；它无权以“未写到我这里”为由否定 S3 中已提交的权威历史。

### 按阶段门交付兼容与迁移证据

### 按阶段门交付兼容与迁移证据

迁移不是“接口还能访问”即可上线，而应以阶段门约束权威、兼容范围与回退证据。应用层必须始终声明：`v2 DB` 是新写入的唯一权威；`/v1`、旧内存 `S2` 或影子副本均不得据此反向裁决历史。

| 阶段 | 接口与客户端责任 | 数据责任 | 放行证据 |
|---|---|---|---|
| 扩展 | 保留 `/v1`，新增未来 `/v2`；旧客户端继续使用稳定语义 | 每次业务写入生成稳定 `message_id`；以事务或事件 `E9` 定义完成边界 | `/v1` 与 `/v2` 的响应映射、`message_id` 去重率、`E9` 成功/失败/待重试状态可审计 |
| 迁移 | 新客户端优先走 `/v2`；`/v1` 仅作兼容入口，不承诺旧存储完整历史 | 双写或影子写必须标明仅 `v2 DB` 权威；旧写失败不得抹除已提交的 `v2` 结果 | 按 `message_id` 对账，区分“v2 已写、旧副本未写”“事件未完成”“可靠来源可回填” |
| 收缩 | 停止新增旧客户端依赖，发布 `/v1` 下线窗口与替代路径 | 关闭旧写入和无权威回填；旧内存只作短期兼容读，不再参与真相判定 | `/v1` 调用量归零或获豁免，未完成 `E9` 清空，回退演练证明不会丢失权威写入 |

回退条件必须是“可逆路由”，而不是“把 `v2 DB` 覆盖回旧内存”。若 `v2` 已提交而旧副本缺失，旧读无结果只能说明兼容副本未同步，不能否定权威记录。只有存在可验证来源、稳定 `message_id` 和明确事件边界时，才允许回填；否则应保留失败状态并重试或人工处置。

> **要点** — v2确认写入后即为权威；旧内存只能兼容或辅助核验，不能以缺失、回填或旧读结果否定新事实。

迁移期间的影子比对用于发现差异，不用于把旧内存回填包装成可追溯、可授权的权威历史。

### 先划清样本身份与权威边界

### 先划清样本身份与权威边界

迁移比对的第一步不是“找出能补的数据”，而是为每条数据标明身份。否则，语义相近的旧内存快照很容易被误写成可审计的历史事实。

- **S2 旧内存**：通常是进程内缓存、聚合状态或已解析对象，可能缺少原始 `conversation_seq`、`message_id`、写入时间、删除痕迹及权限上下文。它只能作为待核验样本，不能天然证明“某消息曾以此形式被授权可见”。
- **可回填样本**：即使包含消息文本，也应保留其来源、提取时间、覆盖范围与不确定性；回填产生的是“迁移导入记录”，不是对原始历史的自动认证。
- **v2 数据库权威记录**：只有具备持久化来源、稳定标识、顺序语义、时间窗以及成员权限/可见范围证据的数据，才能承担查询、审计和授权判断。

因此，不能因为 S2 中有一条内容与 v2 记录文本相同，就断言两者历史等价。至少应核对同一会话的 `conversation_seq`、`message_id`、可见成员集合、权限状态和时间窗；任一关键维度未知，都应标记为“不可比较”或“待确认”，而非自动匹配。

尤其要警惕“回填即补齐”的错觉：旧内存中的 `seq=9` 并不能证明 `seq=8` 存在，连续游标仍只能停在 `7`。同样，数据距今 `25h` 而 broker 保留仅 `24h` 时，只有 v2 数据库确实保留该记录且当前请求者仍获授权，才可将其作为可读历史。

### 隔离影读：比对而不影响用户

### 隔离影读：比对而不影响用户

影读链路的目标是验证迁移结果，而不是为旧内存补写“历史”。它必须与用户请求路径隔离：生产请求只读取当前权威存储；影读任务以只读身份分别查询旧 S2 内存样本与 v2 数据库，再将结果送入独立对账器。影读不得修改游标、确认消费、触发重放、写入业务索引或向用户返回差异。

同一会话的可比条件至少包括：

- `conversation_id` 相同，且按该会话的 `seq` 对齐；不能用到达顺序替代逻辑顺序。
- `message_id` 一致，或存在经验证的一对一映射；仅文本相同不足以证明是同一消息。
- 比较时使用同一成员身份、角色、封禁状态及可见范围；无权读取的消息应标记为“不可比较”，而非“缺失”。
- 时间窗一致，且覆盖保留边界。例如 B 已见 `seq=9`、缺少 `seq=8`，连续游标只能停在 `7`；若样本距今 `25h`，超过 broker 的 `24h` 保留期，则只能在 v2 DB 确实保留该消息且影读身份获授权时进行核验。

对账响应应做遮蔽：仅向内部报告输出哈希、长度、序号、权限判定与差异类型，不回传正文、附件地址或成员名单。报告同时记录覆盖率、缺口、重复、未知项、抽样范围，以及“不比较”的原因。由此发现的数据问题可以进入修复队列，但不能据此把 S2 回填数据宣称为可追溯的权威历史。

### 建立可审计的对账口径

### 建立可审计的对账口径

对账的目标是量化“新旧来源在**可授权、可见、可追溯**条件下是否一致”，而不是把旧内存中的值回填后宣布历史完整。每条比对记录至少固定以下口径：

- `conversation`：仅在同一会话内比较；跨会话即使内容或 `message_id` 相同，也不构成同一历史事件。
- `seq`：按会话序号定位顺序与连续性。已确认连续游标为 `7` 时，观察到 `seq=9` 而缺少 `seq=8`，应记为缺口，不能将游标推进到 `9`。
- `message_id`：用于识别同一消息的重复、冲突或映射失败；同一 `seq` 对应多个 `message_id` 是冲突，不是“覆盖更多”。
- 成员权限与可见范围：只有在比较时点，主体对两侧记录均具备相同或可解释的读取权限，且可见范围一致，样本才可计入可比覆盖率。
- 时间窗：明确起止时间、时区、延迟容忍度和来源保留期。若事件距今 `25h`，而 broker 仅保留 `24h`，则 broker 缺失应标注为“不比较/不可验证”；只有 DB 实际保留该记录且当前授权成立，DB 才能提供可审计证据。

建议将结果分为：**覆盖**（两侧可比且一致）、**缺口**（应存在但一侧缺失）、**重复**（同一标识多次出现）、**未知**（数据存在但无法确认身份、顺序或权限）和**不比较**（语义、权限、时间窗或保留条件不满足）。覆盖率应以“可比较样本”为分母，而非全部旧样本。

对账报告还应保留抽样规则、样本标识、比较时间、授权快照、字段映射版本及每项不比较原因。特别是，语义不同的 S2 内存与 v2 DB 只能作为迁移观察来源，不能被写成等价的历史断言。

### 用断序与过窗案例检验迁移

### 用断序与过窗案例检验迁移

设会话 `C` 的已确认连续游标为 `7`。迁移影子读取中，客户端 B 已收到 `seq=9`，却没有任何可验证的 `seq=8`。此时不能因为 `9` 存在，就把游标推进到 `9`，更不能由旧 S2 内存“补写”一条看似合理的 `8`。正确结论是：B 的可证明连续历史仍止于 `7`，`8` 是缺口，`9` 只能作为非连续样本记录。

对账报告应至少标注：

- 已比较范围：`1..7`；
- 缺口：`seq=8`，说明来源、发现时间及是否可在权威库查询；
- 孤立可见项：`seq=9`，不得据此推断 `8` 的内容、发送者或权限；
- 不比较原因：旧内存缺少稳定 `message_id`、成员资格快照或可见范围证据时，不能与 v2 DB 作等价断言。

再看时间窗：B 在消息产生后 `25h` 才请求补历史，而 Broker 的保留期仅为 `24h`。Broker 未命中只能说明其缓存窗口已过，不能证明消息不存在，也不能授权数据库回放。若要从 v2 DB 补发，必须同时验证：

1. DB 中确有该 `conversation`、`seq=8` 与稳定 `message_id` 的原始记录；
2. 记录时间、排序规则与会话序列一致，未被迁移任务重写；
3. B 在该消息产生时及当前回放时均具备成员资格和目标可见范围；
4. 回放策略允许跨 Broker 保留窗读取，且审计日志记录“DB 授权补发”的依据。

任一证据缺失时，应向用户遮蔽具体内容，返回“历史存在缺口或不可验证”，而不是用 S2 回填制造连续历史。

### 以证据驱动阶段门与责任

### 以证据驱动阶段门与责任

影子对账不是“差异少就上线”的装饰性指标，而应成为扩展、迁移、收缩各阶段的准入证据。每个阶段门都必须绑定固定样本窗、授权主体、比较口径与责任人；不能以 S2 内存回填结果替代 v2 DB 的可追溯历史，更不能将“当前查询可见”误写为“当时已授权可见”。

| 阶段 | 必须满足的证据 | 阻断条件 | 责任与处置 |
|---|---|---|---|
| 扩展 | 只读/隔离样本中，同 `conversation seq`、`message_id`、成员权限、可见范围及时间窗一致；报告列明覆盖率、缺口、重复、未知和不比较原因 | 出现权限扩大、消息错配、时间窗外响应或未知项未分类 | 数据负责人确认口径，安全负责人签署权限结论 |
| 迁移 | 连续游标可推进，缺口有来源级解释；例如 B 已见 `seq=9` 但缺 `seq=8`，游标仍只能停在 7 | 以乱序到达推断连续完成；以旧内存补写缺失历史 | 迁移负责人建立例外单，明确补数来源、授权和失效时间 |
| 收缩 | 旧路径已停止承担权威读，回退演练证明新库可独立满足查询与审计 | 仅因影子命中率高就删除旧依赖 | 发布负责人批准收缩；审计负责人保留报告与签名 |

时间保留尤其不能模糊处理：若查询跨度为 25 小时，而 broker 仅保留 24 小时，则必须证明 v2 DB **真实保留**第 25 小时的数据，且请求者对该数据仍具备对应会话成员资格与可见权限；否则响应应遮蔽、降级为“不可确认”，而非从 S2 内存拼接答案。

例外应有期限、范围和退出条件。不可逆动作——删除旧存储、压缩审计字段、取消双读——必须在连续多个观察窗无高风险差异后执行；一旦收缩完成，只允许回退到保留的只读证据或重新迁移，不允许把临时缓存重新宣称为权威历史。

> **要点** — 影子对账只能验证差异与覆盖；只有具备保留、授权和审计证据的v2记录才能成为权威历史。

兼容不是让旧接口“看起来还能用”，而是明确旧端能证明什么、不能读取什么，以及新旧权威如何隔离。

### 先冻结旧版合同与可证明边界

### 先冻结旧版合同与可证明边界

迁移的第一步不是给 `/v1` 补上新语义，而是冻结它已经对客户端作出的可验证承诺。对旧版而言，`6 UTF8B` 请求的既有结果必须保持稳定：参数合法时可返回 `200 accepted_in_memory`；冲突仍返回 `409`；目标不存在仍返回 `404`。这些状态码描述的是旧接口在当次请求、当个进程内能够判断的事实，不能被事后回填为“已进入权威历史”。

尤其要区分两层：

- **内存受理**：服务实例已解析、校验并暂存该 `6B` 请求；`200 accepted_in_memory` 只证明这一点。
- **权威持久确认**：记录已按新版本的审批、排序、持久化与确认规则进入可查询的权威历史；这需要独立的确认语义，而非复用旧版 `200`。

因此，旧端收到 `200 accepted_in_memory` 后，不能据此推导出“永不丢失”“可跨重启恢复”“其他副本已可见”或“可按全局顺序读取”。同理，`409` 与 `404` 也应维持其旧合同中的判断边界：前者是旧接口可见的冲突，后者是旧接口可见的不存在，而不是对新权威存储全局状态的完整证明。

冻结合同意味着禁止悄然改写响应含义。即使后端开始把部分 `6B` 数据异步写入新系统，`/v1` 的成功响应仍只能表述旧的内存受理；只有具备新确认能力的客户端，才能读取“已持久、已排序、可追游标”的权威结论。

### 未来/v2审批后仍拒绝7B

### 未来/v2审批后仍拒绝7B

`/v2` 可以增加审批、`stored` 确认或更清晰的审计字段，但这改变的是“6B 已被确认写入”的证据强度，不是长度规则本身。若既有业务约束为 UTF-8 字节长度至多 `6B`，则审批通过后的判定仍应是：

- `≤6B`：可进入审批；审批完成后返回 `stored`，表示已按新权威流程确认。
- `7B`：在校验阶段直接拒绝，通常返回 `409` 或约定的业务拒绝结果；不得因调用了 `/v2`、携带审批人或等待更久而变成可存储。
- 不存在的对象仍是 `404`；不能把“长度不合规”伪装成“尚未审批”或“暂未落库”。

可将规则写成：

$$
\operatorname{accept}_{v2}(x)=
(\operatorname{utf8Bytes}(x)\le 6)\land\operatorname{approved}(x)
$$

其中审批是额外条件，而非对 `6B` 上限的覆盖。若 `/v2` 对同一 `7B` 输入悄然成功，旧业务会看到版本升级导致约束漂移：相同标识、相同语义，在不同入口得到不同可接受性。这既破坏迁移可预测性，也会使旧端回填的数据误被当作新权威历史。

确需支持更长内容时，应另开版本、另定义数据模型与读取可见性，例如 `/v3` 明确声明新上限；不能把扩容隐藏在 `/v2` 的审批流程中。

### 旧端不能被回填伪造成历史读者

### 旧端不能被回填伪造成历史读者

旧客户端若没有 `seq` 游标、增量拉取协议和新 `ACK` 语义，就不能证明自己读到了某条权威历史，更不能证明读到的是完整、连续且可重放的历史。它只能消费其原有合同允许的结果，例如 `accepted_in_memory`、既有的 `200/404/409` 响应及其定义的可见状态。

因此，迁移期间可以为 v1 保留“6 UTF8B 已受理”的旧语义，但不得把 v2 审批后写入的 `stored` 记录回填成仿佛由 v1 已确认消费的历史。回填最多是兼容性投影，而非历史证据：

- 旧端看到回填结果，不等于它拥有对应的顺序、版本或确认位置；
- 旧端重试、断线重连或跨设备登录时，不能据此推导“我已读到最新权威状态”；
- 服务端不得用旧端的一次 `200`、本地缓存命中或模糊时间戳，替代新协议中的持久化确认与 `ACK`。

正确做法是按显式能力隔离：仅支持旧合同的会话读取旧可见视图；支持 `seq` 与新 `ACK` 的会话读取权威历史。若必须在同一会话混用，必须先定义权威来源、可见范围及转换规则，例如明确“v1 仅见受理投影，v2 才见审批后存储记录”。不能按 Pod 随机灰度，否则同一 ID 可能在不同请求中被解释为“已受理”“已存储”或“不存在”，破坏兼容承诺。

### 以能力、会话与cohort隔离迁移

### 以能力、会话与 cohort 隔离迁移

迁移路由不能依据“请求恰好落到哪个 Pod”。若同一 ID 的两次请求因负载均衡落入不同版本，可能一次返回旧内存受理结果，另一次读取新权威历史；这会制造不可解释的 `200/404/409` 摆动，且无法靠重试修复。

升级应由显式能力声明决定。例如客户端在建连或请求中声明：

- `capability=v1`：只理解旧语义，无 `seq` 游标、增量读取或新 ACK；继续访问 v1 隔离视图。
- `capability=v2`：理解权威存储确认、游标与新 ACK；可进入 v2 审批和读取路径。
- 未声明或声明不完整：按 v1 保守处理，不因服务端已升级而自动暴露 v2 历史。

路由键至少应包含 `client_capability + session_id + cohort`，并保证同一会话粘滞到同一兼容域。`cohort` 是受控升级集合，例如租户、账号组或明确登记的客户端版本；它不是 Pod 标签，更不能随机采样。这样，同一 ID 在某个 cohort 内始终由同一权威规则解释。

当 v1 与 v2 必须进入同一会话时，先写清三件事：

1. **权威来源**：该 ID 以旧内存受理、v2 已存储确认，还是经转换后的统一记录为准。
2. **可见性边界**：v1 是否只能看到自身旧视图；v2 是否可见旧记录，以及旧记录是否标注为非权威历史。
3. **转换规则**：旧记录转入 v2 时如何分配序号、去重、补写确认；转换失败时返回何种稳定结果。

因此，v1 的 `6 UTF8B/409/404/200 accepted_in_memory` 可以保持不变，但不能被回填伪装成可读取的新权威历史。v2 即使经审批仍只有 `6B`，也只改变“已存储确认”的语义；`7B` 仍拒绝。R9 应另开版本和升级通道，而非让旧端在无游标、无新 ACK 的条件下被动“兼容”新历史。

### 混用与回退必须有阶段证据

### 混用与回退必须有阶段证据

新旧客户端进入同一会话前，不能只按接口版本决定路由；必须先写清四项阶段契约：

- **权威**：`v1` 的 `accepted_in_memory` 仅证明旧受理成功，不等同于可重放的权威历史；`v2` 经审批后的 `stored` 确认才进入权威账本。
- **可见性**：旧端无 `seq` 游标和新确认语义时，只能看到其协议可表达的投影视图，不能声称已读到完整新历史。
- **转换**：`v1 → v2` 需定义补齐、重放或显式放弃规则；`v2 → v1` 只能降级展示，不能把已确认记录伪装成旧端可确认的内存受理。
- **对账**：以权威记录的稳定标识、确认阶段和可见性水位对账，而非以 HTTP `200` 数量或 Pod 日志对账。

一旦 `v2` 数据获得 `stored` 确认，回退不得删除、覆盖或重新编号该记录。允许的回退是：将该会话固定到兼容投影、要求升级、或新建隔离会话；不允许把已确认新数据“降回”无历史保证的旧内存状态。

责任应明确分配：协议负责人定义状态机与转换；存储负责人保证确认后不可逆；网关按客户端能力、会话和 cohort 稳定路由；产品负责人决定旧端可见范围；运维只能执行已定义策略，不能按 Pod 随机灰度。否则同一 ID 在不同实例得到不同结果，便不再是兼容，而是权威分叉。

> **要点** — 旧合同可继续受理，但不能靠回填升级为权威历史；迁移必须以能力隔离、唯一权威和可审计回退为前提。

迁移不是把旧内存回填进数据库就完成历史交接，而是逐阶段明确谁有权、谁可读、谁可写，以及新事实出现后如何不丢失地前进。

### P0：冻结基线与划定旧合同

### P0：冻结基线与划定旧合同

P0 的目标不是立即迁库，而是把“旧系统究竟知道什么”固定为可审计基线。此时唯一权威仍是 **S2 内存态**；`/v1` 接口、R9 读取路径及旧客户端继续按既有合同运行，任何新数据库都只能作为旁路观测或回填目标，不能反向改写线上事实。

应先为每个业务实体记录基线水位，例如 `K1 -> m-8/seq8`，并冻结其来源、生成时间和适用范围。旧内存中的数据必须分成三类：

- **旧权威数据**：S2 已确认、可由 `/v1` 稳定读取的状态；它是 P0 的唯一判定依据。
- **可回填数据**：能够保留原始版本、顺序号、时间戳和来源标识的数据。回填到 DB 后仍只是副本，不能因“写入成功”自动升级为权威历史。
- **未知数据**：缺少版本、顺序、完整载荷，或只存在于日志、缓存、客户端本地状态中的片段。未知不能伪造为历史，更不能以默认值覆盖旧权威。

P0 的读写目标是：业务读仍读 S2，业务写仍按旧路径进入 S2；DB 可接受带证据的回填，但不得承接新写权威。业务门应验证旧客户端行为、`/v1` 响应字段、R9 语义及基线水位均未变化。回退也很简单：停止回填任务并丢弃未认证副本即可，因为此阶段尚未产生由 DB 独占的新事实。

尤其要明确旧合同的边界：D1/D2 的字段含义、K1/K2 的一致性范围、R9 的读取承诺，以及内存重启后哪些状态本来就不可恢复。只有先承认这些“未知”，后续阶段才不会把回填副本误当成完整历史。

### P1：扩展Schema并实行只读验证

### P1：扩展 Schema 并实行只读验证

P1 的目标不是切换权威，而是让数据库具备承载未来历史的能力，同时不改变当前业务事实的产生方式。此时唯一权威仍是旧运行时内存或既有写路径；数据库中的扩展字段只是可验证副本，不能反向驱动业务决策。

可先在记录中加入可空、可版本化字段，例如：

- `D1`：原有业务数据或旧格式摘要；
- `D2`：扩展后的完整数据、归一化结构或新维度；
- `K1`：旧幂等键、旧排序键；
- `K2`：新幂等键、事件序号、来源版本或冲突判定键；
- `schema_version`、`writer_version`、`observed_at`：用于解释“这条记录按什么规则写入”。

写入目标保持“双轨但不双权威”：

1. 旧路径继续处理请求、修改内存状态并服务旧端合同；
2. 同一事实可被旁路投影到数据库，写入 `D2/K2` 等新列；
3. 投影失败只告警、重试或进入待对账队列，不得使数据库残缺副本覆盖旧权威；
4. 新代码只读数据库做影读校验：比较 `D1↔D2`、`K1↔K2`、内存结果与落库结果是否一致，但不得据此拒绝正常旧请求。

业务门应限定为“可观测、可回滚”：字段已部署、索引和约束经过压测、影读差异可定位，且旧客户端读取到的响应完全不变。回退时可以停止扩展字段写入或关闭影读，但不能删除已落库的 `D2/K2` 事实；它们是后续对账证据，而非可随代码回滚抹除的缓存。

### P2：隔离v2小流量并指定新权威

### P2：隔离v2小流量并指定新权威

P2不是“给少量租户同时试用新旧系统”，而是为被选中的小流量租户建立明确的权威切换：对这些租户，`v2 DB` 是唯一可追加、可确认的事实来源；`v1 内存`最多保留为兼容读取来源或观测对照，不再拥有写入裁决权。

- **适用范围**：以稳定租户集合、分片键或业务域隔离，例如租户 `T1、T2`。路由必须在请求入口按租户固定，不能按单次请求随机分流。
- **唯一写入权威**：命中 P2 范围的写请求只写 `v2 DB`，并以单调版本如 `(epoch, seq)`、`m-9/seq9` 或等价提交位点确认。禁止“先写 v1、异步回填 v2”或双端独立成功即返回。
- **读取目标**：优先从 `v2 DB` 读取已确认版本；如确需兼容旧消费者，可由适配层读取 v2 后投影为 v1 形状。不得把 v1 内存中的较旧快照覆盖 v2 的已确认记录。
- **版本标记**：每条响应、事件或聚合结果应携带 `schema_version=v2` 与权威位点。消费者据此拒绝旧版本倒灌，并能定位“读到什么、写到哪里”。
- **业务准入门**：仅允许幂等写入、版本校验、审计链路、监控告警和人工处置均已验证的业务进入；高风险结算、不可逆扣减等操作应后置。
- **回退原则**：P2 故障时先暂停该范围的新写，保留 v2 已确认数据；代码可回退到兼容读，但数据状态只能以前进修复方式处理。若 v2 已确认 `m-9/seq9`，就不能因回退重新把 v1 内存当作该租户的完整历史。

### P3：按口径对账并维持双版本兼容

### P3：按口径对账并维持双版本兼容

P3 的目标不是“两个版本看起来都能用”，而是证明 P2 中已隔离的小流量权威历史与旧接口语义可对应。对账应以可验证的事实为单位，而非仅比较最终余额或聚合字段：

- **消息口径**：同一业务消息是否都被接收、拒绝或延迟；拒绝原因是否一致。
- **序列号口径**：按实体比较连续序列，例如 `m-9/seq9` 后不得在任一读路径中退回到 `seq8`。
- **幂等键口径**：同一 `idempotency_key` 重放时，v1 与 v2 必须返回同一既有结果，不能产生第二笔事实。
- **事件语义口径**：比较事件类型、主体、发生时间、因果关联与终态，而不是把字段排列差异误判为不一致。

此阶段通常保持：v2 数据库是试点实体的唯一写入权威；v1 内存仅供兼容读取或历史映射；影子链路只读，不得以“回填”覆盖 v2 已确认记录。若数据库已确认 `m-9/seq9`，即使应用代码回滚，也必须保留兼容读取、暂停新写，并通过前进修复恢复服务；不能切回 v1 内存后宣称新历史不存在。

兼容层需显式区分 `/v1`、`/v2`、`R9` 与旧客户端。`/v1` 可将 v2 事件投影为旧响应，但应标明无法表达的新字段；`/v2` 返回完整版本化语义；`R9` 等旧读取协议必须固定其排序、分页和空值含义。对账失败时，业务门应关闭扩大流量，仅隔离问题实体；回退的是流量路由或新写入口，不是已提交的数据库事实。D1/D2 的数据迁移、K1/K2 的兼容契约、数据库提交与事件投递也应分别记录状态，避免把某一层成功误作全链路完成。

### P4至P5：扩大流量、前进修复与删旧取证

### P4至P5：扩大流量、前进修复与删旧取证

P4 的扩大不是“把开关调到 100%”，而是在 v2 已确认 `m-9/seq9` 后，承认 v2 已持有不可逆的新历史：即使应用代码回滚，也不得再把 v1 内存视为完整权威。

| 阶段 | 唯一权威与版本 | 读写目标 | 业务门与回退 |
|---|---|---|---|
| P4 扩大 | v2 DB，schema v2 | 新写入 v2；读取优先 v2，兼容读取 v1/D1/D2 | 分批放量、按租户观测；异常时暂停新写，不切回“仅 v1” |
| P4 前进修复 | v2 DB，含 `seq9` 及以后事实 | 修复程序按幂等键补齐缺口，重放事件或对账修正 | 保留 v2；回滚代码只改变执行路径，不删除 v2 历史 |
| P5 删旧 | v2 DB，经证据确认 | 删除旧内存依赖、旧双写和兼容分支 | 未完成证据链，不得删旧；删除后仍保留恢复审计材料 |

发生故障时，安全回退路径是：

1. **暂停新写**：冻结产生新序号或新版本的入口，防止差异继续扩大。
2. **兼容读取**：优先读取 v2；若旧调用方只能理解 v1 结构，则由适配层投影，而不是把 v2 覆盖回旧内存。
3. **前进修复**：以 `m-9/seq9` 为下界，对比 D1/D2、K1/K2、DB 行与事件日志；缺失数据补写 v2，重复数据按幂等键拒绝。
4. **恢复放量**：只有修复完成、对账连续通过后，才重新开启新写和扩大流量。

删旧应有明确责任矩阵：数据负责人证明 DB 与事件序列完整；应用负责人证明兼容读取覆盖旧客户端；运维负责人证明备份、恢复演练和监控可用；业务负责人确认关键账务、状态与权限对账通过。所谓“可删旧”的证据至少包括：全量校验和、序号无断档报告、双读差异归零、回滚演练记录、旧消费者清单归零，以及保留期内可恢复的归档。

> **要点** — 每一阶段都必须写清唯一权威、读写目标、业务门和回退；新库确认的新历史只能兼容保留并前进修复。

迁移不是把旧内存回填进新库就完成了；必须以版本化合同、唯一权威和候选组证据，证明新旧路径可兼容、可对账且可受控回退。

### 版本化合同与权威边界

### 版本化合同与权威边界

旧端“能读到数据”不等于旧数据可直接成为新版历史。迁移首先要冻结旧合同：旧接口返回哪些字段、`404/409/200` 分别意味着什么、旧客户端是否依赖缺省值、排序、幂等键或权限过滤。只有可被证明满足新版语义的数据，才属于可回填集合。

新版应显式定义 `v2 stored` 合同，例如：

- 每条记录具有全局唯一标识、单调或可比较的 `seq`、版本号与写入来源；
- 写入采用唯一约束或幂等键，重复投递不得制造第二份历史；
- `E9` 等业务事件必须保留足以重放、审计和判定先后的证据；
- `404` 表示确实不存在，`409` 表示状态或版本冲突，不能用“统一返回 200”掩盖不兼容。

回填是一次受控导入，而非取得权威的手段。回填记录应标注来源、导入批次和原始时间；无法补齐唯一键、顺序、权限归属或保留期限的数据，只能隔离、降级展示或拒绝迁移。若 `B25h` 仍有权从旧源补拉，也必须规定补拉窗口、去重规则及截止条件。

任何时刻只能有一个写权威：切换前旧库权威；双写期间通常仍以旧库为裁决源，新库仅作为候选副本；完成对账、封口旧写入并验证后，才将权威切至新库。影读和双写可用于发现差异，却不能让两个库同时裁决同一对象；一旦发生冲突，应按已声明的权威与 `seq` 规则处理，而非按“最后回填者”覆盖。

### 扩展、迁移、收缩的阶段门

### 扩展、迁移、收缩的阶段门

采用 Fowler 的“扩展—迁移—收缩”时，任何阶段都不能仅凭“总体 `200` 率正常”放行；应按 Google SRE 的金丝雀原则，对候选用户组、候选会话和候选端版本分别比较新旧路径。

- **扩展（expand）**：先发布兼容的 `v2 stored` 合同，例如新增版本、`seq`、唯一键、状态字段和保留期标记；旧端仍可读旧字段，新端必须能识别缺失的 `v2` 字段。此时允许双写、影读和异步对账，但不得把旧内存回填结果宣称为权威历史。准入证据包括：唯一约束与 `seq` 单调性生效、`E9` 等冲突可观测、`6B/409/404/200` 被分别统计，且权限与保留策略已覆盖新字段。

- **迁移（migrate）**：历史搬迁必须按可重放批次执行，记录来源、版本、校验和与失败原因；`B25h` 等具有授权补拉能力的主体可补拉，普通旧端不能借此越权读取历史。双写数据应与影读结果持续对账，差异需能定位到实体、序列和写入路径。OpenIM 的两份源码只能作为异步边界证据，不能替代数据库中唯一权威的判定。数据库故障、重复投递、部分回填和回退均须经过演练。

- **收缩（contract）**：只有当旧端占比、旧字段读取量和旧写入量均低于明确阈值，且候选组中新路径的成功率、延迟、对账差异和事故率均不劣于旧路径，才可关闭旧接口、旧字段和旧库回填任务。下线后仍应保留审计、回滚窗口及必要的只读兼容期。

阶段门不是单一技术审批：产品确认语义与用户影响，客户端确认旧端升级边界，数据团队确认唯一性、迁移与容量，安全确认权限和保留，值班团队确认告警、故障门槛与回退手册；任一阻断项未签收，即不得进入下一阶段。

### 双写影读与候选组对账

### 双写影读与候选组对账

总体 `200` 率只能说明请求“被接受”，不能证明迁移后的历史、幂等与可见性正确。金丝雀应按候选组对照：同一租户、会话、客户端版本、权限等级和流量类型进入同一组，比较旧路径与新路径的结果，而不是把所有成功请求混为一个指标。

双写期间，旧端仍写旧存储，新端按 `v2 stored` 合同写入新存储；每条记录必须带稳定唯一键 `unique_id` 与单调序列号 `seq`。`unique_id` 用于识别同一逻辑消息，`seq` 用于确认顺序、缺口和重复；不得用写入时间或自增主键跨库对齐。双写失败不能静默降级：旧写成功、新写失败应形成可追踪的补偿任务，而非把旧库回填误称为权威历史。

影读不改变用户结果：在线请求仍以当前权威源返回，同时异步读取另一侧并按候选组对账。至少记录以下口径：

- `200`：两侧均找到同一 `unique_id`，字段、版本、可见范围及 `seq` 一致。
- `404`：权威侧不存在；另一侧若存在，属于幽灵数据或保留策略不一致。
- `409`：同一唯一键对应不同载荷、版本或序列，表示幂等合同冲突。
- `6B`：读取到旧格式、不可解释版本或缺少必要映射，不能计入成功。
- `E9`：序列倒退、重复、断裂或越过已确认水位，属于顺序完整性故障。

对账应输出“候选组 × 状态码 × 差异类型”的比例和样本，而非只报全局成功率。只有 `409/6B/E9` 为零或在预先批准的阈值内，`404` 有明确保留解释，且双写补偿队列可清空，候选组才可扩大；否则停止放量并保留旧路径作为回退入口。

### 旧端兼容与受限回退

### 旧端兼容与受限回退

`/v1` 是旧客户端可继续调用的兼容面，不应被误当作新事实的权威写入入口；未来的 `/v2` 则以版本化合同明确字段、幂等键、错误语义与存储结果。两者可并存，但必须共享同一条权威事实链：同一业务对象只能有一个权威版本、唯一标识与递增 `seq`，不能让旧端重试在 `/v1` 生成第二份历史。

兼容策略应区分读、写与补拉：

- 旧客户端继续访问 `/v1` 时，适配层将旧请求映射为受控的 `v2` 命令；返回体可降级为旧字段，但不得隐去 `409` 冲突、`404` 不存在、`6B` 受限或 `E9` 数据不一致等关键语义。
- `R9` 作为旧协议与新合同之间的兼容规则，必须版本化、可审计；未知字段宁可拒绝或显式忽略，也不能猜测性转换。
- `B25h` 内的客户端可按授权补拉缺失数据，但补拉只能恢复已确认的权威记录，必须按唯一键和 `seq` 去重、续传；超过窗口、权限不足或保留期已过时，应返回明确结果，而非伪造“空成功”。
- 新端写入先获得 `v2 stored` 确认，双写与影读仅用于对账，不构成第二权威。

回退尤其不能等同于“切回旧库”。一旦新数据已被确认、下发或被 `B25h` 补拉，旧库若缺少该事实，直接回退会造成静默丢失。允许的回退是受限回退：冻结新写入，保留新库为事实源；旧端经适配层继续读取，或从新权威库生成兼容投影。只有证明旧路径已追平全部已确认 `seq`、对账无差异、权限与保留规则一致，才可恢复旧写路径。数据库故障、容量门限和事故演练应验证这一限制，而不是只验证总体 `200` 率。

### 演练证据与阻断矩阵

### 演练证据与阻断矩阵

迁移上线前，不能只证明“新库可写、接口返回 `200`”，还要用故障演练证明：旧路径、新路径、回退路径都不会制造第二权威。OpenIM 的两份源码只能作为异步边界参考：消息写入、索引、通知与对账可异步衔接；不得据此推导跨库同步提交、旧内存回填即成为权威历史。

| 演练项 | 必须保留的证据 | 未满足时的阻断方 |
|---|---|---|
| 数据库故障 | 主库不可写、超时、主从切换时的 `6B`、`409`、重试和幂等记录；不得把失败伪装为 `200` | 数据、值班 |
| 回退演练 | 灰度候选组回退后，旧端仍可读写；`v2 stored` 合同、唯一键、`seq` 与 `E9` 对账一致 | 产品、客户端、数据 |
| 权限与保留 | 迁移前后访问控制、租户隔离、删除/保留期限及审计链一致；无权者不得借回填读取历史 | 安全、产品 |
| 容量与事故门 | 压测覆盖双写、影读、补拉和积压；设定延迟、错误率、队列深度、存储水位的事故阈值 | 值班、数据 |

阻断责任应按问题归属，而非由单一团队“签字放行”：

- **产品**：未定义旧端行为、历史可见范围、回退期间功能降级或用户告知，阻断发布。
- **客户端**：旧版本对 `404`、`409`、`6B` 的处理不兼容，或无法识别版本化合同，阻断灰度扩大。
- **数据**：唯一约束、`seq` 单调性、`E9` 对账、双写与影读差异未收敛，阻断切权威。
- **安全**：权限继承、数据保留、审计与补拉授权不闭合，阻断数据迁移。
- **值班**：无数据库故障预案、无明确回退开关、容量事故门不可观测，阻断上线。

最终判断以候选组的新旧对照为准：候选组即使总体 `200` 率正常，只要出现不可解释的 `404`、冲突 `409`、`6B` 失败、对账漂移或未经授权的补拉，就应停止推进并回退。

> **要点** — 迁移的完成标准是候选组证据证明新版合同成为唯一权威，并在旧端兼容与不可丢失回退约束下通过全部阶段门。

迁移不是把旧内存回填进新库就获得历史权威；必须先划定合同、时间轴、唯一真相源与不可逆边界。

### 先分三类事实：旧合同、回填数据与新权威

### 先分三类事实：旧合同、回填数据与新权威

迁移中最危险的误解是：旧系统能读到的数据，一经回填到新库，就自动成为新系统的权威历史。实际上必须把事实分为三类，并为每类规定不同的读、写、修复权限。

- **S2：旧合同事实**  
  这是旧接口、旧字段语义和旧端行为所承诺的内容，例如旧端只认识状态 `7B`。S2 可以被兼容层读取和解释，但不能因为新系统补充了字段、重算了状态，就反向改写旧合同的含义。旧合同是“当时如何对外承诺”，不是新系统的最终裁决依据。

- **S3：可修复的回填历史**  
  回填数据用于恢复查询能力、补齐索引或建立关联，允许发现缺口后重跑、去重、订正。例如批次 B 有 `seq=7` 与 `seq=9`，却缺少 `seq=8`；这只能说明回填链路存在待核验缺口，不能凭相邻序号推断 `8` 必然发生。S3 可修复，但每次修复必须保留来源、时间、规则版本和差异记录。

- **R9：新权威确认事实**  
  R9 是新系统按新合同完成校验、落库并确认后的唯一依据。它决定当前读模型、对外结果和后续写入的幂等边界。即使旧数据更早出现，只要未满足 R9 的确认规则，就不能越级成为权威。

可将关系写为：

$$
\text{可读取}(S2) \neq \text{可确认}(R9),\qquad
\text{已回填}(S3) \neq \text{已权威化}(R9)
$$

因此，双写期间应坚持“**双写，单权威**”：旧端可继续接受 `7B`，新端同时写入兼容记录与 R9 所需事实；读路径可影读比较 S2/S3 与 R9 的覆盖率，却不得用旧读结果覆盖已确认的 R9。尤其当 v2 已存后发生回滚，回滚只能改变路由或写入策略，不能丢弃既有 R9 记录；否则回滚会把“已确认历史”错误降级为“可猜测历史”。

### 扩展、迁移、收缩的阶段门

### 扩展、迁移、收缩的阶段门

迁移应被拆成“扩展—验证—切换—收缩”的可审计阶段，而非一次性回填。每一门都要明确证据、责任人和阻断条件；未过门时，旧路径可以继续服务，但不得借回填数据取得历史权威。

- **P0：合同冻结。** 由数据负责人确认 `expand` 合同：新字段语义、默认值、幂等键、版本兼容范围，以及 S2、S3、R9 在 D/K 轴上的归属。架构负责人签字后方可扩展；若“旧值缺失”和“新值为空”不可区分，禁止进入迁移。

- **P1：扩展上线。** 由应用负责人新增可选字段、读取兼容和双写能力，但旧端仍可只写旧格式。证据是契约测试、双写失败告警和回滚说明；放行条件是新字段未被当作唯一真相源。

- **P2：存量迁移与影读。** 由数据迁移负责人回填可证明的存量，并记录来源、时间、批次和置信度。影读负责人比较新旧读取结果，覆盖率必须包含边界样本：例如 B 的序列有 `7`、`9` 而缺 `8`，不得凭相邻记录虚构 `8`。发现冲突时，以原权威记录为准，回填结果仅是派生数据。

- **P3：切换单权威。** 由业务负责人宣布新路径成为唯一写入权威；双写可以保留，但只能有一个裁决源。放行证据包括影读覆盖率达标、差异已分类、24h 观察窗内无未决错误；若要求连续 25h 稳定，则不能以 24h 记录提前放行。

- **P4：旧路径降级。** 由运维与审计负责人关闭旧路径的权威写入，仅保留受控读取或只读审计。特别地，旧端仍产生的 `7B` 请求必须被拒绝、转换或隔离，不能悄然写回旧事实模型。

- **P5：收缩与不可逆确认。** 由变更负责人删除旧字段、旧索引和旧回滚通道前，确认所有 `v2` 已存数据在回滚时不会丢失或降级。收缩门的核心不是“能否删表”，而是证明：新合同已覆盖全部合法状态，且任何回退都不会把已确立的 `v2` 事实重新解释为旧内存。

### 双写与影读：只能有一个权威

### 双写与影读：只能有一个权威

双写的目标是迁移，不是制造两个都可裁决的历史库。对每条事件都应明确两条轴：

- **D 轴（数据写入轴）**：旧端与新端是否都已持久化。例如事件 `e` 已写入旧系统、也写入 v2，记为 `D=双写成功`。
- **K 轴（确认/权威轴）**：业务读、确认、重试去重和审计究竟以谁为准。迁移期间必须固定为单一权威，例如 `K=v1`；切换门槛通过后才整体变为 `K=v2`。

因此，`D=双写成功` 不等于 `K=双权威`。旧端 7B 即使仍接收请求，也只能是兼容写入目标；若 v2 已经保存成功，随后旧端写入失败、回滚或超时，绝不能因为“旧端未确认”而删除 v2 中已存的事实。反之，旧内存中的记录也不能在迁移后补写进 v2 并宣称获得原始历史顺序、原始确认语义或原始去重资格。

影读用于验证，而不参与裁决。正常请求仍读取 K 轴权威端；旁路同时读取另一端，按同一合同比较：

- 主键、租户、状态、金额等字段一致；
- 顺序与边界一致，例如 B 的 `seq=7`、`seq=9` 之间缺少 `seq=8`，必须报告“缺口”，不能由旧内存猜测补齐；
- 时间窗口一致：观察到 `25h` 的数据不能自动满足 `24h` 保留合同，需确认起止点、时钟和过期规则；
- 幂等键、版本号、删除标记及可见性一致。

影读覆盖率应按**可比较请求**计量，而非只统计成功影读：`覆盖率=已完成对账数/应对账数`。同时记录差异率、未完成率、按序列缺口率和高风险字段差异。P0-P5 门应逐级收紧：先允许观测与告警，再要求覆盖率、差异收敛、回放验证和回滚演练达标；在最终切换前，任何未解释差异都意味着 K 轴不得转移。

### 缺口案例：B的序列7、9与缺失8

### 缺口案例：B的序列7、9与缺失8

B 在旧端内存中只保留了序列 `7` 与 `9`：`7` 的时间为 `T0`，`9` 的时间为 `T0+25h`；而迁移合同规定可接受窗口仅为 `24h`。此时缺失的 `8` 不是“可由相邻记录补齐的小洞”，而是顺序、因果与去重边界都未被证明的断点。

- **旧内存不是历史库**：它可能因重启、淘汰、乱序接收或局部缓存而只剩 `7、9`。即使旧端声称“见过8”，若无满足合同的持久证据，不能把这句话回填为权威事件。
- **补写不等于发现历史**：迁移器可生成“推测的8”以维持连续展示，但该记录的 `D`（数据事实）与 `K`（已知性/证明状态）不同于真实写入。它只能标为派生结果，不能取得 `S2/S3` 的权威地位，更不能以 `R9` 覆盖已有版本。
- **时间不能倒灌**：`9` 已超过 `24h` 窗口到达。即便随后从旧内存找出疑似 `8`，也不可据此重排已提交的权威历史；否则会改变下游已依据 `9` 作出的决定。

因此应执行双写、单权威：新版本 `v2` 已存入的 `7、9` 保持可审计，回滚旧端也不得丢弃；旧端仅作为影读来源，统计“7、9均见而8缺失”的覆盖率与缺口率。P0 确认合同，P1 固化序列规则，P2 标注缺口，P3 影读比对，P4 才允许有限放量，P5 才能切换读取权威。缺失 `8` 可被补证，却不能被推断成已经发生的权威历史。

### 兼容与回退：旧端7B、/v1与/v2的边界

### 兼容与回退：旧端7B、/v1与/v2的边界

`/v1` 是旧端 `7B` 的兼容入口，不是新模型的历史写入通道；`/v2` 才承载新合同、幂等键、序列约束与新库权威写入。旧端无法理解新字段时，可由适配层降级响应，但不得把旧请求回填为“早已发生”的权威事实。

时间窗口应明确分层：`/v1` 保留 **25 小时**受理窗口，覆盖客户端时钟偏差、重试抖动和跨日延迟；业务事件的可接受迟到窗口为 **24 小时**。多出的 1 小时只用于接住旧端请求、记录拒绝或转换结果，不能扩大业务历史的可修改范围。超过 24 小时的事件即使被 `/v1` 接收，也只能进入隔离、人工核验或只读审计路径。

双写期间可同时生成旧格式副本，但必须“单权威”：一旦 `/v2` 已确认写入新数据源，该记录的状态、顺序和去重结果只以新数据源为准。此后若发布失败，允许回退**读流量、接口路由或新功能开关**，不得回退到会遗失 `/v2` 已存数据的旧存储。否则，所谓回滚实际是在删除已对外确认的事实。

可按门禁推进：`P0` 冻结合同；`P1` 建立 `/v1` 适配；`P2` 双写并核对；`P3` 影读比较覆盖率；`P4` 切换 `/v2` 权威读写；`P5` 仅在旧端退出后关闭 `/v1`。例如序列 `7、9` 缺少 `8` 时，不能因旧端重试就补造 `8`；应保留缺口、拒绝越序写入或进入核验队列。

> **要点** — 迁移的核心是阶段化证据下的单一权威；旧数据可兼容、可对账，却不能凭回填改写已确认历史。
