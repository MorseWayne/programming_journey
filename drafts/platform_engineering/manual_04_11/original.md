先把一次“发往远端服务”的发送拆开：客户端并不直接找到远端服务器，而是先把帧交给本地下一跳，再由网络层逐跳转发。

### 先判定目标是否在本地链路

### 先判定目标是否在本地链路

A 要访问 `203.0.113.10:443` 时，第一步不是 ARP 查询“谁拥有 `203.0.113.10`”，而是查自己的地址配置与路由表。

假设 A 的 Wi‑Fi 地址为 `10.0.0.2/24`，则本地直连前缀是：

$10.0.0.0/24$

目标 `203.0.113.10` 不落在该前缀内，因此它不在当前 Wi‑Fi 链路。A 会匹配默认路由，例如：

`0.0.0.0/0 → 下一跳 10.0.0.1`

这意味着 A 应把第一个本地链路帧交给网关 `10.0.0.1`。在 IPv4 中，A 通过 ARP 获取的是**网关**的 MAC 地址，而不是远端服务的 MAC 地址；随后封装大致为：

- 链路层目标：网关的 MAC 地址；
- IP 层目标：仍是 `203.0.113.10`；
- 传输层目标：仍是端口 `443`。

若目标本身是 `10.0.0.0/24` 内的主机，A 才会把它视为直连邻居，并 ARP 查询该主机的链路地址。IPv6 中同样先依据前缀和路由决定下一跳，只是用邻居发现替代 ARP。

因此，“目标 IP 在哪里”和“这一帧交给谁”是两个不同的问题：前者由网络层地址与路由决定，后者由当前链路上的下一跳发现决定。

### 远端连接为何先寻找网关

### 远端连接为何先寻找网关

A 准备连接 `203.0.113.10:443` 时，先用自己的前缀和路由表判断目的地是否在本地链路。若 A 的地址是 `10.0.0.2/24`，本地直连网段为 `10.0.0.0/24`；而 `203.0.113.10` 不属于该前缀，因此不能在 Wi‑Fi 上直接投递给服务端。

路由查找会命中默认路由，例如：

`0.0.0.0/0 → 下一跳 10.0.0.1 → Wi‑Fi 接口`

这里要区分两层对象：

- **网络层目的地址仍是** `203.0.113.10`：这是最终服务的 IPv4 地址，供路由器逐跳查表。
- **链路层目的地址是网关** `10.0.0.1` 的 Wi‑Fi/MAC 地址：这是当前这一段本地链路上应接收帧的下一跳。

因此，A 发起 ARP 查询时，问的不是“谁拥有 `203.0.113.10`”，而是“谁拥有 `10.0.0.1`”。获得网关 MAC 地址后，A 可构造类似：

`Wi‑Fi 帧[目的 MAC=网关] → IPv4 包[目的 IP=203.0.113.10] → TCP 段[目的端口=443]`

网关收到帧后，剥去本地 Wi‑Fi 封装，依据 IP 目的地址继续转发；若经过 NAT，还可能改写源地址和源端口。下一台路由器会重新封装新的链路层帧，所以远端服务器的网卡地址既不需要、通常也无法被 A 直接发现。

IPv6 的逻辑相同，只是通常不用 ARP：主机会通过**邻居发现**解析本地下一跳的链路层地址。无论 IPv4 还是 IPv6，邻居解析解决的都是“这一跳交给谁”，不是“最终服务器的网卡在哪里”。

### 帧逐跳更换，目标地址保持转发语义

### 帧逐跳更换，目标地址保持转发语义

A 要访问 `203.0.113.10:443` 时，先查本机路由表。目标 `203.0.113.10` 不属于本地前缀 `10.0.0.0/24`，因此下一跳是默认网关 `10.0.0.1`，而不是远端服务本身。

在 IPv4 Wi‑Fi 链路上，A 通过 ARP 查询 `10.0.0.1` 的链路层地址，然后发送一帧：

- **链路层帧**：目的地址是“网关的 Wi‑Fi/MAC 地址”
- **IPv4 包**：目的地址仍是“服务 `203.0.113.10`”
- **传输层段**：目的端口仍是 `443`

可把第一跳抽象为：

`帧[A 的 MAC → 网关 MAC]`  
`包[10.0.0.2 → 203.0.113.10]`  
`TCP/UDP[临时端口 → 443]`

路由器收到帧后，先剥去旧链路层封装，检查其中 IP 包的目标地址，依据路由表选择下一跳和出口接口；随后在新的链路上重新封装。例如，下一段可能是以太网、运营商接入链路或隧道，新的帧目的地址将变成**下一跳**的链路层地址。

因此，链路层地址通常只在一段本地链路内有效，经过路由器就会变化；IP 目标地址则表达“最终要送往哪里”，使每台路由器能够继续按目标前缀转发。实际转发中，路由器还会递减 IPv4 的 TTL（或 IPv6 的跳数限制）；若经过 NAT，源 IP 和端口也可能被改写，但这不改变“帧按下一跳交付、包按网络目标转发”的基本分工。

### 纸上追踪一次 Wi‑Fi 到公网的发送

### 纸上追踪一次 Wi‑Fi 到公网的发送

设客户端 A 为 `10.0.0.2`，默认网关为 `10.0.0.1`，目标服务为 `203.0.113.10:443`。A 先根据前缀和路由表判断：`203.0.113.10` 不属于本地 Wi‑Fi 子网，因此不能在 Wi‑Fi 上直接寻找该服务的网卡地址。

1. **A → Wi‑Fi 网关**
   - 网络层数据包：源 IP `10.0.0.2`，目标 IP `203.0.113.10`；若是 HTTPS，还会有源端口（如 `50000`）和目标端口 `443`。
   - A 对 `10.0.0.1` 做 ARP 查询，得到**网关在本地 Wi‑Fi 链路上的地址**；IPv6 中对应工作由邻居发现完成。
   - A 发出的 Wi‑Fi 帧中，链路层目标是“网关”，但 IP 包目标仍是“远端服务”。

2. **网关 → NAT/公网下一跳**
   - 路由器剥掉收到的 Wi‑Fi 封装，检查 IP 目标 `203.0.113.10`，按路由表选择公网出口及下一跳。
   - 若实施 NAT，通常把内部流标识改写为类似 `198.51.100.x:外部端口`，并保存映射；服务端看到的源地址不再是 `10.0.0.2`。
   - 对新的出接口，路由器重新封装链路层帧：该帧的目标地址是**公网侧下一跳**，不是最终服务。

3. **公网路径 → 服务**
   - 中间每台路由器都重复“解封装、查目标 IP、选择下一跳、重新封装”。
   - 最后一跳才把帧交给承载 `203.0.113.10` 的本地链路；服务接收目标端口为 `443` 的数据。

应区分三类地址：链路层地址只负责当前一跳；IP 地址指明端到端的网络层目标；端口标识主机内的应用服务。路由可达只表示包可能抵达，仍不保证 NAT 状态、防火墙规则、MTU 或服务监听允许连接。

### 把“路由可达”与“业务成功”分开

### 把“路由可达”与“业务成功”分开

“有路由”或“能选出下一跳”只回答一个较窄的问题：A 知道应把发往 `203.0.113.10` 的包交给默认网关 `10.0.0.1`。这说明本地网络层具备**尝试转发**的方向，不等于浏览器一定能完成 HTTPS 连接。

可将结果分层判断：

- **本地下一跳可达**：A 能通过 ARP 找到网关的链路地址，并在 Wi‑Fi 上把帧交给它；IPv6 中对应由邻居发现完成。
- **路径可能存在**：路由器可继续依据目标 IP 转发，且各段链路都能承载相应封装。
- **会话能够建立**：NAT 必须创建并维持正确映射；沿途防火墙、访问控制列表和安全组必须允许 TCP 握手及返回流量。
- **业务真正成功**：服务端必须在 `203.0.113.10:443` 监听，TLS 协商、证书校验、应用认证与请求处理也都必须正常。

因此，“默认路由存在”不能排除许多故障。例如 NAT 外侧地址或端口映射耗尽、回程包被防火墙丢弃、路径 MTU 较小而 PMTU 发现受阻、服务未监听 `443`，或空闲过久后 NAT/负载均衡器清除了长连接状态。

排障时应避免把“能发出包”误读为“服务可用”。先确认本地下一跳，再检查 NAT 与双向流量、MTU/分片行为，最后验证 TCP、TLS 和应用层响应；每一层成功，才为上一层的“可达”赋予更完整的业务含义。

> **要点** — 访问远端 IP 时，主机先按路由把本地帧交给下一跳；链路地址逐跳变化，IP 转发语义持续指向远端目标。

NAT 改写的是网络可达路径，不是业务身份、更不是服务器间的数据同步；先看一条出站连接如何被映射与返回。

### 从内侧五元组到外侧映射

### 从内侧五元组到外侧映射

设 IM 客户端位于私网，发起到服务器 `203.0.113.20:443` 的 TCP 连接。其内侧报文五元组为：

`10.0.0.2:53000 → 203.0.113.20:443，TCP`

当报文经过 NAT 网关时，网关会建立一条状态表项，并改写源地址与源端口，例如：

`10.0.0.2:53000 ⇄ 198.51.100.7:62000`

于是离开公网侧的报文变为：

`198.51.100.7:62000 → 203.0.113.20:443，TCP`

服务器实际看到的客户端来源是 `198.51.100.7:62000`，而不是 `10.0.0.2:53000`。服务器的响应包发回 `198.51.100.7:62000`；NAT 根据先前记录的映射，将目的地址改回 `10.0.0.2:53000`，客户端才会收到该连接上的数据。

可将 NAT 抽象为“为出站流量租用一个可返回的公网入口”。同一公网地址可同时服务许多内侧设备，例如：

- `10.0.0.2:53000 → 198.51.100.7:62000`
- `10.0.0.3:53000 → 198.51.100.7:62001`

因此，服务器只看客户端公网 IP 无法区分可靠的用户身份，甚至无法必然区分同一组织中的不同终端。映射也不是永久身份：重连、超时、切换 Wi‑Fi/蜂窝网络，或经过另一层 NAT 后，外侧地址和端口都可能变化。应用应以登录凭证、会话令牌和授权状态识别用户，而非把 NAT 映射当作身份或稳定会话标识。

### 返回包为何能找到原连接

### 返回包为何能找到原连接

客户端先从内侧发起连接：

`10.0.0.2:53000 → 203.0.113.20:443`

NAT 在出站方向创建一条映射，并改写源地址与源端口：

`10.0.0.2:53000 ↔ 198.51.100.7:62000`

因此服务器实际观察到的是：

`198.51.100.7:62000 → 203.0.113.20:443`

服务器回包时，并不需要知道 `10.0.0.2` 的存在；它只按自己看到的对端地址发送：

`203.0.113.20:443 → 198.51.100.7:62000`

该数据包到达 NAT 的外侧接口后，NAT 以目标地址和目标端口 `198.51.100.7:62000` 为线索查询映射表，并结合协议、对端地址/端口等条件确认这是否属于已有流量。若命中上述表项，NAT 将目标恢复为内侧端点：

`203.0.113.20:443 → 10.0.0.2:53000`

随后把包转发给客户端。对客户端而言，它仍在与服务器 `203.0.113.20:443` 通信；对服务器而言，对端始终是 `198.51.100.7:62000`。

关键在于：回包能回来，不是因为 NAT“猜出”了内网主机，而是因为此前的出站流量留下了可查询的映射状态。映射过期、设备重启、网络切换，或新连接获得不同外侧端口时，旧回包就可能无法再匹配原连接。具体匹配范围和超时规则取决于 NAT 类型及 TCP、UDP 的不同要求，不能把某个固定超时值当作普遍规律。

### 映射变化与超时不可臆测

### 映射变化与超时不可臆测

对 NAT 而言，`10.0.0.2:53000 → 198.51.100.7:62000` 是一条会变化的状态记录，而非永久身份。服务器通常只能看到外侧源组：

`10.0.0.2:53000` → NAT → `198.51.100.7:62000` → 服务器

返回包发往 `198.51.100.7:62000` 后，NAT 依靠当前映射和过滤规则，决定是否、以及转交给哪个内侧套接字。该记录可能因空闲、设备重启、路由器切换、客户端重连、移动网络切换或端口重新分配而消失或改变。

TCP 与 UDP 不能混为一谈：

- **TCP**：NAT 可参考连接状态，例如握手、关闭以及后续报文；但具体状态保持多久、异常断链后何时回收，取决于 NAT 实现和实际流量。
- **UDP**：没有 TCP 那样的连接状态，NAT 通常按 UDP 报文活动维护映射；是否允许外部新端点发入、映射何时过期，也由设备策略决定。
- **过滤**：即使外侧地址和端口相同，NAT 是否接受来自某个外部地址、端口的返回或新入站包，仍取决于其过滤行为。

因此，不能从“客户端在 NAT 后面”推出“连接必在 30 秒、60 秒或某个固定秒数后断开”。可靠结论应来自观测：记录连接建立、最后一次双向流量、网络切换、重连结果及中间设备行为。RFC 5382 与 RFC 4787 分别讨论 TCP、UDP 的 NAT 行为要求；它们帮助描述兼容性目标，却不能替某台具体设备承诺统一超时值。

### 外侧地址不是用户身份

### 外侧地址不是用户身份

设两台内侧设备分别建立连接：

- 设备 A：`10.0.0.2:53000 → 198.51.100.7:62000`
- 设备 B：`10.0.0.3:54000 → 198.51.100.7:62001`

服务器可能同时看到它们都来自 `198.51.100.7`。因此，“客户端 IP 相同”通常只说明请求经由同一出口 NAT、公司网关、家庭路由器或移动运营商网络，不能说明它们属于同一用户、同一设备，甚至不能说明是同一个应用实例。

对象授权必须依据应用层身份。例如访问 `/accounts/42/orders/9` 时，服务端应验证登录会话、访问令牌或签名中的主体是否有权读取该对象，而不是写成“只要源 IP 是上次访问者即可继续访问”。否则同一宿舍、企业网络或运营商出口中的其他用户，可能被错误地视作同一主体。

会话归属也应由应用维护：`session_id`、认证令牌、用户 ID、设备凭据及其服务端状态，才是“这是谁的会话”的依据。IP 可作为辅助信号，例如发现短时间内跨地域、跨网络的异常切换；但它会受 NAT 重连、移动网络切换、代理和地址复用影响，不能单独作为登录绑定或拒绝访问的决定条件。

风控可把 IP 用于限速、信誉评估和异常聚类，却应明确其粒度是“网络出口”，不是“人”。对共享出口直接永久封禁，可能误伤大量无关用户；对同 IP 自动互信，则可能把不同用户混为一组。

### NAT 边界与 S2 状态边界

### NAT 边界与 S2 状态边界

设客户端原先位于网络 **N1**，通过 NAT 建立连接：

`10.0.0.2:53000 → 198.51.100.7:62000 → S2`

S2 的连接表中，实际受理的是一个 TCP 连接及其进程内状态，例如已认证用户、会话对象、未确认消息、发送缓冲区和心跳计时器。对 S2 而言，对端可见地址通常是 `198.51.100.7:62000`，而不是内侧的 `10.0.0.2:53000`。

当客户端迁移到 **N2**，即使仍是同一台设备、同一账号，也可能得到另一条外侧路径：

`10.1.0.8:41000 → 203.0.113.9:55001 → S2`

这不是原连接“穿过 NAT 继续存在”，而通常意味着：

1. N1 上的 NAT 映射及原 TCP 路径可能已失效；
2. 客户端向 S2 建立新连接；
3. S2 的新进程或新连接处理器重新认证并绑定会话；
4. 应用层依据消息编号、确认记录或持久化游标，确认哪些历史数据已送达、哪些需要补发。

NAT 只维护“外侧地址端口如何转回内侧”的映射。它不会把 N1 的映射迁移到 N2，也不会把 S2 某个连接处理器的内存复制给另一个处理器。若 S2 有多实例，重连后落到不同实例时，离线历史、会话恢复和去重必须依赖共享存储、消息系统或显式会话协议完成。

因此，`客户端 IP 变化`可提示网络路径变化，却不能单独证明用户变更；`NAT 超时`也只能解释连接可能失效，不能推导业务消息是否丢失。业务连续性最终由认证、持久化状态与重连协议保证。

> **要点** — NAT 提供可返回的地址端口映射；身份、会话状态与跨节点数据一致性必须由应用层分别承担。

MTU约束的是链路或路径中网络层包的大小；它会影响分段与排障，但不等同于业务消息正文容量。

### 先分清包、段与业务正文

### 先分清包、段与业务正文

“消息有多大”必须先说明处于哪一层。它们不是同一个对象：

- **应用消息**：例如 IM 的正文；当前合同限制为最多 `6 UTF-8 B`。
- **HTTP 请求体**：承载应用数据的一部分；当前原始 body 最多 `4096 B`，还不包括请求行、HTTP 头等。
- **TCP 字节流**：TCP 看到的是连续字节，不保留“第几个 HTTP 请求”或“第几条消息”的天然边界。
- **TCP 段**：TCP 为发送字节流切出的片段，包含 TCP 头和一部分数据。
- **IP 包**：IP 在 TCP 段外再加 IP 头；MTU 通常约束的是这一层包在某条链路上的大小。
- **链路帧**：以太网等链路层再封装 IP 包，并加入帧头、帧尾等开销。

若某 IPv4 链路 MTU 为 `1500 B`，且 IPv4 头 `20 B`、TCP 头 `20 B`，则**该条件下**单个 TCP 段最多携带：

$$1500-20-20=1460\text{ B}$$

这只是一个特定封装条件下的上限，不是 HTTP body 上限，更不是 IM 正文上限。`4096 B` 的请求体可被拆入多个 TCP 段和 IP 包；反过来，`6 B` 正文也会连同 HTTP、TLS、TCP/IP 与链路头一起发送。接收端一次 `Read` 读到多少字节由缓冲与时机决定，不能把一次读取误认为恰好一条业务消息。

### 用1500 B链路推导1460 B

### 用1500 B链路推导1460 B

设某一段以太网链路的 MTU 为 `1500 B`。这里的 `1500 B` 指该链路上一个 IPv4 包可承载的最大长度，包含 IPv4 头和其后的 TCP 段内容，但通常不包含链路层帧头、帧尾等开销。

在题设的理想条件下：

- IPv4 基本首部：`20 B`
- TCP 基本首部：`20 B`
- IP 包最大长度：`1500 B`

因此，单个 TCP 段中可用于放置 TCP 数据的最大空间为：

$$
1500 - 20 - 20 = 1460\text{ B}
$$

也就是说，一个长度恰为 `1500 B` 的 IPv4 包可以包含：

```text
[ IPv4 头 20 B ][ TCP 头 20 B ][ TCP 数据最多 1460 B ]
```

这里的 `1460 B` 是由这组前提推导出的**单段 TCP 数据上限**，并非任何业务层正文的固定限制。若 IPv4 或 TCP 使用选项，首部会变长；若经过 VPN、IPsec、GRE、隧道或其他封装，实际可用空间还会继续减少。路径中任一链路的 MTU 小于 `1500 B`，也会使端到端可安全发送的 TCP 数据长度变小。

此外，TLS、HTTP 头、分块编码等属于更高层协议开销；它们会占用 TCP 数据区，但不改变上述“IPv4 头 `20 B`、TCP 头 `20 B` 时剩余 `1460 B`”这一纸面算式。

### 1460 B为何不是通用上限

### 1460 B为何不是通用上限

`1460 B = 1500−20−20` 只是在一组极窄前提下得到的结果：

- 当前链路的 IPv4 MTU 恰为 `1500 B`；
- IPv4 头恰为最小 `20 B`，没有选项；
- TCP 头恰为最小 `20 B`，没有选项；
- 讨论的是**一个 TCP 段中可携带的 TCP 数据**，而不是 HTTP 正文、TLS 明文或业务消息。

任一条件变化，结果都会变化。IPv4 头可因选项超过 `20 B`；TCP 的时间戳、SACK 等选项也会占用头部空间。若路径中最小 MTU 小于 `1500 B`，例如某段链路只能容纳 `1400 B`，即使没有选项，TCP 数据理论上也至多为：

$$1400-20-20=1360\text{ B}$$

隧道进一步减少内层可用空间：外层 IP/UDP、VPN、封装协议都要消耗字节。TCP 在 TLS 之上时，TLS 记录头、认证标签及可能的填充也会占据传输容量；HTTP 请求或响应还包含起始行、字段、分块编码等，故“HTTP body 有 4096 B”并不意味着它能装入一个 TCP 段，更不意味着只产生一个 IP 包。

因此，`1460 B` 不是通用 MSS，更不是 `Message.Body` 的上限。当前 IM 正文限制为 `6 UTF-8 B`，属于业务合同；原始 HTTP body 的 `4096 B` 限制也属于应用层合同。它们与 MTU 解决的是不同问题。网络接收端面对的是字节流：一次 `Read` 可能只读到部分 HTTP 请求，也可能读到多个请求的连续字节，必须按协议帧边界解析，而不能按“一个包”或“1460 B”切分消息。

### IM正文限制与分段读取

### IM正文限制与分段读取

当前 IM 的正文上限是 **6 UTF-8 B**：它是产品与协议层的业务约束，应按编码后的字节数验证，而不是按“字符个数”猜测。例如 `hello!` 为 6 B，`你` 通常为 3 B，两个汉字通常已占 6 B；超过限制应由应用明确拒绝。

这条限制与 MTU 没有直接换算关系。即使正文只有 6 B，请求仍包含 HTTP 起始行与字段、可能的 TLS 记录、TCP/IP 头以及链路层开销；不能据此说“网络包只有 6 B”。

相对地，原始 HTTP body 最多可为 **4096 B**，但它也不保证对应一个 TCP 段、一个 IP 包或一次读取结果。在理想的 IPv4 MTU `1500 B`、最小 IPv4/TCP 头各 `20 B` 时，单个 TCP 段最多携带 `1460 B` 数据；`4096 B` 的 body 连同 HTTP 头通常需要多个段。更小路径 MTU、TLS、隧道及头部选项还会进一步改变实际分段。

接收端应把 TCP 看作连续字节流：一次 `Read` 可能只得到半个 HTTP 请求，也可能得到一个完整请求外加下一个请求的开头。正确做法是按 HTTP 的长度或分块规则持续累积、解析，而非把一次 `Read` 的返回边界当作业务消息边界。

### 定位大包问题的证据链

### 定位大包问题的证据链

怀疑 PMTU（路径最大传输单元）或“大包被丢弃”时，先建立证据链，而不是看到超时就断言“MTU 太小”。应同时观察：

- **路径与出口变化**：记录源、目的地址、路由、网络类型、是否经过 VPN、代理、容器网络或隧道。相同服务在办公网、蜂窝网络和跨境路径上，实际 PMTU 可能不同。
- **发送的实际大小**：区分应用正文、HTTP 请求体、TLS 记录、TCP 段和 IP 包。`4096 B` 的 HTTP body 并不等于一个 `4096 B` 的 IP 包；当前 IM 正文最多 `6 UTF-8 B`，也不意味着线上只传输了 `6 B`。
- **分段与重传迹象**：抓包查看 TCP 段长度、IPv4 分片标志与片偏移、重复 ACK、重传、连接停滞。TCP 会依据 MSS 分段；一次 `Read` 得到多少字节受缓冲与时序影响，不能据此反推“一个请求就是一个包”。
- **控制报文与黑洞特征**：若可见“需要分片但设置了不分片”一类 ICMP 提示，或大请求稳定失败、小请求稳定成功，应提高对 PMTU 的怀疑。若相关 ICMP 被中间设备过滤，可能出现 PMTU 黑洞：握手成功、少量数据成功，较大响应或上传反复超时。
- **可复现实验**：在同一路径上逐步改变有效负载大小，并保持协议、加密、代理和超时配置一致；对比直连与经隧道、不同 MSS 或不同网络出口的结果。

结论应表述为“某路径在某封装条件下，对超过某大小的数据出现丢失或超时”，再继续验证路由、隧道开销、MSS 协商和防火墙策略。不要把单次超时、单次短读，或业务正文长度直接当作 MTU 故障的充分证据。

> **要点** — MTU限制网络包而非业务正文；1460 B只是在特定IPv4/TCP假设下得出的单段数据上限。

移动网络中的晚到、丢失与断连常来自链路和路径变化；恢复连接必须区分传输可达、业务确认与历史补齐。

### 移动路径为何持续变化

### 移动路径为何持续变化

移动设备的“网络已连接”只表示当前有某种接入，并不保证到服务端的路径稳定。Wi‑Fi 信号会随距离、遮挡、漫游到不同接入点而变化；同一信道上的其他设备竞争发送机会，也会使排队时间突然升高。蜂窝网络则受小区覆盖、基站负载、无线资源调度、用户移动和切换影响。

链路层通常会重传暂时丢失的帧。重传可能让数据最终到达，却把原本几十毫秒的传输拉长到数百毫秒；若重传耗尽，才表现为上层可见的丢包。于是应用看到的往往不是稳定延迟，而是：

- 平时很快，偶尔出现长尾延迟；
- 消息先后发送，却因不同队列或重传而乱序到达；
- 短暂失联后恢复，期间请求超时或连接被中断；
- 从 Wi‑Fi 切到蜂窝后，出口地址、NAT 映射和运营商路由改变。

运营商网络中的核心网选择、NAT、负载均衡和跨网互联路径也可能变化；即使无线信号良好，端到端时延仍可能抖动。故一次 IM 消息晚到，只能说明其端到端可见时间较晚，不能反推出发送端应用“没有调用 `Write`”，更不能据此断言服务端未曾受理。网络观察到的是结果，不是完整的发送端执行历史。

### 晚到消息不能反推未写入

### 晚到消息不能反推未写入

一次 IM 消息晚到，只能观察到“接收方在较晚时刻才显示或处理它”，不能倒推出发送端应用没有调用 `Write`。从应用调用到对端呈现之间，至少经过一条可能分叉、排队和重试的链路：

1. 应用将字节交给 TCP、QUIC 或 WebSocket 实现；`Write` 成功通常只表示本机协议栈接受了数据，不等于数据已离开设备，更不等于对端已确认。
2. Wi‑Fi 可能因信号弱、同信道竞争、省电唤醒而延迟发送；蜂窝链路也可能经历调度等待、无线重传或小区切换。
3. IP 路径、NAT 映射、运营商出口和服务端负载均可能变化。报文可能排队、乱序、丢失后由传输层重传，或因连接中断而最终失败。
4. 接收端即使收到字节，仍可能等待应用线程调度、身份校验、去重、持久化或推送展示；“收到”和“用户看见”不是同一时刻。

因此，观察到 B 在数分钟后收到消息，兼容多种事实：A 已调用 `Write` 且数据在链路中延迟；TCP 重传后才送达；服务端已受理但 B 断网后恢复；或应用在某一环节重试。单一晚到事件不能区分这些假设。

要证明“未写入”，需要更直接的证据，例如 A 端调用日志、套接字错误、发送队列状态、服务端请求记录及消息标识关联。反过来，A 获得 `200 accepted_in_memory` 也只证明当前服务实例已内存受理；它不证明 B 已收到，更不构成跨重启、跨切换或离线 25 小时的历史补齐保证。

### 切网后的 TCP 与 WebSocket

### 切网后的 TCP 与 WebSocket

设备从 Wi‑Fi 切到蜂窝网络时，变化的不只是“信号强弱”，而通常是整条网络路径：本机可用 IP 地址、默认网关、运营商 NAT、出口地址以及到服务端的路由都可能改变。一个 TCP 连接由四元组标识：

$$
(\text{源 IP},\ \text{源端口},\ \text{目的 IP},\ \text{目的端口})
$$

原连接若建立在 Wi‑Fi 的私网地址和 NAT 映射上，切到蜂窝后，旧四元组及中间 NAT 状态往往已不存在。服务端继续向旧路径发送 TCP 数据，只会得到超时、重传失败或复位；客户端的 WebSocket 也可能在下一次读写、心跳或超时检测时才发现连接已失效。

因此，不能因为一条 IM 消息晚到或暂未到达，就推断发送端“没有调用 `Write`”。应用可能已写入本地 TCP 缓冲区，或服务端已经受理，但后续链路、NAT 状态、对端网络均可能变化。反过来，客户端一次“发送成功”也不等于接收者已在线收到。

典型恢复流程应按真实结果推进：

1. 发现读写错误、心跳超时或网络变化；
2. 建立新的 TCP 连接，并重新完成 TLS 握手；
3. 重新执行登录、令牌校验或设备身份认证；
4. 重建 WebSocket 会话；
5. 按产品协议重新订阅频道、会话或推送主题；
6. 使用游标、消息序号或服务端同步接口补拉允许恢复的内容。

“重连成功”只表示新的传输通道可用，不表示旧 WebSocket 中未完成的帧自动续传，也不表示历史消息必然补齐。若服务端仅确认 `accepted_in_memory`，该确认通常只说明消息进入当前进程内存；服务重启、会话过期、接收者离线过久时，是否仍可查询或重放，取决于持久化、保留期与产品合同。

### QUIC 迁移的能力与限制

### QUIC 迁移的能力与限制

TCP 连接由四元组标识：`源IP:源端口 → 目的IP:目的端口`。设备从 Wi‑Fi 切到蜂窝后，本地地址、出口 NAT 映射或路径通常改变；旧四元组失效时，原 TCP/WebSocket 不能因为“还是同一用户”而续接，只能新建连接，并按产品协议重新进行 TLS、身份认证、订阅恢复与必要的补拉。

QUIC 则以连接标识符关联连接，而非完全绑定初始四元组。若客户端地址变化后仍能到达同一 QUIC 端点，端点允许迁移且协商条件满足，客户端可在新路径上发送数据；服务端通过路径验证确认该地址确实可达，避免把响应流量放大或转发给伪造地址。NAT 重绑定、Wi‑Fi 与蜂窝切换因此**可能**不必建立全新的传输连接。

但“可能迁移”不等于“业务无感”：

- 端点可禁用迁移，负载均衡、连接标识路由、策略设备也可能使新路径失败；
- 迁移期间仍可能有丢包、乱序、验证等待和短暂不可达；
- HTTP/3/QUIC 的连接仍可能因超时、服务端重启或网络策略而终止；
- 传输连接延续不自动恢复业务状态：过期授权、订阅版本、确认游标和离线消息仍须由应用协议处理。

因此，A 收到 `200 accepted_in_memory` 只说明 A 的请求已被当前 S2 内存受理；即使 B 的 QUIC 连接成功迁移，也不能推出 B 已收到该消息，更不能补齐 B 离线 25 小时期间缺失的历史。

### 恢复边界与 IM 交付合同

### 恢复边界与 IM 交付合同

A 向服务端发送消息后得到 S2 `200 accepted_in_memory`，只表示：该请求已被**当前进程的内存状态**受理。它不证明消息已持久化、已路由到 B、已抵达 B 设备，更不承诺服务重启后仍能补回该消息。

当 B 离线 25 小时，或 B 从 Wi‑Fi 切到蜂窝时，应将恢复责任拆开：

- **连接恢复**：客户端发现 TCP/WebSocket 断开后重连；若 IP、NAT 映射或四元组改变，旧 TCP 连接不能延续。QUIC 在端点和路径验证条件满足时可能迁移，但应用仍须处理失败与重新认证。
- **会话恢复**：新连接完成 TLS、登录令牌校验、设备身份确认，并恢复必要订阅。不能因“同一用户”就默认继承旧连接状态。
- **消息补拉**：应由服务端持久消息日志、会话游标或同步令牌，并由客户端声明“我已处理到的位置”。B 重连后请求缺失区间，而不是假定断线期间的推送会自动重发。
- **去重与排序**：重连、超时重试和多路径传输都可能造成重复。消息应有稳定 `message_id`，客户端按标识幂等落库；顺序则需明确是会话内顺序、发送者顺序还是尽力而为。
- **授权边界**：补拉时必须重新检查 B 当前是否仍属于会话、是否被撤销设备权限、消息保留期是否到期。历史存在不等于当前仍有读取资格。

因此，产品合同应明确写出：S2 是否持久化、离线消息保存多久、服务重启是否保留、可补拉的范围、重复消息的处理方式，以及“已送达”究竟指服务端接收、设备收到，还是用户已读。若只有进程内受理，就不能承诺跨重启历史保证。

> **要点** — 网络切换会改变路径和连接状态；重连恢复传输，不自动证明旧消息已交付或历史可补。

网络故障应按边界分层定位：先找第一个失败环节，再判断大包与切网是否改变了连接条件。

### 建立分层故障定位顺序

### 建立分层故障定位顺序

“连不上”不是一个可诊断的结论，而是一串边界中的某一处先失败。排查应按请求实际经过的顺序记录：**时间、客户端网络、目标名称、观测来源、失败阶段**，避免把后续现象误判为根因。

1. **名称解析**：域名是否解析成功？得到的地址、缓存时间与预期是否一致？名称错误、过期缓存或仅返回不可达地址，都会表现为“无法连接”。
2. **路由与网关**：客户端是否有到目标地址的可用路径？本地网关、企业网络策略、IPv4/IPv6 选择错误都可能使连接尚未离开本地网络。
3. **地址转换与防火墙**：NAT 是否为出站连接建立映射？映射是否超时、端口是否耗尽、回包是否被策略丢弃？此处常见“请求发出但没有响应”。
4. **传输建连**：TCP 三次握手或 QUIC 初始握手是否完成？应区分超时、被拒绝、连接重置与握手后中断；它们对应的责任边界不同。
5. **TLS 与名称校验**：连接建立不等于安全会话建立。证书过期、SNI 名称不匹配、客户端时间错误或协议版本不兼容，都会在此失败。
6. **代理与应用响应**：代理可能返回认证失败、限流、上游不可达；应用返回 `404` 则说明请求已到达应用语义层，不能再笼统称为“网络失败”。

可将一次请求写成链路：

`解析 → 路由 → NAT/策略 → TCP 或 QUIC → TLS → 代理 → 应用响应`

第一个无法验证为成功的节点，就是当前优先检查的坏边界。不要因看到“超时”便跳过前面的名称、路由与映射条件；也不要因应用报错而反推网络必然正常。

### 本地下一跳与NAT映射

### 本地下一跳与NAT映射

访问远端服务时，主机通常并不直接在链路层“找到服务器”。它先依据路由表判断目标 IP 是否属于本地子网：

- **同一子网**：通过 ARP（IPv4）或邻居发现（IPv6）取得目标主机的链路层地址，帧直接交给目标。
- **非同一子网**：IP 包的目标地址仍是远端服务器，但以太网帧的目标地址是**默认网关**。主机只需知道“下一跳是谁”，不需要知道互联网中每一跳的链路层地址。

因此，“能解析域名但连不上”不能仅凭 DNS 成功就判定外网可达：DNS 给出的是目标 IP；随后本机还必须有可用路由、能到达默认网关，并由网关继续转发。

家庭网络、办公网常在出口执行 NAT。内网连接例如：

`192.168.1.20:51000 → 203.0.113.8:443`

经过源地址转换后，公网侧可能看到：

`198.51.100.30:40001 → 203.0.113.8:443`

这里 `198.51.100.30:40001` 是 NAT 临时建立的映射。返回流量必须命中该映射，网关才能还原并交给 `192.168.1.20:51000`。映射可能因空闲超时、切换 Wi‑Fi/蜂窝网络、出口变化或网关重启而失效；这会使旧 TCP 或 QUIC 连接无法继续，即使域名、服务端和用户登录状态都未变化。

还要区分三种“身份”：

- 链路层身份：本地帧交给网关所需的 MAC 地址；
- 网络传输身份：IP、端口及 NAT 映射；
- 业务身份：Cookie、令牌、会话或设备凭据。

NAT 映射改变不等于业务登录失效；反之，重建网络连接成功，也不保证应用凭据仍有效。记录故障时应标明时间、网络来源、旧/新本地地址与端口、连接是否重建，避免把“出口映射失效”笼统写成“网络失败”。

### 小包成功而大包失败的排查

### 小包成功而大包失败的排查

“小请求成功、大请求卡住或失败”说明问题与**大小、分段、处理时间或解析路径**有关，但不能仅凭现象断言为路径 MTU（PMTU）问题。应让同一目标、同一身份、同一网络条件下的请求逐步增大，并记录时间、请求大小、响应码、失败阶段与日志来源。

| 观察现象 | 更可能的边界 | 优先核查 |
|---|---|---|
| 到固定字节数立即返回 `413`、`422` 或业务错误 | 代理、网关、应用 | `Content-Length` 限额、上传字段限额、反序列化/文件解析规则 |
| 请求体尚未发完便断开、超时 | 链路、代理、服务端读取 | 读超时、连接空闲超时、反向代理缓冲、服务端消费速率 |
| 小响应正常，大响应下载停滞或反复重传 | 路径、MTU、丢包 | 封装后报文大小、分片策略、重传次数、不同网络路径差异 |
| 仅特定请求失败，即使总字节数不大 | 协议头与应用 | Cookie、鉴权头、URL、表单字段、压缩前后大小 |
| 直连成功，经代理或 VPN 失败 | 中间层 | 代理体积限制、隧道封装、检查策略、缓冲配置 |

路径 MTU 关注的是单个 IP 报文能否通过，而 HTTP 请求体通常会被 TCP 分段或 QUIC 分帧；因此“请求较大”不等于“单包过大”。但 VPN、隧道、代理协议等会增加封装开销：原本接近链路 MTU 的报文，可能在中间路径上超限。若相关 ICMP 不可达消息被过滤，发送端又未正确降低报文大小，便可能表现为大流量停滞、重传或连接超时。

排查时可做受控比较：保持正文格式不变，只增加填充内容；再保持总大小近似不变，分别增加头部、文件字段或响应大小。若阈值稳定且返回明确状态码，优先查限额；若阈值随网络、VPN 或出口变化，才提高对 MTU、丢包和路径差异的怀疑。日志中应区分“客户端未发完”“代理未转完”“服务端未读完”和“服务端解析失败”，以定位第一个坏边界。

### 手算MTU与应用负载上限

### 手算 MTU 与应用负载上限

先区分三个量：链路 MTU 是某一跳可承载的最大 IP 包大小；单包负载是扣除 IP、TCP/UDP 等头部后本包可放的数据；应用消息大小则可能跨多个 TCP 段或 QUIC/UDP 数据报，通常不等于 MTU。

以常见以太网 `MTU=1500` 为例，且暂不计二层帧头：

- IPv4 最小头 `20 B` + TCP 最小头 `20 B`：  
  `MSS = 1500 - 20 - 20 = 1460 B`。  
  一个 `10 KB` 的 HTTP 请求体可以拆成多个 TCP 段发送，并非只能发送 `1460 B`。
- IPv6 固定头 `40 B` + TCP 最小头 `20 B`：  
  `MSS = 1500 - 40 - 20 = 1440 B`。  
  若有 TCP 选项、IPv6 扩展头或加密封装，可用 MSS 还会继续下降。
- IPv4 + UDP：  
  `1500 - 20 - 8 = 1472 B` 是单个 UDP 数据报可承载的最大 UDP 负载。若应用自行把一条消息塞入超过该值的 UDP 数据报，可能触发 IP 分片；分片丢失任一片，整报都无法复原。

隧道会进一步吃掉预算。假设底层链路 MTU 仍为 `1500 B`，某隧道额外增加 `60 B` 外层头部，则内层 IP 包最多约为：

`1500 - 60 = 1440 B`

若内层再是 IPv4/TCP，保守 MSS 约为：

`1440 - 20 - 20 = 1400 B`

这解释了“本地网卡显示 1500，但跨 VPN 后大包异常”的可能性：真正限制来自路径中封装后的有效 MTU，而非纸面地址或本机接口值。

但不能看到“大请求卡住”就断言 PMTU 问题。应用消息还受 HTTP 服务器请求体上限、反向代理限额、TLS/QUIC 记录切分、超时、丢包重传及服务端解析限制影响。记录诊断时应同时标明时间、观察来源、请求体大小、协议、是否经隧道/代理，以及失败发生在发送、建连还是服务端响应阶段。

### 切网后的长连接恢复边界

### 切网后的长连接恢复边界

从 WiFi 切到蜂窝网络时，变化的不只是“网络类型”：客户端的源地址、默认网关和 NAT 映射通常都会改变。旧连接的四元组

$({源IP}, {源端口}, {目的IP}, {目的端口})$

可能已不再可达；即使服务端仍保留 TCP 状态，也无法向新的网络路径正确回包。因此，切网后的“长连接断开”通常是旧路径失效，而非业务服务必然故障。

应用应把恢复拆成明确阶段，并记录每阶段的时间与结果：

1. **发现失效**：依靠心跳超时、读写错误、系统网络变化通知或 QUIC 路径验证失败。心跳间隔过长会让界面看似在线、实际已失联；过短则增加耗电与网络负担。
2. **关闭旧会话**：旧 TCP 连接通常应标记为不可用并关闭，不能无限等待其自行恢复。QUIC 可能支持连接迁移，但新路径仍需验证；迁移失败也应降级为重连。
3. **建立新连接**：重新 DNS、建连、TLS/QUIC 握手，并重新经过当前网络的代理、NAT 与负载均衡路径。
4. **恢复身份与业务状态**：新传输连接不等于已恢复登录态。应刷新或校验令牌、恢复订阅、携带游标或最后确认的事件序号，避免重复消费或漏消息。
5. **补拉与对账**：实时推送不能保证覆盖切网窗口。客户端应按消息序号、版本号或时间游标补拉缺失数据，再与本地未确认操作对账。

还要区分“连接恢复”与“后端落点恢复”。负载均衡后的新连接可能落到另一台实例；若会话、订阅状态或未确认消息只保存在旧实例内存中，重连虽成功，业务仍可能表现为收不到更新。可恢复状态应放入共享存储，或让客户端用可验证的游标重新建立状态。

不要只记录“网络失败”。至少记录切网通知时间、旧连接最后活动时间、断开原因、新连接成功时间、身份恢复结果、补拉范围与最终同步结果。这样才能定位第一个坏边界：是未发现旧链路失效、重连失败、鉴权失败，还是重连后漏了业务状态恢复。

> **要点** — 记录带时间和来源的分层证据，定位第一个坏边界；网络可达、连接存活与业务成功不是同一件事。

一次请求的“延迟”并非单一数字；先按层次、路径边界与测量口径拆开，才能定位真正等待发生的位置。

### 一条请求跨越的层次与边界

### 一条请求跨越的层次与边界

一次“发送消息”或“加载页面”会穿过多层协议；每层解决的问题不同，看到的现象也不同。排障时应先问：等待发生在哪一层、跨越了哪段边界？

- **链路层**处理本地一跳传输，例如手机到 Wi‑Fi 接入点、接入点到交换机。它关注信号质量、邻居可达性、帧丢失与本地重传。Wi‑Fi 重传可能增加局部等待，但不等于服务器处理慢。
- **网络层**负责把 IP 包送向下一跳，并由路由器逐跳转发。它关注源/目的 IP、下一跳、路由变化、NAT 转换、分片与路径 MTU。移动网络切换或 NAT 出口变化后，外侧地址可能改变。
- **传输层**负责端到端连接与可靠传送。TCP 关注握手、确认、序号、重传、拥塞窗口和接收窗口；一次 TCP 重传通常意味着端到端报文未及时确认，不能直接归因于某个 Wi‑Fi 链路。
- **应用层**处理业务语义，例如 HTTP 请求、代理转发、鉴权、数据库访问及 IM 消息投递。`200`、`404`、`409` 描述的是应用结果，不表示底层路径一定无抖动。

同样是“100 ms”，含义可能完全不同：可以是客户端到代理的往返时间、代理等待上游的时间、TCP 重传后的额外等待，或服务端业务处理时间。记录任何指标时，都应写清**起点与终点、时间窗口、单位、协议/客户端版本及网络环境**。例如“版本 3.2 的客户端，在 Wi‑Fi 下从发送 HTTP 请求到收到首字节的 p95 为 100 ms”，才具有可比较性。

### 从本地下一跳到远端可达

### 从本地下一跳到远端可达

一条 IM 请求发出时，设备并不是“直接到服务器”，而是逐跳交付：

`手机 → Wi‑Fi 接入点/家庭网关 → 运营商或互联网路由器 → NAT → 代理/负载均衡 → IM 服务`

首先是**邻居寻址**：手机依据路由表判断目标是否同网段；若否，就把二层帧交给默认网关的 MAC 地址。这里失败常表现为无法解析网关邻居、Wi‑Fi 信号弱或局部丢帧；它只能说明“到下一跳”是否可交付，不能证明远端服务可用。

随后是**路由转发**：每台三层设备按目的 IP 选择下一跳。移动网络切换、VPN 启停或 Wi‑Fi/蜂窝切换都可能改变本机源 IP、默认路由及后续路径，因此“同一服务昨天可达、现在不可达”未必是服务端故障。

经过 NAT 时，私网源地址和端口可能被映射为外侧公网地址与新端口：

`192.168.1.8:53000 → 203.0.113.7:41023`

返回包必须命中该映射；映射过期、策略限制或切网会使既有连接失效。外侧地址可用于有限网络诊断，但不能当作用户永久身份。

代理与负载均衡器又形成应用边界：它接收请求、可能终止 TLS、补充 `Forwarded` 等转发信息，再向后端发起新连接。故应分别记录“客户端到代理”“代理到后端”的时间，而非把总耗时都归因于网络。

一次可比较的观测应写清：`手机→默认网关，10 秒窗口，毫秒，客户端 4.2.0`；或`代理→IM 后端，5 分钟窗口，成功请求的 p95，毫秒，服务端版本 2025.03`。只有边界一致，才能判断问题在本地下一跳、路径中段，还是远端处理。

### 不同重传与等待不能混算

### 不同重传与等待不能混算

“消息晚到”可能发生在完全不同的层次，计时边界不同，含义也不同：

| 类型 | 常见触发条件 | 典型可见现象 | 应如何计量 |
|---|---|---|---|
| Wi‑Fi 本地重传 | 信号弱、干扰、碰撞、接收端未确认帧 | 同一无线链路上帧重复发送；上层通常看不到 | 从无线网卡发送帧到收到链路确认，单位 `ms`，注明无线制式与信号环境 |
| TCP 重传 | 报文丢失、乱序超时、接收窗口或路径拥塞 | 序号重复、重复确认、超时重传；连接仍可能成功 | 从发送某 TCP 段到其被确认，记录重传次数、RTT、拥塞窗口和连接版本 |
| HTTP/代理处理 | 代理排队、鉴权、缓存未命中、上游连接建立或重试 | 首字节时间升高，可能出现 `502`、`504`；客户端未必知道代理内部等待 | 分别记录客户端→代理、代理→上游、上游处理时间，避免只报总耗时 |
| IM 业务等待 | 离线队列、风控审核、会话路由、推送失败后的补偿 | HTTP 可能已 `200`，但对方尚未收到或已读 | 区分“服务端受理”“入队”“投递”“终端确认”，以消息/会话标识关联 |

例如，Wi‑Fi 重传增加的是局部空口等待；TCP 重传可能跨越多跳路径；HTTP `200` 只表示该接口按约定成功，不等于 IM 已送达。若把四者都写成“延迟 100ms”，既无法定位，也不能横向比较。

记录时至少写清：`起点→终点`、观测时间窗口、单位、客户端与协议版本。地址变化、NAT 或代理存在时，应使用授权范围内的请求或会话标识关联，不能把 IP 当作永久用户标识。

### 为延迟测量标注完整口径

### 为延迟测量标注完整口径

“延迟 100 ms”只有在测量口径完整时才有意义。至少应写清：

- **起止位置**：从哪里到哪里。例如“客户端点击发送 → 收到 HTTP 响应首字节”“代理收到请求 → 上游服务返回”“服务端写入消息 → 对方设备展示”。不要把 Wi‑Fi 接入、TCP 建连、HTTP 排队和业务处理混为同一段。
- **时间窗口**：记录开始与结束事件的定义，以及统计区间。例如过去 5 分钟的 `p50/p95/p99`，而非只报单次样本或均值。
- **单位与时钟**：通常使用 `ms`；跨设备计时需说明是否依赖时钟同步。优先在同一进程或同一可信观测点计算差值，避免客户端与服务端时钟偏差制造“负延迟”。
- **适用版本与环境**：客户端版本、服务端版本、网络类型、地区、是否经代理、是否处于移动切换前后都可能改变结果。
- **关联标识**：在授权范围内使用请求标识、会话标识、链路追踪标识关联日志；不要将 NAT 外侧 IP、`Forwarded` 头或临时移动 IP 视为用户永久主键。

可将指标写成：`客户端 8.3.1，蜂窝网络，请求开始至收到首字节，过去 10 分钟 p95=100 ms，单位 ms，按请求标识关联`。这样才能与“代理至上游 p95=35 ms”并列比较，并判断等待位于客户端网络、代理、传输还是应用业务阶段。

### 移动切换中的诊断与身份边界

### 移动切换中的诊断与身份边界

用户从 Wi‑Fi 切到蜂窝网络时，异常不一定是“网络慢”。切换可能同时改变本机地址、默认网关、NAT 外侧地址和可达路径；原有 TCP 连接也可能因路径状态失效而重传、超时或重新建连。

例如，请求在 Wi‑Fi 上已发出，但切换后客户端收到超时。应按阶段记录：

- 链路层：Wi‑Fi 何时断开、蜂窝何时获得可用链路；单位为毫秒，范围是“设备本地”。
- 网络层：切换前后本机 IP、下一跳或路由是否变化，以及目标地址是否仍可达。
- 传输层：原 TCP 连接是否继续可用，是否出现握手、重传、连接重置或新连接。
- 应用层：请求是否真正到达代理和服务端；响应是 `200`、`409`、`404`，还是客户端等待超时。

日志不能把 IP 当作用户永久身份：NAT 后多个用户可共享外侧地址，移动切换也会改变地址。关联应使用授权范围内的请求标识、短期会话标识、应用版本与网络类型；代理提供的 `Forwarded` 头只有在可信代理链中才可解释，且应避免无必要地长期保存完整地址或请求正文。

S2 离线确认可保留一张纸图：标出“Wi‑Fi 请求开始—切换—TCP 重连—服务端收到—响应显示”的边界，并为每个箭头填写起点、终点、时间窗口、单位和版本。它只训练观察与归因，不产生真实用户指标。

> **要点** — 延迟诊断先分层、定边界、明口径；IP 会变，业务身份与请求结果必须独立确认。

以“B离线25小时后能否收到m-9”为验收问题，分层核查网络可达、进程受理、持久留存与补拉确认，避免把连通性误当交付保证。

### 先拆开消息交付的验收链

### 先拆开消息交付的验收链

以“B 离线 25 小时后能否收到 `m-9`？”验收时，不能把一次网络连通、一次服务端响应或一次重连成功，误写成“消息已交付”。应将链路拆成可独立取证的验收卡：

| 验收项 | 需要的证据 | 实际回答的问题 |
|---|---|---|
| A 的请求到达 | A 侧发送记录、NAT 映射、路径与服务端入口日志 | `m-9` 最远到达哪一跳？ |
| S2 进程受理 | S2 返回 `200 accepted_in_memory`、请求标识匹配 | S2 当时是否把消息放入内存？ |
| N1 进程内状态 | N1 的队列、缓存、重启与迁移记录 | 该内存数据后来是否仍存在？ |
| S3 持久留存 | 数据库提交记录、消息主键、复制或恢复证据 | `m-9` 是否真的可在未来查询？ |
| B 的补拉资格 | 会话身份、游标、授权范围、过期策略 | B 重连后是否有权请求这条消息？ |
| B 的设备确认 | B 设备落盘记录与 ACK 回执 | B 是否实际收到并确认 `m-9`？ |

`200 accepted_in_memory` 只证明某个进程曾受理，既不等于已写入 S3 数据库，也不等于 B 可补拉，更不等于设备 ACK。NAT、MTU、QUIC 迁移等证据主要解释“请求和连接是否能走通”；它们不能替代留存、授权与终端确认的业务证据。

因此，24 小时 broker 留存不能保证 25 小时离线后的完整补齐；这是固定的 14.09 `q-06` 标签，不会因 B 从 Wi‑Fi 切换至蜂窝网络而改变。即使 MTU 优化或连接迁移减少了丢包、握手和数据包数量，也必须回到同一任务，按“到达、留存、补拉、ACK”失败桶验证结果。

### A的请求实际到达哪一跳

### A的请求实际到达哪一跳

判断 `m-9` 是否“发出”，先不要把目标服务地址等同于数据包的下一跳。A 发送请求时，路径至少应拆成以下链路证据：

1. **本地链路**：A 依据路由表判断 S2 的公网地址是否在本地子网。通常不在，因此 A 不会对 S2 的 IP 直接做二层寻址，而是通过 ARP/邻居发现获取**默认网关**的 MAC，将“目的 IP 仍为 S2”的报文封装后交给网关。
2. **默认网关与 NAT**：家庭路由器或蜂窝接入网可能创建 NAT 映射，例如  
   `A私网IP:端口 → 公网IP:映射端口`。此时 NAT 只证明网关已尝试转发并记录会话状态；它不证明报文已经到达 S2，更不证明 S2 的应用进程已受理。
3. **远端路由**：公网中的各跳路由器依据目的 IP 转发，可能经过运营商、骨干网、负载均衡器或安全设备。`traceroute` 所见路径只是探测包路径，不能替代该次 QUIC/UDP 数据报的逐跳送达证据。
4. **S2 入口**：只有当 S2 的边界设备或服务入口日志关联到请求标识、连接标识及时间戳，才能回答“请求到达 S2 了吗”。若入口前还有负载均衡，证据还应区分“到达负载均衡器”与“被转发到 S2 实例”。

因此，验收卡中的第一问应写成：A 的请求最后可证实到达了本地网关、NAT 出口、远端入口，还是具体的 S2 进程？NAT 映射存在、MTU 未分片、QUIC 握手成功，都不能自动推出 S2 已返回 `200 accepted_in_memory`；它们分别只覆盖路径中的局部一跳或局部阶段。

### 受理成功不等于离线可追溯

### 受理成功不等于离线可追溯

对问题“B 离线 25 小时后能收到 `m-9` 吗？”，`200 accepted_in_memory` 只是一次很窄的受理证据。它表明 A 的请求已到达 S2，且 S2 在返回该响应的时刻愿意把消息放入内存；它**不能**证明消息已跨进程、已持久化，更不能证明 B 未来可以找回。

可将三类证据严格区分：

| 证据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| S2 返回 `200 accepted_in_memory` | A→S2 的本次请求大致可达；S2 曾在内存中接受 `m-9` | S2 重启后仍有消息；N1 已收到；数据库有记录；B 能补拉 |
| N1 仍存在进程内数据 | 消息已转交或复制到 N1，且当前进程尚未丢失该状态 | 宕机、发布、驱逐或过期后仍可追溯；S3 已持久保存 |
| 未来查询 S3 数据库仍有持久记录 | `m-9` 跨越进程生命周期保留，可作为离线补拉的候选来源 | B 有读取权限；查询范围覆盖该消息；B 实际拉取并确认收到 |

因此，NAT 映射、MTU 分片或 QUIC 迁移成功，只能改善“A 的请求能否到 S2”这一段网络路径。即使蜂窝切换后连接更顺畅，也不能把 `200` 推导为离线交付完成。

要完成验收，还必须继续检查：S3 是否按保留策略保存超过 25 小时、B 是否具备补拉 `m-9` 的身份与游标权限，以及 B 是否返回设备 ACK。当前 broker 仅保留 24 小时，故“离线 25 小时完整补齐”不能由上述任一受理信号保证；这一结论属于固定业务标签，不会因底层网络切换而改变。

### 25小时离线的补拉判定

### 25小时离线的补拉判定

对问题“B 离线 25 小时后能收到 `m-9` 吗？”，不能以“网络恢复后可连接”为结论。若 broker 的历史保留窗口仅为 24 小时，则 25 小时离线已越过默认补拉边界；NAT 映射、MTU、QUIC 迁移或蜂窝切换只影响后续连接能否建立，不会令已过期的消息重新出现。这也是 14.09 中 `q-06` 的固定验收标签。

验收卡应按证据逐项关闭：

- **请求到达**：A 发送 `m-9` 的请求实际到达哪一跳；仅到 N1、本地代理或边缘节点，不等于服务端已接收。
- **进程受理**：S2 是否返回 `200 accepted_in_memory`。该状态只说明内存中的请求被接住，不证明已写入可跨重启、跨迁移恢复的存储。
- **进程内残留**：N1 上是否仍有待转发或待重试的数据；进程重启、驱逐或连接迁移后，这部分数据可能消失。
- **持久历史**：未来 S3 查询时，`m-9` 是否仍在数据库或消息历史中，且未被 24 小时清理任务删除。
- **补拉资格**：B 的账号、会话游标和设备身份是否有读取该历史段的权限；“消息存在”不自动推出“该设备可补拉”。
- **设备确认**：B 是否实际收到 `m-9`，并上传设备 ACK。没有 ACK，只能称“可能投递”或“已提供补拉机会”。

因此，24 小时 broker 不能承诺 25 小时离线后的完整补齐。若迁移或 MTU 优化使连接更顺畅，仍须在同一用户任务下统计“历史已过期、无补拉权限、补拉失败、无设备 ACK”等失败桶，而非仅报告数据包更少。

### 把网络优化放回同一任务验收

### 把网络优化放回同一任务验收

设验收问题为：**B 离线 25 小时后，能否收到消息 `m-9`？** WiFi 切到蜂窝、NAT 映射恢复、MTU 探测减少分片，或 QUIC 连接迁移成功，都只能说明“新的网络路径较可能可用”，不能直接推出 `m-9` 已被交付。

应按同一条消息、同一用户任务核对证据链：

1. **请求走到哪一跳**：A 发出的 `m-9` 是否仅到达本地客户端，还是已穿过 NAT、负载均衡并到达 S2。
2. **进程是否受理**：S2 是否返回 `200 accepted_in_memory`。这表示某个进程内存曾接受请求，不等于已持久化，更不等于 B 可见。
3. **易失数据是否仍在**：若 N1 重启、扩缩容或连接迁移，N1 的进程内队列、未刷盘缓冲是否还保留 `m-9`。
4. **未来存储是否存在记录**：S3 的数据库、日志或消息存储中，是否确实有可供 B 查询的 `m-9`；“计划异步写入”不是留存证据。
5. **B 是否有权补拉**：B 重连后，其身份、游标、会话和访问策略是否允许读取该消息。
6. **B 是否设备确认**：B 的具体设备是否返回业务 ACK，而非仅完成 TCP/QUIC 握手或收到推送通道通知。

因此，24 小时 broker 留存不足以保证 25 小时离线后的完整补齐；这是固定业务约束，不会因切换到蜂窝网络而改变。迁移、MTU 或 QUIC 优化应在相同的“离线 25 小时后补收 `m-9`”任务下，比较各失败桶：路径不可达、内存受理未落盘、留存过期、无权补拉、未设备 ACK。只报告丢包更少或握手更快，不能构成交付保证。

> **要点** — m-9能否最终送达，必须同时证明受理、留存、授权补拉和设备ACK；网络连通不能覆盖离线历史保证。

通过虚构 IM 客户端的 WiFi、NAT 与移动切换路径，建立“本地交帧、远端转发、端到端确认”三层边界。

### 远端地址与本地下一跳

### 远端地址与本地下一跳

客户端向 `198.51.100.7` 发送 IM 消息时，先用目标 **IP 地址** 判断去向：将目标地址与本机 IP、子网掩码比较。若目标不属于本地子网，就不能直接在 WiFi 中寻找该远端主机；主机依据路由表选择默认路由，将下一跳确定为默认网关。

这里必须同时区分两种地址：

- **网络层目标地址**：IP 包的目标仍是远端服务器，如 `198.51.100.7`。路由器据此逐跳转发，通常不因中转而改写。
- **链路层目的地址**：首个以太网或 WiFi 帧的目的地址是默认网关在本地链路上的 MAC 地址，而不是远端服务器的 MAC 地址。

发送过程可概括为：

1. 应用交付数据给传输层和 IP 层，IP 包填写远端目标 IP。
2. 路由表发现该 IP 不在本地链路，选中默认网关。
3. 主机通过 ARP（或 IPv6 的邻居发现）查询网关的链路地址。
4. 主机封装首个帧：`目的 MAC = 网关 MAC`，但 `目的 IP = 远端 IP`。
5. 网关收到帧后拆除本链路封装，按 IP 路由表选择下一跳，并在下一段链路重新封装新帧。

因此，“发给远端 IP”不等于“在本地 WiFi 中直接发给远端设备”。链路地址只解决当前一跳的交付；远端可达性由 IP 路由及后续各跳共同决定。

### NAT 映射不等于用户身份

### NAT 映射不等于用户身份

设 IM 客户端在内网使用五元组：

`10.0.0.8:53000 → 203.0.113.20:443，TCP`

经过 NAT 后，出口设备可能建立映射：

`198.51.100.7:62000 → 203.0.113.20:443，TCP`

服务端看到的源地址变成 `198.51.100.7:62000`。这只说明：在当前 NAT 状态、协议和超时条件下，返回该公网地址端口的数据可被转回某个内网流。它不是“用户小明”的网络身份证。

映射不能证明身份，原因包括：

- 多个用户可共享同一公网 IP；不同连接会使用不同端口。
- NAT 重启、超时、切换 WiFi/蜂窝网络后，公网地址和端口都可能变化。
- 代理、企业网关或多层 NAT 会让服务端只看到中间设备。
- 攻击者也可能从某个地址端口发起连接；地址本身不构成登录凭证。

用户身份应由应用层机制确认，例如账号密码、令牌、会话 Cookie、签名或设备凭证。即使 NAT 映射保持不变，令牌过期后仍可能被服务端拒绝；即使映射改变，只要新路径重新连接并完成鉴权，用户仍可恢复会话。

同样，NAT 不负责消息持久化。它只改写和维护转发状态，不保存“消息是否已送达、是否已读、离线后是否补发”。这些语义属于 IM 服务端、客户端协议与存储系统。因而“看到了同一公网 IP”既不能推出“同一用户”，也不能推出“消息已经可靠送达”。

### MTU、头部与可承载字节

### MTU、头部与可承载字节

MTU（最大传输单元）限制的是**一条链路上单个二层帧所承载的三层包大小**，并不等于应用一次调用 `send()` 能发送的消息大小。设以太网链路 MTU 为 `1500 B`，且采用无选项的 IPv4 与 TCP：

- IPv4 头部：`20 B`
- TCP 头部：`20 B`
- 单个 TCP 段可承载的应用数据上限，即 MSS：

$$
1500-20-20=1460\ \text{B}
$$

因此，发送端在该条件下通常会把较长的字节流拆成每段最多约 `1460 B` 的 TCP 负载；接收端再按 TCP 序号重组为连续字节流。应用写入 `6000 B` 消息，不意味着网络中存在一个 `6000 B` 的 IP 包，而可能形成多个 TCP 段。

这个 `1460 B` 只是简化推导，成立条件很严格：

- IPv4、TCP 均无选项；TCP 时间戳等选项会占用头部空间。
- 没有 VLAN、PPPoE、VPN、隧道或代理封装；额外封装会进一步压缩可用负载。
- 路径上的实际最小 MTU 不低于 `1500 B`；端到端可用值取决于路径中最小的链路 MTU。
- 未考虑 TLS、WebSocket、HTTP 等应用层或安全层开销；它们消耗的是应用协议可用空间，而非直接改变上述 IP/TCP 计算式。

还要区分“消息长度”与“单包长度”。例如一条 UTF-8 文本当前只有 `6 B`，不能据此推断路径一定能承载更大的包；MTU 是逐包、逐路径的约束。反过来，即使业务允许上传 `10 MB` 文件，也不代表单个 TCP 段能装入 `10 MB`：传输层会分段，接收端重组，应用仍需处理文件大小限制、代理限制、解析开销、超时与重传。

### 移动切换后的连接边界

### 移动切换后的连接边界

从 WiFi 切到蜂窝网络时，变化的不只是“信号来源”，而是本机可用路径、源地址、默认网关与 NAT 映射都可能改变。旧 WiFi 上建立的 TCP 连接通常以四元组标识：`源IP:源端口 → 目的IP:目的端口`。一旦源 IP 或 NAT 映射失效，服务器返回的数据仍会发往旧路径；因此旧 TCP 连接通常不能直接续用，应视为已中断。

QUIC 具有连接 ID，连接标识不必完全依赖原来的四元组，因此它可以尝试在蜂窝路径上继续通信。但这不是“自动必然成功”：

- 新路径必须能到达服务器，且服务器允许该连接 ID 使用新地址；
- QUIC 需要进行路径验证，确认新路径确实可双向收发；
- 新网络的 NAT、防火墙、MTU 或运营商策略仍可能阻断报文；
- 迁移成功只说明传输连接可延续，不等于应用状态天然完整。

可将两者比较为：

| 情形 | TCP | QUIC |
|---|---|---|
| WiFi 断开后旧路径 | 通常失效 | 可尝试保留连接身份 |
| 新蜂窝路径启用 | 一般需新建连接 | 需路径验证后迁移 |
| NAT 映射变化 | 常导致旧连接不可达 | 是迁移线索，不是成功证明 |
| 应用恢复责任 | 重连、鉴权、补拉 | 仍需恢复、去重、确认状态 |

因此，IM 客户端不能把“网络已切到蜂窝”当作“消息已可靠送达”。稳妥流程是：检测连接异常；按实际路径重连或迁移；重新鉴权；根据消息 ID、游标或服务端序号补拉遗漏内容；对未确认发送进行幂等重试。端到端 ACK 仍须由对端或服务端协议明确给出，不能由本地网络切换成功代替。

### 大包与断连的分层诊断

### 大包与断连的分层诊断

虚构 IM 客户端发送失败时，不应把“发不出去”“地址变了”“没有收到确认”混为同一故障。可按以下顺序缩小范围：

1. **先看本地交付与路由**：远端服务器不在本地链路时，主机不会直接寻找远端 IP 的链路地址；它先通过 ARP/邻居发现取得**默认网关**的链路地址，再把帧交给网关。每经过一跳，链路层帧都会重新封装。检查本机地址、默认路由、网关可达性与 DNS 解析，不能从一个私网地址推断真实用户身份。

2. **再看 NAT 与地址变化**：NAT 可能把客户端的私有四元组映射为如 `198.51.100.7:62000` 的公网示意地址。该映射可复用、超时或变化，也可能受代理影响；它只说明潜在回程路径，不等于服务端已收到消息，更不等于对方设备已 ACK。地址转换也不会自动复制、持久化或恢复消息。

3. **检查大包是否触及路径 MTU**：若出口链路 MTU 为 1500 B，IPv4/TCP 且忽略选项时，单个 TCP 负载上限约为  
   $1500-20-20=1460\text{ B}$。  
   但“正文只有 6 个 UTF-8 字节”并不能证明一定可达：实际还受 TLS、隧道、代理封装、分段、路径 MTU 发现和中间设备策略影响。不能期待路由器替应用可靠地处理超大数据；应由端点分段并正确处理 PMTU 信号。

4. **最后核对协议与业务状态**：移动网络从 WiFi 切到蜂窝后，旧 TCP 连接通常不能假定仍有效。客户端应按实际路径重新建连、重新鉴权，并根据消息 ID 补拉、去重或重传。即使传输层收到 ACK，也只代表对端协议栈确认收到字节；“消息已展示给用户”仍需 IM 服务的业务确认。排查时还要区分请求体限额、代理拒绝、应用解析失败、服务端持久化失败与重传超时。

> **要点** — 帧先交本地下一跳，IP 再逐跳转发；NAT、MTU、连接迁移和业务确认必须分层判断。
