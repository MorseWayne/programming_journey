# 13.04 审阅记录：架构风格与边界

DeepTutor BookEngine 八节初稿均 ready、无失败块；本地 HTTP Markdown 导出与归档的 `original.md` SHA256 一致。正式页用同一虚构 IM 旅程比较当前 S2、未来模块化单体+教学 DB 和未来粗粒度服务，拆分代码/部署/数据权威/故障域四轴，附 22 道分层练习。

## 教学重组

- 先定义四种边界，再区别模块化单体、分层依赖、异步事件与独立服务，不按 Pod/服务数量评价架构。
- 用 A→权威 `m-9/seq9`→E9→B 的相同用户目标比较三种方案，逐项问确认点、B 25h 补拉来源及故障恢复。
- 用同 DB 事务与 DB→broker 边界解释 outbox 候选及中继重投，说明 E9 重复仍应只有一条权威消息、broker 投递不等于设备 ACK。
- 使用纸上 10,000 连接/20 入站/s/未来 2,000 设备任务/s 区分压力类型；以事务、运行、团队、迁移与业务停止门决定拆分价值。

## 技术修订

- 初稿导出有重复 `###` 标题和大量同义重述；正式页从基础边界走向三方案、事务、同步/异步、负载与决策卡。
- 初稿一处将 S3 `/v2` 描述为“当前”，并说教学 DB 存储后 B 25h 必可补拉。正式页始终标 S3 待审，另要求历史保留时长、成员可见规则与 DB 可恢复性证据。
- 初稿把当前 S2 单进程写成“内存受理后后台尝试写权威库、生成 E9”，这是没有依据的扩展；正式页只列当前 `200 accepted_in_memory`，未来方案另列。
- 初稿多处将 outbox 作为既成架构，甚至写成“中继崩溃后 E9 必然重复”或“事务成功后即可返回 B”。正式页只用 outbox 作纸上候选，描述**可能**重投；A 的 DB 存储确认、E9 与 B 设备确认分别说明。
- 初稿对迁移写“直接切回单体”“双写可用”，缺少数据权威、回填与兼容验证；正式页只提出停止/回退所需证据，具体迁移留给 13.08。
- 固定 OpenIM 两处源码只支持所读发送与 Mongo 消费异步边界，不证明真实服务拓扑、事务、outbox、设备 ACK 或本章任何候选实现。
