以未来 IM 网关 Pod 滚动退出为场景，先建立“流量可达、连接存活、消息受理、最终确认”彼此独立的判断框架。

### 先拆开五种状态信号

### 先拆开五种状态信号

滚动摘流时，“网关还活着”不等于“还能接新流量”，更不等于“某条消息已被业务确认”。应把五种信号分开设计：

- **启动状态**：进程是否完成初始化，例如配置加载、监听端口、连接注册表恢复。它回答“能否开始接受探测”，不应过早宣布可服务。
- **就绪状态**：实例是否应进入负载均衡后端。摘流第一步通常是将其置为未就绪，使新 HTTP 请求和新长连接不再分配到该 Pod。
- **存活状态**：进程是否卡死或不可恢复。它只回答“是否需要重启”；不能因为主动摘流就让存活探针失败，否则编排器会误杀仍在排空连接的实例。
- **业务确认**：某个请求是否被网关受理或被后端确认。当前 S2/v1 的 `200` 仍只表示内存受理；同 ID 返回 `409`、非成员返回 `404`，这些语义不能被就绪探针替代。静态 `6` UTF8B 正文、原始 HTTP 体 `4096B` 限制也保持不变。
- **长连接状态**：已有 WebSocket、IM 会话或流式请求是否仍可收发、是否已通知迁移、是否排空。它属于连接生命周期，而非 HTTP 存活判断。

因此控制边界应是：就绪信号控制**新流量入口**，长连接管理控制**存量连接排空**，业务响应控制**单次操作语义**，存活信号只保护**进程健康**。S3 即使提议仍为 `6B`，R9 仍待审，也不应借摘流改变既有受理契约。

### 三类探针各自改变什么

### 三类探针各自改变什么

三类探针回答的是不同问题，不能把“探针通过”误读为“消息一定成功”。

| 探针 | 它判断什么 | 失败后主要影响 | 不直接保证什么 |
|---|---|---|---|
| 启动探针 | 进程是否完成慢启动、配置加载、连接初始化 | 在成功前抑制存活与就绪检查，避免过早重启 | 网关是否已对外接流、消息是否被受理 |
| 就绪探针 | 当前实例是否适合接收新流量 | Pod 从 Service 端点中摘除；通常不再分配新 HTTP 请求或新长连接 | 已建立长连接是否立刻断开、已受理消息是否最终送达 |
| 存活探针 | 进程是否仍处于可恢复的健康状态 | Kubernetes 重启容器 | 重启前的内存状态、未完成投递、客户端确认 |

对未来 gateway 而言，启动阶段可让 `startup` 覆盖较长的初始化窗口；只有初始化完成后，`readiness` 才返回成功并发布服务端点。滚动摘流时，应先令就绪检查失败，使实例不再接收新连接，再等待既有长连接迁移或超时退出。

`liveness` 不应被设计成“下游暂时不可用就失败”。否则一次短暂依赖故障会触发重启，反而丢失仅在内存中受理的状态。当前 S2/v1 的 200 仍只表示内存受理；即使探针全部正常，也不改变 UTF8B 正文上限 6B、原始 HTTP 体上限 4096B、同 ID 返回 409、非成员返回 404 的既有语义。探针管理的是实例生命周期与流量入口，不是业务确认协议。

### 从未就绪到终止端点

### 从未就绪到终止端点

Pod 被删除并不等于“立刻没有流量”。对长连接网关而言，必须把**新流量摘除**与**旧连接排空**拆开理解。

正常启动时，应用先监听端口，但此时不应立即通过就绪探针。只有配置加载完成、路由表可用、依赖检查满足条件后，就绪探针才返回成功；Pod 才会成为 Service 的可选后端。存活探针只回答“进程是否卡死”，不能表示“现在适合接收新请求”。

删除 Pod 时，控制面会为其设置 `deletionTimestamp`，并开始终止宽限期。此后应尽快让就绪探针失败，或由终止状态使 EndpointSlice 中该端点不再对新流量可用。可将端点状态理解为：

- `ready=false`：普通负载均衡器不应再把**新请求、新连接**分配给它。
- `terminating=true`：该端点正在退出，消费者可据此避免将其当作正常可用实例。
- `serving=true`：虽然正在终止，但实例仍可能继续服务既有连接；它不是“可接新客”的承诺。

`preStop` 是应用获得的排空窗口，而不是摘流开关本身。一个合理顺序是：

1. `preStop` 通知网关进入 draining：拒绝新的 HTTP 请求、拒绝新的长连接握手。
2. 就绪状态变为失败，使新流量从 EndpointSlice 视角摘除。
3. 对已建立的长连接继续维持一段时间；必要时发送“服务器维护中”的协议级通知。
4. 在终止宽限期内等待会话自然结束或完成业务确认。
5. 宽限期结束后，容器仍未退出则可能被强制终止。

因此，`ready=false` 只能降低新流量进入的概率，不能撤销已经建立的 TCP/WebSocket 连接；`serving=true` 也不能证明业务消息已确认。网关仍需自己维护连接状态与消息确认状态：例如停止受理新的 6 UTF8B 正文请求，但让此前已返回 `200` 的内存受理记录继续等待后续确认。

### HTTP 请求与 WebSocket 分开排空

### HTTP 请求与 WebSocket 分开排空

摘流不能只调用一次 `Shutdown`。普通 HTTP 请求通常短暂，目标是“停止新请求、完成在途请求”；WebSocket 则是长期会话，目标是“拒绝新会话、迁移或通知旧会话、在截止时间前关闭”。

对 HTTP 服务，可先将就绪探针置为失败，使负载均衡不再分配新流量，再调用：

`server.Shutdown(ctx)`

它会关闭监听器，并等待已进入处理器的请求返回。处理器应检查 `ctx.Done()`，避免长轮询、外部调用或消息写入无限阻塞。即使请求已经受理，仍应保持既有语义：正文仍限制为 6 个 UTF-8 字节、原始 HTTP 体限制为 4096 字节、同 ID 返回 409、非成员返回 404；正常 `200` 仍只表示内存受理，不应伪装成最终确认。

WebSocket 不会因 HTTP `Shutdown` 自动优雅结束：连接已升级，不再是普通请求。网关应维护活动会话表，并在进入排空状态后拒绝新的升级握手，例如返回“服务正在维护”的响应。对已有会话，可发送应用层控制消息：

`{"type":"draining","retry_after_ms":30000}`

随后停止向该连接分配新业务，允许客户端重连到其他 Pod。排空期限内仍可处理必要的确认、心跳和关闭帧；期限到达后，先发送 WebSocket 关闭帧，再强制关闭剩余连接。

因此，状态至少应区分：HTTP 是否可接收、WebSocket 是否可新建、已有连接数是否归零、业务是否仍允许受理。只有这些条件分别可观测，滚动更新才不会把“进程还活着”误判为“连接和消息都已安全摘流”。

### 受理成功不等于消息已确认

### 受理成功不等于消息已确认

在当前 S2 静态行为中，客户端向网关提交消息后收到 `200`，只表示网关已将该消息**受理到内存中的当前处理路径**；它不是“对端设备已收到”，也不是“消息已持久化并可在故障后恢复”的证明。

可将结果理解为不同层次：

- `200`：请求格式、成员关系与重复检查均通过，消息被内存受理。
- `409`：同一消息 `ID` 已经存在。客户端不应把它当作新的成功投递；是否可安全重试，要依赖未来定义的幂等语义。
- `404`：发送者或目标不属于该会话/群组，网关拒绝受理。
- `400` 或类似校验失败：正文不是合法 UTF-8，或正文超过当前固定上限 `6` 字节。
- 原始 HTTP 请求体同样受 `4096` 字节上限约束；即使业务正文很短，过大的请求头、字段或包装内容仍可能导致请求被拒绝。

例如，`"你好"` 在 UTF-8 中通常为 `6` 字节，恰好可受理；再增加一个字符就超过 S2 的正文限制。这里限制的是**字节数**，不是字符数。

因此，滚动摘流时不能把“仍能返回 `200`”误判为“消息已经安全送达”。长连接仍存活、网关仍受理、客户端已收到响应、下游设备已确认，是四个不同状态。未来版本才会引入权威确认、设备投递结果等语义；当前 S3 提议仍维持 `6` 字节正文限制，R9 仍待审。

> **要点** — 安全摘流依赖探针摘除新流量、终止预算排空旧连接；HTTP 受理结果不能替代未来消息确认。

长连接网关安全摘流的前提，是让探针只承担其应承担的控制职责，并把流量可达、连接存活与消息确认严格区分。

### 三类探针的控制边界

### 三类探针的控制边界

三类探针都回答“是否健康”，但它们驱动的控制动作完全不同；把它们混成一个检查，往往会让长连接网关在压力或依赖故障时错误摘流、错误重启。

- **启动探针**解决“初始化尚未完成，是否应暂缓其他判定”。网关加载证书、恢复本地状态、建立必要的内部组件时，启动探针未成功前，平台通常不执行或不计入存活、就绪失败。它应给慢初始化留出明确窗口，而不是承担持续服务质量判断。启动成功后，其保护职责结束。

- **就绪探针**解决“此实例是否应接收新的常规流量”。失败时，实例应从常规 `Service` 的可选端点中移出；容器仍可存活，已有长连接也不必被平台立刻杀死。网关可借此停止接纳新会话，继续排空旧连接，或在退出流程中完成优雅摘流。就绪失败不是“进程已死”，更不是重启命令。

- **存活探针**解决“进程是否已失活到需要重启”。连续失败达到阈值后，平台可能终止并重建容器。它应检查事件循环卡死、关键工作线程永久失效等本地且不可自行恢复的问题；若只是暂时拒绝新流量，应优先表现为就绪失败。

尤其不要把权威数据库、远端设备或第三方服务的即时可达性直接绑定为存活失败。数据库抖动时，大量网关同时被重启，会放大重连、冷启动与数据库压力，形成级联故障。探针成功也只证明其覆盖的检查通过：它不证明设备 B 已 ACK，不证明消息已提交到权威数据库，更不证明端到端业务已完成。

### startup：为慢初始化建立保护窗口

### startup：为慢初始化建立保护窗口

长连接网关启动时，常需完成配置加载、证书读取、监听端口绑定、连接池预热、路由表同步或本地状态恢复。若这些步骤尚未完成，`liveness` 过早失败可能触发重启循环，`readiness` 过早执行则会反复报告未就绪。`startup` 探针的作用是声明：**容器正在启动，但尚不应按常规存活与就绪规则处置。**

在 `startup` 首次成功前，Kubernetes 不会启用该容器的 `liveness` 与 `readiness` 探针。于是，启动阶段的失败只由 `startup` 自己累计；只要尚未达到失败阈值，容器仍获得继续初始化的机会。成功一次后，保护窗口结束，后续由存活探针判断进程是否失活、由就绪探针决定是否接收新流量。

可将最长允许初始化时间近似预算为：

\[
T_{\max} \approx initialDelaySeconds + failureThreshold \times periodSeconds
\]

更精确地说，还应预留每次检查的 `timeoutSeconds`、调度抖动和节点负载带来的误差。因此，若网关最坏情况下需要约 \(90\) 秒完成证书拉取与状态恢复，可设置较短检查周期、较大的失败阈值，例如每 \(5\) 秒检查一次、允许 \(24\) 次失败，并额外保留安全余量。

`startup` 检查应验证“启动前置条件已满足”，例如进程已监听管理端口、关键配置已装载、必要本地索引已建立；不宜等待下游设备 ACK，也不应把“权威数据库已完成某笔提交”作为启动成功条件。否则短暂的外部依赖波动会把正常启动误判为不可恢复故障，造成不必要的反复重启。

### readiness：摘除新流量而非终止容器

### readiness：摘除新流量而非终止容器

`readiness` 的职责是回答：**此 Pod 是否还应接收新的常规请求或新建连接？** 当 readiness 探针失败时，Kubernetes 会将该 Pod 标记为未就绪，并将其从引用该 Pod 的常规 `Service` 的可选后端端点中移除。后续经由 Service 负载均衡的新请求，通常不再被分配到它。

这不是“杀死实例”：

- 容器仍然运行，进程不会因 readiness 失败而被 Kubernetes 自动重启；
- 已建立的 TCP、WebSocket、HTTP/2 或其他长连接不会因为端点摘除而被内核立即断开；
- 已经路由到该 Pod 的在途请求，也不因 readiness 状态变化而天然取消；
- 只有新的、经 Service 选择后端的流量会被逐步避开。

因此，长连接网关可以在准备下线时先让 readiness 失败：停止接纳新连接、新会话或新分片任务，同时保留存量连接的服务窗口。随后由应用主动执行摘流逻辑，例如发送“服务器维护中”的协议通知、拒绝新的升级请求、迁移可迁移会话，并等待连接自然结束或达到宽限期。

需要注意“通常”不等于绝对即时。端点更新需要经过控制面、节点代理和负载均衡组件传播；客户端连接池、DNS 缓存、外部负载均衡器或绕过 Service 直接访问 Pod 的流量，也可能继续到达该实例。应用本身仍应维护一个明确的 `draining` 状态，在入口处拒绝新工作，而不能只依赖 readiness。

readiness 证明的是“适合接收新流量”，不证明存量连接已经排空，更不证明远端设备已 ACK，或消息已提交到权威数据库。摘流完成必须由连接数、在途任务数与业务确认状态共同判定。

### liveness：重启机制与级联风险

### liveness：重启机制与级联风险

`liveness` 与 `readiness` 都会返回成功或失败，但失败后的控制后果完全不同：

| 探针 | 失败后的主要动作 | 适合回答的问题 |
|---|---|---|
| 就绪检测 | 将 Pod 从常规 `Service` 后端移出，不再接收新流量 | “现在能否安全接新连接？” |
| 存活检测 | 连续失败达到阈值后，kubelet 重启容器 | “进程是否已卡死、不可自行恢复？” |

因此，数据库不可达通常应首先影响 `readiness`，而不是直接影响 `liveness`。网关失去权威数据库连接时，可能无法鉴权、写入状态或确认业务消息；此时摘除新流量是合理的。但进程本身可能仍在运行，既能维持已有长连接，也能等待数据库恢复。若把“数据库查询成功”纳入 `liveness`，一次数据库抖动会让大量网关同时判死。

典型级联路径是：

1. 数据库延迟升高或连接池耗尽；
2. 每个网关的 `liveness` 查询超时；
3. 多个 Pod 在失败阈值后被同时重启；
4. 重启后的 Pod 重新建连、预热缓存、恢复会话，并再次冲击数据库；
5. 数据库负载进一步升高，更多实例继续重启。

这会把一个外部依赖故障放大为网关层的容量故障。更稳妥的划分是：`liveness` 仅检查事件循环、关键线程、内部死锁或长期无响应等“必须重启才能恢复”的状态；`readiness` 检查是否具备接收新流量的必要依赖。即使探针成功，也只证明其检查项通过，不证明设备 B 已 ACK，更不证明权威数据库已完成提交。

### 探针通过不等于消息已被确认

### 探针通过不等于消息已被确认

未来的 IM 网关中，同一条消息可能经历多个彼此独立的状态：

1. **Pod Ready**：`readiness` 通过，说明该 Pod 可以被 Service 选入新流量后端；它通常只证明进程、监听端口、必要本地依赖和初始化状态可用。
2. **连接可服务**：网关已经认证用户、建立会话，并拥有到 B 设备的有效长连接或可路由通道。这证明“可以尝试投递”，不证明对端已收到。
3. **B 设备 ACK**：B 客户端返回与消息 ID 对应的确认，证明该设备协议栈已接收并处理到指定阶段；设备断网、ACK 丢失或多端登录都会使其与实际展示状态不完全等价。
4. **权威数据库提交**：消息、投递任务或确认状态已提交到权威存储，故障恢复后仍可查询和重试。这是服务端可恢复语义的重要证据，但仍不必然表示 B 已读。
5. **当前 S2 状态**：若消息经由 S2 实例持有的连接发送，还需区分“消息当前在 S2 内存队列中”“S2 已写入 socket”“S2 收到 B 的 ACK”。前两者都可能因 S2 重启而失去后续证据。

因此，探针通过最多说明“该实例适合承接某类流量”。它不能证明 B 设备 ACK，更不能替代权威数据库提交。对外返回“已送达”前，应明确采用的证据等级；对内摘流时，则应先令 `readiness` 失败停止新连接，再按连接、队列、ACK 和持久化状态分别完成迁移或补偿。

> **要点** — startup保护初始化，readiness控制新流量，liveness触发重启；三者都不能证明业务消息已获设备确认或权威提交。

长连接网关退出不是“收到信号就关闭”，而是一场受总预算约束、控制面与应用面并行协作的摘流过程。

### 先把40秒终止窗口算清楚

### 先把40秒终止窗口算清楚

`terminationGracePeriodSeconds: 40` 不是“应用可排空 40 秒”，而是 Pod 终止流程的**总预算**。从终止开始计时，`preStop`、等待钩子结束、发送 `SIGTERM`、应用停止接入与排空既有长连接，都共享这一只总时钟；到期仍未退出，容器会收到 `SIGKILL`。

可将预算先写成：

\[
40\text{s}=5\text{s（preStop）}+30\text{s（应用排空）}+5\text{s（安全余量）}
\]

其中：

- `preStop` 至多占用 5 秒；它结束后才会向容器主进程发送 `SIGTERM`。
- 应用收到 `SIGTERM` 后，应立即进入“拒绝新接入、保留既有连接”的排空状态，并在约 30 秒内主动完成或关闭连接。
- 最后 5 秒不是可随意消耗的业务时间，而是为调度抖动、请求收尾、日志刷新、进程退出和信号传播预留的缓冲。

不要把 `preStop` 当作额外赠送时间：若钩子拖满 5 秒，应用实际可用排空窗口已经只剩约 35 秒；若再把全部时间都用于排空，就几乎必然面临 `SIGKILL` 截断连接的风险。设计退出流程时，应先按总窗口倒推每一步的最坏耗时，而非只配置一个看似充足的优雅退出时长。

### 终止流程中的时间线与强制边界

### 终止流程中的时间线与强制边界

`terminationGracePeriodSeconds=40s` 是 Pod 进入终止流程后的**总预算**，不是应用收到 `TERM` 后才开始计算的 40 秒。可将时间线写为：

$$
t_0\ (\text{开始终止})\rightarrow
t_0\sim t_0+5s\ (\text{preStop})\rightarrow
\text{TERM}\rightarrow
\text{应用排空}\rightarrow
t_0+40s\ (\text{SIGKILL})
$$

若 `preStop` 最多运行 5 秒，则应用实际可依赖的优雅退出窗口至多为：

$$
40s-5s=35s
$$

其中计划用 30 秒停止新连接、等待既有长连接完成、关闭监听与上游资源，并额外保留 5 秒余量。这个余量用于吸收信号调度、连接收尾、日志刷新、控制面传播等抖动；不能把 35 秒全部承诺给业务排空。

关键边界是：`preStop` 结束后才发送 `TERM`，但无论钩子、应用还是连接处于什么状态，一旦到达 $t_0+40s$，运行时会发送 `SIGKILL`，进程无法再清理状态。因此应用应在收到 `TERM` 后立即拒绝新接入，并以小于 30 秒的内部截止时间完成排空；不要假定 EndpointSlice 的摘除、探针变化与信号送达存在严格先后关系。

### EndpointSlice状态不等于立即断流

### EndpointSlice状态不等于立即断流

Pod 进入删除流程后，其对应的 EndpointSlice Endpoint 通常会出现 `terminating=true`。为兼容只识别旧语义的客户端，`ready` 往往同时变为 `false`：这意味着它不应再被当作“可接受新流量的普通后端”。

但 `ready=false` 不等于连接立刻消失。`serving` 可以仍为 `true`，表达该端点虽在终止中，却仍可能继续服务已有长连接、完成在途请求。支持该条件的代理或负载均衡器可据此区分“停止新接入”和“允许存量连接排空”。

更重要的是，控制面更新与进程退出是异步并行的：EndpointSlice 状态变更需要传播到各节点的代理；而 `preStop`、`SIGTERM` 及应用自身排空逻辑也会独立执行。不能假设“端点先摘除，再收到信号”，也不能假设“收到信号后所有代理已停止转发”。

因此，网关不能只依赖 `ready=false` 摘流。应用收到终止意图后也应主动关闭监听或拒绝新连接，并在排空窗口内维持已有会话；即使仍有少量迟到的新请求，也应能安全拒绝，而非无限延长退出。

### 网关必须主动停止新接入

### 网关必须主动停止新接入

不能把“摘流”完全交给 `EndpointSlice` 更新。终止开始后，控制面需要传播 Pod 的 `terminating` 状态，代理、负载均衡器和客户端连接池也各有刷新周期；在这段异步窗口内，旧路由、缓存的端点列表或已建立的上游连接仍可能把请求送到正在退出的网关。

因此，应用收到终止意图后应立即进入“只出不进”状态：

- **拒绝新的 HTTP 请求**：对尚未分配业务处理的请求快速返回 `503 Service Unavailable`，可附带 `Connection: close` 或重试提示；不要再启动可能持续数秒甚至数十秒的新任务。
- **拒绝新的 WebSocket 握手**：握手阶段直接拒绝，而不是先升级连接再关闭。否则一个终止瞬间建立的新长连接会挤占原有连接的排空预算。
- **保留既有连接排空**：已建立的 HTTP 长请求、WebSocket、流式响应仍可在排空窗口内继续完成；网关持续统计活跃连接数、在途请求数和剩余时间。
- **关闭本地接入能力**：若服务器支持，可停止 `accept` 新 TCP 连接，或让新连接在协议层快速失败；但不能依赖这一点替代应用层拒绝，因为复用连接上的新 HTTP 请求仍可能到达。

`EndpointSlice` 的 `ready=false` 表示通常不应再分配新流量，`serving=true` 则可表达端点仍在服务既有连接。但这些字段不是应用排空的精确时钟：信号到达、端点传播与数据面生效没有严格先后保证。网关必须把“停止新接入”做成自身状态机的一部分，才能确保 30 秒排空预算真正留给已经存在的连接。

### 用5秒、30秒、5秒审查退出方案

### 用5秒、30秒、5秒审查退出方案

把 `terminationGracePeriodSeconds` 视为不可透支的总预算，而不是应用独享的排空时间：

\[
40\text{s}=5\text{s（preStop）}+30\text{s（排空）}+5\text{s（余量）}
\]

一个可审查的退出流程如下：

1. **0～5 秒：`preStop` 快速摘流。** `preStop` 最多执行 5 秒，用于标记实例为退出中、停止本地新接入、触发负载均衡摘除等；它不能等待全部连接结束。`preStop` 返回后，Kubernetes 才向容器发送 `SIGTERM`。
2. **5～35 秒：应用排空。** 收到 `SIGTERM` 后，网关立刻拒绝新的连接、请求或升级握手；已有长连接允许在 30 秒内自然结束，必要时发送协议级关闭通知。EndpointSlice 的 `ready` 通常会变为 `false`，但传播存在延迟，应用自身必须兜底拒绝新流量。
3. **35～40 秒：处理尾部与故障余量。** 为关闭日志、上报排空指标、处理少量延迟请求预留 5 秒。到 35 秒仍未排空的连接应主动关闭，而不能赌剩余时间；40 秒到期后可能收到 `SIGKILL`，清理逻辑不再可靠。

监控应至少记录：终止开始时间、`preStop` 耗时、`SIGTERM` 到达时间、存量连接数、拒绝新连接数、强制关闭数及退出码。若排空长期超时，降级策略应明确：缩短长连接最大寿命、提前发送关闭帧、限制重试，或提高预算；不能仅把 `terminationGracePeriodSeconds` 无限加长。

> **要点** — 终止宽限期包含preStop；Endpoint传播并非精确屏障，网关必须自主拒绝新连接并在预算内完成排空。

长连接网关退出时，优雅关停不等于调用一次 Shutdown：普通 HTTP、WebSocket、消息确认与跨 Pod 恢复必须分别处理。

### Shutdown 的边界：HTTP 已停，长连接未必已退

### Shutdown 的边界：HTTP 已停，长连接未必已退

`http.Server.Shutdown(ctx)` 是 HTTP 服务的优雅停止入口，但它的“优雅”有明确边界：

- 它会关闭 `listener`，因此不再接受新的 TCP/HTTP 请求；
- 它会关闭空闲的 HTTP keep-alive 连接；
- 它会等待正在执行的普通 HTTP handler 返回，直到 `ctx` 到期；
- 它不会主动等待、关闭或统计已经被 `Hijack` 的连接。

WebSocket 常经由 `http.Hijacker` 完成协议升级。升级后，该连接已脱离 `http.Server` 对普通 HTTP 连接状态的管理：它不再是可被 `Shutdown` 关闭的 idle HTTP 连接，也不会被 `Shutdown` 的等待逻辑计入。

因此，下面的流程并不充分：

1. 收到终止信号；
2. 调用 `server.Shutdown(ctx)`；
3. `Shutdown` 返回；
4. 进程退出。

此时监听端口可能已经停止服务，但旧 WebSocket 仍可能存活；若进程随后被强制终止，客户端看到的将是无预警断连，尚未完成的消息确认、写缓冲或在途任务也可能丢失。

网关应把长连接视为独立生命周期：升级成功时登记连接，摘流时先停止新连接与新业务进入，再向已登记连接发送关闭通知，例如 WebSocket close frame 或“服务迁移中”控制消息；随后等待连接主动退出、在途任务完成，直到应用级截止时间。期限届满后，才关闭剩余连接并退出进程。

换言之，`Shutdown` 负责“HTTP 不再进来”，连接注册表与应用级协调才负责“长连接真正退场”。

### 连接注册表：为 WebSocket 建立可控退出通道

### 连接注册表：为 WebSocket 建立可控退出通道

`http.Server.Shutdown(ctx)` 会停止监听新连接，并等待普通 HTTP 请求收尾；但已被 `Hijack` 的 WebSocket 通常已脱离 `http.Server` 的连接管理。若网关只调用 `Shutdown`，进程仍可能因 WebSocket 读写协程、消息处理协程或底层连接而无法按预期摘流，或在强制退出时直接丢弃在途工作。

因此，应用应维护自己的连接注册表。每个成功升级的 WebSocket 以唯一连接标识注册，记录至少包括：`conn`、用户/设备标识、取消函数、最后活跃时间、在途任务计数及关闭状态。注册与注销必须成对出现，并受互斥锁或并发安全容器保护：

- 升级成功后注册连接；任何握手失败、读循环退出、写失败都进入统一注销路径。
- 为每条连接创建 `context.CancelFunc`，使业务处理协程能收到“停止接收新工作”的通知。
- 写关闭帧应由单一写协程串行执行，避免关闭帧与业务消息并发写入同一 WebSocket。
- 注册表不仅是“连接列表”，还是关停协调点：它能广播摘流状态、拒绝新消息、等待存量任务结束。

一个可控的关停链路可按如下顺序推导：

1. **标记实例为摘流中**：就绪探针转为失败，负载均衡器不再分配新 HTTP/WebSocket 握手；应用入口也拒绝新的升级请求。
2. **停止普通 HTTP 接收**：调用 `Shutdown`，给短请求有限完成时间。
3. **冻结 WebSocket 新工作**：向注册表广播关闭通知，连接读循环不再投递新的业务任务；已取出的消息可选择完成、回滚或明确标记为待重试。
4. **发送关闭帧**：例如以 `1001` 表示服务端正在离开，并携带简短原因；随后停止读写循环，避免客户端继续发送数据却被误认为已受理。
5. **等待在途协程**：用 `WaitGroup` 或任务计数等待已开始的处理、必要的确认发送与审计落盘完成。
6. **到达总截止时间后强制关闭**：对仍未退出的连接关闭底层 `conn`，取消其上下文，并记录未完成任务，以便后续恢复或补偿。

关键是设置**全局关停期限**，而不是为每条连接无限等待。可将总预算设为 $T$，其中关闭通知、在途处理和强制清理共享同一截止时间；到期后宁可留下可观测的“结果未知”记录，也不能让旧 Pod 永久阻塞发布。

### 在途消息：响应丢失不等于发送失败

### 在途消息：响应丢失不等于发送失败

设设备 A 通过 WebSocket 向网关发送消息 `m-a`：

1. A 发送 `m-a`，网关 S1 已收到并开始处理；
2. S1 将消息转交给下游，或已写入某个业务系统；
3. S1 正准备返回“已受理”响应时退出，连接断开；
4. A 没有收到响应，于是只知道：`m-a` 的结果未知。

这里最危险的误判是把“未收到响应”等同于“发送失败”。实际上，至少存在三种结果：

- S1 尚未处理 `m-a`：重试通常安全；
- S1 已接受但未持久化：重试可能得到不同结果；
- S1 已完成业务提交，只是响应丢失：重试可能造成重复扣款、重复指令或重复通知。

若 A 重连到 S2，S2 的本地内存并不知道 S1 看过 `m-a`。因此，S2 不能仅凭“本机未见过该消息”就认定它是新请求；更不能把本地连接注册表、内存去重表当作跨 Pod 的一致性依据。

客户端应为每条消息携带稳定的消息标识，例如 `message_id=m-a`，并将重试语义表述为：“请确认 `m-a` 的最终状态”，而不是“再执行一次”。网关可返回：

- `已确认`：业务已提交；
- `处理中`：接受过请求，但尚无最终结果；
- `未找到`：当前权威记录中不存在；
- `冲突`：同一标识对应的载荷不一致。

不过，S2 返回 `409` 也不自动证明重复成立：它只能说明 S2 或其依赖系统观察到了冲突。真正可恢复的确认，仍需由未来的权威状态 S3 持久化 `m-a` 的处理结果，并在设备 B 的业务 ACK、下游回执或事务记录中另行验证。网关退出时应尽量通知在途请求失败或未知；客户端则必须把断连后的消息视为“需要查询或幂等重试”，而非简单重发。

### 跨 Pod 恢复：S2 的内存不能成为确认依据

### 跨 Pod 恢复：S2 的内存不能成为确认依据

设客户端 A 向网关发送消息 `m-a`，S2 已将其转发给设备 B，但响应在网络中丢失。此时 A 重试，真正的问题不是“是否收到过请求”，而是“哪一种证据足以证明消息已被处理”。

| 证据位置 | 能证明什么 | 新 Pod 能否读取 | 重试时的结论 |
|---|---|---:|---|
| S2 本地内存去重表 | S2 进程曾见过 `m-a` | 否 | 仅在仍命中同一 S2 时可返回重复 `409` |
| S3 权威记录 | 系统持久确认过 `m-a` 的状态 | 是 | 任意 Pod 都可一致判重、恢复结果 |
| B 设备 ACK | B 实际接收或处理了消息 | 取决于是否被可靠持久化 | 可证明投递/处理，但不能由 S2 内存替代 |

S2 的内存去重适合抑制短时间、同进程内的重复提交：例如 `map[messageID]status`。但 Pod 重启、扩缩容、负载均衡漂移后，A 的重试可能到达 S4；S4 没有 S2 的内存，自然不知道 `m-a` 曾经出现过，因而不会“自动”返回 `409`，甚至可能再次向 B 投递。

因此，`409` 不是网络层重试天然产生的语义，而是某个**共享且可信的状态源**支持的业务结论。未来若引入 S3，记录至少应包含消息标识、状态、结果摘要与期限，例如：

`m-a: 已接受 → 已投递 → 已确认 / 失败 / 超时`

不过，S3 的“已接受”只能证明服务端记录了意图；“B 已处理”仍需 B 的 ACK，且 ACK 必须与消息标识绑定、可验证并写入权威记录。没有这条闭环时，响应丢失后的正确状态仍应是“结果未知”，而不是武断地判定成功、重复或失败。

### 把关闭期限落到执行顺序

### 把关闭期限落到执行顺序

关闭期限不是一个最后才检查的超时，而应拆成按顺序消费的预算。设总期限为 $T$，网关收到 `SIGTERM` 后立即进入“摘流”状态：就绪探针返回失败，使负载均衡器停止分配新请求；同时应用层拒绝新的升级连接、新消息和新任务。不要先调用 `Shutdown` 再改业务开关，否则短暂窗口内仍可能接收 WebSocket 或创建后台任务。

推荐顺序如下：

1. **摘流与冻结入口**：标记 `draining=true`，就绪探针失败；HTTP 处理器、WebSocket 首帧校验和消息入口统一返回“服务关闭中”。预留一小段传播时间，让负载均衡器、服务发现缓存生效。
2. **排空普通 HTTP**：调用 `http.Server.Shutdown(ctx)`，它会停止 listener，并等待普通 HTTP 的活动请求与空闲连接结束；但它**不会等待 hijacked 连接**，因此不能把 WebSocket 排空寄托于此调用。
3. **通知 WebSocket**：从应用维护的连接注册表取出连接，发送“服务器维护/请重连”控制消息或 Close 帧，并停止其读取循环继续派发新任务。注册表应支持并发注销，避免关闭期间遍历已失效连接。
4. **等待在途任务**：以 `WaitGroup`、计数器或任务注册表等待已开始的消息处理、确认发送、持久化等操作完成。每项任务必须接受 `context`，到达自己的子期限后主动取消，而非无限等待外部依赖。
5. **强制收尾**：总期限临近时，关闭仍存活的 WebSocket、取消剩余任务、关闭下游客户端；期限耗尽后进程退出，由编排系统接管最终终止。

可将总预算划分为：摘流传播 $t_1$、HTTP 排空 $t_2$、长连接通知与任务完成 $t_3$、强制收尾余量 $t_4$，满足 $t_1+t_2+t_3+t_4\le T$。所有阶段共享同一个截止时间，而不是每一步各自再等 $T$；否则实际退出时间会远超平台给予的终止宽限期。

> **要点** — Shutdown 只覆盖普通 HTTP 的一部分；长连接排空与消息确认必须由应用状态、期限和权威证据共同保证。

长连接网关的安全退出，不是“停止进程”而是按控制面摘流、按协议排空、按业务恢复的协同过程。

### 三类探针：健康信号不可混用

### 三类探针：健康信号不可混用

探针回答的不是同一个问题，错误复用会把局部故障放大为全站断连：

- **启动探针**：判断进程是否完成冷启动，如加载配置、绑定端口、建立必要的本地状态。启动期间失败应允许较长容忍时间；它控制的是“是否尚未启动完成”，避免存活探针过早杀死慢启动实例。
- **就绪探针**：判断实例**现在能否接收新连接和新请求**。它直接影响负载均衡端点：摘流、发布、滚动更新时应先变为未就绪，使旧 Pod 不再获得新的 WebSocket 握手或升级请求。
- **存活探针**：判断进程是否已不可恢复地卡死，例如事件循环停转、死锁、持续无响应。失败后编排系统会重启容器，因此它控制的是“是否应被强制重建”。

存活探针不应把数据库可达性作为判定条件。数据库短暂抖动、连接池耗尽或网络分区时，网关进程通常仍在运行，且已有 WebSocket 连接可能仍能收发心跳、读取缓存或等待后端恢复；若存活探针因数据库失败，所有网关会被同时判死并反复重启。重启又会关闭现存长连接、增加重连和数据库建连压力，最终形成“数据库越慢—重启越多—用户掉线越多”的重启风暴。

数据库依赖应主要进入就绪判定，或采用降级策略：停止接收需要数据库的新会话，但保留已有会话及可恢复能力。存活探针则只检查进程自身是否真正失去执行能力。

### 就绪摘流：从Ready到EndpointSlice

### 就绪摘流：从 Ready 到 EndpointSlice

安全摘流的第一步不是终止进程，而是先让旧 Pod **不再成为新流量的候选端点**。其传播链路可概括为：

`readinessProbe 失败 → Pod Ready=False → EndpointSlice 更新 → 负载均衡停止选择该端点`

若就绪探针始终返回成功，旧 Pod 即使已收到终止信号、正在等待 WebSocket 排空，仍保持 `Ready=True`。控制面会继续把它发布到 Service 对应的 EndpointSlice；kube-proxy、云负载均衡或服务网格仍可能将新的 HTTP 请求、TCP 连接或 WebSocket 握手导向该 Pod。结果是：旧连接尚未排空，新连接又持续进入，摘流窗口永远无法收敛；最终到达宽限期后被强制杀死，用户看到的就是连接中断、握手失败或请求重试。

EndpointSlice 中与退出相关的条件可这样理解：

- `ready=true`：通常表示可接收常规新流量。
- `serving=true`：端点仍具备服务已有连接的能力，适合排空阶段保留。
- `terminating=true`：Pod 已进入终止流程，消费者应避免再将其作为新连接目标。

理想状态不是“进程退出时才变不健康”，而是在收到摘流指令或 `preStop` 开始时，先让 readiness 立即失败。随后等待 EndpointSlice 更新及各数据面同步，再维持 `serving` 所代表的存量连接处理能力。这样，新的客户端会被导向新 Pod，旧 Pod 只承担已建立的长连接，排空才有明确的结束条件。

### 终止预算：preStop不能吃光宽限期

### 终止预算：preStop不能吃光宽限期

设 Pod 的 `terminationGracePeriodSeconds` 为 $G$。收到终止信号后，网关并不会立刻“无人访问”：控制面需先传播端点变化，负载均衡器还可能保留旧连接；随后才是 HTTP 请求排空、WebSocket 协议收尾和进程退出。因此应按剩余时间倒推：

$$G \ge T_{\text{摘流传播}}+T_{\text{HTTP排空}}+T_{\text{WS收尾}}+T_{\text{进程退出}}+\Delta$$

其中 $\Delta$ 是调度抖动、长尾请求和观测误差的安全余量。`preStop` 的职责是尽快触发“拒绝新连接/摘除就绪端点”等动作，而不是机械地睡眠到接近宽限期上限。

例如宽限期为 40 秒，`preStop: sleep 40` 会占满整个预算。sleep 结束时 kubelet 已可直接发送 `SIGKILL`；应用即使刚收到 `SIGTERM`，也没有时间停止接收 HTTP 请求、等待在途响应完成，或向 WebSocket 客户端发送关闭帧并保存会话状态。用户看到的结果是页面请求偶发 `502`、上传或支付请求中断，长连接客户端则收到突兀断开并触发重连风暴。

更合理的顺序是：`preStop` 立即将 readiness 置为失败并启动摘流，短暂等待传播；进程收到终止信号后关闭监听器，HTTP 仅服务已有请求，WebSocket 发送关闭通知、拒绝新会话并在截止时间到达前主动结束。若 $G=40$ 秒，可将传播等待控制在数秒，把主要预算留给排空与收尾，并让应用内部截止时间早于 kubelet 的强杀时间。

### 协议排空：HTTP关停不等于长连接关停

### 协议排空：HTTP 关停不等于长连接关停

`http.Server.Shutdown(ctx)`的职责是停止接收新 HTTP 请求、关闭空闲连接，并等待正在处理的 HTTP 请求结束。它适合短请求的“完成即释放”模型，但 WebSocket 在升级后通常成为被劫持连接，不再受 HTTP 服务器的常规请求生命周期管理。

| 对象 | `Shutdown` 的典型行为 | 安全摘流所需行为 |
|---|---|---|
| 普通 HTTP 请求 | 拒绝新连接，等待请求返回 | 等待响应完成即可 |
| WebSocket | 不主动关闭，也不等待其业务会话结束 | 停止新建会话、通知客户端迁移、等待或主动收敛存量连接 |

因此，网关若只调用 `Shutdown`，它可能很快返回：监听端口已关闭，HTTP 请求也已清空，但仍在线的 WebSocket 并未被纳入等待集合。随后进程退出、容器终止或连接被内核回收，存量客户端会收到异常断开，而不是可理解的协议关闭。

用户表现通常是：聊天消息发送失败、实时行情停止更新、协作编辑短暂丢失状态；客户端若没有重连与恢复机制，还会表现为“页面看似正常但数据不再变化”。

正确顺序应是：先将就绪状态设为不可用以阻止新流量，再向 WebSocket 连接发送“服务迁移/即将关闭”的关闭帧或业务通知，拒绝新的升级请求，等待连接自然结束或到达排空期限，最后关闭剩余连接并退出。`Shutdown`只是 HTTP 层的一步，不能替代 WebSocket 会话管理。

### 业务恢复：连接断开后的消息确认

### 业务恢复：连接断开后的消息确认

Kubernetes 的 `readiness` 只表示 Pod 是否应被分配**新的网络请求**，不表示某条业务消息已送达、已落库或已在设备侧执行。若把“连接仍可建立”误当作“消息已确认”，网关重启、摘流或 WebSocket 中断时就会产生重复指令、状态丢失和用户界面假成功。

恢复路径应围绕可核对的业务事实设计：

- 客户端为每条命令分配稳定的 `messageId`，重连后携带会话标识、最后确认序号和未决消息列表；服务端按 `messageId` 去重，而非按连接或请求时间去重。
- 网关关闭前停止接收新业务帧，但允许存量连接在截止时间内完成确认；超时连接必须明确返回“结果未知”，不能伪造成功确认。
- 会话恢复后，客户端先执行当前 `S2` 核对：比较本地已确认序号、服务端权威状态及未决命令状态。存在缺口时拉取权威结果，而不是直接重放全部消息。
- 对涉及设备执行的命令，业务结果与设备结果分离记录。服务端已受理不等于设备已完成；设备离线、网关断连或回执丢失时，应通过后续设备回执、查询接口或补偿任务补齐最终结果。
- 用户侧应展示“处理中、已受理、已完成、结果待核对”等状态。连接断开后的真实用户结果应是可恢复、可追踪的等待，而不是静默失败或错误的“操作成功”。

> **要点** — 安全摘流要先停止接新流量，再在终止预算内分别排空HTTP与WebSocket，并依靠业务确认完成恢复。

滚动退出不是“收到终止信号就关闭”。长连接网关必须在控制面摘流、连接排空与业务恢复之间保留可核对的时间边界。

### 以时间线理解滚动退出

### 以时间线理解滚动退出

将一次滚动退出拆成可观测的 `t0—t4`，比假设“信号一到、流量立刻消失”更可靠：

- **t0：P1 进入终止态，端点开始更新。** 控制面可能将 P1 标记为 `Terminating`，服务端点、负载均衡目标或路由规则随之变化。但更新传播有延迟，P1 仍可能收到已在途请求或来自旧连接的新消息。
- **t1：执行 `preStop`，启动旧连接摘流。** 此阶段应先拒绝新建连接、停止注册为可选后端，并对既有长连接发送摘流提示或关闭信号。`preStop` 不是“已经没有流量”的证明，只是留出传播与客户端迁移窗口。
- **t2：应用收到 `TERM`，停止接纳新消息。** 进程应进入明确的排空模式：不再接收新的 HTTP 请求、不再创建 WebSocket 会话，并限制旧会话继续发起新的业务操作。
- **t3：按协议分别限时排空。** 普通 HTTP 等待在途请求完成；WebSocket 则等待会话主动迁移、确认关闭或达到业务定义的截止时间。两者不能共用“连接数归零”这一简单标准。
- **t4：正常退出或被强制终止；替代实例 P4 恢复 `Ready`。** 宽限期内排空完成则退出；超时仍存活可能被强杀。与此同时，P4 的就绪只表示其可接流，不表示 P1 的全部旧消息必然无损完成。

这些事件没有可跨环境承诺的固定先后：端点更新、`preStop`、`TERM`、客户端重连和 P4 就绪可能交叠。应以同一请求/会话 ID 的记录与 B 侧补拉结果核对摘流效果，而非声称零丢包或依赖单一时间顺序。

### 终止状态与端点可达性

### 终止状态与端点可达性

Pod 进入终止并不等于它立刻从所有转发路径消失。控制器、EndpointSlice、各节点代理与外部负载均衡器各自观察到变化的时间不同，因此应把“是否还能收到新流量”视为逐步收敛的结果，而非单一事件。

当删除请求触发时，Pod 会获得删除时间戳并进入 `Terminating`。与其关联的 EndpointSlice 端点通常会体现三类条件：

- `ready=false`：端点不应再作为常规新流量的候选。readiness 探针失败、应用主动切换为未就绪，或终止状态传播，都会推动这一结果。
- `terminating=true`：端点正在退出。支持该语义的消费者可据此避免建立新连接，同时保留对既有连接的更谨慎处理。
- `serving=true`：端点虽然终止中，但仍可能继续服务已有会话；它不表示应接收新连接，而是给排空留出可表达的状态。

可将新流量分配近似理解为：

$$
\text{新请求候选} \approx \text{ready=true} \land \neg \text{terminating}
$$

但这不是跨所有实现都严格成立的协议保证。旧版代理、云负载均衡器、缓存的端点列表，或已建立的四层连接，可能继续将少量流量送到该 Pod。因而网关应尽早让 readiness 失败，并在应用内部同时停止接受新消息、拒绝新的升级请求或新建会话。

`serving` 的价值在于区分“不可再分配”与“必须立即断开”：普通 HTTP 可在有限时间内完成在途请求；WebSocket 等长连接则需要发送关闭信号、等待客户端迁移，并在截止时间到达后主动断开。不要把 `ready=false` 误解为旧连接已排空，也不要假设 `terminating=true` 在所有数据面先于 `TERM` 生效。后续应通过同一实例 ID 的连接日志与指标补拉，并与控制面事件核对，确认摘流窗口内是否仍有新建连接或异常中断。

### preStop、宽限期与TERM预算

### preStop、宽限期与TERM预算

`preStop` 不是终止宽限期之外的“额外等待时间”。对 Pod 而言，删除开始后，`terminationGracePeriodSeconds` 即进入倒计时；`preStop`、`TERM` 后的应用排空、日志与状态收尾都要共同消耗这段预算。若钩子执行过久，应用实际收到 `TERM` 时已接近强杀边界，长连接便没有可预测的排空窗口。

可将总宽限期记为：

$$
G = T_{\text{preStop}} + T_{\text{TERM排空}} + T_{\text{收尾}} + M
$$

其中 $M$ 是调度抖动、控制面传播、进程响应和观测延迟的安全余量，而不是可被业务占满的时间。设计时应先确定允许的最大连接排空时长，再反推 `preStop` 上限，而非先写一个固定睡眠。

典型预算可分为：

- `preStop`：触发本地摘流，例如将健康检查转为未就绪、停止接受新连接，或通知应用进入 draining；它应短且可重复。
- `TERM` 后立即执行：应用停止拉取新消息、拒绝新的升级请求和新的 HTTP 工作；已有 WebSocket 不再接收新业务，只允许必要的确认、关闭帧或有限收尾。
- 排空窗口：普通 HTTP 等待在途请求完成；WebSocket 则设置独立截止时间，到期主动发送关闭帧并断开，不能无限等待客户端。
- 最后余量：刷新日志、提交最小状态、关闭监听器并退出。若超过 $G$，运行时可能发送 `KILL`，此时不应假设清理逻辑仍会执行。

例如宽限期为 60 秒时，可设 `preStop` 最多 5 秒、普通 HTTP 排空 15 秒、WebSocket 排空 30 秒、收尾与余量 10 秒。实际数值应依据连接时长分布和恢复能力校准；若业务无法承受 WebSocket 截止造成的中断，应依赖客户端重连、同 ID 去重与 B 端补拉核对，而不是无限延长 Pod 退出时间。

### HTTP与WebSocket分路排空

### HTTP与WebSocket分路排空

摘流后不能把所有连接按同一种规则处理。普通 HTTP 与 WebSocket 的生命周期、重试语义和客户端感知不同，应分别设置排空边界。

- **普通 HTTP：等待在途请求完成。** 网关停止接收新请求后，允许已进入应用的请求在有限窗口内返回。窗口应覆盖常见慢请求，但不能无限延长；到期仍未完成的请求可由代理或应用终止，并记录请求路径、耗时、状态码与终止原因。客户端应依赖超时、幂等键或重试机制恢复，而不是假定请求必然成功。

- **WebSocket：先停止接入，再引导迁移。** 现有会话可能持续数小时，不能仅靠“等待自然结束”。摘流阶段应拒绝新的升级握手或将其路由到健康副本；对存量会话发送业务级迁移通知或 WebSocket 关闭帧，说明重连地址、原因与截止时间。客户端收到通知后应建立新连接，并通过会话标识、最后消息序号或确认位补拉缺口。

- **限时关闭：为长连接设硬边界。** 到达 WebSocket 排空截止时间后，仍未迁移的连接必须主动关闭。关闭码、服务端实例标识、连接建立时间、最后收发消息序号应进入日志或指标，便于区分客户端未迁移、网络阻塞与应用处理卡住。

这里的目标是“可恢复地缩短旧实例承载时间”，不是承诺固定时序或零丢包。若消息可能在旧连接关闭附近丢失，客户端应以同一业务标识向新副本补拉，并与服务端确认的序号或游标核对；B 副本恢复后也应检查是否存在未确认消息，而非仅凭连接已重建就认定排空成功。

### 确认结果与业务恢复

### 确认结果与业务恢复

S2 的“恢复”不能只看新 Pod 已经 `Ready`。`Ready` 仅表示该实例满足接收流量的条件：探针通过、依赖可达、端口可服务；它不证明旧连接上最后一批业务消息已经送达、处理完成或得到权威确认。

应以同一业务消息 ID 建立核对链路：

- 网关记录消息 ID、接收时间、转发目标、连接 ID 与本地处理结果。
- 客户端或 B 端在重连后携带已确认游标、消息 ID 范围，或主动执行补拉。
- 对于退出窗口内状态不明的消息，不能仅因网关日志显示“已写入 socket”就判定成功；应以 B 端持久化记录、业务回执或可查询的权威结果为准。
- 若 B 端补拉结果显示未收到，则按幂等语义重投；若已收到但回执在摘流期间丢失，则补齐本地确认状态，避免重复执行业务副作用。

可将结果分为“已确认成功”“确认失败”“状态未知”三类。只有“状态未知”需要通过 B 端补拉或查询收敛；不要把连接关闭、`TERM` 到达或新实例 `Ready` 当作成功证据。

恢复完成的判据应是：关键消息 ID 的权威状态已核对，重试队列可继续推进，重复投递被下游幂等机制吸收。这样即使无法承诺固定退出顺序或零丢包，也能把退出期间的不确定性限定为可观测、可补拉、可恢复的业务状态。

> **要点** — 安全摘流依赖端点状态、终止预算和业务核对协同；Ready不等于消息确认，排空也不能承诺零丢包。

长连接网关安全摘流不能只看 Pod 是否退出；必须把镜像版本、探针状态、端点传播、连接排空与业务确认放入同一条证据链。

### 先固定版本与观察证据

### 先固定版本与观察证据

摘流前先回答一个基础问题：**正在接流的到底是哪一版二进制、带着什么配置、处于什么运行状态？** 仅记录镜像标签如 `v1.8.2` 不足以复现现场；标签可被覆盖，应固定部署对象实际使用的镜像 `digest`，并关联 Pod 名称、节点、启动时间、配置版本与变更单。

核对基线至少包括：

- **镜像证据**：容器运行时的完整镜像引用与 `sha256:...` digest，而非仅看 Deployment 清单中的 tag。
- **实际 Pod 配置**：`readinessProbe`、`livenessProbe`、`startupProbe` 的路径、端口、协议、初始延迟、周期、超时和失败阈值；同时确认优雅退出时是否有 `preStop`、终止宽限期及应用自己的停接流逻辑。
- **端点证据**：对应 EndpointSlice 中该 Pod 的 `ready`、`serving`、`terminating` 条件及其变化时间。`ready=false` 表示不应再承担新流量，但不等于现有连接已断；`serving=true` 可表示仍服务存量；`terminating=true` 则标识端点进入终止传播阶段。
- **运行时指标**：摘流前后的新建连接速率、活跃连接数、在途请求数、长连接会话数、拒绝数、队列长度、错误码与强制终止数。指标必须按实例和时间序列观察，不能只看汇总值。

特别要区分“探针返回成功”与“网关可安全承接或排空流量”。探针路径可能只是进程存活检查，未覆盖依赖可用性、连接接纳开关或业务会话状态。固定 OpenIM 的两段源码也只能说明局部实现，不能据此证明生产环境已配置正确探针、端点摘除和连接排空。

若现有观测只覆盖 6B、409、404、200 等业务结果，却没有拒绝、排队、连接存量和强杀缺口，应先补齐指标；在证据缺失期间，停止扩大发布或摘流范围。

### 三类探针的控制边界

### 三类探针的控制边界

`startupProbe`、`readinessProbe`、`livenessProbe` 都在“检查健康”，但控制对象完全不同；把它们混为一谈，常会导致网关尚未初始化就被重启，或仍有长连接时过早摘除、错误接流。

| 探针 | 控制边界 | 失败后的直接结果 | 不应承担的职责 |
|---|---|---|---|
| 启动探针 `startupProbe` | 容器是否完成冷启动 | 在成功前抑制存活、就绪探针；持续失败才重启容器 | 判断是否可对外承接业务 |
| 就绪探针 `readinessProbe` | Pod 是否应进入服务端点 | Pod 变为未就绪，通常从 `EndpointSlice` 的可用端点中撤出 | 修复死锁、触发容器重启 |
| 存活探针 `livenessProbe` | 进程是否已不可恢复 | 失败达到阈值后重启容器 | 表示发布已完成或连接已排空 |

启动较慢的 OpenIM 网关应使用启动探针覆盖配置加载、依赖建立、监听端口创建等阶段。只要启动探针尚未成功，Kubernetes 不应依据暂时不可用的健康接口执行存活重启；否则“慢启动”会被误判为“已卡死”。

就绪探针回答的是“**此刻能否接收新流量**”，而不是“进程是否活着”。摘流时，应先让就绪探针失败或由应用主动返回未就绪，使端点状态传播为不可接入；随后继续保留进程，处理既有 HTTP 请求、WebSocket 或其他长连接。若健康接口仅返回 `200`，却未检查监听是否完成、关键依赖是否可用、拒绝新会话开关是否生效，则该 `200` 不能证明业务可用。

存活探针必须保守：它适合识别事件循环永久阻塞、无法响应管理接口等不可恢复故障。排空期间若因连接数高、下游暂不可达或主动拒绝新请求而让存活探针失败，会直接强杀容器，绕过优雅退出与在途连接保护。

因此，探针证据至少应说明：各探针的路径、阈值与失败动作；就绪失败后端点撤除的实际观测；以及排空阶段存活探针不会误触发。仅有两段 OpenIM 源码，不能证明这些 Kubernetes 配置和运行时行为已经成立。

### EndpointSlice 的终止信号

### EndpointSlice 的终止信号

`EndpointSlice` 不只是“后端地址列表”，其 `conditions` 记录端点是否应承接新流量、是否仍可服务，以及是否已进入终止过程。对长连接网关而言，三个字段必须联合理解：

- `ready`：端点是否可被常规负载均衡器选中。通常 `ready: true` 才表示可接收新建 HTTP 请求、新 WebSocket 或其他长连接。
- `serving`：端点是否仍具备服务能力。终止期间，即使不再接新连接，已有连接、在途请求仍可能需要继续由该端点处理。
- `terminating`：端点所属 Pod 是否已开始终止。该信号表明系统应进入摘流与排空观察，而非把 Pod 消失当作正常完成。

可将安全摘流抽象为以下状态迁移：

| 阶段 | ready | serving | terminating | 含义 |
|---|---:|---:|---:|---|
| 正常接流 | true | true | false | 接收新连接并服务存量连接 |
| 摘除新流量、排空存量 | false | true | true | 不应再建立新连接；已有连接允许完成或自然关闭 |
| 服务结束 | false | false | true | 已不再服务，应等待端点删除或容器退出 |

关键区别在于：`ready: false` 只说明“不应继续导入新流量”，不能证明存量连接已清零；`terminating: true` 只说明终止已开始，也不能证明排空成功。若网关已返回拒绝、排队或连接迁移失败，则即使 EndpointSlice 已完成更新，也应暂停继续发布。

因此，发布证据应同时覆盖 EndpointSlice 条件变化、负载均衡侧新连接下降、应用侧在途请求数与活跃连接数归零，以及最终是否发生超时强杀。仅凭 OpenIM 的两段源码，不能推出探针配置、端点传播时序或连接排空策略已经成立。

### 终止预算与连接排空

### 终止预算与连接排空

网关收到终止信号后，目标不是“尽快退出”，而是在 `terminationGracePeriodSeconds` 的预算内停止接新流量、完成必要在途处理并主动关闭长连接。可将预算拆为：

1. `preStop`：立即将实例切为拒绝新连接或仅返回维护响应，并触发摘流标记；不要在此阶段阻塞等待全部连接自然结束。
2. 端点传播：等待 `EndpointSlice` 中端点从 `ready=true` 变为不可接收新流量。`terminating=true` 表示正在终止；若 `serving=true`，实现仍可能允许既有连接继续服务。传播延迟必须计入总预算。
3. 排空窗口：HTTP 以在途请求数为准，等待请求完成或到达单请求超时；WebSocket 以活跃连接数为准，先发送业务下线通知或关闭帧，再给客户端重连到健康实例的时间。
4. 最后退出：排空截止后关闭监听器、取消后台任务并退出进程。

例如总宽限期为 60 秒，可预留 5 秒执行 `preStop`、10 秒等待端点摘除、40 秒排空、5 秒进程收尾。若排空超过宽限期，Kubernetes 会发送强制终止信号；此时 HTTP 在途请求可能中断，WebSocket 会被硬断，未确认的消息、会话状态或上传内容都可能丢失。

因此应同时观测“新请求拒绝数、HTTP 在途数、WebSocket 连接数、超时关闭数、强杀次数”。连接数归零不等于安全：还需确认端点已摘除、客户端已迁移、关键业务确认已完成。仅凭 OpenIM 的两段源码不能证明探针、`preStop`、端点传播或连接排空已经正确配置；缺少这些证据时，应停止发布或补齐拒绝/排队与排空验证。

### 以业务确认决定发布去留

### 以业务确认决定发布去留

S2 的结论不能仅写成“接口可访问”，而应按结果分层决定是否继续发布。当前观测到 `6B、409、404、200` 时，先区分它们代表的是业务预期、并发保护，还是路由与版本缺陷：

- `200`：请求完成，仍需核对返回内容、写入结果或长连接会话状态是否符合预期。
- `409`：若对应幂等键重复、资源版本冲突或已有任务占用，且符合设计，可记为“受控业务结果”；若由新版本引入的异常冲突，则不能放行。
- `404`：必须确认是测试对象本不存在，还是新旧路由、服务发现、鉴权路径或接口版本不一致。后者属于发布阻断项。
- `6B`：应保留其原始业务含义、响应体、触发条件与关联日志；未能解释的状态码不能被归入成功。

未来进入 S3/B 时，应以权威业务结果和设备侧实际状态形成闭环：控制面返回成功不等于设备已生效，设备离线、延迟执行、状态回报缺失都应单独标注。建议按“接口响应—异步任务—设备回执—最终状态查询”逐层确认，并记录请求标识以便追溯。

发布继续的前提是：关键路径结果符合预期，异常结果均有可验证解释，且 S3/B 的权威与设备证据没有矛盾。只要出现新增拒绝、请求排队、成功率下降，或缺少设备回执、状态查询、原始日志等证据缺口，就应停止扩大发布；维持当前范围、补齐证据并定位原因后，再决定继续、回滚或修复后重试。

> **要点** — 安全摘流的完成标志是端点、连接与业务结果共同收敛，而非 Pod 退出或探针单项通过。

长连接网关安全退出不是“杀掉进程”，而是先停止接新流量、再排空存量连接，并让未完成的业务状态能够恢复。

### 三类探针：分别回答三种控制问题

### 三类探针：分别回答三种控制问题

三类探针不是同一个健康检查的不同频率，而是回答三个不同问题：

- **启动探针**：**进程是否完成启动，值得开始检查？**  
  适合加载配置、预热缓存、建立证书或依赖连接较慢的网关。启动探针未成功前，Kubernetes 不执行存活与就绪检查，避免冷启动被误判为故障而反复重启。

- **就绪探针**：**现在能否接收新流量？**  
  它决定 Pod 是否进入 Service 的可选后端。长连接网关进入摘流时，应先让就绪探针失败，使 Endpoint 从正常可路由集合中移除；已建立的 TCP/WebSocket 连接通常仍由本 Pod 继续处理。就绪失败不应触发重启。

- **存活探针**：**进程是否已经不可自恢复，必须重启？**  
  只检测真正的致命卡死，例如事件循环长期无响应、内部工作线程全部阻塞。不要把短暂的下游超时、数据库抖动、连接池暂满直接作为存活失败条件。

错误的边界会放大事故：若把依赖服务失败写入存活探针，所有网关会同时被重启；重启又丢失连接、触发客户端重连和下游补偿，形成级联雪崩。相反，下游不可用但网关仍能维持已有 WebSocket、返回可控错误或执行本地排队时，应优先使**就绪探针失败**以停止接入新连接，而非让**存活探针失败**。

### 从摘流到退出：40秒终止预算的纸上推导

### 从摘流到退出：40 秒终止预算的纸上推导

设 Pod 的 `terminationGracePeriodSeconds=40`。这 40 秒不是“业务排空后额外再给 40 秒”，而是从 Kubernetes 向容器发送终止信号、开始执行 `preStop` 起就已经开始倒计时。可先做如下纸上预算：

$$40\text{s}=5\text{s（摘流）}+30\text{s（连接排空）}+5\text{s（进程收尾）}$$

- **前 5 秒：`preStop` 摘流。** `preStop` 的目标是让网关先拒绝新连接：关闭新 WebSocket/HTTP Upgrade 接入、停止从服务发现或负载均衡器领取新流量，并等待 Endpoint 传播。它不是独立计时器；若钩子实际执行 8 秒，后续排空与收尾只剩 32 秒。
- **中间 30 秒：存量连接排空。** 进程收到 `SIGTERM` 后进入 `Shutdown`：不再接受新连接，但保留已有 WebSocket、长轮询或正在响应的请求。可向客户端发送“服务即将迁移”的关闭帧或重连提示；到期仍未结束的连接必须主动关闭，不能无限等待。
- **最后 5 秒：进程收尾。** 停止后台任务，提交必要状态、刷新日志与指标、关闭监听器和依赖连接，然后退出。若 40 秒耗尽进程仍在运行，运行时可能发送 `SIGKILL`，此时没有机会执行清理逻辑。

关键是把“摘流完成”与“连接清空”分开验证。Pod 进入终止态后，Endpoint 通常会被标记为 `terminating`，新流量应逐步绕开它；但传播存在延迟，因此 `preStop` 不能只写 `sleep 5`，应用本身也必须在关闭态拒绝新会话。反过来，若过早退出，仍可能有刚被转发过来的连接失败。

预算还应覆盖最长业务尾部：若 WebSocket 允许 30 秒内完成一次状态确认，则 30 秒排空只是上限，不是承诺。超时连接应依赖可恢复状态在新 Pod 上续接，而非阻塞旧 Pod 永久存活。

### EndpointSlice状态：终止不等于立即不可服务

### EndpointSlice 状态：终止不等于立即不可服务

Pod 开始退出时，EndpointSlice 不会简单地把它立刻从世界中“删除”。对长连接网关而言，更关键的是区分三个条件：

- `ready`：端点是否应接收**新的**常规流量。开始终止后通常变为 `false`，负载均衡器据此停止向它分配新连接。
- `terminating`：端点是否正处于终止过程。`true` 表示它已进入摘流、排空或清理阶段，而非已经失效。
- `serving`：端点是否仍可继续服务。终止中的 Pod 可以是 `terminating=true` 且 `serving=true`：不接新客，但维持既有 WebSocket、HTTP/2 流或会话收尾。

因此，安全摘流的理想状态不是“终止即不可达”，而是：

`ready=false → 停止新连接 → serving=true → 排空存量连接 → serving=false → 进程退出`

这也解释了为什么删除 Pod 后，少量旧连接仍可能持续存在：它们已在摘流前建立，不应因控制面更新而被粗暴中断。网关收到 `SIGTERM` 后应进入 Shutdown 模式：关闭监听器或拒绝新的升级请求，向已有 WebSocket 发送关闭帧、等待业务完成，并在 `preStop` 与 `terminationGracePeriodSeconds` 的预算内排空。

要警惕把 `livenessProbe` 失败当作摘流手段。存活探针失败会触发重启，可能跳过有序排空，并在多副本同时误判时造成级联断连。摘流应主要依赖终止流程、`readinessProbe` 和 EndpointSlice 状态；存量状态则必须可恢复，例如连接迁移失败后由客户端重连，S2 跨 Pod 状态从共享存储或设备侧补拉。

### Go网关关停：HTTP排空与WebSocket收口分治

### Go网关关停：HTTP排空与 WebSocket 收口分治

`http.Server.Shutdown(ctx)` 只会关闭监听器、拒绝新的 HTTP 连接，并等待正在执行的 HTTP 请求返回；它不是“关闭所有 TCP 连接”的通用开关。对短请求而言，推荐顺序是：

1. 收到 `SIGTERM` 后立刻将就绪探针置失败，摘除 Service 后端；
2. 在 `preStop` 中留出传播窗口，避免仍有旧连接或缓存中的路由继续送入；
3. 调用 `Shutdown`，等待普通 HTTP 请求完成；
4. 到达截止时间后由上下文取消，必要时强制退出。

纸上可先预算总宽限期：`40s = 5s + 30s + 5s`。前 `5s` 用于就绪状态和 Endpoint 更新传播，中间 `30s` 留给 HTTP 排空与长连接收口，最后 `5s` 留给日志落盘、指标刷新及进程退出。注意：`preStop` 本身消耗 `terminationGracePeriodSeconds`，不是额外赠送的时间；若 `preStop` 睡眠 5 秒，应用实际可用排空时间会相应缩短。

WebSocket 升级后已脱离 HTTP 请求—响应生命周期，`Shutdown` 不会替业务优雅发送关闭帧，也不能保证会话状态完成同步。因此网关应单独维护连接注册表：进入关停后拒绝新升级、新会话创建；向存量连接发送“服务迁移/即将关闭”通知或 WebSocket Close 帧；在限定时间内允许客户端重连或完成必要确认；截止后主动关闭残留连接。

不要把 `liveness` 当摘流开关：若关停时让存活探针失败，Kubernetes 可能重启容器，形成“退出—重启—再退出”的级联。摘流应由 `readiness` 控制；`liveness` 仅表示进程是否卡死。对于跨 Pod 的会话状态，不能假设连接仍会回到原 Pod：设备重连后应能从共享状态、事件日志或设备侧补拉中恢复未完成状态。

### 业务恢复校验：Ready之后仍要确认消息结果

### 业务恢复校验：Ready之后仍要确认消息结果

`Ready=True` 只表示该 Pod 可以进入 Service 的可选后端集合：进程存活、监听端口可达、基础依赖大致正常。它不等价于“此前断开的 WebSocket 已恢复”“消息已送达设备”“业务状态已经确认”。

应区分三层状态：

| 层次 | 回答的问题 | 不能证明什么 |
|---|---|---|
| Kubernetes 就绪状态 | 现在能否接收新连接 | 存量会话、消息确认是否恢复 |
| 当前 S2 跨 Pod 状态 | 连接迁移后，其他 Pod 能否找到会话、路由和待确认消息 | 设备是否实际收到并确认 |
| 权威业务状态与设备补拉 | 消息最终结果是否可追溯、可重放、可确认 | 瞬时网络连接一定仍在 |

网关重启、摘流或会话漂移后，S2 中的临时跨 Pod 状态可用于快速恢复：例如 `userId -> gatewayId` 路由、连接代次、未确认消息索引。但 S2 不是最终事实来源；它可能过期、丢失，或仍指向已退出的网关。权威存储应记录消息标识、目标设备、投递状态、确认序号与幂等键。

因此，设备重连后不应仅因网关 `Ready` 就认定恢复完成，而应携带最后确认游标或消息序号进行补拉：

1. 设备上报已确认的最大序号；
2. 服务端从权威状态查询缺口；
3. 按顺序重发未确认消息；
4. 设备以消息 ID 或幂等键去重；
5. 收到确认后再推进权威游标。

可将恢复判定写为：

$$\text{业务恢复}=\text{网关可接入}\land\text{会话可定位}\land\text{未确认消息可补拉}\land\text{确认可落库}$$

特别要避免把“网络已通”误判为“消息已确认”。`Ready` 是流量入口条件；S2 是短期协调加速器；权威状态加设备补拉，才是退出、迁移和重连后的结果闭环。

> **要点** — 安全摘流依赖正确探针、终止预算、端点语义与协议级排空；Ready只表示可接流量，不保证业务消息已落定。
