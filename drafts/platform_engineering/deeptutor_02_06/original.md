### 两类查询为何走向不同结构

### 两类查询为何走向不同结构

设消息有两种常见访问方式：

- 按唯一 `message_id` 精确找一条：`m-a`
- 在会话 `c-a` 中按序号找一段：`seq ∈ [2,5]`

它们看似都在“找消息”，但需要的索引性质不同。

哈希结构擅长把一个**完整键**直接映射到位置：

`hash(message_id) → m-a`

因此，已知 `message_id = m-a` 时，通常可快速定位。哈希表不必比较大小，也不关心 `m-a` 与 `m-b` 谁在前；键被打散后，只要能回到对应桶即可。这正适合等值条件：

`WHERE message_id = 'm-a'`

但范围条件要求“顺序”。查询：

`WHERE conversation_id = 'c-a' AND seq BETWEEN 2 AND 5`

不仅要找到 `seq=2`，还要继续得到 `3、4、5`。若键被哈希打散，`(c-a,2)`、`(c-a,3)`、`(c-a,4)` 可能落在完全不同的位置；哈希表无法自然回答“下一个序号在哪里”。即使逐个点查，也需要分别查四次，并且不利于连续翻页。

有序结构则按复合键排列：

`(c-a,1) < (c-a,2) < (c-a,3) < … < (c-b,1)`

于是先定位范围起点 `(c-a,2)`，再沿相邻记录顺序读取，直到超过 `(c-a,5)`。这正是树索引，尤其是 B+ 树，适合范围扫描的原因：它既能通过根、父节点逐层缩小搜索范围，也能在叶子层保留有序记录，方便连续读取。

简言之：**哈希回答“是不是这个键”，有序索引回答“从这里到那里有哪些键”。**

### 用c-a序号认识树的基本词汇

### 用 c-a 序号认识树的基本词汇

把会话 `c-a` 中消息的 `seq` 看成可比较的键。下面是一棵**二叉搜索树**：每个节点最多有两个孩子，并满足“左小右大”。

```text
            4
          /   \
         2     6
        / \   / \
       1   3 5   7
```

- `4` 是**根节点**：整棵树的入口，没有父节点。
- `2`、`6` 是 `4` 的**子节点**；反过来，`4` 是它们的**父节点**。
- `1`、`3`、`5`、`7` 没有子节点，称为**叶节点**。
- 从根向下看：
  - 第 0 层：`4`
  - 第 1 层：`2, 6`
  - 第 2 层：`1, 3, 5, 7`
- 树的**高度**是从根到最深叶节点的最长路径长度。若按边数计，这棵树高度为 $2$；若按层数计，则为 $3$，讨论时应说明口径。

二叉搜索树的关键不是“长得像树”，而是大小关系：对任一节点 $x$，左子树所有键都小于 $x$，右子树所有键都大于 $x$。因此查找 `seq=5` 时，可依次比较 `4 \rightarrow 6 \rightarrow 5`，不必检查全部七条消息。

若要找范围 `[2,5]`，树中的有序关系也能帮助跳过明显无关的部分：`1` 小于下界，`6、7` 大于上界。与哈希表擅长精确找到某个 `message_id` 不同，有序树保留了键的前后次序，这正是连续 `seq` 翻页所需要的信息。

### 按不变量查找、遍历与取范围

### 按不变量查找、遍历与取范围

先固定会话为 `c-a`，只把该会话内的 `seq` 放入二叉搜索树（BST）。手工构造：

```text
        4
      /   \
     2     6
    / \   / \
   1   3 5   7
```

BST 的核心不变量是：任一节点的**左子树键都更小，右子树键都更大**。例如根节点是 `4`；其左侧只能出现 `1、2、3`，右侧只能出现 `5、6、7`。这条规则决定了查找时不必逐个检查。

查找 `seq=5`：

1. 从根 `4` 开始，`5>4`，走向右孩子；
2. 到达 `6`，`5<6`，走向左孩子；
3. 到达 `5`，命中。

路径为 `4 → 6 → 5`。树较平衡时，每次比较都排除约一半候选，代价接近 $O(\log n)$；这不同于链表从头逐项走，也不同于哈希表只擅长“键是否恰好相等”。

若按“左子树→节点→右子树”进行**中序遍历**，输出为：

`1, 2, 3, 4, 5, 6, 7`

因此，BST 的中序结果天然有序。要取得范围 `seq ∈ [2,5]`，可沿树找到边界，并只保留区间内节点：

- `1<2`，不输出；
- 输出 `2、3、4、5`；
- `6>5`，其右侧更大，无须继续查看。

最终范围结果是 `2, 3, 4, 5`，可对应 SQL 中 `WHERE conversation_id='c-a' AND seq BETWEEN 2 AND 5` 的连续消息页。

### 退化、平衡与旋转的成本直觉

### 退化、平衡与旋转的成本直觉

把会话 `c-a` 的消息按 `seq` 依次插入二叉搜索树：`1,2,3,4,5`。若每个新键都大于已有键，插入路径会不断向右延伸：

`1 → 2 → 3 → 4 → 5`

这棵树虽然仍满足“左子树键更小、右子树键更大”，却已经退化成链表。查找 `seq=5` 必须比较 5 次；寻找范围 `[2,5]` 时，先定位起点也可能走完整条链。高度为 $n$，最坏查找、插入成本都是 $O(n)$，几乎失去树相对线性结构的优势。

若键被组织得较平衡，例如根为 `3`，左侧有 `1,2`，右侧有 `4,5`，树高约为 $\log_2 n$。查找 `5` 只需沿“`3 → 4 → 5`”下降；数据规模增长时，路径增长很慢。这里的“平衡”不是要求每层完全填满，而是避免某一侧长期比另一侧深得多。

旋转是纠正局部倾斜的工具。以右链中的局部结构为例：

`1 → 2 → 3`

可将 `2` 提到父位置，使 `1` 成为其左孩子、`3` 成为其右孩子。旋转改变的是父子关系，不改变中序遍历顺序；旋转前后读出的键仍是 `1,2,3`。因此，有序索引可以在保持 `seq` 排序语义的同时控制高度，使范围查询的“定位起点”不至于退化为逐条扫描。

### 从二叉树到B+树页索引

### 从二叉树到 B+树页索引

把索引想成按“页”组织的多路树，而不是每个键只分出左、右两个孩子的二叉树。若有 64 条消息键，假设每个叶页容纳 4 个复合键 `(conversation_id, seq)`，则需要 16 个叶页；再假设每个内部页能指向 4 个孩子：

- 叶层：16 页，保存全部键与 `message_id` 等记录定位信息；
- 中间层：4 页，每页管理 4 个叶页；
- 根页：1 页，管理这 4 个中间页。

因此，从根到叶只需经过约 3 层页面。相比之下，平衡二叉树处理 64 个键通常要经过约 6 次分支判断；真实磁盘或缓存系统更关心“访问多少页”，所以希望一个内部页容纳尽可能多的子指针，降低树高。

B+树的关键是：内部页只负责导航，所有完整键按序放在叶页，并且叶页之间相连。查询会话 `c-a` 中 `seq ∈ [2,5]` 时，先沿树找到 `(c-a,2)` 所在叶页，再顺着叶页连续读取直到超过 `(c-a,5)`；这不是对每条消息重新查找。

SQL 游标也可视为这个边界：上一页末尾是 `(c-a, 5)`，下一页使用“键大于该元组”的条件继续扫描。哈希索引适合精确查 `message_id = m-a`，却不能自然回答“下一个 `seq` 是什么”；复合有序索引则以点查能力换来连续范围、排序和稳定翻页能力。

> **要点** — 哈希擅长精确点查；按会话序号连续读取依赖保持顺序且高度受控的树形索引。

先用固定会话 c-a 的序号键构造二叉搜索树，建立“同会话内有序、跨会话需复合定位”的索引直觉。

### 从会话序号界定键的含义

### 从会话序号界定键的含义

构造索引前，先要回答：`seq` 到底在哪个范围内唯一？答案通常不是“全系统唯一”，而是“同一会话内唯一”。例如会话 `c-a` 中可出现序号 `4, 2, 6, 1, 3, 5, 7`；另一会话 `c-b` 也完全可能拥有 `seq=4`。因此，单独使用 `seq` 只能表达某个会话内部的顺序，不能直接定位全局唯一记录。

可以区分三类容易混淆的标识：

- **业务消息标识 `MessageID`**：用于业务语义，如订单消息、聊天消息或事件去重；其生成规则由应用决定。
- **传输序号 `seq`**：描述同一会话中的先后位置，常用于排序、补洞、确认或范围读取。
- **索引键**：数据库或树结构实际比较的键，必须覆盖查询所需的唯一性与排序范围。

若查询是“读取会话 `c-a` 中序号 $[2,6]$ 的消息”，合适的索引键应是复合键：

\[
(\text{SessionID}, \text{seq})
\]

比较时先比较 `SessionID`，会话相同再比较 `seq`。这样 `("c-a", 4)` 与 `("c-b", 4)` 是不同键，同时 `c-a` 内仍保持序号有序。

不要把业务 `MessageID`、TCP 序号和应用层 `seq` 默认视为同一概念。TCP 序号服务于字节流传输；业务消息标识服务于业务对象；索引键服务于存储定位。它们可能恰好相关，但应分别定义其作用域、唯一性和排序语义。

### 用 4、2、6、1、3、5、7 构造搜索树

### 用 4、2、6、1、3、5、7 构造搜索树

固定会话 `c-a` 后，把序号视为可比较的键，依次插入：

`4，2，6，1，3，5，7`

二叉搜索树的规则是：比当前节点小的键进入左子树，比当前节点大的键进入右子树。每次插入都从根开始比较，直到遇到空指针位置。

1. 插入 `4`：树为空，`4` 成为根节点。
2. 插入 `2`：`2 < 4`，成为 `4` 的左孩子。
3. 插入 `6`：`6 > 4`，成为 `4` 的右孩子。
4. 插入 `1`：`1 < 4`，再有 `1 < 2`，成为 `2` 的左孩子。
5. 插入 `3`：`3 < 4`，但 `3 > 2`，成为 `2` 的右孩子。
6. 插入 `5`：`5 > 4`，但 `5 < 6`，成为 `6` 的左孩子。
7. 插入 `7`：`7 > 4`，再有 `7 > 6`，成为 `6` 的右孩子。

所得结构为：

- 根节点：`4`
- `4` 的左、右孩子：`2`、`6`
- `2` 的左、右孩子：`1`、`3`
- `6` 的左、右孩子：`5`、`7`
- 叶节点：`1、3、5、7`

按层观察：

- 第 0 层：`4`
- 第 1 层：`2，6`
- 第 2 层：`1，3，5，7`

若根节点高度记为 0，这棵树高度为 2；若按节点数计路径高度，则为 3。它恰好是平衡的：左右子树规模与高度对称。后续查找键 `5` 时，会沿着 `4 → 6 → 5` 下降；若目标不存在，则最终会走到某个本应继续延伸、却为 `nil` 的左或右指针。

### 沿不变量查找：4→6→5

### 沿不变量查找：4→6→5

在固定会话 `c-a` 内，按 `4, 2, 6, 1, 3, 5, 7` 插入二叉搜索树后，每个节点始终满足：

- 左子树中的键都小于该节点键；
- 右子树中的键都大于该节点键。

查找键 `5` 时，不需要遍历整棵树，只需不断比较：

1. 根节点是 `4`：`5 > 4`，目标只能在右子树，走向 `6`。
2. 节点是 `6`：`5 < 6`，目标只能在左子树，走向 `5`。
3. 节点是 `5`：比较相等，查找成功。

因此路径为 `4 → 6 → 5`。每一步都利用“左小右大”排除另一半候选节点，这正是有序索引比线性扫描更有效的原因。

再查找不存在的键 `8`：

`4 → 6 → 7 → nil`

因为 `8 > 7`，应继续进入 `7` 的右孩子；但该指针为空，说明树中不存在键 `8`。`nil` 不是异常，而是查找失败的明确边界。

对应的静态节点结构可写为：

`type Node struct { Key int64; Left, Right *Node }`

这里的 `Key` 只表示当前 `c-a` 会话内的序号。若跨会话查找，不能假定不同会话的 `seq` 全局唯一；应先按会话定位，或使用“会话标识 + seq”的复合键。

### 重复序号与节点表示的边界

### 重复序号与节点表示的边界

前面的树只服务于固定会话 `c-a`：因此可把 `seq` 当作唯一键，直接比较大小。但这是一种教学前提，不应照搬到真实存储。

最简节点可写为：`type Node struct { Key int64; Left, Right *Node }`。其中 `Key` 只保存可排序的序号，`Left` 指向更小键，`Right` 指向更大键；查找走到 `nil`，表示该键不存在。它描述的是内存中的二叉搜索树形状，不包含磁盘页、并发控制、持久化、平衡调整或范围扫描优化。

若同一会话内出现重复 `seq`，必须先定义语义，不能悄悄插入左边或右边：

- **拒绝重复**：插入时发现 `Key == seq` 即返回错误。适合 `seq` 被业务规则保证唯一的场景。
- **覆盖已有值**：同一 `seq` 代表同一逻辑记录时，更新节点关联的数据，而非新增树节点。
- **使用复合键**：若一个 `seq` 可对应多条记录，应比较 `(SessionID, Seq, TieBreaker)`，其中 `TieBreaker` 可以是时间、递增写入号或记录标识。先比会话，再比序号，最后比消歧字段。

尤其不要把业务 `MessageID`、会话内应用序号与 TCP `seq` 混为同一种键：它们的生成者、唯一性范围、重传语义和排序目的都可能不同。示例树中的 `Key int64` 只是“某个已明确范围的有序键”的占位；真实索引应先写清键定义，再选择 BST、B+ 树或数据库索引实现。

### 从单会话树走向复合索引

### 从单会话树走向复合索引

前面的 BST 只存固定会话 `c-a` 的 `seq`，因此比较规则很简单：左子树键更小，右子树键更大。例如按 `4,2,6,1,3,5,7` 插入后，查找 `5` 沿 `4→6→5` 前进；若应走的孩子指针为 `nil`，便到达失败边界。

但 `seq` 的唯一性通常只在**同一会话内**成立。会话 `c-a` 的 `seq=5` 与会话 `c-b` 的 `seq=5` 可以同时存在，不能仅用 `Key int64` 将它们放入全局索引。此时需要把比较对象从单键升级为复合键：

\[
(\text{conversation\_id},\ \text{seq})
\]

采用字典序比较：先比较 `conversation_id`；只有会话相同时，才比较 `seq`。即：

- `(c-a, 7) < (c-b, 1)`，因为 `c-a < c-b`；
- `(c-a, 3) < (c-a, 5)`，因为会话相同且 `3 < 5`；
- 两个分量都相同，才是同一个索引键。

这使“某会话内按序号查找”自然变成一个连续区间：从 `(c-a, -∞)` 到 `(c-a, +∞)`，或更精确地查 `(c-a, 100)` 至 `(c-a, 200)`。BST 中仍可递归比较，只是节点键不再是单个整数；后续 B+ 树也沿用同一排序规则，并更擅长扫描这段连续叶子区间。

注意，这里的 `seq` 是会话内排序键，不应直接等同于业务 `MessageID` 或 TCP `seq`。若序号重复，必须明确拒绝写入，或继续加入消息类型、方向、时间戳等分量形成可唯一定位的复合键。

> **要点** — BST 用左小右大维护单会话 seq 的查找路径；真实跨会话查询通常需要复合键，而非假设 seq 全局唯一。

以会话 c-a 的连续序号为例，理解中序遍历、范围裁剪与游标分页为何依赖有序结构。

### 中序遍历为何得到递增序列

### 中序遍历为何得到递增序列

设会话 `c-a` 的消息序号被存入一棵二叉搜索树，键为 `1..7`。二叉搜索树满足：

- 任一节点左子树中的键都更小；
- 任一节点右子树中的键都更大。

例如根节点为 `4`，左侧保存 `1,2,3`，右侧保存 `5,6,7`。对它执行**中序遍历**，访问规则是：

`左子树 → 当前节点 → 右子树`，即 LNR。

从根 `4` 开始，不能立刻输出 `4`：因为左子树里还有更小的序号。遍历会先一路进入左侧，依次处理 `1,2,3`；左侧完成后输出 `4`；再处理右侧的 `5,6,7`。最终结果为：

`1, 2, 3, 4, 5, 6, 7`

递增性来自树的结构约束，而不是遍历时额外排序。对任一节点 `x` 而言：

1. 左子树所有键 `< x`，因此应先输出；
2. 再输出 `x`；
3. 右子树所有键 `> x`，因此后输出。

对子树递归应用同一规则，整个输出自然有序。也因此，树不仅能按键查找，还能支持“从某个序号开始，连续读取后续消息”这类范围访问；这正是游标分页依赖有序索引的基础。

### 范围查询的左右剪枝规则

### 范围查询的左右剪枝规则

设二叉搜索树按会话序号组织：任一节点 `x` 的左子树都小于 `x`，右子树都大于 `x`。现在查询闭区间 `[2,5]`，目标是按序得到 `2,3,4,5`。

剪枝并非“猜测哪些节点无用”，而是直接利用排序不变量：

- 若当前节点 `x < 2`，则 `x` 本身不在结果中；更重要的是，`x` 的左子树所有值都满足 `< x < 2`，必然也不在区间内。因此跳过左子树，只可能去右子树继续找。
- 若当前节点 `x > 5`，则 `x` 本身不在结果中；其右子树所有值都满足 `> x > 5`，也必然超出区间。因此跳过右子树，只可能去左子树继续找。
- 若 `2 ≤ x ≤ 5`，节点应被输出；为了保持升序，仍按中序顺序处理：先访问可能落入区间的左侧，再输出 `x`，最后访问可能落入区间的右侧。

可将规则写成递归逻辑：

`若 x > 2，遍历左子树；若 2 ≤ x ≤ 5，输出 x；若 x < 5，遍历右子树。`

注意边界使用的是严格比较：当 `x = 2` 时不能跳过当前节点，但其左子树仍可省略；当 `x = 5` 时不能再进入右子树。这正是闭区间 `[2,5]` 包含两端点的原因。

相比完整中序遍历后再过滤，剪枝会避开整片不可能命中的子树。它也是后续“先定位下界 `2`，再向后连续读取直到超过 `5`”的树索引与游标分页思路的基础。

### 从下界定位到向后取页

### 从下界定位到向后取页

设会话 `c-a` 的消息序号已按键组织为：

`1, 2, 3, 4, 5, 6, 7`

游标分页通常不是“跳过前 `offset` 条”，而是把上一页末尾序号作为游标。例如客户端携带 `afterSeq=2`，并请求 `limit=3`，语义是：返回所有满足 `seq > 2` 的下一批消息，即：

`3, 4, 5`

实现时可分成两步：

1. **找下界**：定位第一个不小于目标值的节点。  
   若要实现 `seq > afterSeq`，可寻找 `afterSeq + 1` 的下界；或者先找 `>= afterSeq`，再判断是否需要跳过相等项。
2. **沿中序后继向后收集**：从定位点开始，持续访问“下一个更大的键”，直到收集满 `limit` 条，或已经到达树的末尾。

以 `afterSeq=2` 为例，搜索会沿树高 $h$ 找到键 `3`；随后依次取得其中序后继 `4`、`5`。因此一次取页的核心代价是：

$$O(h+k)$$

其中 $h$ 是从根到下界位置的搜索路径长度，$k$ 是实际返回的记录数。它不需要重新遍历整棵树，也不会因为页码变大而线性跳过大量旧记录。

若改用有序切片，也能通过二分找到下界，再顺序扫描后续元素，思路相同；但中间插入可能导致切片搬移。普通 `map` 虽然可按序号直接查找单条记录，却没有键的全局顺序，无法自然地执行“从 `2` 之后取连续的 3 条”这一游标查询。B+树等有序索引的价值，正是在于把“定位起点”和“顺序向后读”同时做得高效。

### 路径成本加结果成本

### 路径成本加结果成本

设会话 `c-a` 的消息序号存放在一棵平衡搜索树中，查询游标后的 `k` 条消息，例如“从序号 `20` 开始，返回 10 条”。成本可拆成两部分：

1. **定位成本：$O(h)$**  
   先沿根到叶的路径寻找下界，即第一个满足 `seq >= 20` 的节点。树高为 $h$；对近似平衡的树，若共有 $n$ 条消息，通常有 $h=O(\log n)$。

2. **输出成本：$O(k)$**  
   找到起点后，按中序后继不断向后访问，依次得到 `20, 21, ...`，直到收集满 `k` 条或到达末尾。返回多少条，就至少要读取、构造多少条结果，因此这部分无法省略。

合起来是：

$$
O(h+k)
$$

这里的关键不是“树总共有多少节点”，而是“先走多长的定位路径，再取多少结果”。即使会话有百万条消息，取游标后的 10 条通常仍是 $O(\log n+10)$。

有序切片也能做到类似效果：二分找到下界为 $O(\log n)$，随后连续扫描 $k$ 项为 $O(k)$。而普通 `map` 不保证键的顺序；即使找到某个序号，也不能自然地继续取得后继序号，往往需要额外排序，或扫描全部元素再筛选。B+树索引则把“找下界”和“叶子间向后顺扫”直接组织为高效路径，特别适合数据库游标分页与范围查询。

### 与有序切片和 map 的查询取舍

### 与有序切片和 map 的查询取舍

对会话 `c-a` 的序号做范围查询，例如取 `[2,5]`，三种常见结构的代价并不相同。

- **有序切片**：先对递增数组二分查找下界 `2`，耗时 $O(\log n)$；再从该位置顺序读取直到大于 `5`，输出 $k$ 条记录，合计约为 $O(\log n+k)$。  
  这非常适合“读多写少”、数据可批量加载或追加后较少重排的场景。缺点是中间插入新序号时，需要移动后续元素，代价 $O(n)$。

- **`map`**：按键查找单个序号通常很方便，平均可视为 $O(1)$。但普通哈希 `map` 不保留键的大小顺序：遍历得到的顺序不可依赖，无法直接从 `2` 走到 `5`。若要做范围查询，往往只能扫描全部 $n$ 个键、筛选满足条件的项，再排序，成本接近 $O(n)$ 甚至 $O(n\log n)$。  
  因此它适合精确查询，如“是否存在序号 `37`”，不适合作为分页索引。

- **平衡树 / B+树**：先沿树高 $h$ 找到下界 `2`，再通过中序后继或叶子节点链表向后读取 `3、4、5`。访问量可概括为 $O(h+k)$；若树保持平衡，$h=O(\log n)$。插入、删除也通常只需调整一条根到叶的路径，约为 $O(\log n)$。

游标分页尤其需要这种顺序性：拿到“最后见到的序号 `5`”后，下一页从“大于 `5` 的第一个键”继续，而不是重新扫描前面的记录。切片可用二分实现这一点；平衡树和 B+树则把“找下界并向后迭代”作为结构本身的能力。

> **要点** — 范围查询的关键是利用有序不变量剪枝：先定位下界，再顺序读取结果，成本可理解为 O(h+k)。

连续插入看似自然，却会让普通二叉搜索树退化；本节以会话序号揭示平衡为何关键。

### 从序号顺序插入到右链

### 从序号顺序插入到右链

设同一 `c-a` 会话中的消息按序号到达：

`seq = 1, 2, 3, 4, 5, 6, 7`

普通二叉搜索树（BST）遵循规则：较小键放左子树，较大键放右子树。若按上述顺序逐个插入：

1. `1` 成为根；
2. 插入 `2`：`2 > 1`，成为 `1` 的右孩子；
3. 插入 `3`：依次比较 `1、2`，成为 `2` 的右孩子；
4. 后续 `4..7` 也都不断沿右指针向下。

最终结构为：

`1 → 2 → 3 → 4 → 5 → 6 → 7`

更准确地说，每个节点只有右孩子，没有左孩子；它虽然仍满足 BST 的有序性，却已经退化成一条右链。根到最深节点 `7` 经过 6 条边，因此树高为 6。

查找 `seq=7` 时，必须依次访问：

`1, 2, 3, 4, 5, 6, 7`

即访问 7 个节点，效果接近在有序列表中从头顺序扫描。这里的问题不在于 BST 的比较规则错误，而在于“按递增序号插入”恰好不断制造最坏形状：新节点永远落在当前最右侧。

### 高度决定点查的最坏路径

### 高度决定点查的最坏路径

树的查找代价，取决于从根走到目标节点的最长路径。这里将**高度按边数计算**：单个节点高度为 $0$；根到某个叶子经过 $k$ 条边，该路径高度就是 $k$。

依次插入会话序号 `1,2,3,4,5,6,7` 到普通二叉搜索树时，每个新序号都比已有节点大，只能不断成为右孩子：

`1 → 2 → 3 → 4 → 5 → 6 → 7`

这棵树的根到 `7` 有 $6$ 条边，因此高度为 $6$。查找 `7` 时，需要依次比较并访问 `1` 到 `7` 共 **7 个节点**；最坏情况下，点查成本与节点数同量级，即 $O(n)$。

若将相同键组织为较平衡的形状：

```text
        4
      /   \
     2     6
    / \   / \
   1  3  5  7
```

根到任一叶子只有 $2$ 条边，高度为 $2$。查找 `7` 只经过 `4 → 6 → 7`，最多访问 **3 个节点**。一般地，平衡搜索树把高度控制在 $O(\log n)$，于是点查最坏路径也为 $O(\log n)$。

关键不在于“树通常看起来比较均匀”，而在于最坏形状是否被约束。普通 BST 可能平均表现不错，却仍允许右链这样的 $O(n)$ 最坏情况。

### 平衡形状与对数高度直觉

### 平衡形状与对数高度直觉

仍然插入会话序号 $1\sim7$，若树保持接近平衡，可形成：

```text
        4
      /   \
     2     6
    / \   / \
   1   3 5   7
```

根节点是 `4`，第二层是 `2、6`，第三层填入其余四个序号。树的高度按边数计算为 $2$：从根到任一叶子最多经过两条边。查找 `7` 时只需访问 `4→6→7`，最多比较 $3$ 个节点。

这与按 `1,2,3,4,5,6,7` 依次插入普通 BST 得到的右链形成对比：右链高度为 $6$，查找 `7` 要依次经过全部 $7$ 个节点。两棵树保存的数据完全相同，中序遍历也同样是递增序列；差别只在于节点形状。

直觉上，平衡树让每一层容纳约两倍于上一层的节点：第 $0$ 层约 $1$ 个、第 $1$ 层约 $2$ 个、第 $2$ 层约 $4$ 个。因此容纳 $n$ 个节点只需约 $\log_2 n$ 层，查找、插入和删除的路径长度也随之为 $O(\log n)$。

要特别区分两种说法：

- 普通 BST 在随机或较均匀插入时，**平均**可能较快；
- 但它没有阻止右链出现，**最坏情况**仍是 $O(n)$；
- 平衡搜索树通过维持形状约束，才提供高度 $O(\log n)$ 的最坏保证。

后续的 AVL 树和红黑树，正是用不同规则把这种“不要长成链”的直觉落实为可维护的结构。

### 旋转为何不破坏有序性

### 旋转为何不破坏有序性

设会话序号按 `1 → 2 → 3` 依次插入普通 BST，会得到一条右链：

`1 → 2 → 3`

其中 `1` 是根，`2` 是 `1` 的右孩子，`3` 是 `2` 的右孩子。树高为 2，查找 `3` 必须连续经过 3 个节点。

此时可对节点 `1` 做一次**左旋**：让 `2` 上升为局部根，`1` 变成 `2` 的左孩子，`3` 仍是 `2` 的右孩子：

```text
    2
   / \
  1   3
```

旋转改变的是父子关系和局部形状，不改变搜索树最关键的次序约束。旋转前的中序遍历是：

`1, 2, 3`

旋转后的中序遍历仍是：

`1, 2, 3`

原因在于：原先 `2` 的左侧所有键都小于 `2`，右侧所有键都大于 `2`；左旋只是在满足这一分界的位置重新安排“谁当父亲”。因此，较小的 `1` 仍在 `2` 左边，较大的 `3` 仍在 `2` 右边。

局部看，旋转把偏斜的链压低；整体看，许多这样的局部调整能避免树退化为链表。AVL 树、红黑树会规定何时旋转、旋转后如何维护额外条件；但核心直觉是：**中序顺序代表有序性，树形高度代表查找效率，旋转可以改善后者而不牺牲前者。**

### 从普通 BST 到索引结构的选择

### 从普通 BST 到索引结构的选择

设消息记录按复合键 `(conversation_id, seq)` 排序：先比较会话标识，再比较该会话内的序号。查询“某会话第 100 到 200 条消息”本质上是一次有序索引的范围定位：先找到下界 `(c,100)`，再沿有序结构依次读取直到 `(c,200)`。

普通 BST 在键分布理想、插入顺序随机时，查找常常较快；但这不是最坏保证。若某个会话的 `seq=1..7` 按递增顺序插入，树会退化为右链：

`1 → 2 → 3 → 4 → 5 → 6 → 7`

其高度为 6（按边计），点查 `7` 要访问 7 个节点，复杂度为 $O(n)$。换言之，“数据本来有序”恰恰可能使普通 BST 最差。

平衡树通过在更新时调整局部结构，避免这种单侧拉长。例如对 `1,2,3`，一次旋转可将根从 `1` 调整为 `2`，形成左右孩子 `1`、`3`；中序遍历仍是 `1,2,3`，键的排序语义不变，但高度降低。对于 `4,2,6,1,3,5,7`，树高仅为 2，任意点查最多经过 3 个节点。

因此，AVL 树和红黑树的共同目标不是“让树绝对完美”，而是维持 $O(\log n)$ 高度，使点查、插入、删除在最坏情况下都有对数级界限。AVL 更强调严格平衡，红黑树以较宽松的平衡条件换取较低调整成本；具体旋转、颜色或高度规则可后续学习。

但数据库索引还要面对磁盘页、缓存与范围扫描：二叉树每层分支太少，后续会自然走向 B+ 树等多路索引。此处应先把握边界：普通 BST 可表达排序与查找思想，却不能为持续增长的 `(conversation_id, seq)` 查询提供可靠的最坏性能。

> **要点** — 普通 BST 不保证平衡，顺序插入可退化为 O(n)；旋转与平衡策略的目标是维持 O(log n) 高度。

当前序号索引若继续用二叉指针节点，树高会随数据增长而显著增加；数据库改用“页装多个键”的多路树，以更少层数完成定位与范围扫描。

### 从二叉节点到数据库页

### 从二叉节点到数据库页

内存中的二叉搜索树常把一个节点想成：

`一个键 + 左指针 + 右指针`

每次比较后，只沿两个孩子中的一个继续向下。这种结构适合讲解顺序与查找，但若节点分散存放，查找大量会话序号时，可能每下降一层就要访问一个新的内存块甚至磁盘位置。

数据库更自然的存储单位是**页**：一次从磁盘读取、或一次放入缓存的，通常是一整页连续空间，而不是一个很小的二叉节点。既然已经取得一页，就应尽量在页内放入更多可用信息：

- 多个按序排列的键；
- 多个孩子指针或页号；
- 用键把值域划分为多个区间。

例如某内部页含有键 `20、50、80`，就可有四个孩子，分别负责：

`<20`、`20～49`、`50～79`、`≥80`

查找 `63` 时，不是只在“左/右”二选一，而是在页内比较后直接进入第三个孩子。这样的节点称为多路节点；一页能指向的孩子数越多，称为**扇出**越高。

高扇出的关键收益是降低树高。二叉树每层最多把可覆盖的数据量约扩大 $2$ 倍；而一页若能容纳许多键和孩子，一层就能扩大数十倍甚至更多。于是一次查询只需经过较少的页，减少昂贵的页访问次数，也更容易利用缓存。

### 64 个序号的三层玩具树

### 64 个序号的三层玩具树

设索引中有连续的 `64` 个会话序号，并采用一个刻意简化的页模型：

- 每个**叶页**最多放 `4` 个有序键及其对应条目；
- 每个**内部页**最多指向 `4` 个孩子页，并保存用于分流的导向键；
- 暂不考虑页未装满、重复键、删除、缓存与并发更新。

先看叶层。`64` 个键、每页 `4` 个键，因此需要：

$$
64 \div 4 = 16
$$

即 `16` 个叶页。可以把它们想成：

`[1..4] → [5..8] → … → [61..64]`

箭头表示叶页按键值顺序相连。若查询范围是 `18` 到 `29`，先定位到含 `18` 的叶页，再沿叶页链连续读取，直到超过 `29`；不必为每个后续键重新从根开始搜索。

再向上一层：内部页每页能管理 `4` 个孩子，而叶层有 `16` 页，所以需要：

$$
16 \div 4 = 4
$$

即 `4` 个内部页。每个内部页负责一段连续叶页，例如第一个内部页导向前 `4` 个叶页，覆盖键 `1..16`。

最后，根页再指向这 `4` 个内部页：

$$
4 \div 4 = 1
$$

因此整棵玩具树共有三层：

1. 根页：`1` 页；
2. 内部层：`4` 页；
3. 叶层：`16` 页，容纳全部 `64` 个键。

查找某个序号，如 `42`，路径是“根页 → 某个内部页 → 某个叶页”，只需经过 `3` 层页。这里的内部键主要承担“该往哪个孩子走”的导向职责；真正可遍历的有序条目位于叶层。这正是 B+树适合范围查询的直觉，不过实际的 PostgreSQL、SQLite 页结构、键压缩和分裂策略并不完全等同于这个教学模型。

### 内部导向与叶页顺序链

### 内部导向与叶页顺序链

教学版 B+ 树把“找去哪一页”和“按顺序读哪些记录”分给两类页面：

- **内部页**保存分隔键与子页指针。键不一定代表可直接返回的完整记录，而是路标：例如内部键为 `20 | 40 | 60`，查找 `session_no=37` 时，应沿着 `20` 与 `40` 之间对应的子页继续向下。
- **叶页**保存实际可遍历的索引条目，通常形如 `(键, 行定位信息)`。所有叶页中的键合起来构成完整有序序列。
- **叶页顺序相连**：每个叶页知道其后继叶页。找到范围下界后，不必重新从根开始查每个值，只需沿叶页链持续向右读取。

例如查询：

```text
session_no >= 120 AND session_no < 150
```

先从根和内部页定位到包含 `120` 的叶页；随后在该叶页中顺序读取，若读到页尾仍未达到 `150`，就跳到下一叶页，直到遇到第一个不满足上界的键。这正是范围扫描高效的原因：一次树下降，后续主要是连续叶页遍历。

因此，内部页像目录，叶页像按页码串起的有序正文。这里是帮助理解的简化模型；PostgreSQL、SQLite 等具体实现会有页格式、并发控制、重复键与优化策略差异，不能将其完全等同于该玩具结构。

### 会话序号范围如何扫描

### 会话序号范围如何扫描

查询某个会话的一段消息，条件通常写成：

`conversation_id = 42 AND seq >= 100 AND seq <= 180`

若存在复合有序索引 `(conversation_id, seq)`，索引中的键按“先会话、后序号”排序。数据库可将条件转换为一个连续区间：

- 下界：`(42, 100)`
- 上界：`(42, 180)`

执行时并不需要为每个 `seq` 重新从根查找一次，而是分两步：

1. **定位起点**：从根页经内部页下降，找到第一个不小于 `(42, 100)` 的叶页条目。
2. **顺序扫描**：从该条目开始向后读取；当前叶页读完后，沿叶页间的顺序链接进入下一叶页，持续检查键值。
3. **到达上界即停止**：遇到大于 `(42, 180)` 的键，或会话编号已变成大于 `42` 的值，就结束扫描。

例如叶页中依次有：

`(42,98), (42,99), (42,100), (42,101), ...`

定位后会直接从 `(42,100)` 开始，而不会读取前两个条目。若 `100` 到 `180` 跨越多个叶页，后续读取是连续的页扫描，不必反复走“根页 → 内部页 → 叶页”。

这正是 B+ 树适合范围条件的原因：内部页负责快速找到范围起点，叶页负责按序连续取出结果。实际 PostgreSQL、SQLite 等系统的页面组织、并发控制和访问策略各不相同，但“先定位下界，再沿有序叶页扫描至上界”是理解复合范围索引的核心直觉。

### 高扇出优势与模型边界

### 高扇出优势与模型边界

二叉搜索树的每个内部节点通常只有两个孩子。若有 $64$ 个叶子条目，理想满二叉树大致需要：

- 叶层：$64$ 个叶节点；
- 上一层：$32$ 个父节点；
- 再上一层：$16,8,4,2,1$；
- 从根到叶约需 $6$ 次向下选择。

数据库不希望每次比较都可能触及一个单独的小节点：节点往往对应磁盘页、缓存页或需要锁定与解析的内存块，层数越多，潜在页访问越多。

改用“一个页容纳多个有序键、并指向多个孩子”的多路树后，扇出显著提高。设玩具模型中每个叶页放 $4$ 个键，则 $64$ 个键需要 $16$ 个叶页；若每个内部页也能导向 $4$ 个孩子，则：

- 叶层：$16$ 页；
- 内部层：$4$ 页；
- 根层：$1$ 页。

因此一次精确查找只需经过“根页 → 内部页 → 叶页”共 $3$ 层。相比二叉树约 $6$ 层的路径，高扇出用页内比较换取更少的页间跳转；真实数据库中一页通常可放远多于 $4$ 个键，树高常常更低。

B+树教学模型还强调：内部键主要用于导向，实际可遍历条目集中在叶层，叶页按键顺序相连。查询序号范围时，先定位范围起点所在叶页，再沿叶链连续读取，避免对每个序号重新从根查找。

不过这只是帮助建立直觉的模型。PostgreSQL、SQLite 或 OpenIM 的实际索引会涉及页大小、变长键、重复值、并发控制、分裂合并、缓存、写放大和具体存储引擎差异，不能把“4 键、4 孩子、固定三层”的玩具树当作其精确实现。

> **要点** — 多路页树以高扇出压低树高；B+树借助有序叶页链，使会话序号范围查询可从起点连续扫描。

以会话 c-a 的消息翻页为线索，理解复合键范围查询为何需要有序索引，以及它带来的读写代价。

### 从历史消息翻页定义查询边界

### 从历史消息翻页定义查询边界

设用户正在查看会话 `c-a` 的历史消息。每条消息除全局唯一的 `message_id` 外，还应有在该会话内单调递增的序号 `seq`。一次“继续向上翻”的查询可以精确定义为：

```sql
SELECT *
FROM messages
WHERE conversation_id = 'c-a'
  AND seq < :cursor
ORDER BY seq DESC
LIMIT :page_size;
```

它包含三个彼此独立的边界：

- `conversation_id = 'c-a'`：只看目标会话，不能混入其他会话消息。
- `seq < :cursor`：只取当前游标之前的更早消息；首屏可把 `cursor` 设为一个足够大的值，或改为不带该条件。
- `ORDER BY seq DESC LIMIT 20`：按“从新到旧”返回最多 20 条，客户端展示时再按需要反转为时间正序。

因此，翻页游标不是“第几页”，而是上一页中最旧消息的 `seq`。若本页结果为 `105, 104, ..., 86`，下一页就使用 `cursor = 86`，查询 `seq < 86`。这种边界不会因中间插入新消息而让旧页整体位移，也避免了大偏移量的 `OFFSET` 扫描。

这里的逻辑身份是复合键 `(conversation_id, seq)`：`seq=86` 只有放在会话 `c-a` 中才有意义。相对地，`message_id` 适合“精确找到这一条消息”：

```sql
WHERE message_id = :message_id
```

它不能直接表达“同一会话中、某序号之前的一段连续历史”。这正是后续需要围绕 `(conversation_id, seq)` 建立有序索引的原因。

### 复合键如何先定位会话再走范围

### 复合键如何先定位会话再走范围

设消息表使用复合索引 `(conversation_id, seq)`，其排序不是“分别排序两列”，而是按**字典序**排列：

$$(c_1,s_1) < (c_2,s_2)$$

当且仅当 `c1 < c2`，或 `c1 = c2` 且 `s1 < s2`。因此，索引中的键可能呈现为：

`(c-a, 1) → (c-a, 2) → (c-a, 3) → (c-b, 1) → (c-b, 2)`

同一会话的所有 `seq` 会自然聚集成一段连续区间。这正是查询：

`GET c-a?seq<cursor`

对应的核心条件：

```sql
WHERE conversation_id = 'c-a'
  AND seq < :cursor
ORDER BY seq DESC
LIMIT :n
```

树查找先利用最左列 `conversation_id = 'c-a'` 定位到 `c-a` 这一段；随后在该段内，根据 `seq < cursor` 找到游标附近的位置。由于键本身已按 `seq` 有序，数据库可以沿索引叶子页向较小的 `seq` 方向连续读取，取满 `n` 条即停止，而不必读取该会话的全部历史消息再排序。

可将其直观理解为：`conversation_id` 决定“进入哪条走廊”，`seq` 决定“从走廊中的哪个门开始向前走”。`ORDER BY seq DESC` 与索引顺序相反时，通常可反向遍历该有序范围。

这与 `message_id = ?` 不同：后者是单条记录的精确定位；前者是“先固定会话，再读取一个有序片段”。复合键的列顺序因此关键：`(conversation_id, seq)` 服务于“某会话内按序翻页”，而不是任意组合条件都同样高效。

### message_id 精确查找为何不能替代范围索引

### `message_id` 精确查找为何不能替代范围索引

`message_id` 适合回答“这条消息在哪里”：例如根据通知、引用或跳转链接执行

`WHERE message_id = 'm-9382'`

若 `message_id` 唯一且建有索引，数据库可按键快速定位到一条记录。这是**等值定位**：目标明确，通常只需找到对应索引项，再读取该消息。

但会话翻页问的是另一类问题：

`WHERE conversation_id = 'c-a' AND seq < 120 ORDER BY seq DESC LIMIT 20`

这里并不知道 20 条消息各自的 `message_id`；已知的是会话边界 `c-a`、游标 `120` 和顺序要求。即使表上有 `message_id` 索引，它也没有表达“哪些消息属于 `c-a`”“这些消息的 `seq` 如何排列”。数据库仍可能扫描大量记录、筛出目标会话，再排序并截取 20 条。

复合有序索引 `(conversation_id, seq)` 则把访问路径组织为：

1. 先按 `conversation_id = 'c-a'` 定位该会话的连续索引区间；
2. 在该区间内按 `seq < 120` 做范围查找；
3. 逆序沿索引项读取，取满 `LIMIT 20` 即可停止。

因此，`message_id` 索引解决“已知唯一标识，找一条”；`(conversation_id, seq)` 索引解决“已知分组与游标，按顺序找一段”。两者不是谁替代谁，而是服务于不同访问模式。

### 没有索引与维护索引的成本交换

### 没有索引与维护索引的成本交换

对会话 `c-a` 执行“取游标 `cursor` 之前的 20 条消息”：

`WHERE conversation_id = 'c-a' AND seq < cursor ORDER BY seq DESC LIMIT 20`

没有合适索引时，数据库通常需要扫描大量消息，筛出 `c-a` 的记录和满足 `seq < cursor` 的行，再进行排序，最后取前 20 条。即使最终只返回一页数据，代价也可能接近“读很多行、排很多行”；会话越多、历史越长，翻页越不稳定。

若建立 `(conversation_id, seq)` 复合有序索引，查找可先按 `conversation_id='c-a'` 定位到该会话对应的索引区间，再沿 `seq` 的有序范围向较小序号读取，满足 `LIMIT 20` 后即可停止。这里的优势不是“索引天然更快”，而是避免为每一页重复扫描和排序。PostgreSQL 的 B-tree 可支持 `=、<、<=、>、>=` 等比较条件，正适合这种前缀等值加后列范围的模式。

但索引不是免费的：

- 插入一条消息时，除写数据本身外，还要写入并维护索引项；
- 索引占用额外磁盘与缓存空间，索引越宽、越多，写放大越明显；
- 新键插入到有序页中，页满时可能发生页分裂，带来额外复制和结构维护；
- 对主要按 `message_id` 精确查询的场景，`message_id` 索引有价值；它不能替代按会话和序号连续翻页的复合索引。

因此，索引设计是在“高频读取少量有序结果”和“每次写入都承担维护成本”之间交换。是否真的选择该索引、扫描了多少行，则应在后续用 `EXPLAIN` 验证，而不能只凭直觉判断。

### 从教学 B+树模型到真实数据库边界

### 从教学 B+树模型到真实数据库边界

把消息表的索引抽象成按 `(conversation_id, seq)` 排序的叶子页，可以直观理解：

```sql
WHERE conversation_id = 'c-a'
  AND seq < :cursor
ORDER BY seq DESC
LIMIT 20
```

数据库先利用复合键的第一个字段定位到会话 `c-a`，再在该会话对应的有序 `seq` 区间中向前读取，取到 20 条即可停止。这里的关键不是“树会搜索”，而是索引顺序同时满足了**过滤条件、范围条件和排序方向**。

PostgreSQL 的 B-tree 索引支持 `=、<、<=、>、>=` 等比较运算，因此它适合这种按序号翻页的访问模式。若只有 `message_id` 索引，则它擅长：

```sql
WHERE message_id = :id
```

即按唯一消息标识精确找到一行；但它通常不能直接提供“某会话内按 `seq` 倒序”的连续顺序。

教学中常把这一过程画成 B+ 树：内部节点负责导航，叶子节点保存有序键并可顺序遍历。这个模型用于建立“先定位前缀、再走范围”的直觉即可，不应据此断言 OpenIM 的实际存储引擎、MongoDB 索引页结构或具体节点布局。真实系统还受统计信息、数据分布、缓存、回表成本和查询条件影响；优化器最终是否选择索引，应留待 `EXPLAIN` 分析。

索引也不是免费午餐：没有合适索引时，数据库可能扫描更多行并额外排序；建立索引后，插入消息还要维护索引页，占用额外空间，并可能发生页分裂。

> **要点** — 会话前缀加序号范围把翻页变成有序索引遍历，但查询加速需交换写入维护与存储成本。

以会话 c-a 的 seq 为线索，建立 BST 剪枝与中序有序性的直觉，并比较不同索引结构的实际代价。

### BST 不变量与查找剪枝

### BST 不变量与查找剪枝

二叉搜索树（BST）把每个节点的键值放在一个可推断的位置：对任意节点 `x`，其左子树中所有键都小于 `x.key`，右子树中所有键都大于 `x.key`。注意这里说的是“整棵子树”，而不只是左右孩子。

例如按会话 `c-a` 的 `seq` 建树：

`20` 的左子树可能有 `8、12、17`，右子树可能有 `24、31`。若查找 `seq=17`：

1. 先比较根节点 `20`：`17 < 20`。
2. 因为右子树所有键都大于 `20`，它不可能含有 `17`，可整体排除。
3. 进入左子树，继续比较；每一步都只保留一个可能方向。

这就是“剪枝”的含义：一次比较不只是排除一个节点，而是排除一整片子树。若树高为 $h$，查找最多比较 $h$ 次；平衡时 $h \approx \log_2 n$，而不是线性扫描的 $n$ 次。

查找逻辑可概括为：

- `target == key`：命中；
- `target < key`：只去左子树；
- `target > key`：只去右子树；
- 走到空指针：该键不存在。

空树天然表示“没有任何可查找键”。重复键则必须预先约定策略：例如节点额外保存计数、把相同键放入值列表，或统一规定“相等键进入右侧”。若不统一，严格的“大于/小于”不变量会被破坏，后续查找与范围查询就没有可靠依据。

### 中序遍历为何得到有序序列

### 中序遍历为何得到有序序列

对一棵满足 BST 不变量的树：任一节点 `x` 的左子树所有键都小于 `x.key`，右子树所有键都大于 `x.key`。中序遍历固定采用：

1. 遍历左子树；
2. 访问当前节点；
3. 遍历右子树。

因此，访问节点 `x` 时，左子树中所有键已经输出，且它们都小于 `x.key`；随后输出 `x.key`；最后才输出右子树，而其中所有键都大于 `x.key`。局部次序自然是：

$$\text{左子树键} < x.key < \text{右子树键}$$

再对左右子树递归应用同一规则：若左、右子树各自的中序结果已经递增，把它们与 `x.key` 按“左—节点—右”拼接，整个结果仍递增。这就是中序遍历有序性的归纳直觉。

例如插入会话 `c-a` 的序号 `8, 3, 12, 1, 6`，树的形状不必完全记住；中序访问一定得到：

`1, 3, 6, 8, 12`

这也解释了范围查询为何自然。查询 `seq ∈ [3, 8]` 时，先定位到 `3` 附近，再沿中序后继依次读取 `3, 6, 8`，遇到大于 `8` 的键即可停止，无须扫描无关的 `1` 与 `12`。

前提是比较关系必须形成稳定的全序。若多个记录有相同时间戳或相同 `seq`，不能简单要求“左小右大”；应规定重复键统一放一侧，或使用复合键如 `(seq, recordID)`。空树的中序结果则是空序列，仍然有序。

### 负例：空树、重复键与倾斜插入

### 负例：空树、重复键与倾斜插入

BST 的剪枝依赖一个前提：每个节点都满足“左子树键更小、右子树键更大”（或事先约定允许相等的一侧）。边界条件没有定义清楚，查找和中序遍历的结论都会变得含糊。

- **空树**：查找 `seq=42` 时，根指针为空即可立刻返回“未找到”；插入时则直接创建根节点。空树不是异常，但代码必须把它当作合法状态，而不是访问不存在的根节点。

- **重复 `seq`**：若同一会话 `c-a` 的序号应唯一，插入重复键通常意味着数据错误，或应执行覆盖更新。若业务允许重复，例如按时间戳索引多条消息，就不能只用 `timestamp` 作为严格 BST 键。可使用复合键：
  \[
  (\text{timestamp},\ \text{messageID})
  \]
  先比较时间戳，再比较唯一标识。否则“相等时往左还是往右”虽能维持某种约定，却会让范围查询和去重语义不清晰。

- **并列时间戳**：多个事件拥有相同毫秒时间戳很常见。若索引只保存 `timestamp → 单条记录`，后写入的数据可能覆盖先写入的数据；若值是记录列表，则一个节点可能积累很长的桶。复合键、重复键链表或单独的唯一主键，各自对应不同查询需求。

- **单调插入**：依次插入 `1,2,3,4,5`，普通 BST 会不断向右生长：
  `1 → 2 → 3 → 4 → 5`。  
  此时树高从理想的 $O(\log n)$ 退化为 $O(n)$，查找、插入和范围定位都近似链表扫描。反向顺序插入同样会形成左链。

因此，“BST 查找快”不是只要有左右指针就成立；它还隐含键比较规则明确、重复键策略明确，以及树高没有因输入顺序失控。平衡 BST 与后续的多路页树，正是为限制这种最坏形态而设计。

### 从平衡 BST 到多路页树

### 从平衡 BST 到多路页树

普通 BST 的问题不在于“不有序”，而在于插入顺序可能把它拉成长链：连续插入 `1,2,3,...,64` 时，高度接近 $64$，查找退化为线性扫描。平衡 BST 通过旋转限制左右子树高度差；旋转只重接局部父子关系，不改变节点的中序遍历序列，因此键的全局有序性仍保持不变。

例如右旋前后，局部键序始终满足：

`左子树 < 根 < 右子树`

所以旋转改变的是“树形”，不是“排序结果”。若树近似平衡，$64$ 个键的二叉树高度约为：

$$\log_2 64 = 6$$

一次点查通常需比较约 6 层；范围扫描先定位起点，再按中序后继连续取键。

但磁盘或页缓存中的代价主要是“访问页”，不是单次键比较。多路页树把许多分隔键和多个子指针放进一个页：若每个内部页可分出约 8 路，则 64 个键的玩具模型高度约为：

$$\log_8 64 = 2$$

即根页选择一个子页，再到叶页即可。现实 B+ 树的扇出常远大于 8，因此即使索引含百万级键，高度也往往只有少数几层。叶子页通常按键顺序相连，范围查询可在叶页间顺序前进，局部性优于反复沿二叉树跳转。

代价也随之而来：页内需要维护有序键；插入可能造成页分裂，删除可能合并或重分配。索引缩短读路径，却增加写放大、内存占用和维护成本；读多写少、需要范围查询时尤其值得。

### map、切片与索引结构的取舍

### map、切片与索引结构的取舍

若访问模式是“给定 `(conversation_id, seq)` 找一条消息”，Go `map` 很合适：平均点查与插入接近 $O(1)$。例如可用复合键：

`map[Key]Message`，其中 `Key{ConversationID, Seq}`。

但 `map` 不维护键序。要读取 `c-a` 中 `seq ∈ [100, 200]` 的消息，只能扫描大量元素再过滤，成本接近 $O(n)$；把键取出后排序，又会额外付出 $O(n\log n)$。

有序切片恰好相反。按 `(conversation_id, seq)` 排序后，可二分定位范围起点，再顺序读取：

- 点查：二分查找 $O(\log n)$；
- 范围读：$O(\log n+k)$，其中 $k$ 是返回记录数；
- 插入：需移动后续元素，最坏 $O(n)$。

切片连续存储，缓存局部性好；对“批量写入、较少插入、频繁按序扫描”的场景尤其有效。若消息按 `seq` 单调追加，插入通常接近尾部追加，实际代价更低；但乱序补写会变贵。

平衡 BST 保持左右子树的键序关系，点查、插入、范围定位通常为 $O(\log n)$，范围扫描为 $O(\log n+k)$。代价是节点往往分散分配，指针、颜色或高度等元数据增加内存占用，也较容易造成缓存未命中。

数据库常用 B+ 树等多路页树：一个节点容纳许多键，树高更低，且叶子页相邻连接，适合“定位一次、连续读一段”的范围查询。代价是维护分裂、合并与写放大；索引还会占空间，并让每次写入更新更多结构。

因此，索引不是“加上就更快”：`map` 偏点查，有序切片偏顺序读，平衡树兼顾动态有序，多路索引更适合大量数据与页式存储。应先看读写比例、是否需要范围读取，以及数据能否近似按序到达。

> **要点** — BST 以有序不变量支持剪枝与范围遍历；索引选择必须同时权衡查询形态、更新代价、树高和内存局部性。

以会话 c-a 的递增序号为线索，先用两棵二叉搜索树理解范围查询，再建立从内存结构到 B+ 树页索引的直觉。

### 从序号键认识树与二叉搜索树

### 从序号键认识树与二叉搜索树

把会话 `c-a` 的消息序号 `seq` 看作键：`1,2,3,4,5...`。若逐条扫描数组，要找 `seq=5` 通常需检查多个位置；树则把键组织成“从根向下”的决策路径。

例如：

- 根节点：最先进入当前树比较的键，如 `4`。
- 父节点与子节点：若 `4` 的左边连接 `2`，则 `4` 是 `2` 的父节点，`2` 是其子节点。
- 叶节点：没有子节点的节点，如 `1`、`3`、`5`。
- 层：根在第 0 层；它的子节点在第 1 层。
- 高度：从根到最深叶节点经过的边数；高度越小，查找路径通常越短。

二叉搜索树（BST）要求每个节点都满足不变量：

$$
\text{左子树所有键}<\text{节点键}<\text{右子树所有键}
$$

例如以 `4` 为根，左子树含 `2,1,3`，右子树含 `5`。查找 `seq=5` 时：先比较 `5` 与 `4`，因 `5>4` 而向右；到达 `5` 即命中。无需查看左侧的 `1,2,3`。

这里的“左小右大”不是仅约束直接孩子：若 `2` 位于 `4` 的左子树，那么 `2` 及其全部后代都必须小于 `4`。这个全局顺序约束，正是后续按 `seq` 查找与范围遍历能够跳过无关数据的基础。

### 两种树形与 search(5) 路径

### 两种树形与 `search(5)` 路径

把会话 `c-a` 的消息序号作为键，二叉搜索树（BST）要求：任一节点左子树键都更小，右子树键都更大。相同的键集合 `{1,2,3,4,5,6,7}`，插入顺序不同，形状可以完全不同。

较平衡的一棵树：

```text
        4
      /   \
     2     6
    / \   / \
   1   3 5   7
```

查找 `search(5)` 时，逐层比较：

1. 到根 `4`：`5 > 4`，向右；
2. 到节点 `6`：`5 < 6`，向左；
3. 到节点 `5`：相等，找到。

比较路径是 `4 → 6 → 5`，只访问 3 个节点。树高约为 $\log_2 7$，查找代价随键数增长较慢。

若按递增顺序 `1,2,3,4,5,6,7` 插入普通 BST，则会退化为链：

```text
1
 \
  2
   \
    3
     \
      4
       \
        5
         \
          6
           \
            7
```

此时查找 `5` 必须走 `1 → 2 → 3 → 4 → 5`，访问 5 个节点；查找靠后的键甚至接近扫描整个序列。它仍满足 BST 的大小关系，却失去了“树应当很矮”的效率优势。

因此，BST 的关键不只是“能向左或向右走”，还在于控制高度：平衡形状使查找接近 $O(\log n)$，退化链则变为 $O(n)$。后续的 B+ 树正是用多路分支和页级组织，避免大量索引键形成这种长链。

### 中序遍历与 range[2,5]

### 中序遍历与 `range[2,5]`

对二叉搜索树而言，任一节点都满足：左子树键值更小，右子树键值更大。因此按“左子树 → 当前节点 → 右子树”的中序遍历顺序访问，结果必然递增。

例如树中包含序号 `1,2,3,4,5,6,7`，中序遍历会得到：

`1, 2, 3, 4, 5, 6, 7`

范围查询并不需要完整遍历。查询会话 `c-a` 中 `seq ∈ [2,5]` 时，可利用比较结果剪枝：

- 若当前键 `x < 2`，则其左子树全部 `< 2`，直接跳过，只检查右子树。
- 若 `2 ≤ x ≤ 5`，继续按中序顺序访问，并输出该节点。
- 若当前键 `x > 5`，则其右子树全部 `> 5`，直接跳过；在中序遍历中，当前节点及其右侧也不再可能属于结果。

因此，逻辑路径相当于：先找到不小于 `2` 的第一个键，再连续读取直到遇到大于 `5` 的键。输出为：

`2, 3, 4, 5`

这里的“连续”指的是**排序后的键空间连续**，不要求物理内存地址连续。若索引键是复合键 `(conversation_id, seq)`，则可将范围写作：

`(c-a, 2) ≤ key ≤ (c-a, 5)`

这正是后续 B+ 树游标查询的雏形：定位范围左边界，然后沿有序叶子记录向右扫描，直到越过右边界。

### 高度、旋转与多路页树

### 高度、旋转与多路页树

二叉搜索树的查找成本主要由**高度**决定，而不只是键的总数。仍以会话 `c-a` 的序号为例，若依次插入 `1,2,3,4,5`，会形成右倾链：

`1 → 2 → 3 → 4 → 5`

查找 `5` 必须比较 5 次；范围 `[2,5]` 也几乎要沿整条链前进。此时树虽满足“左小右大”，却退化得接近链表，最坏成本为 $O(n)$。

若将相同键组织为近似平衡的形状：

```text
      3
    /   \
   2     5
        /
       4
```

查找 `5` 只需经过 `3 → 5`，树高约为 $O(\log n)$。平衡树并不要求每层完全填满；关键是避免某一侧持续增长，使最长路径远长于其他路径。

**旋转**是恢复局部平衡的基本动作。比如节点 `1` 的右侧连续出现 `2、3` 时，对 `1` 左旋，可让 `2` 上升、`1` 成为其左孩子。旋转改变的是父子关系，不改变中序序列：

`1,2,3` 旋转后仍按 `1,2,3` 排列。

因此，旋转能缩短高度，同时保持 BST 的有序查询语义。

磁盘索引通常不会采用“每个节点只放一个键”的二叉形状，而使用多路页树。假设一个页可容纳约 64 个键或分隔位置：一层叶页即可覆盖约 64 个键；若根页再指向约 64 个叶页，两层理论上可覆盖约 $64^2=4096$ 个键。相比二叉树每层只缩小约一半搜索空间，多路页树每次读取一个页就排除大批候选键，层数更低。

对 `c-a` 的游标查询可抽象为：先在内部页定位序号 `a` 应落入的叶页，再在叶页中顺序读取 `a,a+1,\dots`，直到达到上界。这里的“64”只是页容量直觉，不是固定事实：真实容量还受键长度、指针、页头和填充率影响。

### 从 c-a 游标到有序索引选择

### 从 c-a 游标到有序索引选择

设会话 `c-a` 的消息按递增序号 `seq` 保存。用户已读到 `last_seq=17`，下一页想取 20 条历史消息，本质查询是：

\[
(\text{conversation\_id}=\texttt{c-a})\land(\text{seq}>17)
\]

并按 `seq` 升序返回前 20 条。把键写成复合键：

\[
K=(\text{conversation\_id},\text{seq})
\]

则目标不再是“查一条消息”，而是在有序键空间中寻找 `(\texttt{c-a},17)` 之后的一小段连续范围。若还给定上界，例如补拉 `[18,35]`，就是：

\[
(\texttt{c-a},18)\le K\le(\texttt{c-a},35)
\]

不同结构对这类游标查询的支持差异明显：

- **哈希表 `map`**：适合通过完整键快速定位，如查 `(\texttt{c-a},18)`；但键没有顺序，找“17 之后的 20 条”通常要扫描、过滤或另建排序结构。
- **有序切片**：按 `(conversation_id, seq)` 排列后，可二分找到游标位置，随后顺序读取 20 项；查找约为 $O(\log n)$，连续读取成本低，但中间插入可能需要移动大量元素。
- **平衡二叉搜索树**：可先搜索下界，再做中序后继遍历，典型成本近似 $O(\log n+k)$，其中 $k$ 是返回消息数。
- **B+ 树式页索引**：内部页用于导航，叶子页保存有序键及记录位置，叶子页之间常可顺序连接。找到起始叶后，后续消息可跨页连续读取，特别适合数据库中的范围扫描与分页。

这里的关键不是“树一定比 `map` 快”，而是访问模式：完整键等值查找偏向哈希；按序号续读、时间线翻页、区间补拉偏向有序索引。复合键的列顺序也重要：`(conversation_id, seq)` 先聚集同一会话，再保证会话内序号连续；若写成 `(seq, conversation_id)`，按单个会话续读通常难以形成紧凑范围。

上述是教学模型，用来建立“游标 $\rightarrow$ 复合范围 $\rightarrow$ 有序索引”的推理链。它不证明 PostgreSQL、OpenIM 或任何具体系统必然采用某个索引、页大小、存储布局或分页语句；真实实现还受表结构、查询条件、执行计划、缓存与分片策略影响。

> **要点** — 范围查询依赖键的有序性；平衡与多路分页通过降低树高，减少定位会话消息区间的比较和页访问。
