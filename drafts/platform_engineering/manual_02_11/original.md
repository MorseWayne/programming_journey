## 02.11 近似与专用结构：前缀、位图、Bloom与并查集

- 按查询形状选择专用结构而非名字
- 手画Trie并区分终止标记/文本单位

- 用Union-Find判断增量连通和删除限制

四类请求看似都能用 map 处理，但查询形状、空间预算与正确性承诺不同，决定了何时值得换用专用结构。

### 先按请求形状选结构

### 先按请求形状选结构

选择结构先问“查询要什么”，而不是先问“哪个名字更高级”。小规模时，一个 `map` 或 `set` 往往最清晰：状态直观、更新容易、便于核对。只有请求频繁、数据很大，或空间与延迟成为约束时，才值得换专用结构。

| IM 请求形状 | 结构能力 | 返回的含义 | 业务上是否还要确认 |
|---|---|---|---|
| 输入会话前缀，补全关键词 | Trie（前缀树）共享公共前缀，能沿字符路径定位 | 精确找出当前词典中该前缀下的候选 | 通常不需再确认；但词典版本必须正确 |
| 标记稠密整数设备号是否在线 | 位图按整数下标存一位 | 精确在线/离线状态 | 不需确认；需保证设备号范围与快照一致 |
| 查询消息 ID 是否可能存在 | Bloom 过滤器用多个哈希位近似成员判断 | “肯定不在”或“可能在” | “可能在”必须查权威集合 |
| 反复问两点是否连通，只增加边 | 并查集维护连通分量代表元 | 对已加入的边集合给出精确连通性 | 不需确认；删除边或历史版本不适用 |

可把 `map` 看作基线实现：`前缀扫描全部键`、`set` 保存在线设备、`set` 保存消息 ID、图搜索判断连通。它们语义清楚，却可能分别付出全表扫描、较高对象开销、昂贵内存和重复搜索的代价。

注意“精确结构”只对其输入状态精确：过期在线快照、漏加关系边、错误词典都会导致错误业务结论；Bloom 的特殊之处是即使输入正确，也允许“误报”，但不应把不存在的元素判成“肯定不在”。

### Trie：从前缀走到词尾

### Trie：从前缀走到词尾

设本地工具记录过关键词：`会议`、`会话`、`会话纪要`、`会务`。若用 `map`，可保存“词 → 统计信息”，但输入前缀 `会` 后仍要扫描许多键来找匹配项。Trie（前缀树）把公共开头直接放进路径：

- 根节点
  - `会`
    - `议` `●`
    - `话` `●`
      - `纪`
        - `要` `●`
    - `务` `●`

沿输入字符逐层走：输入 `会`，到达 `会` 节点，子树中的所有终止词都是候选；输入 `会话`，到达 `话` 节点，可补全 `会话` 与 `会话纪要`；输入 `会纪` 时找不到对应边，应立刻返回空，而不是继续搜索整张词表。

`●` 是终止标记，表示“从根到此处的字符串本身是完整关键词”。它不能省略：`会话` 既是一个词，又是 `会话纪要` 的前缀；若只看叶子节点，会错误漏掉 `会话`。

节点的边通常标记为字符，但“字符”必须先定义文本单位。若业务按用户可见字输入，不能把 UTF-8 字节当作边；中文通常可按 Unicode 码点处理，而包含组合字符或复杂表情时，更稳妥的是按用户感知字符簇切分。插入与查询必须采用同一规则，否则视觉相同的文本也可能走向不同路径。

补全时，先精确走完输入前缀，再只遍历该节点的子树；遍历到终止标记便产出一个候选。实际工具还应设定边界：最多返回 $k$ 个结果、限制最大深度，并可按节点保存的热度排序，而非无界地枚举所有后缀。Trie 精确表示已插入的词；补全是否符合用户意图，则还取决于词库版本、排序信号与文本规范化是否正确。

### 位图：设备号映射到比特

### 位图：设备号映射到比特

设本次纸上快照的设备号范围为 $0\sim31$，其中在线设备为 `{1, 3, 8, 9, 17, 31}`。位图为每个可能的整数号预留一位：第 $d$ 位为 `1` 表示设备 $d$ 在线，为 `0` 表示离线。

若按每字节 8 位存储，则：

| 设备号 $d$ | 字节下标 | 位偏移 |
|---:|---:|---:|
| 1 | $1/8=0$ | $1\bmod8=1$ |
| 9 | $9/8=1$ | $9\bmod8=1$ |
| 17 | $17/8=2$ | $17\bmod8=1$ |
| 31 | $31/8=3$ | $31\bmod8=7$ |

因此需 `ceil(32/8)=4` 字节。采用“低位对应较小设备号”的约定，四个字节依次为：

`00001010 00000011 00000010 10000000`

查询设备 `17` 是否在线，只需计算：

`byte = 17 >> 3 = 2`，`bit = 17 & 7 = 1`，再检查 `bitmap[2] & (1 << 1)` 是否非零。

位图的空间取决于**编号上界**，约为 $U/8$ 字节；集合的空间主要取决于实际在线数 $n$。当设备号稠密、范围可控且快照中多数号码都可能出现时，位图通常更省空间，也支持极快的按位扫描、交并差操作。若设备号是稀疏的巨大 ID，例如最大值为 $10^{12}$、实际仅在线 100 台，则位图会浪费大量空位，集合更合适。

这里的 `1` 只表示“该快照版本中在线”，不表示设备此刻仍在线。必须同时保存快照时间或版本号；拿旧位图回答“现在是否在线”，是版本语义错误，不是位图查询错误。

### Bloom：只做消息 ID 预筛

### Bloom：只做消息 ID 预筛

Bloom 过滤器适合回答一个非常克制的问题：**某个消息 ID 能否肯定不在权威集合中？**它不保存完整 ID，而是维护长度为 $m$ 的位图，并为每个 ID 计算 $k$ 个哈希位置。

插入消息 ID `x` 时：

1. 计算 $h_1(x), h_2(x), \dots, h_k(x)$；
2. 将对应位图位置全部置为 `1`。

查询 `y` 时检查这 $k$ 个位置：

- 只要有一位是 `0`：`y` **必不在**已插入集合中，可跳过昂贵的权威集合查询。
- 全部为 `1`：`y` **可能在**集合中，必须继续查询权威消息 ID 集合。

原因是不同 ID 可能把相同位置置为 `1`。例如 `A` 与 `B` 从未插入过，但 `A` 的三个位置恰好分别被其他消息标记；查询 `A` 会得到“可能在”。这是假阳性。标准 Bloom 过滤器不会产生假阴性：已正确插入且位图未丢失的 ID，不会被判为“必不在”。

因此，本地工具的安全流程应是：

`Bloom 判定全为 1` → 查权威集合 → 权威集合确认不存在才返回 `409`

而不是：

`Bloom 判定全为 1` → 直接返回 `409`

前者只是预筛，减少无谓查库；后者把概率结构误当权威来源，会把真实不存在的消息错误报告为冲突。位图大小 $m$、哈希数 $k$ 与已插入数量共同决定假阳性率：数据越多、位图越小，误报越多；它们不改变“出现 0 就必不在”的逻辑。

### 并查集：只增边的连通判断

### 并查集：只增边的连通判断

把每个用户或设备看作顶点，每条“已建立关系”看作无向边。若边只会增加，反复询问“`a` 与 `b` 是否已连通”，并查集维护的正是连通分量。

初始时每个点各自成组：

`parent = [0, 1, 2, 3, 4]`

加入边 `(0,1)`、`(1,2)`：

- `union(0,1)`：合并 `{0}` 与 `{1}`
- `union(1,2)`：先找到 `1` 所在组，再合并 `{0,1}` 与 `{2}`

此时 `find(0) == find(2)`，所以 `0` 与 `2` 连通；而 `find(0) != find(4)`，所以 `0` 与 `4` 不连通。实现中通常配合**路径压缩**与**按大小合并**，使连续操作的均摊代价接近常数。

与每次查询都做图搜索相比：

- 图搜索：保存邻接表后，从 `a` BFS/DFS 到 `b`；适合需要找路径、枚举邻居或边会删除的场景。
- 并查集：不保存具体路径，只回答“是否同一连通分量”；适合大量加边与连通性查询。

它的承诺有明确边界：

- 删除边后，原有集合可能需要拆分，并查集不能直接修复。
- 查询必须对应同一份关系快照：用今天新增的边回答昨天的快照，会得到版本错误的结论。
- 并发执行 `union` 时，父指针和集合大小更新必须同步；否则可能丢失合并或形成不一致状态。

因此，并查集不是通用图数据库，而是“只增边、只问连通”的精确专用结构。

> **要点** — 专用结构服务于特定查询形状；Bloom仅作预筛，并查集仅适合无删除的增量连通。

Trie以连续文本单位共享前缀路径，适合关键词补全；但命中仅是候选，仍须经过业务权限与确认。

### 从查询形状识别前缀树

### 从查询形状识别前缀树

IM 搜索框中的“输入几个字，立刻补全关键词”具有典型的前缀查询形状：用户输入 `会`、`会话`，系统要找出所有**以该连续开头**的词项，例如：

- `会话`
- `会话历史`
- `会话列表`

Trie 把每个字符（更准确地说，实现中通常按 Unicode 码点）作为一条边。三者共享 `会 → 话`，随后再分叉：

`根 → 会 → 话（完整词项） → 历 → 史（完整词项）`  
`　　　　　　　　　　　 └→ 列 → 表（完整词项）`

其中“完整词项”标记不可省略：若只有路径而没有终止标记，`会话` 既可能是已收录关键词，也可能只是 `会话历史` 的中间前缀。

因此，Trie 擅长的问题是：

1. 沿输入前缀走到对应节点，成本约为 $O(L)$，其中 $L$ 是前缀长度；
2. 从该节点向下枚举词项，得到补全候选；
3. 总成本还应加上枚举和输出的部分，不能把“返回 N 个结果”简单说成 $O(L)$。

它不等同于任意文本检索。查询 `历史` 时，普通 Trie 无法直接找到包含该片段的 `会话历史`；查询“昨天提到会话的消息”也需要倒排索引、全文检索或语义检索等结构。Trie 回答的是“哪些词从这个前缀开始”，而不是“哪些文本在任意位置包含它”。此外，补全命中只是候选；用户是否有权查看某会话，仍必须由后续权限校验决定。

### 手画共享路径与终止标记

### 手画共享路径与终止标记

把每个字符看作一条边上的标签，三个词可合并其公共前缀：

```text
根
└─ 会
   └─ 话  ●「会话」是完整词项
      ├─ 历
      │  └─ 史  ●「会话历史」是完整词项
      └─ 列
         └─ 表  ●「会话列表」是完整词项
```

插入时，先写入“会话”：沿 `根→会→话` 建立路径，并在“话”节点记下终止标记。再插入“会话历史”与“会话列表”时，前两条边已经存在，只需分别从“话”继续分出 `历→史`、`列→表`。

终止标记不可省略。若只凭“节点存在”判断单词是否存在，那么查找“会话”会到达“话”节点；但此时无法区分两种词表：

- 词表只有“会话历史”“会话列表”：`会话`只是公共前缀；
- 词表同时有“会话”“会话历史”“会话列表”：`会话`本身也是词项。

因此，**路径存在**回答“某串是否为已存字符串的前缀”，而“到达节点且带终止标记”才回答“该串是否为完整词项”。终止标记还可附带词频、词项编号等信息；删除“会话”时只清除其标记，不能误删仍被两个长词共享的前缀路径。

### 按码点走边而非按字节截断

### 按码点走边而非按字节截断

Go 的 `string` 保存的是 UTF-8 **字节序列**，不是“每个字符一个槽位”。汉字“会”通常占 3 个字节；若 Trie 按 `word[i]` 取值，走到的是单个 `byte`，会把“会”拆成多个无意义的 UTF-8 片段，既不符合教学图中“会→话”的边，也容易在截取前缀时切进多字节字符内部。

按 Unicode 码点建边时，应使用：

`for _, r := range word { ... }`

其中 `r` 是 `rune`，可表示一个 Unicode 码点。因此词表中的：

- `会话`
- `会话历史`
- `会话列表`

会先共享码点边“会”“话”，再从“话”分出“历”与“列”。查询前缀也应以同样方式遍历；不要把“取前两个字节”误当作“取前两个汉字”。

不过，码点相同并不等于文本语义完全相同。大小写、全角半角、组合字符与预组合字符可能形成不同码点序列；中文词语的分词、繁简转换、同义词也不会由 Trie 自动解决。是否进行 Unicode 规范化、大小写折叠或业务词表归一化，应在插入与查询两端采用一致规则。

### 查询成本包含枚举与输出

### 查询成本包含枚举与输出

设前缀长度为 $L$。在 Trie 中定位前缀节点，需依次沿字符边前进，因此路径成本是 $O(L)$；例如查找“会话”，经过“会→话”即可到达对应节点。

但“补全查询”通常还要求返回结果。若从该节点向下找到 $N$ 个完整词项，例如“会话”“会话历史”“会话列表”，还必须：

- 遍历子树中的节点和边，直到收集到足够候选；
- 检查每个节点的词项结束标记；
- 构造并保存结果字符串；
- 将结果写入响应或界面。

因此，更准确的成本应写成：

$$
O(L + V + \text{输出大小})
$$

其中 $V$ 是为找到这 $N$ 条结果实际访问的子树节点数。若只取前 $N$ 条并在遍历中提前停止，$V$ 可能较小；若前缀下结果稀少、需要过滤，或必须遍历完整子树，$V$ 可能接近该子树规模。

若结果还要按热度、字典序或其他规则排序，排序成本也不能省略。对收集到的 $M$ 条候选排序通常为：

$$
O(M \log M)
$$

所以，“Trie 前缀查找是 $O(L)$”只描述**定位前缀节点**；完整的自动补全查询还包含枚举、过滤、排序与输出。

### 实现取舍与IM确认边界

### 实现取舍与 IM 确认边界

Trie 的关键取舍在于“每个节点如何保存子边”。

- **映射子边**：如 `map[rune]*Node`。只为实际出现的字符分配边，适合汉字、表情等稀疏且字符集很大的场景；代价是映射本身有额外对象、哈希和指针开销。
- **完整字符表**：为每个节点预留固定大小的子指针数组。查边可直接按下标访问，常数较小；但若字符表很大、节点多数分叉很少，会浪费大量空位。它更适合字母表小且稳定的键，例如仅含 `a-z`。
- **压缩前缀**：将只有一个子节点的连续链合并为一条带字符串片段的边。例如“历→史”可压成“历史”。节点数和指针数更少，适合长词、低分叉词表；但插入、删除和按字符分裂边更复杂。

Go 中若按 Unicode 码点建边，应使用：

`for _, r := range word { ... }`

而不是按字节把 UTF-8 汉字拆开。实际系统还应明确大小写折叠、Unicode 规范化、繁简转换和分词策略；Trie 只存储给定的连续单位，并不会自动理解“同义”或“等价”。

在 IM 搜索中，前缀命中只是**候选召回**。即使用户输入命中“会话历史”，也必须在返回前校验：该用户是否仍是会话成员、消息或会话是否已删除、权限是否因角色或时间变化而失效、客户端持有的会话版本是否过期。最终的“打开会话”“发送消息”“导出历史”等操作还要由服务端再次确认，不能把 Trie 的命中结果当作授权结论。

> **要点** — Trie按连续文本单位共享前缀；终止标记区分完整词，补全成本还取决于结果枚举，命中不等于授权。

位图用一个位表示一个固定编号对象的状态，适合稠密编号下的精确快照；但它不能替代身份、授权、送达确认或并发控制。

### 从设备编号到一字节位图

### 从设备编号到一字节位图

若设备编号固定为 `0…7`，可用一个字节保存这 8 个设备的标记状态。约定：**编号 `i` 对应第 `i` 个二进制位，最低位 `bit0` 对应编号 0**。因此，某设备是否被标记可由该位是 `1` 还是 `0` 表示。

例如，设备 `1`、`3`、`6` 被标记：

- 设备 1：$2^1=2$
- 设备 3：$2^3=8$
- 设备 6：$2^6=64$

总值为：

$$
2^1+2^3+2^6=2+8+64=74
$$

`74` 的八位二进制写作 `01001010`。这里从左到右展示的是 `bit7…bit0`，所以最右侧才是编号 0；`bit6`、`bit3`、`bit1` 为 `1`，正好对应集合 `{1,3,6}`。

检查设备 `3` 是否被标记，可计算：

`mask & (1 << 3)`

结果非 `0` 表示该位为 `1`。标记某设备使用按位或：`mask | (1 << i)`；取消标记使用按位与配合取反：`mask & ~(1 << i)`。两个设备集合的并集可用按位或，交集可用按位与。

这表示的是某一时刻的精确标记快照：位为 `1` 不自动说明设备仍在线、连接仍存活，或消息已经送达。

### 手算标记、查询与位序

### 手算标记、查询与位序

规定设备编号为 `0…7`，并令**最低位** `bit0` 对应 0 号设备；`bit1` 对应 1 号设备，依此类推。若 1、3、6 号设备被标记为 1，其余为 0，则该字节的数值是各置位权重之和：

$$
2^1+2^3+2^6=2+8+64=74
$$

因此十进制值为 `74`。

将一个字节按通常书写方向从左到右写成 `bit7…bit0`：

| 位序 | bit7 | bit6 | bit5 | bit4 | bit3 | bit2 | bit1 | bit0 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 标记值 | 0 | 1 | 0 | 0 | 1 | 0 | 1 | 0 |

所以二进制表示为：

`01001010`

注意：左边第一个字符是 `bit7`，不是 0 号设备。设备编号从右向左增加，这正是手算时最常见的位序错误。

检查编号为 `k` 的设备是否已标记，可构造掩码 `1 << k`，再做按位与：

- 查 3 号：`74 & (1 << 3)`，即 `01001010 & 00001000 = 00001000`，结果非零，说明 3 号已标记。
- 查 2 号：`74 & (1 << 2)`，即 `01001010 & 00000100 = 0`，说明 2 号未标记。
- 查 6 号：`74 & (1 << 6)`，结果为 `64`，说明 6 号已标记。

这里的 `1` 只表示该固定快照中对应编号被设置；它本身不证明设备在线、会话有效或消息已经送达。

### 用按位运算处理集合关系

### 用按位运算处理集合关系

设一字节的 bit0…bit7 分别对应设备 `0…7`。若集合 $A=\{1,3,6\}$，则：

`A = 01001010`（十进制 `74`）

再设集合 $B=\{3,4,6,7\}$：

`B = 11011000`（十进制 `216`）

按位运算逐位处理，因此可直接表达集合关系：

- **交集：按位与 `&`**  
  `A & B = 01001000`，得到 $\{3,6\}$。只有两边都为 `1` 的设备保留，可理解为“同时具有两种标记”的对象。

- **并集：按位或 `|`**  
  `A | B = 11011010`，得到 $\{1,3,4,6,7\}$。任一集合出现过的设备均为 `1`。

- **对称差：按位异或 `^`**  
  `A ^ B = 10010010`，得到 $\{1,4,7\}$。两边状态不同的位置为 `1`；共同拥有的 `3、6` 被抵消。异或适合比较两个快照哪些编号发生变化，但不说明变化方向。

- **删除某个成员：与反掩码相与**  
  要从 $A$ 清除设备 `3`，先构造掩码 `1 << 3 = 00001000`，再计算：  
  `A & ~(1 << 3) = 01000010`，结果为 $\{1,6\}$。

- **加入某个成员：与单位置位掩码相或**  
  加入设备 `4`：  
  `A | (1 << 4) = 01011010`，得到 $\{1,3,4,6\}$。

这些结果仅是某一时刻标记集合的精确计算；例如“在线位”相交不等于网络连接仍有效，更不等于消息已经送达。

### 位图成立的编号与生命周期前提

### 位图成立的编号与生命周期前提

位图的第 $i$ 位只能表示“编号 $i$ 的对象处于某状态”，因此它首先依赖一个**稠密、稳定、可解释**的整数编号空间。

若设备号固定为 `0…7`，第 3 位对应 3 号设备，位置与对象的关系直接、唯一，位图既紧凑又精确。反之，真实系统常见的 `user_id`、`device_id` 可能是字符串、雪花 ID 或稀疏大整数：

- 若仅使用 `17`、`900000000`、`4000000000` 三个整数 ID，按最大值开位图需要约 5 亿字节，远不如保存三个键值对。
- 若 ID 是字符串，必须先维护“字符串 $\rightarrow$ 小整数槽位”的映射表；位图节省的空间，可能被映射表、索引和回收元数据抵消。
- 映射不是纯技术细节：它定义身份。`alice-phone` 映射到槽位 42 后，槽位 42 的第 1 位才有明确含义。

更危险的是**位置复用**。旧设备注销后，若其槽位 42 被分配给新设备，而旧状态、缓存或异步任务仍携带“42”，就可能把旧设备的在线、已读或订阅状态错误赋给新设备。稳妥做法包括：

- 槽位附带版本号或 generation，引用使用 `(slot, version)`；
- 删除时清除相关位，并使旧版本失效；
- 延迟复用槽位，等待缓存、消息和后台任务越过安全窗口；
- 将位图视为派生快照，权威身份仍由数据库或目录服务确认。

因此，位图适合“固定工位 0…N-1 是否占用”这类状态，不天然适合开放世界中的用户身份。即使某一位为 `1`，它也只是当前快照中的标记，不能自动证明该对象仍存在、会话仍有效，或拥有访问权限。

### IM快照不能冒充业务事实

### IM快照不能冒充业务事实

在线位、群成员位等位图只描述某个时刻的**本地状态快照**。例如 `online_bits` 的第 6 位为 `1`，最多表示“快照生成时，编号 6 被记录为在线”；它不能证明连接此刻仍存活，更不能证明该用户有权访问某资源。

应明确区分：

- **成员位**：可作为“已知群成员集合”的紧凑缓存，但加入、退出、踢出后必须更新；旧编号若被复用，不能继承前一用户的成员状态。
- **在线位**：适合推送候选筛选或显示在线人数。发送消息前仍应检查当前会话、连接代际或心跳状态；位为 `1` 不等于连接可写。
- **授权判断**：必须基于用户身份、会话、群关系、封禁状态等权威数据执行。对非成员返回隐藏式 `404`，不能仅因某个成员位为 `1` 就放行。
- **送达事实**：`200 accepted_in_memory` 只表示服务端暂存或接受请求；不能由“接收者在线位为 `1`”推导为消息已到达 B，更不等于已读。送达、已读需要独立的消息序号、确认记录与状态机。

删除、下线或退出时，要清除相应 bit，并以版本号、事件日志或原子替换保证快照不会长期陈旧。多个线程同时修改同一字节时，普通“读—改—写”会丢失更新；应使用锁、原子位操作或单线程状态归属。位图节省的是空间，不会自动提供身份隔离、一致性或并发安全。

> **要点** — 位图是稠密稳定编号上的精确状态快照；位为 1 只表示已标记，不能直接证明授权、在线或消息送达。

Bloom 适合做低成本预筛：它能可靠排除“不在”，却不能替代权威存储确认“在”。

### 从查询形状识别 Bloom 的职责

### 从查询形状识别 Bloom 的职责

设消费者收到消息 ID `m`，真正想回答的往往不是“`m` 是否存在”，而是：

> 是否值得访问较慢、较贵但权威的去重库，确认这条消息是否已处理？

Bloom 过滤器正适合放在这个查询之前：

1. 查询 Bloom；
2. 若结果为“必不在”，可跳过权威库查询，并把 `m` 视为首次见到；
3. 若结果为“可能在”，再查数据库、持久化去重表或状态存储；
4. 只有权威库的结果才能决定“已处理”还是“尚未处理”。

例如，`m-x→{1,6}` 的两个位都已被其他消息置为 `1`，Bloom 会回答“可能在”。这不是“已处理”的证据；若直接丢弃 `m-x`，就会把一条实际未处理的消息误判为重复消息，造成漏处理。

相反，`m-y→{0,6}` 遇到 `bit0=0` 时，Bloom 可在其正确使用前提下给出“必不在”。此时它提供的是负面证据：当前集合中不可能已有该 ID。

因此，Bloom 的典型查询形状是：

`候选 ID → Bloom 排除 → 必要时权威确认`

它优化的是“减少无谓查库次数、降低延迟和存储压力”，不是替代数据库承担存在性裁决。位图越满，“可能在”的比例越高，预筛收益也会下降；仍不能把“可能在”当作确定结论。

### 位数组与多个确定位置

### 位数组与多个确定位置

普通 Bloom filter 的核心状态是一段长度为 $M$ 的位数组，初始时所有 bit 都是 `0`。对每个 ID，用 $k$ 个**确定性**位置计算规则得到下标：

$$
p_i(x)\in[0,M-1],\quad i=1,\dots,k
$$

插入 ID `x` 时，不保存 `x` 本身，而是执行：

`bits[p1(x)] = bits[p2(x)] = ... = bits[pk(x)] = 1`

例如 $M=8,k=2$，人为规定：

- `m-1 → {1,5}`：置 `bit1`、`bit5` 为 `1`
- `m-2 → {2,6}`：置 `bit2`、`bit6` 为 `1`

插入两者后，位数组可写作：

`[0,1,1,0,0,1,1,0]`

这里的“多个位置”不是每次随机挑选；同一个 ID 在同一 Bloom 配置下必须总得到同一组位置。否则，写入时置的是一组 bit，查询时检查的却是另一组 bit，即使 ID 确实插入过，也可能错误得到“必不在”。

因此，位置计算依赖的参数必须一致，包括位数组长度 $M$、哈希算法或派生规则、哈希个数 $k$、以及 ID 的规范化方式。例如写入前将 `M-1` 转成小写，而查询仍使用原字符串 `m-1`，两端可能计算出不同下标。

$M$ 决定可用槽位多少，$k$ 决定每次插入要置多少位。元素不断加入时，更多 bit 被置为 `1`；数组越满，未插入 ID 的多个位置也越可能恰好全为 `1`。

### 纸上演算：必不在与可能在

### 纸上演算：必不在与可能在

设 Bloom filter 只有 8 个 bit，编号为 `0` 到 `7`；每个 ID 由两个确定的哈希位置表示。初始状态全为 `0`：

`[0,0,0,0,0,0,0,0]`

插入 `m-1`，其位置为 `{1,5}`，将 bit1、bit5 置为 `1`：

`[0,1,0,0,0,1,0,0]`

再插入 `m-2`，其位置为 `{2,6}`：

`[0,1,1,0,0,1,1,0]`

现在查询从未插入过的 `m-x`，假定它的两个位置是 `{1,6}`。bit1 和 bit6 都是 `1`，Bloom filter 只能回答：**可能在**。

但这两个 `1` 分别可能来自不同元素：bit1 来自 `m-1`，bit6 来自 `m-2`。过滤器只记录“哪些位置曾被置位”，不记录“这些位属于哪个 ID”，于是产生假阳性。

再查询未插入的 `m-y`，其位置为 `{0,6}`。虽然 bit6 为 `1`，但 bit0 仍为 `0`：

`bit0=0, bit6=1`

只要哈希规则一致、插入过程完整且位数组未被错误清除，`m-y` 就能被确定判为：**必不在**。因为若它真的插入过，bit0 必然已经被置为 `1`。

因此，Bloom filter 的查询语义不是二值“存在/不存在”，而是：

- 任一目标位为 `0`：**必不在**
- 所有目标位为 `1`：**可能在，仍需权威存储确认**

随着更多 ID 加入，数组中 `1` 的比例上升，像 `m-x` 这样“借用别人置位结果”的假阳性会更常见。

### 假阳性为何不能直接返回 409

### 假阳性为何不能直接返回 409

Bloom filter 的阳性语义只是“`可能见过`”，不是“该 ID 已被权威系统接受”。因此，若接口收到创建请求后仅因 Bloom 查询全为 1 就返回 `409 Conflict`，会把假阳性误报成真实冲突：用户从未创建过的订单、消息或幂等请求，可能被无故拒绝。

更稳妥的流程是把 Bloom 放在**减少昂贵查询**的位置：

1. Bloom 返回“必不在”：通常可直接尝试写入数据库，或投递消息；仍应由唯一约束、幂等记录等权威机制兜底。
2. Bloom 返回“可能在”：查询数据库唯一索引、幂等键表或消息消费记录。
3. 权威存储确认存在：再按业务语义返回成功重放结果、已有资源，或 `409 Conflict`。
4. 权威存储确认不存在：说明这是 Bloom 假阳性，应继续创建或处理消息。

例如创建用户名 `alice` 时，Bloom 阳性只能触发：

`可能重复 → 查询 users.username 唯一索引 → 确认 alice 已存在 → 返回 409`

而不能省略中间确认。`409` 表达的是已确认的业务状态冲突，不是概率结构的猜测。

还要区分三个层次：Bloom 用于**去重预筛**；数据库唯一索引或条件写入负责**冲突裁决**；HTTP 响应负责向调用方表达**最终结果**。即使 Bloom 判定“必不在”，并发请求也可能同时通过预筛，所以最终仍必须依赖原子唯一约束或事务保证“只有一个写入成功”。

### 容量、版本与并发的使用边界

### 容量、版本与并发的使用边界

Bloom filter 的误判率取决于位数组长度 $m$、哈希个数 $k$ 与已插入元素数 $n$。近似地，

$$
p \approx \left(1-e^{-kn/m}\right)^k
$$

在 $n$ 不变时，$m$ 越大，位越稀疏，误判越少；在 $m,k$ 不变时，$n$ 越大，更多位被置为 1，误判会持续上升。$k$ 也不是越多越好：哈希太少会覆盖不足，太多则使位图更快变满；常见近似最优值为 $k\approx (m/n)\ln2$。

| 变化 | 主要结果 | 代价或风险 |
|---|---|---|
| 增大位数 $m$ | 降低误判率 | 更多内存、传输与持久化成本 |
| 增大元素量 $n$ | 位图更满、误判升高 | 原容量规划失效 |
| 增大哈希数 $k$ | 初期可降低误判 | 查询更慢，过大反而恶化 |
| 降低 $k$ | 操作更快 | 可能未充分利用位图 |

普通 Bloom filter 不能安全删除：删除某个 ID 的位，可能同时清除了其他 ID 依赖的位，造成本不应出现的假阴性。需要删除时，可用“计数 Bloom filter”为每个位置保存计数器；但它占用更多空间，并须防止计数溢出与错误减计数。

过滤器还应带有版本边界。哈希算法、种子、$m$、$k$、编码规则或分片方式任一改变，旧位图都不能按新规则直接查询；应保存参数版本，采用双读、重建或新旧过滤器并行迁移。

并发插入也不能把“置位”视为天然安全：多个写入若使用非原子读—改—写，可能互相覆盖，导致已插入元素出现假阴性。应使用原子位操作、分片锁，或由支持原子 `SETBIT` 类操作的存储负责更新。Bloom 的“可能在”仍必须由权威数据库、索引或对象存储最终确认。

> **要点** — Bloom 的零位可证明必不在；全为一仅表示可能在，业务结论必须由权威数据确认。

并查集不记录“关系边”，而是高效维护“当前是否同属一个连通组”。关键是先识别它适用的查询形状与业务边界。

### 从连通查询识别并查集

### 从连通查询识别并查集

当问题反复出现为“编号 `a` 与 `b` 当前是否属于同一组？”时，应想到并查集。它维护的是若干**互不相交集合**：每个元素恰好属于一个集合，`Find(x)` 找到 `x` 所在集合的代表，比较代表即可判断连通性：

`Find(a) == Find(b)` 表示当前连通；否则不连通。

例如初始时 `0…4` 各自独立：

- `Union(0,1)`、`Union(1,2)` 后，`{0,1,2}` 成为一组；
- `Union(3,4)` 后，`{3,4}` 成为另一组；
- 因而 `Find(0)==Find(2)` 为真，`Find(0)==Find(4)` 为假。

实现中通常令每个元素的 `parent` 指向父节点，根节点作为集合代表。代表可能是 `0`、`1` 或 `2`，取决于合并顺序与策略；对外真正稳定的结论是“是否同组”，而非“根编号是谁”。

并查集适合两个前提：

1. 关系可视为**无向连通**：`a` 连到 `b`，则 `b` 也连到 `a`。
2. 操作以**增加关系、查询连通**为主；合并后通常不需要撤销。

它不保存原始边，也不能回答“`a` 到 `b` 具体经过哪些节点”。若要找路径，应使用 BFS/DFS；若关系会删除、需要保留历史版本或具有方向性，普通并查集也不够。

### 手画父节点与集合代表

### 手画父节点与集合代表

把每个元素看成一个节点，`parent[x]` 指向它的父节点；根节点满足 `parent[x]=x`，它就是该集合当前的代表。

初始时 0～4 各自独立：

`parent = [0, 1, 2, 3, 4]`

可画为：

- `0 → 0`
- `1 → 1`
- `2 → 2`
- `3 → 3`
- `4 → 4`

执行 `Union(0,1)`。假设把 1 的根接到 0 的根下：

- `1 → 0 → 0`
- 其余不变

此时 `parent` 可写为 `[0, 0, 2, 3, 4]`。

再执行 `Union(1,2)` 时，先找根：`Find(1)=0`，`Find(2)=2`。将 2 所在树接到 0 所在树：

- `1 → 0`
- `2 → 0`
- `0 → 0`

于是 0、1、2 同属一组。接着执行 `Union(3,4)`：

- `4 → 3 → 3`

现在集合划分为 `{0,1,2}` 与 `{3,4}`。

因此：

- `Find(0)=0`，`Find(2)=0`，所以 `Find(0)==Find(2)`，两者同组；
- `Find(4)=3`，所以 `Find(0)!=Find(4)`，0 与 4 异组。

若合并时选择相反方向，代表可能变成 1、2 或 4；只要同一组元素最终追溯到同一个根，结论就不变。`parent` 记录的是集合组织方式，不等于原始图中永久存在的边。

### 按规模合并与路径压缩

### 按规模合并与路径压缩

朴素 `Union(a,b)` 若总是把 `root(a)` 接到 `root(b)` 下，连续执行 `Union(0,1)`、`Union(1,2)`、`Union(2,3)`……可能得到深链：

`0 → 1 → 2 → 3 → 4`

此时 `Find(0)` 必须逐层追到根，单次代价为 $O(n)$。大量查询时，链越长越慢。

**按规模合并**维护每棵树的节点数 `size[root]`：总是把较小树的根接到较大树根下。因为一个节点的深度每增加 1，它所在树的规模至少翻倍，所以深度至多为 $O(\log n)$。按秩合并也是同一思想：`rank` 近似记录树高，低秩根挂到高秩根下。

```text
Find(x):
  若 parent[x] != x：
      parent[x] = Find(parent[x])   // 路径压缩
  返回 parent[x]
```

路径压缩会把查找路径上的节点直接改指向根。例如原有 `0 → 1 → 2 → 3`，执行 `Find(0)` 后可变为 `0 → 3`、`1 → 3`、`2 → 3`。后续查找几乎一步到位。

两种优化结合后，连续 $m$ 次操作的总成本为 $O(m\alpha(n))$，其中 $\alpha(n)$ 是增长极慢的反阿克曼函数，在实际规模中可近似看作常数。注意：压缩改变的是内部 `parent` 结构，不改变“哪些元素同组”的结论。

### 同组结论不等于原始关系

### 同组结论不等于原始关系

并查集回答的是一种压缩后的结论：

> 两个元素当前是否属于同一个连通组？

若执行过 `Union(0,1)`、`Union(1,2)`，则 `Find(0)==Find(2)`，这说明 0 能通过已有的无向关系链间接到达 2；但它**不说明**原始数据中存在边 `0—2`。

例如原始边为：

- `0—1`
- `1—2`
- `2—3`

并查集会把 `0、1、2、3` 合成同一组。因此它能回答“0 和 3 是否连通”，却不能回答：

- 0 到 3 经过哪些节点；
- 1 和 2 是否曾直接建立关系；
- 原始图中到底有哪些边；
- 两点之间是否存在某条满足条件的路径。

更要注意，`parent[x]` 也不是原始关系边。路径压缩后，`parent[3]` 可能直接指向根 `0`；这只是内部优化产生的代表指针，不能解释为“3 和 0 直接相连”。

方向关系同样会丢失。若有 `A \to B`、`B \to C`，把它们送入普通并查集后，只会得到 A、B、C 同组；它无法区分“能从 A 到 C”与“能从 C 到 A”。因此，关注可达方向、依赖方向或权限传播方向时，通常应保留邻接表并使用 BFS/DFS。

选择工具时可这样判断：

- 只增不删的无向关系，反复问“是否同组”：用并查集。
- 要输出一条路径、检查经过哪些点：用 BFS/DFS，并保存原始边。
- 要处理有向可达性：使用有向图上的 BFS/DFS。
- 边会删除，且删除后可能使集合拆分：普通并查集不够，需要动态连通性结构或重新计算。

并查集维护的是“连通块摘要”，不是图本身。

### IM关系中的增量维护边界

### IM关系中的增量维护边界

并查集适合回答一种很窄但很高效的问题：在**只新增无向关系**的前提下，两名用户当前是否已处于同一连通组。例如新增好友关系 `A—B`、`B—C` 后，可用 `Find(A)==Find(C)` 判断三人是否经由好友链相连；合并大型社群的成员网络时，也能快速维护“是否属于同一社交圈”。

但 IM 业务通常不止“加边并查连通”：

- **退群、删好友、拉黑是撤销。** `Union(A,B)` 后，DSU 只知道两者所在集合已合并；即使删除原始关系 `B—C`，它也不知道连通块是否应拆成两部分。普通并查集没有“反向拆集合”操作。
- **群成员关系不是简单好友边。** 用户加入群 `G` 可建模为“用户与群节点连通”，但用户退出群后仍无法从 DSU 中删除该连接；更不能由“曾同群”直接推出当前仍可互相可见或私聊。
- **授权必须看精确、当前的规则。** “同一连通组”不等于“有权限”。管理员角色、群禁言、黑名单、单向关注、有效期、审批状态都具有方向性或条件性；`Find` 的布尔结论无法表达这些约束。
- **版本与并发需要确认语义。** 两端同时加好友、撤销后又重新添加时，系统要依据事件顺序、版本号或事务提交结果确定当前状态。DSU 只能维护某个已确认快照，不能替代关系表、事件日志或权限策略引擎。
- **历史查询需要保留时间维度。** 若要问“昨天 10 点两人是否同群”，应查询历史快照、事件流或版本化数据；普通 DSU 路径压缩会覆盖内部结构，不能自然回读旧状态。

因此，可把并查集当作“已确认、只增关系”的连通性加速器；好友原始边、群成员表、撤销记录与授权判定仍应由可审计的业务数据维护。

> **要点** — 并查集适合只增加无向关系后的重复连通查询；它给出同组，不保存边、路径，也不能处理删除拆分。

专用结构的正确性不只取决于算法，还取决于输入版本、编号规则与更新维护是否可追溯。

### 先定义数据版本与失效条件

### 先定义数据版本与失效条件

任何 Trie、位图、Bloom 过滤器或并查集，都应先回答：**它表示的是哪一版输入数据？** 结构本身不是事实来源，而是对某个数据快照或增量日志的编码。若无法追溯版本，即使查询速度正确，也无法保证结果仍适用于当前业务。

可为每个结构记录最小元数据：

- `source_version`：来源词表、设备目录、消息表或边集合的版本号、时间戳或日志偏移量。
- `build_version`：结构构建程序、哈希函数、编号规则与参数版本。
- `covered_range`：已纳入的增量范围，例如“处理到事件序号 18342”。
- `valid_until`：触发失效的条件，而不只是一个模糊的过期时间。
- `rebuild_policy`：失效后全量重建、增量更新，还是直接禁止查询。

统一判断可写成：

$$
\text{可使用} \iff
V_{\text{source}}=V_{\text{covered}}
\land R_{\text{mapping}}\text{ 未变}
\land A_{\text{assumption}}\text{ 仍成立}
$$

其中，$R_{\text{mapping}}$ 是编号或哈希映射规则，$A_{\text{assumption}}$ 是结构依赖的维护前提。

例如：

- Trie 的关键词库新增、删除或分词规则变更后，旧 Trie 只能表示旧词表；若用于权限词、风控词或路由词，应重建或明确降级。
- 位图一旦设备 ID 到整数下标的映射被复用、重排或分片迁移，旧 bit 的语义即失效，不能继续解释为“该设备已出现”。
- Bloom 过滤器可在只追加元素时增量维护；若存在删除、哈希函数变更或过滤器重置，则必须采用支持删除的设计，或重新构建。否则“某位为 0 则元素必不存在”的结论不再可靠。
- 并查集适合只增加边的连通性快照；边删除、回滚、节点编号重用或历史版本查询出现时，普通并查集应视为失效，而非继续报告旧连通关系。

尤其要区分“允许近似”与“允许陈旧”。Bloom 的误判是受参数约束的近似；词表漏更新、位图错编号、并查集未处理撤销，则是输入版本失配。前者可量化，后者应阻止结构承担最终决策。

### Trie：词表版本决定前缀召回

### Trie：词表版本决定前缀召回

Trie（前缀树）把词表中的文本单位逐字符或逐词元展开，共享相同前缀；某条路径末端的`终止标记`表示“这里是一个完整关键词”。查询前缀`北`时，沿路径找到节点后，枚举其子树中所有带终止标记的路径，才得到`北京`、`北方`等候选词。

因此，前缀召回正确性依赖三个共同条件：

- **终止标记正确**：若`北京大学`已插入却未在末节点标记终止，系统可能只能返回更长词，或完全不把它视为合法关键词。反之，把中间节点误标为终止会产生并不存在的短词。
- **文本单位一致**：按字符建树时，`AI助手`、`ＡＩ助手`、`ai 助手`是否归为同一词，取决于大小写、全半角、空白、Unicode 规范化等预处理规则。建树与查询使用不同规则，会导致路径不一致而漏召回。
- **词表版本完整**：Trie 只能返回已写入的词。新上架商品、新增敏感词或改名实体若未增量插入，查询前缀即使完全正确，也会稳定漏掉这些结果。

可将某版本词表记为$V_t$，Trie 返回的是$V_t$中以查询前缀$p$开头的集合，而不是现实中所有应匹配词的集合。词表更新、分片重建、服务重启后，应明确版本号、增量日志与重建完成条件；否则“查询很快”只证明旧索引查得快，不能证明当前结果完整。

### 位图：编号映射不可静默复用

### 位图：编号映射不可静默复用

设系统用位图记录“哪些设备已完成配置”：第 $i$ 位为 `1`，表示设备编号 `i` 已完成。查询与更新都是 $O(1)$，每台设备只需 1 bit；但这个结论隐含前提：**设备编号到位位置的映射在该位图生命周期内稳定且可解释**。

例如，旧设备 `A-17` 曾映射到 bit 42，并被置为 `1`。设备下线后，编号服务把 42 分配给新设备 `B-03`；若位图未清除、未按版本重建，系统会直接把 `B-03` 判为“已完成配置”。这不是位图随机出错，而是旧事实被错误归属给了新实体。

常见风险包括：

- 扩容时改变分片或重排编号，却只搬迁部分 bit；
- 回收设备编号时未清零，或清零与重新分配非原子执行；
- 重启后恢复了位图，却未恢复同版本的编号映射表；
- 多租户共享编号空间，租户维度未编码进位位置；
- 设备目录已更新，消费者仍使用旧编号版本写入。

因此，位图旁应保存映射版本、分片规则和构建时间；编号规则变化、批量回收或目录版本切换时，应整体失效并重建，而非静默沿用。若业务要求“当前设备是否确实完成配置”的最终判断，还应以带设备唯一标识的精确记录为准；位图适合稠密状态加速，不应成为设备身份与历史事实的唯一证据。

### Bloom：预筛结论必须回到精确集合

### Bloom：预筛结论必须回到精确集合

Bloom 过滤器用多个哈希函数把元素映射到位数组。查询某个消息 ID 时：

- 只要有任一对应位为 `0`，可推出“该 ID **必不在**当前过滤器所表示的集合中”；
- 若所有对应位都为 `1`，只能说“该 ID **可能在**”，因为不同 ID 可能碰巧占用同一批位，即存在假阳性。

因此，Bloom 适合降低精确查询次数，例如先过滤明显未见过的候选 ID；但“可能在”绝不能直接当作“已处理、无需投递”或“重复消息”。最终判重、幂等写入和投递确认仍应回到持久化的精确 `map/set`，按当前消息 ID 查询真实记录。

这个“`0` 位必不在”的结论也有维护前提：过滤器必须由正确、完整且版本一致的插入流程构建。若漏插某条已处理消息，查询会得到“必不在”，从而导致重复处理；若把错误 ID 插入，则会增加假阳性，甚至使有效消息被错误跳过。普通 Bloom 过滤器也不能直接删除：清除一个位可能同时清除了其他元素留下的标记，使本应存在的元素被误判为“不在”。需要删除时，应使用计数型 Bloom 过滤器，并保证计数增减与精确集合写入处于可恢复的一致流程。

重启、扩容或更换哈希种子时，旧位图通常不能无条件沿用。必须明确：是从权威精确集合重建 Bloom，还是将其视为失效并暂时退化为精确查询。Bloom 的价值是预筛性能；精确集合才承担最终事实与业务正确性。

### 并查集：增量连通不等于可撤销关系

### 并查集：增量连通不等于可撤销关系

在即时通信中，可把“用户之间已建立可达关系”抽象为无向图：建立群组关联、互加联系人、加入同一协作空间，都可能形成边。并查集用 `find(x)` 判断两人是否属于同一连通分量，用 `union(x, y)` 合并分量；路径压缩与按秩合并后，长期增量查询通常极快。

例如，A 与 B 建立关系、B 与 C 建立关系后：

`union(A, B)`  
`union(B, C)`  
`find(A) == find(C)`

此时并查集可以正确回答：“按已追加的关系记录，A 与 C 已连通。”

但解除关系不是 `union` 的逆操作。若用户撤销 B 与 C 的关系，原集合已经把 A、B、C 压缩到同一代表元；直接删除边无法判断 C 是否仍通过其他路径连接到 A。更危险的是，系统若继续使用旧并查集回答“当前是否可达”，就会把历史连通误报为当前连通，进而错误放行消息投递、联系人推荐或权限继承。

因此，并查集适合以下语义：

- 关系只增加，或查询的是“截至某版本曾形成的连通状态”；
- 批量导入关系后，构建一次静态连通分量；
- 允许删除发生后整体重建，并明确重建期间结果的版本边界。

若业务要求即时解除、审计当前关系或处理封禁，应以带版本的边表、精确图存储或可删除的索引作为事实来源；并查集最多是可丢弃的加速缓存。删除、撤销、账号合并、分库迁移或服务重启后，都应明确其失效条件与重建来源。

> **要点** — 结构快省不等于事实可靠；必须说明数据版本、更新路径、失效条件与最终确认机制。

专用结构的成本不由名称决定，而由词项共享、编号范围、容量上限、更新方式与业务确认链路共同决定。

### 先以小样本数清结构成本

### 先以小样本数清结构成本

不要先问“Trie、位图、Bloom、并查集各占多少内存”，先拿很小的输入手算其状态。结构成本首先取决于输入**形状**，而非元素个数这个单一数字。

- **Trie**：插入 `cat`、`car`、`dog`。根下有 `c`、`d`；`cat` 与 `car` 共享 `c→a`，随后分成 `t`、`r`。若根也计数，共有  
  `root, c, a, t, r, d, o, g`，即 8 个节点，而不是 $3\times3+1=10$。  
  再插入 `cart`，只新增 `t` 一个节点；再插入 `zoo`，则新增 `z→o→o` 三个节点。词项长度相同不代表节点增量相同。

- **位图**：标记用户编号 `3、7、1000`。即使只有 3 个用户，若按最大编号 1000 直接寻址，也至少需要 1001 个 bit，即约 126 字节；编号 `3、7、8` 则只需 9 个 bit。位图对“已用数量”不敏感，对**最大编号范围**敏感。

- **Bloom 过滤器**：设 $m=32$ 位、$k=3$ 个哈希，加入一个词会尝试置 3 位，但碰撞后可能只新增 2 位甚至更少。继续加入词项，置位密度升高；空间仍是 32 位，假阳性却会增加。它节省的是精确集合的存储，不提供“肯定不存在”的零误判承诺。

- **并查集**：元素编号 `0..4` 时，至少有 `parent[5]`；若按大小合并，再有 `size[5]`。加入关系边 `(0,1)`、`(1,2)` 改变的是数组槽中的父指针和集合规模，不会因边数额外保存完整邻接表。若编号跳到 1000，朴素数组实现就要为 `0..1000` 准备槽位。

小样本应记录“每次输入新增了什么状态”：Trie 新节点数、位图最高位、Bloom 新置位数、并查集数组长度与父指针变化。随后再把真实数据的前缀分布、ID 稀疏度和关系增长方式代入，才能避免用平均元素数掩盖第一处坏边界。

### Trie：共享前缀而非词数决定节点

### Trie：共享前缀而非词数决定节点

Trie（前缀树）把词项按前缀合并保存，因此“有多少个词”并不能直接推出“有多少节点”。先手画一组 IM 关键词：

- `@all`
- `@alice`
- `@alex`
- `#公告`

若按字符拆分，根节点下有 `@` 与 `#` 两条边；`@` 后的 `a`、`l` 被三个词共享，直到 `@al` 后才分叉为 `l`、`i`、`e`。`@all` 是 `@alice` 的前缀吗？不是：前者在第二个 `l` 处终止，后者继续到 `i`。因此节点通常还需保存“词在此结束”的终止标记，不能只看是否有子节点。

可将节点数粗略理解为：

$$
N \approx 1+\text{所有词项字符路径的并集长度}
$$

其中 `1` 是根节点。完全没有公共前缀时，$N$ 接近各词长度之和再加根；大量共享前缀时，新增一个词只会增加其与已有路径分叉后的后缀节点。比如已有 `@alice` 后再加入 `@alex`，不会再创建 `@al`，只创建不同后缀所需节点。

估算前必须定义“一个单位”：

- 按字节：实现简单，但 UTF-8 中文字符会拆成多个字节，路径更长。
- 按 Unicode 码点：较符合字符直觉，但组合字符、表情序列未必等于用户看见的一个字。
- 按词元或文本单位：可减少某些路径，但分词规则、词典版本会改变结构。

还要明确终止信息的成本：一个布尔标记、词项 ID 列表、权重、最近使用时间，都会使“节点数”与实际内存不再等价。小样本应记录词数、总单位数、共享前缀长度、节点数和每节点载荷；上线前再按真实关键词分布、语言比例及增删频率测量。第一坏边界通常不是词数突然增大，而是词项变得随机、前缀不再共享，Trie 逐渐退化为接近总文本长度的节点集合。

### 位图与 Bloom：范围、容量和误判

### 位图与 Bloom：范围、容量和误判

位图与 Bloom 过滤器都把“集合成员资格”压缩为比特，但它们回答的问题不同，成本边界也不同。

- **位图**适合编号可直接映射为下标的对象。若最大编号为 $U$，即使实际只有 $n$ 个元素，也通常需要约 $U+1$ 个 bit，空间约为：
  $$
  \frac{U+1}{8}\text{ 字节}
  $$
  例如只保存 100 个用户，但用户 ID 最大为 $10^9$，位图仍约需 125 MB。它没有误判：某 bit 为 0 则必不在集合，为 1 则必在集合；但删除、稀疏 ID、编号持续增长都会影响适用性。

- **Bloom 过滤器**不按最大 ID 分配，而按预期加入量 $n$、位数组长度 $m$ 和哈希函数数目 $k$ 设计。查询结果具有非对称语义：  
  - 任一对应 bit 为 0：**必不在**；  
  - 全部对应 bit 为 1：**可能在**。  

Bloom 会产生假阳性，不会产生漏判：已加入元素不应被判为“不在”。在给定 $m,n,k$ 时，假阳性率近似为：
$$
p \approx (1-e^{-kn/m})^k
$$
常用近似最优哈希数为：
$$
k \approx \frac{m}{n}\ln 2
$$

因此不能把 Bloom 报价为“零误判”。容量超过设计的 $n$ 后，bit 越来越密，假阳性会显著上升；可扩展实现可能新增子过滤器，节省重建成本，却增加查询时需要检查的过滤器数量。

设计时先用小样本记录实际 bit、元素数和假阳性，再观察真实 ID 最大值、集合增长、删除比例与查询比例。更重要的是确认业务后果：Bloom 假阳性若仅触发一次权威存储查询，通常是性能成本；若“可能已存在”直接导致拒收消息或跳过投递，则是业务失败，必须保留确认链路。

### 并查集：父节点数组与增量连通

### 并查集：父节点数组与增量连通

并查集适合维护“关系只增加”的连通性。例如，IM 中用户 `A` 与 `B` 成为好友、`B` 又与 `C` 成为好友后，可快速判断 `A` 和 `C` 是否处于同一关系群组。

对每个用户 ID 保存两个数组槽位：

- `parent[x]`：节点 `x` 的父节点；根节点满足 `parent[x] = x`。
- `size[x]` 或 `rank[x]`：仅对根有意义，记录集合规模或树高估计，用于控制树深度。

查询 `Find(x)` 不断沿 `parent` 向上找到根；使用路径压缩后，可把访问路径上的节点直接改指向根。合并 `Union(a, b)` 先求两个根；若根不同，就把较小集合挂到较大集合下，或按秩连接。两种优化结合后，均摊操作成本近似为常数。

例如初始时 `parent[101]=101`、`parent[205]=205`。执行 `Union(101,205)` 后，两者共享一个根；后续 `Find(101)==Find(205)` 即表示连通。数组空间主要是每个已登记元素的一份父指针及规模/秩，而不是关系边数。

它的关键限制是**不擅长删除**。若撤销 `B-C` 的关系，原集合可能被拆成多个部分，但并查集没有足够信息判断应如何拆分；直接修改某个父指针还可能破坏其他连通路径。因此它适用于入群、关注、合并身份等增量场景；涉及频繁删好友、退群后精确连通判断时，应使用图结构、重建分量或离线算法。

### 从容器估算走向业务测量

### 从容器估算走向业务测量

小样本只能验证结构是否“能装下”，不能证明它适合业务。测量应从真实数据分布和可见结果出发，而非只报告节点数、位数或数组长度。

- **Trie**：记录词项数、平均长度、共享前缀比例、节点数与内存；同时观察热词更新是否造成锁竞争。
- **位图**：按真实最大 ID 与稀疏度估算，而非按当前元素数估算。若用户 ID 最大到 $10^9$，即使只活跃一万个用户，直接位图仍可能需要约 $10^9$ bit。
- **Bloom**：固定 $m,k,n$，分别记录设计容量、实际加入量、查询量、命中后权威确认次数与观测假阳性。它没有假阴性；但“可能存在”必须经权威存储确认。容量超过设计值后，假阳性会上升；可扩展 Bloom 可能新增子过滤器，节省重建成本，却增加查询检查工作。
- **并查集**：测量元素槽位数、`parent` 与 `size/rank` 数组内存、合并/查找比例，以及删除需求；普通并查集并不擅长删除。

业务指标必须把结构结果接到用户后果：Bloom 假阳性若仅多一次数据库查询，是延迟与成本；若据此跳过消息投递、拒绝好友申请或遗漏风控事件，则是业务失败。记录正反例、误判/漏判、版本延迟、更新成本、内存峰值和“第一坏边界”——例如 ID 范围何时突然扩张、Bloom 在何种加入量后误判不可接受。

最后明确并发所有权：多个 goroutine 更新 Trie、位图、Bloom 或并查集时，应由单一所有者串行处理，或使用锁等同步；普通 `map`、切片和位操作本身并不线程安全。

> **要点** — 按输入形状和业务后果选结构；先算边界，再测真实分布、更新成本与确认链路。

从查询形状出发识别四类专用结构，并在虚构 IM 场景中推演其正确边界与业务确认链路。

### 四类查询形状与结构选择

### 四类查询形状与结构选择

先看“要回答什么”，再选结构；不要因为数据都叫“用户、消息或会话”就使用同一种索引。

- **关键词补全：Trie（前缀树）**  
  输入是逐字符扩展的前缀，如 `会话`，需要找出 `会话历史`、`会话列表` 等候选。关键还要区分：`会话` 本身是否是一个完整词项，还是仅为更长词的前缀。Trie 的节点路径表示前缀，终止标记表示完整词。

- **稠密标记：位图**  
  若对象 ID 是稳定、稠密的非负整数，可用第 $i$ 位表示 ID $i$ 是否存在、是否已读或是否命中。例如 $74=2+8+64$，按 8 位写为 `01001010`。稀疏的大 ID 会造成大量空位，通常不适合直接使用位图。

- **消息预筛：Bloom 过滤器**  
  对“这条消息是否可能已处理过”这类问题，Bloom 用多个哈希位置快速给出结论：某一位为 0，则**肯定未插入**；全部为 1，则只是**可能插入**，仍可能是假阳性。因此它适合减少昂贵查询，不能代替权威消息 ID、操作记录或权限校验。

- **关系分组：并查集**  
  对“两个账号是否属于同一合并群组”“两个节点是否连通”，使用 `Find` 查代表、`Union` 合并集合。两个元素 `Find` 结果相同即同组；但并查集不提供具体路径，也不能把根节点误解为业务上的固定负责人。

结构能力决定业务边界：Bloom 的“可能存在”必须精确确认；位图清位前要确认没有共享语义；并查集面对删除或拆组通常需要重建，不能充当实时授权事实源。

### Trie：前缀、终止标记与文本单位

### Trie：前缀、终止标记与文本单位

Trie（前缀树）把词项按“从左到右共享前缀”的方式存储。对虚构词典中的：

- `会话`
- `会话历史`
- `会话列表`

可手画为：

- 根
  - `会`
    - `话`（终止标记：`会话` 是完整词项）
      - `历`
        - `史`（终止标记：`会话历史`）
      - `列`
        - `表`（终止标记：`会话列表`）

节点 `会→话` 同时承担两种角色：它是更长词项的公共前缀，也是一个可独立查询、可独立匹配的完整词项。因此，Trie 不能只看“节点是否存在”；还必须保存“此处是否为词尾”的终止标记。

查询 `会话` 时，字符路径存在只能说明它是某个已存词项的前缀；只有 `话` 节点带有终止标记，才能确认 `会话` 本身在词典中。若词典只有 `会话历史` 和 `会话列表`，则路径仍可走到 `会话`，但它仅是前缀，不应被当作完整命中。

实现中，“字符”也要先定义文本单位：可按字节、Unicode 码点或用户感知字符切分。面对中文词项，通常按 Unicode 字符处理较直观；面对表情、组合字符时，需统一切分规则，否则插入与查询可能走出不同路径。

### 位图与 Bloom：位编号和预筛结论

### 位图与 Bloom：位编号和预筛结论

位图适合表示**稠密、稳定的非负整数 ID**是否出现：ID 直接对应一个 bit，值为 `1` 表示出现，`0` 表示未出现。若 ID 范围很大但实际对象稀疏，例如只使用少量随机的大号用户 ID，直接开位图会浪费大量空间，此时应考虑哈希集合或先建立稳定映射。

设位图按每字节 8 位存储，采用“低位对应较小偏移”的约定：

- `byteIndex = id / 8`
- `bitOffset = id % 8`
- 掩码为 `1 << bitOffset`

例如 ID 为 `74`：

- `74 = 9 × 8 + 2`，因此位于第 `9` 个字节；
- 字节内偏移为 `2`；
- 对应位值为 $2^2=4$；
- 若只看编号 `74` 的二进制表示，则 `74=2+8+64`，写作 `01001010`。

写入时执行 `bitmap[9] |= 4`；查询时检查 `bitmap[9] & 4` 是否非零。这里最容易出错的是位序约定：系统必须统一“偏移 0 对应最低位”还是最高位，否则同一 ID 会读写到不同位置。

Bloom 过滤器也使用 bit，但一个元素会经多个哈希函数映射到多个位置。查询结论只有两种：

- **存在某个目标位为 0**：该元素**肯定没插入过**；
- **所有目标位都为 1**：该元素**可能插入过**，仍可能是假阳性。

假阳性指 Bloom 返回“可能在”，但真实记录从未插入；原因是其他元素恰好共同占满了这些位。因此，Bloom 适合在访问权威数据库、精确 ID 表或操作记录前做预筛：判“必不在”可直接跳过，判“可能在”必须继续精确确认，不能据此直接授权、拒绝或执行不可逆操作。

### 并查集：增量连通与删除限制

### 并查集：增量连通与删除限制

在虚构 IM 中，可把用户、联系人或群组映射为节点：`Union(a,b)` 表示新增“同一关系圈”连接，`Find(x)` 返回节点所在集合的代表元。若 `Find(甲)==Find(乙)`，则两者当前属于同一连通组；否则尚无已记录的连接链，除非后续出现跨组 `Union`。

代表元只是集合内部标识，不是业务上的“群主”“最早成员”或固定用户 ID。按秩合并、路径压缩后，根节点可能变化，因此不能把根值直接展示或持久化为业务身份。

并查集回答的是“是否连通”，不回答“经谁连接”：

- 要展示甲到乙的关系路径，应维护图边并进行图遍历；
- 要校验成员权限、资料可见性，仍须查询权威权限记录；
- 它适合连接不断增加的场景，如联系人关系逐步导入。

其硬限制是删除：移除一条联系人边或把成员移出群组后，并查集无法局部拆分原集合；随意修改根或清理状态会误伤其他连通关系。需要准确处理删除时，应重建相关连通分量，或改用支持动态连通的图方案；不能将并查集作为实时授权判定来源。

### 业务硬门：版本、容量、并发与精确确认

### 业务硬门：版本、容量、并发与精确确认

四类结构解决的是不同形状的问题，但都不能脱离业务约束单独使用：

- **前缀树**适合补全与词项检索。`会话`是否命中，取决于它是否被标记为完整词，而不只是存在于`会话历史`的路径上。
- **位图**适合稠密、稳定的非负整数 ID。它依赖`ID → bit`映射；映射必须唯一、版本明确。ID 清理、分片迁移或复用时，旧版本位图不能与新版本混读。
- **Bloom 过滤器**适合“先排除”的高吞吐场景：回答“肯定不在”或“可能在”。容量、哈希函数数量与预计元素数共同决定假阳性率；超过规划容量后，假阳性会显著增加。
- **并查集**适合只增不删的连通性归类。`Find(a)=Find(b)`表示同组，不表示路径、权限继承链或谁是谁的上级；根节点也只是结构代表。

并发下更要区分“结构状态”与“权威事实”。位图置位、Bloom 插入、并查集合并应保证原子性或通过批次版本发布；否则读者可能看到半完成状态。Bloom 不能随意清位，因为多个元素可能共享同一位；并查集通常也不能实时删除成员关系，删除后往往需要重建或改用支持动态连通的方案。

在 IM 场景中，任何影响授权、拒绝、审计或扣费的决定都必须回查权威数据。例如 Bloom 说某操作 ID“可能已处理”，只能触发精确查询操作记录，不能直接拒绝请求；位图命中某用户，也不能证明其仍有资料访问权。权限、成员资格和操作幂等状态应由带版本、事务或一致性语义的权威存储最终确认。

> **要点** — 专用结构只回答特定形状的问题；近似命中、连通结果和位标记都不能替代权限与权威精确确认。
