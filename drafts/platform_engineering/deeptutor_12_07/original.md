### 配置与秘密的分层边界

### 配置与秘密的分层边界

`ConfigMap` 用于保存非秘密的运行参数，例如 `gateway/transfer/history-migrate` 的服务地址、超时、日志级别、功能开关，以及 `db/events` 的连接主机名或库名。它解决的是“进程以什么方式运行”，不应存放口令、令牌、私钥或可复用的连接串。

`Secret` 用于保存敏感材料，例如数据库密码、TLS 证书、第三方访问令牌、消息签名密钥。容器可通过环境变量或挂载文件读取它；应限制读取范围、避免写入日志，并考虑轮换与失效策略。注意：Secret 是编码后的资源，不天然等于加密后的保险箱；是否静态加密、谁能读取，取决于集群配置与访问控制。

两者都只是**部署层输入**，不能成为业务授权依据。例如：

- Pod 能读取某个 `ConfigMap`，不表示用户 `u-c` 能读取会话 `c-a`。
- Pod 挂载了数据库 `Secret`，不表示任意请求都可查询 `db/events`。
- Kubernetes RBAC 允许工作负载读取 Secret，只说明该工作负载可取得凭据，不说明请求中的用户是会话成员。
- 网络策略允许 gateway 连接 transfer 或数据库，只说明链路可达，不说明业务动作获准。

因此，gateway 即使凭 Secret 成功连接后端，仍须在应用层验证成员关系。对既有 S2/v1 合同，静态 UTF-8 正文仍限制为 `6B`、原始请求正文仍限制为 `4096B`；同 ID 返回 `409`，非成员返回 `404`，`200` 仅表示内存受理。未来迁移到数据库或事件流时，配置来源可以变化，但这些业务语义与权限判定不能被 ConfigMap、Secret、RBAC 或网络连通性替代。

### Secret 编码、加密与读取控制

### Secret 编码、加密与读取控制

Secret 的 `data` 字段通常写成 base64，例如：

`token: YWJjMTIz`

这只表示 `abc123` 被编码，任何拿到 YAML、API 响应或 etcd 数据的人都可轻易解码；它不是加密，更不能作为“u-c 可以读 c-a”的业务授权依据。

真实保护边界应分层理解：

- **静态加密**：为 Kubernetes API Server 配置 Secret 的静态加密，使 etcd 中保存的是密文。它保护存储介质泄露场景，但不能阻止已获 API 读取权限的主体获得明文。
- **ServiceAccount 身份**：gateway、transfer、history-migrate、db/events 应使用不同的 ServiceAccount。容器内挂载的令牌代表工作负载身份，不代表某个用户或某个会话成员。
- **RBAC 最小授权**：仅给需要读取某个 Secret 的 ServiceAccount 授予特定 `get` 权限；避免宽泛的 `list`、`watch`，因为它们可能暴露命名空间内全部 Secret。
- **挂载范围**：优先将 Secret 作为明确环境变量或只读卷挂载给必要容器，避免注入所有 Pod，也不要写入日志、错误响应或 ConfigMap。

即使 gateway 的 ServiceAccount 被允许读取数据库凭据，也只能说明它可连接数据库；不能推出用户 `u-c` 有权读取会话 `c-a`。前者是基础设施凭据权限，后者必须由应用层成员关系校验决定。

因此，S2/v1 仍应保持：正文按 UTF-8 限制 6B、原始请求体限制 4096B、同 ID 返回 409、非成员返回 404、成功返回 200 且仅内存受理。未来迁移到 DB 或 `db/events` 时，Secret 保护数据库连接信息；成员授权与这些既有合同仍由业务代码执行。

### 三类身份不能互相替代

### 三类身份不能互相替代

同一个请求链路中，至少存在三类身份；它们回答的问题不同，不能互相“推导授权”。

| 身份层 | 典型主体 | 决定什么 | 不能决定什么 |
|---|---|---|---|
| Pod 的 ServiceAccount | `gateway` Pod | 工作负载以谁的名义访问 Kubernetes API | 某个 IM 用户能否阅读某会话 |
| 集群 RBAC | `Role`、`RoleBinding` | ServiceAccount 能否读取 `ConfigMap`、`Secret` 或查看 Pod | 用户是否为会话成员、是否可迁移历史 |
| 数据库或 IM 用户身份 | `u-c`、`u-a`、会话 `c-a` | 业务数据的归属、成员关系与读写权限 | Pod 能否调用 Kubernetes API |

例如，`gateway` 使用的 ServiceAccount 即使被 RBAC 授予读取某个 `Secret` 的权限，也只说明该工作负载可取得数据库连接配置。它不意味着请求中的 `u-c` 自动拥有数据库中任意记录的读取权，更不意味着 `u-c` 可读取会话 `c-a` 的历史。

业务授权必须在应用层按请求身份检查：

`允许读取 history(c-a) ⇔ u-c 是 c-a 的成员`

因此，面对非成员请求，应继续返回既有合同中的 `404`，而不是因为网络可达、数据库账号可连、Pod 可读取配置，就返回数据或改为基础设施错误。`200` 仍只表示当前 S2/v1 的内存受理；未来 `gateway/transfer/history-migrate` 与 `db/events` 的演进，也不得绕过成员校验。

### 网络策略与服务通信闭环

### 网络策略与服务通信闭环

网络策略解决的是“工作负载之间能否建立连接”，而不是“用户是否有权读取会话”。即使 `u-c` 的请求经 `gateway` 成功到达 `transfer` 或 `db`，仍必须由业务层判定其是否为 `c-a` 成员；非成员继续返回 `404`，同 ID 冲突继续返回 `409`，不能因网络已放通而绕过既有 S2/v1 合同。

先确认集群的网络插件实际执行 `NetworkPolicy`；仅能创建策略对象、但网络插件不支持执行时，策略不会形成隔离。实施时应先做连通性清单，再默认拒绝，避免一次性封锁 DNS、迁移任务或事件投递：

- `gateway` 仅接受 Ingress/网关控制器的入站流量；其出站仅允许到 `transfer`，以及必要的集群 DNS。
- `transfer` 仅接受 `gateway` 的入站调用；出站允许到 `db`、`events` 和 DNS。它仍负责 UTF-8 正文最多 `6B`、原始请求正文最多 `4096B` 的校验，并在 `200` 时保持“内存受理”语义不变。
- `history-migrate` 是批处理身份，不应复用 `transfer` 的宽泛权限。它仅在运行期间出站访问 `db`；若需要发布迁移结果，再单独允许到 `events`。
- `db` 只允许来自 `transfer` 与 `history-migrate` 的数据库端口入站，不应对 `gateway`、其他命名空间或公网开放。
- `events` 只允许明确的生产者，例如 `transfer` 和经审查后需要发布事件的迁移任务；消费者另建定向规则。

策略必须同时检查入站与出站：允许 `transfer → db` 不等于允许数据库响应，实际还需数据库入站规则匹配 `transfer`；而启用出站隔离后，忘记放行 DNS 会表现为服务名解析失败。使用标签选择器限定命名空间、服务账号与端口，并为 `gateway/transfer/history-migrate` 分配不同身份。R9 的数据库提议仍待审，未批准前不要以“预留通路”为由扩大 `db` 的网络暴露面。

### 配置演进与角色验收卡

### 配置演进与角色验收卡

配置更新应被视为“部署输入变化”，而不是业务授权变化。`ConfigMap` 可承载网关地址、超时、功能开关与迁移批次；`Secret` 承载数据库凭据、签名密钥等敏感值。无论通过环境变量、挂载文件还是滚动发布传播，配置生效都不得改变既有 S2/v1 的可观察合同。

验收时先固定版本边界：

- S2/v1 仍接受正文不超过 `6` 个 UTF-8 字节的消息。
- 原始请求正文上限仍为 `4096` 字节；超限、编码异常等行为不得因网关或配置切换而漂移。
- 同一消息 ID 重复提交仍返回 `409`。
- 非会话成员查询、发送或读取相关资源仍返回 `404`，不得泄露“资源存在但无权访问”。
- 合法请求返回 `200` 时，仅表示已由内存路径受理；不得因 `gateway/transfer/history-migrate` 或 `db/events` 配置出现而暗示 S3 数据库持久化已完成。

角色验收必须区分基础设施身份与业务成员身份。Pod 的 ServiceAccount 能读取某个 `ConfigMap`、连接网络或调用内部服务，只说明其具备运行权限；它不能证明用户 `u-c` 有权读取会话 `c-a`。业务层仍须根据会话成员关系判定，非成员统一维持 `404`。

可将发布前检查压缩为一张验收卡：

| 检查项 | 期望结果 |
|---|---|
| 配置热更新或滚动发布 | 不改变 S2/v1 状态码、字节限制与幂等语义 |
| `gateway/transfer/history-migrate` | 仅作为未来路由/迁移配置，不提前启用未定义持久化承诺 |
| `db/events` | S3 提议仍限制为 `6B` 正文，不能覆盖当前内存受理语义 |
| 最小权限 | 工作负载仅获必需配置、密钥和网络访问 |
| 业务读取 | `u-c` 非 `c-a` 成员时始终为 `404` |
| R9 | 保持待审，不可借配置或基础设施权限提前视为已验收 |

> **要点** — Kubernetes 管的是工作负载与基础设施边界；成员可见性、消息合同和业务授权必须由应用层独立验证。

IM 服务上线前，先将普通运行参数与敏感凭据分离，避免因错误存放或过宽权限造成泄露。

### 配置与秘密的分类边界

### 配置与秘密的分类边界

IM 平台应先按“泄露后是否会导致未授权访问、冒用身份或扩大攻击面”分类，而不是按数据格式分类。

- **ConfigMap：非敏感运行配置。**例如 `LOG_LEVEL=info`、服务名 `im-gateway`、监听端口、功能开关、消息大小限制、公开的后端地址等。这些值可能影响行为，但即使被看到，通常不会直接让攻击者登录数据库或冒充机器人。
- **Secret：认证材料与私有密钥。**例如数据库用户名和口令、Redis 认证口令、JWT 签名密钥、TLS 私钥、第三方短信密钥、机器人令牌、对象存储访问密钥。攻击者拿到这些值，可能直接读取消息、伪造用户身份或调用外部服务。

`Secret` 中的数据常以 Base64 表示，但 Base64 只是编码，不是加密；能读取清单、导出 Secret 或取得其挂载文件的人，通常都能还原原文。更重要的是，etcd 默认并不保证 Secret 已在静态存储中加密，集群还应配置静态数据加密、严格的 RBAC 与审计。

不要把数据库口令、机器人令牌写入课程示例、Git 仓库、镜像层、Pod 日志或错误信息；也不要因“只是测试环境”而改用 ConfigMap。测试凭据同样应视为 Secret，并与生产凭据隔离、定期轮换。

### Secret 不是天然加密保险箱

### Secret 不是天然加密保险箱

`Secret` 的作用是把密码、令牌、私钥等敏感值与 Pod 清单分离，并以环境变量或挂载文件注入容器；它并不意味着“数据已经加密”。

首先，清单中的 `data` 字段只是 **base64 编码**：

`cGFzc3dvcmQxMjM=` 可以被任何人轻易解码为原文。编码便于传输和存储二进制数据，却不提供保密性。因此，不能因为字段位于 Secret 中，就把它直接提交到 Git、课程作业文件或聊天记录。

其次，Secret 最终通常保存在 etcd 中。若集群未启用 **静态加密**，etcd 中保存的仍可能是可读内容；备份文件、快照和拥有 etcd 访问权的管理员都可能接触原文。生产集群应配置 API 服务器的静态加密提供方，并妥善管理加密密钥；仅依赖默认配置并不足够。

RBAC 也只能限定 API 访问边界：应尽量避免授予 `get`、`list`、`watch secrets` 等宽泛权限，尤其不能把 `list` 或 `watch` 开给普通应用身份。但还要注意一个间接读取路径：应用的 ServiceAccount 即使没有读取 Secret 的权限，只要某个主体拥有在该命名空间创建或修改 Pod 的权限，就可能把目标 Secret 挂载进 Pod，再从容器内读取它。因此，“能创建 Pod”在实践中接近于“能使用该命名空间的 Secret”。

最后，明文一旦进入镜像层、启动命令、环境变量回显或应用日志，后续即使轮换 Secret 也难以完全清除历史副本。不要把凭据写入 Dockerfile、镜像、课程示例、`kubectl` 输出或日志；发生泄露时，应立即撤销并轮换凭据，而非只删除文件。

### 注入权限不等于读取接口权限

### 注入权限不等于读取接口权限

Pod 使用 Secret 时，常见误解是：应用进程必须以其 `ServiceAccount` 调用 API，再执行 `get secret`。实际上，Secret 注入通常由 Kubernetes 控制面和节点组件完成，而非应用容器主动读取。

当 Pod 规范声明环境变量、卷挂载或镜像拉取凭据引用某个 Secret 时，大致流程如下：

1. 提交 Pod 的用户、控制器或工作负载身份需要有权创建该 Pod。
2. API Server 校验该 Pod 对 Secret 的引用，并保存 Pod 规格。
3. Pod 被调度到节点后，节点上的 kubelet 代表该 Pod 获取所需 Secret，将其写入临时卷，或在启动容器时填入环境变量。
4. 容器内应用只看到文件或环境变量，并未调用 `GET /api/v1/namespaces/.../secrets/...`。

因此，应用的 `ServiceAccount` 即使没有 `get`、`list`、`watch` Secret 的 RBAC 权限，也仍可使用已注入的数据库密码、令牌或证书。这是较好的最小权限实践：应用只能消费分配给自己的凭据，不能枚举或任意读取命名空间中的 Secret。

但这不意味着 Secret 自动安全。拥有“创建或修改 Pod/Deployment”等权限的主体，可能构造一个引用目标 Secret 的 Pod，再通过挂载文件、环境变量或日志将内容导出。换言之，`create pods`、`patch deployments` 等工作负载写权限，常可间接获得同一命名空间内可引用 Secret 的内容。

RBAC 设计应同时审查两类权限：

- 直接读取：`get/list/watch secrets`；
- 间接读取：创建、修改可引用 Secret 的 Pod、Job、Deployment 等资源。

应将工作负载创建权限与 Secret 管理权限分离，并限制高权限发布身份的使用范围。

### 创建 Pod 也是敏感能力

### 创建 Pod 也是敏感能力

Secret 的读取不只发生在调用 `GET /api/v1/namespaces/.../secrets/...` 时。若某主体能够在同一命名空间创建 Pod，它通常可以构造一个引用任意 Secret 的 Pod：

- 以卷挂载 Secret，再读取挂载目录中的文件；
- 将 Secret 键注入环境变量，再通过容器命令输出；
- 使用现有高权限 ServiceAccount 启动 Pod，扩大后续访问范围。

例如，创建者无需拥有 Secret 的 `get` 权限，也可以提交“挂载 `db-credential` 并执行 `cat`”的 Pod；kubelet 会代表该 Pod 获取并注入 Secret。因而，**同命名空间的 Pod 创建权限可间接等价于读取该命名空间中可被 Pod 引用的 Secret**。

最小权限设计不能只检查 `secrets` 资源的 `get/list/watch`，还要审查：

- 谁拥有 `pods` 的 `create`，以及 `deployments`、`jobs`、`cronjobs` 等工作负载的创建或修改权限；
- 谁可使用哪些 ServiceAccount；避免普通发布者指定高权限身份；
- 哪些命名空间混放了高敏感 Secret 与低信任工作负载。

实践上，应按信任边界拆分命名空间和 ServiceAccount：部署流水线仅可发布到指定命名空间，业务身份只挂载其所需 Secret，高权限运维 Secret 放入独立命名空间；再配合准入策略限制 `serviceAccountName`、Secret 卷和环境变量引用。这样即使某个开发角色能够创建 Pod，其可间接接触的凭据范围也被限制在必要集合内。

### IM 服务的最小权限验收卡

### IM 服务的最小权限验收卡

将权限按“谁创建、谁使用、谁审计”拆分，而不是把所有成员加入同一高权限角色。

| 角色 | 最小权限 | 禁止事项 |
|---|---|---|
| 开发者 | 在开发命名空间读写 `ConfigMap`；提交 Secret 模板、引用名和轮换说明 | 不提交真实密码、令牌或私钥；不读取生产 Secret |
| 部署机器人 | 在目标命名空间创建或更新 `Deployment`、`Service`、`ConfigMap`；按需创建或更新指定 Secret | 不授予跨命名空间权限；不授予列出全部 Secret 的权限 |
| 运行中服务 | 通过环境变量或挂载文件接收 `LOG_LEVEL`、服务地址、数据库凭据等 | 不因“已挂载 Secret”而额外授予 ServiceAccount `get/list/watch secrets` |
| 运维审计者 | 读取 RBAC、工作负载引用关系、事件与审计日志；在受控流程下核验 Secret 元数据 | 不将 Secret 明文打印、下载到工单或复制到聊天记录 |

验收时逐项检查：

- 非敏感参数如 `LOG_LEVEL`、服务名、端口、功能开关位于 `ConfigMap`；密码、访问令牌、证书私钥仅位于 `Secret`。
- 明确 `base64` 只是编码，不是加密；确认集群已启用 etcd 静态加密与访问审计。
- Secret 不进入 Git、镜像层、课程示例明文、应用日志、错误栈和监控标签。
- Pod 通过 `secretKeyRef` 或卷引用所需 Secret；运行 ServiceAccount 无直接读取 Secret API 的权限。
- 特别审查“创建 Pod/Deployment”权限：能够创建引用某 Secret 的 Pod，可能间接读取同一命名空间的 Secret。因此部署机器人只能操作受限命名空间，并限制可用的 Secret 名称与工作负载模板。
- 凭据轮换后，验证新 Pod 已加载新值、旧凭据失效，且日志中不出现凭据内容。

> **要点** — ConfigMap 存非秘密参数，Secret 存凭据；base64 不等于加密，权限与投递链路必须共同最小化。

本节厘清工作负载访问 Kubernetes API、数据库和 IM 平台时的身份边界，避免把“能拿到密码”误解为“拥有系统权限”。

### 三类身份：API、数据库与业务用户

### 三类身份：API、数据库与业务用户

同一个 Pod 可能携带多种身份，但它们服务于不同的认证域，不能相互推导：

- **ServiceAccount（SA）**：工作负载调用 Kubernetes API 时使用的身份。它决定 Pod 能否读取 ConfigMap、查询 Job、创建 Pod 等；其权限由 RBAC 控制。
- **数据库账号**：应用连接 MySQL、PostgreSQL 等数据库时使用的用户名、密码、证书或云数据库令牌。它决定能访问哪个库、表、视图及可执行的 `SELECT`、`INSERT` 等操作。
- **IM 业务身份**：调用企业微信、Slack、飞书或短信平台时使用的机器人令牌、应用凭证或用户授权令牌。它决定消息以谁的名义发送、可操作哪些会话或频道。

可将其理解为三把不同的钥匙：

| 身份 | 面向系统 | 典型权限 |
|---|---|---|
| SA | Kubernetes API | `get pods`、`create jobs` |
| 数据库账号 | 数据库服务 | 查询、写入指定表 |
| IM 业务身份 | IM 平台 API | 向指定群组发送消息 |

Secret 只是敏感配置的**存放与分发机制**。Pod 能挂载数据库密码，不表示其 SA 因而拥有 `get/list secrets`；SA 能读取某个 Secret，也不表示该 Secret 中的数据库账号具备高权限。设计时应分别为每个边界配置最小权限，并独立轮换、审计和撤销。

### RBAC 授权对象与绑定关系

### RBAC 授权对象与绑定关系

RBAC 管理的是“某个 Kubernetes 身份能否对 Kubernetes API 中的某类对象执行某种动作”，而不是数据库、消息平台或操作系统权限。一次授权可抽象为：

`主体 × 规则 × 绑定范围 → API 访问能力`

- **Role**：命名空间级规则集。它用 `rules` 描述可访问的 `apiGroups`、`resources` 与 `verbs`，例如允许读取本命名空间的 `configmaps`：
  `resources: ["configmaps"]`，`verbs: ["get", "list", "watch"]`。Role 本身只在其所在命名空间生效。

- **ClusterRole**：集群级规则集。它适合节点、命名空间、持久卷等集群范围资源，也可定义对普通命名空间资源的通用规则。后者是否跨命名空间，取决于绑定方式，而非 ClusterRole 名称。

- **RoleBinding**：在**一个命名空间内**把 Role 或 ClusterRole 授予主体。即使绑定的是 ClusterRole，权限仍只落在该 RoleBinding 所在命名空间。例如将“读取 Secret”的 ClusterRole 绑定到 `prod`，并不意味着可读取 `dev` 的 Secret。

- **ClusterRoleBinding**：将 ClusterRole 授予整个集群范围。若规则包含命名空间资源，通常意味着主体可在所有命名空间执行对应动作；应谨慎使用。

主体可以是 ServiceAccount、用户或用户组。工作负载通常通过其 ServiceAccount 被识别。权限是**累加**的：多个 Binding 的允许项会合并，RBAC 没有显式 `deny` 用于抵消已有授权。因此应按最小权限拆分规则，例如仅授予 `get` 某配置对象，而不要习惯性授予 `list/watch` 或整个 `secrets` 资源。

### 权限累加与最小授权设计

### 权限累加与最小授权设计

Kubernetes RBAC 采用“允许即获得、多个来源累加”的模型：`Role` 或 `ClusterRole` 定义对 API 资源的操作许可，`RoleBinding` 或 `ClusterRoleBinding` 将这些许可授予 ServiceAccount、用户或用户组。某个主体只要通过任一绑定获得某项权限，就可以执行该操作。

RBAC 没有通用的显式“拒绝”规则。也就是说，不能先授予：

`pods: get, list`

再用另一条规则表示“禁止读取某个 Pod”来覆盖前者；后续绑定只会增加能力，不会收回已有能力。因此，排查“为什么这个工作负载能访问资源”时，应检查该 ServiceAccount 的全部绑定，而不是只看某一个 Role。

最小授权设计应按职责拆分，而非复用“万能 SA”：

- `gateway-sa`：若网关不调用 Kubernetes API，设置 `automountServiceAccountToken: false`，无需 RBAC 权限。
- `history-job-sa`：仅授予其确实需要的 API 动词，例如对特定命名空间中的 `jobs` 使用 `get`、`list`；数据库权限则由数据库账户单独控制。
- `controller-sa`：仅在控制器确需协调资源时，授予对应对象的 `get`、`list`、`watch`、`create` 或 `update`，避免笼统授予 `*`。

尤其不要因为工作负载需要数据库密码，就授予其 `secrets` 的 `get`、`list` 权限。密码可通过预先挂载的 Secret、外部密钥系统或注入机制提供；“能使用一个已注入的密码”不等于“能枚举或读取集群中的其他 Secret”。

### Gateway 不访问 API 时的令牌关闭

### Gateway 不访问 API 时的令牌关闭

Gateway 若只负责接收请求、查询数据库并调用 IM 平台，它的 Kubernetes 身份通常不需要参与运行时逻辑。数据库密码来自已注入的环境变量或已挂载的专用文件，并不表示应用需要调用 Kubernetes API 去读取 `Secret`。

因此，不应仅因“Gateway 要使用数据库凭据”就授予其：

- `secrets` 的 `get`、`list` 或 `watch`；
- 查询 Pod、Service、ConfigMap 等对象的权限；
- 默认挂载的 ServiceAccount 令牌。

可在 Pod 模板中显式关闭令牌自动挂载：

`automountServiceAccountToken: false`

这会阻止 Kubernetes 将 ServiceAccount 令牌及集群 CA 文件自动注入容器。即使攻击者取得 Gateway 容器内的文件系统访问权，也无法顺手获得一个可用于访问 Kubernetes API 的工作负载令牌。

注意两类“取密”方式的边界：

- **由 Kubernetes 注入 Secret**：控制面在创建 Pod 时完成引用和挂载；Gateway 不必拥有读取 `Secret` 的 API 权限。
- **应用自行调用 API 读取 Secret**：才需要令牌以及对应的 RBAC `get` 权限；除非确有动态取密需求，否则应避免这种设计。

若 Gateway 将来需要访问 Kubernetes API，应单独评估所需对象与动词，再创建专用 ServiceAccount 和最小 RoleBinding；不要为了方便重新启用默认令牌或授予宽泛的 `secrets` 权限。

### History Job 的独立数据库权限验收

### History Job 的独立数据库权限验收

历史消息归档任务（History Job）应与 Gateway 使用不同的 `ServiceAccount`，因为二者的运行职责和数据库操作面不同：

- Gateway 通常只读写在线会话、路由或实时消息，不应天然拥有查询历史库、批量导出或删除归档记录的能力。
- History Job 仅在执行归档、补偿、清理等任务时连接历史数据库，其数据库账号应独立创建、独立轮换、独立审计。
- `ServiceAccount` 解决的是“谁调用 Kubernetes API”；数据库账号解决的是“谁连接数据库”。即使 Job 通过 Secret 获得数据库密码，也不意味着它需要 `get/list secrets` 权限。

建议为 Job 配置专用账号，例如 `history-archiver`，并仅将指定数据库凭据以挂载文件或环境变量方式注入。若 Job 不调用 Kubernetes API，可设置：

`automountServiceAccountToken: false`

数据库权限应按操作拆分。归档任务可拥有源表的 `SELECT`、目标归档表的 `INSERT`，必要时拥有受限条件下的 `UPDATE`；清理任务若确需删除，应使用独立账号并只授予指定表的 `DELETE`。禁止直接授予库级管理员、`ALL PRIVILEGES` 或跨业务库访问权限。

可用以下验收卡确认边界：

- **身份**：Job 使用独立 `ServiceAccount` 和独立数据库用户。
- **凭据**：仅注入所需 Secret；Pod 不具备枚举其他 Secret 的权限。
- **Kubernetes API**：不需访问 API 时未挂载自动令牌；需要时仅绑定目标对象和动词。
- **数据库**：归档账号只能读源数据、写归档数据；清理权限与归档权限分离。
- **验证**：用该账号执行越权查询、跨表删除、读取其他业务库，均应失败。

> **要点** — ServiceAccount 只代表 Kubernetes API 身份；API 权限、数据库权限和 IM 业务权限必须分别按最小权限配置与验收。

网络策略是工作负载间的最小网络边界，但其生效依赖CNI能力，且不能替代IM成员关系等应用层授权。

### 先确认策略能否真正执行

### 先确认策略能否真正执行

`NetworkPolicy` 是 Kubernetes 的策略声明，不是集群必然具备的防火墙。它只有在所用 CNI 网络插件实现并启用了该能力时，才会被转换为节点上的实际转发、过滤或 eBPF 规则；若 CNI 不支持，策略对象即使已成功创建、`kubectl get networkpolicy` 也能查到，Pod 间流量仍可能完全不受限制。

先核实三个事实：

- 集群当前使用的 CNI 是什么，以及其版本、安装模式是否支持 NetworkPolicy。
- 该 CNI 的网络策略组件是否实际启用；有些插件需要额外安装控制器、代理或显式开启策略功能。
- 策略是否覆盖目标工作负载所在的节点、命名空间与网络路径；混合网络、主机网络 Pod、特定加速路径可能存在例外。

不要把“清单已提交”误当成“边界已建立”。应在测试环境用临时 Pod 做连通性验证：先确认默认 Pod 通常可自由入站、出站通信，再施加拒绝基线和最小允许规则，分别测试允许路径与应被拒绝的路径。若被拒绝连接仍可建立，优先排查 CNI 能力与运行状态，而不是继续修改选择器。

NetworkPolicy 只能约束已被 CNI 接管的 L3/L4 网络流量；它不能依据 `c-a` 成员资格、`m-9` 身份或业务角色完成应用授权。网络边界有效的前提，始终是底层执行者真实存在。

### 默认开放与隔离方向

### 默认开放与隔离方向

若集群的 CNI 支持并实际执行 `NetworkPolicy`，才可以把策略视为网络边界；否则即使 API 对象创建成功，流量也可能仍然畅通。未被任何网络策略选中的 Pod，默认处于**入站、出站均不隔离**状态：任意来源可连入，Pod 也可主动访问任意可路由目标。

隔离不是“创建一条允许规则”本身，而是从策略的 `podSelector` 与 `policyTypes` 推导出来：

- 某 Pod 被包含 `Ingress` 的策略选中后，其入站变为隔离；此后仅策略 `ingress` 中明确允许的来源、端口和协议可进入。
- 某 Pod 被包含 `Egress` 的策略选中后，其出站变为隔离；此后仅 `egress` 中明确允许的目标、端口和协议可访问。
- 同一 Pod 可同时被多条策略选中；规则按方向**累加取并集**，不会因新增策略而收紧已有允许项。

一次连接要成功，必须同时满足两端条件：源 Pod 的出站方向允许到目标端口，且目的 Pod 的入站方向允许来自该源；任一侧隔离后未匹配规则，连接即失败。例如 `gateway → db:5432`，既要允许 gateway 的出站到数据库 5432，也要允许数据库入站来自 gateway。

因此，设计时先为受保护工作负载建立默认拒绝的入站或出站基线，再逐项放行 `gateway`、`transfer`、`migration` 所需路径；同时显式保留 DNS 解析及必要的集群外出站。网络策略只约束三、四层流量，不能依据 `c-a` 成员资格或 `m-9` 身份标识完成应用授权。

### 双向允许决定连通性

### 双向允许决定连通性

NetworkPolicy 不是“写了一条允许规则就一定能通”。当 CNI 支持并实际实施策略时，Pod 的连通性要分别看**源端出站**与**目的端入站**；同一方向上的多条策略取并集，但一条连接只有在两端都不拒绝时才能建立。

以 `gateway` 访问 `db:5432` 为例，判定过程是：

1. `gateway` 是否被某个出站策略选中？  
   - 未被任何出站策略选中：其出站默认不隔离，可向外发起连接。  
   - 被选中：必须存在允许访问 `db` 对应 Pod、TCP `5432` 的出站规则。

2. `db` 是否被某个入站策略选中？  
   - 未被任何入站策略选中：其入站默认不隔离，可接收连接。  
   - 被选中：必须存在允许来自 `gateway` 对应 Pod、TCP `5432` 的入站规则。

可将结果概括为：

$$
\text{gateway}\rightarrow\text{db:5432}
=
\text{gateway 出站允许}
\land
\text{db 入站允许}
$$

若 `db` 的入站规则仅允许 `migration`，即使 `gateway` 已放行到 `db:5432`，连接仍会失败；反过来，`db` 虽允许 `gateway`，但 `gateway` 的出站隔离未放行该目标，也同样不可达。

“策略累加”指多个匹配策略会共同扩大允许集合，而不是后写的策略覆盖先写的策略。因此，应按实际通信边逐条检查：`gateway → db:5432`、`transfer → events`、`transfer → db`，并同时确认 DNS 查询及其他必要出站流量没有因隔离而被遗漏。

### 为IM平台绘制最小通信矩阵

### 为IM平台绘制最小通信矩阵

先按“谁必须主动连接谁”而非按部署位置制定规则。假设 `gateway` 对外提供 IM 接入，`transfer` 处理文件或消息转发，`migration` 只执行数据库变更，`events` 提供事件流，`db` 监听 `5432`，并统一依赖集群 DNS。

| 发起方 | 目标 | 必要端口/协议 | 用途 |
|---|---|---|---|
| `gateway` | `db` | TCP `5432` | 用户、会话等业务数据 |
| `gateway` | `events` | 事件服务端口 | 发布或订阅消息事件 |
| `transfer` | `db` | TCP `5432` | 文件元数据、任务状态 |
| `transfer` | `events` | 事件服务端口 | 传递异步处理事件 |
| `migration` | `db` | TCP `5432` | 执行结构迁移 |
| 各业务 Pod | DNS | UDP/TCP `53` | 解析 Service 名称 |

据此明确禁止项：`migration` 不应访问 `events`、`gateway` 或 `transfer`；`db` 不应主动连接业务 Pod；`gateway` 与 `transfer` 也不因同属 IM 平台而默认互通。除 DNS、镜像拉取代理、审计或外部依赖等已确认目的地外，业务 Pod 的出站应默认收紧。

实施时，对每个目标服务同时检查两面：源 Pod 的 `egress` 必须允许目标 IP/端口，目标 Pod 的 `ingress` 也必须允许该来源；任一方向缺失，连接即失败。策略按方向累加为允许集，不是“后写规则覆盖前写规则”。

NetworkPolicy 只能约束 L3/L4 连通性，例如“`transfer` 可到 `db:5432`”。它不能判断请求是否来自某个 IM 成员、是否拥有 `m-9` 资源权限；这些仍须由 gateway、数据库权限和应用鉴权实现。并且只有 CNI 实际支持 NetworkPolicy 时，这张通信矩阵才能成为可执行边界。

### 网络边界不等于成员授权

### 网络边界不等于成员授权

`NetworkPolicy` 解决的是“哪个工作负载能与哪个工作负载的端口建立连接”。它通常在 L3/L4 层按 Pod 标签、命名空间、IP 段、协议和端口放行，例如允许 `gateway` 访问 `db:5432`，允许 `transfer` 访问 `events` 与数据库。前提是所用 CNI 实现支持并实际执行策略；否则策略对象存在也未必形成边界。

但网络可达不应被解释为业务有权。策略无法表达：

- 用户是否属于成员关系 `c-a`；
- 请求操作的资源是否确为 `m-9`；
- 该成员在当前组织、项目或租户中是否具备读取、转移、删除等权限；
- 令牌是否过期、是否被撤销，或请求是否满足审批、额度、状态机等条件。

例如，`gateway` 被允许访问订单服务，只说明网关可以发起 TCP 请求；订单服务仍必须验证调用者身份、解析业务主体，并检查“该主体是否可操作 `m-9`，且是否属于 `c-a`”。同理，内部 `transfer` 服务即使可连接数据库，也不能凭网络位置绕过租户隔离、对象归属和操作授权。

因此应分层承担责任：网络策略收缩攻击面、限制横向移动；服务代码依据认证后的业务身份执行成员关系与资源级授权；数据库再以独立账号和最小权限限制数据面能力。设计策略时还要显式保留 DNS 与必要外部出站，否则“最小放行”可能先阻断名称解析、身份校验或事件投递。

> **要点** — NetworkPolicy只能在受支持CNI上实施L3/L4最小连通；通信须双向允许，业务成员权限仍应由应用层验证。

配置更新不是一次“改值即生效”的操作：注入方式、应用重载能力与新旧实例并存，共同决定变更是否安全。

### 先建立配置传播的时间线

### 先建立配置传播的时间线

判断配置是否生效，先不要只看 `ConfigMap` 或 `Secret` 的当前内容，而要沿着时间线区分四个时点：

1. **配置创建**：创建 `ConfigMap`、`Secret` 时，只是把数据写入 Kubernetes API；此时没有 Pod 使用它，因而不存在“已生效”的应用行为。

2. **Pod 启动**：若通过环境变量注入，容器创建时会读取一次值，例如 `VERSION=v1`。之后即使配置改为 `v2`，该 Pod 的进程环境仍是 `v1`。若通过卷投影挂载，Pod 启动后读取的是挂载目录中的文件。

3. **配置变更**：更新对象本身不等于所有应用立即更新。环境变量注入的旧 Pod 不会自动变化；卷投影通常会在一段同步延迟后更新文件内容，但应用必须重新读取文件或具备热加载能力。使用 `subPath` 挂载单个文件时，通常不会获得后续投影更新。

4. **工作负载替换**：通过滚动更新、删除 Pod、重启 Deployment 等方式创建新 Pod，新实例才会按启动时的配置读取新值。替换期间常出现新旧 Pod 并存：新 Pod 使用 `v2`，旧 Pod 仍使用 `v1`。

因此，配置传播要分别回答：**对象何时更新、Pod 何时看到、进程何时采用、旧实例何时退出**。尤其进行 Secret 轮换时，必须验证新旧凭据能否在混部窗口内同时工作。

### 环境变量注入：重建才会取新值

### 环境变量注入：重建才会取新值

将 ConfigMap 键值注入容器环境变量时，Kubernetes 会在 **Pod 创建、容器启动前**解析引用，并把结果写入该容器的进程环境。进程启动后，环境变量属于其初始执行上下文；即使随后修改 ConfigMap，运行中的容器也不会被回写新值。

```yaml
env:
  - name: FEATURE_MODE
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: feature-mode
```

若 `app-config` 中 `feature-mode` 从 `v1` 改为 `v2`：

- 已运行 Pod 仍看到 `FEATURE_MODE=v1`；
- 新创建的 Pod 才会看到 `FEATURE_MODE=v2`；
- 单纯执行 `kubectl apply` 更新 ConfigMap，不会触发 Deployment 的 Pod 模板变化，也不会自动滚动更新。

因此，配置变更后的生效路径必须包含“替换实例”：

1. **滚动更新 Deployment**：修改 Pod 模板中的镜像、注解或显式配置版本标记，触发新 ReplicaSet 创建；新 Pod 读取新 ConfigMap，旧 Pod 按更新策略退出。
2. **滚动重启工作负载**：例如执行 `kubectl rollout restart deployment/app`，通过更新模板时间戳重建 Pod。
3. **删除由控制器管理的 Pod**：控制器会补建新 Pod，但应注意删除节奏，避免同时损失过多副本。
4. **替换独立 Pod**：裸 Pod 不会自动补建，必须重新创建其定义。

滚动期间必然可能出现旧、新 Pod 混部：部分请求使用 `v1`，部分使用 `v2`。因此配置应尽量保持前后兼容，并在 Secret 轮换或协议字段调整时观察客户端版本、连接存活时间和旧实例退出进度，而不能假设“改掉 ConfigMap 后全局立即一致”。

### 卷投影更新：文件会变，进程未必会读

### 卷投影更新：文件会变，进程未必会读

将 ConfigMap 或 Secret 以卷挂载到 Pod 后，Kubernetes 会把键值投影为文件。对象更新时，节点上的 kubelet 会在一段同步延迟后更新该卷；因此它提供的是**最终一致的文件视图**，而不是“修改对象后业务立刻切换”。

- **普通卷投影**：例如挂载到 `/etc/app-config`。ConfigMap 更新后，目录中的文件最终会指向新内容。应用若在每次请求、定时任务或收到重载信号时重新读取文件，就能逐步使用新配置。
- **进程启动时只读一次**：许多程序仅在启动阶段解析配置，并将结果保存在内存中。即使 `/etc/app-config/config.yaml` 已变化，运行中的进程仍继续使用旧值；此时需要应用支持热重载，或通过滚动重启替换 Pod。
- **`subPath` 挂载**：若把单个文件通过 `subPath` 挂入容器，例如将 `config.yaml` 挂到 `/app/config.yaml`，该挂载不会随 ConfigMap 或 Secret 更新而刷新。即使源卷已经更新，容器看到的仍可能是旧文件，通常必须重建 Pod。

因此要区分三层状态：

1. Kubernetes API 中的 ConfigMap/Secret 是否已更新；
2. 节点投影文件是否已最终刷新；
3. 应用是否重新读取并实际采用新值。

对敏感配置或 Secret 轮换，不能只观察对象版本。应同时检查新旧 Pod 是否并存、旧连接是否仍持有旧凭据，以及应用日志或健康指标是否证明新配置已被加载。若无法确认应用具备可靠重读能力，使用带版本的配置并滚动替换 Pod，通常比假设文件变化会自动生效更安全。

### IM服务变更：旧合同与新合同并行

### IM服务变更：旧合同与新合同并行

设想某 IM 平台的消息正文合同为：`v1` 客户端发送固定 `6B` 正文，服务端按 `6B` 解码、签名并落库。现需扩展为 `v2` 的 `9B` 正文。即使把服务端环境变量从 `BODY_LEN=6` 改为 `9`，也不能视为一次安全升级。

首先，环境变量注入到 Pod 后不会自动更新；旧 Pod 仍携带 `6`。即使重启部分 Pod，也会出现混部：新实例按 `9B` 解析，旧实例仍按 `6B` 解析。若客户端、网关、消费者、重放任务或异地集群尚未同步升级，可能产生截断、越界读取、签名校验失败、消息积压等问题。更危险的是，变量只改变“本端期待长度”，并没有让旧客户端凭空理解新合同。

正确做法是显式维护兼容窗口：

- 服务端先发布兼容版本：同时识别 `v1(6B)` 与 `v2(9B)`，可通过版本字段、消息头或不同接口路径区分，而非仅依赖长度猜测。
- 写入侧按灰度逐步启用 `v2`：先让少量新客户端发送 `v2`，持续观察解析失败率、死信队列、签名错误和消费者版本分布。
- 读取侧保持双读/双解码：存储、索引、审计及下游消费者均须能处理两种格式。
- 回滚时优先停止 `v2` 写入，而不是立即删除 `v2` 解析能力；已落库的 `v2` 消息仍需要被读取和重放。

因此，`6B → 9B` 是消息合同演进，不是配置改值。配置只能选择某个已实现的行为；兼容代码、灰度范围和可验证的回滚路径，才决定变更是否可控。

### 秘密轮换：验证新旧客户端混部

### 秘密轮换：验证新旧客户端混部

Secret 轮换的验收对象不是“新 Pod 能否启动”，而是轮换窗口内所有仍在服务的客户端。尤其当凭据以环境变量注入时，旧 Pod 会持续使用旧值；即使使用卷投影，文件虽会最终更新，应用若未重读文件或未重建连接，实际认证身份仍可能是旧凭据。

应先明确旧、新凭据的并存策略：

- **重叠有效期**：服务端在窗口内同时接受旧凭据和新凭据，待旧 Pod 全部替换、旧连接排空后再吊销旧凭据。
- **立即失效**：仅适用于能够原子切换、快速重启且允许短暂失败的场景；否则旧实例、长连接或重试请求会集中认证失败。
- **双凭据迁移**：应用同时读取主、备凭据，优先尝试新凭据，失败时按受控策略回退旧凭据；必须记录回退次数，避免永久依赖旧值。

观测应覆盖四类组合：旧 Pod 使用旧凭据、旧 Pod 获取新投影值后重连、新 Pod 使用新凭据，以及外部旧客户端仍携带旧凭据。重点检查认证成功率、`401/403` 或握手失败、连接池重建次数、长连接断开率及重试放大。

验收顺序可为：更新 Secret → 创建新 Pod 并确认其认证为新身份 → 滚动替换旧 Pod → 等待旧连接排空 → 确认旧凭据请求归零 → 最后撤销旧凭据。若仅看到新实例成功，不能证明混部期间安全；旧实例仍可能因环境变量未更新、`subPath` 不刷新或连接未重建而继续使用旧秘密。

> **要点** — 配置是否生效取决于注入方式与应用重载；安全变更必须兼容旧实例，并验证新旧版本混部。

本节以四类高风险误配为反证，建立从配置存放、工作负载身份、网络流量到更新回退的完整权限边界。

### 先分清配置、秘密与编码假象

### 先分清配置、秘密与编码假象

最小反证：某应用将数据库密码写入 ConfigMap，只是做了 `base64` 编码：

`DB_PASSWORD=c2VjcmV0MTIz`

这并不构成保护。任何能读取 ConfigMap 的主体、查看清单的人员，或取得 Pod 环境变量与挂载文件的人，都可立即解码得到明文。`base64` 是可逆编码，用于传输二进制或避免字符格式问题，不是加密、更不是访问控制。

应按数据性质划分边界：

- **ConfigMap**：服务地址、功能开关、日志级别、非敏感默认参数等可公开给相应工作负载的配置。
- **Secret**：密码、令牌、私钥、证书、第三方凭据等必须限制读取范围的数据。
- **base64**：Secret 的常见序列化形式；即使字段显示为编码文本，也默认应视为敏感明文。
- **静态加密**：保护 Secret 在存储后端中的落盘数据，降低存储介质、备份或底层数据库泄露风险；它不能替代 Kubernetes API 的读取权限控制。

用户影响往往不是“配置泄露”这么简单：攻击者可借数据库密码读取或篡改业务数据，使用云令牌横向移动，或通过私钥伪造服务身份。

修正时，将敏感值迁移至 Secret，删除 ConfigMap 中的旧键及其 Git 历史、构建日志和备份副本；为 Secret 配置静态加密，并以最小 RBAC 仅授予实际需要的 ServiceAccount `get` 指定 Secret 的权限。工作负载优先以卷挂载读取，避免密码长期暴露在环境变量、诊断输出和进程信息中。

回退不应把旧密码重新放回 ConfigMap。若迁移异常，保留受限的旧 Secret 引用并切换应用版本；一旦 ConfigMap 曾含真实凭据，应立即轮换凭据，因为“删除编码文本”不能撤销已发生的泄露。

### 身份链路不能用集群管理员替代

### 身份链路不能用集群管理员替代

`gateway` 是外部请求进入集群的重要边界，但它需要“转发请求”并不等于需要“管理整个集群”。以下两种授权都是典型反证：

- 将 `gateway` 的 ServiceAccount 绑定到 `cluster-admin`；
- 为其授予跨命名空间 `list/get/watch secrets`，以便“动态读取业务凭据”。

ServiceAccount 只是 Pod 在 Kubernetes API 中使用的**工作负载身份**；RBAC 决定该身份可操作哪些 Kubernetes 资源；数据库账号、IM 机器人令牌、用户 JWT 则是**业务系统身份**。三者不能互相替代：

| 身份层 | 应解决的问题 | 不应承担的职责 |
|---|---|---|
| ServiceAccount | Pod 如何向 Kubernetes API 认证 | 访问数据库、伪装终端用户 |
| RBAC | 可对哪些 API 资源执行何种动词 | 授予业务数据权限 |
| 数据库/IM 身份 | 访问具体业务服务和数据 | 管理 Kubernetes Secret 或工作负载 |

最小反证是：攻击者只需通过网关漏洞拿到其 Pod 的令牌，若该令牌拥有 `cluster-admin`，即可创建特权 Pod、读取任意 Secret、修改 RBAC，最终接管集群；即使仅能读取全部 Secret，也可能取得数据库密码、云访问密钥和第三方令牌。

修正方式是先删除高权限绑定，再按实际调用建立命名空间内的 `Role` 与 `RoleBinding`。例如网关若仅需读取自身命名空间的 TLS Secret，应限定为特定名称，并只授予 `get`：

`resources: ["secrets"]`、`resourceNames: ["gateway-tls"]`、`verbs: ["get"]`

若网关根本不调用 Kubernetes API，应关闭自动挂载令牌：`automountServiceAccountToken: false`。数据库和 IM 凭据应由各自的短期凭据、专用账号或外部密钥系统管理，而非扩大网关 RBAC。

回退时不要立即恢复 `cluster-admin`。先记录被拒绝的 API 请求，补充最小化规则；确有紧急需求时，创建带到期时间、限定资源和命名空间的临时绑定，并在故障恢复后立即撤销。

### 网络策略必须同时约束进出流量

### 网络策略必须同时约束进出流量

最小反证是：团队只为 `gateway` 配置入站 `NetworkPolicy`，允许 `frontend` 访问其 `443` 端口，却没有任何出站规则。此时 `gateway` 虽然“只接受指定来源”，仍可主动访问集群内任意服务、云元数据地址或外部互联网；一旦应用被利用，攻击者可借此横向探测、外传数据。反过来，若直接收紧出站但遗漏 DNS，Pod 将无法解析服务名，表现为间歇性连接超时或全部依赖不可用。

策略生效的前提是：网络插件必须实现 `NetworkPolicy`；仅创建对象不等于流量已被拦截。并且，入站与出站隔离分别独立：某方向一旦被策略选中，该方向默认拒绝，通信只有同时满足两端要求才成立：

$$
A \rightarrow B\ \text{允许}
\iff
A\text{ 的出站允许 }B
\land
B\text{ 的入站允许 }A
$$

因此应从最小通信集合推导规则，而非按网段宽泛放行：

- `gateway` 入站：仅允许 `frontend` 的标签、目标端口和协议。
- `gateway` 出站：仅允许实际依赖，如订单服务、数据库代理、消息系统。
- DNS：明确允许到集群 DNS 的 `UDP/TCP 53`；不要以“允许全部出站”替代。
- 外部依赖：经固定出口、代理或受控 CIDR 放行，并记录域名到地址变化的运维责任。

修正前先盘点连接日志、服务依赖和健康检查流量；发布后观察 DNS 失败、连接拒绝与延迟。回退不应删除全部策略，而应临时扩展到经过确认的缺失目标，并设定到期时间；否则一次故障处置会重新打开无边界的出站通道。

### 配置更新取决于注入方式与旧合同

### 配置更新取决于注入方式与旧合同

将 ConfigMap 以环境变量注入容器后修改其内容，并不会让已运行的 Pod 自动获得新值。环境变量只在容器启动时解析一次；旧 Pod 继续使用启动瞬间的“配置合同”。最小反证是：将 `FEATURE_FLAG=false` 写入 ConfigMap，以 `env` 注入 Deployment；更新为 `true` 后，进入旧 Pod 执行 `printenv`，仍会看到 `false`。

这类误判的用户影响通常不是“配置未生效”这么简单：功能开关、上游地址、限流阈值可能在不同副本间不一致；重启后的新 Pod 使用新值，未重启的旧 Pod 使用旧值，导致灰度行为不可预测，甚至出现请求路由到不兼容后端。

修正前先区分注入方式：

- **环境变量**：不自动更新，必须重建 Pod，通常通过修改 Deployment 的 Pod 模板触发滚动发布。
- **ConfigMap 卷挂载**：kubelet 会最终同步文件内容，但存在传播延迟；应用还必须主动重新读取文件，或支持热加载。使用 `subPath` 挂载时，文件通常不会随 ConfigMap 更新。
- **启动参数或模板渲染结果**：本质上也属于启动时快照，应按重启生效处理。

推荐为配置计算版本或校验和，并写入 Pod 模板注解，例如 `config-hash`。配置变更即改变模板，从而触发可观察、可审计的滚动更新。发布前应确认新旧配置兼容：字段可选、默认值明确、协议地址可同时服务旧客户端；否则应先部署兼容应用，再切换配置。

回退不能只“改回 ConfigMap”。若配置通过环境变量注入，必须同时回滚工作负载版本或再次滚动重启，确保所有副本恢复到同一合同。滚动期间保留足够的 `maxUnavailable=0`、就绪探针和发布记录，才能在新配置导致错误率上升时停止扩散并恢复稳定副本。

### 按角色交付修正方案与验收卡

### 按角色交付修正方案与验收卡

将修正拆分给平台、应用与安全角色，避免“修好配置”却遗漏可用性验证。

- **配置存放：平台/安全**
  - 最小反证：ConfigMap 中的 Base64 字符串可被直接解码，仍是明文密码。
  - 修正：密码、令牌、证书改存 `Secret`；更高敏感度场景接入外部密钥系统并限制读取主体。
  - 用户影响：滚动更新期间可能出现短暂重连；禁止在日志、环境诊断页回显密钥。
  - 回退：保留旧版本 Secret 引用与应用配置版本；新凭据异常时切回旧引用，随后立即轮换旧凭据。
  - 验收卡：`kubectl get configmap -o yaml` 无密码字段；非授权 ServiceAccount 无法 `get secret`；应用可用新凭据完成连接。

- **工作负载身份：平台**
  - 最小反证：gateway 的 ServiceAccount 绑定 `cluster-admin`，或拥有跨命名空间 `list secrets`。
  - 修正：按实际 API 调用建立命名空间级 `Role`/`RoleBinding`，仅授予必要的 `get`、`watch` 或特定资源权限。
  - 用户影响：若遗漏真实依赖，网关启动或路由同步会失败。
  - 回退：保留原绑定清单但不长期保留高权绑定；根据审计日志补充最小权限后重新发布。
  - 验收卡：`kubectl auth can-i` 显示仅允许所需操作；网关健康检查、路由发布和证书加载正常。

- **网络边界：安全/平台**
  - 最小反证：NetworkPolicy 只限制入站，Pod 仍可任意访问外网或集群服务。
  - 修正：同时声明 `egress`，显式放行依赖服务、必要网段与集群 DNS。
  - 用户影响：遗漏 DNS 或第三方依赖会造成解析失败、支付/登录等链路超时。
  - 回退：先恢复上一版策略，再依据流量日志逐项增加出口规则，不使用全量放通。
  - 验收卡：允许业务访问与 DNS 解析；未授权目标连接失败且有策略命中证据。

- **配置更新：应用**
  - 最小反证：以环境变量注入 ConfigMap 后更新 ConfigMap，旧 Pod 的环境变量不会自动变化。
  - 修正：将配置变更纳入部署版本，触发滚动重启；需要热更新时采用挂载文件与应用重载机制。
  - 用户影响：滚动发布可能降低瞬时容量，应设置副本冗余与就绪探针。
  - 回退：回滚 Deployment 的镜像/配置版本，并确认旧 Pod 已替换完成。
  - 验收卡：新 Pod 显示目标配置版本；业务请求行为符合新规则；回滚后配置与服务指标同步恢复。

> **要点** — 安全配置不是单一资源选择，而是秘密存储、身份授权、网络双向边界与可回退发布的协同约束。

以虚构IM平台为例，为gateway、transfer、migrate等角色建立从配置来源到网络访问的可审计最小权限边界。

### 先画角色、资源与信任边界表

### 先画角色、资源与信任边界表

先把“谁需要什么”写成表，而不是直接堆 YAML。以下表只描述**应有权限**；真实集群是否已授予，仍须以 API 查询、RoleBinding/ClusterRoleBinding 和网络策略为准。

| 角色 | 配置与 Secret | 身份与接口 | 网络目标 | 业务理由与边界 |
|---|---|---|---|---|
| `gateway` | 读取本命名空间 `ConfigMap`；仅引用 TLS、签名密钥等指定 `Secret`，不读取值 | 使用专属 `ServiceAccount`；仅可 `get` 必要服务发现对象 | 仅接收入口流量，并访问 OpenIM 后端、鉴权服务 | 负责请求入口，不应创建工作负载、读取迁移凭据或访问对象存储 |
| `transfer` | 读取传输参数配置；引用 S3 凭据、临时令牌等指定 `Secret` | 专属 SA；对任务对象仅 `get/list/watch` 或按名称 `get` | 仅访问 S3 端点、消息队列、内部传输服务 | 负责数据搬运；S3 的对象、桶和区域以权威记录 `m-9` 为准，B 设备确认应单独验真 |
| `migrate` | 读取迁移计划配置；引用源端、目标端的必要凭据 | 专属 SA；可对迁移 CR、Job 等执行最小 `get/create/update` | 仅连接源集群、目标集群及迁移控制面 | 负责受控迁移，不应继承 `gateway` 的入口身份，也不应获得全局管理员权限 |

表中的“引用 Secret”不等于可读取 Secret 内容：应用可通过卷或环境变量获得所需字段，但排障人员、流水线和普通 SA 不应因而拥有 `secrets get/list`。同理，API 的 `get` 应优先限定名称与命名空间；`list/watch` 只有控制器确需持续观察时才授予。

网络边界还要单列允许的出站连接、端口、DNS 依赖和入站来源。对于应用返回的 `u-c404`、重复 `409`，先区分路由不存在、幂等重试或状态冲突，不能据此推断 Kubernetes 权限。即使拿到两份 OpenIM 源码，也只能说明程序可能请求哪些资源，不能证明真实集群中的 SA、RBAC 绑定和网络策略已经允许这些访问。

### 配置版本与秘密引用分离

### 配置版本与秘密引用分离

`ConfigMap` 适合承载可公开、可审计且需要版本追踪的配置，例如网关路由规则、迁移批次、对象存储端点、功能开关与来源版本：

- `config.sourceVersion: m-9`
- `transfer.targetRegion: cn-east-1`
- `gateway.timeoutSeconds: "30"`

其中版本号应指向可追溯的发布来源，如镜像清单、配置仓库提交或经审批的数据快照。它说明“工作负载按哪一版规则运行”，但不证明该版本拥有真实集群中的权限；即使 OpenIM 的两份源码配置一致，也不能据此推导 ServiceAccount、RBAC 或网络策略已正确生效。

敏感值应存入 `Secret`，工作负载仅保存引用关系，而不在 `ConfigMap`、环境说明、日志或工单中重复写入值：

`secretRef: { name: s3-credential, key: accessKey }`

这使部署清单可审计“谁依赖哪个秘密”，同时避免泄露 `accessKey`、令牌、数据库口令或私钥。应用读取后也不应回显秘密；排障日志只记录 Secret 名称、键名、挂载是否成功及版本标识。

需特别区分三件事：

1. `base64` 只是编码，不是加密；能够读取 Secret 对象的人通常可解码其内容。
2. 静态加密保护 Secret 在 etcd 或存储介质中的落盘数据，不能替代访问控制。
3. 真正限制泄露面的，是读取权限：RBAC 应只允许指定 ServiceAccount 对指定 Secret 执行必要的 `get`，避免宽泛的 `list`、`watch` 或跨命名空间读取。

例如 gateway 只需读取 `tls-cert`，transfer 只需读取 `s3-credential`；两者不应因“同属同一平台”而共享全部 Secret。这样即使某个 Pod 被攻陷，攻击者可取得的秘密范围也被限制在该角色的最小运行需求内。

### 三层身份不可互相替代

### 三层身份不可互相替代

`gateway`、`transfer`、`migrate` 往往同时携带三类身份，但它们回答的是不同问题：

| 层次 | 认证对象 | 授权范围 | 典型凭据 |
|---|---|---|---|
| ServiceAccount | 哪个 Pod/工作负载在调用 Kubernetes API | 仅作为集群内调用主体 | 投射令牌 |
| Kubernetes RBAC | 该主体可对哪些 Kubernetes 资源做什么 | `get/list/watch/create` 等 API 动词及命名空间范围 | Role、RoleBinding |
| 数据库或 IM 业务身份 | 哪个业务客户端访问数据库、IM 服务或对象存储 | 业务接口、租户、表/频道/对象前缀等 | 密码、证书、访问令牌 |

ServiceAccount 本身不等于权限。为 `transfer` 配置 `serviceAccountName: transfer-sa`，只说明 Pod 以 `transfer-sa` 身份访问 API；若未绑定 RBAC，它仍不能读取 ConfigMap、查询 Job 或引用相关 Secret。反过来，Role 也不能独立生效，必须经 RoleBinding 绑定到具体 ServiceAccount。

RBAC 更不能替代业务身份。允许 `migrate-sa` 对某个 Secret 执行 `get`，仅表示它可从 Kubernetes API 读取该 Secret 对象；数据库是否接受其中的账号、该账号能否写目标库，仍由数据库自身验证。审计时应记录 Secret 的**引用名、版本来源和读取主体**，而非输出密钥值。

同样，数据库管理员账号或 IM 管理令牌不能自动获得 Kubernetes API 权限。将其塞入 Pod 并不能使其列出 Pod、读取 ConfigMap；若为方便而授予 `cluster-admin`，会把一次业务凭据泄露扩大为集群级接管风险。

因此应分别收敛：Pod 使用专用 ServiceAccount；RBAC 将 `get` 限到必要资源名和命名空间；业务账号按数据库、租户或 IM 能力拆分。网络策略再限定其只能连接必要的数据库、IM 端点或 S3 服务，避免“身份正确但网络可横向访问”。

### 最小API权限与双向网络准入

### 最小API权限与双向网络准入

最小权限应按工作负载拆分，而不是让 `gateway`、`transfer`、`migrate` 共用高权限 ServiceAccount。权限审计时应同时回答：它能读取什么对象、位于哪个命名空间、是否能列举全部对象、以及该读取是否真的必要。

| 工作负载 | 必要 API 范围 | 不应授予 |
|---|---|---|
| `gateway` | 仅 `get` 自身命名空间内指定 `ConfigMap`、指定 `Secret`；必要时读取自身 `Service` | `list/watch` 全部 Secret、跨命名空间读取、写入工作负载 |
| `transfer` | `get` 传输端点配置、S3 凭据引用的指定 Secret | 读取 Secret 值以外的无关凭据、创建 RBAC 对象 |
| `migrate` | `get` 迁移任务配置、目标连接凭据；必要时 `create/get` 自身 Job 或状态对象 | 集群级 `*` 权限、修改 Deployment、读取全部 ConfigMap |

例如，Secret 引用应限定到明确名称，而非依赖 `list` 后自行筛选：

`resources: ["secrets"]`、`verbs: ["get"]`、`resourceNames: ["transfer-s3-credential"]`

这只能限制 Kubernetes API 中的读取范围；它不证明运行中的 Pod 已获得真实集群权限。尤其 OpenIM 存在两套源码或多份清单时，必须以实际生效的 `ServiceAccount`、`RoleBinding`、Pod `serviceAccountName` 和 API 审计记录为准。S3 对象及版本权威性仍应由 S3 端确认，例如以权威版本 `m-9` 和 B 设备独立验收为证，不能仅凭应用返回 `u-c404` 或重复 `409` 推断权限、幂等性或迁移成功。

网络边界同样是双向准入。若 NetworkPolicy 已由支持它的 CNI 实际执行，则通信成立需同时满足：

- **出口允许**：源 Pod 可访问目标 Pod、DNS、S3 网关或外部地址的对应端口；
- **入口允许**：目标 Pod 接受源 Pod 标签、命名空间或 IP 段发起的对应端口连接；
- **解析允许**：访问域名时，必须允许到集群 DNS 的 UDP/TCP `53` 出口。

例如 `gateway → transfer:8443` 不仅要在 `gateway` 的 `egress` 中放行 `transfer`，还要在 `transfer` 的 `ingress` 中允许来自 `gateway` 的 `8443`。若策略仅写入口或仅写出口，连接仍会失败。还应确认 CNI 是否支持并启用了 NetworkPolicy；未生效的策略文件只是声明，不构成网络隔离。

### 用业务验收卡闭环异常合同

### 用业务验收卡闭环异常合同

为 `gateway`、`transfer`、`migrate` 建立一张可执行的业务验收卡，不只验证“请求成功”，还要验证异常语义、证据来源与权限边界是否符合旧合同。

| 验收场景 | 请求与预期 | 必须保留的证据 |
|---|---|---|
| 用户 `u-c404` 不存在 | 查询或迁移请求返回旧合同约定的“用户不存在”；不得因后端改造变成泛化 `500` | 网关请求标识、版本号、返回码、审计日志中的调用身份 |
| 重复提交 | 同一幂等键再次发起 transfer/migrate，返回 `409`，且不创建第二份任务、不重复扣费或复制数据 | 幂等键、原任务 ID、`409` 响应、数据库或队列去重记录 |
| S3 迁移结果 | `m-9` 是对象迁移状态的权威记录；应用缓存、消息回执只能辅助，不可覆盖其结论 | `m-9` 记录版本、对象 ETag/版本号、写入者服务账号、时间戳 |
| B 设备确认 | B 设备“已确认”仅证明设备侧确认链路完成，不能自动证明 S3 对象已落盘或迁移已完成 | B 设备签名/回执、关联任务 ID；与 `m-9` 分开验收 |

验收时应刻意注入权限拒绝：例如让 `transfer` 的服务账号缺少读取指定 Secret 或获取某 ConfigMap 的权限，预期得到明确的 `403`，而非通过扩大 RBAC、改用默认服务账号或在日志中泄露 Secret 值来“修复”。API 权限应限定到实际所需的 `get`、指定资源名与命名空间；配置变更须能追溯到来源版本、提交记录和生效对象。

还要验证网络边界：`gateway` 可调用允许的内部入口，`transfer` 仅可访问必要的 S3 端点及依赖服务，`migrate` 不应因便捷而获得跨命名空间或公网任意出口。两份 OpenIM 源码或配置样例只能说明实现意图，不能证明真实集群已授予相同权限；最终依据必须是集群中的 ServiceAccount、RoleBinding、NetworkPolicy 与实际审计记录。

> **要点** — 安全边界应按角色、资源、版本和连接逐项授权；Secret不等于加密，源码也不等于真实集群权限。

以虚构IM平台为线索，建立“配置、凭据、集群身份、业务成员身份、网络边界”五层权限模型，避免把便利性误当成安全性。

### 配置与凭据：先划清数据边界

### 配置与凭据：先划清数据边界

对 IM 平台而言，首先要回答的不是“能否放进 Kubernetes”，而是“这份数据泄露后是否会扩大权限”。据此划分：

- **ConfigMap**：保存非敏感配置，如 `LOG_LEVEL`、功能开关、消息大小上限、服务地址、公开证书链。
- **Secret**：保存敏感材料，如数据库密码、第三方 API Token、TLS 私钥、签名密钥、机器人令牌。

两者都可通过环境变量或卷挂载提供给 Pod：

- 环境变量适合启动时读取、无需热更新的少量键值；但值容易出现在进程环境、诊断输出或误配的日志中。
- 卷挂载适合证书、配置文件及需要更新的内容。ConfigMap/Secret 卷内容通常会被 kubelet 异步刷新，但**不会自动让应用重载配置**；应用必须监听文件变化，或通过滚动重启生效。

Secret 的 `data` 字段通常使用 Base64：

`password: bXktZGItd2Fzcw==`

这只是编码，不是加密；任何能读取 Secret 清单或 etcd 数据的人都可解码。真正的保护边界包括：限制 `get/list/watch secrets` 的 RBAC 权限、启用 etcd 静态加密、使用外部密钥管理系统，并避免将 Secret 提交到 Git、镜像层、日志和错误页面。

例如，聊天室的 `MAX_GROUP_MEMBERS=500` 应放入 ConfigMap；`DB_PASSWORD`、对象存储访问密钥应放入 Secret。反例是把数据库密码写进 ConfigMap，或把仅用于开发的默认 Token 烘焙进镜像：前者误判数据敏感性，后者会使配置漂移与密钥轮换失控。

### 三类身份：工作负载、集群与业务

### 三类身份：工作负载、集群与业务

同一个 IM 服务中，“谁在运行”“谁能操作集群资源”“谁能读某个会话”是不同问题，不能由同一套账号体系回答。

| 身份与机制 | 回答的问题 | 典型对象 | 不应承担的职责 |
|---|---|---|---|
| `ServiceAccount` | 这个工作负载以什么身份向 Kubernetes API 发起请求？ | `im-api`、`message-worker` 的 Pod | 不能直接表示终端用户或群成员 |
| Kubernetes RBAC | 该身份可对哪些 Kubernetes 资源执行什么动作？ | `Role`、`RoleBinding`、`ClusterRole` | 不决定数据库行数据或聊天室成员资格 |
| 数据库账号 | 应用连接数据库时可访问哪些库、表、操作？ | `im_writer`、`im_reader` | 不识别“用户 A 是否属于群 B” |
| IM 成员授权 | 当前用户能否加入、读取或发送某个会话的消息？ | 用户、群成员、会话管理员 | 不控制 Pod 是否可读取 Secret |

例如，`message-worker` 使用 `ServiceAccount/message-worker` 运行；RBAC 只授予其 `get` 某个 ConfigMap、`list` 本命名空间内 Job 的权限。它连接数据库时使用专门的数据库账号，通常仅有消息表的必要读写权限。用户请求“读取群消息”后，业务层仍必须检查：

`用户 ∈ 会话成员`，或用户具备该会话的管理员角色。

常见错误是把集群管理员权限误当业务管理员权限：某运维人员能够 `kubectl get pods`，并不意味着他可以查看任意私聊内容；反过来，群主能够移除成员，也不应获得 Kubernetes API 或数据库超级账号。权限应沿调用链逐层验证，并遵循最小权限原则。

### 网络策略：默认行为与双向放行

### 网络策略：默认行为与双向放行

`NetworkPolicy` 不是 Kubernetes 自身的数据包过滤器，而是对网络插件的声明；只有所用插件支持并实际启用策略执行时，规则才会生效。若集群未部署支持策略的插件，即使对象已创建，Pod 往往仍可互相直连。

默认情况下，Pod 对入站和出站流量通常都是开放的。策略一旦选择某个 Pod，才会改变该方向的默认语义：

- 存在选择该 Pod 的入站策略时：仅允许所有匹配入站规则的流量。
- 存在选择该 Pod 的出站策略时：仅允许所有匹配出站规则的流量。
- 未被某方向策略选中时：该方向仍默认开放。

策略是**累加并集**，不是按创建顺序覆盖，也不存在“拒绝优先”。例如两条入站策略分别允许 `api` 与 `worker` 访问 `db`，则 `db` 接受两者；删除其中一条才会收回相应通路。

通信成功需要双向推导。设 `api → db:5432`：

1. `db` 的入站策略必须允许来自 `api` 的 TCP 5432；
2. 若 `api` 已被出站隔离，其出站策略也必须允许到 `db:5432`；
3. 返回包通常由连接跟踪自动放行，无须另写 `db → api` 的独立返回规则。

因此，“数据库已放行 API”不等于连接必然成功：API 若有默认拒绝出站策略，却未允许数据库地址、端口及必要 DNS 查询，连接仍失败。实践中先确认插件能力，再为命名空间建立默认拒绝基线，随后按业务依赖显式增加双向所需的出站与入站许可。

### 配置更新：传播路径与版本合同

### 配置更新：传播路径与版本合同

同一份 ConfigMap 或 Secret，进入容器后的“更新语义”并不相同。设计时应先问：配置是**启动时快照**，还是**运行时可感知的文件**？

- **环境变量注入**：Pod 创建时，kubelet 将值写入容器环境；后续 ConfigMap、Secret 即使更新，已运行容器的环境变量也不会变化。要生效通常需要重建 Pod，例如滚动重启 Deployment。
- **卷挂载注入**：以卷形式挂载的 ConfigMap、Secret 会由 kubelet 经过一定同步延迟更新到挂载目录。应用还必须自行重新读取文件；若只在启动时读一次，效果仍等同于环境变量。
- **`subPath` 挂载**：将单个键通过 `subPath` 挂载时，不会获得后续自动更新，应视为固定快照。

例如 IM 平台的 `chat-api` 用环境变量读取 `MAX_GROUP_SIZE`，配置从 `500` 改为 `1000` 后，旧 Pod 仍执行 `500`；而用卷读取 `feature-flags.yaml` 的网关，文件可能已更新，但若进程未监听文件变化或未执行热加载，实际行为依然不变。

这正是 R9 配置漂移的典型来源：**声明状态已更新，运行状态仍保留旧版本合同**。若新配置提高群成员上限，但旧 `chat-api`、异步消费者和数据库校验约束未同时更新，就会出现“入口允许、后端拒绝”或不同副本行为不一致。

治理重点是把配置视为可版本化接口：

1. 为配置定义版本号、默认值、兼容范围和废弃周期，例如 `membership-policy.v2`。
2. 对影响数据约束、权限判断、计费规则的配置，采用“先兼容代码，再切配置，最后清理旧逻辑”的发布顺序。
3. 将配置版本写入日志、指标和健康检查，排障时能确认每个 Pod 实际使用的版本。
4. 对必须一致生效的安全策略，不依赖卷的最终一致更新；应使用带校验的滚动发布或显式重载机制。

### IM平台最小权限验收卡

### IM平台最小权限验收卡

将每次上线视为一次“谁能读什么、调用什么、连到哪里”的验收，而非仅检查 Pod 是否运行。

- **运营人员**
  - 配置放入 `ConfigMap`，令牌、数据库口令、第三方密钥放入 `Secret`；注意 Secret 的 `base64` 只是编码，不是加密，应配合静态加密、外部密钥库和审计。
  - 运营账号按命名空间授予最小 RBAC：可查看日志、重启指定工作负载，不应默认拥有 `secrets/get`、集群管理员或跨命名空间修改权限。
  - 正例：通过受审计的发布流程轮换密钥。反例：在工单、镜像、Git 仓库或 ConfigMap 中明文保存 `DB_PASSWORD`。

- **消息服务**
  - 使用专用 `ServiceAccount`；仅在确需访问 Kubernetes API 时绑定精确的 `Role`/`RoleBinding`，并关闭无用的自动挂载令牌。
  - 数据库账号仅授予消息表所需的 `SELECT`、`INSERT`、`UPDATE`，不得使用数据库超级用户。
  - 网络策略同时限制入口与出口：仅接收网关流量，仅访问数据库、DNS 和必要的对象存储端点。策略是**累加**的，且依赖支持 `NetworkPolicy` 的网络插件；未设策略通常等于默认放通。
  - 正例：消息服务只能写入自己的会话记录。反例：服务账号可读取全命名空间 Secret，或 Pod 可任意出网。

- **数据库**
  - 密码以 Secret 挂载文件提供，避免作为环境变量长期暴露；环境变量中的 Secret 更新不会自动进入已运行进程，轮换后需重启或实现重新加载。
  - 仅允许消息服务和备份任务的网络身份连接，入口、出口均显式收紧；数据库不应可主动访问普通业务 Pod。
  - 验收 `R9` 配置漂移：声明文件、集群实际 RBAC、Secret 引用版本和网络策略必须一致。

- **普通成员**
  - 成员身份是业务层授权，不等同于 Kubernetes `ServiceAccount`。成员只能读取自己所在会话、频道或租户的数据。
  - 正例：接口按 `member_id` 与会话成员关系二次校验。反例：仅凭“已登录”即可按消息 ID 查询任意私聊记录。

> **要点** — 配置不等于秘密，集群权限不等于业务身份；最小授权、双向网络控制与版本化配置合同必须同时成立。
