### 从用户任务建立命令合同

### 从用户任务建立命令合同

设本地文件 `history-c-a.json` 保存会话 `c-a` 的历史：参与者为 `u-a`，其中一条消息标识为 `m-a`。工具只处理本地文件；命令成功仅表示本次本地读取、校验或写出符合约定，**不表示**消息已送达、存在服务端历史，或获得跨文件系统的原子持久化保证。

先把每个用户任务写成可观察的合同：

- `check history-c-a.json`：读取文件并验证版本、结构、必要字段及大小限制。合法时向标准输出写摘要，例如 `检查通过：会话 c-a，消息数 1`，以退出码 `0` 结束。文件不存在、无法读取、超过大小上限、JSON 非法或版本不是 `1` 时，向标准错误写原因，以非 `0` 退出。
- `list history-c-a.json`：先执行与 `check` 相同的验证；验证通过后，将消息按文件中的既定顺序输出，例如 `m-a u-a 你好`。若验证失败，不输出部分消息，标准错误报告错误并以非 `0` 退出。
- `export history-c-a.json 已验证副本.json`：先验证输入，再创建导出副本。成功时标准输出说明目标路径并返回 `0`；目标已存在、目标不可写或复制失败时返回非 `0` 并写标准错误。导出过程拒绝修改 `history-c-a.json`；即使导出失败，也不把“源文件未变”夸大为整个操作具有原子性。

版本 `1` 与文件大小上限是输入边界的一部分，而非实现细节。命令参数缺失、参数过多或路径不符合预期同样属于用户可预见的失败，应给出简短用法提示并返回非零退出码。文档中的命令和输出只是静态预期，未在读者环境中执行。

### 子命令、选项与配置优先级

### 子命令、选项与配置优先级

根命令只负责分派，不直接处理历史数据。可将工具约定为：

- `history check`：检查输入文件是否可读、大小是否超限、版本是否为 `1`、结构是否有效。
- `history list`：在完成同样的读取与验证后，将消息显示到标准输出。
- `history export`：验证输入后，把已验证的副本写入目标文件；拒绝覆盖或修改源文件。

每个子命令使用独立的 `flag.FlagSet`，避免无关选项混在一起：

```text
history check  [-input history-c-a.json] [-max-bytes 1048576]
history list   [-input history-c-a.json] [-max-bytes 1048576]
history export [-input history-c-a.json] [-output verified-history-c-a.json] [-max-bytes 1048576]
```

建议默认值保持保守且可预测：

| 选项 | 默认值 | 含义 |
|---|---:|---|
| `-input` | `history-c-a.json` | 本地历史文件路径 |
| `-max-bytes` | `1048576` | 最大允许读取大小，单位为字节 |
| `-output` | `verified-history-c-a.json` | 导出的新文件路径，仅 `export` 使用 |

配置优先级应明确为：**命令行选项 > 程序默认值**。例如：

```text
history check -input m-a.json -max-bytes 2048
```

此时程序检查 `m-a.json`，并以 `2048` 字节为上限；未提供的选项仍采用默认值。若后续加入配置文件或环境变量，也应继续保持“显式命令行参数最高优先级”的规则。

`check` 成功时可向标准输出给出简短摘要；错误信息写入标准错误，退出码为非零。`list` 的消息内容写入标准输出，诊断信息仍写入标准错误。`export` 只有在输入完整通过验证、输出路径不等于输入路径且目标可安全创建时才成功。

这些退出码只说明本地命令完成了预期操作：它不表示消息曾送达服务端，不表示真实 IM 历史完整，也不表示跨文件系统的持久化或原子写入已经获得保证。

### 版本化 JSON 的限量读取与严格核对

### 版本化 JSON 的限量读取与严格核对

版本 1 只接受明确的本地文件格式，例如 `history-c-a.json`：

`{"version":1,"messages":[{"id":"m-a","from":"u-a","to":"u-a","content":"你好"}]}`

读取顺序应先限制资源，再解析内容，最后进行业务核对：

1. 用 `os.Open` 只读打开输入文件；`check`、`list`、`export` 都不得原地改写它。
2. 通过 `io.LimitReader` 限制最大字节数，例如 `$1\text{ MiB}$`。文件超过上限时应拒绝，而不是继续读取全部内容。
3. 用 `json.Decoder` 解码，并确认输入只有一个完整 JSON 值；`{...}垃圾` 也必须视为非法。
4. 先检查 `version`。仅接受整数 `1`；缺失、字符串 `"1"`、`0`、未来版本 `2` 都拒绝。
5. 检查顶层和消息字段：`messages` 必须是数组；每条消息的 `id`、`from`、`to`、`content` 必须存在且符合约束，例如 `id` 非空、消息 ID 不重复、`from` 与 `to` 为允许的用户标识。
6. 未知字段应拒绝。版本 1 不“忽略以后再说”：未知数据可能表示调用方误用了新格式，也可能掩盖拼写错误。

可使用 `decoder.DisallowUnknownFields()` 实现未知字段拒绝；解码后再读取一次，只有得到 `io.EOF` 才说明没有额外 JSON 或尾随内容。

核对成功时，`check history-c-a.json` 向标准输出打印静态预期结果，如 `有效：版本 1，1 条消息`，并以退出码 `0` 结束。文件不存在、超限、JSON 损坏、版本不支持或字段非法时，诊断写入标准错误，退出码为非零。此“成功”只表示本地文件通过当前工具的格式验证，不表示消息已送达、服务端保存，或任何跨进程原子保证。

### 单向分层与导出写入边界

### 单向分层与导出写入边界

将工具分为三层：`domain` 只表达历史、消息和核对规则；`adapter` 负责读取、解析和写入 JSON 文件；`cmd` 负责参数、标准输入输出、退出码。依赖方向始终向内：

`cmd → adapter → domain`

领域层不应导入 `os`、`encoding/json` 或终端输出包。这样，“版本必须为 1”“消息 ID 不重复”“时间字段合法”等规则可直接用内存数据测试，不依赖文件。

`history-c-a.json` 是外部输入，不是可信对象。适配器读取后先限制大小，例如超过约定上限立即拒绝；再反序列化为领域对象；最后调用核对函数。`check` 成功只说明该本地文件符合当前规则，不能表示消息已送达、服务端仍保存历史，或多步骤操作具有原子性。

`list` 只能展示已核对的数据。消息正文可能敏感，默认应避免无边界地输出全部内容；可显示发送者、时间、消息 ID 和截断摘要，例如：

`m-a 2025-01-01T10:00:00Z u-a: 你好，……`

完整正文应仅在明确设计了相应选项时显示，并仍写到标准输出；解析失败、核对失败和文件错误写到标准错误。

`export` 的边界尤其重要：它读取并核对源文件，再把已验证副本写入目标路径；绝不修改源文件。目标已存在时，覆盖行为必须由参数约定明确，例如要求 `--force`。写入后必须检查关闭错误：

`写入 → Close → 报告成功`

仅写入成功而忽略 `Close` 失败，不能宣称导出成功。成功返回 `0`；参数错误、超限、JSON 错误、规则不通过或写入失败返回非零码。所有示例命令与输出只是静态预期，不代表已经执行。

### 结果通道、退出码与验证案例

### 结果通道、退出码与验证案例

命令的正常结果写入标准输出，诊断信息写入标准错误；调用者可据退出码判断是否成功。以下均为静态预期，未实际执行。

```text
$ imhist check history-c-a.json
版本：1
会话：c-a
用户：u-a
消息数：2
状态：有效
```

预期：`stdout` 为上述摘要，`stderr` 为空，退出码为 `0`。这只表示本地文件通过本工具的版本 1 格式与大小检查；不表示消息已送达服务端，也不表示存在服务端历史。

文件不存在时：

```text
$ imhist check missing.json
错误：无法读取输入文件 missing.json：文件不存在
```

预期：`stdout` 为空，`stderr` 输出错误，退出码为 `1`。若文件超过约定大小上限，或 JSON 损坏、版本不是 `1`、会话/用户/消息字段不合法，也应拒绝处理并返回非零退出码；拒绝路径不得修改源文件。

`list` 仅在验证成功后显示消息，例如：

```text
$ imhist list history-c-a.json
[1] u-a: 你好
[2] m-a: 收到
```

`export` 将已验证内容复制到新路径：

```text
$ imhist export history-c-a.json verified.json
已导出：verified.json
```

预期退出码为 `0`，且 `verified.json` 内容与已验证输入一致。这里的“导出成功”仅表示本地写入完成；它不承诺跨文件系统的原子性或持久化到物理介质。

测试应直接对应需求表：单元测试覆盖版本、必填字段、消息格式与大小判断；临时目录集成测试创建 `history-c-a.json`，捕获 `stdout`、`stderr` 和退出码，并断言失败输入后源文件字节内容不变。

> **要点** — 可靠 CLI 的核心是先写清合同，再用分层、限量验证、明确诊断和测试落实边界。

本节以可教学的 Go CLI 骨架为目标，先划清包边界，再确定命令入口与退出流程，避免领域逻辑被命令行细节污染。

### 从用户任务拆分项目目录

### 从用户任务拆分项目目录

用户看到的是三类任务：导入聊天记录、核对已导入数据、导出可迁移文件。目录设计应让每类变化落在明确位置，而不是把解析文件、业务规则和命令行参数混进一个 `main.go`。

```text
imhistory/
├── go.mod
├── history/
│   └── history.go
├── internal/
│   └── historyfile/
│       └── file.go
└── cmd/
    └── imhistory/
        └── main.go
```

- `go.mod`：声明模块路径与依赖版本。例如模块名为 `example.com/imhistory` 时，其他包通过该路径导入领域能力。
- `history/`：放置稳定的领域模型与规则，例如消息、会话、导入后的历史集合，以及“记录是否合法”“如何按时间核对”等逻辑。这个包只依赖标准的抽象能力或自身类型，不应知道 `os`、`flag`、终端输出或具体文件格式。
- `internal/historyfile/`：文件适配器。它负责把 CSV、JSON 或某个 IM 导出的原始文件转换为 `history` 中的类型，也负责把领域数据写回文件。其依赖方向是 `historyfile → history`；反过来不成立，因此领域规则不会被文件格式绑住。
- `cmd/imhistory/`：可执行程序入口。`main.go` 解析 `import`、`check`、`export` 等子命令及其参数，连接标准输入输出、调用适配器和领域服务，并将结果呈现给用户。

可以把依赖关系记为：

`cmd/imhistory → internal/historyfile → history`

其中 `cmd` 还可以直接调用 `history`，但 `history` 绝不反向导入命令行包。这样，新增一种导入文件格式时主要修改 `internal/historyfile`；调整核对规则时主要修改 `history`；改变参数名称、帮助文本或输出样式时只修改 `cmd/imhistory`。

### 领域包保持纯粹与可测

### 领域包保持纯粹与可测

`history` 只表达“什么是本地 IM 历史”以及“历史是否满足业务规则”，不关心文件位于何处、参数如何解析、结果如何打印。建议目录中的职责如下：

- `history/`：消息模型、版本规则、核对接口与纯业务实现。
- `internal/historyfile/`：把磁盘文件转换为 `history` 模型；可导入 `history`。
- `cmd/imhistory/`：解析命令行参数、组装依赖、输出文本；可导入前两者。

领域模型可保持为普通 Go 值，不引入 `os`、`flag`、`fmt` 的输出能力：

```go
// history/message.go
package history

import "time"

type Message struct {
	ID        string
	SentAt    time.Time
	SenderID  string
	Body      string
}

type Archive struct {
	Version  int
	Messages []Message
}
```

版本属于历史格式的业务约束，而非命令行约束。核对结果也应结构化返回，使调用方自行决定显示方式：

```go
// history/check.go
package history

const CurrentVersion = 1

type Issue struct {
	Message string
}

type Checker interface {
	Check(Archive) []Issue
}

type VersionChecker struct{}

func (VersionChecker) Check(a Archive) []Issue {
	if a.Version != CurrentVersion {
		return []Issue{{Message: "不支持的历史版本"}}
	}
	return nil
}
```

这样测试无需创建临时文件、伪造参数或捕获终端输出：

```go
func TestVersionChecker(t *testing.T) {
	issues := history.VersionChecker{}.Check(history.Archive{Version: 2})
	if len(issues) != 1 {
		t.Fatal("期望发现版本问题")
	}
}
```

领域包若导入 `os` 或 `flag`，就会把“数据规则”绑定到进程环境；若直接向标准输出写文本，则调用者无法选择终端、日志、图形界面或测试断言方式。保持输入为值、输出为值或错误，才能让规则稳定复用。

### 文件适配器负责受限读取

### 文件适配器负责受限读取

`internal/historyfile` 是文件格式与领域模型之间的适配层：它可以依赖 `history`，却不应反向要求领域包理解 JSON、路径或 `os.File`。这样，`history` 只表达“什么是合法历史”，文件包只负责“如何从磁盘取得或写回它”。

建议让文件内容带显式版本，避免未来字段演进时静默误读：

```go
package historyfile

import (
	"encoding/json"
	"fmt"
	"io"

	"example.com/imhistory/history"
)

type document struct {
	Version int             `json:"version"`
	Records []history.Record `json:"records"`
}

func Decode(r io.Reader) ([]history.Record, error) {
	var doc document

	dec := json.NewDecoder(r)
	dec.DisallowUnknownFields()
	if err := dec.Decode(&doc); err != nil {
		return nil, fmt.Errorf("解析历史文件: %w", err)
	}
	if doc.Version != 1 {
		return nil, fmt.Errorf("不支持的历史文件版本: %d", doc.Version)
	}
	if err := history.Validate(doc.Records); err != nil {
		return nil, fmt.Errorf("历史记录无效: %w", err)
	}
	return doc.Records, nil
}
```

`Decode` 接受 `io.Reader`，因此可被文件、测试缓冲区或网络输入复用；版本检查、未知字段拒绝和领域验证共同构成严格读取。尤其不要只因 JSON 能反序列化成功就视为数据可信。

涉及路径和关闭操作时，再提供薄包装：

```go
func Load(path string) ([]history.Record, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, fmt.Errorf("打开历史文件: %w", err)
	}
	defer f.Close()

	return Decode(f)
}
```

导出也应限定为该包的职责：先构造版本化 `document`，再用 `json.Encoder` 写入 `io.Writer`。命令层决定输出文件、标准输出及覆盖策略；适配器不解析 Flag，也不直接打印错误。这样既能防止文件细节渗入领域，又能保证打开的文件通过 `defer` 被关闭。

### 命令入口集中解析与编排

### 命令入口集中解析与编排

`cmd/imhistory/main.go` 是唯一认识命令行参数、环境变量和终端流的地方。它解析子命令后，为每个子命令创建独立的 `flag.FlagSet`；领域包只接收已经整理好的值，不应导入 `os` 或 `flag`。

```go
package main

import (
	"flag"
	"fmt"
	"io"
	"os"
)

func main() {
	if err := run(os.Args[1:], os.Stdout, os.Stderr); err != nil {
		fmt.Fprintln(os.Stderr, "错误：", err)
		os.Exit(1)
	}
}

func run(args []string, stdout, stderr io.Writer) error {
	if len(args) == 0 {
		return fmt.Errorf("缺少子命令：可用 import、check、export")
	}

	switch args[0] {
	case "import":
		return runImport(args[1:], stdout, stderr)
	case "check":
		return runCheck(args[1:], stdout, stderr)
	case "export":
		return runExport(args[1:], stdout, stderr)
	default:
		return fmt.Errorf("未知子命令 %q", args[0])
	}
}

func runImport(args []string, stdout, stderr io.Writer) error {
	fs := flag.NewFlagSet("import", flag.ContinueOnError)
	fs.SetOutput(stderr)

	input := fs.String("input", "", "待导入的历史文件")
	store := fs.String("store", defaultStore(), "本地历史目录")
	if err := fs.Parse(args); err != nil {
		return err
	}
	if *input == "" {
		return fmt.Errorf("import 需要 --input")
	}

	fmt.Fprintf(stdout, "导入 %s 到 %s\n", *input, *store)
	return nil
}

func defaultStore() string {
	if v := os.Getenv("IMHISTORY_STORE"); v != "" {
		return v
	}
	return "history"
}
```

配置优先级应固定且可预测：**显式参数 > 环境变量 > 内置默认值**。例如 `--store` 覆盖 `IMHISTORY_STORE`，环境变量缺失时才使用 `history`。`stdout` 只承载成功结果、导出内容等可被脚本消费的数据；用法错误、进度和诊断信息写入 `stderr`。

注意不要在 `run` 内调用 `os.Exit`：它会立刻终止进程，所有尚未执行的 `defer` 都会被跳过。入口只在 `run` 返回后统一输出错误并退出，便于内部安全关闭文件、刷新缓冲区和编写测试。

### 统一 run 合同与安全退出

### 统一 `run` 合同与安全退出

命令行程序通常需要区分三类结果：正常完成、用户输入或业务错误、运行环境错误。`run` 的返回约定必须全项目一致，常见有两种方案：

| 方案 | `run` 签名 | 优点 | 代价 |
|---|---|---|---|
| 返回错误 | `func run(args []string, stdout, stderr io.Writer) error` | Go 风格自然；错误可保留上下文并用 `%w` 包装；测试可直接断言错误 | `main` 需要统一把错误映射为退出码 |
| 返回退出码 | `func run(args []string, stdout, stderr io.Writer) int` | 调用方直接得到进程状态；适合复杂子命令分级 | 错误文本、错误类型与退出码容易分散处理 |

这里选择“返回 `error`”作为全局合同：领域层和文件适配器本就以错误表达失败，`run` 负责解析参数、编排导入/核对/导出，并将错误交给最外层决定如何展示。默认约定为：`nil` 表示成功；非 `nil` 输出到标准错误并以退出码 `1` 结束。

```go
func main() {
	if err := run(os.Args[1:], os.Stdout, os.Stderr); err != nil {
		os.Exit(1)
	}
}
```

关键顺序不能颠倒。`os.Exit` 会立即终止整个进程，**不会执行任何已注册的 `defer`**。因此，`run` 内部可以安全地使用延迟关闭、临时文件清理或输出刷新：

```go
func run(args []string, stdout, stderr io.Writer) error {
	f, err := os.CreateTemp("", "imhistory-*")
	if err != nil {
		return err
	}
	defer os.Remove(f.Name())
	defer f.Close()

	// 解析 args、调用应用服务、写入 stdout。
	return nil
}
```

若在 `run` 深处直接调用 `os.Exit`，上述清理会被跳过，测试也无法观察错误结果。故规则应明确：除 `main` 外，任何包都返回错误，不退出进程；`main` 只在 `run` 完整返回后调用一次 `os.Exit`。

> **要点** — 让领域规则、文件适配和命令入口单向依赖，并以统一 run 合同保证输出、清理与退出语义可验证。

本节把命令行参数视为用户合同：每个子命令独立解析、明确取值来源，并在执行前拒绝含糊、空缺或越界的输入。

### 从任务拆分独立子命令

### 从任务拆分独立子命令

完整工具不应把所有操作塞进一组参数，而应先按用户任务划分入口。`check`、`list`、`export` 虽然都读取本地 IM 历史，但它们回答的问题不同，因此应拥有独立的位置参数、选项和输出责任。

- `check`：回答“这个历史文件能否被读取和解析？”  
  输入通常是文件路径；输出是核对结果、记录数量或首个错误位置。它不应生成导出文件。

- `list`：回答“历史中有哪些会话、日期或消息摘要？”  
  输入是文件路径及筛选条件；输出是终端中的可读列表。它不应把列表结果隐式写入磁盘。

- `export`：回答“把符合条件的历史保存到哪里？”  
  输入除源文件外，还必须包含目标路径 `-out`；输出责任是创建导出文件，并报告写入数量与实际位置。

命令行可抽象为：

`imhitory <子命令> [位置参数] [选项]`

其中，子命令是第一个位置参数，例如：

`imhistory check -file history.json`  
`imhistory list -file history.json`  
`imhistory export -file history.json -out messages.csv -max-bytes 10485760`

位置参数适合表达“要执行什么任务”；`-file`、`-out`、`-max-bytes` 这类具名选项适合表达可选或容易混淆的配置。尤其是导出目标若靠第二、第三个位置参数传递，用户很容易把源文件与目标文件写反；显式的 `-out` 更清楚，也便于验证。

这种拆分还意味着每个子命令只接受自己理解的参数：`check` 不需要 `-out`，`list` 不应默默接受导出专用选项。未知选项、缺失值和多余位置参数都应在执行前报错，避免“命令看似成功，实际做错任务”。

### 用 FlagSet 隔离参数解析

### 用 FlagSet 隔离参数解析

顶层命令只负责识别子命令，例如：

`imh check ...`、`imh list ...`、`imh export ...`

随后应为每个子命令创建独立的 `flag.FlagSet`：

```go
fs := flag.NewFlagSet("export", flag.ContinueOnError)
file := fs.String("file", "", "历史文件路径")
out := fs.String("out", "", "导出目录")
maxBytes := fs.Int64("max-bytes", 0, "最大读取字节数")
```

这里的隔离不是形式问题，而是参数合同不同：`check` 可能只需要 `-file`，`list` 需要 `-file` 与筛选条件，`export` 则额外需要 `-out`、`-max-bytes`。若所有参数都注册到全局集合，某个命令会错误接受本不属于它的选项，帮助信息也会混杂。

必须先定义该子命令支持的**全部** flag，再调用：

`err := fs.Parse(args)`

`Parse` 之后，`fs.Args()` 才是未被 flag 消费的位置参数。例如 `imh export backup -out result` 中，`backup` 可作为导出名称；而 `-out result` 由 `FlagSet` 解析。位置参数的数量、是否允许为空，应由子命令单独验证，不能依赖解析器自动保证。

选择 `flag.ContinueOnError` 的关键在于：解析失败时不直接退出进程，而是返回错误。命令层可以统一补充上下文、输出该子命令的用法，并决定返回何种退出码：

`if err := fs.Parse(args); err != nil { return fmt.Errorf("解析 export 参数: %w", err) }`

这也使测试可以断言非法 `-max-bytes`、未知选项或缺少选项值确实产生错误。注意，解析成功只说明语法成立；`-file ""`、`-out ""`、`-max-bytes <= 0` 或超过合理上限，仍必须在后续验证阶段明确拒绝。

### 定义 file、out 与 max-bytes 合同

### 定义 `file`、`out` 与 `max-bytes` 合同

命令行合同首先要回答：参数由谁使用、表示什么、缺省时从哪里取得。这里将三个标志限定为：

- `-file`：输入历史文件路径，适用于 `check`、`list` 与 `export`。它是显式输入来源；若用户未提供，再按配置优先级尝试环境变量 `IMHISTORY_FILE`，最后才使用教学默认路径。
- `-out`：导出结果文件路径，仅适用于 `export`。`check` 和 `list` 不应悄悄接受并忽略它；出现不适用的标志应视为调用错误。
- `-max-bytes`：允许读取的最大文件字节数，适用于所有需要读取历史文件的子命令。它限制资源消耗，而不是“建议值”：必须是正整数，且不得超过预设的合理安全上限。

位置参数用于表达子命令自身的对象，例如：

`imhistory check [选项]`  
`imhistory list [选项]`  
`imhistory export [选项] 导出格式`

其中 `导出格式` 是 `export` 的位置参数；`-file`、`-out`、`-max-bytes` 则是带名称的选项。不要把文件路径同时设计成位置参数和 `-file`，否则两个来源冲突时无法解释。

每个子命令都应创建独立的 `flag.NewFlagSet`，并使用 `flag.ContinueOnError`，使解析失败返回错误而非直接退出进程。注册顺序也必须固定：**先定义该子命令允许的全部标志，再调用 `Parse(args)`**。例如先注册 `file` 与 `max-bytes`，`export` 额外注册 `out`，然后才解析用户输入。

默认值只是在“未显式提供”时给出候选值，不代表输入已经有效。解析后仍需单独验证：路径不能为空，`-out` 不能是空字符串，`-max-bytes` 不能为零、负数、非数字或超过上限。这样，默认、环境配置与用户显式参数才能在进入文件操作前形成清晰且可审计的最终配置。

### 按优先级合并配置来源

### 按优先级合并配置来源

`check`、`list`、`export` 都需要知道历史文件在哪里。这个值可能来自三处：用户本次调用传入的 `-file`、环境变量 `IMHISTORY_FILE`，或教学提供的默认路径。应把它们写成固定、可追踪的优先级：

1. 显式命令行标志 `-file`
2. 环境变量 `IMHISTORY_FILE`
3. 教学默认路径，例如 `./im-history.json`

这里“显式”很重要：`flag.String("file", "", ...)` 返回空字符串，并不能区分“用户没有写 `-file`”和“用户写了 `-file ''`”。前者可继续回退到环境变量；后者是明确提供了空路径，应当报错。

可通过 `FlagSet.Visit` 记录用户实际出现过的标志：

```go
fileFlag := fs.String("file", "", "历史文件路径")
// 定义全部 flag 后再 fs.Parse(args)

fileSpecified := false
fs.Visit(func(f *flag.Flag) {
	if f.Name == "file" {
		fileSpecified = true
	}
})
```

随后集中合并，而不是让各子命令各自猜测来源：

```go
path := ""
source := ""

switch {
case fileSpecified:
	path, source = *fileFlag, "命令行 -file"
case os.Getenv("IMHISTORY_FILE") != "":
	path, source = os.Getenv("IMHISTORY_FILE"), "环境变量 IMHISTORY_FILE"
default:
	path, source = "./im-history.json", "教学默认路径"
}
```

合并后仍必须验证。默认值只是“缺省时采用什么”，不代表它天然可用；`-file ""`、只含空白的路径，以及无法访问的文件都应分别拒绝或在后续打开阶段报告。将 `source` 一并保留，错误信息便能说明“当前路径来自环境变量”还是“来自默认路径”，用户也知道应修改哪一层配置。

### 把默认值与参数验证分开

### 把默认值与参数验证分开

默认值只是在用户**没有提供某项输入**时补齐候选值；验证则判断最终候选值能否安全执行。两者不能混为一谈：`-file ""`、环境变量内容损坏、`-max-bytes 0` 都不应被默认值悄悄掩盖。

以导入文件和导出上限为例，可先按优先级取得原始值：

1. 显式 `-file` 优先；
2. 否则读取 `IMHISTORY_FILE`；
3. 两者都未提供时，才使用教学默认路径。

但得到路径后仍必须验证：

```go
if strings.TrimSpace(file) == "" {
    return fmt.Errorf("输入文件路径不能为空：请使用 -file 或设置 IMHISTORY_FILE")
}
```

这里要区分“未提供”和“明确提供空值”。前者可以回退到环境变量或默认路径；后者通常是用户请求了一个无效路径，应给出诊断，而不是静默改用别的文件。

`IMHISTORY_MAX_BYTES` 也应严格解析。若环境变量存在却不能转换为整数，例如 `IMHISTORY_MAX_BYTES=tenMB`，应返回错误：

```go
n, err := strconv.ParseInt(raw, 10, 64)
if err != nil {
    return fmt.Errorf("IMHISTORY_MAX_BYTES 必须是整数：%w", err)
}
```

随后统一验证来自 `-max-bytes`、环境变量或默认值的结果。设合理安全上限为 `1<<30` 字节，则必须满足：

$$0 < \text{maxBytes} \le 1\text{GiB}$$

非正数表示“没有可读空间”或可能绕过限制；过大值则会使工具承担不合理的内存、磁盘或处理风险。错误信息应说明原因和可接受范围，例如“`-max-bytes` 必须在 1 到 1073741824 之间”。

诊断负责告诉用户哪里错、如何修正；退出结果负责让脚本知道命令失败。`check`、`list`、`export` 在参数验证失败时都应返回非 `nil` 错误，由统一入口打印诊断并以非零状态退出。

> **要点** — 独立解析、显式优先级和严格验证共同构成可预测且可测试的命令行合同。

导入本地 IM 历史的关键不在于“能解析 JSON”，而在于把资源、格式、版本与领域规则串成可解释的拒绝链。

### 先定义导入成功的完整合同

### 先定义导入成功的完整合同

导入函数的“成功”必须是强合同：它返回给调用方的历史记录，已经是**完整读取、严格解析、版本可识别且业务规则全部成立**的数据；调用方无需再猜测文件是否截断、字段是否遗漏或消息是否重复。

可将成功条件按拒绝链定义：

1. **文件可读且资源可释放**：`os.Open` 成功后立刻 `defer Close`。读取时使用 `io.LimitReader(r, max+1)`，再 `ReadAll`；若实际字节数超过 `max`，立即拒绝，不能把超大文件当作正常输入。
2. **JSON 结构严格有效**：使用 `json.Decoder` 并调用 `DisallowUnknownFields()`，拒绝拼写错误字段和未声明扩展字段。首次 `Decode` 成功仅说明读到了一个合法 JSON 值；还必须第二次 `Decode`，且仅接受 `io.EOF`，以拒绝 `对象1 对象2` 这类尾随内容。
3. **版本明确可支持**：当前仅接受 `Version == 1`。未知未来版本必须拒绝，因为字段含义、时间语义或去重规则都可能已变；若要兼容旧版本，应单独定义迁移规则，而非模糊放行。
4. **领域数据可用**：每条消息的 `ConversationID`、`MessageID`、`SenderID`、`Body` 均非空；时间必须能按 RFC3339 解析；同一会话内不得出现重复的 `MessageID`。

因此，JSON 语法成功不等于业务合法。例如 `{"version":1,"messages":[]}` 可能语法正确，却未必满足历史记录的领域约束。导入器只处理本地文件，不执行网络认证，也不因此证明消息来源真实；它保证的是输入符合本地格式合同。

### 受限读取与文件关闭的固定顺序

### 受限读取与文件关闭的固定顺序

文件导入首先面对的不是 JSON，而是资源边界：文件可能打不开、异常巨大、读取中失败，或在任一路径上泄漏文件描述符。因此流程应固定为“打开成功即登记关闭；受限读取；读取后判定是否超限；再进入解析”。

```go
f, err := os.Open(path)
if err != nil {
	return nil, fmt.Errorf("打开导入文件: %w", err)
}
defer f.Close()

const maxImportSize = 16 << 20 // 16 MiB
data, err := io.ReadAll(io.LimitReader(f, maxImportSize+1))
if err != nil {
	return nil, fmt.Errorf("读取导入文件: %w", err)
}
if len(data) > maxImportSize {
	return nil, fmt.Errorf("导入文件超过大小上限 %d 字节", maxImportSize)
}
```

`defer f.Close()` 必须紧跟在 `os.Open` 成功之后。后续无论是读取失败、大小超限、JSON 语法错误还是业务校验失败，函数返回时都会关闭文件；不要把关闭动作推迟到“解析完成后”，因为中间每个新增的返回分支都可能形成泄漏。

限制读取时使用 `max+1` 而非 `max`。若只读取 `max` 字节，得到恰好 `max` 字节的数据时，无法区分“文件正好等于上限”与“文件还有未读取内容”。额外读取一个字节即可建立明确判定：

- `len(data) <= max`：文件完整落在允许范围内；
- `len(data) == max+1`：文件至少比上限大一个字节，应拒绝；
- 读取错误：不能假定已有的部分数据可用，应拒绝。

这里的上限保护的是本次导入进程的内存与处理预算，不是认证机制，也不说明文件内容可信。只有完成受限读取后，才应将字节交给 JSON 解码及后续版本、字段、时间和重复消息校验；任一环节失败，都不向调用方返回部分导入结果。

### 严格解析版本化 JSON 文档

### 严格解析版本化 JSON 文档

`json.Decoder` 能把字节流解析成 Go 值，但“解析成功”只说明 JSON 语法和字段类型基本匹配，不说明该文件是当前工具认可的历史文档。导入器应把格式边界收紧为：字段不能悄悄遗漏、文件不能夹带第二份内容、版本不能被误当成兼容。

首先使用解码器而非直接反序列化，并启用未知字段拒绝：

`dec := json.NewDecoder(r)`  
`dec.DisallowUnknownFields()`

这样，拼错的字段名、调用方误传的包装字段，以及未来版本新增但当前程序不理解的字段，都会立即失败。若不启用它，`"mesages"` 之类的拼写错误可能被静默忽略，最终得到“成功导入但消息为空”的错误结果。

完成第一次解码后，还必须再解码一次并确认结果为 `io.EOF`：

`if err := dec.Decode(&extra); err != io.EOF { ... }`

这一步拒绝合法 JSON 后附加的第二个 JSON 值、垃圾文本或被拼接的文件。例如 `{...}{...}` 的第一段可以成功解析，但整个文件并不是一份唯一、完整的导出文档。第二次读取若得到非 `io.EOF`，应报告“存在尾随内容”；若得到其他语法错误，则报告文件结尾不合法。

版本字段同样是协议契约，而非装饰信息。当前只接受：

`if doc.Version != 1 { return err }`

未知的未来版本必须拒绝：版本 `2` 可能改变时间格式、消息删除语义、字段含义或加密表示；把它按版本 `1` 猜测处理，会产生看似成功、实际失真的导入。若未来需要兼容旧版本，应明确实现“版本分派—旧格式转换—统一校验”的路径，而不是放宽为“任何版本都试着读”。这些检查仅验证本地文件格式，不提供网络认证或来源真实性保证。

### 从语法有效走向领域有效

### 从语法有效走向领域有效

`json.Decoder.Decode` 成功只说明输入能组成目标结构：括号、逗号、字段类型等 JSON 语法正确；它并不证明这是一份可被本地 IM 使用的历史记录。例如，下面的数据可以成功解析，却不应进入系统：

```json
{"version":1,"conversation_id":"","messages":[{"message_id":"m1","sender_id":"","body":"","sent_at":"not-a-time"}]}
```

因此，导入流程应把“解析成功”与“业务合法”分开。只有完成全部领域校验后，才向调用方返回结果；中途发现任一问题，都应返回带上下文的错误，而不是交付部分数据。

核心校验可集中在会话及其消息上：

- `ConversationID` 必须非空，作为会话归属与去重范围。
- 每条消息的 `MessageID`、`SenderID`、`Body` 必须非空；空字符串虽然符合 `string` 类型，却没有可用业务含义。
- 时间字段必须能按 RFC3339 解析，例如 `2025-03-08T10:30:00Z`；不能把任意字符串当作时间保存。
- 同一会话内的 `MessageID` 必须唯一。导入时用 `map[string]struct{}` 记录已见标识，发现重复立即拒绝，避免导出、搜索或后续合并出现歧义。

可将校验表达为：对每个会话建立空集合 $S$，依次处理消息 $m$；若 $m.\text{MessageID}\in S$，则该会话无效；否则加入 $S$。这限定的是“会话内重复”，不同会话是否允许相同消息标识，则应由数据模型另行明确。

版本同样属于领域规则：当前仅接受 `Version=1`。未知的未来版本必须拒绝，因为字段含义、时间语义或身份规则都可能已改变；若要兼容旧版本，应显式编写迁移规则，而非让解析器静默猜测。这里的合法性仅针对本地文件格式，不包含网络认证、账号真实性或发送者身份验证。

### 以失败样本验证导入边界

### 以失败样本验证导入边界

导入测试应证明：程序不是“尽量读入”，而是在每个边界给出稳定、可定位的拒绝结果。JSON 语法成功并不等于历史记录可被业务接受；只有资源读取、结构解析、版本判断和领域校验全部通过，调用方才得到导入结果。

可建立以下失败样本表：

- **空文件**：`ReadAll` 后长度为零，应报告“导入文件为空”，而非返回空历史。
- **超限文件**：构造大小恰为 `max+1` 的文件；`io.LimitReader(max+1)` 读完后必须拒绝，避免无界内存占用。
- **未知字段**：在合法对象中加入未声明字段；启用 `json.Decoder.DisallowUnknownFields()` 后应失败，防止拼写错误或未支持语义被静默忽略。
- **尾随数据**：在完整 JSON 后追加第二个对象、文本或额外数组；第一次 `Decode` 成功后，第二次解码必须确认 `io.EOF`，否则拒绝。
- **版本不符**：`Version != 1`，包括未来版本 `2`，均应拒绝。未来格式不能猜测解释；若需兼容旧版本，应另行定义迁移规则。
- **缺失关键字段**：分别覆盖空 `ConversationID`、`MessageID`、`SenderID`、`Body`，断言错误指出具体字段。
- **非法时间**：使用非 RFC3339 字符串、无效日期或错误时区格式，确保不会生成零值时间后继续导入。
- **会话内重复消息**：同一 `ConversationID` 下重复 `MessageID` 必须失败；不同会话是否允许相同消息标识，应按既定领域规则断言。

每个案例还应断言：发生任一失败时，调用方拿不到部分成功的数据。该导入器只验证本地文件内容，不发起网络请求，也不提供身份认证、签名校验或远端可信性保证。

> **要点** — 安全导入要求先限量读完，再严格解析，最后完成全部领域校验；任一步失败都不得返回部分可用数据。

本节将把已验证的本地消息数据转化为安全、可脚本化的命令行输出，并明确展示、导出与失败处理的边界。

### 先定义三类命令的结果合同

### 先定义三类命令的结果合同

命令行工具的“结果合同”应在实现前固定：成功时输出什么、失败时如何报告、哪些数据绝不默认暴露，以及调用方可依赖的退出码。三类命令可统一约定：`stdout` 只承载成功的机器可读结果，`stderr` 只承载诊断；成功退出码为 `0`，参数、读取、校验、编码或写入失败均为非零。诊断中不得拼入真实账号、联系人名称、消息正文或完整文件内容。

- `check <输入>`：读取并验证导入数据的结构、字段约束、时间范围与关联关系。成功时仅输出已验证摘要，如消息数、会话数、时间边界、警告数与格式版本；不输出正文、身份标识或原始记录。任一必需校验失败即返回非零，且不产生“部分已验证”的成功摘要。

- `list <输入>`：先完成与 `check` 等价的验证，再按输入文件中的显式记录次序列出条目。默认输出稳定字段，如记录 `ID`、时间、类型、会话内部标识及可选状态；正文应省略或使用 `--redact` 进一步脱敏。读取失败、验证失败、排序依据缺失或过滤条件非法均返回非零；不得为了展示少量可读记录而悄悄跳过坏记录。

- `export <输入> <目标>`：先验证，再构造导出数据并完成编码，最后才创建或写入目标文件。默认目标已存在即失败；只有显式指定 `--replace` 才允许覆盖。成功时在 `stdout` 输出导出摘要与目标范围，而非完整敏感内容。写入失败返回非零，并提示目标可能已有部分内容；若使用 `O_EXCL` 创建文件，还必须检查 `Close` 错误，因为缓冲落盘可能在关闭时失败。

### check：输出可解释的已验证摘要

### check：输出可解释的已验证摘要

`check` 的职责不是展示聊天内容，而是回答一个更基础的问题：**输入文件是否已被完整解析，并通过领域规则校验**。因此，只有严格解析、字段约束、时间顺序、消息标识等校验全部成功后，才向标准输出写入摘要；任一步失败都应返回非零状态，并仅向标准错误输出经脱敏后的诊断。

建议将成功结果设计为稳定的机器可读结构，例如：

`版本=1 消息数=248 时间范围=2024-01-03T08:12:04Z..2024-02-18T21:46:10Z 校验=通过`

其中：

- **版本**：表示已识别的数据格式版本，而非工具自身版本；未知版本应在解析阶段拒绝。
- **消息数**：表示实际通过校验并纳入历史集合的消息总数，不能只报告文件中粗略扫描到的记录数。
- **时间范围**：使用最早与最晚有效消息的规范化时间；空历史可明确输出`时间范围=空`，避免伪造零值时间。
- **校验状态**：应体现领域校验已经完成，如`通过`、`通过（含空历史）`；不要把“文件可打开”误报为“校验通过”。

摘要不得包含发送者真实身份、会话名称、消息正文、附件路径或原始记录片段。即使某些字段看似无害，多个字段组合也可能扩大可识别范围。若需要帮助用户定位问题，错误信息可说明失败类别与记录序号，例如“第 17 条记录时间格式无效”，但不回显该条正文、用户名或完整原始行。

标准输出只承载成功摘要，便于脚本消费；标准错误承载解析失败、校验失败及读取失败等诊断。这样，调用方可以安全地记录`stdout`中的验证范围，同时避免日志系统意外收集敏感历史。

### list：按文件次序列出安全字段

### list：按文件次序列出安全字段

`list` 的职责是把**已经通过导入与核对的数据**转换为稳定、可阅读、可脚本处理的索引；它不是全文搜索，也不应成为无意泄露聊天内容的通道。

输出顺序必须保持输入文件中的**显式消息顺序**，即按消息在文件数组或记录流中出现的先后列出，不能为了“方便”按时间戳、ID 或方向重新排序。时间字段可能相同、缺失或受设备时钟影响；文件次序才是本工具承诺的可复现顺序。每条记录可输出：

- `id`：消息唯一标识；
- `time`：已规范化的时间表示；
- `direction`：如“发送”“接收”；
- `type`：文本、图片、系统事件等；
- `status`：核对后的有效状态或摘要；
- 必要时的附件数量、正文长度等非敏感统计值。

默认输出应采用安全摘要，例如正文仅显示“文本，长度 18”，或显示固定截断后的脱敏片段。若需要进一步限制暴露，可使用 `--redact`，将正文完全替换为`[已脱敏]`，同时保留 ID、时间、方向等定位字段。即使用户显式请求展示，也应避免默认打印完整敏感正文；完整内容属于受控导出或专门查看流程，而非普通列表命令。

机器可读结果写入标准输出，例如每行一条稳定的 JSON 记录或制表字段；进度、警告和解析诊断写入标准错误。错误信息只说明记录序号、字段类别或校验原因，例如“第 12 条记录时间格式无效”，不得回显真实姓名、账号、正文或附件路径。命令还应记录本次输出的范围，如“按文件次序列出 37 条已验证消息，正文已脱敏”，使操作者知道哪些数据被展示、哪些内容被刻意省略。

### export：验证后写入与覆盖保护

### export：验证后写入与覆盖保护

`export` 的职责不是“尽快生成文件”，而是将**已验证、已编码**的数据安全地提交到目标路径。推荐顺序为：

1. 读取并解析本地历史；
2. 完整执行一致性、签名、字段约束等验证；
3. 按选定格式编码为内存中的字节序列；
4. 检查目标路径与覆盖策略；
5. 最后才创建或写入目标文件。

这样，验证失败、序列化失败或敏感字段过滤失败时，磁盘上不会留下看似成功的导出文件。导出前还应确定输出范围，例如时间区间、会话数量、消息数量、是否脱敏；这些摘要写入 `stderr`，而机器可读取的结果仅写入 `stdout`。

默认必须拒绝覆盖已有文件。只有用户显式传入 `--replace`，才允许替换目标：

- 未指定 `--replace`：使用排他创建，例如 `os.OpenFile(path, os.O_WRONLY|os.O_CREATE|os.O_EXCL, 0600)`；若文件已存在，应返回简洁错误。
- 指定 `--replace`：才可使用覆盖写入策略，并在诊断中说明目标已被替换。
- 不要仅凭“目标不存在”的预检查决定安全性；检查与创建之间存在竞态，应依赖 `O_EXCL` 的原子语义。

即使使用 `os.WriteFile`，写入失败也可能已写入部分内容。因此失败信息应明确说明“目标文件可能包含不完整数据”，建议用户删除后重试；不要把真实联系人、消息正文或完整路径中的身份信息拼入错误文本。

使用 `OpenFile` 时，`Close` 同样是写入流程的一部分：缓冲刷新、文件系统提交可能在关闭时失败。应先报告写入错误，再调用 `Close`；若写入成功但关闭失败，则导出仍应判定失败，并提示文件可信性无法保证。对于更强的完整性要求，可写入同目录临时文件、成功关闭后再原子重命名，避免将半成品直接暴露为最终导出结果。

### 分离标准输出、诊断与测试证据

### 分离标准输出、诊断与测试证据

命令行工具应把三类结果严格分开：`stdout` 供脚本消费，`stderr` 供人类诊断，退出码供自动化流程判断。混用会使管道、重定向和测试都变得不可靠。

| 通道 | 应输出的内容 | 不应输出的内容 |
|---|---|---|
| `stdout` | `check` 的已验证摘要；`list` 的文件顺序、消息 ID、时间、类型等字段；`export` 成功后的目标路径或机器可读结果 | 进度条、警告、调试日志、完整敏感正文 |
| `stderr` | 参数错误、校验失败原因、无法写入、覆盖被拒绝等诊断 | 真实联系人身份、消息正文、密钥、完整原始记录 |
| 退出码 | `0` 成功；非 `0` 表示用法、验证或 I/O 失败 | 依赖解析字符串来判断状态 |

例如，`list --format json` 的 `stdout` 应保持纯 JSON；即使发现某条记录被脱敏，也应将提示写入 `stderr`。错误信息可写“第 17 条记录校验失败”，而非回显该记录的发送者和正文。

测试应同时验证输出范围与失败边界：

- 捕获 `stdout`，断言成功结果字段稳定、顺序与输入文件一致。
- 捕获 `stderr`，断言诊断存在，但不含联系人名称、正文片段或原始字节。
- 断言退出码：成功为 `0`，验证失败、目标已存在、编码失败分别为非零。
- 对导出使用临时目录：默认目标已存在时不得改写；只有显式 `--replace` 才允许覆盖。
- 模拟 `os.WriteFile` 或底层写入失败，确认命令返回错误，并在文档与测试中承认目标可能留下部分内容。
- 若采用 `OpenFile(..., O_EXCL, ...)` 防止竞态覆盖，除检查写入错误外还必须检查 `Close` 错误；关闭失败同样可能意味着数据未完整落盘。

这样，脚本只依赖稳定的机器结果，用户只在诊断通道获得必要信息，测试则把“没有泄漏”和“失败不会伪装成成功”作为可验证证据。

> **要点** — 命令行工具的可信性来自先验证、少暴露、慎写入，以及可预测的输出、诊断和退出合同。

本节为命令行工具建立可预测的失败合同：让用户、脚本与测试都能依据退出码、诊断信息和错误身份稳定协作。

### 先定义命令的失败合同

### 先定义命令的失败合同

命令行工具首先不是“能跑”，而是要让人和脚本都能预测其结果。可将用户任务划分为四类，并为每类固定退出码、输出位置与诊断粒度：

| 情形 | 退出码 | 标准输出 | 标准错误 |
|---|---:|---|---|
| 成功导入、核对或导出 | `0` | 结果数据、摘要或指定导出内容 | 可选的简短进度日志 |
| 子命令、参数或组合错误 | `2` | 无 | 用法提示与具体参数问题 |
| 输入历史损坏或版本不支持 | `3` | 无 | 指出输入文件、损坏位置或不支持的版本 |
| 文件读取、写入、权限、路径等 I/O 故障 | `4` | 无 | 指出操作与路径，保留底层原因 |

例如，`imtool export --format csv history.db` 成功时，CSV 写入标准输出或目标文件；`--format` 缺少值时返回 `2`；数据库结构无法识别时返回 `3`；目标目录无写权限时返回 `4`。这样脚本可以只依据状态码分支，而用户仍能从标准错误获得可行动的解释。

帮助信息也应有明确合同：显式执行 `help`、`--help` 或 `-h` 是正常查询，返回 `0`；完全没有子命令则属于用法不完整，应输出总览帮助并返回 `2`。不要把“展示帮助”一律视为失败，也不要让缺少必要操作悄悄成功。

诊断中可以记录操作名和路径，例如“无法读取历史文件：`/data/chat.db`”，但不要写入消息正文、附件内容、令牌、密码或用户凭据。若需要结构化日志，可在标准错误侧使用 `slog` 记录阶段、路径和错误类别；它是实现位置，而非本节合同的强制依赖。

### 建立稳定的教学退出码映射

### 建立稳定的教学退出码映射

退出码是命令行工具对脚本、测试和运维环境公开的接口，不应随内部实现细节漂移。可为本工具约定一组小而稳定的教学映射：

| 退出码 | 含义 | 典型场景 |
|---:|---|---|
| `0` | 成功 | 导入、核对或导出完成，结果已写入目标位置 |
| `2` | 使用方法或参数错误 | 缺少子命令、未知参数、参数值非法、输入路径未提供 |
| `3` | 输入历史损坏或版本不支持 | 历史文件格式不完整、记录无法解析、校验失败、文件版本过新或过旧 |
| `4` | 文件 I/O 失败 | 文件不存在、权限不足、目录不可写、磁盘错误、读取或写入中断 |

边界应按“用户需要采取什么动作”划分，而不是按底层函数名称划分。用户传错命令或参数，应修正调用方式，返回 `2`；输入文件本身无法被本版本程序理解或已损坏，应更换、修复或升级工具，返回 `3`；路径可理解但操作系统拒绝访问或读写失败，则返回 `4`。

例如，`--format json` 拼写错误属于 `2`；JSON 语法损坏、缺少必要字段属于 `3`；指定文件不存在通常属于 `4`，因为这是读取目标失败，而非参数语法错误。若“文件必须存在”是某个参数的明确语义，也应在文档中固定这一判定，避免不同子命令各自解释。

帮助信息也应有明确结果：显式请求 `--help` 或 `help` 后成功展示，返回 `0`；不带子命令直接运行则属于错误用法，输出简短提示和帮助入口，返回 `2`。应在 `--help`、使用文档和测试中同步列出这些退出码；一旦发布，脚本可能依赖它们，修改映射应视为兼容性变更。

### 以错误身份驱动分类

### 以错误身份驱动分类

命令行工具不应依据 `err.Error()` 的文本分类错误。错误文本面向人类，可能因补充上下文、翻译或底层库升级而变化；脚本、测试和退出码映射应依赖稳定的“错误身份”。

先为可预期的业务失败定义哨兵错误：

```go
var (
    ErrHistoryCorrupt      = errors.New("历史记录损坏")
    ErrUnsupportedVersion  = errors.New("不支持的历史版本")
)
```

读取器发现格式不合法时，应保留底层原因并包装身份：

```go
return fmt.Errorf("%w：第 %d 行字段缺失", ErrHistoryCorrupt, line)
```

调用方随后用 `errors.Is` 判断原因链，而不是比较字符串：

```go
switch {
case errors.Is(err, ErrUnsupportedVersion):
    return 3
case errors.Is(err, ErrHistoryCorrupt):
    return 3
}
```

当错误需要携带结构化信息时，使用类型错误。例如文件操作失败既要保留 `os.PathError`，又要让诊断输出具体路径：

```go
if err != nil {
    return fmt.Errorf("读取输入文件 %q: %w", path, err)
}
```

上层可用 `errors.As` 提取类型身份：

```go
var pathErr *os.PathError
if errors.As(err, &pathErr) {
    return 4
}
```

包装必须使用 `%w`；若写成 `%v`，原因链会断裂，`errors.Is` 和 `errors.As` 都无法匹配。通常可按“参数错误—历史内容错误—文件 I/O 错误—未知内部错误”依次分类，并为每类映射固定退出码。这样既能向用户显示带路径、行号的上下文，也能让自动化调用稳定识别失败类别。

### 安排main、run与资源清理边界

### 安排 `main`、`run` 与资源清理边界

`os.Exit(n)` 会立刻终止进程：它不会执行当前函数或调用栈中尚未运行的 `defer`。因此，不应在承担文件打开、导入解析、导出写入等工作的函数内部直接调用它；否则缓冲区可能未刷新，临时文件未清理，打开的文件也失去正常关闭机会。

推荐把边界划分为两层：

- `main`：只负责取得最终状态并退出；
- `run`：负责参数解析、业务调度、资源获取与释放、错误分类及诊断收尾。

```go
func main() {
	os.Exit(run(os.Args[1:]))
}

func run(args []string) int {
	out, err := os.Create("history.json")
	if err != nil {
		fmt.Fprintln(os.Stderr, "无法创建导出文件:", err)
		return 4
	}
	defer out.Close()

	// 解析、核对、导出……
	return 0
}
```

这里 `run` 返回时，`defer out.Close()` 会先执行；随后控制回到 `main`，再由 `os.Exit` 把状态交给 shell。即使需要记录“导出结束”或关闭日志、清理临时目录，也应放在 `run` 的延迟调用或正常返回路径中。

更稳妥的写法是让 `run` 返回状态码，并可在内部把领域错误映射为稳定的教学退出码：参数错误返回 `2`，输入历史损坏或版本不支持返回 `3`，文件读写失败返回 `4`。`main` 不解释错误、不重复输出诊断，从而避免多个出口产生不一致的行为。

日志可在 `run` 中写入标准错误输出，例如记录操作名、文件路径和错误类别；不要记录聊天消息正文、令牌、密码或其他用户凭据。若使用 `slog`，它适合放在这一层承担结构化诊断，但并非实现该边界的前提。

### 规范帮助、诊断与敏感信息

### 规范帮助、诊断与敏感信息

命令行界面应把“用户想了解如何使用”和“用户没有提供可执行操作”明确区分。建议约定：

- `imtool --help`、`imtool import --help`：在 `stdout` 输出帮助文本，返回状态码 `0`。
- `imtool`：在 `stderr` 提示“缺少子命令”及简短用法，返回状态码 `2`。
- `imtool unknown`：在 `stderr` 报告未知子命令并给出用法提示，返回状态码 `2`。
- 参数格式错误、互斥参数同时出现、必填参数缺失：均输出诊断到 `stderr`，返回状态码 `2`。

这样，交互用户能看到可行动的提示，脚本也能将帮助内容与失败诊断分别重定向：

```text
imtool export --output out.json >result.txt 2>diagnostic.txt
```

正常导出产生的机器可读结果应写入 `stdout`，例如导出文件路径、记录数或 JSON 摘要；错误说明、警告和进度信息写入 `stderr`。不要把“成功结果”和“失败诊断”混在同一流中，否则管道、测试和自动化任务难以稳定解析。

诊断信息应说明操作、对象和下一步，而非暴露内部实现。例如：

```text
错误：无法读取历史文件 /data/chat.db：权限不足
提示：请检查文件是否存在且当前用户具有读取权限
```

日志可记录操作名、输入路径、输出路径、记录数量、耗时和错误类别；若使用 `slog`，应在应用入口配置其输出位置与级别，但不必强制所有代码依赖它。日志和诊断都不得记录消息正文、附件内容、访问令牌、密码、会话凭据或完整认证头。路径本身通常可记录，但在多用户环境中也应评估其是否包含用户名、客户名等敏感信息，必要时脱敏或改用逻辑标识符。

> **要点** — 可靠CLI的关键是稳定分类错误、固定退出码、分离输出通道，并在退出前完成资源清理与敏感信息控制。

本节把需求表转化为可复核的测试证据，覆盖领域规则、文件边界、命令契约与兼容性承诺。

### 从需求表建立测试证据矩阵

### 从需求表建立测试证据矩阵

测试不应从“给哪个函数补用例”开始，而应从需求表中的用户可见规则开始。为每条规则建立一行证据矩阵，至少记录：测试层级、前置状态、输入、预期结果、可观察证据与对应源代码版本。

| 规则 | 测试层级 | 输入条件 | 预期结果 | 证据 |
|---|---|---|---|---|
| 导入数据满足领域约束 | 纯领域测试 | 合法消息、固定时间 | 生成一致的领域状态 | 返回值、聚合内容 |
| 版本为 `max+1` | 文件/应用测试 | 当前最大版本加一 | 成功导入 | 导入后版本号 |
| 版本跳跃 | 文件/应用测试 | `max+2` | 拒绝且状态不变 | 错误、导出前后字节一致 |
| 重复 ID | 领域与集成测试 | 已存在消息 ID | 拒绝且不部分写入 | 错误、计数不变 |
| 未知字段、第二个 JSON 值 | 文件解析测试 | 宽松 JSON 或尾随值 | 严格拒绝 | 解析错误、无输出文件 |
| 源文件不存在 | CLI 测试 | 不存在路径 | `stderr` 有诊断，非零退出码 | 标准错误、退出码 |
| 导出目标已存在 | CLI 测试 | 已有目标文件 | 默认拒绝 | 原文件内容未变 |
| 显式 `--replace` | CLI 测试 | 已有目标文件 | 覆盖成功，并提示风险语义 | 新文件内容、退出码 |

使用 `t.TempDir()` 隔离文件系统，用固定时钟避免时间戳漂移；测试应构造输入、调用边界并断言结果，但不实际运行外部命令或依赖真实用户目录。CLI 证据必须同时检查 `stdout`、`stderr` 与退出码：成功信息不能混入错误流，失败不能伪装为零退出。

覆盖率只说明代码是否被执行，不说明每项需求是否被证明。矩阵还应单独标注“测试证据版本”和“源代码版本”，防止代码更新后沿用过期结论。文件格式升级到 v2 时，补充“v2 能读取旧格式”的兼容样本；变更 CLI flag 时，明确旧 flag 的弃用、错误提示及退出码是否保持稳定。

### 纯领域校验与状态不变性

### 纯领域校验与状态不变性

先把不依赖文件、命令行参数和时钟的规则收敛为领域测试：给定一份初始消息集合，调用导入或追加入口后，只断言返回结果与内存状态。这样失败原因不会被 JSON 解析、路径权限或输出格式掩盖。

重点不是“返回了错误”，而是证明失败具备原子性：校验失败后，集合长度、消息顺序、各消息字段、索引和版本号均保持调用前状态。可先对状态做深拷贝，失败后比较完整快照；不要只检查长度，因为“先插入、后报错”仍可能留下被污染的数据。

建议覆盖以下表驱动用例：

- **重复消息 ID**：已有 `id=m1`，再次导入 `m1`；期望返回重复标识错误，原消息内容不被新输入覆盖，消息数不变。
- **批量中的后续重复**：输入前半条合法、后半条与已有 ID 冲突；期望整批拒绝，前半条也不得被提前写入。这是最容易遗漏的部分修改场景。
- **非法字段**：空 ID、空会话 ID、非法角色、空正文或超出领域允许范围的字段值；错误应指向领域约束，而非产生半合法对象。
- **时间边界**：固定基准时刻 `T`，分别测试恰好等于边界、边界前后一个最小单位，以及零值时间。明确规则是允许还是拒绝，避免测试依赖真实 `time.Now()`。
- **顺序与唯一性**：若时间相同，验证既定排序规则；若领域规定 ID 全局唯一，则不同会话中的同 ID 也必须拒绝。

测试中使用固定时间，如 `2025-01-02T03:04:05Z`，避免时区、精度和运行时钟造成偶发失败。领域测试不应启动 CLI，也不应创建临时文件；它提供的是“规则与状态转换”的证据。即使覆盖率显示相关分支已执行，也不能替代对“失败后状态完全不变”这一需求的明确断言。

### 版本化文件导入的边界案例

### 版本化文件导入的边界案例

版本化导入测试的目标不是“能读回一个文件”，而是把文件格式视为长期契约：旧数据可继续读取，超出当前承诺的输入必须被明确拒绝，且失败不得污染内存状态。

- **Version1 往返**：用固定时间构造含多条消息的领域对象，导出为 Version1 文件，再导入到空仓库。断言消息数量、ID、发送者、正文、时间戳及顺序均一致；不要只比较“导入成功”。固定时间避免序列化精度、时区或当前时间导致测试漂移。

- **未来 v2 对旧格式兼容**：当实现升级到 `version: 2` 时，应保留读取 Version1 文件的测试夹具。测试应证明：旧文件仍被识别、缺失的新字段采用定义好的默认值、领域校验仍照常执行。兼容的是既有格式语义，不是无条件接受任意残缺 JSON。

- **最大条数加一拒绝**：若上限为 $N$，构造恰好 $N+1$ 条合法消息的文件。导入应返回“超出容量”错误，并断言导入前后的仓库快照相同。该断言防止实现边读边写，失败时留下前 $N$ 条半成品。

- **严格解析合同**：未知字段应按契约决定：若格式要求严格，应拒绝如 `{"version":1,"messages":[],"debug":true}`；若允许扩展，也必须明确测试其忽略规则。文件末尾再附加第二个 JSON 值，如 `{} {}`，必须拒绝，避免解析器只读取第一个值后静默忽略垃圾内容。

- **版本号边界**：缺失版本、非整数版本、未知未来版本都应失败；错误信息可说明“不支持的版本”，但测试不宜绑定完整措辞。尤其不能把未知版本当作 Version1 猜测解析，否则未来格式变更会被错误解释。

这些测试应在 `t.TempDir()` 中创建独立文件，并把“需求覆盖证据”和“当前源代码版本”分别记录：覆盖率数字只能说明执行过哪些代码，不能证明上述格式承诺都已被验证。

### 导出覆盖策略与资源隔离

### 导出覆盖策略与资源隔离

导出测试不应只验证“文件写出来了”，还要证明不会意外覆盖用户已有数据。集成测试以 `t.TempDir()` 创建独立目录，所有源文件、目标文件和导出结果均置于其中；测试结束后目录自动清理，避免污染工作区或依赖机器上的真实历史文件。

可将覆盖策略拆为三个案例：

1. **目标不存在：成功创建**  
   给定固定时间、固定消息与临时输出路径，执行导出后断言：退出码为 `0`，`stderr` 为空或仅含约定提示，目标文件存在且可被导入器读取。不要仅比较原始字节；更稳妥的是反序列化后比较版本、会话、消息 ID、时间戳与正文。

2. **目标已存在：默认拒绝**  
   预先写入标记内容，如 `KEEP-ME`，再执行未带 `--replace` 的导出。断言命令返回非零退出码，错误写入 `stderr`，原文件字节完全不变。这里的核心证据是“拒绝发生在打开截断或写入之前”，而非仅检查最终导出失败。

3. **显式 `--replace`：允许替换但提示风险**  
   对已有目标传入 `--replace`，断言导出成功且旧标记被替换；同时核对约定的风险提示、退出码和输出流。该选项应是明确授权，不能因同名文件、空文件或路径归一化而被隐式开启。

测试中必须关闭自行打开的文件与读取器；否则 Windows 等平台可能因句柄未释放而掩盖覆盖行为。固定时钟可避免导出元数据、排序或文件名中的当前时间导致非确定性。

覆盖率报告只能说明哪些代码行被执行，不能证明“默认不覆盖”这一需求已被验证。测试证据应记录需求编号、案例、断言、结果及对应源代码版本；敏感正文则使用最小化假数据，断言结构和完整性即可，避免把真实聊天内容写入夹具、失败日志或持续集成产物。

### 命令可观察行为与稳定承诺

### 命令可观察行为与稳定承诺

命令行工具的契约不止是“功能是否成功”，而是调用者可观察到的三元组：

- `stdout`：成功结果，供脚本、管道或用户消费；
- `stderr`：诊断信息、警告与失败原因；
- 退出码：供自动化流程判断成功、参数错误、业务拒绝或系统故障。

测试应分别断言三者，避免只检查错误对象。例如，导出成功时应在 `stdout` 输出目标路径或摘要，`stderr` 为空，退出码为 `0`；目标文件已存在且未指定替换时，应保持原文件不变，在 `stderr` 给出明确拒绝原因，并返回约定的非零码。不能仅因提示文字存在就认为行为正确。

| 场景 | stdout | stderr | 退出码 |
|---|---|---|---|
| 导入、核对、导出成功 | 结果摘要 | 空 | `0` |
| `max+1`、重复 ID、格式不合法 | 空 | 可定位的业务诊断 | 稳定的业务失败码 |
| 文件不存在、无法写入 | 空 | 路径与系统原因 | 稳定的输入/IO 失败码 |
| `--replace` 覆盖已有文件 | 覆盖结果 | 可选风险提示 | `0` |

`--replace` 不是普通便利开关：它改变了“默认不破坏已有数据”的安全承诺。测试既要验证未显式指定时拒绝，也要验证显式指定后确实覆盖，并在文档和诊断中暴露风险。

Flag 名称、默认值和退出码都属于外部接口。重命名 Flag、把失败码改成 `0`、或将原有业务失败合并为另一类码，都会破坏脚本兼容性；若必须变更，应保留旧 Flag 的兼容期或提供迁移说明。文件格式演进到 v2 时，同样应保留旧格式读取测试。

覆盖率只能说明代码被执行过，不能证明需求表中的每项承诺均被断言。测试证据应记录对应需求、输入、预期三元组及执行结果，并与源码版本分离保存：测试报告证明“某次构建满足了什么”，提交哈希则说明“它对应哪份实现”。

> **要点** — 测试应证明需求合同而非仅提高覆盖率：验证状态、文件、诊断、退出码与版本兼容边界。

本节以虚构本地 IM 历史为对象，规划一个可验证、可解释且严格限定于本地文件处理范围的 Go 命令行工具。

### 从任务表到命令合同

### 从任务表到命令合同

工具只处理指定目录中的本地历史文件，不连接服务端、不调用 OpenIM 接口；源码阅读仅用于理解本地数据字段，不据此推断线上行为。

| 子命令 | 用户任务 | 输入与参数 | 标准输出 | 失败与退出码 | 验收 |
|---|---|---|---|---|---|
| `check` | 核对历史是否可安全导入 | `--input` 必填，`--strict` 可选 | 汇总记录数、时间范围、重复 ID 数 | 文件不存在、JSON 非法、版本或业务规则不符：`2` | 严格 JSON、版本、时间、必填字段、重复 ID 均有明确结论 |
| `list` | 浏览已核对的记录 | `--input`，`--limit`，位置参数可覆盖同名 Flag | 一行一条脱敏摘要 | 参数非法或输入不合格：`2` | `limit+1` 判定“还有更多”，正文不泄露敏感内容 |
| `export` | 导出可交换的本地副本 | `--input`、`--output`、`--force` | 导出条数与目标路径 | 目标已存在且未 `--force`：`3`；写入失败：`1` | 输出为严格 JSON；临时文件写完再替换，避免半成品 |

参数优先级固定为：显式位置参数 > 显式 Flag > 默认值；冲突时输出诊断到 `stderr`。业务结果写 `stdout`，错误、警告与 `slog` 诊断写 `stderr`。`main` 只负责解析与映射退出码：避免在含 `defer` 的深层函数直接 `os.Exit`，否则清理、关闭文件及临时文件删除不会执行。

示例合同：

`imhistory check --input ./history.json --strict`  
`imhistory list --input ./history.json --limit 20`  
`imhistory export --input ./history.json --output ./safe.json --force`

阶段顺序为：先 `check` 固化输入质量，再 `list` 验证可读摘要，再 `export` 生成副本，最后设计失败变式并记录个人环境、命令、退出码与脱敏后的输出。测试使用 `t.TempDir` 隔离文件覆盖场景，并固定时钟或注入时间来源，避免时间导致结果漂移。

<details><summary>练习：为什么 list 读取 limit+1 条？</summary>

多读一条仅用于判断是否存在下一页；输出仍最多 `limit` 条，避免“恰好等于 limit 时是否还有数据”的歧义。

</details>

<details><summary>练习：重复 ID 应在何时失败？</summary>

`check --strict` 应失败；非严格模式可报告数量并保留诊断，但 `export` 是否允许必须由合同明确，推荐拒绝导出。

</details>

### 文件树与单向调用流程

### 文件树与单向调用流程

建议先固定依赖方向：命令层只解析输入与呈现结果，领域层只表达规则，文件适配器只读写本地 JSON；测试从外部验证行为，不反向侵入生产代码。

```text
imhistory/
├── cmd/imhistory/main.go          # 进程入口、退出码
├── internal/cli/run.go            # FlagSet、参数优先级、stdout/stderr
├── internal/domain/
│   ├── message.go                 # Message、会话、导出模型
│   ├── service.go                 # Check/List/Export 用例
│   └── validate.go                # 版本、时间、重复 ID、业务规则
├── internal/storage/jsonfile/
│   └── repository.go              # 严格 JSON 解码、本地文件读写
└── internal/..._test.go           # t.TempDir、夹具、行为断言
```

主链路应保持单向：

`main` → `cli.Run` → `domain.Service` → `jsonfile.Repository` → `历史 JSON 文件`

其中，`main` 仅负责调用 `Run` 并将返回的退出码传给 `os.Exit`。注意：`os.Exit` 不执行延迟调用，因此日志刷新、文件关闭等清理应在 `Run` 或适配器内部完成，不能依赖 `main` 的 `defer`。

代表性入口可静态约定为：

`imhistory check --input history.json`  
`imhistory list --input history.json --limit 20`  
`imhistory export --input history.json --output result.json`

参数优先级宜明确为：命令行 Flag > 环境默认值 > 程序内默认值；位置参数若存在，必须规定其是否覆盖 Flag，避免歧义。`check` 先验证 JSON 语法、文件版本、必填字段、时间合法性与重复消息 ID；`list` 在核对通过后读取并展示，采用 `limit+1` 判断是否还有下一页；`export` 仅导出已通过业务校验的数据。

验收时不运行程序也可检查：领域包不导入 `os`、`flag` 或 `encoding/json`；JSON 适配器不决定退出码；CLI 不直接遍历消息业务字段；标准输出承载正常结果，标准错误承载诊断信息。官方资料可查阅 `flag`、`os`、`encoding/json`、`testing` 与 `log/slog` 包文档。

### 代表函数与参数解析

### 代表函数与参数解析

工具只处理本地历史文件，参数优先级固定为：命令行显式参数 > 环境变量 > 配置文件 > 默认值。`FlagSet` 不使用全局 `flag.CommandLine`，便于测试并将解析错误写入 `stderr`。

代表性函数应完成“打开—限量读取—严格解码—关闭”：

`func 读取记录(path string, limit int) ([]Record, error) { f, err := os.Open(path); if err != nil { return nil, err }; defer f.Close(); dec := json.NewDecoder(f); dec.DisallowUnknownFields(); var all []Record; if err := dec.Decode(&all); err != nil { return nil, err }; if err := dec.Decode(&struct{}{}); err != io.EOF { return nil, fmt.Errorf("JSON 尾部存在额外内容") }; if limit > 0 && len(all) > limit { return all[:limit], nil }; return all, nil }`

列表命令若需判断“还有更多”，读取上限应为 `limit+1`：保留前 `limit` 条，并以第 `limit+1` 条设置 `more=true`；不能只读 `limit` 条后猜测。`defer f.Close()` 仅在函数正常返回时可靠，因此最外层 `main` 不应在资源尚待关闭的路径中直接 `os.Exit`；应由 `run(args) int` 返回退出码，再由 `main` 最后调用 `os.Exit`。

官方资料：[`flag`](https://pkg.go.dev/flag)、[`os`](https://pkg.go.dev/os)、[`encoding/json`](https://pkg.go.dev/encoding/json)、[`testing`](https://pkg.go.dev/testing)、[`log/slog`](https://pkg.go.dev/log/slog)。

### 结果通道与失败变式

### 结果通道与失败变式

命令行工具的“结果”不只是一段文本，而是由 `stdout`、`stderr`、退出码和文件副作用共同构成的契约。建议将可被脚本消费的业务结果写入标准输出，将人类诊断、警告和失败原因写入标准错误：

| 情形 | stdout | stderr | 退出码 |
|---|---|---|---|
| `check` 成功 | 严格 JSON 核对结果 | 空 | `0` |
| `list` 成功 | 条目或 JSON 列表 | 可选警告 | `0` |
| 参数错误 | 空 | 缺少文件、非法 Flag 等 | `2` |
| 业务校验失败 | 空或部分诊断 JSON（须预先约定） | 版本不支持、重复 ID 等 | `1` |
| 导出目标已存在且未允许覆盖 | 空 | 明确指出目标路径 | `1` |

严格 JSON 时，`stdout` 只能出现 JSON；日志不能混入其中。可将 `slog` 配置为输出到 `os.Stderr`，避免一条调试日志破坏下游解析。

```go
func writeExport(path string, data []byte, overwrite bool) error {
	if _, err := os.Stat(path); err == nil && !overwrite {
		return fmt.Errorf("导出文件已存在：%s；如确认覆盖，请指定 --overwrite", path)
	}
	return os.WriteFile(path, data, 0o600)
}
```

覆盖写入不是默认行为：它可能毁掉此前导出结果。验收时应分别确认“默认拒绝覆盖”和“`--overwrite` 后成功替换”，并检查导出权限与内容。

失败变式应在进入导出前集中拦截：

- **版本失败**：文件 `version` 不在支持集合中，提示当前版本与支持范围。
- **时间失败**：时间戳无法解析、结束时间早于开始时间，或超出查询区间。
- **重复 ID**：同一消息 ID 出现多次；不能静默“以后者覆盖前者”，应报告冲突位置。
- **限制失败**：列表使用 `limit+1` 判断是否还有下一页；返回超过 `limit` 条仅用于计算 `has_more`，最终输出仍截断到 `limit`。
- **严格解码失败**：未知字段、尾随 JSON、字段类型错误均应拒绝，而非猜测修复。

尤其要避免在带有资源清理的深层函数中调用 `os.Exit`：

```go
defer file.Close()
if err != nil {
	os.Exit(1) // defer 不会执行
}
```

`os.Exit` 会直接终止进程，所有延迟调用都不会运行。更稳妥的结构是让 `run` 返回错误，由最外层 `main` 统一写诊断并决定退出码；这样临时文件、打开句柄和测试中的 `t.TempDir()` 资源都能正常清理。个人运行记录只保留命令、退出码、摘要和脱敏路径，不记录真实消息正文、用户标识或令牌。

### 分阶段实现与验证记录

### 分阶段实现与验证记录

按固定顺序记录静态验收，不运行、不发布，也不连接 OpenIM 服务；工具只读写本地导出的历史文件。

1. **`check`**：解析 `--input`，严格解码 JSON，检查版本、必填字段、时间格式与重复消息 ID；验收为错误写入 `stderr` 且返回非零退出码。
2. **`list`**：在通过核对后按时间列出会话或消息摘要；验收为 `stdout` 只含机器可读结果，`--limit` 使用 `limit+1` 判断是否还有下一页。
3. **`export`**：按筛选条件写出新文件；验收为默认拒绝覆盖，显式 `--force` 才允许替换，并对输出 JSON 再次严格校验。
4. **失败变式**：分别构造空文件、未知字段、版本不符、业务字段矛盾、重复 ID、非法时间、不可写输出路径。
5. **个人记录**：写明命令、输入文件摘要、预期退出码、实际观察、脱敏后的错误文本，以及未覆盖的边界。

代表性测试应以 `t.TempDir()` 创建隔离目录：输入、输出和损坏样本均在临时目录内；记录中不得保留真实用户 ID、消息正文、令牌或绝对路径。
