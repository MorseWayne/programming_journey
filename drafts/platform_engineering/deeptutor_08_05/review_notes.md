## 教学重组

- 基础层区分分片键、逻辑桶、物理节点和副本，再比较用户、会话与消息 ID 作键对历史/权限/序号的影响。
- 固定玩具哈希 5/6/9 与 4 桶，手算 `c-a=b1,c-b=b2,c-g=b1`；epoch7 b1→N1，epoch8 b1→N3。移动 b1 同时搬 `c-a/c-g`，不能自动拆开 `c-g` 单热流。
- 用 M0–M6 把单写者、快照 `S0`、可续读变更 `L0`、围栏旧写、路由版本、旧客户端重试、增量对账和回退写成连续故事。
- 数据库桶迁移和 Kafka P0 在消费者组 W1→W2 的再平衡分别评审；E9/E10 的业务 seq、DB 位置与 broker offset 不互换。

## 技术修订

- 原稿多次重复 epoch/围栏说明，末段又切换成 epoch41/42。正式页统一 epoch7/8 与 M0–M6，避免同一练习里路由版本漂移。
- 原稿把“只记 `H=seq9`，捕获 `seq>9`”写得像足以覆盖整个 b1；正式页指出 b1 还含 `c-g`，必须配对一致快照与该范围增量 `L0`，不能把一个会话 seq 当全局游标。
- 原稿迁移时较少讨论复制后的 outbox 双 relay；正式页增加旧新发布所有权交接、ACK 丢失重复与消费者版本幂等。消息行追平本身不代表事件意图或发布状态齐全。
- 原稿表述“围栏和幂等保证 E9/E10 不乱序”过强；正式页将**数据所有权**与**生产侧事件顺序闸门**分开，明说同键 broker 分区仅排序实际接收到的记录。
- Kafka 增分区对旧数据的影响按官方文档限定：旧记录不自动重新分区，新记录若按 `hash(key)%n` 可能换分区。Redis Cluster 16,384 槽不是一致性哈希环。
- 固定 OpenIM `send.go` 与 `MsgToMQ` 仅证明群聊路径会话相关 key 传到 `producer.SendMessage`；生产者分区算法、topic 分区数、存储拓扑与迁移协议均未由两处证明。
