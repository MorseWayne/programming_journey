# 单章课程生产与项目同步流程

本流程适用于本项目的 Go 系统课程及其 DeepTutor Books 章稿。每次新写或刷新章节，先阅读本文件和当前学习路线，再开始生成。

## 完成的定义

一章依次经过：**选题与先修确认 → 教学设计 → DeepTutor 生成 → 技术与教学审阅 → 同步到本项目 → 静态接入检查 → 更新交付记录**。

“生成完成”表示取得了原稿。“本章交付完成”要求审阅正文已写入 src、导航可达、来源可追溯、检查通过。DeepTutor 页面链接或 drafts 中的一份文件，只能证明前面的相应步骤完成。

## 1. 按学习路线确定单章边界

- 对照[学习路线](../../src/docs/platform_engineering/curriculum/learning_path.md)，记录章号、阶段、前置与下一步。
- 区分已经学过、需要本章解释、留到深化部分的概念。章节编号用于定位，具体学习顺序遵循路线中的依赖。
- 从一个虚构业务需求起步，写出输入、输出、约束和失败成本。
- 业务主线使用 IM；对照[OpenIM 版本与源码地图](../../src/docs/platform_engineering/curriculum/im_reference.md)，选择消息、会话、连接、群组、同步或恢复中的一个具体问题。
- 先检查本项目已有正文与来源记录，避免重复生成或覆盖已经审阅过的修改。

## 2. 设计各节与生成要求

一章拆成可分次学习的若干节。每节明确问题、定义、推导、完整示例或片段、执行过程、反例、练习及反馈；为初学者逐一解释首次使用的符号和术语。

生成要求保存为 generation_request.json，包含上一章能力摘要、内容顺序、代码边界、虚构案例、预期结果约定及核对资料。经典书籍用于知识覆盖与结构参考；只有实际导入材料时，才能记录为 DeepTutor 的知识库输入。

IM 章稿还需提供固定源码版本、实际读取的文件或函数、相关事实摘要，以及教学模型与上游实现的差异。不要只把 GitHub 链接交给生成器就声称它已阅读源码；尚未输入或核对的 SDK、协议、配置与保证明确标记。

## 3. 调用 DeepTutor 并保存原始结果

使用现有 BookEngine 配置创建章稿，分内容块展开；检查块状态、失败信息及导出结果。记录 book_id、page_id、块数和生成要求。失败块需要补齐并审阅，不能把页面外壳计为完整正文。

原始导出保存到 `drafts/platform_engineering/deeptutor_XX_YY/original.md`，保持可追溯。原稿中的自动导览、生成要求、内部元信息不直接成为课程正文。

当前已验证的入口是本地 Python SDK；HTTP 创建接口曾发生 token 上限参数冲突，使用过单次进程适配。后续先检查实际可用入口，兼容问题及处理范围如实记录，不把临时绕行称为持久修复。

## 4. 审阅与补写

形成 reviewed.md 和 review_notes.md：

1. **先修检查**：前置有具体位置，新增术语在使用前解释，工程示例不会突然引入框架或复杂语法。
2. **技术核对**：按官方规范和文档核对规则、代码与预期，分别标注版本条件、故意错误和未运行结果。
3. **叙事整理**：合并重复内容，保持由具体例子到机制、再到业务取舍的顺序。
4. **练习补充**：覆盖预测、复现、独立变式、业务迁移，答案解释原因与边界。
5. **来源与脱敏**：使用虚构组织、身份和数据；保留资料链接与修订原因。
6. **IM 保证与源码对照**：区分受理、持久、交付和已读，检查顺序/去重/恢复的前提；项目事实、教学简化和备选设计分别标注，保留固定提交链接。

reviewed.md 是审阅后的完整教学内容。后续发现错误时同时维护审阅稿与正式正文，避免两边持续分叉。

## 5. 同步到本项目：每章交付的必需步骤

### 5.1 写入正式正文

- 目标目录：`src/docs/platform_engineering/curriculum/<分卷>/`。
- 为章稿确定稳定文件名，保留原有地址；添加 title、icon、order、date 等页面元信息。
- 同步审阅正文，转换草稿中的相对链接，增加卷内返回和前后章节入口。
- 项目正文保留教学内容；生成状态、内部 ID 与兼容处理记录在 drafts。
- 刷新已有章稿时，先比较原稿、上次审阅稿和当前正式正文；保留用户与后续审阅的修改，合并确认后的变化。

### 5.2 同步目录与学习状态

逐项检查这些位置是否需要更新：

| 位置 | 同步内容 |
|---|---|
| 分卷 README.md | 章节链接、完成状态、先修说明 |
| src/.vuepress/sidebar.ts | 新页面可达、无重复入口 |
| curriculum/learning_path.md | 当前可读内容、下一学习步、尚缺正文 |
| curriculum/assessment.md 与系列入口 | 已完成章稿数量与具体章号 |
| progress.md、concept_map.md | 学习记录行、关键概念定位 |
| drafts/platform_engineering/README.md | 原稿、审阅稿、正式文件和审阅记录入口 |

计划单元总数仅在教学设计真正变化时更新。新完成一章，通常只增加完成章稿数。已写正文、项目已同步、学习者已掌握、示例已运行分别记录。

### 5.3 更新来源清单

provenance.json 至少记录生成标识、生成状态、原稿与审阅稿哈希，以及正式 `course_file` 和 `course_sha256`。有 generation_request.json 时也记录其哈希；旧章缺少的历史材料不补造。

文档和链接合并完成后再计算最终哈希。同步完成指本地项目已经接入；Git 提交、远端推送和站点发布按会话中实际授权与完成情况分别报告。

## 6. 静态接入检查

检查本地 Markdown 链接、页面与侧栏覆盖、课号、代码围栏、表格、折叠块、来源哈希、前置顺序和脱敏内容。核对新增章节所需知识确实已有讲解或在章内补齐。

本课程当前约定为静态教材工作：不为了交付章稿执行站点构建、Go 示例或教学服务启动。DeepTutor 生成本身使用已有模型服务；生成成功不代表代码已运行。若检查发现问题，先修正受影响内容和记录，再报告本章交付状态。

## 7. 记录交付与下一步

在 verification.md 记录本次实际检查范围，在 drafts 保存来源和审阅差异。交付说明给出正式课程文件、主要新增内容、检查结果及仍未执行的验证。

更新下一章的前置摘要：本章真正讲过哪些概念、哪些只作预告、学习者需要留下什么证据。下一次生成由此承接，不能只依靠章名猜测前置已经掌握。

## 并行编写与统一合并

用户已授权使用多个 agent 并行完成章稿。按知识依赖选取独立任务；同批优先安排已具备稳定前置的不同章节，例如集合、需求基础和 Git 起步。每个写作 agent 完成自己负责章节的完整生成与审阅链路。

### 每个章节独占的内容

- 一个 drafts/platform_engineering/deeptutor_XX_YY 目录。
- 一个指定的正式课程文件。
- 独立 DeepTutor book_id、page_id、chapter_id 和临时 output_dir。
- 自己的生成要求、原稿、审阅稿、修订说明、来源与前置交接。

不得复用另一章的临时输出目录、覆盖公共 runner 或同时修改同一书籍。模型调用报错时，先保存该章状态并核查，再按需要重试，避免重复创建同一章的多份任务。

### 统稿职责

主 agent 负责共同规则、前置关系与交叉审阅，并集中维护卷目录、侧栏、路线、完成数、进度和档案索引。写作 agent 可以同步其独占的正式页，但只有统稿完成导航、来源和静态检查后，才计入完整交付数。

已有本地 IM 规则和概念边界见[共同教学约定](./common_contracts.md)，用于新章生成要求及跨章复核。

重点核对：不同章节是否使用相同的消息长度单位和失败优先级，新增规则是否明确标注，源码事实是否越过实际阅读范围，后续章是否偷用了前章尚未解释的语法。需要修订时，审阅稿与正式页一起更新并重算哈希。

并行提高的是章稿生产能力；学习者仍按路线分层阅读。一次批次完成不等于余下全部章稿完成，批次清单与实际正文状态分别记录。
