### 先划清当前合同与未来环境

### 先划清当前合同与未来环境

阅读本仓库时，先以代码中已经实现并测试的 **S2/v1 静态 HTTP 合同**为准，而不是先根据 `Compose` 文件推断系统能力。当前接口边界可固定为：

- 正文必须是 UTF-8，最大 **6 字节**；
- 原始请求体最大 **4096 字节**；
- 重复提交返回 `409`；
- 非成员访问返回 `404`，不额外暴露资源是否存在；
- 返回 `200` 仅表示请求已被当前进程的**内存状态**受理，不能理解为已写入数据库、已投递消息或已持久化。

因此，当前服务并不是完整的即时通信系统；它没有因为目录中出现 `db`、`broker` 或 `gateway` 就自动获得数据库存储、消息队列转发、跨进程一致性等能力。

`Compose` 中的 `gateway`、`db`、`broker` 应理解为未来多服务隔离部署的纸上环境：它们说明可能的服务名、网络边界和后续接入方向，但不构成“本仓库已经部署 IM”的证据。验证能力时应优先看路由、处理函数、内存模型、测试及实际启动日志。

后续 **S3/v2** 虽提出接入数据库的演进方向，但正文限制仍为 **6 字节**；这是一项提议，不应倒灌为当前实现事实。**R9** 仍处于待审状态，同样不能被当作已生效需求。代码事实优先，Compose 设想其次，评审结论最后。

### 用服务名定位未来依赖

### 用服务名定位未来依赖

在 Compose 网络中，`gateway`、`db`、`broker` 是同一私有网络里的**服务名**，可被当作内部主机名解析。它们用于表达未来依赖边界，而不是说明当前仓库已经连接了数据库或消息系统。

需要区分四个概念：

- **服务名**：容器间访问地址。例如 gateway 访问数据库应使用 `db`，访问消息代理应使用 `broker`。
- **容器端口**：服务在容器网络内监听的端口，例如 `db:5432`、`broker:5672`。
- **宿主端口**：为开发者从本机进入容器而映射的端口，例如 `localhost:15432 -> db:5432`。
- **`localhost`**：永远指“当前进程所在环境”。在 gateway 容器内，`localhost` 是 gateway 自己，不是宿主机，也不是 db 容器。

因此，未来 gateway 的配置应类似：

- 数据库地址：`db:5432`
- 消息代理地址：`broker:5672`
- 本机调试数据库：`localhost:15432`

不要让 gateway 在容器内连接 `localhost:15432`；这会把“从宿主机调试”的入口误当成“服务间通信”的路径。Compose 中的端口映射主要服务于人和外部工具，服务之间应优先使用服务名加容器端口。

这套命名只是在为后续 S3/v2 的数据库与 broker 提议预留隔离环境。当前 S2/v1 仍是静态 HTTP 合同：UTF-8 正文上限 6B、原始请求体上限 4096B、重复请求返回 `409`、非成员返回 `404`，`200` 仅表示已在内存中受理；R9 仍待审。

### 启动、健康与业务就绪分层

### 启动、健康与业务就绪分层

不要把“容器已启动”误读为“服务已经能处理请求”。在 Compose 的未来隔离环境中，`gateway`、`db`、`broker` 至少有三层不同含义：

| 层次 | 表示什么 | 不能保证什么 |
|---|---|---|
| `depends_on` 启动顺序 | Compose 先创建或启动被依赖服务 | 数据库已完成初始化、端口已可连接 |
| `service_healthy` 健康门 | 被依赖服务的 `healthcheck` 已返回成功 | 迁移完成、账户权限正确、业务表可用 |
| 业务就绪 | 应用已能完成真实业务所需操作 | 不代表所有未来功能都已实现 |

例如，`gateway` 依赖 `db` 的健康状态，只能说明数据库探针通过；若 `gateway` 启动后还需要执行迁移、检查表结构、建立连接池或验证凭据，则这些步骤成功后，才应视为“业务就绪”。

对当前仓库尤其要克制：现行 S2/v1 是静态 HTTP 合同，成功的 `200` 仅表示请求已被内存受理；UTF-8 正文限制为 `6B`、原始请求体限制为 `4096B`，重复提交返回 `409`，非成员返回 `404`。它并不要求真实 `db` 或 `broker` 已运行。

因此，Compose 中的 `gateway/db/broker` 应被标记为未来架构隔离方案，而非已部署即时通信能力。未来 S3/v2 即使提出数据库方案，`6B` 限制仍保持；R9 仍待审，不能据此宣称持久化、消息投递或跨服务就绪已经成立。

### 安全追踪配置与运行证据

### 安全追踪配置与运行证据

追踪配置应分三层核查：**规划值、容器生效值、运行证据**。三者一致，才能说明未来隔离环境可被复现；但这不等于仓库已经部署了数据库或消息中间件。

- **规划配置**：检查 Compose 的变量插值，例如 `${DB_HOST}`、`${BROKER_URL}`、`${TRACE_ENDPOINT}`。可用 `docker compose config` 查看插值后的结构，重点确认服务名、端口、网络和卷路径；不要把 `.env`、令牌、密码或完整连接串提交到日志。
- **容器生效环境**：启动后以 `docker compose exec gateway env` 或容器检查结果核对非敏感变量，如 `APP_ENV`、`PORT`、`TRACE_ENABLED`。密码类变量只确认“已设置”或来源为 secret，不回显具体值。
- **卷挂载**：核查 gateway 是否挂载只读配置文件、日志目录是否落到预期卷。配置卷应尽量使用 `:ro`，避免应用意外修改追踪规则；持久卷名称只证明数据隔离设计存在，不证明 db/broker 已承担当前 S2/v1 请求。

运行证据以 gateway 日志和健康检查为主：记录启动时间、监听端口、配置摘要、请求关联 ID、状态码与耗时。日志中可证明当前合同的 `200` 仅表示内存受理，重复请求仍为 `409`，非成员为 `404`；不得据此推断已写入 DB、已投递 broker 或已形成持久审计链。

### 以静态合同验证当前结果

### 以静态合同验证当前结果

当前验证应只针对已实现的 S2/v1 静态 HTTP 合同，而不是根据 Compose 文件推断数据库或消息队列能力。可用服务名访问 `gateway`，但 `db`、`broker` 在此阶段只是未来隔离环境中的依赖占位；本仓库当前的成功结果不表示已写入 DB，也不表示已投递 broker。

以创建或提交类请求为例，测试应覆盖以下边界：

- 正文按 UTF-8 编码后的字节数计算，最多 `6B`。例如 `"你好"` 通常占 `6B`，可接受；`"你好！"` 超过 `6B`，应被拒绝。
- 请求体整体按**原始字节**限制，最多 `4096B`。即使业务正文很短，过大的 JSON、填充字段或额外字节仍应触发大小限制。
- 首次使用某个请求标识提交，若成员关系与正文均合法，返回 `200`。这里的 `200` 仅表示 gateway 已在当前进程内存中受理该请求。
- 使用相同请求标识再次提交，应返回 `409`，用于表达重复请求；不要把它解释为数据库唯一键冲突，因为当前合同并不承诺 DB 持久化。
- 调用者不是目标成员时返回 `404`。该状态表示当前合同不向非成员暴露目标资源，不应改为“未来可由 broker 异步判断”。

可将验证写成连续断言：先提交 `6B` 正文并期待 `200`，原样重试期待 `409`；再用非成员身份提交期待 `404`；最后分别构造超过 `6B` 的正文和超过 `4096B` 的原始体。未来 S3/v2 即使提议引入 DB，正文上限仍为 `6B`；R9 仍待审，不能提前把这些未来预期当作当前实现结果。

> **要点** — 当前先验证静态 HTTP 合同；Compose 服务名、端口、健康与配置用于理解未来隔离部署，不代表 IM 已接入数据库或消息队列。

在同一 Compose 网络中，服务应通过稳定的服务名通信；先分清“谁在访问、从哪里访问”，才能正确理解端口、localhost 与重建后的连接行为。

### 先确定访问者所在的位置

### 先确定访问者所在的位置

排查连接问题时，先问一句：**发起连接的程序运行在哪里？** 同一个地址在不同网络视角中的含义不同。

- **宿主机上的程序**访问数据库，应使用宿主机发布的端口，例如 `127.0.0.1:15432`。这里的 `15432:5432` 表示：宿主机的 `15432` 转发到 `db` 容器的 `5432`。
- **gateway 容器**访问数据库，应使用 Compose 服务名与容器端口：`db:5432`。同一 Compose 网络会提供内部 DNS，`db` 会解析到当前数据库容器。
- **db 容器自身**中，`localhost:5432` 才表示它自己的 PostgreSQL 服务。

因此，gateway 中配置 `localhost:5432` 是常见错误：`localhost` 指向 gateway 容器本身，而不是宿主机，也不是 db 容器。除非 gateway 自己运行了数据库，否则连接必然失败。

可以把地址理解为“相对当前位置的路线”：

| 访问者 | 正确目标 |
|---|---|
| 宿主机 | `127.0.0.1:15432` |
| gateway 容器 | `db:5432` |
| db 容器自身 | `localhost:5432` |

容器重建后，`db` 的内部 IP 可能变化，但服务名保持稳定；应用应依赖 `db:5432`，并在旧连接失效时重新建立连接。

### 服务名 db 是容器间的稳定入口

### 服务名 `db` 是容器间的稳定入口

在同一 Compose 网络中，`gateway` 不应记住数据库容器的 IP，而应使用服务名连接：

`db:5432`

这里的 `db` 是 Compose 为服务提供的网络名称。容器启动后，网络内的 DNS 会将 `db` 解析到当前数据库容器的内部地址；`5432` 则是 PostgreSQL 在容器网络中监听的端口。因此，`gateway` 的连接配置通常应写为：

`postgresql://用户:密码@db:5432/数据库名`

关键是区分访问位置：

- `gateway` 容器访问数据库：使用 `db:5432`。
- 宿主机上的客户端访问数据库：若配置了 `15432:5432`，使用 `127.0.0.1:15432`。
- `gateway` 中的 `localhost:5432`：指向 `gateway` 自己，不是 `db`。

容器 IP 并非稳定契约。数据库服务重建、扩缩容或网络重新创建后，`db` 对应的内部 IP 可能变化；服务名仍保持不变。应用应让 DNS 在新建连接时重新解析 `db`，并对已有连接失败实现重连或连接池恢复。这样，服务发现由网络负责，业务配置只依赖稳定的服务名。

### 端口映射只服务于宿主访问

### 端口映射只服务于宿主访问

假设 Compose 中数据库声明为：

`ports: ["15432:5432"]`

这表示：

- 左侧 `15432`：**宿主机端口**
- 右侧 `5432`：**`db` 容器内数据库监听端口**

因此，访问地址取决于“访问者在哪里”。

| 访问者 | 正确地址 | 原因 |
|---|---|---|
| 宿主机上的命令行、IDE、迁移工具 | `127.0.0.1:15432` | 宿主机通过映射端口转发到容器的 `5432` |
| 同一 Compose 网络中的 `gateway` 容器 | `db:5432` | `db` 是服务名，Compose DNS 会解析到数据库容器 |
| `gateway` 容器中的 `localhost:5432` | 错误目标 | `localhost` 指向 `gateway` 容器自身，不是 `db` |

可将映射理解为一条面向宿主机的入口：

`宿主机 127.0.0.1:15432 → db 容器:5432`

而容器间通信走的是内部网络：

`gateway 容器 → db:5432 → db 容器`

因此，应用配置通常应区分运行位置：本地直接在宿主机运行时使用 `127.0.0.1:15432`；作为 `gateway` 容器运行时使用 `db:5432`。即使未暴露 `15432`，同网络服务仍可通过 `db:5432` 通信；端口映射并不是容器互联的前提。

### localhost 在 gateway 中为何不是数据库

### localhost 在 gateway 中为何不是数据库

假设 Compose 中有两个服务：`gateway` 与 `db`。数据库容器监听 `5432`，并声明宿主机映射：

`15432:5432`

此时在 `gateway` 内执行：

`psql -h localhost -p 5432 ...`

很可能连接失败。原因是 `localhost` 永远表示“当前网络命名空间中的本机”。命令运行在 `gateway` 容器里，因此：

- `localhost` / `127.0.0.1` 指向 `gateway` 容器自身；
- 它不会自动跳转到 `db` 容器；
- `15432:5432` 是“宿主机端口 → db 容器端口”的映射，不是容器间通信地址。

因此，`gateway` 应使用 Compose 提供的服务名访问数据库：

`postgresql://用户:密码@db:5432/数据库名`

其中 `db` 会被 Compose 的内部 DNS 解析为当前数据库容器的地址，`5432` 是数据库在容器网络内监听的端口。

宿主机上的开发工具则应连接：

`127.0.0.1:15432`

可以按访问者区分：

| 访问位置 | 正确目标 |
|---|---|
| `gateway` 容器 | `db:5432` |
| 宿主机 | `127.0.0.1:15432` |
| `db` 容器自身 | `localhost:5432` |

只有数据库进程也运行在 `gateway` 容器内时，`localhost:5432` 才可能正确。容器重建后 `db` 的内部 IP 可能变化，但服务名 `db` 保持稳定；应用仍应使用服务名，并在旧连接失效时建立新连接。

### 重建后名称不变，连接仍需恢复

### 重建后名称不变，连接仍需恢复

Compose 网络中的服务名 `db` 是稳定的访问入口，而不是固定 IP。`db` 容器被重建后，Docker 可能为新容器分配新的网络 IP；但同一网络内再次解析 `db`，会得到新地址。因此，`gateway` 应始终连接：

`db:5432`

而不应把某次查询到的容器 IP 写入配置、环境变量或连接池缓存。

不过，“名称仍可解析”不等于“旧连接自动恢复”。重建发生时，原 `db` 进程退出，`gateway` 已建立的 TCP 连接会断开，常表现为连接重置、读写失败、连接超时，或连接池取出失效连接。即使 DNS 已指向新 IP，旧 socket 仍然指向已经消失的旧容器。

应用应把数据库连接视为可失效资源：

- 为连接、查询和启动等待设置合理超时，避免无限阻塞。
- 对短暂网络错误、连接被关闭等可恢复错误执行有限次数重试。
- 失败后丢弃旧连接，重新解析 `db` 并建立新连接。
- 使用连接池时启用连接健康检查、空闲连接回收或失败后自动重建。
- 在数据库真正完成启动、迁移和监听前，`gateway` 不应仅因容器已启动就假定其可用。

因此，服务名解决“新实例在哪里”，重连机制解决“旧连接已经失效”。两者配合，才能让 `db` 重建后的短暂中断变成可恢复故障，而非长期不可用。

> **要点** — 容器间使用服务名和容器端口，宿主机使用映射端口；名称稳定不代表既有连接永久有效。

多服务环境中，“容器已启动”不等于数据库已经能安全处理业务请求。关键在于明确依赖条件、健康信号与迁移契约分别证明什么。

### 启动顺序不等于可连接

### 启动顺序不等于可连接

`depends_on` 的默认语义只是协调**启动先后**：Compose 会先创建并启动被依赖服务，再启动当前服务。它并不承诺数据库已经完成初始化，更不承诺应用此刻能够成功执行 SQL。

例如：

```yaml
api:
  depends_on:
    - db
```

这通常只能推导出“`db` 容器的启动动作先发生”。但在 `api` 进程开始连接时，数据库仍可能处于以下阶段：

- 数据库进程尚未开始监听端口；
- 端口已监听，但仍在恢复数据、回放日志或初始化系统表；
- 数据库可接受连接，但业务账号、密码或授权尚未生效；
- 账号可登录，但目标数据库、表、索引或迁移版本尚不存在；
- 连接成功，却因事务隔离、权限不足或初始化任务未完成而无法处理业务请求。

因此，“容器运行中”与“服务可用”是不同层次的事实。前者最多说明入口进程没有立即退出；后者至少应对应业务真正需要的能力，例如“可用指定账号连接”“可查询关键表”“可执行最小读写操作”。

如果应用只依赖默认 `depends_on`，应自行具备连接重试、退避等待和失败恢复能力。不要把偶然成功的启动顺序误当作稳定契约：本地机器上一次启动正常，不代表首次拉取镜像、清空数据卷、重建容器或数据库恢复较慢时仍然可靠。

### 用 service_healthy 建立基础门槛

### 用 `service_healthy` 建立基础门槛

`depends_on` 的默认语义通常只是“先启动依赖容器”：数据库进程已经被创建或运行，并不表示它已接受连接、完成恢复或加载初始化数据。若业务服务在此刻立刻执行 SQL，仍可能遇到连接拒绝、认证失败或数据库尚未创建等竞态。

可将依赖条件提升为 `service_healthy`：

```yaml
services:
  api:
    depends_on:
      db:
        condition: service_healthy

  db:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 12
```

其推导关系是：

1. `db` 容器启动；
2. Compose 按 `healthcheck.test` 周期执行探测命令；
3. 探测命令连续或累计满足配置要求并以退出码 `0` 结束；
4. `db` 状态变为“健康”；
5. `api` 才被允许启动。

这里的关键边界是：`service_healthy` **只采信健康探测命令的退出状态**。它不理解“数据库是否真的满足业务契约”。例如，`pg_isready` 能证明服务端大致可响应连接请求，却未必证明目标 schema 已迁移、业务账号拥有所需权限、种子数据存在，或事务与扩展已准备完毕。

因此，健康检查应至少覆盖当前服务启动所必需的基础能力；但不要把“端口可达”误写成“业务可用”。更强的 schema、权限和迁移保证，应由明确的迁移服务及其完成契约承担。

### 端口健康为何不代表业务就绪

### 端口健康为何不代表业务就绪

“端口可连接”只是最弱的存活证据：它通常只能说明目标进程正在监听某个 `TCP` 端口。数据库容器即使已经监听 `5432` 或 `3306`，仍可能处于恢复、初始化、重放日志、创建默认用户等阶段；此时应用连接可能超时、被拒绝，或连接后立即失败。

可以把就绪证据理解为逐层增强的合同：

| 证据层次 | 能证明什么 | 仍不能证明什么 |
|---|---|---|
| 端口开放 | 网络可达，进程在监听 | 数据库接受认证、表存在、权限正确 |
| 数据库可认证 | 指定用户能建立会话 | 目标 schema 已创建、迁移已完成 |
| 执行简单查询 | 连接、认证和基本 SQL 可用 | 业务表、索引、扩展及数据版本正确 |
| 检查迁移版本 | schema 达到预期版本 | 应用账户拥有实际读写权限 |
| 业务探针 | 关键表、权限、事务路径可用 | 所有业务流程都绝对无故障 |

例如，健康检查若仅执行 `nc -z db 5432`，只能回答“数据库端口开了吗”；即使改为 `pg_isready`，也主要证明 PostgreSQL 已接受连接。更接近应用真实需求的探针应使用**应用实际账户**，验证必要的 schema 版本及最小读写能力，例如在可回滚事务中执行：

`BEGIN; SELECT version FROM schema_migrations; INSERT ...; ROLLBACK;`

因此，`condition: service_healthy` 的价值完全取决于 `healthcheck` 的合同。若探针只测端口，编排系统只会可靠地等待“端口开放”，不会等待“业务可安全使用”。迁移完成则应由独立的一次性迁移服务负责，并以 `service_completed_successfully` 明确表达“迁移命令成功退出”；不要把“容器启动”误当成“数据库已满足应用契约”。

### 一次性迁移服务的完成契约

### 一次性迁移服务的完成契约

数据库迁移通常不是常驻服务，而是“执行脚本、退出、留下确定状态”的一次性任务。此时可让应用依赖迁移服务的成功完成：

`condition: service_completed_successfully`

它表达的不是“迁移容器已启动”，也不是“数据库端口可连接”，而是：迁移进程以退出码 `0` 结束。应用因此可在结构变更完成后再启动，避免代码已发布、表或索引却尚未创建的短暂不一致。

但这个条件只证明**迁移命令成功返回**；迁移是否真的构成可靠契约，仍需单独约定：

- **脚本幂等**：重复执行应安全，或由迁移工具记录版本并拒绝错误重放。不能把“容器重启后再次执行”变成重复建表、重复写初始化数据。
- **失败即失败**：连接超时、权限不足、语法错误、锁等待超时都必须返回非零退出码；不得捕获异常后打印日志并以 `0` 退出。
- **原子性边界**：明确每个迁移是否在事务内执行。某些 DDL 不支持事务，应说明失败后的残留状态及人工恢复步骤。
- **执行者唯一性**：多副本应用不能各自触发迁移；应指定唯一迁移服务，或使用数据库锁、部署流水线互斥机制。
- **版本兼容性**：迁移应优先采用“先扩展、后切换、再清理”的方式，使新旧应用版本在滚动发布期间都能工作。

因此，`service_completed_successfully` 是编排层的等待信号，不是迁移正确性的证明。真正的完成契约应包含：目标版本、执行账号权限、失败退出规则、可重试策略、回滚或修复流程，以及应用启动前必须满足的模式版本。

### 为未来 IM 服务设计分层依赖

### 为未来 IM 服务设计分层依赖

设想一个即时通信系统由 `gateway`、`db`、`broker` 与一次性 `migrate` 服务组成。不要把它们的依赖理解为“按顺序启动”，而应拆成四层证据：

1. **进程已启动**：`db`、`broker` 容器进入运行状态。默认 `depends_on` 通常只保证这一层；此时数据库可能仍在恢复日志，消息代理也可能尚未加载队列元数据。

2. **基础设施可用**：为 `db` 配置健康检查，例如用专用账户执行轻量查询；为 `broker` 检查其管理接口或协议握手。`gateway` 可声明：

   ```yaml
   depends_on:
     db:
       condition: service_healthy
     broker:
       condition: service_healthy
   ```

   但“端口可连接”只能证明监听已出现，不能证明业务账户拥有正确权限、目标库存在，或事务与复制状态已经满足要求。

3. **数据契约已完成**：`migrate` 应是独立的一次性服务。它等待 `db` 健康后执行版本迁移、索引创建和必要的初始数据写入；成功退出才表示当前代码预期的模式版本成立。`gateway` 再依赖：

   ```yaml
   migrate:
     condition: service_completed_successfully
   ```

   迁移脚本应具备幂等性、版本记录与失败可诊断性；不能把“迁移容器退出”误当作“数据库一定适合所有业务版本”。

4. **业务路径已验证**：`gateway` 启动后仍应在自身就绪检查中验证关键配置，例如连接数据库、访问所需表、建立 broker 发布/订阅连接。只有这些检查通过，负载均衡器才应把 `/ready` 标记为可接流量。

因此，`db` 健康证明基础设施可用，`migrate` 成功证明数据契约完成，`gateway` 就绪证明当前业务实例能够服务请求；三者不能互相替代。

> **要点** — 依赖条件只能证明约定的信号；要让服务安全启动，必须把进程、健康、迁移和业务就绪分层验证。

本节厘清 Compose 模型插值与容器环境变量的边界，建立可审计、无泄密的本地多服务配置实践。

### 两类变量：模型插值与容器运行环境

### 两类变量：模型插值与容器运行环境

Compose 中常被统称为“环境变量”的内容，实际分属两个阶段，不能混用。

- **模型插值变量**：在 Compose 读取并生成服务模型时使用。来源通常是执行命令的 shell 环境，以及项目目录中的 `.env` 文件。例如：

  `ports: ["${WEB_PORT:-8080}:8080"]`

  这里的 `${WEB_PORT}` 在容器启动前就已被替换；它决定的是 Compose 模型中的端口映射，而不是容器内进程必然能读取到的 `WEB_PORT`。

- **容器运行环境变量**：在容器启动时注入给进程。通过 `environment` 或 `env_file` 声明，例如：

  `environment: [DATABASE_URL=${DATABASE_URL}]`

  或 `env_file: [.env.app]`。前者将解析后的值写入容器环境；后者将文件中的键值对注入容器。容器内可用 `printenv`、应用配置加载逻辑读取它们。

两者可同时出现：shell 或 `.env` 可用于插值 `env_file` 的路径、镜像标签、端口和变量值；但 `.env` 本身**不会自动进入容器**。若应用需要某个变量，必须显式写入 `environment` 或 `env_file`。

建议将用途分开：`.env` 保存本地 Compose 参数，`.env.app` 保存应用运行参数；密钥使用受控的本地密钥文件或密钥管理机制，并避免将 `docker compose config` 的完整输出提交到仓库或日志，因为该输出可能已展开敏感值。

### Compose 插值来源与覆盖优先级

### Compose 插值来源与覆盖优先级

Compose 在读取文件时，先构造“插值环境”，再把 `${变量}` 替换为具体值；这与容器启动后的环境变量注入是两件事。同名变量之所以“被覆盖”，通常是因为它同时存在于多个插值来源。

典型取值链可理解为：

1. 命令前在宿主 shell 中导出的变量优先，例如 `端口=18080 docker compose up`。
2. 若未显式指定，Compose 读取当前工作目录的 `.env` 作为补充来源。
3. 使用 `docker compose --env-file 文件名` 时，显式文件替代默认 `.env`；应将其路径和版本纳入记录。
4. 若上述来源均未提供，才使用 Compose 文件中的默认表达式，如 `${端口:-8080}`。其中 `:-` 在变量未设置或为空时回退，`${端口-8080}` 则仅在未设置时回退。

例如：

`ports: ["${网关端口:-8080}:8080"]`

若 shell 中已有 `网关端口=19090`，即使 `.env` 写着 `网关端口=18080`，最终仍使用 `19090`。默认值不是强制值，只是最后的回退。

不要混淆插值与容器变量：`environment:`、`env_file:` 决定容器内可见的变量；`${变量}` 只是生成 Compose 模型时的替换。容器启动命令中的 `-e` 又可覆盖其环境变量。排障时应记录 Compose 文件版本、所用 `--env-file` 路径及非敏感配置摘要，但不要将 `docker compose config`、环境转储或密钥写入日志。当前 v1 6B 的资源与安全限制也必须保持固定，不能借由本地 `.env` 或默认值悄悄放宽。

### environment 与 env_file 的职责边界

### environment 与 env_file 的职责边界

`environment` 与 `env_file` 都会向**容器进程**注入环境变量，但职责不同：前者适合显式、少量、需要随服务定义审查的配置；后者适合复用一组非敏感或由本地安全文件提供的变量。

- `environment` 可写成映射或列表，通常用于端口、运行模式、服务地址等关键覆盖项：

  ```yaml
  environment:
    APP_ENV: development
    REDIS_URL: redis://redis:6379/0
  ```

- `env_file` 指向变量文件，适合数据库连接参数、开发工具选项等成组配置：

  ```yaml
  env_file:
    - .env.local
  ```

同一服务中，`environment` 的同名键会覆盖 `env_file` 中的值；两者未声明的变量，则保留镜像通过 `ENV` 设置的默认值。因此可将镜像 `ENV` 视为最低层默认配置，将 `env_file` 视为环境配置包，再用 `environment` 放置该服务必须明确的最终覆盖值。

注意，`env_file` 不是 Compose 文件插值用的 `.env`：前者注入容器，后者主要参与 `${VAR}` 替换。不要因文件同名而混淆其作用域。密钥应放入未提交的本地安全文件或专用密钥机制，避免写入 `environment`、`docker compose config` 输出及日志；配置只能收紧或补全当前限制，不能通过本地变量悄悄放宽 v1 6B 的既定约束。

### 用配置快照追踪实际生效值

### 用配置快照追踪实际生效值

本地多服务排障时，最可靠的证据不是“我改过 `.env`”，而是某次启动实际采用了哪一版 Compose 模型、镜像与非敏感配置。应在启动前生成可审计快照，并把快照标识写入启动记录。

先区分两类值：

- `shell` 与 `.env`：用于 Compose 文件中的 `${变量}` 插值，影响镜像标签、端口映射、挂载路径、服务副本等模型内容。
- `environment` 与 `env_file`：用于向容器进程注入环境变量；其优先级可能覆盖镜像内 `ENV` 或其他来源。

可执行：

`docker compose config > compose.resolved.yaml`

但该命令可能展开敏感变量，不能将原始输出直接提交、上传或打印到持续日志。应使用受控脚本生成脱敏副本：保留变量名、服务名、端口、镜像摘要和配置版本，将 `PASSWORD`、`TOKEN`、`SECRET`、`KEY` 等字段替换为 `***`；对于 URL，也应隐藏其中的用户名、密码和查询参数。

每次启动记录至少包含：

- 配置快照版本，如 Git 提交号或 `CONFIG_REV`；
- Compose 文件及覆盖文件列表；
- 镜像标签，最好再记录不可变摘要；
- 已解析的非敏感端口、服务名、网络名；
- 快照文件的校验和与生成时间；
- 启动命令及操作者可识别的本地会话标识。

例如可将 `CONFIG_REV=2025-03-08.1` 写入非敏感启动元数据，并在应用健康检查日志中仅输出该版本号，而非完整环境变量。

特别注意：配置快照用于证明“实际生效”，不是绕过约束的入口。当前 v1 6B 的资源上限、并发限制或安全策略必须由受版本控制的配置明确声明；不得通过本机 `.env`、未记录的覆盖文件或临时 shell 变量悄悄放宽。若确需变更，应更新配置版本、重新生成脱敏快照，并让启动记录与该快照一一对应。

### IM 网关的配置边界与验证清单

### IM 网关的配置边界与验证清单

设想未来本地环境包含 `im-gateway`、`db` 与 `broker`。应先区分两条配置链路：

- shell 或 `.env` 中的值用于 Compose 模型插值，例如镜像标签、端口映射、挂载路径：`${IM_GATEWAY_PORT}`。
- `environment` 与 `env_file` 才会把变量传入容器进程，例如 `DATABASE_URL`、`BROKER_URL`。
- 两者可以同名，但含义并不自动相同；宿主机变量可能覆盖 `.env` 插值值，也可能改变 `environment` 中引用的结果。

纸上示例中，`im-gateway` 通过 `environment` 获得 `DATABASE_URL` 和 `BROKER_URL`，`db`、`broker` 仅暴露内部网络端口；对宿主机开放的端口必须显式记录，不能依赖默认值。尤其是当前 v1 的 6B 约束应写成不可变的配置断言：不得通过 `.env`、shell 覆盖、Compose 默认值或开发模式开关悄悄放宽。若某项值会影响该约束，应由受版本控制的配置明确给出，并在启动前拒绝不合法组合。

验证按层进行：

1. **模型层**：执行 `docker compose config` 检查服务名、网络、端口与最终插值；输出应脱敏，不保存或上传密钥。
2. **容器层**：检查各容器实际环境变量，仅确认变量“存在、格式正确、来源符合预期”，不要在日志中打印值。
3. **就绪层**：`im-gateway` 不应仅因进程启动即宣称可用；应等待 `db` 健康、`broker` 可连接，并验证自身配置断言。
4. **版本层**：记录 Compose 文件版本、镜像摘要与非敏感配置摘要；密钥只保留引用位置或指纹，避免进入 `config` 输出、终端历史和诊断日志。

> **要点** — Compose 插值决定配置模型，容器变量决定进程行为；必须记录脱敏后的生效配置，并守住既定业务约束。

排查本地多服务问题时，日志只能说明服务说了什么，不能证明依赖、配置、权限与业务结果已经正确交付。

### 日志的证据边界

### 日志的证据边界

`docker compose logs`回答的是“容器输出了什么”，而不是“调用方已经拿到可用结果”。一条 `started`、`listening` 或 `connected` 日志，通常只证明某个进程曾进入某个状态；它不能自动证明网络名称、端口、认证、数据库结构和业务数据均正确。

例如，网关日志中的“连接 PostgreSQL 成功”可能来自错误配置：在容器内写 `localhost:15432`，`localhost` 指向网关容器自身，而非数据库服务；数据库日志显示“已启动”也不等于已接受连接、更不等于迁移完成。数据库重建后 IP 改变，则依赖固定 IP 的旧配置可能仍让日志看似正常，却把请求发往错误目标。

应把日志视为线索，并逐站补足反证：

- **名称与端口**：在调用容器内确认 `db:5432` 等服务名可解析、目标端口可连通。
- **配置来源**：核对实际生效的环境变量、挂载文件和 Compose 覆盖配置，而非只看源码默认值。
- **健康与就绪**：`healthcheck` 通过应代表依赖可服务；进程存活或端口监听只算“已启动”。
- **权限与 SQL**：用应用同一账号执行连接、建表或查询，确认权限、schema、迁移版本一致。
- **业务结果**：最终以一次真实请求的响应、写入结果及可验证查询为准。

日志能帮助定位“哪一站可能失败”，但只有请求沿名称、网络、认证、SQL 到业务响应完整走通，服务才算可交付。

### 先还原连接视角

### 先还原连接视角

`gateway` 配置 `localhost:15432` 时，先不要判断“端口是否开着”，而要问：**这条连接从哪里发起，`localhost` 又指向谁？**

同一串地址在三种视角中的含义不同：

- **宿主机视角**：若 Compose 将数据库发布为 `15432:5432`，宿主机上的客户端可连 `localhost:15432`。这里 `15432` 是宿主机端口，经端口映射转到数据库容器的 `5432`。
- **gateway 容器视角**：容器内的 `localhost` 只指向 gateway 容器自身。`gateway:15432` 或 `localhost:15432` 都不会自动到达数据库；除非 gateway 自己恰好监听该端口。
- **Compose 服务网络视角**：gateway 应通过服务名访问数据库，例如 `postgres:5432`。服务名由 Compose 内置 DNS 解析，`5432` 是数据库容器实际监听端口，不是宿主机发布端口。

因此，下面两类配置用途不同：

`postgres://user:pass@localhost:15432/appdb`  
适用于宿主机运行的迁移工具、`psql` 或本地调试程序。

`postgres://user:pass@postgres:5432/appdb`  
适用于与 `postgres` 同一 Compose 网络中的 `gateway` 容器。

可按连接路径逐项反证：

1. 确认发起者：命令是在宿主机执行，还是在 `gateway` 容器内执行。
2. 确认名称：容器间使用 Compose 服务名，而非容器临时 IP，也通常不是 `localhost`。
3. 确认端口：容器到容器用目标容器端口；宿主机到容器才用发布端口。
4. 在 gateway 内执行 `getent hosts postgres`、`nc -zv postgres 5432`，验证 DNS 与 TCP 路径。
5. 再用实际连接串执行认证与 SQL，避免把“端口可达”误判为“数据库可用”。

### 从启动到业务就绪

### 从启动到业务就绪

多服务环境中，“容器起来了”并不等于“应用可交付”。应把以下状态严格区分：

| 状态 | 实际证明 | 不能证明 |
|---|---|---|
| `depends_on` | Compose 已按依赖关系尝试启动服务 | 依赖已监听端口、可认证、可执行查询 |
| 服务启动 | 进程已运行，日志可能出现 `started` | 数据库恢复完成、网络可达、配置正确 |
| 健康检查通过 | 某个 `healthcheck` 命令返回成功 | 应用所需账号、目标库、表结构和业务数据可用 |
| 数据库接受连接 | 指定主机、端口、账号可建立会话 | schema 已迁移，权限覆盖实际 SQL |
| schema 已迁移 | 迁移记录与目标版本一致 | 网关、应用配置和端到端业务请求正确 |

例如，`depends_on` 只能避免应用比数据库容器更早被“启动”；它不能避免应用在 PostgreSQL 尚未就绪时立即连接失败。即使数据库日志显示 `database system is ready to accept connections`，仍需确认应用使用的是服务名和容器端口，如 `db:5432`，而不是宿主机映射 `localhost:15432`。

健康检查也要贴近真实依赖。仅执行 `pg_isready` 只能说明数据库可响应，不能证明业务账号能访问目标数据库，更不能证明迁移后的表存在。更可靠的交付链应为：

1. 服务名可解析，端口可连接；
2. 应用实际读取到预期配置；
3. 业务账号可认证且具备所需权限；
4. 迁移完成，schema 版本符合要求；
5. 执行关键 SQL 成功；
6. 发起真实业务请求，并验证返回结果、写入结果或副作用。

因此，日志、启动顺序和绿色健康状态都只是证据链中的一站；只有业务路径的输入、查询与结果同时成立，才算真正就绪。

### 四类纸上故障反证

### 四类纸上故障反证

所谓“纸上故障”，是指从日志、容器状态或配置文字看似合理，但请求沿真实网络与真实数据库执行时失败。不要停在“服务启动了”，应逐段反证连接链路。

1. **网关连接 `localhost:15432`**

   网关容器中的 `localhost` 指向网关容器自身，不是宿主机，也不是数据库容器。即使宿主机可用 `localhost:15432` 连库，网关仍会连接失败。

   正确判断是：Compose 内部服务间使用服务名和容器端口，例如：

   `postgresql://app:secret@db:5432/appdb`

   `15432:5432` 只是“宿主机访问数据库”的端口映射；`gateway → db` 不应经过它。

2. **数据库已启动，但尚未就绪**

   日志出现“数据库系统已启动”不等于已经接受目标用户、目标库和 SQL 请求。初始化脚本、恢复数据、创建账号期间，应用可能过早连接并报认证、库不存在或连接被拒绝。

   应分别验证：`db` 容器是否运行、健康检查是否通过、应用账号能否登录、目标数据库是否存在。应用若依赖数据库，应等待 `service_healthy`，并保留自身重试，而非只依赖启动顺序。

3. **重建后仍使用旧 IP**

   容器重建会得到新 IP。把数据库 IP 写入环境变量、配置文件或缓存，首次可能可用，重建后即失效；日志中旧地址仍“看起来像数据库地址”，却已指向不存在的端点。

   Compose 网络提供稳定的是服务名，不是 IP。配置应写 `db:5432`，由内部 DNS 每次解析；不要把 `docker inspect` 得到的地址当作应用配置。

4. **健康为绿，但 schema 未迁移**

   健康检查常只执行 `pg_isready` 或简单 `SELECT 1`，它证明数据库可响应，不证明业务表、索引、扩展和版本已准备好。于是 `db` 显示健康，网关也启动成功，首个业务请求却报“表不存在”或字段缺失。

   此时应继续反证：迁移任务是否执行成功、迁移用户是否有建表权限、迁移版本是否到达预期值，以及实际业务 SQL 是否能返回正确结果。绿色健康状态只是链路中的一站，不是应用交付的终点。

### 分层核验交付结果

### 分层核验交付结果

`docker compose logs` 只能提供线索：进程打印“已启动”不等于应用已能完成真实请求。应沿请求路径逐站反证，而非仅凭某一条“成功”日志下结论。

1. **名称与网络**：容器内访问数据库应使用服务名和容器端口，例如 `postgres:5432`，而不是 `localhost:15432`。`localhost` 指向当前容器；`15432:5432` 中的 `15432` 通常只供宿主机访问。可在 gateway 容器内执行 `getent hosts postgres`，确认名称可解析。

2. **端口与监听**：名称解析成功不表示端口可达。用 `nc -zv postgres 5432` 或应用镜像中的等价工具检查连接；再检查数据库是否监听正确地址，而非仅监听 `127.0.0.1`。

3. **配置来源**：检查运行中容器实际收到的环境变量、挂载配置和连接串，而不是只看 `.env` 或 Compose 文件。重点排除变量未展开、旧容器未重建、开发配置覆盖生产式配置等情况。

4. **健康与就绪**：数据库进程 `started` 不等于可认证、可执行查询。`healthcheck` 应验证真实连接；应用启动依赖应等待 `service_healthy`，但仍须处理重试，因为健康检查不能替代业务初始化。

5. **权限与 SQL**：使用与应用相同的账号连接，验证目标库、schema、表及读写权限。健康状态为绿，仍可能是迁移未执行：卷保留了旧数据库，或初始化脚本只在空卷首次创建时运行。

6. **业务结果**：最后发起一次真实 API 请求，核对响应、数据库记录、消息或文件等副作用。若结果异常，再结合 `docker compose logs`、`docker compose exec` 与卷挂载状态定位：是请求未到达、SQL 未执行，还是执行后未正确提交。

> **要点** — Compose 排障应验证完整依赖链：日志可见只是起点，服务名、端口、配置、就绪和业务结果缺一不可。

命名卷让数据库文件脱离容器生命周期，但它只解决文件留存，不自动证明数据可恢复、消息可补偿或权限仍然有效。

### 命名卷与容器生命周期

### 命名卷与容器生命周期

容器、命名卷、数据库数据文件是三层不同对象：

- **容器**：运行数据库进程及其镜像配置的实例，例如 `postgres` 服务容器。删除或重建容器后，容器可写层通常随之消失。
- **命名卷**：由 Docker 管理、具有稳定名称的存储对象，例如 `postgres_data`。它独立于某一次容器创建。
- **数据库数据文件**：实际位于卷挂载目录中的文件，如 PostgreSQL 的`/var/lib/postgresql/data`。只要卷仍在，这些文件通常仍在。

典型 Compose 配置如下：

`postgres_data:/var/lib/postgresql/data`

当执行服务重建、升级镜像或 `docker compose up -d --force-recreate` 时，旧数据库容器会被替换，但新容器重新挂载同一个 `postgres_data`，因此数据库文件会被继续使用。换言之，**重建服务不等于清空数据库**。

但命名卷并非永久保险箱。以下操作可能删除数据卷及其中的数据文件：

- `docker compose down -v`
- `docker volume rm postgres_data`
- 清理未使用卷的 Docker 运维命令
- 改变 Compose 项目名、卷名或挂载声明，导致新容器挂载了另一个卷

因此，排障时应先确认“容器是否重建”和“卷是否仍是同一个卷”是两个问题。可用 `docker volume ls`、`docker volume inspect` 检查卷名和挂载关系。

命名卷只保证本机 Docker 存储层面的文件生命周期相对独立；它不自动证明事务完整、备份可恢复、消息可补偿，或访问 S3 等外部资源的权限仍有效。数据库文件留下来，不等于整个业务状态已经具备恢复能力。

### 何时数据会被保留或删除

### 何时数据会被保留或删除

命名卷把数据库文件从容器可写层中分离出来，因此“容器没了”通常不等于“数据库没了”。关键在于操作是否同时删除了卷。

| 操作 | 容器状态 | 命名卷中的数据库文件 |
|---|---|---|
| `docker compose stop` | 容器停止，仍可再次启动 | 保留 |
| `docker compose restart` | 容器重启 | 保留 |
| `docker compose up --force-recreate` | 旧容器被替换为新容器 | 保留，只要仍挂载同一命名卷 |
| `docker compose down` | 删除容器与网络 | 默认保留命名卷 |
| `docker compose down -v` | 删除容器、网络及声明的卷 | 删除，数据库文件随之丢失 |
| `docker volume rm 卷名` 或清理脚本 | 与容器是否存在无关 | 删除该卷及其全部文件 |

因此，服务重建、镜像升级或临时停止通常不会清空 DB；但“环境重置”、CI 清理、人工执行 `down -v`、删除卷或宿主机磁盘故障都可能造成不可逆删除。

还要区分“文件存在”和“业务可恢复”：卷保留了某一时刻的数据库目录，不等于事务完整、备份可用、消息可重放或权限仍有效。尤其当 B 离线 `25h` 而 broker 保留期仅 `24h` 时，缺失消息不能仅靠卷解决，仍需由 DB 历史、顺序号与 outbox 等权威记录补偿。

### 持久化不等于事务与备份

### 持久化不等于事务与备份

命名卷只能提供一类证据：数据库文件通常不随容器重建而消失。`docker compose up --force-recreate` 后，挂载同一命名卷的数据库仍可看到原有数据；但执行 `docker compose down -v`、手动删除卷，或宿主机磁盘损坏时，文件仍可能丢失。

因此，至少要区分四个层次：

- **磁盘文件持久化**：数据库目录位于命名卷中，容器删除不等于数据删除。这解决的是本地开发中“重建服务后数据还在”。
- **事务可靠性**：一次业务操作必须在数据库内部满足原子性、一致性与崩溃恢复。例如订单状态已提交而库存未扣减，不能仅因两张表都在卷里就被视为可靠；需要数据库事务、约束、隔离级别和提交语义作为证据。
- **备份与恢复能力**：卷中有文件不等于存在可用备份。必须证明可在指定时间点导出、保存副本，并在新实例中恢复和校验。可恢复性关注的是“原卷失效后能否重建”，而非“原卷尚未删除”。
- **跨环境迁移能力**：本机卷依赖本机 Docker、宿主机路径、数据库版本及权限配置。把卷直接搬到另一台机器未必可用；更稳妥的迁移证据通常是逻辑备份、迁移脚本、版本化 schema 与恢复演练。

同样，持久化也不能替代消息与权限证明。若服务 B 离线 `25h`，而 broker 仅保留消息 `24h`，即使 B 的数据库卷仍在，也不能从 broker 补到缺失事件；此时应由权威数据库历史、`outbox` 或其他可追溯记录支持补偿。未来接入 S3、m-9/seq9 等链路后，还需分别证明权威来源、顺序与访问权限，不能把“数据库文件还在”误写成“事务、备份和补偿都成立”。

### 离线用户的历史补偿边界

### 离线用户的历史补偿边界

设用户 B 离线了 $25$ 小时，而消息代理的消息保留期仅为 $24$ 小时。即使生产者曾成功发布消息、消费者也曾正常在线，B 重新连接时仍不能假定“从代理重放即可恢复全部历史”：最早的 $1$ 小时消息可能已经因保留策略到期而被清理。

消息代理适合承担**实时分发、短期缓冲与在线重试**，但不应被当作用户历史的唯一权威。应用需要把可见事件、会话消息或业务状态变更持久化到数据库，并以数据库中的权威记录作为补偿来源：

1. B 重连后携带最后确认的序号、时间戳或游标，如 `last_seq=120`。
2. 服务端先查询数据库中 B 有权访问且序号大于 `120` 的历史记录。
3. 按稳定顺序补发，例如按 `(created_at, id)` 或单调递增的 `seq` 排序。
4. 补偿完成后，再切换到代理的实时订阅；切换期间要处理去重与乱序。

这里的关键不是“数据库文件仍在命名卷中”，而是数据库是否保存了可查询的权威历史，以及补发查询是否重新执行权限判断。若历史只存在于代理中，`25h > 24h` 已足以造成不可恢复的缺口；若仅依赖 `down -v` 前后的卷存活，也无法证明事务完整、备份可用或对象存储中的附件仍可访问。

因此，代理保留期定义的是实时系统的补偿窗口；数据库历史、序列号与 outbox 机制才构成跨越该窗口的可靠补偿基础。

### 面向未来IM的权威数据验证

### 面向未来 IM 的权威数据验证

命名卷保存的是数据库文件，不是“未来 IM 一定正确”的证据。验证应按权威来源分层：对象存储确认附件，数据库确认消息历史，`outbox` 确认待投递事件，认证与授权系统确认当前权限。

假设用户 B 离线 `25h`，而 broker 的消息保留期仅为 `24h`。此时不能假设 B 重连后仍能从 broker 补到全部消息；服务端应以数据库中 `m-9` 及 `seq=9` 之后的历史为补偿依据：

1. **S3 层**：检查消息附件引用的对象是否存在、大小与校验值是否匹配；对象存在不代表消息对该用户可见。
2. **消息历史层**：以会话的单调序号查询 `seq > 9`，确认 `m-9` 之后的消息记录、发送时间、撤回状态与可见范围。
3. **Outbox 层**：检查这些消息对应的事件是否已发布、失败重试中或尚未投递。`outbox` 是“数据库提交后应传播什么”的权威记录，不应由日志或 broker 当前积压替代。
4. **权限层**：重新判定 B 当前是否仍是会话成员、是否被禁言、消息是否因删除或合规策略失效。历史存在也不能绕过当前授权。

可将恢复路径理解为：先通过权限过滤，再从数据库补齐 `seq > 9` 的权威历史；附件按需从 S3 获取；实时 broker 只承担在线增量。命名卷使上述数据库状态在容器重建后仍可能存在，但执行 `docker compose down -v`、卷损坏或错误迁移仍会破坏它，因此仍需独立备份、恢复演练与跨系统一致性校验。

> **要点** — 命名卷保存数据库文件，但业务可靠性仍需由事务、备份、权威历史、outbox与权限验证共同证明。

先用一张可审计的纸上清单固定本地环境事实，再隔离执行与分层验证，避免把“容器已启动”误判为业务已成功。

### 纸上清单：先固定可复现事实

### 纸上清单：先固定可复现事实

在执行任何 `Compose up` 之前，先写一张可审计的环境清单。它记录的是“此次实验应当是什么”，而不是终端里偶然出现过什么。清单至少覆盖：

- **镜像与版本**：服务镜像名、不可变 `digest`、构建来源；不要只写浮动标签如 `latest`。
- **项目与网络**：Compose 项目名、网络名、各服务在网络中的服务名；容器间应优先用服务名访问，而非宿主机端口。
- **端口边界**：分别列出“容器端口—宿主机映射端口—调用方实际地址”。例如 `$S2$` 可监听容器内 `8080`，但宿主机暴露为 `18080`。
- **生效配置**：配置文件路径、环境变量、默认值覆盖关系、关键回调地址与存储地址；以渲染后的 Compose 配置为准，而非只看模板。
- **就绪条件**：每个服务的 `healthcheck`、依赖条件、探针路径和预期状态。进程存活不等于服务已就绪。
- **日志与秘密**：日志位置、关联请求标识、脱敏规则；秘密只记录引用名或挂载路径，绝不抄入明文。
- **卷与持久化**：卷名、宿主机路径、读写方、初始化数据和清理策略，明确哪些数据跨重启保留。
- **正反业务样本**：预先定义成功请求及应有证据，也定义错误端口、错误凭据、未就绪调用等失败样本及预期错误。

随后将执行隔离在该项目名和网络内。`Compose up` 显示绿色，只能证明编排层已尝试启动；它不能证明 `$S2$` 返回 `200`、`$S3$` 已写入数据，或设备 `$B$` 已发送 ACK。即使固定两份 OpenIM 源码，也只固定了代码输入，仍须用网络、端口、日志与业务证据验证实际拓扑。

### 网络视角：服务名优先于端口与地址

### 网络视角：服务名优先于端口与地址

同一套 Compose 环境中，“地址能否访问”取决于请求从哪里发出。先区分三种视角，再决定该写 `localhost`、宿主映射端口，还是服务名。

| 发起位置 | 访问 `openim` 服务的推荐写法 | 原因 |
|---|---|---|
| 宿主机终端、浏览器、测试工具 | `http://localhost:映射端口` | 宿主机只能看到已发布的端口，例如 `"18080:8080"` 中的 `18080`。 |
| `openim` 容器自身 | `http://localhost:容器端口` | 此时 `localhost` 指向当前容器自己的网络命名空间。 |
| 同一 Compose 网络的其他容器 | `http://openim:容器端口` | `openim` 是网络内 DNS 服务名；容器间直接走内部端口，不经过宿主端口映射。 |

例如服务声明为 `openim`，容器内监听 `8080`，并发布 `"18080:8080"`。则宿主机调用 `localhost:18080`；`openim` 容器内可调用 `localhost:8080`；`gateway` 容器应调用 `openim:8080`，而不是 `localhost:18080`。

关键推导是：

$$\text{宿主映射端口仅属于宿主机入口，服务名属于容器网络入口}$$

因此，容器配置中的 `OPENIM_URL=http://localhost:18080` 往往是错误设计：它会把请求发回该容器自身，并不自动到达宿主机或另一服务。应在纸上清单记录“服务名—内部端口—宿主映射端口—调用方视角”，并在容器内用服务名验证 DNS 与连通性。即使 `docker compose up` 显示绿色，也只说明进程可能启动；仍需分别确认目标服务 health、接口返回，以及实际业务状态。

### 启动、健康与业务就绪的三层边界

### 启动、健康与业务就绪的三层边界

本地多服务环境中，`docker compose up` 显示绿色，只能说明某些容器进程已经被创建或仍在运行；它不能证明 OpenIM 的业务链路已经可用。应把以下三层状态严格分开记录和验证。

| 层次 | 典型机制 | 它能说明什么 | 它不能保证什么 |
|---|---|---|---|
| 启动顺序 | `depends_on` | Compose 先创建被依赖服务，再创建当前服务 | 被依赖服务是否已监听端口、迁移完成、可处理请求 |
| 健康门 | `condition: service_healthy` 与 `healthcheck` | 被依赖服务通过了指定探针 | 探针之外的真实业务路径、数据正确性、外部依赖可用性 |
| 业务就绪 | 真实读写、端到端请求、断言结果 | 服务能够完成目标业务操作 | 其他未覆盖场景仍可能失败 |

例如，`depends_on: [mongo]` 仅表达“先启动 MongoDB 容器”。MongoDB 进程可能仍在恢复数据、初始化副本集，或尚未接受认证连接。即使改为：

`depends_on: { mongo: { condition: service_healthy } }`

也只表示 MongoDB 的健康检查成功。若健康检查只是 `mongosh --eval 'db.runCommand({ ping: 1 })'`，它并未验证 OpenIM 使用的数据库名、账号权限、集合索引、初始化脚本和迁移版本。

因此，数据库的业务就绪应至少包含一次与目标服务相同配置的可执行操作，例如：使用实际连接串建立连接、读取所需集合、写入测试记录后再读取并清理。对于消息队列、对象存储和 Redis，也应采用对应的真实操作，而非只检查端口 `$host:$port` 可连接。

同样地，服务健康不等于业务成功：S2 返回 HTTP `200` 不等于 S3 已保存消息；S3 有日志也不等于 B 设备已收到 ACK。验证应沿链路逐层断言：入口响应、数据库状态、下游日志或事件、目标设备确认。固定两份 OpenIM 源码目录更不能自动证明它们处于预期网络拓扑；仍须核对项目名、网络服务名、解析结果、映射端口及双方实际连接日志。

### 配置、秘密、日志与卷的可追踪验证

### 配置、秘密、日志与卷的可追踪验证

配置追踪的目标不是“看到变量存在”，而是证明**运行中的服务确实使用了预期配置**，且秘密未进入镜像、终端回显或普通日志。纸上清单可为每个服务记录：

- 生效配置：配置文件路径、环境变量名、默认值、覆盖优先级与配置版本；
- 秘密引用：只记录 `DB_PASSWORD_FILE`、`OPENAI_API_KEY` 等引用名或挂载路径，不记录明文；
- 日志证据：启动时的配置摘要、依赖连接目标、请求标识、错误码；
- 数据卷：卷名、宿主机映射、容器内路径、初始化条件与应保留的数据；
- 业务样本：一条应成功的配置驱动请求，以及一条故意使用错误配置的失败请求。

验证时分层进行。先检查 Compose 渲染后的生效定义，确认服务名、环境变量来源、`secrets`/只读挂载和卷挂载均符合清单；再进入隔离环境查看**非敏感**配置摘要，例如数据库主机、端口、存储桶名、功能开关。若必须确认秘密可用，应以“认证成功/失败”的受控操作证明，禁止 `echo $PASSWORD` 或将完整环境输出到日志。

日志应能把一次业务请求关联到配置与依赖结果：`request_id`、目标服务名、重试次数、持久化记录标识均可记录；令牌、Cookie、连接串、身份证明和完整请求体不得记录。出现问题时，区分“变量未注入”“引用文件不可读”“服务读取了旧配置”“依赖认证失败”。

卷验证也不能只看“卷已创建”。重启容器后，检查预期记录是否仍在；更换空卷时，检查初始化是否符合设计。`compose up` 为绿色只说明编排启动，不能证明 S2 返回 200、S3 已存入对象，或另一设备已 ACK。

### 正反业务样本：拒绝绿色状态幻觉

### 正反业务样本：拒绝绿色状态幻觉

以未来教学 IM 的 `gateway`、数据库与消息代理为例，先把“当前连接结果”和“未来业务结果”拆开记录。`docker compose up -d` 显示绿色，只能说明 Compose 已尝试创建并启动容器；它不能证明网关已返回 S2 `200`、消息已进入 S3 持久化，更不能证明目标设备已 ACK。

| 层次 | 正样本：应观察到的证据 | 反样本：常见绿色幻觉 |
|---|---|---|
| 容器与网络 | `gateway`、`db`、`broker` 均运行；网关能以服务名连接 `db:端口`、`broker:端口` | 容器运行，但网关仍连接 `localhost`、错误项目网络或旧端口 |
| 就绪与配置 | health 通过；生效配置中数据库 DSN、代理地址、秘密引用均符合纸上清单 | health 仅检查进程存在；环境变量虽写入但应用未读取，或仍使用默认密码 |
| 网关接收 | 向网关提交合法请求，得到当前接口约定的成功响应，并在网关日志看到请求 ID | 端口可访问、返回 `200`，但请求只被 Web 层接受，未进入业务处理 |
| S2 业务确认 | 后续教学协议中的 S2 `200` 与同一请求 ID、会话和业务状态对应 | 把 HTTP `200`、反向代理 `200` 或 Compose 成功误当作 S2 `200` |
| S3 持久化 | 用受控查询或消费记录确认消息已写入数据库/存储，并可按消息 ID 找回 | 日志出现“发送成功”，实际事务回滚、写入副本或仅停留在内存 |
| 设备投递 | 模拟设备在线，记录 ACK、设备 ID 与消息 ID 的对应关系 | 代理已接收消息，却无订阅者、ACK 超时或 ACK 属于另一设备 |

可设计一组故障注入：让数据库密码错误、代理服务名拼错、设备离线。预期是容器可能仍为绿色，但健康检查、请求链路、持久化或 ACK 分别失败。固定 OpenIM 两份源码也不证明拓扑正确；只有服务名解析、端口连通、生效配置、日志关联和分层业务证据共同成立，才可声明相应层级成功。

> **要点** — Compose 绿色只证明部分基础设施状态；服务名、就绪证据与业务结果必须分层核验。

用一套纸上 Compose 环境建立正确心智模型：服务如何互相定位、何时真正可用、配置从哪里生效，以及如何在不泄露敏感信息的前提下完成分层验收。

### 三种网络视角与端口映射

### 三种网络视角与端口映射

同一套 Compose 环境中，`localhost` 的含义取决于“谁在发起连接”。先区分三个视角：

- **宿主机视角**：宿主机访问映射出来的端口。例如：

  `ports: ["15432:5432"]`

  表示宿主机可用 `localhost:15432` 访问数据库；左侧 `15432` 是宿主端口，右侧 `5432` 是容器端口。

- **容器自身视角**：容器内的 `localhost` 只指向**该容器自己**。应用容器若连接 `localhost:5432`，是在寻找应用容器内部的 PostgreSQL，而不是名为 `db` 的数据库容器。

- **同一 Compose 网络中的其他服务视角**：服务应通过服务名和容器端口通信，例如应用连接 `db:5432`。Compose 会为服务名提供内部 DNS；即使数据库容器重建、IP 改变，`db` 仍会解析到当前实例，不应把容器 IP 写进配置。

因此，下面两条连接字符串服务于不同边界：

- 在宿主机运行迁移工具：`postgres://...@localhost:15432/...`
- 在 `api` 容器中连接数据库：`postgres://...@db:5432/...`

`ports` 是“容器—宿主机”的发布规则，不是容器之间互联的前提。同一 Compose 网络内，`api` 即使看不到数据库的宿主端口，仍可直接访问 `db:5432`。反过来，若数据库只供内部服务使用，通常无需发布 `15432:5432`，可减少宿主机暴露面。

验收时分别确认：宿主机连接使用 `localhost:15432`；容器内配置使用 `db:5432`；任何容器间配置都不依赖固定 IP 或宿主映射端口。

### 服务名定位：DNS 稳定而 IP 可变

### 服务名定位：DNS 稳定而 IP 可变

在 Compose 网络中，服务之间应使用**服务名加容器端口**定位，而不是写死容器 IP。例如应用连接 PostgreSQL 时应使用：

`db:5432`

其中 `db` 是 Compose 服务名，`5432` 是数据库在容器网络内监听的端口。Compose 会为同一网络中的服务提供内部 DNS：应用查询 `db` 时，DNS 返回当前 `db` 容器的内部 IP。

这与从宿主机访问不同。若配置为：

`15432:5432`

则含义是：

- 容器内其他服务访问数据库：`db:5432`
- 宿主机上的本地客户端访问数据库：`localhost:15432`
- 容器内不能把 `localhost:15432` 当作数据库地址

原因是容器中的 `localhost` 只指向**当前容器自身**。例如 `api` 容器访问 `localhost:5432`，实际是在寻找 `api` 容器自己的 5432 端口，而不是 `db`。

容器 IP 不应成为配置合同。`db` 重建、扩缩容或重新接入网络后，IP 可能变化；服务名仍是稳定的逻辑身份。应用应在建立新连接时通过 DNS 解析 `db`，避免把旧 IP 写入环境变量、配置文件或代码。若客户端长期缓存 DNS 结果或保持失效连接，数据库重建后仍可能短暂失败，因此还应具备连接重试、超时和重连机制。

可将地址选择理解为两套边界：

- **宿主机边界**：`localhost:宿主机映射端口`
- **Compose 网络边界**：`服务名:容器端口`

验收时确认：`api` 的数据库配置是 `db:5432`，开发者本机工具使用 `localhost:15432`；两者不是可互换的写法。

### 启动、健康与业务就绪的边界

### 启动、健康与业务就绪的边界

`depends_on` 首先解决的是**启动顺序**：例如应用依赖数据库时，Compose 可先创建并启动 `db`，再启动 `api`。但“容器已启动”通常只表示主进程已经被拉起，不表示 PostgreSQL 已完成恢复、建库、执行初始化脚本，更不表示业务所需表、迁移版本和账户权限都已满足。

为依赖方增加 `condition: service_healthy` 后，`api` 会等待 `db` 的健康检查通过。例如数据库探针可执行：

`pg_isready -U app -d appdb`

这比仅等待容器启动更可靠：它至少表明数据库正在接受连接请求。不过，健康探针仍只是一个**局部、短时的可观测信号**，不能自动证明完整业务就绪。

常见边界如下：

- `depends_on`：保证创建/启动的先后关系；不等待端口可连接。
- `service_healthy`：等待被依赖服务的 `healthcheck` 成功；其语义完全取决于探针写了什么。
- 业务就绪：应用实际执行关键操作后确认，例如连接 `db:5432`、读取必需配置、检查迁移表版本、查询关键数据或执行最小读写。

因此，即使 `db` 显示健康，`api` 仍可能因迁移尚未完成、初始化数据缺失、凭据错误或网络瞬断而失败。更稳妥的合同是：数据库提供健康探针；应用在启动阶段实现连接重试与迁移确认；验收时查看应用日志，确认其已成功连接服务名 `db:5432`，而不是把宿主机映射端口 `localhost:15432` 误当作容器间地址。

### 配置链路：插值、生效环境与秘密保护

### 配置链路：插值、生效环境与秘密保护

Compose 中最容易混淆的是：**变量用于渲染 Compose 文件**，不等于**变量一定进入容器运行时环境**。应将链路拆成两层。

- `.env`：通常供 Compose 做 `${变量}` 插值；也可被 `env_file` 显式导入容器。
- 宿主环境：运行 `docker compose` 的 shell 中已导出的变量，通常可覆盖 `.env` 中同名值。
- `compose.yaml`：插值后生成最终服务定义；例如 `ports: ["${DB_PORT:-15432}:5432"]`。
- 容器环境：只有 `environment:`、`env_file:` 或镜像自身 `ENV` 提供的变量会真正被进程读取。

例如：

```yaml
services:
  api:
    environment:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/app
```

这里 `${DB_PASSWORD}` 在启动前由 Compose 渲染；容器最终拿到的是完整的 `DATABASE_URL`。若宿主 shell 已执行 `export DB_PASSWORD=prod-value`，它通常优先于 `.env` 中的同名值。因此验收配置时，应区分“渲染值来自哪里”和“进程实际收到什么”。

可用 `docker compose config` 检查插值后的结构，但它可能展开密码、令牌和连接串，**不得直接贴入工单、终端录屏或共享日志**。同样，`printenv`、应用启动时打印全部配置、异常栈回显连接串，都会造成 secret 泄露。

更稳妥的做法是：

- `.env` 仅保存本地开发值，并加入 `.gitignore`；提交 `.env.example`，只保留变量名和非敏感示例。
- 密码、令牌优先通过秘密文件、部署平台的密钥注入或受控环境变量提供，而非写死在 YAML、镜像层或 volume 中。
- 日志只确认“变量已配置”“数据库连接成功”，不要输出变量值、`Authorization` 头、完整 `DATABASE_URL`。
- 对配置变更做分层确认：S2 检查 Compose 渲染与容器环境是否符合预期；S3 验证应用确实能以该配置连接 `db:5432`；B 确认日志、配置导出和仓库历史均未暴露秘密。

### 分层验收：卷、日志与 IM 业务合同

### 分层验收：卷、日志与 IM 业务合同

本地多服务环境不能只看“容器都启动了”。应按三层验收，把存储、运行证据与未来 IM 合同分开确认。

- **基础设施层：卷是否真的持久化。** 数据库应挂载命名卷，而不是依赖容器可写层。例如删除并重建 `db` 容器后，创建过的测试表或记录仍存在，才说明卷生效。注意：`docker compose down` 通常保留卷，`docker compose down -v` 会删除命名卷；后者只能用于明确允许清空数据的场景。卷名、挂载路径和初始化脚本共同构成数据合同。

- **服务连通性层：日志是否能解释状态。** 应分别检查应用与数据库日志，而非只看编排器输出。应用容器连接数据库时应使用 `db:5432`；宿主机调试工具才使用 `localhost:15432`。日志中应能看到 DNS 解析、连接成功、迁移完成或失败原因。不要把密码、令牌、完整连接串写入日志；环境变量插值后的敏感值同样属于 secret，日志应仅记录脱敏后的配置来源或连接目标。

- **业务合同层：为 IM 预留可验证边界。** 即使 S2/S3 尚未实现，也应确认服务能以稳定配置启动、存储可复用、日志可追踪，并定义未来接口所需的最小合同：用户身份、会话或频道标识、消息内容、时间戳、幂等键及持久化结果。可以将验收写成：  
  `B：卷重建后数据仍在；S2：服务可通过服务名访问依赖；S3：健康后可执行一次真实读写。`

其中，`depends_on` 只约束启动顺序；若依赖“可用”，必须结合 `service_healthy` 与实际探针验证。健康检查也只是有限信号：端口可监听不等于迁移完成、权限正确或 IM 消息合同已满足。

> **要点** — 本地多服务环境的关键是按网络视角定位、按就绪层级验收，并让配置与持久化合同可追踪。
