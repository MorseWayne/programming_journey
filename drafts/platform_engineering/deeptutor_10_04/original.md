## 10.04 测试替身与设计：控制依赖，验证消息规则

- 用输入、状态和外部依赖区分被测行为与替身职责

从消息字节、重复ID与本地CLI出发，先划清被测行为和外部依赖，才能让测试既稳定又能提供可信证据。

### 识别被测对象与可观察结果

### 识别被测对象与可观察结果

测试先回答一个边界问题：**究竟要证明谁的行为正确？** 被测对象（SUT，System Under Test）是本次测试直接验证的代码单元；它不一定是一个函数，也可以是一个服务方法或命令执行流程。

例如，虚构的消息历史写入规则是：

- 消息按收到的原始字节保存；
- `ID` 已存在时拒绝重复写入；
- 写入成功后可查询到该消息。

此时可把 `Append` 视为 SUT：

```go
err := history.Append(Message{
    ID:   "m-17",
    Body: []byte{0x41, 0x00, 0x42},
})
```

这里应清楚区分五类事物：

- **输入**：`Message` 的 `ID` 与 `Body`，包括不能随意转成字符串的原始字节。
- **初始状态**：历史是否为空，或其中是否已存在 `"m-17"`。
- **SUT**：实施“检查重复 ID 并写入”的 `Append` 规则。
- **协作者**：文件、数据库、时钟、日志器等由 SUT 调用的外部对象；它们不是本测试要证明的业务规则。
- **可观察结果**：返回的 `err`、写入后的历史状态，以及必要时协作者收到的调用消息。

对空历史，测试可用 got/want 断言成功状态：

```go
want := []byte{0x41, 0x00, 0x42}
got, err := history.Get("m-17")
// 断言 err 为 nil，got 与 want 字节完全相等
```

对已有 `"m-17"` 的历史，重点不是“文件有没有被打开”，而是重复规则的结果：`Append` 返回重复 ID 错误，且历史条目数和原有字节保持不变。这样，返回值与状态共同构成证据。

纯函数通常只有“输入 → 输出”，可直接比较 got/want；一旦涉及文件、stdout/stderr 或当前时间，就要额外定义边界后的可观察结果。测试不应猜测内部实现，而应验证调用者真正能看到的返回、状态变化和对外消息。

### 依赖为何会破坏测试稳定性

### 依赖为何会破坏测试稳定性

纯函数只依赖参数，结果也只由参数决定；同一输入应得到同一输出。例如消息字节解析与重复 ID 判定可以直接写成：

`got := IsDuplicate(seen, msg.ID)`

测试只需准备 `seen`、消息和 `want`，再比较 `got/want` 或调用后的状态。它不读磁盘、不看时钟、不写终端，因此运行快，失败原因通常也集中在业务规则。

相对地，依赖外部环境的代码会把不可控因素带进测试：

| 依赖 | 不稳定或变慢的来源 | 难以验证的行为 |
|---|---|---|
| 文件 | 路径、权限、遗留文件、磁盘速度 | 文件不存在、写入失败、内容损坏 |
| 当前时间 | 测试执行时刻、时区、跨秒或跨日 | “刚过期”“恰好到期”等边界 |
| `stdout`/`stderr` | 全局输出混杂、并发测试交错 | 是否输出正确提示或错误信息 |
| 外部存储 | 网络、服务状态、残留数据、响应延迟 | 超时、拒绝连接、保存失败 |

例如 CLI 直接调用 `time.Now()`、读取真实配置文件并 `fmt.Println`。测试不仅要构造消息字节和重复 ID，还要安排临时文件、捕获输出，并接受“现在到底是什么时间”的影响；若要证明写文件失败时是否向 `stderr` 报错，真实磁盘又未必容易稳定地产生该故障。

这里的被测对象（SUT）是要验证的业务行为，如“重复 ID 被拒绝”。文件、时钟、输出流和存储是协作者；它们与 SUT 相接的位置是边界。测试应优先观察边界可见的结果：返回值、错误、状态变化，以及写入到提供的输出或存储中的消息。把协作者替换为可控制的替身，才能稳定地制造成功、失败和边界条件。

### 用小接口划定协作边界

### 用小接口划定协作边界

被测对象（SUT）不应直接依赖“整个文件系统”或“真实时钟”，而应只声明自己实际消费的能力。假设 CLI 接收消息字节，拒绝重复 ID，并在保存时记录当前时间；它真正需要的协作者能力只有两项：

- 按 ID 查询是否已存在，并保存消息；
- 读取当前时间。

不要为了“方便”把庞大的具体类型传进来。例如 `*os.File`、数据库客户端或全局 `time.Now` 会把打开文件、网络、权限、真实时间等细节带入测试边界。

```go
type 消息存储 interface {
    查找(id string) (消息, bool, error)
    保存(消息) error
}

type 时钟 interface {
    现在() time.Time
}

type 服务 struct {
    存储 消息存储
    时钟 时钟
}

func 新服务(存储 消息存储, 时钟 时钟) *服务 {
    return &服务{存储: 存储, 时钟: 时钟}
}
```

接口应由消费方推导，而不是照着某个基础设施实现照搬。若 SUT 只调用 `查找`、`保存` 与 `现在`，接口就不应额外暴露删除、列举目录、关闭连接或调整时区等方法。这样，边界清楚地落在“消息规则”与“外部效果”之间：

- SUT：验证消息字节、检查重复 ID、决定成功或失败结果；
- 存储协作者：提供已有状态并接收待保存消息；
- 时钟协作者：提供可控的当前时刻；
- 可观察结果：返回错误、保存调用及其参数、最终状态。

构造参数注入使测试可替换协作者：存储替身预置重复 ID，时钟替身固定返回某个时刻。于是仍可使用 `got/want` 断言返回值和状态，并进一步验证“重复 ID 时未保存”“成功时保存的时间等于固定时间”。真实文件与真实时间只留给少量集成测试。

### 围绕重复ID建立断言证据

### 围绕重复ID建立断言证据

重复 `ID` 不是只检查“返回了错误”即可；还要证明失败请求没有污染既有消息历史。这里的被测对象（SUT）是 `Append`，消息仓库是协作者，而消息切片与错误值都是可观察结果。

```go
type Message struct {
	ID   string
	Body []byte
}

type Store struct {
	history []Message
}

func (s *Store) Append(m Message) error {
	for _, old := range s.history {
		if old.ID == m.ID {
			return ErrDuplicateID
		}
	}
	s.history = append(s.history, m)
	return nil
}
```

测试先写入一条基线消息，再尝试写入相同 `ID`、不同字节内容的消息。不同内容很重要：它能排除“实现偷偷覆盖旧消息”的情况。

```go
func TestAppend_重复ID返回错误且不改历史(t *testing.T) {
	sut := &Store{}
	first := Message{ID: "m-1", Body: []byte("hello")}
	dup := Message{ID: "m-1", Body: []byte("changed")}

	if err := sut.Append(first); err != nil {
		t.Fatalf("初次写入错误: %v", err)
	}

	err := sut.Append(dup)
	if !errors.Is(err, ErrDuplicateID) {
		t.Fatalf("重复ID错误 = %v，want ErrDuplicateID", err)
	}

	got := sut.history
	want := []Message{{ID: "m-1", Body: []byte("hello")}}
	if diff := cmp.Diff(want, got); diff != "" {
		t.Fatalf("消息历史不应改变，(-want +got):\n%s", diff)
	}
}
```

这组证据包含三层：错误断言证明请求被拒绝；`got/want` 比较证明历史仍是原消息字节；状态断言隐含验证长度未增加。若只断言 `err != nil`，即使实现先追加、后报错，测试也可能错误通过。

### 替身职责与集成证据分层

### 替身职责与集成证据分层

先区分两类证据：**局部规则证据**证明某个规则写对了；**集成证据**证明真实边界能协同工作。前者应快、稳定、可精确构造失败；后者应覆盖文件、命令行参数、`stdout/stderr` 等真实路径。

设 SUT 是“接收消息并按 ID 去重”的服务，协作者是消息仓库。若核心规则可写成纯函数，例如：

`接受 = 消息字节合法 && ID 尚未出现`

则直接传入字节、已有 ID 集合，按 10.02 的 `got/want` 与状态断言测试即可，无需替身。

当 SUT 需要访问协作者时，可选替身承担不同职责：

- **fake**：可工作的轻量实现，例如内存仓库 `map[string][]byte`。它最适合预览真实行为：首次写入成功，重复 ID 返回“已存在”，并可断言最终内存状态。
- **stub**：按预设返回值响应，例如固定让 `Load(id)` 返回“未找到”或磁盘错误。它用于验证 SUT 遇到边界失败时的返回错误和状态。
- **spy**：除提供行为外，还记录调用，如记录 `Save` 收到的消息字节。它用于验证可观察消息：传出的 ID、字节内容、调用次数。
- **mock**：预先声明期望交互，例如“必须调用一次 `Save`，且参数为某消息”。它适合协议本身就是规则时；不要为内部实现细节强行设期望，否则重构会造成脆弱测试。

局部测试可用 fake 加 stub 覆盖“重复 ID 不再写入”“存储失败不改变状态”等规则。它们不能证明真实文件权限、路径处理或 CLI 输出正确。因此还应保留少量本地文件集成测试：在临时目录创建输入文件，运行 CLI，检查退出结果、文件内容及 `stdout/stderr`。时间则应经由可注入时钟控制，避免直接依赖当前时间。

> **要点** — 测试先验证业务结果，再以小接口控制协作者；替身应降低不确定性，而非复制业务实现。

当构造函数直接打开文件并读取当前时间时，业务规则会被环境绑住；参数注入让依赖、状态与责任重新可见。

### 从隐式环境依赖识别测试障碍

### 从隐式环境依赖识别测试障碍

若构造函数内部直接调用 `os.Open` 和 `time.Now`，它表面上是在“初始化对象”，实际却同时承担了三类责任：

- **接收业务输入**：例如消息内容、用户标识；
- **读取外部环境**：文件是否存在、文件内容、权限、路径；
- **生成运行时状态**：当前时间、时区、时钟精度。

这会让测试无法只描述业务规则。假设规则是“每条消息追加到历史记录，并记录创建时间”。若构造函数自行打开历史文件、自己读取当前时间，测试必须先创建临时文件，安排初始内容，并接受一个不可预测的时间戳。失败时也难以判断：是追加规则错了，文件读取错了，还是环境状态不同？

```go
func NewService(path string) (*Service, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	return &Service{
		history: load(f),
		now:     time.Now(),
	}, nil
}
```

这里的 `path` 看似是输入，但真正影响结果的还有文件系统和系统时钟；它们没有出现在函数合同中，却参与了对象状态的形成。这类依赖称为**隐式环境依赖**。

尤其是消息历史规则常需要验证顺序、数量、时间和错误处理。例如“保存失败时不得把消息标记为已追加”。若 `Save`、当前时间和既有历史都由对象偷偷获取，测试只能间接观察最终文件，无法稳定构造“保存失败”“固定时刻”“已有两条历史”等条件。

识别信号很简单：构造函数或业务方法中出现文件、网络、数据库、随机数、时钟、全局变量等调用时，先问一句：**这是真正的业务输入，还是未声明的环境依赖？** 后者通常应被显式传入，才能让规则在测试中被精确控制。

### 以消费方接口收紧协作边界

### 以消费方接口收紧协作边界

`AppendHistory` 并不关心“仓储”还能删除、分页、建索引还是迁移数据；它只需要把一条消息保存下来。若直接依赖一个庞大的 `Repository` 接口，业务代码会被迫知道无关能力，测试替身也必须实现大量用不到的方法。

应从消费方的真实需求反推最小方法集合：

```go
type Message struct {
	UserID string
	Text   string
	At     time.Time
}

type Store interface {
	Save(Message) error
}

type Service struct {
	store Store
	now   func() time.Time
}

func (s Service) AppendHistory(userID, text string) error {
	msg := Message{UserID: userID, Text: text, At: s.now()}
	return s.store.Save(msg)
}
```

这里 `Store` 定义在使用它的业务侧：`Service` 的合同是“给我一个能保存 `Message` 的对象”。具体实现无需声明“我实现了 Store”；只要拥有签名完全一致的 `Save(Message) error` 方法，就隐式满足该接口：

```go
type FileStore struct{ /* ... */ }

func (f *FileStore) Save(m Message) error {
	// 写入文件；失败时返回写入错误
	return nil
}
```

测试中只需一个记录输入的替身：

```go
type memoryStore struct{ saved []Message }

func (m *memoryStore) Save(msg Message) error {
	m.saved = append(m.saved, msg)
	return nil
}
```

若 `AppendHistory` 还必须先查询历史，再决定是否追加，可以将合同扩展为恰好所需的 `Find`：

```go
type Store interface {
	Find(userID string) ([]Message, error)
	Save(Message) error
}
```

不要因为底层实现有十个方法，就把十个方法都放进接口。接口描述的是调用者所需的消息，而非提供者全部能力；也不必给每个函数都造接口。只有存在替换实现、隔离外部环境或明确协作边界时，小接口才值得引入。

### 用构造参数显式注入消息服务依赖

### 用构造参数显式注入消息服务依赖

将“现在几点”和“如何保存”作为构造参数交给服务，而不是在方法中调用 `time.Now()`、打开文件或连接数据库。这样，`AppendHistory` 的合同就很清楚：成功时追加一条带时间戳的消息；保存失败时返回错误，且不承诺状态已更新。

```go
type Message struct {
	Text string
	At   time.Time
}

type Store interface {
	Save(Message) error
}

type Service struct {
	store Store
	now   func() time.Time
}

func NewService(store Store, now func() time.Time) *Service {
	return &Service{store: store, now: now}
}

func (s *Service) AppendHistory(text string) (Message, error) {
	if text == "" {
		return Message{}, errors.New("消息不能为空")
	}

	msg := Message{
		Text: text,
		At:   s.now(),
	}
	if err := s.store.Save(msg); err != nil {
		return Message{}, fmt.Errorf("保存历史消息: %w", err)
	}
	return msg, nil
}
```

这里的 `Store` 由消费方定义，只包含服务真正需要的 `Save`，不应把创建、删除、统计等无关仓储方法一起塞入接口。任何拥有 `Save(Message) error` 方法的类型都会隐式实现它，无须声明“实现了 Store”。

生产环境可传入真实仓储和 `time.Now`：

```go
svc := NewService(fileStore, time.Now)
```

测试则传入内存替身与固定时钟：

```go
svc := NewService(memStore, func() time.Time {
	return time.Date(2025, 1, 1, 0, 0, 0, 0, time.UTC)
})
```

因此测试验证的是消息内容、时间和保存调用，而非文件系统或真实时钟的偶然行为。

### 把读写流视为标准库自然边界

### 把读写流视为标准库自然边界

业务代码若直接调用 `os.Open`、`os.Create`，就同时承担了文件路径、权限、关闭时机和操作系统错误等环境责任。更稳妥的边界是接收 `io.Reader` 与 `io.Writer`：前者提供字节输入，后者接收字节输出；至于数据来自文件、网络还是内存，由调用方决定。

```go
func AppendHistory(in io.Reader, out io.Writer, store Store) error {
	data, err := io.ReadAll(in)
	if err != nil {
		return fmt.Errorf("读取消息失败: %w", err)
	}

	msg := Message{Body: strings.TrimSpace(string(data))}
	if msg.Body == "" {
		return errors.New("消息不能为空")
	}
	if err := store.Save(msg); err != nil {
		return fmt.Errorf("保存消息失败: %w", err)
	}

	_, err = fmt.Fprintf(out, "已保存：%s\n", msg.Body)
	return err
}
```

生产环境可以传入打开后的文件：

```go
in, _ := os.Open("message.txt")
defer in.Close()
err := AppendHistory(in, os.Stdout, store)
```

测试则无需创建临时文件。`strings.Reader` 提供可控输入，`bytes.Buffer` 保留可断言的输出证据：

```go
var out bytes.Buffer
err := AppendHistory(strings.NewReader("学习 Go"), &out, fakeStore)

if err != nil { t.Fatal(err) }
if got := out.String(); got != "已保存：学习 Go\n" {
	t.Fatalf("输出为 %q", got)
}
```

这里验证的是局部合同：输入为空应失败，保存失败应向上传递，成功时应写出确认信息。`Reader`、`Writer` 是标准库已建立的最小能力接口；只有当函数确实依赖“读”或“写”这一能力时才引入它们，而不必为每个参数抽象接口。

### 选择适度注入而非框架化抽象

### 选择适度注入而非框架化抽象

参数注入不等于必须引入依赖注入容器。Go 中最常见、也最清晰的方式，是在构造函数或函数参数中显式传入依赖：

```go
type Service struct {
    store Store
    now   func() time.Time
}

func NewService(store Store, now func() time.Time) *Service {
    return &Service{store: store, now: now}
}
```

生产环境传入真实的 `Store` 与 `time.Now`；测试传入内存仓储和固定时间函数。依赖来源、生命周期与替换点都直接可见，通常无需反射、注册表或全局容器。

容器更适合依赖层级很深、组件数量很多，且创建规则需要统一管理的程序，例如大型服务进程的启动装配。但它也可能把“对象依赖什么”隐藏到配置之外：缺失依赖往往在运行时才暴露，阅读一个构造函数也无法立刻知道其真实需求。对多数 Go 服务而言，在 `main` 或初始化函数中完成装配即可。

接口同样应当按边界创建，而非成为每个函数的装饰。若服务只需保存消息，就定义最小能力：

```go
type Store interface {
    Save(Message) error
}
```

不要为了“通用”暴露 `Find`、`Delete`、`List` 等未被该消费者使用的方法。只有依赖存在可替换实现、外部副作用或高业务风险时，接口才带来明确收益；纯计算函数、稳定的数据结构和仅有一种实现的内部协作，直接使用具体类型通常更简单。

标准库已经展示了这种适度抽象：函数接收 `io.Reader`、输出写入 `io.Writer`，测试时自然用 `strings.Reader` 和 `bytes.Buffer` 替换文件、网络或终端。抽象应贴近真正需要控制的边界，而不是先建立框架，再寻找其用途。

> **要点** — 将时间、存储和读写边界作为显式依赖注入，以消费方小接口隔离环境，才能让消息规则的状态与错误合同可验证。

测试替身不是测试技巧清单，而是为消息规则隔离依赖、收集恰当证据的设计选择。

### 测试替身：以职责而非名称界定

### 测试替身：以职责而非名称界定

测试替身（test double）是对真实协作者的替代物这一**总称**。Fowler 借用电影替身的比喻，强调它让被测对象可以在不依赖真实数据库、网络服务或时钟的条件下运行；Meszaros 则进一步按替代物在测试中承担的职责区分类型。关键不在于给对象贴上某个标签，而在于说清：它替代了谁、提供什么行为、测试据此获得什么证据。

常见职责可概括为：

- **dummy**：仅为满足参数、构造或类型要求而传入，通常不应真正参与计算。
- **stub**：对查询提供预先安排的回答，例如“库存查询始终返回 `3`”。
- **fake**：具有可工作的简化实现，例如内存中的 `OrderStore`；它可证明读写逻辑与该内存语义一致，却**不能证明**文件落盘、事务、索引或真实数据库配置正确。
- **spy**：除提供必要行为外，还记录收到的调用，供测试随后断言，例如记录发送过哪些通知。
- **mock**：预先声明期望的消息、参数、次数或顺序，并由对象主动验证交互是否符合期待。

因此，测试可以验证两类证据：

| 验证方式 | 关注点 | 典型替身 | 能证明 | 不能证明 |
|---|---|---|---|---|
| 输出/状态验证 | 返回值、最终状态、副作用结果 | stub、fake、spy | 业务规则产生了预期结果 | 未观察到的内部消息细节 |
| 交互验证 | 向协作者发送了什么消息 | mock、spy | 必要协作是否发生且符合协议 | 整个外部系统真实执行成功 |

术语在不同社区常被宽泛使用：有人把所有可配置替代物都称为 mock，也有人把记录调用的对象称作 spy mock。比起争论名称，更准确的表述是：“这是一个返回固定费率的替身”“这是一个记录 `send` 调用的替身”“这是一个预设 `save` 必须调用一次的交互替身”。职责、可观察行为与断言方式，才是测试设计真正需要交流的内容。

### 五类对象及其可提供的证据

### 五类对象及其可提供的证据

`test double` 是测试中替代真实协作者的总称。Fowler 与 Meszaros 的分类关注其**行为及可形成的证据**；社区术语常有宽泛用法，因此测试应明确说明替身“返回什么、记录什么、期待什么”，而非只贴标签。

| 类型 | 行为与典型用途 | 能证明 | 不能证明 |
|---|---|---|---|
| dummy（哑对象） | 仅为满足参数、构造或类型要求；通常不应被使用 | 被测路径不依赖该参数的实际行为 | 任何业务协作、调用细节 |
| fake（伪实现） | 有可工作的简化实现，如内存消息存储、内存仓库 | 读取、写入、查询等业务规则在该存储语义下成立；可配合状态断言 | 数据确实写入文件、数据库事务与索引正确、跨进程持久性 |
| stub（桩） | 按预设条件返回固定数据或抛出指定异常 | 被测对象面对某个响应、失败或边界值时的输出/状态 | 协作者是否真的完成该行为；调用次数和顺序 |
| spy（间谍） | 正常或简化地响应，同时记录调用参数、次数、顺序 | 测试后可核对实际发出的消息 | 预先阻止错误交互；协作者真实外部效果 |
| mock（模拟对象） | 测试前声明交互期待，结束时验证是否满足 | 必要消息是否以约定参数、次数、顺序发送 | 最终状态本身是否正确；真实协作者的实现正确性 |

状态验证关注“执行后得到什么”：例如向内存消息存储发布后，断言其中存在正确主题和载荷。交互验证关注“向谁发送了什么消息”：例如断言失败时通知器收到一次 `send(alert)`。前者通常更贴近可观察结果；后者适合消息规则本身就是契约、且不应暴露内部状态的场景。

优先选用真实的简单对象或内存 fake：它既减少对实现细节的耦合，也能提供可检查的状态证据。仅当依赖位于慢、昂贵、随机、不可控的外部边界——如网络、时钟、支付服务或文件系统——再以 stub、spy 或 mock 精确控制该边界。

### 消息历史规则：状态验证与交互验证

### 消息历史规则：状态验证与交互验证

设需求为：用户发送消息后，系统应写入历史记录，并通知外部服务。它其实包含两类可观察规则：

1. **结果规则**：历史中出现一条内容、发送者、时间正确的消息。
2. **协作规则**：系统向通知服务发送了恰当的通知，且不应重复通知或越过该服务直接操作其内部资源。

状态验证关注执行后的输出或可见状态：

```text
发送消息 → 查询历史 → 断言新增消息存在且字段正确
```

若使用内存消息仓库 `InMemoryMessageStore`，测试证明的是“应用能通过仓库接口保存并读回历史”。它通常比模拟仓库更接近真实使用方式，也能覆盖查询、排序、重复写入等行为；但不能证明文件格式、数据库事务、网络连接或实际持久化配置正确。

交互验证关注对象间的消息历史：

```text
发送消息 → 断言 notifier.notify(message) 被调用一次
```

这适合外部通知服务：真实调用可能慢、收费、不可控，且其效果未必能在测试中可靠查询。模拟对象可预设期待：调用的方法、参数、次数与顺序；间谍对象则先记录调用，再由测试断言。

| 需求 | 优先选型 | 能证明 | 不能证明 |
|---|---|---|---|
| 写入后可读取历史 | 真实简单对象或内存实现 | 业务状态与仓库协议配合 | 文件/数据库持久性 |
| 通知被正确请求 | 间谍或模拟对象 | 调用参数、次数、顺序 | 外部服务实际送达 |
| 通知后的最终效果 | 受控集成测试 | 端到端可见结果 | 所有生产环境故障 |

因此，先问“用户最终能看到什么状态”，再问“是否存在必须遵守的协作边界”。仅验证调用会把实现细节误当需求；仅验证状态又可能漏掉必须通知的外部契约。术语可宽泛，但测试应明确说明替身记录了什么、预设了什么，以及证据覆盖到哪里。

### 从依赖边界选择最小替身

### 从依赖边界选择最小替身

测试替身的选择不应从“我会不会用 mock 框架”开始，而应从两件事开始：该依赖是否构成慢、易变、不可控的边界；本测试究竟需要证明结果，还是证明消息规则。Fowler 与 Meszaros 将 dummy、fake、stub、spy、mock 统称为 test double；社区用词常有宽泛化，因此应明确其行为，而非只报名称。

优先保留真实但简单的对象，例如值对象、纯函数、领域集合；若需要存储协作，优先使用内存实现。只有跨越数据库、文件系统、网络、时钟、第三方服务等外部边界，或必须验证调用协议时，才引入更窄的替身。

| IM 需求 | 依赖选型 | 能证明 | 不能证明 |
|---|---|---|---|
| 只关心计算结果 | 真实简单对象 | 输入到输出的业务规则 | 外部协作是否发生 |
| 需要查询结果但不关心过程 | stub：固定返回 | 分支、异常与结果组装 | 是否以正确参数调用依赖 |
| 需要可运行的存储语义 | fake：内存 store | 保存、查询、更新等应用内语义 | 文件格式、事务、真实数据库持久性 |
| 需要事后检查调用 | spy：记录调用 | 调用次数、参数、顺序 | 未记录的外部真实效果 |
| 协议本身是规则 | mock：预设交互期待 | 必须发送的消息及其顺序 | 更广泛的最终状态或真实集成行为 |

例如，订单服务写入仓储后返回订单，可用内存仓储验证“订单能被取回”；这通常比 mock 更贴近可观察结果。但若规则是“库存不足时绝不能调用支付网关”，则 spy 或 mock 能直接提供交互证据。注意：内存 store 只能证明内存中的仓储契约，不能证明文件落盘、数据库索引、事务隔离或崩溃后的数据恢复。

### 避免用替身复制被测逻辑

### 避免用替身复制被测逻辑

设想 `RecentMessageService` 负责筛选“未撤回、近 7 天”的消息，并按时间倒序返回。若测试中的 `FakeMessageStore` 也实现了“过滤近 7 天、排除撤回、排序”，测试即使通过，也可能只是服务与 fake 以同一错误规则得到了同一结果：

- 服务错误地把边界写成 `< 7 天`；
- fake 恰好也使用同样边界；
- 测试只证明两份实现一致，不能证明业务规则正确。

fake 应提供可信但尽量朴素的依赖行为，例如内存保存、按标识读取、返回已存对象；业务筛选和排序应由被测服务完成。测试数据要包含过期消息、撤回消息、同一时间戳等边界，以直接断言输出状态。

| 需求 | 选型 | 能证明 | 不能证明 |
|---|---|---|---|
| 验证服务过滤、排序规则 | 简单内存 fake 或 stub | 服务对输入数据的业务决策 | 文件格式、落盘成功 |
| 验证是否发出保存消息 | spy 或 mock | 调用次数、参数、顺序 | 真实存储后的可读取性 |
| 验证本地文件读写 | 临时目录中的真实文件实现 | 序列化、路径、持久化与重启后读取 | 远程存储的网络语义 |

因此，局部单元测试可用内存 fake 隔离文件系统并快速验证业务规则；另设文件集成测试，才为“数据确实写入并能从本地文件恢复”提供证据。不要让 fake 模拟持久化细节，更不要把 fake 的通过误解为文件持久性的证明。

> **要点** — 替身应隔离不可控边界并提供有限证据；内存 fake 能证明规则，不能证明文件持久化。

以单会话本地消息历史为例，先厘清规则证据，再选择不会掩盖缺陷的替身与断言边界。

### 从需求拆分被测行为与依赖职责

### 从需求拆分被测行为与依赖职责

单会话历史的契约可先写成两条可观察规则：

1. `ID` 不能为空；空 `ID` 被拒绝，历史不变。
2. 同一 `ID` 不能重复写入；重复写入被拒绝，已有消息不被覆盖、不追加。

这不是“某个 `if` 应该怎样写”，而是输入、返回结果与状态迁移的要求。可将职责拆开：

- **被测行为**：接收消息、判断其是否合法、决定是否写入，并向调用方报告成功或失败。
- **存储依赖**：保存消息、按 `ID` 查询或拒绝重复；不应替业务层悄悄修正空 `ID`。
- **状态断言**：失败后不仅要断言有错误，还要断言 `before == after`。

例如内存历史可作为明确的依赖实现：

```go
type Message struct {
	ID   string
	Body string
}

type History struct {
	items map[string]Message
}

func (h *History) Add(m Message) error {
	if m.ID == "" {
		return errors.New("消息ID不能为空")
	}
	if _, exists := h.items[m.ID]; exists {
		return errors.New("消息ID重复")
	}
	h.items[m.ID] = m // 存入值副本
	return nil
}

func (h *History) Get(id string) (Message, bool) {
	m, ok := h.items[id]
	return m, ok // 返回值副本
}
```

表驱动测试应从契约列出边界：空 `ID`、首次写入、重复 `ID`。每个用例先建立 `before`，执行后检查错误与 `after`：首次写入才增加一条；空值和重复值都必须保持原状态。

若服务测试使用这个真实内存实现，得到的是内存集成测试或领域规则证据；若被测对象本身就是 `History`，不能再拿同一实现充当 oracle。此时应直接依据需求构造预期状态，而非复制生产代码中的分支逻辑。

### 用小型接口和构造参数建立边界

### 用小型接口和构造参数建立边界

单会话历史只需表达“按 ID 读取”和“按 ID 写入”两种能力，不应让业务依赖具体 `map`、数据库客户端或全局变量。接口应由使用方需要什么来决定：

```go
type Message struct {
	ID      string
	Content string
}

type History interface {
	Get(id string) (Message, bool)
	Put(msg Message) error
}
```

构造函数接收该接口，使服务的依赖在创建时明确，而非运行中偷偷访问全局存储：

```go
type ChatService struct {
	history History
}

func NewChatService(history History) *ChatService {
	return &ChatService{history: history}
}
```

本地内存实现可以作为开发实现或测试中的真实内存集成环境。其契约是：`ID` 不得为空；重复 ID 返回错误，且原有消息绝不被覆盖；读取不到时返回 `false`。

```go
type MemoryHistory struct {
	items map[string]Message
}

func NewMemoryHistory() *MemoryHistory {
	return &MemoryHistory{items: make(map[string]Message)}
}

func (h *MemoryHistory) Get(id string) (Message, bool) {
	msg, ok := h.items[id]
	return msg, ok // 返回值副本，不暴露 map 槽位
}

func (h *MemoryHistory) Put(msg Message) error {
	if msg.ID == "" {
		return errors.New("消息 ID 不能为空")
	}
	if _, exists := h.items[msg.ID]; exists {
		return errors.New("消息 ID 已存在")
	}
	h.items[msg.ID] = msg // 写入值副本
	return nil
}
```

`Message` 为值类型时，`Get` 返回复制值，调用方修改 `msg.Content` 不会改写内部状态。若字段含切片、映射或指针，还必须进行深复制，否则仍会泄露可变内部数据。

测试服务时使用 `MemoryHistory`，是在验证服务与真实内存实现协作，或为领域规则提供证据；它不是天然的“正确答案”。尤其当被测对象本身就是 `MemoryHistory`，不能再调用同一实现预测结果。应从需求列出表驱动案例，并断言失败前后状态：空 ID 后仍不存在记录，重复 ID 后原消息内容保持不变。

### 真实内存实现与各类替身的证据范围

### 真实内存实现与各类替身的证据范围

消息历史契约可先写成：`ID` 必须非空；重复 `ID` 的追加必须失败，且已有历史完全不变；单会话按写入顺序读取消息。不同替身提供的证据并不相同：

| 类型 | 在消息历史中的用途 | 能证明什么 |
|---|---|---|
| 真实内存实现 | 用 `map[string]Message` 保存消息，再复制返回值 | 领域规则在该实现上的实际效果 |
| fake | 简化但可运行的历史仓库 | 服务层与仓储接口能协作 |
| stub | 固定返回预设历史或预设错误 | 被测服务对读取结果、错误分支的处理 |
| spy | 记录 `Append`、`List` 调用参数 | 是否向依赖发送了正确消息 |
| mock | 预先声明期望调用及次数 | 交互协议是否被遵守 |

一个可用的内存 `fake` 应避免泄漏内部状态：

`func (s *Store) Get(id string) (Message, bool) { m, ok := s.byID[id]; return m, ok }`

这里返回的是 `Message` 的复制值；若含切片、映射等引用字段，还应继续深复制。`Append` 在发现空 ID 或重复 ID 后直接返回错误，不能先写入再报错。

用真实内存实现测试服务时，这通常是**内存集成测试**，或对“服务应遵守仓储规则”的证据；它不能单独证明外部数据库实现也正确。反过来，若被测对象就是这个内存 `Store`，绝不能再实例化同一份 `Store` 代码作为预言机：相同缺陷会同时存在于实现和“期望”中。

此时应从需求导出表驱动断言：记录 `before`，执行追加，再比较 `after`。例如重复 ID 的用例应断言“返回重复错误、`after` 与 `before` 相等”，而不是在测试中复写生产代码的 `if _, ok := map[id]`。这样测试验证的是契约边界，而非实现细节。

### 以表驱动边界断言保护状态不变

### 以表驱动边界断言保护状态不变

本地历史的契约可写成三条：消息 `ID` 不得为空；首次写入成功；重复 `ID` 必须返回可识别的重复错误，且历史内容完全不变。测试关注的是可观察结果与状态迁移，而不是逐行复写 `if` 分支。

```go
var ErrEmptyID = errors.New("消息ID不能为空")
var ErrDuplicateID = errors.New("消息ID重复")

type Message struct {
	ID   string
	Text string
}

type History struct {
	items map[string]Message
}

func NewHistory() *History {
	return &History{items: make(map[string]Message)}
}

func (h *History) Add(m Message) error {
	if m.ID == "" {
		return ErrEmptyID
	}
	if _, exists := h.items[m.ID]; exists {
		return ErrDuplicateID
	}
	h.items[m.ID] = m // 按值保存
	return nil
}

func (h *History) Get(id string) (Message, bool) {
	m, ok := h.items[id]
	return m, ok // 返回值副本
}

func (h *History) Snapshot() map[string]Message {
	cp := make(map[string]Message, len(h.items))
	for id, m := range h.items {
		cp[id] = m
	}
	return cp
}
```

表驱动测试把边界条件表达为需求样例；`before` 与 `after` 快照直接验证失败操作没有污染既有历史：

```go
func TestHistoryAdd(t *testing.T) {
	tests := []struct {
		name    string
		initial []Message
		input   Message
		wantErr error
		want    map[string]Message
	}{
		{"空ID被拒绝", nil, Message{Text: "x"}, ErrEmptyID, map[string]Message{}},
		{"首次写入", nil, Message{ID: "a", Text: "x"}, nil,
			map[string]Message{"a": {ID: "a", Text: "x"}}},
		{"重复ID不改变历史", []Message{{ID: "a", Text: "旧"}},
			Message{ID: "a", Text: "新"}, ErrDuplicateID,
			map[string]Message{"a": {ID: "a", Text: "旧"}}},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			h := NewHistory()
			for _, m := range tt.initial {
				if err := h.Add(m); err != nil { t.Fatal(err) }
			}
			before := h.Snapshot()
			err := h.Add(tt.input)
			if !errors.Is(err, tt.wantErr) { t.Fatalf("错误=%v", err) }

			after := h.Snapshot()
			if !reflect.DeepEqual(after, tt.want) { t.Fatalf("历史=%v", after) }
			if tt.wantErr != nil && !reflect.DeepEqual(before, after) {
				t.Fatal("失败写入不应改变历史")
			}
		})
	}
}
```

若业务服务测试使用该真实内存实现，它属于内存集成测试，或为领域规则提供证据；但若被测对象本身就是 `History`，不能再拿同一实现充当预言机。此时应以契约定义的期望状态、错误身份和状态不变性作为断言依据。

### 注入失败并分层解释测试证据

### 注入失败并分层解释测试证据

失败路径不能只断言“返回了错误”，还要证明错误可识别、状态未被部分写入。可为历史仓库注入一个确定失败的替身：`errDisk := errors.New("写入失败")`；其 `Append` 始终返回 `errDisk`，且不修改内部状态。应用服务调用后应满足：`errors.Is(err, errDisk)` 为真，并且失败前后的消息数、既有消息内容均相同。

若接口为 `Append(id string, msg Message) error`，测试应分别覆盖空 ID、重复 ID 与底层失败。空 ID、重复 ID 属于领域契约：它们通常返回各自的哨兵错误，如 `ErrEmptyID`、`ErrDuplicateID`；底层失败则是依赖故障。调用方不应依赖错误字符串，而应使用 `errors.Is`，因此包装错误也仍可被识别：`return fmt.Errorf("保存历史: %w", errDisk)`。

失败后的状态断言应来自需求，例如“写入失败不得新增消息”，而非复制生产代码中的 `if` 分支。可在表驱动测试中保存 `before := store.List()`，执行操作后取得 `after := store.List()`，再断言失败案例 `reflect.DeepEqual(before, after)`。`List` 必须返回消息切片的副本；基于 `map[string]Message` 的内存实现读取时也应返回值或复制值，避免测试通过修改返回对象意外污染仓库。

证据层级需要明确：

- 局部替身测试：验证应用服务如何传播、包装和处理可控失败。
- 真实内存实现测试：属于内存集成测试，或为领域规则提供证据；它验证接口协作与 ID 契约。
- 本地文件实现测试：属于文件集成测试，应额外验证路径、序列化和写入失败。

若被测对象本身就是内存 `store`，不能再用同一实现充当断言 oracle；应直接检查需求定义的可观察状态，或使用独立构造的期望消息集合。

> **要点** — 替身应为业务风险提供可控证据；重复写入与依赖失败都必须证明既有历史未被修改。

通过可控的存储依赖模拟保存失败，测试消息服务在错误路径上的返回、状态与调用契约，而不把测试绑死在具体实现细节上。

### 以最小接口划定存储边界

### 以最小接口划定存储边界

消息服务若只需要“保存一条消息”，就不应依赖具体文件、数据库或完整仓储对象。将边界收缩为业务真正使用的能力，测试便可替换存储实现而不触及外部环境：

```go
type Message struct {
	Text string
}

type Store interface {
	Save(Message) error
}

type Service struct {
	store Store
}

func NewService(store Store) *Service {
	return &Service{store: store}
}

func (s *Service) Send(text string) error {
	msg := Message{Text: text}
	if err := s.store.Save(msg); err != nil {
		return fmt.Errorf("保存消息失败: %w", err)
	}
	return nil
}
```

接口应由消费者定义，而不是从某个“万能存储接口”中挑选方法。这样 `Service` 只知道 `Save` 的契约：成功返回 `nil`，失败返回错误；它不需要知道数据写入文件、内存还是远程服务。

测试中可注入专门表示存储失败的错误及替身：

```go
var ErrStorage = errors.New("存储不可用")

type stubStore struct {
	saveErr error
}

func (s stubStore) Save(Message) error {
	return s.saveErr
}
```

构造参数显式注入 `Store`，避免服务内部自行创建文件存储；后者会使错误路径依赖权限、磁盘或清理逻辑。`stubStore{saveErr: ErrStorage}` 能稳定触发失败分支，而 `stubStore{}` 则表示保存成功。此处替身只负责控制依赖结果，不应模拟真实文件系统的部分写入、原子性或持久化语义。

### 用可配置存根注入保存错误

### 用可配置存根注入保存错误

为依赖定义最小接口，只暴露服务真正需要的操作。存根通过 `SaveErr` 稳定注入失败，不需要权限、磁盘空间或真实文件环境：

```go
type Store interface {
	Save(message string) error
}

var ErrStorage = errors.New("存储不可用")

type StoreStub struct {
	SaveErr   error
	Saved     []string
	SaveCalls int
}

func (s *StoreStub) Save(message string) error {
	s.SaveCalls++
	if s.SaveErr != nil {
		return s.SaveErr
	}
	s.Saved = append(s.Saved, message)
	return nil
}

type MessageService struct {
	store Store
}

func (s MessageService) Publish(message string) error {
	if err := s.store.Save(message); err != nil {
		return fmt.Errorf("发布消息失败: %w", err)
	}
	return nil
}
```

测试可直接配置错误，并同时验证错误身份与成功结果未出现：

```go
func TestPublish_保存失败(t *testing.T) {
	store := &StoreStub{SaveErr: ErrStorage}
	service := MessageService{store: store}

	err := service.Publish("你好")

	if !errors.Is(err, ErrStorage) {
		t.Fatalf("期望保留 ErrStorage 身份，实际为 %v", err)
	}
	if store.SaveCalls != 1 {
		t.Fatalf("期望保存一次，实际为 %d 次", store.SaveCalls)
	}
	if len(store.Saved) != 0 {
		t.Fatal("保存失败时不应记录成功保存结果")
	}
}
```

`%w` 让调用方能用 `errors.Is` 判断可恢复的底层失败，而不依赖错误文本。这里的 `Saved` 仅表示存根认定的“成功保存”；单纯 `Save` 返回错误并不能证明真实文件系统没有部分写入。涉及原子写入、临时文件或回滚时，应另在真实文件层单测或集成测试中验证。

### 包装错误并验证错误身份

### 包装错误并验证错误身份

存储失败是服务必须显式处理的边界条件。服务层可以补充“保存消息失败”等业务语境，但应使用 `%w` 保留底层错误链；同时不能把失败伪装成成功结果。

```go
var ErrStorage = errors.New("存储不可用")

type Store interface {
	Save(string) error
}

type MessageService struct {
	store Store
}

func (s MessageService) Send(text string) (string, error) {
	if err := s.store.Save(text); err != nil {
		return "", fmt.Errorf("保存消息失败: %w", err)
	}
	return text, nil
}

type saveErrStub struct {
	err error
}

func (s saveErrStub) Save(string) error {
	return s.err
}
```

测试注入可配置的失败替身，并验证两项契约：成功结果为空，且错误仍具有 `ErrStorage` 身份。

```go
func TestMessageService_Send_包装存储错误(t *testing.T) {
	svc := MessageService{
		store: saveErrStub{err: ErrStorage},
	}

	got, err := svc.Send("你好")

	if got != "" {
		t.Fatalf("Send() 结果 = %q，失败时应为空", got)
	}
	if err == nil {
		t.Fatal("Send() 错误 = nil，期望存储错误")
	}
	if !errors.Is(err, ErrStorage) {
		t.Fatalf("errors.Is(%v, ErrStorage) = false", err)
	}
}
```

不要比较 `err.Error()` 的完整文本：包装时增加上下文、调整措辞或更换语言都会使这类断言脆弱。`errors.Is` 检查的是错误链中的身份，因此既允许服务提供可读上下文，也让调用方能够针对 `ErrStorage` 采取重试、告警等策略。

### 按副作用顺序验证状态不变

### 按副作用顺序验证状态不变

保存失败时，不能笼统地断言“状态没有变化”：内存对象、服务内部缓存与底层存储是不同层次的状态。测试应先明确业务契约：失败后哪些状态必须保持原样，哪些临时计算结果允许存在但不可对外观察。

例如，服务创建消息并调用 `Store.Save`：

```go
var ErrStorage = errors.New("存储失败")

type Store interface {
	Save(Message) error
}

type Message struct {
	ID   string
	Text string
}

type Service struct {
	store Store
	last  Message
}

func (s *Service) Create(id, text string) error {
	msg := Message{ID: id, Text: text}
	if err := s.store.Save(msg); err != nil {
		return fmt.Errorf("保存消息 %q: %w", id, err)
	}
	s.last = msg
	return nil
}
```

这里副作用顺序是：构造局部值 → 持久化 → 更新 `last`。因此保存失败时，`last` 必须不变；返回值必须非空，且保留原始错误身份：

```go
type saveErrStub struct{ err error }

func (s saveErrStub) Save(Message) error { return s.err }

func TestCreate_Save失败不更新最后消息(t *testing.T) {
	old := Message{ID: "old", Text: "旧消息"}
	svc := Service{
		store: saveErrStub{err: ErrStorage},
		last:  old,
	}

	err := svc.Create("new", "新消息")

	if err == nil {
		t.Fatal("保存失败时应返回错误")
	}
	if !errors.Is(err, ErrStorage) {
		t.Fatalf("错误应包装 ErrStorage，实际为：%v", err)
	}
	if svc.last != old {
		t.Fatalf("保存失败不应更新内存状态，实际为：%+v", svc.last)
	}
}
```

若实现先修改 `s.last` 再保存，那么“失败不改变内存状态”就要求显式回滚；否则应调整实现顺序。注意，`Save` 返回错误只证明服务收到了失败信号，并不证明真实文件、数据库或远程系统完全没有部分写入；后者应由具体存储层的单元测试或集成测试验证。

### 谨慎使用 spy 与真实文件证据

### 谨慎使用 spy 与真实文件证据

`spy` 的价值是记录可观察的业务消息：`Save` 收到了什么参数、被调用了几次。只有业务契约明确规定“本次操作恰好保存一次”时，才应断言调用次数；例如创建消息成功后必须持久化一次，可断言 `spy.calls == 1`，并检查 `spy.saved` 等于期望消息。

`spy` 不应泄露实现细节。服务内部将校验、转换、序列化拆成几个 helper，或调整 helper 的调用顺序，都不应导致测试失败；因此不要断言私有 helper 调用次数，也不要把“调用过 `Save`”误当成完整业务结果。

一个最小 spy 可记录 `Save` 参数与次数：`type SpyStore struct { saved Message; calls int; err error }`；其 `Save(m Message) error` 应先执行 `s.calls++`，再保存 `s.saved = m`，最后返回 `s.err`。当测试保存失败路径时，可令 `err` 为 `ErrStorage`，并断言服务返回的错误满足 `errors.Is(err, ErrStorage)`；若契约要求失败不改变服务内存状态，还应断言该状态保持原值。

但 spy 只能证明服务**尝试**发送了一次保存请求，不能证明底层文件没有部分写入。真实文件系统可能已创建文件、截断旧内容或写入部分字节后才返回错误。原子替换、临时文件清理、权限错误处理等证据，应由文件存储层的单元测试验证；跨越服务与真实存储的行为，则交给集成测试。这样，服务测试验证消息契约，文件测试验证持久化事实，边界才清晰而稳定。

> **要点** — 错误替身用于证明服务的错误契约与状态边界；底层是否部分写入仍须由真实存储层证据确认。

消息写入一旦依赖真实时钟，边界时刻、时区与等待时间都会让测试失去确定性。本节以本地消息历史为例，建立可验证且不扭曲真实合同的时间与CLI测试设计。

### 识别真实时钟造成的不确定性

### 识别真实时钟造成的不确定性

消息写入看似只是“保存正文”，实际常包含时间戳：

`appendMessage(path, author, body)` 内部直接调用 `time.Now()`，再把时间格式化后写入历史文件。

这里混合了三类东西：

- **业务输入**：`author`、`body`、目标文件路径；
- **环境依赖**：当前时间、本地时区、文件系统；
- **可观察状态变化**：新增了一条消息，且其作者、正文、时间字段和存储位置符合规则。

直接调用 `time.Now()` 会让同一测试的预期随执行时刻变化。例如测试先记录 `before := time.Now()`，写入后再断言时间戳位于 `[before, time.Now()]`：边界可能因格式化截断、时区转换或跨秒而失败。若期待精确字符串，测试又会立刻变成“猜测当前时间”的脆弱测试。

更常见的错误是用 `time.Sleep` 等待时间变化。等待既不能证明逻辑正确，也会拖慢测试；在繁忙机器、低精度时钟或跨越日期边界时，仍可能不稳定。

先把时间视为明确输入：

`appendMessage(path, author, body, now time.Time)`

测试即可传入固定时刻，例如 `2025-01-02 03:04:05 UTC`，并验证写入结果中的时间格式、时区和正文。此时测试应关注“给定该时刻，产生该记录”，而不是“运行时恰好是什么时间”。

还要明确窗口边界规则：若查询条件是“`since` 之后”，`>` 与 `>=` 的语义不同；消息恰好位于边界时，必须有单独测试。时间依赖被显式化后，这类规则才能被精确验证。

### 优先把当前时间作为显式参数

### 优先把当前时间作为显式参数

消息写入通常只有一个“取当前时间”的位置。此时不必立刻抽象 `Clock`：让业务函数接收 `now time.Time`，依赖就已显式化，测试也能精确控制边界。

```go
func appendMessage(path, body string, now time.Time) error
```

生产入口仍可保持自然：

```go
err := appendMessage(path, body, time.Now())
```

而测试传入固定时刻：

```go
now := time.Date(2025, 1, 12, 10, 0, 0, 0, time.UTC)
err := appendMessage(path, "hello", now)
```

这样可直接验证三类规则：

- **写入时间**：持久化记录是否使用传入的 `now`，而非函数内部再次调用真实时钟。
- **查询窗口**：例如“最近 24 小时”应明确为 `[now-24h, now]` 还是 `(now-24h, now]`。
- **边界消息**：分别构造恰好位于起点、终点、起点前一纳秒、终点后一纳秒的记录，断言是否包含。

时间比较必须统一语义。存储格式可使用 UTC 的 RFC 3339；展示给用户时再按 CLI 契约转换时区。测试不应依赖机器本地时区，固定时刻也应显式指定 `time.UTC` 或目标时区。

不要写“先写入，再 `sleep`，然后查询最近一分钟”的测试：它既慢又会在调度延迟、时钟跳变或边界秒上失败。单一调用点下，`now time.Time` 已足够让时间从隐式环境条件变为可构造输入。

### 多个调用点再引入Clock接口

### 多个调用点再引入 Clock 接口

单个写入动作只需一次当前时间时，优先传入显式参数：

`appendMessage(path, body, now time.Time)`

测试直接构造固定值，生产代码在入口处调用一次 `time.Now()`。这种依赖最透明：函数签名明确说明“结果取决于时间”，也不会为简单逻辑引入额外接口。

当一个用例需要在多处取时，例如创建消息、更新索引、记录审计事件、判断过期窗口时，反复传递 `now` 容易遗漏，且无法表达“这些时间读取来自同一可控时钟”。这时再引入窄接口：

`type Clock interface { Now() time.Time }`

生产实现可为 `realClock`，其 `Now()` 返回 `time.Now()`；测试使用 `fixedClock{t: want}`，每次均返回同一时刻。这样可验证多个字段是否采用统一时间基准，而不依赖真实时间流逝。

不要把 `Clock` 扩展成计时器、休眠、日期格式化等“万能时间服务”。若逻辑只需一次时间，显式 `time.Time` 更直接；只有存在多个独立取时点，且它们必须被统一控制时，接口才带来价值。

无论哪种方式，都应固定时区并明确窗口边界。例如使用 `UTC` 格式化，过期判断写成 `now.Before(deadline)` 还是 `!now.After(deadline)` 必须与契约一致。测试不应用 `sleep` 等待跨秒、跨日或过期；应直接提供边界前、边界时和边界后的固定时间。

### 围绕边界、时区和失败建立证据

### 围绕边界、时区和失败建立证据

先把时间规则写成可断言的合同，而不是让测试猜测 `time.Now()` 的结果。写入函数接收显式的 `now time.Time`，测试即可固定在有代表性的时刻：

- 格式：明确持久化的是 RFC 3339、日期字符串还是 Unix 时间戳；断言完整输出，避免只检查“包含年份”。
- 时区：输入可位于 `Asia/Shanghai`，但存储统一转换为 UTC；测试应验证同一瞬间转换后仍表示相同时间，而非误把本地钟表时间当成 UTC。
- 边界：时间窗口建议采用半开区间 `$[start, end)$`。消息恰在 `start` 时应被选中，恰在 `end` 时不应被选中；相邻窗口因此不会重复或遗漏消息。
- 跨日与跨月：选择 `23:59:59`、月末、夏令时切换附近等时刻，证明筛选依据的是瞬间和规则，而不是字符串字典序或机器本地时区。

写入失败也必须留下反向证据。预先保存历史文件内容或内存状态，令底层写入返回错误后，断言：错误被返回、原文件内容未变、内存索引未提前追加、不会留下半条记录。若采用“先写临时文件再原子替换”，可进一步验证失败时临时产物被清理或不会成为可见历史。

不要用 `sleep` 等待时间流逝：它既不能可靠跨越边界，也会让测试变慢并受调度影响。单个调用点传入固定 `now` 即可；只有多个组件都需要取当前时间时，才引入 `Clock` 接口和 `fixedClock`，让所有断言共享同一可控瞬间。

### 分层验证CLI输出与真实文件

### 分层验证 CLI 输出与真实文件

CLI 测试应同时验证两类事实：**用户可见合同**与**本地持久化结果**。不要把二者混成一次脆弱的端到端断言。

先让入口保持可注入的流：

`run(args []string, stdout, stderr io.Writer) error`

测试用 `bytes.Buffer` 捕获输出，断言命令的真实合同：成功时写入必要的确认信息，失败时写入错误流并返回错误。例如只验证“已保存消息”“记录数”等稳定字段，而不是把完整提示文本、空格或内部实现细节都写死。

```go
var out, errOut bytes.Buffer
err := run([]string{"add", "--title", "会议"}, &out, &errOut)

if err != nil {
    t.Fatal(err)
}
if !strings.Contains(out.String(), "已保存") {
    t.Fatalf("stdout = %q", out.String())
}
if errOut.Len() != 0 {
    t.Fatalf("stderr = %q", errOut.String())
}
```

敏感正文默认不应出现在确认输出中。若命令保存的是私密消息，断言输出包含标识、时间或摘要状态即可，并显式检查正文未泄露：

`if strings.Contains(out.String(), secretBody) { t.Fatal("输出泄露消息正文") }`

第二层使用 `t.TempDir()` 创建真实但隔离的目录，将其作为消息文件位置。运行命令后读取实际文件，验证记录确实落盘、可被后续读取，必要时检查序列化后的时间格式与时区。这里不是模拟文件系统，而是保留真实文件语义，同时避免污染用户目录和测试之间互相干扰。

输出测试回答“用户看到了什么”；文件集成测试回答“程序到底写入了什么”。前者遵守 CLI 契约，后者提供持久化证据。两层都不需要 `sleep`：时间应由显式 `now` 或固定时钟提供，文件存在与内容正确也应在命令返回后立即可验证。

> **要点** — 先显式固定时间，再按调用复杂度引入时钟接口；局部替身验证规则，真实文件验证集成合同。

替身的价值在于控制不确定性，而非把每个协作都写成脆弱的调用脚本。应按业务风险选择证据强度，并保留必要的跨边界验证。

### 先划清规则、状态与外部边界

### 先划清规则、状态与外部边界

以“向本地消息历史追加一条消息”为例，先问测试要证明什么事实，而不是先决定要不要 mock。

- **纯消息规则**：输入是否合法、文本是否超过字节上限、空内容如何处理、消息对象如何规范化。这类逻辑应写成无状态函数，直接传入数据、断言返回值或错误。例如限制从 `6` 字节改为 `9` 字节时，主要修改边界用例：`6/7` 改为 `9/10`；与存储、发送无关的测试不应改动。

- **服务协调**：服务负责“先校验，再追加，再返回结果”这一顺序和错误传播。这里可用替身验证关键结果：校验失败时不写入；写入失败时服务返回失败；成功时写入的是规范化后的消息。不要把“每个方法恰好调用一次”都写成预期，否则提取辅助方法、增加日志或批处理都会让测试无意义地失败。

- **文件存储边界**：若生产代码读写本地文件，应使用真实临时目录和临时文件验证序列化、追加、重启后读取、权限或损坏文件的处理。内存 fake 可以快速覆盖服务场景，但不等于证明文件格式真的可用；更不能把生产校验逻辑复制进 fake，否则两者可能同错同过。

- **端到端证据**：从公开入口执行到本地历史落盘，验证用户可观察结果与关键链路。它证明组件组合正确，但不据此声称网络已经发送、或 OpenIM 发生了真实行为；这些结论需要对应的受控集成环境证据。

替身本身只需少量合同检查，例如存储实现都应在追加后可读回消息。高风险业务链则至少保留一次跨越真实文件边界的验证。避免共享可变 fake：每个测试新建状态；避免用 `sleep` 等待时间，改为注入时钟或显式推进时间。

### 过度模拟为何让重构变成失败

### 过度模拟为何让重构变成失败

当测试为每个协作方法都写下“恰好调用一次”的预期时，它验证的往往不是业务规则，而是当前实现的操作剧本：

- 先调用 `校验()`
- 再调用 `编码()`
- 最后调用 `保存()`
- 每一步都只能一次，顺序也不能变化

这类测试与内部步骤强耦合。假设实现把两次局部校验合并为一次，或为了可读性提取出 `构建消息()` 方法；对用户而言，输入、输出和失败语义完全不变，但 mock 断言会失败。测试于是把“允许重构”的安全网，变成“禁止改变实现”的围栏。

更稳健的测试应优先验证可观察的业务结果。例如，给定合法输入后，服务返回已生成的消息；给定长度不足的输入后，返回明确的校验错误；保存失败时，调用方得到可处理的失败结果。若规则要求消息字段长度为 $6$ 字节，则测试应关注：

- 合法的 $6$ 字节数据被接受；
- 少于或多于 $6$ 字节的数据被拒绝；
- 成功时产生的领域结果或写入内容正确；
- 失败时不会留下不完整状态。

协作消息仍可验证，但应限于真正的边界合同：例如“成功路径会向仓储提交一次最终构造的记录”，而非断言所有辅助对象各被调用一次。这里的“一次”描述的是可见副作用的幂等性或重复写入风险，不是对内部编排细节的逐行复刻。

当需求从 $6$ 字节改为 $9$ 字节时，长度规则测试、相关边界合同测试应修改；只验证调用方得到正确成功或失败语义的测试通常不必改。若大量无关测试同时失败，说明它们锁定了实现步骤，而没有守住业务行为。

### 替身失真：同错同过与漏测失败

### 替身失真：同错同过与漏测失败

替身应提供可控证据，而不是复制被测系统的错误。最危险的失真通常有三类。

- **复制生产验证逻辑的 fake：同错同过。**  
  若生产代码和 fake 都以相同方式判断“消息长度必须为 6 字节”，两者同时把边界写错为 `< 6` 或按字符数而非字节数计算时，测试仍会通过。此类 fake 实际是在用一份未经独立验证的实现证明另一份实现正确。更稳妥的做法是：fake 只保存收到的数据、提供预置结果；长度、编码、格式等规则应由纯函数测试覆盖，并用少量真实边界测试确认接口契约。

- **永远成功的 stub：失败路径消失。**  
  `send()` 无论输入为何都返回成功，只能证明调用方能走通“成功分支”，不能证明它会处理超时、拒绝、返回错误或部分失败。对业务高风险链路，应显式配置 stub 返回失败，并断言重试、错误映射、状态回滚或告警行为；不要把“未抛异常”误当作可靠性证据。

- **共享可变 fake：测试顺序决定结果。**  
  多个测试复用同一个带队列、计数器或已发送记录的 fake，前一测试留下的状态会污染后一测试。例如已消费的预置失败、累积的调用次数都会使单独运行与全量运行结果不同。每个测试应新建 fake，或在固定夹具中彻底重置；并避免断言跨测试累积状态。

替身本身只需少量合同检查：能记录输入、能按配置成功或失败、状态重置语义明确。它不应悄悄成为第二套生产验证器。这样，当长度规则从 6 字节改为 9 字节时，纯规则测试和相关业务断言应更新；只验证“失败可被处理”的 stub 测试、隔离状态的 fake 测试则不应改动。

### 固定时间、注入错误与保护状态

### 固定时间、注入错误与保护状态

时间和失败不应依赖“恰好发生”。将时钟与外部依赖作为构造参数注入，使测试能精确安排条件：

- `now func() time.Time`：固定返回某一时刻，验证过期、冷却、日期切换等规则，无须 `sleep`。
- 可失败的端口：例如 `Store`、`Sender`、`Writer`，由替身按测试需要返回指定错误。
- 初始状态显式给定：测试先建立一份历史快照，再触发失败路径。

例如规划器仅在写入成功后提交新计划：

`err := planner.Plan(input)`  
`if err != nil { return err }`  
`p.history = nextHistory`

测试重点不是“调用了几次内部方法”，而是失败后的可观察不变量：

1. 写入依赖返回哨兵错误 `errDiskFull`；
2. `Plan` 返回错误；
3. `errors.Is(err, errDiskFull)` 为真，允许上层附加上下文而不丢失错误身份；
4. `history`、已确认的配额、已发布的计划仍与调用前相同；
5. 下一次使用正常依赖执行时，不会继承失败调用留下的半成品状态。

可用一个故意失败的服务替身，而非复制生产校验逻辑：

`type failingStore struct { err error }`  
`func (s failingStore) Save(Plan) error { return s.err }`

固定时钟适合纯规则及服务替身测试；真实临时文件可补充验证写入失败时的原子性或清理行为；跨网络、OpenIM 等真实边界则需要端到端证据，本节不据此声称消息已真实发送。若长度规则由 6 字节改为 9 字节，纯长度规则测试应更新；时间、错误身份与“失败不改变历史”的测试不应改变。

### 按风险分层选择证据与改动范围

### 按风险分层选择证据与改动范围

消息长度上限由 `$6$` 字节调整为 `$9$` 字节时，先问“规则在哪里”，再问“哪些证据能证明规则仍被正确执行”。不要因为一个常量变化，就机械修改所有测试。

- **纯规则测试必须更新**：直接覆盖边界值，例如 `$9$` 字节可接受、`$10$` 字节被拒绝；若按 UTF-8 字节数而非字符数计算，还应保留中文、emoji 等多字节输入。这里测试的是业务规则，期望值应随需求改变。
- **服务协作测试通常不改**：例如验证“校验通过后调用保存接口一次”“校验失败时不调用保存接口”。它们应关注消息与分支，而非把 `$6$` 写进 mock 期望。若测试为每个方法调用次数、参数细节都设定脚本式预期，重构实现就会无意义地破坏测试。
- **临时文件集成证据应保留**：使用真实临时目录和真实文件读写，证明长度校验、序列化及落盘边界能够共同工作。该测试可更新输入样例为 `$9$` 与 `$10$` 字节，但不应以 fake 文件系统复制生产校验逻辑；否则两处同错仍会一起通过。
- **端到端证据范围有限**：可证明本应用链路到达自身可控边界，不能据此声称网络已发送，或 OpenIM 已产生真实行为。

替身自身只需少量合同检查，例如 fake 是否正确保存数据、stub 是否能返回失败。高风险链路仍要跨越至少一个真实边界验证。避免共享可变 fake 造成测试顺序敏感，也不要用 `sleep` 等待时间；应注入可控时钟或明确同步点。

> **要点** — 替身应隔离依赖而不复制实现；高风险业务链仍须以真实边界证据补足。

本节以本地消息历史为线索，将直接依赖逐步改造成可注入协作，并用替身证据覆盖规则、失败与真实文件行为。

### 从直接依赖到可注入边界

### 从直接依赖到可注入边界

消息写入逻辑若直接调用 `time.Now()`、`os.WriteFile` 和 `fmt.Println`，测试便同时受真实时间、磁盘状态与终端环境约束。先识别协作点，再只为**消费方真正需要的能力**建立边界：

```go
type Clock interface {
    Now() time.Time
}

type HistoryStore interface {
    Append(message Message) error
}

type Output interface {
    Println(string)
}
```

改造顺序应小而连续：

1. **固化现状**：保留原有 `Send` 行为，先写一条端到端验收：重复消息如何处理、历史文件写入什么、CLI 显示什么。
2. **抽出时间来源**：把 `time.Now()` 替换为构造参数中的 `Clock`；生产实现仍可只是调用真实时钟。
3. **抽出存储意图**：业务层传递完整消息给 `HistoryStore.Append`，不要让业务层关心路径、打开模式或编码细节。
4. **抽出可见输出**：经由 `Output` 发布成功、重复或失败提示；测试检查消息内容，而非捕获全局标准输出。
5. **组装生产对象**：在 `main` 或组合根创建真实时钟、文件存储和终端输出，再注入服务。

构造函数表达依赖关系：

`NewMessageService(clock Clock, store HistoryStore, out Output)`

接口不应按底层库机械镜像。若业务只需要追加历史，就不要暴露 `Open`、`Seek`、`Close` 等文件细节；窄接口既降低替身成本，也避免测试验证实现步骤而非业务消息。

可按风险选择替身：规则判断用假时钟和内存存储；断言是否调用、参数是否正确时用记录型替身；模拟磁盘失败时用返回错误的存储替身；最终仍以临时目录中的真实文件覆盖编码、追加与持久化行为。这样，重复消息、时间边界、写盘失败和 CLI 输出分别可控，又能在验收层重新连成完整路线。

### 替身选择矩阵与证据边界

### 替身选择矩阵与证据边界

选择替身的原则不是“隔离得越多越好”，而是让测试以最低成本证明当前规则。替身只能证明它实际观察到的行为，不能替代真实边界的验收。

| 类型 | 适用场景 | 可提供的证据 | 主要风险 | 不能证明 |
|---|---|---|---|---|
| 真实内存实现 | 集合、消息历史、领域状态 | 状态转换、重复消息处理、查询结果 | 与生产存储语义不同 | 磁盘写入、权限、序列化 |
| fake | 简化但可工作的仓储、时钟、传输层 | 多步骤协作、可重复的业务流程 | 偷偷复制生产业务逻辑 | 真实适配器协议与性能 |
| stub | 固定返回值，如“磁盘已满” | 分支是否正确处理失败 | 返回值过于理想化 | 实际失败发生条件 |
| spy | 记录调用参数与顺序 | 是否输出一次、是否携带正确消息 | 过度断言调用细节 | 用户真正看到的 CLI 文本 |
| mock | 预先声明交互契约 | 必须发送或禁止发送的消息 | 测试绑定实现顺序，重构脆弱 | 最终状态及真实副作用 |

可按问题选择：

- 要验证“重复消息不重复保存”，优先真实内存实现或小型 fake，检查最终消息数。
- 要验证“保存失败时 CLI 显示错误且不报告成功”，用 stub 触发写入失败，再用 spy 检查输出；最后必须以真实文件验收补足证据。
- 要验证“截止时刻后拒绝提交”，注入可控时钟；不要在测试中依赖系统当前时间。
- 要验证“必须通知审计器”，才使用 mock；若只关心审计记录内容，spy 通常更宽松。

一个健康的 fake 实现接口语义，而不重写用例逻辑。若 fake 内部也判断“重复消息应忽略”，而生产服务同样判断该规则，两个实现可能共同犯错；此时测试只证明它们一致，未证明规则正确。应将重复判定放在唯一的领域位置，fake 仅负责存取或传递。

证据边界应明确写出：内存替身可证明业务规则与调用意图；stub 可证明失败分支；spy/mock 可证明消息协作；只有真实文件、真实 CLI 进程和受控时间边界的验收，才能证明路径、格式、退出码与用户可见输出。任何未实际运行的检查，都只能声明为“设计上覆盖”，不能宣称已验证。

### 可重复的消息规则测试

### 可重复的消息规则测试

重复消息规则不能只断言“返回了某个结果”，而应同时验证四层证据：输入解释、状态变化、依赖消息与错误身份。先将时间、存储和输出边界注入，使同一组测试在任意机器、任意时刻都可重复。

设规则为：同一用户在窗口 $\Delta t$ 内提交相同消息，仅记录一次；窗口外视为新消息。测试固定 `now`，并让存储替身记录调用：

- 输入：`"你好"`、重复的 `"你好"`、不同内容、空消息。
- 初始状态：无历史、窗口内已有记录、恰在边界、窗口外。
- 依赖调用：是否调用 `Load`、`Save`，保存次数及保存内容。
- 结果：成功状态、CLI 文本、返回错误及其可识别身份。

建议按“规则优先、失败随后、真实行为收尾”组织验收：

1. **正例**：首次消息应保存一次，并输出“已记录”。检查替身收到的消息与固定时间完全一致。
2. **重复例**：窗口内同内容应不再保存；若产品要求提示，则仅断言稳定的提示语，不依赖日志顺序。
3. **边界例**：`now-last == Δt` 必须明确归属。测试应直接写出“边界包含”或“边界排除”，避免隐藏在 `>`、`>=` 中。
4. **错误例**：磁盘 `Save` 返回预设错误时，业务层应返回或包装该错误；使用 `errors.Is(err, diskErr)` 验证身份，不比较易变的完整文本。
5. **真实文件例**：仅在集成验收中使用临时目录，确认首次写入后文件存在、重复消息未增加记录；不得以替身测试替代文件格式与权限行为。

可用如下检查表审阅每题或每个测试：

- 固定时钟是否避免了 `time.Now()` 导致的偶发失败？
- 重复判定是否同时覆盖内容相同与时间接近？
- 替身是否验证了“不应调用 `Save`”这一负向消息？
- 外部错误是否保留可追踪身份？
- CLI 是否只断言面向用户的稳定输出，而非内部实现细节？

这些测试能够证明既定输入、固定时钟和受控依赖下的消息规则；不能证明真实磁盘在所有平台的故障模式，也不能证明并发竞争安全。后两者需由真实文件集成测试、故障注入或并发测试补充。设计取向可参照 Go 官方测试与 `errors.Is` 文档，以及 Martin Fowler 对测试替身和交互验证的讨论；本节仅规划验证，不运行示例，也不修改项目软件。

### 四层练习：正向、失败与边界

### 四层练习：正向、失败与边界

以下练习围绕“消息写入本地历史”的协作：接口接收消息、持久化到文件、重复消息需保留、失败时状态不变，并通过 `errors.Is` 识别底层错误。

**基础层**

1. 将直接调用 `os.WriteFile` 的代码改为依赖接口。检查：业务结构体不再自行创建外部依赖。  
2. 为存储接口写最小方法签名。检查：参数表达业务意图，而非暴露无关细节。  
3. 编写成功替身，记录收到的消息。检查：断言内容与调用次数。  
4. 输入一条普通消息。检查：返回成功，替身记录该消息。  
5. 连续输入两条相同消息。检查：两次调用都发生，不能擅自去重。  

**原理层**

6. 区分“返回值正确”和“协作正确”。检查：测试同时验证结果与发送给依赖的消息。  
7. 让替身返回包装后的磁盘错误。检查：`errors.Is(err, ErrDiskFull)` 为真。  
8. 让替身返回无关错误。检查：不得错误地映射为磁盘空间不足。  
9. 存储失败后读取内存历史。检查：历史状态未新增该消息。  
10. 时间恰为日切边界。检查：归档路径或日期规则符合约定。  

**工程层**

11. 为替身保存调用顺序。检查：先写消息，再更新成功状态。  
12. 模拟第一次成功、第二次失败。检查：仅第一条进入已确认历史。  
13. 模拟部分写入错误。检查：业务层不宣称消息已完整保存。  
14. 注入固定时钟。检查：测试不依赖真实当前时间。  
15. 用临时目录运行真实文件存储。检查：文件确实创建且内容含两条重复消息。  

**业务层**

16. 从 CLI 输入一条消息。检查：标准输出显示成功提示。  
17. CLI 输入空消息。检查：输出明确校验提示，存储接口零调用。  
18. CLI 写入遇到磁盘失败。检查：输出可行动的失败信息，进程状态符合约定。  
19. 重复消息经 CLI 连续提交。检查：输出两次成功，真实文件保留两条记录。  
20. 日切前后各提交一条。检查：文件归属、输出日期与固定时钟一致。  
21. 重启后读取历史。检查：此前真实文件中的重复记录仍可见。  
22. 存储不可用时重试提交。检查：失败尝试不污染状态，恢复后仅成功提交被确认。  

这些练习可证明接口注入、消息协作、错误分类、状态不变与真实文件行为；不能证明所有操作系统、文件系统或终端环境均一致。示例未运行，也不修改项目软件；错误语义可对照 Go 官方 `errors.Is` 文档，以及 Fowler 关于测试替身的资料。

### 从局部替身到文件验收路线

### 从局部替身到文件验收路线

局部替身证明“某个依赖被正确调用”，文件验收则证明“用户实际得到正确结果”。两者应形成递进证据，而非互相替代：

1. **规则层：替身记录消息**  
   为消息仓库、时钟、输出器注入接口；替身保存收到的参数与调用次数。检查重复消息是否被拒绝、是否只写入一次、错误是否向上返回。  
   - 重复消息：断言返回“已存在”类错误，`Save` 调用次数为 `0` 或符合既定幂等规则。  
   - 时间边界：注入固定时钟，验证截止时刻前后行为；避免直接断言真实当前时间。  
   - 磁盘失败：令仓库替身返回写入错误，断言应用层不报告成功，也不输出误导性路径。

2. **交互层：检查 CLI 可见输出**  
   将 `stdout`/`stderr` 作为可注入写入器，验证退出结果、成功提示与错误提示。应检查关键语义，不要把完整文案、空格和颜色码全部固定为脆弱断言。  
   例如：成功时包含消息标识与保存位置；重复时包含“重复”原因；磁盘失败时错误输出存在且成功输出为空。

3. **真实行为层：临时目录文件验收**  
   使用测试专属临时目录，执行真实文件仓库实现，再读取生成文件。验收文件存在、内容包含预期消息、重复写入未产生额外记录；对不可写目录或受控失败路径，验证错误传播。测试结束后由临时目录机制清理，禁止触碰用户真实历史文件。

可采用如下验收路线：

`固定时钟 → 提交消息 → CLI报告成功 → 读取真实文件 → 再次提交同一消息 → CLI报告重复 → 模拟写盘失败 → CLI报告失败`

这条路线可证明：应用规则、依赖协作、命令行可见结果及本地文件持久化在受控场景下相互一致。它**不能证明**所有操作系统权限模型、真实磁盘耗尽、并发竞争或生产环境终端行为；未运行的示例只能说明建议的测试设计，不能声称已验证本项目。

接口与临时目录实践可查阅 Go 官方 `testing`、`os` 与 `filepath` 文档；替身分类、状态验证与交互验证可参照 Martin Fowler 的《Mocks Aren't Stubs》及其测试替身资料。

> **要点** — 以小接口注入依赖；用匹配风险的替身验证规则，并以真实文件行为补足局部证据。
