网关Pod成功调度、显示Ready，只说明它具备当前运行条件；这并不等于消息已被权威存储，更不等于重启后能够恢复。

### 先分开四个判断：能调度、能运行、已就绪、可恢复

### 先分开四个判断：能调度、能运行、已就绪、可恢复

对网关 Pod 而言，这四个判断属于不同层次，不能因为其中一个成立，就推导其余三个也成立。

- **能调度**：调度器在某个 Node 上找到了可放置位置。它主要比较 Node 的可分配资源与 Pod 的 `resources.requests`，例如 CPU、内存、临时存储。`request` 是调度准入依据；`limit` 是容器运行时可使用的上限。Node 尚有资源，只说明“可以放进去”，不说明进程一定能正常工作。

- **能运行**：容器镜像已拉取、进程已启动，且没有立即因参数错误、端口冲突、OOM、依赖缺失等原因退出。即使 Pod 处于 `Running`，也可能尚未监听服务端口，或已启动但业务初始化失败。

- **已就绪**：Pod 的 `Ready=True` 通常表示就绪探针成功，Service 可以把流量发送给它。它回答的是“当前能否接请求”，不是“请求结果是否已经写入权威介质”。探针可能只检查 `/healthz`、进程存活或内存状态。

- **可恢复**：节点、进程或 Pod 重启后，已接受的消息仍能从权威存储重新读取，并保持必要的顺序、去重与成员关系语义。这需要持久化责任，而不是仅靠 Ready 状态。

当前 S2/v1 的 `200` 仅表示消息被**内存受理**：正文仍限制为 6 个 UTF-8 字节，原始 HTTP 请求体上限为 4096 字节；重复提交返回 `409`，非成员返回 `404`。这些 A/B 结果描述当前接口合同，并不意味着消息已经落盘。

因此，若 Pod 被驱逐、节点故障或进程重启，内存中的已受理消息可能消失；此前的 `200` 不应被解释为“可恢复”。未来 S3/v2 即使提议引入 DB，也仍受 6B 合同约束，且 R9 尚待审；在该责任正式落地前，不能把“有数据库计划”当作当前持久保证。

### 用requests判断调度，用limits判断运行边界

### 用 requests 判断调度，用 limits 判断运行边界

调度器首先看节点的**可分配资源**，而不是节点机器的物理总量。对某个资源，近似计算为：

$$
\text{剩余可分配量}=\text{Node allocatable}-\sum\text{已调度 Pod 的 requests}
$$

设某节点 `allocatable` 为 `cpu=2000m`、`memory=4Gi`；已有 Pod 共声明 `cpu requests=1500m`、`memory requests=3Gi`。新 IM 网关 Pod 声明：

```yaml
resources:
  requests:
    cpu: 400m
    memory: 768Mi
  limits:
    cpu: 1000m
    memory: 1Gi
```

则剩余资源只有 `500m CPU` 与 `1Gi 内存`，均不小于网关的 request，因此它可以被调度。反之，即使节点监控显示当前 CPU 空闲很多，只要 `requests` 放不下，调度器仍会拒绝该节点。

`limit` 不决定“能不能放进去”，而是决定容器运行时的上界：

- CPU 使用超过 `cpu limit=1000m` 时，通常被 CFS 节流：请求变慢、处理积压，但进程一般不会立刻退出。
- 内存超过 `memory limit=1Gi` 时，容器可能被内核 OOM Kill，随后重启；仅内存受理的 `200` 消息会丢失。
- `Ready=True` 只表示当前健康检查通过，不能证明数据库已持久化消息，也不能证明 OOM 或节点重启后可恢复。

因此，结果 A“Pod 已调度且 Ready”只能推出网关当前可接流量；结果 B“消息重启后仍可恢复”还需要权威持久存储。S2/v1 的 `200` 仅表示内存受理，不能把资源充足误读为可靠存储。

### Ready与200：请求成功不代表消息已经落盘

### Ready与200：请求成功不代表消息已经落盘

`Ready=true` 表示网关Pod当前通过了就绪检查，可以接收流量；`HTTP 200` 则只表示该请求已被当前版本接受并完成了合同规定的处理。二者都不是“已持久化”的证明。

在 S2/v1 静态合同中，发送消息时应先按边界判断：

- 正文最多为 `6 UTF-8B`；注意是编码后的字节数，不是 Go 的 `len([]rune(s))` 字符数。
- 整个原始 HTTP 请求体最多为 `4096B`。
- 同一消息标识重复提交，返回 `409`。
- 发送者不是会话成员，返回 `404`。
- 只有通过上述校验的新消息，才可能返回 `200`。

但这里的 `200` 含义是：消息被网关的**内存状态**受理，例如写入进程内的会话消息列表。它并未承诺写入磁盘、数据库、消息队列或其他权威副本。因此可出现以下结果：

| 观察到的状态 | 实际含义 |
|---|---|
| Pod 已调度 | Node 有足够资源满足Pod的 `request`，并不说明有存储 |
| Pod Ready | 容器当前可处理请求，并不说明历史消息可恢复 |
| 返回 200 | 本进程内存已接受消息，并不说明重启后仍存在 |
| 重启后消息消失 | 符合 S2/v1 的内存受理语义，不应据此推断接口故障 |

例如，客户端收到 `200` 后，若网关因超出 `limit` 被终止、滚动更新或Node故障而重建，内存中的消息自然消失。此前的 `200` 仍是正确响应：它没有违反“仅内存受理”的合同。

未来 S3/v2 即使提出接入数据库，也不能自动改变语义。正文仍受 `6B` 限制，R9 仍处于待审状态；在合同明确把 `200` 定义为“权威存储确认”之前，客户端不能把成功响应当作落盘确认。

### emptyDir、PV与PVC：数据跟谁一起消失

### emptyDir、PV与PVC：数据跟谁一起消失

`emptyDir` 的归属对象是 **Pod**，不是容器。容器因崩溃而重启时，只要 Pod 未被删除，挂载在同一 Pod 中的 `emptyDir` 通常仍在；因此它可用于缓存、临时文件或同 Pod 容器间交换数据。可是 Pod 被驱逐、滚动更新后重建、迁移到其他节点，或节点故障导致原 Pod 不可恢复时，`emptyDir` 中的数据应视为丢失。它不能承担网关消息恢复。

PV 是实际存储资源，PVC 是 Pod 对该资源提出的声明。Pod 重建后，只要新的 Pod 重新挂载同一 PVC，且后端存储与挂载过程正常，数据可以跨 Pod 延续；这与 `emptyDir` 的生命周期不同。但“使用了 PVC”仍不等于“消息已持久化”：

- 容器把数据写入内存后返回 `200`，尚未写卷，重启仍会丢；
- 写入卷不代表已经完成数据库事务、复制确认或索引更新；
- 节点故障时，网络卷可能需要解绑、重挂载；短暂不可用不应被误判为数据已消失；
- PVC 被删除、PV 回收策略生效、底层盘损坏或误挂载，均可能改变数据可见性或保留性。

因此，`Ready` 只能说明当前实例可接流量，不能证明恢复链路成立。S2/v1 中 `200` 的含义仍是“仅内存受理”；即使未来 S3/v2 引入数据库，仍须在合同中明确：哪一步构成权威提交、失败时返回何种结果、重试如何保持重复请求 `409`、以及成员不存在为何仍是 `404`。卷提供的是存放条件，业务权威性来自可验证的提交协议。

### 从RWO/RWOP到S3：为数据库恢复责任留接口

### 从RWO/RWOP到S3：为数据库恢复责任留接口

`RWO`（ReadWriteOnce）表示卷可被**一个节点**以读写方式挂载；同一节点上的多个 Pod 在具体存储驱动允许时可能共享它。`RWOP`（ReadWriteOncePod）更严格：读写挂载权限定为**一个 Pod**。它们解决的是“谁能挂载磁盘”，不是“消息是否已恢复”。

因此，网关 Pod 即使满足 Node 资源、通过 `request/limit` 调度并显示 `Ready`，也只能说明当前进程可服务。若 S2/v1 的 `200` 仅表示消息进入内存队列，那么：

- Pod 重启、迁移或节点故障后，内存消息仍会丢失；
- RWO/RWOP 卷即使存在，也不自动把 Go 内存对象写入数据库；
- 多副本网关不能把“某个 Pod 的本地内存”当作共同权威状态。

当前静态合同仍应明确：UTF-8 正文最多 `6B`，原始 HTTP 体最多 `4096B`；重复消息返回 `409`，非成员返回 `404`，`200` 仅表示内存受理，而非持久化确认。

未来 S3/v2 即使继续保留 `6B` 正文限制，恢复语义的责任边界也将转移到数据库提议：只有事务提交、可按消息标识去重、重启后可重新读取，才可声称具备恢复能力。R9 尚待审时，不应提前把 PVC、RWO、RWOP 或 `Ready` 描述为“消息可靠恢复”的证据。

> **要点** — 调度与Ready证明资源和探针状态；只有明确的权威持久存储与恢复合同，才能证明消息可恢复。

网关Pod能否启动，首先取决于调度器账本中的请求量，而非节点监控里瞬时空闲的CPU。

### 先算可分配资源，不看瞬时利用率

### 先算可分配资源，不看瞬时利用率

调度器决定 Pod 能否落到节点时，核对的是**可分配资源**与各 Pod 的 **request 总和**，不是监控面板上“当前 CPU 用了多少”。

设节点 N1 的 `allocatable` 为：

- CPU：`2` 核
- 内存：`4GiB`

节点上现有工作负载已声明：

- CPU request：`1.7` 核
- 内存 request：`3GiB`

现在部署 gateway，其资源请求为：

```text
cpu:    500m
memory: 512MiB
```

调度器的账本计算为：

$$
CPU: 1.7 + 0.5 = 2.2 > 2
$$

$$
Memory: 3 + 0.5 = 3.5 < 4
$$

因此，尽管内存满足，N1 仍因 CPU request 超出 `allocatable` 而不能接收该 Pod，gateway 会保持 `Pending`。即使节点监控显示实时 CPU 利用率只有 20%，结论也不变：瞬时空闲不等于可被调度器承诺的容量。

需要区分三类指标：

- `capacity`：节点物理或逻辑总资源。
- `allocatable`：扣除系统、Kubernetes 组件预留后，可供 Pod 调度的资源。
- `request`：Pod 请求的调度账本额度；调度器主要按它做准入判断。

若 N2 的剩余 request 容量足够，调度器可以将 gateway 放到 N2。`cpu request` 表示争用时的相对保障和调度依据，并非持续独占；即使设置 `limit: 1CPU`，高负载时也可能被 CFS 节流。

### N1算例：CPU超账即Pending

### N1算例：CPU超账即Pending

设 N1 的可分配资源为 `2 CPU / 4 GiB`，节点上已被其他 Pod 的 `request` 记账为：

- CPU：`1.7 CPU`
- 内存：`3 GiB`

现在提交一个网关 Pod，其资源请求为：

- `cpu request = 500m = 0.5 CPU`
- `memory request = 512MiB = 0.5 GiB`

调度器将其加入 N1 的账本后，逐项计算：

\[
\text{CPU 请求总量}=1.7+0.5=2.2\ \text{CPU}
\]

\[
\text{内存请求总量}=3+0.5=3.5\ \text{GiB}
\]

与 N1 可分配量比较：

| 资源 | 加入后请求量 | N1 可分配量 | 结果 |
|---|---:|---:|---|
| CPU | 2.2 CPU | 2 CPU | 超出 0.2 CPU |
| 内存 | 3.5 GiB | 4 GiB | 尚余 0.5 GiB |

因此，N1 不满足该 Pod 的 CPU 请求，调度器会将其判定为不可放置；即使内存仍有余量，也不能用“内存足够”抵消 CPU 的不足。资源检查是逐维约束：任意一种已请求资源超账，该节点就会被排除。

这里的关键是，调度器依据的是 `request` 账本，而不是监控页面显示的瞬时 CPU 使用率。即便 N1 此刻实际只用了很少的 CPU，`1.7 CPU` 的既有请求加上网关的 `500m` 仍会使账面达到 `2.2 CPU`，网关 Pod 因而保持 `Pending`。若 N2 的剩余可分配 CPU 至少为 `500m`、内存至少为 `512MiB`，调度器才可能将它放到 N2。

### N2有余：调度器如何寻找落点

### N2有余：调度器如何寻找落点

调度器会逐节点核对“可分配资源减去已请求资源”，而不是查看监控图上的瞬时 CPU 利用率。设网关 Pod 声明：

- `requests.cpu: 500m`
- `requests.memory: 512Mi`
- `limits.cpu: 1`

N1 的 `allocatable` 为 `2 CPU / 4GiB`，已有工作负载累计请求 `1.7 CPU / 3GiB`。放入网关后：

$$CPU=1.7+0.5=2.2>2$$
$$Memory=3+0.5=3.5<4$$

虽然内存仍够、监控中 CPU 也许实时空闲，但 N1 的 CPU 请求账本超额，因此该节点不满足条件。调度器会跳过 N1；这不是网关镜像、配置或应用进程故障，而是明确的节点资源约束。

若 N2 尚有 `1 CPU / 2GiB` 可用于新的请求，则网关加入后仍满足 CPU 与内存约束，N2 成为可行落点。调度器会在所有可行节点中再按打分策略选择节点，随后 Pod 才能绑定并启动。

还要区分：`request` 决定能否调度及 CPU 争用时的相对权重，不代表持续独占；`limit: 1 CPU` 则是运行期上限。网关即使成功落到 N2，负载高时也可能被限制在 1 CPU 而发生节流，但这与 N1 上的 `Pending` 是两个不同阶段的问题。

### 请求是准入账本，不是CPU保底

### 请求是准入账本，不是 CPU 保底

调度器先看 `request`，把它当作节点容量账本中的准入成本；它不会依据监控面板上“此刻 CPU 空闲多少”来决定放置 Pod。若 N1 的可分配资源为 `2 CPU/4GiB`，已有工作负载请求 `1.7 CPU/3GiB`，网关声明：

`requests: 500m CPU, 512MiB memory`

则 CPU 请求合计为 `2.2 CPU`，超过 N1 的 `2 CPU`，即使节点实时 CPU 利用率很低，Pod 仍会在该节点上不可调度并保持 `Pending`。内存合计虽仅为 `3.5GiB`，也不能抵消 CPU 账本超额；应选择仍有足够请求余量的 N2，或调整请求配置。

`CPU request` 有两层含义：

- **调度阶段**：占用准入账本，决定节点是否“放得下”。
- **运行争用时**：影响相对 CPU 份额。多个容器竞争 CPU 时，较高 request 通常获得更高权重；但在节点空闲时，`500m` 并不表示容器只能使用 `0.5` 核，也不表示一定持续获得 `0.5` 核。

`CPU limit: 1` 则定义可使用的硬上限。网关突发超过 1 核时，可能被 CFS 节流，表现为延迟升高、吞吐下降，而非因 CPU 超限被直接杀死。

内存的边界不同：`memory request` 同样用于调度准入；`memory limit` 是更严格的运行上限，进程超过后通常触发 `OOMKilled`。因此，CPU limit 主要防止无限抢占并可能带来节流，内存 limit 则必须为峰值、缓存和恢复期负载留出安全余量。

### 1CPU限制下的网关节流影响

### 1CPU限制下的网关节流影响

网关即使被成功调度到节点，也可能因 `cpu limit: 1` 在高峰期出现明显抖动。这里的 1CPU 不是“平均可用 1 个核”，而是容器在 CFS 配额周期内最多消耗约一个逻辑核的计算时间；超过配额时，内核会暂停该容器直到下一个周期，形成 CPU 节流。

网关的 CPU 消耗往往具有突发性：

- 大量客户端同时建连、TLS 握手或认证；
- 消息批量到达，需要协议解析、序列化/反序列化、压缩或编解码；
- 上游或下游短暂变慢，导致连接管理、重试、积压扫描和转发同时增加；
- 日志、指标采集、垃圾回收与业务线程竞争同一份 1CPU 配额。

因此，`request: 500m`、`limit: 1` 表示调度时仅按 0.5 核记账，但运行中最多只能使用 1 核。`request` 影响调度与争用权重，不等于持续获得 0.5 核；`limit` 才是不可越过的硬上限。节点实时仍有空闲 CPU 时，容器也可能因自身配额耗尽而被节流。

排查时重点关联网关延迟、连接建立失败、消息积压与 CPU 节流指标，例如 `container_cpu_cfs_throttled_seconds_total`、节流周期数和容器 CPU 使用率。若使用率长期贴近 1 核且节流同步上升，应区分是正常突发还是容量不足：可先降低编解码与日志开销、优化批处理和并发模型，再根据峰值负载提高 CPU limit；同时评估提高 request 对节点装箱与调度可行性的影响。

> **要点** — N1实时CPU空闲不改变请求账本超额；请求决定能否调度，CPU限制决定运行时是否被节流。

网关Pod能被调度，只说明资源账本暂时允许；当负载逼近限制时，真正决定用户是否掉线、消息能否恢复的是内核证据、应用行为与持久化责任。

### 从资源限制读出运行边界

### 从资源限制读出运行边界

设网关 Pod 配置为 `requests.cpu=1`、`limits.cpu=1`、`requests.memory=1GiB`、`limits.memory=1GiB`。它的边界不是“永远拥有一颗核和 1GiB 内存”，而是三组不同含义的数据：

- **请求值**：调度器的账本。`1 CPU/1GiB` 表示节点必须有相应可分配资源，Pod 才能被放置；它不保证运行时没有竞争。
- **限制值**：内核 cgroup 的运行上限。CPU 到顶通常触发 CFS 限速，进程仍存活但请求排队、心跳延迟、连接超时；内存接近或超过 `1GiB` 时，内核可能回收页缓存、触发 OOM，最终杀死容器进程。
- **实际使用量**：监控看到的瞬时或累计消耗，如 CPU 使用率、RSS、工作集、页缓存和内核记账。它决定当前是否逼近边界，但不能只看单个应用指标下结论。

对 CPU，可将 `1 CPU` 理解为平均每个调度周期最多获得约一颗逻辑核的计算时间；突发并发即使短暂超过，也会形成 `cpu.stat` 中的节流证据。对内存，`1GiB` 是整个容器 cgroup 的总账，不只是 Go 堆：Go heap、goroutine 栈、运行时元数据、RSS、共享库、网络缓冲区及部分页缓存都会占用额度。`GOMEMLIMIT` 只能约束 Go 运行时的内存目标，不能把容器总内存锁定在安全线内。

因此，排障应把“接近限制”与“已经受限”分开：前者看使用量趋势，后者同时核对 `cpu.stat`、`memory.events`、Pod 状态、容器重启次数与退出码。资源限制定义的是运行边界，不是消息恢复能力；进程未被杀，也可能因 CPU 节流而错过协议时限。

### CPU超限通常是节流而非终止

### CPU超限通常是节流而非终止

对设置了 `limit: 1 CPU` 的网关 Pod，CPU 使用需求超过 1 核时，Linux cgroup 通常不会像内存超限那样直接杀进程，而是通过 CFS 配额限制其可运行时间。Pod 仍可能处于 `Running`、`Ready`，却已无法及时处理握手、心跳、转发和确认。

可在容器对应 cgroup 中查看 `cpu.stat`，重点关注：

- `usage_usec`：累计实际获得的 CPU 时间；
- `nr_periods`：进入 CPU 配额统计周期的次数；
- `nr_throttled`：发生节流的周期数；
- `throttled_usec`：累计被迫等待、未获 CPU 的时间。

若 `nr_throttled` 持续增长，且 `throttled_usec` 在流量高峰陡增，说明延迟并非一定来自网络或下游服务，而是网关本身在等待 CPU 配额。其链路通常是：

$$
\text{CPU 节流} \rightarrow \text{事件循环延迟} \rightarrow \text{请求/消息处理变慢}
\rightarrow \text{队列积压} \rightarrow \text{心跳超时与重连}
$$

此时 Kubernetes 状态往往没有明显异常：容器未重启、退出码为空或仍为 `0`、Pod 也未必触发 `OOMKilled`。因此，不能仅凭“Pod 正常运行”排除资源问题。

排查时应将同一时间窗内的 `cpu.stat`、容器 CPU 使用率、请求延迟、队列长度和连接断开率并列观察。尤其要区分“平均 CPU 未满 1 核”与“短时间突发被节流”：平均值可能平稳，但关键请求恰好落在被限速的周期内，用户看到的仍是卡顿、消息确认变慢或连接频繁重建。

### 内存逼限为何可能导致进程死亡

### 内存逼限为何可能导致进程死亡

`limit: 1GiB` 不是“应用可稳定使用 1GiB”，而是 cgroup 内存账本的硬边界。内核会先尝试回收可回收页：文件缓存、部分匿名页或可交换页；回收成功时，请求可能只是变慢、延迟升高。若回收无法满足新的内存分配，cgroup 进入 OOM 路径，内核选择受害进程终止，网关便可能直接中断连接与处理中消息。

先在容器对应 cgroup 观察：

- `memory.events` 中 `high` 增长：曾越过 `memory.high`，发生节流或回收压力；
- `oom` 增长：内存分配失败，触发 OOM 判断；
- `oom_kill` 增长：该 cgroup 内确有进程被 OOM killer 杀死；
- `max` 增长：触及 `memory.max`，通常意味着已碰到限制边界。

再与 Kubernetes 状态链路交叉验证。容器状态出现 `reason: OOMKilled`，且终止退出码通常为 `137`（收到 `SIGKILL`），可将“容器重启”归因到 cgroup 内存超限。仅看 `restartCount` 或 `137` 不足以定论：`137` 也可能是人为强制停止；应以 `memory.events` 的 `oom_kill`、容器终止原因和节点日志共同确认。

还要区分节点压力驱逐：此时 Pod 可能显示 `Evicted`，事件中带有 `MemoryPressure` 或节点可用内存不足；它是 kubelet 为保护节点主动驱逐，不等同于容器自身触发 OOM。QoS 会影响驱逐排序，但即使是 `Guaranteed`，进程仍可能因自身 `1GiB` cgroup 上限被杀。尤其 Go 的 heap、`GOMEMLIMIT` 与 RSS 都不是容器总内存：运行时元数据、goroutine 栈、mmap、网络缓冲及文件缓存都会共同消耗该账本。

### Go内存指标不能替代容器证据

### Go内存指标不能替代容器证据

Go 网关暴露的 `heap_alloc`、`heap_inuse` 或 GC 次数，只描述 Go 运行时管理的堆；它们不是 Pod 的实际内存账本。即使堆看似稳定，容器仍可能因总内存接近 `limit` 而被内核回收或 OOM 杀死。

需要区分四层含义：

- **Go heap**：Go 对象占用及运行时保留的堆空间，受 GC、对象生命周期和分配策略影响。
- **RSS**：进程当前驻留在物理内存中的页，除 Go 堆外，还可能包含 goroutine 栈、运行时元数据、二进制代码、`mmap`、动态库及部分页缓存。
- **`GOMEMLIMIT`**：Go GC 的软内存目标，用于更积极地回收可回收堆；它不是 cgroup 限制，也不能阻止栈增长、原生库分配或内核记入容器的其他内存。
- **容器内存使用量**：cgroup 统计的总量，可能包含进程 RSS、共享页计费、匿名页、文件页缓存，以及同一 Pod 中其他容器的消耗。

因此，`GOMEMLIMIT=800MiB` 并不意味着 `1GiB` 容器一定安全：剩余空间还要容纳运行时非堆内存、网络缓冲、TLS/压缩库、日志、页缓存及突发分配。反过来，heap 接近上限也不必然立即 OOM，关键仍是 cgroup 当前使用量和内核事件。

排障时应同时比对：应用堆指标、进程 RSS、`memory.current`、`memory.events` 中的 `high`、`max`、`oom`、`oom_kill`，以及 Kubernetes 的重启原因和退出码。只有当这些证据在同一时间窗内一致，才能判断是 Go 堆压力、容器总内存逼限，还是节点驱逐导致的失败。

### QoS排序不等于消息恢复保证

### QoS排序不等于消息恢复保证

Kubernetes 的 QoS 影响节点发生内存压力时的驱逐倾向，但它是**资源回收排序线索**，不是会话、消息或业务状态的可靠性承诺。

- **Guaranteed**：Pod 中每个容器都为 CPU 和内存同时设置 `request=limit`。在同等优先级和资源使用条件下，通常最不容易被驱逐。
- **Burstable**：至少有一个容器设置了资源请求或限制，但并非所有容器都满足 `request=limit`。当其实际使用量超过请求值时，更可能成为回收对象。
- **BestEffort**：所有容器均未设置 CPU、内存请求和限制，通常最先被驱逐。

实际驱逐还会结合 Pod 优先级、内存使用是否超过请求、节点压力类型等判断；即使是 Guaranteed Pod，也可能因进程自身 OOM、节点严重压力或应用异常而失败。QoS 只能降低“谁先被赶走”的概率，不能让网关天然具备恢复能力。

尤其要区分状态边界：S2 阶段若连接上下文、未确认消息、订阅关系仅保存在网关内存中，Pod 被驱逐、重启或 OOM 后，这些状态仍会丢失；`Guaranteed` 不能把 RAM 变成持久存储。进入未来 S3 阶段后，数据库、消息系统或复制日志才承担恢复责任：需要明确写入确认点、副本数量、重放规则与幂等键。资源配置负责降低故障频率；持久化协议才负责决定故障后能恢复什么。

> **要点** — 调度成功不是可靠性证明：CPU节流看延迟，内存异常看证据，消息恢复必须由权威持久化承担。

网关Pod能够被调度，只说明计算资源满足条件；消息能否在替代、故障与恢复后保留，取决于数据实际写入的位置及其责任边界。

### 从Pod UID理解emptyDir的消失边界

### 从Pod UID理解emptyDir的消失边界

`emptyDir` 是为**某个具体 Pod 实例**创建的临时目录，其生命周期绑定的是 Pod 的 `UID`，而不是 YAML 中的 Pod 名称、Deployment 名称或网关实例名。

这一区分决定了两类看似相近、实际结果不同的故障场景：

- **容器重启：数据通常仍在**  
  同一 Pod 内的业务容器因进程崩溃、健康检查失败或 OOM 被重启时，Pod 本身并未被删除，`UID` 不变。挂载到该 Pod 的 `emptyDir` 目录仍存在，因此容器可以再次看到先前写入的文件、缓冲消息或本地状态。

- **Pod 被替代：数据必然丢失**  
  当 Pod 被删除、驱逐、节点故障后重建，或 Deployment 创建新的副本时，新 Pod 即使名称恰好相同，也会获得新的 `UID`。Kubernetes 会为它创建新的 `emptyDir`；旧 Pod 对应目录随旧 Pod 生命周期结束而失去，不会自动迁移或恢复。

例如，网关将待投递消息写入：

`/var/lib/gateway/queue`

若该路径来自 `emptyDir`，则“容器重启后消息还在”不能证明“滚动更新、节点失效或副本替代后消息可恢复”。前者只是同一 Pod 内的进程恢复；后者已经进入新的 Pod 身份边界。

因此，`emptyDir` 适合缓存、解压目录、进程间共享文件和可重新生成的临时数据；不应承担需要跨 Pod 替代保存的消息队列、未确认投递记录或恢复检查点。判断持久性时，应问：**数据是否仍属于同一个 Pod UID？**

### PV、PVC与StorageClass的职责分层

### PV、PVC与StorageClass的职责分层

要判断网关状态、消息队列文件或本地数据库能否跨 Pod 恢复，先应把“存储对象”拆成三层，而不是只看 PVC 是否显示为 `Bound`。

- **PV（持久卷）**是集群级存储资源。它描述一块可被挂载的存储及其属性，例如容量、访问模式、回收策略、底层类型与拓扑限制。PV 可能由管理员预先创建，也可能由系统动态创建；它不属于某个命名空间。
- **PVC（持久卷声明）**是命名空间内工作负载提出的存储请求。声明通常包含所需容量、访问模式以及期望的 `StorageClass`。Pod 并不直接“拥有”底层磁盘，而是引用 PVC；控制面为该请求选择或创建可匹配的 PV，并建立绑定关系。
- **StorageClass（存储类）**定义“如何供应或约束存储”。它可指定供应器、性能等级、允许的卷扩展、回收策略、卷绑定时机，以及是否受可用区、节点拓扑等条件限制。它不是数据本身，也不等同于备份策略。

关系可概括为：

`Pod → PVC（命名空间请求）→ PV（集群存储资源）`

当 PVC 指定 StorageClass 且没有现成 PV 满足条件时，常见流程是：

`PVC → StorageClass → 动态供应器创建 PV → PVC 与 PV 绑定 → Pod 挂载 PVC`

但 `Bound` 只说明“某个声明已经获得可挂载的卷”，不能推出更多结论。它不证明应用已将消息写入该卷，不证明数据库事务一致，不证明卷可跨可用区挂载，也不证明存在备份、快照或异地副本。尤其当 StorageClass 使用本地盘、分区卷或具有节点亲和性的后端时，替代 Pod 能否调度到可访问该卷的位置，仍需结合 PV 拓扑、访问模式与故障域单独判断。

### Bound状态不能证明业务可恢复

### Bound状态不能证明业务可恢复

`PVC` 显示 `Bound`，仅能证明：某个命名空间中的存储请求，已经成功绑定到一个 `PV`，并满足其容量、访问模式、`StorageClass` 等声明条件。它不是“消息已持久化”“数据库可回滚恢复”或“跨可用区可用”的证明。

应把证据链分开检查：

- **PVC 已绑定**：卷对象存在且可被声明引用；还需确认网关或数据库容器实际挂载的是该卷，而非把关键数据写入镜像层、`emptyDir` 或错误路径。
- **数据库事务已提交**：应用必须收到数据库提交成功的确认。卷可用不代表事务完成；请求可能在写入前失败、在提交响应返回前超时，或因主从复制滞后而丢失最近数据。
- **备份可用**：需要存在独立于在线卷的备份副本，并验证备份时间点、保留策略、加密密钥、恢复权限与实际恢复演练。快照创建成功也不等于能恢复出可启动、数据一致的数据库。
- **跨可用区容灾成立**：需确认底层卷的拓扑范围、复制机制和故障切换方式。某些 `PV` 是单可用区资源；即使 `PVC` 为 `Bound`，节点或可用区故障后，替代 Pod 仍可能无法挂载原卷。

因此，`Bound` 是“存储声明已配对”的控制面状态。业务恢复能力应以“已提交数据可从独立副本恢复，并在目标故障域重新提供服务”的演练结果作为证据，而不能由一个 PVC 状态字段推断。

### RWO与RWOP如何限制挂载行为

### RWO与RWOP如何限制挂载行为

`ReadWriteOnce（RWO）`表示一个卷可被**单个节点**以读写方式挂载。限制对象是节点，不是 Pod：同一节点上的多个 Pod 在底层驱动允许时，可能同时挂载并读写同一 PVC；不同节点上的 Pod 则通常不能同时获得读写挂载。因此，RWO 不等于“只能有一个副本”，更不等于“只能有一个进程写入”。

`ReadWriteOncePod（RWOP）`更严格：在整个集群范围内，同一时刻只允许**一个 Pod**以读写方式挂载该卷。若旧 Pod 尚未完成卸载，替代 Pod 即使已经调度成功，也可能因卷仍被占用而卡在挂载阶段。RWOP 适合明确要求单实例占有的数据目录，例如单副本数据库的本地数据卷；其支持还依赖 CSI 驱动及 Kubernetes 版本能力。

需要区分三个层面：

- **访问模式**：RWO/RWOP 是 PVC 对卷挂载拓扑与并发挂载的声明、约束或期望，具体可执行范围受 StorageClass 和存储驱动支持影响。
- **节点条件**：RWO 的关键是“是否同一节点”；Pod 被重新调度到另一节点时，常需先完成旧节点卸载、再附加和挂载到新节点。
- **应用写入安全**：即使多个 Pod 能挂载，也不代表应用可以安全并发写入。文件锁、日志格式、数据库一致性协议、崩溃恢复与缓存一致性仍由应用和文件系统负责。

因此，看到 PVC 为 `Bound`，只能说明它已绑定某个 PV；不能据此推断故障切换一定无数据损失，更不能推断数据库事务、备份策略或跨可用区恢复已经成立。

### IM网关缓存与未来数据库权威分工

### IM网关缓存与未来数据库权威分工

以 S2、S3 两代 IM 网关演进为例，应先区分“加速数据”和“权威数据”。

S2 网关可将在线会话、连接索引、未确认消息副本放入内存，并用 `emptyDir` 暂存重试队列、分片拉取结果或短期文件缓存。这样做能降低数据库读写压力，也允许同一 Pod 内的容器共享临时文件；但 `emptyDir` 绑定的是 Pod UID，而不是 Deployment 名称或节点名称。Pod 被删除、驱逐或替代后，新 Pod 即使名称相同，也会得到新的空目录。

因此，S2 中的临时卷只能承担：

- 请求去重窗口、限流计数、热点会话缓存；
- 可重新从上游拉取的消息副本；
- 可接受丢失的重试状态，或能由幂等机制重建的工作项。

S3 引入数据库后，消息正文、会话序号、投递状态、已读游标等恢复所必需的数据，应在确认成功前写入持久化系统。网关可先写缓存，但不能把“写入 `emptyDir` 成功”视为消息已持久化；客户端确认、服务端投递确认与数据库事务提交需要有明确的顺序和失败语义。

PV 提供集群层面的存储资源，PVC 是命名空间内对该资源的请求与绑定，StorageClass 则定义供应方式、性能或拓扑约束。即使 PVC 显示为 `Bound`，也只说明卷绑定完成，不能自动证明数据库事务正确、备份可恢复，或故障切换后跨可用区仍可访问。消息恢复责任应落在数据库及其复制、备份、校验和演练机制上，而非网关的内存或临时卷。

> **要点** — Pod可调度和PVC已绑定都不等于消息可恢复；恢复能力必须由权威数据库、事务、备份与容灾证据共同保证。

卷能挂载不代表消息能恢复：访问模式、拓扑约束与数据库事务共同决定故障后的真实边界。

### 从访问模式读懂共享边界

### 从访问模式读懂共享边界

`ReadWriteOnce（RWO）`约束的是**节点**，不是 Pod：卷可被单个节点以读写方式挂载；同一节点上的多个 Pod 在驱动、挂载方式与权限允许时，可能同时访问该卷。因此，RWO 不等于“只能有一个 Pod 写入”，更不等于应用天然获得单写者保证。

`ReadWriteOncePod（RWOP）`进一步约束到**单个 Pod**：同一时刻仅允许一个 Pod 读写该卷。它适合需要排他磁盘语义的数据库实例，但依赖 CSI 驱动及 Kubernetes 版本支持；不能假定所有存储类都能正确实施这一限制。

更危险的误解是：多个 Pod 能挂载同一卷，就等于拥有共享状态。共享文件系统只提供字节可见性，不自动提供：

- 写入顺序、互斥锁与故障后的锁恢复；
- 副本复制、数据校验与仲裁；
- 消息去重、偏移量提交和事务原子性；
- 网络分区时的主从判定。

因此，多个网关 Pod 即使共同访问一个 `RWX` 卷，也可能并发覆盖文件、读到部分写入，或在故障恢复后重复投递。卷访问模式回答的是“谁能挂载”，不是“谁拥有消息事实”。消息的 `m-9/seq9` 是否已确认、是否可重放，仍应以数据库日志及其事务提交记录为权威。

### RWO 约束节点，不等于只允许一个 Pod

### RWO 约束节点，不等于只允许一个 Pod

`ReadWriteOnce（RWO）` 的含义通常是：卷可被**一个节点**以读写方式挂载；它并不天然等价于“只能有一个 Pod 使用该卷”。如果多个 Pod 被调度到同一节点，并且运行时与 CSI 驱动允许，它们可能同时读写同一个 RWO 卷。

这一区别对网关故障处理很关键：

- 网关 Pod 重建到**同一节点**时，RWO 往往仍可挂载；但两个误配置的副本若同节点运行，可能共同访问同一数据库目录、日志目录或缓存文件。
- 网关 Pod 漂移到**另一节点**时，原节点尚未完成卸载、节点失联或存储后端存在附着延迟时，新的挂载可能失败，形成“Pod 已调度、卷未就绪”。
- RWO 不提供文件锁、写入仲裁、复制或一致性协议。多个 Pod 同时写入同一目录，不能据此推断消息状态可恢复。

`ReadWriteOncePod（RWOP）` 则进一步要求该卷在集群范围内只能被**一个 Pod**以读写方式挂载，更贴近“单实例持久状态”的意图。例如 `db-0` 的数据卷使用 RWOP 后，替代 Pod 必须等待原 Pod 完全释放卷，不能与其并行挂载。

但 RWOP 不是仅改一个声明就必然生效：它依赖 CSI 驱动及相关组件支持；不兼容的驱动、旧版本集群或错误的供应配置，可能无法提供预期的单 Pod 排他性。

因此，RWO/RWOP 解决的是挂载边界，不是消息权威性。`m-9/seq9` 是否已提交、是否可重放，仍应以数据库日志及其事务提交结果为准，而不能以“卷已重新挂载”作为判断依据。

### 同卷多挂载不是复制与仲裁

### 同卷多挂载不是复制与仲裁

把同一个卷挂到多个 Pod，解决的只是“多个客户端看见同一份存储”的问题；它并不自动产生副本，更不会替应用决定谁有资格写入。

- **不是复制**：共享文件系统或可多挂载的块设备通常只有一份后端数据。存储节点、网络路径或所在可用区失效时，多个挂载者可能同时失去访问能力；这与三副本数据库、跨节点日志复制完全不同。
- **不是写入序列化**：文件系统可能提供文件锁、追加写或元数据一致性，但不会理解 `m-9`、`seq=9`、消费者确认等业务含义。两个 Pod 同时更新同一条消息状态，仍可能出现覆盖、重复投递或“已确认但未持久化”的窗口。
- **不是故障仲裁**：旧 Pod 网络隔离后，新 Pod 若也获得写权限，就可能形成双写。存储侧是否支持 fencing、CSI 是否正确解绑、应用是否用租约或数据库事务排他，决定了故障切换是否安全。
- **不是恢复语义**：消息恢复应以数据库日志事务中的权威记录为准：消息写入、序号推进、确认状态变更必须具有明确提交边界。卷上“还能读到文件”只能说明数据介质可见，不能证明该消息已经提交、未被重复处理，或应由哪个实例继续执行。

因此，多 Pod 共享卷适合共享输入、静态文件或受控的单写者场景；若它承载消息状态，仍需由数据库事务、唯一约束、租约与 fencing 明确复制、排序和主写者规则。

### StatefulSet 稳定关联与重挂风险

### StatefulSet 稳定关联与重挂风险

以数据库工作负载 `db-0` 为例，`StatefulSet` 通过 `volumeClaimTemplates` 为每个副本生成带序号的独立 PVC。若模板名为 `data`、StatefulSet 名为 `db`，则 `db-0` 通常稳定绑定到 `data-db-0`；即使 `db-0` 因升级、驱逐或容器崩溃而重建，新 Pod 仍会请求同一个 PVC，而不会随机获得其他副本的数据卷。

这种稳定关联保证了“逻辑身份—数据目录”的连续性：

- `db-0` 重建后继续读取原有 WAL、数据文件与事务日志；
- `db-1` 不会误挂 `db-0` 的卷；
- 删除并重建 Pod 不等于删除 PVC，数据通常仍保留。

但稳定关联不等于随时可恢复。假设 `data-db-0` 是云盘，其拓扑位于可用区 `zone-a`，原 Pod 所在节点故障后，调度器若将新 `db-0` 放到 `zone-b`，该卷可能无法跨区挂载。即使新节点也在 `zone-a`，仍可能经历“旧节点挂载未释放、云盘正在解绑、CSI 附加操作等待”等阶段。

因此可出现如下状态：

`db-0` 已重建 → PVC 仍为 `Bound` → Pod 却长期 `Pending` 或卡在 `ContainerCreating`

这里的 `Bound` 只说明 PVC 与 PV 的声明关系仍有效，不表示卷已成功附加到新节点，更不表示数据库已经启动并完成日志恢复。对于依赖 `db-0` 持久日志确认消息权威状态的系统，网关 Pod 即使能够调度，也不能据此认定消息可恢复；必须等待数据库卷完成重挂、数据库完成崩溃恢复，并重新具备事务提交能力。

### 消息权威仍在数据库事务日志

### 消息权威仍在数据库事务日志

以消息 `m-9`、序号 `seq9` 为例，网关在 S2 阶段内存中可以暂存连接会话、未确认窗口、重试计时器与“已向下游发送”的局部标记。这些状态有助于降低延迟，却不能构成恢复依据：Pod 重启、驱逐、节点失效或进程崩溃后，S2 内存会消失；即使卷仍可重新挂载，也不能从内存推断 `m-9` 到底是否已被持久接收、是否已提交，或是否已对外生效。

未来 S3 的恢复权威应是数据库事务日志。处理 `m-9/seq9` 时，至少要在同一事务语义下记录：

- `seq9` 对应的消息标识、载荷或可重建引用；
- 消费/投递状态，例如“已接收”“处理中”“已完成”；
- 去重键或唯一约束，防止恢复后重复执行；
- 必要的业务结果与提交位置。

只有数据库确认事务提交后，系统才能把 `seq9` 视为可恢复的事实。若网关在提交前崩溃，恢复实例应允许重放 `m-9`；若提交已完成但确认响应丢失，则应依据日志和唯一键识别重复，而不是再次产生业务副作用。

因此，卷的 RWO、RWOP 或 StatefulSet 稳定卷关联，只解决“谁能挂载数据”的一部分问题；它们不自动提供消息复制、提交仲裁或幂等判定。消息恢复的最终边界应由数据库日志事务定义，而不是由某个网关 Pod 曾经保存过的 S2 内存定义。

> **要点** — RWO/RWOP只定义挂载边界；卷不提供消息一致性，m-9/seq9 的恢复权威必须落在数据库事务日志。

网关Pod能够调度，只说明资源账本暂时允许它运行；它并不证明CPU高峰稳定、内存不会被杀，更不证明重启后的消息还能恢复。

### 从N1到N2：先算清请求能否落点

### 从N1到N2：先算清请求能否落点

在 $t0$，网关请求不能落到 N1，并不意味着镜像、端口或应用配置异常；调度器首先检查的是节点**可分配资源**能否覆盖 Pod 的 `requests`。

节点可分配量不是机器物理总量，而是：

$$
\mathrm{Allocatable}
=
\mathrm{Capacity}
-\mathrm{system\ reserved}
-\mathrm{kube\ reserved}
-\mathrm{eviction\ reserved}
$$

例如，N1 有 `4 CPU`，扣除系统与驱逐预留后 `allocatable=3500m`；其已运行 Pod 的 CPU `requests` 合计为 `3200m`。新网关 Pod 声明：

`requests.cpu=500m`，`requests.memory=1Gi`

则 N1 的剩余 CPU 仅为：

$$
3500m-3200m=300m<500m
$$

即使 N1 此刻监控显示 CPU 实际使用率不高，调度仍会拒绝它：调度依据是已承诺的 `requests`，不是瞬时利用率。

再看 N2：若其 `allocatable=3500m`，已有请求合计 `2500m`，则剩余 `1000m`；同时剩余可分配内存不少于 `1Gi`，新 Pod 才能落到 N2。应逐项核对 CPU、内存以及可能的 `ephemeral-storage`、扩展资源；任一请求无法满足，节点即不合格。

因此，“网关被调度到 N2”只可推出：N2 在该时刻有足够的资源承诺余量。它不表示 N2 上实际 CPU 峰值稳定，更不表示该 Pod 后续不会因内存压力重启。

### 请求、上限与1CPU节流边界

### 请求、上限与1CPU节流边界

`request` 与 `limit` 回答的是两类不同问题：

- **CPU request**：调度器据此判断节点是否“放得下”Pod。网关申请到例如 `500m` CPU，只表示节点资源账本中能为它预留相应份额；这解释了它为何能够被调度。
- **CPU limit**：运行时的硬上界。若网关被限制为 `1` CPU，则在任意 CFS 配额周期内，它最多只能使用一个核的计算时间；超过配额会被内核节流。
- **内存 request**：用于调度与资源预留，不等于进程实际只会使用这么多内存。
- **内存 limit**：内存不能像 CPU 那样靠“稍后再算”平滑处理。进程逼近或超过可用上限时，可能触发回收、分配失败，严重时被 OOM 杀死。

因此，t1 中“网关已成功调度”与“网关处理请求稳定”并不矛盾。连接突增、TLS 握手、JSON 编解码、路由计算或批量发送同时到来时，网关短时需要超过 `1` CPU。限额不会让请求消失，而是使可运行任务等待下一轮 CPU 配额：延迟升高、队列积压、心跳晚到，客户端可能观察到 WebSocket 卡顿、超时或重连。

应将 CPU 节流视为**性能边界**，而不是可恢复性保证。可结合容器的 `throttled` 时间、节流次数、请求延迟分位数和连接积压量确认影响；仅看到 Pod 为 `Running` 或 `Ready`，不能推出其在峰值期间未被 `1` CPU 上限限制。

### 从cgroup事件确认OOM而非猜测

### 从 cgroup 事件确认 OOM 而非猜测

t2 出现连接中断、Pod 重启或就绪状态短暂变为未就绪时，不能仅凭“内存看起来很高”就断言 OOM。应把容器级 cgroup 事件、Kubernetes 状态和应用现象按时间核对，形成可复查的证据链。

先读取对应容器 cgroup 的 `memory.events`，重点关注：

- `oom`：发生过内存分配无法满足的 OOM 条件；
- `oom_kill`：内核实际杀死了 cgroup 中的某个进程；
- `high`：内存超过 `memory.high`，进程开始被回收或节流；
- `max`：内存尝试超过 `memory.max` 的次数。

其中，`oom_kill` 在 t2 前后递增是最强证据。例如重启前为 `oom_kill 3`，重启后为 `oom_kill 4`，同时容器重启计数增加，则可推导：

$$
\text{cgroup 内存上限触发} \rightarrow \text{内核杀进程} \rightarrow \text{容器退出并重启}
$$

再与 Pod 状态对齐：`restartCount` 增加、上一次终止原因显示为 `OOMKilled`、就绪探针在重启窗口失败，分别对应“进程被替换”“退出原因”“服务暂不可接流量”。若 `memory.events` 未增长，却只有探针失败，则更可能是应用卡顿、CPU 节流、依赖超时或主动退出，不能写成 OOM。

最后还要区分“恢复运行”和“恢复消息”。Pod 重新 Ready 仅表示新进程已通过就绪检查；旧 WebSocket 已随旧进程消失，S2 中仅存在于内存的 `m-a` 也不会跨进程出现。是否已送达、是否需补发，应以后续数据库权威记录和设备 ACK 为准，而不是以 Ready 状态替代消息恢复证据。

### 重启后为何旧连接与S2消息消失

### 重启后为何旧连接与S2消息消失

WebSocket 是建立在某个具体进程、具体 TCP 连接上的长连接。网关 Pod 因内存超限被 `oom_kill`、容器退出、探针失败而重启时，旧进程持有的文件描述符、连接状态、收发缓冲区都会随进程消失。客户端看到的通常是连接关闭、超时或后续读写失败；即使新 Pod 使用相同 Service、相同地址重新 `Ready`，它也不是原来的那个连接端点。

S2 若只把消息 `m-a` 保存在进程内存，例如：

- WebSocket 会话对象中的待发送队列；
- 内存 Map 中的“已接收、待转发”记录；
- 尚未来得及刷入持久化系统的业务事件；

那么重启会直接清空这些数据。新进程最多重新监听端口、接受客户端重连，却无法从自身内存找回旧会话，更不知道 `m-a` 曾处于“已收未发”“已发未确认”还是“根本未收到”的阶段。

因此，`Ready=True` 只表示当前实例通过了就绪检查，可以接收**新的**流量；它不证明旧 WebSocket 已恢复，也不证明 S2 内存中的 `m-a` 被保存、重放或送达 N2。

要判断消息能否恢复，必须另查权威存储中的消息记录、投递状态与设备 ACK；若没有数据库、消息队列或可恢复日志作为依据，就不能把客户端重连或 Pod 重新 Ready 解释为消息恢复。

### 临时卷、持久卷与未来恢复责任

### 临时卷、持久卷与未来恢复责任

`emptyDir` 与 PV/PVC 的差别，首先是生命周期，而不是“是否挂载成功”。

- `emptyDir` 随 Pod 创建而创建、随 Pod 删除而删除。同一 Pod 内的容器重启通常仍可见其中数据；但 Pod 被驱逐、重建或调度到新节点后，旧卷内容不应视为可恢复状态。它适合临时缓存、转码中间文件或进程间短暂交换，不适合作为网关消息、会话或待确认命令的恢复依据。
- PV/PVC 将存储对象与 Pod 生命周期解耦。Pod 重建后，只要 PVC 仍绑定且后端存储可用，新的 Pod 可以重新挂载同一份数据。因此它可保存需要跨 Pod 存续的数据，但仍须验证应用是否真正落盘、日志是否刷写完成、数据格式是否能被新进程正确恢复。

访问模式进一步限制“谁能同时使用”该卷：

- `RWO`（单节点读写）：同一时刻通常只允许一个节点以读写方式挂载；同节点多个 Pod 是否可共享，还取决于存储实现。
- `RWOP`（单 Pod 读写）：同一时刻仅允许一个 Pod 读写该 PVC，适合避免主备网关同时写入同一状态目录造成竞争。

因此，网关从 `NotReady` 变为 `Ready`，最多证明新进程已通过就绪检查；它不证明旧 WebSocket 连接仍在，也不证明 S2 中内存的 `m-a` 已跨进程恢复。即使使用 PV，卷中存在文件也不等于消息语义完整：请求是否提交、是否已发送、设备是否已执行，仍可能未知。

未来恢复责任应明确拆分：数据库中的权威记录需单独核查事务、状态机与幂等键；设备 ACK 需单独核查协议确认、超时与重试结果。PVC 只能提供持久化载体，不能替代数据库权威性，更不能把“重新 Ready”解释为“消息已经恢复”。

> **要点** — 调度成功只代表请求可放置；限流、OOM与重启仍会中断连接并清空内存态，消息恢复必须由权威持久存储和ACK证据证明。

网关Pod显示可调度，只说明当前请求能被节点接纳；它并不等于高峰时延稳定、进程不会被杀，更不等于消息状态可以恢复。本节先建立资源、存储与业务责任的统一核对框架。

### 先固定证据边界，再讨论扩容

### 先固定证据边界，再讨论扩容

“可调度”只是调度器按 `request` 判断节点尚有可分配资源，并不证明网关在真实高峰下拥有足够的 CPU、内存、磁盘吞吐或可恢复的消息状态。扩容前先冻结证据边界，否则一次偶发超时、重启或消息缺失都可能被误判为“资源不够”。

至少同时记录以下事实：

- **版本边界**：OpenIM 服务端、网关、消息队列、数据库、镜像标签、Helm Chart 与 Kubernetes 版本；固定配置提交和生效时间。两个源码仓库存在，不等于当前集群资源参数正确或配置已发布。
- **负载窗口**：选定同一高峰时段，明确在线连接数、请求速率、消息写入速率、消息大小、突发比例及重试量。不能拿低峰 CPU 平均值解释高峰 P99 延迟。
- **业务 SLI**：同时观察登录/连接成功率、发送成功率、端到端消息延迟、重连率、积压深度与恢复后的消息完整性；仅看 Pod 存活率会遗漏用户可见故障。
- **节点资源口径**：区分节点 `capacity`、`allocatable`、已分配 `requests` 与实际使用量。`request` 是调度准入账本，不是价格，也不是进程获得的保留性能；`limit` 则可能引入 CPU 节流或内存 OOMKilled。
- **持久卷身份**：确认 PVC、PV、StorageClass、卷类型、挂载模式、容量、IOPS/吞吐上限及实际绑定关系。尤其要确认消息状态写入的是预期卷，而非临时目录、错误副本或已替换 PV。

还应把节点故障纳入同一窗口：按 **N-1** 节点可用资源重新核算 requests、热点 Pod 分布和卷可访问性。若失去一台节点后只有“能重新调度”而无余量承载峰值，增大单个 Pod 限额通常只是把瓶颈从 CPU 移到磁盘、网络或热点卷。

### 可调度只比较请求与可分配资源

### 可调度只比较请求与可分配资源

调度器判断一个 Pod 能否落到节点上，核心比较的是：

$$\sum \text{已调度 Pod 的 requests}+\text{新 Pod 的 requests}\leq \text{Node Allocatable}$$

其中 `Node Allocatable` 不是节点标称容量。它应从物理容量中扣除操作系统、`kubelet`、容器运行时及驱逐阈值等预留：

$$\text{Allocatable}=\text{Capacity}-\text{system-reserved}-\text{kube-reserved}-\text{eviction-reserved}$$

例如节点有 `16 CPU / 64Gi`，扣除系统与 Kubernetes 预留后，实际可分配为 `14 CPU / 56Gi`。若该节点上业务 Pod 的 CPU `requests` 已为 `13.5 CPU`，再部署一个请求 `1 CPU` 的网关 Pod 会失败；即使这些 Pod 的 `limits` 总和远低于或远高于物理核数，均不改变这一次调度结论。

因此，排查“还能不能扩容”时，应逐节点汇总：

- 可分配 CPU、内存、临时存储；
- 普通业务 Pod 的 `requests`；
- DaemonSet、日志采集、网络插件等常驻 Pod 的 `requests`；
- 污点、亲和性、拓扑约束导致的可用节点子集。

`limits` 主要约束运行期可使用的上限：CPU 超限可能被节流，内存超限可能触发 OOM；它不是调度时的“已保留容量”。把 limit 调大，不能制造新的调度余量，反而可能让多个 Pod 在峰值同时争抢 CPU、内存或节点临时盘。

还要按 N-1 重算。若网关只能运行在 3 个节点，任一节点故障后，其余 2 个节点必须容纳全部关键 Pod 的 `requests`：

$$\text{N-1 余量}=\sum \text{存活节点 Allocatable}-\sum \text{故障后需承载的 requests}$$

余量为负时，当前“可调度”只是在完整节点集存在时成立；节点维护、故障或驱逐后，消息网关可能无法恢复副本。

### 请求、限额与热点的三层运行边界

### 请求、限额与热点的三层运行边界

资源配置应同时看“调度准入、运行上限、实际热点”，不能把 `request` 当作已购买的性能，也不能把 `limit` 当作稳定可用的容量。

- **CPU request：调度账本上的最低需求。** 调度器依据各 Pod 的 CPU request 与节点 `allocatable` 比较，决定 Pod 能否放入节点。它主要影响调度、CPU 争用时的相对权重；节点空闲时，进程通常可以使用超过 request 的 CPU。
- **CPU limit：容器可被允许使用的 CPU 上界。** 超过 limit 时，内核通过 CFS 配额进行节流，而不是立即杀死进程。用户侧常表现为请求排队、网关转发变慢、心跳延迟、长尾时延升高；若节流发生在热点 Pod，平均 CPU 利用率即使不高，业务 SLI 也可能恶化。
- **memory request：内存调度预估。** 它帮助调度器判断节点是否有能力承载该 Pod，也影响节点内存压力下的驱逐优先级；但并不保证应用永远只需这些内存。
- **memory limit：不可越过的内存边界。** 容器实际内存超过该值，通常触发 `OOMKilled`。与 CPU 节流的“变慢”不同，OOM 往往造成进程中断、连接重置、重启与短时不可用；若状态尚未持久化，还会放大消息恢复风险。

因此，排查热点时至少分三层核对：节点是否因 `allocatable` 不足而挤压调度空间；Pod 是否因 CPU limit 被节流或因 memory limit 被 OOM；流量、连接数、队列分区是否集中到少数实例。单纯增大 limit 可能只是把瓶颈从容器配额迁移到节点 CPU、内存、磁盘或网络，必须结合同一时间窗的业务时延、错误率与重启事件判断。

### 从cgroup与OOM证据回溯用户影响

### 从 cgroup 与 OOM 证据回溯用户影响

容器的 `request` 主要影响调度与节点资源分配，`limit` 则由 cgroup 执行上限约束。用户感知的“消息慢、偶发丢失、连接断开”不能仅凭 Pod 处于 `Running` 判断，必须把资源证据与同一时间窗内的消息 SLI 对齐。

优先固定版本、压测负载、业务流量窗口及 PV 身份，再采集以下链路：

- **内存压力**：比较工作集、RSS、`memory.current` 与 `memory.max`；检查容器状态中的 `OOMKilled`、退出码 `137`、内核 OOM 事件及 Pod 重启次数。
- **CPU 受限**：同时看 CPU 使用率和 cgroup 节流时间/节流周期。CPU 未跑满但节流明显，说明进程已被 `limit` 截住；此时请求处理排队可能推高消息投递延迟。
- **重启影响**：将每次重启、就绪探针失败、连接数骤降与消息发送成功率、消费滞后、端到端延迟放在同一时间轴。若重启后未确认消息、会话状态或本地队列无法从 PV 恢复，资源事件就已转化为用户可见故障。
- **存储连带效应**：内存增大后，瓶颈可能转为卷 IOPS、fsync 延迟、磁盘空间或节点网络；消息 SLI 仍恶化时，不能宣称“扩容已解决”。

例如，提升内存 `limit` 后 OOM 消失，但 CPU 节流、PV 写入延迟和消费滞后同步上升，结论应是瓶颈从内存迁移，而非系统恢复。反之，只有在相同版本、相同负载和相同业务窗口下，OOM/重启下降且消息成功率、延迟、恢复完整性同时改善，才可将限额调整视为有效缓解。OpenIM 源码存在相关逻辑，也不能单独证明 Kubernetes 资源设置正确。

### 卷生命周期不等于消息恢复责任

### 卷生命周期不等于消息恢复责任

`emptyDir` 随 Pod 创建，存放在节点本地临时存储；容器重启时通常仍可见，但 Pod 被删除、驱逐或迁移后即失效。它适合缓存、临时文件和可再生索引，不能承担待投递消息、会话账本等恢复责任。即使网关重新调度成功，原节点上的 `emptyDir` 数据也不会随之迁移。

PV/PVC 将存储生命周期从 Pod 生命周期中分离：Pod 重建后可重新挂载同一 PVC，前提是卷后端、绑定关系、回收策略和数据本身均仍有效。但“挂上旧卷”不自动等于“恢复正确消息状态”；还必须确认数据格式、写入完整性、幂等键和版本兼容性。

访问模式限制的是挂载关系，而非业务一致性：

- `RWO`：卷可被单个节点读写；该节点上的多个 Pod 可能共同挂载，不能据此假定只有一个网关写入。
- `RWOP`：卷在集群范围内只允许一个 Pod 读写，更适合需要单写者约束的状态目录；其实际支持还依赖存储驱动能力。
- 两者都不替代数据库事务、主从切换或消息确认协议。

在 S2 阶段，内存中的连接、未确认消息和路由缓存应被视为易失运行状态：进程重启后允许重建或由客户端重传。未来 S3 的数据库才应保存权威消息事实，例如持久消息、消费位点、去重记录与确认结果。PVC 的责任是提供某类数据文件的持久载体；消息能否恢复，最终由权威数据边界、写入时机及恢复协议决定。

> **要点** — 调度成功只证明请求可被接纳；恢复能力取决于运行边界、卷身份、访问模式及权威数据责任。

网关Pod被调度成功，只说明节点愿意接纳它；消息能否恢复，还取决于资源边界、临时存储生命周期与数据库权威归属。

### 从可分配资源判断能否调度

### 从可分配资源判断能否调度

调度器比较的是节点的**可分配资源**与各 Pod 的 `requests` 之和，而不是节点当前监控到的实际使用率：

$$
\text{剩余可调度 CPU}
=
\text{Allocatable CPU}
-
\sum \text{已调度 Pod 的 CPU request}
$$

设节点 N1 的可分配 CPU 为 $8$ 核，已运行 Pod 合计申请 $5.8$ 核：

$$
8 - 5.8 = 2.2\text{ 核}
$$

因此，N1 最多只能再接纳 `cpu request ≤ 2.2` 的 Pod。若新网关 Pod 配置为：

`requests.cpu: 2500m`，`limits.cpu: 3000m`

则其调度请求为 $2.5$ 核，超过 N1 剩余的 $2.2$ 核。即使节点监控显示实际 CPU 使用率很低，Pod 仍会处于 `Pending`，事件通常类似“CPU 不足”。

关键区分：

- `request`：调度准入与资源预留依据；$2500m=2.5$ 核。
- `limit`：运行期上限，不决定节点是否有资格接纳该 Pod。
- CPU 实际空闲不等于可调度空闲；已被其他 Pod 的 `request` 预留的额度不能重复分配。

因此，排查 Pending 时，应先计算 `Allocatable - 已分配 requests`，再检查新 Pod 的 `requests`，而不能仅凭 CPU 利用率图判断。

### 请求、上限与两类资源故障

### 请求、上限与两类资源故障

`request` 是调度承诺：调度器按它为 Pod 选择有足够可分配资源的节点；`limit` 是运行边界：容器运行时据此限制实际可用资源。两者不能混为一谈。

- CPU：`requests.cpu` 决定调度与竞争权重，`limits.cpu` 决定可使用的最高核数。
- 内存：`requests.memory` 用于调度预留，`limits.memory` 是硬上限；进程超过上限通常会被内核杀死。

例如节点剩余 `2 CPU`，网关 Pod 的总 CPU request 为 `2.2 CPU`，即使其实际负载很低，仍会保持 `Pending`：这是调度失败，不是 CPU 节流。应查看事件中的“可用 CPU 不足”，再决定缩小 request、扩容节点或拆分工作负载。

已运行的 Pod 则可能出现两类完全不同的故障：

1. **CPU 节流**：实际 CPU 使用试图超过 `limits.cpu`，容器通常不会退出，但请求排队、延迟升高、心跳超时。用户看到的是“慢”或间歇性超时；应结合 CPU throttling 指标、P99 延迟和队列堆积判断。
2. **内存 OOM**：进程分配内存超过 `limits.memory`，容器可能以 `OOMKilled` 重启。用户看到的是连接中断、短暂不可用，以及未持久化的会话或消息状态丢失风险。

因此，CPU limit 过低主要制造性能退化；memory limit 过低则可能直接制造进程死亡。网关的恢复设计不能只看“Pod 会自动重启”，还要确认重启前的状态是否已写入权威存储。

### 临时目录不能充当消息账本

### 临时目录不能充当消息账本

`emptyDir`、PV 与 PVC 都能被 Pod 挂载，但它们解决的问题完全不同。把三者混为一谈，常会得到“Pod 已经有磁盘，因此消息可恢复”的错误结论。

| 对象 | 绑定关系 | 生命周期 | 节点/Pod 故障后的数据 |
|---|---|---|---|
| `emptyDir` | 直接属于某个 Pod | Pod 被删除即销毁 | 不可保证；Pod 重建后为空 |
| PVC | Pod 声明的存储请求 | 通常独立于 Pod | 取决于其绑定的 PV 与回收策略 |
| PV | 集群中的实际存储资源 | 独立于 Pod，可被 PVC 绑定 | 可保留，但不等于数据库一定一致 |

`emptyDir` 的价值是共享临时文件：例如网关与 sidecar 共享缓存、解压文件、短期缓冲区。它通常位于节点本地磁盘；即使只是容器重启，只要 Pod 尚在，目录可能仍存在，但这不是持久化承诺。一旦 Pod 被删除、驱逐、迁移到另一节点，目录内容就应视为丢失。因此，未确认投递消息、会话账本、消费位点不能只写入 `emptyDir`。

PVC 是应用与存储之间的声明式契约：Pod 挂载 PVC，PVC 再绑定某个 PV。Pod 重建后重新挂载同一 PVC，才**可能**看到原数据。这里的“可能”还受访问模式和后端能力约束：`RWO` 通常允许单节点读写，适合单副本数据库；`RWOP` 则限制同一时刻仅一个 Pod 读写，更能避免两个副本同时写同一卷。

但“卷还在”不等于“消息账本可信”。数据库写入是否完成、事务日志是否刷盘、复制副本是否确认，决定了消息是否真正可恢复。网关本地目录最多保存待上传缓存；权威状态应落在经确认的数据库或对象存储中，并在收到 S3/B 等持久化确认后，才推进消息确认位点。

### 访问模式约束多副本写入

### 访问模式约束多副本写入

`ReadWriteOnce`（RWO）表示一个卷在**同一时刻只能被一个节点以读写方式挂载**，并不严格等价于“只能被一个 Pod 使用”。若多个 Pod 恰好位于同一节点，具体能否共同挂载还取决于存储驱动实现；因此不能把 RWO 当作应用层单写入锁。

`ReadWriteOncePod`（RWOP）更严格：一个卷同一时刻只能被**一个 Pod**读写挂载。它适合要求独占工作目录、单实例数据库数据盘等场景；当第二个 Pod 尝试使用同一 PVC 时，通常会因挂载冲突而无法就绪。

StatefulSet 的常见模式是通过 `volumeClaimTemplates` 为每个副本创建独立 PVC：

- `gateway-0` 使用 `data-gateway-0`
- `gateway-1` 使用 `data-gateway-1`

这解决的是“每个副本有独立持久卷”的问题，而不是“多个副本对同一逻辑数据库的写入一致性”问题。即使每个 Pod 都有自己的 RWO 卷，若它们分别保存本地会话、消费位点或消息状态，就会形成多份互不协调的状态；故障恢复时无法据此判断哪份数据权威。

因此，卷访问模式负责限制**挂载者**，StatefulSet 负责稳定绑定**副本与卷**，数据库一致性则仍须由单主协议、事务数据库、外部共识系统或明确的消息确认链路保证。不要用“PVC 没被共享”推导出“业务写入天然一致”。

### 守住S2状态与S3恢复责任

### 守住 S2 状态与 S3 恢复责任

设 IM 网关将状态分为：`S2` 为连接会话、心跳时间、未确认推送索引等本地运行态；`S3` 为用户消息、会话游标、已读回执等需要跨重启恢复的数据。

判定 `S2` 能否丢失，关键不在于它存于内存、`emptyDir` 还是本地文件，而在于丢失后的协议后果：

- 若客户端可自动重连，并通过令牌、最后确认序号向服务端重新同步，则 `S2` 可视为可丢失缓存。Pod 重建后允许连接短暂中断，但不能导致消息永久缺失。
- 若 `S2` 中保存唯一的未投递消息、唯一确认位点或无法重建的加密上下文，则它已不是纯本地状态；仅依赖 `emptyDir` 或节点磁盘会使驱逐、升级、节点故障变成数据丢失事故。

`S3` 的恢复责任必须明确交给未来数据库 `B`：消息先被 `B` 持久化并取得可恢复的序列号或提交确认，网关才可向发送方确认成功。网关本地队列只能承担削峰、重试或短暂断连缓冲，不能成为消息唯一副本。

因此，Pod 即使因 `2.2 CPU` 请求超过节点可分配 CPU 而保持 `Pending`，或运行后遭遇 CPU 节流、内存 OOM 重启，恢复路径仍应成立：客户端重连，网关从数据库 `B` 按游标补拉 `S3`。不要把 `PVC`、`RWO/RWOP` 或 StatefulSet 的稳定卷名误当作消息权威来源；卷能改善存活性，却不能替代数据库 `B` 的一致性、确认语义与恢复承诺。

> **要点** — 调度只验证请求资源；恢复能力必须由持久卷、访问语义和权威数据库共同保证。
