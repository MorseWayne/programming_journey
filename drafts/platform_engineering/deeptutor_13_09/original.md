## 13.09 跨团队交付：网关、客户端与数据变更如何同日过业务门

- 把交付单位固定为A到B用户旅程
- 定义提供/消费双方的版本化契约
- 区分执行者、决定者与值班责任
- 按真实依赖安排可并行里程碑
- 以跨团队故障反例验收业务结果
- 写发布/回退/交接与阻断风险卡

本节以S2到S3迁移为例，把“接口做完”转化为可证明的A发送、B离线25小时后仍能补拉的跨团队业务交付。

### 先固定A到B的业务旅程

### 先固定 A 到 B 的业务旅程

不要先按“网关接口”“客户端页面”“数据库表”拆任务；先把唯一交付单位写成用户可感知的闭环：

1. **A 发送**：A 作为会话成员提交正文。当前规则是正文非空、最多 `6 UTF-8 字节`，原始 HTTP 请求体最多 `4096 字节`。同一消息 ID 重复提交必须得到 `409`，非成员必须得到 `404`。
2. **系统持久化**：成功发送不能只返回 `200 accepted_in_memory`。它仅表示本进程内存接受，进程重启、实例切换或 B 长时间离线后都不能证明消息仍在。S3/v2 的目标状态应是 `stored_in_teaching_db`。
3. **B 离线**：B 离线 `25 小时`不应改变 A 已成功发送的业务事实；离线不是“消息可以丢失”的例外。
4. **B 补拉**：B 重新上线后，以会话和游标补拉，能取得 A 的那条消息，且不因重复请求产生重复业务消息。
5. **B 确认**：客户端展示并确认已处理；端到端验收应能指出 A 的消息 ID、持久化记录、B 的补拉响应与确认时间。

因此，“网关已转发”“客户端已调用”“数据库已建表”都只是局部完成。真正完成是：在约定身份、成员关系、消息 ID 与字节限制下，A 发送后，即使 B 离线 25 小时，B 仍可补拉并确认该消息。

这里还要冻结一个待决契约：S3/v2 是否继续沿用 `6 UTF-8 字节`限制。目前只能标为 **R9 待审**，由指定决定人批准；未决定前，各团队不得自行把“6B”解释为 6 个字符或放宽限制。验收证据也必须覆盖这条完整旅程，而非仅附上各服务的 `200` 日志。

### 绘制S2与S3的版本化契约地图

### 绘制S2与S3的版本化契约地图

先把“接口路径变了”拆成可核对的契约差异。S2/v1 已上线的事实不能被 S3/v2 提议覆盖；尤其 `accepted_in_memory` 不是“已持久化”的同义词。

| 维度 | S2/v1 当前契约 | S3/v2 提议契约 | 主要消费者与责任方 |
|---|---|---|---|
| 发送请求 | 正文非空，最多 `6` 个 UTF-8 字节；原始 HTTP 体最多 `4096` 字节 | 暂仍提议正文最多 `6` 字节，整体体积限制须明确继承或重定 | 客户端负责本地校验；网关负责按原始体拒绝超限请求 |
| 成功响应 | `200`，`accepted_in_memory`，仅表示本进程已接收 | 应返回可证明已写入 `teaching_db` 的状态，如 `stored_in_teaching_db` | 客户端不得把 S2 的 `200` 当作离线补拉保证；数据层提供持久化证据 |
| 重复发送 | 同一 ID 重复提交返回 `409` | 必须决定：保持 `409`，或返回同一已存资源；不能含糊 | 网关实现幂等判定；客户端据此决定重试策略；决定人确认语义 |
| 权限隐藏 | 非成员返回 `404`，而非泄露资源存在性 | 应保持同一可见性规则，并覆盖发送、查询、补拉 | 网关执行成员鉴权；客户端将 `404` 视为不可访问，不擅自推断原因 |
| 离线补拉 | 无跨进程、跨时间保证 | B 离线 `25h` 后仍可按授权读取 A 的消息 | 数据层保存消息及成员关系；网关暴露读取契约；客户端保存游标并发起补拉 |

可将端到端路径写成：

`客户端发送 → 网关校验/鉴权/幂等 → 数据层事务写入 → 网关确认已存储 → B 上线后客户端补拉 → 网关鉴权 → 数据层查询`

其中，网关“已转发”、客户端“已收到 200”、数据层“有一条记录”都只是局部完成；只有 B 在离线 `25h` 后以成员身份实际读到 A 的消息，才是业务结果完成。

R9 尚待审时，不能把 S3/v2 当成既定承诺。应由指定决定人确认：`6` 字节限制是否保留、`409` 的重复语义、成功状态码与持久化字段、补拉保留期及查询游标。验收证据至少包括：超长正文与超大原始体的拒绝记录、重复 ID 的响应、非成员 `404`、数据库持久化记录，以及 B 离线 `25h` 后补拉成功的端到端测试结果。

### 划分责任、决定权与值班边界

### 划分责任、决定权与值班边界

跨团队交付不能把“谁写代码”误当成“谁对结果负责”。本次迁移至少分四类角色：

- **代码执行者**：网关团队实现`v2`路由、鉴权与错误映射；客户端团队实现发送、补拉和离线重试；数据团队实现教学库写入、读取及迁移脚本。其完成标准是合并代码、通过本团队测试，不等于用户已可补拉。
- **契约决定者**：由接口负责人明确`v2`请求/响应、`6 UTF-8B`正文限制、`4096B`原始 HTTP 体限制、重复 ID 的`409`、非成员的`404`，以及`stored_in_teaching_db`的语义。契约变更必须有版本记录和兼容结论。
- **发布批准者**：业务交付负责人根据端到端证据决定是否放量，而非根据“各团队均已完成”批准。证据应覆盖：A 发送成功、B 离线超过 25 小时、B 恢复后以授权身份补拉到同一消息。
- **事故值班责任人**：发布后由网关值班首先接收入口告警，数据值班处理持久化或查询失败，客户端值班处理重试、展示与版本兼容；业务负责人负责协调及决定降级、回滚。

`R9`“S3/v2 是否仍限制 6B”尚待审时，不允许执行者自行猜测。接口负责人是决定人；若在联调截止前未决，由其升级至业务交付负责人，在“保持 6B”“扩大限制”“暂缓发布”中作出书面选择。值班人员可为止损临时关闭`v2`流量，但不得永久改变契约；永久规则仍须由契约决定者确认。

### 按真实依赖编排并行里程碑

### 按真实依赖编排并行里程碑

不要按“网关、服务端、客户端”分工顺序排期，而要按用户结果倒推：A 的消息必须进入教学数据库；B 离线 25 小时后，以成员身份能够补拉到该消息。`200 accepted_in_memory` 只证明当前进程接收过请求，不能作为 S3 业务门的通过证据。

可先冻结 S3/v2 契约：正文仍按 UTF-8 最多 `6B`、原始 HTTP 体最多 `4096B`；同一消息 ID 重复提交仍为 `409`，非成员仍为 `404`；成功语义改为 `stored_in_teaching_db`。R9“是否仍限制 6B”未裁决前，契约负责人不得把它当作已放宽；决定人应明确记录“沿用 S2 限制”或“批准新限制”。

并行阶段可以同时进行：

- 服务端实现 v2 校验、成员判定、幂等冲突及教学数据库写入；
- 网关配置 v2 路由、体积限制转发和错误码透传；
- 客户端实现本地游标、断网后的补拉请求与 `404/409` 展示；
- 测试准备固定消息 ID、成员关系和“离线 25 小时”的可重复数据夹具。

但以下业务门必须串行：

1. **契约门**：决定人签署请求、响应、错误码和持久化语义；否则各方只能使用模拟接口。
2. **写入门**：服务端证明重启后数据仍在教学数据库，且重复 ID 返回 `409`；网关才能发布真实写路径。
3. **端到端门**：网关已指向真实 v2，A 经网关发送成功，B 断开 25 小时后重新上线补拉并看到同一消息。
4. **验收门**：保留请求日志、数据库记录、网关版本、客户端补拉截图或自动化测试结果，证明的是用户结果而非团队“已完成”。

### 用故障反例验收并完成交接

### 用故障反例验收并完成交接

“接口返回 200”不是交付完成；验收应主动证明错误路径没有破坏业务门槛。对 A 发送、B 离线 25 小时补拉这一目标，网关、客户端、数据团队共同维护一张故障验收表：

| 故障反例 | 预期契约 | 必须提交的证据 | 阻断级别 |
|---|---|---|---|
| A 用同一 `id` 重复发送 | S2 返回 `409`；S3 的幂等语义须经 R9 明确，不能静默改成重复写入 | 两次请求及响应、数据库记录数、日志中的请求 ID | 阻断 |
| 非成员请求发送或补拉 | 返回 `404`，不得泄露会话或消息是否存在 | 成员与非成员对照测试、审计日志 | 阻断 |
| B 离线 25 小时后补拉 | 发布后仍能读到 A 的消息；不能仅依赖 `accepted_in_memory` | 可复现实验时间线、重启服务后的补拉结果、存储查询结果 | 阻断 |
| 原始 HTTP 体超过 `4096B` 或正文超过 6 个 UTF-8 字节 | 在网关与服务端一致拒绝；错误码和错误体已约定 | 边界值测试：6B、7B、4096B、4097B | 高 |
| S3 发布失败或数据迁移失败 | 流量停留或回退至 S2；不得出现“写 S3、读 S2”导致 B 不可见 | 发布记录、开关状态、回退演练、迁移前后数据校验 | 阻断 |

阻断风险卡至少写明：风险现象、受影响用户、触发条件、当前版本、决定人、停止发布条件和回退命令。例如，若 S3 尚未证明 `stored_in_teaching_db` 可在重启后保留消息，则“B 离线 25 小时补拉”未成立，即使发送接口已联调通过也必须阻断上线。

交接不是口头说“已完成”，而是移交可运行证据：接口契约版本、R9 状态与决定人、测试账号和复现步骤、请求/响应样本、监控面板、告警阈值、数据校验脚本、发布与回退负责人。接收团队应按同一时间线独立执行：A 发送→服务重启或发布→等待或模拟 25 小时→B 补拉。只有结果与证据一致，才算端到端过门。

> **要点** — 跨团队交付的完成标准是B能可靠补拉消息，而非网关、客户端或数据团队各自宣称完成。

同日过业务门不是“接口都上线”，而是让A到B的完整消息旅程在版本、数据、可见性、告警与回退上共同成立。

### 以A到B旅程划定交付边界

### 以 A 到 B 旅程划定交付边界

交付单位不应是“客户端发出了请求”或“数据库新增了一行”，而应是：A 发送一条消息后，B 能在连续历史中**恰好一次、按可解释顺序、以正确成员权限看见它**。因此验收链路固定为：

`A 发送 → 网关确认 → 消息落库 → 事件分发 → 历史同步 → B 可见`

每一跳都必须能关联同一业务事实：客户端发送用例携带稳定 `message_id` 与 `(c-a, seq9)`；网关 `/v1` 返回既定状态码，同时为 `/v2` 拟议数据库确认定义版本化语义；数据层写入稳定事件标识 `evt:m-9:v1`，并以 `message_id` 实现幂等。重复提交不得生成第二条消息、第二个事件或第二个历史游标。

验收时不要只看单点成功，而要验证旅程闭环：

- A 收到成功确认后，重试同一请求，结果仍指向同一消息。
- B 先通过事件收到消息，再拉取历史，连续游标不得跳跃、重复或倒退。
- 非成员即使猜到 `message_id`，也不能从事件、历史或详情接口获得内容。
- 事件延迟、消费者重放或历史补偿后，B 的最终可见集合仍一致。
- 任一步失败均有明确结果：客户端可重试、网关可拒绝、数据可回滚或补偿、平台可告警。

交付边界由“B 端可验证”收口，而非由某个服务的部署完成收口。旧版 `7B` 继续拒绝；`R9` 因语义不同单独评审，不得借本旅程的成功结论自动放行。

### 版本化契约与状态码门禁

### 版本化契约与状态码门禁

客户端与网关的契约不能只写“请求成功/失败”，而要把**协议版本、状态码语义、数据库确认边界**同时固定。`/v1` 是当前业务门的稳定入口：客户端提交请求后，网关仅在完成必要校验并得到可判定结果时返回状态码；客户端不得把网络连通、HTTP 已发送或收到任意 `2xx` 误判为业务已落库。

| 契约项 | 约定 |
|---|---|
| 提供方 / 使用方 | 网关提供，客户端使用 |
| 版本 | `/v1` 为已发布稳定契约；`/v2` 为拟议契约，未审批不得替换 `/v1` |
| 成功语义 | `/v1` 返回成功状态码，表示网关已接受并完成该版本定义的处理；若业务要求“已持久化”，响应必须携带可核验的确认标识 |
| 失败语义 | 参数、鉴权、幂等冲突、版本不支持、下游不可用必须映射为稳定状态码及机器可读错误码 |
| 失败时客户端结果 | 对可重试错误按退避重试；对不可重试错误停止发送并展示/记录明确原因；不得自行降级改写业务数据 |
| 测试 | 契约测试覆盖成功、重复提交、超时、下游失败、旧版本请求及状态码到客户端动作的映射 |
| 状态 | `/v1` 已门禁；`/v2` 待数据库确认与联合评审 |

`/v2` 的关键变化是将“网关已接收”与“数据库已确认”区分开。若响应宣称写入成功，则必须对应数据库事务已提交，或至少存在可查询、可恢复的持久化确认记录；不能在异步投递尚未落稳时提前返回最终成功。若只能确认受理，应返回明确的“处理中”结果，并提供后续查询或回调依据。

旧版 `7B` 请求继续拒绝，不能因兼容压力被静默转换为 `/v1` 或 `/v2`。拒绝响应应稳定包含“版本已淘汰”错误码、可升级版本及关联追踪标识，便于客户端定位升级路径。`R9` 属于独立变更：即使接口形状相近，也必须单独评审其状态码、数据确认和回退影响，不得借 `/v2` 发布一并放行。

### 消息标识、事件与幂等链路

### 消息标识、事件与幂等链路

一次发送不能只以“请求成功”结束，而要形成可追溯、可重放且不重复生效的标识链路。Go 发送用例生成稳定的 `message_id`，并以 `(c-a, seq9)` 作为会话内定位键；数据侧据此落库、发布事件 `evt:m-9:v1`，消费者再以同一业务身份执行幂等处理。

| 契约项 | 约定 |
|---|---|
| 提供方 | Go 发送服务、数据写入服务 |
| 使用方 | 网关、事件消费者、历史查询与设备同步服务 |
| 版本 | 消息标识契约 `v1`；事件类型 `evt:m-9:v1` |
| 稳定标识 | `message_id` 在重试、超时补发、异步投递中不得变化 |
| 定位键 | `(conversation_id=c-a, sequence=seq9)` 唯一定位该会话中的消息位置 |
| 事件载荷 | 至少含 `message_id`、`conversation_id`、`sequence`、事件版本与写入结果 |
| 幂等键 | 优先使用 `message_id`；若消费者按会话顺序处理，则联合校验 `(c-a, seq9)` |

Go 侧必须区分“生成新消息”与“重试发送”：前者创建新的 `message_id`，后者复用原值。不得因网络超时、网关返回 `5xx` 或客户端重新发起同一提交而生成第二个标识，否则数据侧会把一次用户操作误判为两条消息。

数据侧处理 `evt:m-9:v1` 时，应将“消息持久化”和“幂等记录”置于同一原子边界。若 `message_id` 已存在，返回既有写入结果，不新增消息、不重复推进未读数、不重复发布对外可见事件；若 `(c-a, seq9)` 已被不同 `message_id` 占用，则判定为定位键冲突并告警，拒绝静默覆盖。

失败结果也必须可预测：事件发布失败时保留待投递记录并重试；消费者重复收到事件时无副作用；顺序缺口或版本不识别时进入隔离队列。测试至少覆盖：同一 `message_id` 重试、多次投递 `evt:m-9:v1`、`seq9` 冲突、落库成功但发布延迟，以及旧 `7B` 仍被拒绝。`R9` 作为独立风险项审查，不得借由幂等逻辑放宽其准入。

### 可见性验证与跨团队故障反例

### 可见性验证与跨团队故障反例

验证不能止于“写库成功”或“接口返回 `200`”，而应从真实成员、真实设备的读取结果反推交付是否成立。历史团队与数据团队至少共同确认：事件 `evt:m-9:v1` 落库后，成员在其有权访问的会话中，能以连续游标读取一次且仅一次；重试不会制造第二条业务消息。

可采用以下反例验收：

- **游标断裂**：设备已读至 `(c-a,seq8)`，随后服务端接受消息 `m-9`，历史接口却返回 `seq10`，或下一页重复返回 `seq8`。这不是分页细节，而是设备无法建立可靠增量同步；结果应阻断业务门，并保留游标生成链路日志。
- **成员不可见**：数据侧已持久化 `message_id=m-9`，但成员权限索引、会话成员快照或历史过滤条件未同步，发送者可查、接收者查不到。此时“写入成功”无效；网关应报告业务失败或降级状态，而非宣称投递完成。
- **重复投递**：Go 客户端因超时重发同一 `(c-a,seq9)`，网关可能收到两次请求。数据层必须将其归并到稳定事件 `evt:m-9:v1`，返回同一业务结果；若历史流出现两条可见消息，说明幂等键只保护了写入、未保护读取投影。
- **旧版本误放行**：旧 `7B` 客户端发送不具备 `message_id` 或游标语义的请求，若被兼容路径接受，后续无法证明重复与顺序。应继续拒绝，并将 `R9` 的兼容审查与本次验收隔离。

验收测试应覆盖“首次发送—超时重试—双设备拉取—成员变更后再拉取—告警触发”。任何一环只出现局部成功，都应视为跨团队契约未兑现，并进入可回退、可告警的失败结果。

### 里程碑、值班与发布风险卡

### 里程碑、值班与发布风险卡

发布门应按“契约可证明”而非“服务已部署”推进。每条契约建立同一张风险卡：`提供方 → 使用方 → 版本 → 错误语义 → 失败结果 → 测试证据 → 当前状态 → 值班负责人`。

| 契约 | 提供方/使用方 | 版本与错误 | 失败时结果 | 测试与状态 |
|---|---|---|---|---|
| 客户端状态查询 | 网关 / 客户端 | `/v1`；旧 `7B` 仍拒绝 | 客户端展示可重试，不误判成功 | 状态码兼容回归；待签收 |
| 数据确认 | 网关 / 数据服务 | `/v2`；确认 `message_id` | 不确认即不推进业务状态 | `(c-a,seq9)` 重放与乱序测试；阻塞项 |
| 事件写入 | 数据服务 / 历史服务 | `evt:m-9:v1` | 幂等命中返回既有结果 | 重复投递、断点恢复；已通过 |
| 历史可见性 | 历史服务 / 设备、成员 | 连续游标、成员权限 | 游标不跳跃；无权限不可见 | 跨页、换端、撤权测试；待灰度 |
| 运行保障 | 平台 / 全体 | 告警与回退版本绑定 | 超阈值停止扩量并回退 | 演练记录；发布前必过 |

里程碑分为：先冻结契约与错误码；并行完成网关—客户端、数据—历史两条链路；再进行全旅程联调；最后以灰度告警、回退演练和业务验收过门。`R9` 不得随主链路默认放行，必须单独评审其兼容性、数据影响与回退路径。

值班采用“一主一备”：主值班负责实时判定扩量、暂停或回退；备值班负责日志、追踪和数据对账。告警至少覆盖确认失败率、`message_id` 幂等冲突、事件积压、游标倒退、成员越权可见及 `/v1` 的 `7B` 异常接受率。

事故交接必须记录影响窗口、受影响版本、游标范围、待补偿消息、已执行回退和下一班行动项；未经数据对账与客户端结果核验，不得仅因告警恢复而宣布发布完成。

> **要点** — 跨团队交付以完整用户旅程验收；契约、幂等、可见性、回退和责任必须同时闭环。

同日过业务门不是“大家都完成开发”，而是围绕一条A到B用户旅程，把规则、契约、数据、发布和事故责任同时闭环。

### 先固定A到B的用户旅程与业务门

### 先固定 A 到 B 的用户旅程与业务门

先写清一条可演练、可验收的旅程，而不是分别罗列网关、客户端和数据库需求：

1. 用户 A 在群内发起退群；服务端确认其当前成员身份后，完成成员关系变更并生成可追溯事件。
2. 用户 B 仍留在群内，刷新历史或继续收消息时，看到与新规则一致的群历史、成员状态及必要提示。
3. A、B 分别使用新旧客户端时，都能理解“已退群”意味着什么：是否还能看历史、是否还能收到后续消息、操作失败时如何提示。
4. 客户端以 `seq`、回执和 `ACK` 收敛消息状态；重复投递、乱序重连后，B 的展示结果不得与服务端权威状态冲突。

业务门应把“25 小时”写成可测目标：从 A 成功退群起，在 **25 小时内**，B 的历史可见性、后续消息接收状态和跨端展示均达到既定规则；不能只写“最终一致”。验收至少覆盖：A 退群成功、重复退群、群不存在、A 非成员、B 在线与离线、旧端进入群页、重连补拉、超过 25 小时仍未收敛。

旧端不能被当作例外。产品必须给出确定文案，例如“你已退出该群，仍可查看此前消息”或“你已退出该群，群消息将不再显示”，并明确该文案是否仅为兼容提示、是否允许实际行为不同。若旧端无法表达新规则，则该规则尚未具备上线条件。

最终验收结果应能回答一句话：**A 退出后，B 在规定时间内、任意受支持端上看到什么，收到什么，以及为何如此。**

### 用不变量建立单一决定权

### 用不变量建立单一决定权

跨团队交付先列出不可被实现细节改变的业务不变量，再为**每条不变量**指定一个决定负责人，而不是把“产品、安全、研发共同负责”写进会议纪要。共同参与可以存在，最终裁决只能有一个。

| 不变量 | 决定负责人 | 执行参与者 | 最终值班责任 |
|---|---|---|---|
| 用户在 25 小时内确认目标、旧端文案与降级提示一致 | 产品 | 客户端、后端、运营 | 产品值班 |
| 退群后历史消息是否可见、何时失效、审计如何保留 | 安全 | 产品、Go 后端、数据 | 安全值班 |
| 回执、`seq` 连续性、ACK 重试与乱序处理 | 客户端 | Go 后端、测试 | 客户端值班 |
| 身份校验边界、资源不存在返回 `404`、状态冲突返回 `409`、写入确认语义 | Go 后端 | 客户端、安全、数据 | 后端值班 |
| 哪份数据权威、留存期限、恢复点与回放方式 | 数据 | Go 后端、平台、安全 | 数据值班 |
| 发布窗口、灰度门槛、观测指标、回滚与事故升级 | 平台 | 全部交付方 | 平台值班 |

“决定负责人”拥有规则的最后解释权：例如退群历史可见性不能由客户端根据接口方便性临时决定，也不能由后端以“数据库里还有记录”为由改变。参与者负责提出约束、实现和验证；值班责任人负责在上线后按既定规则处置告警、降级或回滚。

未定的不变量是阻断依赖：没有安全结论，就不能冻结权限接口；没有数据权威定义，就不能确认恢复方案。但不依赖该结论的工作仍可并行，如客户端完成 ACK 状态机、平台预配仪表盘。这样既避免带着模糊规则上线，也避免等待被误解为停工。

### 把规则翻译为版本化跨团队契约

### 把规则翻译为版本化跨团队契约

“退群后还能看多少历史”不是一句产品文案，而是一组必须可执行、可验证、可回滚的契约。先把用户规则拆成稳定不变量，再为每个不变量指定**唯一决定负责人**与明确参与者：

| 不变量 | 决定负责人 | 提供方与消费方 | 契约要点 |
|---|---|---|---|
| 退群历史可见范围 | 产品 | 后端提供、客户端消费 | 明确截止时点、旧端提示、留存期与恢复条件 |
| 消息顺序与去重 | 客户端 | 后端下发、客户端落地 | `seq` 单调递增；同一 `seq` 可重放但不可重复展示 |
| 回执与确认 | 客户端 | 客户端发送、后端持久化 | `ACK(seq)` 仅表示已确认到该序号，不等于已读 |
| 操作身份 | 后端 | 网关透传、后端校验 | 以服务端鉴权身份为准，禁止信任客户端传入成员身份 |
| 退群后的写入结果 | 后端 | 后端提供、客户端处理 | 已退群写入返回 `409`；目标或会话不存在返回 `404` |
| 成功定义 | 数据团队 | 后端写入、数据核验 | 以数据库确认提交为准，不能以网关 `200` 替代 |

契约必须版本化，例如接口声明 `history_visibility_version=v2`，事件中携带 `seq`、`ack_seq` 与成员状态版本。提供方承诺旧字段保留、默认语义不反转；消费方承诺未知字段忽略、未知枚举安全降级。这样新客户端可使用新可见性规则，旧客户端仍能显示受控文案，而不会误把“不可继续加载”解释成“历史被删除”。

未定规则应显式标为阻断项：例如“退群后是否允许恢复历史”未决时，依赖该答案的查询接口、缓存策略和旧端文案不得进入联调；但 `seq` 持久化、`ACK` 幂等、身份校验等独立准备可以继续。阻断的是**语义依赖**，不是整条交付链路。

### 按依赖拆分可并行里程碑

### 按依赖拆分可并行里程碑

先把工作拆成“规则先决”和“可独立准备”两类，而不是按网关、客户端、后端分别排期。关键判断是：某项产出是否会改变用户可见结果、授权边界或数据事实；会改变的，必须先定规则，未定即阻断交付。

- **规则里程碑：必须先决。**产品负责人在25小时内确认旧端文案、退群后历史可见性；安全负责人确认身份校验与越权边界；数据负责人确认权威来源、留存期限和恢复语义。每条不变量只指定一名最终负责人，例如“退群者不可读取后续消息”由安全负责人决策，产品、客户端、后端参与评审，不能写成“共同负责”。

- **契约里程碑：依规则落接口。**规则明确后，客户端与Go后端冻结回执、`seq`、`ACK`、幂等键及错误语义：身份或状态冲突返回`409`，目标不存在返回`404`，数据库提交成功才确认送达。客户端可先实现状态机、重试与降级页，但不得猜测未定的可见性规则。

- **准备里程碑：可并行推进。**数据团队可预建迁移脚本、备份校验和回滚演练；平台可配置灰度、按`409/404`比例和ACK延迟的观测告警；客户端可完成旧端兼容壳与埋点；后端可搭建鉴权中间件、审计日志和契约测试骨架。

用依赖图管理而非口头催办：未决规则阻断其下游发布、验收和对外承诺；不依赖该规则的代码、数据、观测和事故预案继续推进。Go前必须逐项证明：规则有负责人签字、接口有可执行契约、数据可恢复、平台有人值班且告警能定位到责任方。

### 以故障反例验收并完成交接

### 以故障反例验收并完成交接

不要只验收“正常路径成功”，应把最可能跨团队失配的故障反例写进发布门禁，并逐项证明：能发现、能止血、能回退、能升级。

- **网关已放行，客户端未确认**：后端返回成功，但旧端不识别 `seq`、不发送 `ACK`，导致发送方误以为消息已可靠送达。验收需确认：网关按版本或能力位拒绝不兼容流量；客户端上报回执率、`ACK` 延迟和未知字段解析错误；未确认消息有明确重试上限与降级文案。值班卡必须写明“回执率低于阈值时，先暂停灰度，再关闭网关能力开关”，负责人只能有一名。

- **恢复任务写回错误权威数据**：备份恢复覆盖了较新的成员关系，已退群用户重新获得会话历史。验收需演练：恢复前后按权威版本比较成员状态、退群时间与历史可见范围；恢复任务只能补齐缺失数据，不能覆盖更高版本记录；异常时可停止任务并按批次撤销。观测至少包含恢复批次、冲突数、被拒绝写入数及权限校验失败数。

- **退群后历史泄露**：客户端本地缓存仍展示旧消息，或接口仅检查“曾经是成员”而未检查当前可见性。应使用真实退群账号验证：历史查询返回 `404` 或无权限结果，缓存被清除，推送停止；服务端身份与可见性校验不可依赖客户端标记。发现泄露时，事故卡应明确升级安全负责人、冻结相关接口或开关、保全审计日志及用户告知决策路径。

交接时，平台值班接收的不是一句“已发布”，而是一张风险卡：每项不变量的唯一负责人、参与者、开关位置、仪表盘、告警阈值、回退步骤、升级联系人与未决规则。未定的历史留存或恢复规则必须阻断其依赖发布；不依赖该规则的客户端埋点、网关观测和演练准备可以继续。

> **要点** — 跨团队同日交付的核心，是让每条用户旅程、每个不变量和每个故障路径都有明确契约、单一决定者与可执行交接。

跨团队交付不能按单个服务的完成度判断，而要以A到B的完整用户旅程、可验证契约与可回退路径作为共同门槛。

### 用纸上里程碑统一交付语言

### 用纸上里程碑统一交付语言

纸上里程碑不是甘特图上的真实进度，而是一套跨网关、客户端、数据与支持团队共享的“业务过门”语言：只有某个用户旅程的契约、证据与回退条件同时成立，才可称为进入下一门。

- **里程碑0：现状、目标与契约已决定。** 明确历史数据是否可见、授权边界、`v1/v2` 会话语义、失败提示、审计字段及验收样例；此时只是达成设计承诺，不表示代码已开始。
- **里程碑1：各方可并行准备。** 数据库完成 schema、唯一约束与序列设计；客户端具备解析和降级能力；网关补齐观测与指标。但生产环境尚不启用 S3 相关路径，不能因“代码已合并”宣布上线。
- **里程碑2：隔离的 v2 会话端到端可验证。** 在受控租户、测试账号或隔离流量中，证明写入、读取、授权查询、客户端展示及审计链路一致，并覆盖重复写入、乱序与回退场景。
- **里程碑3：受控灰度与旧端混跑。** 小范围真实流量进入新路径，旧客户端仍可工作；通过新旧结果对账、错误率和延迟阈值判断能否扩量。
- **里程碑4：交接与支持就绪。** 值班人员掌握告警、runbook、回退开关和客户沟通口径，业务门才算真正通过。

它可粗略映射 13.08 的 P0–P5：从问题澄清、契约冻结、实现验证、灰度到运营交接；但映射仅用于对齐讨论。某团队可能处于 P5，而整体仍停在里程碑1，因为端到端用户旅程尚未具备可证明的安全启用条件。

### 先画阻断依赖图，再安排并行准备

### 先画阻断依赖图，再安排并行准备

跨团队计划的第一步不是排日期，而是把“哪些条件不成立就不能过门”画成阻断依赖图。图中的节点应是可验收事实，而非“后端完成”“客户端联调”等模糊状态：

- **历史可见规则明确** → 才能编写并通过**授权查询测试**。必须回答：历史数据按创建时权限、当前权限还是租户策略可见？撤权后是否仍可查？
- **数据库唯一约束与序列号规则落库** → 才能安全写入 **v2 会话存储**。例如唯一键应覆盖业务幂等键，`seq` 必须单调、不可重复，并定义重试和乱序到达时的处理。
- **客户端能力可识别** → 才能进入**受控灰度**。服务端不能仅凭版本号猜测，应以明确能力声明决定是否下发 v2 字段、是否启用新链路。
- **运行手册、监控与回退路径就绪** → 才能**扩量**。手册至少包含开关位置、告警阈值、数据核对命令、降级步骤及责任人；没有可演练回退，就没有安全扩量。

可将关系写成一条门槛链：

`可见规则 → 授权测试 → v2端到端验证 → 客户端灰度 → 对账与扩量`

同时保留并行支路：数据库架构迁移、客户端解析兼容、指标与日志埋点可以并行准备，但在未满足前置契约前不得启用 S3 或改变默认读写路径。这样，里程碑 0—4 只是“可进入下一门”的状态映射，而不是各团队各报进度的百分比。任何阻断节点未绿，都应明确标记其影响范围、验证证据与解除条件。

### 里程碑1：不开启S3的契约预备

### 里程碑1：不开启S3的契约预备

此里程碑的目标不是让新路径对真实业务生效，而是把“可被安全启用”的条件提前做实。所有建设均可上线，但开关保持关闭：网关不向 S3 路由，客户端不依赖新字段作决策，写入不改变既有业务语义。

并行准备四类能力：

- **数据库模式**：增加 `v2_session` 所需表、索引、唯一约束与递增 `seq`，采用向后兼容的扩展式变更；旧读写路径必须不受影响。`(session_id, seq)` 的唯一性是后续乱序、重复写入与对账的基础。
- **版本化契约**：明确提供方输出的 `v1/v2` 字段、必填性、默认值、错误码和幂等语义。消费者应按版本解析：未知字段忽略，缺失的可选字段降级，禁止把“暂未启用”误判为失败。
- **网关兼容逻辑**：网关能够识别客户端能力、请求版本和目标会话类型，但在本阶段固定落到旧路径；路由判定与实际放量开关分离，避免部署即启用。
- **客户端与观测**：客户端完成 `v2` 响应解析、降级展示及能力标识上报；埋点覆盖版本、路由候选、解析结果、`session_id`、`seq` 和错误原因，以便后续隔离验证定位断点。

验收重点是契约可验证，而非功能“看起来已完成”：数据库迁移可重复执行，契约测试覆盖历史可见规则与授权查询，旧客户端能消费新增响应，且观测可区分“具备 S3 条件”与“实际进入 S3”。此时任何请求都不应真正开启 S3。

### 里程碑2至3：隔离验证、灰度混跑与对账

### 里程碑2至3：隔离验证、灰度混跑与对账

里程碑2不是“接口已通”，而是在隔离的 `v2` 会话中证明完整旅程可成立：网关按版本路由，客户端声明并使用 `v2` 能力，服务端写入满足唯一键与递增 `seq` 约束的数据，授权查询仅返回历史可见范围。测试应覆盖新建、重试、乱序、重复提交、权限变更及回退后重进会话；每条请求携带会话、版本、操作者和关联业务单号，确保可追踪。

进入里程碑3前，必须确认以下阻断链已解除：

- 历史可见规则已固化，并有授权查询回归测试；
- 数据库唯一约束、`seq` 分配和 `v2` 存储读写均经过并发验证；
- 客户端能力开关可识别旧端、新端与不支持端；
- 运行手册明确降级、停止放量、数据修复和责任人。

灰度不应只按流量比例切分，还应按风险隔离：先内部账号、低风险租户或单一业务类型，再逐步扩大。旧端继续读取兼容视图或旧协议，新端走 `v2`；两侧对同一业务键定期对账，比较记录数、状态迁移、`seq` 连续性、授权结果及关键金额/计费字段。

对账发现差异时，先冻结扩量而非立即全量回退：区分展示差异、延迟同步、重复写入和语义不一致。只有当差异可解释、可修复且回退演练仍有效时，跨团队才能将“技术灰度成功”升级为“业务验收通过”。

### 里程碑4：用回退与交接证明可运营

### 里程碑4：用回退与交接证明可运营

里程碑4不是“功能已上线”，而是证明系统在故障、旧端混跑和人员轮换时仍可被安全运营。它对应13.08中的交接与支持阶段，但这里只是交付门槛，不表示真实项目进度。

| 角色 | 核心职责 | 不应替代 |
|---|---|---|
| 执行者 | 按发布单扩量、执行对账、演练回退、更新看板 | 单独决定是否继续扩量 |
| 决定者 | 基于业务指标、错误预算和阻断风险卡批准发布/暂停/回退 | 代替当班处置具体告警 |
| 当班责任人 | 接收告警、按`runbook`分诊、升级、记录时间线 | 为未经授权的业务风险背书 |

验收应覆盖完整闭环：

- **发布可控**：灰度开关、目标用户范围、旧客户端兼容窗口和停止扩量条件均已写入发布单。
- **回退可行**：演练关闭S3/v2入口后，存量会话仍按旧路径服务；不得依赖删除已写入的`v2 stored`数据。回退时间目标、数据补偿责任人及判定证据明确。
- **告警可行动**：对授权失败、`seq`冲突、解析失败、双写/对账差异分别设阈值；每个告警必须指向首查面板、缓解动作和升级对象。
- **支持可接手**：一线支持知道如何识别新旧路径、收集会话标识与客户端版本；二线拥有查询权限、历史可见规则说明及已知限制清单。

阻断风险卡必须逐项关闭，而非口头确认：`runbook/回退`未验收时，即使客户端能力和数据库契约都已完成，也不得扩量。真正的完成证据是：非原开发者能在值班中依据文档发现问题、限制影响、完成回退，并将事件交回业务与工程负责人。

> **要点** — 同日过业务门的关键不是同时上线，而是按依赖推进、按旅程验收，并在扩量前证明可观测、可回退、可交接。

本节以A到B的消息可见旅程为交付单位，设计网关、客户端与数据团队同日过业务门的契约证据。

### 以用户旅程锁定交付边界

### 以用户旅程锁定交付边界

交付边界不应是“网关新增了接口”“客户端发了版本”“数据库加了字段”，而应是一条可由用户感知、可被端到端证明的旅程：

> A 发出消息 → 网关接受并鉴权 → 数据可靠落库 → B 可见且可继续同步 → 任一环节失败后可恢复 → 回滚后旧用户仍能读取正确数据。

因此，同日过门的最小单位是“消息从 A 到 B 可见、可恢复、可回退”，不是三个团队各自的完成声明。每一方都要对同一结果提供证据：

- **客户端团队**说明 A 如何发送、旧客户端 `v1` 遇到 `6B` 时为何收到预期的 `409/404/200`，以及旧版 `7B` 被拒绝后不会写入半成品。
- **网关团队**说明版本路由、身份与权限判定、错误码语义，以及 `E9` 重投是否保持幂等而非重复创建。
- **数据团队**说明 `v2` 仅在数据库提交成功后才可被标记为已存储；事件、游标与可见记录不能先于提交泄露。

验收应沿真实用户旅程设计。例如 B 已看到消息 `9`，但尚未拿到 `8`，其同步游标仍必须停在 `7`；这证明“看见新数据”不等于“确认连续消费”。又如 B 在离线 `25h` 后回来，超过 broker 的 `24h` 保留期，仍应从有权限的数据库取得缺失消息，而不是把 broker 过期误判为消息不存在。

回退同样属于旅程：新版本撤回后，旧客户端对 `7B` 的拒绝不应污染数据；已经由新版本写入的合法数据，旧客户端仍须能读取或以明确兼容方式呈现。这里关注的不是 mock 被调用多少次，而是数据、权限、失败和恢复在真实边界上是否一致。

### 版本化消费契约与提供方验证

### 版本化消费契约与提供方验证

消费契约不是“客户端成功调过一次接口”，而是消费方对可观察业务结果的声明：在何种状态、以何种权限读取何种数据，失败时必须得到何种语义明确的响应。将 A、B 的需求样例写成版本化契约，提供方据此在接近真实的数据、权限与故障条件下验证。

- **v1 契约**：旧客户端请求 `6B` 时，资源不存在返回 `404`，版本冲突或状态不允许返回 `409`，合法且有权读取返回 `200`；旧客户端提交 `7B` 必须被拒绝，且失败或回滚后，先前已提交的新数据仍可读取，不能因拒绝旧写入而损坏现有状态。
- **v2 契约**：仅数据库事务已提交的数据才可标记为 `stored`；`E9` 重投必须具备幂等语义，不能生成重复业务记录。B 先看到序号 `9`、尚未看到 `8` 时，游标仍停在 `7`，不得越过缺口推进确认。
- **权限与保留期**：B 在消息代理保留期 `24h` 之后、例如 `25h` 才恢复，也必须能从其被授权访问的数据库补读所需记录；“消息过期”不等于“业务数据不可追溯”。

验证证据应由提供方执行：以真实权限主体、已提交与未提交数据、乱序到达、重投、回滚及代理过期后的补读场景，逐条产出状态、响应码、游标和数据一致性的记录。Mock 调用次数只能证明桩被调用，不能替代对真实数据可见性、授权边界和失败恢复的验证。

### 用失败反例设计业务证据门

### 用失败反例设计业务证据门

不要把“接口能返回成功”当作交付完成，而要把最容易造成业务误判的反例写成消费方可验证的契约。消费方先声明业务需求样例，提供方据此验证；证据关注真实数据、权限、持久化状态与失败后的恢复，而非模拟调用了多少次。

以旧版客户端处理 `6B` 为例，可设计三条互斥路径：

- **无权限：`409`**。客户端携带无效或已撤销的业务权限访问 `6B`，网关返回 `409`；必须证明未创建订单、未推进游标、未写入可见缓存。仅断言状态码不足以说明副作用被阻止。
- **资源不存在：`404`**。权限有效但 `6B` 已不存在或尚未同步，返回 `404`；客户端应保留可重试上下文，不得将其误记为已消费，也不得生成空业务记录。
- **正常读取：`200`**。返回完整、授权范围内的 `6B` 数据；验收应核对客户端展示、数据库落库和确认游标一致，证明读取的是实际提供方数据而非测试替身。

再把失败边界推进到 `v2`：一条消息只有在提供方数据库提交成功后才允许被存储和对外可见。若事件 `E9` 在提交后投递失败，重投必须幂等，不能重复生成业务记录。乱序时，B先看见序号 `9`、缺少 `8`，其游标仍应停在 `7`，不能因“见到更大序号”跳过缺口。

这些证据门应明确记录请求、响应、数据库提交标识、授权判定、客户端状态和游标变化。它们尚未执行，却已定义了上线当天必须能被证明的业务事实。

### 按依赖而非团队排布里程碑

### 按依赖而非团队排布里程碑

不要把“网关完成、客户端完成、数据迁移完成”当作三个并列里程碑；它们会掩盖真实依赖。应以一条消息从写入、投递、消费到查询的业务结果排期，并让每个节点产出可审查的契约证据。

1. **先冻结跨边界契约**：消费方 B 提交可执行的需求样例，而非仅提交接口字段说明。例如：旧版 `/v1` 对 `6B` 分别返回 `409`、`404`、`200` 的条件；B 收到 `E9` 后重投；B 已见事件 `9`、缺失 `8` 时游标仍停在 `7`。提供方确认每个样例的状态码、幂等键、排序/缺口语义和权限前提。  
   **阻断条件**：任一消费方关键场景未被提供方接受，或只存在 mock 调用次数、没有真实输入输出与失败预期。

2. **并行准备数据迁移与网关兼容**：数据侧为 `/v2` 建立“仅数据库提交成功才可 stored”的写入证据；网关侧保留 `/v1` 的 `6B` 行为，同时明确 `/v2` 的新语义。迁移不能以表结构上线为完成，必须说明回滚后新写入数据仍可被旧路径读取。  
   **阻断条件**：`/v2` 可在事务未提交时暴露为已存储，或回滚方案导致旧客户端读不到新数据。

3. **客户端灰度前验证长期与权限路径**：B 的 `25h` 重放需求超过 broker `24h` 保留期，应证明其从有权限的数据库补读，而非假定消息仍在 broker 中。旧客户端对 `7B` 必须拒绝，且拒绝不污染游标、重试或后续可读性。  
   **阻断条件**：补读依赖越权访问；`7B` 被静默接受；失败后的 `E9` 重投无法证明幂等。

4. **最后定义端到端业务门**：验收把网关响应、数据库提交、事件可见性、B 的游标推进、权限拒绝和回滚后读取串成同一证据链。测试此时尚未运行，但每项应有明确输入、预期结果、责任提供方及阻断结论；任何一环缺证据，即不得宣称可同日交付。

### 发布回退与事故交接责任卡

### 发布回退与事故交接责任卡

发布与回退不能只写“谁来操作”。责任卡应明确三类角色，避免网关、客户端、数据团队在事故中互相等待：

| 角色 | 核心问题 | 本场景中的证据与动作 |
|---|---|---|
| 执行者 | 谁执行发布、开关、回退、重投？ | 发布方执行版本切换；发现旧客户端对 `7B` 拒绝时，执行兼容开关或回退；数据人员执行受控恢复任务。 |
| 业务决定者 | 谁判断可否继续、降级或停止？ | 业务负责人确认：回退虽恢复旧路径，但回退期间已提交的新数据仍须可读；不得以“先回退再补数据”掩盖丢单。 |
| 值班责任人 | 谁持续拥有告警、沟通与闭环？ | 值班人接收 `7B` 拒绝、积压和恢复失败告警，维护事件时间线，直到 B 完成核对并由业务方签收。 |

责任边界可用两组对比检验：

- **旧客户端拒绝 `7B`**：执行者负责止损，却无权自行决定长期关闭新能力；业务决定者选择“阻断新写入、兼容降级或回退”；值班责任人须记录受影响请求、拒绝原因及是否存在重复提交。
- **回退后新数据可读**：回退只改变处理版本，不得撤销已成功提交的数据语义。证据应证明旧路径能够读取新数据，或明确展示受控的只读降级范围。
- **B 离线 25 小时**：既然超过 broker 的 24 小时保留期，不能把“重连成功”当作恢复完成。值班责任人应交接从授权数据库按游标恢复的步骤；执行者提供身份授权、查询范围与幂等写入证据；业务决定者确认恢复窗口和对账口径。

事故交接卡至少包含：当前版本与回退点、`7B` 拒绝量、最后确认游标、数据库恢复起点、授权主体、重投/去重规则、业务签收人及下一次状态更新时间。这样交接的是可验证的恢复责任，而非一句“已通知相关团队”。

> **要点** — 跨团队同日交付靠版本化契约和失败证据闭环，而非接口联通或模拟调用次数。

同日过业务门不是让所有组件同时上线，而是确保用户旅程、历史数据与故障责任在任一切换点都可验证、可回退、可接管。

### 以用户旅程定义交付边界

### 以用户旅程定义交付边界

交付边界不应写成“网关已发布、客户端已提审、数据库迁移完成”，而应写成一个可观察的用户结果：用户 A 向用户 B 发送消息后，B 在支持的客户端版本上可见该消息；消息可按 `seq` 连续追溯；刷新、重登、跨端同步及失败重试不会丢失或重复业务语义。

因此，D1/D2 镜像、K1/K2 配置、DB 模式、E9 事件处理与客户端版本不是独立验收项，而是同一旅程的依赖节点。上线门禁至少覆盖：

- **写入链路**：A 的请求经网关进入正确版本服务，生成稳定的 `m-9, seq9`，并持久化为可恢复历史。
- **读取与呈现链路**：B 的新旧客户端都能兼容读取；不识别新字段时降级展示，而非拒收、崩溃或错序。
- **追溯链路**：对账可证明“已确认的 `m-9, seq9`”同时存在于主存储、投递记录与必要索引中。即使旧代码回滚，也不得覆盖、截断或遗失这段新历史。
- **异常链路**：重复发送、网络中断、切换 K1/K2、DB 迁移回退时，用户看到的最终结果仍可解释：成功、处理中或明确失败。

触发发布暂停的信号也应来自旅程，例如“B 收不到已确认消息”“跨端历史断档”“新旧客户端对同一消息状态不一致”，而不是仅看 Pod Ready。出现此类信号时，明确由谁停止扩大流量、谁暂停新写，谁维持兼容读与数据对账，谁向用户说明影响，谁进入值班处置。

这符合 Google SRE 的早期介入与生产就绪思想：在发布前就把用户可见结果、观测指标、回滚约束和责任人写成可执行承诺，而非在多个组件“都绿了”之后才猜测业务是否真正可用。

### 拆开版本独立与兼容契约

### 拆开版本独立与兼容契约

版本独立不等于“各自随时发版”，而是把每个依赖边界明确为可验证的读写契约。D1/D2 镜像、K1/K2 配置、数据库模式、E9 事件与客户端应分别编号；提供方承诺兼容窗口，消费方声明最低可接受版本，切换是否完成则以用户结果而非 `Pod Ready` 判定。

| 边界 | 提供方写入契约 | 消费方读取契约 | 回退要求 |
|---|---|---|---|
| D1/D2 镜像 | D2 先保持 D1 接口、字段和错误语义 | 网关可按路由逐步导向 D2 | 流量可回 D1，不能要求数据回旧形态 |
| K1/K2 配置 | K2 新增键须有默认值，旧键保留至窗口结束 | 客户端忽略未知键，缺失新键可降级 | 配置回 K1 不改变已提交业务事实 |
| 数据库模式 | 先扩展、双读或双写、再迁移、最后收缩 | 旧代码仍能读取新记录的核心字段 | 禁止依赖破坏性删列或改义回滚 |
| E9 事件 | 事件含版本、幂等键、顺序标识 | 消费者可处理旧版与新版，未知字段不失败 | 重放不得重复扣款、重复发货 |
| 客户端版本 | 服务端兼容仍在使用的旧客户端 | 新客户端不得假设服务端已全量升级 | 客户端可独立回退或停止放量 |

尤其要区分“代码回滚”与“历史回滚”。若未来 `v2` 已确认收到 `m-9 seq9`，该事实已进入业务历史；即使旧代码恢复服务，也必须继续兼容读取、对账和解释该记录，绝不能因旧版本不认识新字段而丢弃、覆盖或重编号。

契约还应写明责任：提供方负责停止扩大不兼容变更；业务负责人可暂停新写；消费方保留兼容读与对账；支持团队告知受影响用户；值班人员持有切流、冻结和恢复权限。按 Google SRE 的早期介入与生产就绪思路，在上线前演练这些动作；触发冻结的信号应是下单失败、状态错乱、事件积压或对账差异，而不是单纯的实例就绪。

### 确认历史后的回退约束

### 确认历史后的回退约束

一旦未来版本 `v2` 已确认写入并对外可见事件 `m-9`、序列号 `9`，回退就不再是“把代码和配置切回旧版”。`m-9/seq=9` 已成为业务事实：用户可能已据此看到状态、发起后续操作，外部系统也可能已消费该事件。任何回退若让这段历史消失、重复或被旧状态覆盖，都会造成“系统看似恢复，账实却已分叉”。

因此，回退必须遵守以下不可逆约束：

- **新历史不可删除**：旧代码、旧镜像或旧配置恢复后，必须仍能保存并查询 `m-9/seq=9` 及其后的记录；禁止以旧库快照覆盖生产库，禁止用“重放旧数据”抹去已确认的新事件。
- **兼容读取优先于兼容写入**：旧版本至少要能识别 `v2` 新增字段、事件类型或状态值。无法完整处理时，应保留原始载荷、以只读或降级展示，并将未知状态路由至人工处理；不能把未知值默认解释为“未发生”。
- **序列号单调且去重**：写入与消费均以业务主键、事件标识和序列号校验。旧代码回退后不得重新分配已用序列号，也不得把 `seq=9` 当作可再次执行的请求。
- **回退后必须对账**：比较数据库事实、事件流、网关响应与下游消费结果，至少核验事件数量、最大序列号、关键状态迁移和失败补偿记录。对账未通过，只能维持受控降级，不得恢复新写。
- **暂停扩大而非倒退历史**：发现 `v2` 缺陷时，负责人应先停止流量扩大、暂停受影响的新写或切换为排队；兼容读与对账链路继续运行。是否告知用户、由谁值班处置、何时恢复写入，必须在交付预案中明确。

触发回退或暂停的信号应来自用户结果，例如提交成功但订单不可查询、余额与流水不一致、下游未收到确认；`Pod Ready`、进程存活或接口返回 `200` 只能证明组件可用，不能证明历史仍然正确。按照 Google SRE 的早期介入与生产就绪思路，应在发布前演练“已确认新历史后的旧版回退”，并把兼容读取、对账指标、人工接管入口和责任人作为上线门槛。

### 按依赖安排并行里程碑

### 按依赖安排并行里程碑

并行的对象应是“准备与证据收集”，而不是“不可逆业务状态”。将交付拆为依赖图，而非按团队各自排期：

- **可并行**：网关准备 D1/D2 镜像与路由能力；服务端预置 K1/K2 配置；数据库先扩展兼容模式；客户端分批发布可识别新旧响应的版本；各方同时进行双读校验、指标埋点和回放验证。此阶段即使某个 Pod 已就绪，也只说明进程可运行，不代表用户可完成旅程。
- **必须串行**：先确认旧读写路径仍完整，再开启新格式的兼容读；确认客户端覆盖率、网关路由和数据库约束满足条件后，才允许首次新写；新写稳定后才能切换默认读路径；最后以历史对账门槛关闭旧路径或收紧模式。

例如，未来 `v2` 已确认写入 `m-9 seq9` 后，任何旧代码回滚都不得覆盖、截断或忽略该历史。故回滚前必须先冻结会扩大差异的新写，保留 `v2` 兼容读与对账任务；若旧版本不能安全读取新历史，则回滚范围只能止于流量和配置，不能退回不兼容的存储语义。

每个里程碑应写清责任：谁有权暂停新写，谁维护兼容读和差异对账，谁向用户说明延迟或降级，谁在切换窗口值班并拥有升级路径。借鉴 Google SRE 的早期介入与生产就绪评审，放行条件应是用户结果：关键旅程成功率、确认写入可检索率、跨版本读取一致率及对账差异均达标，而非仅看 `Pod Ready`。

### 用故障反例验收交接

### 用故障反例验收交接

设想一次“看似成功”的发布：网关 D2、客户端新版本和数据库模式已部署，所有 Pod 均为 Ready；但 K2 配置尚未生效，用户消息进入网关后无法路由到消费端。更糟的是，客户端已按 v2 写入 `m-9, seq9`，随后旧代码回滚，只识别旧字段或按旧序列覆盖写入，导致新历史不可见、重复或丢失。

这不是“服务健康”，而是用户旅程失败。交接验收应以反例驱动，并把责任写成可执行的故障卡：

- **触发条件**：不是 Pod Ready，而是“发送消息后可送达、可读取、可在新旧客户端一致展示”；对关键对象验证写入、读取、排序、重试和对账。
- **暂停新写**：一旦 D2/K2/DB 任一环节无法证明兼容，数据负责人宣布暂停 v2 新写或降级为只读；已确认的 `m-9, seq9` 必须保留，回滚代码只能兼容读取，不能以旧模式重写或截断。
- **停止扩大**：发布负责人立即冻结扩容、灰度放量和新租户迁移，保留当前流量比例，避免故障从单个用户扩大为全量历史风险。
- **兼容读与对账**：客户端和服务端负责人维持 v1/v2 双读或转换读；数据团队按消息数、序列连续性、可见性和幂等键对账，确认无缺口后才恢复写入。
- **用户告知**：产品或客服值班明确说明影响范围、临时行为和下一次更新时间；不得把“基础设施正常”表述为“消息已送达”。
- **值班与回退**：网关、客户端、数据三方各有主值班人和升级路径。回退风险卡必须写明：回退版本是否认识 v2 历史、是否保留兼容读、谁有权暂停写入、何时宣布数据恢复。

这符合 Google SRE 的早期介入与生产就绪思路：在上线前就演练跨团队故障，证明失败时仍能保护用户结果，而非仅证明组件能够启动。

> **要点** — 跨团队交付以用户结果为门槛：版本可独立、历史不可丢、责任可定位、故障可暂停并可交接。

跨团队同日过业务门，不靠服务数量或口头承诺，而靠每项交付可追责、可验证、可升级、可回退。

### 以用户旅程固定交付边界

### 以用户旅程固定交付边界

交付单位不应是“网关改完”“客户端发版”或“数据库加字段”，而应是一条可被用户感知、可验收的完整旅程：A 用户发起操作，系统完成鉴权、路由、持久化、异步处理与通知，最终由 B 用户在其客户端看到符合业务规则的结果。

例如，“A 在热群发送消息，B 可见且历史可追溯”应覆盖：

- A 端输入、协议版本与失败提示；
- 网关鉴权、限流、幂等与路由；
- 消息服务写入权威存储、投递异步任务；
- 消费者处理积压、生成 B 端所需状态；
- B 端兼容展示、拉取历史与重连补偿；
- 监控证据：请求链路、写库结果、任务消费、客户端可见截图或自动化断言。

每条旅程必须指定唯一负责人，但负责人不是替所有团队编码，而是对“端到端结果”负责：明确输入依赖、各团队产物、验收证据、截止时间、升级路径，以及失败时由谁决定降级、暂停发布或回退。

团队是否独立，也不能按服务数量判断。只有某团队能够在不等待他人临时配合的情况下，独立构造输入、验证输出、部署自身变更，并证明不会破坏既有旅程，才具备交付独立性。反之，即使网关、客户端、数据服务分别归属不同小组，只要一次验证仍需多人手工拼接环境，就只是组织拆分，不是可交付的边界。

### 为每项交付建立责任卡

### 为每项交付建立责任卡

跨团队交付的最小管理单位不是“网关改造”“客户端发布”这类大任务，而是一张可独立验收的责任卡。每张卡只描述一个明确结果，并让任何人都能回答：谁交付、依赖谁、怎样证明完成、晚了找谁、失败后谁拍板。

建议固定包含以下字段：

- **负责人**：唯一直接负责人，而非“网关组”“客户端组”。负责人协调输入、暴露风险、提交证据。
- **输入依赖**：例如协议字段定义、鉴权规则、数据库迁移脚本、客户端最低版本、灰度开关权限；同时写明依赖负责人和最晚到位时间。
- **产物**：可被定位的交付物，如接口版本、迁移文件、安装包、配置项、监控面板、回退脚本。
- **验收证据**：不能写“已测试”，应写可复核证据，例如接口契约测试记录、旧端兼容截图、迁移前后校验结果、压测曲线、发布单与告警查询链接。
- **截止与升级路径**：规定正常截止时间，以及依赖未到、测试失败、风险未关闭时，何时升级给谁。
- **失败决定人**：明确谁有权选择延期、降级、关闭开关、停止发布或接受风险；负责人负责报告，决定人负责取舍。

可将卡片压缩为一句可执行承诺：`负责人A在T日前，基于依赖B，交付产物C，并以证据D验收；若失败，T+1小时升级至E，由F决定继续、降级或回退。`

这里的关键不是增加文档，而是消除“大家都以为别人会处理”的空白。尤其当网关、客户端和数据迁移必须同日过业务门时，责任卡把技术完成转换为可验证的业务放行条件。

### 用版本化契约连接网关客户端与数据

### 用版本化契约连接网关客户端与数据

同日交付的边界不应写成“网关已改、客户端已发、数据库已迁移”，而应写成可独立验收的版本化契约。契约至少覆盖接口、事件、数据结构和兼容窗口，并明确提供方与消费方分别承担什么责任。

- **提供方责任**：网关或服务端定义版本号、字段语义、默认值、错误码、幂等规则与废弃日期；新增字段应可被旧消费方忽略，删除或改变语义必须升主版本。数据库迁移应提供前向兼容的读写路径、迁移脚本、校验与回退条件。
- **消费方责任**：客户端声明支持的最低/最高契约版本，未知字段忽略、缺失字段采用约定默认值；对事件按版本解析，并记录无法识别的事件类型、字段或状态。不得把“当前服务端恰好这样返回”当成未声明的隐式契约。
- **网关责任**：将外部请求路由到可用版本，必要时做显式适配，而非悄悄篡改业务语义。版本选择应可观测：请求携带的版本、命中的规则、降级结果和拒绝原因都应进入日志与指标。

例如，事件可约定为 `TaskCreated.v2`，其中新增 `source` 字段；旧端仍按 `v1` 必需字段处理，新端读取 `source`。若某字段从“可空”改为“必填”，这不是普通补丁，而是破坏性变化：要么保留旧字段并双写，要么通过新事件版本和明确迁移窗口发布。

数据迁移尤其要区分三个阶段：先扩展结构，再双读/双写并回填，最后在旧端退出兼容窗口后收缩旧结构。禁止把“数据库脚本执行成功”作为完成证据；证据应包括迁移前后行数与校验和、双写一致性抽样、旧客户端真实请求回放、失败重试与回退演练结果。

每份契约纸面上都应列出：提供方负责人、消费方负责人、输入依赖、版本边界、兼容截止日、验证证据链接，以及不兼容或回退会导致权威数据丢失时的决定人。这样，网关、客户端和数据变更才能各自独立测试与部署，却仍在同一业务门前证明它们连接的是同一份事实。

### 按真实依赖编排并行里程碑

### 按真实依赖编排并行里程碑

并行不等于把网关、客户端、数据变更分别分给三个团队。只有某项工作具备独立输入、可隔离测试、可单独部署，且失败不会阻塞他项验证时，才是真正可并行的里程碑。

以“热群每秒 20 条入站消息、每条扇出 2000 个任务”为例，应先画出真实依赖链：

- 网关负责限流、鉴权与请求幂等，但其压测输入依赖客户端真实重试行为；
- 异步队列可先验证吞吐，却必须使用接近生产的消息大小、分区策略和消费者并发；
- 数据团队验证积压恢复时，不仅看队列清空速度，还要确认顺序、去重、未读数与历史规则未被破坏；
- 客户端灰度依赖服务端兼容字段；旧端不能理解的新语义，不能靠“忽略未知字段”假定安全。

每个里程碑应明确：`owner`、前置输入、可交付产物、验收证据、截止时间、升级对象，以及失败时由谁决定降级、暂停或回退。例如，“积压恢复”证据应包含：峰值积压量、恢复时长、恢复期间新增流量、重复投递率、用户可见延迟和数据库写入压力，而非一张队列消费速率截图。

尤其要警惕把 OpenIM 两份源码中存在异步调用路径，当成团队能够独立推进的证明。源码只能说明技术上可异步；若共享同一数据库迁移、同一消息语义、同一发布窗口或同一回退开关，组织上仍是串行依赖。最后还应将维护成本纳入验证：新增补偿任务、监控告警、人工处置和双写期限，是否能被长期承担；否则“成功上线”只是把风险延期。

### 以阻断风险和故障反例过业务门

### 以阻断风险和故障反例过业务门

“能发布”不等于“能过业务门”。评审应从故障反例出发：一旦发生，谁有权阻断、谁决定降级、回退后哪一份数据仍是权威，必须在发布前写清。

| 阻断反例 | 必问问题 | 通过证据 | 失败时决定人 |
|---|---|---|---|
| 产品历史规则被新逻辑改写 | 新旧规则并存时，历史订单、权益、状态机按哪个版本解释？ | 历史样本回放、规则版本标记、差异清单 | 产品规则负责人 |
| 数据库不可持久 | 写入失败、主从延迟或重试后，任务是否仍可恢复？ | 断库演练、幂等键、积压恢复记录 | 数据负责人 |
| 旧端无法理解新字段/状态 | 旧客户端收到未知枚举、空字段或新跳转指令时是否崩溃、误展示？ | 最低支持版本测试、兼容降级截图与日志 | 客户端负责人 |
| 回退丢失权威 | 新版本已写入的数据，旧版本是否读错、覆盖或无法解释？ | 回退演练、双读/迁移策略、权威源声明 | 发布总负责人 |

发布门禁至少覆盖一次完整链路：新端与旧端并发入站、网关灰度、异步任务积压、数据库短暂不可用、恢复后补偿，以及版本回退。尤其要验证热群场景：`20` 个热点群同时入站、`2000` 个任务堆积时，队列是否可观测，恢复速率是否高于新增速率，补偿是否重复发放或遗漏。

阻断决策不能留给临场讨论。若回退会使新写入数据失去解释能力，应明确“禁止代码回退，只允许开关降级或前向修复”；若旧端不能识别新状态，则新状态不得进入全量写路径。值班交接也应附带当前开关、积压水位、权威数据源、升级联系人和停止条件。

独立性不以服务数量判断，而以能否独立测试、部署、回退且不破坏他方权威为准。即使固定 OpenIM 的两份源码只支持异步路径，也只能说明技术调用方式，不能证明网关、客户端、数据团队已经具备可独立交付的组织边界。

> **要点** — 同日交付的核心是旅程验收与责任闭环：契约可验证、依赖可排期、失败可决策、回退不失权威。

跨团队同日过业务门，不是把若干任务同时标绿，而是让用户旅程、版本契约、数据状态与值班处置在同一时刻闭环。

### 从任务清单改写为A到B用户旅程

### 从任务清单改写为 A 到 B 用户旅程

“网关已发布、客户端已合并、数据迁移已完成”只是团队任务状态，不等于用户已经成功完成一次消息交付。应把交付对象改写为可观察的旅程：

> 用户 A 向用户 B 发送消息；B 在新旧客户端上均能看见该消息、重新进入后可取回，并在异常时获得可处置结果。

这一定义把“完成”从内部动作转为外部结果。可按旅程拆解责任，但不能把结果切碎：

1. **A 发起**：客户端构造请求，网关接受并按契约校验；失败时 A 能看到明确失败，而非无限等待。
2. **服务持久化与投递**：服务为消息分配序号并写入数据；例如 `seq=7/9` 但缺少 `8`，不能仅因写入成功就宣称连续可取回。
3. **B 可见**：B 收到实时事件或刷新后读取到消息。若数据库已有 `E9`，但事件未发出，则“已存”不等于“已见”。
4. **B 可取回**：断网、重登或旧端 `7B` 仍能通过拉取协议恢复消息，不能依赖一次实时推送。
5. **异常可处置**：网关、客户端、数据层任一环失败时，责任人、阻断条件和止损动作清楚；例如停止放量、关闭新路径，或执行 D/K/DB 的兼容回退。

因此，任务清单应改成验收问题：A 是否得到确定结果？B 是否可见、可取回？旧端是否仍读懂？数据已存而通知缺失时谁负责补偿？只有这些问题同时为“是”，跨团队交付才真正过门。

### 用版本化契约连接网关、客户端与数据

### 用版本化契约连接网关、客户端与数据

跨团队交付的单位不是“网关完成、客户端完成、数据脚本完成”，而是一个可被用户走通的版本化结果。应先把契约写成三段：

- **网关提供、客户端消费**：请求字段、响应字段、错误码、幂等语义及版本协商规则。
- **网关消费、数据侧提供**：读写模型、状态迁移、事件序列号与可见性约束。
- **客户端消费、数据状态证明**：客户端看到“成功”时，数据库中的业务状态和后续事件必须与之对应。

以 S2、S3、R9 为例，不能只写“支持 S2/S3、返回 R9”，还应明确：S2 请求进入网关后由谁决定是否接受；S3 响应对新旧客户端分别保证哪些字段；R9 是可重试、需降级还是必须阻断。**责任**回答“谁维护契约”，**决定权**回答“字段冲突、灰度失败或兼容取舍由谁拍板”。

兼容边界可用反例推演：

1. 旧端 7B 不认识新增字段时，网关必须保持旧字段语义不变；新字段应可忽略，不能把 S3 的必填要求反向施加给 7B。
2. 若事件序列出现 `seq7/9` 而缺少 `seq8`，客户端不能仅因收到了 9 就展示最终完成；数据侧需定义缺序是等待、补偿还是拒绝推进。
3. 若数据库已存 E9、但事件未发出，则“写库成功”不等于“用户结果完成”。契约必须规定 E9 的补发责任、去重键和可观测状态。
4. 若 R9 依赖尚未满足的前置数据，网关应阻断并返回稳定的可处理结果，而非让客户端猜测数据是否最终会出现。

因此，S2/S3/R9 的验收应落在一张兼容矩阵：新端/旧端各消费什么，网关承诺什么，数据库何时成为事实来源，缺序与漏发由谁止损。只有 D、K、DB 的回退边界也被写入契约，才可能在异常时停止扩大影响，而不是把不一致扩散到更多用户。

### 拆开执行责任、业务决定与值班归属

### 拆开执行责任、业务决定与值班归属

同日过业务门至少有三类“谁负责”，不能因某人最熟悉系统就合并：

| 角色 | 核心问题 | 典型产物 |
|---|---|---|
| 执行责任人 | “谁实际完成变更？” | 网关路由、客户端包、数据迁移、回退脚本 |
| 业务决策者 | “证据足够时，谁签字放行或阻断？” | 放行结论、风险接受、延期决定 |
| 事故值班人 | “上线后 S2/S3 出现时，谁在时限内响应？” | 告警确认、止损动作、升级记录 |

开发负责人可执行 D、K、DB 的发布准备，却不当然拥有业务放行权；业务负责人可以决定“暂不开放”，却不应被期待在 S2 告警时修改网关；值班人负责响应和止损，也不能自行改变已批准的业务范围。

可用一句责任链写清边界：**执行人交付可验证证据，决策者基于证据放行，值班人按预案处置偏差。** 例如 DB 已存 E9 但事件未发，执行人确认补发或回退路径；决策者判断是否阻断业务门；值班人若出现 S2，则在约定窗口内关闭入口、降级旧端 7B，并升级决策者。

特别要区分“负责”与“有权决定”：负责修复不等于有权放行，负责值守不等于可接受风险。若三者未显式列名，seq7/9 缺 8、B25h/24h 临界或契约提供方与使用方不一致时，就会出现无人敢停、多人同时改的失控局面。

### 按真实前置依赖设计并行里程碑

### 按真实前置依赖设计并行里程碑

并行不等于同时开工，而是前置条件彼此独立。先把“任务完成”改写为可验收的用户结果：用户通过网关提交请求，客户端按契约展示结果，数据状态可追溯，异常时值班人员能止损。

以 `B25h` 为例，若业务门要求在 `24h` 内完成，则它不是“还差 1 小时”的普通风险，而是已违反时限的阻断项。此时不能用客户端页面完成、网关接口已合并来抵消；应先确认计时起点、责任人和可接受的降级结果。

可并行推进的工作包括：

- 网关团队冻结字段、错误码和幂等语义；
- 客户端团队依据已冻结契约完成适配与旧端 `7B` 兼容策略；
- 数据团队准备迁移、校验规则和回退脚本；
- 值班团队明确 `D/K/DB` 各自的回退边界与触发条件。

但以下门槛必须串行：

1. **契约先于联调放行**：提供方未确认请求、响应及失败语义时，使用方只能做模拟适配，不能宣称可交付。
2. **数据写入先于状态展示**：若 `DB` 已存 `E9` 但事件未发出，客户端不能把“已提交”当作“已生效”；应标记为待处理，并将补发或人工处置列为放行条件。
3. **时限校验先于业务过门**：`B25h/24h` 必须在门禁中显式判定，超时即阻断或按预先批准的降级路径止损。
4. **回退方案先于不可逆变更**：涉及数据结构、网关路由或客户端开关的变更，须先证明 `D/K/DB` 能分别回退，不能以“必要时再处理”代替方案。

里程碑应写成“契约冻结—数据可用—状态闭环—时限达标—可回退放行”，而非“网关、客户端、数据团队均完成任务”。

### 以故障反例验收发布、回退与止损

### 以故障反例验收发布、回退与止损

验收不应问“网关、客户端、数据脚本是否完成”，而应问：用户能否完成旅程，且失败时是否可解释、可止损。以反例覆盖契约断裂：

- **数据反例**：`DB` 已存事件 `E9`，但未向下游发出。此时不能仅验“写库成功”；应验收用户结果是否缺失、补发责任归属、幂等键与补偿窗口。若 `B` 在 `25h` 后才发现、而承诺窗口为 `24h`，即使最终补发也构成业务门失败。
- **兼容反例**：旧端 `7B` 不识别新字段或状态。契约提供方必须给出降级语义，使用方必须确认未知值不会误展示、误提交或阻塞；不能把“旧端占比低”替代兼容验收。
- **顺序反例**：收到 `seq=7`、`seq=9`，缺少 `seq=8`。应明确是等待、跳过、重拉还是阻断；否则网关、客户端与数据侧会各自作出不同决定。
- **回退反例**：`D` 要回退展示，`K` 要回退契约，`DB` 已写入不可逆状态。三者不能分别回退：必须先判定数据是否可逆、旧端是否仍可消费、回退后是否产生双写或漏发。

交接时用一张止损卡固化决定：`S2` 由值班负责人在影响扩大前执行降级；升至 `S3` 时阻断新流量并冻结变更；`R9` 记录“谁负责处置、谁有权决定、何时复盘”。卡中还应写明前置依赖、监控信号、用户影响阈值、补偿路径及恢复验收条件。没有统一的阻断条件和回退边界，“同日发布”只是同步上线，不是同步过业务门。

> **要点** — 同日交付的最小单位是可验收的用户旅程；契约、依赖、决定权与回退路径必须共同闭环。
