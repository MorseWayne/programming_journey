从“能回答规则”到“能改变状态”，关键不在模型会不会说“已发送”，而在动作是否受契约、状态、权限与证据约束。

### 回答、工作流与智能体的边界

### 回答、工作流与智能体的边界

三者的区别不在“是否用了大模型”，而在系统是否需要**改变外部状态**、是否允许动态决策，以及失败后能否验收与恢复。

- **资料回答**：输入问题，检索有权证据，生成可追溯答案。例如回答“正文上限是 6 UTF-8 B”。它的主要风险是答错、越权引用或遗漏证据；通常不会改变 IM、成员或消息历史。此时应优先使用 RAG、规则查询或确定性计算，而非引入执行能力。

- **固定工作流**：程序预先规定状态机与关卡，例如  
  `起草 → UTF-8 字节校验 → 权限核验 → 人工批准 → 调用发送接口 → 记录回执`。  
  模型只能在受限节点完成起草、分类或解释，不能自行跳过批准、替换频道或把“建议发送”变成“立即发送”。适合高频、流程稳定、审计要求明确的动作。

- **动态智能体**：模型在授权工具集合内，根据观察结果选择下一步，例如先读取频道信息、发现正文超限后压缩草稿、请求批准、发送并核对接口回执。它适合步骤不完全可预知的任务，但会扩大状态空间：重复调用、工具参数错误、部分成功、上下文漂移和错误恢复都必须设计与评测。

选型先问失败成本：答错合同上限，可要求引用证据并人工复核；误发一条公告，需审批、幂等键和回执；误删历史或批量通知，则应收紧权限，甚至禁止智能体自主执行。模型输出“已发送”只是文本；只有受控接口返回成功记录，且必要时确认设备或服务端状态，动作才可视为完成。

### 受控发送的工具契约

### 受控发送的工具契约

“发送消息”应被定义为可验证的工具调用，而非让模型在自然语言中自行宣称结果。最小工具集可分为只读与有副作用两类：

- `读取频道信息(channel_id)`：返回频道是否存在、调用者角色、可发送范围、正文上限、成员摘要与策略版本。只读不等于无风险：返回内容仍须按调用者权限过滤。
- `起草消息(channel_id, content)`：只生成候选正文及其 `utf8_bytes`、风险提示，不改变频道状态。
- `发送消息(channel_id, content, approval_id, idempotency_key)`：唯一允许改变 IM 状态的接口。

发送工具的输入契约至少包括：

1. `channel_id` 必须指向允许操作的频道，例如 `c-a`；
2. `content` 是原始待发送文本，不能只传“公告”之类的摘要；
3. `utf8_bytes(content) <= 6` 是本例正文限制；`公告` 恰为 $3+3=6$ B；
4. 原始 HTTP body 还必须满足独立的 `<=4096` B 限制；
5. `approval_id` 必须对应当前内容哈希、当前频道和未过期的人工批准；
6. `idempotency_key` 用于重试去重，避免超时后重复发送。

前置条件由服务端重新核验，不能信任模型或前端：调用者仍有发送权限、频道未归档、成员范围未变化到需重新批准的程度、内容通过长度与策略校验。任何一项失败，接口应返回明确状态，如“批准失效”“正文超限”或“权限不足”，而不是模糊地回答“可能未发送”。

成功输出应含不可伪造的 `message_id`、服务端时间、实际字节数、目标频道、策略版本与投递状态；失败输出应含机器可处理的错误码及是否“未产生消息”。审计记录还应关联请求者、批准者、工具版本、内容哈希、幂等键和结果。模型只能依据该结果说“已发送”；若仅完成起草或调用超时，只能如实说明“未确认发送结果”。

### 草稿到发送的状态机

### 草稿到发送的状态机

一次受控发送不应被表示为一句“已发送”，而应是可检查、可重试、可终止的状态迁移：

`草稿 → 校验通过 → 待批准 → 已批准 → 执行中 → 已确认`

- **草稿**：模型只生成候选内容，例如向 `c-a` 发送“公告”。此时不得调用发送接口。
- **校验通过**：程序验证频道、操作者权限、正文 UTF-8 字节数、原始 HTTP body 上限、敏感词及成员范围。任一失败进入`校验失败`终止状态，并返回具体原因。
- **待批准**：向有权限的人展示不可变的动作摘要：目标频道、正文、预计影响、请求标识。批准的是这份摘要，不是模型之后可改写的自然语言。
- **已批准**：批准记录绑定`动作 ID`、草稿版本和过期时间；内容或目标改变后，必须回到`待批准`。
- **执行中**：服务端以`动作 ID`作为幂等键调用接口。网络超时不等于发送失败，也不等于发送成功，应转入`结果未知`。
- **已确认**：通过接口响应中的消息 ID，或后续查询到带同一幂等键的消息，确认实际落库；同时记录审计证据。

`结果未知`是恢复关键：系统先查询是否已存在该动作，而非盲目重发；查到则转`已确认`，查不到且仍在重试窗口内才安全重试，超过窗口转`人工处置`。此外可设`已拒绝`、`已取消`、`执行失败`等终止状态。模型可以提出下一步建议，但只有状态机和工具层能推进真实 IM 状态。

### 重复冲突与响应丢失

### 重复冲突与响应丢失

设受控发送工作流的发送步骤为 S2：向频道 `c-a` 提交一条已批准的公告。S2 的危险不在“接口报错”，而在客户端无法仅凭一次网络结果判断消息是否已经进入服务端状态。

若同一审批单被重复提交，服务端可能返回 `409`，表示该操作的幂等键、业务请求号或消息指纹已存在冲突。此时不能把 `409` 当作“发送失败”并换一个新键重发：原请求可能已经成功创建消息；新键会把重复内容再发一次。正确分支应是查询该请求号对应的动作记录，确认其最终状态、消息标识与目标频道。

更棘手的是“发送后响应丢失”：客户端超时、连接中断或进程重启时，存在两种不可区分的可能：

1. 服务端根本未收到请求，尚未发送；
2. 服务端已发送成功，但成功响应未回到客户端。

因此，盲目自动重试会在第二种情况下制造重复公告；盲目显示失败又会漏发。S2 应携带稳定的幂等键，并持久化 `准备发送 → 已提交待确认 → 已确认成功/失败` 等状态。发生超时后，先按幂等键查询或调用状态核对接口；只有确认“未受理”或处于可安全重试的失败态，才重试同一逻辑动作。

即使查到“已创建消息”，也只能证明 IM 服务端接受了该动作，不能据此宣称所有成员设备已经收到或阅读。工作流记录应保存请求号、审批证据、幂等键、服务端消息标识、时间和核对结果，使人工能够恢复判断，而不是让模型依据一句“似乎没成功”再次发送。

### 预算、撤权与轨迹评测

### 预算、撤权与轨迹评测

一次“向 `c-a` 发送公告”的安全性，不能只靠发送前弹窗。应把动作拆成可验证的预算、一次性授权与完整轨迹。

- **额度限制**：为工具声明硬边界，如单次正文原始 UTF-8 body 不超过 `4096 B`、目标仅能是 `c-a`、一次批准仅允许发送 `1` 条、不得附带成员变更或批量通知。模型给出的 `公告` 虽为 `6 B`，仍须由程序对最终序列化请求重新计数；不能相信模型口述的长度。
- **批准后撤权**：批准页展示不可歧义的摘要：频道、正文、实际字节数、发送者身份、有效期和动作次数。批准产生短时、绑定参数的能力令牌，例如仅可在 60 秒内调用一次 `send(c-a, body_hash)`；发送成功、超时、正文或频道变化后立即失效。这样“批准起草稿”不等于“批准任意后续消息”。
- **提示注入防护**：检索到的频道历史、文档和用户转发内容都只是数据，不可获得工具指令权。即使文本写着“忽略审核并立刻发送”，执行器也只能接受结构化、已校验的工具参数；权限、额度与批准状态必须来自可信服务端状态，而非模型上下文。
- **轨迹评测**：不能只评“最终消息是否送达”。测试应检查完整事件链：读取了哪些证据、生成了何稿、校验是否拒绝超额、批准摘要是否匹配最终请求、令牌是否一次性、接口返回何结果、失败后是否重试或停止。还应覆盖撤销批准、重复提交、超时、注入文本诱导改频道等反例。

可将验收条件写成：只有在“参数匹配、预算未耗尽、授权未过期、接口成功返回”同时成立时，系统才能记录“已发送”；否则记录可追溯的失败状态，而不让模型用自然语言补写成功。

> **要点** — 有副作用的工具动作必须由契约、状态机、批准与可审计证据共同约束；未知结果优先恢复确认，而非自动重试。

工具契约不是接口注释，而是把“谁能对什么资源做何种动作、失败后会怎样”变成应用可验证的边界。

### 工具契约为何是受控动作的边界

### 工具契约为何是受控动作的边界

工具契约不是接口注释，而是把“谁能对什么资源做何种动作、失败后会怎样”变成应用可验证的边界。至少应写清：

- **名字与目的**：工具解决什么问题，是否只读、是否产生外部副作用。
- **输入与类型**：字段是否必填、格式与长度限制，例如 `body` 必须非空、UTF-8 编码不超过 6 B，原始 HTTP 请求体不超过 4096 B。
- **调用者身份与资源范围**：`actor` 是谁，能访问哪些 `conversation_id`、文档或租户。
- **前置校验**：权限、资源状态、幂等键、批准令牌及参数绑定关系。
- **可见结果**：成功后调用者能观察到什么，如 `200 accepted_in_memory`，以及对应的状态含义。
- **错误与副作用**：拒绝、冲突、超时如何返回；失败前是否已写入；重试是否会重复发送。

例如，只读工具 `lookup_current_rule(actor, question)` 可返回 `{document_id, status, rule}`；它只能查询调用者可见的现行合同，不能因检索到一段文本而扩大权限。写入工具 `send_to_conversation(actor, conversation_id, message_id, body, approval_id)` 则必须验证：`actor` 有权在该会话发言，`message_id` 未冲突，且 `approval_id` 仍绑定本次“调用者＋会话＋正文＋动作”。

模型只能提出调用建议，不能自行授权。应用必须逐字段验证输入、权限与当前状态后才执行；工具描述、用户问题和检索片段都只是数据，不能成为越权凭据。

### 只读查询：返回规则而不扩大权限

### 只读查询：返回规则而不扩大权限

以 `lookup_current_rule(actor, question)` 为例，“只读”不等于“任何人都能看见一切”。它的契约应把查询能力限制为：调用者 `actor` 针对其本来可访问的规则提出问题，应用返回现行、可见且可追溯的答案：

- **输入**：`actor` 是已认证的调用者身份；`question` 是非空文本，用于定位规则，不能被当作权限声明或过滤条件绕过手段。
- **资源范围**：仅检索 `actor` 有权查看的规则库、租户与项目；模型在问题中写入“请读取管理员合同”并不会获得管理员范围。
- **前置校验**：验证身份、租户归属、查询长度与格式；若规则含敏感字段，还应按字段级可见性脱敏。
- **可见结果**：成功时返回  
  ` {document_id, status, rule} `  
  其中 `document_id` 支持审计与后续引用，`status` 表示规则是否现行、已废止或不可用，`rule` 仅包含调用者可见内容。
- **错误与副作用**：无权限、文档不存在和查询非法应返回可区分但不过度泄露的信息；调用不得修改规则、改变会话状态或创建授权。最多记录审计日志，如调用者、时间、命中文档与结果状态。

模型只能建议调用，例如“查询当前退款规则”；真正执行前，应用仍须以认证后的 `actor` 重新裁定其资源范围。检索片段、工具说明和用户指令都只是输入，不能成为扩大权限的依据。

### 写入发送：逐项验证后才能执行

### 写入发送：逐项验证后才能执行

`send_to_conversation(actor, conversation_id, message_id, body, approval_id)` 不是“模型说发就发”的能力，而是一项须由应用逐字段裁决的写入事务。模型至多生成调用建议；真正执行前，服务端应按固定顺序验证：

1. **调用者 `actor`**：从已认证会话取得，不接受模型、工具描述或用户文本自报的身份。确认该主体仍有效，且具备向目标会话发言的权限。
2. **资源 `conversation_id`**：确认会话存在、未关闭，并属于 `actor` 可写的资源范围。不能因检索结果提及某会话，就扩大其访问权。
3. **幂等键 `message_id`**：检查格式与长度，并查询是否已处理。重复请求必须返回既有结果或明确冲突，不能再次投递，从而避免重试造成重复消息。
4. **正文 `body`**：要求非空、可按 UTF-8 编码，且编码后不超过 $6\text{ B}$；同时在入口限制原始 HTTP 请求体不超过 $4096\text{ B}$。长度校验应针对规范化后的实际字节，而非模型估计的字符数。
5. **批准凭据 `approval_id`**：必须绑定此次 `actor + conversation_id + body + 动作`，并验证未过期、未撤销、未使用。正文、会话或动作任一变化，都应使原批准失效并要求重新批准。

只有全部前置条件成立，才写入并返回如 `200 accepted_in_memory` 的可见结果；权限不足、批准失效、消息冲突或状态不允许时，应返回可区分的错误，并保证不产生部分发送副作用。尤其不能把“工具可用”“用户要求发送”或“文档建议发送”误当作授权。

### 错误、已知结果与未知结果的区别

### 错误、已知结果与未知结果的区别

工具返回值必须区分“没有执行”“已拒绝”“已经执行”和“无法确认是否执行”，否则重试会把一次发言变成多次发言。

- `200 accepted_in_memory`：应用已通过全部校验，并已接受本次发送请求；应同时记录 `actor`、`conversation_id`、`message_id`、正文摘要、`approval_id`、时间和状态。它表示已知的受理结果，但若消息异步投递，仍应继续记录投递状态。
- `400` 校验失败：例如正文为空、不是有效 UTF-8、正文超过 6 B、原始 HTTP 请求超过 4096 B、字段缺失或类型不符。此时不得产生消息副作用；调用者修正输入后可用新的请求重试。
- `403` 权限拒绝：`actor` 无权向该会话发言，或批准不属于该调用者、会话、正文和动作。拒绝不是模型可协商的提示，工具描述和检索内容也不能扩大权限。
- `409` 冲突：`message_id` 已存在。服务应返回该幂等键对应的既有处理结果或状态，而不是再次创建消息；这使客户端可安全重试。
- 响应丢失或超时：客户端不知道服务端是否已受理，属于**未知结果**，不能直接换一个 `message_id` 重发。应以原 `message_id` 查询操作记录，或按同一幂等键重试。

副作用记录应是可审计的状态机，例如“已校验→已受理→已投递/投递失败”，并保存关联的请求摘要与错误原因。日志记录的是事实，不是授权依据；真正的执行仍由应用逐字段、逐权限、逐状态验证。

### 按工具最小授权设计执行层

### 按工具最小授权设计执行层

工具入口应把模型输出视为“调用建议”，而非授权。应用为每个工具建立独立契约：`lookup_current_rule(actor, question)` 只读，可返回 `{document_id, status, rule}`；它只能查询调用者可见的现行合同，不能因问题文本或检索结果扩大范围。

`send_to_conversation(actor, conversation_id, message_id, body, approval_id)` 属于写入工具，执行前由 Go 服务依次验证：

- `actor` 是否具备向该 `conversation_id` 发言的权限；
- 会话是否存在、状态是否允许发送；
- `body` 非空、为合法 UTF-8，并满足正文与原始 HTTP 请求体大小限制；
- `message_id` 是否已处理，借此实现幂等；
- `approval_id` 是否仍绑定本次“调用者＋会话＋正文＋动作”，且未过期或撤销。

通过后才写入内存队列或消息存储，并记录审计事件：工具名、调用者、资源、参数摘要、批准记录、校验结果、时间和结果码。成功可返回 `200 accepted_in_memory`；权限、状态、重复请求或批准失效应返回明确错误，且不得产生部分发送副作用。

关键原则是按工具授权，而非按模型授权：工具描述、用户提示和文档内容都不能替代服务端的权限判断。

> **要点** — 模型只能建议调用；应用必须依据明确契约验证身份、资源、状态与批准后，才可执行有副作用的工具。

“下一步就发”不是可执行保证。受控IM必须先把自然语言意图拆成可审计、可批准、可恢复的离散状态与转移。

### 从自由文本到离散状态

### 从自由文本到离散状态

“下一步就发”只是模型生成的文本，不是授权、事务记录，更不是发送成功的证据。若直接把这句话连接到写工具，系统会失去三个关键边界：谁批准了什么、失败后能否安全重试、调用后究竟是否已被服务端受理。

应将一次发送建模为带证据的状态机：

`draft → validated → awaiting_approval → approved → executing → accepted_in_memory`

其中也可转入终止或异常分支：`rejected`、`expired`、`result_unknown`、`failed`。

- `draft`：候选正文、目标会话和动作参数，仍可编辑。
- `validated`：完成纸面检查，例如字节上限、成员身份、资源范围、当前会话合同与禁止项；验证通过不表示允许发送。
- `awaiting_approval`：冻结待审内容，等待用户或可信授权方确认。
- `approved`：批准必须绑定**特定 actor、会话标识、正文散列、动作类型和有效期**。正文、目标会话或关键参数任一变化，旧批准立即失效，回到待审批。
- `executing`：唯一允许调用写工具的状态；应保存幂等键、请求标识和开始时间，便于恢复。
- `accepted_in_memory`：当前 S2 下最强的成功观察，仅表示本进程或工具已受理请求；它不证明已落库、消息 broker 已持久化，更不证明 B 设备已送达。

`rejected` 表示审批拒绝，`expired` 表示批准超时，二者都不能自动发送；`failed` 表示获得明确失败结果；`result_unknown` 则表示调用超时、连接中断或进程崩溃，不能把它误判为失败后盲目重发。此时应依据幂等键查询、人工确认或进入补偿流程。

批准来自用户或可信应用的人机交互边界，而非模型声称“我已获批”。状态、转移原因、审批证据与工具回执都应可审计，才能让发送动作可控、可恢复。

### 校验与批准的可信边界

### 校验与批准的可信边界

`validated` 与 `approved` 解决的是两类不同问题：前者回答“这个请求是否合规、可执行”，后者回答“谁在何时明确授权执行它”。两者都不能由模型的自然语言自述替代。

进入 `validated` 前，应把候选动作规范化为不可歧义的请求，例如：

`{actor, session_id, action, body_hash, resource_scope, contract_version}`

其中至少检查：

- 正文编码与字节长度是否符合当前合同；
- `session_id` 是否存在，成员关系与权限是否匹配；
- 目标资源是否处于允许范围，动作是否为允许的写操作；
- 当前合同版本、工具参数与风险策略是否兼容；
- 正文经规范化后的散列 `body_hash` 是否已固定，避免“批准 A，发送 B”。

校验通过只说明纸面条件成立，不表示已经获得写入许可。因此状态应转入 `awaiting_approval`，由可信应用界面、授权服务或具备权限的人生成批准凭证。模型输出“用户已同意”没有安全含义；模型既不是审批者，也不能自行伪造审批证据。

批准应被视为一张短期、一次性或可追踪使用的能力票据：

\[
approval = Sign(actor, session\_id, action, body\_hash, expires\_at, nonce)
\]

执行器仅在以下绑定全部一致时接受该票据：

- 执行主体是获准的 `actor`；
- 写入目标仍是指定 `session_id`；
- 动作类型完全一致；
- 待发送正文的 `body_hash` 完全一致；
- 当前时间未超过 `expires_at`，且票据未撤销、未消费；
- 校验所依据的合同与资源范围仍有效。

任一字段变化——例如改了收件会话、补充了一句话、切换执行账号或审批超时——都必须使旧批准失效，回到 `awaiting_approval`。这样，`approved → executing` 才不是“模型觉得可以发”，而是执行器验证到一份针对这一次具体写操作的可信授权。

### 写工具只在执行态调用

### 写工具只在执行态调用

`executing` 是唯一允许调用“会产生外部副作用”的写工具的状态，例如发送消息、编辑消息、撤回、创建群组或变更成员。模型生成的“现在发送”、工具参数已填充，均不构成执行授权。

写工具调用前应再次核验不可变执行契约：

- `actor`：由哪个已认证账号执行；
- `conversation_id` 与目标成员：发往哪个会话、哪些对象；
- `action`：例如 `send_message`，不能用“发送”泛化覆盖编辑或撤回；
- `body_hash`：正文及附件、引用、格式化后的规范化内容散列；
- `approval_id` 与 `expires_at`：批准来源可信，且尚未过期；
- 权限与资源范围：该账号当前仍可向该会话执行该动作。

批准应绑定上述字段，而非绑定模糊意图。例如，用户批准“向项目群发送 `明日 10 点开会`”，不能自动授权将其改为“今日 10 点”、改发给另一群，或附加新文件。正文、附件、目标会话、动作、执行账号任一项变化，都必须使旧 `approval_id` 失效，状态退回 `awaiting_approval`。

进入 `executing` 后，工具层还应使用幂等键，例如 `idempotency_key = approval_id + action + body_hash`，避免网络超时后的重复发送。工具返回成功时，只能转为 `accepted_in_memory`：这表示当前进程已观察到受理；若调用超时、连接中断或响应缺失，应转为 `result_unknown`，而不是擅自重试或宣称已送达。

### S2响应丢失与未知结果

### S2响应丢失与未知结果

设客户端请求 S2「发送消息」，服务端完成校验、取得批准并将消息交给当前进程内存中的会话处理器，随后准备返回：

`202 Accepted { status: accepted_in_memory, request_id: r1 }`

但响应在网络中丢失。客户端超时后并不知道两件事：请求是否根本未到达服务端，还是服务端已经受理、仅仅丢了响应。此时状态必须记录为 `result_unknown`，而不是直接重试。

若客户端以同一个幂等键 `k1` 重发，服务端可能返回：

`409 Conflict { request_id: r1, status: accepted_in_memory }`

这个 `409` 不是“发送失败”，而是提示：相同意图已存在，当前不能把它当作一项全新的发送再执行。尤其当请求没有可靠幂等键、正文散列或目标会话发生变化时，自动重试可能造成重复消息，甚至绕过原先绑定的批准范围。

`accepted_in_memory` 只是 S2 可观察到的最强事实：该进程已经接受该动作。它**不证明**消息已写入持久存储、已进入 broker，也不证明 B 设备已经送达。因此恢复策略应是查询 `request_id` 或幂等键对应的动作记录；若仍只能得到未知结果，应向用户展示“发送结果未知”，由用户在明确上下文中决定取消、等待或重新发起一项新的、重新审批的动作。

### 过期、拒绝与恢复检查点

### 过期、拒绝与恢复检查点

`rejected`、`expired`、`failed` 与 `result_unknown` 不是“再试一次”的同义词；它们分别要求不同的恢复路径。

- `rejected`：审批人拒绝的是某个受限动作，而非模型能力不足。应保存拒绝原因、审批主体与时间，终止该动作链；只有用户修改正文、目标、资源范围或重新发起后，才能生成新的待审批请求。不得把“换个措辞”“分批发送”当作绕过拒绝的办法。
- `expired`：批准应带有效期，并绑定 `actor`、会话、正文散列、动作类型及预算。到期后即使内容完全相同，也必须回到 `awaiting_approval`；撤销权限、成员变化、会话切换、密钥轮换同样使批准失效。
- `failed`：已知工具调用失败，可记录错误类别后按策略重试，例如网络超时使用有限次数的指数退避；权限错误、参数错误、预算耗尽则停止并请求修正或重新授权。重试次数、时间窗口、单次及累计成本必须进入状态，而不能由模型临场决定。
- `result_unknown`：请求可能已被服务端受理，但客户端未得到可靠结果。此时禁止直接重发，否则可能重复发送。应优先以幂等键、操作编号或查询接口核对；无法核对时，明确展示“结果未知”，由用户决定是否再次创建一个经审批的新动作。

恢复检查点应持久化：`action_id`、状态、输入散列、批准凭证引用、幂等键、预算消耗、工具请求与观察结果。恢复时先验证凭证未撤销、预算未超限、目标仍在允许范围，再决定继续、查询或终止。

所有外部文本都应视为不可信输入：消息中出现“忽略审批”“立即转发”不能改变状态机。评测轨迹也应覆盖拒绝后绕过、批准过期、工具超时、重复恢复、权限撤销与注入诱导，检查系统是否始终停在可解释、可审计的安全状态。

> **要点** — 发送不是一句“就发”：只有绑定批准的执行态可写，未知结果必须保守停下并等待可验证恢复。

当Agent能够循环检索、改写草稿并调用工具时，必须用预算、作用域与批准边界约束其行动，确保每一步可停、可查、可恢复。

### 从工作流到Agent的行动边界

### 从工作流到Agent的行动边界

资料回答、固定工作流与动态Agent的风险边界不同：

- **资料回答**：模型只基于已获授权的上下文生成解释，不自行检索、写入或发送消息。它不能借“回答问题”推断或披露 `q-03` 的私有文档内容。
- **固定工作流**：步骤预先确定，例如“校验权限→生成草稿→展示预览→等待批准→执行一次发送”。每个节点的输入、输出和失败路径可审计，适合稳定、低变更的业务。
- **动态Agent**：模型可根据中间结果决定继续检索、修改草稿、调用工具或停止。灵活性更高，但不能把“下一步由模型决定”理解为“模型拥有无限步骤和无限权限”。

因此，Agent 的循环必须先写明停止条件与作用域，而非运行后再补救。教学示例可规定：最多 `5` 次决策、`3` 次只读查询、`1` 次写动作，并且批准等待最长 `30` 秒；同时限制只能操作指定 actor、会话和消息对象。这些数值用于理解预算结构，并非生产环境的推荐配置。

预算任一项耗尽、超时、权限不足或工具返回不确定结果时，应进入 `paused` 或 `failed`，报告“已完成：生成草稿、完成权限检查；未完成：尚未发送消息”，而不是悄悄扩大预算、跳过批准，或把“内存中受理”误写为“已发送”。

尤其是批量发送、成员变更、删除等高风险动作，应配置更窄的工具权限、更短的作用域和更严格的人工批准。批准绑定的是一份具体计划；若正文、目标会话或动作类型变化，即使只从“公告”改为“公告9”，也必须重新校验并重新审批。

### 把预算写成可检查的契约

### 把预算写成可检查的契约

Agent 的“能做什么”还不够，必须明确“最多做多少、做到何时、只能碰哪些资源”。将预算写入执行契约，而不是留给模型自行判断，可防止循环检索、反复改稿或工具重试无限扩张。

教学中的一份契约可以写为：

- 最大决策步数：`5`；每次“观察—推理—选工具/结束”计为一步。
- 模型预算：限定调用次数与总 Token，例如最多 `5` 次推理、总计 `12000` Token。
- 工具预算：只读查询最多 `3` 次；写动作最多 `1` 次；失败重试也计入次数。
- 时间边界：整体截止时间为 `30` 秒；涉及写操作时，最多等待人工批准 `30` 秒。
- 资源作用域：仅读取已授权会话或文档；写入仅允许目标会话 `c-a`，不得因模型生成了新目标而扩大范围。

可将其理解为可机读的限制：

`决策≤5 ∧ 只读≤3 ∧ 写入≤1 ∧ 时间≤30秒 ∧ 资源∈允许集合`

任一条件触发时，运行器应停止继续调用模型或工具，进入 `paused` 或 `failed`。状态报告必须区分：哪些查询已完成、草稿是否已生成、批准是否仍在等待、写动作是否**未执行**。尤其不能因预算耗尽或批准超时，就把“准备发送”记录成“已发”。

上述 `5/3/1/30` 仅用于教学，帮助识别预算维度，并非生产推荐值。生产配置应按动作风险、延迟目标、成本上限、失败模式和审计要求分别设定；批量发送、删除、成员变更等高风险操作通常需要更小作用域、更少写入配额与更严格的批准条件。

### 草稿、校验与批准的绑定关系

### 草稿、校验与批准的绑定关系

批准的对象不应是模糊的“发送这条消息”，而应是一次**已校验、可复现的具体计划**。可将待执行计划记为：

\[
P=(actor, session, body, bytes, messageId, authz, acceptScope)
\]

例如，界面应明确展示：

- 操作者：`u-a`
- 目标会话：`c-a`
- 正文：`公告`
- 编码长度：`6 UTF-8 B`
- 当前消息 ID：`m-...`
- 权限检查：`allow`，且检查依据仍有效
- 成功确认范围：`HTTP 200` 仅表示服务在**内存中受理**，不等于已持久化、已投递或对方已读

人工批准产生的不是永久通行证，而是对该计划指纹的短时授权，例如：

`approval = hash(P, policyVersion, expiry)`

执行前必须重新计算计划并逐项比对。若模型将正文从“公告”改为“公告9”，即使只多了 `1 UTF-8 B`；或将会话从 `c-a` 换成其他会话；或消息 ID、权限结果、确认语义发生变化，原批准即失效，必须重新校验并重新展示后批准。

这种绑定避免了“先批准一个安全草稿，再偷偷执行另一个动作”的替换攻击。尤其是批量发送、成员变更、删除等高风险操作，应使用更窄的权限范围、更短的批准有效期，并要求计划包含受影响对象列表与不可逆后果。批准前后的每次校验、批准人、计划摘要和实际执行结果都应记录；若未执行，只能报告“未执行”或“等待批准”，不能写成“已发”。

### 计划变更为何必须重新审批

### 计划变更为何必须重新审批

批准不是“允许这个 Agent 随便继续”，而是用户对一份**冻结计划**的授权。计划至少应绑定：动作类型、目标会话、正文、当前消息 ID、执行者、权限检查结果、预算与确认语义。

例如，用户看到并批准的计划为：

- actor：`u-a`
- 目标会话：`c-a`
- 动作：发送正文 `公告`
- 正文长度：6 UTF-8 B
- 当前消息 ID：`m-17`
- 权限检查：`u-a` 可向 `c-a` 发送
- 结果说明：`200` 仅表示服务在内存中受理，不表示已持久化或已送达

随后模型继续推理，把正文改成 `公告9`。即使只多了一个字符，这也已不是原计划：内容、字节长度及潜在业务含义均发生变化。系统必须重新执行权限与输入校验，生成新的计划摘要，并要求新的人工批准；不得沿用针对 `公告` 的批准令牌。

目标从 `c-a` 改为 `c-b` 时更是如此。会话变化意味着接收者、可见范围和权限结论都可能变化；原先“可发送到 `c-a`”绝不推出“可发送到 `c-b`”。应使原批准立即失效，重新检查 actor 对新会话的权限后再审批。

可将批准绑定为计划摘要的不可变指纹，例如：

`approve(hash(actor, target, body, message_id, action, scope))`

任一字段改变，指纹即改变，执行器只能进入 `paused`，报告“原计划未执行；检测到计划变更，等待重新批准”。尤其不能把未执行动作写成“已发”，也不能让模型借由重新检索或改写草稿悄悄扩大已批准的作用域。

### 耗尽、撤权与越权检索的处置

### 耗尽、撤权与越权检索的处置

预算是停止条件，不是“尽量完成”的建议。以教学示例为例，Agent 最多作出 5 次决策、执行 3 次只读查询和 1 次写动作；等待人工批准超过 30 秒即停止继续推进。任一上限触发时，编排器应冻结后续工具调用，而不是让模型自行“补一次”“再试一次”。

可按是否可安全续跑区分状态：

- `paused`：等待批准、等待外部输入，或预算耗尽但已保存可恢复检查点。
- `failed`：权限已撤销、计划完整性不符、工具返回不可恢复错误，或已超出任务允许时间。
- `completed`：仅在目标动作获得确认后使用；“请求已受理”不等于“消息已发送”。

停止报告应明确记录：已完成步骤、未完成步骤、消耗的决策/token/工具预算、最后一次工具结果、当前计划摘要、是否发生写入，以及恢复所需条件。例如：“已查询 2 次；未发送公告；等待 `u-a` 对会话 `c-a` 的计划批准。”不得把未执行动作表述为已完成。

撤权必须立即影响正在运行的任务。每次工具调用前重新检查 actor、会话、动作范围和权限版本；若 `u-a` 被撤销发消息权限，即使此前计划已获批准，也应转为 `failed` 或 `paused`，留下不可抵赖的轨迹：计划版本、批准记录、权限检查结果、调用参数摘要、时间戳与状态迁移原因。

尤其不能把检索当作权限旁路。`q-03` 私有文档无权时，Agent 不得先调用检索工具、再由模型决定是否复述结果；权限门应位于检索前，拒绝结果也不得泄露标题、片段、命中数量或推断性摘要。检索工具返回的数据同样受原始作用域约束，不能因为进入模型上下文就获得传播权限。

> **要点** — Agent的自主性必须被预算、最小权限和绑定式批准约束；停止或失败时如实报告，绝不越权执行或伪称已发送。

检查点让工作流可暂停、可恢复、可审计，但不能凭空消除外部写入后的未知结果。

### 检查点的职责与边界

### 检查点的职责与边界

检查点是在一次状态转移后，将工作流保存为**可恢复、可审计、可判断下一步**的持久记录。它解决的是“进程退出、人工审批延迟、工具调用中断后，系统依据什么继续”的问题，而不是宣称外部动作必然成功。

一个合格的检查点至少应记录：

- 工作流或请求 ID、当前 `actor`；
- 计划摘要与当前阶段；
- 批准记录：谁、何时、基于何种版本批准；
- 已完成步骤、下一待执行步骤与待调用工具；
- 工具参数的安全摘要、可观察结果、错误或未知状态；
- 引用资料的版本、来源链接与检索时间。

其中应遵循最小披露原则：不要把私有正文、访问令牌、会话凭据或敏感附件直接写入无保护日志。需要关联原文时，保存受控存储中的引用、摘要、哈希或版本号即可。

模型声称“我已经发送过”不是检查点：模型上下文可能被截断、重置或生成错误记忆，也不能作为审计证据。进程内变量同样不可靠；重启、故障转移或并发接管后，它们会消失，其他执行者也无法验证其真实性。

检查点还不能抹平外部写入的空隙。例如 `send_to_conversation` 已被 S2 受理，但客户端在读取响应前断线，此时应记录为 `result_unknown`，而非擅自标记成功或安全重试。持久状态提供的是诚实的恢复依据，不是对未知结果的虚假确定性。

### 可恢复状态的最小结构

### 可恢复状态的最小结构

检查点不是“模型的记忆摘要”，而是一份可由新进程读取、验证并继续执行的状态记录。要支持暂停、重启、人工接管与审计，最小结构应覆盖“谁在执行、要做什么、做到哪里、下一步是什么、外部世界已观察到什么”。

- `workflow_id`、`request_id`：分别关联整条工作流与一次具体请求；二者应稳定、可追溯，不能在重试时随意改写。
- `actor`：发起者、代表其执行的 Agent、权限上下文与租户边界。恢复时必须重新校验权限，不能仅因旧检查点存在就继续写入。
- `plan_summary`：计划版本、目标会话、预期动作及关键约束。例如“向会话 C 发送一条已批准通知”，而非保存全部推理正文。
- `approval_record`：批准人、批准时间、批准范围、所依据的计划版本与失效条件。计划变化后，旧批准不应自动复用。
- `completed_steps`：每步的状态、开始/结束时间、输入摘要、错误分类与重试次数，用于避免把“已完成”和“未开始”混为一谈。
- `pending_tool_call`：准备调用的工具名、目标、规范化参数摘要、关联请求 ID 与调用阶段，如 `prepared`、`result_unknown`。
- `observable_result`：可从外部系统验证的事实，如响应状态、服务端消息 ID、查询时间、事件序号；它不同于“模型认为发送成功”。

可将状态抽象为：

`Checkpoint = 身份 + 权限 + 计划 + 批准 + 步骤账本 + 待执行意图 + 外部证据`

其中“待执行意图”和“外部证据”必须分开保存：前者说明本地曾准备发送，后者才说明观察到了服务端结果。若调用后断线，记录应转为 `result_unknown`，等待查询、人工确认或按合同处理，而不是凭重试或 409 推断成功。

检查点、日志与引用资料均应最小化保存：不得写入私有正文、访问令牌、凭据或完整敏感参数；必要内容可采用脱敏摘要、加密存储、访问控制与保留期限。外部依据则记录来源链接、版本、获取时间与适用条款，确保恢复者能复查当时依据。

### 暂停恢复与批准衔接

### 暂停恢复与批准衔接

将 IM 动作拆成可持久化的状态机，而非依赖模型上下文或进程内变量：

`草稿 → 已校验 → 待批准 → 已批准待执行 → 执行中 → 已发送／结果未知／失败`

每次状态转移后写入检查点，至少记录：

- `workflow_id`、`request_id`、`actor` 与当前节点；
- 草稿的摘要、目标会话、接收者范围、内容哈希，而非无保护地保存私密正文或凭据；
- 校验规则版本、校验结果及引用资料的版本和可查来源；
- 批准人、批准时间、批准所对应的草稿哈希与计划摘要；
- 已完成步骤、下一待调用工具、工具参数摘要及可观察结果。

批准必须绑定具体版本：草稿、收件人或附件一旦变化，即使文本看似相近，也应使旧批准失效并回到`待批准`。重启后，工作流读取检查点：`待批准`恢复为等待人工输入；`已批准待执行`恢复到发送前的确认节点；`执行中`不能直接重发，而应转入`result_unknown`并查询可观察证据。

例如，调用 `send_to_conversation` 前先写入“准备发送”。若客户端在读取响应前断线，S2 可能已受理，也可能未受理；此时不能仅凭同一 ID 重试得到的 `409` 判定发送成功。应保留请求 ID、发送时间和目标摘要，进行服务端查询、人工核验或显式补偿。HTTP 方法的幂等性也不会自动使自定义 IM 写操作幂等。检查点保证恢复到正确的待执行节点，但不替代外部结果确认。

### 外部发送后的未知结果

### 外部发送后的未知结果

设工作流准备调用 `send_to_conversation`：

1. 写入检查点：`准备发送`，记录请求 ID、会话 ID、actor、计划摘要与工具参数摘要。
2. 向 S2 `/v1` 发起发送请求。
3. S2 已在内存中受理消息并执行写入。
4. 客户端尚未来得及读取响应，网络断开、进程崩溃或超时。

此时客户端只能确认“请求发出过”，不能确认“服务端未处理”。恢复后若自动重试同一请求 ID，S2 会返回 `409`；该响应至多说明该 ID 已被占用，**不能证明本次消息内容已成功写入、写入位置正确，或先前请求确实完成了预期动作**。即使 HTTP 某些方法具有幂等语义，也不意味着自定义 IM 发送动作天然可安全重复。

因此，检查点不应直接标记为“已发送”，而应进入：

`result_unknown`

该状态应保存可观察证据：发送时间、请求 ID、目标会话、参数摘要、断线/超时原因、已获得的响应片段，以及待执行的核查动作。后续流程优先查询会话消息、服务端操作记录或带版本的投递状态；仅在能够证明未受理，或服务端提供明确的去重与结果查询合同后，才决定重发。若无法核实，应升级人工确认，而不是让模型凭“我刚才已经发送”继续执行。

### 409、幂等与恢复决策

### 409、幂等与恢复决策

必须区分三层概念，它们不能相互替代：

- **HTTP 方法幂等**：RFC 9110 中，重复执行 `PUT`、`DELETE` 等方法，其“预期效果”应与执行一次相同；这只是协议语义，不保证某个自定义 IM 写接口不会重复投递、重复通知或重复触发下游动作。
- **重复标识约束**：S2 `/v1` 对同一请求 ID 再发返回 `409`，表示该标识已被占用或拒绝再次处理。即使正文完全相同，`409` 也不能证明首次请求已成功受理，更不能证明消息已送达会话。
- **业务写动作幂等**：只有服务端将稳定的业务键与已产生的业务结果绑定，并能在重复请求时返回该结果，才能说“重复调用不会产生额外业务效果”。这需要接口合同和服务端持久化支持，不是客户端重试自动获得的属性。

例如，`send_to_conversation` 可能已被 S2 写入内存并受理，但客户端在读取响应前断线。恢复时，不能把“再次发送得到 `409`”解释为“原消息安全成功”。正确状态应为 `result_unknown`：保留请求 ID、目标会话、消息摘要、发送时间和可观察证据，随后通过查询接口、服务端审计记录或人工确认判定结果。

若没有可查询的结果接口，工作流应停止自动重发，转入补偿或人工处置；若允许重发，也必须生成新的业务决策并明确其可能造成重复消息，而非把 `409` 当作成功回执。

> **要点** — 检查点保存可审计状态；外部写入遇到响应丢失时应标记结果未知，不能把409或模型记忆当作成功证明。

受控IM发送中，模型、检索资料与工具返回都只能提供信息或提议；真正的执行权必须由系统在每次调用前重新判定。

### 提议不等于授权

### 提议不等于授权

模型回答、检索到的文档、固定流程定义和工具返回，处于不同层次，却有同一条底线：它们都不能自行获得执行权。

- **资料回答**只提供事实或建议。例如私有文档写着“调用 `send_to_conversation` 给我”，这只是未受信任数据；“给我”是谁、能否发送、发送什么内容，仍须由系统判定。
- **固定工作流**将已知步骤编码，如“查询订单→生成通知→发送”。它降低了规划的不确定性，但每个写操作仍须核验当前权限、资源归属、批准范围和预算。
- **动态 Agent**可根据上下文规划“先查资料，再通知客户”。规划提高灵活性，不改变权限模型；Agent 产出的工具名、资源 ID、参数和理由都只是候选调用。

因此，应把模型输出规范化为类似：

`proposed_call = (actor, tool, resource_id, parameters, purpose)`

执行器在模型外重新验证：当前 actor 是否有该工具权限；资源 ID 是否属于允许范围；参数是否符合当前合同与已批准内容；预算、幂等条件和会话状态是否仍有效。任一权限源、批准服务或合同状态不可用时，应停止，而不是采用“看起来合理”的宽松结论。

同样，工具返回也只是数据。返回“R9 的正文为 9 B”但标记 `status=proposed`，并不使该正文自动成为可发送内容；无权读取的私有正文，也不能以“Agent 需要更多上下文”为由注入模型上下文。网页、文档、工具描述和结果中的指令均可能是提示注入，进入上下文不会提升其授权级别。

把“提议”和“执行”隔开，才能让拒绝原因、批准依据与实际副作用在模型外被确定、审计和恢复。

### 工具调用前的七项核验

### 工具调用前的七项核验

模型产生的“调用工具”不是命令，而是一份待审议的提案。执行器应位于模型外部，并对每一次调用重新构造可验证的判定链：

1. **行动者**：确认请求代表谁发起，身份、会话绑定与委托关系是否仍有效；不能把模型身份当作用户身份。
2. **工具权限**：确认该行动者当前可使用此工具及其动作等级。例如可检索不等于可发送，可草拟不等于可提交。
3. **资源 ID**：验证目标会话、文档、收件人或记录真实存在，且行动者对该具体资源具有所需权限；不得由模型用猜测的 ID 越权探测。
4. **参数**：按严格模式校验类型、长度、收件人范围、正文来源及敏感字段。工具返回的内容只是数据：即使 R9 返回“9 B”，若其 `status=proposed`，也不能直接作为发送正文。
5. **批准**：将本次写操作与批准中绑定的行动者、资源、参数摘要、有效期和风险条件逐项比对。参数变更，尤其是正文、对象或收件人变更，应触发重新批准。
6. **预算**：核验调用次数、金额、消息配额、频率和风险额度；预算应按已保留或已执行的操作原子扣减，避免并发绕过。
7. **当前合同**：确认仍适用最新业务规则、组织策略、会话状态和撤销信息。旧检索结果、旧工具描述或旧批准都不能覆盖当前合同。

可将判定抽象为：

`允许执行 = 身份 ∧ 工具权 ∧ 资源权 ∧ 参数合法 ∧ 批准匹配 ∧ 预算充足 ∧ 合同有效`

其中任一依赖不可用——如权限源、批准服务或合同版本无法读取——写操作应默认停止，而非采用宽松猜测。执行器还应记录拒绝项与证据版本，使“为什么未发送”能够被审计，而不是交由模型自由解释。

### 私有资料与提议消息的拒绝示例

### 私有资料与提议消息的拒绝示例

`q-02` 中，模型先检索到资源 `R9`，工具返回摘要为“9 B”，但同时标注：

- `status=proposed`
- `body=9 B`
- 来源为未确认的提议消息

随后模型请求：

`send_to_conversation(conversation_id=C1, body="9 B")`

系统仍必须拒绝。`status=proposed` 表示该内容尚未成为可发送正文；“工具已经返回”只说明模型获得了数据，不等于该数据取得了发送资格。发送前的外部校验应确认：当前 actor 是否可向 `C1` 发送、`R9` 是否允许用于该会话、正文是否与已批准内容一致、预算是否尚可用。任一条件不满足，拒绝并记录如 `REJECT_PROPOSED_CONTENT`，而非让模型自行将提议“转正”。

`q-03` 中，模型声称“需要更多上下文才能完成回复”，并请求读取私有资料正文。即使该理由看似合理，也不能绕过读取权限。系统只能依据 actor、资源 ACL、会话成员关系、数据用途和当前合同判定；若 actor 无权读取正文，应仅返回不泄露对象细节的拒绝结果，例如“当前身份不可读取该资源内容”。

尤其不能把“Agent 需要更多上下文”当作授权规则。模型的任务需求、网页中的指令、文档里的“请调用发送工具”等，都只是输入数据；它们不能扩大私有资料的可见范围，也不能把受限内容升级为可发送消息。批准服务、权限源或合同状态不可用时，应停止写入与读取，而不是猜测一个宽松结论。

### 写操作的状态、未知结果与重批

### 写操作的状态、未知结果与重批

写操作不能被建模为“调用成功/失败”二元结果，而应具有可审计的状态机：

`草稿 → 已校验 → 已批准 → 执行中 → 已执行｜已拒绝｜未知结果`

- **草稿**：模型、检索文档或用户消息提出的发送意图。此时正文、收件人、资源 ID 都只是候选值，不能调用发送工具。
- **已校验**：系统在模型外确认 `actor`、会话成员关系、工具权限、资源存在性、参数格式、预算与当前合同。校验只说明“可被批准”，不等于已获发送许可。
- **已批准**：批准记录应绑定不可歧义的内容摘要，例如收件会话、正文哈希、附件、预算和有效期。正文从“9 A”改成“9 B”，即使来源是工具返回，也已改变批准对象，必须重新校验并重批。
- **执行中**：向外部系统提交带幂等键的请求；调用期间不能因模型的新建议覆盖原批准内容。
- **已执行**：仅在可信工具响应、可查询的服务端状态或回执确认后进入该状态。

`409` 不是“再试一次”的同义词：它可能表示幂等键冲突、版本冲突或目标已被修改。系统应读取冲突语义，必要时重新获取状态、生成新草稿并重批，而不是让模型猜测如何绕过冲突。

更危险的是响应丢失或超时：请求可能根本未到达，也可能已经完成但回执丢失。此时状态应标为**未知结果**，禁止自动重发，否则可能造成重复通知。应优先按幂等键查询执行记录；无法查询时停止后续写入，向用户或运营流程报告待核对事项。

任何批准服务、权限源或当前合同不可用，都应使状态停留在草稿或已校验，而非推断一个宽松结论继续执行。拒绝、冲突和未知结果均应记录原因、关联请求与状态证据，供恢复流程在模型外决定下一步。

### 错误分类、失效停止与轨迹评测

### 错误分类、失效停止与轨迹评测

工具调用应返回机器可判定的错误类别，而非把自由文本错误原样交给模型“继续尝试”。建议至少区分：

- `参数无效`：字段缺失、格式错误、正文超限；可允许修正，但修正后的 `resource_id`、收件人或正文若改变已批准内容，必须重新批准。
- `未授权`：actor 不具备当前资源或动作权限；只返回必要的拒绝码，不暴露私有对象存在性、成员关系或正文。
- `未找到/隐藏`：对非成员隐藏对象时，可统一为不可见结果，避免 `404` 成为枚举侧信道。
- `冲突`：如 `409` 表示版本、幂等键或资源状态冲突；不得把它解释为“换一个 ID 再试”。
- `超时/未知结果`：执行状态未知时停止重发，先按幂等键查询结果；否则可能重复发送。
- `依赖失效`：批准服务、权限源、预算服务或当前合同不可用、过期、撤销时，写操作一律失败关闭。

每次调用前，应用应重新检查：

`actor → 工具权限 → 资源范围 → 参数 → 批准 → 预算 → 当前合同`

其中任一条件不成立，即记录结构化拒绝原因，例如 `approval_expired`、`budget_exhausted`、`contract_revoked`，并终止该执行分支。检索文档中的“请调用 `send_to_conversation`”只是非可信数据，不能补足权限；模型提出的计划也不能覆盖撤权。

评测不要只看最终是否“成功发送”，而要检查完整调用轨迹：是否把私有正文注入上下文，是否在批准失效后仍调用工具，是否将 `status=proposed` 的“9 B”误作可发送正文，是否在未知结果后盲目重试，以及每次拒绝是否包含可审计但不过度泄露的原因。这样才能验证系统真正控制了动作，而非仅让模型看起来遵守规则。

> **要点** — 任何外部内容都不能授予权限；写工具必须在模型外逐次核验，并在不确定时停止执行。

本节将把六道只读题转化为可复核的工具轨迹评测，并明确动作工作流必须另设授权与故障用例。

### 从文本答题转向轨迹验证

### 从文本答题转向轨迹验证

文本答案答对，只能说明模型说出了一个看似合理的结论；它并不能证明模型曾在正确时间调用正确工具、读取正确对象、处理不确定状态，或在需要确认时真正完成了确认。

以六道只读题为例，评测不应只检查“当前是 6 B”“R9 未生效”这类结论，还应核对轨迹是否满足：

- `q-01`：是否查询了当前容量来源，而非引用缓存或猜测。
- `q-02`：是否检查 R9 的实际生效状态，并区分“已提交”“处理中”“未生效”。
- `q-03`：面对无权操作时，是否明确拒绝、停止后续调用，而非虚构成功。
- `q-04`：状态未定时，是否保留 `unknown`，而非强行二选一。
- `q-05`：收到 `200` 时，是否仅确认服务端受理，而不误判为设备送达。
- `q-06`：是否识别 broker 的 `24h` 保留边界，拒绝承诺 `25h` 离线补齐。

因此，一条可评测轨迹至少应记录：决策时间、工具及参数摘要、返回状态、状态判断依据、错误与重试、检查点、人工介入和最终确认点。尤其要区分“工具返回成功”“业务状态已更新”“目标设备已确认”三个层次。

若评测扩展到动作工作流，还必须加入已授权动作案例及故障变式：草稿不得执行；批准后参数不得漂移；正文需校验仍为 `6 B`；越权请求必须拒绝；响应丢失后停在 `unknown`；重启后不得擅自重发。评测对象是可复核的过程，不是语言上像正确答案的文本。

### 六类只读能力基线

### 六类只读能力基线

六题应评测“是否沿正确证据链得出结论”，而非仅匹配最终文本。每题至少记录：查询时间、调用工具与参数摘要、返回证据、推理结论、置信状态及停止原因；断言应直接绑定可观察事实。

| 题目 | 应观察的证据与断言 | 常见误判 |
|---|---|---|
| `q-01` 当前 `6 B` | 读取最新余额或状态快照；断言结论为当前值 `6 B`，且时间戳与对象标识匹配 | 使用过期缓存、把流水累计当余额 |
| `q-02` `R9` 未生效 | 查询规则版本、启用状态与生效时间；断言 `R9` 尚未进入有效配置 | 看到规则存在便断言已生效 |
| `q-03` 无权拒绝 | 读取角色、权限范围和审批策略；断言主体无拒绝权限，并明确其可升级给谁 | 把“不能执行”误写成“已拒绝” |
| `q-04` 未定 | 证据不足、状态冲突或等待外部确认时，断言输出“未定”及缺失证据 | 为追求完整答案而猜测 |
| `q-05` `200` 非设备送达 | 区分接口响应成功、broker 接收、设备回执；断言 `200` 仅表示请求层成功 | 将 HTTP `200` 等同于设备已收到 |
| `q-06` broker `24h` 边界 | 对照离线时长、保留策略和补齐机制；断言 broker 不能保证 `25h` 离线后的补齐 | 将“通常可重试”说成“必然送达” |

评测时可要求轨迹停在最小充分证据处：例如 `q-04` 不应继续臆测，`q-03` 不应尝试执行拒绝动作，`q-06` 不应把超出保留窗口的结果包装为成功保证。最终答案正确但工具查询对象错误、版本错误或忽略时间边界，仍应判为失败。

### 动作案例与状态机断言

### 动作案例与状态机断言

只读题只能验证“能否判断”，不能证明 Agent 会“安全地执行”。动作工作流应把一次 IM 操作建模为可持久化的状态机，而非一段从理解到发送的自由文本：

`draft → validated → awaiting_approval → approved → executing → unknown|failed|confirmed`

其中每次迁移都需满足明确门槛，并写入检查点。

- **草稿 `draft`**：生成候选动作、目标、参数和理由，但不得调用发送、删除、拒绝等副作用工具；“草稿不执行”应是独立断言。
- **校验 `validated`**：验证接收者、设备标识、正文、时效和权限。例如“当前 6 B”不能只匹配数字，必须校验正文确为 `6 B`，而非 `16 B` 或含混改写。
- **待批准 `awaiting_approval`**：凡涉及发送、拒绝、覆盖配置等动作，均冻结参数摘要，等待具备权限的主体批准；无权用户的拒绝请求必须停在此处或被拒绝。
- **已批准 `approved`**：批准应绑定动作标识与参数哈希。批准后若接收人、正文、设备或时限变化，批准自动失效，必须重新校验与批准。
- **执行中 `executing`**：仅在存在有效授权时调用工具，并记录时间、工具、参数摘要、费用、步数和幂等键。
- **未知 `unknown`**：工具响应丢失、超时或进程中断时，不能假定成功，更不能自动重发；应查询外部确认点或转人工。
- **已确认 `confirmed`**：确认的是设备实际送达或服务端可核验结果，不能把 HTTP `200` 误作设备送达。
- **失败 `failed`**：保存错误、已完成步骤和恢复条件；重启后从检查点恢复，未经确认不得重复产生副作用。

动作评测至少应覆盖：草稿未执行、批准后参数未变、`6 B` 正文校验、越权拒绝、响应丢失停在 `unknown`、重启后不擅自重发。断言对象应是完整工具轨迹与状态迁移，而非最终文本是否“答对”。

### 未知结果下的停机边界

### 未知结果下的停机边界

动作型 IM 工作流最危险的状态不是“失败”，而是“结果未知（`unknown`）”：请求可能尚未到达服务端，也可能已经执行成功但响应在网络、代理或进程崩溃中丢失。此时，系统不能把“未收到成功响应”等同于“未执行”。

例如，Agent 已获批准向用户发送消息，调用发送工具后连接超时。它应记录请求标识、参数摘要、调用时间、授权与批准证据、超时错误及当前检查点，并进入：

`已批准 → 已提交 → unknown → 等待核验/人工介入`

而不能自行重发。重发可能造成重复私信、重复扣费、重复关闭工单，甚至在参数已变化时产生与原批准不一致的动作。

重启同样不能消除不确定性。恢复器应从持久化检查点读取“已提交但未确认”的操作，优先使用只读工具按幂等键、消息标识或服务端审计记录核验结果：

- 已确认执行：写入最终确认点，不再发送；
- 已确认未执行：回到待批准或允许重试的状态，重新检查授权范围；
- 仍无法确认：保持 `unknown`，升级人工处理；
- 授权已过期、参数与原批准不一致：即使判断未执行，也不得沿用旧批准。

因此，评测不能只看最终文本是否“发对了”，还要检查轨迹是否在响应丢失后停止、是否保存足够的核验线索、重启后是否避免擅自重发。`unknown` 是安全停机边界，不是可由模型猜测填补的空白。

### 审计字段与生产评测边界

### 审计字段与生产评测边界

工具轨迹是否可信，不能只看最终文本答对与否；必须能复核“何时决定、调用了什么、为何停止”。每次运行至少记录：

| 字段 | 记录重点 |
|---|---|
| 决策时间 | 规划、调用、重试、停止及恢复的时间戳 |
| 工具与参数摘要 | 工具名、目标资源、查询条件、参数哈希或脱敏摘要；避免无必要保存敏感正文 |
| 授权与批准 | 当前权限、请求动作、批准人、批准时间、批准后参数是否变化 |
| 预算 | 已用/剩余步数、时间、费用、重试次数及触发的上限 |
| 错误与状态 | 超时、权限拒绝、响应丢失、校验失败，以及 `pending`、`unknown`、`confirmed` 等状态 |
| 检查点与人工介入 | 可恢复检查点、介入原因、人工决定及恢复入口 |
| 最终确认点 | 来自设备、服务端或业务系统的确认，而非仅记录 HTTP `200` |

六道题只适合作为教学用的只读基线：例如 `q-05` 必须区分“接口返回 200”与“设备实际送达”，`q-06` 不能把 broker 的 24 小时保留承诺误写成 25 小时离线补齐。它们可以验证读取、解释和证据引用，却不能推出生产成功率。

一旦评测动作工作流，案例必须显式包含授权动作及故障变式：草稿不得执行；批准后参数不得漂移；6 B 正文必须校验；无权请求必须拒绝；响应丢失后停在 `unknown`；重启后不得擅自重发。生产阈值也不能沿用教学题正确率，而应依据业务失败成本、真实流量分布、权限模型与人工兜底能力制定。

> **要点** — 评测应验证受权工具轨迹与状态边界；只读题基线不能替代动作安全性或生产成功率。

虚构IM发送不是“调用接口即可完成”，而是要把工具合同、状态迁移与业务授权共同设计为可审计、可暂停、可恢复的受控流程。

### 先选对形态：资料回答、工作流与Agent

### 先选对形态：资料回答、工作流与Agent

面对“帮我发一条 IM”这类请求，先不要把所有自动化都称为 Agent。三种形态的关键差异在于：**谁拥有下一步的决策权，以及决策能否越过既定边界。**

- **资料回答**：系统检索有权访问的资料，再生成说明或建议；输出是信息，不直接改变外部世界。若问题只是“这个群能否发送公告”“发送上限是多少”，固定检索链通常已足够。
- **工作流**：程序预先规定步骤、分支、校验与停止点。例如：解析请求 → 校验权限 → 校验正文 UTF-8 字节数 → 请求批准 → 调用发送工具 → 查询结果。模型只能填写受限字段或解释结果，不能自行跳过批准、改发件人或扩大发送范围。
- **Agent**：模型可在许可范围内动态决定下一步、选择工具、继续检索或调整计划。它适合任务路径确实未知的场景，但也意味着更大的工具选择空间、更复杂的审计与恢复要求。

虚构 IM 发送优先采用**固定工作流**。因为发送会产生外部副作用，且常受 `actor`、会话、正文、有效期、频率和批准状态共同约束。模型可以协助理解用户意图，例如把“通知项目群”解析为候选会话；但“向哪个会话、以谁的身份、发送哪段不可变正文、是否已获批准”必须由显式合同和可信状态决定。

可用一个简化原则判断：若错误答案只需更正文本，偏向资料回答；若错误动作会发出消息，偏向工作流；只有当任务必须在多个受控工具间探索、且每一步都能被严格限制和审计时，才考虑 Agent。这里的“已发送”也不能由模型宣称，而要看可信工具轨迹及其实际结果。

### 工具合同：读写分离与副作用声明

### 工具合同：读写分离与副作用声明

工具合同应明确：**谁能调用、可读写什么、成功究竟证明什么、失败后能否安全重试**。不要把“函数返回成功”笼统等同于“消息已送达”。

- **查询工具**：如`查询会话`、`获取成员权限`、`查询消息状态`。只读、无副作用，输出应含数据来源、版本或查询时间；它只能提供决策证据，不能代替授权。
- **草稿工具**：如`创建草稿`、`更新草稿`。可写入可撤销的草稿区，但不得发送。输入包括会话、正文、操作者；输出草稿`id`、版本、字节数及状态`draft`。
- **校验工具**：如`校验发送请求`。检查 actor、会话、资源范围、正文摘要、UTF-8 字节预算、频率限制与有效期。校验通过只表示“当前参数符合规则”，不表示已经批准，更不表示已经发送。
- **批准工具**：如`批准发送`。批准记录必须绑定具体`actor`、会话/资源、动作、正文或参数摘要、有效期及策略版本。正文、收件人或权限变化后，旧批准失效。
- **发送工具**：唯一允许产生外部副作用的工具。必须显式声明副作用：可能写入服务端、进入 broker、触发推送；返回`accepted_in_memory`只证明本进程受理，不能证明持久化或对端设备收到。

发送输入还应携带`idempotency_key`、已批准的参数摘要和预期草稿版本。输出不能只给布尔值，而应区分`sent`、`rejected`、`result_unknown`等可信状态，并附服务端消息 ID、回执或错误证据。网络超时后若结果未知，流程应停止自动重发，改用查询工具核验权威记录；不能因“本地没有成功记录”而假定未发送。

### 受控发送状态机：从草稿到检查点

### 受控发送状态机：从草稿到检查点

把“发送消息”建模为显式状态机，而非一次函数调用。每次迁移都应记录 `actor`、会话/资源、动作、正文摘要、预算、权限版本、工具调用标识与证据；只有可信工具轨迹及实际结果，才能证明状态已变化。

```text
draft
  → validating
  → awaiting_approval
  → executing
  → succeeded（写入检查点）
  ↘ rejected
  ↘ result_unknown
```

- `draft`：仅有意图，允许编辑正文和收件目标。
- `validating`：检查参数、会话权限、内容策略与预算。例如当前正文上限为 6 UTF-8 B，则每个汉字约占 3 B；“你好”恰为 6 B，“你好啊”即超限。
- `awaiting_approval`：校验通过但尚未获得业务批准。批准必须绑定具体 `actor`、会话、动作、正文/参数摘要和有效期；正文、目标或权限变化后，旧批准失效，必须重新校验。
- `executing`：已提交工具调用，但尚无权威完成证据。此时不能因本地超时就回退到草稿或直接重发。
- `succeeded`：服务端或权威查询确认成功后，写入带版本、结果和幂等标识的检查点。检查点不是“内存里已受理”，而是可恢复、可审计的可信状态记录。
- `rejected`：校验、权限或批准失败；流程停止，修改后从 `draft` 重新开始。
- `result_unknown`：网络中断、超时或响应丢失时进入。服务端可能已经受理，因此禁止自动重发；应查询权威证据或等待人工处理。

合法迁移的关键是单向保守：`executing → succeeded` 需要实际成功证据，`executing → result_unknown` 用于证据缺失。重复标识返回 `409` 也不能单独证明本次或原操作成功；它只说明该标识已存在，仍须查验对应结果。

### 响应丢失时为何不能自动重试

### 响应丢失时为何不能自动重试

设 S2 执行“向会话 `c17` 发送正文 `你好`”，携带幂等键 `k-42`。客户端发出请求后网络断开：它既没有收到成功响应，也没有收到失败响应。此时唯一可靠结论是：**结果未知**，应写入 `result_unknown`，而非把它当作“发送失败”。

自动重试看似安全，却可能把不同层次的事实混为一谈：

- `accepted_in_memory`：服务进程暂时受理，不证明已落库、已写入 broker，或已投递到 B 设备。
- 持久化受理证据：例如可信服务端记录显示该幂等键对应的消息已保存；这仍不等于用户已看到消息。
- 实际送达：需要独立的投递或已读回执，不能由一次请求响应替代。

更棘手的是，当前 S2 对重复 `k-42` 返回 `409`。这个 `409` 只能说明“该键已存在或被拒绝重复使用”，**不能证明**原操作成功，也不能证明本次重试安全完成。若响应丢失后改用新幂等键重发，系统则可能生成两条内容相同的消息。

因此流程应停止自动发送，保留原始键、参数摘要和时间线，转而查询权威状态：该键是否持久化、对应消息标识为何、投递处于何种阶段。只有取得可信证据，才能决定恢复等待、提示人工处理，或在明确未受理时重新创建动作。

### 把权限和预算变成业务决策门

### 把权限和预算变成业务决策门

在虚构 IM 中，工具可调用不等于业务可发送。应用层应在执行前设置“批准门”：只有可信身份、明确目标、有限内容和未过期授权同时成立，流程才可从 `awaiting_approval` 进入发送阶段。

批准令牌至少绑定：

- 主体：具体 `actor`，不可由其他用户或模型代用；
- 范围：会话、资源与允许动作，例如“仅向会话 A 发送”；
- 内容：正文或参数摘要、哈希及版本；
- 有效期：短期失效，策略、会话、正文或收件人变化后必须重新批准。

预算也是业务规则，而非模型建议。若当前合同规定每条消息最多 `3 B`，两条合计 `6 B`，则新正文超限、拆分后总量超限，或剩余额度不足时，都应停在 `awaiting_approval` 或直接拒绝；不得为了“完成任务”自动压缩、改写或扩大额度。

撤权应优先于重试：令牌失效、用户撤销、风险策略升级、发送结果为 `result_unknown` 时，停止自动重发，先查询权威轨迹。`accepted_in_memory` 只表示进程接收，不证明落库、broker 持久化或对端设备收到；重复 ID 返回 `409` 也不能证明原操作已安全完成。

对提示注入应把外部消息、检索文本和附件一律视为不可信数据。它们可以提供内容候选，不能改变工具范围、批准令牌、预算或状态机。评测时检查可信工具轨迹及实际结果：是否在正确状态申请批准、是否携带匹配令牌、是否遵守字节预算、未知结果时是否停止，以及撤权后是否仍有发送尝试。

> **要点** — 可信IM自动化依赖受限工具合同、可恢复状态机和权威结果证据；未知结果必须停下核查，不能凭本地感受重发。
