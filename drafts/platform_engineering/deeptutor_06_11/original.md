本节从“消息已提交却在历史列表消失”的现象出发，厘清本机提交、复制推进与副本可见之间不可混同的边界。

### 一条消息经历的五个位置

### 一条消息经历的五个位置

以会话 `c-a` 的稳定消息标识 `m-a`、顺序号 `seq1..8` 为例：用户发送 `seq8` 后，不能只问“它是否成功”，而要问它目前位于哪一层。

1. **客户端已发出**：设备将 `m-a` 与 `seq8` 提交给服务端；此时网络重试可能发生，因此 `m-a` 必须用于幂等去重，不能仅靠到达次数判断新消息。

2. **主库事务已提交**：主库写入消息行、会话游标及必要索引，并返回 `COMMIT`。这表示主库崩溃恢复后应保留 `seq8`，但不表示任何副本已经拥有它。

3. **变更已进入复制流**：提交产生的 WAL/日志被发送给副本。异步复制下，主库可先确认客户端，再等待副本接收；此处仍可能存在复制延迟。

4. **副本已应用**：副本接收并回放日志，`seq8` 的行和索引才真正出现在副本的数据版本中。若历史查询固定读副本，在此之前仍只能读到 `seq1..7`。

5. **查询副本已可见**：副本完成应用，且查询所需快照、索引和路由均已切换到该副本，历史列表才会返回 `m-a`。可见性还受读事务快照影响：旧快照即使在副本已应用后也未必看到新行。

因此，主库 `COMMIT`、副本接收、副本应用、历史可读是不同确认点。`m-a` 保证重试不重复，`seq` 保证会话内排序；两者都不能替代“副本已可见”的确认。

### 提交不等于副本可见

### 提交不等于副本可见

设会话 `c-a` 的消息按 `seq=1..8` 写入主库，且每条消息都有稳定标识 `m-a`。当 A 发送第 8 条消息时，服务端执行：

`INSERT message(conversation_id, seq, message_id, ...) VALUES ('c-a', 8, 'm-a-8', ...)`

随后 PostgreSQL 在主库返回 `COMMIT` 成功。此时真正得到的保证是：该事务的 WAL 已按当前提交策略持久化到**主库**，后续主库查询应能看到 `seq=8`；它并不保证副本已经收到、重放并向查询连接可见。

一个典型时间线如下：

1. `t0`：主库已有 `c-a` 的 `seq=1..7`。
2. `t1`：A 写入 `seq=8`，主库 `COMMIT` 成功。
3. `t2`：A 立即请求历史列表，但请求被路由到只读副本。
4. `t3`：副本尚未接收或尚未应用对应 WAL，只返回 `seq=1..7`；若复制刚建立、查询条件又较严格，甚至可能返回空列表。
5. `t4`：副本接收并重放 WAL 后，`seq=8` 才出现在副本历史中。

这里的“异步复制”意味着主库不等待副本确认就完成提交；“应用确认”则表示副本不仅收到了 WAL，还已重放到可查询状态。两者之间存在复制延迟。

因此，`COMMIT` 不能被解释为“所有副本可见”，更不能解释为“另一台设备已收到消息”。前者属于复制与读路由问题，后者还涉及推送、拉取和设备确认。若故障发生在副本应用前，这段未复制的数据构成恢复点目标（RPO）风险；切换后多久恢复服务，则属于恢复时间目标（RTO）。

### 异步复制的延迟与确认

### 异步复制的延迟与确认

对主库而言，`COMMIT`只说明事务已写入本机的持久化日志；对副本而言，同一变更还要经历一条独立链路：

1. **接收**：副本收到主库发送的日志数据。
2. **持久**：副本将收到的日志写入自己的日志文件。
3. **回放**：副本重放日志，实际修改本地数据页。
4. **可见**：副本上的查询快照能够读到该修改。

设消息 `m-a` 在主库提交位置为 $L_c$，副本当前接收、持久、回放位置分别为 $L_r,L_f,L_a$。通常有：

$$L_a \le L_f \le L_r$$

只有当 $L_a \ge L_c$，并且读请求取得的是此后的快照时，副本历史列表才应看到 `m-a`。因此，“副本已收到”不等于“副本查询可见”；“副本已持久”也不等于“已回放”。

异步复制下，主库提交无需等待副本的任何确认。应用确认只能安全地表述为“消息已在主库提交”，不能表述为“已同步到副本”“另一设备已收到”或“历史查询必然可见”。若 A 写入 `c-a` 的 `seq=8` 后立刻路由到副本读取，副本仍停在 `seq=7` 是正常的读取陈旧性，而非消息丢失。

复制延迟可按阶段观察：接收延迟、持久延迟、回放延迟，以及最终查询可见延迟。要保证“写后立刻读到”，应将该读路由主库，或携带最低日志位置/提交令牌，等待副本回放至该位置后再读。异步模式降低写入等待，却扩大了故障时未复制数据的 **RPO**；恢复服务所需时间则属于 **RTO**，二者都不能由一次本机 `COMMIT` 自动消除。

### 故障切换中的 RPO 与 RTO

### 故障切换中的 RPO 与 RTO

故障切换时，先分清两个问题：**会丢多少数据**，以及**多久恢复可用**。

- **RPO（恢复点目标）**：允许丢失的数据窗口。若主库采用异步复制，主库已 `COMMIT`、但尚未发送或尚未被副本持久化的消息，主库故障后可能消失。RPO 不是“消息表里最后一条记录”，而是切换目标副本实际拥有的最新一致状态。
- **RTO（恢复时间目标）**：从故障发生到服务重新可写、可读所需时间。它包括故障检测、选主或人工提升副本、WAL 回放、连接切换、缓存失效与对账等时间。

以会话 `c-a` 的 `seq=1..8` 为例，主库已确认写入 `seq=8`：

1. `seq=8` **未复制到副本**：提升副本后历史最高只到 `seq=7`；`seq=8` 落入 RPO 窗口。
2. `seq=8` **已复制但未回放**：副本磁盘可能已有 WAL，但查询列表暂时仍只见 `seq=7`。切换时必须等待回放完成，或在恢复流程中明确其可见边界。
3. 客户端已收到“发送成功”确认：这只证明应用曾接受请求，或主库曾提交；除非确认语义明确要求“副本持久化/多数副本确认”，否则不能推导出切换后一定可查。

因此，`m-a` 这样的稳定消息 ID 必不可少：切换后以 ID 和序号对账，补发缺失消息时做幂等写入；发现副本已有但客户端未获确认的消息，则避免重复展示或重复投递。同步复制可缩小 RPO，却通常增加写入延迟；它也不能自动缩短 RTO，因为服务恢复仍取决于切换与回放流程。

### 三类确认边界不可混用

### 三类确认边界不可混用

以会话 `c-a` 的 `seq=1..8` 为例，消息 `m-a` 在主库 A 写入成功，只能说明它跨过了**数据库提交确认**：事务已提交，主库崩溃恢复后仍应保留该行。本机 WAL 已持久化，不等于副本已经收到，更不等于用户设备已经展示。

| 确认边界 | 回答的问题 | 对历史查询的含义 |
|---|---|---|
| 数据库提交确认 | 主库 A 是否接受并持久化 `m-a`？ | 从 A 读应能看到；立即从副本读未必可见。 |
| 副本复制确认 | 副本是否收到并应用该变更？ | 只有副本已应用后，副本历史列表才可稳定返回 `m-a`。 |
| 设备送达确认 | 客户端是否收到、落盘或展示消息？ | 与数据库复制独立；副本可见也不表示设备在线或已送达。 |

异步复制中，A 返回 `COMMIT` 后才开始或继续向副本传输 WAL；副本接收、重放和建立查询可见性都需要时间。这段复制延迟会造成“发送成功，但刷新历史缺消息”的读写不一致。若主库在副本追上前故障，尚未复制的已提交消息可能丢失，其时间窗口构成 RPO；恢复到可服务状态所需时间则是 RTO。

因此接口口径应分层：发送接口可返回“主库已提交”；历史查询若路由副本，应允许短暂滞后、携带游标重试，或对刚写入内容回读主库；投递系统则另行记录设备回执。不能把 PostgreSQL 本机 `COMMIT` 宣称为“副本可见”或“已送达”。

> **要点** — 主库提交只证明本地持久化；副本可见、故障可恢复与设备已收消息分别需要独立的进度和确认语义。

PostgreSQL 的高可用与历史消息切换，关键不在“副本是否存在”，而在准确判断 WAL 已到达、已落盘、已回放以及何时对读请求可见。

### 从主库提交到副本可读的进度链

### 从主库提交到副本可读的进度链

一次主库事务的“提交”，并不等于副本已经能读到该事务。应将 WAL 的进度拆成连续但不同的阶段：

1. **生成与本地提交**：主库执行事务时生成 WAL；提交记录在主库 WAL 刷盘后，事务才对主库读者可见。
2. **发送**：`walsender` 将 WAL 流发送给副本的 `walreceiver`。网络已发送不代表副本已持久保存。
3. **接收与写入**：副本接收 WAL，并写入本机 WAL 文件。此时可用“接收位置”描述传输进度。
4. **刷盘**：副本将已写入的 WAL 刷入稳定存储；“刷盘位置”才意味着故障重启后仍可恢复这些记录。
5. **回放**：恢复进程读取副本 WAL，重做其中的数据页与事务状态变更；“回放位置”反映副本实际追赶到哪里。
6. **只读可见**：只有提交记录已经在副本完成回放后，该事务才会出现在副本的只读查询结果中。

可概括为：

`主库生成 → 主库刷盘/提交 → 发送 → 副本接收 → 副本写入 → 副本刷盘 → 副本回放 → 副本可读`

因此，监控“复制正常”不能只看连接是否存在，还要比较 WAL 位置：发送、接收、刷盘与回放之间的差距分别对应网络、磁盘和回放负载造成的延迟。尤其在历史消息切读时，真正决定读到哪一批消息的是副本的**回放位置**，而不是主库最新提交位置。

### receive、write、flush、replay 的状态含义

### receive、write、flush、replay 的状态含义

物理 standby 以 WAL 的 `LSN`（日志序列号）描述复制进度。同一段 WAL 从主库提交到副本可查询，至少跨越四个边界；“已同步”必须说明停在哪个 LSN。

- `receive`：备用库的 WAL 接收进程已从主库收到 WAL 字节流，对应接收位置。它说明数据到达了副本内存或接收链路，但不能据此断言已写入磁盘；进程异常、机器掉电时，未持久化部分仍可能丢失。
- `write`：接收进程已将 WAL 写入备用库的 WAL 文件，对应写入位置。这里的“写”通常是操作系统写入，不等于存储设备已经保证持久保存。
- `flush`：备用库已将 WAL 刷新到稳定存储，对应落盘位置。此位置以前的 WAL 在备用库崩溃并重启后仍可用于恢复，因此它是讨论远端持久性时最重要的边界。
- `replay`：恢复进程已读取并回放 WAL，将其中的记录应用为数据页、索引页、事务状态等实际变更，对应回放位置。只读查询通常只能看到 `replay LSN` 之前、且满足恢复一致性的内容。

可将进度关系概括为：

`replay LSN ≤ flush LSN ≤ write LSN ≤ receive LSN`

例如主库已提交到 `0/500`，而备用库显示 `receive=0/500`、`flush=0/500`、`replay=0/480`，表示 WAL 已安全到达副本磁盘，但最后一段尚未回放；副本读请求仍不能看到 `0/480` 之后的提交。因而，对账或切读前应比较目标事务的提交 LSN 与备用库的回放 LSN，而不能只看网络连接正常或接收位置追平。

### 同步提交级别与确认语义

### 同步提交级别与确认语义

`synchronous_commit` 决定主库向客户端返回“提交成功”前，必须等到什么程度。它不是“是否复制”的开关，而是在**提交延迟**与**故障后已确认事务的可恢复性**之间取舍；远端确认还需正确配置同步备库。

| 级别 | 返回成功前的条件 | 主要防护 | 代价与边界 |
|---|---|---|---|
| `local`（默认） | 主库 WAL 已本地刷盘 | 主库进程崩溃、普通宕机后可恢复 | 副本可能尚未收到该事务；主库存储永久丢失时，已确认提交可能丢失 |
| `remote_write` | 同步备库已接收并写入操作系统缓存 | 降低网络中断或主库故障时的丢失窗口 | 备库尚未 `fsync`；备库突然断电时，确认记录仍可能丢失 |
| `on` | 同步备库 WAL 已刷入持久存储 | 主库故障、备库重启后仍保有确认事务 | 每次提交等待网络往返与备库刷盘；默认同步复制语义通常对应此级别 |
| `remote_apply` | 备库已回放 WAL，事务对其查询可见 | 除持久化外，保证指定同步备库上的读请求能看到已确认提交 | 等待接收、刷盘、回放；长查询、恢复冲突或回放阻塞会直接拉长提交时间 |

可将确认链理解为：

`主库本地刷盘 → 备库接收/写入 → 备库刷盘 → 备库回放并可读`

`remote_write` 确认到第二步，`on` 确认到第三步，`remote_apply` 确认到第四步。因而“副本可读”并不天然意味着读到刚提交的数据；只有使用 `remote_apply`，且读取的是被要求确认的同步备库，才可将该可见性纳入提交确认。

### 复制滞后如何影响消息历史与权限读取

### 复制滞后如何影响消息历史与权限读取

应用不能把“主库提交成功”直接等同于“所有副本都能立即读到”。物理复制中，WAL 可能已被副本接收、写入甚至刷盘，却尚未 `replay`；在回放前，热备副本对查询仍呈现旧快照。

这会直接影响消息类业务：

- **历史消息缺失**：用户发送消息后，写入主库已确认；若随即被路由到滞后副本拉取会话历史，刚发送的消息可能不存在，表现为“发送成功但列表没更新”。
- **撤回、编辑未生效**：主库已将消息标记为撤回，副本尚未回放对应 WAL 时，读者仍可见原文。对隐私消息、违规内容或误发附件，这不是普通的界面延迟，而是信息暴露风险。
- **权限变化滞后**：禁言、移出群组、撤销成员资格或收回频道访问权已在主库提交；副本仍可能返回旧权限、旧成员关系或旧消息范围。若授权判断和内容读取都落在副本，用户可能在短窗口内继续读取本应无权访问的历史。
- **对账误判**：后台任务从副本扫描“未同步消息”或“未撤回记录”，可能将复制滞后误判为业务缺失，进而重复投递、重复通知或错误修复。

路由边界应按一致性要求划分，而非按“读请求”一概下沉。写后立即读取、撤回确认、权限校验、敏感消息访问及管理操作结果查询，应固定读主库，或携带提交位置并等待副本回放到该位置。普通历史翻页、搜索、统计等可容忍陈旧数据的请求，才适合读 standby。

尤其要避免“主库写入 + 副本鉴权”的拆分：写操作在主库依据新权限成功或失败后，后续读取仍应在同一一致性边界内完成。同步提交只能约束提交等待到远端写入、刷盘或 `remote_apply` 的程度；只有要求并达到 `remote_apply`，才更接近“确认返回时副本已可读”，但应用仍需明确选定哪一台副本及其故障降级策略。

### 逻辑复制与复制槽的迁移约束

### 逻辑复制与复制槽的迁移约束

逻辑复制按“发布—订阅”传播**被选定表**的行级变更：订阅端接收 `INSERT`、`UPDATE`、`DELETE`，适合将历史消息表逐步迁移到新集群，或让新旧系统并行消费。它不是完整的数据库克隆，切换前必须区分“数据变更已复制”和“数据库对象已就绪”。

| 内容 | 逻辑复制的默认覆盖情况 | 迁移时的处理 |
|---|---|---|
| 已发布表中的增删改 | 可传播 | 核对发布表集合、主键/复制标识及初始同步状态 |
| 表结构、索引、约束 | 不传播 | 先在订阅端执行 DDL，版本需兼容 |
| 序列当前值 | 不随行变更自动同步 | 切换前按源端最大值校正序列，避免新写入冲突 |
| 函数、触发器、视图、权限 | 不传播 | 通过迁移脚本或 schema 工具单独部署 |
| 未加入发布的表 | 不传播 | 明确是否需要补数、归档或停止使用 |

尤其要注意：订阅端初始复制完成，不代表所有对象都可安全写入。消息表若依赖 `BIGSERIAL`、分区创建函数或触发器生成派生记录，目标端缺少对应对象时，可能出现主键冲突、写入失败或数据语义不一致。

复制槽则决定发布端能否回收旧 WAL。槽会记录订阅端确认的消费位置；订阅延迟、网络中断或订阅失效时，发布端必须持续保留其尚未消费的 WAL。于是“复制没停”可能表现为 `pg_wal` 持续膨胀，最终挤满磁盘并影响主库写入。

迁移期间应持续监控槽的滞后量与 WAL 目录容量，并为异常订阅设定处置规则：恢复订阅、重新初始化订阅，或在确认不再需要后删除槽。不要仅因磁盘告急直接删除仍在使用的槽；这会使订阅失去所需变更，通常只能重新进行数据同步。

> **要点** — 安全切换必须以 WAL 的持久化与回放水位界定读写边界；同步级别、逻辑复制范围和复制槽容量都需显式设计。

历史消息“写后读不到”常非数据丢失，而是读到了尚未追平的副本；先拆清复制进度，才能定义可靠读路径。

### 用 seq8 与 seq7 还原问题现场

### 用 seq8 与 seq7 还原问题现场

设会话 `c-a` 的消息按单调递增序号写入。用户发送第 8 条历史消息后，主库已确认提交：

- 主库提交水位：`committed_seq = 8`
- 副本已接收日志：可能已收到 `seq8`
- 副本已持久化：可能也已落盘 `seq8`
- 副本已回放并建立可查询记录：`replayed_seq = 7`

此时，用户从主库查询会话历史，会得到：

`[seq1, seq2, ..., seq7, seq8]`

但若请求被路由到该副本，查询结果仍是：

`[seq1, seq2, ..., seq7]`

这不是“`seq8` 写丢了”，也不必然说明复制失败；准确边界是：`seq8` 已在主库对写入者提交，但尚未在该副本的**读模型**中可见。接收、持久化与回放是不同阶段，只有回放完成后，副本上的普通历史查询才能读到它。

因此，排查时不能只问“副本是否收到 `seq8`”，而应记录各水位：

`主库提交 = 8；副本接收 ≥ 8；副本持久 ≥ 8；副本回放 = 7；副本可读 = 7`

若本次读取要求写后立即可见，可选择主库读取，或等待目标副本满足 `replayed_seq ≥ 8` 后再读；若业务允许陈旧结果，则可接受副本暂时只返回 `seq7`，但响应语义应明确为“截至序号 7 的历史”。同样，成员关系、禁言和权限变更也可能停在 `seq7`：不能拿副本上的旧成员状态去授权一笔依赖 `seq8` 后新状态的写入。

### 复制链路的四层进度

### 复制链路的四层进度

设主库已提交历史事件 `seq=8`，副本只回放到 `seq=7`。此时“副本有没有 8”不能只用一个“已同步”回答，至少要区分四层水位：

1. **已接收**：副本网络端已收到 `seq=8` 的复制消息。它可能仍在内存缓冲区，进程崩溃、连接重置或消息校验失败后都未必保留。
2. **已持久**：事件已写入副本的日志、队列或本地存储，并满足该系统定义的落盘条件。它说明副本大概率可恢复该事件，但不代表查询路径已经使用它。
3. **已回放**：副本已将事件应用到可查询的数据结构、索引、状态机或物化视图中。只有回放到 `seq=8`，按业务数据查询才可能得到 8。
4. **对读请求可见**：具体读请求实际路由到该副本、选中了包含 `seq=8` 的版本，并未被缓存、快照隔离、索引刷新或读事务边界遮蔽。可见水位才直接对应“这次读能否看到 8”。

这些状态是单向推进关系，但不能互相替代：

- 已接收 $\neq$ 已持久：收到确认不等于崩溃后仍存在。
- 已持久 $\neq$ 已回放：日志中有 8，不等于状态表已更新。
- 已回放 $\neq$ 对本次读可见：读可能命中旧快照、缓存或另一台落后副本。

因此，主库读到 8、副本读不到 8，通常只说明该副本的**可见水位**仍为 7，而非 8 丢失。读路径应明确选择：强制主读、等待目标副本可见水位达到 `seq=8`，或显式接受“最多陈旧到 7”的结果；不能把“副本已接收”当作读己之写的承诺。

### 读策略由一致性承诺决定

### 读策略由一致性承诺决定

同一条历史消息在主库已提交、在副本尚未回放时，选择哪里读不是性能优化问题，而是在选择对用户作出的“一致性承诺”。设写入已在主库提交到水位 `seq=8`，副本仅回放到 `seq=7`：主库可见 8，副本读不到 8；副本即使已接收或已持久该消息，只要未完成回放，也不能据此承诺可读。

- **主库读取**：写入后的关键确认、支付状态、成员变更、权限校验等应直接读主库。它最容易提供写后读一致性：确认 `seq=8` 提交后，后续读主库至少应见到 8。代价是主库负载、跨地域延迟和可用性依赖更高；主库故障切换期间还需重新确认提交水位与新主身份。

- **等待副本追至指定水位再读**：客户端携带自己刚写成功时获得的令牌，如 `seq=8`、日志位置或提交时间戳；服务端仅当目标副本的“对读可见水位”满足 `replay_seq >= 8` 时返回，否则等待、改读主库或超时失败。这适合希望利用本地副本低延迟、但不能接受“刚发消息却看不到”的场景。代价是需要传播水位、维护副本进度，并处理等待超时与副本落后。

- **容忍陈旧副本读取**：消息列表浏览、历史搜索、统计看板、推荐等可直接读副本，并明确允许短暂缺少最新内容。它吞吐高、延迟低、易于分流，但不能宣称 read-your-writes；界面应避免把“未显示”解释为“写入失败”。

尤其不能用陈旧副本上的旧成员资格或旧权限状态授权新写：副本可能尚未回放“已移除成员”或“已撤销权限”的记录。涉及授权时，应读取满足所需水位的权威状态，通常是主库或已追平的副本。

### 不要默认副本支持写后读

### 不要默认副本支持写后读

以 `seq=8` 为例：主库已提交，副本仅回放到 `seq=7`。此时“副本收到了消息”不等于“副本已持久化”，更不等于“副本已回放并对查询可见”。若业务从副本读取，自然可能读不到刚写入的 `seq=8`。

PostgreSQL 的流复制通常由主库生成 WAL、副本接收 WAL、写入本地并回放。应用若写主库后立刻将读请求路由到热备库，读取结果只对应该热备当前已回放的 LSN；即使提交事务已在主库成功，也不能推导该副本已经可见。需要写后读时，应继续读主库，或等待目标副本回放到该事务对应的 LSN 后再读。

MongoDB 的主从复制则以 primary 的 oplog 为来源，secondary 异步拉取并应用操作。`readPreference=secondary` 只是选择从 secondary 读取，不是写后读保证；写入即使采用较强的 `writeConcern`，也只说明满足了相应确认条件，不能保证任意被选中的 secondary 已应用该写入。若要求会话内写后读，应优先使用 primary，或采用会话、因果一致性与适当的读关注级别，并确认读取节点的可见水位。

因此，复制配置中的“副本数”不应被误解为“每个副本都能立即读到最新值”。业务应明确选择：

- 强写后读：写后固定主读，或等待指定副本追平指定水位；
- 可容忍陈旧：允许副本读，但界定最大滞后和降级策略；
- 权限与成员关系：不要拿滞后的副本状态授权新写，否则旧成员、旧角色可能被错误接受。

### 权限滞后比消息滞后更危险

### 权限滞后比消息滞后更危险

消息副本少一条，通常表现为“暂时看不到”；权限副本少一条，却可能把“已撤销”误判为“仍有效”。例如成员在主库的 `seq=8` 被移出项目，副本仅回放到 `seq=7`。若应用随后向该副本查询成员关系，再允许该成员提交新消息，就发生了基于旧权限状态的越权写入。

必须区分两类读：

- **展示读**：消息列表、动态流可容忍短暂陈旧，可读副本。
- **授权读**：加入、退出、封禁、角色降级、租户隔离、额度扣减等决定“能否写”的状态，不能默认读任意副本。

安全边界应明确为：

1. **权限变更以权威状态为准**：对新写入的鉴权查询主库、强一致存储，或固定的权限权威服务。
2. **若使用副本，必须证明水位**：请求携带已知权限版本或提交序号，如要求副本已回放至 `seq≥8`；未追平则等待、转主库或拒绝本次操作。
3. **撤权优先于可用性**：无法确认“仍有权限”时，应按无权限处理，而非沿用缓存或旧副本结果。
4. **权限缓存必须可失效**：缓存键应包含成员关系版本、角色版本或策略版本；撤销、封禁后应主动失效，不能仅依赖短 TTL。

因此，不应承诺“所有 secondary 都能保证 read-your-writes”。更准确的承诺是：普通内容可容忍陈旧；涉及授权的新写入，只在权威权限状态或已确认追平的副本上判定。

> **要点** — 副本是否收到数据不等于读者可见；历史与权限读取都必须绑定明确水位和一致性承诺。

旧主失联时，切换的核心不是“尽快恢复”，而是确认新主可承载的安全进度，并彻底阻断旧主恢复后继续写入。

### 先界定提交与安全进度

### 先界定提交与安全进度

故障切换前，最危险的误解是把“旧主已提交”直接等同于“新副本一定拥有”。在异步复制中，一条消息至少会经历不同水位：

- **旧主本地提交水位**：旧主已写入本地日志并向客户端确认成功。它只证明旧主当时接受了消息，不证明副本已收到。
- **副本接收水位**：新副本已收到复制数据，但数据可能仍在内存、网络缓冲或未完成校验的暂存区。
- **副本持久化水位**：副本已将数据可靠落盘；这是提升时通常最基本的候选边界。
- **副本回放水位**：副本已按日志顺序应用数据，状态机、索引或消息队列视图已追上该位置。
- **副本可见水位**：回放后的数据已对消费者、查询或后续写入可见。可见不应越过持久化，也不应越过已确认的顺序边界。

因此，提升新副本不能只看“复制连接曾经正常”或“延迟监控接近零”，而要确认其**已持久化且可正确回放的连续日志位置**。若旧主最后确认给客户端的位置为 $L_c$，新副本安全水位为 $L_s$，则只有 $[0,L_s]$ 可作为新主无歧义继承的历史；区间 $(L_s,L_c]$ 中的消息可能已被客户端视为成功，却未到达新主。

还要注意，副本收到的日志不一定连续：中间缺洞、批次未校验完成、事务未提交、跨分区顺序未闭合时，最高接收位置不能代表安全进度。提升依据应是“最长连续、已校验、已持久化、可回放”的提交点，而不是最大的字节偏移或最新时间戳。

这个水位决定后续承诺：新主可以从安全水位继续服务，但不能宣称自动保留其后的旧主本地提交。那些不确定消息必须依靠稳定消息 ID、生产者重试记录和后续对账来确认，而不是在切换时被默认为“已经存在”。

### 提升前的进度确认

### 提升前的进度确认

异步复制中，一条消息的确认链路通常是：

`客户端 → 旧主本地追加并确认 → 复制链路 → 副本落盘`

因此，客户端收到“提交成功”只说明旧主已经接受该消息，并不等价于任何副本都已拥有它。若旧主在复制完成前失联，副本的进度只能由其已持久化的复制位点决定。

设旧主最后已确认给客户端的位点为 $L_c$，候选副本已安全落盘的位点为 $L_r$。提升该副本后，能够保证继续提供的数据前缀至多为 $L_r$；区间 $(L_r, L_c]$ 中的消息可能已被客户端视为成功，却尚未到达候选副本。这一差值就是故障切换时的潜在恢复点目标（RPO）损失边界。

选择可提升副本时，不能只看“在线”或“延迟低”，而应比较：

- **复制进度**：优先选择已落盘位点最高、且进度可证明的副本；
- **进度稳定性**：确认其日志、索引和提交元数据一致，而非仅收到内存中的复制数据；
- **副本共同前缀**：若需要重新加入其他副本，新主应位于可验证的共同历史上，避免从分叉日志继续写入；
- **确认语义**：若业务要求更低 RPO，应在正常运行时采用副本确认、仲裁提交或同步复制；故障发生后无法补回未复制的数据。

例如，旧主已向客户端确认消息 `m100`，但候选副本只持久化到 `m98`。即使 `m99`、`m100` 曾在旧主本机提交，切换后也只能以 `m98` 为安全起点；客户端必须凭稳定消息 ID 对账并重投缺失消息。提升流程能缩短恢复时间（RTO），却不能自动消除异步复制留下的 RPO 缺口。

### 隔离旧主并授予唯一写权

### 隔离旧主并授予唯一写权

旧主失联不等于旧主已经停止：它可能只是网络隔离、控制面故障，甚至仍在接受部分客户端写入。若新副本此时直接提升，就会形成“双主”，产生不可判定的分叉历史。因此，提升流程的第一目标是 **fencing（隔离或围栏）**：让旧主即使恢复，也不再拥有有效写权。

常见做法是由仲裁或配置服务维护单调递增的**纪元号**（epoch/term）或带过期时间的**租约**：

1. 新主申请更高纪元，或取得当前租约；
2. 存储层、复制层和写入网关只接受最新纪元携带的写请求；
3. 旧主的纪元较低，或其租约到期后，写入必须被拒绝；
4. 完成隔离确认后，才将新主标记为可写。

写入请求不能只依赖“客户端连到了哪个地址”。应携带由控制面签发的写入令牌，例如 `(主节点标识, 纪元号, 租约截止时间)`；服务端在提交前验证令牌仍有效。这样，旧主即使保留了旧连接、缓存了旧配置，也会因令牌过期或纪元落后而无法落盘。

连接路由同样是安全边界：服务发现、代理、负载均衡器应只把**写流量**导向当前纪元的新主，并主动断开或拒绝指向旧主的写连接。但路由切换本身不是 fencing；DNS 缓存、长连接和错误配置都可能让请求到达旧主。真正的保证必须由旧主本机或共享存储的纪元校验兜底。

因此，“唯一主写权”不是一次提升动作，而是控制面授权、旧主隔离、请求令牌验证与路由收敛共同维持的不变量：任一时刻，至多一个节点能让新写入成为权威历史。

### 消息缺口与稳定ID对账

### 消息缺口与稳定ID对账

切换后不能只比较“双方各有 100 条消息”。计数相同，仍可能是旧主有 `{A,B,C}`、新主有 `{A,B,D}`；计数不同，也可能只是重复投递。因此，对账的基本单位应是**会话标识 + 稳定消息ID**，而不是行号、时间戳或消息总数。

稳定消息ID应由客户端在首次发送前生成，并在重试、断线重连、跨主切换时保持不变。例如：

`conversation_id = c42`，`message_id = 8f3a...`

服务端以 `(conversation_id, message_id)` 建立唯一约束或幂等写入记录：同一ID再次到达时，返回既有结果而非再生成一条消息。这样，客户端无法确认“请求是否成功”时可以安全重发。

对账接口通常按会话返回：

- 服务端已确认接收的消息ID集合，或其压缩摘要；
- 连续确认水位 `ack_watermark`，表示此前序号均已持久化；
- 水位之后实际存在的消息ID，用于处理乱序、跳号和补写；
- 每条消息的状态，如“已接收”“已复制”“不可恢复”。

客户端应维护本地待确认队列。切换后，以稳定ID计算差集：

- `本地待发送 − 服务端已知`：重新投递；
- `服务端已知 − 本地已确认`：补写本地确认状态；
- 同ID但内容摘要不同：视为协议或数据损坏，禁止静默覆盖。

水位只能说明连续区间完整，不能替代ID核验：异步复制可能丢失水位之后已在旧主本机提交的消息；乱序传输也会使“最大序号”看似靠前而中间仍有缺口。对账完成前，应向用户明确展示“正在恢复”或“发送状态待确认”，而非宣称切换自动实现零丢失、零重复。

### 切换承诺、回退与数据库口径

### 切换承诺、回退与数据库口径

**RPO** 是可接受的数据丢失上限：旧主故障后，新主最多可能缺少多久或多少条“已向客户端确认”的写入。**RTO** 是恢复服务所需时间：从判定故障、选主、路由切换到可写的耗时。二者不能互相替代：复制延迟很小不代表切换很快；切换很快也不代表最后确认的写都能保留。

“回退窗口”则是旧主恢复后，仍可安全观察、对账或导出其独有数据的时间段。它不是允许旧主重新接客的窗口。只要新主已提升，旧主必须被隔离、降级或用租约/代际号拒绝旧写请求；否则两个节点各自接受写入，会形成双写分叉，之后无法仅靠时间戳无损合并。

PostgreSQL 以 WAL 的 LSN 描述复制进度。异步复制下，主库本地提交即可返回，备用库可能尚未接收或回放对应 WAL；故障提升时，这部分确认写可能落在 RPO 内而丢失。同步提交可要求备库达到 `remote_write`、`on`（刷盘）或 `remote_apply`（已回放），承诺强度依次提高，但写延迟和可用性代价也更高。读副本“已看到”的数据，应以其回放位置为准，而非主库当前提交位置。

MongoDB 以复制日志中的 `opTime` 和多数提交点描述进度。`writeConcern: "majority"` 表示写入已获多数节点确认，通常可避免被选举回滚；`w: 1` 仅说明当前主节点确认，故障切换后可能回滚。读取同样需区分：`readConcern: "local"` 可见本地尚未多数提交的数据，`"majority"` 才以多数提交点为口径。

因此，切换公告应明确“新主从哪个 LSN 或 `opTime` 开始承诺”，客户端再按稳定消息 ID 对账、幂等补发。不能把“完成切换”宣传为自动零丢失、零重复；只有确认语义、复制模式与实际故障边界共同决定结果。

> **要点** — 安全切换依赖可验证进度、旧主隔离和唯一写权；异步复制须承认RPO，并以稳定ID完成对账。

将历史消息从存储A迁往存储B，关键不在“把数据拷过去”，而在于证明任一消息版本都未丢失、未重复、未被旧状态覆盖。

### 先固定权威写入与迁移边界

### 先固定权威写入与迁移边界

迁移开始前，先声明：**存储 A 在切换完成前仍是唯一权威写入端**。所有发消息、编辑、撤回、删除、反应状态变更等请求，仍先提交 A；存储 B 只是复制目标，不接受会改变业务事实的独立写入。否则 A、B 都可能产生同一 `message_id` 的不同版本，后续无法仅靠“最后写入胜出”安全合并。

迁移边界应以源端的可恢复变更位置表示，记为 $W_0$。它可以是数据库日志位点、CDC offset、事务提交序号或一致性快照对应的变更水位。复制任务从 A 在 $W_0$ 对应的一致快照读取历史数据；CDC 则从 $W_0$（或更早的安全位置）持续消费之后的变更。其目标不是“复制到某个时间”，而是保证：

$$
\text{B 的快照数据}+\text{从 }W_0\text{ 起的变更事件}
=\text{A 的完整状态}
$$

必须区分三个常被混淆的编号：

- **源变更水位 $W_0$**：描述 A 的全局或分片变更日志位置，用于衔接快照与 CDC。
- **会话序号 `seq`**：描述某个会话内消息的展示或排序顺序，例如 `seq=1..5`；它不能代表 CDC 的消费位置。
- **消息版本 `version`**：描述同一 `message_id` 的状态演进，如创建、编辑、撤回、删除。B 应按 `(message_id, version)` 幂等应用，并拒绝旧版本覆盖新版本。

例如，快照中复制了会话 `c-a` 的 `seq=1..5`，并不意味着 CDC 应从 `seq=6` 开始；CDC 必须从源端水位 $W_0$ 衔接，可能收到消息 6、7、8，也可能收到对消息 3 的编辑或删除。迁移边界固定后，后续复制、追平和校验才有共同的事实基准。

### 一致快照与增量变更如何衔接

### 一致快照与增量变更如何衔接

设源存储 A 的可排序变更日志位置为 $W$，在时刻选择一个可校验水位 $W_0$。迁移不是“先复制、再订阅”，而是构造两个无缝覆盖的集合：

- 存量副本：一致快照中所有在 $W_0$ 时刻可见的消息版本；
- 增量副本：日志中位置满足 $W>W_0$ 的全部变更事件。

因此目标存储 B 的最终状态应满足：

$$B=\operatorname{Apply}(\operatorname{Snapshot}(A,W_0),\operatorname{CDC}(W_0,+\infty))$$

这里的关键前提是：快照读取与 $W_0$ 必须属于同一一致性边界。若先读数据、后记录水位，则两者之间写入的消息可能既不在快照中，也未被 CDC 消费；若先记录水位、再读非一致快照，则快照可能混入 $W_0$ 之后的新版本，造成重放顺序混乱。

安全做法是：

1. 从 A 获取可验证的一致快照及其日志位置 $W_0$；
2. 以该快照复制历史记录；
3. CDC 从 $W_0$ 开始，或从略早位置开始消费；
4. 将每个事件按 `message_id + version` 幂等写入 B。

“从略早位置开始”通常更稳妥：重叠事件会被版本比较吸收，但遗漏事件无法补救。应用规则应是“仅当事件版本新于 B 中版本时覆盖”；删除也必须作为带版本的墓碑事件处理，不能只复制追加消息，否则已删除或已编辑的历史会在 B 中复活。

注意 $W_0$ 是源库变更日志位置，不是会话内 `seq`。`seq=1..5` 可构成某会话的快照内容，而 CDC 中的 `6,7,8` 只是业务示意；真实 CDC 顺序还可能交织其他会话、更新和删除。无缺口的证明依据是日志位置连续、可追溯且保留期覆盖迁移全程，而非单个会话序号连续。

### 按消息标识和版本幂等落库

### 按消息标识和版本幂等落库

B 端不能把迁移数据和 CDC 都当作“新消息追加”。复制批次、CDC 重放、消费者重试都会产生重复；CDC 到达顺序也可能不同于会话内 `seq` 顺序。应以稳定的 `message_id` 定位逻辑消息，以单调递增的版本号 `version` 判定新旧状态。

对每个事件统一表达为：

`{message_id, version, op, payload, source_position}`

其中 `op` 至少包括创建、更新、删除。B 端维护消息当前版本及删除标记，并执行条件写入：

- 若不存在该 `message_id`，写入事件状态；
- 若已存在且 `incoming.version > stored.version`，用新状态覆盖旧状态；
- 若 `incoming.version = stored.version`，视为重复投递，直接成功返回；
- 若 `incoming.version < stored.version`，视为乱序旧事件，忽略但记录度量；
- 删除不是物理“什么也不做”，而应写入墓碑：`deleted=true` 与对应版本。否则较晚到达的旧创建或旧更新可能把已删除消息复活。

可将核心规则理解为按版本的比较交换：

`apply(e) ⇔ e.version > current_version(message_id)`

例如，复制阶段先写入 `m42@v1`，CDC 又重放同一创建事件，B 保持 `v1`；随后先收到更新 `m42@v3`，再迟到 `m42@v2`，最终仍保留 `v3`。若 `v4` 为删除事件，则写入 `v4 + tombstone`；之后任何 `v1~v3` 的重放都不得改变可见结果。

版本必须来自 A 的权威变更序列或可靠的行版本，不能用 B 的接收时间生成。`source_position` 用于推进 CDC 消费与对账水位，`seq` 用于会话展示顺序；两者都不应替代消息版本。这样，无论复制和 CDC 如何交叠、重试或乱序，B 都能收敛到 A 在同一变更边界上的最终状态。

### 从追平到影子读的验证链路

### 从追平到影子读的验证链路

`copy` 完成不等于迁移完成：B 可能缺少复制期间的更新、删除，或因乱序消费而保留旧版本。验证链路应围绕**同一源变更水位**建立，而不是拿会话内 `seq` 当作全局进度。

- **复制阶段**：在 A 的一致快照或可校验位置 `W0` 读取历史范围，例如会话 `c-a` 的 `seq=1..5`。每条记录携带 `message_id`、业务版本、内容哈希、删除标记及源位置；B 按 `(message_id, version)` 幂等写入。若同一消息存在更新，版本较低的到达不得覆盖版本较高的状态。
- **追平阶段**：CDC 从 `W0`（或更早位置）持续消费源变更 `6,7,8...`。`W0` 是数据库日志、LSN 或事务水位；`seq` 只是会话排序键，二者不可混用。对于更新和删除，应写入新版本或墓碑，而非只执行追加插入。
- **同水位对账**：选择稳定水位 `W1`，分别在 A、B 构造“截至 `W1` 的可见状态”。先比较键集：`message_id`、会话归属、`seq`、删除状态；再比较内容：版本、正文哈希、附件元数据、编辑时间等。仅比较总数会漏掉“删一条、错写一条后计数仍相同”或“同键内容被旧版本覆盖”的问题。
- **影子读阶段**：正式读仍来自 A，同时将相同查询异步投向 B。比较结果的键集合、排序、分页边界与字段内容；差异应记录查询条件、读水位、两侧版本和哈希，便于定位是 CDC 延迟、索引可见性还是转换逻辑错误。

当 B 在连续多个水位窗口内追平，且影子读差异归零或仅剩已解释的延迟差异，才具备进入 `fence/cutover` 的证据。

### 围栏切换、回滚与双写风险

### 围栏切换、回滚与双写风险

切换围栏（fence）不是“宣布 B 上线”的时间点，而是一个可证明的边界：在围栏前，写入只以 A 为权威；在围栏后，某个会话、租户或全局路由范围内的新写入只允许落到 B。读路径也应随围栏明确归属，避免同一 `message_id` 在 A、B 间随机读取而看到不同版本。

| 阶段 | 写权威 | 读策略 | 关键证明 |
|---|---|---|---|
| `copy/catch-up` | A | A | B 已追平至目标复制位置 |
| `shadow-read` | A | A 返回、B 比较 | 比较版本、删除标记与排序结果 |
| `fence/cutover` | 按路由切至 B | 按同一路由切至 B | 围栏前事件已全部应用到 B |
| 回滚 | 仅在条件满足时回 A | 与写权威一致 | A 仍拥有 B 期间的完整增量 |

回滚并非天然安全。若切换后 B 接受写入，而这些写入未可靠回灌 A，则回到 A 会丢失围栏后的新版本。安全回滚通常要求：保留 B→A 的变更流、使用同一 `message_id + version` 幂等合并、确认回灌水位覆盖故障点；否则应采用“前滚修复”，而非直接改回 A。

双写看似降低风险，实则引入双主冲突：A、B 的写入成功顺序可能不同，某一侧超时也不代表未提交。不要以“两个库都写成功”作为一致性模型；应指定单一写权威，由变更日志异步复制。若不得不双写，必须携带单调版本、删除墓碑和确定性的冲突规则，且任何一侧失败都进入可重放任务，不能静默忽略。

复制位置也不能与会话 `seq` 混用。PostgreSQL 通常以 WAL 的 `LSN` 表示全局提交日志位置；MongoDB 常以 oplog 的时间戳或恢复令牌表示变更流位置。它们都描述“源库变更流推进到哪里”，而 `seq=1..8` 只描述某个会话内消息顺序。围栏校验应以 `LSN`、oplog 位置或恢复令牌追平；消息展示与版本判定则仍以 `message_id`、版本和会话 `seq` 为准。

> **要点** — 安全迁移依赖权威写入、快照与CDC无缝衔接、版本幂等和同水位对账；切换必须由围栏限定边界。

迁移验收不能只看“消息条数相等”。只有在同一快照水位下逐项核对键集、内容与版本，才能发现漏写、重复和错写。

### 计数相等为何仍会错

### 计数相等为何仍会错

设源端会话 `c-a` 在同一迁移范围内的消息键为：

`{1,2,3,4,5,6,7,8}`

目标端为：

`{1,2,3,4,5,6,8,9}`

两端都是 8 条，`COUNT(*)` 完全相等，却并不一致：目标端缺少键 `7`，又多出不应存在的键 `9`。因此，计数只能说明“记录数量相同”，不能说明“记录是同一批”。

即使按日期、会话或分表做分区计数，也仍可能漏检：若键 `7` 与键 `9` 落在同一分区，分区内仍可保持“少一条、多一条”的数量平衡。抽样检查同样只能提高发现问题的概率；恰好抽到 `1`、`3`、`8`，并不能证明未抽到的 `7` 已成功复制。

验收至少应比较键集差异：

- 缺失：`源 \ 目标 = {7}`
- 多余：`目标 \ 源 = {9}`
- 共同键：`源 ∩ 目标 = {1,2,3,4,5,6,8}`

随后还要对共同键核对正文、发送者、时间、状态及内容哈希；键相同不代表字段没有被截断、覆盖或错配。比较时必须固定到同一快照水位，否则源端持续写入产生的新消息会被误判为“目标缺失”。修复缺失和多余记录后，应在相同水位重新执行键集与字段校验，而不是仅复查总数。

### 以会话和范围定义对账边界

### 以会话和范围定义对账边界

对账的最小单元不应是“整库消息数”，而应明确为：

\[
R=(\text{会话标识},\ \text{消息序列范围},\ \text{统一快照水位})
\]

例如，对会话 `c-a` 的第 `1..8` 条消息，在源端水位 \(W=1200\) 读取键集：

\[
K_s=\{1,2,3,4,5,6,7,8\}
\]

目标端即使得到：

\[
K_t=\{1,2,3,4,5,6,8,9\}
\]

两边计数都为 \(8\)，也不能判定成功：目标缺少键 `7`，却多出不属于该范围的键 `9`。因此应先比较键集，派生出：

- 缺失集：\(K_s-K_t=\{7\}\)
- 多余集：\(K_t-K_s=\{9\}\)
- 共同键：\(K_s\cap K_t\)，再对其逐条比较内容哈希、版本号、删除标记等字段。

范围通常按稳定的消息序列号、事件偏移量或时间窗口定义；其中序列号优于可变的展示时间。范围必须归属于单一会话，不能把多个会话的消息汇总后比较，否则会出现“会话 A 少一条、会话 B 多一条，整体正好相等”的假象。

更关键的是，源端和目标端必须使用同一快照水位。若迁移期间仍有写入，源端读到 \(W=1200\)，目标端却已包含 \(W=1210\) 的新消息，那么目标的“多余”可能只是正常并发写入；反过来，目标尚未追平时的“缺失”也未必是迁移失败。应固定一个已确认可见的水位 \(W\)，只比较不晚于 \(W\) 的记录；晚于 \(W\) 的数据留给下一轮增量对账。

授权关系、附件对象、表情反应等也应各自形成独立的“标识＋范围＋水位”单元。修复缺失、多余或内容不一致后，必须在新的统一水位重新执行全量比较，而不是只验证被修复的那几条记录。

### 四类差异逐层定位

### 四类差异逐层定位

对账应以“会话 + 时间范围（或消息序号范围）+ 同一快照水位”为比较单元，而不是只比较总条数。源端 `c-a` 的键为 `1..8`，目标端为 `{1,2,3,4,5,6,8,9}`，两边都是 8 条，却同时存在漏迁和多迁。

1. **键集差异：先找对象是否齐全**  
   计算集合差：
   - 源端减目标端：缺失键 `{7}`
   - 目标端减源端：多余键 `{9}`
   
   键集不一致时，优先修复缺失、清理或隔离多余记录；不要被“计数相等”误导。

2. **字段或哈希差异：再查内容是否正确**  
   对共同键 `{1,2,3,4,5,6,8}` 比较正文、发送者、时间戳、回复关系、删除状态等关键字段。大字段或附件可比较规范化后的 `hash`，例如：
   `hash(正文 + 元数据 + 附件清单)`。  
   哈希不同即标记为“不一致”，并输出具体字段差异，避免只能得到“内容不同”的无效结论。

3. **版本或水位差异：确认比较是否处于同一历史点**  
   消息持续写入时，源端和目标端必须冻结在同一迁移批次、水位号或逻辑时间点。若源端已到水位 `W=120`，目标只完成 `W=118`，后两条差异可能只是尚未同步，而非迁移错误。版本不同的记录还应区分“目标旧版本”“目标异常新版本”。

4. **诊断输出：形成可执行修复清单**  
   最终按“缺失、多余、不一致、版本滞后”分类输出，附带会话、键、源/目标版本、字段摘要和建议动作。授权关系、附件对象、表情或引用等应分域对账；修复后必须在新的同一快照水位重新全量复查。

### 消息之外的分域核验

### 消息之外的分域核验

消息表一致不代表迁移完整。授权关系、会话元数据、附件对象和检索索引具有不同的主键与一致性语义，必须分域对账，并固定在同一快照水位或迁移截止位点。

- **授权关系**：以`主体ID + 资源ID + 权限类型`作为复合键，比较授权键集；再核对生效状态、过期时间、继承来源与策略版本。仅比较“授权记录数”会漏掉权限错配，例如同一用户少了`写入`却多了`读取`。
- **会话元数据**：以`会话ID`为主键，核对创建者、参与者集合、标题、标签、归档/删除状态、最近消息引用及版本号。若最近消息由异步任务更新，应同时校验其引用的消息键是否存在且属于该会话。
- **附件对象**：数据库记录与对象存储文件需双向核验。以`附件ID`、对象键和所属消息ID建立引用链；比较大小、媒体类型、内容哈希、上传状态及扫描状态。存在元数据但对象缺失、对象存在但无引用，均应列为异常。
- **索引与派生数据**：以原始消息或附件的引用键为基础，核对索引文档是否多余、缺失或指向旧版本；内容可比较规范化文本哈希，状态应区分“待建索引”“已完成”“失败”。

修复时先补齐源端存在而目标缺失的实体，再处理目标多余项和版本冲突；完成后以新的统一水位重新全量或增量复查。

### 修复、复查与切换准入

### 修复、复查与切换准入

对账发现差异后，不能立即切流，而应按差异类型生成可审计的修复计划。以会话 `c-a` 为例，源端键集为 `{1,2,3,4,5,6,7,8}`，目标端为 `{1,2,3,4,5,6,8,9}`：虽然两端都是 8 条，但应补齐缺失键 `7`，清理或隔离多余键 `9`，并继续核验共同键的内容、附件引用、授权状态及版本。

修复动作通常分为：

- **缺失**：按源端记录补写，并保留原始消息键、创建时间、版本号与幂等标识。
- **多余**：确认其是否为迁移窗口内的新写入；若非合法数据，执行软删除、隔离或按规则清理。
- **不一致**：比较字段或内容哈希；目标版本落后时重放源端更新，目标版本领先或双端均写入时进入冲突队列，由版本规则、时间戳或业务仲裁决定最终值。
- **分域差异**：消息正文通过不代表附件、成员授权、表情、已读水位等域也通过；每个域应独立修复、独立验收。

修复完成后必须在**同一快照水位**重新对账。若迁移期间仍允许写入，应先记录源端水位 $W$，同步至 $W$，再冻结写入或通过增量日志持续追平；不能拿源端较新的结果与目标端较旧的结果比较。复查应同时确认键集无缺失/多余、哈希一致、版本一致，并保存对账报告与修复记录。

只有全部必需域在约定水位通过对账，才满足切换准入条件。切换后仍应保留旧端只读或可回滚窗口；一旦监控发现新增差异、权限异常或附件不可用，应以已验证的水位为边界停止切流并回滚，而不是在不确定状态下继续扩大影响。

> **要点** — 同水位下按会话与范围比较键集、内容和版本；计数相等只能说明数量相同，不能证明历史消息正确。

存储切换不是把写流量改指向新库：双写缺少跨源原子性，一次失败或乱序都可能让历史消息与权限状态分叉。

### 双写为何不能保证一致

### 双写为何不能保证一致

应用层双写通常是：

`先写 A → 再写 B → 任一步失败则重试或告警`

它提高了迁移期间的数据覆盖率，却不等于一致性。关键原因是 A、B 没有共享的提交协议：应用无法让两次独立写入“要么同时生效，要么同时撤销”。

- **部分失败**：A 已写入成功，B 因超时、限流或网络中断失败。此时应用看到的可能只是“请求超时”，却无法判断 B 是未写入、已写入但未返回，还是仅写入了一部分关联记录。
- **重试重复**：为补偿失败而重试时，若没有稳定的消息唯一标识与幂等约束，同一条消息可能在 B 中出现多次；即使消息表幂等，附件、索引、未读计数、会话摘要等派生状态也可能重复累加。
- **写入乱序**：并发请求、异步队列和不同重试时延会改变到达顺序。原本 `编辑消息` 在 `发送消息` 之后发生，B 却可能先收到编辑；`撤回`、权限变更、删除会话尤其容易被旧事件覆盖。
- **跨库事务缺失**：单库事务只能保证本库内消息、索引和状态的一致，不能覆盖另一套数据库。分布式事务即使可用，也会带来可用性、锁等待和故障恢复复杂度，通常不应把它当作迁移默认方案。

因此，双写只能被视为**可观测的复制过程**。每条写入应携带全局事件标识、会话内单调序号、版本号和幂等键；失败进入可重放的补偿日志，并按同一顺序消费。更重要的是持续对账：不仅比较消息数量，还要核对内容版本、删除标记、权限状态及派生状态。只有确认差异可解释、可修复，双写才具备切换价值。

### 单权威写入与影子校验

### 单权威写入与影子校验

迁移期首先要回答：**哪一个存储对某条消息拥有最终写入权？**答案必须唯一。若应用同时向 A、B 直接双写，看似提高了切换速度，实际上没有跨源原子提交：A 成功而 B 超时、B 先收到编辑而 A 后收到原消息、某次重试只落到一侧，都会形成不可由“改回路由”自动修复的分叉。

因此，在一个迁移阶段内固定权威库，例如：

- 旧库 A 是唯一写入口；应用只确认 A 的写入结果。
- 变更日志、订阅流或可靠任务将 A 的已提交数据异步复制到新库 B。
- 复制事件必须携带稳定事件标识、对象版本或单调序号；B 按版本幂等写入，拒绝旧版本覆盖新版本。
- 复制延迟、失败队列、重放次数与积压量都是切换门槛，而非仅供监控的指标。

B 在此时是“影子副本”，不能承担正式写入，但应尽早承担**影子读**。对同一请求，可在不影响用户响应的前提下，从 A 返回正式结果，并异步从 B 查询后比较。比较不能只看“是否查到记录”，还应覆盖消息正文、删除/撤回状态、编辑版本、会话排序、分页边界、权限过滤及聚合计数。对允许最终一致的数据，应按复制水位或容忍时间窗比较，避免把尚未同步误判为数据错误。

可将差异分为三类：复制尚未追平、查询语义不兼容、真实数据分叉。前两者分别通过等待水位和适配查询解决；真实分叉则必须从 A 的权威日志重放或执行受控修复，不能直接把 B 的结果写回 A。只有当 B 持续追平、影子差异归零或处于明确阈值内，才具备转移写权威的资格。

### 切换边界与回滚窗口

### 切换边界与回滚窗口

切换必须按时间和写入权威划出明确边界，而不是“发现问题就把路由改回去”。建议将过程分为四阶段，并为每阶段预先声明写入规则、可接受异常与回滚动作。

- **预切换阶段**：A仍是唯一权威写库，应用向B复制历史数据，并可进行影子读、校验计数和抽样比对。此时B中的差异只能用于修复复制链路，不能由业务直接写入；否则无法判断差异来自复制延迟还是双端写入。

- **切换阶段**：设置切换水位线，例如最后一个已确认复制的消息偏移量或时间戳 $W$。先确保B已覆盖A中不晚于 $W$ 的全部数据，再以短暂停写、消息队列栅栏或按会话分片排空方式建立边界。边界之后，B成为唯一权威写库；A不再接受业务写入，只保留可验证的快照或受控增量记录。

- **观察阶段**：在预设窗口内监控写入成功率、读取差异、权限校验、消息顺序、延迟和积压。回滚条件应可执行，例如出现无法重试的写入丢失、权限状态不一致、关键查询错误率超过阈值。若要回退到A，必须先将B在切换边界后的增量按顺序同步回A，并完成对账；不能直接把流量切回A。

- **稳定阶段**：当观察窗口结束、增量核对通过且回滚所需反向同步链路已关闭或归档后，正式宣布B为长期权威。此后A仅是备份、审计副本或待下线资源。

回滚窗口的本质是“仍能安全重建旧权威”的期限。窗口越长，反向同步、双向冲突控制和运维成本越高；若业务不能承受短暂停写，就需承担更复杂的顺序标识、幂等写入与逐分片切换设计。

### 切后继续写为何难以回退

### 切后继续写为何难以回退

设切换时刻为 $t_0$，A、B 已完成历史数据校验，且把写入路由切到 B。此后新增消息、撤回、编辑、已读位置、权限变更都首先落在 B；若 A 不再接收这些变化，则从 $t_0$ 起形成增量缺口：

$$
\Delta_{B\rightarrow A}=\{\text{切换后在 B 成功、但 A 未确认的变更}\}
$$

因此，“把路由改回 A”并不是回退，而是把业务重新指向一个缺少 $\Delta_{B\rightarrow A}$ 的旧视图。用户可能看到刚发送的消息消失、已撤回消息复现，或按旧权限访问本应禁止的会话。

要使 A 可回退，必须在切后持续进行反向同步。但反向同步并非简单复制：B 中一次操作到达 A 时，A 可能已有旧版本、延迟到达的正向双写，或人工修复产生的独立修改。于是必须定义全局顺序、幂等键、版本号与冲突规则；否则同一消息可能出现“编辑覆盖撤回”“旧权限覆盖新权限”等乱序结果。

若 A、B 在切后都允许写入，则问题升级为双主：两个源可同时产生冲突，且没有跨源原子提交来保证消息正文、索引、附件、权限状态一起一致。此时回退依赖双向复制、冲突仲裁和完整对账，复杂度通常高于迁移本身。

更安全的策略是始终指定单一权威写入端：切至 B 后，A 仅作影子副本或只读回退源，并明确回滚窗口。在窗口内维持 B→A 同步；窗口结束后，回退应采用重新迁移或受控停写，而不能仅修改路由。

### 消息迁移的安全切换方案

### 消息迁移的安全切换方案

以即时通信历史消息迁移为例，安全切换的目标不是“把请求路由到新库”，而是证明新库在切换点拥有与旧库一致、可继续追加的消息序列、会话状态与权限关联。

1. **确定旧库为唯一写权威**  
   迁移初期，应用只向旧库写入；新库接受全量复制和增量变更，不承担正式写入。可允许影子读：同一查询同时读取新库并与旧库结果比较，但用户结果仍以旧库为准。这样避免应用双写中“旧库成功、新库失败”或两个源写入顺序不同的问题。

2. **快照导入并持续追平增量**  
   在时刻 $T_0$ 对旧库做一致性快照，导入新库；随后从变更日志、消息事件流或按递增序列号扫描中持续复制 $T_0$ 之后的新增、编辑、撤回、删除及会话成员变更。增量不能只复制“发送消息”，还必须覆盖幂等键、消息状态、已读游标、置顶和权限等影响展示与访问控制的数据。

3. **设置短暂停写或只读窗口**  
   当增量延迟接近零时，进入明确公告的切换窗口：暂时拒绝发送、编辑、撤回等写操作，或将业务降级为只读。等待复制消费者处理完最后一条旧库变更，记录旧库最终水位 $W$；确认新库已应用至 $W$ 后，冻结旧库写入。该窗口的代价是短暂发送失败或排队，应提前设计重试提示与时长上限。

4. **对账后切流，而非直接改路由**  
   对账至少覆盖消息总数、按会话/日期分桶计数、最大序列号、消息摘要校验、撤回状态及成员权限；对不一致分桶做逐条比对和补偿。通过后先将读流量切至新库，观察查询错误、空会话和权限拒绝；再授予新库唯一写权威并切写。

5. **定义可执行的回滚边界**  
   切写前可直接回到旧库；一旦新库已接受正式写入，旧库已落后，不能仅改回路由。此时必须将新库新增写入反向同步到旧库并完成对账，或再次进入暂停写窗口。因此应预先规定回滚窗口、反向同步能力和“超过窗口仅修复、不回切”的决策条件。

> **要点** — 安全迁移依赖单权威写、可验证追平和明确回滚边界；切换后写入B，回退A必须同步数据而非仅改路由。

本节以MongoDB副本集为边界，建立从写入确认、读取可见到迁移回填、切换回滚与水位对账的完整安全切换方法。

### 副本集中的提交、复制与可见性

### 副本集中的提交、复制与可见性

MongoDB 副本集里，“客户端收到成功”“从节点已复制”“读取端能看到消息”是三个不同边界。历史消息迁移、双写和切流必须分别定义，不能把一次 `insert` 成功等同于全链路安全。

- **主节点写入确认**：默认由 Primary 接收写入并返回结果。若使用 `writeConcern: { w: 1 }`，仅表示 Primary 已接受该写入；Primary 随后故障时，尚未来得及复制的消息可能发生回滚。
- **复制与多数派提交**：`writeConcern: { w: "majority" }` 要求该写入已复制到多数投票节点后再确认。它降低主从切换导致已确认消息丢失的风险，但确认延迟通常更高。`wtimeout` 超时表示客户端未能在期限内取得所要求的确认，不应直接把结果视为成功。
- **日志落盘**：`j: true` 要求参与确认的节点将操作提交到 journal。它关注宕机恢复后的持久性；`j` 与 `w` 解决的问题不同，不能只配置其中之一就宣称“绝不丢消息”。
- **读取可见性**：Primary 上已接受的写入，不代表 Secondary 已可读取。`readPreference: primary` 读取主节点，通常避免复制延迟造成的旧视图；`secondary` 或 `secondaryPreferred` 可能读到滞后的历史消息，适合容忍延迟的查询，不适合作为切换完成的唯一判据。

迁移期间可将消息写入采用多数派确认，将关键核验读固定到 Primary，或使用与多数派提交一致的读取策略。若业务从 Secondary 验证回填结果，应显式记录允许的复制延迟窗口，并把“暂未读到”区分为“尚未复制”与“确实缺失”。

Change Streams 用于持续捕获后续变更时，应保存 MongoDB 返回的 `resume token`，以便中断后继续消费；该 token 是 MongoDB 变更流的位置标识，不能用 PostgreSQL WAL LSN、时间戳或自增消息号替代。切换前的最终判断应结合回填边界、已处理 token 与抽样对账，而非仅凭某个从节点“看起来已经追平”。

### 写关注与读偏好的消息一致性

### 写关注与读偏好的消息一致性

消息系统的“已发送”至少包含三个不同层次：主节点已接受写入、写入已进入日志、写入已复制到足够多成员。若应用把它们混为一谈，复制滞后就会表现为消息缺失、撤回延迟或权限旧读。

设消息写入在主节点完成的时间为 $t_0$，某从节点复制到该写入的时间为 $t_1$。当客户端采用从节点读取时，在区间 $[t_0,t_1)$ 内可能看不到刚发送的消息：

- `writeConcern: { w: 1 }`：主节点确认即可返回。主节点故障并在写入复制前发生选举时，该消息可能被回滚；从节点读还会暂时缺失。
- `writeConcern: { w: "majority" }`：多数投票成员确认后才返回，降低已确认消息在故障切换后被回滚的风险，但不意味着每个从节点立刻可读。
- `j: true`：要求确认前写入 journal；它增强节点崩溃后的持久性，不等价于跨节点复制确认。通常应与合适的 `w` 一起评估。

读偏好决定用户看到哪个复制进度。`primary` 读取主节点，可避免“自己刚写却读不到”的典型滞后，但不能替代多数确认；`secondary` 或 `secondaryPreferred` 可能读取落后副本，适合可容忍陈旧的历史浏览，不适合发送后即时回显、撤回结果确认和权限判定。

撤回本质上是对消息状态的后续写入。若撤回写到主节点后，列表却从滞后从节点读取，用户仍会短暂看到原消息；若成员资格或封禁状态从从节点读取，则可能出现“已撤权仍可读”的旧权限窗口。对此应将安全敏感的鉴权、撤回确认和关键会话读固定到主节点，并以 `majority` 写关注承载需要在故障后仍成立的业务承诺。

### 唯一权威写入与故障切换时间线

### 唯一权威写入与故障切换时间线

应用层必须承认：副本集任一时刻只有当前 `primary` 是写入权威。客户端应将写请求发送至副本集连接串，由驱动发现主节点；不要缓存“主库地址”，更不能在网络超时后向旧主或任一 `secondary` 补写。

建议关键消息写入采用 `{ w: "majority", j: true }`：`j: true` 要求写入主节点日志，`w: "majority"` 要求多数投票节点确认，从而降低已确认写在选主后回滚的风险。应用收到超时不等于写入失败，必须以稳定业务幂等键重试，而非生成第二条消息。

| 时间点 | 副本集事件 | 应用动作 | 写入边界 |
|---|---|---|---|
| T0 | 原主节点正常 | 接收写入并等待确认 | 仅原主可写 |
| T1 | 原主失联或网络分区 | 驱动报连接/选主错误 | 暂停确认未知的业务结果 |
| T2 | 多数派完成选举 | 新主产生 | 重新发现主节点后重试幂等写 |
| T3 | 旧主恢复 | 以 `secondary` 身份追赶复制 | 禁止旧主直接承接写流量 |
| T4 | 复制追平、业务核对通过 | 继续正常服务 | 新主仍是唯一权威 |

迁移状态机可简化为：`正常写入 → 选主不确定 → 新主已确认 → 旧主隔离追平 → 对账完成`。其中“选主不确定”期间，允许客户端保留待确认请求，但不得把超时直接解释为失败；“旧主隔离追平”期间，不应根据旧主本地数据发起补偿或覆盖新主数据。

| 失败情形 | 风险 | 处置与回滚 |
|---|---|---|
| 写入超时 | 实际已写入或未写入均可能 | 用业务唯一键查询/重试，禁止盲目插入 |
| 新主尚未选出 | 无写入权威 | 返回可重试错误，暂存请求 |
| 旧主网络孤岛 | 误向旧主写入 | 网络与服务发现均隔离旧主；只接受当前主响应 |
| 选主后发现少数派写 | 已确认语义不满足或数据回滚 | 以多数确认记录为准，重放幂等业务命令 |
| 恢复节点数据滞后 | 读取到旧视图 | 关键读使用主节点或满足业务要求的读关注级别 |

读取可使用 `readPreference` 分流，但“写后立即校验、迁移水位确认、对账裁决”应读取当前主节点或采用明确的一致性策略。变更捕获使用 change streams 时，恢复位置只能使用 MongoDB 返回的 `resume token`；不得将 PostgreSQL WAL 的 LSN 误作 MongoDB 恢复令牌。

### 快照加变更流的迁移状态机

### 快照加变更流的迁移状态机

安全迁移不是“导出一份数据再导入”，而是把某一时刻的**一致快照**与其后的**有序增量**连接起来。MongoDB 中，增量来源应为 change streams；其 `resume token` 仅表示变更流恢复位置，不能用 PostgreSQL WAL LSN、业务自增 ID 或时间戳替代。

可将流程定义为以下状态机：

1. **准备**：确认源端为副本集或分片集群，目标端索引、集合结构、权限和写入策略已就绪；记录迁移批次号。
2. **建立监听**：先打开 change stream，持久化最近一次已成功落库事件对应的 `resume token`。消费者必须具备幂等性，例如按 `_id` 加版本号或事件唯一键去重。
3. **获取快照**：取得可说明边界的一致快照并分批导入目标端。快照期间持续消费变更流，但可先写入增量暂存区，避免回放先于基础记录。
4. **增量回放**：快照导入完成后，按变更事件顺序应用暂存增量及后续实时增量；每批提交成功后再推进已确认 token。
5. **追平验证**：当目标端处理延迟持续低于阈值，冻结或限制源端写入窗口；继续回放至切换边界，并进行计数、抽样哈希、关键实体关联及最近更新时间对账。
6. **切换**：将读写流量切至目标端，保留源端只读观察期；确认无误后才解除迁移保护。
7. **完成或回滚**：完成时归档批次、token 与对账证据；失败时停止目标写入、保留现场，并按既定方向恢复流量。

`resume token` 应与迁移批次、集合范围、处理时间和目标端提交结果一并持久化。恢复时使用最后一个**已确认** token 重新订阅，而不是内存中最近收到的 token；前者至多重复处理，后者可能丢失尚未提交的事件。

若 token 已失效、操作日志窗口不足或增量出现不可解释缺口，不应继续“猜测补齐”。应将状态退回“建立监听/获取快照”，重新形成可信边界，再执行全量加增量流程。

### 同水位对账与错误定位样本

### 同水位对账与错误定位样本

对账的前提不是“两个库当前行数相同”，而是两侧均冻结在**同一迁移水位**。PostgreSQL 可用已确认的提交边界或导出快照描述水位；MongoDB 则应记录迁移程序已处理并持久化的 `resume token`、对应集群时间及批次完成标记。二者都是各自系统内的进度证据，不能把 PostgreSQL WAL 的 LSN 当作 MongoDB 的恢复令牌。

建议按“键集—摘要—计数”三层比较：

1. **键集层**：比较同一水位内的业务主键集合。  
   - 源有、目标无：漏写、过滤条件错误或回填中断。  
   - 源无、目标有：重复导入、删除事件遗漏或水位越界。  
2. **内容摘要层**：按主键规范化字段、排序后计算摘要，例如  
   `$h=\operatorname{SHA256}(\text{主键}\Vert\text{版本}\Vert\text{规范化内容})$`。  
   键相同而摘要不同，通常是字段映射、时区、默认值、更新覆盖顺序或幂等键设计问题。  
3. **计数层**：按时间桶、租户、会话或哈希分桶比较 `count`。计数只能快速缩小范围，不能证明一致。

例如，源端某租户应有键集 `{a,b,c}`，目标为 `{a,b,b}`：总计数同为 3，却同时存在 `c` 漏写和 `b` 重复，属于“仅计数正确”的伪一致。若键集一致但 `b` 的摘要不同，应进一步检查更新事件是否按版本条件写入；不能仅因 MongoDB 中较晚到达就覆盖较新内容。

错误定位宜输出最小证据包：迁移批次号、源侧水位、MongoDB `resume token`、分桶规则、差异主键、两侧规范化摘要及最后修改版本。发现差异后，先暂停推进水位，再按主键重放或补偿；完成局部复核后才允许恢复切换。

> **要点** — 安全切换依赖明确确认语义、单一写入权威、可续传增量与同水位内容对账；MongoDB的resume token不能替代其他数据库水位。
