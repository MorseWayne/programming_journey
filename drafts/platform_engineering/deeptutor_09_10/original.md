## 09.10 协议兼容与RPC：能解析消息不代表业务安全

- 区分HTTP阶段、RPC/事件格式与消息业务版本
- 理解Protobuf编号、optional存在性和未知字段
- 解释gRPC deadline/重试的未知结果边界
- 设计授权/错误码安全映射
- 完成旧新客户端/生产者/消费者兼容矩阵
- 写出扩展迁移收缩和回退证据

先将传输协议、线格式与业务语义拆成独立版本轴，再讨论兼容性：能成功解析消息，绝不等于请求可被安全执行。

### 先画四层版本矩阵

### 先画四层版本矩阵

不要把所有“版本号”理解成同一件事。一个请求即使携带了可识别的 `v2` 字段，也未必属于可执行的业务版本；反之，业务消息升级为 `m-9:v2`，也不必要求 HTTP 路径或事件编码同步升级。应先分离四条轴：

| 版本轴 | 当前已生效契约 | 未来或并行内容 | 它决定什么 |
|---|---|---|---|
| HTTP 服务契约 | `S2/v1`，正文恰为 6 个 UTF-8 字节 | `S3/v2` 的 `stored_in_teaching_db` 仅是提议 | 路径、方法、状态码、响应语义 |
| Protobuf/RPC 字段 | 既有字段可解析、未知字段可忽略 | 新增字段、弃用字段、默认值演进 | 调用方与服务端如何交换结构化数据 |
| 事件线格式 | `event_v1` | `event_v2` | 事件在队列、日志或订阅流中的编码布局 |
| 业务消息版本 | 如 `m-9:v1`、`m-9:v2` | 业务规则与编辑能力演进 | 此消息能否由该身份、该状态安全执行 |

当前 HTTP 事实必须精确保留：`S2/v1` 成功时返回 `200 accepted_in_memory`；同一消息 ID 重复提交返回 `409`；非成员返回 `404`。这些结果描述的是当前服务的可观察行为，不能被“未来会写入教学数据库”的设想改写。

可将一次请求标记为四元组：

`(HTTP=S2/v1, RPC字段=F, 事件=event_v1, 业务=m-9:v2)`

其中每一维都要独立验证兼容性。尤其 `m-9:v2` 表示业务编辑版本，并不自动等价于 `event_v2`，更不意味着 HTTP 已升级到 `S3/v2`。而 `R9` 从 6 字节放宽到 9 字节仍属待审变更，不能提前按新长度接受。09.09 中的 `v3` 异步导出也应通过另一个接口表达，不能借现有提交接口暗中改变语义。

### 当前契约与未来提议隔离

### 当前契约与未来提议隔离

比较协议时，先固定“已经生效”的基线，不能把设计讨论中的字段、状态码或容量变化倒灌进当前实现。

| 维度 | 当前 S2/v1 契约 | 未来 S3/v2 提议 | R9 容量提议 |
|---|---|---|---|
| 正文限制 | 最多 `6` 个 UTF-8 字节 | 未改变已生效契约 | 拟由 `6` 扩至 `9` 字节 |
| 成功结果 | `200 accepted_in_memory` | 拟为 `stored_in_teaching_db` | 待审，不能实现为现状 |
| 重复消息 ID | `409` | 未定 | 无关 |
| 非成员发送 | `404` | 未定 | 无关 |
| 协议地位 | 已发布、可依赖 | 仅提议 | 仅待审 |

这里的“6 个 UTF-8 字节”不是“6 个字符”。例如 ASCII 字符通常占 1 字节，中文常占 3 字节；因此 `"abcdef"` 可通过，而 `"你好a"` 通常为 7 字节，应被当前 S2/v1 拒绝。验证应针对编码后的字节长度，而非界面显示长度：

`len(body.encode("utf-8")) <= 6`

`200 accepted_in_memory` 的含义也必须收窄：服务端已接收并放入内存中的处理路径，不承诺已经持久化到教学数据库。若客户端看到成功就展示“已永久保存”，便把未来 S3/v2 的语义错误投射到了 S2/v1。

同样，`409` 与 `404` 是可观察的业务边界：相同 ID 的重放不是幂等成功，而是冲突；调用者不是成员则不存在可发送的业务资源。解析出合法 Protobuf 消息、满足 `event_v1` 线格式，都不足以绕过这些检查。

因此实现与测试应明确标注版本：S2/v1 断言 `6` 字节和内存接收；S3/v2、`stored_in_teaching_db`、R9 的 `9` 字节只作为候选用例或特性开关，未批准前不得改变默认行为。

### Protobuf字段兼容不等于语义兼容

### Protobuf字段兼容不等于语义兼容

Protobuf 的兼容性首先是**线格式可解析性**，不是“新旧客户端可以安全互操作”的承诺。字段编号一旦发布，就应永久绑定其原始含义：删除字段后应使用 `reserved` 保留编号和名称，绝不能把旧的 `field 6` 改作另一种业务含义。旧客户端可能仍发送该编号；新服务若将其解释为新命令，便会发生静默的语义错配。

`optional` 还引入“值”与“是否出现”的区别。以 `optional uint32 retry_count = 4` 为例：

- 未出现：调用方未表达该意图；
- 出现且为 `0`：调用方明确要求 `retry_count=0`；
- 旧实现若只能读取数值而不能区分存在性，可能把两者混为一谈。

未知字段同样不能被想当然地依赖。中继、日志重放、JSON 转换、旧 SDK 的“解析后再序列化”等路径，可能保留未知字段，也可能将其丢弃。因此，不能把未知字段当作可靠的端到端扩展通道；需要新语义时，应明确规定接收方版本、降级行为与丢失后的安全后果。

这里至少有两条独立验证轴：

| 轴 | 需要验证的问题 |
|---|---|
| `event_v1` / `event_v2` 线格式 | 字段号、类型、存在性、未知字段经转发后是否仍符合预期 |
| `m-9:v1` / `m-9:v2` 编辑语义 | 同一编辑是否仍满足成员资格、幂等性、冲突处理和权限规则 |

例如，`event_v2` 即使能被 `event_v1` 消费者解析，也不表示 `m-9:v2` 的编辑可以交给只理解 `m-9:v1` 语义的处理器执行。前者回答“字节能否读出”，后者回答“读出后能否安全地改变业务状态”；两项都通过，才构成真正的兼容。

### 以混部矩阵暴露安全缺口

### 以混部矩阵暴露安全缺口

混部时至少存在两条独立版本轴：一条是传输与线格式，如 HTTP S2/v1、未来可能的 S3/v2、事件 `event_v1/v2`；另一条是业务编辑语义，如 `m-9:v1/v2`。前者决定“能否读懂字节”，后者决定“能否安全执行”。

| 发送方 / 接收方 | 旧 RPC 服务 | 新 RPC 服务 | 旧事件消费者 | 新事件消费者 |
|---|---|---|---|---|
| 旧客户端：S2/v1，正文 6 UTF-8 字节 | 可解析、可接受、可执行；成功返回 `200 accepted_in_memory` | 应保持同样语义，不能因服务升级暗改持久化承诺 | 若产生 `event_v1`，可消费 | 可消费 `event_v1`，以默认值补齐新增字段 |
| 新客户端：S3/v2（仅提议） | 必须拒绝或显式降级；不得把未知格式猜成 S2 | 仅在 S3/v2 正式批准后可接受 | 不应直接投喂旧消费者 | 仅在 `event_v2` 有版本路由和迁移策略后消费 |
| 新业务编辑：`m-9:v2` | 即使消息可解析，也必须拒绝未知业务语义 | 需逐项校验成员资格、幂等性与状态迁移 | 旧消费者不可按 v1 猜测执行 | 可按 v2 规则执行，并保留回放兼容路径 |

当前 S2/v1 的边界应写死：正文恰为 6 个 UTF-8 字节；同一 ID 重复提交返回 `409`；非成员返回 `404`。这些结果不是“协议解析失败”，而是业务授权与幂等性判定，不能被新版本统一改写为成功。

`stored_in_teaching_db` 只是 S3/v2 的未来提议，不能提前作为现网成功语义；R9 从 6 字节扩至 9 字节仍待审，也不能让服务端宽松接受。09.09 的 v3 异步导出应使用另一个接口，而非复用写入 RPC。矩阵中凡是“可解析但语义未知、权限未知、回退不可证明”的格子，默认必须拒绝。

### 超时重试与授权错误映射

### 超时重试与授权错误映射

`deadline exceeded` 表示客户端在期限内未得到响应，不表示服务端未执行：请求可能尚未到达、正在执行，或已写入成功但响应丢失。因此，客户端不得把超时直接当作失败后生成新消息重发。

对创建类 RPC，应以稳定的幂等键或业务消息 ID（如 `m-9:v1`）建立可查询证据：

- 首次提交：服务端原子记录“已接受”与对应 ID，当前 HTTP S2/v1 的成功响应为 `200 accepted_in_memory`。
- 同一 ID、相同有效载荷重试：返回既有接受结果，或允许客户端查询该 ID 的状态；不得再次产生副作用。
- 同一 ID、不同有效载荷：返回 `409`，提示调用方存在 ID 复用或并发写入错误。
- 超时后：先按原 ID 查询，再以同一幂等键有限退避重试；不能改换新 ID 来“碰碰运气”。

这里的“已接受”仅表示当前内存路径已接收，不应被解释为未来 S3/v2 所提议的 `stored_in_teaching_db`。持久化确认、投递确认与 09.09/v3 的异步导出任务状态属于不同接口和不同证据链；导出轮询不能承担消息写入结果查询。

错误映射还必须先经过授权判定。调用者未授权时返回认证或权限错误；已认证但不是目标成员时，当前约定返回 `404`，避免借由 `403` 确认成员关系或资源存在。对不存在的资源同样返回 `404`，并保持响应体、时序和重试建议尽量一致。客户端只应对超时、暂时不可用等可恢复错误重试；对 `404`、`409` 和授权错误停止重试并进入人工或业务补偿流程。

> **要点** — 兼容设计必须逐轴建模并用矩阵验证：解析成功只是起点，授权、持久化、幂等与回退证据才决定业务安全。

消息能被解析只说明线格式尚可兼容；要安全升级，还必须验证字段语义、权限判断、索引链路与回退路径。

### 三层兼容边界：传输、格式与业务

### 三层兼容边界：传输、格式与业务

兼容性不能只问“请求成功了吗”。一次消息升级至少跨越三层边界，它们彼此独立：

1. **传输层兼容**：HTTP 路由、状态码、鉴权头、超时与重试策略仍可工作。例如客户端能访问 `/messages` 并收到 `200`，只说明网关和接口阶段可达；并不说明客户端理解响应中的新语义。

2. **线格式兼容**：RPC 或事件载荷能否被编码、传输和解析。`MessageEventV1` 使用：
   - `message_id = 1`
   - `conversation_id = 2`
   - `seq = 3`

   V2 可以新增 `optional message_version = 4`、`visibility = 5`。旧二进制 Protobuf 解析器通常会跳过未知字段，因此“V1 能解析 V2 二进制消息”属于线格式安全。字段编号却绝不能重用：已删除字段的编号仍应保留为 `reserved`，否则历史数据中的字段可能被新字段误解释。

3. **业务层兼容**：服务是否按正确版本、正确可见性和正确权限处理消息。即使旧消费者忽略了 `visibility`，它也可能把本应仅管理员可见的消息写入 `SearchIndex`；即使 RPC 调用成功，旧的排序、去重、审计和回退逻辑也未必理解 `message_version=2`。

尤其要区分“缺失”和“默认值”。proto3 普通标量中，未提供的 `visibility` 与提供 `visibility=0` 往往都表现为 `0`；`optional` 字段则具有 presence，可判断发送方是否明确给值。迁移时应定义：缺失字段代表旧版本默认策略，还是拒绝处理，而非把两者混为一谈。

还要警惕兼容链路断点：二进制未知字段可保留，不代表 ProtoJSON 转换、JSON 解析、逐字段复制或索引写入仍会保留它们。结论应分别验证：**HTTP 可达、消息可解析、业务语义安全**；三项都成立，才算完成兼容升级。

### 从V1到V2：字段编号是长期契约

### 从V1到V2：字段编号是长期契约

设 V1 已经发布：

`message_id = 1`、`conversation_id = 2`、`seq = 3`。

这些编号不是源码中的临时位置，而是二进制线上消息的永久标签。编码时，字段键由“字段编号 + wire type”构成；因此接收端靠编号识别含义，而不是靠字段名识别。V2 的安全扩展应当只追加未使用编号：

```proto
message MessageEventV2 {
  string message_id = 1;
  string conversation_id = 2;
  int64 seq = 3;

  optional int32 message_version = 4;
  Visibility visibility = 5;
}
```

这样，V1 接收 V2 二进制消息时，能读取 `1~3`，并跳过不认识的 `4、5`；V2 接收 V1 时，则按缺失字段处理新增语义。这是 wire-safe 的基础，但它依赖一个不可破坏的前提：**旧编号的业务含义和 wire type 不得改变**。

尤其不能把 `seq = 3` 改作 `visibility = 3`，也不能删除旧字段后“回收利用”其编号。旧客户端、本地缓存、消息队列中的历史数据仍可能携带编号 `3`；一旦重用，接收方会把旧语义误解释为新语义，且通常不会产生明显的解析错误。

删除字段时应显式保留编号及名称：

```proto
message MessageEventV2 {
  reserved 3;
  reserved "seq";
  // ...
}
```

实际演进中，若 `seq` 仍承担排序或去重职责，通常应继续保留它；只有确认不再使用时才删除并 `reserved`。`reserved` 的作用不是兼容旧消息，而是阻止未来开发者误将历史编号重新分配。

`message_version = 4` 使用 `optional` 还有额外含义：proto3 普通标量的“未提供”与“提供了默认值 `0`”难以区分；`optional` 则保留 presence。于是 V2 可以区分“这是 V1 发送、根本没有版本字段”与“V2 明确声明版本为 0”，并据此定义迁移、回退与校验规则。

### 默认值与存在性：0不等于未提供

### 默认值与存在性：0不等于未提供

在 proto3 中，普通标量字段具有隐式默认值：未编码的 `int64 seq = 3` 读取后是 `0`，`string` 是空串，`bool` 是 `false`。因此，接收方通常无法区分以下两种输入：

- 发送方明确写入：`seq = 0`
- 发送方根本没有提供 `seq`

这对版本、权限和迁移判断尤其危险。例如把 `visibility = 0` 约定为“仅自己可见”，旧客户端未携带该字段时也会读到 `0`；若服务端据此放行或隐藏消息，就把“未知能力的旧请求”误判成了明确授权。

V2 中应对需要判断“是否提供”的标量使用 `optional`：

`optional int32 message_version = 4;`  
`optional int32 visibility = 5;`

接收方应基于存在性而非默认值分支：

- `has_message_version()` 为假：按 V1 兼容路径处理，不能假定其理解 V2 语义。
- 字段存在且值为 `2`：允许进入 V2 校验、权限与索引流程。
- `visibility` 不存在：执行明确的迁移默认策略，例如拒绝写入、补齐后再校验，或按服务端可信上下文推导。
- 字段存在但值为 `0`：这是一个真实输入，必须按枚举约定验证，而非当作缺失。

存在性解决的是“有没有表达意图”，不自动保证“意图合法”。仍应校验版本范围、可见性取值、调用者权限及旧索引链路是否理解 V2。尤其在 ProtoJSON、网关转换或逐字段复制后，要确认 `optional` 的存在性没有被抹平；否则“未提供”仍可能悄悄退化为 `0`。

### 未知字段可跳过，不等于业务可用

### 未知字段可跳过，不等于业务可用

设 `MessageEventV1` 已定义：

- `message_id = 1`
- `conversation_id = 2`
- `seq = 3`

`MessageEventV2` 新增：

- `optional message_version = 4`
- `visibility = 5`

二进制 Protobuf 的兼容性主要是**线格式兼容**：旧端读取 V2 二进制消息时，不认识字段 `4`、`5`，通常可按标签和长度跳过，仍正确得到 `message_id`、`conversation_id`、`seq`。因此，新增字段编号不得重用；即使字段删除，其编号也应声明为 `reserved`，否则旧数据中的未知字段可能被新定义误解释。

但“能跳过”不等于“业务正确”：

| 路径 | 新增字段/未知字段的典型结果 | 风险 |
|---|---|---|
| 二进制 Protobuf 解析后再序列化 | 许多运行时可保留未知字段 | 旧业务仍不知道 `visibility` 的访问语义 |
| ProtoJSON 转换 | 未知字段常不在 JSON 表示中，行为依赖实现与选项 | 往返转换可能丢失 V2 信息 |
| 普通 JSON 解析到旧结构体 | 未声明字段常被忽略，或被配置为报错 | `visibility` 被静默丢弃尤其危险 |
| 手工逐字段复制 | 只复制已知字段 | unknown fields 必然丢失，且容易漏复制新字段 |

`proto3` 普通标量字段还有另一层陷阱：未提供的 `visibility` 与显式传入 `0` 在旧式 API 中都可能表现为默认值 `0`。`optional message_version = 4` 则具有 presence：可区分“发送者未提供版本”与“明确提供值”，适合承载升级分支或兼容策略。

更关键的是，旧 `SearchIndex` 即使能解析并保存 V2 消息，也未必理解 `visibility`。它可能仍把私有消息建立为全局索引，查询结果也可能绕过新权限判断。安全升级必须逐链路确认：写入、复制、ProtoJSON 网关、索引、检索、缓存和回退路径，是否保留字段并执行 V2 的可见性语义。

### 兼容矩阵与安全回退证据

### 兼容矩阵与安全回退证据

升级准入不能只问“V1 能否解析 V2 二进制”。应针对生产者、消费者、客户端与 `SearchIndex` 建立矩阵，并为每一项保留测试或线上证据。

| 角色/路径 | 发送与解析 | 保留与转换 | 授权与索引 | 回退准入 |
|---|---|---|---|---|
| V1 生产者 | 仅发送字段 `1~3` | 不影响 V2 消费者 | 按既有会话权限写入 | 可继续运行 |
| V2 生产者 | 可发送 `message_version=4`、`visibility=5` | 字段号不得重用；删除字段必须 `reserved` | 必须在写入前校验 `visibility` | 降级时不得把受限消息伪装为公开消息 |
| V1 消费者 | 二进制可忽略未知字段 | 中转、逐字段复制、ProtoJSON 转换可能丢失未知字段 | 不得因不认识 `visibility` 而默认放行 | 无法理解新权限语义时，应拒绝、隐藏或走安全默认值 |
| V2 消费者 | 识别 `optional` 字段是否出现 | 区分“未提供”与显式 `0`；普通 proto3 标量无法区分 | 缺失 `visibility` 时采用明确定义的兼容策略 | 读取旧消息应得到可审计的默认可见性 |
| SearchIndex | 验证实际解析器与部署版本 | 确认消息队列、缓存、重建任务不丢字段 | 索引、召回、摘要、权限过滤均识别 V2 | 不支持 V2 时禁止索引受限内容，或延迟发布 |

重点验证三类反例：

1. **线格式兼容不等于业务兼容**：旧消费者忽略字段 `5` 后，是否把本应仅成员可见的消息展示给所有会话参与者。
2. **转换链路不等于字段保留**：消息经 ProtoJSON、网关映射或“读出再写入”后，未知字段是否消失；一旦消失，后续 V2 服务可能误判为“未设置”。
3. **回退不等于关闭新字段**：V2 发布后写入的数据已带有新语义，回滚到 V1 前必须证明旧服务不会错误授权、错误建索引或覆盖该语义。

准入证据至少包括：跨版本二进制与 JSON 用例、`optional` presence 用例、未知字段透传测试、权限拒绝测试、索引可见性测试，以及“V2 写入→V1 读取/转发→V2 读取”的端到端回归。若任一链路无法解释新字段，应选择拒绝、隔离或停止索引，而非静默按默认公开处理。

> **要点** — Protobuf新增字段的线格式兼容只是起点；字段存在性、未知字段保留、权限语义和下游消费能力共同决定业务是否安全。

一次 Send RPC 超时，并不等于消息未发送；必须把传输结果、服务端执行结果与业务合同分层判断。

### 从网关到服务端：一次发送的多层结果

### 从网关到服务端：一次发送的多层结果

一次 `Send` 请求通常经过四层：客户端 → HTTP Gateway → gRPC 服务端 → 存储层。每层的“成功”都只说明本层状态，不能直接推出“消息已安全发送”。

- **客户端成功**：收到 HTTP `200` 或 gRPC `OK`，表示客户端获得了一个正常响应；它通常意味着服务端已按协议答复，但仍应以响应中的业务字段、消息标识和合同定义判断结果。
- **网关成功**：Gateway 已接收 HTTP 请求、完成鉴权和转码，并成功向后端发起 gRPC 调用。它不等于后端已写入存储，更不等于对方已收到消息。
- **gRPC 服务端成功**：处理器返回 `OK`，表示该次 RPC 的服务端执行路径正常结束。若响应在回传途中丢失，客户端仍可能看到 `DEADLINE_EXCEEDED`，而消息其实已经写入。
- **存储层成功**：数据库事务提交、消息进入队列或持久化日志落盘，才接近“已接受发送”的业务事实；但“已投递”“已展示”“已阅读”仍是后续状态。

因此，`DEADLINE_EXCEEDED` 的含义是：**客户端未能于期限内确认结果**，不是“服务端未执行”。客户端取消也只是通知链路停止等待；服务端可能尚未开始、正在执行，或已完成，取消不是远程回滚。

还要避免混淆两个“提交”：

- gRPC 在请求头已被服务端接收后，可能将该调用视为已提交，重试策略未必允许自动重放；
- SQL `COMMIT` 则表示数据库事务持久化完成。

前者是传输语义，后者是存储语义，二者没有必然等价关系。面对未知结果，客户端应使用稳定的 `client_msg_id` 发起查询或按合同恢复，而不是盲目再次发送。

### 超时与取消：未知结果不是失败结果

### 超时与取消：未知结果不是失败结果

设客户端调用 `Send(client_msg_id, body)`，经 HTTP gateway 转发至 gRPC 服务端。一个典型时序是：

1. 客户端发出请求，gateway 已收到并转发。
2. 服务端完成鉴权、落库、投递等业务操作。
3. 响应尚未返回客户端时，客户端 deadline 到期，得到 `DEADLINE_EXCEEDED`。
4. 客户端主动取消，或 gateway 向下游传播取消信号。
5. 服务端可能已完成，也可能仍在执行；取消只能请求其停止，不能撤销已发生的写入。

因此，`DEADLINE_EXCEEDED` 表示“客户端在期限内未取得成功响应”，而非“服务端必然未执行”。客户端取消同样是协作协议：服务端若尚未开始或正处于可中断阶段，可以停止；若消息已持久化、已进入队列或已触发下游副作用，则不存在自动的远程回滚。

尤其不要把“响应头已收到后 RPC 已提交”误解为 SQL `COMMIT`。前者描述的是 gRPC 传输层对本次调用结果的判断；后者描述的是数据库事务持久化。两者的时点、范围和恢复方式都不同。

面对未知结果，正确恢复路径应由业务合同规定：使用稳定的 `client_msg_id` 查询发送状态，或以同一标识重试并由服务端判重。当前 S2 中，即使正文完全相同，重复使用同一 `client_msg_id` 仍按既有合同返回 `409`，不能仅因实现了去重就改成幂等 `200`；若 S3 要引入新语义，必须作为独立协议变更重新评审。

### 重试边界：传输提交不等于数据库提交

### 重试边界：传输提交不等于数据库提交

一次 `Send` 调用至少要区分三层状态，不能用“超时”或“已提交”一概而论：

| 状态 | 含义 | 能否推出业务已成功 |
|---|---|---|
| gRPC `committed` | 客户端已收到响应头；gRPC 认为该次调用不再适合透明重试 | 不能 |
| 服务端已接收请求 | HTTP gateway 或 gRPC 服务端已拿到完整请求，可能已进入队列、校验或执行 | 不能 |
| 业务已落库 | 消息及其必要状态已按业务事务持久化 | 仍需以业务合同确认 |

`committed` 是**传输语义**：响应头已经回来，客户端不能再假设“服务端完全未见过此请求”。它不是 SQL `COMMIT`，更不表示消息已经写入数据库、已投递或可见。反过来，客户端收到 `DEADLINE_EXCEEDED` 时，服务端也可能已经完成落库，只是响应在 deadline 后才返回。

取消同样是协作信号：客户端取消或 deadline 到期后，服务端可以停止尚未开始的工作，但不构成远程回滚。已经执行的写入、已发布的任务或已提交的事务不会自动撤销。

因此，重试策略必须假设请求可能被**重放**：网关重试、gRPC retry policy、调用方手工重试都可能令服务端再次收到同一意图。恢复应使用稳定的 `client_msg_id` 查询或发送，并按合同解释结果。当前 S2 中，同一 ID 即使正文相同仍返回 `409`；不能为了“重试方便”擅自改成幂等 `200`。若 S3 要支持“同 ID 同正文视为成功”，那是新的业务语义，必须单独评审。

### 用稳定标识恢复：幂等合同不能被响应码掩盖

### 用稳定标识恢复：幂等合同不能被响应码掩盖

`DEADLINE_EXCEEDED` 后，客户端不知道服务端是“尚未执行”、正在执行，还是已经持久化成功但响应丢失。因此恢复路径不能依赖再次盲发，而应围绕调用前生成并持久保存的稳定标识 `client_msg_id`。

一次发送可按如下流程恢复：

1. 客户端生成全局唯一且长期稳定的 `client_msg_id`，连同消息正文提交。
2. RPC 超时、连接断开或收到不确定错误时，不立即假设失败。
3. 客户端调用查询接口，例如 `GET /messages/by-client-msg-id/{id}`，查询该标识的服务端状态。
4. 若已存在记录，则以查询结果为准；若确认不存在，才按合同决定是否重新提交同一标识。

关键在于：稳定标识只提供“关联”和“恢复依据”，不自动改变既有业务语义。当前 S2 合同若规定“重复提交同一 `client_msg_id` 返回 `409`”，那么即使正文完全相同，第二次 `Send` 仍应返回 `409`。不能为了让重试代码方便，就把它伪装成 `200` 或“幂等成功”。

`409` 表达的是：该标识已被占用，当前请求不再是一次可安全接受的新建操作；客户端应转入查询与对账，而不是把响应码自行解释为成功。特别是占用记录可能对应不同正文、不同接收方，或处于异步处理中，服务端不能仅凭“看起来重复”就回放成功结果。

未来 S3 若要支持“同一标识、同一请求返回原结果”的真正幂等语义，需要单独定义请求指纹、状态保存期限、处理中响应、结果回放与冲突规则。那是新的业务合同，不能通过把 S2 的 `409` 改成 `200` 偷偷完成。

### 版本演进与回退：S2 规则不能预支 S3 语义

### 版本演进与回退：S2 规则不能预支 S3 语义

设想混部期间同时存在旧客户端 S2、新客户端 S3、HTTP gateway 与多版本服务端：

- S2 客户端调用 `Send`，因 `DEADLINE_EXCEEDED` 或 gateway 重试而再次提交相同 `client_msg_id`。
- S2 服务端合同规定：只要该标识已被接收，重复请求一律返回 `409`；即使正文、收件人完全相同，也不承诺返回成功，更不提供“查询原结果”的隐含能力。
- S3 希望改善体验，拟把“相同 `client_msg_id` 且请求摘要一致”的重复发送改为返回历史成功结果，或允许通过 `Query(client_msg_id)` 恢复最终状态。

这不是给 S2 的 `409` 打补丁，而是新的业务语义。S3 必须独立评审：请求摘要覆盖哪些字段、不同摘要为何仍拒绝、历史结果保存多久、跨地域复制未完成时如何回答、权限变化后是否还能查询，以及 gateway 或 gRPC 重放是否会触发该路径。

混部时，S3 客户端不能因自身支持恢复协议，就假定任意服务端都实现该协议。应通过显式版本协商、能力标志或独立接口启用；未协商成功时，仍按 S2 处理：收到 `409` 后以稳定的 `client_msg_id` 查询既有合同允许的证据，或提示用户确认，而不是把 `409` 解释成幂等 `200`。

回退同样需要证据：记录客户端版本、协商结果、请求摘要、`client_msg_id`、gateway 转发次数、服务端接收时间与最终状态。这样当 S3 灰度撤回时，已发生的发送可审计、可查询；但回退后的新请求仍严格遵守 S2 合同，避免用未来语义重写过去的失败含义。

> **要点** — 超时后的正确动作是按稳定标识查询并恢复；重试、取消和传输提交都不能替代明确的业务幂等合同。

网关的状态码映射不仅是协议转换，更决定调用方能看到什么、能重试什么，以及哪些资源信息必须被隐藏。

### 分层识别：传输状态不等于业务合同

### 分层识别：传输状态不等于业务合同

一次调用的“失败”至少有四层含义，不能只看某个状态码：

- **HTTP 响应**描述网关对外的请求结果，如 `400`、`401`、`404`、`409`、`503`。
- **gRPC 状态**描述一次 RPC 的传输与服务端执行状态，如 `INVALID_ARGUMENT`、`UNAUTHENTICATED`、`PERMISSION_DENIED`、`UNAVAILABLE`。
- **事件处理结果**描述异步消费者是否已接收、是否可重试、是否进入死信队列；它不等价于同步接口已经成功。
- **业务错误码**描述领域规则，例如 `ORDER_ALREADY_PAID`、`SEAT_NOT_AVAILABLE`、`MEMBERSHIP_REQUIRED`，供客户端决定展示、修正输入或终止流程。

gRPC 状态不会自动继承为 HTTP 语义。网关必须维护显式合同，例如：

| gRPC/业务条件 | 对外 HTTP | 对外含义 |
|---|---:|---|
| `INVALID_ARGUMENT` | `400` | 参数或格式无效 |
| `UNAUTHENTICATED` | `401` | 缺少或失效身份凭证 |
| `ALREADY_EXISTS` | `409` | 与当前资源状态冲突 |
| 非成员导致的 `PERMISSION_DENIED` | `404` | 按隐藏策略避免泄露资源存在性 |

同一个 `PERMISSION_DENIED` 不能机械映射为 `403`：若调用者已知资源且仅缺少操作权限，可返回 `403`；若“是否存在该资源”本身敏感，则应统一返回 `404`。

对于 `RESOURCE_EXHAUSTED`、`UNAVAILABLE`、`DEADLINE_EXCEEDED`，合同还必须说明依赖位置、是否可重试及幂等要求。尤其 `DEADLINE_EXCEEDED` 只表示调用方未在期限内获得结果，**不表示服务端未提交**；客户端应通过幂等键、查询接口或操作状态确认，而不是直接当作失败重放。

### 基础映射与授权隐藏策略

### 基础映射与授权隐藏策略

网关不能机械地把 gRPC 状态码“翻译”为 HTTP；映射应从**调用方可修复性**与**资源可见性**推导。

- `INVALID_ARGUMENT → 400 Bad Request`：请求虽已到达服务端，但字段格式、范围、组合约束或业务前置条件不成立。调用方应修改请求后再发起新请求。例如分页大小为负数、时间区间倒置、枚举值非法。不要把服务端内部校验异常一律伪装成 `400`，否则会掩盖缺陷。
- `UNAUTHENTICATED → 401 Unauthorized`：调用方没有有效身份凭据，包括未携带令牌、令牌过期、签名无效或认证上下文无法建立。`401` 表示“先认证”，而不是“你没有该资源的权限”；可配合 `WWW-Authenticate` 提示认证方式。
- `ALREADY_EXISTS → 409 Conflict`：请求与当前资源状态冲突，典型如创建时唯一键重复、幂等键已绑定到不兼容的请求，或同名资源已存在。客户端通常应读取现状、改名，或以相同幂等键查询既有结果，而非盲目重试。

授权失败需要额外处理。内部服务可精确返回 `PERMISSION_DENIED`，因为可信调用方可能需要区分“资源存在但无权访问”和“资源不存在”。但对外网关若采用资源隐藏政策，则对**已认证但非成员**的访问返回 `404 Not Found`：

`外部可见状态 = 404`，而非 `403` 或原样透传 `PERMISSION_DENIED`。

其边界是：仅当暴露“该资源存在、该租户存在或该项目可被访问”本身构成信息泄露时才隐藏；请求格式错误仍应优先返回 `400`，身份缺失或无效仍应返回 `401`。同时，审计日志必须保留内部真实原因，如“已认证、资源存在、成员关系缺失”，避免外部隐藏策略削弱运维与安全追踪。

### 依赖故障：耗尽、不可用与超时

### 依赖故障：耗尽、不可用与超时

`RESOURCE_EXHAUSTED`、`UNAVAILABLE`、`DEADLINE_EXCEEDED`都可能表现为“请求失败”，但它们回答的是不同问题，不能统一映射为同一种 HTTP 错误，更不能据此推断业务操作没有发生。

- `RESOURCE_EXHAUSTED`：某项可用配额被耗尽，例如限流额度、消息大小、数据库连接池、下游并发槽位。若是调用方可见的配额，应返回 HTTP `429`，并可给出 `Retry-After` 或重试窗口；若是服务内部容量不足，则更接近 `503`。响应中不得暴露具体连接池大小、租户配额或内部节点信息。
- `UNAVAILABLE`：依赖暂时不可达、实例摘除、服务发现失败或正在维护。通常映射为 HTTP `503`，表示调用方可以在退避后重试。只有当操作具备幂等语义，或请求携带幂等键且服务端能去重时，才应鼓励自动重试。
- `DEADLINE_EXCEEDED`：截止时间已到，但网关不知道请求究竟停在排队、执行前、执行中，还是已提交后等待响应。因此通常映射为 HTTP `504`，其语义是“调用方未在期限内得到结果”，不是“操作未执行”。

尤其要区分请求阶段。若在鉴权、参数校验或提交事务前超时，可较有把握地报告未完成；一旦请求已发送给可写依赖、已进入事务提交或消息已投递，超时仅意味着结果未知。例如“创建订单”超时后立即重试，可能得到重复订单；正确合同应要求客户端使用幂等键，并提供按请求标识查询最终结果的能力。

安全负例是把所有超时改写为“未创建”或 HTTP `404`：这既会诱发重复写入，也会把暂时性依赖问题伪装成资源不存在。状态码应表达观测到的协议事实，业务最终状态应由可查询、可去重的应用合同确认。

### 安全负例：错误映射如何泄露资源

### 安全负例：错误映射如何泄露资源

以“向群组 `g123` 发消息”为例，后端可能返回 `PERMISSION_DENIED`：调用者已登录，但不是该群成员。若网关机械映射为 HTTP `403`，攻击者即可批量枚举群组 ID：

- `404`：群组可能不存在；
- `403`：群组存在，但自己无权访问；
- `200`：自己是成员。

这会把“资源是否存在”变成可探测信息。对于遵循隐藏策略的 IM 产品，非成员访问内部 `PERMISSION_DENIED` 应对外统一为 `404`，同时在审计日志中保留真实原因、用户、群组和请求标识。客户端只应看到“群组不存在或不可访问”，而不是“你不是成员”。

成员操作同样如此。`DELETE /groups/g123/members/u456` 若操作者不是管理员，直接返回 `403` 会确认群组及目标成员关系；若产品要求隐藏成员名单，也应按策略返回 `404`。但“群组存在、操作者是成员、仅缺少管理员权限”可返回 `403`，前提是该存在性本就允许被该调用者知晓。

消息发送的另一类负例是错误重试提示。后端 `DEADLINE_EXCEEDED` 只表示调用方未在期限内得到结果，不表示消息未写入。若网关返回“发送失败，请直接重试”，客户端可能产生重复消息。应返回可重试语义，并要求携带幂等键；服务端依据该键查询或去重。`UNAVAILABLE`、`RESOURCE_EXHAUSTED` 也应明确“可稍后重试”及退避建议，而不能伪装成 `404`、`400` 或确定性的未提交结果。

### 应用合同、测试矩阵与回退证据

### 应用合同、测试矩阵与回退证据

网关应把“状态码映射”写成可版本化的应用合同，而非散落在拦截器中的条件判断。合同至少固定三件事：对外 HTTP 状态、稳定的机器可读错误码、允许暴露的上下文。比如 `INVALID_ARGUMENT→400`、`UNAUTHENTICATED→401`、`ALREADY_EXISTS→409`；对非成员访问内部资源产生的 `PERMISSION_DENIED`，若隐藏政策要求避免资源存在性泄露，则统一返回 `404`，且不得在消息、字段或响应时间中暗示真实原因。

对依赖故障必须区分阶段：

- `RESOURCE_EXHAUSTED`：返回 `429` 或受控的 `503`，明确是否可重试及退避时间。
- `UNAVAILABLE`：通常返回 `503`，可重试，但必须结合幂等键。
- `DEADLINE_EXCEEDED`：返回 `504` 不等于“操作未提交”；响应应标记“结果未知”，并提供按请求标识查询最终状态的路径。

建议错误体保持稳定，例如：

`{ "code": "RESULT_UNKNOWN", "request_id": "...", "retryable": false }`

其中 `retryable` 表示“原请求可否直接重放”，不是“用户能否再次发起业务操作”。创建、扣款、写入等操作应接受 `Idempotency-Key`；服务端将键、调用方、请求摘要与最终结果绑定。相同键且摘要一致时返回已有结果；摘要不一致则报冲突，避免把超时重试变成重复提交。

测试矩阵至少覆盖旧客户端、新客户端和混合部署：验证旧客户端能解析新增错误字段、未知错误码有安全回退、新客户端不会把 `404` 误判为资源必然不存在。再加入安全负例：非成员请求存在与不存在的资源，应获得等价的 `404` 形态、长度与审计策略；超时后重试同一幂等键，不得产生第二次副作用。

最后保留回退证据：按 `request_id` 关联网关映射前后的 gRPC 状态、HTTP 响应、依赖耗时、幂等命中与业务提交状态；发布时按版本和映射规则打指标。这样出现 `504` 激增或 `404` 隐藏策略误伤时，才能灰度切回旧映射，并证明回退没有掩盖已提交的请求。

> **要点** — 网关应显式定义安全错误合同；超时只表示结果未知，授权错误映射必须防止资源存在性泄露。

兼容性不是“能解析就能上线”。在新旧端、生产者与消费者混部时，必须把字段可读、业务语义、安全授权和回复结果逐层验证。

### 建立跨层兼容检查框架

### 建立跨层兼容检查框架

兼容性检查应从“消息能否到达”升级为“业务是否仍然安全成立”。可按五层逐项验证：

1. **传输层**：请求、事件或回放记录能否路由到目标；超时、重试、幂等键、死信处理是否一致。RPC 可达不等于操作已成功执行。

2. **格式层**：Protobuf 是否能解析未知字段、字段号和类型是否兼容；ProtoJSON 转码后，字段名、枚举字符串、`oneof`、`null` 与缺省值是否改变含义。`parse` 成功只说明字节可读。

3. **语义层**：新字段缺失时的默认值是否安全。例如 `visibility` 缺失被解释为“公开”，会使旧消息在新服务中扩大可见范围；业务 `version` 应明确控制新旧规则分支。

4. **安全层**：每次读取、消费和回放都要按权威授权信息校验，而非仅信任消息中的缓存字段。旧 consumer 若忽略 `visibility`，可能把原本受限事件投递给无权对象。应先升级读端，或在安全 fallback 中回查权威数据；无法回查时隔离版本。

5. **结果层**：检查回复状态、错误码、部分成功、异步最终状态与降级行为。新 client 调旧 server 时，不能因服务端忽略新字段就把“未执行新语义”误判为成功。

因此，每条兼容路径都应记录：解析结果、默认值决策、授权结论和最终业务结果；任一安全语义无法证明成立，就应拒绝、降级或隔离，而不是仅凭可解析放行。

### 客户端与服务端的双向混部

### 客户端与服务端的双向混部

客户端—服务端兼容至少要分别验证两个方向；“请求能被解析、响应能被反序列化”只是最低门槛，不等于业务可用或安全。

| 场景 | 主要风险 | 应对策略 |
|---|---|---|
| 旧客户端 → 新服务端 | 旧端未发送新字段，服务端得到默认值；新服务端改变默认语义或强制新校验，可能误拒绝旧请求 | 服务端按`业务版本`解释缺失字段，保持旧默认语义；若无法安全推断，返回明确的“需要升级”状态，而非把零值当作授权、范围或开关 |
| 新客户端 → 旧服务端 | 新字段被旧端忽略；新客户端以为能力已生效，实际仍按旧规则执行 | 客户端依据服务端能力版本、特性协商或响应中的生效版本决定是否启用；收到“不支持字段/能力”时降级为旧流程，不能假设静默成功 |

尤其要区分协议默认值与业务默认值。`visibility`缺失在 Proto 中可能解析为零值，但零值究竟表示“私有”“继承旧策略”还是“未指定”，必须由服务端按请求版本明确判定。不得仅因字段缺失便扩大查询范围、跳过权限校验，或把未指定解释为公开。

错误码也属于兼容契约。新服务端对旧请求应优先返回旧客户端可理解的状态：例如参数非法、权限不足、资源不存在或操作不支持；只有客户端声明支持时，才返回更细的新状态。新客户端遇到未知错误码，应保守处理：停止可能产生副作用的重试，展示可恢复失败，并回退到已验证的旧能力。

推荐将响应写成可判定的结果，而非只返回“成功”：

- `status`：成功、拒绝、需要升级、暂不支持；
- `effective_version`：本次实际采用的业务规则版本；
- `applied_features`：哪些新能力真正生效；
- `fallback_required`：客户端是否必须切换旧流程。

若旧协议无法表达安全拒绝、能力协商或必要的权限上下文，就不应依赖“兼容解析”继续混部；应隔离版本入口，或先升级服务端的安全兜底与旧客户端。

### 事件生产消费与历史回放

### 事件生产消费与历史回放

事件流的兼容对象不只是“正在运行的消费者”，还包括延迟消费、死信重放、归档恢复和审计回放。`能反序列化`仅说明字节格式可读；它不保证事件仍可被安全地解释和执行。

- **旧生产者 → 新消费者**：新消费者可以读取新增的 `visibility`、`version` 等字段，但必须为旧事件定义保守语义。旧事件缺少 `visibility` 时，不能因默认值为“公开”就放行；应按“未知/受限”处理，并通过事件主体、资源归属或权威服务补查授权。
- **新生产者 → 旧消费者**：旧消费者通常忽略未知字段。若新生产者增加 `visibility=internal`，而旧消费者忽略该字段并按历史逻辑向所有订阅者分发，就会发生泄露。此时应先升级全部读端，或在旧读端之前设置安全网关、主题隔离、权限过滤；做不到时，新旧版本必须隔离发布。
- **存量事件回放 → 新消费者**：历史记录中的缺失字段、已废弃枚举值、旧身份标识都应被显式识别。回放逻辑不能把“字段不存在”误判为“权限无限制”，也不能用当前默认策略重写历史安全语义。

建议将事件解释分为两层：格式层接受可识别的消息，业务层再判定其 `version`、`visibility`、租户、资源状态和授权上下文。对于无法安全判定的事件，选择拒绝、隔离到人工队列或仅执行无副作用处理，而不是静默降级为可见、可投递或可重放。

### ProtoJSON转码与安全默认值

### ProtoJSON转码与安全默认值

Protobuf 的兼容性以字段编号为核心：新字段对旧二进制消费者通常只是“未知字段”，可被跳过；但经过 ProtoJSON 转码后，未知字段往往被直接丢弃，`optional` 的“未设置”也可能与默认值混淆，因而不能把“成功解析”当作安全语义保持。

例如：

`optional bool visibility = 7;`

在二进制消息中，接收方可区分：

- 字段不存在：调用方没有声明可见性；
- `visibility = false`：调用方明确要求不可见；
- `visibility = true`：调用方明确允许可见。

若转成 ProtoJSON 时省略默认值，前两种都可能表现为字段缺失；若网关、旧客户端或中间服务把缺失补成 `false`、`true`，则语义已被改写。尤其危险的是旧消费者根本不认识 `visibility`，却仍按旧逻辑展示、转发或导出内容：新生产者以为“默认私有”，旧读端却可能执行历史上的“默认公开”。

编号复用更不可接受。即使把字段名从 `visibility` 改为 `role`，只要仍使用编号 `7`，旧存量事件、缓存消息或重放日志都可能被新消费者解释为另一种权限含义。字段应永久保留编号与废弃声明，而不是删除后再利用。

安全字段必须采用拒绝优先的推导：缺失、无法识别、转码丢失、版本不支持时，不能推断为公开或已授权；应回查权威权限系统，回查失败则拒绝、隔离或返回明确的“不支持”。只有全部读端已具备该安全兜底，才能启动携带新权限语义的生产者。

### 以读端先行完成安全迁移

### 以读端先行完成安全迁移

新增 `visibility`、租户范围、数据分级等字段时，最危险的路径通常不是新读端，而是**旧读端收到新消息后忽略未知字段**：消息能够解析，却按旧逻辑展示、转发或执行，造成越权泄露。

因此迁移顺序应是“读端先行、生产后置”：

1. **先升级所有可控读端**：新消费者、RPC 服务端、事件回放程序都必须识别新字段，并将其纳入授权判断。
2. **提供权威查验回退**：字段缺失、版本未知或转码丢失时，不应默认放行；应以 `resource_id`、主体和租户向权威服务查询当前可见性，再决定允许、脱敏或拒绝。
3. **保留显式失败语义**：RPC 回复应区分“字段不支持”“需要升级”“无权访问”“资源不可见”，不能把拒绝伪装成空结果或成功。
4. **确认旧读端处置策略**：若旧消费者无法升级，且没有可用的权威回退，就必须隔离版本：新生产者只投递到新主题、新队列、新方法或新协议版本，禁止混投。

兼容矩阵应记录证据，而非只写“可解析”：

| 路径 | 允许条件 | 新字段生产 |
|---|---|---|
| 新生产者→旧消费者 | 旧端有权威查验或已隔离 | 否/仅隔离后 |
| 旧事件回放→新消费者 | 缺字段时默认拒绝或权威补查 | 可 |
| ProtoJSON 转码 | 字段保留、名称映射和默认值已验证 | 可 |
| 新客户端→旧服务端 | 服务端明确拒绝或安全降级 | 不依赖新语义 |

只有当所有实际读路径都已安全处理“字段存在、字段缺失、字段被忽略、字段转码丢失”四种状态，才开启新字段生产。

> **要点** — 兼容发布必须证明旧数据不会绕过新安全语义；无法安全回退时，应隔离版本而非宽松兼容。

兼容不是“新旧都能解析”即可；字段、能力、持久化事件与回滚路径都必须证明业务语义仍然安全。

### 分层识别：格式兼容不等于业务可用

### 分层识别：格式兼容不等于业务可用

“能收到、能解码、能反序列化”只证明某一层格式兼容，不能推出业务可用。应把兼容边界至少拆为四层，并分别定义版本、能力与拒绝规则：

- **传输协议层**：例如 HTTP、gRPC、消息队列连接及认证方式。它关注连接、帧、超时、压缩与路由；请求可达不代表服务理解其意图。
- **编码格式层**：例如 Protobuf、JSON、Avro 的字段编号、可选字段与未知字段保留。新增字段可能可被旧端忽略，但“忽略”是否安全取决于字段语义。
- **事件线格式层**：持久化事件、日志、索引中的记录结构。事件一旦写入，就会被回放、重建索引和审计；新字段是否在旧二进制回滚后保留，必须单独验证。
- **业务消息版本层**：定义操作语义、前置条件、能力协商与状态迁移。例如 `R9` 请求即使仅增加到 9 字节，也必须显式获批；旧客户端 `S2` 仍应按原规则拒绝，不能因“缺字段”而混入新版本默认逻辑。

因此，消息应同时携带或可推导出`版本`、`能力`与`来源`，消费者按业务版本门控，而非仅按解码成功放行。对未知字段，要明确其策略是保留、隔离、拒绝还是降级；对可回放事件，还要验证旧消费者读取新事件时不会丢失关键语义。兼容测试的结论应写成：“哪些层可互通、哪些业务操作允许、哪些组合必须拒绝”，而不是笼统地宣称“新旧兼容”。

### 新增字段与双读：记录未知值和重放风险

### 新增字段与双读：记录未知值和重放风险

新增字段不能只看“旧端能否跳过”。设事件从版本 $v_1$ 演进到 $v_2$，新增可选字段 `mode`：其状态至少有三种——字段缺失、字段存在且值为已知、字段存在但值未知。若业务把“缺失”直接默认成某个新语义，就会把历史事件、旧生产者事件与未来版本事件混为一类。

双读的正确推导是：先保留原始存在性，再按版本和能力解释语义。例如：

- `mode` 缺失：按旧协议路径处理，并记录“旧格式”来源；
- `mode=known`：启用新语义；
- `mode=unknown`：不得静默降级为默认值，应隔离、拒绝或以明确的兼容策略转发。

持久化尤其危险。服务若读取 $v_2$ 事件后再写回、建立索引或转发给下游，必须确认未知字段是否被原样保留。否则一次“读—改—写”就可能删除未来字段；当事件日后重放时，重放的已不是原始业务事实，而是被旧二进制截断后的版本。

因此事件记录应同时保存：原始载荷或可无损重编码形式、解析版本、字段存在性、生产者能力及处理决策。重放时按当时记录的语义上下文判定，而非仅用当前默认值重新解析。上线前还应验证：新事件已持久后回滚旧二进制，未知字段、索引含义和副作用不会丢失；“部署可回滚”并不等于“事件语义可回滚”。

### 能力协商与生产者门控

### 能力协商与生产者门控

“能解析”只说明字节可被读取，不说明接收方会按新语义执行。生产者发送新增字段、扩展枚举值或新版事件前，必须同时确认三类条件：

- **客户端能力**：调用方是否显式声明支持该请求形态、返回字段或行为变化。
- **服务端版本**：当前处理节点及其降级路径是否理解新语义，而非仅忽略未知字段。
- **消费者状态**：所有会读取已持久化事件的消费者、索引器、审计任务、重放工具是否已升级并完成验证。

门控应是明确的决策，而不是“字段缺失则取默认值”。例如 R9 请求要求固定为 9 字节，只有能力协商已批准时才能发送；旧版 S2 即使可收到请求，也必须继续拒绝，不能把缺失能力标记解释为“允许按新规则处理”。否则同一业务动作会因客户端版本不同落入两套规则，形成难以审计的语义分叉。

可将发送条件表达为：

$$
\mathrm{emitNew} =
\mathrm{clientCapable}
\land \mathrm{serverReady}
\land \mathrm{consumersReady}
\land \mathrm{rollbackSafe}
$$

其中 `rollbackSafe` 尤其关键：新事件一旦持久化，回滚旧二进制并不等于恢复旧语义。必须验证旧版本遇到未知字段时不会丢弃关键状态、错误重写事件或在重放时产生不同结果。若不能证明，应保留新读取路径，或将新事件隔离到独立主题、索引与保留期内，等待迁移完成后再收缩旧路径。

### 迁移旧事件：索引、保留期与隔离工单

### 迁移旧事件：索引、保留期与隔离工单

旧事件补迁移不是一次“批量重放”操作，而是对历史语义、查询能力和审计证据的重建。先明确迁移范围：按事件类型、产生版本、租户、时间窗口和状态建立清单；不要仅以“能被新消费者解析”为完成条件。每条旧事件都应能回答：原始载荷在哪里、按何种规则转换、转换后写入了哪些新字段、是否已被业务消费。

迁移任务应具备可重入性与可验证性：

- 使用稳定事件标识作为幂等键，避免重跑生成重复状态、重复通知或重复索引。
- 保留`原始事件版本`、`迁移规则版本`、`迁移时间`与`迁移操作者/任务号`；新旧载荷至少保留可关联的摘要或不可变归档地址。
- 索引重建与事件转换分离：先验证主存储中的新语义正确，再异步重建搜索、统计和物化视图索引，避免“索引成功”掩盖事件写入失败。
- 对金额、权限、状态机等关键字段做总量核对与抽样逐条比对；例如迁移前后应满足 $\sum amount_{old}=\sum amount_{new}$，且终态分布不异常漂移。

日志与原始事件的保留期必须覆盖“迁移执行期 + 验证窗口 + 可回滚窗口”，不能在索引尚未稳定、旧消费者尚未下线时提前清理。若新事件已持久化，回滚旧二进制前还要确认其会保留未知字段，且不会把新语义降级为旧默认值。

无法转换、字段冲突、缺失上下文或重放产生副作用的记录，应进入隔离队列，而非静默跳过。每张隔离工单应包含事件标识、原始载荷、失败阶段、规则版本、影响范围、重试次数和人工处置结论；修复后通过受控重放回流，并保留“为何能安全重放”的证据。这样，历史数据不仅被迁移，也能被追溯、解释和审计。

### 收缩与回退：以证据而非部署版本决策

### 收缩与回退：以证据而非部署版本决策

三种动作看似都在处理“新旧兼容”，但证据标准不同，不能以“已发布新版本”或“已回滚旧二进制”代替验证。

| 动作 | 可以推进的条件 | 核心风险 |
|---|---|---|
| 前向扩展 | 新字段可选；旧消费者忽略未知字段后语义仍正确；生产者按能力或版本门控 | 把“能解析”误当成“能执行” |
| 收缩旧路径 | 活跃用户、离线客户端、异步消费者、重放任务均已迁移；旧格式索引、日志和保留事件已处置 | 长尾客户端或延迟消费者重新触发旧协议 |
| 回滚旧二进制 | 已验证其读取新持久化事件时不会丢弃未知字段、改变默认值或破坏幂等语义 | 旧程序解析成功，但写回时抹掉新语义 |

例如，R9 请求要求 9 字节且必须经批准，旧 S2 即使能读到该请求，也必须继续拒绝；不能通过“缺失能力字段时默认允许”来混合两套规则。生产者应仅向已声明 R9 能力的目标发送该请求，并记录能力、版本、未知字段出现率与重放来源。

收缩前至少检查：

- 用户和设备版本分布，含长期离线、灰度组与第三方集成；
- 所有消费者：在线服务、批处理、索引器、审计管道、死信重放器；
- 事件与日志保留期，确认旧事件是否仍可能被重放；
- 旧索引、迁移失败记录和隔离工单是否已闭环。

尤其要区分“回滚部署”和“回滚数据语义”。新事件一旦持久化，回滚前应抽样或全量验证旧二进制对未知字段的读取、转发、更新和重写行为；若它会丢字段或将新状态折叠为旧默认值，应停止回滚，或先隔离新事件与写入路径。

> **要点** — 协议可解析只证明格式可读；安全演进必须以能力门控、历史数据迁移、消费者状态与可验证回退为依据。

从源码中看到消息进入队列并被消费者落库，只能证明局部数据流存在，不能据此推定协议升级、确认语义与业务安全已经成立。

### 先界定源码证据的边界

### 先界定源码证据的边界

以 OpenIM 的单聊、群聊发送路径为例，若 `send.go` 在构造 `MsgData` 后调用 `MsgToMQ`，而另一 Mongo 消费者最终调用 `BatchInsertChat2DB`，静态阅读能够直接建立的证据链很有限：

| 源码位置 | 可直接观察的事实 | 不能据此推出 |
|---|---|---|
| 单聊/群聊发送逻辑 | 请求被转换或填充为 `MsgData` | 客户端已收到可靠送达确认 |
| `MsgToMQ` 调用点 | 服务端尝试把消息交给消息队列 | 队列已持久化、已复制或一定会被消费 |
| Mongo 消费逻辑 | 消费者可解析某类 `MsgData` 并调用批量落库 | 所有版本消息都兼容、不会重复或乱序 |
| `BatchInsertChat2DB` | 存在聊天记录写入数据库的代码路径 | 写入成功等于业务安全、离线推送和会话更新也成功 |

因此，可以谨慎表述为：源码显示消息协议对象可能沿“发送服务 → 消息队列 → Mongo 消费者 → 数据库”传播。这里的“可能”仍取决于路由、主题、开关、错误处理与部署是否实际生效。

尤其不能把这两段代码外推为已经采用教学 RPC、事件 V2，或已经完成版本协商。`MsgData` 能被两端解析，只说明某个字段结构在当前依赖组合下可用；它不能证明生产者确认等级是仅写入本地、等待队列确认，还是等待副本确认，更不能证明失败时的重试、幂等、死信与补偿策略。

运行前应继续核对：`protocol` 依赖的具体提交与 schema、队列主题及确认配置、客户端版本、消费者镜像版本和部署副本；运行时再通过日志、指标与故障注入验证“发送响应”究竟对应哪一级确认。

### 建立只读源码证据表

### 建立只读源码证据表

将源码观察限定为“可定位的事实”，避免把函数调用链误读为完整协议保证。可按下表记录证据：

| 观察点 | 只读证据 | 当前可得结论 | 仍然缺失的证明 |
|---|---|---|---|
| 发送入口 | 单聊、群聊 `send.go` 接收请求并构造消息 | 两类业务入口都进入发送流程 | 客户端版本是否兼容、请求字段是否经过版本协商 |
| `MsgToMQ` | 发送流程调用 `MsgToMQ` | 服务端尝试将消息交给消息队列层 | 调用成功是否等于 broker 持久化成功；失败重试与幂等策略 |
| 消息载体 | 可见 `MsgData` 被组装、传递或序列化 | 消息内容在生产侧具有统一载体 | `MsgData` 的 schema 版本、未知字段处理、跨版本字段语义 |
| 队列配置 | 代码或配置中存在 topic、broker 地址、生产者参数 | 生产者面向某个队列或主题发布 | 实际部署使用的配置、确认等级、复制因子、超时与降级行为 |
| 消费者 | Mongo consumer 订阅相应消息来源 | 存在一条消费并处理聊天消息的路径 | 消费组部署数量、消费位点、重平衡、积压和死信处理 |
| `BatchInsertChat2DB` | consumer 最终调用批量写库函数 | 已消费的部分消息可能被批量写入 MongoDB | 批次失败后的回滚、重复写入、顺序保证与写入确认 |
| 响应返回 | `send.go` 在 `MsgToMQ` 后构造响应 | 调用方可收到“已受理”或类似结果 | 响应究竟表示本地校验、生产者确认、broker 落盘，还是数据库可见 |

这张表支持的最强结论是：`MsgData` 可从发送入口进入队列路径，并存在消费者调用 `BatchInsertChat2DB` 的落库意图。它不能证明教学 RPC、事件 V2、协议版本协商或生产者确认等级已经启用。

运行时仍需核验：当前 `protocol` 依赖的具体提交与 schema、服务端和客户端版本矩阵、实际队列配置、生产者 `acks`/确认参数、consumer 实例与消费组状态，以及发送响应与最终 MongoDB 可查询记录之间的对应关系。

### 消息可传递不等于版本可协商

### 消息可传递不等于版本可协商

`send.go` 调用 `MsgToMQ` 后返回 HTTP 响应，Mongo 消费者再以 `BatchInsertChat2DB` 落库，最多说明某个 `MsgData` 可沿“接入层→队列→消费者→数据库”传递。它不能自动证明客户端、RPC 服务、事件消费者都理解同一版本的业务语义。

| 层次 | 可从“调用成功”推得什么 | 不能推得什么 |
|---|---|---|
| HTTP 响应 | 请求被当前网关或服务处理 | 下游已持久化、客户端字段语义兼容 |
| RPC 调用结果 | 某个方法名和请求结构可被服务端接受 | RPC 接口存在版本协商、旧客户端不会误读新字段 |
| 事件线格式 | 消费者可反序列化当前队列消息 | 所有消费者均已升级、重复投递与未知字段安全 |
| Protobuf `MsgData` | 已知字段可编码、解码和转发 | 业务消息 V2 的类型、扩展字段、降级规则一致 |
| 业务消息 V2 | 应用层可能识别新的消息类型 | 老客户端展示正确、审核/推送/离线同步均具备对应逻辑 |

Protobuf 的“未知字段通常可跳过”是**线格式兼容**，不是业务兼容：新增 `contentType` 即使不导致解码失败，旧端仍可能把 V2 当作普通文本、空消息或不可展示消息。反过来，HTTP 的 `200` 也只表示该层选择确认；它未定义生产者确认等级，更不等价于 Mongo 已写入或所有事件处理完成。

只读源码应记录证据边界：`MsgToMQ` 的入参与返回处理、队列事件的序列化类型、`BatchInsertChat2DB` 的消费字段及错误路径。仍需运行验证：锁定 protocol 依赖的具体提交与 schema，核对配置中的主题和消费者部署版本，以新旧 client 交叉发送 V2 消息，并观察 RPC 返回、队列确认、消费者日志、落库结果及旧端展示。

### 识别确认与重试的未知结果

### 识别确认与重试的未知结果

`MsgToMQ` 调用后立即向单聊或群聊请求返回响应，最多说明服务端已完成某个同步阶段；它**不等价于消息已被队列可靠接收，更不等价于 Mongo 消费者已成功落库**。若随后由 consumer 的 `BatchInsertChat2DB` 异步处理，则请求响应与最终持久化之间存在天然断点：

| 源码可见证据 | 不能据此推出的结论 |
|---|---|
| `MsgData` 被构造并传入 `MsgToMQ` | 队列已持久化、已复制或已被消费 |
| 调用后返回成功响应 | 已达到“至少一次”或“恰好一次”确认等级 |
| consumer 批量调用 `BatchInsertChat2DB` | 每条消息都已提交 Mongo 且可查询 |
| 失败路径可能记录日志 | 已配置重试、退避、死信队列或告警 |

尤其要区分三类确认：生产者是否收到 broker 确认、broker 是否确认消息持久化、业务是否确认 Mongo 写入成功。若客户端因网络超时未收到响应，它可能重发同一 `MsgData`；若生产者已成功投递而响应丢失，重试会造成重复投递。consumer 重启、批处理部分失败或 Mongo 写入超时，也可能让同一消息再次被消费。

因此，当前静态阅读只能标记“可能重复、结果未知”。运行时仍需验证：消息 ID 是否全链路唯一；Mongo 是否以消息 ID 建立唯一约束或幂等写入；MQ producer 的确认等级与重试次数；consumer 提交位点相对数据库提交的顺序；失败消息是否进入重试或死信机制。只有这些证据闭环后，才能判断“响应成功”真正代表什么。

### 列出运行时待验证项

### 列出运行时待验证项

静态源码只能确认 `MsgData` 可能从 `send.go` 经 `MsgToMQ` 进入 Mongo 消费链路；上线前必须把“代码存在”转化为可复核的运行证据。建议建立只读证据表：每项记录仓库地址、具体提交号、文件或配置路径、采集时间、环境、负责人及结论。

| 验证对象 | 运行时待验证问题 | 证据与动作 |
|---|---|---|
| 生产者提交 | 当前发布镜像对应哪个 `commit`？`MsgToMQ` 是否等待 Broker 确认，失败如何返回？ | 镜像标签、构建流水线、发送日志、Broker 确认指标 |
| 协议定义 | `MsgData` 的字段号、必填性、默认值、未知字段策略是否变化？ | `.proto`/IDL 提交、生成代码版本、序列化样本 |
| 序列化规则 | 是否使用 Protobuf/JSON，是否存在字段改名、枚举扩展、压缩或加密？ | 抓取脱敏消息、编码/解码双向测试 |
| 配置生效 | Topic、消费者组、Mongo 地址、重试与死信队列配置是否与代码一致？ | 实际容器环境变量、配置中心快照、启动日志 |
| 客户端版本 | 老客户端能否解析新字段；新客户端收到旧消息时如何降级？ | 客户端版本分布、灰度名单、兼容测试结果 |
| 消费者部署 | `BatchInsertChat2DB` 是否运行、订阅正确 Topic、消费延迟是否可接受？ | Deployment 镜像、消费组状态、积压量与延迟图表 |
| 落库一致性 | 重复投递是否幂等；批量写入失败是否重试、补偿或进入死信？ | 唯一键设计、失败日志、重放演练记录 |
| 可观测性 | 能否按 `sendID`、`clientMsgID` 或消息 ID 串联生产、消费、落库？ | 链路追踪、结构化日志、告警规则 |

据此制作兼容矩阵：横轴为客户端、生产者、消费者版本，纵轴为协议版本和字段组合，标注“可互通、降级可用、拒绝发送、需迁移”。发布应采用先扩消费者、再扩生产者、最后升级客户端的顺序；新字段应保留默认语义，破坏性变更使用新 Topic 或显式版本字段。回退时必须能停止新格式生产、将流量切回旧消费者，并对已进入队列的消息提供兼容消费或可审计重放。

> **要点** — MsgData 从发送端到落库端可见，只证明局部链路；版本协商、确认语义、重试安全与回退能力必须由运行证据补全。

兼容评审不能只问“能否解析”，还必须沿协议阶段、线格式、业务语义与运行结果四轴验证安全边界。

### 建立四轴兼容边界

### 建立四轴兼容边界

“新旧客户端能通信”不是单一结论，而是四条独立边界都成立：协议阶段、线格式、业务语义与运行结果。任一轴失败，都可能出现“可解析但不安全”的上线事故。

- **协议阶段轴**：先确认请求是否应被接受。HTTP/RPC 层的认证、路由、版本协商与状态码必须明确：`401` 表示未认证，`404` 表示资源或路由不可见，`409` 表示当前状态冲突；不能把这些失败降级为业务成功。gRPC 还应约束 `deadline`、取消与重试：超时后的请求可能已在服务端提交，客户端重试必须携带幂等键或请求标识。

- **线格式轴**：关注字节是否能被旧版/新版正确读取。Protobuf 的兼容关键是稳定的 field number、字段类型与 `oneof` 语义；已发布字段不得复用编号。`presence` 需区分“未传”和“传零值”，否则默认值会被误解释。未知字段通常可被保留或忽略，但“能忽略”不等于“可安全执行”。

- **业务消息版本轴**：事件或 RPC 消息应声明版本、能力和必填语义。新版发送的字段若承载权限、金额、状态迁移等关键含义，旧消费者忽略后可能绕过约束。此时应采用双写、降级字段、版本门控或拒绝投递，而不是仅依赖 unknown field。

- **运行结果轴**：验证副作用是否一致，包括重试、乱序、重复投递、回放与回滚。特别标记 `R9 pending`：若新语义尚无旧端等价行为，不得默认放行；应保留待处理状态，并提供可观测证据与人工/自动补偿路径。

兼容矩阵至少覆盖 old→old、old→new、new→old、new→new，并分别记录请求、响应、事件消费与重放结果。上线阶段门应要求：字段编号审计、语义差异评审、超时重试证明、回退后消息可处理证明。回退条件包括关键事件无法被旧端安全解释、`409` 冲突异常增长、幂等失败或 OpenIM 固定边界外出现未受控消息转换。

### 字段演进与语义守恒

### 字段演进与语义守恒

Protobuf 的兼容性首先是**线格式可解析**：字段编号决定二进制槽位，修改字段名通常无影响；但复用已删除的字段编号、改变 wire type，或将 `string` 改为不兼容的数值编码，都会使旧消息被误读。因而删除字段后应保留编号与名称，禁止重新分配。

更隐蔽的是 presence（存在性）变化。旧版 `bool enabled = 3` 无法区分“未发送”与“发送 `false`”；新版改为 `optional bool enabled = 3` 后，服务端若把“缺失”解释为“沿用默认允许”，把显式 `false` 解释为“禁用”，就必须确认旧客户端产生的缺失值不会绕过安全策略。线格式仍能解析，不代表授权语义仍守恒。

未知字段保留也不能被误判为端到端兼容：中间旧版本若“解析—修改—重新序列化”时丢弃未知字段，新客户端写入的 `risk_level`、幂等键或审批状态会在转发链路消失。应分别验证：

| 路径 | 线格式 | 语义风险 | 结论 |
|---|---|---|---|
| 新客户端→旧服务 | 未知字段可跳过 | 新约束未执行 | 不可直接放量 |
| 新→旧代理→新服务 | 可能可解析 | 未知字段可能丢失 | 需实测保留 |
| 旧客户端→新服务 | 缺失字段可解析 | 默认值改变含义 | 需兼容分支 |

评审证据应覆盖字段编号清单、`optional` 缺失/显式零值用例、未知字段经旧节点往返后的字节或语义断言。上线门槛不是“旧端不报错”，而是每个缺失、默认与未知字段都不会把拒绝、待审批或幂等语义降级为允许。

### 超时重试的未知结果

### 超时重试的未知结果

gRPC 的 `deadline exceeded` 只说明客户端未在截止时间内得到响应，**不说明服务端没有执行**。请求可能尚未送达、正在排队、已提交数据库，或已完成但响应在网络中丢失。因此，超时后的“立即重试”可能把一次创建、扣款、发消息或权限变更执行两次。

应将结果区分为三类：

- **明确成功**：收到成功响应，可保存业务结果。
- **明确失败**：收到可判定的业务错误，例如参数非法、`401` 未认证、`404` 目标不存在、`409` 冲突。
- **未知结果**：超时、连接中断、服务端不可达等；不得直接视为失败，更不得无条件重试。

对会产生副作用的调用，客户端必须携带稳定的幂等键 `idempotency_key`。同一业务意图在重试、断线恢复和回放时复用同一键；服务端以“调用方身份 + 幂等键”建立去重记录，并持久化首次执行结果。重复请求应返回原结果，而不是再次执行业务动作。

未知结果进入 `R9 pending`（待确认）状态：

1. 记录请求标识、幂等键、deadline、目标版本和最后错误；
2. 通过查询接口按幂等键或业务单号确认是否已生效；
3. 已生效则收敛为成功；明确未生效才允许以原幂等键重试；
4. 超过确认窗口仍无法判断，保留待定并进入人工或异步对账，不允许改用新键重新提交。

评审时应验证旧客户端/新服务端、旧服务端/新客户端矩阵中，幂等键与查询语义均兼容；回退后仍能识别升级期间写入的待定记录。证据至少包括：超时后服务端实际成功的测试、重复投递只产生一次副作用的日志，以及 `R9 pending → 成功/失败` 的可追踪状态迁移。

### 授权与错误码安全映射

### 授权与错误码安全映射

兼容层最危险的“成功”之一，是把不同安全语义压缩成同一种错误。`401`、`404`、`409` 都可能让客户端“操作失败”，但它们回答的是完全不同的问题：

| 状态码 | 对外语义 | 服务端事实 | 可否由兼容层改写 |
|---|---|---|---|
| `401` | 未完成身份认证或凭证无效 | 调用方身份不可信 | 不得降级为“资源不存在”或业务成功 |
| `404` | 资源不存在，或按资源隐藏策略不暴露其存在性 | 资源确实不存在，或调用方无权获知 | 仅在明确的防枚举策略下用于隐藏 |
| `409` | 身份已确认、资源语义可见，但当前状态不允许操作 | 并发版本、幂等键、生命周期或状态机冲突 | 不得伪装成认证失败或不存在 |

授权失败还应区分“未认证”与“已认证但无权”。后者通常应映射为 `403`；若产品规定资源隐藏，则可对外返回 `404`，但审计日志、指标和内部错误码仍必须保留真实拒绝原因。否则，攻击者虽看不到资源，运维也同时失去了授权拒绝证据。

`409` 尤其不能被旧客户端兼容逻辑吞掉。例如删除已进入“处理中”的会话、用旧版本号覆盖新资料、重复提交同一迁移请求，都属于状态冲突；若兼容层改为 `404`，客户端可能误以为对象消失并触发重建，造成重复写入或越权恢复。

上线评审应固定映射表：每个 RPC 分别记录认证缺失、权限不足、资源隐藏、真实缺失、版本冲突和幂等重放的外部码、内部原因码与审计字段。回退条件是：新旧版本对同一请求出现“`401/403/404/409` 互换”、冲突被报告为成功，或资源隐藏策略泄露对象存在性。

### 混部矩阵与上线回退

### 混部矩阵与上线回退

混部评审应将“旧/新”拆为客户端、生产者、消费者三个角色，并分别检查协议阶段、线格式、业务语义、运行结果四轴；“可解析”仅证明线格式未立即失败。

| 生产者 | 消费者 | 必验结论 | 风险处置 |
|---|---|---|---|
| 旧 | 旧 | 基线行为、错误码稳定 | 作为回放对照 |
| 旧 | 新 | 新端保留未知字段、正确识别 `presence` | 禁止把缺失字段误判为默认业务值 |
| 新 | 旧 | 新字段号不复用，旧端忽略 unknown 后业务仍安全 | 新能力必须有旧端可接受降级 |
| 新 | 新 | 语义、幂等、deadline/retry 一致 | 验证重复投递与乱序 |

固定 OpenIM 边界：仅在适配层转换内部模型与 OpenIM 请求/响应；不得让客户端依赖 OpenIM 私有字段、错误文本或未声明的 unknown 行为。`field number` 一经发布不得改义或复用；区分“字段未出现”和“出现默认值”，尤其是权限、状态、版本与删除标记。

上线前保留可审计证据：

- **回放证据**：用脱敏生产消息覆盖旧字段、缺字段、未知字段、重复消息和乱序消息；比较 wire 解码结果与 semantic 业务结果。
- **阶段门**：灰度前矩阵全绿；灰度中监控 `401` 身份边界、`404` 资源可见性、`409` 状态冲突，不将其笼统重试；gRPC 必须设置 deadline，retry 仅限幂等请求。
- **待定项**：R9 `pending` 不得随版本发布自动转为成功；需明确旧端展示、超时终态及人工处置。
- **回退条件**：出现权限扩大、重复写入、`409` 激增、deadline 耗尽或回放语义不一致即停止扩量；回退先切流和停用新写入，再恢复旧消费者，避免新字段已写入而旧逻辑误判。

回退后仍需保存版本、字段映射、样本回放结果、监控截图与决策记录，证明回退本身没有造成不可逆语义损失。

> **要点** — 解析成功只是起点；安全兼容必须同时证明语义、授权、重试结果与回退路径均受控。
