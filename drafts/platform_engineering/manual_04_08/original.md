TCP交付的是连续字节，不是消息；本节以6字节中文正文练习帧为线索，建立读写、期限、取消与复用的正确边界。

### 字节流不等于应用消息

### 字节流不等于应用消息

TCP 向应用提供的是**有序、可靠的连续字节流**，并不保留发送端 `Write` 的调用边界。发送方一次写入 8 B，不表示接收方一次 `Read` 必然得到 8 B；接收方一次读取到的数据，也可能同时跨越多条应用消息。

练习帧规定：

`长度头 2 B（大端） | 正文 N B`

正文“公告”的 UTF-8 编码为：

`E5 85 AC E5 91 8A`

因此完整帧是：

`00 06 | E5 85 AC E5 91 8A`

若底层依次到达 `1 B、1 B、2 B、4 B`，接收方应：

1. 累积读取，直到凑满 2 B 长度头；
2. 将 `00 06` 解释为正文长度 $6$；
3. 继续读取，直到凑满 6 B 正文；
4. 仅在此时，才认为一条应用帧完成。

`Read` 返回的 `n` 只表示“本次拿到了 `n` 个字节”，不是消息完成标志。`Write` 返回成功也只表示数据已交给本机网络栈或连接对象处理；TCP ACK 说明对端 TCP 栈确认了字节，并不等价于对端业务已经返回 `200 accepted_in_memory`、完成存库，或已送达下游设备。

因此，可靠字节传输、帧完整接收和业务处理成功是三个不同层次的结论，必须分别定义与确认。

### 用长度前缀重组练习帧

### 用长度前缀重组练习帧

长度前缀把连续字节流切分为“头 + 正文”。本练习规定：前 `2 B` 是正文长度，采用网络字节序（大端）；随后紧跟该长度的载荷。

正文为 `公告`。其 UTF-8 编码逐字节为：

`公`：`E5 85 AC`  
`告`：`E5 91 8A`

因此正文长度是 `6`，写成 16 位无符号大端整数为 `00 06`。完整练习帧为：

`00 06 | E5 85 AC E5 91 8A`

总长度为 $2+6=8\text{ B}$。

接收端不能假定一次 `Read` 恰好得到这 8 B。若底层依次交付 `1 B、1 B、2 B、4 B`，正确过程是：

1. 累积读取前 `2 B`，得到头部 `00 06`；
2. 按大端解释：`length = 6`；
3. 先检查 `length` 未超过协议允许的最大值；
4. 再持续读取，直到恰好收齐 `6 B` 载荷；
5. 将载荷按约定解释为 UTF-8，得到 `公告`。

这里的“读齐”通常应使用 `io.ReadFull` 一类语义，而不是把单次 `Read` 的返回值当作帧边界。反过来，一次读取也可能同时拿到本帧末尾和下一帧开头；多余字节应留给下一轮解帧，而不能丢弃或误并入当前正文。

### 读满、短写与部分结果

### 读满、短写与部分结果

练习帧为 `00 06 | E5 85 AC E5 91 8A`。底层即使按 `1 B、1 B、2 B、4 B` 到达，`Read` 每次返回的 `n` 只表示“本次复制出的字节数”。不能假设第一次 `Read` 就拿到 2 B 头，更不能假设下一次就拿到完整 6 B 正文。

对固定长度字段，使用 `io.ReadFull` 表达“必须读满”：

```go
var hdr [2]byte
if _, err := io.ReadFull(conn, hdr[:]); err != nil {
    return err
}
n := int(binary.BigEndian.Uint16(hdr[:]))
body := make([]byte, n)
if _, err := io.ReadFull(conn, body); err != nil {
    return err
}
```

`io.ReadFull` 成功时才保证缓冲区填满；失败时仍可能已读到部分字节。其返回的数量有诊断意义：`n=1` 读头失败，说明已消费 1 B，不能把该连接剩余字节当作新帧开头继续解析。对 TCP 长连接，帧中途超时、取消或发生非预期错误时，通常应关闭连接；否则协议边界已无法可靠恢复。

写入同样可能短写。`conn.Write(frame)` 返回 `(n, err)` 后，`n < len(frame)` 表示已有前缀进入内核或链路；即使 `err != nil`，也不能断言“对端完全没收到”。应循环写完剩余部分：

```go
for len(frame) > 0 {
    n, err := conn.Write(frame)
    frame = frame[n:]
    if err != nil {
        return err
    }
}
```

但“本地写满”仅表示字节交给本机 TCP 栈，不等于对端已解析、已存库或已执行。需要业务完成语义时，仍须等待应用层响应。

### 连接前后采用不同取消机制

### 连接前后采用不同取消机制

建连与已建立连接的阻塞点不同，取消手段也应分开。

- **建连阶段**：使用 `DialContext`。它把 `context.Context` 传给拨号过程；当上下文超时或被取消时，尚未完成的 DNS 查询、TCP 握手或等待连接会尽快退出。

  ```go
  ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
  defer cancel()

  conn, err := (&net.Dialer{}).DialContext(ctx, "tcp", addr)
  ```

  这里的 `ctx` 主要约束“能否连上”，不是对后续每次 `Read`、`Write` 的持续控制。

- **连接建立后**：`net.Conn` 的 `Read`/`Write` 不直接接收 `context.Context`。要限制一次 I/O 的等待时间，应设置截止时间：

  ```go
  conn.SetReadDeadline(time.Now().Add(2 * time.Second))
  n, err := io.ReadFull(conn, header[:])
  ```

  截止时间到达时，操作通常返回超时错误；它不表示对端关闭，也不表示已读到一条完整帧。读完帧头后，应为读取载荷设置合适的读期限，避免无限等待剩余字节。

- **需要立即取消已阻塞 I/O**：关闭连接最直接。`conn.Close()` 会使正在阻塞的读写尽快返回，并且该连接通常不应再复用。若只是取消某个请求而连接承载多路业务，不能随意关闭整条共享连接；应使用协议自身的取消语义，或采用支持流级取消的协议。

因此：`DialContext` 管建连，`Deadline` 管单次或一段 I/O 的时间边界，`Close` 管整条已建立连接的终止。不要把 TCP ACK、`Write` 返回成功或拨号成功误当作应用处理完成。

### 复用连接时守住帧与受理边界

### 复用连接时守住帧与受理边界

一条 TCP 连接可被多个请求复用，但它在字节层只有**一个有序读写序列**。因此，若多个 goroutine 直接对同一连接交错 `Write`，`00 06 | E5 85 AC E5 91 8A` 这样的练习帧可能被拼成“半个头 + 另一条正文 + 剩余正文”，接收方随即失去定界能力。

发送端应以“整帧”为临界区：先编码长度头和载荷，再由同一写入序列完整发送；必要时用互斥锁保护写操作，或建立单独的发送队列，由一个 goroutine 统一写连接。接收端通常也只能有一个 goroutine 持续执行“读满 2 B 头 → 解析长度 → 读满载荷”，再把完整消息分发给后续处理者。不要让多个读取者竞争同一连接。

还要明确“成功”的层次：

- `Write` 返回成功：数据已交给本机内核，不等于对端收到。
- TCP ACK：对端 TCP 栈确认了字节，仍不等于应用读取或处理。
- S2 `200 accepted_in_memory`：应用已在内存中受理，进程崩溃时仍可能丢失。
- 已持久化：数据写入满足约定的存储边界，才可宣称持久化成功。
- B 设备确认：只有设备协议中的明确回执，才能表示设备已接收或执行。

复用连接时，响应也必须与请求建立可验证的对应关系，例如请求标识、顺序约束或并发复用协议。超时、取消或读写失败后，若无法判断当前帧是否完整、对端是否已处理，就不要把连接当作“干净可复用”的连接；关闭并重建通常比继续猜测字节边界更安全。

> **要点** — TCP只可靠交付字节；应用必须自行定界、限长、读满写全，并为I/O与业务确认分别建立边界。

TCP只提供连续字节，不承诺一次读满应用消息。固定长度字段必须按“读取、限长、分配、读齐、校验”的顺序处理。

### 一次读取不等于一帧

### 一次读取不等于一帧

`Read(p)` 的含义是“尝试把一些字节放入 `p`”，而不是“必须填满 `p`”。即使底层连接后续还会到达更多数据，本次也完全可能只返回一部分：

```go
n, err := r.Read(buf)
```

调用方必须同时检查 `n` 与 `err`：

- `n > 0, err == nil`：本次取得了 `n` 字节，但消息可能尚未完整。
- `n > 0, err == io.EOF`：先处理这 `n` 字节；`EOF` 表示之后没有更多字节。
- `n == 0, err == io.EOF`：当前已无可读数据。
- `n == 0, err != nil`：本次没有取得数据，读取失败或被取消。

因此，不能写出“读一次就认为得到一帧”的代码：

```go
r.Read(header) // 错：header 未必已读满
```

若协议规定头部固定为 2 B、正文长度为 `n`，应使用 `io.ReadFull` 读取固定长度部分。它会内部循环，直到填满缓冲区或无法继续读取：

```go
var head [2]byte
_, err := io.ReadFull(r, head[:])
```

对固定长度读取，错误含义尤其重要：

- 一个字节也未读到便结束：返回 `io.EOF`。
- 已读到部分字节才结束：返回 `io.ErrUnexpectedEOF`。

`io.ReadFull` 只保证“读齐指定字节数”，并不保证这些字节构成合法业务消息。正确顺序应是：读满头部，解析长度 `n`，确认 `1 <= n && n <= maxBody`，再 `make([]byte, n)` 并读满正文，最后校验 UTF-8 与业务规则。长度上限必须在分配前检查；长度字段能表示多大，不等于服务端应当接受或分配多大。

### 用读满操作获取固定字段

### 用读满操作获取固定字段

`Read(p)` 的契约是“尽力读取”，而不是“必须填满”。即使 `p` 长 2，也可能第一次只得到 1 字节；这在 TCP 分段、缓冲读取器、限速连接中都很正常。因此，固定长度字段不能假设一次 `Read` 就完整到达。

`io.ReadFull(r, p)` 将这一循环封装起来：只要还有空间且底层暂未报错，它就继续调用读取操作，直到 `p` 被填满。可将其理解为：

1. 维护已读取长度 `got`；
2. 重复读取 `p[got:]`；
3. 若 `got == len(p)`，读取成功；
4. 若底层结束而 `got == 0`，返回 `EOF`；
5. 若底层结束而 `0 < got < len(p)`，返回 `ErrUnexpectedEOF`。

两种结束错误表达的含义不同：

- `EOF`：连固定字段的第一个字节都没有取得。例如准备读取下一帧头，但对端已正常关闭连接。
- `ErrUnexpectedEOF`：字段已经开始，却在中途断开。例如 2 B 长度头只收到 1 B，或声明了 6 B 正文却只收到 4 B。这通常表示截断帧，不能把已读部分当作完整消息。

读取 2 B 头和正文时，可按固定顺序处理：

`ReadFull(头)` → 解析长度 `n` → 检查 `1 ≤ n ≤ 6` → `make([]byte, n)` → `ReadFull(正文)` → UTF-8 与业务校验。

关键点是：必须先验证 `n`，再分配正文缓冲区。长度字段虽然可表示到 `65535`，协议却只允许本练习中的 6 B；若先执行 `make([]byte, n)`，恶意对端可用伪造长度触发不必要的内存申请。

`ReadFull` 只保证“指定数量的字节已读齐”。它不保证这些字节是合法 UTF-8、不保证长度字段合理，也不保证正文构成完整且有效的业务消息。

### 六字节长度帧的安全读取顺序

### 六字节长度帧的安全读取顺序

设一帧格式为：

`[2 字节大端长度 n][n 字节正文]`

其中正文必须非空，且练习上限为 `maxBody = 6`。读取顺序不能写成“读长度后立刻分配”，而应固定为：

1. 用 `io.ReadFull` 读满 2 字节头。
2. 将头按大端序转换为整数 `n`。
3. 检查 `1 ≤ n ≤ 6`。
4. 仅在检查通过后执行 `make([]byte, n)`。
5. 用 `io.ReadFull` 读满 `n` 字节正文。
6. 校验 UTF-8 与业务规则。

示意代码如下：

`var head [2]byte`  
`if _, err := io.ReadFull(r, head[:]); err != nil { ... }`  
`n := int(binary.BigEndian.Uint16(head[:]))`  
`if n < 1 || n > 6 { return errInvalidLength }`  
`body := make([]byte, n)`  
`if _, err := io.ReadFull(r, body); err != nil { ... }`  
`if !utf8.Valid(body) { return errInvalidUTF8 }`

例如头为 `00 03`，则 $n=3$，可分配 3 字节并继续读取正文；头为 `00 00`，则拒绝空正文；头为 `00 07`，虽然长度字段能表达它，也必须因超过 6 字节而拒绝。更极端地，`FF FF` 表示 65535，绝不能先据此申请内存。

`io.ReadFull` 处理的是“读齐”：若一个字节也未读到便遇到流结束，返回 `EOF`；若已读到部分字节才结束，返回 `ErrUnexpectedEOF`。这说明帧被截断，但不说明正文一定可信。即使读满 6 字节，仍需检查编码、字段含义和业务约束。

HTTP 场景还应在 HTTP 边界限制原始请求体，例如限制为 4096 字节；随后解析出的本协议正文仍须满足 6 字节上限。前者限制整份 HTTP 输入，后者限制帧内字段，二者不能互相替代。

### 读齐不代表消息可信

### 读齐不代表消息可信

`io.ReadFull` 只回答一个传输问题：**指定的 `n` 个字节是否已经读齐**。它不能证明这些字节构成了可信、合法的业务消息。

设 2 B 头解析出的长度为 `n`，正确顺序是：

1. 读取 2 B 头，并用 `io.ReadFull` 保证头完整。
2. 将头转换为长度 `n`。
3. 在分配前检查协议限制：`1 ≤ n ≤ 6`。
4. 执行 `body := make([]byte, n)`。
5. 用 `io.ReadFull` 读满正文。
6. 校验 UTF-8 与业务规则。

长度字段若为无符号 16 位，理论上可表示 `0` 到 `65535`；这只是**编码容量**，不是协议授权。当前练习中，`0` 不允许表示非空正文，`7` 到 `65535` 也都必须拒绝。若先按声明长度分配：

`make([]byte, n)`

再检查 `n`，对方就可通过伪造超大长度诱导内存分配。

读齐后的正文仍可能无效。例如 3 B 数据可能不是合法 UTF-8；即使是 UTF-8，也可能是空白文本、未授权命令或不满足字段格式的内容。因此可将检查分层：

- **传输完整性**：`io.ReadFull` 是否读齐；
- **文本有效性**：是否为合法 UTF-8；
- **协议有效性**：长度、必填字段、编码格式是否符合约定；
- **业务有效性**：身份、权限、状态与语义是否允许。

此外，HTTP 的原始请求体应在 HTTP 边界限制为最多 `4096 B`，例如使用 `http.MaxBytesReader`；随后若请求体内还包含本帧格式，仍须再次执行正文 `6 B` 的协议限制。前者限制网络输入总量，后者限制帧中字段含义，二者不能互相替代。

### 帧限制与外层请求限制

### 帧限制与外层请求限制

HTTP 请求体上限与 TCP 帧正文上限解决的不是同一个问题，必须分别实施。

- **HTTP 边界**：在 handler 一进入时限制原始请求体最多 `4096 B`，例如使用 `http.MaxBytesReader`。这防止客户端用超大、持续不断的 HTTP body 占用连接、带宽或解码资源；应在读取、JSON/表单解码之前设置。
- **协议帧边界**：对帧中的 `2 B` 长度头，先读齐头部并解析 `n`，检查 `1 <= n <= 6`，再执行 `make([]byte, n)`，最后用 `io.ReadFull` 读齐正文。`4096 B` 不能替代 `6 B`：一个 HTTP body 可以包含包装字段、多帧或编码开销，而单个 S2 正文仍不得超过练习规定的 `6 B`。

推荐顺序是：

1. 限制 HTTP 原始 body 为 `4096 B`；
2. 读取 S2 的长度头；
3. 在分配前拒绝 `n=0`、`n>6` 或非法长度；
4. 仅分配 `n` 字节，并用 `io.ReadFull` 读取正文；
5. 校验 UTF-8 与业务规则；
6. 将通过校验的数据写入 S2 内存受理边界；
7. 只有设备确认成功后，才推进“已确认”业务状态。

`io.ReadFull` 只保证指定字节数已读齐；它不能证明请求未超过 HTTP 外层限制，也不能证明正文是合法命令、已被内存受理，或已获得设备确认。三类边界应各自保留，避免把“读到数据”误当成“业务完成”。

> **要点** — 先读固定头并限长，再分配和读满正文；读满只保证字节数，不保证消息合法。

一次 Write 写全，不等于消息已送达、更不等于业务已受理；必须沿着字节、帧与确认边界理解结果。

### Write 返回值的真实含义

### Write 返回值的真实含义

`io.Writer.Write(p)` 返回 `(n, err)`，其中 `n` 只表示：本次调用中，**本端 Writer 已接受**了 `p[:n]` 这部分字节。它不表示远端已收到这些字节，更不表示远端已拼出完整帧、解析成功或执行业务成功。

健壮调用方应按 `n` 推进剩余数据，并在错误出现时停止：

```go
for len(p) > 0 {
    n, err := w.Write(p)
    p = p[n:]
    if err != nil {
        return err
    }
    if n == 0 {
        return io.ErrShortWrite // 防止无进展循环
    }
}
```

标准 `io.Writer` 合同要求：若 `len(p) > 0` 却发生短写，即 `n < len(p)`，应返回非空错误；但封装网络连接、测试替身或第三方 Writer 时，仍应防御 `n=0, err=nil`。

例如要写入 8 B，第一次返回 `n=3`，则只能确认 Writer 接受了前 3 B；第二次写剩余 5 B 前遇到网络错误，远端可能只看到不足一帧，也可能已在连接关闭前收到更多字节。调用方不能从这里推出远端状态。

即使 `n==len(p)` 且 `err==nil`，也仅说明请求字节被本端写入路径接受。若 HTTP 响应在途中丢失，服务端可能已经受理；以同一 ID 重试得到 `409`，也不自动等于幂等成功。业务结果必须依赖协议响应、查询或专门的未知结果处理方案确认。

### 按 n 推进：处理短写与零进展

### 按 `n` 推进：处理短写与零进展

`Write(p)` 的 `n` 表示本次被该 `Writer` 接受的前 `n` 个字节。若还需写入完整缓冲区，待发送区间必须随每次返回前移：

```go
func writeAll(w io.Writer, p []byte) error {
	for len(p) > 0 {
		n, err := w.Write(p)

		// 防御性检查：避免不合法返回值导致切片越界。
		if n < 0 || n > len(p) {
			return fmt.Errorf("Writer 返回非法写入长度: %d", n)
		}

		p = p[n:] // 即使同时有 err，也先确认这 n 字节已被接受

		if err != nil {
			return err // 剩余字节未能由本次调用确认接受
		}
		if n == 0 {
			return io.ErrShortWrite // 否则 p 不变，循环永远无进展
		}
	}
	return nil
}
```

设原始数据为 8 B。第一次返回 `n=3, err=nil` 时，下一次必须写剩余 5 B，而不是重写全部 8 B；重写会在某些实现或协议层造成重复字节，破坏帧边界。标准 `io.Writer` 合同规定：若 `len(p)>0` 且发生短写，应返回非空错误；因此 `n< len(p), err=nil` 属于不合规实现。但通用封装不能据此无限循环，仍应把“零进展”转成失败。

若第二次对剩余 5 B 返回网络错误，调用方最多确认前 3 B 曾被本端 `Writer` 接受；这不是“8 B 帧已到达远端”，更不是“服务端业务已受理”。即使请求曾写全，响应丢失后结果仍是未知，不能仅凭写入字节数或重试得到的 `409` 推导 exactly-once；必须依赖请求标识、查询或业务确认协议判定。

### 八字节发送的部分结果

### 八字节发送的部分结果

设应用要发送一个恰好 8 B 的帧：

```text
[类型 1 B][长度 1 B][载荷 6 B]
```

调用方第一次执行 `Write(p)`，得到：

```text
n = 3, err = nil
```

这只表示当前 `Writer` 报告已接受前 3 B；待发送数据必须推进为 `p = p[3:]`。虽然标准 `io.Writer` 约定“短写应返回非空错误”，这里的 `err == nil` 仍是防御性封装必须处理的异常组合：不能把它当作“8 B 已发送”，更不能原地重试整个帧。

第二次写剩余 5 B 时：

```text
n = 0, err = 网络错误
```

此时调用方能确认的最强事实仅为：本端曾接受 3 B，随后报告失败。远端可能只看到这 3 B，因帧不完整而等待更多字节；也可能在连接关闭、缓冲转发或实现细节作用下看到了更多数据。仅凭本次调用结果，无法确定远端可见的精确字节数，更无法断言远端已解析出完整帧。

稳健循环按 `n` 推进、遇错误立即停止，并防止 `n == 0 && err == nil` 导致无进展循环：

```text
for len(p) > 0:
    n, err = Write(p)
    p = p[n:]
    if err != nil: 停止
    if n == 0: 视为短写失败，停止
```

即使最终累计写满 8 B，也只说明本端 `Writer` 已接受全部字节；完整帧是否到达、是否被解析，仍需协议确认。

### 短写合同与防御性封装

### 短写合同与防御性封装

`io.Writer` 的合同是：`Write(p)` 返回本次已接受的字节数 `n`；若 `n < len(p)`，则应同时返回非空错误。标准库用 `io.ErrShortWrite` 表示“未报告原因的短写”。因此，正常的调用方不能把 `err == nil` 直接翻译为“整个 `p` 已写完”，而应同时检查 `n`。

| 返回结果 | 合同含义 | 调用方动作 |
|---|---|---|
| `n == len(p), err == nil` | 本端 Writer 接受全部字节 | 本次写入完成 |
| `0 < n < len(p), err != nil` | 已接受前缀，后续失败 | 停止；仅将 `p[:n]` 视为已交给 Writer |
| `n == 0, err != nil` | 未接受字节即失败 | 停止并处理错误 |
| `n < len(p), err == nil` | 违反 Writer 合同或非规范实现 | 防御性报短写，避免误判或死循环 |

封装“写满”逻辑时，应按 `n` 推进切片，并对无进展显式失败：

```go
func writeAll(w io.Writer, p []byte) error {
	for len(p) > 0 {
		n, err := w.Write(p)
		if n > 0 {
			p = p[n:]
		}
		if err != nil {
			return err
		}
		if n == 0 {
			return io.ErrShortWrite
		}
	}
	return nil
}
```

这里的“写满”仍只表示所有字节被**本端 Writer**接受，不表示远端已收到完整帧、已解析请求，更不表示业务已受理。短写后的重试尤其不能仅依据已写字节数推断业务结果；网络中断可能留下“远端已处理、响应丢失”的未知状态，必须依赖协议确认、幂等键或业务查询处理。

### 写全之后仍是未知业务结果

### 写全之后仍是未知业务结果

在连接 S2 发送消息时，`Write` 写满请求只说明：本端的 `Writer` 已接受全部请求字节。即使这些字节随后进入内核发送缓冲区，也不能推出远端服务已经完整收到帧、成功解析请求，或已经执行业务操作。

更棘手的是响应丢失：

1. 客户端写全 HTTP 请求；
2. 服务端可能已经创建消息、扣减额度或提交事务；
3. 服务端响应在网络中丢失，或客户端在读取响应前断开；
4. 客户端只看到超时、连接关闭或读取失败。

此时结果是**未知**，而不是“请求失败”。不能因为本端没有拿到成功响应，就用同一个消息 ID 直接重试，并断言第一次没有生效。

同 ID 重试返回 `409` 也不天然表示幂等成功。`409` 至少可能表示：

- 该 ID 已被先前请求成功占用；
- 该 ID 已被不同正文占用，存在冲突；
- 服务端检测到重复，但无法证明原操作已完成；
- 当前请求违反状态约束，与幂等去重无关。

因此，网络层只能报告“写入了多少字节”与“是否拿到响应”；业务层还需要确认协议：例如按消息 ID 查询最终状态、由服务端返回可验证的操作结果，或使用明确的幂等键与请求摘要校验。只有获得业务确认，才能把“可能已受理”的未知结果收敛为成功、失败或可安全重试。

> **要点** — Write 只报告本端接受的字节；短写须按 n 续写，业务是否受理必须依赖帧后确认与未知结果处理。

连接建立后的读写控制，不能依赖拨号时的 context。理解 deadline 的绝对时间语义，才能避免复用连接上的“遗留超时”。

### Deadline 是连接状态，不是单次调用参数

### Deadline 是连接状态，不是单次调用参数

`net.Conn` 的 deadline 记录在**连接对象**上，而不是作为某一次 `Read` 或 `Write` 的临时参数。调用：

```go
conn.SetReadDeadline(time.Now().Add(2 * time.Second))
conn.SetWriteDeadline(time.Now().Add(2 * time.Second))
```

设置的是绝对截止时刻：到达该时刻后，正在阻塞的对应 I/O 会返回超时错误；此后发起的相关 I/O 也仍受这个截止时刻约束。若截止时刻已经过去，下一次读或写可能立即超时。

因此，deadline 很适合表达“这一步最多还能使用到什么时间”，却不能误解为“本次调用自动拥有两秒”。长期复用连接时，上一条消息留下的 deadline 会污染下一条消息：

1. 请求 A 设置了很短的读截止时间；
2. A 结束后没有更新或清除；
3. 请求 B 复用同一连接；
4. B 的 `Read` 因旧截止时间已过而立刻失败。

每次逻辑操作都应按自己的时间预算重新设置。例如，在发请求前设置写 deadline，在等响应前设置读 deadline；操作完成后，若后续阶段不应继承限制，可用零值取消：

```go
conn.SetReadDeadline(time.Time{})  // 清除读 deadline
conn.SetWriteDeadline(time.Time{}) // 清除写 deadline
```

读、写 deadline 相互独立；设置读 deadline 不会限制写，反之亦然。`SetDeadline(t)` 则同时设置两者。

超时错误只表示：本次 I/O 未能于本地规定的时间点前完成。它**不能**证明对端没有收到数据、没有执行请求，或没有产生业务副作用。特别是写入超时时，部分字节可能已经发出；协议设计必须依靠请求标识、幂等性或确认机制处理这种不确定性。

### 按消息预算刷新截止时间

### 按消息预算刷新截止时间

`net.Conn` 的 deadline 是连接级、绝对时间点的状态，不是“本次调用等待多久”的局部参数。设定

$$
d=\text{Now()}+\text{本次操作预算}
$$

后，所有相关的当前及后续 `Read` 或 `Write` 都受该时间点约束，直到再次设置 deadline，或以零值 `time.Time{}` 清除它。

因此，长期复用连接时应把一次消息交互看成独立预算单元：

1. 发送请求前，设置本次写截止时间；
2. 写完后，按协议需要设置读截止时间；
3. 收到完整响应后，清除 deadline，或为下一条消息重新设置；
4. 任一步超时、协议解析失败或连接状态不确定时，通常丢弃该连接。

例如，不能只在建连后设置一次五秒 deadline：

```go
conn.SetDeadline(time.Now().Add(5 * time.Second))
// ... 第一条消息耗时 4.9 秒才完成
// 第二条消息的读写几乎会立刻超时
```

更合理的写法是让每条消息拥有自己的预算：

`SetWriteDeadline(now + 写预算)` → 完整写入帧 → `SetReadDeadline(now + 读预算)` → 读完整帧。

若请求与响应之间存在较长的本地计算，旧截止时间仍会继续流逝；下一次 I/O 可能一进入内核就返回超时。故“操作完成后清零”适合把连接交还给通用连接池；“下一操作前覆盖设置”适合由单一会话循环独占连接。核心不是选择哪种风格，而是不得让上一条消息的时间预算隐式支配下一条消息。

### 旧截止时间如何制造立即超时

### 旧截止时间如何制造立即超时

设想一个复用的 IM 连接，协议为“`4` 字节大端长度 + 消息体”。第一条消息到来前，客户端只愿等待 `200ms`：

```go
_ = conn.SetReadDeadline(time.Now().Add(200 * time.Millisecond))

var n uint32
if err := binary.Read(conn, binary.BigEndian, &n); err != nil {
    return err
}
body := make([]byte, n)
if _, err := io.ReadFull(conn, body); err != nil {
    return err
}
```

第一条消息恰好在 `100ms` 内读完，代码继续处理业务，却没有清除或更新 deadline。注意：deadline 是连接上的**绝对时刻**，不是“本次 `ReadFull` 自动消耗掉的 200ms”。

当程序准备读取第二条帧时，最初设定的时刻已经过去：

```go
// 此处仍保留第一条消息设置的旧截止时间
if err := binary.Read(conn, binary.BigEndian, &n); err != nil {
    // 常见为 net.Error，Timeout() == true
    return err
}
```

即使第二条消息已经在对端缓冲区中，或即将到达，本次读也可能立刻返回超时；因为连接当前的读 deadline 已经过期。写入同理：第一条发送设置的 `SetWriteDeadline` 若未更新，下一次 `Write` 可能尚未写出一个字节就失败。

长期复用时，应让每条操作声明自己的预算：

```go
_ = conn.SetReadDeadline(time.Now().Add(readBudget))
_, err := io.ReadFull(conn, body)
_ = conn.SetReadDeadline(time.Time{}) // 不再需要时取消
```

超时只表示这次读写没有在预算内完成；若写入发生超时，不能据此断言对端没有收到任何字节，更不能断言对端业务未执行。

### 拨号取消与已连接读写取消

### 拨号取消与已连接读写取消

`net.Dialer.DialContext(ctx, ...)` 中的 `ctx` 管的是“连接能否建立”：例如 DNS 解析、等待 TCP 握手、代理协商等。`ctx` 到期或被取消时，拨号应尽快返回；一旦成功得到 `net.Conn`，该 `ctx` 的职责通常已经结束。

```go
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()

conn, err := (&net.Dialer{}).DialContext(ctx, "tcp", addr)
// 成功后，即使 ctx 随后超时，conn.Read 也不会因此自动返回。
```

这是常见误解：`context.Context` 不是自动附着在连接全部后续字节读写上的取消标签。若已连接的 `conn.Read` 正在阻塞，需选择明确的中断手段：

- **deadline**：为本次读或写设定绝对截止点。`SetReadDeadline(t)` 到时会使阻塞读取返回超时错误；下一次读取仍受该 deadline 影响，除非更新或用零时间清除。
- **`Close`**：关闭连接通常会唤醒本地阻塞的读写，但这意味着连接一般不能再复用；它只表示本地停止使用，不证明远端业务未执行或未完成。
- **协议自身机制**：TLS、WebSocket、HTTP/2 等可能有关闭帧、取消流或半关闭语义，应优先遵循对应协议与库的约定。

长期复用连接时，应把操作预算落实到每次 I/O：

```go
conn.SetReadDeadline(time.Now().Add(2 * time.Second))
n, err := conn.Read(buf)
```

读超时仅说明“在两秒预算内没有完成这次读取”。它不能证明对端没有收到请求、更没有证明对端没有开始执行业务。因此，写入或请求超时后的重试必须结合幂等键、请求编号或协议确认设计，而不能仅凭超时错误断言“操作没有发生”。

### 超时、关闭与业务确认边界

### 超时、关闭与业务确认边界

`Read` 或 `Write` 超时，只能说明本次 I/O 没有在预算内完成；`Close` 只说明本地不再使用该连接。二者都不能推出“对端没有收到请求”或“对端没有执行业务”。

典型的不确定窗口是：

1. 客户端已写出全部或部分请求字节；
2. 服务端收齐帧、写入内存队列，甚至已驱动设备；
3. 回包尚未到达客户端；
4. 客户端读超时、取消或关闭连接。

此时若直接重试，可能造成重复扣款、重复下发、重复创建。因此，应用协议应把“传输结果”和“业务确认”分开设计。

- **S2 内存受理确认**：服务端返回“已校验并进入内存队列”。它证明请求已被当前进程接受，但不等于已持久化，更不等于设备完成。
- **设备确认**：设备实际执行后，以业务状态、回执或查询结果确认。客户端超时后应优先按请求 ID 查询，而不是盲目重发。
- **幂等键**：每个可重试命令携带稳定的 `request_id`；服务端保存处理结果或至少保存去重状态，使重复请求返回同一业务结论。

连接资源归属也必须明确：创建者通常负责 `Close`；发生协议错误、写入结果不确定、读到截断帧时，连接通常应丢弃而非复用。复用前还要重新设置本次操作的 deadline，不能继承上一请求的过期时间。

对 TLS、WebSocket 等协议，关闭还应遵循各自的关闭握手语义；本地关闭 TCP 连接并不能替代业务层确认。可靠策略不是把超时当作“失败证明”，而是把它视为“结果未知”，再借助幂等、查询与明确状态机收敛结果。

> **要点** — deadline 是会遗留的绝对连接状态；每条消息应自带预算。超时或关闭只说明本地 I/O 结果，不能替代业务确认。

长连接节省建连成本，却把帧边界、排队、失效与关闭责任变成必须明确的协议合同。

### 复用连接不等于复用协议状态

### 复用连接不等于复用协议状态

一条 TCP 连接可继续使用，只说明其传输层可能仍可读写；并不说明下一个请求可以继承上一个请求的任何应用状态。连接池复用的是“字节通道及其已完成的建连成本”，不是某次业务操作的上下文。

可复用前至少要满足：

- 上一帧请求与响应均已完整消费，读取缓冲区没有残留字节；
- 协议没有进入关闭、升级、半关闭或错误后的不可恢复状态；
- 连接未超过空闲期限、生命周期或服务端声明的失效条件；
- 此连接仍属于相同的池分组，例如目标地址、代理配置、TLS/SNI、协议版本等一致；
- 当前调用者能够接受该连接上已协商的传输属性。

尤其不要把应用状态偷偷绑到池中连接上。例如 `message_id` 必须为本次消息重新分配；认证令牌、租户、用户身份、追踪上下文和权限判断必须按请求重新注入与校验。即使服务端支持“登录后会话”，也应明确会话是否与连接绑定；若绑定，则池的键必须包含会话身份，或禁止跨身份复用。

一个常见错误是：请求 A 超时后将连接归还池，但其响应可能仍在路上。请求 B 取到该连接后，会把 A 的残余响应误当作自己的响应。此时连接已失去帧同步，应关闭而非复用。原则是：**只有协议边界明确、状态已知且输入已排空的连接，才可归还连接池。**

连接池也不能替应用承担取消语义。调用者取消某个请求时，要按协议决定是丢弃该请求的结果、发送取消帧，还是直接废弃连接；不能仅因本地 `context` 已取消，就假定对端从未执行该操作。

### 帧级串行化防止写入交错

### 帧级串行化防止写入交错

`net.Conn` 允许多个 goroutine 并发调用 `Read`、`Write`、`Close` 等方法，这解决的是连接对象的并发安全，不等于应用协议自动获得“消息原子性”。

例如协议帧为：

`长度头（4 字节） + 载荷`

两个 goroutine 分别发送 `A`、`B`，若各自分两次写入：

```text
G1: Write(A头) → Write(A载荷)
G2: Write(B头) → Write(B载荷)
```

实际字节流可能变成：

```text
A头 | B头 | A载荷 | B载荷
```

接收端按 `A头` 读取其声明长度时，随后读到的却可能是 `B头` 和部分 `A载荷`；帧边界一旦错位，后续数据通常都无法再可靠解析。即使单次 `Write` 常常看似连续，也不能把这种经验当作协议保证；写入还可能短写，必须处理返回的已写字节数。

因此，并发发送应把“完整帧”作为串行化单位，而不是分别保护头和载荷：

- **单写者 goroutine**：其他组件把待发送消息投入有界队列，只有写者编码并完整写出帧。
- **帧级互斥锁**：持锁完成“编码头 + 写全头 + 写全载荷”，再释放锁；不可只锁每次 `Write`。
- **预组装帧**：将头和载荷合并为一个字节序列后执行 `writeFull`，但若存在多个写者，仍应通过锁或队列保证整帧不交错。

队列还必须有容量、超时或取消策略。否则慢连接使写者阻塞时，生产者会无限堆积消息；关闭连接时，也要明确谁停止入队、谁关闭队列、谁唤醒等待中的发送者。

### 有界连接池与等待策略

### 有界连接池与等待策略

连接池的目标不是“尽可能复用”，而是在复用、并发和资源上限之间建立可预测的边界。至少应区分：

- **总连接上限**：正在使用、空闲、建立中的连接总数均计入，防止突发请求同时建连耗尽文件描述符、端口或服务端配额。
- **每个目标的上限**：不同主机、代理、TLS 配置或租户通常不能混用连接；一个慢目标不应占满全局池。
- **空闲上限与空闲期限**：空闲连接过多会占用本地资源，也可能已被对端、负载均衡器或防火墙静默回收。复用前仍应能处理“看似空闲、实际失效”的错误。
- **连接寿命上限**：即使持续繁忙，也可定期淘汰连接，避免长期绑定到过期的 DNS、证书、代理路径或异常对端状态。

池满时，请求不应无限排队。等待队列本身会积累请求对象、载荷和 goroutine；若下游设备慢，内存压力会从网络延迟扩散为整个进程的拥塞。应为“获取连接”设置独立的等待上限，并服从调用方 `context`：

`获取连接超时` 不等于 `单次读写超时`，更不等于 `整个业务请求截止时间`。

典型策略是：池有空闲连接则借出；未达上限则建立新连接；达到上限则最多等待到 `context` 取消或获取期限到期，随后返回可识别的拥塞错误，由上层限流、降级或重试。重试必须有次数和总时间预算；否则超时后的重试会再次压满池。

归还连接前还要判断其是否可复用：协议帧是否完整、是否发生取消或读写错误、是否收到关闭语义、是否仍有未消费的数据。无法确认协议状态时，宁可关闭而不要放回池中；“污染连接”的错误复用通常比一次重连更难排查。

### 失效识别、期限与重连边界

### 失效识别、期限与重连边界

连接“仍然存在”不等于“仍然可用”。应用应把连接淘汰条件写成明确规则，而非依赖一次 `Write` 成功或 TCP 未报错。

- **读期限识别沉默连接**：对一次请求设置读取期限；超过协议允许的响应时间，应将该连接视为不可复用。`net.Conn.SetReadDeadline` 影响后续及正在阻塞的读；若要继续使用，必须显式重置期限。
- **写期限限制背压**：`SetWriteDeadline` 防止对端不读、代理阻塞或内核缓冲耗尽时永久卡住。写超时后，当前帧是否已被对端部分收到通常未知；不要盲目在同一连接重发非幂等请求。
- **EOF 与协议错误通常淘汰**：`io.EOF` 表示对端已关闭写方向；若协议要求持续双向通信，连接应退出池。帧长度非法、认证失败、TLS 解密错误、响应与请求不匹配等协议错误，也应关闭而非“跳过这条消息继续复用”。
- **取消不必然终止底层读写**：`context.Context` 的取消只在调用链主动检查它时生效。直接阻塞在 `Conn.Read` 上时，常需由拥有者设置更早的 deadline，或关闭连接来唤醒阻塞操作。关闭是一种强取消，因此必须确认没有其他请求仍共享该连接。
- **代理、TLS 与身份变化应重建**：代理地址、TLS 服务器名、根证书、客户端证书、会话身份或权限上下文变化时，旧连接的安全与路由前提可能已失效。连接池键应包含这些影响复用语义的维度。

重连也应有边界：仅在连接尚未写入应用帧、请求可安全重试，或协议具有 `message_id` 去重保证时重试；采用带抖动的退避、最大次数和总 deadline。池中连接关闭后应从池摘除，等待者得到失败或新建机会，不能把一个永久失效的连接反复归还给后续请求。

### 关闭责任与读写组件协作

### 关闭责任与读写组件协作

连接交给多个组件时，最危险的问题通常不是“谁能读写”，而是“谁有权关闭、关闭意味着什么”。应先选定一种所有权模型，并把在途操作与关闭后行为写入接口合同。

| 模式 | 优点 | 主要风险 | 适用方式 |
|---|---|---|---|
| 单组件持有连接 | 状态、读写、重连和关闭集中；最易保证帧级串行化 | 组件职责较重，调用方需经由其接口通信 | 协议复杂、需要会话状态或自动重连时 |
| 读写组件分离 | 读循环可专注解帧，写循环可专注排队与背压 | 双方都可能关闭、重连或继续使用旧连接 | 高并发消息分发、明确有连接管理者时 |

读写分离并不意味着读组件和写组件各自拥有连接。更稳妥的结构是：**连接管理者拥有 `net.Conn` 的关闭权**；读循环、写循环只持有受控使用权。管理者负责创建连接、启动循环、广播失效、等待退出，以及最终调用 `Close`。

关闭规则应明确：

- `Close` 是幂等的：多次请求关闭只产生一次实际关闭动作。
- 关闭开始后，停止接收新的写请求；已进入写队列的消息要么在规定期限内发送，要么以“连接关闭”失败，不能无限等待。
- 读循环收到 EOF、协议错误或期限超时，应报告“连接失效”；它可以触发关闭请求，但不应自行偷偷替换连接。
- 写入失败时，不能假定对端完全没有收到数据。对有副作用的请求，应依靠 `message_id`、确认机制或幂等语义决定是否重试。
- 调用方在关闭后继续使用连接，应立即得到确定错误，而不是复活旧队列或向已失效连接写入。

TCP 的半关闭也需单独约定。`CloseWrite` 表示“本端不再发送”，并不表示不能继续读取对端剩余数据；`CloseRead` 则可能使对端写入失败。若协议没有定义半关闭语义，通常只暴露完整关闭，避免一个组件半关闭、另一个组件仍期待双向会话。

取消应从请求上下文传播到排队、读写和等待响应处；但取消某个请求不必关闭共享连接。只有连接级故障、显式停机或管理策略判定失效时，才由拥有者关闭整条连接。

> **要点** — 连接池管理的是有限且可能失效的传输资源；应用帧、状态、排队和关闭责任必须另行明确。

以 A 向 B 发送“公告”为线索，按名称、连接、安全、帧、时间与业务层定位故障，避免用一种“重试”掩盖所有问题。

### 一次发送跨越的层次与错误归属

### 一次发送跨越的层次与错误归属

A 向 B 发送“公告”并不是一次单一操作，而是一条分层路径：

`名称 → 地址 → TCP 连接 → TLS 安全握手 → 帧/HTTP 请求 → 业务校验 → 响应语义`

每一层的失败含义、可否重试、应记录的信息都不同。

- **名称层**：DNS 查不到 B 的域名，说明名称无法解析为地址；此时尚未建立连接。应检查域名、解析器、缓存和网络配置，而不是把它当作 B 拒收消息。
- **连接层**：TCP `connection refused` 表示已到达目标地址，但对应端口没有接受连接；可能是服务未启动、防火墙规则或地址/端口配置错误。
- **安全层**：TLS 名称校验失败，说明连接可能已建立，但服务端证书不能证明“它就是所访问的名称”。不能通过跳过证书校验来“重试成功”。
- **帧层**：长度头只读到 `1 B`、载荷只读到 `4/6 B`，属于短读或连接中断。`Read` 不保证填满缓冲区；教学协议可将提前 `EOF` 视为截断帧，但真实 HTTP、WebSocket 应按各自协议错误和关闭码解释。
- **时间层**：deadline 到期表示某阶段未在预算时间内完成。它可能发生在解析、握手、读取或写入，必须记录具体阶段。
- **请求与业务层**：HTTP body 超限通常是请求格式/资源限制；非成员 `404` 是可见性或资源语义；重复消息 ID 的 `409` 表示冲突；`200` 若仅表示“已内存受理”，则不等于已持久化、更不等于 B 已阅读。

因此，日志至少关联请求 ID、连接生命周期、各阶段耗时、已读/已写字节和错误类别；正文等私有内容不应直接写入无保护日志。

### TCP字节流与六字节长度帧

### TCP 字节流与六字节长度帧

A 向 B 发送正文 `公告`。若约定应用帧格式为：

`[4 字节大端长度][正文载荷]`

UTF-8 中，`公` 编码为 `E5 85 AC`，`告` 编码为 `E5 91 8A`，因此正文不是 2 B，而是 6 B：

`公告 = E5 85 AC E5 91 8A`

长度头应写入十进制 `6`，以 4 字节大端表示：

`00 00 00 06 E5 85 AC E5 91 8A`

发送端一次调用 `Write` 并不意味着接收端一次 `Read` 就得到这 10 B。TCP 提供的是**有序、可靠的字节流**，不保留应用消息边界；网络分段、缓冲、调度都可能导致不同拆分。例如接收端可能依次读到：

1. `00`：长度头仅 1 B，尚不能解析长度；
2. `00 00 06`：补齐其余 3 B，得到载荷长度 6；
3. `E5 85 AC E5`：载荷已读 4/6 B；
4. `91 8A`：补齐载荷，才得到完整正文 `公告`。

因此，不能把“本次 `Read` 返回的数据”直接当作一条完整公告。接收方应先循环读取恰好 4 B 的长度头，再按该长度循环读取完整载荷；实现中可使用 `io.ReadFull`。若读取长度头或载荷时提前出现 `EOF`，在这个教学帧协议里表示对端关闭导致帧不完整，应丢弃该半帧，而不是把已有字节当成完整消息。

长度还必须受上限约束，例如最大 `64 KiB`。否则恶意长度头如 `FF FF FF FF` 可能诱导程序分配异常大的内存。帧边界来自这里定义的“4 字节长度 + 载荷”协议，而不是来自 TCP、一次 `Write`、一次 `Read` 或某个数据包边界。

### 短读、短写与限长读取

### 短读、短写与限长读取

A 给 B 发送“公告”时，应用层常把消息编码为：

`[4 字节长度头][载荷]`

但 TCP 提供的是**字节流**，不是“消息包”。一次 `Read` 只保证“读到一些字节或返回错误”，不保证读满缓冲区。因此，长度头需要 4 B，第一次却可能只得到 1 B；已知公告载荷长 6 B，后续也可能先读到 4 B。它们不表示协议损坏，只表示本次读取尚未完整。

应使用 `io.ReadFull` 明确要求读满指定字节数：

```go
var head [4]byte
if _, err := io.ReadFull(conn, head[:]); err != nil {
    // EOF：尚未读到任何长度头；UnexpectedEOF：长度头只到了一部分
    return err
}

n := binary.BigEndian.Uint32(head[:])
if n > maxAnnouncementSize {
    return fmt.Errorf("公告过大：%d", n)
}

body := make([]byte, n)
if _, err := io.ReadFull(conn, body); err != nil {
    // 例如应读 6 B，实际只到 4 B 后连接关闭
    return err
}
```

关键顺序是：**先读满长度头，再检查上限，最后分配并读满载荷**。绝不能直接相信对端声明的长度后 `make([]byte, n)`；恶意或异常对端可给出极大长度，造成内存耗尽。`maxAnnouncementSize` 应是协议和业务共同规定的硬限制。

写入也可能短写。`Write` 返回 `n < len(p)` 且 `err == nil` 在接口语义上是允许的；对普通 `net.Conn` 虽较少见，通用发送代码仍应循环补齐：

```go
for len(p) > 0 {
    n, err := conn.Write(p)
    if n > 0 { p = p[n:] }
    if err != nil { return err }
    if n == 0 { return io.ErrShortWrite }
}
```

不要把“读到 4/6 B”立即当作可重试的业务失败：若已向对端写出完整请求，连接中断时无法确定 B 是否已经受理。短读、短写首先是帧与连接生命周期问题；是否重试还需结合请求 ID 与服务端幂等语义判断。

### 连接建立、期限与取消边界

### 连接建立、期限与取消边界

A 向 B 发送“公告”前，失败可能已发生在不同阶段；应按阶段分类，而非统一重试。

| 现象 | 所在阶段 | 含义 | 合理处置 |
|---|---|---|---|
| DNS 查不到 | 名称解析 | 域名无记录、解析器不可用或网络不可达 | 检查名称、解析配置与缓存；可有限重试 |
| TCP 连接拒绝 | 连接建立 | 地址可达，但目标端口没有监听或被主动拒绝 | 检查服务监听、端口和防火墙；不要立即高频重试 |
| TLS 名称校验失败 | 安全握手 | 已连到某服务器，但证书身份不匹配目标名称 | 修正域名、证书 SAN 或 SNI；通常不可通过重试恢复 |

`DialContext` 只约束“解析、选路、拨号并建立连接”这段过程。其 `context` 被取消或超时后，拨号应停止；但一旦 `DialContext` 已成功返回 `net.Conn`，后续读写不会自动继承该取消信号。

因此，连接成功后需分别设置读写期限：

```go
conn.SetReadDeadline(time.Now().Add(3 * time.Second))
conn.SetWriteDeadline(time.Now().Add(3 * time.Second))
```

读期限到期会中断阻塞读取，写期限到期会中断阻塞写入；它们是连接级状态，若不更新，之后操作仍可能继续超时。若业务取消意味着“无论当前卡在读还是写都必须停止”，最可靠的边界通常是关闭连接：`conn.Close()` 会使并发中的阻塞 I/O 返回错误。

注意：关闭连接只能中断本地 I/O，不能撤销对端已经收到的公告。若写入中断，发送方往往无法判断对端是否已收到完整请求；此时重试必须依赖请求 ID 和服务端去重，而不能仅根据本地错误决定“未发送成功”。

### 请求结果、重试与连接复用纪律

### 请求结果、重试与连接复用纪律

A 向 B 提交“公告”时，HTTP 状态码只是传输后的业务结果，不应被简化为“非 200 就重试”。

- `413` 或正文超限：请求在解析或读取阶段被拒绝。应缩小正文、改为分块上传或调整明确的配额；原样重试只会再次耗尽带宽与连接。
- `404` 非成员：A 无权向该目标投递，或目标不存在。为避免枚举成员关系，服务端可对“不存在”和“无权限”返回相同的外部语义；客户端不应自动重试。
- `409` 重复公告 ID：这是幂等键已存在的正常业务冲突。客户端应查询该 ID 的既有结果，确认是否已被受理，而不是生成新 ID 后重复发送。
- `200` 仅内存受理：只能证明服务器进程当前接受了请求，不能证明公告已持久化、已投递或 B 已看到。响应应标明确认边界，例如 `accepted-memory`、`persisted`、`delivered`。

重试必须绑定幂等语义。为每次逻辑发送生成稳定的 `request_id` 或 `Idempotency-Key`：网络超时、连接中断等“结果未知”时，可带同一键有限次数重试；明确的参数错误、权限错误、正文超限则不重试。若系统要求可靠确认，至少区分：

`S1：服务接收` → `S2：持久化/可恢复写入` → `S3：B 已投递或已读`

只有跨过承诺边界的 `S2`，才适合作为“可在故障后恢复”的成功确认。

连接复用时，同一连接上的 HTTP 请求必须遵守协议的帧边界与并发规则。HTTP/1.1 中应完整读取或主动关闭响应正文后再复用连接；未消费的正文会让后续响应边界错位。自定义 TCP 教学帧则应对单连接读写串行化，避免两个 goroutine 交错写入“长度头 + 载荷”。

观测记录 `request_id`、幂等键、状态码、确认级别、重试次数、连接是否复用及读写字节数；正文、令牌和成员关系属于敏感信息，不应直接写入无保护日志。

> **要点** — 先判定故障层次，再按帧、期限和业务确认边界处理；重试必须以幂等性与已完成阶段为依据。

本节以虚构 IM 的六字节正文为线索，建立从 TCP 字节流、长度帧到取消、确认与连接复用的完整读写边界。

### TCP 字节流与二字节长度帧

### TCP 字节流与二字节长度帧

TCP 提供的是**有序连续字节流**，不保留应用消息边界：一次 `Write` 可能被拆成多次 `Read`，多次 `Write` 也可能在一次 `Read` 中合并。因此，不能把“读到一次数据”当作“收到一条消息”，必须由应用协议自行分帧。

一种简单格式是：

`[2 B 正文长度][正文]`

长度头约定为无符号 16 位**大端序**（网络字节序）。例如虚构 IM 正文为六个字节：

`68 65 6c 6c 6f 21`，即 UTF-8 文本 `hello!`

则帧为：

`00 06 68 65 6c 6c 6f 21`

其中 `00 06` 表示长度：

$0\times256+6=6$

若收到头 `01 2c`，长度为：

$1\times256+44=300$

理论范围是 `0` 到 `65535`；实际协议应另设上限，例如仅允许 `1` 到 `4096` 字节。读取长度头后，必须先检查长度是否在允许范围内，再分配正文缓冲区；坏长度应立即拒绝，不能按对端声明分配巨量内存。若正文要求是文本，还应在收齐后用 UTF-8 检查确认其合法性。

读取时应使用“读满”语义：头不足 2 字节即连接结束，属于 `EOF` 或 `ErrUnexpectedEOF`；已知正文长度却只收到部分正文，同样是截断帧。写入也可能短写，必须循环写完全部头和正文，或把未写完视为失败。帧格式只适用于本协议的裸 TCP 字节流；不能把既有 WebSocket 帧误解为自定义的 `2 B` 长度前缀。

### 安全读帧：限长、完整读取与文本校验

### 安全读帧：限长、完整读取与文本校验

TCP 只提供连续字节流，不保留“发送一次就是一条消息”的边界。假设协议规定：前 `2 B` 是无符号大端长度，随后是 UTF-8 正文。六字节正文 `你好` 的长度应是 `6`，帧形如：

`00 06 e4 bd a0 e5 a5 bd`

读取必须分两步进行，而不能一次 `Read` 后假定拿到了完整消息：

1. 用 `io.ReadFull` 读取恰好 `2 B` 头部。
2. 以大端解析长度；在分配正文缓冲区**之前**检查范围。
3. 为合法长度分配缓冲区，再用 `io.ReadFull` 读满正文。
4. 若协议要求文本，使用 `utf8.Valid` 检查正文，拒绝非法编码。

```go
func readTextFrame(r io.Reader, maxBody int) (string, error) {
	var head [2]byte
	if _, err := io.ReadFull(r, head[:]); err != nil {
		return "", err
	}

	n := int(binary.BigEndian.Uint16(head[:]))
	if n == 0 || n > maxBody {
		return "", fmt.Errorf("非法正文长度: %d", n)
	}

	body := make([]byte, n)
	if _, err := io.ReadFull(r, body); err != nil {
		return "", err
	}
	if !utf8.Valid(body) {
		return "", errors.New("正文不是合法 UTF-8")
	}
	return string(body), nil
}
```

长度上限既是协议约束，也是资源边界。例如正文最多 `4096 B`，则应拒绝 `0`、超过上限及其他保留长度；不能先按对端声明的长度分配，再判断是否过大。尽管 `2 B` 的理论最大值是 `65535`，应用仍应采用更小、明确的业务上限。

`io.ReadFull` 的错误有边界含义：读取头部前立即遇到 `EOF`，表示对端在下一帧开始前关闭；已读到部分头部或部分正文后连接结束，通常得到 `io.ErrUnexpectedEOF`，表示帧被截断。二者都不能把已读取的残片交给业务层，更不能猜测缺失字节。读取期间若期限到达、上下文取消或连接被关闭，也应将当前帧视为未完成并丢弃。

### 可靠写帧：短写、期限与关闭所有权

### 可靠写帧：短写、期限与关闭所有权

`net.Conn.Write` 并不承诺一次写完全部字节。即使底层是 TCP，调用仍可能返回：

- `n == len(p), err == nil`：本次调用已把全部数据交给本机网络栈；
- `0 < n < len(p), err != nil`：前 `n` 字节可能已发出，剩余部分失败；
- `0 < n < len(p), err == nil`：不应默认其余字节会自动发送，应继续写完；
- `n == 0, err != nil`：本次没有可确认写入的字节。

因此，长度帧必须用“写满”循环，而不是一次 `Write`：

```go
func writeFull(c net.Conn, p []byte) error {
	for len(p) > 0 {
		n, err := c.Write(p)
		p = p[n:]
		if err != nil {
			return err
		}
		if n == 0 {
			return io.ErrShortWrite
		}
	}
	return nil
}
```

帧头和正文最好作为一个连续缓冲区写出，或在同一把写锁内依次写出；否则两个 goroutine 的“头—正文”可能交叉，接收端便无法恢复边界。连接上的写帧应串行化，例如用 `sync.Mutex` 或单独写 goroutine。

`DialContext` 的取消只约束“建立连接”阶段：DNS、握手或拨号超时后返回。连接一旦建立，原 `context.Context` 不会自动中断后续 `Read`/`Write`。建连后的 I/O 应设置读写 deadline；若业务取消需要立即打断阻塞操作，通常由拥有该连接关闭权的一方执行 `Close`，使等待中的读写返回错误。

关闭权必须明确：连接池或会话管理器拥有连接时，单个请求取消不能随意关闭共享连接，否则会误伤其他请求；独占连接则可由请求生命周期负责关闭。发生写入超时或部分写入后，该帧是否完整到达对端通常未知，连接不宜继续复用，应关闭并由上层记录“未知”，不能把本地 `Write` 成功误当成业务确认。

### 并发复用与双重容量门

### 并发复用与双重容量门

TCP 连接是连续字节流，不是“消息队列”。多个 goroutine 同时向同一连接 `Write`，即使每次调用看似发送一整帧，也可能在字节层面交错，破坏 `2 B 长度头 + 正文` 的边界。因此，一条连接的帧写入必须串行化：

- 简单做法：以 `sync.Mutex` 覆盖“编码完整帧到处理短写”的整个过程。
- 更适合高并发的做法：每连接一个写协程，业务方将完整帧投递到有界发送队列；队列满时返回背压错误，而非无限堆积内存。
- 关闭连接、设置写期限与写协程退出必须协调所有权；不要一边关闭、一边让未知数量的 goroutine 继续写。

连接池也需要上限：限制总连接数、每目标地址连接数、空闲连接数与空闲存活时间。池满时应排队、拒绝或复用空闲连接，不能因突发请求无界新建连接。复用前还需确认该协议允许复用，且上一次请求没有遗留未读字节。

HTTP 层与应用帧层应设置**独立容量门**。例如 HTTP 原始请求体最多 `4096 B`，用于限制传输与解析成本；HTTP body 中承载的聊天帧，其正文仍最多 `6 B`，由帧的 `2 B` 长度头检查：

```text
HTTP 原始 body：≤ 4096 B
帧：2 B 长度头 + 正文，其中正文长度 ≤ 6 B
```

前者不能替代后者：`4096 B` 合法 HTTP 请求仍可能包含长度为 `100 B` 的非法帧；后者也不能替代前者：大量小帧可能使 HTTP body 超限。两道门都应在对应层尽早拒绝，并在按声明长度分配缓冲区前完成帧长度校验。

### 确认边界与协议演进策略

### 确认边界与协议演进策略

一次 `Write` 成功只表示数据已交给本机内核；TCP ACK 只表示对端 TCP 栈确认收到字节。两者都不等于消息被应用解析、授权或持久化。确认点应明确区分：

| 确认点 | 能证明什么 | 不能证明什么 |
|---|---|---|
| `Write` 返回 `nil` | 本机内核接受了字节 | 对端是否收到、解析或处理 |
| TCP ACK | 对端内核收到了字节 | 对端应用是否读取 |
| HTTP 响应 | 服务端已按该响应语义处理请求 | 响应丢失时客户端是否知道结果 |
| S2 `accepted_in_memory` | S2 已在内存中接受消息 | 进程崩溃后的保留、DB 已写入、设备已收到 |
| 未来 DB 存储 | 数据库提交成功 | 目标设备已收到或展示 |
| 设备 ACK | 设备按协议确认接收 | 用户是否阅读、业务是否最终完成 |

因此，响应超时或连接中断时，客户端状态应为“未知”，不能因重试方便而乐观认定失败或成功。重试必须依赖消息 ID、幂等键和服务端去重；身份及会话成员资格仍由应用层核验，不能因为 TLS 或既有连接自动授权。

帧格式演进应显式携带版本，例如首字节为版本、后续为类型和长度。旧端只处理已知版本；新端应兼容旧版本，或通过协商降级。收到未知版本、未知类型、保留位非法或长度不符合该版本规则时，应在分配前拒绝并关闭或返回协议错误，绝不“猜测解析”。

WebSocket 已有自己的帧格式和边界，不能把其负载误解释为自定义 `2 B` 长度前缀；若需要应用消息版本，应放在 WebSocket 消息负载内部。

> **要点** — 帧边界须由应用显式定义并限长校验；取消、确认、授权和连接复用各有独立边界，不能相互替代。

通过纸上推演六字节教学消息，建立从字节流定帧、完整读写到超时取消、连接复用与业务确认的边界意识。

### TCP字节流与教学长度帧

### TCP字节流与教学长度帧

TCP 交付的是**有序、可靠的连续字节流**，并不保留发送方“调用一次 `Write` 就是一条消息”的边界。发送方即使连续写入两段各 `3 B` 的数据，接收方也可能一次读到 `6 B`、两次各读到 `3 B`，或先读到 `1 B` 再读到其余 `5 B`。因此，应用必须自行规定如何从字节流切出消息帧。

这里使用一个教学帧：

`[2 B 长度头][正文]`

长度头采用无符号大端整数，表示正文长度，不包含自身。若正文为 `6 B`，长度头为：

`00 06`

完整帧共有 `2 + 6 = 8 B`。例如正文为 `GoTCP!`，可抽象为：

`00 06 | 47 6f 54 43 50 21`

接收端的纸上推演顺序是：

1. 先累计读取固定的 `2 B` 头部；
2. 解出正文长度 `6`；
3. 检查该长度是否不超过预设上限；
4. 再累计读取恰好 `6 B` 正文；
5. 只有正文完整到达，才把它交给上层处理。

“长度字段”不是可信输入。若对端声称正文长度极大，直接按该值分配内存可能导致内存耗尽；应先比较最大帧长。若头部仅收到 `1 B` 后连接结束，则帧已截断，不能猜测长度，更不能继续分配或把残片当作完整消息。

该 `2 B` 头只是教学协议，不是 HTTP、WebSocket 或现行即时通信协议的通用线格式。关键不在头部恰好占几字节，而在于：TCP 只提供字节，**消息边界由应用协议定义并由接收端完整验证**。

### 限长、完整读取与截断

### 限长、完整读取与截断

设教学帧格式为：`2 B` 大端无符号长度头 `L`，后接 `L B` 正文。接收端不能把一次 `Read` 当作“一帧到达”：TCP 只保证有序字节流，固定头与正文都可能被拆成多次交付。

推演流程应严格分两阶段：

1. 用 `io.ReadFull(r, header[:])` 读取恰好 `2 B` 的帧头。
2. 将例如 `00 06` 解码为 $L=6$。
3. 先检查 `L <= MaxFrameSize`，再执行 `make([]byte, L)`。
4. 用 `io.ReadFull(r, body)` 读取恰好 `6 B` 正文，成功后才把该帧交给上层处理。

限长检查必须在分配之前。若对端发送 `FF FF`，长度为 `65535`；在真实协议中，若长度字段更宽或恶意值更大，先分配可能造成过量内存占用，甚至被远端触发拒绝服务。长度合法只说明“允许接收”，不说明正文已经完整到达。

错误分支也必须按读取位置区分：

- 帧头一个字节都未读到且连接结束：可得到 `io.EOF`，表示没有新帧开始。
- 帧头已读到部分字节后结束：`io.ErrUnexpectedEOF`，这是截断帧头，不能继续解码或分配正文。
- 正文目标为 `6 B`，实际只读到 `3 B` 后结束：`io.ErrUnexpectedEOF`；这 `3 B` 不能作为完整消息交付。
- 长度超过上限：应拒绝该帧并按协议策略关闭连接或报告错误，不能相信该长度继续申请缓冲区。

因此，“读到了一些数据”不等于“收到了一条消息”；只有固定头完整、长度合规、正文完整三个条件同时成立，应用层才获得一帧。

### 短读短写的部分结果

### 短读短写的部分结果

设教学消息为 2 字节长度头加 6 字节正文，共 8 B。TCP 只提供有序字节流，不承诺一次 `Read` 恰好交付一帧。

假设对端依次发送：

`00 06 41`，随后发送 `42 43 44 45 46`

第一次调用 `Read(buf)` 即使 `buf` 长达 8 B，也可能得到：

`n=3, err=nil`

此时已取得长度头 `00 06` 和正文首字节 `41`，不能把“本次无错误”误解为“消息完整”。应根据帧格式累计字节：先用 `io.ReadFull` 读满 2 B 固定头，解析出长度 6；检查长度上限后，再用 `io.ReadFull` 读满 6 B 正文。

若正文阶段仅到达 5 B 后连接关闭，则可能得到：

`n=5, err=io.ErrUnexpectedEOF`

这表示帧截断，已读到的 5 B 不能作为完整正文交付。只有一个字节也未读到时，`ReadFull` 才可能返回 `io.EOF`。

写入也相同。若调用：

`n, err := conn.Write(frame)`

得到 `n=5, err=nil`，并不表示剩余 3 B 会自动补发；这是“无错误但无进展不足”的异常结果，应按封装约定报告短写，不能盲目无限重试。若得到 `n=5, err=某错误`，前 5 B 可能已到达对端，重连后重发整帧会产生重复请求风险。

因此，判断网络 I/O 结果必须同时看 `n`、`err` 与协议期望长度：`err=nil` 不等于完整，`err!=nil` 也不等于零字节生效。

### 连接后的期限与取消

### 连接后的期限与取消

拨号阶段与已连接阶段的“取消”不是同一件事。`DialContext` 的 `context.Context` 主要约束**建立连接**：域名解析、等待连接、握手尚未完成时，若上下文取消或到期，拨号应返回。

一旦 `net.Conn` 已建立，原先传给拨号器的上下文通常不会自动中断后续 `Read`、`Write`。因此下面的推理是错误的：

- 用 `DialContext(ctx, ...)` 建立连接；
- `ctx` 在 2 秒后到期；
- 认为随后阻塞的 `conn.Read` 也会在 2 秒后自动返回。

连接后的阻塞 I/O 应使用连接级期限或显式关闭：

| 机制 | 作用范围 | 典型结果 |
|---|---|---|
| `DialContext` | 拨号过程 | 取消尚未完成的连接建立 |
| `SetReadDeadline(t)` | 后续读操作 | 到达 `t` 后读返回超时错误 |
| `SetWriteDeadline(t)` | 后续写操作 | 到达 `t` 后写返回超时错误 |
| `conn.Close()` | 整条连接 | 阻塞读写被唤醒，连接不可再复用 |

期限是**绝对时间点**，不是“从现在起持续 5 秒”的自动滑动窗口：

`conn.SetReadDeadline(time.Now().Add(5 * time.Second))`

该调用设置的是一个具体截止时刻。若连接进入连接池、空闲一段时间后又被取出，旧期限可能早已过期，下一次读会立刻超时。因此复用连接前或每次关键 I/O 前，应按策略重新设置期限；不再需要时可用零值清除：

`conn.SetReadDeadline(time.Time{})`

若业务层希望“上下文取消就停止当前读”，常见做法是由协调协程在 `ctx.Done()` 后关闭连接，或使用支持上下文的更高层协议 API。代价是关闭通常会牺牲该连接的复用能力。超时或取消只能说明本端未获得结果，不能证明对端没有收到请求，更不能直接推出业务未执行。

### 复用连接与业务确认边界

### 复用连接与业务确认边界

连接池复用的是传输连接，不是“天然可并发的消息通道”。TCP 只保证单条连接上的字节有序；若两个 goroutine 同时向同一连接写帧，字节可能交错：

`[A头][B头][A体][B体]` 或更细粒度地混合。

接收端无法再按教学帧的“长度头 + 正文”恢复原消息。因此，池中每条连接至少应具备以下约束之一：

- 对一次“写请求帧—读响应帧”加连接级互斥，完成后才归还连接；
- 由单一读写协程独占连接，通过请求 ID 分发响应；
- 协议明确支持多路复用，并实现帧级串行写入、响应关联、取消后的残余响应处理。

仅给 `Write` 加锁通常不够：若请求 A 写完即解锁、请求 B 写入后抢先读取，B 可能读到 A 的响应。连接池必须审查“请求与响应配对”的完整临界区，而非只审查单次写操作。

更重要的是，网络成功不等于业务成功。可区分三个层次：

1. **S2 内存受理**：服务端进程已收到并暂存命令；
2. **设备确认**：命令已被下游设备执行或确认；
3. **客户端获知结果**：响应已完整到达客户端。

例如客户端写入 5 B 后读超时，只能说明本次调用结果未知；不能断言服务端未收到，更不能断言设备未执行。此时用同一业务 ID 重试，收到 `409` 也未必表示“本次重试成功”，它可能表示首次请求早已被受理。

因此，未知结果应由业务协议处理：携带稳定的幂等键或命令 ID，提供查询状态、去重记录或明确的最终确认语义。连接池负责隔离帧与管理连接生命周期；它不能替应用把“字节已发送”升级为“业务已完成”。

> **要点** — TCP只保证有序字节；应用必须自行定帧、限长、处理部分结果，并分清传输完成与业务确认。
