重构不是“测试通过就安全”的代码整理，而是在不改变用户可观察行为的前提下，逐步改善内部结构，为未来支持 JSON v2 留出清晰边界。

### 界定不变的外部行为

### 界定不变的外部行为

Fowler 所说的重构，是“在**不改变软件可观察行为**的前提下改善内部结构”。对 `c-a/u-a/m-a` 而言，观察者不只有在终端前输入命令的人，还包括调用它的脚本、读取其导出文件的程序，以及依赖错误信息定位问题的运维工具。

因此，重构前先把行为合同写清楚。以下内容即使实现完全重写，也必须保持不变：

- **输入边界**：现有 JSON v1 的合法输入仍被接受；原本非法的字段、类型、缺失值或损坏 JSON 仍应以原有类别失败。
- **命令结果**：`check`、`list`、`export` 对同一输入产生相同的成功或失败结论；对应退出码仍为 `0/2/3/4/5`。
- **输出通道**：正常结果继续写入 `stdout`，诊断信息继续写入 `stderr`；不能为了“统一打印”而混合两者。
- **文本与顺序**：`list` 的条目顺序、字段展示方式及脱敏结果保持一致。脚本可能逐行解析输出，顺序也是接口的一部分。
- **文件副作用**：`export` 默认不覆盖已有目标文件；成功时生成的文件格式与内容仍满足 v1 消费者预期。
- **错误身份**：不仅要失败，还要以相同的错误类别失败。例如“参数错误”和“输入文件不存在”即使都非零退出，也不能互相替代。

仅仅“测试绿了”并不能证明完成重构：测试可能遗漏 `stderr`、退出码或已有文件的覆盖保护。若改变了错误文案、修正了原有错误分类，或新增 v2 参数、输出格式，那么它分别可能是修 bug 或加功能；只有需求合同未变、内部组织变得更清晰，才是本轮重构。

### 区分重构、修复与功能变更

### 区分重构、修复与功能变更

判断一次改动是不是重构，关键不在“代码更漂亮”或“测试全绿”，而在用户能否观察到差异。对 `c-a`、`u-a`、`m-a` 而言，可观察行为包括：接受哪些 JSON、拒绝哪些 JSON、错误信息属于哪一类、退出码、`stdout`/`stderr` 内容、文件是否被覆盖，以及 `list` 的排序和脱敏规则。

| 改动类型 | 示例 | 是否属于本轮重构 |
|---|---|---|
| 重构 | 将三条命令共用的 JSON 读取逻辑抽到 `internal/input`，但合法 v1 输入仍成功，非法 JSON 仍输出原错误身份并以 exit `2` 退出 | 是 |
| 修复缺陷 | `m-a list` 原本泄露 token；改为始终显示 `***` | 否，虽然是必要改进，但脱敏输出已改变 |
| 修复缺陷 | `u-a` 遇到不存在的输入文件原先错误地返回 exit `0`，现改为 exit `3` | 否，退出码是外部契约 |
| 新增功能 | `c-a check --format v2 data.json` 可验证 JSON v2 | 否，新增了可调用接口 |
| 功能变更 | `m-a list` 从名称排序改为修改时间排序 | 否，即使新顺序“更合理” |

例如，以下改动可算重构：解析 v1 后先转换为内部 `Account` 模型，再由命令层输出原有格式。前提是：

- `c-a check bad.json` 仍在 `stderr` 给出同类诊断，并返回约定的 exit `2`；
- `u-a export out.json` 在目标文件已存在时，仍默认拒绝覆盖并返回原 exit `4`；
- `m-a list` 对同一份数据仍按原顺序输出，敏感字段仍按原规则脱敏。

Fowler 所说的重构强调“改变内部结构，不改变可观察行为”。因此，测试绿灯只能说明测试覆盖到的断言未变；若测试没有检查错误流、退出码或列表顺序，绿灯并不能证明契约仍被遵守。修复和新增功能应单独命名、单独评审，再明确更新行为契约与测试。

### 从历史工具识别职责混杂

### 从历史工具识别职责混杂

历史 `c-a/u-a/m-a` 工具常见的形态是：`main` 解析参数后，直接读取 JSON、判断版本、校验字段、脱敏、排序、写出文件，并在各处分支中打印错误和调用 `os.Exit`。它能工作，却把多个变化原因绑在同一处：

- 命令解析变化：如 `export` 新增选项；
- 格式读取变化：未来兼容 JSON v2；
- 业务校验变化：字段缺失、类型错误、非法值；
- 展示变化：`list` 的排序与敏感字段隐藏；
- 输出变化：导出路径、默认不覆盖；
- 协议变化：错误身份、`stdout/stderr` 与退出码 `0/2/3/4/5`。

因此，“把读取逻辑抽成函数”并不天然安全。若抽取时把“JSON 语法错误”统一包装成“校验失败”，即使测试仍绿，也可能把原本的退出码 `3` 改成 `4`，或把原本写到 `stderr` 的诊断写到 `stdout`。对脚本调用者而言，这已经是外部行为变化。

重构前应先建立证据，而非先移动代码。为每个命令记录一张行为表：

| 场景 | stdout | stderr | 退出码 | 文件副作用 |
|---|---|---|---:|---|
| 合法 `list` | 已排序、已脱敏列表 | 空 | 0 | 无 |
| 非法 JSON | 空 | 保留原错误身份 | 3 | 无 |
| 校验失败 | 空 | 字段诊断 | 4 | 无 |
| 导出目标已存在 | 空 | 不覆盖提示 | 5 | 原文件不变 |

这里的“错误身份”不仅是文字；还包括错误类别、出口码和输出流。Fowler 所说的重构要求可观察行为不变，所以提取 `Load`、`Validate`、`Redact`、`Sort`、`Export`、`MapError` 等边界时，应让它们先复现既有规则。修复原有缺陷是修 bug，接受 v2 是加功能；两者都应在重构提交之后，以新的契约和测试单独表达。

### 按小步提取边界与依赖

### 按小步提取边界与依赖

为 JSON v2 做准备时，不要先把 `main`、解析、校验、文件访问全部拆成许多包。更稳妥的顺序是：先识别变化方向，再以小步移动代码；每一步都检查 CLI 契约仍然成立。

1. **先提取纯逻辑函数**：例如把“字段是否缺失”“版本是否为 v1”“导出时如何脱敏”从命令处理流程中提取出来。它们只接收数据、返回结果或错误，不读文件、不打印、不退出：

   `func ValidateV1(doc Document) error`

   `func Redact(doc Document) ExportView`

   此时错误仍应保留可识别身份，例如 `ErrInvalidInput`、`ErrUnsupportedVersion`；不能为了“统一漂亮”而把原有应映射到退出码 `2`、`3`、`4`、`5` 的错误压成同一种错误。

2. **再提取基础设施依赖**：将读取 JSON、列举文件、原子写出等操作放在明确边界后，例如 `Store`。接口应由消费方定义，而不是按实现细节设计：

   `type Store interface { Load(name string) ([]byte, error); List() ([]string, error); Create(name string, data []byte) error }`

   `application` 只知道“加载”“列举”“创建”，不知道目录布局、`os.Open` 或临时文件策略。尤其 `Create` 必须表达“默认不覆盖”，不能改成含义模糊的 `Write`。

3. **最后移动命令编排**：`check`、`list`、`export` 保留在应用层，负责参数解释、调用顺序、stdout/stderr 与退出码映射。`list` 的排序和脱敏输出也是外部行为，不能因改用 `map` 或并发读取而偶然改变。

命名应描述职责，而非当前实现：用 `DecodeV1` 代替 `parseFile`，用 `ExportView` 代替 `safeData`。每移动一次函数，都确认合法与非法输入、错误文本身份、输出流和退出码未变。测试全绿只能说明覆盖到的断言未变；真正的边界仍由 CLI 契约决定。

### 用契约证据保证可审阅回退

### 用契约证据保证可审阅回退

重构提交应让审阅者能回答：**若现在回退到旧版本，用户看到的命令行行为是否完全一致？** 这里的证据不是“测试全绿”，而是逐项对应既有契约。

对 `check`、`list`、`export` 建立静态评审清单：

- **退出码不漂移**：成功仍为 `0`；参数或 JSON 语法非法为 `2`；输入文件不可读为 `3`；业务校验失败为 `4`；写出失败为 `5`。不要把底层 `os` 错误直接映射为新的退出码。
- **输出通道固定**：成功结果只写 `stdout`；诊断、用法和错误只写 `stderr`。尤其不要为“方便统一输出”而把错误改用 `fmt.Println`。
- **默认不覆盖**：`export` 的目标文件已存在时，未显式指定覆盖选项必须失败，且不得截断原文件。评审时检查创建顺序：应先确认目标状态，再写临时文件或创建目标。
- **`list` 顺序稳定**：若 v1 按输入出现顺序列出，重构后不得因改用 `map` 而随机化；若按名称排序，则比较规则也必须保留。
- **脱敏格式逐字保留**：例如令牌显示为 `abcd…wxyz`，省略号、保留位数、空值表示都属于外部行为，不能仅因内部字段改名而变化。

可将提交说明写成可回退的证据链：

| 契约项 | 旧行为证据 | 重构后检查点 |
|---|---|---|
| 已存在导出目标 | `stderr` 报错、退出 `5`、文件未变 | 创建前检测，禁止直接 `os.Create` |
| 非法 JSON | `stderr` 保留错误身份、退出 `2` | 解析层错误映射保持不变 |
| 列表结果 | 固定顺序、字段脱敏 | 显式排序或保留切片顺序 |

若发现旧行为本身错误，先单独提交“修 bug”并更新契约；若增加 v2 输入，则是“加功能”。只有在这些可观察项均不变时，提取解析器、错误类型或 v1/v2 边界才叫重构。

> **要点** — 重构应逐步改善内部职责和模块边界，同时以明确的 CLI、错误与文件合同证明外部行为未变。

重构的起点不是把长函数切碎，而是识别哪些变化理由应被隔离，并证明命令对外合同未被改变。

### 从可观察行为界定重构边界

### 从可观察行为界定重构边界

重构的判据不是“代码更短”或“函数更多”，而是：在既定输入、环境与依赖条件下，命令的**可观察行为**保持不变。用户、脚本和其他包并不关心 `run` 内部如何拆分；它们会观察参数、标准输出、标准错误、退出状态、文件副作用及错误文本。

对本地 IM 工具而言，先写清外部合同：

- **命令行合同**：旗标名称、默认值、必填关系、重复参数规则，以及非法参数的诊断方式。
- **输入合同**：读取哪些文件；JSON 是否必须合法；缺字段、未知字段、类型错误分别如何报告。
- **领域合同**：例如消息长度上限为 9 字节、收件人不能为空、时间戳格式合法；这些是业务规则，不是 JSON 解析细节。
- **输出合同**：成功时写到标准输出还是指定文件；输出 JSON 的字段、顺序、缩进、末尾换行及编码。
- **失败合同**：错误输出的流向、错误前是否已创建目标文件、退出码，以及是否保留原文件内容。
- **副作用合同**：目标路径覆盖、目录不存在、权限不足、临时文件清理等行为。

因此，改变内部调用关系、提取 `parseFlags`、`loadJSON`、`validateMessage`、`render`、`writeTarget` 可以是重构；修正“9 字节限制误按 9 个字符计算”是修复；新增 `v2` 输入格式或改为表格输出则是功能变更。三者都可能改代码，但只有前者承诺合同不变。

不要按 `run` 的行数平均切块。应按变化理由划界：格式变化应局限于解析或渲染层，领域规则应集中于验证层，文件系统细节应藏在 I/O 边界后，命令层只负责编排。随后为函数、接口和包补上前置链接：谁调用谁、依赖何种抽象、哪些错误可穿透。这样未来面对 `v2`、9 字节上限调整或输出格式替换时，修改点才可定位，而不会重新搅动整个命令。

### 解剖过长的 run：按变化理由识别职责

### 解剖过长的 `run`：按变化理由识别职责

一个典型的 `run` 往往串起完整流程：解析 `flag`，打开输入文件，解码并校验 JSON，检查 IM 领域约束，显示结果，再写入目标。它看似是“一项工作”，实际承受了多种彼此独立的变化理由：

| 片段 | 应归属的职责 | 可能的变化 |
|---|---|---|
| `flag` 解析、参数组合检查 | 命令边界 | 新增 `--format`、调整默认值、改进报错文案 |
| 打开文件、读取、关闭、写目标 | I/O | 支持标准输入、原子写入、远程存储、权限处理 |
| JSON 解码、字段缺失与类型错误 | 格式适配 | JSON 升级为 v2、兼容旧字段、改用其他编码 |
| 名称长度、引用合法性等检查 | 领域业务规则 | 名称上限由 8 改为 9 字节，增加新的 IM 约束 |
| 文本、表格或机器可读输出 | 展示格式 | 人类输出改列宽，新增 JSON 输出格式 |

因此，不应因为 `run` 超过某个行数就机械拆分。更可靠的问题是：**若 v2 出现、名称限制改为 9 字节、输出格式改变，分别应修改哪里？** 若三种变化都要进入同一个函数并穿过同一批条件分支，说明职责仍然耦合。

可先建立清晰的前置连接：命令包只依赖一个应用入口，例如 `Execute(request)`；格式包负责把字节转换为输入模型；领域包暴露 `Validate(model)`；I/O 通过读取器、写入器或目标接口注入。这样 `run` 保留编排职责：收集命令参数、调用各阶段、把错误映射为命令可见的诊断。

关键不是让函数变短，而是提高内聚并隐藏信息：领域规则不应知道文件路径或 JSON 字段名；JSON 解码不应决定显示文本；展示层不应绕过校验直接解释原始输入。包依赖应从命令边界指向应用、格式和基础设施，而不让领域包反向依赖 `flag`、文件系统或终端。这样重构后，外部命令的参数、输出与失败语义保持不变，内部变化却有了明确落点。

### 用未来变更表检验拆分是否合理

### 用未来变更表检验拆分是否合理

判断拆分是否合理，不看 `run` 减少了多少行，而看一次明确的未来需求会迫使哪些位置修改。理想状态是：一个变化理由主要落在一个模块；命令入口只负责编排，不重新解释规则。

设当前命令流程为：解析 flag → 打开文件 → 解码 JSON → 校验领域对象 → 显示结果 → 写入目标。可用变更表反推边界：

| 未来变化 | 应修改的位置 | 不应修改的位置 |
|---|---|---|
| 增加 `v2` JSON 格式 | 格式解码器或版本适配器 | 文件打开、领域校验、显示、目标写入 |
| 名称上限从 8 改为 9 字节 | 领域校验器或领域类型构造函数 | JSON 字段读取、终端输出、文件系统代码 |
| 输出从文本改为表格或 JSON | 展示器/渲染器 | JSON 解码、上限规则、写目标逻辑 |

例如，“名称最多 9 字节”是业务规则，不应散落为 `len(name) > 9`。应集中为类似 `校验名称(name)` 的领域接口；无论输入来自 `v1`、`v2` 还是测试构造，都会执行同一规则。这里“字节”也必须明确是 UTF-8 编码后的长度，而不是字符数。

若加入 `v2` 时必须改 `run` 中大量 `if version == ...`，说明格式细节泄漏到了命令边界；应让解码器输出稳定的领域对象。若换输出格式时需要触碰校验逻辑，说明显示层拿到了过多内部信息。

可将 `run` 保持为窄编排：

`解析命令参数 → 读取输入 → 解码为领域对象 → 校验 → 渲染 → 写出`

其中包依赖应单向流动：命令包依赖应用服务；应用服务依赖领域接口；基础设施实现文件、JSON 和终端细节。这样未来变化只替换相应实现，外部命令行为——参数、退出码、错误语义与既有输出合同——仍可被前置链接和回归测试保护。

### 以高内聚和信息隐藏收紧包依赖

### 以高内聚和信息隐藏收紧包依赖

重构后的边界不只存在于函数之间，也存在于包之间。判断一个包是否合理，关键不是“文件是否放在同一目录”，而是它是否围绕同一种变化理由组织：会因协议版本变化而一起修改的代码，应靠近；会因终端输出变化而修改的代码，不应拖着领域校验一起变化。

**内聚**描述包内成员是否共同完成一个明确职责。例如，`im` 包可以负责“解析并验证一条 IM 记录”；其内部可包含 JSON 解码、字段必填检查、`9` 字节上限检查以及未来 `v2` 的兼容分支。这些步骤共同决定“输入是否为有效 IM”，具有高内聚。反之，把 `flag` 读取、文件创建、终端渲染和协议校验混入同一包，会让任何一种变化都扩散。

**耦合**描述包之间了解彼此细节的程度。命令层应依赖稳定的能力，而非依赖 `im` 包的内部表示：

```go
type Decoder interface {
    Decode(r io.Reader) (Message, error)
}

type Writer interface {
    Write(Message) error
}
```

这里命令层只需知道“从输入得到消息”“将消息写到目标”；它不应知道 JSON 使用了哪个解码器、`v1` 与 `v2` 如何分支、长度按字节还是字符计数。这样，当 `v2` 改变字段结构或 `9` 字节规则调整时，修改集中在 `im` 包内；当输出改为表格、文本或其他格式时，修改集中在显示或写出包内。

消费方应声明**自己真正需要的小接口**。若命令只调用 `Write(Message)`，就不应依赖包含 `Open`、`Flush`、`Close` 等十个方法的大型接口。小接口降低替换成本，也避免命令层反向窥探基础设施细节。

包依赖方向应保持单向：

`命令层 → 应用编排 → 领域/协议 → 基础设施适配`

命令层可以创建文件、接收参数并组装依赖，但不应承担协议规则；领域包可以返回结构化错误，但不应打印终端文本或直接打开路径。将实现细节留在拥有规则的包内，外部只看到稳定合同，才能在持续重构中保持 IM 工具的外部行为不变。

### 按可验证的小步完成并审阅改造

### 按可验证的小步完成并审阅改造

重构应是一串可回退、可审阅的行为保持步骤，而不是一次“整理完再测试”的大提交。对 `run` 而言，每一步都先明确不变量：相同参数、相同输入文件时，退出码、标准输出、标准错误、目标文件内容与写入时机均不变。

推荐顺序如下：

1. **先补证据，再动结构**  
   为当前命令建立前置链接：参数解析测试、非法 JSON 测试、领域校验测试、写文件失败测试，以及端到端快照。特别固定边界案例：9 字节上限、空值、已有目标文件、错误信息格式。测试应描述外部合同，而非断言内部函数被调用。

2. **提取纯规则函数**  
   优先提取不触及文件、终端或全局状态的逻辑，例如 `校验消息长度`、`校验领域字段`。输入输出明确后，直接补表驱动测试；此时 `run` 仍负责原有 I/O 流程，风险最小。

3. **提取格式与 I/O 操作，但保留命令编排**  
   JSON 解码、输出渲染、目标写入可以各自成为函数或接口；`run` 只保留“解析 flag → 打开输入 → 解码 → 校验 → 显示/写入”的顺序。不要为了缩短函数把错误处理拆散：错误上下文与退出语义本身也是合同。

4. **移动函数后再重命名**  
   先以原名移动并通过测试，再改为表达职责的名称。一次提交只做一种主要变化，避免“移动、改名、改逻辑”混在一起，使审阅者无法定位行为差异。

5. **最后调整包边界**  
   当领域校验不再依赖命令行、文件或 JSON 细节时，才移入领域包；命令包依赖领域包，领域包不得反向导入命令包。接口应放在使用方附近，例如写入方只依赖 `写入器`，而非暴露整个存储实现。

每个小步都应有可运行的测试、可读的提交说明和明确回退点。审阅时逐项追问：v2 输入格式来了改哪里？9 字节限制变化改哪里？输出从文本改为 JSON 改哪里？若答案仍是“改 `run` 的多个分支”，说明边界尚未建立。

> **要点** — 好的重构按变化理由建立边界，并以错误、退出码、输出和文件合同证明外部行为不变。

重构本地 IM 工具时，先以独立的可观察证据锁定外部行为，再逐步调整内部结构，避免把猜测、缺陷或实现细节误当合同。

### 先界定行为保持的证据边界

### 先界定行为保持的证据边界

“保持行为”不等于逐行保留旧实现，而是重构后仍满足外部调用者能够观察到的合同。对本地 IM 工具而言，至少应把一次命令执行抽象为：

\[
\text{输入参数}+\text{初始文件状态}\longrightarrow
(\text{退出码},\ \text{stdout},\ \text{stderr},\ \text{最终文件状态})
\]

因此，重构前后应比较以下证据：

- **退出码**：成功、参数错误、目标已存在、输入无效等情形是否仍返回约定结果。
- **标准输出**：成功提示、生成的 ID、正常查询结果等是否保持可用格式。
- **标准错误**：诊断应出现在哪里、是否包含稳定的错误类别信息。
- **文件前后状态**：写入是否产生预期记录；失败时是否不应改动文件；字段顺序、格式化差异是否属于合同，需由规范明确。
- **输入与输出是否为同一文件**：例如源文件与目标文件相同时，工具应遵循明确规则，而非依赖偶然的覆盖顺序。

应区分三类工作：

1. **重构**：仅改变内部组织，如把分支改为表驱动、替换文件访问层；可观察合同不变。
2. **修复**：旧行为违反已知规范或基本正确性，例如 `messages: null` 被误当作合法消息列表；应更新测试以表达规范，而非固化缺陷。
3. **功能变更**：新增字段、改变重复 ID 处理、调整 `max+1` 分配规则或修改错误文本；必须显式声明为合同变化。

面对未知老行为，可先写 characterization test，固定时间、使用 `t.TempDir` 隔离文件，并记录真实的退出码、stdout、stderr 与文件快照。但该测试只是观察证据，不自动成为需求；若观察到明显缺陷，应优先补充规范，再决定兼容、修复或迁移。课程中的静态示例只能说明应验证什么，不能表述为“已经通过”。

### 以独立期望设计表驱动样例

### 以独立期望设计表驱动样例

表驱动测试的关键不在“把现有实现跑一遍”，而在于先根据需求表写出期望，再让实现接受比对。若先阅读代码、复制当前输出或用同一套辅助函数推导结果，测试往往只是在确认实现自己没有改变，无法成为重构边界。

可将每个样例描述为“输入文件状态 + 操作参数 + 预期可观察结果”：

- `输入`：JSON 文本、目标 ID、固定时钟，例如 `2025-01-02T03:04:05Z`；
- `预期退出`：成功或指定错误类别；
- `预期 stdout/stderr`：是否为空、是否包含诊断；
- `预期文件`：操作前后内容、是否新建目标、源文件是否保持不变。

例如，需求明确 v1 格式合法时，应独立写出一份最小合法 JSON，并断言写入后的消息 ID 为当前最大 ID 加一；若最大值为 `41`，新消息必须是 `42`，而不是“某个未冲突的 ID”。测试数据应同时覆盖：

| 场景 | 独立期望 |
|---|---|
| v1 合法输入 | 成功，保留既有记录并追加新消息 |
| 未知字段 | 若规范允许前向兼容，则成功且不因未知字段失败 |
| `messages: null` | 按规范视为空列表或报格式错误，不能由当前实现偶然决定 |
| 重复 ID | 明确拒绝、保留原文件，并检查错误输出 |
| 最大 ID 后追加 | 新 ID 为 `max+1` |
| 目标文件已存在 | 按规范拒绝覆盖或采用明确覆盖策略 |
| 输入与输出同一文件 | 明确是否允许；若不允许，断言文件内容不变 |

固定时间可避免输出中的时间戳使测试漂移。对文件断言应读取真实的临时目录文件，比较操作前后字节或结构化内容；不要只检查函数返回值。

遇到历史行为未知时，可先写 characterization test 记录观察到的 `exit/stdout/stderr/文件变化`，但须标注其为待确认行为。明显缺陷，例如重复 ID 仍成功写入，不能因为“旧版本如此”就升级为需求；应优先回到规范，决定应保留、迁移还是修复。

### 用特征测试记录未知老行为

### 用特征测试记录未知老行为

当旧工具缺少可靠规范、却必须在重构前维持兼容时，可先写**特征测试**：它不宣称行为“正确”，只记录当前版本在固定输入下的可观察结果。观察面应包括：

- 退出码；
- `stdout` 与 `stderr`；
- 输出文件是否生成、内容如何变化；
- 输入文件是否被修改；
- 时间、随机数等非确定因素是否已固定。

例如，对 `null messages`、未知字段、重复 ID、`target` 已存在、输入与输出为同一文件等边界输入，可在 `t.TempDir()` 中准备真实文件，调用旧二进制或替身，再将观察到的结果写成测试名称明确的案例：

```text
给定重复 ID 的本地 v1 数据，旧版本退出码为 0，
stderr 为空，结果文件保留两条记录。
```

这类测试的价值是为重构提供“不要无意改变它”的护栏，尤其适合无法立即判断历史兼容性含义的行为。测试应标注为“已观察行为”，而非“产品需求”；课程中的静态示例也只能说明测试应如何写，不能声称已经在某个旧版本上通过。

但有明确规范时，应优先测试规范，而不是让旧实现决定合同。例如，规范已定义 v1 的合法字段、未知字段处理方式，或要求 ID 按 `max+1` 分配，就应直接断言这些规则。若旧程序对非法输入静默成功、覆盖已有 `target`、把 `null messages` 当作可写入状态等，且这明显违背安全性或已知约束，不应把它机械固化为需求。

实务上可将结论分三类：**规范已定义**，按规范测试；**规范未知且行为可接受**，用特征测试暂时锁定；**行为明显是缺陷**，记录观察、补充回归证据，并推动澄清或修复，而不是把缺陷命名为兼容性。

### 借助替身隔离文件与时间因素

### 借助替身隔离文件与时间因素

本地工具的测试应只依赖测试自己创建的环境。用 `t.TempDir()` 建立临时目录，把输入、输出和状态文件都放入其中；测试结束后目录自动清理，不会污染真实工作目录，也不会误读开发者机器上的旧文件。

```go
dir := t.TempDir()
input := filepath.Join(dir, "messages.json")
before := `{"messages":[]}`
if err := os.WriteFile(input, []byte(before), 0o644); err != nil {
    t.Fatal(err)
}
```

时间也应作为依赖注入，而非在业务逻辑中直接调用 `time.Now()`。固定时钟可使新增消息的时间戳、排序结果和序列化内容稳定：

```go
now := time.Date(2025, 1, 2, 3, 4, 5, 0, time.UTC)
tool := NewTool(WithNow(func() time.Time { return now }))
```

若工具原本会调用外部 IM 服务，应以替身记录调用参数，避免测试真的发送消息。替身应暴露可观察事实，例如是否调用、目标 ID、消息正文和返回错误，而不是复刻远端系统的复杂实现。

测试执行前后都读取文件，分别断言：

- 退出码、`stdout`、`stderr`；
- 原文件是否保持不变；
- 目标文件是否创建、覆盖或拒绝写入；
- JSON 中消息数量、重复 ID 处理及新增 ID 是否为 `max+1`；
- `null messages`、未知字段等输入的最终文件表示。

固定目录、时间与服务替身后，失败通常能定位到本地行为变化，而不是当前日期、机器文件或网络状态。对于尚无规范的旧行为，可先用 characterization test 记录观察；但若观察到明显缺陷，应标注为待澄清，而不能自动固化为需求。

### 把证据嵌入可回退的小步重构

### 把证据嵌入可回退的小步重构

重构不是先“整理代码”，再祈祷行为未变；每一步都应有可运行的证据、可审阅的意图和可快速回退的边界。这里的合同仅覆盖本地工具的进程可观察行为：退出码、`stdout`、`stderr`、文件修改前后状态及固定时间下的确定性结果；不讨论崩溃原子性或远端送达。

推荐将改动拆成窄提交，并让每个提交对应一类证据：

1. **先补 characterization test**  
   对未知老行为，使用独立临时目录、替身依赖和固定时钟记录观察。例如输入文件与目标文件相同、目标已存在、消息为 `null`、存在未知字段、重复 ID、`max+1` 条消息时，分别断言进程输出和文件内容。  
   但观察不是规范：若发现明显缺陷，例如重复 ID 被静默覆盖，不应把该测试命名为“必须覆盖”；应在评审中标注“现状记录，待规范确认”。

2. **提取纯函数，再移动函数**  
   先从命令处理代码中提取如 `解析本地v1`、`校验消息`、`计算下一个ID` 等函数，并以表驱动测试锁定合法输入与拒绝输入。确认测试不变后，再移动到新文件或新包。  
   这样失败范围清晰：提取后失败，多半是参数、时间或错误转换变化；移动后失败，多半是依赖方向或可见性变化。

3. **重命名必须保持黑盒断言稳定**  
   重命名内部类型、文件或包时，不借机修改错误文案、写入顺序或默认值。提交说明应写明：  
   - 保持哪些外部行为；  
   - 新增的是规范测试还是现状记录；  
   - 回退时可撤销的提交点。  

4. **包边界调整后复查副作用**  
   新包不应直接获得命令行、文件系统或真实时钟的隐式访问；通过接口或参数注入，使 `t.TempDir`、假时钟和文件替身继续可控。特别检查“读写同一文件”与“目标已存在”：测试应比较操作前后字节内容，而非只断言“文件存在”。

一个安全节奏是：`补证据 → 单一结构改动 → 全量测试 → 审阅可观察差异 → 提交`。若规范尚未明确，就保留观察测试的注释与问题链接；若规范已明确，则让测试表达规范，而不是迁就旧实现。

> **要点** — 先用独立期望与可观察证据锁定合同，再以可审阅、可回退的小步重构改善模块边界。

以历史消息检查命令为例，先锁定外部可观察行为，再按可验证、可回退的小步重构职责与包边界。

### 先写清不变的行为合同

### 先写清不变的行为合同

重构前先回答一个问题：用户、脚本和其他工具**已经依赖了什么**？这些可观察结果就是本次重构的边界，而不是代码内部调用关系。

以 `history check` 为例，先用现有测试、命令快照和手工样本写出 `want`：

- 非法消息长度仍返回同一个可识别错误，例如 `history.ErrMessageTooLong`；不要仅保证错误文案“看起来差不多”。
- 命令捕获该错误后仍映射为原来的退出码，例如参数或内容错误继续退出 `2`，文件读取失败继续退出 `1`。
- 标准输出保持不变：成功时是否静默、是否打印检查数量、换行符位置都属于合同；诊断信息写入标准错误也不能悄悄交换。
- JSON 文件格式保持兼容：顶层结构、字段名、可选字段、未知字段处理方式、空数组与缺失字段的语义都先固定。
- 长度规则保持原样。例如原逻辑按 UTF-8 字节数限制 `len(message.Content) <= 6`，就不能在“顺手优化”时改成字符数、符文数，或调整边界为 `< 6`。

可先建立类似的表格或测试名称：

| 输入 | 既有结果 |
| --- | --- |
| `{"content":"123456"}` | 通过 |
| `{"content":"1234567"}` | `ErrMessageTooLong`，退出码 `2` |
| 损坏的 JSON | 原有解码错误类别，退出码 `1` |
| 不存在的路径 | 原有文件错误类别，退出码 `1` |

此时提交一个只补证据的提交，例如 `test: lock history check behavior`。它不改变生产代码，因此可独立回退。

随后每次只改变一类事情：先把 `run` 中的长度判断提取为 `history.ValidateMessage`，验证错误、输出和退出码不变；再移动 JSON 解码到 `internal/historyfile`，但路径解析仍留在 `cmd`。不要在同一提交中同时改“6 字节”规则、错误包装层级或输出格式。

提取函数本身并不自动改善设计。若 `ValidateMessage` 需要接收命令对象、文件路径、打印器等跨层参数，反而说明边界更混乱；应回退该提交，重新缩小函数输入，而不是继续把依赖一路传下去。

### 从 run 提取消息校验函数

### 从 `run` 提取消息校验函数

先写出外部行为的 `want`：消息超过 6 字节时，命令仍输出原有错误文本，并以原有退出码退出。此次提交只移动判断位置；不改变 6 字节规则、不改输出格式、不顺带调整参数解析。

重构前，命令层同时承担读取、校验和错误映射：

```go
func run(msg string) error {
	if len(msg) > 6 {
		return exitError("message is too long", 2)
	}
	return save(msg)
}
```

提取后，`history` 只表达领域判断；它不认识命令退出码，也不决定终端输出：

```go
package history

import "errors"

var ErrMessageTooLong = errors.New("message too long")

func ValidateMessage(msg string) error {
	if len(msg) > 6 {
		return ErrMessageTooLong
	}
	return nil
}
```

命令层保留原有的外部契约，将领域错误映射回原来的错误文字和退出码：

```go
func run(msg string) error {
	if err := history.ValidateMessage(msg); err != nil {
		if errors.Is(err, history.ErrMessageTooLong) {
			return exitError("message is too long", 2)
		}
		return err
	}
	return save(msg)
}
```

测试应分两层对照：

- `history.ValidateMessage("123456")` 成功，`history.ValidateMessage("1234567")` 返回 `ErrMessageTooLong`。
- 命令集成测试仍断言：超长输入的标准错误包含 `message is too long`，退出码仍为 `2`。

这应是一个独立、可回退的提交，例如“提取历史消息校验”。提取函数本身不等于设计改善：若 `ValidateMessage` 很快需要接收命令上下文、文件路径、打印器等跨层参数，说明边界并未变清晰，应撤回提取，重新检查职责归属。

### 移动 JSON 解码与路径职责

### 移动 JSON 解码与路径职责

先写出不变量：命令仍接受相同参数，找不到文件、JSON 非法、消息非法时仍输出原有错误并返回原退出码；本步不修改“6 字节”长度规则，也不调整 JSON 或诊断文本格式。

重构前，`cmd` 同时负责路径、文件和解码：

```go
func run(path string) error {
    b, err := os.ReadFile(path)
    if err != nil {
        return err
    }
    var h History
    if err := json.Unmarshal(b, &h); err != nil {
        return err
    }
    return history.ValidateMessage(h.Messages)
}
```

重构后，命令仍是参数与路径的拥有者：它解析 `args`、决定相对路径基准、保留面向用户的错误映射；`internal/historyfile` 只隐藏“如何从一个已确定路径读取历史文件”。

```go
// cmd：路径语义留在边界层
path, err := resolveHistoryPath(args[0])
if err != nil {
    return usageError(err)
}
h, err := historyfile.Load(path)
if err != nil {
    return mapLoadError(err)
}
return history.ValidateMessage(h.Messages)
```

```go
// internal/historyfile：文件格式细节不泄漏
func Load(path string) (History, error) {
    b, err := os.ReadFile(path)
    if err != nil {
        return History{}, err
    }
    var h History
    if err := json.Unmarshal(b, &h); err != nil {
        return History{}, err
    }
    return h, nil
}
```

这里的消费方小接口是 `Load(path) (History, error)`：调用者无需知道 `json.Unmarshal`、字段缺失处理或文件读取顺序。不要让 `historyfile` 接收命令参数、工作目录或 `flag`；那些信息属于 `cmd` 的交互边界。

对照测试应覆盖：同一合法文件产生同一检查结果；不存在路径仍映射为原错误和退出码；非法 JSON 仍使用原诊断。先提交“新增 `Load` 并保持旧调用”，再提交“`cmd` 切换调用”，每个提交都可独立回退。若提取后反而需要在 `cmd`、`historyfile`、验证器之间传递更多路径上下文或选项，说明边界未变清晰，应退回而非强行迁移。

### 逐步对照差异与测试证据

### 逐步对照差异与测试证据

先把命令的外部契约写成 `want`，再移动代码。假设 `history check` 要求每条消息不超过 `6` 字节，超限时输出既有错误文本并返回退出码 `2`：

| 场景 | want |
|---|---|
| `hello` | 成功，退出码 `0` |
| `你好` | 成功，`len("你好")==6` |
| `你好！` | 输出 `消息过长`，退出码 `2` |
| 非法 JSON | 保持原有解析错误与退出码 |
| 路径不存在 | 保持原有文件错误与退出码 |

第一提交只提取规则，不改规则、不改输出：

```go
// Before: cmd/history.go
if len(msg.Content) > 6 {
    return usageError("消息过长")
}

// After: internal/history/validate.go
func ValidateMessage(msg Message) error {
    if len(msg.Content) > 6 {
        return ErrMessageTooLong
    }
    return nil
}
```

命令层仍负责映射，因而用户看不到重构痕迹：

```go
if err := history.ValidateMessage(msg); err != nil {
    if errors.Is(err, history.ErrMessageTooLong) {
        return usageError("消息过长") // 仍为退出码 2
    }
    return err
}
```

此时补边界测试：`5`、`6`、`7` 字节，以及中文 UTF-8 字节数；再用输出样例或集成测试断言 `stderr` 和退出码。不要顺手把“6 字节”改成“6 字符”，也不要将错误改写得更友好；两者都是独立需求。

第二提交才移动 JSON 解码：`cmd` 保留参数和路径解析，`internal/historyfile` 只接收已确定的文件路径并返回历史记录。测试随之分层：命令测试验证参数、输出和退出码；`historyfile` 测试验证 JSON、空文件与字段缺失。

若提取后只是把 `path`、`stdout`、命令选项等更多参数跨层传递，复杂度反而上升，应回退该提交，重新划分边界。提取函数本身不是改进；可验证的职责收敛才是。

### 识别无效提取并设计回退点

### 识别无效提取并设计回退点

提取函数的目标不是“代码变短”，而是让职责边界更清晰、调用方更少知道细节。若提取后只是把原来 `run` 中已有的参数继续跨层传递，通常没有改善设计，应该退回到上一个可工作的提交。

例如，下面的提取看似把校验移入 `history`，实际仍由命令层计算消息文本、长度规则和错误上下文：

```go
func ValidateMessage(text string, maxBytes int, source string) error {
    if len(text) > maxBytes {
        return fmt.Errorf("%s: message exceeds %d bytes", source, maxBytes)
    }
    return nil
}
```

若每个调用点都要传入 `maxBytes`、`source`，并自行决定 `text` 是原文、截断文本还是 JSON 字段，那么规则的所有权仍在调用方；`history` 只是参数中转站。更好的边界是让校验函数接收领域对象，并由包内部拥有固定规则：

```go
func ValidateMessage(msg Message) error {
    if len(msg.Content) > maxMessageBytes {
        return ErrMessageTooLong
    }
    return nil
}
```

命令层只负责把 `ErrMessageTooLong` 映射为既有错误文本和退出码。不要在这一步顺便修改 `6` 字节规则、错误措辞或 JSON 输出格式；先用测试写出 `want`，锁定行为后再移动职责。

评审时应能给出四类证据：

- **命名**：`ValidateMessage` 表示领域校验；路径解析仍命名为 `resolveHistoryPath` 并留在 `cmd`。
- **注释**：仅说明非直观约束，如“按 UTF-8 字节数而非字符数限制”，不重复函数名。
- **差异测试**：覆盖超长消息、恰好 `6` 字节、无效 JSON，以及原有 stderr 与退出码。
- **依赖方向**：`cmd` 调用 `internal/historyfile` 解码；`historyfile` 不导入 `cmd`，也不接触终端输出。

每一步单独提交：先增加行为测试，再提取校验，再移动 JSON 解码。若发现新函数需要不断增加参数、调用链更长或测试需要了解多层实现，立即回退该提取提交；保留前一提交即可恢复已验证的外部行为。

> **要点** — 重构先证明外部行为不变，再以单一职责的小步提交调整实现与包边界。

重构本地历史工具时，目录调整和接口抽取都必须服从既有外部合同：依赖方向清晰，内部状态不可被意外改写，v1 文件与命令行行为保持稳定。

### 从目录依赖图识别边界

### 从目录依赖图识别边界

先画出依赖图，再移动文件。对于本地 IM 历史工具，一个稳定的分层通常是：

`cmd → 文件适配器 → history`

其中：

- `history` 是核心领域包，定义消息、会话、查询规则及必要的不变量；
- 文件适配器负责把 v1 JSON 文件读写转换为 `history` 的数据模型；
- `cmd` 解析命令行参数、组织输出，并同时依赖 `history` 与文件适配器。

箭头表示“导入并使用”，因此依赖只能向内收敛。`history` 不应导入 `os`、`flag`、`encoding/json` 等面向运行环境或传输格式的包；否则核心模型会知道“文件在哪里”“参数如何传入”“JSON 长什么样”，以后改为数据库、网络同步或图形界面时都会被牵连。

更重要的是识别反向依赖。例如，若文件适配器为了调用命令行展示逻辑而导入 `cmd`，就形成：

`cmd → 文件适配器 → cmd`

Go 会直接拒绝循环导入；即使通过全局变量、回调等方式绕开，职责也已混乱。类似地，`history` 反向导入文件适配器，也意味着核心层被具体存储实现绑死。

接口应由消费者一侧定义。若 `cmd` 或应用服务只需要“保存消息”，可在其需要的位置声明最小接口：

`type MessageSaver interface { Save(history.Message) error }`

文件适配器自然实现该接口，但无需让 `history` 知道它的存在。这样依赖的是能力而非具体文件实现，测试也可替换为内存实现。

`internal` 能限制包只能被父目录树内的代码导入，适合放置文件适配器等实现细节；但它不是安全沙箱，不能替代清晰的 API 边界。真正的边界仍由依赖方向、导出符号和不变量共同决定。

### 由消费方定义最小接口

### 由消费方定义最小接口

`cmd` 的需求并不是“拥有一个 `history`”，而是“在收到消息后能保存它”。因此，接口应由消费方按这一项实际需求声明，而不是由文件适配器预先暴露一大组能力：

```go
type MessageSaver interface {
    Save(Message) error
}
```

命令层只依赖 `MessageSaver`，启动时再把具体的文件实现传入：

```go
func run(saver MessageSaver, msg Message) error {
    return saver.Save(msg)
}
```

这样，依赖方向变为：

`cmd → MessageSaver ← 文件适配器`

更准确地说，`cmd` 定义抽象并消费抽象；文件适配器实现该抽象，并可依赖 `history` 中的消息模型、序列化规则或路径约定。`history` 无须知道命令行参数、`flag`、`os` 或 `json` 的具体使用场景，更不应反向导入 `cmd`。依赖图因此保持单向，也避免循环导入。

接口要“小”，因为它是调用方对实现方提出的最低合同。若 `cmd` 只调用 `Save`，就不应加入 `List`、`Delete`、`Path` 等方法；否则测试替身和未来实现都被迫承担无关能力。测试时可直接传入内存实现：

```go
type memorySaver struct{ messages []Message }

func (m *memorySaver) Save(x Message) error {
    m.messages = append(m.messages, x)
    return nil
}
```

注意接口抽取不意味着改变外部行为。文件实现仍必须写出原有 v1 格式，`cmd` 仍须接受原有参数并维持原有错误语义；变化仅限于内部依赖由“依赖具体文件类型”改为“依赖保存消息这一能力”。

### 隐藏状态与控制可变性

### 隐藏状态与控制可变性

Go 的值复制并不总意味着“完全独立”。结构体按值传递时，标量字段会复制；但切片、`map`、指针、通道等字段复制的通常只是描述符或地址，底层数据仍可能共享。若 `history` 将内部消息直接返回，调用方就可能绕过 API 改写历史：

`msgs := h.Messages(); msgs[0].Text = "篡改"`  
`msgs[0].Tags["source"] = "other"`

因此，导出类型不应等同于暴露全部实现状态。将存储细节放在未导出字段中，并通过受控方法维护不变量：

- 消息时间必须存在，或统一由创建逻辑填充；
- 消息顺序只能追加，不能由调用方任意重排；
- `ID` 一经分配不可修改；
- 元数据不得为 `nil`，或由方法统一规范化。

对于读取方法，应明确复制边界。仅复制切片头部是不够的：

`out := append([]Message(nil), h.messages...)`

这能阻止调用方替换、扩缩返回切片，但若 `Message` 内含 `map`、切片或指针，仍需逐项深拷贝。`map` 尤其危险：两个变量看似独立，实际写入任一方都会影响另一方。可以在构造、保存和读取时复制元数据，或干脆只暴露只读字段与查询方法。

```go
type History struct {
    messages []Message
}

func (h *History) Append(m Message) error { /* 校验并复制 */ return nil }
func (h *History) Messages() []Message    { /* 返回深复制 */ return nil }
```

未导出字段限制了包外直接访问，但并非安全沙箱：同包代码仍可修改，反射或不安全操作也可绕过约束。真正的边界来自清晰的 API、集中校验和稳定不变量。这样即使文件适配器或命令行层重构，`history` 的状态也不会被外部别名意外污染。

### 在小步移动中保持外部合同

### 在小步移动中保持外部合同

重构不是“代码能编译即可”。对本地 IM 历史工具而言，用户和脚本依赖的是可观察行为：v1 历史文件的字段与编码、命令行参数、标准输出、退出状态以及错误文本的语义。实现从 `cmd` 移到 `history` 或文件适配器时，这些合同不应被顺手改变。

建议将一次大调整拆成可独立审阅、可单独回滚的步骤：

1. **先提取纯函数**：把时间排序、消息校验、格式转换等逻辑从命令处理函数中抽出；保持输入、输出和错误不变，并补上针对 v1 样例文件的测试。
2. **再引入最小接口**：由消费者定义所需能力，例如 `MessageSaver` 只表达“保存消息”，而不是暴露整个历史仓库。参数类型决定依赖方向：`cmd` 可依赖接口与实现组合处，`history` 不应因此导入 `flag`、`os` 或 `json`。
3. **随后移动实现文件**：先复制实现并让旧入口委托新实现，确认测试、命令输出和错误路径一致后，再删除旧代码。避免在“移动文件”的提交中同时修改序列化格式。
4. **最后重命名包和符号**：重命名应是机械变化。若必须保留旧导出 API，可用薄包装兼容；不要让内部字段名意外成为新的公共承诺。

尤其要固定 v1 文件格式：字段缺失如何处理、时间格式、消息顺序、空文件行为，都应由测试锁定。CLI 同样如此，例如原有 `-history`、`-output` 参数的默认值、非法参数的报错位置和输出流不应因内部包调整而改变。

内部状态也属于实现边界。返回切片或 `map` 时应复制，避免调用者修改历史对象后绕过校验规则。`internal` 只能限制导入路径，不能替代接口设计、值复制和不变量检查。重构的完成标准不是目录更“漂亮”，而是旧用户在相同输入下仍得到相同结果。

### 评审边界设计与回退证据

### 评审边界设计与回退证据

`internal` 的作用是**编译期导入限制**：位于 `history/internal/...` 的包只能被其父目录树中的代码导入。它有助于阻止其他模块直接依赖实现细节，却不是安全边界：同一进程中的代码仍可读取文件、修改内存，错误的导出方法仍会泄露可变状态。

评审时先画出依赖图，而不是只看目录是否“整齐”：

- `history`：领域模型、查询规则与最小接口，不导入 `os`、`flag`、`encoding/json`。
- 文件适配器：依赖 `history`，负责 v1 JSON 的读写。
- `cmd`：依赖 `history` 与文件适配器，负责解析命令行参数、选择路径、打印结果。
- 依赖箭头只能向内：`cmd → adapter → history`；若 `history` 为了保存数据反向导入适配器，就会形成循环或污染领域层。

接口应从消费点反推。例如命令层只需保存消息，则由消费者声明：

`type MessageSaver interface { Save(history.Message) error }`

不要把文件路径、JSON 编码器或完整仓储能力塞进接口。这样测试可用内存替身，真实文件实现可替换，回退也只需恢复适配器装配关系。

回退证据应覆盖外部合同清单：

- v1 文件名、字段名、时间格式、缺失文件与损坏文件的处理保持不变；
- CLI 参数、默认值、退出码、标准输出和错误输出保持不变；
- 旧数据可读取，新写入仍被旧版本接受；
- `go test ./...`、端到端命令测试及典型历史文件夹的回归样例均通过。

最后检查状态边界：返回的 `Message` 是值复制并不代表完全隔离；其中的切片、`map`、指针字段仍可能共享底层数据。对外应复制可变字段，或只暴露不可变视图，确保调用者不能借由返回值改写历史记录。

> **要点** — 模块重构的关键不是移动代码，而是在依赖单向、状态封装的同时保持既有文件和命令行合同。

重构本地 IM 工具时，命名、注释与错误处理并非表层整理；它们共同决定使用者能否继续依赖既有行为合同。

### 先界定哪些改动仍属重构

### 先界定哪些改动仍属重构

重构的判定标准不是“代码是否更漂亮”，而是**调用者和运维者可观察到的行为是否保持不变**。对本地 IM 工具而言，可观察行为通常包括：

- 命令名、子命令、参数、环境变量和配置键；
- 标准输出、标准错误、退出码，以及机器脚本依赖的文本格式；
- 导出的 Go 包路径、类型、函数、字段、接口语义；
- 错误的可识别类别，例如调用方能否继续用 `errors.Is(err, ErrUnauthorized)` 判断；
- 文件位置、缓存格式、日志字段、权限要求与网络请求时机。

仅移动私有函数、拆分未导出文件、改进内部命名，通常属于重构。修正“消息发送成功却返回失败”这类违背既有承诺的问题，属于缺陷修复；即使它改变了输出，也应明确记录行为变化。新增筛选条件、改变默认发送目标、把错误类别从“认证失败”改为“网络失败”，则是功能或兼容性变更，不能以重构名义合入。

尤其要警惕公开改名。将导出的 `SendMessage` 改为 `SendIMMessage`、将包路径 `im` 改为 `client`，对 Go 调用方意味着编译失败；将 CLI 参数 `--token` 改名，也会破坏自动化脚本。除非版本策略允许破坏性升级，否则应保留旧入口，通过废弃注释、兼容包装或迁移期双支持逐步过渡。

### 用业务名词划清职责边界

### 用业务名词划清职责边界

Go 的命名应让调用点自然读成一句话。包名优先表达**业务单位或稳定职责**，而不是技术动作、存放形式或“杂项”：`conversation`、`contact`、`attachment`、`history` 往往比 `data`、`process`、`util` 更能说明模块边界。

例如，本地 IM 工具需要读取会话、筛选消息并导出附件时，可按领域拆分：

- `conversation`：会话定位、成员关系、会话元数据；
- `message`：消息解析、筛选与展示模型；
- `attachment`：附件定位、复制、校验与导出；
- `store`：本地数据库或索引的访问实现；
- `report`：面向用户的报告与诊断输出。

避免把不相干能力塞进 `util`：它会成为无明确所有者的依赖中心，也使调用者无法判断某个函数是否涉及文件、数据库、隐私数据或业务规则。若函数只服务一个领域，应留在该领域包内；若确有跨领域的稳定抽象，使用具体名词，如 `clock`、`path`、`redact`，而非 `common` 或 `helper`。

类型和函数也应避免重复包名前缀。包已经提供上下文：

```go
conversation.Lookup(id)
message.Parse(raw)
attachment.Export(file)
```

比 `conversation.ConversationLookup`、`message.ParseMessage` 更简洁。类型名表达实体或角色，如 `Message`、`Locator`、`Exporter`；函数名表达操作或查询，如 `Find`、`Load`、`Export`。只有在跨包使用时可能歧义，才补充限定词。

重命名时尤其要区分内部符号与公开 API。导出的包名、类型名、命令参数、配置键及错误文本都可能被脚本、插件或运维流程依赖。即使新名字更符合规范，也不能把它当作纯内部整理：应评估兼容层、弃用周期和迁移说明，确保职责边界变清晰，而外部行为合同不被悄然改变。

### 让注释说明决策与约束

### 让注释说明决策与约束

好的注释不复述代码，而是补足代码无法可靠表达的合同。`for` 循环、排序字段、分支条件等“怎么做”应由清晰命名和小函数呈现；若注释只是“遍历消息”“设置超时”，通常应删除或改进代码本身。

值得保留的注释主要回答四类问题：

- **为什么这样取舍**：例如本地索引故意采用最终一致性，以避免同步扫描阻塞 IM 客户端启动。
- **什么不变量不能破坏**：例如“同一会话内序号必须单调递增；重放时不得再次发送消息”。
- **输入范围与边界**：例如“仅接受 UTF-8 文本，长度按字节计不得超过 64 KiB；空字符串表示不更新正文”。
- **风险与兼容性**：例如“此字段写入磁盘后即成为持久化格式，重命名或改变零值语义需提供迁移”。

```go
// 保留原始错误身份，使调用方仍可用 errors.Is(err, ErrSessionExpired)
// 决定是否要求重新登录；不要改为新的通用解析错误。
return fmt.Errorf("读取本地会话缓存失败: %w", ErrSessionExpired)
```

注释应贴近被约束的导出类型、函数或关键分支，并使用可验证的表述，避免“尽量”“可能”“以后优化”等模糊承诺。对外导出标识符的文档还应说明调用者可依赖的行为：副作用、并发限制、返回错误类别，以及是否可能处理敏感正文。

每次重构应设置一个删除检查点：代码改动后逐条核对邻近注释是否仍为真；若实现已使其失效，立即更新或删除。过时注释比缺少注释更危险，因为它会把维护者引向错误的兼容性判断，并使“内部整理”悄然改变外部合同。

### 保持错误、退出码与诊断合同

### 保持错误、退出码与诊断合同

重构不能把“报错方式变了”当作无关紧要的内部调整。脚本、调用方和运维人员可能依赖三类稳定信号：错误身份、进程退出码、标准输出与标准错误中的诊断格式。即使功能结果相同，改变这些信号也可能破坏自动化流程。

在 Go 中，为错误补充上下文时应保留可识别的根因：

```go
return fmt.Errorf("读取会话配置 %q: %w", path, ErrConfigNotFound)
```

这样调用方仍可使用 `errors.Is(err, ErrConfigNotFound)` 判断类别；不要改写为仅含字符串的新错误：

```go
return fmt.Errorf("配置不存在：%s", path) // 丢失错误身份
```

重构时尤其要警惕将已有错误替换成“更统一”的 `ErrFailed`、`ErrInvalid`。若原合同区分认证失败、会话过期、文件缺失与网络不可达，这些类别通常对应不同的重试策略、提示文案或退出码。包装可以增加“在哪一步失败”，但不应改变“失败属于哪一类”。

退出码同样是公开行为。例如参数错误始终退出 `2`、认证失败退出 `3`、临时网络错误退出 `4`，则新的命令分层、错误类型或 `main` 函数都必须维持该映射。不要因为引入统一错误处理就把所有失败收敛为 `1`。

诊断信息应当足以定位问题，但默认不泄漏敏感正文。日志和错误消息可记录操作名、对象标识、状态码、请求追踪号；不应打印消息内容、访问令牌、Cookie、完整会话文件或未脱敏响应体。若需要详细诊断，应通过显式调试开关输出，并仍执行脱敏。

注释应说明这些约束的原因，例如“此错误类别供调用脚本判断是否重新登录”“退出码与旧版命令兼容”。当实现或合同已变化时，及时删除过时注释；错误地承诺旧行为，比没有注释更危险。

### 把改名和整理拆成可审阅步骤

### 把改名和整理拆成可审阅步骤

改名、提取包和整理注释应拆成小提交，而不是一次“清理代码”。先把既有需求表转为兼容清单：命令名、参数、退出码、标准输出格式、错误类别、配置路径，以及被其他包或脚本调用的公开标识符。测试应覆盖这些边界，而非只验证内部实现。

建议按以下顺序推进：

1. **先建立消费方视图**：为命令入口、配置读取、消息发送等能力定义小接口，例如 `MessageSender`、`ConfigLoader`。接口应表达业务角色，不使用泛化的 `Util`、`Data`、`Process`。
2. **提取实现但不改行为**：将实现移入以业务单位命名的包，如 `message`、`session`、`profile`；原位置保留适配层。此提交只改变文件归属，测试输出、错误和退出码必须完全一致。
3. **迁移调用方**：逐个调用方改为依赖小接口或新包，并保留端到端测试。每次迁移都应可独立回退，避免“提取和全量改名”混在同一差异中。
4. **最后处理命名**：包内名称无需重复包名，例如 `message.Client` 优于 `message.MessageClient`。公开名称改动不是纯内部重构：应保留旧名称的兼容包装、标记弃用，并明确删除版本。
5. **同步校验诊断行为**：错误包装继续保留身份，确保 `errors.Is(err, ErrNotFound)` 仍成立；新增上下文不得改变错误类别。日志只记录必要元数据，消息正文、令牌和会话内容默认不输出。

注释也应随迁移审查：说明“为何必须这样做”、并发或状态不变量、允许的输入范围及风险；若实现或协议已变化，删除过时注释比保留误导性说明更安全。

> **要点** — 命名与注释应暴露职责和约束；错误身份、退出码及诊断边界必须作为重构合同持续验证。

重构的价值不在“代码更漂亮”，而在不改变本地工具可观察行为的前提下，降低后续修改、评审与回退的成本。

### 先用可观察行为矩阵锁定合同

### 先用可观察行为矩阵锁定合同

重构前先写下“用户和脚本究竟看到了什么”。内部包结构、接口数量、函数命名都可以变化；命令参数、退出码、标准输出、错误身份、文件副作用与 JSON 字节格式，则构成本地工具的外部合同。没有这份合同，评审只能凭“看起来等价”判断，最容易漏掉短小却致命的边界差异。

| 可观察面 | 重构前证据 | 重构后必须核对 |
|---|---|---|
| 命令参数 | 必填/可选参数、默认值、参数顺序、未知参数处理 | 相同输入是否接受、拒绝或显示同一用法提示 |
| 退出码 | 成功、参数错误、找不到对象、权限失败等码值 | 码值及触发条件是否不变 |
| 标准输出 | 正常结果、空结果、换行、字段顺序 | 内容、目标流与末尾换行是否一致 |
| 错误身份 | 错误类别、错误码、可匹配文本 | 调用方能否继续按原方式识别错误 |
| 文件副作用 | 创建路径、覆盖规则、权限、原子写入 | 文件集合与失败后的残留状态是否一致 |
| JSON 格式 | 标签名、缺失字段、`null`、数组顺序、缩进 | 语义和字节边界是否符合既有消费者预期 |

证据应来自真实命令样例、黄金文件、失败用例和调用脚本，而非仅从实现推断。例如测试已覆盖 JSON 可解析，并不能证明兼容：字段标签从 `user_id` 改为 `userId`，或输出末尾少了换行，都可能破坏消费者；同样，复制了正确内容但写入标准错误而非标准输出，也已改变合同。

可将每个关键场景记录为“输入—环境—可观察结果”：`im export --format json` 在空仓库、损坏配置、已有目标文件等条件下分别产生什么输出、错误和退出码。重构提交的差异评审应逐项标记：**预期不变、刻意变化、尚未验证**。只有“刻意变化”才应附迁移说明；其余项目必须用测试或命令实测关闭。

### 识别大爆炸重写的失控信号

### 识别大爆炸重写的失控信号

重构应让外部观察者看到“同一个工具”，而不是借整理代码之名悄悄获得一个新工具。小步提取、移动和改名的共同特点是：每一步都能独立验证、独立回退，且行为差异可定位；大爆炸重写则把结构变化、接口调整、输出格式和新需求混在一起，失败时很难判断问题来自哪里。

可将两类变更对比为：

| 类型 | 典型动作 | 风险 | 推荐验证 |
|---|---|---|---|
| 小步重构 | 提取解析函数、移动文件、内部符号改名 | 影响面可控 | 单测、黄金输出、一次小提交 |
| 大爆炸重写 | 同时替换模块结构、命令行框架和数据模型 | 差异来源不可追踪 | 难以有效比较与回退 |
| 夹带功能变更 | 重构时顺便修改默认值、排序、错误文案 | 行为回归被伪装为“新设计” | 将功能需求拆成后续提交 |
| 表面改名 | 把内部字段名直接映射到 CLI 标签 | 破坏脚本、快照和用户习惯 | 比较参数、标准输出、错误输出与退出码 |

失控通常有以下信号：

- 一个提交同时出现大量删除、新增和文件迁移，却没有可逐步运行的中间状态。
- 评审说明使用“全面现代化”“统一架构”等词，但说不清哪些 CLI 输入输出必须保持不变。
- 内部重命名波及 `--help`、JSON 键、错误消息、文件名或输出列顺序。
- 新旧实现无法并行执行，因而没有基准输出可做差异比较。
- “顺手修复”默认行为、容错规则或排序逻辑，却未提供独立需求与迁移说明。

例如，将 `scan` 内部对象改名为 `artifact` 本身无害；若同时把 CLI 输出从 `scan_id` 改为 `artifact_id`，则已是公开契约变更。前者可单独提交，后者应明确版本策略、兼容期和测试样例。

判断是否应暂停重写，可问一个简单问题：能否把本次改动拆成若干提交，并让每个提交都通过同一组行为测试？若不能，先建立可观察行为矩阵，再选择提取、移动、改名等可逆步骤，而非押注一次性替换。

### 以职责和信息隐藏划定包边界

### 以职责和信息隐藏划定包边界

历史本地工具常把“读取参数→解析输入→校验规则→写入文件→打印结果”堆在同一处。此时拆包的依据不是文件大小，而是：某项变化应当只迫使哪些代码重新理解、修改和测试。

可先沿依赖方向分出稳定职责：

- **解析层**：把命令行、文件或 JSON 转成内部数据；不决定业务是否允许。
- **校验层**：表达字段约束、状态转换和错误语义；不认识终端颜色或文件路径。
- **存储层**：负责读写、原子替换、权限和格式迁移；向上提供“保存/查询”的小接口。
- **呈现层**：将结果和错误转为 CLI 输出；不得反向要求领域对象适配打印格式。

接口应由**消费方需要什么**来定义，而非把实现的方法逐一搬进接口。例如呈现层只需 `查询任务(id)`，就不应依赖包含 `打开事务()`、`重建索引()` 的全能仓储接口。小接口减少变更传播：替换存储实现时，受影响的是该接口的消费者，而不是整个程序。

JSON 标签通常属于边界适配层。若领域结构体直接带有 ``json:"task_id"``，外部字段名、兼容别名和空值规则会渗入业务代码；更稳妥的做法是用传输结构体承接 JSON，再显式转换为领域对象。只有当 JSON 本身就是该工具长期公开、稳定的领域表示，且转换层只会制造重复时，才可让标签留在领域附近；此时仍应把版本兼容逻辑隔离。

边界不宜为未来 `v2` 预建大量空接口。评估标准是变更传播成本：存储格式、CLI 输出或校验规则是否确有独立演化节奏，是否需要独立替换和测试。适度隐藏易变细节即可；抽象既不会自动保证性能，也不会天然带来持久性。

### 反例检验：抽象并非越多越安全

### 反例检验：抽象并非越多越安全

“全部代码接口化”常把简单依赖变成多层转发：解析器、编码器、文件系统都先定义接口，调用路径却只有一个实现。结果是阅读时无法判断真实行为，排错需跨越多层；接口本身既未降低变更传播成本，也不自动带来性能、持久性或可替换性。只有确有多个实现、外部资源边界或测试替身需求时，接口才值得存在。

为消除重复而建立全局单例也很危险。例如把配置、时钟、临时目录或编码选项放入全局实例，会让一次命令的状态泄漏到下一次调用，测试顺序开始影响结果，并发执行时更难定位问题。应优先显式传参；确需共享的不可变表，可限制在包内并禁止运行期写入。

过度拆包同样会制造假边界：一个字段改名要同时修改 `model`、`service`、`adapter`、`helper`，却没有任何独立演进需求。适度边界应围绕变化率不同的部分，例如“领域对象不认识 JSON 标签”“CLI 输出集中在命令层”“编解码细节留在基础设施层”；不要仅为未来可能的 v2 预建空壳。

高覆盖率尤其可能掩盖协议边界错误。测试若只断言“大文件能读写”，仍可能漏掉恰好 `6` 字节的头部、分片末尾、空输入或截断输入：覆盖率显示分支执行过，外部字节行为却已改变。评审时至少逐项核对：

- 输入：空值、`6` 字节边界、截断与非法 JSON；
- 输出：字节序、换行、字段名、错误文本与 CLI 退出码；
- 状态：重复调用、并发调用、临时文件清理；
- 兼容：旧命令参数、默认值与文件格式。

抽象的衡量标准不是层数，而是一次局部修改是否能保持这些可观察行为不变，并让影响范围更容易预测与回退。

### 用评审清单控制传播与回退

### 用评审清单控制传播与回退

差异评审不应只问“能否编译”，而要沿着可观察行为检查变更传播路径：命令行输入、标准输出、错误输出、退出码、文件内容、字节布局与默认配置。尤其是本地 IM 工具，`6` 字节头部、JSON 字段名或帮助文本都可能是外部合同。

可按以下顺序审查：

1. **命名与注释**：重命名是否改变 CLI 子命令、日志文本、错误信息或序列化标签？注释是否把实现细节误写成稳定承诺？
2. **依赖方向**：领域对象不应携带 JSON 标签、文件路径或终端输出格式；适配层可以依赖领域层，反向依赖会放大修改范围。
3. **合同与字节**：新增接口前，确认是否真有两个独立实现或替换需求。对协议、持久化和命令输出保留黄金样例及边界长度测试，不能仅依赖覆盖率。
4. **提交边界**：重构提交不得夹带新功能、默认值变化或文案调整；应能单独回退，并在回退后恢复原有输出。
5. **传播成本**：统计一次修改需触及的包、调用点、测试夹具和发布物。若接口只转发一次、实现永远唯一，优先保留直接依赖，避免“全接口化”。

可建立简短矩阵：

| 行为面 | 变更前后必须一致 | 验证方式 |
|---|---|---|
| CLI | 参数、帮助、退出码、文本 | 快照与集成测试 |
| JSON | 字段名、缺省值、编码 | 固定样例比较 |
| 文件/协议 | 顺序、长度、边界字节 | 十六进制黄金测试 |
| 依赖 | 初始化与资源生命周期 | 架构检查、回归测试 |

为未来 `v2` 预留边界，应围绕已知易变点，如编码器、存储适配器或传输端口；不要为假设中的扩展拆散核心流程。抽象只能降低耦合与回退成本，不能自动保证性能、持久性或兼容性。

> **要点** — 可靠重构以可观察行为为锚点：小步改变内部结构，用证据、边界与评审保证可回退。

以P1本地CLI为例，先冻结外部合同，再按可验证、可回退的小步重构；功能升级必须与重构证据分离。

### 先冻结阶段0前后的外部合同

### 先冻结阶段0前后的外部合同

重构不是“代码看起来更好”，而是在**可观察行为不变**的约束下改变内部结构。对 P1 本地 CLI，阶段0应先记录合同基线：相同命令、参数、输入文件与环境下，必须得到可比较的退出码、标准输出、标准错误、生成文件及其内容、写入位置和副作用顺序。

合同应覆盖：

- 命令形状：子命令、参数名、默认值、帮助文本中的承诺。
- 成功路径：输出格式、字段顺序、文件编码、是否覆盖既有文件。
- 失败路径：非法参数、缺失文件、损坏数据时的退出码、错误类别与关键措辞。
- 数据边界：接受的文件格式、别名字段、空值含义、未知字段处理方式。
- 环境依赖：当前目录、配置文件、权限、时区等是否影响结果。

建立证据时，将**静态教材样例**与**个人真实运行记录**分开：前者说明期望与复现步骤；后者保存命令、环境、输入摘要、完整输出、退出码及生成文件校验和。不要把某次机器上的偶然路径、用户名或时间戳写成稳定合同。

可用“黄金样本”比对阶段0前后结果；若输出含时间、临时目录等易变值，应先规定归一化规则，再比较。依据 Fowler，重构提交应能独立验证；依据 Ousterhout，外部接口应保持简单且稳定；Go 中则尤其要避免把内部包名、未导出类型或实现细节泄漏为 CLI 承诺。

1. 退出码可观察吗？**可以，应记录。**  
2. 日志顺序是合同吗？**仅当用户或脚本依赖它。**  
3. 临时文件名不同算回归吗？**先按合同决定。**  
4. 帮助文本可忽略吗？**不能，若已对外发布。**  
5. 错误文案必须逐字相同吗？**保留关键语义即可。**  
6. 内部包移动是合同变化吗？**通常不是。**  
7. 输出字段改名是重构吗？**不是，是接口变更。**  
8. 默认值改变呢？**属于行为变化。**  
9. 数据别名删除呢？**属于兼容性变化。**  
10. 新增必填参数呢？**属于破坏性变化。**  
11. 可只测成功案例吗？**不行，要测失败路径。**  
12. 真实运行记录可替代测试吗？**不可以，只是证据。**  
13. 样例可含个人绝对路径吗？**不应，应参数化。**  
14. 比对文件要关注编码吗？**要。**  
15. 错误应暴露内部类型吗？**不应。**  
16. 命名重构能改 CLI 名称吗？**不能。**  
17. 注释变更需要黄金样本吗？**通常不需要。**  
18. “更友好”的新提示算重构吗？**若改变脚本输出，就不是。**  
19. 新增 JSON 输出格式算重构吗？**不是，应另立功能变更。**  
20. 阶段0完成标志？**合同、样本和真实证据均可复现。**

### 阶段1：提取纯验证并保留错误身份

### 阶段1：提取纯验证并保留错误身份

P1 的旧命令常把参数读取、文件访问、规则判断和错误打印揉在一起。阶段1只做一件事：把**不依赖文件、环境、时钟或全局状态**的规则提取为纯验证函数；不要顺手修改文案、退出码、参数含义或默认值。

例如，原实现直接在命令入口中判断：

`if name == "" { return errors.New("名称不能为空") }`

可提取为：

`func validateName(name string) error`

但“返回 `error`”不等于可以随意换错误。外部合同可能依赖：

- 错误文本：脚本以 `名称不能为空` 匹配失败原因；
- 错误类型或哨兵值：调用方以 `errors.Is(err, ErrInvalidName)` 分类；
- 包装链：上层需要保留 `读取配置失败: ...` 的原因；
- 命令行为：错误仍写入原来的输出流，并由同一入口映射为原退出码。

推荐让验证层返回可识别的领域错误，而由 CLI 边界决定呈现方式：

`var ErrInvalidName = errors.New("名称不能为空")`

`func validateName(name string) error { if name == "" { return ErrInvalidName }; return nil }`

入口层仍按旧路径处理该错误。若旧行为是打印 `错误：名称不能为空` 并退出码 `2`，阶段1后也必须如此；不要因为函数更“干净”而改成 JSON、英文消息或退出码 `1`。

纯函数的价值在于可直接用表驱动测试覆盖边界：空字符串、空白字符、最大长度、非法字符、合法输入。测试不仅断言“会失败”，还应断言错误身份，例如 `errors.Is(got, ErrInvalidName)`；若文本属于公开合同，再额外断言文本。不要用字符串比较代替错误身份，也不要在验证函数中打印日志：打印属于 CLI 适配层，会使验证失去可复用性与确定性。

这一阶段的真实运行记录应单独保存：重构前后对同一组命令输入记录退出码、标准输出和标准错误；教材中的示例只是静态说明，不能替代本机证据。下一阶段才处理文件读取等副作用。

### 阶段2：隔离文件适配与数据边界

### 阶段2：隔离文件适配与数据边界

阶段1已把纯验证逻辑提取出来；阶段2要进一步把“不稳定的外部细节”关进适配层：文件路径、读写时机、权限错误、JSON/CSV 等格式编解码，以及可变数据的别名风险。核心层只接收稳定的领域数据，不应知道文件系统或序列化字段名。

可将边界组织为：

- `文件适配器`：负责读取、写入、原子替换、将 `os` 错误转换为本工具约定的错误。
- `编解码器`：负责字节与数据模型互转，拒绝格式错误、未知必填字段或版本不兼容数据。
- `核心服务`：只处理 `配置`、`记录`、`诊断` 等领域类型；不得直接调用文件 API。
- `命令层`：组合适配器与核心服务，保留原有参数、标准输出、退出码和错误文本合同。

特别警惕数据别名：若适配器把内部 `map`、切片或指针直接交给核心层，调用方修改数据就可能反向污染缓存或后续写盘结果。边界处应复制可变数据，或明确采用不可变约定；注释要说明“返回值是否可修改”，而非重复函数名称。

例如，不要让验证函数接受 `文件路径`；应由适配器读出 `配置`，再调用：

`诊断列表 = 验证(配置副本)`

这样格式从 JSON 改为 YAML、文件改为内存输入时，验证规则无需改动。重构期间真实运行记录应单独保存：执行的命令、输入样本、退出码、标准输出与错误输出；教材中的示例只能说明方法，不能替代本机证据。

**快速自检**

1. 核心包是否导入了文件系统或编解码包？若是，边界可能泄漏。  
2. 格式解析失败与业务验证失败是否有不同、稳定的错误分类？  
3. 返回的切片、映射是否可能被调用方修改？若可能，是否复制或写明所有权？  
4. 替换存储格式后，CLI 的参数、输出和退出码能否保持不变？  
5. 这一步是否只移动依赖，未顺带新增字段、默认值或业务规则？若新增，应留到阶段4。

### 阶段3：拆分检查CLI与消费方接口

### 阶段3：拆分检查 CLI 与消费方接口

阶段3不改变检查规则，只让“谁负责什么”变得可见：命令层处理参数、输出和退出码；检查逻辑接收已准备好的数据；数据访问层负责文件路径、读取与反序列化。依赖方向应始终朝内：

`cmd → check → 数据接口 ← 文件适配器`

命令层不应直接解析数据文件，否则同一检查无法被测试、批处理或未来服务接口复用。检查包也不应导入具体文件适配器；它只依赖自己消费的数据能力。

```go
type ProfileSource interface {
    LoadProfile(id string) (Profile, error)
}

func CheckProfile(src ProfileSource, id string) ([]Issue, error)
```

接口由消费方定义且保持小：若检查只需按 `id` 取得 `Profile`，就不要暴露 `List`、`Save`、`Delete`。文件实现可在外层组装：

```go
src := filedata.NewProfileSource(root)
issues, err := check.CheckProfile(src, id)
```

命名应描述职责而非实现细节。`ProfileSource` 比 `FileReader` 更稳定；`CheckProfile` 比 `Run` 更明确。导出的 `ProfileSource`、`CheckProfile` 需有以名称开头的注释，说明合同：找不到数据、格式错误和业务检查失败分别如何返回。尤其不要把“发现问题”混同为程序错误：可检查的 `Issue` 通常是正常结果，文件不可读才是 `error`。

重构记录应分别保存：原 CLI 输入、退出码、标准输出/错误输出，以及重构后同一命令的对比。不要在本阶段顺便新增字段别名、改变默认路径或修改问题文本；这些属于后续 v2 的业务变化，而非接口拆分。

### 阶段4：将v2业务变更独立立项

### 阶段4：将 v2 业务变更独立立项

阶段0—3的目标是**保持 P1 本地 CLI 的既有外部合同**；v2 则允许有意改变合同。两者不能混在同一变更中：

| 类型 | 是否改变外部行为 | 主要证据 | 回退方式 |
|---|---|---|---|
| 重构 | 否 | 旧合同测试、命令行快照、真实运行记录 | 回退实现提交 |
| 修复 | 仅修正已确认的违约行为 | 缺陷复现、期望合同、回归测试 | 回退修复提交 |
| v2 功能 | 是，且需声明新合同 | 需求说明、v1/v2 对比、迁移测试 | 开关、兼容层或回退版本 |

v2 单独立项应写明：新增/废弃命令、输入输出、退出码、错误文本、文件格式及数据别名策略。例如 `--format json` 是功能；把验证函数移入新包而输出不变是重构。真实运行记录应注明机器、命令、输入、时间和结果；教材中的示例输出只是**静态证据**，不能伪装为真实执行日志。评审先确认“这是 v2 业务变化”，再确认迁移、兼容、灰度与回退点。

#### 分层练习（含反馈）

1. 输出不变地拆分函数属于？  
   **反馈：**重构。

2. 修正错误退出码属于？  
   **反馈：**若旧合同规定该退出码，属于修复。

3. 新增 `--dry-run` 属于？  
   **反馈：**v2 功能。

4. 为什么不能以教材截图代替运行记录？  
   **反馈：**截图可复制，不能证明当前代码真实执行。

5. 重构提交应包含什么基线？  
   **反馈：**v1 命令、样例数据、输出与退出码。

6. v2 评审先看什么？  
   **反馈：**新旧合同差异，而非内部代码优雅度。

7. 把 `users` 改名为 `accounts` 是否必然重构？  
   **反馈：**否；若脚本依赖该字段，就是接口变化。

8. 数据别名的安全策略？  
   **反馈：**同时接受旧名与新名，并规定弃用期限。

9. 删除旧别名应放在哪个阶段？  
   **反馈：**独立的破坏性 v2 计划中。

10. “重命名并顺便改变默认路径”有什么问题？  
    **反馈：**混合重构与功能变化，难定位回归。

11. 错误文案改变是否是接口变化？  
    **反馈：**若用户、脚本或测试依赖它，就是。

12. 哪种证据证明文件适配隔离成功？  
    **反馈：**纯验证测试无需访问真实文件。

13. 包边界评审要问什么？  
    **反馈：**业务包是否依赖具体文件、命令行或全局状态。

14. 注释应解释什么？  
    **反馈：**约束与原因，不复述代码动作。

15. “v2 更好，所以直接替换”是好计划吗？  
    **反馈：**不是；缺少迁移与回退。

16. 回退点应位于何处？  
    **反馈：**每个可独立验证、可部署的提交后。

17. 真实记录最少包含什么？  
    **反馈：**命令、输入、环境、输出、退出状态。

18. 静态教材证据的正确用途？  
    **反馈：**说明预期和教学路径，不宣称已运行。

19. v2 新增字段但保持旧字段，属于什么策略？  
    **反馈：**兼容扩展。

20. v2 删除字段前必须补什么？  
    **反馈：**弃用公告、迁移说明、兼容窗口和测试。

21. 一个提交同时改包名、修 bug、加子命令，评审结论？  
    **反馈：**拆分；三类变化的证据与回退粒度不同。

22. 最终验收如何区分阶段3与阶段4？  
    **反馈：**阶段3证明“行为未变”；阶段4证明“新行为被明确批准且可迁移”。

> **要点** — 先以合同和证据锁定行为，再逐层收拢职责；v2业务变化不得伪装成重构。
