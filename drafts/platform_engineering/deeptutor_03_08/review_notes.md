## 教学重组

- 先明确 `write` 调用结果、当前运行时路径可见性、掉电后耐久三种不同合同；当前业务是 P1 本地导出，不偷换为 S2 HTTP 内存受理或 S3 提议的数据库提交。
- 用直接 `O_TRUNC` 覆盖旧版构造空文件/部分新版反例，再按同目录临时文件完整写、文件 `fsync`、检查 `close`、单次 `rename` 覆盖已有目标、父目录同步逐步增加保证。
- C0–C4 表格分别记录已完成步骤、当前可见版本、崩溃后有无足够证据；22 道分层题要求学习者先判断再展开反馈。

## 技术修订

- 原稿在多个位置使用不同的同步顺序，包括“改名后才同步新文件”和“先同步临时文件再改名”。正式页固定 **写完整→文件同步→关闭检查→改名→目录同步**，没有把它们当成可任意交换的步骤。
- 原稿部分 C2 表格把文件 `fsync` 后的**临时名字**直接写成可恢复；文件同步不自动同步父目录项。正式页只称 V2 文件内容有同步证据，临时名字掉电后是否存在仍未证明。
- 原稿有 C3 崩溃后“旧版或新版二选一”的过强表述。正式页只给出运行时新路径可见 V2，以及目录切换的崩溃后耐久**未证明**；不对未经验证的文件系统恢复状态作封闭枚举。
- 原稿有 `File.Write` 成功后数据可能仍在用户态缓冲的笼统说法。正式页只依据系统调用/Go File 入口讨论实际 n 与内核/设备后续写回，不推断额外用户态缓冲。
- `rename` 的同文件系统原子可见性与文件/目录分别同步的职责，按 Linux `rename(2)`、`fsync(2)` 和 OSTEP 核对；旧 FD 仍指旧 inode，03.07 的“先改旧名再创建原名”两步流程有空档，与本章覆盖已有目标不同。
- 即使同步均成功，业务内容校验、文件系统/设备兑现刷新、跨平台行为和设备故障仍是限定条件；不能用文件系统日志自动证明应用记录正确或设备已收到 IM 消息。
