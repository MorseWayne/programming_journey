## 教学重组

- 当前 S2 `accepted_in_memory`、拟议 S3 `stored_in_teaching_db` 和额外纸上权威读合同 L 严格分开；不把 08.06 的独立 Raft 消息日志玩具与 S3 SQL 同时说成部署的双权威。
- C0–C9 每阶段都列稳定身份、可确认结果和恢复来源；C4 SearchIndex 与 C5 Notify 可并行，C6 网关尝试不能代表 C7 设备收到或 C9 已读。
- 三个裂缝是 Commit 回应丢、broker 发布 ACK 丢与 E-bad(P0:44)/E11(P0:45) 队头阻塞；后半再加入元数据少数分区、旧 G1 迟到、b1 epoch7→8、协议 v1/v2、B 25h 离线与 `u-c` 越权。
- 验证分三类：同库消息/outbox 原子快照，额外声明的权威读 L 的调用历史，以及 SearchIndex/Notify/设备各自有期限的追赶/回执，不用一项绿色代替全链。

## 技术修订

- 原稿曾写“S2 提交回应未知时按 client_message_id 查内存记录，已存在则返回原 message_id”，与当前 S2 同 ID 即使同内容仍 409、且不承诺持久恢复的合同冲突。正式页保持 409，未来 S3 的状态查询另按新合同评审。
- 原稿毒事件段落说主消费位点可越过并登记跳过理由，容易让 E-bad 在严格同会话顺序下被静默 ACK。正式页要求是否前进由显式派生缺口政策裁决，保存隔离/修复和对账责任。
- 原稿有“旧 relay 向 broker 发布请求会被 epoch 围栏拒绝”的直接断言，未证明 broker 校验该应用 epoch。正式页改成发布所有权交接与稳定事件 ID/下游幂等，承认重复/未知。
- 原稿同一篇里给 C0–C9 分配了多套不同阶段名称。正式页只用一张 C0–C9 表，并明确它和先前章节的同名故障编号不是同一坐标。
- 原稿混用 `m9:v2` 消息版本与 `event_v2` 线格式版本；正式页单独标注两个版本轴，迟到 `evt:m-9:v1` 不能覆盖权威 `m-9:v2`。
- 固定 OpenIM 两段源码只能证明所述发送入队返回和另一 MongoDB 消费调用，不能据此证明教学 SQL、元数据复制、N9、线性化读或设备送达已实现。
