### 先锁定当前版本的事实边界

### 先锁定当前版本的事实边界

讨论资源故障前，先把当前 `S2/v1` 已实现的行为与未来 `S3` 方案分开。当前版本是**内存受理**模型，不包含数据库、预写日志（WAL）或落盘确认语义。

- 请求正文按原始 HTTP 请求体读取，最大为 `4096B`；超过该边界的请求不应被当作普通消息继续处理。
- 当前成功写入的消息正文固定为静态 `6` 个 UTF-8 字节。这里的“字节”不是字符数；UTF-8 字符可能占多个字节。
- 对同一消息 ID 的重复提交，返回 `409 Conflict`，表示该 ID 已存在，而不是再次创建一条消息。
- 非成员访问对应资源时，返回 `404 Not Found`。这是权限可见性语义：调用者不应据此推断资源是否真实存在。
- 成功响应 `200 OK` 仅表示服务已经在当前进程内存中受理该请求；它不表示消息已写入磁盘，也不表示进程重启后仍可恢复。

因此，`S2/v1` 中可以分析的资源压力主要是 HTTP 请求体、进程堆内存、连接与文件描述符等运行时资源。相反，“WAL 写满磁盘”“数据库提交失败”“刷盘成功后才能确认”属于未来 `S3` 持久化设计的风险与语义，不能倒写为当前版本已经发生过的事故。

后续提到 FD 耗尽、页缓存回收压力或收到 `SIGTERM` 时，也应把它们视为纸上独立变式：分别说明触发条件、可观测症状和退出策略，而非拼接成一次既发的线上故障。

### 用额度手算定位描述符耗尽

### 用额度手算定位描述符耗尽

把“描述符耗尽”当作纸上变式，而非当前 S2/v1 已发生的事故。先查看进程额度：`ulimit -Sn` 是软限制，`ulimit -Hn` 是硬限制；进程实际可用上限还会受 systemd 的 `LimitNOFILE` 影响。设软限制为 $L=1024$。

一个 IM 网关启动后并非从 0 开始使用描述符。假设它已有：

- 标准输入、输出、错误：$3$
- 监听套接字：$1$
- 日志文件、配置文件、事件轮询器等：$15$
- 上游连接或其他常驻套接字：$5$

则固定占用为：

$$F=3+1+15+5=24$$

理论上可同时维持的客户端连接数约为：

$$C_{\max}=L-F=1024-24=1000$$

但不能把 1000 当作安全容量：连接建立瞬间可能还需临时文件、DNS、日志轮转或额外上游连接，应预留余量，例如按 $80\%$ 使用，则告警线约为 $800$ 个连接。

当网关调用 `accept`、`socket`、`open` 等操作时，若**该进程**的描述符表已满，通常得到 `EMFILE`。此时监听 socket 可能仍存在，但新连接无法被接受；已有连接是否继续服务取决于其状态。错误处理若只是持续重试，会造成日志刷屏和 CPU 空转；若错误地关闭监听器，则会扩大为整体不可接入。

`ENFILE` 不同：它表示**系统全局**文件表耗尽，其他进程也可能受影响，不能仅通过提高单个服务的 `LimitNOFILE` 解决。还要辨析 `pids` 限制：它限制线程或进程数量，触发时常表现为无法创建 goroutine 所依赖的新线程、无法 `fork`，并不等同于打开文件过多。

因此，排查顺序应是：确认 `EMFILE`/`ENFILE` 错误文本，核对 `/proc/<pid>/fd` 数量与限制，再区分连接泄漏、日志文件未关闭和全局系统额度问题。当前 S2/v1 的“200 内存受理”是业务受理边界，不是 FD 容量承诺。

### 将磁盘满限定为未来WAL变式

### 将磁盘满限定为未来 WAL 变式

当前 S2/v1 的成功路径是“内存受理”：请求正文受静态大小限制，校验通过后写入进程内存并返回 `200`。它不包含数据库、预写日志（WAL）或本地持久化文件，因此不能把“磁盘满导致写入失败”描述为当前版本已经发生的事故。

未来 S3 若引入数据库，可将一次写入抽象为：

`请求校验 → 追加 WAL → WAL 刷盘/确认 → 更新内存或数据页 → 返回成功`

此时 `ENOSPC`（磁盘空间不足）才成为真实故障分支。但其报告时机不一定等于应用调用 `write` 的时机：写入可能先进入页缓存，较晚在 `fsync`、日志轮转、检查点或后台回写时才暴露失败。因而“`write` 返回成功”不自动等价于“数据已经持久”。

应先定义 S3 的提交语义：

- 若 `200` 表示仅接受到内存或页缓存，进程崩溃后该记录可能丢失。
- 若 `200` 表示持久提交，则必须在 WAL 达到约定的持久化边界后返回；`fsync` 报 `ENOSPC`、`EIO` 等错误时应返回失败，不能继续宣称写入成功。
- 若 WAL 已追加但后续数据页更新失败，需要依靠恢复流程重放或回滚，避免“客户端收到成功、查询却找不到记录”。

测试可在独立的 S3 纸上变式中构造小容量卷：持续写入直至 WAL 扩展或刷盘返回 `ENOSPC`，验证错误映射、成功响应边界、重启恢复和告警。该证据链只说明未来持久化设计的风险与要求，不应反向归因给当前无磁盘写入的 S2/v1。

### 区分页缓存压力与OOM终止

### 区分页缓存压力与 OOM 终止

页缓存压力不等于 Go 进程已经“内存泄漏”或即将被杀。Linux 会把近期读写的文件内容保留在页缓存中；当其他进程申请内存时，这部分通常可回收。即使监控显示主机已用内存很高，只要 `MemAvailable` 尚可、回收正常，Go 进程仍可能稳定服务。

匿名内存则不同：Go 堆、goroutine 栈、运行时元数据等属于匿名页，不能像文件页缓存那样直接丢弃。若请求积压、对象长期被引用或并发失控，匿名内存持续增长，垃圾回收后仍不回落，才是更直接的容量风险。

两者应按证据区分：

- **页缓存回收压力**：文件缓存较大，`MemAvailable` 下降但仍可波动；可能出现磁盘读写变慢、回收扫描增多，Go 服务延迟升高，但进程通常仍存活。
- **匿名内存增长**：进程 RSS、Go 堆指标持续上涨，GC 更频繁、暂停或 CPU 占用增加；应检查对象保留、队列长度和并发上限。
- **OOM 终止**：内核日志出现 OOM 选择与杀死进程的记录，容器可能显示 `OOMKilled`，进程退出并导致请求中断；这不是普通 GC 的结果。

当前 S2/v1 的 `200` 仅表示请求正文已在内存中受理，并不证明面对大请求、长期积压或未来 S3 数据库/WAL 写入时仍具备足够内存。页缓存压力、匿名内存膨胀与 OOM kill 应作为纸上独立变式分别验证，不能合并叙述为一次已经发生的事故。

### 以SIGTERM设计连接关停与恢复边界

### 以 SIGTERM 设计连接关停与恢复边界

设想网关进程收到 `SIGTERM`：这是一种独立的纸上变式，不表示当前 S2/v1 已发生过退出事故。目标不是“立刻杀进程”，而是在有限时间内停止接入、处理存量连接，并把未完成工作的责任边界说清楚。

1. **停止新接入**  
   收到信号后，先将实例从负载均衡或服务发现中摘除；HTTP 监听器停止接受新连接，已建立的 keep-alive 连接不再接收新请求。WebSocket 停止升级新连接，并向既有客户端发送关闭帧，例如状态码 `1001`，提示客户端重连到其他实例。

2. **排空存量请求与会话**  
   HTTP 正在执行的请求可在截止时间内完成；WebSocket 可允许短暂发送已排队消息，但不应无限等待客户端。网关应记录“开始排空”“剩余连接数”“排空超时”等事件，便于区分正常关停与异常中断。

3. **超时退出**  
   设置明确的关停预算，例如 `T_grace`。到期后主动关闭剩余连接并退出。不要把 `SIGTERM` 当作可无限延迟的通知：编排平台通常会在宽限期后发送 `SIGKILL`，后者不可捕获，进程没有机会写日志、刷新缓冲或发送 WebSocket 关闭帧。

4. **恢复责任核对**  
   当前 S2/v1 的 `200` 表示请求已在内存中受理；若进程在响应后被 `SIGKILL`，内存状态随进程消失，客户端必须依靠重试、查询或幂等标识确认结果。S2 中静态 `6 UTF8B` 正文、原始 HTTP 请求正文 `4096B`、同 ID 返回 `409`、非成员返回 `404`，都不构成跨进程持久恢复承诺。

未来 S3 若引入数据库与 WAL，恢复责任才转向“提交点、WAL 落盘与重放”；未来 S5 的连接状态、重连令牌或消息补偿也应另行定义。不能倒推出当前 S2 已具备这些能力。

> **要点** — 先以版本事实划界，再用独立证据分析资源故障；S2内存受理不等于S3/S5的持久恢复承诺。

从“还差几个连接能接入”出发，建立描述符额度、报错归因与连接行为之间的证据链。

### 先界定：一个进程到底受什么限制

### 先界定：一个进程到底受什么限制

“文件描述符耗尽”不是单一限制，而是至少三类不同对象的约束，必须先分清计数单位。

- **进程级 `RLIMIT_NOFILE`**：限制某个进程可持有的文件描述符编号上限。它通常有软限制与硬限制；软限制是当前实际执行 `open()`、`accept()`、`socket()` 等操作时遵守的额度，硬限制是普通进程可将软限制提高到的上界。监听 socket、已建立连接的 socket、日志文件、管道、`epoll` 实例、文件等都会占用 FD。若软限制为 `1024`，当前已打开 `1020` 个 FD，在“每个新连接仅新增 1 个 FD、期间没有其他打开或关闭”的玩具模型中，只剩 `4` 个名额。

- **系统级文件表限制**：内核还维护全系统共享的打开文件对象与文件表资源。即使某一进程尚未达到自己的 `RLIMIT_NOFILE`，系统范围资源也可能先耗尽；此类情形通常应考虑 `ENFILE`，而非进程自己的 `EMFILE`。

- **`pids.max`**：这是 cgroup 对任务数的限制，约束的是进程或线程等 task 的数量，不是 FD 数量。线程爆炸、频繁 fork、工作进程扩容失败，应优先检查它；单纯 socket 或日志文件过多，则不能用 `pids.max` 解释。

因此，`accept()` 或 `open()` 返回 `EMFILE`，首先指向调用进程的描述符额度；返回 `ENFILE` 才指向系统级文件表压力。不要把“连接接不进来”“客户端被拒绝”“旧连接断开”直接等同于某个错误码：监听 FD 是否仍在、accept 队列、应用错误处理与连接超时策略都需要额外证据。

### 手算余量：1024 配额为何只剩 4 个

### 手算余量：1024 配额为何只剩 4 个

先限定一个刻意简化的玩具模型：

- 进程的 `RLIMIT_NOFILE` **软限额**为 `1024`；
- 当前该进程已经打开 `1020` 个文件描述符；
- 不考虑任何其他并发的打开或关闭操作；
- 每接入一个新连接，恰好额外占用 `1` 个文件描述符。

则可用描述符余量为：

$$
\text{余量}=\text{软限额}-\text{当前已打开数}
=1024-1020=4
$$

因此，该进程至多还能成功分配 `4` 个描述符；若每个新连接只消耗 `1` 个描述符，那么理论上还能接纳：

$$
\text{可新增连接数}=4\div1=4
$$

接入第 1～4 个新连接后，打开数依次变为 `1021`、`1022`、`1023`、`1024`。此时额度已满；下一次需要创建描述符的操作，例如 `accept()` 接受连接、`open()` 打开日志或配置文件，可能失败并返回 `EMFILE`，其含义是**该进程自身的文件描述符限额已耗尽**。

这里的 `1020` 不应被误读为“已有 1020 个客户端连接”。它可能同时包含监听 socket、已建立连接的 socket、`epoll` 实例、日志文件、标准输入输出错误、管道、共享库或其他打开文件。上述“还能接 4 个连接”只在“每个新增连接只额外占 1 个 FD，且没有其他 FD 变化”的前提下成立。

### 描述符不只属于连接：清点占用来源

### 描述符不只属于连接：清点占用来源

文件描述符（FD）是进程持有内核对象的编号，不等同于“客户端连接数”。因此，估算容量时不能简单用 `RLIMIT_NOFILE - 已连接数`，而应先清点进程实际打开了什么。

常见占用包括：

- **监听 socket**：例如服务监听 `0.0.0.0:443`，即使没有客户端也会占用至少 1 个 FD。
- **已连接 socket**：每个已 `accept` 的 TCP 连接通常占 1 个 FD；但一个代理进程若同时维护下游客户端和上游后端连接，一次请求链路可能涉及多个 socket。
- **日志文件**：访问日志、错误日志、轮转后的文件句柄、审计文件等都会占用 FD。
- **事件机制对象**：Linux 上的 `epoll` 实例本身是 FD；此外还可能有 `eventfd`、`timerfd`、`signalfd`。
- **配置与资源文件**：证书、静态文件、数据库文件、Unix 域 socket、管道、共享内存相关对象等，也可能表现为 FD。
- **运行时遗留或继承的 FD**：父进程传入的 socket、守护进程重载时保留的监听器、未及时关闭的文件，都会改变基线。

例如，软限制为 `1024`、当前已打开 `1020` 个 FD 时，在“无其他打开或关闭、每个新连接只占 1 个 FD”的玩具模型中，最多只余 `4` 个额度。但真实系统中，新连接可能触发日志写入、后端拨号或临时文件打开；反过来，也可能有旧连接关闭并释放 FD。

排查应以观测为准，例如查看 `/proc/<pid>/fd/` 的条目数量与类型，或使用 `lsof -p <pid>`。先确认“1020 个 FD 分别是什么”，再讨论还能接入多少连接，才不会把描述符限额误读为纯粹的连接上限。

### 报错归因：EMFILE、ENFILE 与任务受限

### 报错归因：EMFILE、ENFILE 与任务受限

`accept()`、`open()` 等调用失败时，先看错误码，再判断资源层级；不要把所有“资源不够”都归为连接数或进程数问题。

| 现象 | 含义 | 直接检查对象 |
|---|---|---|
| `EMFILE` | **当前进程**的文件描述符表已满 | `RLIMIT_NOFILE`、`/proc/<pid>/fd` |
| `ENFILE` | **系统范围**的打开文件表已满 | 系统文件句柄上限与全机使用量 |
| 创建任务失败或受限 | cgroup 的 `pids.max` 已触顶 | cgroup 中的任务数、`pids.current`、`pids.max` |

`EMFILE` 的关键是“进程级”。若某进程软限制为 `1024`，当前已打开 `1020` 个 FD，且玩具模型假设没有其他打开或关闭操作、每个新连接只额外占用 `1` 个 FD，则理论上仅还能成功接入：

$$1024-1020=4$$

之后再次执行 `accept()`，可能得到 `EMFILE`。这里的已用 FD 不只包括已连接 socket，还可能包含监听 socket、日志文件、`epoll` 实例、管道、配置文件、共享库或其他运行时资源；因此真实余量应以进程实际 FD 清单为准，而非只数业务连接。

`ENFILE` 则表示系统级文件表压力：即使该进程尚未达到自己的 `RLIMIT_NOFILE`，全机也可能无法再分配新的打开文件条目。此时其他进程的文件、socket 与设备句柄同样构成竞争者，排查范围必须扩大到宿主机。

`pids.max` 是另一条资源链：它限制 cgroup 可创建的**任务**数量，任务通常对应进程或线程，而不是 FD。达到 `pids.max` 可能导致 `fork()`、创建线程等失败，但不能据此推出 `accept()` 必然报 `EMFILE` 或 `ENFILE`。

还需谨慎解释连接行为：`EMFILE` 只证明本次描述符分配失败，不能单独推出客户端一定被拒绝、一定排队，或既有连接一定断开。监听队列、应用错误处理、反向代理重试以及内核状态，都会影响最终可见现象。

### 连接后果：哪些能确定，哪些不能臆断

### 连接后果：哪些能确定，哪些不能臆断

在玩具模型中，进程软限制为 `1024`，已打开 `1020` 个描述符，且后续每个连接恰好额外占用 `1` 个描述符，则最多只剩 `4` 个可分配额度。额度耗尽后，进程再执行 `accept()`、`open()`、创建新 socket 等需要描述符的操作，可能得到 `EMFILE`；若是全系统文件表耗尽，则可能是 `ENFILE`。`pids.max` 限制的是任务数，不应据此解释为文件描述符耗尽。

但“出现 `EMFILE`”只能直接证明：**该进程当时无法再取得新的描述符**。它不能单独证明客户端必然立刻收到“连接被拒绝”。

- 若监听 socket 仍存在，内核可能仍完成部分 TCP 握手，并把连接暂存于监听队列；应用随后因 `accept()` 的 `EMFILE` 无法取走它们。
- 队列满、内核策略、重试与超时会影响客户端最终看到的是连接超时、重置、拒绝，还是短暂建立后被关闭。
- 应用也可能在耗尽前预留“应急 FD”，遇到 `EMFILE` 时关闭该 FD、接受一个连接并立即关闭，以提示客户端重试；这属于实现策略，不是错误码的必然含义。
- 已建立的老连接通常已经持有各自 socket FD；`EMFILE` 不会自动关闭它们。但其后续读写是否正常，还取决于事件循环、缓冲区、日志写入、磁盘空间、业务线程和超时策略。

因此应把结论限定为“新资源分配失败风险上升”，并结合 `accept` 错误日志、监听队列指标、客户端现象及老连接读写记录，判断实际连接后果。

> **要点** — 1024 配额且已用 1020 时玩具模型仅余 4；EMFILE 是进程 FD 限额，不等于系统任务或既有连接必然失效。

S3 的教学事务必须把“已写入”与“已持久”分开：磁盘相关错误可能延迟出现，内存中的成功状态不能替代可恢复承诺。

### 事务承诺与成功语义边界

### 事务承诺与成功语义边界

对未来 S3 的教学事务 `m-9/seq9` 而言，`stored_in_teaching_db` 不是“进程已经收到了请求”，也不是“对象暂存在 S2 内存”，而是一个可恢复承诺：即使网关随后退出、进程重启，也能从教学数据库及其 `outbox` 中找回该事务，并继续或重放后续教学动作。

因此，只有同时满足以下条件，接口才能返回“已存入教学数据库”的成功语义：

1. `m-9/seq9` 的业务记录已写入持久存储；
2. 对应 `outbox` 记录已与业务记录处于同一原子事务中；
3. 该事务已经提交，且提交结果满足系统规定的持久性边界；
4. 返回成功前未观察到写入、提交或同步阶段的错误。

关键陷阱是：`write()` 返回成功，只表示内核暂时接受了字节；它不证明数据已经稳定落盘。`ENOSPC` 可能在本次 `write()` 出现，也可能延迟到后续 `write()`、`fsync()`、事务提交，甚至 `close()` 才报告。故障还不只来自“磁盘容量为零”，还可能是 inode 耗尽、用户或项目 quota 用尽，或文件已被删除但仍被打开的旧文件继续占用空间。

S2 返回的内存 `200` 只能表示“本次进程内暂存成功”。若尚未达到 `stored_in_teaching_db` 的持久边界，就不得把它包装为可恢复的数据库成功；网关退出后该状态消失，`outbox` 也无法补发。正确做法是明确区分：

- `accepted_in_memory`：可丢失，不承诺恢复；
- `stored_in_teaching_db`：已提交、可恢复；
- `outbox_pending`：已持久，但副作用尚待投递。

### ENOSPC 的延迟报错路径

### ENOSPC 的延迟报错路径

`ENOSPC` 并不保证在第一次 `write()` 时立即出现。对教学事务 `m-9/seq9+outbox`，应把一次写入拆成“内核接受字节”与“稳定落盘”两个阶段：

1. **`write()` 当场失败**  
   文件系统无法分配数据块、元数据或 inode 时，`write()` 可直接返回 `-1`，并置 `errno=ENOSPC`。此时 WAL 记录或 outbox 内容未获得写入承诺，不能返回 `stored_in_teaching_db`。

2. **首次 `write()` 成功，后续 `write()` 才失败**  
   首次调用可能只把数据复制进页缓存；真正分配块、回写脏页或扩展文件时，空间耗尽才暴露。因而“已写入若干字节”只能说明本次调用被接受，不能证明整条教学事务已持久。

3. **`fsync()` 才报告失败**  
   `fsync(fd)` 迫使相关脏数据及必要元数据落盘。若回写阶段发现 `ENOSPC`、配额不足或设备错误，`fsync()` 才是失败点。只有 WAL 与 outbox 的必要文件均 `fsync` 成功，才可将 `stored_in_teaching_db` 作为可恢复承诺返回。

4. **`close()` 才报告失败**  
   某些延迟写回错误可能在关闭描述符时才可见；因此必须检查 `close()` 返回值。忽略它会把“关闭失败”误判成“事务已提交”。

可将安全判定概括为：

$$
\text{可宣称已存储}=
\text{write 成功}\land\text{fsync 成功}\land\text{close 成功}
$$

S2 返回的内存 `200` 仅表示进程暂时接受请求；若持久化链路尚未完成，它不能替代上述承诺。排障时还应区分：数据块耗尽、inode 耗尽、用户或项目 quota 耗尽，以及“文件已删除但仍被进程打开”导致空间尚未回收。

### 空间、inode、配额与未释放文件

### 空间、inode、配额与未释放文件

`ENOSPC` 并不总是“磁盘容量用完”。对 m-9/seq9+outbox 而言，必须先辨认耗尽的是哪一种资源；否则即使清理了“看起来很多”的文件，WAL 或教学数据库仍可能无法追加。

| 类型 | 典型证据 | 常见误判 | 处理方向 |
|---|---|---|---|
| 磁盘块耗尽 | `df -h` 显示目标挂载点接近 `100%`；大文件、WAL、日志持续增长 | 只查看整个主机，而非实际数据目录所在挂载点 | 清理或扩容该挂载点，保留恢复所需 WAL |
| inode 耗尽 | `df -i` 的 inode 使用率为 `100%`，但 `df -h` 仍有容量 | “还有几十 GB，为什么不能创建文件？” | 删除海量小文件、临时文件、分片或缓存条目 |
| 配额耗尽 | 文件系统尚有余量，但该用户、项目或容器写入失败；配额工具显示超限 | 把容器内可见空间当作可用配额 | 提升或释放用户/项目/容器配额，确认限制对象 |
| 删除但仍打开 | `df -h` 很高，目录统计却找不到对应大文件；进程仍持有标记为 deleted 的文件 | 认为 `rm` 后空间已立即归还 | 定位持有描述符的进程，安全重启或关闭文件句柄 |

删除目录项只会让文件名消失；只要某进程仍打开该文件，数据块仍被占用。可通过 `lsof +L1` 或检查 `/proc/<pid>/fd` 发现这类“已删除但未释放”的文件。

教学事务不能因 S2 内存中已有 `200` 状态就宣称 `stored_in_teaching_db`。若 WAL、数据文件或 outbox 因上述任一限制未能完成可恢复写入，`write` 的暂时成功也不足以构成持久承诺；错误还可能在后续 `write`、`fsync`，甚至 `close` 才暴露。

### m-9/seq9 加 outbox 的持久提交流程

### m-9/seq9 加 outbox 的持久提交流程

对教学事务 `m-9/seq9`，应用层应把“接受请求”“业务记录可恢复”“消息可投递”拆成不同阶段。只有 `stored_in_teaching_db` 所需的 WAL、教学事务记录及 outbox 均已按承诺持久化，才能返回对应成功语义；S2 中的内存 `200` 仅表示进程暂时看见了结果。

推荐顺序如下：

1. **校验幂等键与状态**：查询 `m-9/seq9`。若已有已持久提交记录，直接返回其既有结果；若存在未完成记录，则进入恢复或重试路径，不能再次生成独立事务。
2. **写入 WAL 意图**：追加“准备提交”的 WAL，包含请求摘要、目标教学记录、outbox 事件标识及幂等键。`write` 成功只代表数据进入内核缓冲，尚不能宣称持久。
3. **写入教学事务记录与 outbox**：在同一可恢复提交边界中保存业务状态和待发送事件，例如 `TeachingStored(m-9, seq9)`。outbox 必须与教学记录具有一致的提交结果：不能出现业务已提交但事件完全无迹可寻。
4. **同步持久化并确认**：执行必要的 `fsync`/提交操作；若接口承诺“已存入教学数据库”，应在该步骤成功后才返回成功。注意 `ENOSPC` 可能在后续 `write`、`fsync`，甚至 `close` 才报告。
5. **异步投递 outbox**：后台投递者读取已提交事件，向下游发送；发送成功后再持久化“已投递”标记。投递可重复，因此消费者必须按事件 ID 去重。

失败时，任何 `write`、`fsync` 或 `close` 错误都应使本次请求返回未确认成功，并保留足够状态供恢复判断。磁盘空间不足、inode 耗尽、用户 quota 限制，以及“文件已删除但仍被进程打开”都可能导致看似有空间却无法完成持久化。重试边界应放在“尚未确认提交”或“已确认但可按幂等键读取结果”处，而不是简单重放整段业务逻辑。

### 故障注入与恢复验收

### 故障注入与恢复验收

以事务 `m-9/seq9` 为例，先明确验收断言：只有教学数据库中的业务记录与 outbox 记录都已达到可恢复状态，接口才能返回 `stored_in_teaching_db`。S2 的内存 `200` 仅表示“进程当时接受”，不能证明重启后仍可查询或投递。

可设计三组注入：

- **WAL 写入遇到 `ENOSPC`**：在 `write` 时注入失败。应返回资源失败，不得留下可见业务成功；重启后不得出现仅有业务记录、缺少 outbox 的半提交状态。
- **延迟报错**：允许 `write` 成功，但令后续 `write`、`fsync` 或 `close` 返回 `ENOSPC/EIO`。此时先前返回值不构成持久化证明；若尚未完成所需同步与原子提交，仍不得返回 `stored_in_teaching_db`。
- **提交后立即杀进程**：分别在业务记录落盘前、outbox 落盘前、两者提交后但响应前终止。重启恢复应将前两类视为未成功或可安全回滚；最后一类可恢复为已存储，并允许客户端重试得到幂等结果。

验收时还应分别耗尽**块空间、inode、用户 quota**，并测试“文件已删除但仍被进程打开”导致空间未释放的情形。恢复扫描的责任是重建 S3 已承诺的教学记录与待投递 outbox；未来 S5 只负责从已持久的 outbox 重试投递、去重和确认，不能替 S3 补造丢失的持久化承诺。

> **要点** — 只有持久提交成功后才能兑现已存储承诺；write 成功、内存状态与可恢复状态均不可混同。

容器内存告警不能只看主机剩余内存；应以 cgroup 限额、事件计数与进程实际内存构成为证据判断压力和恢复边界。

### 从主机视角切换到容器内存边界

### 从主机视角切换到容器内存边界

主机仍有大量“可用内存”，并不意味着某个容器没有内存压力。容器首先受自身 cgroup 边界约束：`memory.current` 表示该 cgroup 当前计入的内存使用量，比较对象应是 `memory.high` 与 `memory.max`，而不是主机的 `MemAvailable`。

- `memory.current < memory.high`：通常尚未触发高水位压力，但仍需观察增长速率与缓存构成。
- `memory.current` 持续逼近或越过 `memory.high`：内核会开始对该 cgroup 施加回收和限速压力，优先回收可回收页缓存；业务未必 OOM，但文件读写、写回、分配内存都可能变慢。
- `memory.current` 逼近 `memory.max`：可回收页面不足时，新的内存分配可能失败；若无法释放足够内存，才可能触发该 cgroup 内的 OOM 处理与进程终止。

可将容器边界理解为独立配额池：即使主机还有空闲页，容器也不能自然“借用”超过 `memory.max` 的额度。反过来，`memory.current` 下降也不必然说明业务 RSS 降低，可能只是页缓存被回收。

排障时应同时读取：

`memory.current`、`memory.high`、`memory.max`、`memory.events`

其中 `memory.events` 的 `high` 增长说明发生过高水位节流或回收压力，`max` 增长说明曾撞击硬上限，`oom_kill` 增长才是进程被内核杀死的直接证据。不要用主机空闲内存替代这些 cgroup 证据。

### 内存逼近上限时的两条路径

### 内存逼近上限时的两条路径

设 cgroup 的当前用量为 `memory.current`，硬上限为 `memory.max`。当 `memory.current` 持续逼近上限，并不意味着进程会立刻被 OOM 杀死；内核通常先尝试在该 cgroup 内回收可回收内存，形成“回收—节流”与“分配失败—OOM”两条递进路径。

- **路径一：页缓存回收与 `memory.high` 压力。**  
  文件读取、日志写入等 I/O 会形成页缓存，它计入 cgroup 内存用量，但不等同于进程匿名 RSS。压力出现时，内核可回收较少使用的文件页缓存，使 `memory.current` 暂时下降。因此，业务可能表现为磁盘读取增多、缓存命中下降、请求延迟升高，而不会发生 OOM。  
  若配置了 `memory.high`，超过该阈值的分配会受到直接回收和节流影响：进程仍可运行，也可能继续接近 `memory.max`，但分配路径变慢，尤其容易放大 I/O 延迟。此时应观察 `memory.events` 中 `high` 的**增量**，而非只看某一刻的内存占比。

- **路径二：触达 `memory.max` 后的失败与 OOM。**  
  当页缓存已难以回收、匿名页又无法释放，新的内存分配会触及 `memory.max`。内核先尽力在该 cgroup 内回收；仍无法腾出所需页面时，分配可能失败，或触发 cgroup OOM 选择受害进程。`memory.events` 的 `max` 增加表示曾因硬上限进入受限分配/回收，`oom` 表示发生 OOM 条件，`oom_kill` 增加才说明实际有任务被杀。

因此，`RSS` 或 Go heap 未显著增长，也不能排除容器内存压力：页缓存、内核记账及回收节流都可能让 `memory.current` 接近限额。主机仍有空闲内存同样无关紧要；cgroup 的 `memory.max` 是该容器可用内存的边界。

### 用 memory.events 还原压力证据

### 用 `memory.events` 还原压力证据

`memory.events` 是 cgroup v2 的累计事件计数，应记录两次采样的差值，而非只看当前值。它回答的是“该容器是否真正碰到内存控制边界”，比主机剩余内存、应用堆大小更直接。

- `high` 增加：内存使用超过 `memory.high`，内核开始施加回收与限速压力。此时可能回收页缓存、压缩或回收匿名页，业务常表现为 I/O 延迟升高、吞吐下降、请求抖动；并不意味着已经 OOM。
- `max` 增加：分配尝试触及 `memory.max`，内核已无法按普通路径满足内存请求，会更激进地回收。若持续增长，说明容器反复顶到硬上限，即使 `memory.current` 随后下降，也不能据此判定恢复。
- `oom` 增加：cgroup 内发生了无法满足的内存分配，即 OOM 条件被触发；它说明压力已越过“变慢”的阶段，但不必然代表进程已被杀。
- `oom_kill` 增加：内核实际选择并杀死了该 cgroup 中的任务，是最强的故障证据。应立即关联容器重启、退出码、应用日志和存活探针失败时间。

可按时间窗判断：仅 `high` 增加而 `max=0`，多为持续软压力；`max` 增加但 `oom_kill=0`，属于反复触顶、侥幸回收成功；`oom` 与 `oom_kill` 同增，则已发生真实杀进程。与此同时对照 `memory.current`、RSS 与 Go heap：三者都不能替代事件计数。页缓存、内核记账和非 Go 分配都可能使容器承压，即使主机仍有空闲内存。

### RSS、页缓存与 Go 堆为何不相等

### RSS、页缓存与 Go 堆为何不相等

这三个指标回答的问题不同，不能互相替代：

| 指标 | 统计范围 | 主要诊断含义 |
|---|---|---|
| `memory.current` | cgroup 内被记账的内存 | 容器距离 `memory.max`、`memory.high` 的真实压力 |
| 进程 RSS | 进程当前驻留的匿名页与文件映射页 | 某个进程实际占用的物理页规模 |
| 文件页缓存 | 读写文件后保留在内核中的缓存页 | I/O 是否通过缓存占用容器额度、是否可能被回收 |
| Go heap | Go 运行时管理的堆对象及其相关统计 | Go 业务对象、分配速率、GC 效果 |

`memory.current` 往往大于应用报告的 Go heap：除 Go 堆外，还可能包含 goroutine 栈、运行时元数据、`mmap`、动态库、内核为该 cgroup 记账的页缓存，以及其他进程的内存。反过来，RSS 也不等于“不可回收内存”：其中的文件映射页可能在压力下被回收，而匿名页通常更难立即释放。

例如，服务批量扫描大文件后，Go heap 仍稳定在 `500MiB`，进程 RSS 为 `1.2GiB`，但 `memory.current` 升至 `3.8GiB/4GiB`。此时更合理的解释可能是容器积累了页缓存，而非 Go 堆泄漏。若 `memory.events` 中 `high` 持续增长，内核已开始施加 `memory.high` 回收与节流压力，业务会表现为读写变慢；即使主机仍有空闲内存，也不能据此否定容器压力。

排查时应同时观察增量：`memory.current`、`memory.stat` 中的 `anon` 与 `file`、进程 RSS、Go 的 `HeapAlloc`/`HeapInuse`，以及 `memory.events` 的 `high`、`max`、`oom_kill`。只有 `anon`、RSS 和 Go heap 一起持续增长，才更接近 Go 堆或进程私有内存膨胀；若主要增长的是 `file`，优先检查缓存型 I/O 与回收行为。

### IM 服务变慢但未 OOM 的处置边界

### IM 服务变慢但未 OOM 的处置边界

IM 服务出现发送延迟、消息落盘变慢或新连接握手超时，而容器尚未被 OOM Kill 时，应按“内存压力导致 I/O 退化”处理，而非等待进程退出。`memory.current` 接近 `memory.max` 时，内核可能持续回收页缓存；消息持久化依赖的文件页缓存缩水后，写入更频繁地下沉到磁盘，尾延迟会先于 OOM 明显恶化。若触发 `memory.high`，cgroup 还可能对分配路径施加回收与节流。

S2 受理期内优先执行：

- 对新建连接、群发、历史消息拉取和大附件上传限流；保留已建立会话、心跳、鉴权和关键消息投递。
- 降低持久化批次的内存堆积：缩短队列上限、拒绝超大消息、限制重试风暴，避免待写消息同时占用 RSS 与 Go heap。
- 观察增量而非单点值：`memory.events` 中 `high` 持续增长表示已越过压力阈值，`max` 增长表示碰到硬上限并发生分配失败/强制回收；`oom_kill` 未增长只能说明尚未杀进程，不能说明没有压力。
- 同时采集 `memory.current`、`memory.max`、`memory.high`、容器 RSS、Go heap、文件缓存、磁盘写延迟与消息队列深度。RSS 或 Go heap 未显著上升，也可能是页缓存回收造成持久化变慢。

不要因主机仍有空闲内存就放宽判断：容器受自身 cgroup 上限约束，主机空闲页不能自动突破 `memory.max`。

向 S3/S5 交接时明确：限流规则与豁免业务、`high/max/oom_kill` 的时间增量、队列积压与磁盘延迟、是否发生重启，以及恢复条件。恢复应满足事件计数停止快速增长、`memory.current` 持续回落并保留安全余量、消息积压下降后，再分阶段解除限流。

> **要点** — 容器内存压力以 cgroup 限额和事件增量判定；I/O 变慢可能源于回收与节流，并不等于已发生 OOM。

资源故障下的正确退出，不是“收到信号就结束”，而是先停止接入、处理在途请求、处置长连接，并明确哪些内存状态不能恢复。

### 从信号语义建立退出边界

### 从信号语义建立退出边界

`SIGTERM` 表示“请求进程自行终止”：程序可以捕获它，并把一次外部终止转化为**可控退出流程**。收到该信号后，服务不应立刻调用 `os.Exit`，而应进入明确阶段：

1. **停止接入**：标记实例为不可用，摘除负载均衡或就绪检查；随后关闭监听器，使新连接不再进入。
2. **处理在途请求**：为已有请求设置统一的截止期限，允许正常完成；超时后取消其上下文或执行降级。
3. **处置长连接**：WebSocket、hijacked 连接等通常不随普通 HTTP 关闭自动结束，应由应用通知客户端、停止读写并等待有限时间。
4. **退出进程**：关闭后台任务、刷新必要的持久化状态，然后返回主流程，由进程自然退出。

这是一条“尽力而为”的边界：`SIGTERM` 给了程序收尾机会，但不保证所有请求、所有内存数据都能保住。退出期限必须小于编排平台的终止宽限期，否则后续强制终止会打断收尾。

`SIGKILL` 则完全不同。它不能被捕获、忽略或延迟；内核会直接终止进程。因此，任何依赖信号处理器执行的逻辑——例如写入内存队列、更新本地状态、通知长连接——在 `SIGKILL` 下都没有保证。

尤其不要假设进程退出后，实例 `S2` 的内存状态会在未来实例中恢复。重启后的 `S3` 应重新向权威存储查询事实；只有已成功持久化、且具备一致性语义的数据，才能作为恢复依据。

### SIGTERM：停止接入与在途期限

### SIGTERM：停止接入与在途期限

`SIGTERM` 是“请求进程退出”，不是“立刻销毁进程”。程序应捕获该信号并进入排空（drain）阶段：先拒绝新的工作，再给已经开始的工作一个有限完成窗口。

典型顺序如下：

1. **切换就绪状态**：将健康检查或就绪检查改为失败，使负载均衡器停止把新请求路由到本实例。若有服务注册中心，也应先注销或标记为不可接流量。
2. **停止接受新连接**：调用 `http.Server.Shutdown(ctx)`。它会关闭监听器，因此后续 TCP/HTTP 新连接不能进入；对 keep-alive 连接，服务器也会尽量避免继续复用。
3. **设定全局截止时间**：使用带超时的上下文，例如 `context.WithTimeout(context.Background(), 25*time.Second)`。这段时间是“在途请求仍可完成”的预算，而不是无限等待。
4. **等待可完成工作**：`Shutdown` 会等待活动 HTTP 请求结束并变为 idle。请求处理函数应传播 `ctx.Done()`，让数据库查询、下游调用、队列投递等能够在期限临近时主动取消。
5. **期限到达后退出**：若仍有请求未结束，`Shutdown` 返回超时错误；程序应记录未排空情况并退出。不要为了等待少数卡住的请求而无限延长进程寿命。

可将停止过程理解为状态转换：

`接流量 → 不再就绪 → 关闭监听器 → 等待在途请求 → 到期退出`

关键在于“等待”必须有边界。没有截止时间，慢查询、失效下游或卡死的客户端会使发布、扩缩容和故障恢复永久阻塞；截止时间过短，则会无谓中断本可完成的请求。该期限应小于平台提供的终止宽限期，并为日志刷新、连接关闭及最终退出预留余量。

### Shutdown实际等待什么

### Shutdown实际等待什么

`net/http.Server.Shutdown(ctx)` 的核心语义是“停止接入，并等待普通 HTTP 服务自然排空”，而不是无条件等待整个进程中的所有连接与任务结束。

调用后，服务器会先关闭 `listener`：

- 不再接受新的 TCP 连接；
- 已建立但尚未发送请求的连接，不应再被当作新的业务入口；
- 正在处理中的 HTTP 请求仍可继续执行；
- 空闲 HTTP keep-alive 连接会被关闭，避免它们无限占用退出时间。

随后，`Shutdown` 会轮询等待服务器管理的活动 HTTP 连接变为 `idle`，即请求处理完成、不再处于活跃读写状态。若所有这类连接都排空，`Shutdown` 返回；若 `ctx` 到期，则返回上下文错误，例如 `context deadline exceeded`。这表示优雅退出期限已耗尽，而非请求一定已经停止。

可将过程理解为：

`停止监听 → 拒绝新接入 → 在途 HTTP 请求完成 → 活动连接清空 → Shutdown 返回`

但“活动 HTTP 连接”有重要边界。通过 `Hijacker` 劫持的连接不受 `Shutdown` 等待，例如 WebSocket、部分升级协议连接或自行接管的原始 TCP 流。对 `net/http` 而言，它们已经脱离普通 HTTP 生命周期；即使 `Shutdown` 返回，这些连接也可能仍在运行。

因此，WebSocket 等长连接必须由应用额外治理：停止新会话创建，向客户端发送关闭通知，等待有限期限，并在总退出截止时间到达时主动关闭底层连接。不能把 `Shutdown` 返回误解为“所有用户会话和后台任务均已完成”。

此外，`Shutdown` 只协调当前进程内的服务状态。进程退出后，内存中的 S2 状态不具备恢复承诺；后续实例 S3 必须从数据库、消息系统或其他权威持久化来源重新确认事实。

### WebSocket不是普通HTTP在途请求

### WebSocket不是普通HTTP在途请求

普通 HTTP 请求有明确的“在途”边界：`Server.Shutdown(ctx)` 会关闭监听器，拒绝新的连接与请求，并等待活动请求完成、连接回到空闲状态。因此，收到 `SIGTERM` 后，服务可以先停止接入，再在截止期限内让已有请求自然返回。

WebSocket 的生命周期不同。完成 HTTP Upgrade 后，连接通常已被 `Hijack`，不再由 `net/http.Server` 按普通 HTTP 连接管理。`Shutdown` 不会等待这些连接关闭，也不会自动向客户端发送“服务即将下线”的通知：

| 对象 | `Shutdown` 的处理 | 应用需要做什么 |
|---|---|---|
| 普通 HTTP 在途请求 | 等待其完成或上下文超时 | 尽快完成响应、传播取消信号 |
| 空闲 HTTP keep-alive 连接 | 关闭或不再接受后续请求 | 通常无需额外管理 |
| WebSocket / 被劫持连接 | 不等待，不保证自动关闭 | 自行通知、关闭、等待退出 |

因此，应用应维护 WebSocket 会话注册表。进入排空阶段时：先停止新会话建立；向现存客户端发送关闭帧或“服务维护中”消息；等待客户端主动断开或在期限到达后强制关闭底层连接。等待对象应是应用维护的会话计数或 `WaitGroup`，而不是仅依赖 `Server.Shutdown` 返回。

若期限耗尽仍有长连接，进程必须按退出策略继续结束；此时客户端可能看到断连，并在 S3 启动后的新实例上重新连接。不要承诺 S2 内存中的订阅关系、未发送消息或会话状态一定能够恢复；恢复依据应来自外部权威存储，而非旧进程内存。

### 资源故障后的恢复承诺边界

### 资源故障后的恢复承诺边界

设 S2 为当前进程内存中的受理状态，例如：已通过校验但尚未落库的请求、幂等键缓存、排队任务、WebSocket 会话映射、临时重试计数与正在执行的后台操作。资源故障导致进程退出后，S2 随地址空间一并消失；即使客户端曾收到“已受理”响应，也不能仅凭这份内存状态承诺其最终完成或可恢复。

因此，恢复时必须区分“可证明的持久事实”和“已丢失的运行时事实”：

- S3（如数据库、对象存储、消息队列）中的已提交记录，才可作为任务是否创建、订单是否落账、文件是否写入的权威依据。
- S5（如外部支付、第三方接口、远端服务）的执行结果必须重新查询、回调核验或按幂等键补偿；不能把退出前的本地“调用中”“大概成功”当作结论。
- 对仅存在于 S2 的请求，恢复策略应是“未知”，而非默认成功或默认失败。需要通过请求标识、事务记录、消息投递记录或外部查询重新判定。
- 若业务需要承诺“受理后必可恢复”，受理成功前就必须将必要意图持久化，例如写入事务日志、可靠队列或数据库状态；内存队列不能承担此承诺。

优雅退出只能尽量缩短不确定窗口，不能消除它。`SIGTERM` 下停止接入、限定在途请求期限并等待可控工作完成，是为了让更多状态进入 S3；`SIGKILL`、磁盘满、描述符耗尽等场景仍可能让进程在持久化前中断。故恢复流程应以“查询权威状态、幂等重放、补偿未知项”为中心，而不是试图从已退出进程的 S2 重建事实。

> **要点** — 优雅关停依赖SIGTERM和应用协作；SIGKILL不可接管，WebSocket与内存状态都不能被HTTP关停机制自动保全。

以同一时间窗内的连接失败、客户端断线与消息状态未知为线索，建立可证伪的资源故障排查路径。

### 先按时间窗拼接症状与实例证据

### 先按时间窗拼接症状与实例证据

不要分别处理“A 连不上”“B 断线”“m-9 状态未知”。先确定统一时间窗：以用户首次报错为中心，向前后各扩展一段缓冲，例如 $[t_0-5\text{ min},\,t_0+10\text{ min}]$；再按实例、连接和消息三条线拼接。

- **请求线**：记录 A 的发起时间、目标地址、错误类型与持续时间。区分连接建立超时、已建立连接后的读写超时、立即被拒绝；同一时段内是否有其他请求成功。
- **连接线**：定位 B 的断线时刻、连接标识、最后一次收发数据及关闭方向。若服务端日志只有 `accept EMFILE`，它更能解释“新连接失败”，未必能解释既有 B 为何断开。
- **消息线**：为 m-9 建立状态序列：发送确认、网关接收、下游投递、持久化、消费确认。`状态未知`表示证据链中断，不等于消息丢失；应查询是否存在重复投递、延迟落库或消费者确认。
- **实例线**：对齐实例启动时间、容器重建、进程退出码、退出信号、负载均衡摘除与恢复时间。重启后恢复只能说明故障被重置，不能证明根因是“偶发网络”。

时间线应允许反证。例如，若 A 超时早于实例重启且同时出现连接数骤降，优先检查网关或网络路径；若 `memory.events` 中 `oom_kill` 紧邻断线，而重启日志显示被 `SIGKILL` 终止，则“应用主动关闭连接”的解释应被推翻。每个推断都要标明：它解释了哪些症状、仍无法解释什么，以及需要哪条日志或监控指标来证伪。

### 接入失败：用accept错误区分FD与任务耗尽

### 接入失败：用 `accept` 错误区分 FD 与任务耗尽

连接超时不能直接等同于“网关挂了”。先看监听进程的 `accept()` 返回值：`EMFILE` 表示**该进程**文件描述符表已满，`ENFILE` 表示**系统全局**文件表耗尽；两者都可能使监听端口仍存在，却无法接纳新连接。

设进程软限制为 $L$，启动时已占用描述符为 $B$，监听套接字数为 $S$，每条客户端连接通常占用 $c$ 个描述符，则理论连接上限近似为：

$$
N_{\max}=\left\lfloor\frac{L-B-S}{c}\right\rfloor
$$

例如 `ulimit -n=1024`，进程已有日志、配置、管道等 $B=40$，有 $S=4$ 个监听 socket，单连接仅占 $c=1$，则最多约 $980$ 条连接；若连接还持有上游 socket、TLS 文件或事件通知 FD，$c>1$，实际上限会更低。应同时核对 `/proc/<pid>/limits`、`/proc/<pid>/fd` 数量、进程日志中的 `accept: Too many open files`，以及该实例时间窗内的连接数和 FD 曲线。

但 `EMFILE` 不能自动证明“连接泄漏”：若 FD 数在流量峰值后回落，且连接数与 FD 数线性同步增长，更可能是额度配置不足；若连接下降后 FD 仍持续增长，或大量 FD 指向已删除文件、匿名管道、重复 socket，才支持泄漏判断。反证是：错误发生时 FD 使用量远低于限制，或错误实际来自代理层而非业务进程。

若出现 `ENFILE`，应检查 `/proc/sys/fs/file-nr` 与 `fs.file-max`；单个实例 FD 尚有余量、多个服务同时报错，支持全局耗尽。反之，系统文件表远未接近上限即可推翻该结论。

任务耗尽是另一条路径：连接处理可能需要 `fork`、线程或容器任务。检查 `pids.current`、`pids.max`、`memory.events` 中的 `oom`/`oom_kill`，以及日志里的 `EAGAIN`、`Resource temporarily unavailable`。若 `pids.current≈pids.max` 而 FD 充足，应转向任务限制；若 PID 余量充足且无创建任务失败证据，则不能把断线归因于 pids 限制。重启后暂时恢复只说明资源计数被清空，不能替代上述时间窗证据。

### 状态未知：以fsync定位延迟暴露的磁盘满

### 状态未知：以 `fsync` 定位延迟暴露的磁盘满

消息 `m-9` 显示“状态未知”时，不能把“应用曾返回写入成功”当作已持久提交。常见路径是：网关先将消息追加到页缓存或日志文件，随后异步执行 `fsync`；磁盘空间在此时耗尽，`fsync` 返回 `ENOSPC`，此前看似成功的写入才暴露无法落盘。

应按消息流水重建边界：

1. 找到 `m-9` 的接收、写入、`fsync`、确认发送及消费者可见记录。
2. 若存在“已接收/已写入”但没有成功 `fsync`，且同一实例日志出现 `fsync(...)= -1 ENOSPC`，则不能确认 `m-9` 已提交。
3. 若确认记录、提交偏移或下游消费记录存在于故障前，则可将恢复边界推进到该记录之后；否则应按未确认消息重投或由幂等键去重。
4. 对照故障实例的时间窗，而非仅看重启后的磁盘状态。重启后释放临时文件、轮转日志或扩容，可能使写入恢复，却不能补回故障窗口内失败的持久化。

同时检查块空间与 inode：

- `df -h` 显示可用空间为零，支持数据块耗尽；
- `df -i` 显示 inode 为零，亦可导致 `ENOSPC`，即使仍有大量容量；
- 文件系统只读、配额限制或容器挂载卷满，也应纳入同一证据链。

可推翻“磁盘满导致 m-9 未提交”的证据包括：故障时间窗内 `fsync` 均成功、目标卷与 inode 均有余量、`m-9` 已有持久确认记录，或错误实际来自其他实例/其他挂载点。只有将 `ENOSPC`、对应文件、实例时间窗和 `m-9` 的确认缺口串联，才能把“状态未知”收敛为可恢复的消息边界。

### 断线与退出：辨析页缓存压力、OOM和终止信号

### 断线与退出：辨析页缓存压力、OOM和终止信号

连接断开不等于“内存不够”。先将客户端断线时刻与实例重启、容器退出、`memory.events`、内核日志置于同一时间窗比对，再判断是可回收页缓存压力、内存分配受理失败，还是进程被杀。

- **页缓存压力**：文件读写增大时，`cache` 上升而匿名内存未持续逼近限制；内核可回收页缓存，进程通常不会退出。即使延迟升高、`fsync` 变慢，也不应出现对应的 `oom_kill` 计数或进程死亡记录。能推翻此判断的证据是：同窗内 `memory.events` 的 `oom`、`oom_kill` 增长，或内核日志明确记录杀死目标进程。

- **内存受理失败**：cgroup 达到 `memory.max` 时，新分配可能失败，`memory.events` 中 `max`、`oom` 增加；应用可能记录分配失败、接受连接失败或主动关闭会话，但进程仍存活。若退出码、重启时间与断线完全吻合，则不能仅归为“受理失败”。

- **OOM kill**：检查 `memory.events` 的 `oom_kill` 增量，以及内核日志中的 `Out of memory`、`Killed process`。容器常表现为退出码 `137`，对应 `SIGKILL`；客户端会在进程消失后集中断线，消息可能停留在 `m-9` 状态未知。若没有杀进程日志且 `oom_kill=0`，OOM 根因不成立。

还须区分编排器终止：`SIGTERM` 常对应退出码 `143`，应有优雅下线、停止探针失败或发布事件；超时后再收到 `SIGKILL` 才可能变为 `137`。重启后连接恢复只能证明新实例可用，不能证明此前断线由资源故障造成。

### 恢复判定：重启后暂稳不等于根因消失

### 恢复判定：重启后暂稳不等于根因消失

重启只能证明进程重新获得了部分资源，不能证明故障链已消失。S2 的判定重点是：恢复后的实例是否仍能在受压时**受理新请求**，而非健康检查是否变绿。

- **S2 内存受理验证**：记录重启前后 `memory.current`、`memory.max`、`memory.events` 中 `oom`、`oom_kill`、`high` 的增量；以固定并发发送小请求，观察成功率、排队时间与拒绝比例。若内存持续爬升、`high` 继续增加，或压力下再次超时，则“重启恢复”被推翻。
- **S3 持久恢复边界**：进程启动后不等于数据已持久。必须验证重放、补偿或写入队列中的消息最终可查询，且 `fsync` 不再返回 `ENOSPC`。磁盘空间暂时释放、但 inode 耗尽、日志快速回涨或挂载只读，均说明根因未消除。
- **S5 连接恢复边界**：HTTP 应在过载时返回明确的 `429`、`503` 或带 `Retry-After` 的拒绝，而不是无限等待直至客户端超时。WebSocket 应保留优雅关停证据：停止接收新连接、发送关闭帧、等待已有会话排空，并记录关闭码与未完成消息数。

还应将恢复时间与实例启动时间、容器重建时间、退出信号对齐。若故障恰在实例替换后消失，但资源曲线、磁盘余量和连接压力均未改善，只能说明故障被迁移或被短暂掩盖，不能宣布根因已修复。

> **要点** — 以同窗证据和可证伪假设定位资源故障；重启后的暂时恢复不能替代持久性、内存与关停边界验证。

资源故障时，首要目标不是立刻“修好”，而是阻止损失扩大、保留证据，并在权限与一致性边界内恢复服务。

### 先止损：冻结接入与写入扩散

### 先止损：冻结接入与写入扩散

资源告警一旦指向文件描述符耗尽、磁盘空间不足或网关异常退出，应先把系统从“继续扩大损失”切换为“受控拒绝”。首轮目标不是恢复吞吐，而是避免更多连接、写入、重试和副本传播消耗最后的资源。

建议按以下顺序处置：

1. **限流并摘除流量**：在负载均衡、网关或入口层降低并发，摘除异常实例；优先保护已有会话和关键查询，停止批量导入、历史回放、索引重建等高消耗任务。
2. **拒绝新接入与新写入**：关闭新客户端连接、订阅和非必要管理接口；将新写请求明确返回可重试的过载或不可用响应，而不是让请求进入队列后无声超时。
3. **冻结扩散路径**：暂停跨节点复制、异步投递、自动重连风暴及无限重试。对仍在途的请求，只能标记为“结果未知”，不能据此推断成功或失败。
4. **保留现场证据**：记录告警时间、实例状态、`ulimit`、打开文件数、磁盘与 inode 使用率、内存压力、关键日志及入口请求标识。证据应先导出到安全位置，再进行清理或重启。

此阶段禁止为腾挪空间而直接删除权威消息、权威状态或审计记录；也不得自行重放 `m-9` 来“补偿”未知结果。删除缓存、临时文件或可再生构件前，必须确认其不承担权威语义，并获得相应权限。资源恢复可以后置，事实与一致性边界不能被破坏。

### 描述符与任务额度：定位耗尽层级

### 描述符与任务额度：定位耗尽层级

资源“耗尽”必须先判定是哪一层额度触顶；三者症状相似，却不能用同一种修复动作。

- **单进程 `EMFILE`**：某个进程达到自身文件描述符上限，常见报错为“打开文件过多”。它不能再接受连接、打开日志、创建套接字或读取配置；其他进程未必受影响。先查该进程的 `RLIMIT_NOFILE`、实际打开数及增长来源。
- **系统级 `ENFILE`**：内核全局文件表耗尽，多个无关服务都可能无法打开文件或建立连接。此时单独提高某个服务的 `nofile` 并不能创造全局表项，还可能加剧竞争。
- **任务数限制**：`pids.max`、`RLIMIT_NPROC` 或系统任务上限耗尽时，`fork`、创建线程、拉起工作进程失败。它不是 FD 问题；关闭少量空闲连接未必有效，必须识别线程池、子进程重试或失控重启是否持续制造任务。

可用预算式判断风险。设进程 FD 上限为 $L$，已知固定开销为 $F$，每条客户端连接平均占用 $c$ 个 FD，后台任务、日志轮转和临时文件预留为 $R$，则可接受连接数近似为：

$$N_{\max}=\left\lfloor\frac{L-F-R}{c}\right\rfloor$$

其中 $F$ 不只是监听套接字：配置文件、证书、管道、监控 socket、数据库连接池、日志文件都应计入。若 HTTP/网关连接一端占 1 个 socket，而代理上游、TLS 相关文件或审计链路又占额外描述符，实际 $c$ 往往大于 1。日志轮转瞬间同时持有旧文件与新文件，也会侵蚀 $R$。

处置顺序应是先停止新接入或限流，保留 `ulimit`、`/proc/<pid>/fd` 数量、cgroup `pids.current`、内核错误和连接分布证据；再按权限提高正确层级的额度，或关闭可安全重建的非权威连接。不要为“腾 FD”直接删除权威消息、日志证据，亦不要重放 `m-9`。额度恢复后，已在途请求仍可能结果未知，必须通过有权状态查询确认。

### 磁盘满与持久化：识别延迟失败

### 磁盘满与持久化：识别延迟失败

`ENOSPC` 不一定在业务调用“写入”时立即返回。应用可能先写入页缓存、运行时缓冲区、消息队列或临时日志；此时接口已返回成功，但真正分配块、落盘或更新元数据可能发生在后续的批量刷盘、`fsync`、日志轮转、数据库检查点或事务提交阶段。因此，“已接受请求”不等于“已持久化”，尤其不能据此确认消息已成为权威历史。

发现磁盘逼近满载时，先阻止损失扩大：

- 暂停新的写入、上传、导入和大对象发送；必要时将实例摘流，避免继续产生不可提交的数据。
- 保留有限证据：记录磁盘使用率、inode 使用率、挂载点、最近的 `ENOSPC`/`I/O error`、失败时间窗、进程日志及待刷盘队列状态。
- 区分数据层次：权威消息、数据库文件、提交日志、审计记录不可直接删除；可优先清理明确可再生且非权威的空间，如过期临时文件、构建产物、可重建缓存、已确认上传的副本。

清理后不能只看“磁盘有空余”。应确认目标挂载点和 inode 均恢复余量，再执行一次受控的小写入，并检查其完整路径：写入返回、事务提交、`fsync` 或等价持久化确认、重启后读取验证。若故障窗口内存在“请求已答复但提交失败”的记录，应标记为结果未知，允许有权状态查询或补偿，而非假定成功、更不能重放既有权威消息。只有持续写入、提交和重启恢复均通过，才可逐步恢复接入。

### 内存压力与进程退出：回收、杀死和排空

### 内存压力与进程退出：回收、杀死和排空

页缓存回收、内存压力和 OOM kill 看似都表现为“内存不够”，但处置边界不同：

- **页缓存回收**：内核优先释放可重新从磁盘读取的文件页；通常不代表业务数据丢失，却会放大磁盘读取延迟。应先限流新连接、新上传和高扇出查询，观察延迟、换页、文件描述符与磁盘空间，避免把缓存抖动误判为应用故障。
- **内存压力**：匿名页、连接缓冲、消息队列或运行时堆持续增长时，频繁回收会造成延迟尖峰。可在权限范围内降低并发、暂停非关键任务、缩短空闲连接存活时间；不能为了“腾内存”直接删除权威消息、会话状态或重放 `m-9`。
- **OOM kill**：内核已无法满足分配请求，可能按评分杀死某个进程。被杀进程来不及完成清理、刷盘或回复，因此在途 HTTP 请求和 WebSocket 消息结果应标记为**未知**，只能通过有权状态查询确认，不能由客户端超时推断失败。

计划终止优先使用 `SIGTERM`：进程停止接收新 HTTP 请求，健康检查转为不可用，已有请求在截止时间内完成或返回明确的可重试结果；WebSocket 则先发送关闭帧或服务迁移提示，停止接收新业务消息，再等待在途处理排空。到达排空期限仍未退出，才使用 `SIGKILL`；它不提供任何应用层清理保证。

恢复后，HTTP 应验证当前响应如 `6B`、`409`、`404`、`200` 的语义，不能只看端口恢复；B 的重连结果与未来 S3 的权威历史、设备 ACK 必须分别核验。固定 OpenIM 源码或重启成功，也不能证明此前确为真实资源故障或在途操作已落盘。

### 恢复验收：当前响应与未来一致性分层

### 恢复验收：当前响应与未来一致性分层

恢复后不能只看进程存活、端口可连或告警消失；验收必须把“当前请求是否可判定”与“未来数据是否重新形成权威链路”分开。

- **A 当前 `6B` 的验收**：再次提交或查询时，预期返回应明确区分：
  - `409`：同一业务键已存在、状态冲突或幂等结果可被确认；
  - `404`：对象、会话或可查询状态确实不存在；
  - `200`：当前操作已被服务正常接受并得到可验证结果。  
  这些响应证明当前接口恢复了判定能力，不等于故障窗口内的操作都已成功或失败。

- **在途请求一律视为结果未知**：资源耗尽、写盘失败或网关退出期间，客户端可能已发送请求、服务端可能已处理部分步骤，但响应未返回。不能因为重试得到 `200`，就倒推原请求成功；也不能因当前 `404`，就擅自重放历史消息 `m-9`。应保留请求标识、时间、连接日志和可用审计证据，由有权状态查询或业务对账决定后续动作。

- **状态查询与 B 重连分离验收**：有权限的查询者可读取权威状态，确认对象是否存在、版本为何、是否已提交。B 的重连只证明传输通道恢复；重连成功、订阅成功或收到欢迎消息，均不证明 B 漏失的数据已补齐。

- **未来一致性另行验证**：从恢复点开始，S3 的新权威历史应持续可写、可查、顺序与版本规则正常；设备 ACK 也应独立观察，确认设备实际接收并确认后续命令。`S3` 历史恢复不自动推出设备 ACK 恢复，反之亦然。

固定 OpenIM 源码版本只能降低软件变更变量，不能证明描述符、磁盘或内存等真实资源故障已经消除。

> **要点** — 资源恢复须先止损后修复；不删权威消息、不重放m-9，并将当前结果与未来一致性分开验收。

本节以独立IM服务的资源故障为线索，建立从错误码、内核资源到优雅关停与恢复边界的完整证据链。

### 文件描述符与任务数：先辨明耗尽对象

### 文件描述符与任务数：先辨明耗尽对象

资源“耗尽”不能只看“打开文件失败”，必须先确认被耗尽的内核对象及其作用域。

- **`EMFILE`**：当前进程的文件描述符表已满，受 `RLIMIT_NOFILE` 影响。socket、管道、`epoll`、日志文件都会占用描述符。若软限制为 `1024`，进程当前已用 `1020`，则仅剩 `1024-1020=4` 个；并发连接或一次重连风暴即可迅速触顶。常见现象是 `accept`、`socket`、`open` 返回 `EMFILE`，单个服务实例率先失去接入能力。
- **`ENFILE`**：系统全局打开文件表耗尽，受内核全局文件句柄限制约束。此时不止一个进程失败，节点上的代理、数据库、监控或其他服务都可能出现 `open`/`socket` 失败；提高单进程 `nofile` 并不能解决根因。
- **pids 任务限制**：耗尽的是任务数，而非描述符。线程也计入任务，因此“线程创建失败”、`fork` 失败、容器无法拉起新工作线程，通常应检查 cgroup 的 `pids.max`、系统 `pid_max` 与僵尸进程，而不是只检查 `ulimit -n`。

可按错误—对象映射排查：

| 错误或现象 | 优先怀疑对象 | 关键证据 |
|---|---|---|
| `EMFILE` | 单进程描述符 | `/proc/<pid>/fd` 数量、`LimitNOFILE` |
| `ENFILE` | 系统文件表 | `/proc/sys/fs/file-nr`、全机日志 |
| 创建线程或子进程失败 | pids/线程任务 | `pids.current`、`pids.max`、线程数 |

恢复前还要确认泄漏类型：连接未关闭、文件句柄遗失，还是短时并发峰值。盲目调高上限只会延后故障，并可能把压力转移为内存、page cache 或 OOM 问题。

### 额度手算：1024限制为何只剩4个描述符

### 额度手算：1024限制为何只剩4个描述符

设进程的文件描述符软限制为 `RLIMIT_NOFILE=1024`，当前已打开 1020 个描述符，则理论剩余额度为：

$$1024-1020=4$$

这 4 个并不等于“还能接 4 个用户”。描述符是进程访问内核对象的编号，IM 服务中常见消耗包括：

- 监听套接字：每个监听端口至少占 1 个；
- 已建立连接：每个 TCP/WebSocket 连接通常占 1 个；
- 日志文件、配置文件、证书、数据库连接、Unix Socket；
- 临时文件、上传附件、消息落盘文件及目录句柄；
- DNS、监控、管道、事件通知等内部资源。

例如服务已持有 1 个 WebSocket 监听 FD、900 个长连接、30 个后端连接、40 个日志或文件 FD、49 个运行时内部 FD，合计正好 1020。此时即使只到来一个新客户端，`accept()` 也可能因 `EMFILE` 失败；若系统全局文件表也耗尽，则可能看到 `ENFILE`。二者分别表示“本进程额度耗尽”和“系统级文件表耗尽”。

更危险的是，剩余 4 个 FD 可能被日志轮转、附件打开或健康检查抢占。进程随后无法接受新连接、无法打开日志，甚至无法建立恢复所需的控制连接。排查时应同时检查：

- `ulimit -n` 或 `/proc/<pid>/limits`：确认软、硬限制；
- `/proc/<pid>/fd`：统计并分类 FD 来源；
- `lsof -p <pid>`：识别异常增长的连接、删除但仍被占用的文件；
- 容器或服务管理器配置：确认其是否覆盖了 shell 中的限制。

恢复不能只把限制调大；还应限制单进程连接数、关闭泄漏的文件与空闲连接，并预留描述符给监听、日志和关停流程。

### 磁盘满并非立即报错：write、fsync与close

### 磁盘满并非立即报错：`write`、`fsync` 与 `close`

应用调用 `write()` 成功，只表示数据通常已被内核接受并写入页缓存（page cache），并不等价于数据已经落盘。内核可能稍后才把脏页回写到文件系统；若此时发现空间不足，`ENOSPC` 可能延迟到不同阶段出现：

- `write()`：文件系统需要立即分配数据块、扩展文件或页缓存回写压力已无法继续吸收时，直接返回 `ENOSPC`。
- `fsync()`/`fdatasync()`：应用要求把此前缓存的数据及必要元数据提交到稳定存储时，回写过程发现无可用块，返回 `ENOSPC`。这是最关键的持久化失败点。
- `close()`：某些文件系统或库在关闭时触发刷新、提交元数据或报告延迟写回错误，因此 `close()` 的失败也必须检查，不能忽略返回值。

因此，`write()` 成功不能作为“消息已持久化”的证据。若 IM 服务先写消息日志、再确认客户端成功，持久提交判定点应定义为：

$$
\text{提交成功}=\text{write 完整写入}\land \text{fsync 成功}\land \text{close 成功（若关闭）}
$$

其中“完整写入”还要求处理短写：循环调用 `write()` 直到所有字节完成，或遇到不可恢复错误。仅将数据交给页缓存就返回确认，会在磁盘满、宕机或回写失败后制造“客户端已收到成功、服务端实际未保存”的一致性漏洞。

恢复时先停止新的持久化确认，释放或扩容磁盘，并检查日志、临时文件、分区配额和 inode；空间恢复后不能自动假定此前请求成功，应依据 `fsync` 前后的提交记录、幂等键或事务日志进行补拉与重放。

### 内存压力：页缓存可回收不等于不会OOM

### 内存压力：页缓存可回收不等于不会 OOM

页缓存（page cache）用于缓存文件数据，通常属于“可回收”内存：当进程申请新页时，内核可回收较少使用的缓存页。因此，`buff/cache` 很高并不自动表示内存泄漏，也不能仅凭“缓存很多”断定会 OOM。

但可回收不等于可立即、无代价地回收。写入繁忙时，脏页必须先回写磁盘；若磁盘满、I/O 卡顿或回写速度低，页缓存会积累，回收受阻。与此同时，匿名内存——如进程堆、线程栈、连接缓冲、消息对象和运行时分配——通常不能像文件缓存一样直接丢弃。匿名页持续增长、交换空间不足或受 cgroup 内存上限约束时，内核会进入内存回收；回收仍无法满足分配，便可能触发 OOM kill。

可将两类压力对比为：

- **页缓存压力**：可回收，但脏页回写依赖磁盘与文件系统；常表现为写入阻塞、`fsync`/`close` 延迟报错或延迟升高。
- **匿名内存压力**：对象仍被引用就不可回收；连接堆积、WebSocket 缓冲未释放、消息队列积压更容易直接推向 OOM。
- **OOM kill**：不是“机器内存用满”才发生；容器的 `memory.max`、进程组限制或节点整体分配失败都可能触发。被选中的进程常以 `SIGKILL` 异常退出，来不及执行清理逻辑。

恢复时应明确状态边界。S2 只受理能够在内存中确认、且可由后续持久化补偿的状态；若内存已逼近限制，应停止扩大受理窗口。S3 的持久化提交不能仅因写入返回成功而判定完成，仍需处理回写、`fsync` 与磁盘故障。S5 的在线连接与 WebSocket 会话属于可重建状态：重启后应通过鉴权、订阅恢复与权限补拉重建，不能假定 OOM 前的内存会话仍然存在。

### 网关退出与恢复：信号、连接和权限补拉

### 网关退出与恢复：信号、连接和权限补拉

`SIGTERM` 表示“请求进程自行退出”：网关应停止接收新连接，摘除负载均衡实例，等待存量请求完成，并在超时后关闭监听套接字、刷新关键状态。`SIGKILL` 则由内核直接终止进程，应用没有清理机会；未完成的响应、WebSocket 会话和内存态订阅都会立即丢失。因此，编排系统应先发 `SIGTERM`，设置足够的宽限期，最后才以 `SIGKILL` 兜底。

对 HTTP，`Shutdown` 的典型策略是：

1. 先将实例标记为不可用，避免新流量继续进入；
2. 调用 `Shutdown` 停止监听并等待在途请求；
3. 超过截止时间后取消长请求，记录未完成请求数；
4. 依赖客户端重试保证最终完成，而不是无限等待。

WebSocket 不能只依赖 HTTP `Shutdown`。它通常是长连接，应先停止新的升级请求，再向已有连接发送关闭帧或“服务重连”事件，给客户端短暂重连窗口；到达截止时间后强制关闭。服务端不应假设进程内连接状态可恢复，重连后的会话必须重新认证、重新订阅，并从持久化游标补齐消息。

恢复时，权限补拉必须按边界执行，而非把所有权限全量缓存。可将边界理解为：`S2` 仅补拉用户自身身份与基础会话权限；`S3` 补拉当前组织、群组或项目范围的成员关系与角色；`S5` 才允许访问高敏感、跨域或管理权限。客户端重连后先完成 `S2`，再依据当前页面、订阅主题和资源归属请求 `S3`；涉及管理操作时按需验证 `S5`。这样既避免旧 WebSocket 携带过期授权，也避免恢复高峰中的无差别权限全量拉取。

> **要点** — 资源故障恢复必须依据错误位置、可持久化证据与阶段边界，而非仅凭进程是否重启。
