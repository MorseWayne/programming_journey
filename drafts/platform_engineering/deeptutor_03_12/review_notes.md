# 03.12 审阅记录：资源故障案例

DeepTutor BookEngine 八节初稿均 ready、无失败块；本地 HTTP Markdown 导出与生成稿 SHA256 一致。`original.md` 保存完整初稿。正式页将 FD 耗尽、未来 S3 磁盘写失败、页缓存/内存回收压力和信号退出写成**四张彼此独立**的 IM 纸上故障卡，再从错误码、资源作用域和业务确认点推恢复，附 22 道分层练习。

## 教学重组

- 当前 S2 `/v1` 的 6 UTF-8 B/4096 B/409/404/200 内存受理合同保持不变；权威 WAL/DB 盘满是未来 S3 独立变式，设备确认是更后的阶段。四张卡不是本项目曾发生的一场综合事故。
- `RLIMIT_NOFILE` 软限 1024、当前已打开 1020 FD，在**无其它打开/关闭且每新连接恰占 1 FD**条件下只余 4 个槽位；`EMFILE` 是进程范围，`ENFILE` 是系统范围，`pids.max` 管 task/TID，彼此不能互换。
- 未来 S3 的 `write` 返回和 `fsync/close` 可能延迟暴露的 `ENOSPC/EIO` 分开；只有符合明确定义的事务/持久承诺，才能返回拟议的 `stored_in_teaching_db`。
- `memory.events high/max` 与 `oom_kill` 分开；`SIGTERM` 可安排有界关停，`SIGKILL` 没有处理机会；Go `http.Server.Shutdown` 不自动等待已 hijack 的 WebSocket。

## 技术修订

- 初稿先用 `1024−24=1000` 直接推出“最大客户端数”，后文才给出当前 1020 FD 的情景。正式页只保留已打开 1020 FD 时的**条件剩余 4 槽位**，不把 FD 预算当真实最大连接数。
- 初稿把 S2 写成“已实现的在线服务”及“没有任何本地持久文件/WAL”，均超出仓库当前静态合同。正式页说当前课程尚无运行中 S2/S3 服务；S2 200 只承诺本进程内存受理，不据此断言辅助日志/文件是否存在。
- 初稿对未来 S3 的 WAL/outbox `fsync` 顺序、错误映射、跨重启恢复作出过于具体的既定机制描述。正式页限定为**未来事务假设**，要求在配置和合同确定后验证，不从一次普通文件 `write` 推出 DB 提交。
- 初稿有“SIGTERM 后平台通常 SIGKILL”的泛化叙述。正式页只说平台具体信号顺序/宽限期要据实际配置，信号语义与 Go HTTP/WebSocket 关停边界分开。
- 初稿把 S2 内存受理具体列为幂等缓存、未落库任务和订阅映射，随后把 S3 泛称对象存储/消息队列。正式页只守已核对的 S2 合同和拟议 S3 教学 DB 语义，不虚构服务结构。
- 固定 OpenIM 两处源码只支持选定发送与 Mongo 消费的异步边界，不证明真实 FD、磁盘、信号、排空或设备恢复行为。
