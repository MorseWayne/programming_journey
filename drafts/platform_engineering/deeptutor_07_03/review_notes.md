# 07.03 审阅记录：缓存读取与更新

## 教学重组

- 固定未来 S3 教学 DB 权威，当前 S2 `accepted_in_memory` 不变。读路径 GET→miss→权威查询→可缓存时回填；写路径 DB COMMIT→DEL 缓存，明确 Redis 与数据库不是同一原子事务。
- 先删再写：DB V8/cache V8，W DEL，R miss 读/填 V8，W COMMIT V9 无后续 DEL，最后 DB V9/cache V8。
- 先提交再删仍会迟到回填：DB V8/cache 空，R miss 并读取 V8 后暂停，W COMMIT V9 再 DEL 空键，R 迟到 SET V8；`SET NX` 因键仍空也无法阻止。
- 30 秒 TTL 仅玩具值，从**实际旧回填**时起算；反复旧回填可续长窗口。负缓存 R 查 `m-x` 无、W 插入并失效、R 迟到写 ABSENT 也会制造假不存在。
- `u-c` 的隐藏 404 属于主体相关授权结果，绝不能按 `message_id` 写全局“不存在”让 `u-a` 命中；依赖失败也不能缓存为业务 404。

## 技术修订

- 原稿一处说“先写权威再失效”避免并发读把旧值重新回填，但同一原稿后文又给出正确的迟到回填反例。正式页用两张独立状态表明确：更换顺序只消除**先删后写的那条竞态**，不消除更早读取、较晚 SET 的窗口。
- 给缓存值带 `source_version=V8` 或用 `SET NX` 本身不构成严格一致：若 DEL 后没有保留独立的最低有效版本，旧读仍可写入。正式页说明围栏/条件比较也需可靠顺序、原子步骤和写侧失败政策。
- `cache miss`、真正业务不存在、授权隐藏 404、Redis/DB 依赖错误四类状态分开。负缓存须限定可见范围和失效，不得跨用户共享私有查询结果。
- TTL 只控制一次缓存值生命周期，不证明 TTL 内新鲜，也不在重复旧填入或不同缓存副本下给绝对业务陈旧上限。
- DB 已知提交而 Redis DEL 失败，不把消息自动回滚；预览可重建时要记录修复/读己之写绕过策略，若合同要求同步新鲜则需另有可证协议或明确失败。
