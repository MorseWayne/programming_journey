## 09.03 程序组织：让 handler、业务规则与内存适配器各守边界

- 按变化原因拆分启动、handler、应用服务、领域与内存适配器

- 限定handler对路径、大小、JSON、HTTP响应的职责
- 让应用服务维护可信主体、授权与内存受理状态

以消息查询与提交为线索，按变化原因拆开职责：HTTP边界不替业务决策，内存实现也不绑住未来替换。

### 先识别混装带来的变更耦合

### 先识别混装带来的变更耦合

设想 `POST /v1/conversations/c-a/messages` 的 handler 一次做完所有事：

1. 从 CLI flag 或请求头读取当前用户；
2. 解析 JSON，检查 `text` 是否存在且不超过 `4096B`；
3. 判断用户 `u-a` 是否能向会话 `c-a` 发言；
4. 直接操作内存 `map`，生成消息 `m-a`；
5. 写日志，并返回 `200 accepted_in_memory`。

它看似短小，却把多种**变化原因**塞进同一处。于是一个无关需求也会牵动整个 handler：

- 查询参数 `limit` 从默认 `20` 调整，或范围从 `1..100` 改为别的规则，会碰到 HTTP 解析与响应逻辑。
- 身份来源从本地 CLI 切换为 Bearer Token，会改到原本夹着 JSON 校验和会话写入的代码。
- `text` 的最小长度从 `6B` 改为允许空文本，影响的是消息规则，却可能误伤错误响应格式。
- 内存 `map` 改为数据库或远程服务时，认证、状态码、日志位置也被迫一起重写。
- 日志字段增加 `conversation_id`，开发者不得不阅读业务判断和存储细节，才能确认记录时机。

问题不在于“一个函数太长”，而在于它同时承诺了 HTTP 协议、身份取得、业务规则、数据保存和可观测性。不同原因变化时，修改者必须穿过不相关代码；测试也只能构造完整请求、用户和内存状态，难以单独验证规则。

拆分的目标不是堆出许多层，而是让每个部分只因一种主要原因改变：handler 负责边界转换，业务规则决定是否接受消息，内存适配器负责保存，日志围绕明确结果记录。这样未来替换认证或存储时，不必重新讨论“`u-a` 能否向 `c-a` 发消息”这一业务事实。

### 按变化原因划分包与单向依赖

### 按变化原因划分包与单向依赖

先按“什么变化会迫使这里修改”划边界，而不是按文件行数机械分层。对于当前仅由本地 CLI 启动、提供 `GET/POST /v1/conversations/c-a/messages` 的程序，可形成如下职责链：

- `cmd`：组装程序。读取启动参数、选择监听地址，创建内存存储与应用服务，再注册 HTTP 路由。它知道“如何启动”，不应知道 `limit` 的业务含义或消息如何保存。
- `internal/httpapi`：HTTP 边界。解析路径、查询参数和 JSON，检查请求体上限 `4096B`，把 `limit` 转为应用层输入；将应用错误映射为 HTTP 状态与响应 JSON。它不直接操作 `map`，也不决定消息是否允许提交。
- `internal/app`：用例协调。实现“查询会话消息”“提交消息”等动作，执行 `limit` 必须在 `1..100`、文本至少 `6B`、会话与用户关系是否合法等规则，并返回如 `accepted_in_memory` 的结果。
- `internal/domain`：稳定业务概念与规则，如 `Conversation`、`Message`、`UserID`、领域错误类别。这里不导入 HTTP、CLI 或内存存储。
- `internal/memorystore`：存储适配器。用 `map` 保存 `u-a`、`u-b`、`c-a`、`m-a` 等测试数据，实现应用层所需的读取、追加接口；未来换数据库时，主要替换此处。

依赖方向必须向内收敛：

`cmd → httpapi → app → domain`  
`cmd → memorystore → domain`

更准确地说，`app` 定义它需要的存储能力接口，例如“按会话列出消息”“追加消息”；`memorystore` 实现该接口。这样应用层不 import 内存实现，HTTP 层也不越过应用层访问存储。

将这些包放入 `internal/`，可阻止仓库外模块直接依赖尚未承诺稳定的 API。若把 flag、JSON、认证判断、`map` 写进同一个 handler，任一变化——改 CLI、换鉴权、调整错误格式、接入数据库——都会碰到同一处；按变化原因拆开后，变化只沿依赖方向进入，不会从适配器反向污染业务规则。

### Handler只守HTTP合同边界

### Handler只守HTTP合同边界

`GET /v1/conversations/c-a/messages?limit=20` 与 `POST /v1/conversations/c-a/messages` 的 handler 是 HTTP 适配层：它只把网络请求翻译成应用可理解的输入，再把应用结果翻译回 HTTP 响应。它不应决定“谁能向谁发消息”、不应直接读写 `map`，也不应知道数据当前是否存于内存。

对 GET，handler 的职责是：

- 从路径提取 `conversationID`，例如 `c-a`；
- 读取可选的 `limit`，默认 `20`，并校验范围为 `1..100`；
- 调用用例，如 `ListMessages(conversationID, limit)`；
- 将消息编码为 JSON，并提交成功响应；
- 将“会话不存在”“无权访问”“参数非法”等领域结果映射为约定的 HTTP 状态与错误体。

对 POST，边界校验更明确：

- 限制请求体最大为 `4096B`，避免无界读取；
- 解码 JSON，例如只接受 `{ "text": "hello" }`；
- 校验 `text` 至少为 `6B`，空对象、类型错误、截断 JSON 都属于请求格式或输入错误；
- 将已解析的命令交给用例；
- 成功时返回 `200` 及 `accepted_in_memory`，这是当前本地 CLI、内存适配器下的提交语义，而不是 handler 自己发明的业务状态。

可将 handler 理解为一段窄转换：

`HTTP 请求 → 路径/查询/body 校验 → 用例调用 → 结果/错误映射 → HTTP 响应`

不要把认证判断、会话成员规则、`u-a` 是否可向 `u-b` 所在的 `c-a` 提交消息，塞进这里；这些规则变化时，应只改业务用例。也不要在 handler 中操作 `m-a` 的内存 `map`、加锁或打印存储日志；未来替换为数据库时，应只改适配器。

这样拆分不是为了堆叠“控制器—服务—仓储”层数，而是为了隔离变化原因：HTTP 合同变化改 handler，消息规则变化改用例，存储方式变化改适配器。

### 应用服务维护可信身份与受理规则

### 应用服务维护可信身份与受理规则

应用服务负责把“谁正在操作”和“这次操作是否应被受理”变成稳定规则，而不是让 HTTP handler 直接读写 `map` 后自行判断。以提交消息为例，handler 只应提供已验证的可信身份、路径中的 `c-a` 与请求文本；服务据此完成授权、校验和结果判定。

```text
提交消息(actor=u-a, conversation=c-a, text)
```

服务可按以下顺序处理：

1. **确认可信身份**：`u-a` 必须来自认证中间件或受信任上下文，而不是客户端 JSON 中的 `user_id`。请求声称“我是 `u-b`”不能改变实际操作者。
2. **执行会话授权**：查询 `c-a` 的成员关系。若 `u-a` 属于该会话，可继续；若 `u-b` 不在会话中，即使知道 `c-a`，也不能读取或提交消息。
3. **校验业务输入**：消息文本至少为 `6B`，同时由边界层保证整个请求体不超过 `4096B`。前者是受理规则，后者是传输资源限制；不要把两者混成同一种错误。
4. **生成受理结果**：校验通过后，服务创建如 `m-a` 的消息记录，并返回 `accepted_in_memory`。该结果表达“当前内存适配器已接收”，并不暗示消息已持久化、已投递或可跨进程恢复。

因此，服务的返回值应携带业务语义，例如“未认证”“无权访问 `c-a`”“文本不足 `6B`”“已在内存中受理”。handler 再将这些类别映射为相应 HTTP 状态和 JSON 响应。未来认证从本地 CLI 换成令牌、会话从内存换成数据库时，受理规则仍集中在服务层，无须在每个路由中重复修改。

### 以内存适配器和小接口保留替换空间

### 以内存适配器和小接口保留替换空间

若服务直接操作 `map[string][]Message`，查询、去重、追加、加锁和“消息不存在”的判断都会散落在业务代码中：

- 改为数据库时，handler 或服务必须同时理解 SQL、事务、分页与连接失败；
- 并发控制从 `sync.Mutex` 变为数据库约束，原有判断可能失效；
- 测试只能构造真实 map，并间接依赖内部存储结构。

更稳妥的边界是：由业务服务依赖它实际消费的小接口，而非依赖具体内存结构。例如：

`MessageStore` 只暴露 `List(ctx, conversationID, limit)`、`Append(ctx, message)` 等操作；内存适配器负责 map、锁和本地数据生命周期。服务负责规则：`limit` 必须在 `1..100`、正文不得超过 `4096B`、文本不能为空且至少 `6B`、会话 `c-a` 是否允许提交。HTTP handler 则负责读取 JSON、认证为 `u-a` 或 `u-b`、把错误映射为状态码。

接口不应预先模仿未来数据库的全部能力。当前只需要追加和列表，就不要加入事务、过滤器或通用查询对象；接口应随消费方的稳定需求增长，而不是随实现想象膨胀。

通过构造函数注入依赖：

`NewMessageService(store MessageStore, logger Logger, cfg Config)`

这样 CLI 启动时装配内存适配器，未来服务进程可替换为数据库适配器，handler 无须改写。`context.Context` 从 HTTP 请求一路传到服务和 `store`，即使内存实现暂不使用，也为取消、截止时间和未来 I/O 保留一致调用链。

配置集中读取，例如最大正文长度、默认 `limit` 与日志级别；日志只在边界或失败处记录必要字段，如 `conversation_id`、`user_id`、错误类别，绝不记录消息正文、认证令牌或完整请求体。测试也随边界分层：handler 测试状态码与 JSON；服务测试长度、权限和错误规则；内存适配器测试追加、排序、并发与查询行为。

> **要点** — 边界按变化原因划分：HTTP守合同，应用守规则，适配器管存储，启动层负责接线。

先用静态目录示意建立依赖地图：每个包按变化原因承担职责，依赖只能朝业务核心单向流动。

### 从模块到包：先画清静态目录地图

### 从模块到包：先画清静态目录地图

先把 `example.com/teachingim` 看成一个教学用模块；下面的目录是**目标组织图**，不表示这些文件已经全部创建：

```text
example.com/teachingim
├── cmd/teachingim/main.go
├── internal/httpapi/
├── app/
├── domain/
└── memorystore/
```

各包按“为什么会变化”划分边界，而不是按文件类型堆放：

- `cmd/teachingim`：程序入口与接线处。它创建内存仓库、应用服务和 HTTP 处理器，读取启动配置并启动服务；它可以依赖其他包，但不承载聊天规则。
- `internal/httpapi`：HTTP 协议适配器。负责解析请求、校验传输格式、调用 `app`、把结果编码为响应；不要让 handler 直接操作内存切片或决定业务规则。
- `app`：用例编排层。例如“发送消息”“查询历史”。它定义自己需要的 `HistoryStore` 接口，并协调领域对象完成用例。
- `domain`：最内层业务概念与规则，如消息、会话、时间顺序约束。它不导入 `http`、`os`、`encoding/json` 等基础设施或传输细节。
- `memorystore`：内存适配器，实现 `app` 所需的存储能力；它依赖 `domain` 中的对象定义，却不反向影响业务规则。

依赖方向应保持单向：

`cmd → httpapi → app → domain`

同时，`memorystore → domain`，并由 `cmd` 将其注入 `app`。若 `app` 中声明：

`type HistoryStore interface { Append(Message) error }`

则 `memorystore` 只要提供同签名方法，就会隐式满足接口，无需让核心层导入具体实现。这样既避免 import cycle，也能在未来替换为数据库适配器。`internal` 仅限制其他模块导入路径，并不是安全隔离或权限边界。

### 单向依赖：让业务核心不认识外部细节

### 单向依赖：让业务核心不认识外部细节

可以先把静态目录理解为一张依赖图，而不是已经存在的完整项目：

`cmd/teachingim/main.go → internal/httpapi → app → domain`  
`cmd/teachingim/main.go → memorystore → domain`

其中，箭头表示“左侧导入并使用右侧”。

- `cmd/teachingim/main.go` 是组合根：创建内存存储、创建应用服务、注册 HTTP 路由并启动进程。它可以认识所有具体实现，因为它只负责接线，不承载业务规则。
- `internal/httpapi` 负责 HTTP 请求、响应和 JSON 编解码；它调用 `app` 暴露的用例，不应直接操作内存数据结构。
- `app` 编排“发送消息”“查询历史”等用例，并依赖 `domain` 中的实体、值对象和规则。
- `memorystore` 是基础设施适配器：它把数据保存在内存中，因此依赖 `domain` 的 `Message` 等类型。
- `domain` 位于核心，不能反向导入 `http`、`os`、`encoding/json` 或任何存储包；否则业务规则会被传输协议和运行环境污染。

关键在于：接口由消费方定义。若 `app` 需要读取历史消息，就在 `app` 中声明：

`type HistoryStore interface { Append(Message) error; List(RoomID) ([]Message, error) }`

这里的 `Message`、`RoomID` 来自 `domain`。`memorystore` 只要实现这些方法，便隐式满足该接口；它无需导入 `app`。于是依赖保持为 `app → domain`、`memorystore → domain`，而不是形成 `app ↔ memorystore` 的双向关系。

导入环通常意味着职责倒置：例如 `domain` 为了输出 JSON 导入 `httpapi`，或 `app` 为了创建具体内存仓库导入 `memorystore`。把创建具体实现的工作移回 `cmd`，把接口留给使用者，就能切断环路。`internal` 只能限制外部模块导入，并不是安全边界；真正的边界来自清晰、单向的依赖关系。

### 消费方小接口：由应用层定义 HistoryStore

### 消费方小接口：由应用层定义 `HistoryStore`

`app` 不应依赖某个具体的内存仓库类型，而应只声明自己完成用例所需的最小能力。例如，“发送消息”用例只需要追加历史记录，“查询会话”用例只需要按会话读取记录：

```go
package app

import "example.com/teachingim/internal/domain"

type HistoryStore interface {
	Append(domain.Message) error
	ListByConversation(conversationID string) ([]domain.Message, error)
}
```

接口放在消费方 `app`，因为只有应用层知道用例真正需要什么。若把接口放进 `memorystore`，接口往往会被具体实现的能力、命名和数据结构牵引；未来改用 SQLite、Redis 或远程服务时，`app` 仍会被迫理解旧实现的设计。

应用服务通过构造函数接收接口，而不是自行创建仓库：

```go
type ChatService struct {
	history HistoryStore
}

func NewChatService(history HistoryStore) *ChatService {
	return &ChatService{history: history}
}
```

`memorystore` 只需实现同名方法即可隐式满足接口，无须导入 `app` 来声明“我实现了它”：

```go
type History struct {
	// 内存中的消息索引
}

func (h *History) Append(m domain.Message) error { /* ... */ return nil }

func (h *History) ListByConversation(id string) ([]domain.Message, error) {
	/* ... */
	return nil, nil
}
```

在 `cmd/teachingim/main.go` 中完成接线：创建 `memorystore.History`，传给 `app.NewChatService`，再将服务交给 `httpapi`。这样依赖方向保持为实现层服务于应用层，而非应用层绑死实现层。

这种设计也让测试更直接：测试 `app` 时可传入一个很小的假仓库，验证业务规则、调用顺序和错误处理，无须启动 HTTP、读写文件或准备真实数据库。接口不是为了“抽象一切”，而是为稳定的消费需求留下替换点。

### internal 的可见性边界不是安全边界

### internal 的可见性边界不是安全边界

`internal` 解决的是**编译期导入资格**，不是运行时权限问题。位于 `example.com/teachingim/internal/httpapi` 的包，只能被其父目录 `example.com/teachingim` 树内的代码导入；外部模块即使知道路径，也会在编译时报错。

这很适合表达“这是项目内部实现”：

- `cmd/teachingim` 可以导入 `internal/httpapi`、`app`、`memorystore` 并完成接线；
- `internal/httpapi` 可以调用 `app`；
- 外部调用者不能直接把 `internal/httpapi` 当作公共库使用。

但它**不能**保证：

- 请求者已经登录；
- 某用户有权读取某条消息历史；
- 管理接口只能由管理员访问；
- 内存中的敏感数据不会被日志、调试接口或错误处理泄露。

这些属于运行时安全控制，应在 HTTP 中间件、认证逻辑和业务规则中明确实现，例如由 `app` 在查询历史前验证 `$actorID$` 是否允许访问 `$conversationID$`。目录结构无法替代令牌校验、会话管理、权限判断、输入校验或审计日志。

还要区分 `internal` 与包封装：小写标识符只能在**同一包**内访问；`internal` 则限制**哪些目录中的包**可以导入该包。前者隐藏实现细节，后者限制复用范围。二者都服务于代码组织，不能被当作安全边界。

### 启动包只接线：为配置、日志与测试预留位置

### 启动包只接线：为配置、日志与测试预留位置

`cmd/teachingim/main.go` 应当是进程的组合根：它知道“要启动什么”，但不承载“业务如何判断”。在尚未创建实际文件前，可以先把静态目录理解为未来的装配地图：

`cmd/teachingim/main.go` → `internal/httpapi`、`internal/app`、`internal/memorystore`  
`internal/httpapi` → `internal/app`  
`internal/app` → `internal/domain`  
`internal/memorystore` → `internal/domain`

启动包的职责集中而有限：

1. 读取配置：端口、超时、日志级别、存储实现等；不要让领域对象直接读取环境变量或命令行参数。
2. 初始化日志：统一创建日志器，并约定对令牌、密码、会话标识等敏感字段脱敏。
3. 装配依赖：创建 `memorystore`，将其作为 `app.HistoryStore` 注入应用服务，再把应用服务交给 `httpapi`。
4. 建立根 `context.Context`：监听关闭信号，将取消信号传播给 HTTP 服务、应用调用和存储操作。
5. 启动与优雅退出：启动监听器，等待取消，按超时关闭服务。

例如，装配关系应接近：

`store := memorystore.New()`  
`service := app.NewChatService(store)`  
`handler := httpapi.NewHandler(service)`

这里 `main` 可以导入具体的 `memorystore`，因为它负责选择实现；`app` 不应反向导入它，只消费自己定义的 `HistoryStore` 接口。这样测试时可在 `main` 之外直接为应用服务注入假的存储实现。

`internal` 只是 Go 对导入范围的编译期约束，不是安全边界；配置校验、认证、脱敏和权限控制仍必须由代码明确实现。

> **要点** — 按变化原因分包并保持依赖向内，可让 HTTP、存储与启动细节替换而不侵入领域规则。

HTTP handler 是协议边界：它只负责接住不可信请求、提取可信上下文，并把应用结果稳定地翻译为响应。

### Handler 的边界：处理协议，不处理业务

### Handler 的边界：处理协议，不处理业务

Handler 是 HTTP 协议适配层：把不可信的 `Request` 转成应用服务可用的命令，把应用结果转成稳定的 HTTP 响应。它不判断聊天成员资格、不决定消息排序规则，也不直接读写内存 `map`。

典型职责可分为四步：

1. **解析协议输入**：从路径取得会话标识 `c-a`，从查询参数读取 `limit`、`before`、`sender`；解析 JSON 请求体。
2. **执行边界校验**：限制原始请求体最多 `4096B`，再解码并检查必填字段、格式与范围。认证中间件提供可信的 `principal`；不能相信 JSON 中的 `sender_id`。`S3` 尚未实现时，应由隔离的测试桩注入身份，而非将测试入口公开到生产接口。
3. **调用应用服务**：将已校验的数据和 `r.Context()` 传入应用层，由应用层执行授权、业务规则和存储操作。
4. **映射响应**：统一设置 `Content-Type: application/json` 与 `Cache-Control: no-store`，将应用错误映射为状态码和错误体。

```go
r.Body = http.MaxBytesReader(w, r.Body, 4096)
var in SendMessageInput
if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
    writeError(w, http.StatusBadRequest, "请求体无效")
    return
}
principal := principalFromContext(r.Context())
out, err := app.SendMessage(r.Context(), principal, conversationID, in)
writeResult(w, out, err)
```

响应必须在首次 `Write` 前决定状态：

```go
w.WriteHeader(http.StatusCreated)
json.NewEncoder(w).Encode(out)
```

`Write` 若先发生，默认已提交 `200 OK`；之后再调用 `WriteHeader` 无法改变最终状态。因此，Handler 应先完成错误映射，再写响应头和响应体。

### 受限读取请求体与校验输入

### 受限读取请求体与校验输入

请求体属于不可信输入，处理顺序应当固定为：**先限制原始字节数，再解码 JSON，最后校验业务字段**。不能先 `Decode` 再考虑大小；否则攻击者可以提交巨大的 body，占用连接、内存或解码器资源。

```go
r.Body = http.MaxBytesReader(w, r.Body, 4096)

var in struct {
    Text string `json:"text"`
}

dec := json.NewDecoder(r.Body)
dec.DisallowUnknownFields()

if err := dec.Decode(&in); err != nil {
    // 400：JSON 非法、字段类型不匹配、请求体为空或超过 4096B
    writeError(w, http.StatusBadRequest, "invalid_request")
    return
}
```

`MaxBytesReader` 限制的是**原始 body**，包括 JSON 的空白、冗余字段和编码开销；这比仅限制某个字符串字段更靠近网络边界。超过 `4096B` 时，读取会失败，handler 应将其翻译为统一的客户端错误响应，而不是把底层读取错误直接暴露出去。

成功解码不表示输入有效。还应检查必填字段、长度与格式，例如消息文本不能为空：

```go
in.Text = strings.TrimSpace(in.Text)
if in.Text == "" || len(in.Text) > 1000 {
    writeError(w, http.StatusBadRequest, "invalid_text")
    return
}
```

身份字段尤其不能信任 JSON。例如客户端提交的 `sender_id` 只能算声明，不能决定消息发送者；真正的发送者应来自认证边界产生的 `principal`。路径中的 `c-a`、查询参数中的 `limit`、`before` 等也同样需要分别解析和校验。完成这些协议层检查后，handler 才把已验证的值与 `r.Context()` 一并交给应用层。

### 路径参数、查询参数与可信主体

### 路径参数、查询参数与可信主体

路径、查询串、请求体都来自客户端，必须分别解析、校验，再转换为应用层可接受的输入。以消息列表接口为例，`c-a` 是路径中的会话标识，`limit`、`before`、`sender` 是查询条件：

```go
conversationID := r.PathValue("c-a")

limit := 50
if raw := r.URL.Query().Get("limit"); raw != "" {
    n, err := strconv.Atoi(raw)
    if err != nil || n < 1 || n > 100 {
        writeError(w, http.StatusBadRequest, "invalid_limit")
        return
    }
    limit = n
}

before := r.URL.Query().Get("before")
sender := r.URL.Query().Get("sender")
```

不要把“参数存在”当作“参数有效”。`c-a` 应符合业务规定的标识格式；`before` 若表示游标或时间，应由应用层解析并拒绝非法值；`sender` 即使格式正确，也只是客户端提出的筛选条件，不能因此获得读取该发送者数据的权限。

认证后的 `principal` 属于可信上下文：它应由认证中间件或外部认证边界写入 `r.Context()`，handler 只提取并传递：

```go
principal, ok := PrincipalFromContext(r.Context())
if !ok {
    writeError(w, http.StatusUnauthorized, "unauthenticated")
    return
}
```

尤其不能信任 JSON 中的 `sender_id`、`user_id` 或类似字段来决定“当前是谁”。这些字段最多是待校验的业务输入；真正的操作者只能来自 `principal`。例如创建消息时，应用服务应使用 `principal.ID` 作为发送者，而不是请求体中的发送者字段。

这样可明确三类责任：路径和查询参数描述“想访问什么、如何筛选”；JSON 描述“想提交什么数据”；`principal` 描述“谁在发起请求”。handler 将它们组装为命令或查询，并携带 `r.Context()` 调用应用层；授权规则则由应用层根据 `principal` 与 `c-a` 判断。

### 传递 Context 并调用应用服务

### 传递 Context 并调用应用服务

Handler 完成请求解析后，应立即停止处理业务细节：把已校验的路径参数、查询条件、请求体字段，以及认证中间件注入的可信身份 `principal` 组装为应用命令，并将 `r.Context()` 原样传入应用服务。

```go
func (h *Handler) CreateMessage(w http.ResponseWriter, r *http.Request) {
    channelID := chi.URLParam(r, "c-a")
    principal, ok := PrincipalFromContext(r.Context())
    if !ok {
        writeError(w, http.StatusUnauthorized, "未认证")
        return
    }

    var in createMessageInput
    r.Body = http.MaxBytesReader(w, r.Body, 4096)
    if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
        writeError(w, http.StatusBadRequest, "请求体无效")
        return
    }
    if err := validateMessage(in); err != nil {
        writeError(w, http.StatusBadRequest, err.Error())
        return
    }

    msg, err := h.app.CreateMessage(r.Context(), CreateMessageCommand{
        ChannelID: channelID,
        SenderID:  principal.ID, // 不信任 JSON 中的 sender_id
        Content:   in.Content,
    })
    if err != nil {
        writeAppError(w, err)
        return
    }
    writeJSON(w, http.StatusCreated, msg)
}
```

这里的 `r.Context()` 承载取消信号、截止时间和请求范围元数据。应用服务及其后续依赖应继续传递该 Context，使客户端断开或超时后，正在执行的操作能够尽早停止。

关键边界是：Handler 不应出现 `h.messages[channelID] = ...`、遍历内存 `map`、生成适配器专用键或判断存储冲突等代码。它只调用 `h.app.CreateMessage`；至于数据保存在哪个内存适配器、测试桩如何隔离、未来是否替换为数据库，都属于应用服务及其依赖的职责。这样 HTTP 层保持可替换，业务规则也不会被协议细节污染。

### 统一响应提交与错误映射

### 统一响应提交与错误映射

`http.ResponseWriter` 的关键约束是：第一次 `WriteHeader` 或 `Write` 就会提交响应头。尤其是 `Write` 未指定状态时，Go 会隐式提交 `200 OK`；此后即使发现业务失败，再调用 `WriteHeader(404)` 也无法改变客户端已收到的最终状态。

| 写法 | 实际结果 | 问题 |
|---|---|---|
| `w.Write(body)` 后 `w.WriteHeader(400)` | 状态仍为 `200` | 错误体与成功状态矛盾 |
| `w.WriteHeader(400)` 后 `w.Write(body)` | 状态为 `400` | 正确 |
| 先计算结果，再统一提交 | 状态、头、错误体一致 | 推荐 |

因此，handler 应在写出任何字节前完成：参数解析、认证、调用应用层、错误分类与状态选择。统一响应函数可固定协议外观：

- 始终设置 `Content-Type: application/json; charset=utf-8`；
- 始终设置 `Cache-Control: no-store`，避免私有消息或认证错误被缓存；
- 成功与失败都输出稳定 JSON；
- 对外暴露机器可读的 `code`，而不是直接泄露底层错误文本。

示意：

`writeJSON(w, status, payload)` 应先设置响应头，再 `WriteHeader(status)`，最后编码 JSON。错误响应可统一为：

`{"error":{"code":"invalid_limit","message":"limit 必须为正整数"}}`

应用层错误不应散落在各 handler 中临时判断，而应集中映射。例如：

- 参数格式错误、字段校验失败 → `400 Bad Request`
- 未认证 → `401 Unauthorized`
- 已认证但无权访问 `c-a` → `403 Forbidden`
- 会话或消息不存在 → `404 Not Found`
- `before` 游标失效或请求与当前状态冲突 → `409 Conflict`
- 限流 → `429 Too Many Requests`
- 未预期的存储或程序错误 → `500 Internal Server Error`

这里的 `sender_id` 即使出现在 JSON 中也不能决定身份；身份只来自认证边界提供的 `principal`。这样，HTTP 状态表达协议语义，机器码服务客户端分支，应用错误则保留在边界内统一翻译。

> **要点** — Handler 守住 HTTP 与可信身份边界；业务决策交给应用服务，响应状态必须在写入正文前确定。

本节把发送与查询收拢到应用服务：HTTP只做边界处理，业务规则、授权与内存受理状态由用例层统一维护。

### 以用例签名界定应用服务

### 以用例签名界定应用服务

应用服务以面向业务的签名暴露能力，而不是暴露 HTTP、路由或 JSON 细节：

`Send(ctx, principal, conv, id, body)`  
`List(ctx, principal, query)`

`ctx` 用于取消、超时与链路信息；`principal` 是已认证的调用者；`conv`、`id`、`body` 与 `query` 是业务输入。应用层首先按动作授权：发送者是否可向该会话发送，查询者是否可读取该会话；不能把“已登录”误当作“允许执行所有动作”。

`Send` 负责调用领域规则验证消息，例如 `ValidateMessage` 检查正文、标识与消息种类。消息种类若由服务器拥有，就不能信任客户端传入的 kind。验证通过后，经由小型存储接口原子追加；重复 `id` 必须由存储层在追加时判定，避免“先查再写”的竞态。成功结果表示 `accepted_in_memory`：消息已被当前内存适配器受理，不代表已持久化、投递或通知对方。

`List` 在授权后委托存储读取，并保持既定分页契约：按 `seq` 倒序，游标表示下一页边界，返回项目与后续游标。

应用服务返回业务结果或业务错误，例如未授权、无效消息、重复消息、游标无效；它不依赖 HTTP 状态码、URL、请求头或 JSON，也不负责真实登录、数据库写入与消息投递。存储仅需由调用方拥有的窄接口提供 `Append` 与 `List`，内存适配器即可满足当前用例。

### 发送前授权与服务端消息规则

### 发送前授权与服务端消息规则

`Send(ctx, principal, conv, id, body)` 的首要职责不是“把 JSON 写进存储”，而是判定当前主体能否在该会话中执行“发送”动作。授权应按动作拆分：能查看会话不等于能发送消息，能发送普通消息也不等于能发送系统通知或以他人身份发言。

因此，用例层应先依据 `principal` 与 `conv` 执行发送授权，例如确认主体已认证、属于该会话、未被禁言，并具有 `message:send` 权限。HTTP 中的令牌、请求头或路由参数只用于构造输入；应用服务不依赖 HTTP 状态码、URL 或 JSON 字段来作出授权结论。

消息的可信字段必须由服务端拥有。客户端可提交的通常只有内容 `body`、客户端生成的请求标识 `id` 等有限数据；`author_id` 必须取自 `principal`，`kind` 应固定为服务端允许的用户消息类型，`seq`、创建时间及受理状态也不能相信客户端输入。否则客户端可能伪造管理员消息、冒充其他成员，或指定任意排序序号。

将这些规则收敛为领域校验，例如：

`ValidateMessage(kind, author, body)`

它至少保证：

- `kind` 是服务端允许创建的消息种类，而非任意字符串；
- 作者身份非空且来自已验证的 `principal`；
- 内容满足长度、非空、字符或结构约束；
- 系统消息、投递回执等服务端专属种类不能由普通发送入口创建。

授权回答“谁能发送”，`ValidateMessage` 回答“这是否是一条合法消息”。二者不能互相替代：已授权用户仍可能提交非法内容；格式正确的消息也仍可能来自无权主体。通过先授权、再构造服务端拥有字段、最后执行领域校验，用例层才能向内存适配器提交可被接受的业务消息。

### 原子追加、去重与内存受理结果

### 原子追加、去重与内存受理结果

`Send(ctx, principal, conv, id, body)` 在完成会话级发送授权、`ValidateMessage` 等领域校验后，不应先“查询是否存在相同 `id`”，再执行写入。并发请求可能同时查到不存在，随后各自写入，造成重复消息。重复标识检测必须是存储层 `Append` 的原子语义：

- 若 `(conv, id)` 尚不存在：追加消息，分配单调递增的 `seq`，返回受理结果；
- 若该标识已存在：不再追加，返回明确的重复错误或幂等结果；
- 检测重复、分配序号、写入消息必须处于同一个临界区。

因此，应用层依赖的是小接口的行为契约，而不是内存实现细节：

`Append(ctx, conv, message) -> accepted_in_memory / duplicate / error`

内存适配器可用互斥锁保护每个会话的消息集合及其 `id` 索引，使“查重 + 追加 + 分配 `seq`”不可分割。`List` 再按 `seq` 倒序读取，并依据上一节定义的游标继续分页；不能用数组下标或时间戳代替稳定序号。

`accepted_in_memory` 的含义必须克制：消息已被当前进程的内存存储接受，能够被后续查询读到。它**不**表示已持久化到数据库、已投递给对方、已推送通知，也不表示进程重启后仍存在。应用服务返回这一业务结果，让外层 HTTP 自行映射状态码和 JSON；未来替换为数据库、队列或投递系统时，用例边界无需改变。

### 面向消费方的小型存储接口

### 面向消费方的小型存储接口

应用服务需要的不是“内存数据库”，而是两项能力：原子追加消息与按约定查询消息。因此接口应由消费方——`Send`、`List` 用例——定义：

```go
type MessageStore interface {
    Append(ctx context.Context, m Message) (Message, error)
    List(ctx context.Context, conv ConversationID, q MessageQuery) (MessagePage, error)
}
```

与直接依赖 `InMemoryStore` 相比，小接口把边界说得更准确：

- **直接依赖具体实现**：应用层知道锁、切片、映射等内存细节；未来替换为数据库、远程存储或测试替身时，改动会扩散到用例代码。
- **依赖消费方接口**：`Send` 先完成动作级授权、`ValidateMessage` 与服务端字段生成，再调用 `Append`；重复检测与“写入一次”的原子性由存储适配器负责。
- **查询契约保持稳定**：`List` 只要求结果按 `seq` 倒序，并遵守游标分页规则；内存适配器如何扫描、数据库适配器如何建立索引，都不泄漏给应用层。

构造时显式注入适配器：

```go
app := NewApp(InMemoryStore{})
```

这里的内存实现表示“已受理到本进程内存”，并不意味着已登录、已持久化或已投递。应用服务也不应知道 HTTP 状态码、URL、JSON；它只返回业务结果或业务错误。这样，适配器可替换，而 `Send` 与 `List` 的业务语义不随传输层和存储层变化。

### 查询排序、游标与业务错误

### 查询排序、游标与业务错误

`List(ctx, principal, query)` 是应用层用例：它确认调用者可查看该会话，落实稳定的分页语义，并返回业务结果或可识别的业务错误；它不认识 HTTP 状态码、URL 参数或 JSON 响应结构。

查询结果必须按服务器分配的 `seq` **倒序**排列，即最新消息在前。游标遵循第 09.02 节的合同：它描述“本页末尾记录之后”的位置，而不是页码。若本页最后一条记录的序号为 `seq=42`，则下一页只能返回满足 `seq < 42` 的记录；适配器即使在内部采用数组、切片或其他索引，也不得把重复项或边界项带到下一页。

应用服务应校验并规范化查询条件，例如限制 `limit` 的上限、拒绝无效游标，并将已验证的条件交给消费者拥有的存储接口：

`List(ctx, principal, query) -> (items, nextCursor, error)`

其中内存适配器负责按 `seq` 过滤、倒序排列和截取；应用层负责将存储结果组织为用例结果，并确保 `nextCursor` 仅在仍有后续记录时出现。这样，分页规则不依赖某个路由、查询字符串名称或前端页面实现。

错误也应保留业务身份，例如“未认证”“无权查看会话”“会话不存在”“游标无效”。传输层随后自行映射为状态码和 JSON；应用层只返回领域可判断的错误值。内存查询成功仅表示当前受理状态可读，不暗示已登录、已持久化到数据库或已投递给任何客户端。

> **要点** — 应用服务守住可信身份、动作授权、领域校验与存储语义；HTTP合同和内存实现都应停留在其外侧。

内存适配器适合教学与单进程验证，但必须明确其并发保护、游标约束和易失性边界。

### 以内存适配器落实应用端口

### 以内存适配器落实应用端口

`memorystore` 的职责不是“提供一套内存数据库”，而是实现应用层定义的最小端口。应用服务只依赖诸如“保存消息”“按会话读取”“创建或校验游标”这类接口，不应知道数据实际存放在 `map`、SQL、Redis 还是远程服务中。

内存实现通常维护三类受保护状态：

- `map`：按消息标识快速定位记录；
- `order`：保存插入顺序或会话内顺序，用于稳定分页；
- `seq`：生成单调递增的序号，作为排序与游标依据。

这些状态必须由同一把 `mutex` 协调：写入时同时更新记录、顺序和序号；读取时在锁保护下取得一致快照，再执行必要的过滤与分页。这样可以避免并发请求看到“记录已存在但顺序尚未写入”之类的中间状态。

游标也属于应用语义，而非 HTTP 参数技巧。游标必须绑定产生它的会话和过滤条件；若客户端拿某个会话、某种筛选条件下的游标去请求另一范围，适配器应拒绝，而不是继续从全局顺序中猜测位置。游标只在当前进程、当前内存状态中有效。

因此，`memorystore` 只能依赖端口所需的领域类型与标准同步原语，不能导入 `handler`、HTTP 请求对象或鉴权实现。它是可替换的基础设施适配器：测试可使用它，未来也可替换为持久化实现，而应用服务无需改写。

同时必须明确边界：每个进程各自拥有一个 store；多进程之间没有共享、复制或一致性保证；进程重启后 `map`、`order` 与 `seq` 全部丢失。它适合教学、单进程开发和验证，不是持久化方案。

### 用互斥锁保护 map、顺序与序号

### 用互斥锁保护 map、顺序与序号

内存存储不只是一个 `map`：为了按会话读取消息、保持插入顺序并生成稳定的消息标识，通常同时维护三类共享状态：

- `map[会话ID][]消息`：按会话定位消息集合；
- `order`：记录会话或消息的创建顺序，用于列表展示、分页或最近访问排序；
- `seq`：单调递增序号，用于分配新的消息 ID。

这三者必须视为一个一致性整体。一次“追加消息”不是仅执行 `append`，而是完成“读取当前序号 → 生成 ID → 写入消息 → 更新顺序 → 递增序号”的状态转换。若多个请求并发执行而没有互斥保护，可能得到重复 ID、丢失追加结果，或出现 `map` 中已有消息但 `order` 未更新的半完成状态。

```go
type MemoryStore struct {
    mu    sync.RWMutex
    msgs  map[string][]Message
    order []string
    seq   uint64
}
```

写操作应持有 `mu.Lock()`，并覆盖所有会共同变化的字段；即使当前只修改 `msgs`，也不要把 `seq` 的递增放到锁外。读操作可持有 `mu.RLock()`，但必须在锁保护下完成游标定位、过滤与切片边界计算。尤其不能先在锁内取得切片，再在锁外直接返回其底层数组：后续写入可能改变其内容或容量。更稳妥的做法是复制本次响应所需的消息。

临界区不应包含认证、参数解析、网络调用或复杂业务规则；这些工作应在进入存储层前完成。存储层锁只负责保护内存状态及其不变量：`seq` 不回退、顺序与消息内容一致、读取不会观察到中间状态。

### 将游标绑定到会话与筛选条件

### 将游标绑定到会话与筛选条件

分页游标不是“第几条记录”，而是某次查询在特定视图中的续读位置。内存存储应将游标与会话、筛选条件及顺序边界共同绑定；客户端只能继续读取自己刚才请求的那一组数据，不能把游标挪到另一会话或另一筛选条件中使用。

可将游标编码为至少包含以下语义的信息：

- `conversationID`：游标所属会话；
- `filter`：如消息类型、时间范围或状态等查询条件的规范化表示；
- `lastSeq`：本页最后一项的单调序号；
- 可选的版本、签名或不可预测令牌，用于拒绝伪造值。

处理下一页请求时，适配器必须先验证游标中的 `conversationID` 与当前请求一致，再比较筛选条件是否完全一致，最后检查 `lastSeq` 是否处于该会话当前可见记录的合法边界。任何不匹配、已失效、超过最大序号或无法解析的游标，都应返回明确的参数错误，而不是悄悄从头分页或返回空页。

```text
请求会话 A + 游标(A, filter=X, seq=12)  → 可续读
请求会话 B + 游标(A, filter=X, seq=12)  → 拒绝
请求会话 A + 游标(A, filter=Y, seq=12)  → 拒绝
请求会话 A + 伪造或越界 seq              → 拒绝
```

这种校验既避免跨会话数据混入，也防止筛选条件变化导致重复、遗漏或错误定位。游标只描述本进程内当前内存快照的逻辑位置：服务重启后，`map`、顺序索引和序号计数器都会丢失，旧游标自然不再有效；它不提供跨进程、跨重启的一致性承诺。

### 识别单进程内存状态的边界

### 识别单进程内存状态的边界

教学用内存存储通常以 `map + order + seq` 保存实体、排序索引与递增序号，并用互斥锁保护并发读写。它实现应用层定义的存储接口，因此 handler 和业务服务不必知道数据实际放在哪里；但这种“可替换”不意味着它具备持久化或分布式能力。

| 维度 | 单进程内存存储 | 持久化/多进程存储 |
|---|---|---|
| 状态归属 | 当前进程私有 | 由文件、数据库或共享服务维护 |
| 重启后数据 | 全部丢失 | 可恢复或持续存在 |
| 多实例访问 | 各进程各有一份副本 | 多实例可见同一逻辑数据 |
| 并发保护 | 本进程内用互斥锁即可 | 还需事务、锁或一致性协议 |
| 适用场景 | 教学、测试、单机演示 | 生产部署、横向扩容、长期保存 |

因此，启动两个服务进程并不会得到“同一个内存库”，而是得到两份彼此独立的状态：进程 A 创建的会话、消息和游标，进程 B 完全不可见。负载均衡若把同一用户的后续请求分发到另一进程，可能表现为会话不存在、列表为空或游标无效。

互斥锁只解决单个进程内的竞争条件，不能同步跨进程数据；递增 `seq` 也只在该进程生命周期内唯一。进程退出、崩溃或重启后，内存被释放，新的存储实例从空状态重新开始。

因此，命令根入口应在读取并校验配置后构造一个存储实例，再注入私有测试授权器、服务与 handler/server。固定授权的桩只应服务测试，不能作为可公开运行的认证方案。

### 在 cmd 根目录集中完成接线

### 在 cmd 根目录集中完成接线

`cmd` 的根入口只负责“装配”，不承载业务规则，也不让 HTTP handler 自行创建依赖。启动流程应当是：读取环境变量、配置文件或命令行参数；完成必填项、端口、运行模式等校验；随后按依赖方向构造组件。

```text
已校验配置
   │
   ├──> 内存存储（每个进程一个实例）
   ├──> 私有测试鉴权器（仅测试装配可用）
   │
   └──> 应用服务 ──> HTTP handler ──> HTTP 服务器
```

典型依赖链为：存储实现应用层定义的仓储接口；服务接收仓储与鉴权相关抽象；handler 只调用服务；服务器只注册路由、超时和监听地址。这样，替换内存存储为数据库、替换测试鉴权为真实身份提供方时，业务规则与路由代码无需重写。

配置必须在创建监听器之前校验。例如地址非法、必需密钥缺失、生产环境误选测试鉴权器，都应使进程快速失败，而不是带着不完整依赖启动。尤其不能把“固定返回某个用户”的鉴权桩暴露为公开可运行选项：它可以是测试中的私有构造器，或仅在测试文件中注入的实现，但不能成为生产二进制的默认路径。

内存存储的生命周期也由根入口明确：一次启动创建一个实例，进程内的请求共享它；进程重启、崩溃或多副本部署都会失去或分裂状态。它不提供跨进程一致性，因此适合本地验证与教学，不应被装配层伪装成持久化方案。

> **要点** — 内存存储实现应用端口而非业务规则；以锁和受限游标维持进程内一致性，并由 cmd 集中装配可替换依赖。

配置与日志是服务启动的边界：先拒绝不安全或不完整的运行参数，再以可追踪但不泄密的方式观察请求。

### 配置作为唯一运行入口

### 配置作为唯一运行入口

服务不应把运行参数散落在 `main`、处理器闭包和环境变量读取逻辑中。为新服务定义唯一的 `Config`，由启动层构造、校验后一次性注入应用：

```go
type Config struct {
    ListenAddr      string
    RequestCap      int
    BodyMaxBytes    int64
    DefaultPageSize int
    MaxPageSize     int
}
```

一组明确的默认值可以减少部署歧义：

- `ListenAddr`：必须显式指定，例如 `:8080`；
- `RequestCap`：`4096`，限制单次请求可处理的条目或结果规模；
- `BodyMaxBytes`：`6 << 20`，即 $6\text{ MiB}$；
- `DefaultPageSize`：`20`；
- `MaxPageSize`：`100`，客户端请求更大页数时应截断或拒绝。

启动时完成校验，而不是等请求到达才暴露错误：

```go
func (c Config) Validate() error {
    if c.ListenAddr == "" || c.RequestCap <= 0 ||
        c.BodyMaxBytes <= 0 || c.DefaultPageSize <= 0 ||
        c.MaxPageSize < c.DefaultPageSize {
        return errors.New("无效服务配置")
    }
    return nil
}
```

配置优先级也必须可说明：显式传入的服务配置最高，其次是部署环境提供的值，最后才是安全默认值。不要把本地命令行工具的 `IMHISTORY_FILE` 规则偷偷复用于 HTTP 服务；它属于另一种运行边界。服务配置确定后，处理器只读取已注入的限制，不再自行读取环境变量，从而保证测试、部署与实际行为一致。

### 启动时校验与明确优先级

### 启动时校验与明确优先级

服务配置应在监听端口、注册路由之前完成解析与校验；错误配置必须导致进程启动失败，而不是把风险延后到某次请求。推荐顺序是：

1. 读取内建默认值：监听地址、单次请求上限 `4096`、请求体最大值 `6`、默认分页大小 `20`、分页最大值 `100`。
2. 加载服务级配置来源，例如环境变量或部署配置文件。
3. 应用显式启动参数覆盖；显式参数优先级最高，便于测试、灰度和容器部署。
4. 归一化并校验最终配置。
5. 只有校验通过，才创建服务、初始化日志器并开始监听。

可将结果理解为：

`最终配置 = 显式启动参数 > 环境/部署配置 > 内建默认值`

校验不仅检查“是否存在”，还要检查边界关系。例如请求上限必须为正；请求体限制不能为负；默认分页大小应满足 `1 ≤ pageDefault ≤ pageMax`；`pageMax` 不应超过服务约定的 `100`。监听地址为空、端口非法或分页边界矛盾时，应返回清晰错误并退出，而不是静默回退到不可预期的值。

配置对象应集中表达服务运行契约，例如：

`Config{ListenAddr, RequestCap: 4096, BodyMax: 6, PageDefault: 20, PageMax: 100}`

这里的配置属于网络服务本身，尤其不要与本地命令行工具的 `IMHISTORY_FILE` 混用。后者只决定交互式命令历史保存到哪里，不影响服务监听、请求限制或数据行为。将两者分开，才能避免某个开发机上的本地习惯意外变成线上服务的运行规则。

### 请求限制落在HTTP边界

### 请求限制落在 HTTP 边界

HTTP handler 的职责不只是“把 JSON 解码后交给服务层”，还要在请求进入业务规则前完成资源保护与输入整形。请求体大小、消息数量、分页参数都属于传输层约束：它们防止异常客户端消耗内存、制造超大日志或绕过预期的查询成本，不应由内存适配器或领域对象被动承担。

建议将限制集中在服务配置中，例如：

- 请求体最大 `4096` 字节；
- 单次请求最多 `6` 条消息；
- 分页默认大小 `20`；
- 分页最大大小 `100`。

读取请求体时使用 `http.MaxBytesReader`，而不是先完整读取再检查长度：

`r.Body = http.MaxBytesReader(w, r.Body, cfg.BodyMaxBytes)`

随后解码 JSON；若超过限制、JSON 格式错误或消息数大于 `6`，handler 应返回明确的 `400 Bad Request`。这类错误表示请求不满足接口契约，不应进入领域服务，更不应写入存储。

分页参数同样在 handler 规范化。缺省或为零时使用默认值 `20`；超过 `100` 时可以拒绝请求，或统一截断到 `100`。前者契约更严格、客户端错误更可见；后者兼容性更好，但必须在接口文档中说明。无论选择哪种策略，领域服务接收到的都应是已经验证过的分页值。

```text
请求 → 体积限制 → JSON 解码 → 数量/分页校验 → 领域服务 → 适配器
```

不要把完整请求体、消息文本、令牌或原始 JSON 写入日志。handler 只记录操作标识、处理阶段、状态码、耗时及消息数量等摘要信息。这样既能定位“请求过大”或“分页越界”，又不会因边界日志泄露用户内容。

### 用slog记录可操作证据

### 用slog记录可操作证据

日志的目标不是“复述请求”，而是让运维者能回答：哪次操作失败了、失败在哪个阶段、影响了多少对象、耗时是否异常。标准库 `log/slog` 提供结构化字段，适合作为服务边界的统一观测出口。

启动时记录已生效的非敏感配置，例如监听地址、请求上限、正文大小上限与分页范围：

`logger.Info("服务启动", "监听地址", cfg.ListenAddr, "请求上限", cfg.RequestCap, "默认分页", cfg.DefaultPageSize, "最大分页", cfg.MaxPageSize)`

每个 HTTP 请求在入口生成或提取操作标识 `op_id`，并在 handler 结束时记录关键证据：

- `op_id`：关联同一次请求的验证、查询与响应日志；
- `stage`：如 `decode`、`validate`、`service`、`respond`；
- `status`：最终 HTTP 状态码；
- `duration_ms`：总耗时，便于发现慢请求；
- `count`：返回条目数、写入条数或拒绝条数；
- `code`：稳定的业务错误码，而非仅依赖易变的错误文本。

例如，handler 在边界处汇总日志：

`logger.Info("请求完成", "op_id", opID, "stage", "respond", "status", status, "duration_ms", elapsed.Milliseconds(), "count", len(items))`

参数错误或业务失败可用 `Warn`，内部故障用 `Error`；但不要把日志器传入领域对象。领域规则应返回结果和可分类错误，由 HTTP 适配器决定状态码与日志字段。这样业务层不会依赖 `slog`，测试也无需断言日志实现细节。

尤其不要记录请求正文、认证令牌、完整 JSON、密码或可能含个人信息的查询条件。日志应保留“发生了什么”的证据，而非“用户提交了什么”的副本。认证与 TLS 会在后续章节补齐；在此之前，更不能因调试便利而把 stub 服务直接公开暴露。

### 日志边界与未来安全接线

### 日志边界与未来安全接线

边界日志回答“请求如何进入、如何离开服务”，领域日志回答“业务规则为何作出某个决定”。两者不能混用：前者服务于运行观测与故障定位，后者若散落在用例、实体或内存适配器中，会把具体日志框架和运维策略渗入核心逻辑。

| 位置 | 应记录 | 不应记录 |
|---|---|---|
| HTTP handler / 中间件边界 | 操作 ID、路径、阶段、状态码、耗时、分页数量、返回条数 | 请求体、令牌、完整 JSON、密码或身份声明 |
| 领域服务 | 必要时返回可分类错误或业务结果 | 直接调用 `slog`、拼接 HTTP 细节、输出用户私密数据 |
| 适配器 | 存储失败等可包装错误 | 把内部数据结构完整打印到日志 |

推荐在启动时构造 `slog.Logger`，再由 handler 或中间件持有它。一次请求至少关联同一个操作 ID，并在开始、校验失败、业务完成等阶段输出结构化字段，例如 `op_id`、`stage`、`code`、`duration_ms`、`count`。这样可按字段检索异常，而不必依赖脆弱的文本匹配。

当前的身份信息只能是开发期占位：它可以帮助接口先形成“请求上下文中存在调用者”的形状，却不能代表认证已经完成。若服务监听非本机地址，或被反向代理、容器端口映射暴露，就不得公开提供这种 stub 服务；否则任何调用者都可能伪造身份。

为后续接线预留明确边界：认证中间件负责验证凭证并写入调用者上下文，授权规则在应用层读取该上下文；TLS 由监听层或可信反向代理终止。后续章节接入真实认证与 TLS 时，应替换边界组件，而不改动领域规则。

> **要点** — 集中配置、启动校验和脱敏边界日志，使服务可控、可观测且不把临时实现误当作公开安全能力。

本节建立统一失败出口：领域、存储与应用层只表达稳定错误身份，HTTP 边界集中翻译状态码、机器码与响应，并为后续分层测试预留接口。

### 以稳定错误身份贯穿分层

### 以稳定错误身份贯穿分层

错误文本面向人，错误身份面向程序，错误上下文面向排障；三者不能混为一谈。若处理器通过

`if err.Error() == "not found"`  

判断失败，文案改动、补充对象信息或更换语言都会破坏协议。分层之间应传递可判定的稳定身份，并保留调用链上下文。

领域层定义业务语义的哨兵错误，例如：

`ErrInvalidInput`、`ErrForbidden`、`ErrConflict`、`ErrUnsupportedMedia`

内存存储定义持久化语义错误，例如：

`ErrNotFound`、`ErrAlreadyExists`、`ErrCapacityExceeded`

应用服务不把底层错误文本重新拼成字符串，而是按需要补充上下文并包装：

`return fmt.Errorf("创建成员 %q: %w", id, ErrConflict)`

或保留存储错误身份：

`return fmt.Errorf("保存会话: %w", err)`

调用方统一使用 `errors.Is`：

`if errors.Is(err, store.ErrNotFound) { ... }`

这样，包装后的 `"保存会话: 记录不存在"` 仍可被判定为不存在，而日志也能显示操作、对象和调用位置。哨兵错误应是包级稳定契约，避免每次失败都临时 `errors.New(...)`；后者即使文本相同，身份也不同。

应用层负责组合认证、领域规则与存储结果，但不决定 HTTP 状态码。HTTP 边界才将错误身份映射为 `400`、`401`、`403`、`404`、`409`、`413`、`415`、`406` 或 `500`。未知错误一律作为内部错误处理，既不字符串匹配，也不向客户端泄露底层实现细节。

### 在唯一 HTTP 出口映射失败

### 在唯一 HTTP 出口映射失败

HTTP handler 是错误到协议语义的唯一翻译点。领域层、存储层和应用层不应返回“`404 not found`”之类的 HTTP 文本，更不能让上层通过字符串比较判断失败；它们只暴露可稳定识别的哨兵错误，并用 `%w` 保留错误链：

- 领域规则：`ErrInvalidInput`、`ErrConflict`
- 认证与授权：`ErrUnauthenticated`、`ErrForbidden`
- 存储访问：`ErrNotFound`、`ErrConflict`
- 请求表示：`ErrTooLarge`、`ErrUnsupportedMediaType`、`ErrNotAcceptable`

handler 在一次集中判断中使用 `errors.Is` 映射响应：

| 错误身份 | HTTP 状态 |
|---|---:|
| 输入无效 | 400 |
| 未认证 | 401 |
| 无权限 | 403 |
| 资源不存在 | 404 |
| 状态或唯一性冲突 | 409 |
| 请求体超过限制 | 413 |
| `Content-Type` 不受支持 | 415 |
| `Accept` 无可协商表示 | 406 |
| 其他未知错误 | 500 |

例如，应用层可返回 `fmt.Errorf("创建项目：%w", store.ErrConflict)`；handler 仍能以 `errors.Is(err, store.ErrConflict)` 得到 `409`，而无需依赖包装后的错误文本。响应体同时输出稳定机器码，如 `{"code":"conflict"}`，日志则保留原始错误链以供诊断。

必须保证响应只提交一次。写入状态码、响应头或正文后，连接已获得可见结果；随后即使发现错误，也不能改写为 `500`，最多记录日志并停止后续写入。尤其当 `r.Context()` 因客户端断连而取消时，取消只表示客户端不再等待：已经被内存适配器接受并写入的变更不自动回滚，最终结果可能对客户端未知。handler 应停止无意义工作，但不得声称该操作必然失败或必然撤销。

### 一次提交响应的不可逆边界

### 一次提交响应的不可逆边界

HTTP 响应一旦开始写出，便进入不可逆状态：调用 `WriteHeader`、写入正文，或由 `Write` 隐式提交 `200` 后，状态码和响应头通常都不能再可靠修改。此后即使发现权限、存储或编码错误，也不能把已发出的成功响应改成 `500`。

因此，handler 应把“可能失败的工作”全部放在提交之前：

1. 解析并验证请求：方法、路径参数、认证信息、`Content-Type`、请求体大小与业务字段。
2. 调用应用服务：由其协调认证、领域规则和存储操作。
3. 在唯一的出口翻译错误：通过 `errors.Is` 判断稳定哨兵错误，映射为对应 HTTP 状态与机器码。
4. 仅当结果已确定后，统一写入响应头、状态码和正文。

```go
result, err := app.Execute(r.Context(), input)
if err != nil {
    writeError(w, err) // 唯一失败提交点
    return
}
writeJSON(w, http.StatusOK, result) // 唯一成功提交点
```

不要在深层辅助函数中直接写 `ResponseWriter`，也不要先输出部分 JSON、日志式文本或成功状态，再继续执行可能失败的操作。若写出后发生失败，只能记录错误、停止后续写入；客户端看到的结果可能已不完整，但服务器不能伪造另一份状态。

### 取消请求与内存受理结果

### 取消请求与内存受理结果

`r.Context()` 在客户端断连、超时或上游主动取消时会变为完成状态。应用层应把它作为**停止继续协调工作**的信号：在调用认证、领域服务和存储适配器前后检查 `ctx.Err()`，并将上下文传递给支持取消的依赖。

但取消不是事务回滚指令。尤其对内存适配器而言，一次写入可能已经完成：

1. 请求到达应用层，开始创建或更新；
2. 内存适配器已加锁、校验并写入状态；
3. 客户端断连，`ctx.Done()` 触发；
4. 应用层无法确认响应是否送达客户端。

此时不能因为 `ctx.Err()` 就擅自删除已写入的数据；那会把“客户端未收到结果”错误地变成“业务操作未发生”。正确语义是：**受理结果可能已成功，但调用方结果未知**。

应用层应区分两个时点：

- **适配器受理前取消**：停止调用，返回取消错误，不产生变更。
- **适配器受理后取消**：保留适配器已提交的状态；不再尝试重写 HTTP 响应或补偿删除。客户端应通过幂等键、资源查询或后续读取确认最终结果。

内存适配器若不支持中途取消，也应明确其原子边界：要么尚未写入，要么写入完成。这样请求取消只影响等待与响应协调，不模糊已受理变更的事实。

### 按边界安排未来验证

### 按边界安排未来验证

后续测试不应让所有场景都穿过 HTTP 与内存适配器；不同边界验证不同承诺，才能定位错误归属。

- **纯领域规则测试**：直接构造输入与状态，断言规则返回稳定的哨兵错误，如“名称冲突”“状态不允许转换”。这里不关心 HTTP 状态码、认证身份或上下文取消；重点是禁止依赖错误字符串，调用方应使用 `errors.Is(err, ErrConflict)` 判断身份。

- **应用服务测试**：注入伪认证器与伪存储，覆盖认证失败、无权操作、对象不存在、版本冲突、容量超限等组合。验证应用层只编排身份、权限和领域规则，并保留可被 `errors.Is` 识别的错误链；不应提前写入响应或自行决定 `404`、`409`。

- **`httptest` handler 测试**：从请求到响应验证唯一 HTTP 边界的映射：请求格式、媒体类型、协商失败分别对应 `400`、`415`、`406`；认证与授权对应 `401`、`403`；领域与存储错误对应 `404`、`409`、`413`，未知错误统一为 `500`。同时断言响应只提交一次；一旦已写出成功头或正文，后续失败只能记录，不能改写状态。

- **内存集成测试**：使用真实内存适配器检查跨调用可见性、冲突检测与提交时机。尤其应模拟 `r.Context()` 因客户端断开而取消：若写入已被接受，取消不等于回滚，调用方只能得到“结果未知”，不能据此断言内存状态必然未改变。

> **要点** — 错误身份跨层传播、HTTP 统一翻译且响应只提交一次，才能让失败语义稳定可测。

通过同一组请求轨迹观察包边界、状态变化与响应提交：每个组件只处理自己拥有的信息和变化。

### 先建立请求轨迹与责任地图

### 先建立请求轨迹与责任地图

先用一条成功请求固定边界：合法成员 `u-a` 向会话 `m-a` 提交一条消息。请求沿依赖方向进入，状态只在拥有它的层中变化：

`cmd → httpapi → app → domain → memorystore → app → httpapi`

| 步骤 | 包/责任拥有者 | 处理内容 | 数据归属与可观察结果 |
|---|---|---|---|
| 1 | `cmd` | 装配路由、应用服务与内存存储实现 | 不解释业务含义；仅决定组件如何连接 |
| 2 | `httpapi` | 接收 `POST /meetings/m-a/messages`，读取身份 `u-a`、路径参数和请求体 | HTTP 状态码、响应头、响应体尚未提交 |
| 3 | `httpapi` | 将输入转换为“发送消息”命令 | 负责协议格式错误，如缺字段、非法 JSON；不直接修改会话 |
| 4 | `app` | 编排用例：加载会话、请求领域规则、保存结果 | 拥有用例流程；不拥有 HTTP 细节或内存索引 |
| 5 | `memorystore` | 按 `m-a` 读取会话聚合 | 拥有内存中的键、记录及查找方式；找不到时返回明确结果 |
| 6 | `domain` | 判断 `u-a` 是否为成员、消息是否有效，并创建消息 | 拥有成员资格与消息创建规则；成功后会话新增一条消息 |
| 7 | `memorystore` | 保存更新后的会话 | 内存状态从“旧消息序列”变为“旧序列 + 新消息” |
| 8 | `app` | 返回创建结果 | 返回领域/用例结果，而非 HTTP 响应 |
| 9 | `httpapi` | 映射为成功响应并提交 | 客户端观察到如 `201` 与消息表示；提交后不可再改状态码或响应体 |

关键不是“每层都检查一次”，而是让检查落在信息最完整的拥有者：`httpapi` 判断请求是否符合协议，`app` 组织读取—判定—保存，`domain` 判断成员能否发言，`memorystore` 管理数据存取。于是这条轨迹同时给出可验证的不变量：

- 成功响应前，`m-a` 中恰好多出一条由 `u-a` 创建的消息。
- `httpapi` 不得绕过 `app` 直接写入存储。
- `domain` 不依赖路径、状态码或 JSON。
- 存储只保存结果，不把“是否成员”这样的业务裁决藏进索引逻辑。

### POST：从合同校验到消息受理

### POST：从合同校验到消息受理

以合法请求为例，轨迹应跨越明确边界：

1. `handler`拥有 HTTP 合同：确认路径与方法、限制正文大小、解码 JSON、检查字段形状；格式错误立即返回 `400`，状态不变。
2. `handler`从认证上下文取得可信身份，而不信任正文中的用户标识；随后调用应用层。
3. 应用服务拥有业务规则：核验发送者身份、目标会话存在性与成员资格；非成员映射为业务错误，`handler`据此写出 `403`。
4. 内存适配器拥有存储变化：以幂等键或业务唯一键原子查找／写入消息。首次提交创建消息，应用服务返回“已受理”，`handler`提交 `201`。
5. 响应一旦提交，消息已在适配器状态中可见；后续日志、连接中断或请求取消都不能把已提交的写入解释为失败。

重复 POST 仍会通过相同的路径、大小与 JSON 检查，但适配器识别到既有幂等记录，不新增消息；应用服务将其归为“重复但成功”，`handler`返回原有结果或约定的成功状态。幂等不是“忽略错误”，而是让同一意图只改变状态一次。

可按以下问题检查边界：①谁校验方法？②谁限制大小？③谁解码 JSON？④谁信任身份？⑤身份来自何处？⑥谁判成员资格？⑦谁定义幂等键？⑧谁保证原子性？⑨首次写入改变什么？⑩重复写入改变什么？⑪谁决定业务错误？⑫谁写 HTTP 状态？⑬何时提交响应？⑭提交后能否回滚？

### GET：游标分页与成员可见性

### GET：游标分页与成员可见性

设内存适配器中消息按创建顺序保存为 `m-1,m-2,m-3`，`u-a` 是会话 `m-a` 成员。处理 `GET /messages?limit=2` 时，各层只承担自己的职责：

1. **handler**：解析查询参数。缺省游标表示从首条开始，`limit=2` 被转换为页大小；无效整数、负数或超过上限时直接返回机器码，如 `invalid_limit`。
2. **业务规则**：先确认请求者是 `m-a` 成员，再请求仓储读取消息。成员资格是可见性规则，不应由适配器猜测“谁可以看”。
3. **内存适配器**：按已确定的会话、游标与页大小切片读取，不修改消息表。

首次响应可表示为：

```text
items = [m-1, m-2]
next_cursor = m-2
```

游标通常是“本页最后一条已见消息”的稳定标识，而不是数组下标。随后请求 `GET /messages?limit=2&cursor=m-2`，适配器从 `m-2` 之后继续读取：

```text
items = [m-3]
next_cursor = 空
```

空游标表示没有后续页；它不是错误，也不意味着消息列表为空。若游标不存在、属于另一会话或格式非法，业务层应拒绝或按课程约定返回 `invalid_cursor`，避免客户端借游标探测其他会话状态。

对照非成员 `u-b` 请求同一路径：handler 仍可正常解析 `limit` 与 `cursor`，但业务规则在读取消息前发现 `u-b ∉ members(m-a)`，立即返回授权拒绝机器码，例如 `not_member`。此时观察结果应明确：

- 响应：拒绝状态与稳定机器码；
- 消息集合：不变；
- 成员集合：不变；
- 分页游标：不产生可用的消息位置信息。

因此，“空列表”和“无权读取”必须可区分：前者是成员看到的业务结果，后者是访问边界的拒绝结果。

### 提交响应后的取消不能改写事实

### 提交响应后的取消不能改写事实

请求的 `context` 应沿调用链传递：handler 从请求取得它，将配置中的超时、请求标识交给日志记录；应用服务据此判断操作是否仍可继续；内存适配器在读写前后检查取消信号。`slog` 日志应记录同一请求标识、取消原因和已完成阶段，而不替业务状态作推测。

关键边界是“响应提交”与“状态提交”：

1. 尚未写入内存适配器时取消：应用服务返回取消结果；handler 不应继续执行业务写入。
2. 内存适配器已成功写入、handler 尚未提交响应时取消：状态已经成为事实。可记录“客户端已取消，写入已完成”，但不能把成员关系或消息从适配器中删除。
3. 成功响应已提交后才取消：HTTP 状态码、响应体和内存状态都不可改写。日志可补充取消事件；不能改发错误响应，也不能声称操作失败。
4. 重复提交请求在取消前已被识别：适配器保持原状态，应用服务返回重复规则结果；取消只影响本次传输，不改变既有事实。

因此，`context` 是停止后续工作的信号，不是事务回滚命令。配置决定检查策略，handler 管理 HTTP 生命周期，应用服务解释业务结果，内存适配器维护状态事实；任何一层都不应越界“撤销”另一层已经提交的结果。

### 把轨迹转成可替换与可验证的设计

### 把轨迹转成可替换与可验证的设计

直接让 `handler` 调用内存仓库，会把 HTTP、业务判断和存储细节绑在一起：替换存储时改处理器，重复报名、游标分页等规则也难以脱离请求验证。更稳妥的边界是：消费方声明小接口，构造时注入实现；规则层只接收数据与依赖，不知道 `net/http`、日志器或具体内存结构。

| 方案 | 依赖方向 | 替换成本 | 验证重点 |
|---|---|---|---|
| 直接依赖内存实现 | handler → 内存适配器 | 高 | 只能偏集成地验证 |
| 小接口＋构造注入 | handler → 用例接口；用例 → 仓储接口 | 低 | 可分层替身验证 |

将轨迹拆为四层：纯规则验证“重复报名”判定；服务替身验证 handler 对成功、非成员、取消的映射；HTTP 边界验证 POST、GET、`limit=2` 与 `cursor`；内存集成验证提交后状态确已改变。取消发生在提交之后时，状态可以保留，但尚未提交的响应应遵循请求取消语义；不能把“客户端未收到响应”误判为“写入未发生”。`net/http` 的响应提交规则与 `slog` 的结构化字段约定可作为边界参考。
