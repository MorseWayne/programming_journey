## 10.10 持续交付与版本管理：发布成功为何还要看消息

- 保持当前S2/拟议S3/R9/事件格式四轴独立
- 列出候选制品与部署配置身份
- 安排数据库和事件读写端兼容顺序
- 设计有代表性的灰度及停止门
- 区分Pod更新与IM连接/任务在途
- 审查代码、配置和数据各自的回退能力

发布窗口首先要保护用户已见行为：当前S2/v1合同不变，S3、R9与event_v2分别作为独立演进轴审查。

### 先冻结当前用户可见合同

### 先冻结当前用户可见合同

发布前先把 **S2/v1** 当作不可漂移的兼容性基线：后续即使引入 S3/v2、R9 或 `event_v2`，也不得反向改写旧接口已承诺的可见行为。

当前 `POST` 消息接口的合同应明确写成：

- 请求消息正文最多 **6 个 UTF-8 字节**；限制按编码后的字节数计算，不按字符数计算。ASCII 字符通常各占 1 字节，中文等字符可能占 3 字节；“两个汉字”恰好可能用满 6B。
- 合法请求返回 `200`，响应语义为 `accepted_in_memory`：服务端仅确认消息已被当前内存态接受，不能向客户端暗示已持久化、已进入教学数据库或永久可恢复。
- 同一消息标识重复提交返回 `409`：这是冲突，不是“幂等成功”。客户端不能把 `409` 解释为本次请求已重新写入或更新。
- 非成员身份提交返回 `404`：对外保持“目标不可见/不存在”的语义，不泄露成员资格、房间存在性或权限细节。

可将基线概括为：

`S2/v1 = 6B UTF-8 + 200 accepted_in_memory + 重复ID为409 + 非成员为404`

这里的状态码和措辞都是用户可见合同的一部分。例如，未来实现可能实际写入教学数据库，但旧客户端收到的仍是 `accepted_in_memory`，就不能据此推断其消息已持久化。类似地，若未来准备把上限提高到 9B，也不能让 v1 请求悄然接受第 7～9 字节；那会改变已有验证失败、重试和界面提示的行为。

冻结合同并非停止演进，而是为演进划清边界：任何候选变更先逐项说明它是否改变 v1 的请求校验、成功承诺、冲突语义或信息暴露范围；只要答案为“是”，就必须通过新版本或显式协商交付。

### 拆开四条演进轴

### 拆开四条演进轴

发布时最危险的误解，是把“接口升级”视为一个总开关。这里至少有四条彼此独立的演进轴，必须分别定义合同、兼容策略与回滚条件。

| 演进轴 | 当前或拟议行为 | 不应自动联动的内容 |
|---|---|---|
| S2/v1 协议 | `POST` 消息最多 `6` 个 UTF-8 字节；成功返回 `200 accepted_in_memory`；同一 ID 重复返回 `409`；非成员返回 `404` | 不能因存储实现变化而改写响应语义或放宽长度 |
| S3/v2 协议 | 拟议成功返回 `200 stored_in_teaching_db`，但仍只是教学提议，不等于正式采纳 | 不应顺带启用 R9 的 9 字节限制 |
| R9 长度规则 | 从 `6B` 放宽到 `9B`，仍处于待审状态 | 不应因推出 v2 或新增事件字段而默认生效 |
| 教学 `event_v2` | 增加 `message_version`、`visible` 字段，用于说明消息版本与展示状态 | 不应改变 `POST` 的请求校验、状态码或持久化承诺 |

因此，旧客户端看到的 S2/v1 合同应保持稳定：超过 6 字节仍被拒绝，重复 ID 仍是 `409`，非成员仍是 `404`。即使服务端内部已经写入教学数据库，也不能把 `accepted_in_memory` 悄悄改成 `stored_in_teaching_db`；这会让客户端把实现细节误判为可依赖的持久化保证。

推荐的发布顺序是：先明确并冻结 S2/v1 的用户可见行为；再单独评审 S3/v2 的响应承诺；R9 通过后独立调整长度校验；最后让事件消费者按能力识别 `event_v2` 的新增字段。事件格式升级尤其应采用“可忽略新增字段”的兼容方式：旧消费者继续读取已知字段，新消费者才解释 `message_version` 与 `visible`。

### 用旧客户端检验发布顺序

### 用旧客户端检验发布顺序

设想一款尚未升级的 IM 客户端，它仍向 `S2/v1` 发送：

`POST /messages`，消息体为 UTF-8 文本。

它只认识以下可见合同：

- 消息最多 `6` 个 UTF-8 字节；
- 成功返回 `200 accepted_in_memory`；
- 相同消息 ID 重复提交返回 `409`；
- 非会话成员提交返回 `404`。

现在先发布 S3：服务端可将消息写入教学数据库，并在内部标记为 `stored_in_teaching_db`。这不等于可以改变旧客户端所见行为。对于该旧客户端，S3 上线后的验收应仍是：

| 请求 | 旧客户端应见结果 | S3 内部可发生的事 |
|---|---|---|
| `6B` 以内的新消息 | `200 accepted_in_memory` | 同时写入教学数据库 |
| 超过 `6B` 的消息 | 原有长度校验失败 | 不得因数据库能力而放宽 |
| 重复 ID | `409` | 不得再次写入或产生第二条教学记录 |
| 非成员发送 | `404` | 不得写入教学数据库 |

关键在于，`stored_in_teaching_db` 是服务端教学流程的提议状态，而不是 v1 响应语义。若 S3 直接把成功响应改成 `200 stored_in_teaching_db`，旧客户端可能无法识别状态、错误展示“发送失败”，或触发不必要的重试。

因此发布顺序应是：先让 S3 在 `v1` 既有校验和状态码之后旁路写入；再通过新版本接口、能力协商或新事件字段暴露教学存储信息。R9 的 `6B→9B` 放宽必须另行审批，`event_v2` 的 `message_version`、`visible` 也应独立演进；它们都不能借 S3 发布窗口悄然改变旧客户端合同。

### 把候选制品与配置写成身份清单

### 把候选制品与配置写成身份清单

发布审批的对象不应只是“某次构建成功”，而应是一份可追溯的身份清单：每个候选制品都要声明**版本、开关、读写能力、依赖条件与回滚边界**。这样才能证明 S2/v1、S3/v2、R9 与 `event_v2` 没有被一次配置变更意外捆绑。

| 对象 | 身份与版本 | 开关/启用条件 | 读写能力 | 不可改变的合同 |
|---|---|---|---|---|
| 应用代码制品 | `api-service@S2/v1` | 当前生产默认启用 | 仅接受最多 6 个 UTF-8 字节；内存接收 | `200 accepted_in_memory`；重复 ID 为 `409`；非成员为 `404` |
| 候选应用制品 | `api-service@S3/v2` | 仅在版本路由或白名单开启后接流量 | 仍限制 6B，可写教学提议存储 | `200 stored_in_teaching_db` 仍表示教学提议，不得暗示正式生效 |
| 配置包 | `release-config@R9` | 字节上限从 6→9B，状态为“待审” | 只提供参数，不自动改变接口版本 | 未获批准时，任何客户端仍按 6B 校验 |
| 数据库迁移 | `migration@teaching-db-xxx` | 先完成向后兼容迁移，再允许 S3 写入 | 新表/新列可写，旧路径不得依赖新字段 | 回滚应用时，数据与模式仍可被旧制品读取 |
| 事件消费者 | `consumer@event_v2` | 消费者独立灰度 | 可读取 `message_version`、`visible` | 新字段是事件演进轴，不代表消息长度或持久化语义已升级 |

清单还应明确依赖顺序：先部署可兼容的迁移与消费者，再投放 S3 候选制品，最后单独审批 R9。旧客户端继续调用 S2/v1 时，必须既不看到 `event_v2` 字段带来的行为变化，也不因 9B 配置而突破 6B 限制。若需回滚，只撤销对应制品或开关，而不是同时撤销数据库、接口和事件演进。

### 以消息观察决定是否继续发布

### 以消息观察决定是否继续发布

灰度是否推进，不能只看 `200` 比例，而要验证用户可见合同是否仍成立。对当前 S2/v1，成功响应 `200 accepted_in_memory` 仅说明消息被内存接受；长度超过 6 个 UTF-8 字节应被拒绝、同一 ID 重发应为 `409`、非成员应为 `404`。因此应按请求类别分别统计，而非把所有非 `200` 都当作故障：

- **成功路径**：合法成员、消息长度不超过 6B 的请求，`200` 比例及延迟应稳定；异常下降可能表示鉴权、容量或编码处理回归。
- **幂等边界**：刻意重放同一 ID，`409` 应稳定出现。若变成 `200`，可能产生重复消息；若变成 `5xx`，说明冲突处理不再可靠。
- **权限边界**：非成员请求应持续返回 `404`，不能因发布而泄露会话存在性或误写入消息。
- **事件边界**：订阅端确认教学事件是否仍符合既有可见范围；`event_v2` 的 `message_version`、`visible` 只用于观察新事件合同，不得反向改变 v1 的判断。

停止门应以这些分组指标设定：合法成功率或延迟越界、`409`/`404` 语义漂移、事件可见性出现越权或漏发，任一项即停止扩容。回退也必须独立：S3/v2 可退回 S2/v1 响应语义；R9 的 9B 提议可撤销而保持 6B；`event_v2` 可停止投递或降级消费。尤其不能因 S3 返回 `200 stored_in_teaching_db` 就同时放开 R9 或启用 `visible`，因为三者分别改变存储说明、长度规则与事件合同。

> **要点** — 先守住S2/v1用户合同，再让S3、R9与event_v2按独立身份、兼容顺序和消息证据逐项推进。

持续交付不仅要确认镜像能部署，更要证明本次发布的制品、配置、迁移与观察责任可追溯。

### 发布对象不是一个镜像标签

### 发布对象不是一个镜像标签

`service:latest` 或 `service:v1.8.3` 只能指向某个容器镜像，不能完整说明“这次发布了什么”。真正的候选发布应被视为一个可追溯的组合身份：

\[
Release = Artifact + DeployConfig + Migration + RuntimeFlags
\]

其中：

- **代码制品**：镜像摘要（digest）、源码提交 `SHA`、Go 版本、依赖构建清单、Proto 生成器版本与产物签名。标签可被重推，摘要才是不可变定位。
- **部署配置**：目标集群、命名空间、Helm/Kustomize 渲染结果、资源配额、环境变量引用、密钥版本与副本策略。
- **数据迁移**：迁移脚本 ID、执行顺序、是否已执行、是否可回退，以及迁移与应用版本的兼容窗口。
- **运行开关**：Feature Flag 状态、灰度规则、限流阈值、动态配置快照。相同镜像在不同开关下，业务行为可能完全不同。

因此，发布记录不应只写“部署了 `v1.8.3`”，而应记录：谁在何时将哪个镜像摘要部署到哪里、关联哪些迁移和配置快照、面向哪组客户端灰度、观察哪些指标，以及异常时由谁执行何种回退。

制品可重现、镜像已签名，只能证明“拿到的是预期字节”；它们不能证明迁移安全、开关正确或业务指标健康。静态检查通过也不等于真正完成部署：只有这些身份要素在目标环境中被实际绑定并可查询，发布才是可审计的发布。

### 为制品建立可追溯身份证

### 为制品建立可追溯身份证

一次发布不能只写“版本 `v1.8.0`”。标签可被重新指向，分支会继续前进；真正可定位制品来源的是一组不可变的身份证明。建议在构建产物、镜像标签、部署记录和发布消息中同时保留以下字段：

- **源代码提交**：`source_sha`，记录完整 Git SHA，而非仅记录分支名或短 SHA。它回答“这份二进制究竟由哪一行代码编译而来”。
- **编译环境**：`go_version`，例如 `go1.22.5`；同一源码在不同编译器版本下可能产生不同结果或暴露不同运行时行为。
- **依赖构建列表**：保存 `go list -m all` 的结果，或对应的 `go.mod`、`go.sum` 摘要。源码 SHA 相同不代表依赖解析结果必然相同。
- **协议生成器版本**：记录 `protoc`、`protoc-gen-go`、`buf` 等版本及其配置摘要。接口代码由生成器派生，生成器漂移会改变序列化、字段兼容性或生成文件。
- **镜像摘要**：使用不可变的 `image_digest`，如 `sha256:...`，而非只记录 `service:latest` 或 `service:v1.8.0`。部署系统实际拉取的应是摘要对应的内容。
- **数据库迁移编号**：记录本次包含并已执行的 migration ID，例如 `20240618_add_order_status`，以及目标 schema 版本。这样才能区分“应用已发布”和“数据结构已到位”。

可以将这些信息写入二进制的版本端点、镜像 OCI 标签、构建证明和部署事件：

`source_sha=...; go_version=...; image_digest=...; migration_ids=[...]`

它们描述的是制品如何被推导出来，而不是业务是否正确。即使镜像可复现、摘要一致、签名有效，也仍需结合部署后的客户端范围、配置与功能开关快照、指标观察及回退负责人，才能解释一次发布为何成功或为何需要撤回。

### 可重现与签名为何仍不够

### 可重现与签名为何仍不够

可重现构建回答的是“相同输入能否得到相同制品”：同一 `source SHA`、Go 版本、依赖锁定、Proto 生成器与构建参数，应产生可核验的镜像 `digest`。签名则回答“制品是否确实来自受信任的构建身份”，可防止镜像被替换、来源被伪造。

但这两者都不能证明“发布后业务仍然正确”。一个签名有效、字节完全可重现的镜像，仍可能在真实环境中失败：

- **旧客户端兼容性**：新服务删除了旧字段、改变默认值，仍在使用旧协议的客户端可能解析失败或行为漂移。
- **事件格式兼容性**：消费者尚未升级时，事件字段改名、枚举值扩展、语义变化都会造成积压、丢弃或重复处理。
- **数据库迁移兼容性**：迁移 `ID` 已执行不代表安全；若代码先删除旧列、迁移不可逆，回退到旧版本便可能直接故障。
- **配置与开关语义**：同一镜像在不同 feature flag、限流阈值、区域配置下，实际执行的路径并不相同。

因此，制品身份是发布的必要证据，而非成功结论。发布记录还应关联部署时的配置快照、迁移状态、目标客户端群体、事件版本，以及负责观察指标和执行回退的人。只有这些运行时事实与错误率、延迟、消费积压、关键业务转化共同成立，才能说明“可信制品”真正成为了“正确发布”。

### 部署记录要回答哪些问题

### 部署记录要回答哪些问题

一份发布单不是“已部署”的截图，而是一次可审计、可停止、可回退的业务变更记录。它至少应让值班人员在几分钟内回答以下问题：

- **谁在何时发布了什么？**记录发布者、审批者、开始与结束时间，以及制品身份：`source SHA`、镜像 `digest`、构建版本、数据库迁移 ID。不要只写“发布 v1.8.0”，因为同一标签可能被重建或覆盖。
- **部署到了哪里、影响了谁？**明确目标环境、区域、集群、命名空间与灰度批次；客户端群组应可识别，例如“5% Android 新版用户”“华东企业租户”“内部员工”。这决定异常出现时的影响边界。
- **运行时采用了什么配置？**附上配置与 feature flag 快照或其不可变引用，包括开关状态、关键阈值、外部依赖地址、限流策略。相同镜像在不同配置下可能表现为不同系统。
- **用什么指标判断成功？**预先写明观测窗口与基线，例如部署后 15 分钟内，成功率不低于 `99.9%`、`p95` 延迟增幅不超过 `10%`、支付失败数不高于历史同期 `1.2×`。指标必须关联仪表盘、查询链接和告警规则。
- **何时停止、由谁回退？**定义停止门：一旦错误率、延迟、业务漏斗或资源指标越界，暂停后续批次。记录回退负责人、回退目标版本、是否需要反向迁移，以及联系路径。

制品签名与可重现构建只能证明“部署的是预期字节”；发布单还要证明“在预期对象、配置和风险边界内运行”，并使事故中的停止与回退不依赖临场猜测。

### 静态检查不能替代发布观察

### 静态检查不能替代发布观察

以虚构 IM 服务的灰度发布为例：新版本镜像已通过签名校验，`source SHA`、Go 版本、依赖清单、Proto 生成器版本和镜像摘要均可追溯；数据库迁移 `20250308_add_message_trace_id` 也已执行，消息路由开关仅对 5% 客户端启用。静态检查只能说明“制品与声明一致”，不能说明真实消息链路正确。

例如，新镜像把 `trace_id` 写入消息表，但旧版长连接网关仍按旧 Proto 反序列化；或者配置快照中将重试间隔从 `200ms` 改为 `20ms`，导致失败消息在高峰期被放大重投。部署不会立刻报错，客户端仍显示在线，但可能出现：

- 发送成功后对方迟迟收不到；
- 同一消息因重试被重复投递；
- 在途 WebSocket 连接断开后无法正确恢复会话；
- 新旧客户端对消息状态的解释不一致；
- 迁移锁表使消息持久化延迟持续升高。

因此，灰度后必须按消息链路观察：发送请求量、写库延迟、队列堆积、投递成功率、重复率、端到端到达时延，以及断线重连成功率。观察应关联本次镜像摘要、配置快照、迁移 ID、灰度客户端群组和生效时间。

若指标恶化，回退负责人不能只“回滚镜像”：还要确认开关是否关闭、迁移是否兼容旧代码、已建立的长连接如何排空或重连。可重现制品证明能复建；发布观察才证明它没有伤害正在通信的用户。

> **要点** — 发布身份必须覆盖制品、配置、迁移与责任记录；可构建可签名，不等于消息业务已正确发布。

发布成功只证明新制品已运行；消息、数据库、旧客户端与在途任务是否仍能正确协作，才决定变更是否真正安全。

### 先分清四条演进轴与制品身份

### 先分清四条演进轴与制品身份

一次发布往往同时触及四条彼此独立、却必须协调的演进轴：

- **业务状态轴**：当前系统处于 $S2$，目标是 $S3$。例如 outbox 新增 `message_version`、`visibility`，其默认值、回填规则和权限含义属于状态迁移，而不只是表结构变化。
- **关系模型轴**：发布候选为 $R9$，描述数据库 schema、索引、约束、迁移脚本及其执行顺序。`ALTER TABLE` 能否快速完成、是否持锁、是否需要分批回填，取决于实际 PostgreSQL 版本与表规模，不能仅凭迁移“执行成功”判断。
- **事件格式轴**：`event_v1` 与 `event_v2` 是独立兼容面。新增字段虽可能在 wire 层可解析，却未必语义安全：旧消费者可能忽略 `visibility`，从而错误处理本应受限的消息。
- **制品与配置轴**：同一代码镜像在不同配置下可能表现不同。消费者是否双读、生产者是否仍写 v1、回源开关、目标接口门控、DLQ 留存期，都是部署配置的一部分。

因此，每个候选制品都应可追溯地标识为：

`镜像摘要 + Git 提交 + 迁移版本 R9 + 事件契约版本 + 配置快照 + 开关状态`

不要用“已部署版本”替代这组身份。只有明确当前 $S2$、拟议 $S3$、关系版本 $R9$ 与事件版本之间的对应关系，才能判断某次异常来自代码、数据库迁移、消息契约，还是配置漂移。

### 扩展阶段：新增列先可空且默认安全

### 扩展阶段：新增列先可空且默认安全

以 `messages`、`outbox` 新增 `message_version` 与 `visibility` 为例，扩展阶段的目标不是立刻启用新语义，而是让新旧代码、历史数据和在途消息可以同时存在。

先做兼容性模式变更：

```sql
ALTER TABLE messages
  ADD COLUMN message_version integer NULL,
  ADD COLUMN visibility text NULL;

ALTER TABLE outbox
  ADD COLUMN message_version integer NULL,
  ADD COLUMN visibility text NULL;
```

新增列应先允许为空，且应用读取时采用安全默认值：`message_version IS NULL` 按 `event_v1` 处理；`visibility IS NULL` 按既有可见范围处理，通常是更保守的“仅原有授权主体可见”，而不是意外扩大访问范围。不要在同一次发布中新增列、强制 `NOT NULL`、切换生产者和删除旧字段。

Postgres 的 `ALTER TABLE` 虽然看似简单，仍可能申请较强锁；表大、长事务未结束、复制延迟或并发写入高时，短暂的元数据操作也可能排队成发布事故。发布前应确认：

- 当前是否存在长查询、未提交事务或维护任务；
- 锁等待超时、语句超时是否已设置；
- 新增默认值是否会触发高成本改写；应优先由应用层补默认，而非立即依赖数据库回填；
- 回填总行数、每批大小、写入速率、WAL 增量及副本承载能力。

历史数据回填必须异步、分批、可重试，例如按主键范围更新空值，并持续记录进度。回填期间，旧生产者仍可写出没有新字段的记录；新消费者必须能双读：字段缺失或版本为空时走 `event_v1` 解析与安全回源，明确标记为 `event_v2` 时才启用新逻辑。

因此，“字段已经在线上”只说明 wire-safe：旧客户端不会因未知字段崩溃；却不代表语义安全。只有旧路径仍可用、空值含义明确、权限默认不放大，并且回填预算可控，扩展才算完成。

### 事件双读：兼容格式不等于兼容语义

### 事件双读：兼容格式不等于兼容语义

新消费者上线时，应同时识别 `event_v1` 与 `event_v2`，但不能把“都能反序列化”当作兼容完成。双读的目标是：无论消息来自旧生产者、旧客户端还是在途重试任务，都能得到一致、可审计的业务结果。

可采用“统一内部模型 + 版本适配器”：

- `event_v1`：按旧字段解释，缺失的新字段使用**安全默认值**，或标记为“未知”。
- `event_v2`：读取新增的 `message_version`、`visibility` 等字段，并执行新语义校验。
- 两者都映射到内部命令，例如 `HandleOrderChanged`；业务处理层不应散落版本分支。

```text
收到消息
  ├─ event_v1 → 适配旧语义 → 必要时按 ID 安全回源
  └─ event_v2 → 校验版本/可见性 → 适配新语义
                         ↓
                    幂等业务处理
```

“安全回源”是关键：当 `v1` 未携带权限范围、可见性或完整版本号时，可按实体 ID 查询权威数据库或服务，而不是猜测新字段值。回源必须受权限、租户、时间点和版本约束；若无法确认，应拒绝执行敏感动作、进入待处理队列或记录告警，而非默认公开。

旧客户端仍发送或消费 `v1` 时，语义边界必须明确：它只能获得旧契约承诺的行为，不能因新增 `visibility` 而意外看到本应隐藏的数据，也不能触发只属于 `v2` 的副作用。新增字段在网络层“可忽略”，不代表旧消费者在权限、幂等、状态迁移上仍然安全。只有在 `v1` 流量、重试、日志与死信队列均越过留存窗口后，才能停止双读并收缩旧契约。

### 灰度观察：对账、停止门与在途连接

### 灰度观察：对账、停止门与在途连接

灰度期间，`Pod` 全部更新完成只是“新代码已部署”；真正需要确认的是：旧消息、旧客户端、长连接与异步任务仍能按旧契约完成闭环。尤其是新增 `message_version`、`visibility` 后，字段可被旧消费者忽略，并不意味着其权限语义、回源逻辑和幂等行为仍然正确。

先对历史数据执行低优先级、可续跑的回填，并持续观察 `S0/L0`：例如待处理消息量、消费延迟、失败率、死信增量、回填扫描速率与数据库负载。回填应按主键分片，记录检查点；不要用一次大事务更新全表，否则即使 `ALTER TABLE` 成功，也可能在回填阶段制造锁等待、复制延迟或连接池耗尽。

灰度样本应覆盖代表性组合，而非只看总体成功率：

- 旧客户端发送、旧消费者处理的 `event_v1`；
- 新客户端发送、新消费者处理的 `event_v2`；
- 新消费者读取 `event_v1` 后安全回源；
- 私聊、群聊、撤回、禁言、跨租户等权限敏感消息；
- 发布前已入队、发布中执行、发布后重试的异步任务。

对账至少包含三组不变量：

1. **标识一致**：消息 `ID`、业务主键、幂等键与关联会话不能因版本转换而漂移或重复。
2. **版本可解释**：`event_v1` 与 `event_v2` 的数量、转换数、回源数、解析失败数可按生产者和消费者拆分。
3. **权限一致**：`visibility` 缺失时采用安全默认值；新旧路径对同一用户的可见、可消费、可回放结果一致。

预先设定停止门，而不是异常后临时讨论：出现未知版本、权限拒绝突增、重复投递、DLQ 增长、回填滞后超过可恢复窗口，立即停止新生产者或目标接口流量，保留旧写入路径并回滚灰度。还要单独追踪 IM 长连接与在途任务：它们可能持续数小时，部署完成不代表连接已重连、旧协议已退出或旧任务已清空。只有在其自然完成、超时收敛或被安全迁移后，才具备进入 `contract` 的证据。

### 收缩与回退：确认留存期后再删除旧路

### 收缩与回退：确认留存期后再删除旧路

`contract` 不是“新版本已发布”的清理动作，而是主动放弃回退能力。代码、配置、数据三者的可回退窗口不同，必须分别确认：

| 层面 | 可逆条件 | 过早删除的后果 |
|---|---|---|
| 代码 | 旧消费者、旧客户端、旧任务镜像仍可部署 | 回滚后无法识别 `event_v1` 或旧字段 |
| 配置 | 路由、开关、权限策略仍保留旧路径 | 只能回滚二进制，不能恢复实际流量 |
| 数据 | 旧列、映射表、回填来源仍存在 | 新旧版本无法对账或安全回源 |

只有同时满足以下条件，才可删除 `event_v1`、旧列或兼容分支：

- 旧日志与 DLQ 的最长留存期已经结束，确认不会有延迟重放的旧消息；
- 所有生产者已停止写旧格式，所有消费者、批任务和外部客户端已退出旧读写路径；
- `S0/L0` 回填完成，且按 `ID + version + permissions` 对账无缺失、无越权；
- 新接口和新消息格式已被门控验证，旧路径的监控、告警与重试量归零；
- 已演练“仅使用新数据结构”的回退边界：此时只能回退应用行为，不能承诺恢复旧协议。

新增字段即使在 wire 层面可忽略，也未必语义安全：旧消费者可能将缺失字段解释为默认公开、默认未处理或默认最新版。因此，删除旧路应在留存期后分阶段进行：先停写、再停读、保留只读诊断能力，最后删除数据与配置。

> **要点** — 安全发布依赖可识别制品、兼容顺序、可观测灰度与分层回退；新增字段可传输，不代表旧系统能正确理解。

灰度发布不是把流量按1%、10%、100%切换即可；真正的发布判断，必须回到不同客户端、连接状态与消息链路的实际效果。

### 把灰度对象从流量比例还原为用户切片

### 把灰度对象从流量比例还原为用户切片

“先放 1%，再到 10%，最后全量”只描述了请求比例，没有描述**哪些用户真的经历了新链路**。若 1% 流量恰好主要来自新版、英文、在线且低活跃用户，即使指标正常，也不能说明旧客户端、中文用户、离线补拉或热群场景安全。

灰度对象应按风险维度建立可验证的用户切片，而非随机抽样：

- **版本切片**：至少覆盖仍有存量的旧客户端，以及当前主流版本；重点观察协议兼容、消息解析与重试行为。
- **语言切片**：单列中文 `6B/9B` 等可能触发编码、长度、分词或本地化差异的客户端，不以英文成功替代中文成功。
- **成员关系切片**：覆盖成员、非成员 `u-c`；后者常暴露鉴权、可见性与 `404/409` 处理问题。
- **群活跃度切片**：覆盖普通群与热群 `c-g`。热群的并发写入、乱序、重复投递和索引延迟，往往不会在低负载样本中出现。
- **在线状态切片**：覆盖在线发送/接收者，以及用户 B 离线后重新上线、设备同步和历史补拉的完整路径。

因此，1% 阶段应理解为“每个高风险切片都有足够样本”，而不是“全体用户随机命中 1%”。例如，若离线用户仅占很小比例，随机 1% 可能一个 B 离线样本都没有；若旧版本占比低，灰度成功也可能只是没有测到旧版本。

发布配置应显式记录每个切片的纳入规则、最小样本量和观测窗口。只有当各切片均实际命中新版本，并与同时间窗对照组比较后仍满足门槛，`1%→10%→100%` 才是有意义的放量，而不是把基础设施就绪误当成用户效果已验证。

### 构造旧客户端与消息状态的代表性样本

### 构造旧客户端与消息状态的代表性样本

不要只随机抽取在线用户，而应把“可能走到不同协议分支”的条件组合成样本矩阵。设发送者为 `A`、接收者为 `B`，群为 `c-g`，非成员查询者为 `u-c`；至少覆盖：

| 维度 | 代表取值 | 要验证的问题 |
|---|---|---|
| 客户端版本 | 当前版、旧版 | 新字段、游标格式、错误码是否仍被旧版正确处理 |
| 消息内容 | 中文约 `6B`、`9B` | UTF-8 字节长度、截断边界、索引与分页是否一致 |
| 成员关系 | 成员、`u-c` 非成员 | 非成员读取、补拉或搜索是否稳定返回 `403/404`，而非泄露消息 |
| 群负载 | 普通群、热群 `c-g` | 并发写入下顺序、去重、未读数与补拉游标是否漂移 |
| 连接状态 | `B` 在线、`B` 离线后重连 | 离线消息、推送失败后的补拉、重复投递处理 |

一个高价值场景是：旧版 `A` 向热群 `c-g` 连续发送中文 `6B/9B` 消息，`B` 在中途离线；服务端完成写库、outbox 投递和索引后，`B` 用旧版重连并按游标补拉。验收不只是“收到了消息”，还要核对消息 ID、顺序、内容字节数、未读计数，以及重复补拉时的幂等性。

同时让 `u-c` 用旧版执行群详情、历史消息和搜索请求，明确预期：无权限时应返回约定的 `403` 或资源隐藏策略下的 `404`，绝不能出现 `200` 且携带消息摘要。每个组合应预先写明成功条件、允许错误码、观测窗口与对照版本结果；否则灰度中的“正常”很可能只是样本没有碰到旧协议、离线补拉或热群竞争。

### 按版本和链路建立同窗对照观测

### 按版本和链路建立同窗对照观测

灰度的核心不是“实验组成功率是否好看”，而是：**在相同时间、相近负载下，实验组是否劣于未升级版本**。因此应同时保留对照组，而非将全量流量都切到新版本后才寻找基线。

设同一观测窗为 $W$，按客户端版本、服务版本与链路状态分桶。例如：

- 客户端：旧客户端、中文 6B、中文 9B；
- 身份与会话：成员、非成员 `u-c`、热群 `c-g`、离线用户 B；
- 服务端：新版本实验组、旧版本对照组；
- 链路阶段：发消息、写 outbox、消费、建索引、补拉、设备同步。

对每个桶分别比较：

| 指标 | 关注含义 |
|---|---|
| `200` 比率 | 请求是否正常完成 |
| `409` 比率 | 幂等、版本冲突或状态竞争是否放大 |
| `404` 比率 | 资源、会话、消息索引或路由是否缺失 |
| 错误率与超时 | 是否出现服务端异常、重试风暴或依赖退化 |
| `outbox oldest` | 最老未投递消息的滞留时长，反映消费是否堵塞 |
| SearchIndex 缺口 | 已写入消息与可检索消息的差量或延迟 |
| 设备同步与补拉 | 多设备是否收齐，离线后是否能补回消息 |

可用相对劣化量表达发布风险：

$$
\Delta_e=\frac{r_{\text{实验}}-r_{\text{对照}}}{\max(r_{\text{对照}},\epsilon)}
$$

其中 $r$ 可为错误率、`409` 率或索引缺口率。成功率看绝对差，低基线错误则看相对倍数；例如 `404` 从万分之一升至万分之五，虽绝对值小，仍可能意味着旧客户端路由被破坏。

发布前应明确门槛和持续时间：如错误率不得高于对照组 20%，`outbox oldest` 不得连续 10 分钟增长，SearchIndex 缺口须在 5 分钟内回落，离线补拉成功率不得下降。`Pod Ready`、镜像已回滚只能说明部署状态，不代表用户消息链路已经恢复；最终依据仍是同窗、分版本、分链路的用户可见结果。

### 用停止门约束扩量而非依赖Pod就绪

### 用停止门约束扩量而非依赖Pod就绪

每个灰度阶段都应先写清“何时允许扩量、何时必须停止”，而不是看到 Kubernetes Pod Ready、镜像拉取成功或无自动回滚就从 1% 直接升到 10%。这些信号只说明进程可运行，不能证明用户消息链路正确。

以 `1% → 10% → 100%` 为例，每一档至少预设：

- **观测时长**：覆盖正常高峰与异步补偿周期，例如持续观察 30～60 分钟，而非刚上线几分钟。
- **样本下限**：达到最小请求量、消息量和活跃设备数后才判定；1% 流量可能完全未命中旧客户端、中文 6B/9B、非成员 `u-c`、热群 `c-g` 或离线用户 B。
- **对照口径**：在同一时间窗比较灰度组与未灰度组，按版本、设备、群规模和在线状态拆分，避免把整体波动误判为发布影响。
- **停止门**：任一关键指标越界即冻结扩量：`200` 下降、`409/404` 或业务错误上升、outbox oldest 持续变老、SearchIndex 缺口扩大、设备投递失败或补拉率异常。

可将规则写成明确条件：若灰度组错误率比对照组高出阈值，或关键链路样本不足，则“保持当前比例并继续观察”；若异常持续两个观测窗口，则“停止扩量并回滚或关闭开关”。尤其不能因 Pod 全部 Ready 就宣布成功：容器健康不等于旧客户端可用，不等于离线消息最终送达，更不等于搜索索引和补拉链路没有静默丢失。

### 从在途消息验证发布与回退结果

### 从在途消息验证发布与回退结果

Pod 更新完成只说明新镜像已就绪，不说明用户消息链路已经恢复。发布与回退都存在不同步窗口：旧 Pod 上仍挂着长连接，异步任务仍在消费旧配置，B 处于离线状态，设备侧还可能在稍后才触发补拉。因此，不能以 `Pod Ready`、滚动更新完成或镜像已回滚代替用户效果验证。

应在同一观测时间窗内比较实验组与未更新对照组，并按版本、连接状态和消息类型拆分：

- **在途长连接**：观察旧客户端与存量连接是否继续出现 `200` 以外的 `409`、`404`、超时或协议错误；尤其覆盖中文 6B/9B、非成员 `u-c`、热群 `c-g`。
- **异步投递**：检查 outbox 最老消息年龄及积压增长率。若回退后最老消息仍持续变老，说明问题可能留在消费者、重试任务或下游，而非仅在服务镜像。
- **索引一致性**：比较 `SearchIndex` 缺口，即已确认投递但未被索引的消息数。回退若只恢复发送接口，却扩大索引缺口，用户仍会看到“消息发出但搜不到”。
- **离线补拉**：让 B 离线后再上线，审查设备侧增量游标、重复消息、漏消息和补拉失败率；回退期间产生的消息尤其要覆盖。

发布前应预设门槛，例如错误率不得高于对照组、outbox 最老消息在限定时长内回落、SearchIndex 缺口不增长、离线补拉成功率稳定，并持续观察至少覆盖一次重试与一次离线重连周期。小流量样本可能未命中罕见客户端或热群重负载；只有这些在途消息最终被送达、索引并可被设备补回，才能证明发布或回退真正有效。

> **要点** — 灰度是否成功要由代表性消息样本、同窗对照和预设停止门证明，而非由流量比例、Pod就绪或镜像回滚判断。

滚动更新能替换Pod，却不会自动处理长连接、在途任务与消息消费位点；发布是否成功，必须从真实流量与消息交接来判断。

### 滚动更新控制的边界

### 滚动更新控制的边界

`maxUnavailable` 与 `maxSurge` 控制的是更新期间的 **Pod 数量与就绪副本供给**：

- `maxUnavailable`：允许同时减少多少个可用副本；
- `maxSurge`：允许额外创建多少个新副本；
- 新 Pod 通过 `readinessProbe` 后，才通常会进入 Service 的后端端点。

因此，它们能降低“新旧版本替换时容量不足”的风险，却不等于“业务流量已经安全切换”。`Ready` 只说明该 Pod 当前可被选为新请求目标，不说明旧 Pod 已经没有工作。

例如，旧版 IM Pod 仍可能持有大量 WebSocket 连接；HTTP 服务可能仍在处理耗时请求；worker 可能已拉取消息但尚未完成处理或提交 offset。即使 Deployment 已显示更新完成，旧实例被终止仍可能造成连接断开、请求中断、任务重复或消息遗漏。

更准确地说，滚动更新只完成了：

$$
\text{副本替换与容量约束}
$$

而服务切换还需要应用层完成：

$$
\text{停止接新流量} \rightarrow \text{drain 在途连接/任务} \rightarrow \text{交接消费状态} \rightarrow \text{有界退出}
$$

`maxUnavailable=0` 也只是尽量保持就绪 Pod 数量，不是零中断承诺。发布验收应继续观察连接迁移、请求失败率、任务积压、消费者 lease 与 offset，而不能只看 Deployment 的 `Available` 状态。

### 新版本就绪后再接流

### 新版本就绪后再接流

`Pod Ready` 不应等同于“进程已启动”或“端口可连接”。只有新版真正具备处理语义完整请求的能力，才应通过就绪探针并加入 Service 后端；否则，滚动更新只是把未准备好的实例提前暴露给用户。

新版通常应按以下顺序建立接流资格：

1. **启动并完成本地初始化**：加载配置、密钥、路由、限流规则和必要缓存；进程监听端口后，仍保持 `NotReady`。
2. **校验关键依赖**：确认数据库连接池可用、broker 元数据可读、认证服务与必要下游可达。不能只检查 TCP 连通；若依赖已降级，应明确该实例是否仍允许承接对应流量。
3. **完成状态恢复**：worker 读取 checkpoint、租约或消费位点；需要预热的缓存、模型或连接池应先完成。否则首批请求可能超时，消费者也可能在恢复位点前误领任务。
4. **通过就绪检查再接流**：就绪探针应回答“现在能否正确处理新工作”，而非“进程是否活着”。`livenessProbe` 只用于发现卡死，不能替代 `readinessProbe`。

可将接流条件抽象为：

$$
Ready = 启动完成 \land 关键依赖可用 \land 状态恢复完成 \land 接流开关开启
$$

对于 HTTP，Ready 后 Service 才会转发新请求；对于 WebSocket，Ready 后才允许建立新会话，并应确认鉴权、会话存储和消息通道均可用。对于消息消费者，Ready 更应意味着已安全取得分区 lease 或已完成 offset 对齐，而不是仅仅连上 broker。

因此，建议把“监听端口”和“允许接流”分离：启动阶段返回存活，依赖与状态确认后才置 Ready。这样旧版尚未 drain 完成时，新版也不会因过早接流而放大错误、重复消费或造成会话断裂。

### 旧版本停止接新与排空

### 旧版本停止接新与排空

旧 Pod 被终止不等于业务已完成交接。滚动更新期间，旧版本应先进入“排空”状态：**不再获得新流量，但允许已接收的工作在限定时间内结束**。这一过程通常比 `maxUnavailable`、`maxSurge` 更直接决定用户是否断线、请求是否失败、任务是否重复。

可将旧 Pod 的生命周期拆为：

1. **摘除新流量**：将就绪探针变为失败，或通过应用的 `drain` 开关使其返回“不接流”。此后 Service、Ingress 等不应再把新的 HTTP 请求、WebSocket 握手或任务分配给该 Pod。
2. **保留在途工作**：已经建立的连接和已经开始的请求仍可能继续存在；仅靠就绪探针无法取消它们。
3. **有界等待**：在 `terminationGracePeriodSeconds` 及应用自身超时内完成排空；超过上限必须按明确策略关闭、失败或转交，不能无限等待。

不同负载的排空语义不同：

- **HTTP 请求**：停止接收新连接和新请求；等待在途请求完成。超时后可返回可识别的失败，如 `503`，让调用方重试。
- **WebSocket**：旧 Pod 应先发送“服务迁移/即将关闭”信号，拒绝新握手，并在宽限期后主动关闭连接。客户端必须具备重连能力，连接迁移并非 Kubernetes 自动提供。
- **worker 任务**：停止拉取新任务，已取得但未完成的任务继续执行；临近超时时，应释放租约、延长租约或将任务标记为可重试，避免 Pod 被强杀后留下“处理中”的假象。

一个常见顺序是：收到 `SIGTERM` → 切换为未就绪并关闭接流 → 停止领取新工作 → 排空连接、请求与任务 → 在宽限期结束前退出。应用必须把排空时间设计为有界值，并让上游、客户端和 broker 的重试/租约策略与之匹配；否则旧 Pod 即使已不接新流，也可能因长连接或卡住任务阻塞发布。

### 消费者位点与租约交接

### 消费者位点与租约交接

消费者滚动发布时，真正被交接的不是 Pod，而是“某个消费者对某些分区的处理权”及其进度。broker 通过消费者组、分区分配与租约（heartbeat/session）判断所有者；offset 则表示已确认的处理边界。两者若顺序错误，就会产生重复消费、短暂停顿，甚至越过未完成消息。

典型风险发生在旧实例退出期间：

1. 旧消费者仍持有分区，却已停止处理；若不再心跳，租约到期后才触发再平衡，期间该分区积压。
2. 旧消费者正在处理消息 `offset=100`，但尚未提交；新消费者接管后会从已提交的 `99` 重读 `100`，因此业务必须幂等。
3. 更危险的是“先提交、后完成”：若先提交 `100`，随后旧实例被终止，消息效果未落库但位点已越过，形成不可恢复的丢失。
4. 再平衡期间旧实例若继续处理已被撤销的分区，可能与新实例并发写入同一业务对象。

因此，发布交接应遵循受控顺序：新版先启动、鉴权并 `ready`，加入消费者组但不假定立即拥有分区；旧版收到终止信号后停止拉取新消息，对已拉取任务设置有界 drain 时间；任务完成并持久化业务效果后，再提交对应 offset；随后主动释放分区或退出组，由 broker 完成再平衡，新版获得租约后才继续消费。

可将安全边界概括为：

$$\text{完成业务效果} \rightarrow \text{提交位点} \rightarrow \text{释放租约} \rightarrow \text{新实例接管}$$

`terminationGracePeriodSeconds`、broker 会话超时和任务最大处理时长必须协调：优雅退出时间应覆盖在途任务与最后一次位点提交；超时后宁可让未提交消息被重放，也不能伪造“已完成”。对于外部已发送的 G1 消息，即使旧实例随后被终止也无法撤销，只能依赖幂等键、去重记录或补偿流程收敛结果。

### 发布观察与不可撤销消息

### 发布观察与不可撤销消息

发布完成不等于交接完成。`maxUnavailable` 与 `maxSurge` 只约束 Pod 数量和就绪副本，不能证明旧实例上的 WebSocket、HTTP 在途请求、后台任务或消息消费者已经安全退出。因此，灰度发布应设置覆盖全链路的“停止门”。

- **连接门**：新版 Pod `Ready` 后才加入服务发现并接收新流量；旧版先标记为 `draining`，从负载均衡摘除，拒绝新建 WebSocket 或新会话，但保留已有连接至超时。观察连接数是否持续下降，而非只看 Pod 是否终止。
- **请求门**：旧版停止接收新 HTTP 请求，保留在途请求完成；超过有界超时后取消或返回可重试错误。发布指标应包括在途请求数、超时率、5xx、重试量及延迟分位数。
- **任务门**：worker 停止拉取新任务，只完成已领取任务；任务必须具备幂等键、租约和可见性超时，避免实例被强制终止后任务永久悬挂或重复执行。
- **消费门**：消费者先暂停领取或撤销分区，再提交已完成处理对应的 offset；新版本确认获得 lease 或分区所有权后才继续消费。应观察消费滞后、重复率、死信量、offset 提交失败与重平衡次数。

可以把发布判定写成：新版错误率稳定、旧版连接/在途请求/持有任务归零或超时处置、broker 的位点与租约已完成交接，才允许终止旧 Pod。

尤其要区分“处理完成”与“消息已外发”。旧 G1 若已向外部 IM、支付、邮件或第三方系统发送消息，该副作用通常不可由镜像回滚撤销。回滚只能阻止后续新版行为，不能收回已送达内容。对此应预先采用幂等键、去重、延迟发送、补偿消息或人工处置流程，而不能把 Kubernetes 回滚误当作业务撤销。

> **要点** — Pod滚动完成不代表发布完成；必须显式交接新旧流量、在途工作和消费位点，并以消息结果验证发布。

发布成功只说明新版本已运行；消息、数据与在途连接是否仍可被安全理解，决定回退是否真正可控。

### 回退不是撤销既成事实

### 回退不是撤销既成事实

将服务镜像从新版本切回旧版本，只改变**之后由谁执行代码**，不会自动抹除已经发生的外部事实。一次发布至少要沿四条彼此独立的轴观察：

- **事件轴**：新版本已发出的 `event_v2` 可能已被写入事件流、进入 outbox，甚至被多个消费者处理。回滚生产者镜像不会让这些事件消失。
- **数据轴**：已填充的新列、状态迁移、补偿记录或关联 ID 已提交到数据库；旧二进制即使不再写新格式，也可能读不懂、覆盖或违反这些数据约束。
- **消息轴**：消息一旦提交给队列、日志系统或对象存储，便可能处于“已持久化、未消费”“已消费、未确认”“已确认、下游继续传播”等不同阶段。S3 中已提交的消息文件尤其不能靠镜像回滚撤销。
- **客户端轴**：B 端或其他客户端已收到“操作成功”“进入新流程”等提示，用户已据此行动。服务端回退后，客户端看到的事实不会自动回到旧状态。

因此，回退前首先问的不是“旧镜像能否启动”，而是：

1. 旧二进制能否兼容读取历史 `event_v2`、新列与新状态；
2. 新消费者能否安全处理旧版本继续产生的数据；
3. outbox、重试队列、延迟消息与在途消费是否已稳定；
4. 已通知客户端的状态是否仍与服务端可执行能力一致。

若任一答案是否定的，应先停止新格式写入，保留兼容读取与幂等消费，再通过反向回填、补偿迁移和按 `ID/version` 对账恢复一致性。回退是一次新的状态转换，不是对既成事实按下“撤销”键。

### 用制品身份追踪发布边界

### 用制品身份追踪发布边界

“已回滚”不是一个单一状态，而是多个可独立变化的制品身份重新组合。一次发布至少应记录并关联以下边界：

- **镜像身份**：服务镜像摘要、二进制版本、构建提交号。例如应用已从 `img@sha256:new` 切回 `img@sha256:old`，只说明运行代码变旧。
- **部署配置**：环境变量、灰度比例、消费者组、权限策略、客户端最低版本；旧镜像配上新配置，仍可能执行新路径。
- **数据库迁移版本**：已执行的 migration、已新增或回填的列、索引与约束。代码回退不会自动删除 `event_v2` 已写入的列值，也不会撤销已提交事务。
- **事件格式身份**：事件名、schema version、序列化方式、生产者版本与消费者兼容范围。`event_v2` 一旦进入 outbox、消息队列或 S3，即构成不可忽略的历史事实。
- **路由 epoch**：分片、租户或 `b1` 迁移后的路由代数。回退后若需再次切换，必须使用更高 epoch，不能复用旧 epoch，否则缓存、重试消息与长连接可能接受过期路由。
- **功能开关身份**：新写开关、兼容读开关、双写/双读开关及其生效时间。关掉新写不等于历史数据消失；保留兼容读才允许旧二进制继续处理新历史。
- **外部可见事实**：B 已收到的提示、S3 已提交对象、R9 是否已批准、客户端是否已看到 9B。它们不能被服务端镜像回退“收回”。

因此发布记录应形成可对账的元组：`镜像 + 配置 + 迁移 + 事件版本 + 路由epoch + 开关状态 + 外部确认`。若 R9 未批准，系统不应产生 9B 事实；若批准上线后旧端只能返回 6B，应依据客户端能力矩阵降级，而非假设回滚即可恢复一致性。

### 先停止新写，再稳定读链路

### 先停止新写，再稳定读链路

发现新版本的消息格式、数据库列或对象存储提交可能无法被旧版本安全理解时，恢复顺序不是立刻回滚二进制，而是先冻结不可逆增量：

1. **关闭新写开关**：停止产生 `event_v2`、新字段值、新路由版本及依赖新语义的 S3 提交；开关应按配置版本、租户或流量分片生效，并记录关闭时刻与生效范围。
2. **保留兼容读取**：读取端必须同时识别旧/新格式。旧端遇到未知字段应忽略或降级，不能把“无法解析”误判为“数据不存在”；新端则需接受历史空值、旧枚举和值缺失。
3. **稳定 outbox 与消费者**：不要删除已落库的 outbox 记录，也不要通过重置消费位点“抹平”问题。先暂停高风险消费者，确认幂等键、重试策略、死信队列及消息顺序；已投递事件按 `event_id`、业务 `id` 与 `schema_version` 对账。
4. **选择数据恢复路径**：若新列只是派生数据，可反向回填旧表示并继续双读；若语义已变化，应新增迁移而非撤销原迁移，保留来源版本、转换规则与审计记录。
5. **完成闭环后再回退程序**：核对数据库行、outbox、消息主题、S3 对象和下游消费结果是否一一对应。只有确认旧二进制能读取存量历史、消费者已稳定且不存在未解释的新版本记录，代码回滚才不会制造第二次数据事故。

### 灰度观察覆盖消息与在途连接

### 灰度观察覆盖消息与在途连接

灰度不能只按实例比例切流；应同时抽样验证“谁写入、谁消费、谁仍持有旧状态”。尤其当 `event_v2`、新数据库列或 S3 提交消息已出现时，回滚代码并不会抹除这些事实。

建议建立覆盖矩阵：

- **新旧消费者**：新生产者→旧消费者、新消费者→历史消息、重复投递与乱序投递；确认未知字段可忽略、缺失字段有默认语义、幂等键仍有效。
- **旧 IM 客户端**：按客户端版本、能力位和地区灰度。若 R9 尚未批准，任何路径都不应产生 `9B` 事实；若批准后旧端只能返回 `6B`，必须由能力矩阵决定降级展示或拒绝该操作，而非把 `6B` 当作 `9B`。
- **长连接**：观察发布前已建立的 WebSocket/IM 会话、断线重连、服务端热切换和连接迁移。连接携带的协议版本、路由 `epoch`、订阅游标必须可验证；若发生 `b1` 迁移，回退也必须使用更高的 `epoch`，不得复用旧值。
- **重试与异常载荷**：主动注入超时重试、死信重放、旧 schema、字段缺失、未知枚举、超大消息及部分写入消息，验证 outbox、消费者和补偿任务不会放大副作用。

停止门应绑定事实指标，而非“错误率看起来正常”：未知版本解析失败、反序列化降级、重复消费、死信积压、客户端协议拒绝、长连接重连峰值、路由 epoch 倒退均应触发暂停扩量。灰度结束前还要按事件 ID、版本和迁移批次对账，确认生产、outbox、消费记录与数据库状态一致；不一致时先冻结新写入，再稳定消费与回填路径。

### 按能力矩阵实施分层回退

### 按能力矩阵实施分层回退

回退对象不同，前提也不同；不能把“镜像切回旧版本”误当成完整回退。

| 层次 | 可回退条件 | 不可直接回退时的处理 |
|---|---|---|
| 代码 | 旧二进制仍能读取当前消息、数据库列和配置 | 保持兼容读取，关闭新写入路径，再发布兼容补丁 |
| 配置 | 配置语义未被新代码写入持久状态 | 用显式版本化配置；撤销开关不应删除已产生的事实 |
| 数据 | 新列、索引、状态值可被旧代码忽略或降级解释 | 保留列和迁移记录，反向回填或新建迁移，不做危险的物理删列 |
| 协议 | 历史事件、已提交消息可被新旧消费者解析 | 稳定 `outbox` 与消费位点，按事件版本、消费者能力逐步切流 |

尤其要区分“停止产生新事实”与“撤销既有事实”。例如 `event_v2` 已写入、数据库新列已填充、S3 消息已提交，或服务 B 已收到提示时，纯代码回滚不会让这些副作用消失。应先关闭新写 `flag`，保留兼容读和幂等消费；随后依据 ID、事件版本和处理状态对账，再决定反向回填、补偿事件或新的数据迁移。

R9 一旦批准并上线，系统可能已经形成 `9B` 事实；但旧端仅支持 `6B`，不能因回退而把 `9B` 直接投递给旧客户端。能力矩阵至少应记录客户端版本、可解析协议、可展示状态及降级规则：支持 R9 的端接收完整 `9B`，旧端获得可安全映射的 `6B` 视图、延迟提示或明确升级提示，而不是伪造未发生的状态。

若 b1 涉及路由迁移，回退也必须发布**更高**的路由 `epoch`。复用旧 `epoch` 会使缓存、重试请求或乱序消息无法判断新旧归属，可能把流量重新送入已废弃分片。正确方式是以更大的 `epoch` 宣告反向路由，并在所有节点确认后再清理旧路径。

> **要点** — 回退代码不能抹去消息和数据事实；先止写、保兼容、稳消费、再按版本与能力矩阵恢复。

发布完成不等于演进完成：旧客户端、滞留消息与历史权限会让协议弃用周期远长于一次部署窗口。

### 把弃用对象拆成四条独立时间线

### 把弃用对象拆成四条独立时间线

“已发布 S3”不能推出“可以删除 S2、R9 或旧事件字段”。兼容性至少应拆为四条彼此独立的时间线，并分别记录状态、最低支持版本与退出条件：

- **当前协议 S2**：明确哪些客户端仍在使用、最低支持版本是什么、服务端何时停止接受 S2。退出条件通常不是新服务上线，而是旧客户端比例低于阈值、强制升级覆盖完成，且灰度期内无 S2 回退需求。
- **拟议协议 S3**：在文档、代码和网关中标记为“拟议”或“试运行”，不能因存在 schema、分支或测试而宣称已成为默认协议。只有客户端实现、服务端兼容、观测指标和回滚方案齐备后，才进入正式支持窗口。
- **R9 等存储或资源版本**：其生命周期取决于读取者、迁移任务和备份恢复路径。即使在线数据已迁移，旧索引、导出文件或恢复工具仍可能要求保留 R9 解析能力。
- **事件格式**：事件的弃用最晚。broker 中的滞留消息、重试队列和 DLQ（死信队列）可能在数日或数周后重放；旧 schema 必须保留到消息最大存活期、重试窗口、DLQ 保留期及人工补偿窗口全部结束。

可将删除条件写成：

$$
T_{\text{删除}}=\max(T_{\text{旧客户端}},T_{\text{数据恢复}},T_{\text{broker}},T_{\text{DLQ}})
$$

此外，私有历史消息的权限校验不随协议弃用而失效：无论消息来自 S2、S3、R9 还是旧事件重放，读取、补偿和重放路径都必须持续执行当前授权规则。对于具体 OpenIM 项目，也不能仅凭 `send.go` 中 `MsgToMQ` 返回或 Mongo `BatchInsertChat2DB` 推断其部署方式、事件版本或对象存储；应以 `go.mod`、配置、部署清单及实际运行证据为准。

### 用客户端证据决定最低支持线

### 用客户端证据决定最低支持线

最低支持版本不能凭“新版已发布”决定，而应由客户端证据驱动。首先持续记录各版本客户端的请求比例、日活用户数、关键功能调用量、地域与渠道分布；尤其要区分“安装存量”和“真实活跃存量”。例如，旧版仅占请求量 $1\%$，但承载大量高价值私聊、企业客户或弱网地区用户时，仍不宜直接停止服务。

建议为每个协议版本建立可审计的弃用记录：

- `版本范围`：如 `< 2.6.0` 使用旧字段或旧消息结构。
- `观测指标`：近 7/30 天请求占比、活跃设备数、发送失败率、升级率。
- `最低支持线`：明确写出“自某日期起最低支持 `2.6.0`”。
- `触达计划`：应用内弹窗、登录页提示、商店强更、短信或企业客户通知。
- `弃用日期`：通知开始、灰度限制、全面拒绝旧协议的时间点。
- `回滚条件`：升级异常、关键客户未完成迁移、旧版本仍有不可忽略活跃量。

停止旧协议服务通常应同时满足：旧版本活跃比例连续多个统计周期低于阈值；已完成至少一轮可验证的升级触达；服务端、Broker、消费者和重放工具均不再依赖旧 schema；历史消息在 DLQ 与重放窗口内也可被新代码安全处理。仅关闭入口而保留无法解析的滞留消息，会把兼容性故障延后到消费、补偿或重放阶段。

还应注意，客户端升级不改变权限边界。即使旧协议已弃用，私有会话、历史消息查询和重放操作仍必须逐次校验用户身份、会话成员关系与数据可见性；“这是历史消息”不是绕过授权的理由。

### 消息格式保留到重放窗口结束

### 消息格式保留到重放窗口结束

一次发布中，生产端切换到新消息格式，只说明“从现在开始优先写新事件”，并不说明旧格式已经失去价值。历史消息可能仍位于 broker 的保留队列、消费者本地积压、失败后的重试队列，以及 DLQ（死信队列）中；它们会在未来某次扩容、故障恢复或人工重放时再次被消费。

因此，schema 的删除顺序应由**最晚可能重放的旧事件**决定，而不是由写端发布日期决定：

1. 先发布能同时解析旧 schema 与新 schema 的消费者；必要时按 `version`、字段存在性或兼容转换器分流。
2. 再让生产端写入新 schema；旧字段可标记弃用，但不要立即从事件中删除。
3. 持续观察旧版本消息比例、旧客户端比例、消费者解析失败率和 DLQ 数量。
4. 等待 broker 消息保留期、延迟重试期、DLQ 保留期及人工重放承诺窗口全部结束。
5. 确认不存在仍会投递旧格式的生产者后，才删除旧 schema、兼容解析分支和相关测试。

可将安全删除时间近似表示为：

$$
T_{\text{删除}} \ge
\max(T_{\text{broker保留}},T_{\text{重试}},T_{\text{DLQ保留}},T_{\text{人工重放}})
+ T_{\text{验证}}
$$

例如，正常主题只保留 7 天，但 DLQ 保留 30 天，且运维承诺可在 14 天内发起重放，则旧消费者兼容能力至少应覆盖这 30 天及验证期。否则，重放一条旧事件就可能触发反序列化失败、字段语义误判或数据丢失。

特别要区分“代码中存在 `MsgToMQ` 后返回”或“批量写入 MongoDB”的事实，与实际部署拓扑无关：它们不能证明当前项目使用了某个 broker、Kubernetes 或特定发布流程。应从 `go.mod`、配置、部署清单、运行日志和队列保留策略中确认真实重放窗口，再制定 schema 的弃用日期。

### 私有历史权限不能随版本降级

### 私有历史权限不能随版本降级

兼容旧协议的目标是“能解析、能迁移、必要时能重放”，不是让旧数据绕过当前安全策略。私有会话消息即使产生于旧客户端、旧 `schema`，或从 DLQ（死信队列）延迟重放，也必须按**当前**权限模型重新鉴权。

应把鉴权放在所有会再次暴露或处理消息的边界：

- **读取历史记录**：查询条件不仅是 `conversationID` 或消息时间范围，还必须验证请求者当前是否属于该私有会话、是否仍具备查看历史的权限。
- **DLQ 重放**：重放者有处理权限，不等于原消息可被投递给所有旧消费者；消费者侧仍应校验接收者、会话状态与撤销关系。
- **补偿与迁移任务**：批量修复索引、回填通知、导出审计记录时，不能因“内部任务”省略租户隔离、会话成员关系和最小权限控制。
- **旧字段兼容**：旧消息缺少新权限字段时，应由可信服务根据消息归属补全并校验；不能把“字段不存在”解释为“默认允许”。

例如，成员 `A` 曾在私有群组中发言，之后被移除。即使该群组历史消息仍保留、旧客户端仍可请求旧版接口，或该消息数日后从 DLQ 重放，`A` 也不应因此重新获得读取或接收权限。版本兼容只延长解析窗口，不延长已撤销的授权。

### 以运行证据审查真实项目边界

### 以运行证据审查真实项目边界

代码片段只能证明其所在分支的局部行为，不能自动推出完整架构事实。比如 OpenIM 的 `send.go` 在调用 `MsgToMQ` 后返回，最多说明该路径将消息交给消息队列后结束当前处理；Mongo 中存在 `BatchInsertChat2DB`，最多说明项目具备批量落库实现。它们都不能证明当前部署已经采用 Kubernetes、某套教学发布流程，或正在使用 S3、R9、`event_v2` 等组件、版本或事件协议。

审查时应区分“代码中出现”与“生产中启用”：

- `go.mod`：确认依赖是否真实引入，并查看版本、替换规则与间接依赖；未出现相关模块，通常不能声称采用该能力。
- 配置文件与环境变量：检查消息主题、对象存储端点、数据库地址、协议版本开关、弃用期限等是否已配置且被加载。
- 部署清单：从 Dockerfile、Compose、Helm、Kubernetes YAML、CI/CD 脚本确认实际启动了哪些服务、挂载了哪些配置、注入了哪些密钥。
- 运行证据：结合启动日志、指标、链路追踪、消息消费记录、对象存储访问日志和数据库数据，证明目标路径确实被执行。
- 发布证据：核对镜像标签、提交号、制品摘要、灰度范围与回滚记录，避免把仓库中的未来代码误当作线上事实。

尤其在协议弃用中，不能因新版本已发布就删除旧 schema。应以运行数据确认旧客户端比例、最低支持版本、broker 中滞留消息及 DLQ 重放窗口均已结束；同时，历史消息重放仍必须重新校验私有会话权限。真实项目边界应由“依赖—配置—部署—运行”闭环界定，而非由单个函数名推断。

> **要点** — 协议弃用应由旧客户端、broker与DLQ重放窗口共同决定；兼容历史格式时，权限校验与运行证据审查不可省略。

发布成功不等于变更安全：制品、配置、数据库、消息与长连接必须在同一发布窗口内分别验证。

### 先固定四条版本轴与发布身份

### 先固定四条版本轴与发布身份

一次发布至少同时移动四条“版本轴”，它们不能用一个“已上线”笼统代替：

- **服务版本**：当前运行的兼容面为 `S2`，候选代码拟升级为 `S3`。它描述接口、行为与依赖能力，不等同于镜像标签。
- **制品版本**：候选镜像、二进制或前端包必须有不可变身份，如镜像摘要 `sha256:...`、构建号、提交哈希和构建时间。`artifact` 是可部署物；`deployment` 是它在某环境、某批实例上的实际落点。
- **数据库版本**：以迁移编号 `R9` 标识模式与数据状态。`R9` 可能已执行但服务仍为 `S2`；也可能 `S3` 已部署而迁移尚未完成。二者必须分别记录。
- **事件格式版本**：消息的 `wire` 格式是字段如何编码、传输；`semantic` 版本是字段含义、幂等规则和消费行为。字段未变并不保证语义未变。

发布单应明确写出基线与目标，例如：`S2 + R8 + E1 → S3 + R9 + E2`，并注明兼容边界：`S3` 是否可读 `R8`，`S2` 是否可在 `R9` 上继续运行，旧消费者是否能安全处理 `E2`。

候选身份还应绑定部署配置：镜像摘要、配置版本、密钥引用版本、迁移校验和、消息主题与消费者组、OpenIM 实例及站点。这样出现异常时，才能回答“哪一批机器运行了哪个制品、连到了哪个数据库状态、发布了哪种事件”，而不是只知道“刚刚发过版”。

### 按扩展—迁移—收缩安排兼容顺序

### 按扩展—迁移—收缩安排兼容顺序

跨服务发布不能按“代码上线顺序”安排，而应按兼容性推导：先让旧端继续可用，再让新端开始使用，最后删除旧能力。推荐采用 **扩展（expand）→迁移（migrate）→收缩（contract）** 三阶段。

- **扩展阶段**：先发布数据库、协议和消费者都能容忍新旧形态的版本。新增字段应提供默认值或允许空值；事件消费者忽略未知字段；接口读端同时识别旧字段 `status` 与新字段 `state`。此时只“写旧、读双”，避免旧客户端收到无法解析的数据。
- **迁移阶段**：发布写端与生产者，开始“双写”或将新字段作为权威来源；后台回填历史数据，并用样本 `1/10/100` 验证单条、抽样和规模数据的一致性。消费者应按语义版本处理，而非仅看消息是否能反序列化。
- **收缩阶段**：确认旧读端、旧消费者、积压消息和长连接均已退出后，停止旧字段写入，删除兼容分支，最后移除旧列、旧事件类型和旧索引。

“线格式兼容”不等于“语义兼容”。例如把 `status="paid"` 改为 `state="settled"`，旧消费者即使能读取字符串，也可能把“已结算”误判为“已支付”；金额单位、时间语义、幂等键和事件顺序同样需要显式审查。

Postgres 的 `ALTER TABLE` 还要单独评估锁风险：添加带非恒定默认值的列、修改列类型、设置 `NOT NULL` 都可能阻塞业务写入。优先采用“新增可空列 → 分批回填 → 建立约束/索引 → 切换读写 → 延后删除旧列”，并在预发实测锁等待、回填速率与失败回退路径。数据库变更一旦已被新代码依赖，代码可回退，数据通常不能直接回滚；因此收缩动作应作为独立、延后的发布门槛。

### 用消息链路设计灰度样本与停止门

### 用消息链路设计灰度样本与停止门

灰度不应只按流量比例扩容，而应按“可证明的消息闭环”扩容：先选取业务代表性最强、可追踪、可回滚的 `1 → 10 → 100` 个样本，分别覆盖新建、更新、撤销、重试及跨端同步。

- **1 个样本：验证链路存在。** 检查应用是否写入 outbox、投递器是否消费、OpenIM 是否返回可关联的消息标识；同时确认事件字段满足接收端的**线格式兼容**，即字段名、类型、必填项均可解析。
- **10 个样本：验证语义正确。** 覆盖不同租户、会话类型和在线状态，核对消息顺序、幂等键、撤销语义及重复投递后的最终状态。能解析不代表含义正确：例如 `status=deleted` 在线格式上合法，却可能被旧消费者理解为普通更新。
- **100 个样本：验证稳定性。** 观察至少一个完整业务周期内的投递成功率、消费者失败率、端到端延迟、重试次数与 outbox 积压量；还应抽查 OpenIM 侧的送达、离线存储或失败证据，而非仅看发布平台显示“部署成功”。

停止门应预先写成可执行条件：任一关键事件无法关联应用日志、outbox 记录与 OpenIM 回执；失败率超过基线阈值；积压持续增长且超过可恢复窗口；出现语义错投、越权会话或消息乱序，即停止扩量。停止后先冻结新版本流量，保留现场证据，再判断是重试、修复数据还是回退代码；已发出的消息通常不能靠代码回退撤销，必须单独评审数据与补偿事件。

### 区分Pod完成更新与连接完成迁移

### 区分 Pod 完成更新与连接完成迁移

以 IM 服务为例，滚动更新显示所有 Pod `Ready`，只说明新版本实例已通过存活、就绪或基本接口检查；它不表示旧版客户端已完成协议迁移，也不表示旧 WebSocket 连接已经离开旧实例。

典型情形是：负载均衡器停止向旧 Pod 分配**新握手**，但旧客户端仍保持 WebSocket 数小时。若旧 Pod 被立即终止，可能造成：

- 长连接被强制断开，客户端集中重连，形成重连风暴；
- 正在投递或确认中的消息丢失、重复消费，或出现“服务端已发送、客户端未确认”；
- 新旧版本对消息字段、确认语义的理解不同，产生协议兼容但业务语义不兼容的问题。

因此，发布门槛应拆分为两类：

1. **流量切换完成**：新连接进入新 Pod；新版本错误率、握手成功率、消息发送延迟正常。
2. **连接迁移完成**：旧 Pod 的活跃 WebSocket 数持续下降，排空窗口内无异常断连；客户端重连成功率、在途消息确认率满足阈值。

旧 Pod 应先进入 `drain`：摘除新流量、继续服务已有连接、向客户端发送可重连提示，并设置最长排空时间。到期仍未迁移的连接才受控关闭。对关键消息，应依赖消息标识、幂等处理与确认机制恢复在途任务，而非假定“连接断开即任务失败”。

可观察指标至少包括：旧版本连接数、连接年龄分布、重连率、WebSocket 异常关闭码、未确认消息数与 outbox 积压。只有这些证据表明连接和消息状态完成迁移，才能把“Pod 更新成功”升级为“发布完成”。

### 用回退矩阵审查代码配置与数据

### 用回退矩阵审查代码配置与数据

回退不是“重新部署上一版”这么简单。应把变更拆成代码、部署配置、数据三类，并分别判断：能否回退、回退条件、回退后是否仍保持业务正确。

| 变更对象 | 典型内容 | 可逆性判断 | 回退风险与门槛 |
|---|---|---|---|
| 代码 | Go 服务、消费者、WebSocket 处理 | 通常可回退，但依赖兼容接口 | 新代码写入的数据、消息格式必须能被旧代码读取 |
| 部署配置 | 环境变量、路由、限流、开关、镜像标签 | 多数可快速回退 | 配置应版本化；密钥、迁移开关和流量比例需保留审计证据 |
| 数据 | PostgreSQL 表、索引、枚举、历史回填 | 常常不可直接回退 | 禁止把“删列/改类型/批量回填”视为普通发布回退项 |

协议兼容还要区分两层。**字节兼容**表示旧客户端收到新字段、未知枚举或扩展消息时不会解码失败；**语义兼容**表示它即使能解码，也不会把新状态误判为成功、离线或已读。前者可通过消息样本验证，后者必须用业务场景验证。

数据库迁移采用 `expand/contract`：先扩展 schema，例如新增可空列、索引、双写逻辑；灰度确认后再切读路径；最后才收缩旧列和旧代码。PostgreSQL 的 `ALTER TABLE` 可能持有锁，需在预发和低峰窗口实测锁等待、执行时长及对写入延迟的影响。

建议在发布评审中明确矩阵：

- 代码回退：旧版本是否兼容新消息、新字段及 outbox 积压消息。
- 配置回退：开关是否可在不重启条件下恢复，灰度比例能否从 `100%` 降至 `10%`、`1%` 或 `0%`。
- 数据回退：是可逆迁移、补偿脚本，还是只能前向修复；负责人必须签字确认。
- 实测待验证：WebSocket drain 后重连率、outbox lag 清空时间、OpenIM 消息投递与回执证据、`ALTER` 锁影响。

尤其应避免“代码已回退，数据仍停留在新语义”的假安全状态：代码可以回滚，数据往往只能兼容、补偿或前向修复。

> **要点** — 可靠发布要让版本、消息、数据和长连接各自可观测、可停止、可回退。
