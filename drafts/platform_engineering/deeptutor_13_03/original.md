承接 m-9/seq9/E9 模型，本节用 IM 接口区分应公开的业务承诺与应隐藏的存储实现，避免把表名、分区和确认语义混为一谈。

### 模块边界：围绕变化决策划分

### 模块边界：围绕变化决策划分

模块不是“一个目录”或“一个包名”，而是一组应当共同变化的决策。划分边界时，先问：**未来最可能独立变化的是什么？** 若存储方案、分区规则、表名、重试策略可能变化，而客户端不应随之改动，它们就应留在模块内部。

以消息写入为例，公开接口应表达稳定的业务承诺，例如：

- 输入：会话、成员身份、消息内容、客户端请求标识；
- 输出：消息是否被当前进程接受，以及重复请求、非成员、正文超限等结果；
- 约束：S2/v1 正文最多 `6` UTF-8 字节、原始 HTTP 体最多 `4096` 字节、同一标识重复提交返回 `409`、非成员返回 `404`；
- 确认语义：`200 accepted_in_memory` 仅表示本进程已接受，不表示已持久化。

内部实现则可以自由演进：S2/v1 先保存在内存，S3/v2 改为 `stored_in_teaching_db`；表从 `messages` 改名，按会话分区，甚至将 R9 的上限从 `6B` 提议调整到 `9B`，都不应迫使调用方了解数据库细节。

因此，接口不应出现“写入哪张表”“分区键是什么”之类字段。它们会让调用者依赖偶然实现，形成抽象泄漏。信息隐藏隐藏的是**实现选择**，不是隐藏业务确认语义：`accepted_in_memory` 与“已可靠存储”是不同承诺，必须明确公开。

### 消息接口不应携带分区与表名

### 消息接口不应携带分区与表名

泄漏式接口把数据库布局带进了业务请求，例如：

`POST /partitions/2025_03/messages?table=im_message_s2`

或请求体：

`{"conversation_id":"c-9","sender_id":"u-1","body":"你好","partition":"p03","table":"message_v1"}`

这看似让调用方“明确指定写到哪里”，实则破坏模块边界。`partition`、`table`、索引、分库规则都属于服务端内部实现；调用方一旦依赖它们，后续从按月分区改为按会话哈希、从 `im_message_s2` 迁移到教学库，都会变成接口兼容性问题。更糟的是，客户端可能选错分区，或借表名推测、访问不应接触的数据结构。

语义型接口只表达业务事实：

`POST /conversations/c-9/messages`

`{"sender_id":"u-1","content":"你好"}`

这里公开的是：谁在向哪个会话发送什么内容；服务端再自行完成成员校验、重复 ID 判断、长度限制与存储路由。S2/v1 中正文最多 `6 UTF-8 字节`、原始 HTTP 体最多 `4096 字节`、同一消息 ID 重复提交返回 `409`、非成员返回 `404`，都是可观察的业务契约；`200 accepted_in_memory` 则只承诺已被**当前进程内存**接受，不等同于已落库。

S3/v2 即使改为 `stored_in_teaching_db`，客户端也不应获知具体表名；R9 将正文上限从 `6` 调整为 `9 字节`仍待审，更应作为版本规则公布，而不是让调用方通过分区或表结构自行猜测。信息隐藏隐藏的是实现选择，不是确认语义、校验规则或错误结果。

### S2 与 S3：承诺可见，实现可替换

### S2 与 S3：承诺可见，实现可替换

沿用 `m-9/seq9/E9`，客户端真正依赖的是**可观察的业务承诺**，而不是服务端怎样落库。

S2 的 `v1` 接口可公开写成：

- 正文非空，最多 `6 UTF-8` 字节；
- 原始 HTTP 请求体最多 `4096` 字节；
- 同一消息 ID 重复提交返回 `409`；
- 非会话成员提交返回 `404`；
- 成功返回 `200`，其含义仅为 `accepted_in_memory`：消息已被**当前进程**接受。

这些规则应出现在接口文档、测试和调用方判断逻辑中。例如，调用方看到 `200` 后可以展示“已发送到当前服务”，却不能据此推断“已永久保存”“重启后仍存在”或“其他副本已经可见”。

S3 的 `v2` 将成功语义升级为 `stored_in_teaching_db`，即消息已写入教学数据库；同时正文上限仍是 `6` 字节。这里“已存入教学库”是新的公开承诺，因此属于契约。相反，数据库中的表名、索引名、分区键、分区数量，以及去重记录究竟放在何处，都应是内部实现。

```text
公开：最多 6B、409、404、200 的确认含义
隐藏：message_log 表、按 room_id 分区、唯一索引实现去重
```

若 R9 提议把上限从 `6B` 改为 `9B`，即使数据库字段本来足够大，也不能直接改实现后悄悄上线：长度限制是调用方可见契约，必须经过评审并形成新版本或兼容策略。

信息隐藏并不意味着隐藏业务事实。S3 若承诺“已存储”，就必须明确可被确认的存储语义；隐藏的只是“存到哪张表、哪一分区、如何事务提交”。当接口泄露表名或分区时，未来迁移存储方案会迫使客户端跟着修改，这正是抽象泄漏。

### 确认点、错误与不确定结果必须公开

### 确认点、错误与不确定结果必须公开

信息隐藏隐藏的是“怎样做到”，不是“做到什么程度”。因此，模块可以不向调用者暴露教学库的表名、分区键、索引或事务细节；但必须公开一次发送在何处被确认，以及调用者面对重复、无权限和网络中断时应如何解释结果。

对当前 S2/v1，`200 accepted_in_memory` 的公开含义是：服务已在**本进程内存**中接受该消息。它不是“已写入持久库”，更不是“对方已收到”。进程崩溃、重启或切换实例后，这个确认可能丢失。调用者据此可以更新本地界面为“已被当前服务接受”，却不能把它当作跨进程可靠投递的凭证。

错误同样属于接口契约，而非内部细节：

- `409`：同一消息 ID 已提交过。调用者应将其视为幂等重试遇到既有请求，而不是再生成一条新消息。
- `404`：发送者不是该会话成员，或目标会话不可见。调用者不能通过重试把它变成成功，应转向权限、成员关系或会话状态处理。
- 超时、连接断开：结果是**不确定**的；请求可能未到达，也可能已被内存接受但响应丢失。调用者应保留原消息 ID，以同一 ID 重试或查询，而非盲目创建新 ID。

因此，公开结果模型至少要区分“已接受”“确定拒绝”和“不确定”。S3/v2 即使仍提议 6B 正文上限，`stored_in_teaching_db` 也会把确认点推进到教学数据库；这是一项可见语义升级，不是可随意藏在实现后的替换。R9 从 6B 调整到 9B 尚待审，则更不能被提前当成既成承诺。

### Go 包与消费侧接口的变更检验

### Go 包与消费侧接口的变更检验

Go 的包边界不应按“数据库有什么”来设计，而应按“调用者需要什么”来设计。发送消息的应用层只需依赖一个小接口，例如：

`Send(ctx, conversationID, senderID, body) (MessageID, error)`

它公开的业务承诺是：正文最多 `6 UTF-8` 字节；原始 HTTP 请求体最多 `4096` 字节；重复提交同一消息标识返回 `409`；非会话成员返回 `404`；成功的 `200 accepted_in_memory` 仅表示本进程已接受。它不应要求调用方知道消息写入哪张表、按何键分区，或是否经过队列、缓存与异步落库。

接口应由消费者一侧定义，而不是由存储包反向主导。若处理器只需要“提交消息”，就不应依赖带有 `InsertTeachingDB`、`PartitionForConversation` 之类方法的仓储接口；这些名字把内部实现泄漏给了上层，也会迫使 HTTP 层跟随表结构变化。

用待审变更 R9 检验边界：正文上限从 `6B` 调整为 `9B`。

| 位置 | 应否变化 | 原因 |
|---|---:|---|
| 请求校验与错误响应 | 应变化 | 这是公开业务规则 |
| `Send` 的方法签名 | 通常不变 | 参数仍是 `body`，未改变抽象能力 |
| 消费侧接口 | 不变 | 调用者不关心具体上限存于何处 |
| 测试用例 | 应变化 | 补充 `7B` 至 `9B` 可接受、`10B` 被拒绝 |
| 表名、分区键、SQL | 不应因规则直接暴露 | 属于实现选择 |
| S3 `stored_in_teaching_db` | 仅内部适配 | 落库实现可更新约束，但不应改变调用协议 |

若 R9 一改就需要修改大量调用方、HTTP 路由或暴露 `teaching_db` 表名，说明模块边界已经泄漏。反之，隐藏实现并不等于隐藏确认语义：`accepted_in_memory` 与 `stored_in_teaching_db` 的差别是客户端可观察的业务承诺，必须在公开响应或版本契约中明确表达，而不能藏在包内部。

> **要点** — 隐藏表名和分区，公开业务语义、确认点与错误；好的模块让存储和规则变更只影响少数实现。

模块边界不应围绕数据库表或队列分区命名，而应围绕可能独立变化的设计决策建立稳定的语义承诺。

### 按变化决策划分模块

### 按变化决策划分模块

Parnas 的关键观点是：模块边界应当隐藏“将来可能改变的设计决策”，而不是把当前实现步骤、代码目录或数据表原样切开。若一个消息服务按 `messages` 表、`partitions` 表、`offsets` 表分别建模块，表结构一变，调用者往往也必须跟着修改；这只是把存储细节扩散到了更多位置。

更稳健的划分方式是先问：哪些决策会以不同节奏变化？

- 存储引擎可能从关系数据库换成日志存储、分布式数据库或对象存储；
- 消息序号可能从全局递增改为分区递增、时间编码或服务端生成的不可比较标识；
- 队列分区、`offset`、再均衡策略可能随吞吐量和消费模型调整；
- 成员历史、重放窗口、删除规则可能受合规要求改变；
- 客户端协议则可能因兼容性承诺而变化得更慢。

因此，模块应向外承诺“发布消息”“订阅事件”“确认已处理”“查询可重放范围”等语义，而把表名、分区号、内部位点和索引策略留在模块内部。调用者依赖的是稳定能力，不是某张表或某个分区的存在。

可用简易矩阵检查泄漏：

| 可能变化 | 影响存储模块 | 影响消息语义接口 |
|---|---:|---:|
| 更换存储引擎 | 高 | 低 |
| 调整分区策略 | 高 | 低 |
| 改变重放/保留规则 | 中 | 高 |
| 修改客户端确认语义 | 中 | 高 |

前两类应被实现模块吸收；后两类若改变了用户可观察行为，就必须演进公开合同。尤其 R9 一类需求若直接影响订阅、确认或历史可见性，不能声称“已被模块隐藏”：它需要明确的版本化接口、兼容策略或迁移说明。

### IM消息链路中的变化源

### IM消息链路中的变化源

IM 链路中的实现决策并非以相同速度变化，也不会触及相同范围。按 Parnas 的原则，模块边界应隔离“可能独立变化的设计决策”；按 Ousterhout 的观点，深模块应以少量稳定语义吸收大量内部复杂性。

| 变化源 | 典型变化频率 | 主要冲击范围 | 是否应直接暴露给客户端 |
|---|---:|---|---|
| 存储引擎 | 低 | 持久化、索引、读写路径 | 否 |
| 序号分配 | 中 | 去重、排序、补拉、幂等 | 仅暴露语义序号，不暴露生成方式 |
| 队列分区与 offset | 中高 | 吞吐扩展、迁移、消费恢复 | 否 |
| 成员历史规则 | 中 | 新成员可见范围、退群后查询 | 应暴露为明确的可见性规则 |
| 客户端协议 | 高 | 兼容性、灰度、版本演进 | 应提供可演进的契约 |

例如，底层从单库迁移到分片存储，或将队列从固定分区改为动态扩容，不应迫使客户端理解“表名、分区号、offset”。客户端真正需要的是：消息如何定位、是否有序、能否去重、从何处继续拉取。服务端可将内部 offset 映射为稳定的 `cursor`，将物理分区隐藏在消息服务之后。

但信息隐藏不是“假装不存在”。若 R9 规定客户端必须携带分区号或 offset 才能续拉，那么它已经进入公开合同：分区重平衡、offset 重置、迁移兼容都会外溢到协议、SDK 和业务逻辑。此时模块无法完全遮蔽该变化，只能承认其契约地位，并通过版本化、弃用窗口和兼容映射控制冲击。

### 深模块为何只暴露消息语义

### 深模块为何只暴露消息语义

Ousterhout 所谓“深模块”，不是接口功能少，而是**用较小、较稳定的接口隐藏较大的实现复杂度**。消息系统的复杂性通常包括：消息落在哪个存储引擎、如何分表、按何种键分区、序号怎样生成、消费者位点如何保存、重试与死信如何处理。这些都是实现决策，不应成为调用方必须理解的事实。

浅接口往往直接泄露物理结构：

- `insert into message_partition_17 ...`
- `select ... from queue_order_2024 where offset > ?`
- `update consumer_offset set ...`

这类接口看似直接，却把客户端绑定到表名、分区编号、`offset` 语义和存储事务模型。今后从 MySQL 切换到日志存储、从固定分区改为动态路由、从连续序号改为游标令牌时，所有调用方都会受到冲击。

深接口则只承诺业务可理解的消息语义，例如：

- `投递(消息)`：系统负责持久化、路由与去重；
- `拉取(订阅者, 数量)`：返回该订阅者当前可处理的消息；
- `确认(订阅者, 消息标识)`：声明处理完成；
- `查询状态(消息标识)`：查询投递、处理中、完成或失败等状态。

| 可能变化 | 暴露分区/表名的接口 | 暴露消息语义的接口 |
|---|---|---|
| 存储引擎替换 | 客户端改 SQL | 服务内部适配 |
| 分区策略调整 | 客户端重算分区 | 路由规则内部变化 |
| 位点模型变更 | 客户端依赖 `offset` | 保持确认语义 |
| 重试规则演进 | 客户端拼接补偿逻辑 | 服务统一执行 |

信息隐藏并不等于“任何变化都无影响”。若 R9 明确写入公开合同，例如“同一键严格有序”或“确认后绝不再次投递”，它就是接口承诺，不能声称被模块隐藏。深模块隐藏的是实现路径；语义保证一旦公开，就必须被版本化、测试并长期维护。

### 变更冲击矩阵检验边界

### 变更冲击矩阵检验边界

Parnas 的检验问题是：某项设计决策改变时，哪些地方必须一起改？若存储、分区或协议细节频繁穿透接口，说明模块边界画错了。可用简易矩阵记录冲击范围：

| 可能变化的决策 | 公开合同 | 模块实现 | 调用方 |
|---|---:|---:|---:|
| 更换存储引擎、索引或表结构 | 否 | 是 | 否 |
| 调整消息的物理分区数与迁移策略 | 否 | 是 | 否 |
| 修改队列内部 offset 编码、压缩或保留方式 | 否 | 是 | 否 |
| 更换序号分配器或去重实现 | 否 | 是 | 否 |
| 修改成员历史判定规则 | 视语义而定 | 是 | 可能 |
| 增加协议字段、废弃客户端版本 | 是 | 是 | 是 |
| R9：改变调用方可观察的投递、顺序或确认语义 | 是 | 是 | 是 |

理想的深模块把前三类变化吸收在实现内部：调用方只提交“发送消息”“读取下一条”“确认已处理”等语义请求，不应指定 `table_name`、`partition_id`，也不应把内部 `offset` 当作长期业务标识。

矩阵中的“是”并非失败；关键在于它是否诚实地暴露了语义变化。成员历史规则若只改变内部缓存淘汰，合同可不变；但若它改变“新成员能否看到旧消息”，调用方的可观察结果已经变化，便必须升级或澄清合同。

尤其是 R9：如果它影响公开的顺序、重复投递、可见性或确认保证，就不能声称“由模块完全隐藏”。信息隐藏只能隐藏实现选择，不能隐藏已承诺语义的改变。此时应通过版本化消息协议、能力协商或新的语义接口管理迁移，而不是让客户端猜测分区、表名和 offset 的新含义。

### R9与无法隐藏的公开承诺

### R9与无法隐藏的公开承诺

Parnas 的信息隐藏并不意味着“任何变化都对外不可见”。若 R9 已把某项行为写入消息接口合同，例如投递顺序、重复消息处理、确认时限、失败码或可见性规则，它就成为调用者可依赖的公开承诺；即使内部实现从数据库表切换到日志存储、从单队列改为多分区，也不能假装该变化被模块完全吸收。

简易冲击矩阵如下：

| 可能变化的决策 | 应隐藏于模块内 | 是否可能冲击 R9 |
|---|---|---|
| 存储引擎、表名 | 是 | 否 |
| 序号分配算法 | 通常是 | 若承诺连续或全局顺序，则是 |
| 队列分区与 offset | 是 | 若客户端可见分区或 offset，则是 |
| 成员历史、重放规则 | 部分 | 若影响可读取范围，则是 |
| 客户端协议字段 | 否，已公开 | 是 |

深模块应提供稳定的语义接口，而非暴露“分区号 + offset + 表名”。但当 R9 承诺的语义必须调整时，正确做法不是把变更藏在实现说明里，而是显式管理公开合同：

- 用版本字段或新接口并行承载新旧语义；
- 明确兼容窗口、弃用日期与迁移路径；
- 对无法安全解释的旧请求返回可识别的错误码；
- 将“顺序范围”“重放边界”“幂等要求”等写成可测试合同。

因此，模块可以隐藏实现决策，却不能隐藏已经出售给调用者的行为保证。

> **要点** — 隐藏的是可变实现决策；一旦行为写入公开合同，就必须承担其兼容性与变更成本。

一个消息接口若要求调用者理解成员关系、序号、集合和分区，实际是在把系统最易变的内部决策变成公开承诺。

### 识别泄漏式发送接口

### 识别泄漏式发送接口

典型的泄漏式接口看似“灵活”，实则要求调用者替模块完成内部工作：

`Send(groupID, senderID, receiverID, seq, mongoCollection, kafkaPartition, offset, payload)`

它至少泄漏了四类本应隐藏的实现决策：

- **成员关系判断**：调用者必须先确认 `senderID`、`receiverID` 是否属于群组，意味着权限与成员查询规则被复制到多个调用方。成员变更、禁言、移除后的边界很容易不一致。
- **序号分配策略**：要求调用者传入 `seq`，等于公开了消息排序、并发冲突处理与幂等依据。分区切换、改用数据库自增、采用逻辑时钟后，所有客户端都可能被迫修改。
- **存储位置**：暴露 Mongo 集合名，调用者就知道消息按何种表结构、分片键或归档策略保存。集合拆分、冷热迁移、改用其他数据库都会成为破坏性变更。
- **队列投递位置**：暴露 Kafka 分区和 offset，意味着调用者必须理解路由规则、分区顺序及消费进度；而这些本应由生产端统一决定。尤其 `offset` 通常由 Kafka 分配，调用者声称“已写入某 offset”并不能证明权威提交已完成。

更隐蔽的问题是失败语义：调用者完成成员检查、写库和投递后，仍无法判断“数据库提交但队列失败”“队列已收但事务回滚”等中间状态。接口把复杂性转移出去，却没有把权威确认边界一起交代。

发送接口应接收意图，例如 `Send(ctx, SendCommand)`；成员校验、序号、存储和分区选择均留在模块内部。调用者只应看到稳定的 `MessageID`、明确的接受或失败结果，而不应看到集合名、分区号或伪造的“已送达”承诺。

### 以变化决策划定模块边界

### 以变化决策划定模块边界

模块边界不应按“数据存在哪里”划分，而应按“哪些决策会变化”划分。消息发送中，成员校验、序号生成、Mongo 集合选择、Kafka 分区路由与 offset 推进都可能因扩容、迁移、排序策略或权限模型调整而改变；因此它们都应属于消息模块的内部职责。

若接口要求调用者先检查成员，再自行分配 `seq`，并指定集合、分区或期待的 offset，调用者就被迫依赖如下内部事实：

- 谁是会话成员，以及成员关系从何处读取；
- 序号是全局递增、按会话递增，还是由数据库事务生成；
- 消息写入哪个 Mongo 集合、是否按时间分表；
- Kafka 按会话、用户还是哈希键选择分区；
- offset 何时推进，是否已代表权威存储完成。

这些事实一旦变化，所有调用方都要同步修改；更危险的是，不同调用方可能以不同顺序执行“校验—写库—投递”，从而无法判断失败时权威状态是否已经提交。

因此，外部只应表达稳定意图，例如 `Send(ctx, SendCommand)`：某个发送者要向某个会话发送一条带有稳定 `MessageID` 的消息。模块内部负责校验成员、生成顺序、持久化与投递重试，并返回清晰确认边界。当前 `/v1` 若只能保证已受理到内存，就明确返回 `AcceptedInMemory`；未来 `/v2` 若承诺已写入 TeachingDB，则以新合同返回 `StoredInTeachingDB`。内部可以更换事务、集合和分区策略，但不能伪造“已经送达”的确认。

### 用SendCommand表达发送意图

### 用 `SendCommand` 表达发送意图

泄漏式接口常把一次“发送消息”拆成调用者必须完成的内部操作：

`Send(ctx, conversationID, memberID, seq, mongoCollection, kafkaPartition, offset, payload)`

这类参数看似精确，实际公开了承诺不该公开的事实：成员如何校验、序号如何分配、消息落在哪个集合、投递到哪个分区、偏移量是否连续。任何存储迁移、分区重平衡或排序策略调整，都会反过来破坏调用方。

更严重的是，调用者拿到的 `seq`、`offset` 或“写入成功”并不能回答关键问题：权威消息记录是否已经提交？消息是否只是进入内存队列？是否会在故障后丢失？接口把实现细节交出去，却没有给出可验证的业务确认边界。

语义型接口只公开调用者真正能决定的意图：

`Send(ctx, SendCommand{ConversationID, SenderID, MessageID, Content})`

其中：

- `ConversationID` 表示发往哪个会话；
- `SenderID` 表示谁请求发送，服务端据此完成成员与权限校验；
- `Content` 是业务载荷；
- `MessageID` 是稳定的客户端意图标识，而不是数据库主键、序号或 Kafka offset。

`MessageID` 应在重试时保持不变。这样，超时后的重复提交仍代表“确认同一条消息是否被接受”，而不是创建另一条消息。若该意图已被处理，可返回 `409`；会话不存在或发送者不是成员，可返回 `404`。这些错误描述业务事实，而非泄露集合名、事务状态或分区布局。

当前 `/v1` 的成功语义若只能保证 `AcceptedInMemory`，就必须明确说明：命令已被进程接受，但尚不等于已持久化、更不等于已送达。未来若 `/v2` 提供 `StoredInTeachingDB`，应作为新的确认合同单独声明。事务、去重、序号分配与重试留在模块内部演进；公开接口只承诺稳定的发送意图及其明确结果。

### 把确认边界和失败结果说清楚

### 把确认边界和失败结果说清楚

`v1` 的确认不能写成含糊的“发送成功”。当前实现若只是把消息放入进程内队列，唯一诚实的成功语义是：

`AcceptedInMemory`：服务已完成基本校验，并已将该发送意图接收入当前进程内存；它**不表示**消息已写入教学数据库、已进入 Kafka、已被消费者处理，更不表示对方已读到。

因此，接口应让调用者能区分三类结果：

- **明确失败**：请求没有被接受，调用者可以根据错误安全地修正后重试。  
  - 发送者或接收者不属于该会话：返回 `404`；不要泄露“用户存在但无权限”等额外信息。  
  - 相同 `MessageID` 已经提交过：返回 `409`；这表示意图标识冲突或重复提交，而不是再次投递。  
  - 参数非法、会话状态不允许发送：返回对应的明确客户端错误。

- **明确接受**：返回 `AcceptedInMemory`。此时服务承诺“本进程已经接住了这条命令”，但调用者必须理解：进程崩溃、后续持久化失败或异步链路故障，都可能使最终送达未发生。

- **未知结果**：例如客户端超时、连接中断，调用者没有收到响应。它不能自行推断“失败”或“成功”：服务端可能已接收命令，也可能尚未处理。调用者应保留稳定的 `MessageID`，以同一意图查询或重试，而不是生成新序号、新消息。

`MessageID` 表示用户的发送意图，应跨重试保持不变；成员校验、重复检测、事务编排和异步重试则留在模块内部。未来若 `v2` 能在响应前完成教学数据库持久化，才能另行定义 `StoredInTeachingDB`；不能把尚未具备的可靠性伪装成“已送达”。

### 在Go中保持接口方向与变更隔离

### 在Go中保持接口方向与变更隔离

接口应由应用服务的消费者定义，而不是由 MongoDB、Kafka 或事务框架反向塑形。调用者只表达意图：谁要向哪个会话发送什么内容；实现层自行判断成员资格、生成或校验顺序、选择持久化与投递策略。

例如，应用层依赖的端口可以是：

`Send(ctx context.Context, cmd SendCommand) (SendReceipt, error)`

其中 `SendCommand` 至少包含稳定的 `MessageID`、会话标识、发送者和消息内容；`SendReceipt` 则明确确认边界。当前 `/v1` 的成功含义只能是 `AcceptedInMemory`：服务已接受该意图，但不声称教学数据库已提交，更不声称 Kafka 已送达。重复 `MessageID` 返回 `409`，会话不存在或发送者非成员返回 `404`；这些语义不应依赖集合名、分区号或 offset。

Go 中可让处理器依赖小接口，例如 `MessageSender`，而具体实现组合成员查询、内存状态、事务协调器、教学数据库仓储和 Kafka 发布器。这样重试、幂等记录、outbox 或补偿逻辑都留在模块内部；尤其不能因后台投递尚未完成，就伪造“已送达”的成功结果。

可用变更冲击矩阵检验隔离效果：

| 未来变化 | 调用方 | `SendCommand` | `/v1` 合同 | 实现内部 |
|---|---:|---:|---:|---:|
| Mongo 集合改名 | 不变 | 不变 | 不变 | 调整仓储 |
| Kafka 分区策略调整 | 不变 | 不变 | 不变 | 调整发布器 |
| 加入事务或重试 | 不变 | 不变 | 不变 | 调整协调逻辑 |
| `/v2` 承诺 `StoredInTeachingDB` | 不变或按版本迁移 | 可复用 `MessageID` | 新增合同 | 增加可验证落库边界 |

因此，`/v2` 不是把内部“现在恰好落库”泄露给客户端，而是经明确批准后新增更强确认语义；旧版仍只承诺其真实能够证明的边界。

> **要点** — 公开接口应承诺稳定业务语义与确认边界，而非存储、分区、序号等可变实现细节。

接口的位置由谁需要抽象决定，而非由实现技术决定；分清用例、领域规则、存储适配与HTTP映射，才能避免依赖倒置沦为层数堆叠。

### 从调用者需求决定接口归属

### 从调用者需求决定接口归属

Go 的接口描述的是“调用者需要什么能力”，而不是“实现者愿意暴露什么能力”。因此，接口通常应定义在消费侧包中：用例包只声明完成当前用例所需的最小方法，存储实现、消息系统或第三方客户端再去满足它。

例如，“查看历史”用例只需要读取记录，不需要知道数据来自 Mongo、分区表还是 Kafka：

```go
package history

type Reader interface {
	List(ctx context.Context, userID string, limit int) ([]Message, error)
}

type Service struct {
	reader Reader
}
```

`history` 包拥有 `Reader`，因为它承担调用和解释结果的责任。基础设施包不应反过来定义一个巨大的 `MessageRepository`，再要求所有用例依赖它；那会把实现方的存储模型、操作集合和未来扩展压力泄漏给业务代码。

实现可以位于内部适配器中：

```go
package mongostore

type Store struct {
	// Mongo 客户端、集合名等实现细节
}

func (s *Store) List(ctx context.Context, userID string, limit int) ([]history.Message, error) {
	// 查询实现
	return nil, nil
}
```

这里的依赖方向是：用例定义需求，适配器满足需求；内层不导入具体 Mongo、Kafka 或 HTTP 框架。若另一个用例还需要写入消息，它应自行声明更贴近自身语义的 `MessageWriter`，而非被迫依赖读取、删除、批量迁移等无关方法。

这也解释了为什么不能仅为 mock 制造“大而全”的接口。测试替身应替换真实协作点；若用例实际只读取历史，就 mock `HistoryReader`。接口的价值来自真实的调用边界、替换需求或测试隔离，而不是为了让架构图多出一层。

### 四类职责与单向依赖

### 四类职责与单向依赖

把“发送消息”拆开，关键不是多建目录，而是让每类代码只回答一种问题：

- **HTTP 映射层**：把请求解析为命令、从上下文取得调用者、调用用例，并将结果映射为状态码和响应体。它知道 `http.Request`，但不应包含权限判定或 Mongo 查询。
- **应用用例层**：编排一次业务动作，例如“用户向会话发送消息”：校验输入、请求领域规则、写入消息、发布后续事件。它依赖所需能力，而非 `MongoClient`、Kafka Producer 等实现。
- **领域对象与权限规则**：表达稳定业务含义，如成员资格、禁言状态、会话可写性。规则应接收领域数据并返回业务结论，不导入 HTTP、数据库驱动或消息队列包。
- **内部存储端口与适配器**：端口描述用例真正需要的能力；适配器把该能力落实到 Mongo、Kafka、PostgreSQL 等技术。技术细节停留在最外侧。

```go
type HistoryReader interface {
	LoadHistory(ctx context.Context, roomID RoomID, after MessageID) ([]Message, error)
}

type MessageWriter interface {
	Append(ctx context.Context, msg Message) error
}

type SendMessage struct {
	history HistoryReader
	writer  MessageWriter
}
```

依赖方向应始终向内：`HTTP → 用例 → 领域`；Mongo/Kafka 适配器也指向用例定义的端口，即 `MongoAdapter → MessageWriter`。因此内层可以在不启动 Mongo 或 Kafka 的情况下被测试，也不会因更换存储而改写权限规则。

端口不是“每层一个接口”的装饰。只有当用例确实需要替换实现、隔离外部资源或构造测试替身时，才定义像 `HistoryReader` 这样窄的接口；若只有唯一实现且不存在替换需求，直接依赖具体类型通常更清晰。

### 以发送与补拉用例提炼小接口

### 以发送与补拉用例提炼小接口

接口应从调用者的动作出发。发送用例只需“写入一条已校验的消息”，补拉用例只需“按会话和游标读取后续消息”；它们不应知道 Mongo 集合、分区键、Kafka 主题或分页查询语法。

可在应用用例包中定义：`type MessageWriter interface { Append(ctx context.Context, m Message) error }`。发送服务依赖 `MessageWriter`，先调用领域对象或权限规则完成成员资格、禁言、内容限制等判断，再写入消息。其 Mongo 适配器自行决定集合名、`conversation_id` 索引与事务策略；Kafka 投递也可作为另一个内部适配器，而非暴露给用例。

补拉用例需要的契约则不同：`type HistoryReader interface { ReadAfter(ctx context.Context, conversationID string, after MessageID, limit int) ([]Message, error) }`。这里返回领域 `Message` 与稳定的 `MessageID`，而不是 `bson.M`、`partition`、`tableName` 或数据库游标。HTTP 层仅把请求参数映射为 `conversationID`、`after`、`limit`，再将结果编码为响应；它不拥有存储接口的定义权。

反例是：`type MessageRepository interface { Insert(collection string, partition int, doc bson.M) error; Query(table string, cursor string) ... }`。这类接口把实现细节推给调用者，使更换存储、调整分片或测试时都要修改用例代码。

`MessageWriter` 与 `HistoryReader` 可以由同一持久化适配器实现，但不必合并成巨大“仓储接口”。只有确有替换实现或测试替身需求时才抽象；测试发送用例时，实现一个记录 `Append` 调用的假写入器即可，无须为模拟而让实现方承诺全部数据库能力。

### 不为模拟测试制造万能接口

### 不为模拟测试制造万能接口

测试需要替身，不等于每个实现都要先声明一个“大而全”的接口。接口应描述调用方真正依赖的能力；若调用方只需读取历史和写入消息，那么依赖可以很小：

```go
type HistoryReader interface {
	Load(ctx context.Context, userID string) ([]Message, error)
}

type MessageWriter interface {
	Append(ctx context.Context, m Message) error
}
```

用例包依赖这两个能力，生产环境可由 Mongo 适配器实现，测试可用内存假实现替换。这里的接口有明确价值：存在真实的替换边界，且调用方不必知道集合名、分区或 Kafka 主题。

相反，常见反模式是在存储实现方预先定义：

`type Repository interface { Create; Update; Delete; Find; List; Query; Transaction; ... }`

随后所有用例都注入它，只因“方便 mock”。代价通常高于收益：

- 新增一个实现细节，接口、所有假实现和测试夹具都要同步修改；
- 用例获得远超所需的权限，依赖关系变得模糊；
- 测试围绕调用次数和 mock 配置编写，反而难以表达业务结果；
- 具体类型本可直接使用，却被迫穿过一层没有语义的抽象。

若某个用例只在进程内调用稳定的 `Policy`、`Clock` 或内存对象，直接持有具体类型往往更清晰。只有当存在独立演进的实现、昂贵或不稳定的外部资源、需要确定性测试替身，或多个调用方确实共享同一能力契约时，才引入小接口。

接口不是“可测试性装饰”。好的测试设计先问：这里是否真的需要替换？答案是否定时，直接使用具体类型，通常是维护成本最低的选择。

### 用变更冲击验证边界是否有效

### 用变更冲击验证边界是否有效

判断边界是否合理，不要只看目录是否分层，而要设想一次真实变更会迫使哪些包修改。理想状态是：变化停留在其应属的边界，核心用例既不认识分区、集合名，也不关心 HTTP 状态码或 Kafka 的投递细节。

- **Mongo 更换为其他数据库**：应用用例仍只依赖它实际需要的能力，例如 `HistoryReader`、`MessageWriter`；变动应集中在存储适配器及其装配处。若用例中出现 `mongo.Collection`、查询过滤器或事务会话，说明基础设施细节已穿透边界。
- **引入 Kafka 异步投递**：若“写入消息后发布事件”是用例承诺，则应用层可依赖一个窄的发布端口；Kafka 的主题名、分区键、重试策略属于适配器。若 Kafka 只是审计或通知优化，不应反向污染核心写入流程。
- **HTTP 协议调整**：路径、请求体、鉴权头、`400` 或 `409` 的映射应留在 HTTP 层。应用层接收已解析的命令，返回领域结果或可判定的错误；HTTP 层在此处确认“权限不足”“参数非法”“资源不存在”分别如何呈现。
- **权限规则修改**：谁能读取历史、谁能撤回消息，属于领域对象或权限规则；应用用例负责协调“加载—检查—执行—保存”，不应把角色字符串比较散落在处理器和数据库查询中。

接口也应经受同样检验。`MessageWriter` 的责任是写入消息，而不是暴露 `InsertOne`、集合名和索引选项；`HistoryReader` 的责任是提供用例所需历史，而不是复制整个数据库客户端。只有存在真实替换点或测试隔离需求时才引入它们。若一个接口仅为模拟实现而罗列几十个方法，变更 Mongo、Kafka 或权限规则时，反而会让无关调用者一起破裂。

> **要点** — 接口应贴近使用者的稳定语义；仅在真实替换或测试边界需要时抽象，具体基础设施始终停留在外层适配器。

消息接口应承诺用户可理解的结果，而非暴露分区、表名或 broker offset 等易变实现；但状态确认、权限与未知结果必须如实表达。

### 先划清：语义承诺与实现泄漏

### 先划清：语义承诺与实现泄漏

消息接口首先应定义客户端可依赖的**业务语义**，而不是让客户端绑定某次存储或投递实现。客户端真正关心的是：

- 一条带稳定 `message_id` 的消息是否被系统接受；
- 接受后是仅进入内存，还是已经持久化；`200 accepted_in_memory` 不等于未来一定可查询为 `stored`；
- 同一 `message_id` 重复提交时，是否明确返回 `409`，而非再次产生副作用；
- 发送者或查询者不属于该会话时，是否返回 `404`；
- 超时、连接中断后，本次操作结果是否**未知**，以及能否按 `message_id` 查询最终状态；
- 用户补拉历史时，能否在授权范围内获得权威消息记录。

相反，下列内容属于可替换的内部决策，不应成为 API 承诺：

- 数据库自增序号、消息表名、分库分表规则；
- broker 的 partition、offset、重试主题；
- 缓存键、事务批次、消费者组或归档位置。

例如，不能把 Kafka offset 当作用户游标：分区调整、重放、迁移都会改变其含义。对外应提供稳定的历史游标或按时间、消息 ID 查询；客户端“25 小时补拉”也必须经过成员权限校验，并读取权威历史，而非从内部 offset 推导。

信息隐藏不是模糊失败原因。实现细节可以隐藏，但 `accepted_in_memory`、`stored`、`409`、`404` 与“结果未知”是客户端恢复流程所必需的语义边界。

### 发送接口应暴露哪些状态

### 发送接口应暴露哪些状态

泄漏式接口把内部实现当成客户端契约，例如：

`POST /topics/orders/partitions/7/messages → { "offset": 38192, "table": "msg_p7" }`

这看似精确，实际含义脆弱：分区扩缩容、重平衡、迁表、切换 broker 后，`7`、`38192` 与 `msg_p7` 都可能失去原语义。更糟的是，客户端会据此构造“从 offset 补拉”的用户游标，绕过权限、保留期和历史重放规则。

语义型接口应返回稳定身份与可理解状态：

`POST /conversations/{id}/messages → 202`

`{ "message_id": "msg_...", "status": "accepted_in_memory" }`

其中 `accepted_in_memory` 表示服务已接收并进入本进程或可靠队列的待持久化流程，但尚不能承诺历史查询可见；后续状态可变为 `stored`，表示已写入权威历史，可被授权成员查询、补拉和审计。客户端应以 `message_id` 查询结果或订阅状态变化，而不是猜测底层 offset。

状态与错误也必须区分：

- `409`：相同幂等键或 `message_id` 已存在，返回既有消息结果；
- `404`：会话不存在，或调用者不是成员；不得借此泄露成员关系；
- `202`：已受理但尚未持久化；
- 超时：结果可能未知，不能笼统视为失败，更不能一律包装为 `500`。

请求 `context` 被取消，也不必然意味着已提交的数据库事务会回滚：服务端可能已完成写入，只是响应未送达。因此客户端应使用稳定的 `message_id` 重试，并查询其最终状态。25 小时后的补拉必须经权限校验并读取权威历史；内部 offset 只能服务存储与消费实现，不能成为用户可见协议。

### 确认点决定错误与未知结果

### 确认点决定错误与未知结果

一次“发送消息”并非只有成功或失败，而是会跨越多个确认点：

1. **内存接收**：服务已完成鉴权、成员关系校验与基本格式校验，并把消息交给进程内队列。此时可返回 `200 accepted_in_memory`，其含义只是“当前实例已接收”，不等于消息已经持久保存。
2. **数据库提交**：消息记录及其稳定的 `message_id` 已在权威数据库事务中提交。只有越过此点，系统才能可靠承诺未来可查询、可补拉。
3. **异步存储完成**：例如写入搜索索引、对象存储或下游投递完成。这应建模为可查询的后续状态 `stored`，而不应迫使请求同步等待全部链路。

超时与 `context` 取消尤其容易产生“结果未知”。客户端断开或服务端 `context` 被取消，可能发生在数据库提交之前，也可能发生在提交之后但响应尚未来得及写回。因此，取消请求**不必然回滚已提交的数据库事务**；若服务无法确定提交是否发生，应返回可表达未知的结果，而不是笼统包装为 `500`。

解决方式是由客户端提供稳定且可重试的 `message_id`。同一 ID 已存在时返回 `409`；用户不是会话成员时返回 `404`；超时后客户端用该 ID 查询最终状态。这样，重试不会制造重复消息，未知也能被后续查询收敛为“未保存”或“已存储”。

### 历史补拉不能把 offset 交给用户

### 历史补拉不能把 offset 交给用户

客户端离线 25 小时后重新连接，真正需要表达的是“从我上次确认的位置继续获得我有权看到的消息”，而不是“从 broker 的 offset=123456 开始读”。`offset` 属于分区日志的物理位置：扩容、迁移、压缩、重放或存储替换都可能改变其含义；把它作为用户游标，会把内部拓扑永久绑进 API。

补拉接口应先验证调用者仍是会话、群组或频道成员；无成员关系时返回 `404`，而不是借由“空列表”泄露历史是否存在。确认权限后，查询应来自权威历史：已持久化消息库、可验证的事件历史或逻辑消息流，而非临时从 broker offset 拼装用户记录。

推荐使用稳定、单调的逻辑游标，例如服务端签发的 `history_cursor`：

`GET /conversations/{id}/messages?after={history_cursor}&limit=100`

返回中包含：

- `messages`：按逻辑顺序排列的可见历史；
- `next_cursor`：继续读取的稳定续传点；
- `has_more`：是否还有可读取历史；
- 可选的 `watermark`：本次读取所观察到的历史边界。

游标应绑定会话、排序规则和权限范围，并可签名或编码，防止客户端伪造、跨会话复用。它不必暴露数据库主键、分表名、分区号或消息队列位置。

若 25 小时已超过保留期，应明确返回“游标过期”或“历史不可用”的业务错误，并告知客户端执行全量同步、从指定时间重建，或展示可获得的最早消息；不能悄悄从最新位置开始，制造无声丢失。历史补拉的承诺应是：在当前权限与保留策略下，从稳定逻辑位置读取权威历史，而不是读取某个易变实现细节。

### 用变更冲击检验模块边界

### 用变更冲击检验模块边界

判断接口边界是否合理，一个直接方法是设想内部发生变更：如果客户端必须跟着修改请求参数、解析规则或游标含义，说明实现细节已经泄漏。

- **分库分表或表名迁移**：消息从 `message_2024_01` 迁到冷热分层存储，客户端不应知道、更不应传入表名。接口只接受会话、内容与稳定的 `message_id`，查询也只按用户可理解的消息标识和时间范围进行。
- **重分区或 broker 迁移**：从 8 个分区扩到 64 个分区、替换消息队列时，`partition`、`offset` 都可能失效。因此不能把 offset 设计成用户“从此处继续读”的游标；客户端 25 小时后补拉，应依据有权限访问的权威历史，以消息时间、稳定消息 ID 或服务端签发的逻辑游标查询。
- **重试与去重**：网络超时后，服务端可能已提交数据库事务，只是响应未送达。`context` 取消不等于事务必然回滚。客户端应以相同 `message_id` 重试或查询结果；服务端返回同一消息的既有结果，而非重复插入。
- **存储迁移期间**：内部可经历“已接受、异步持久化、已存储”等阶段，但必须公开有业务意义的差异：`200 accepted_in_memory` 表示已接收但尚未保证持久化；后续可查询到 `stored` 才表示进入权威历史。

相反，以下结果不能因“内部复杂”而隐藏：重复 ID 应返回 `409`，非成员或无权访问应返回 `404`，超时后的提交结果未知应明确可查询，而不是一律包装成 `500`。好的模块边界让实现可以自由重构，同时让客户端始终知道：请求是否被接受、是否已持久化、是否重复，以及未知时如何恢复。

> **要点** — 隐藏可变存储机制，公开可判断的业务状态、权限错误与不确定结果，才能让接口在内部演进中保持稳定。

消息接口的价值不在于“能调用”，而在于把存储、投递与失败处理的复杂性封装在稳定的语义承诺之后。

### 从公开承诺识别实现泄漏

### 从公开承诺识别实现泄漏

消息发送接口应承诺的是业务结果，而非某次底层写入的物理坐标。调用者真正关心的通常是：事件是否被系统接受、是否获得可追踪的事件标识、失败是否可判定、重试是否会造成重复，以及何时可以安全推进本地业务状态。

若公开接口返回 `KafkaPartition`、`Offset`，调用者很容易据此建立错误依赖：把分区号当作业务分片、把 offset 当作全局顺序号或确认凭据。随后一旦改为按键重分区、切换消息系统、引入中继主题，甚至仅调整分区数量，业务代码和合同都会被迫修改。物理位置本应只属于投递模块。

同理，返回 `MongoDocument` 会使调用者了解集合结构、`_id` 生成方式、字段命名和持久化时机。调用者可能直接保存文档 ID、读取内部状态，或据此补偿；将来改用关系库、事件存储或将消息元数据独立存放时，迁移便不再局限于模块内部。

更合适的接口可返回业务语义明确的结果，例如：

- `事件ID`：用于审计、幂等查询与关联追踪；
- `接收状态`：如“已持久接收”“已拒绝”，而非“已写入第 3 分区”；
- `确认句柄`：仅当调用者确实需要等待后续处理时提供，且定义其完成语义；
- `领域错误`：区分参数非法、重复提交、暂时不可用与未知结果。

关键判断是：若替换 Kafka、MongoDB 或内部表结构后，调用者仍应按原方式工作，该信息就不该出现在公共返回值中。公开合同应描述“系统承诺了什么”，而不是“当前实现把它放到了哪里”。

### 语义型接口与空泛参数的双重风险

### 语义型接口与空泛参数的双重风险

接口泄漏实现细节与接口缺少语义，都会把本应由模块承担的复杂性转移给调用者。

- **暴露分区、偏移量、表名**：若 `Publish(topic, partition, offset, payload)`、`Save(table, document)` 成为公共接口，调用者就必须知道 Kafka 的分区策略、MongoDB 的集合结构及其迁移时机。之后改为按租户分区、拆表归档或更换消息中间件，不只是基础设施模块修改，所有调用点及其测试都要随之重写。更危险的是，调用者可能把 offset 当作业务确认点，而它其实只是某个消费实现的游标。

- **只收发 `map[string]any`**：这看似不绑定存储，却同样空泛。字典无法表达“这是成员已加入事件”“事件唯一标识是什么”“何时可确认”“确认的是已持久化、已投递还是已被消费”。字段名、类型转换、必填规则和幂等键会散落到各处；漏写 `seq`、误用 `groupId` 或忽略确认状态，编译器和契约都难以发现。

- **语义型接口**：公共接口应描述业务承诺，而非传输载体。例如 `发布成员加入事件` 接收结构化事件，返回明确的投递结果：`已持久化`、`可重试`、`重复已接受` 或 `未知结果`。确认令牌可以是领域级的 `事件编号`，而不是 Kafka offset；订阅方收到的是 `成员变更`，而不是 Mongo 文档。

因此，大群扇出改为异步批次、成员历史规则改为“仅新成员可见”时，应修改扇出策略模块、历史可见性规则及其契约；调用者仍只表达“加入成员”“查询可见历史”。测试也应覆盖端到端语义：重复提交是否幂等、数据库成功而 E9 发送失败如何恢复、确认未知时是否可安全重试，而非仅断言某个 mock 被调用一次。

### 把校验、排序与投递收进深模块

### 把校验、排序与投递收进深模块

设“成员加入大群”需要完成：校验成员资格、为该群分配递增序号、写入成员历史库、发布 `E9` 事件。若接口拆成五个薄包装：

- `ValidateMember(...)`
- `NextSequence(...)`
- `InsertHistory(...)`
- `PublishE9(...)`
- `Rollback(...)`

调用者便被迫编排：

`校验 → 分配 seq → 写历史 → 发事件 → 失败时补偿`

这不是复用，而是把业务事务和失败边界泄漏给每个调用点。调用者必须回答一系列本应由模块负责的问题：

- 历史写入成功、`E9` 发布失败时，是否重发、补偿还是标记待投递？
- 序号已分配但校验后续失败时，是否允许序号空洞？
- 并发加入时，`seq` 的唯一性、顺序性由谁保证？
- 重试 `PublishE9` 时，消费者如何避免重复处理？
- 群规则从“所有成员可加入”变为“禁止曾被移除者加入”时，历史查询应插在什么位置？

深模块应提供一个语义完整的操作，例如：

`JoinGroup(ctx, groupID, memberID) -> JoinResult`

其合同不是“依次调用若干存储函数”，而是：成功后成员历史具有确定顺序，并最终可观察到对应的 `E9`；重复请求不会产生重复历史或重复业务效果；失败结果明确区分“未接受”“已接受但待投递”“已完成”。

实现内部可采用事务外盒、消息表、幂等键和后台投递器，把“写库成功但发布失败”收敛为可恢复状态，而非要求调用者猜测补偿顺序。这样，当大群扇出策略、历史保留规则或事件载荷演进时，主要修改集中在该模块及其 `JoinGroup` 合同；调用方仍只表达“让成员加入群”，不依赖分区、表名、序号表或投递重试机制。

### 用变化冲击矩阵检验模块边界

### 用变化冲击矩阵检验模块边界

判断模块边界是否成立，不要只看当前调用是否方便，而要问：业务规则变化时，修改能否被限制在少数拥有该规则的模块内。

以“向大群发布事件 $E9$”为例，可建立变化冲击矩阵：

| 变化 | 应修改的内部模块 | 应调整的合同 | 不应修改的调用方 |
|---|---|---|---|
| 小群逐成员写入改为批量扇出、异步物化或按需拉取 | 扇出策略、投递任务、消息存储实现 | `Publish` 的投递保证、可见性时机、查询一致性 | 发布者、普通收件箱读取者 |
| 新成员只能看到加入后的消息 | 成员资格历史、可见性判定、查询过滤器 | `ListMessages` 应以“当前成员资格”还是“历史资格”为准 | 发送消息的业务流程 |
| 新成员可回看最近 30 天历史 | 历史窗口策略、索引、授权查询 | 返回范围、分页中的历史边界 | 调用者不应自行按时间过滤 |
| 被移出群的成员保留既有消息但不可见新消息 | 成员区间记录、消息可见性规则 | 可见性以 `joinedAt/leftAt` 区间计算 | 调用者不应保存成员快照再筛选 |

理想合同表达业务语义，例如 `Publish(groupID, command)` 返回可追踪的消息标识或确认状态，`ListVisibleMessages(memberID, groupID, cursor)` 保证只返回该成员依法可见的消息。它不应暴露 `KafkaPartition`、`Offset`、Mongo 集合名，也不应让调用方拿到 `map[string]any` 后自行猜测“是否已确认”。

若策略变化迫使所有调用方依次执行“校验成员→分配序号→写数据库→发送 $E9$”，说明规则散落在五个薄包装之间；重试、幂等、部分失败与可见性将无法统一。正确的冲击范围应集中于消息域内部，而非扩散到每个业务入口。

测试也应验证矩阵：端到端覆盖大群异步扇出、重复发布、存储成功但投递失败、成员加入/退出边界；契约测试固定“可见消息”的语义，而不是只断言某个 mock 被调用了几次。

### 以确认点和失败变式设计测试

### 以确认点和失败变式设计测试

消息模块的测试不应停在“是否调用了 `Publish` 两次”或“仓储是否被调用一次”。这类模拟对象断言只能证明包装器按预期互调，不能证明系统在失败、重试和规则演进下仍保持业务语义。

先把可观察的确认点写入用例：例如“成员 A 最终收到 E9，且同一 `seq` 只出现一次”“数据库中事件记录与已发布事件具有相同业务标识”“发布失败后，调用方得到可重试结果而非误判成功”。端到端用例应覆盖完整路径：

1. 校验输入与成员历史规则；
2. 为事件分配单调或可比较的 `seq`；
3. 持久化业务状态与待投递事件；
4. 投递 E9；
5. 消费端确认、去重并更新确认点。

尤其要构造失败变式，而非只测试全成功路径：

- **写库后发布失败**：事件不得永久丢失；重试或后台投递应最终发布同一业务事件，不能重新分配 `seq`。
- **发布成功但响应丢失**：生产者重试可能产生重复消息；消费者必须按事件标识或确认点幂等处理。
- **部分成员投递失败**：大群扇出不能让已成功成员重复收到不一致的历史；失败成员应可独立补偿。
- **规则在重试期间变更**：成员资格或历史可见性改变时，合同必须明确按“事件产生时快照”还是“投递时规则”处理。

契约测试则验证模块边界：调用者只提交业务事件和幂等键，消息模块返回业务确认结果，不暴露分区、偏移量、集合名或文档结构。若替换 Kafka、MongoDB 或扇出策略，以上端到端断言应继续成立；需要改变的应是消息模块内部及其契约版本，而不是每个调用者的编排代码。

> **要点** — 稳定接口应暴露业务语义、确认点与不确定结果，隐藏存储、分区和内部编排细节。

通过变更冲击清单检验IM消息模块边界：分区、表名和投递机制应留在内部，客户端只依赖稳定的消息语义与结果合同。

### 先划定证据边界与讨论对象

### 先划定证据边界与讨论对象

当前可确认的证据仅覆盖一条最小异步链路：`send.go` 在选定分支中调用 `MsgToMQ`，随后返回；消费者从消息队列取得消息，并通过 `BatchInsertChat2DB` 写入 MongoDB。它至多证明：

- 发送端存在“入队后返回”的路径；
- 消费端存在“批量消费后入库”的路径；
- 队列与数据库处于该实现链路中。

但不能由此推出更强的架构结论。尤其不能断言：

- `send.go` 所在目录就是完整的消息模块或真实包边界；
- 返回即代表消息已持久化、已送达、已读，或获得任一端 ACK；
- `BatchInsertChat2DB` 与投递、重试、去重、顺序、事务构成同一原子操作；
- broker 可无代价替换，或 MongoDB 表/集合结构就是客户端应依赖的合同；
- 群成员历史规则、R9 待审消息、S3 未来权威源、E9 重投和 B 多端 ACK 已被这两段代码完整覆盖。

因此，本节讨论对象不是“从代码猜出全部系统”，而是据已知路径划分修改面：MQ 分区、主题、broker 类型、MongoDB 集合与批写策略属于内部实现；客户端可依赖的应是稳定消息语义，例如提交结果、消息标识、可见性状态、失败原因与确认规则。证据不足处必须标为待验证，而不能包装成既成合同。

### 把六类变化列入修改面清单

### 把六类变化列入修改面清单

判断模块边界，不能只问“代码改在哪里”，还要问“谁被迫重新理解系统”。可将六类变化逐项列入修改面：

- **R9 待审**：若消息先进入审核状态，再决定是否可见、可投递，则需要调整状态机、审核结果事件、失败原因与查询语义。`审核中/已拒绝`若对用户可见，就是客户端合同；审核队列、审核表及其分区策略仍是内部实现。
- **S3 未来权威**：某个未来数据源成为消息、会话或成员关系的权威来源时，要迁移写入归属、读模型同步、冲突裁决和回填逻辑。客户端只应依赖“消息与成员关系的最终语义”，不应知道权威数据位于哪个库、表或主题。
- **E9 重投**：重投会波及幂等键、去重窗口、顺序约束、死信处理及可观测指标。公开合同应明确“至少一次”还是“至多一次”、重复消息如何识别；重投次数、延迟策略和死信 broker 不应暴露。
- **broker 换型**：从一种消息 broker 迁到另一种，会改动生产、消费、确认、积压恢复和运维监控。若客户端必须改用新的 topic、分区键或 ACK 协议，说明基础设施细节已经泄漏。
- **成员历史规则**：新成员是否可见入群前历史，会影响消息查询、权限判定、历史快照与缓存失效。客户端可依赖明确的可见性规则，却不应依赖“成员历史表”或其过滤字段。
- **B 多端 ACK**：多设备已读、送达和离线补偿会改变 ACK 聚合、设备状态、回执事件及未读数计算。应公开每端还是每用户的回执语义，而非公开 ACK 存在哪张表、由哪个消费者聚合。

已观察到 `MsgToMQ` 返回、以及 Mongo 消费后 `BatchInsertChat2DB`，只能证明存在两段异步路径；它不能证明真实包边界、全部 ACK 规则、事务范围或 broker 可替换性。上述清单正用于防止把这些尚未证实的内部猜测写成公开合同。

### 区分内部实现、公开合同与迁移责任

### 区分内部实现、公开合同与迁移责任

判断模块边界时，关键不在“代码位于哪个包”，而在于某项变更是否迫使客户端修改。可用变更冲击矩阵分类：

| 变更项 | 应归属 | 客户端是否感知 | 迁移责任 |
|---|---|---:|---|
| 分区数、分区键、broker 换型 | 内部实现 | 否 | 服务端适配、回放与校验 |
| Mongo 集合/表名、`BatchInsertChat2DB` 写入批次 | 内部实现 | 否 | 存储迁移、双写或回填 |
| E9 重投次数、退避策略、死信处理 | 内部实现 | 不应依赖次数 | 服务端保证幂等与可观测性 |
| R9 待审状态、审核流转 | 公开消息状态语义 | 是 | 服务端兼容旧状态并说明转换 |
| S3 未来权威来源 | 数据权威与读取合同 | 可能 | 提供版本、回填和一致性策略 |
| 成员历史可见规则 | 公开授权合同 | 是 | 服务端执行历史裁剪，客户端刷新视图 |
| B 多端 ACK | 确认语义合同 | 是 | 明确 ACK 范围、聚合规则与缺失含义 |

客户端应依赖“消息被接受、是否可见、何时确认、失败是否不确定”等语义，而非“写入了哪个分区、哪张表、重试了几次”。例如，`MsgToMQ` 后返回只能证明请求进入所选异步路径；Mongo 消费端调用 `BatchInsertChat2DB` 只能证明存在批量落库路径。它们不能单独推出真实包边界、全部 ACK 定义、端到端事务，或 broker 是否可替换。

因此，迁移时服务端负责隐藏基础设施替换，并保持消息标识、幂等语义、状态机和错误结果兼容；客户端只在公开合同确有变化时升级。

### 用语义型发送接口隔离变化

### 用语义型发送接口隔离变化

泄漏式接口把基础设施细节直接交给调用方，例如：

`Send(topic, partition, tableName, payload)`

这会使客户端绑定 `broker` 主题命名、分区策略、Mongo 表结构乃至写入路径。一旦发生 `broker` 换型、分区重平衡、冷热表拆分或 `BatchInsertChat2DB` 调整，原本只想“发送消息”的客户端也被迫修改。更严重的是，调用方可能把“选定分区”误解为投递成功，把“指定表名”误解为持久化事务边界。

应用层应提供表达业务意图的接口，例如：

`SendMessage(发送请求) -> 发送结果`

其中请求至少包含：

- `会话标识`、发送者、接收者或群组：表达投递语义；
- `消息体`、消息类型、引用关系：表达内容语义；
- `客户端消息标识`：作为 E9 重投时的幂等键；
- `期望策略`：如普通发送、定时发送、仅在线投递，而非主题或分区；
- `追踪标识`：支持日志、链路追踪和问题定位。

结果也应描述可观察语义，而非内部步骤：

- `消息标识`与`受理状态`：表示服务是否接受该发送意图；
- `去重结果`：新建、已存在或请求冲突；
- `投递状态查询凭据`：供客户端后续观察，而不是承诺同步入库；
- 明确的失败类别：参数非法、无权限、会话不存在、暂时不可用等。

固定分支中 `MsgToMQ` 返回、以及消费者调用 `BatchInsertChat2DB`，只能证明存在“先异步投递、后异步落库”的阅读证据；不能据此把主题、分区、集合名，或“返回即已持久化”写成公开合同。R9 待审、S3 未来权威、成员历史规则和 B 多端 ACK 都可能改变内部处理链。客户端合同应稳定地承诺“消息意图被受理、可幂等重试、状态可观察”，其余实现细节留在模块内部迁移。

### 以Go消费侧接口安排迁移路径

### 以 Go 消费侧接口安排迁移路径

消费方不应依赖 `topic`、分区号、Mongo 表名或 broker 类型，而应声明完成业务所需的最小能力。例如，消息落库消费者真正关心的是“取得可处理消息”和“提交处理结果”：

```go
type MessageSource interface {
    Next(ctx context.Context) (Message, error)
    Commit(ctx context.Context, id string, result ConsumeResult) error
}

type HistoryStore interface {
    BatchInsert(ctx context.Context, msgs []Message) error
}

type AckPublisher interface {
    Publish(ctx context.Context, ack AckEvent) error
}
```

这里的 `MessageSource` 是可迁移边界：当前实现可从 MQ 拉取；broker 换型时改为 Kafka、NATS 或其他实现；E9 重投时包装为带幂等键、重试次数和死信状态的适配器。`HistoryStore` 隔离成员历史规则：S3 成为未来权威来源后，可由“写 Mongo 历史”迁移为“写权威事件流，再投影历史视图”，而消费流程不必改写。

需要明确分类修改面：

- **内部实现**：`MsgToMQ` 后的投递细节、消费批次大小、`BatchInsertChat2DB`、分区路由、表结构、重投队列及 broker 客户端。
- **客户端公开合同**：消息标识、发送结果状态、可见性语义、失败码、顺序与去重承诺、ACK 是否代表“服务端已接收”还是“多端已确认”。
- **迁移层**：旧消息模型到新权威模型的转换、历史成员规则补偿、双写/回放、ACK 聚合与版本兼容。

多端 ACK 不应直接侵入发送接口。可先将 ACK 记录为独立事件，由 `AckPublisher` 适配旧的单端确认与新的设备级确认；待客户端协商版本完成后，再提升公开合同。已知的“发送后入 MQ”“MQ 消费后批量入库”仅说明两段异步路径存在，不能据此假定 ACK、事务边界或具体包结构；接口设计应保留这些实现选择。

> **要点** — 模块边界应围绕变化决策建立：内部可换实现，外部只承诺稳定语义、确认点与不确定结果。

消息接口若要求调用者填写分区、表名或偏移量，内部存储策略便成为公开承诺。本节以IM发送与历史补拉为例，训练识别泄漏、设计语义边界并评估变更冲击。

### 模块边界：隐藏会变化的决策

### 模块边界：隐藏会变化的决策

模块接口承诺的是**调用者可依赖的语义**，而不是内部如何完成。例如“向会话发送消息”“从某序号后补拉消息”是语义；“写入 `message_03` 表”“路由到分区 7”“查询 offset=128”则是实现。

Parnas 的信息隐藏强调：应把**最可能变化、最难局部控制的设计决策**藏在模块内。消息系统中的分库分表规则、分区数量、主从切换、索引结构、冷热迁移都可能调整；一旦出现在接口参数中，调整便从内部重构变成全体调用方迁移。

Ousterhout 则要求模块具有“深度”：接口简单，内部承担复杂性。深模块可以提供：

- `发送消息(会话ID, 发送者ID, 内容)`
- `拉取历史(会话ID, 起始序号, 数量)`

其内部自行决定路由、持久化、排序与去重。相反，`写入消息表(表名, 分区ID, offset, 内容)` 是浅模块：调用者仍须理解并承担存储复杂度。

判断某个参数是否应暴露，可问：

1. 调用方的业务语义是否真正需要它？
2. 改变它的规则时，是否希望调用方同时修改？
3. 不暴露它，模块能否自行推导或维护？

若答案分别是“否、否、能”，它就是应隐藏的实现细节。好的边界不是隐藏所有信息，而是只公开稳定的业务承诺，把易变决策留在拥有该决策的模块内。

### 发送接口：从分区参数到业务语义

### 发送接口：从分区参数到业务语义

坏接口把“如何存”伪装成“要做什么”：

`Send(partition, table, seq, senderID, payload)`

调用者必须知道分区规则、消息表、序号生成方式，甚至自行选择写入位置。这样一来，分库分表、冷热迁移、按会话改分区、由自增序号改为雪花 ID，都会变成破坏性接口变更。`partition`、`table`、内部 `seq` 都属于实现，不是发送者的业务意图。

语义接口应描述调用者真正关心的事实：

`SendMessage(ctx, senderID, recipient, content, clientMessageID)`

其中：

- `recipient` 表示收件人或会话，而非某张表；
- `content` 表示待发送内容，而非待插入的行；
- `clientMessageID` 表达重试去重需求：同一发送意图重复提交，应返回同一消息结果，而不是重复写入；
- 返回值可包含服务端消息 ID、会话内序号 `seq`、发送时间和投递状态，但不应返回分区名。

`seq` 是否可以公开，取决于其含义。若它承诺“会话内可排序、可用于补拉”，它是领域语义，可作为游标返回；若它只是数据库 offset、Kafka 位点或表内自增键，则不应暴露。更稳妥的历史接口是：

`ListMessages(conversationID, afterSeq, limit)`

这里的 `afterSeq` 是“已确认看到会话中的哪条消息”，不是“从某个存储分区的 offset 开始读”。

这体现了 Parnas 的信息隐藏：模块应隐藏最可能变化的设计决策。也符合 Ousterhout 的深模块观点：接口越小，内部可替换的复杂性越多。调用者发送的是“向该会话发送此消息”，服务端自行完成鉴权、路由、分区选择、持久化与幂等判定；调用者不应被迫参与这些实现决策。

### Go包与消费侧接口：依赖方向由谁决定

### Go包与消费侧接口：依赖方向由谁决定

在 Go 中，接口不应由“实现者有哪些能力”决定，而应由“调用者完成任务需要什么”决定。发送消息的上层通常只需要语义动作：

```go
type Sender interface {
    Send(ctx context.Context, req SendRequest) (Message, error)
}
```

它不应依赖 `MySQLSender`、`KafkaSender`，更不应要求填写 `tableName`、`partition` 或内部 `seq`。接口放在消费侧包中，依赖方向便是：实现层依赖业务语义，而业务层不反向依赖存储细节。这符合 Parnas 的信息隐藏：容易变化的设计决策留在模块内部；也符合 Ousterhout 的思想：接口应提供高层抽象，而非暴露实现复杂度。

但“接口小”不等于“所有复杂性都能隐藏”。例如 R9 若要求客户端获得“会话内严格连续、可检测缺口、可在 25 小时后补拉”的序列语义，那么 `seq` 已经是跨层可观察事实。服务端可以隐藏它来自数据库自增列、Redis 计数器还是分区内 offset，却不能假装不存在顺序与缺口：客户端取消请求后，无法仅凭网络结果判断消息是否已写入；重试可能得到 `409`（重复）而非新的成功；非成员查询历史应是 `404`，避免泄露会话存在性。  

因此，应隐藏“实现编号”，保留“业务承诺”。例如历史接口返回 `nextSeq`、消息接口支持幂等 `clientMsgID`，而不返回表名和 offset。若未来把单表改为分库分表，或把 offset 改为逻辑序号，前者不应影响调用方；若修改连续性、去重窗口或补拉期限，则必须视为 API 语义变更。OpenIM 等实现资料最多可作为其当前字段和行为的证据，不能自动证明这些字段就是不可变的公共契约。

### 确认点与历史补拉：错误不能替代结果语义

### 确认点与历史补拉：错误不能替代结果语义

发送消息不能只返回“成功/失败”。尤其在请求被取消、连接超时或服务端响应丢失时，调用者面对的是**结果未知**：消息可能未提交，也可能已持久化并分发。此时把错误直接解释为“发送失败”会诱发重试，而重试又可能产生重复消息。

因此，发送接口应以客户端生成的幂等键定义确认点，例如：

`发送消息(会话标识，内容，客户端消息标识) → {服务端消息标识，序列号，状态}`

- 首次成功：返回已接受及其 `seq`。
- 相同幂等键再次提交：返回 `409`，但响应必须携带原确认结果，或提供“按幂等键查询结果”的语义；`409` 不应只表示模糊的“冲突”。
- 调用取消：返回“结果未知”，调用者应查询确认状态或使用同一幂等键重试，而非换一个标识重新发送。
- 非会话成员：返回 `404` 可避免暴露会话存在性；它表达“对此调用者不可见或不可操作”，而不是数据库中绝对不存在。

历史补拉也应暴露业务顺序而非存储位置。`offset` 是某个分区、日志或表中的物理游标，扩容、迁移、分片合并后含义可能改变；`seq` 则是会话内可比较、可续读的逻辑序列。接口可采用：

`拉取历史(会话标识，起始seq，数量) → {消息列表，下一个seq，是否还有更多}`

若产品承诺“最近 25 小时可补拉”，这是一项可观察的语义：服务端须保证该时间窗内按 `seq` 查询仍可判定，超过窗口则明确返回“已过期/需全量同步”，不能以空列表伪装“没有新消息”。这样，取消、重复、权限不足和历史缺口分别具有明确含义，不再由调用者猜测底层执行结果。

### 变更冲击矩阵：检验接口是否泄漏实现

### 变更冲击矩阵：检验接口是否泄漏实现

用“内部变化后，调用者是否必须改代码”检验接口边界：

| 内部变更 | 泄漏型接口的冲击 | 语义型接口的冲击 |
|---|---|---|
| 分库分表 | `table`、`db` 参数失效 | 无；服务自行路由 |
| 分区迁移 | `partition`、`offset` 失效 | 无；按会话与游标续拉 |
| 排序从 `seq` 改为时间/混合键 | 客户端比较规则失效 | 返回不透明游标 |
| OpenIM 替换或降级 | 暴露其表、字段、错误码即破坏兼容 | 仅承诺业务语义与证据范围 |

**基础题（答）**  
1. `Send(uid, partition, table, body)`泄漏什么？答：存储路由。  
2. `List(offset, limit)`必然泄漏吗？答：若 offset 是物理位移，泄漏。  
3. `cursor`为何较安全？答：其含义可由服务演进。  
4. `seq`等于数据库自增 ID 吗？答：不应承诺。  
5. 重复发送返回 `409` 表示什么？答：幂等键已被接受或冲突。  
6. 非群成员返回 `404` 合理吗？答：可隐藏资源存在性。  
7. R9 能隐藏吗？答：若协议已要求客户端填写 R9，则不能。  
8. OpenIM 文档能证明什么？答：公开接口语义，不能证明内部表结构。

**推演题（答）**  
1. 分区迁移后客户端重试失败，根因？答：分区成为 API 参数。  
2. 取消请求后消息是否送达？答：不确定，应查询幂等结果。  
3. 补拉 25 小时为何不能靠 offset？答：压缩、迁移会改变物理位置。  
4. `seq` 出现空洞是否错误？答：不一定；只应承诺单调或可续读。  
5. 返回表名能否帮助排障？答：会把运维细节变成兼容承诺。  
6. OpenIM 返回码可直接透传吗？答：不宜，应映射业务错误。  
7. 游标跨版本失效怎么办？答：定义失效语义并允许重新同步。  
8. 排序改造的最低兼容条件？答：历史游标仍可解释，或明确版本化。

**决策题（答）**  
1. 新接口选 `offset` 还是 `cursor`？答：`cursor`。  
2. 是否让 Go 调用方传分区？答：否；接口应由消费侧定义业务能力。  
3. 重复发送如何设计？答：客户端幂等键＋查询结果接口。  
4. 权限失败选 `403` 还是 `404`？答：需隐藏成员关系时选 `404`。  
5. 迁移期间是否双写细节外露？答：否，仅内部实现。  
6. 证据不足时能否断言 OpenIM 使用某表？答：不能；标注为未知。

> **要点** — 好接口承诺业务结果、确认状态与错误语义，而非分区、表名、offset等可能变化的内部决策。
