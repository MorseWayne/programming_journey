# 07.05 审阅记录：缓存服务的持久与故障

## 教学重组

- 明确当前 S2 `200 accepted_in_memory` 仅为进程内受理；未来 S3 DB 权威 `c-a.seq9`、Redis 派生 `preview:c-a`、临时 presence/rate 和 DB 事务 `next_seq` 是不同角色。Redis 故障不能反向改写现有接口合同。
- 纸上 t0 RDB 存预览 seq8→t1 DB 提交 seq9→t2 Redis 从旧 RDB 恢复 seq8，且本题旧键 TTL 尚未到。能恢复键不说明值新鲜；恢复出“在线”也不证明旧进程连接仍在。
- 无持久重启空缓存，预览在未来 S3 中可从 DB 重建；presence 标未知并等新连接/心跳；临时限流按风险合同选择重置/收紧，`next_seq` 绝不能因 Redis 清空而归零。
- AOF 的 fsync 模式按 Redis 官方文档说明不同掉电窗口；完整恢复出的派生值仍要与权威源核对。Redis 默认异步复制，Sentinel 切换到落后副本可能回退预览；`WAIT` 不是强一致切换保证。
- 冷缓存沿 07.04 的持续 1000/s 请求与 DB 安全 200/s 纸上预算，未控制时净积压 800/s；需要有界回源、预热和明确降级，权限旧许可不准作为可用性回退。

## 技术修订

- 原稿部分段落把当前 S2 受理与 Redis 实例重启绑成同一已部署路径；正式页只称 S2 当前进程内存受理，不推断其用 Redis，也不借未来 S3 DB 为 S2 消息补持久性。
- 原稿一处将 RDB 恢复出的旧在线值归为“可容忍”，后文又标未知；正式页统一为旧连接已失效、在线需新运行代次的连接/心跳证据，缓存缺键或旧键不能证明当前在线/离线。
- RDB/AOF 恢复仅说明 Redis 找回某时刻数据；即使持久文件完整，预览仍可能是比权威 DB 旧的 seq8。持久与新鲜、复制与副本可读、Sentinel 切换与已确认写保留均不能画等号。
- `WAIT` 只增强副本传播确认，官方明确不能把 Redis 变强一致 CP 系统；缓存写入若变权威，必须重审持久、复制、故障切换、备份、容量/逐出及业务确认。
- 分片分散不同键，不自动拆开 `preview:c-g` 单个热键；10000 成员大 Set 的迁移/全取成本需实测，不凭规模数字编造字节和 P95。
