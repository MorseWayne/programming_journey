Redis恢复后先别问“数据还在不在”，而要先按状态角色判断：哪些可丢，哪些必须由权威来源重新确认。

### 先按状态角色划定可丢边界

### 先按状态角色划定可丢边界

以会话 `c-a` 为例，恢复策略不能由“Redis 是否持久化”统一决定，而应先标记状态角色：

- **DB 权威消息**：未来 S3 中 `c-a` 的消息已提交至 `seq=9`，这是恢复后唯一可直接信任的会话事实。即使 Redis 丢失全部数据，服务仍应从 DB 重建消息视图；`06.12` 的 `next_seq` 也仍以 DB 为准，不能根据缓存中残留的序号继续分配。
- **Redis 派生预览**：如 `preview:c-a`，只是由权威消息提取的最近一条摘要。进程重启、设备掉电或副本切换后可直接丢失；首次读取时可回源 DB 的 `seq=9` 重算，或异步预热。它短暂陈旧影响展示，不得影响消息顺序、未读语义或写入结果。
- **在线状态**：如 `presence:u-a:dev-1`，描述的是租约期内的观察结果，不是用户永久事实。重启后应视为未知或离线，等待设备心跳重新登记；不能因旧副本恢复出一个键，就断言设备仍在线。
- **限流计数**：临时 `rate` 计数允许在故障后归零、缩短窗口或保守重建，但必须明确代价：归零会放宽短时限额，保守重建会误拒正常请求。它只能保护资源，不能成为业务正确性的依据。

因此，S2 的 `200 accepted_in_memory` 只说明“已被内存接受”，并不具备 S3 的 DB 提交含义。若 Redis 在该消息落库前重启或掉电，该消息可以丢失；恢复后客户端必须按确认协议重试，而服务端以 DB 中实际存在的序列状态裁定结果。

### 四类故障改变的不是同一份状态

### 四类故障改变的不是同一份状态

故障名称相同地叫“Redis 挂了”，实际留下的状态缺口却不同。判断恢复策略时，应同时看：内存是否还在、已确认写入是否落盘、客户端连接是否连续，以及故障范围是否跨分片。

- **Redis 进程重启**：同一台机器上的 Redis 被重启，内存中的 `presence:u-a:dev-1`、临时限流计数通常直接消失；若 `preview:c-a` 依赖快照或追加日志，可能恢复到较早版本。未来 S3 中 DB 已提交的 `c-a` 消息 `seq=9` 不受影响，预览应由 DB 或消息流重建。不能把重启前 S2 返回的 `200 accepted_in_memory` 当成已恢复的权威事实。

- **设备掉电**：除内存丢失外，还要考虑尚未刷盘的追加日志、操作系统页缓存和最后一次快照之间的窗口。即使 Redis 配置了持久化，也可能只恢复到某个较早时点；临时状态可接受丢失，但若 Redis 曾被误用为消息确认依据，就会暴露确认早于持久化的缺陷。

- **副本切换**：主节点故障后提升副本，缺口通常是主节点已接收、却尚未复制到新主的最后一段写入。此时旧主曾返回成功并不等于新主可见；`preview` 可按 DB 的最高连续 `seq` 回填，`presence` 应要求设备重新心跳，限流计数可从零或保守值重新开始。

- **分片故障**：影响范围取决于键落在哪个分片。`preview:c-a` 不可读不代表 `presence:u-a:dev-1` 也丢失；跨分片流程更不能假设原子恢复。恢复程序应逐键按角色处理，而不是把整个 Redis 集群视为一份统一状态。

因此，可接受丢失的是派生预览、在线标记与临时计数；不可接受丢失的是 DB 中消息及 `next_seq` 所定义的顺序权威。

### RDB与AOF只是在选择丢失窗口

### RDB与AOF只是在选择丢失窗口

RDB 与 AOF 解决的是“Redis 重启后能带回多少内存状态”，而不是“Redis 中的状态因此变成可信事实”。

- **RDB 点时快照**：只保留某个快照时刻的全量视图。若最近一次快照在 $t_0$，实例在 $t_1$ 掉电，则 $(t_0,t_1]$ 的写入可能全部丢失。它适合可重建的 `preview:c-a`、`presence:u-a:dev-1`，恢复快、文件紧凑，但丢失窗口通常按快照间隔计。
- **AOF 每秒刷盘**：追加写命令并约每秒 `fsync` 一次；故障时通常可能丢失约一秒内已接受的写入。对临时限流计数而言，这意味着恢复后额度可能略微回退，应允许短暂多放行或重新计窗。
- **AOF 每次写入刷盘**：每条命令确认前都刷盘，掉电丢失窗口最小，但写入延迟和吞吐成本最高；即便如此，也不能用它承载未来 S3 中的权威 `c-a` 消息序列。
- **从不主动刷盘**：依赖操作系统落盘，性能较好但掉电丢失范围不可预测，只适合明确可丢的缓存。

无论选择哪种策略，`200 accepted_in_memory` 都只表示当前 Redis 进程接受过请求；它不能替代 S3 的 DB 提交，更不能据此推进 06.12 中仍由 DB 权威维护的 `next_seq`。副本切换或 Redis 恢复后，应以 DB 的已提交消息及序号重建派生预览、在线状态和限流窗口；持久化文件最多是加速恢复的旧副本，而非裁决冲突的依据。

### 切换后的旧预览必须回查源版本

### 切换后的旧预览必须回查源版本

`preview:c-a` 是消息流的派生视图，不是可独立裁决的事实。它通常由消费者根据会话 `c-a` 的消息内容、已读位置或摘要规则生成；真正可追溯的源仍是数据库中的消息 `seq` 与相应版本。

异步复制下，主 Redis 已写入的新预览未必已到副本；Sentinel 将副本提升为新主后，客户端可能读到较旧的 `preview:c-a`。这不表示数据库消息回退，只表示派生缓存发生了可接受的丢失或陈旧。设备掉电、进程重启也同理：预览即使从持久化文件恢复，也只能被视为“候选结果”。

`WAIT N T` 只能要求当前写入在超时前获得至多 `N` 个副本确认；它不能保证这些副本随后不会故障，不能替代跨故障域的持久提交，更不能把 Redis 中的预览提升为权威状态。因此，不能因 `WAIT` 返回成功就跳过源版本校验。

恢复或切换后，读取预览应携带其生成依据，例如：

`preview:c-a = { text, source_seq: 9, source_version: v9 }`

服务端以 DB 中会话消息的权威 `seq=9`（及消息版本）校验它：

- 缓存依据与 DB 一致：可直接返回预览。
- 缓存缺失、`source_seq` 落后或版本不符：从 DB 重建预览，再异步回填 Redis。
- 缓存声称更“新”却无法由 DB 证实：丢弃该缓存，不能反向覆盖 DB。

这也与 `next_seq` 仍由 DB 权威分配一致：缓存切换后可以暂时失去派生结果，但不能据旧预览推断下一条消息编号或消息事实。

### 用状态级恢复表指导冷启动

### 用状态级恢复表指导冷启动

Redis 冷启动、节点掉电或副本切换后，不应把“缓存未命中”统一当成数据库读取问题；必须按状态角色决定回源、降级与可接受丢失范围。

| 状态/键 | 权威来源 | 恢复方式 | 未恢复时行为 | 可接受丢失 |
|---|---|---|---|---|
| `preview:c-a` | S3 的消息 DB，权威为 `c-a` 的最高已提交 `seq=9` | 首次读取时按会话从 DB 重建，或由后台预热最近活跃会话 | 返回基于 DB 的预览，必要时短暂变慢 | 缓存内容可丢，消息事实不可丢 |
| `presence:u-a:dev-1` | 设备心跳/连接会话，不是 DB 历史记录 | 不从 DB 回填；等待设备下一次心跳、重连或网关重新上报 | 显示“未知/离线”，不可伪造在线 | 在线状态可短暂丢失 |
| 临时 `rate:*` 计数 | Redis 窗口内计数本身 | 不回源；重启后从空窗口重新计数，或进入保守限流窗口 | 优先保护服务，允许短时误限或限额重置 | 计数可丢，防护目标不可放弃 |

消息预览的回源要防止大量请求同时击穿 DB。可使用单飞锁：同一 `preview:c-a` 仅一个请求执行重建，其余请求等待短暂结果或读取旧值；重建值写入时加入随机过期抖动。对热点会话，可由恢复任务按最近访问列表限速预热，而不是启动时全量扫描。

presence 的关键是“不知道就承认不知道”。Redis 丢失后，不能依据旧 DB 登录记录恢复为在线；连接网关可在恢复期主动触发存活探测，但探测未完成前应降级为未知。

尤其不能把 S2 的 `200 accepted_in_memory` 解释成 S3 可从 DB 恢复：S2 仅表示消息曾被当前进程内存受理，若尚未持久化，进程掉电后该消息可能消失。只有 DB 已提交、并推进权威 `next_seq` 的记录，才可在 S3 冷启动后作为可信回源状态。

> **要点** — Redis恢复策略取决于状态角色；DB权威消息可重建派生缓存，副本切换与WAIT都不能替代版本校验。

Redis重启后的“有数据”不等于状态可信。应先辨别数据角色，再决定能否直接使用、必须校验或只能按策略重建。

### 先按状态角色判断能否丢失

### 先按状态角色判断能否丢失

判断 Redis 故障后能否继续服务，关键不在于“缓存是否恢复”，而在于该状态属于哪一种角色：

- **权威状态**：决定业务事实的最终依据，例如订单、余额、消息正文、权限授予记录。它必须由数据库、日志系统或专门的强持久存储承担；Redis 不应是唯一副本。若 Redis 中的值与权威源冲突，应以权威源为准。
- **派生状态**：可由权威状态重新计算或回填，例如文章预览、商品详情缓存、聚合计数、搜索索引片段。丢失会影响延迟和吞吐，但原则上不应改变业务事实。恢复时可缓存未命中后从数据库重建，或异步预热。
- **临时状态**：只描述某一时刻的在线协作或控制信息，例如 presence 在线状态、会话、分布式锁、限流计数、短期去重标记。它往往天然过期，丢失后不能简单“补回”；必须按风险策略重新判定。

因此，**无持久 Redis 重启后，全部内存状态都归零**：缓存键、过期时间、锁、在线标记、限流窗口都会消失。派生缓存可以从数据库重建；但“某用户是否在线”应视为未知，而不是默认在线或离线。限流器丢失计数后，也不能假装仍处于原窗口，应按业务风险选择放宽、保守拒绝、降级限额或切换到其他持久计数源。

先给状态定角色，才能决定它是“可丢后重建”、还是“丢后未知”、抑或“绝不能只放在 Redis”。

### 无持久重启：空缓存不是数据丢失

### 无持久重启：空缓存不是数据丢失

未启用持久化时，Redis 重启后通常以空实例启动。此时丢失的是缓存中的派生状态与短期控制状态，而不必然是业务数据；关键在于不同键代表的“事实”是否能从其他权威来源恢复。

| 数据类型 | 空缓存后的含义 | 推荐处理 |
|---|---|---|
| 预览、详情摘要、列表页缓存 | 缓存副本消失，数据库中的源记录通常仍在 | 缓存未命中后回源 DB，重新生成并写回；可采用单飞、互斥锁防止热点击穿 |
| 在线状态 `presence` | “在线”往往依赖心跳 TTL，Redis 清空后无法区分“确实离线”与“状态已遗失” | 一律视为**未知**，等待客户端重新心跳或重新建立连接；不要直接把未知解释为离线 |
| 限流计数、配额窗口 | 计数消失会放宽限制；直接重置可能造成突发流量、刷接口或配额绕过 | 按风险政策恢复：低风险接口可从零开始；高风险操作应临时收紧、降级到持久化限流或要求额外校验 |

预览缓存的键即使消失，`preview(id)` 仍可由 DB 中的正文、版本号和权限规则重建，因此空缓存主要影响延迟与数据库负载。应确保回源读取仍执行权限检查，不能因“缓存刚恢复”而返回未经授权的内容。

`presence(user)` 则不同：它不是 DB 中稳定保存的业务事实，而是“最近一段时间收到心跳”的暂态判断。Redis 清空后，正确语义是：

$$presence(user)=unknown$$

只有收到新的心跳、连接事件或其他可信信号后，才可恢复为在线或离线结论。

限流最需要显式选择策略。若接口涉及登录、验证码、支付、导出或写入，应优先保证安全性：宁可短暂更严格，也不要让重启成为绕过频率限制的手段。

### RDB快照只记录某个时刻

### RDB快照只记录某个时刻

RDB 是内存数据在某一时刻的快照，而不是数据库提交历史的逐条回放。设商品预览缓存是由数据库中的商品记录派生而来，其版本号为 `seq`：

- `t0`：Redis 执行 RDB 快照，缓存中保存预览 `seq=8`。
- `t1`：用户发布修改，数据库事务成功提交，业务权威状态变为 `seq=9`；应用本应更新或删除对应缓存。
- `t2`：Redis 故障并从 `t0` 的 RDB 恢复，键重新出现，但其内容仍是 `seq=8`。

恢复后的 Redis “有值”，只说明该值曾在 `t0` 存在：

\[
\text{RDB恢复值}=\text{缓存于 }t_0\text{ 的状态}
\neq \text{业务于 }t_2\text{ 的权威状态}
\]

因此，若客户端刚完成 `seq=9` 的发布，系统不能仅因 Redis 返回了预览就断言“刚发必见”。`seq=8` 可能覆盖了更新后的缓存，也可能是 `t1` 已失效、但故障恢复又被快照重新带回的旧键。

对可由数据库重建的预览，应将 RDB 恢复结果视为候选派生状态：可比较缓存版本与数据库版本，或在恢复后主动失效、回填。RDB 的价值是缩短冷启动时间，而非把快照时刻的缓存提升为业务事实；真正的权威仍是已提交的数据库状态。

### 旧预览为何必须校验源版本

### 旧预览为何必须校验源版本

设会话预览缓存记录为：

`preview:chat:42 = {seq: 8, text: "上一条消息"}`

在 $t_0$，Redis 执行 RDB 快照，保存了这份 `seq=8` 的预览。随后在 $t_1$，用户发送新消息：数据库事务成功提交 `seq=9`，应用本应更新或删除该预览缓存。此时即使缓存更新已完成，RDB 中仍只有较早的 `seq=8`。

若 Redis 随后故障，并从该 RDB 恢复，则 $t_2$ 重新出现的 `seq=8` 只是“快照时曾经存在过的值”，不是“当前会话的最新业务状态”。

因此，面对“我刚发的消息是否已经可见”这类请求，不能因为 Redis 命中预览就直接回答“不可见”或展示旧内容。正确做法是：

1. 将数据库中的消息序号、会话版本号或最后消息时间视为权威依据；
2. 比较缓存版本与权威版本：仅当 `cache.seq == db.latest_seq` 时，预览才可直接使用；
3. 若发现 `8 < 9`、版本缺失或无法确认，应读取数据库重建预览，并回填新缓存；
4. 若读取数据库暂时失败，应明确返回“状态待确认”或采用保守展示，不能把旧预览伪装成最新结果。

RDB 快照保证的是缓存数据可恢复，不保证它覆盖了快照之后已提交的业务更新。缓存中的版本号因此不是装饰字段，而是恢复后判断该值是否仍可回答“最新状态”问题的证据。

### 为状态写出恢复动作表

### 为状态写出恢复动作表

恢复策略不能只问“Redis 是否有数据”，而要按状态角色定义动作。可将每类键登记为：权威来源、可接受陈旧度、恢复后动作、对外响应语义。

| 状态 | 权威来源 | 恢复后动作 | 对外语义 |
|---|---|---|---|
| 内容预览 `preview:{id}` | 数据库中的已提交版本与序号 | 优先回源重建；命中旧值时校验版本号或失效标记 | 未校验缓存不得承诺“刚发布内容一定可见” |
| 在线状态 `presence:{user}` | 实时心跳、连接会话 | 清空或标记为“未知”，等待客户端重新上报 | 不把旧在线记录当作当前在线事实 |
| 限流计数 `rate:{subject}` | 通常无完整业务回源 | 按风险选择保守拒绝、降级额度或渐进恢复 | 安全敏感接口宁可暂时更严，不可因重启无限放行 |

例如，`t0` 的 RDB 保存了预览 `seq=8`；`t1` 数据库已提交 `seq=9`，应用本应更新或删除缓存；`t2` Redis 从 RDB 恢复出 `seq=8`。此时该键“存在”只说明快照曾记录过它，不说明它仍对应当前业务版本。应用可比较数据库版本，或在发布路径写入可验证的版本令牌；校验失败即删除并重建。

无持久化重启时，预览缓存为空通常是可接受的：首次请求回源数据库并回填即可。presence 则不能从数据库“重建在线”，因为历史登录记录不等于此刻连接存活；应显示未知、离线或要求心跳确认。

限流最需显式写政策：支付、登录、验证码等接口可在恢复窗口保守拒绝或使用较低临时阈值；普通搜索可从空计数渐进恢复。恢复动作表的核心是：RDB 快照是恢复材料，不是源业务权威。

> **要点** — RDB恢复的是历史缓存副本；数据库仍是权威，旧预览须经源版本校验后才能对外使用。

AOF让Redis具备命令日志恢复能力，但恢复出的数据仍可能是旧的派生状态，不能替代权威数据库的版本判断。

### 先界定AOF保存的状态边界

### 先界定 AOF 保存的状态边界

AOF保存的是Redis已执行的**写命令序列**，例如`SET`、`HSET`、`INCR`、`EXPIRE`；重启时Redis重放这些命令，恢复出某一时刻曾存在过的内存状态。它不是业务事实日志，更不自动证明恢复结果仍是最新、正确的事实。

可将缓存中的状态分为三类：

- **权威状态**：订单最终状态、账户余额、库存扣减结果等，唯一可信来源应是权威数据库或具备一致性协议的主存储。即使AOF中有对应值，也只能视为副本，恢复后应按版本号、更新时间或事件序号核对。
- **派生状态**：商品详情缓存、排行榜、聚合计数、数据库查询结果等。AOF可使其快速恢复，但其源数据可能已在Redis宕机期间变化；恢复值“存在”不等于“新鲜”，必要时应失效、回源或异步重建。
- **临时状态**：验证码、限流计数、会话、短期分布式锁等。其价值通常受TTL和时间语义约束。恢复后尤其要检查过期时间；对于锁，不应因AOF重放就认定持有者仍有效。

因此，AOF回答的是“Redis此前写过什么”，而不是“业务现在应当相信什么”。恢复策略应先按状态类别划分，再决定保留、校验、失效或重建。

### 追加写入与三种刷盘策略

### 追加写入与三种刷盘策略

AOF（追加文件）把会改变数据集的写命令按执行顺序追加记录。命令先进入 Redis 的 AOF 缓冲区，再写入操作系统页缓存；只有调用 `fsync`/`fdatasync`，才会要求操作系统将相关数据同步到持久化介质。因而“已经追加”不等于“已经断电可恢复”。

`appendfsync` 决定 Redis 主动刷盘的频率：

- `always`：每次写命令追加后都同步刷盘。异常断电时，按 Redis 的设计目标，已完成同步的命令不应因 Redis 未刷盘而丢失；代价是每次写都可能等待磁盘同步，延迟和吞吐量受存储性能显著影响。
- `everysec`：Redis 通常每秒在后台执行一次同步刷盘，兼顾性能与耐久性。若进程或主机突然故障，官方说明可能丢失最近约一秒内尚未同步的写入；同步线程受阻时，实际风险窗口还应结合运行告警判断。
- `no`：Redis 不主动执行同步刷盘，只负责把追加内容交给操作系统，由操作系统决定何时落盘。性能开销最低，但断电可丢失的范围最大；在常见 Linux 配置下，内核可能约每 30 秒刷新一次，不能把它当作固定保证。

三者保护的是“Redis 已接受的命令能否写入 AOF”的不同风险范围，并不证明恢复后的派生缓存一定新鲜或正确。恢复后仍需以权威数据库的版本、时间戳或业务状态核对。

### 恢复成功不代表数据仍然新鲜

### 恢复成功不代表数据仍然新鲜

AOF 能记录 Redis 已执行的写命令；重启时重放日志，键可以“恢复出来”。但这只证明**日志中的状态可重建**，并不证明该值仍与权威数据库一致。

例如，商品详情缓存、页面预览、搜索索引状态都属于派生值：

- 权威数据库已将商品版本从 `v17` 更新到 `v18`；
- Redis 中更新缓存的命令尚未落入可恢复的 AOF 范围，或更新任务根本未执行；
- Redis 重启后从 AOF 恢复出 `v17`。

此时 `v17` 是一个可读取、格式正确、甚至未过期的值，却不是可直接信任的新鲜值。持久化保存的是“曾经写入过什么”，不是“该值仍然代表当前事实”。

因此，派生数据最好携带可核验信息，如 `db_version`、`updated_at`、生成批次号或失效标记。读取时可采用以下判断：

1. 缓存版本与权威数据库版本一致，才使用派生值；
2. 发现版本落后、失效标记存在或无法确认版本时，视为缓存未命中；
3. 回源权威数据库，重新生成预览、缓存或索引内容；
4. 对异步索引，可记录待重建范围，而非把 AOF 恢复结果当作最终索引事实。

RDB 与 AOF 组合能够改善恢复速度或降低部分数据丢失窗口；AOF 重写也能压缩恢复所需日志。但它们解决的是 Redis 自身状态如何保存和重建，不能消除 Redis 与权威数据库之间可能存在的版本差。

### RDB与AOF组合及重写机制

### RDB与AOF组合及重写机制

RDB是某一时刻的数据快照：文件紧凑、加载通常较快，但它只覆盖生成快照时已经落盘的状态。若故障发生在两次快照之间，之后的写入是否可恢复，取决于是否还有AOF等增量日志。

AOF记录写命令序列，恢复时按顺序重放，因此能覆盖快照之后持续发生的变更；但其可恢复范围仍受 `appendfsync always`、`everysec`、`no` 的刷盘策略及故障类型影响。AOF并不意味着所有已确认写入都绝不丢失。

混合持久化可将AOF重写后的基础部分保存为RDB格式快照，再附加后续AOF命令：启动时先装载紧凑的基础状态，再重放增量命令，以平衡文件体积与恢复速度。

AOF重写也不是简单复制旧日志，而是把当前内存中的最终键值状态改写为一组更短的重建命令。例如同一键经历多次更新，重写后通常只需表达最终值。它的作用是压缩恢复基础、减少日志膨胀，不会提高状态的权威性。

因此，即使RDB+AOF完整恢复，所得仍可能是故障前某个时点的派生缓存值。涉及版本、订单状态、余额等关键字段时，仍应以权威数据库或其版本号、时间戳进行核对与修正。

### 为IM状态制定恢复核验表

### 为 IM 状态制定恢复核验表

Redis 重启后，不应把“已从 AOF/RDB 恢复”直接等同于“业务状态正确”。应按状态的权威来源、可再生性和错误代价建立核验表：

| 状态 | 恢复后处理 | 核验依据 | 说明 |
|---|---|---|---|
| 会话预览（最后消息、草稿摘要） | 需回源校验 | 消息库中的会话版本、最后消息序号 | Redis 中的预览可能停留在较早命令点；以消息库确认最新消息后再修正缓存。 |
| 未读计数 | 需回源校验或重算 | 已读游标、消息序号、服务端确认记录 | 不能仅信恢复出的计数；应按 `未读数 = 最新序号 - 已读序号` 或权威计数结果校准。 |
| 在线标记、心跳过期键 | 必须重建 | 客户端重连、网关会话、重新上报心跳 | 这是瞬时租约状态。恢复旧键会把已离线用户误判为在线，应清理并等待重新建立。 |
| 幂等标记 | 按操作类型处理 | 权威订单/消息记录、请求流水 | 对“已创建消息”等不可重复副作用，优先查询权威记录；缓存标记丢失时仍必须避免重复写入。 |
| 限流计数、输入中状态、临时推荐 | 可丢弃 | 无需核验 | 允许短暂失真或自然过期，恢复后可从空状态重新积累。 |

实现上可给派生缓存附带 `source_version` 或消息序号。恢复后若缓存版本小于数据库版本，或无法证明两者一致，就删除该键并回源重建，而不是继续提供旧值。

AOF 的 `appendfsync always`、`everysec`、`no` 只影响命令写入与刷盘时的风险范围；即使日志成功恢复，也不能证明其中的派生 IM 状态仍然新鲜。RDB+AOF 组合和 AOF 重写改善恢复与存储机制，但不替代上述业务核验规则。

> **要点** — AOF降低命令丢失风险，却不赋予缓存权威性；恢复后的派生值仍须由权威DB版本与业务规则核验。

Redis 主从复制默认异步，故障切换得到的不是“最后写入”，而是新主实际拥有的那份状态。

### 异步复制为何会回退预览

### 异步复制为何会回退预览

Redis 主从复制默认是异步的：主库先执行写入并向客户端返回成功，再把复制流发送给副本。于是，“客户端看见成功”与“副本已经拥有该数据”之间存在一个时间窗口。

设某个预览对象的版本号依次递增：

1. 主库当前已有 `preview_seq=8`，副本也同步到 `8`。
2. 客户端提交新预览，主库写入 `preview_seq=9`，并立即返回成功。
3. 此时复制消息尚在网络中、尚未被副本处理，副本仍停留在 `preview_seq=8`。
4. 主库突然宕机，Sentinel 或人工运维将该副本提升为新主。
5. 新主只能以自己实际持有的数据继续服务，因此读取结果变回 `preview_seq=8`。

可将时间线理解为：

`主库：8 → 9 → 故障`  
`副本：8 ─────→ 被提升为新主`

这里回退的不是 Redis “主动撤销”了版本 `9`，而是版本 `9` 从未可靠地到达将被提升的副本。故障切换后，系统的可见状态由“旧主最后确认过的状态”变成“新主已复制到的状态”。

对于预览、会话、临时计算结果等可从数据库或上游重新构建的缓存，这通常意味着一次可接受的旧读或重算；但若 `preview_seq=9` 对应订单、余额、库存扣减等权威事实，客户端已经收到成功却在切换后消失，就会形成“确认成功但状态不存在”的语义断裂。因此，不能仅因 Redis 能持久化或有副本，就把它当作无丢失的权威写入链路。

### 先判定状态能否回源

### 先判定状态能否回源

判断 Redis 故障风险前，先问一个更根本的问题：**这份状态丢失、回退或短暂不一致后，能否从更可靠的来源重建？**

可回源的典型是缓存型状态。例如商品详情、用户主页聚合结果、搜索预览、图片处理结果等，Redis 中保存的是数据库或对象存储内容的派生副本：

- Redis 主节点已有预览版本 `seq=9`，副本仍为 `seq=8`；
- 主节点故障后，落后的副本被提升，新主只能提供 `seq=8`；
- 缓存读取到旧预览，或键暂时不存在，并不意味着权威数据丢失；
- 可以删缓存、设置较短过期时间，或按“缓存未命中 → 查数据库/对象存储 → 回填 Redis”的路径恢复。

此时 Redis 的复制延迟主要影响**新鲜度、命中率和恢复期间的后端压力**。仍需防止缓存击穿、雪崩和旧值覆盖，但业务正确性锚定在数据库或对象存储，而不在 Redis。

不能简单回源的则是权威状态。例如余额扣减结果、订单支付状态、库存最终扣减、优惠券核销、幂等请求记录、分布式锁归属等。若 Redis 是唯一保存位置，那么 `seq=9` 在故障切换后退回 `seq=8`，不是“缓存旧了一点”，而是一次已确认操作可能从系统视角消失。

| 状态类型 | Redis 回退后的含义 | 可接受策略 |
|---|---|---|
| 可重建缓存 | 预览变旧或暂时缺失 | 回源重建、失效后回填 |
| 权威业务状态 | 事实、账目或操作结果丢失 | 写入权威存储，Redis 仅作加速或协调 |

`WAIT` 可以要求部分副本确认收到写入，降低丢失概率；Sentinel 可以发现故障并完成主从切换。但两者都不能把异步复制变成“故障后必保留最后一次写入”的强一致承诺。只要 Redis 承载权威事实，就必须额外设计持久化、提交确认、幂等补偿与权威数据源。

### WAIT 的确认边界

### WAIT 的确认边界

设主库已处理写入 `preview=seq9`，客户端随后执行：

`WAIT 1 1000`

若返回 `1`，其含义是：在等待窗口内，至少一个副本确认自己已经接收并处理了这次写入。它提高了“写入已传播”的把握，但不能把异步复制推导为强一致提交。

关键区别在于，`WAIT` 不是分布式提交协议：

- 它不要求所有副本确认，更不要求多数派形成可用于选主的提交点。
- 它不阻止主库在确认返回后立刻故障。
- 它不保证已确认的副本一定会在故障后被提升为新主。
- 它不保证 Sentinel 或其他故障转移机制能识别“哪台副本拥有最新写入”。
- 超时返回较小数量，只表示当时未收到足够确认；即使返回目标数量，也不等于故障切换后必然可见。

因此，可能出现这样的时序：主库写入 `seq9`；副本 A 收到并确认，`WAIT 1` 成功；主库故障；Sentinel 却提升尚停留在 `seq8` 的副本 B。切换完成后，客户端从新主读到的仍可能是 `seq8`，此前已经收到成功响应的 `seq9` 看似“消失”。

`WAIT` 适合降低缓存预览、会话镜像等数据的丢失概率，或让调用方据确认数量决定是否继续操作。它不能单独承担订单状态、余额、库存扣减等权威事实的提交语义。若业务要求“成功返回即经故障切换仍不可回退”，应将权威提交交给具备相应一致性保证的数据库或共识系统；Redis 中的 `WAIT` 只能作为传播确认，而非不可逆提交证明。

### Sentinel 切换不等于零丢失

### Sentinel 切换不等于零丢失

Sentinel 的职责是监控 Redis 主从节点、判定主节点不可达，并在满足法定票数后从副本中选出新主，令其余副本改为复制新主。它解决的是“谁来发现故障、谁来发起切换”，不是“如何让每次写入都被多数节点持久确认”。

典型过程是：

1. Sentinel 对主节点连续探测失败，先形成主观下线；
2. 多个 Sentinel 达成法定票数，确认客观下线；
3. 由领导 Sentinel 选择较合适的副本提升为新主；
4. 其他副本执行 `SLAVEOF NO ONE`、重定向复制关系，客户端经 Sentinel 获取新主地址。

问题在于，副本被提升时只能提供自己已经收到的复制流。若旧主刚写入 `seq=9`，副本仍停在 `seq=8`，旧主随即故障，则新主恢复的是 `seq=8`；`seq=9` 即使曾向客户端返回成功，也可能消失。

`WAIT` 能要求若干副本在限定时间内确认收到写入，从而缩小普通主机故障时的丢失窗口；但它不把 Redis 变成强一致系统：确认副本未必会被选为新主，确认信息也不能阻止故障切换期间的竞态。

更危险的是旧主并未真正宕机，而只是网络隔离。它可能继续接受写入，形成双主视角。待旧主重新加入后，其未复制出去的数据通常会被新主状态覆盖。因此，缓存允许回源数据库重建；订单、余额等权威状态则不能仅依赖 Sentinel 切换来承诺零丢失。

### 为预览设计恢复与校验链路

### 为预览设计恢复与校验链路

预览状态应被视为“可重建缓存”，而不是唯一事实。主库写入了 `seq9`、Redis 故障切换后新主只保留 `seq8` 时，应用不能仅因键存在就继续展示旧预览；应让每次读取都能判断“这份缓存对应哪一版源数据”。

建议为预览值附带源版本，例如：

`preview:{docId} -> {sourceVersion, renderedContent, generatedAt}`

读取链路如下：

1. 先从权威数据源读取或轻量查询当前 `sourceVersion`。
2. 命中缓存且 `cached.sourceVersion == sourceVersion`，才返回预览。
3. 缓存缺失、版本落后或反序列化失败时，删除旧值并进入受控回源。
4. 从数据库、对象存储或可重放事件中重建预览，再以版本条件写回缓存；写入时避免旧任务覆盖新版本。

为防止故障恢复后的集中回源造成击穿，可组合使用：

- `singleflight`／分布式互斥：同一 `docId` 同时只允许一个重建者；
- 短暂软过期：旧预览可在明确标注“可能更新中”的前提下有限返回，后台刷新；
- 随机 TTL、限流与队列：避免大量键在同一时刻失效；
- 空值缓存与负缓存：降低不存在对象的重复查询。

恢复边界必须明确：S2 中，预览丢失或回退通常可通过版本校验后回源修复；S3 中，若预览本身承载审批结果、发布资格或不可重算的用户操作，则不能只依赖 Redis 恢复，必须把该状态写入可验证的权威存储，并以持久版本或事件序列作为恢复依据。

> **要点** — 复制切换只能继承被提升副本已有的数据；缓存可校验回源，权威状态必须由可靠存储兜底。

Redis Cluster通过哈希槽分散键，但“分片更多”不等于单个热点自动变快；恢复与扩容都必须回到键、槽位和访问模式判断。

### 从键到槽位：分片实际分散的对象

### 从键到槽位：分片实际分散的对象

Redis Cluster并不是把一个大对象切成多份存到不同节点，而是先将**键**映射到固定的 `16384` 个哈希槽，再由节点负责一部分槽位。其路由关系可概括为：

$$
slot = CRC16(key)\bmod 16384
$$

客户端先计算键所属槽位，再请求负责该槽位的节点；若槽位已迁移，节点会返回重定向信息，客户端据此更新路由并重试。

因此，扩容的本质是把一部分**槽位责任**从旧节点迁到新节点。例如新增节点后，可以迁移若干槽位及其中的键，使更多不同键的请求分布到更多机器。但一个键始终只属于一个槽位，也通常完整地存放在该槽位当前所属节点上。

这带来两个容易误判的结论：

- 单个热键不会因节点增多而自动拆分。一个超大 `Set`、一个高频计数键或一个热门缓存键，仍集中落在同一槽位、同一主节点。
- 热点是否缓解取决于是否存在足够多的、可分散到不同槽位的热键，而不是仅看集群节点数。
- 大键迁移也不能按其内部成员并行分片；迁移的是该键所在槽位中的数据，迁移期间还需考虑网络、阻塞与访问重定向成本。

若业务需要让同类数据分散，应在键设计阶段显式拆分，例如按用户、分桶编号或业务分区生成多个键；反之，使用哈希标签 `{tag}` 会强制相关键进入同一槽位，便于多键操作，却也可能主动制造局部热点。

### 槽位迁移中的路由与短暂不稳定

### 槽位迁移中的路由与短暂不稳定

Redis Cluster 以 `$0\sim16383$` 个哈希槽组织键：`slot = CRC16(key) mod 16384`。迁移的单位是**槽位**，不是单条键；因此一个槽位从源节点迁往目标节点时，其中全部键都要逐步复制并切换归属。

迁移期间，源节点与目标节点会进入协作状态：

- 源节点将槽位标记为 `MIGRATING`，表示自己仍是当前责任节点，但正在向外迁出。
- 目标节点将槽位标记为 `IMPORTING`，表示自己准备接收该槽位的数据。
- 已迁移的键可能已存在于目标节点，尚未迁移的键仍留在源节点，因此短时间内同一槽位的数据分布并不完整。
- 迁移完成后，集群配置更新：该槽位正式归目标节点所有。

客户端若仍按旧拓扑把请求发给源节点，可能收到两类重定向：

- `MOVED slot target`：槽位归属已稳定变更。客户端应刷新本地槽位映射，并将后续请求直接发往目标节点。
- `ASK slot target`：这是迁移中的临时指引。客户端应仅对本次请求连接目标节点，先发送 `ASKING`，再执行原命令；不能据此永久修改槽位映射。

因此，集群客户端不能只在启动时加载一次节点列表。它应维护槽位到节点的缓存，识别并处理 `MOVED`、`ASK`，在连接失败、超时或重定向后进行有限次数重试。重试还要考虑命令语义：读请求通常可安全重发；非幂等写入若在超时后无法确认服务端是否已执行，盲目重试可能造成重复写入。

迁移带来的不稳定通常不是“数据丢失”，而是短暂的路由陈旧、额外跳转和延迟抖动。应用侧应预留超时与重试预算，并避免在高峰期同时迁移承载热点键的槽位。

### 单热键为何仍会压垮一个节点

### 单热键为何仍会压垮一个节点

以 `preview:c-g` 为例，Redis Cluster 会根据键名计算哈希槽：

`slot = CRC16("preview:c-g") mod 16384`

这个键无论集群有 3 个分片还是 30 个分片，都会稳定落在**一个固定槽位**；而在任一时刻，一个槽位只由一个主节点负责写入和提供主要读服务。因此，大量请求同时访问 `preview:c-g` 时，压力会集中到该槽位所属主节点：

- 读取集中：该节点的网络带宽、CPU、命令执行队列先达到瓶颈；
- 写入集中：同一键的更新仍需在该主节点串行处理，并复制给其副本；
- 大对象更严重：若 `preview:c-g` 是大型字符串、Set 或序列化预览结果，单次传输、反序列化和网络输出都会放大热点成本。

扩容新增分片只能让**不同键**分布到更多节点。例如将部分槽位迁移到新节点后，`preview:c-g` 要么仍在原节点，要么整体迁移到某个新节点；它不会被自动拆成多份并由多个主节点共同处理。迁移完成后，热点只是“换了一台机器承受”。

因此，发现单键热点时，应先确认其请求量、值大小、读写比例及访问是否可拆分。常见缓解方向包括：将内容按业务维度拆为多个键、对可接受短暂不一致的读请求使用本地缓存或副本读取、预计算并缓存较小的结果片段。若键本身不可拆分，扩分片只能改善其他键的负载，不能从根本上提高该单热键的吞吐上限。

### 大集合键：迁移成本与重建选择

### 大集合键：迁移成本与重建选择

以 `candidate_members:c-g` 这类大 Set 为例，先不要假定“迁移到新分片”一定优于“恢复后重建”。Redis Cluster 的槽位迁移以键为单位：一个 Set 无论有多少成员，仍只属于一个槽位，迁移时需要搬运整份键值及其过期信息；集合越大，网络传输、序列化、目标节点内存申请和迁移窗口内的访问抖动越明显。

决策前至少测量两类数据：

- `MEMORY USAGE candidate_members:c-g`：估计内存体积，而非只看成员数；
- `SCARD candidate_members:c-g`、成员平均长度与编码情况：判断集合规模；
- `SISMEMBER`、`SMISMEMBER`、`SADD`、`SREM` 的访问频率与延迟：判断它是容量问题还是热点问题；
- 重建数据源的完整性、重放耗时及可接受的新鲜度：判断故障后能否安全重建。

可比较三种路径：

- **整体迁移**：保留原键和访问语义，适合集合较小、必须立即保持完整状态的场景；但不能把同一键分散到多个槽位，也不能消除单键热点。
- **故障后重建**：若成员关系可从数据库、事件日志或上游索引可靠导出，可优先恢复服务后异步重建。它降低搬迁压力，但必须明确重建期间查询返回“未知”、旧值还是降级结果。
- **拆键设计**：按成员标识或业务维度拆为 `candidate_members:c-g:{分桶}`。注意 `{}` 内相同内容会强制同槽；若目标是分散负载，应让不同分桶落入不同槽位。代价是全量集合查询、去重、计数与原子更新需要客户端聚合或额外索引。

因此，扩分片只能为拆开的键提供更多落点；`candidate_members:c-g` 本身仍是单槽对象。先量化其大小和访问模式，再选择迁移、重建或重构，避免把容量扩展误判为热点治理。

### 面向恢复的分片状态决策表

### 面向恢复的分片状态决策表

恢复、扩容和冷启动前，应把缓存键登记为可执行的状态决策表，而非仅记录“在哪台 Redis”。核心问题是：该状态是否权威、丢失后从何处重建、落在哪个槽位，以及重建或访问会不会形成热点。

| 状态类型 | 权威性与恢复来源 | 槽位与迁移判断 | 热点风险与操作 |
|---|---|---|---|
| 预览结果 `preview:{id}` | 通常为派生缓存；由对象存储、数据库记录或计算任务重建 | 同一键永远属于一个槽位；迁移时由 Cluster 完成槽位归属切换 | 单个超热预览仍集中于一个槽位、一个主节点；扩分片不会自动分散它，应设短 TTL、限流或拆分读路径 |
| 候选集合 `candidates:{id}` | 多为可再生中间状态；需明确可由检索索引、数据库条件或上游任务重建 | 大 Set 作为单键整体归属一个槽位，不能按成员自动分散 | 先测量基数、内存、序列化体积与访问频率；大键迁移、加载和重建都可能阻塞或放大流量 |
| 会话、任务游标等 | 若仅加速读取，可容忍丢失；若影响业务推进，则不能只存缓存 | 使用哈希标签时，`{id}` 内相同部分会强制共槽 | 不要因跨键原子操作方便而把大量高频键固定到同一槽位 |
| 路由与元数据缓存 | Cluster 槽位映射可由客户端刷新；业务元数据须有独立权威来源 | 槽位迁移期间客户端可能收到重定向 | 客户端必须处理 `MOVED`、`ASK` 并刷新拓扑，不能长期硬编码节点地址 |

建议为每类键补充字段：`权威副本`、`最大可接受恢复时间`、`重建限流策略`、`预计键大小`、`峰值 QPS` 与 `槽位标签`。故障后优先恢复不可替代状态；可再生预览和候选集合则按访问热度逐步回填，避免所有实例同时重建同一批热键。

> **要点** — Cluster分散的是键所属槽位，不是键内部数据；热点单键和大集合键都需按访问与重建成本单独治理。

Redis缓存清空或失效后，真正的风险不是“变慢”，而是回源洪峰压垮数据库并让系统产生不可信状态。

### 冷缓存为何会形成回源债务

### 冷缓存为何会形成回源债务

Redis 中的预览缓存一旦被清空，原本由缓存吸收的请求会突然全部回到数据库。设预览请求稳定为 $1000/s$，而数据库在不影响核心读写、连接池和复制延迟的前提下，最多只能安全处理 $200/s$ 回源查询，则每秒都会新增：

$$
1000 - 200 = 800
$$

次未被及时完成的工作。这 $800/s$ 不是瞬时峰值，而是持续累积的“回源债务”。若请求持续 $10$ 秒，理论上已有 $8000$ 个请求在排队、超时或重试；持续 $1$ 分钟，则债务达到 $48000$ 次。

更危险的是，排队不会只影响预览接口。大量等待中的请求会占住数据库连接、应用工作线程和网络缓冲区；客户端超时后再次发起请求，又会把同一份冷数据重复回源。于是实际到库速率可能高于原始的 $1000/s$，形成“慢—超时—重试—更慢”的正反馈。

因此，缓存恢复不能理解为“让请求自然回源，等缓存慢慢热起来”。在数据库安全能力只有 $200/s$ 时，系统必须把回源也限制在这个量级：其余请求应等待合并后的单次加载、返回明确的“预览暂不可用”降级结果，或按热点顺序预热。预览数据可由 S3 或原始文件重新计算，宁可暂时不给预览，也不能为了快速响应而编造在线状态、复用过期权限许可。

### 先划定可重建与不可编造的状态

### 先划定可重建与不可编造的状态

缓存恢复的第一步不是“尽快填满 Redis”，而是给每类状态标注恢复语义：它能否由权威数据重新计算？短暂缺失时应拒绝、降级，还是允许重算？

| 状态 | 缓存丢失后的处理 | 依据 |
|---|---|---|
| S3 预览结果、缩略图、转码地址 | 可按需重算，或按热点顺序预热 | 原文件及其元数据仍在权威存储中；预览只是派生物 |
| 权限、订阅资格、封禁状态 | 必须回权威来源确认；确认失败时默认拒绝 | 许可决定访问边界，旧缓存可能已过期或已被撤销 |
| 在线状态、会话存活、设备活跃度 | 不得由缓存缺失、旧值或历史访问记录推断 | “最近见过”不等于“当前在线”，编造会污染业务判断 |

因此，S3 预览缓存为空时，可以把请求转为“等待重建”或“稍后可用”：以对象版本、参数和算法版本构成键，限制重算并发，并优先恢复热点内容。即使预览暂不可得，系统仍可诚实地返回“处理中”。

权限则相反。缓存中没有命中，不能把“曾经允许”当作“现在允许”；缓存中的旧许可也不能在失去校验能力后无限延用。权威权限服务不可达时，应按风险选择拒绝访问、只读受限或要求稍后重试，而非放行。

在线状态最容易被误处理。Redis 清空后，不能因用户刚请求过预览、数据库有登录记录，便显示“在线”。只能等待新的心跳、连接事件或会话确认到达；未知应显示为“状态暂不可确认”，而不是伪装成在线。

### 以有界并发控制回源闸门

### 以有界并发控制回源闸门

缓存失效时，若每个未命中请求都立即访问数据库，原本 `1000/s` 的预览请求会直接变成 `1000/s` 回源；而数据库安全处理能力只有 `200/s`，则净积压为：

$$
\Delta Q = 1000 - 200 = 800/s
$$

积压会抬高延迟，客户端重试又会继续放大流量，最终形成缓存击穿与重试风暴。解决目标不是让所有请求“尽快回源”，而是把回源速率限制在数据库可承受范围内。

- **互斥合并**：对同一缓存键，只允许一个请求成为“重建者”；其余请求等待该结果、短暂轮询，或直接获得降级响应。这样，某个热点键即使同时有数千请求，也只产生一次数据库查询。
- **全局或分片信号量**：限制同时执行的回源任务数。例如数据库允许 `200` 个安全并发回源，则信号量耗尽后的请求不得继续穿透缓存。不同业务可分别设置配额，避免预览流量挤占登录、订单等关键读路径。
- **有界队列**：无法立即获得信号量的请求进入有限队列；队列满时应立刻拒绝、返回“预览暂不可用”或可重算的 S3 preview，而不是无限排队。队列是削峰工具，不是隐藏积压的容器。
- **超时与取消**：等待锁、等待队列、数据库查询都必须有短超时。请求已断开或超过用户可接受延迟时，应取消其等待，避免无效工作继续占据回源槽位。

可将路径理解为：

`缓存未命中 → 同键合并 → 获取回源信号量 → 有界队列 → 数据库 → 回填缓存`

若任一步骤失败，就明确降级，而非绕过闸门。尤其权限、会话、在线状态等安全状态不能因缓存为空而返回旧许可，更不能根据历史数据编造“仍在线”。预览内容通常可从 S3 或源数据重算，适合作为降级对象；授权结论则应宁可拒绝或要求重新校验。

### 按热点预热并提供明确降级

### 按热点预热并提供明确降级

Redis 清空后，不应让所有键同时“自然回填”。若原本每秒有 $1000$ 个预览请求，而数据库安全回源能力仅为 $200/\text{s}$，无控制时将持续以 $800/\text{s}$ 积压；超时重试又会放大压力。恢复目标因此不是尽快填满缓存，而是优先恢复最有价值、最常被访问且可安全重建的状态。

重建队列应同时考虑访问热度与业务优先级，例如：

1. **第一层：核心热门预览**  
   首页、当前活跃会话、近期频繁访问对象的预览。按近 5 分钟访问次数、活跃用户数或请求速率排序，优先预热。
2. **第二层：普通热门内容**  
   可异步批量从 S3 源文件重算并写入缓存；工作线程必须受并发数、每秒回源数和队列长度限制。
3. **第三层：长尾内容**  
   不主动预热，等待用户请求触发；同一对象使用请求合并或单飞锁，避免并发请求重复计算。
4. **不应重建的状态**  
   权限许可、在线状态、租约等安全或时效状态必须重新向权威服务确认，不能因缓存缺失而返回旧值，更不能编造“在线”或“已授权”。

对于尚未恢复的预览，应用必须给出语义明确的降级响应，而不是无限等待：

- 可在短暂预算内等待，例如等待 `200ms` 的在途重建；
- 未完成则返回“预览正在生成”的占位结果，并携带可轮询或稍后重试的标识；
- 队列过载时直接返回“暂不可用，请稍后重试”，附带退避建议；
- 若 S3 中保留原始文件，可允许预览异步重算，但不要把同步重算压力转嫁给每个用户请求。

这样，缓存恢复从无序的回源竞争变成受控的容量分配：热门体验先恢复，数据库负载有上限，未恢复内容也具有诚实、可预测的响应语义。

### 用状态级恢复表约束Go服务行为

### 用状态级恢复表约束 Go 服务行为

恢复逻辑不能只写成“缓存未命中就查库”。Go 服务应先判断自己处于哪个状态，再决定可读数据、允许写入的范围及对用户的承诺。以下以 **S2 内存受理**与 **S3 提议数据库恢复**为例：

| 恢复阶段 | 读取来源 | 写入规则 | 用户可见结果 |
|---|---|---|---|
| 缓存为空 | 不信任 Redis；优先读进程内已验证的必要状态 | 仅接受幂等请求、草稿、上传分片等可延后确认的操作；写入追加日志或待处理队列 | 预览可提示“正在恢复”；权限、库存、在线状态等强一致结果明确降级或拒绝 |
| 回源中 | 热点键按优先级受控回源；单键使用 `singleflight` 合并；总并发限制在数据库安全能力内 | 禁止请求触发无限制全量重建；只允许恢复任务写 Redis，并设置短 TTL 与版本号 | 冷门预览可返回“稍后重试”；不能因缺缓存而把旧许可当作有效，也不能编造“用户在线” |
| 重建完成 | Redis 为主读源，数据库作为校验与失效后的受控回源 | 正常写数据库后删除或更新对应缓存；恢复队列清空前持续记录版本 | 逐步恢复完整预览与搜索体验；仍以数据库权限判定为最终准则 |

例如，原本每秒 `1000` 次预览请求在 Redis 清空后若全部直达数据库，而数据库安全处理能力仅为 `200/s`，积压会以 `800/s` 增长。服务应将预览重算视为可降级能力：先预热首页、热门对象和当前活跃用户相关键，其余请求返回可解释的恢复提示。

S2 的目标是“先安全受理”，不是假装状态完整；S3 的目标是“按可信来源重建”，不是让每个用户请求都成为恢复任务。这样即使 S3 上的 preview 可重新计算，也不会把不可重算的权限结论、支付结果或在线状态混入缓存恢复过程。

> **要点** — 缓存可空，但回源必须有界；预览可重算，权限与在线状态必须回到可信来源确认。

Redis恢复的是某个时间点的副本，不等于业务真相。先划分状态权威性，再决定能否丢失、如何校验与怎样恢复。

### 先定权威：缓存不是消息历史的事实来源

### 先定权威：缓存不是消息历史的事实来源

恢复设计的第一步不是选择 RDB、AOF 或副本，而是回答：**这份状态到底谁说了算？** Redis 恢复出的只是某个持久化时刻或副本切换时刻的内容；它可以加速读取，却不能自动成为业务事实。

可将状态分为三类：

- **权威状态**：必须有可审计、可恢复、可确定顺序的事实来源。例如消息记录、会话成员关系、消息 `next_seq`、权限变更。消息历史应以数据库中的事务提交结果为准：Redis 中即使还有消息，也只能视为缓存；Redis 丢失消息时，则从数据库回填。
- **派生状态**：可由权威状态重新计算，例如最近消息预览、未读摘要、会话列表排序缓存。恢复后允许暂时为空或偏旧，但应标记失效、按需重算，而非把旧缓存误当最新结果。
- **临时状态**：只描述短时活性，例如在线 presence、输入中标记、限流窗口计数。它们通常允许丢失，但必须定义丢失后的默认语义。

一个实用判断是：若 Redis 清空后，系统能否仅依靠数据库和事件日志重建该状态？能，则它通常是派生或临时状态；不能，且错误会造成消息丢失、顺序冲突或越权，就不应只存于可逐出的 Redis。

因此，消息读取路径可以是“先查 Redis，未命中回源数据库”，但写入确认必须以数据库提交为边界。缓存恢复后应主动预热或惰性回填；在回填完成前，宁可缓存未命中，也不要用来源不明的旧值覆盖数据库事实。

### RDB与AOF：恢复时间点决定可丢范围

### RDB 与 AOF：恢复时间点决定可丢范围

RDB 是某一时刻的内存快照：恢复快、文件紧凑、适合备份与灾难恢复，但故障后只能回到最近一次成功快照。若每 15 分钟生成一次 RDB，最坏情况下可丢失约 15 分钟写入，实际 RPO 还要叠加快照生成、落盘和副本复制的延迟。

AOF 记录写命令，恢复时重放日志。其 RPO 取决于刷盘策略：

| 策略 | 最坏可丢范围 | 性能与风险 |
|---|---:|---|
| `appendfsync always` | 单条命令附近 | 延迟高，受磁盘抖动影响明显 |
| `appendfsync everysec` | 约 1 秒，异常时可能更多 | 常用折中方案 |
| `appendfsync no` | 由操作系统决定 | 吞吐较高，但不可预测 |

AOF 通常比 RDB 恢复慢，因为需要重放大量命令；日志越长，RTO 越大。启用 AOF 重写可压缩历史，但重写期间仍需评估额外 CPU、磁盘与写放大。实践中常同时保留 RDB 与 AOF：RDB 便于快速加载和异地备份，AOF 降低近期数据丢失窗口。

权限、封禁、角色、会话撤销等安全状态不能仅按“可接受一秒丢失”处理。撤销记录丢失可能使已失权用户重新获得访问；授权记录丢失则可能误拒合法用户。此类状态应以关系数据库或专用身份系统为权威，Redis 仅作缓存；若必须以 Redis 为权威，至少需要持久化、跨节点复制、可验证备份、禁止逐出以及明确的故障切换流程。`WAIT` 只能等待副本确认，不能替代落盘、备份或恢复演练。

### 预览与在线状态：恢复后必须重新验证

### 预览与在线状态：恢复后必须重新验证

`preview` 与 `presence` 都常放在 Redis，但恢复后的处理原则完全不是“读到什么就信什么”。

- **预览可重算，不等于可直接展示。**  
  例如消息预览、最近会话摘要、未读列表中的最后一条文本，本质上是消息主库记录的派生结果。Redis 恢复出的 `preview` 可能对应旧消息版本：消息已编辑、撤回、被权限策略隐藏，或会话最后一条消息已变化。应将预览与源数据版本绑定，例如保存 `message_id`、`message_version` 或递增序号；恢复后若版本不匹配，则从消息库重算或异步刷新。在权限敏感场景，宁可暂时显示“内容已更新”，也不要展示可能已撤回或无权读取的旧文本。

- **在线状态不能从旧快照继承。**  
  `online` 是对“客户端近期仍存活”的判断，而不是可持久化事实。RDB/AOF 中恢复出的 `online=true` 只说明故障前某一时刻收到了心跳；服务重启、网络分区或客户端已退出后，该结论已失效。恢复时应把旧在线状态视为“未确认”，等待客户端在新的心跳窗口内重新上报，例如仅在收到当前实例周期内的心跳后才标记在线。

可将状态划分为：

| 状态 | 恢复后处理 |
|---|---|
| `preview` | 校验源消息版本；不匹配则重算 |
| `online` | 默认未确认；等待新心跳 |
| `last_seen` | 可保留为历史信息，但不能推导当前在线 |

核心区别是：预览可以由权威数据重新导出；在线状态只能由恢复后的新观测重新证明。

### 复制切换与分片：副本确认不等于不回退

### 复制切换与分片：副本确认不等于不回退

Redis 主从复制通常是异步的：主库先接受写入，再把命令流发送给副本。主库宕机而副本尚未收到最后一段复制流时，Sentinel 或集群会提升副本为新主库；这段未复制的写入便会在切换后消失，即发生**回退**。

`WAIT N T` 只能要求当前主库等待至少 `N` 个副本确认收到此前写入，最多等待 `T` 毫秒。它能缩小丢失窗口，却不能提供强一致故障切换：

- 确认的是副本“已接收复制数据”，不等于数据已落盘、可恢复；
- `WAIT` 返回成功后，已确认副本仍可能先故障，最终被提升的是较旧副本；
- 网络分区时，旧主可能继续接受写入，新主也开始写入，形成脑裂；旧主恢复后其独有写入通常会被覆盖；
- `WAIT` 超时不意味着写入一定没复制，只表示调用方不能获得足够确认。

分片进一步扩大判断范围：每个槽位有独立主副本链路和切换过程。一次业务操作若涉及多个分片，不存在天然的“共同提交点”；某分片可能保留写入，另一分片可能回退。因此，跨分片的余额、序号、权限授予等状态不能把 Redis 复制确认当作事务提交证明。

对可重算的预览、缓存索引，允许按 RPO 接受回退并从数据库重建；对消息序号、扣费、权限等不可回退状态，应以数据库或具备明确持久提交语义的存储为权威。若必须以 Redis 为权威，还需设计持久化、跨故障域副本、备份、禁止逐出、脑裂隔离与切换后的校验补偿；单独增加 `WAIT` 不足以消除回退风险。

### 冷启动恢复表：计数降级与序号保底

### 冷启动恢复表：计数降级与序号保底

冷启动时先区分“可重建的派生状态”和“决定正确性的提交状态”。恢复顺序应先保证序号与受理边界，再恢复体验类数据；不能因为 Redis 中存在旧值就直接启用。

| 状态 | 正常存放 | 冷启动策略 | 故障保护 |
|---|---|---|---|
| 限流计数 | Redis | 不回源，允许窗口计数重置；按接口风险重新建桶 | 登录、发码、支付等高风险接口采用 `fail-closed` 或更严格的临时阈值；普通读接口可 `fail-open`，并记录降级审计 |
| `next_seq` | 数据库或可持久化序号服务 | 从权威数据库读取最后已提交序号，分配时使用事务、行锁或原子条件更新 | 不得只存 Redis；Redis 丢失或逐出会造成序号回退、重复消息或覆盖 |
| S2 内存受理状态 | 进程内存 | 重启后全部视为未受理；客户端重连、重传或由上游重放 | 不把“已收到但未提交”的内存对象伪装成成功；超时后要求幂等重试 |
| S3 提议数据库记录 | 数据库 | 扫描 `proposed/pending` 记录，按幂等键恢复提交、撤销或标记待人工处理 | 对外确认应以最终提交状态为准；恢复任务必须可重复执行 |

序号的核心不只是“递增”，而是恢复后仍满足单调性：`next_seq > max(committed_seq)`。若批量预分配过序号，允许出现空洞，但不允许复用已暴露给客户端的序号。

限流重置也不是纯技术问题：计数丢失会放大攻击面，应结合权限和操作风险设定降级矩阵。高权限管理员操作、验证码校验、资金相关写入宁可暂时拒绝；公开查询可短暂放行，但应启用更低的全局保护阈值与告警。

> **要点** — 恢复策略由状态权威性决定：可重算的重建，影响顺序、权限或提交语义的必须有独立可靠存储与故障方案。

Redis故障恢复时，关键不在于“数据是否还在”，而在于恢复出的状态是否仍可被业务信任。

### 先判状态角色，再谈能否丢失

### 先判状态角色，再谈能否丢失

缓存故障后的第一问不应是“Redis 丢了多少”，而是：**这份状态在业务上扮演什么角色？** 同样存于 Redis 的数据，丢失后果可能从“多一次数据库查询”到“账务错乱、消息重复”完全不同。

- **权威状态**：系统认定的最终事实，必须有可追溯、可恢复的可靠来源。例如订单状态、余额、支付结果、IM 消息正文与已读回执的最终记录。  
  Redis 即使保存了它，也不应是唯一可信副本；若 Redis 是唯一存储，则持久化、复制、故障切换与写入确认语义都成为数据正确性设计的一部分。

- **派生状态**：可由权威状态计算、聚合或同步得到，例如会话列表排序、未读数、用户在线汇总、热点内容计数、消息索引。  
  它可以短暂丢失，但必须定义重建来源、重建算法与完成前的降级行为。尤其要警惕“未读数丢了可重算”：若重算依赖已过期的消息、缺失的游标或不完整日志，它实际上并不可重建。

- **临时状态**：仅为性能、限流或短生命周期协作服务，例如验证码、接口限流计数、短期幂等键、分布式锁、缓存热点值。  
  通常允许丢失，但仍要评估副作用：限流计数归零可能导致突发流量穿透；锁丢失可能造成并发执行；幂等键丢失可能引发重复扣款或重复发信。

对 IM 而言，可用一个边界快速判断：

| 数据 | 常见角色 | 能否直接丢失 |
|---|---|---|
| 消息正文、发送顺序 | 权威状态 | 不可 |
| 会话游标、已读位置 | 权威或关键派生状态 | 不应无条件丢失 |
| 未读数、会话列表 | 派生状态 | 可丢，但须可验证重建 |
| 在线状态、输入中提示 | 临时状态 | 通常可丢 |
| 登录令牌、幂等键 | 临时但安全敏感 | 可过期，不可任意清空 |

因此，“可丢”不等于“无影响”，而是指系统能够在可接受的时间、成本和一致性范围内恢复业务语义。先写清每类数据的权威来源、最大可接受陈旧量，以及重建后的校验条件，才有资格讨论选无持久、RDB、AOF 还是副本切换。

### 无持久、RDB与AOF的恢复账本

### 无持久、RDB 与 AOF 的恢复账本

故障后的“最终状态”取决于 Redis 在故障前把哪些内存变化写到了可恢复介质。可把每次写入记为递增序列号：`t0: seq=8`、`t1: seq=9`。若 `seq=9` 尚未进入可恢复账本，重启后即使业务曾读到它，也不能把它当作可靠事实。

| 方案 | 恢复依据 | 典型丢失窗口 | 性能与恢复特征 | 适合的状态 |
|---|---|---|---|---|
| 无持久 | 空内存或外部回源 | 故障前全部内存写入 | 写入最快；重启后无本地数据，重建最慢且依赖源站 | 可再生缓存、限流计数等可容忍归零状态 |
| RDB | 最近一次时间点快照 | 上次成功快照之后的全部写入 | 平时开销较低；加载二进制快照较快；快照间隔越长，风险越大 | 可批量重建、允许回退到较早时点的数据 |
| AOF | 已落盘的命令追加日志 | 取决于刷盘策略；每秒刷盘通常可能丢失约 1 秒 | 写入与磁盘同步成本较高；日志较大时重放较慢，可经重写压缩 | 需要较小数据丢失窗口的会话、订单阶段、关键计数 |

例如，`t0` 时 RDB 已保存 `seq=8`；`t1` 写入 `seq=9`；`t2` 实例宕机。若没有 AOF，恢复只能得到 `seq=8`，此时“旧值”不是 Redis 读错了，而是恢复账本只证明了 `seq=8`。若 AOF 已记录并成功刷盘 `seq=9`，则可重放到 `seq=9`；若命令只在内存或操作系统页缓存中，则仍可能回退。

选择不能只问“会不会丢”，还要问业务能否接受回退：商品详情缓存可无持久并回源；排行榜可接受 RDB 的分钟级回退；支付、库存等权威事实不应仅依赖 Redis 持久化，应以数据库或日志系统为准。恢复后还应验证：恢复序列号、AOF 完整性、关键键的版本/过期时间，以及冷缓存回源是否会压垮源站。

### 从seq8到seq9：旧缓存为何不能直接相信

### 从seq8到seq9：旧缓存为何不能直接相信

设商品 `P` 的权威数据在数据库，缓存只保存派生副本，并携带版本号：

- `t0`：数据库与缓存均为 `P=(价格100, version=seq8)`。
- `t1`：业务将数据库更新为 `P=(价格120, version=seq9)`；缓存本应同步更新或失效。
- `t2`：缓存节点故障后按较早快照恢复，重新出现 `P=(价格100, version=seq8)`。

此时，`seq8` 并不因为“成功恢复”而重新正确。它只是某个历史时刻的有效值；相对于当前权威状态 `seq9`，它已是陈旧副本。若应用直接命中该值，可能展示旧价格、覆盖新库存，甚至把过期状态写回数据库。

因此，缓存值最好表达为：

$$C[P]=(\text{业务数据},\ \text{sourceVersion},\ \text{生成时间})$$

读取或重建时，不能只问“缓存有没有”，还要问“它对应的源版本是否仍可接受”。常见验证门包括：

1. **版本比对**：缓存的 `sourceVersion=seq8` 小于权威源的 `seq9`，判定失效并回源。
2. **写入条件保护**：重建缓存时使用“仅当新版本不低于现有版本才写入”，避免较慢的旧请求把 `seq8` 覆盖 `seq9`。
3. **失效标记或代际号**：源数据更新时推进代际；恢复出的旧代际缓存即使存在，也不能被正常读取。
4. **关键路径强校验**：库存扣减、权限、余额等不能仅依赖缓存命中，应以权威存储或可验证版本为准。

恢复后的缓存应被视为“候选状态”，而非“可信状态”。只有通过源版本校验，或经过受控回源重建，旧值才可重新进入服务路径。

### 异步复制切换与WAIT的保证边界

### 异步复制切换与 `WAIT` 的保证边界

Redis 主从复制默认是异步的：主库先执行写入并向客户端返回成功，再把复制流发送给副本。因此可能出现时间线：

- `t0`：主库写入 `k=v8`，序号为 `seq=8`，副本已追上。
- `t1`：主库写入 `k=v9`，序号为 `seq=9`，客户端收到成功；但复制报文尚未到达副本。
- `t2`：主库故障或网络隔离，Sentinel 将仍停在 `seq=8` 的副本提升为新主。

此时恢复后的可服务状态是 `k=v8`。`v9` 曾被旧主确认，却未进入新主的历史；这不是“读到了旧缓存”，而是一次已确认写的回退。旧主若稍后恢复，通常会被重新配置为新主副本，其本地 `v9` 也可能被新主的 `v8` 覆盖。

`WAIT n timeout` 可在写入后等待至少 `n` 个副本确认已接收该连接此前的写入，例如：

`SET order:1 paid` → `WAIT 1 100`

若返回值为 `1`，说明至少一个副本已确认；若超时返回 `0`，业务可将该次写标记为风险状态、重试或进入补偿流程。它降低“主库独有最新写立刻丢失”的概率，但不提供强一致性：

- `WAIT` 确认的是副本接收进度，不是事务提交到多数派的共识承诺。
- 已确认的副本仍可能随后宕机，或在复杂网络分区中未被选为新主。
- Sentinel 的故障判定与选主需要时间；切换前后客户端可能短暂写失败、读到不同节点状态。
- 超时不等于写失败：主库可能已写入，只是未获得足够副本确认。

因此，`WAIT` 适合提高订单状态、扣减标记等写入的耐故障性；但若业务不能接受 `seq=9→seq=8` 回退，就不能只依赖异步复制与 Sentinel，应额外设计幂等号、版本号、持久化记录及恢复后的对账补偿。

### 冷启动回源预算与状态级恢复表

### 冷启动回源预算与状态级恢复表

冷启动不是“缓存为空就查库”，而是一次受预算约束的恢复：数据库、下游接口与网络连接都可能在同一时刻被大量未命中压垮。应先定义回源额度，再决定哪些数据值得预热。

|恢复状态|可信来源|恢复动作|对外策略|
|---|---|---|---|
|S2：内存已受理|进程内短暂状态|重建后不可直接视为已提交|返回“处理中”或重试令牌|
|S3：数据库已提议/提交|数据库事务、事件日志|按版本号或序列号重放、校验|可读；写入需幂等校验|
|冷缓存|数据库或权威服务|限流回源、填充缓存|优先读降级数据或稍后重试|

建议将回源预算拆为：全局并发上限、单键并发上限、每租户额度、超时上限。对热点键使用“单飞”：第一个请求回源，其余请求等待同一结果；等待超时则返回降级值，不能继续穿透。预热应分批按业务优先级进行：配置、权限、商品基础信息优先；长尾画像、统计聚合延后。缓存填充必须携带版本或`seq`，避免旧回源结果覆盖新写入。

恢复验证门可设为：关键键命中率达标、回源错误率低于阈值、S3序列连续、抽样比对缓存值与权威值一致后，才逐步放开流量。

1. 冷缓存的主要风险？答：回源洪峰。  
2. 单飞解决什么？答：同键并发穿透。  
3. 限流对象只应是全局吗？答：否，还应限键和租户。  
4. S2可直接当已提交吗？答：不可。  
5. S3权威依据是什么？答：事务或日志。  
6. 预热先做什么？答：高优先级关键数据。  
7. 长尾数据如何处理？答：按需回源。  
8. 回源为何要超时？答：保护调用链。  
9. 等待单飞超时怎么办？答：降级或重试。  
10. 缓存写入为何带版本？答：防旧值覆盖。  
11. 命中率高就可放量吗？答：还需校验一致性。  
12. `seq`连续说明什么？答：重放未明显缺段。  
13. 数据库慢时可无限排队吗？答：不可。  
14. 热点键预热失败怎么办？答：保守限流并降级。  
15. 配置数据为何优先？答：影响全局行为。  
16. 权限缓存错误风险？答：越权或误拒绝。  
17. 降级值应当是什么？答：安全且可解释的结果。  
18. S2请求恢复后如何处理？答：确认、重试或补偿。  
19. 回源预算由谁决定？答：下游容量与业务优先级。  
20. 批量预热为何分批？答：避免挤占正常流量。  
21. 验证门的作用？答：阻止错误状态扩散。  
22. 最终可信状态优先级？答：权威持久状态高于内存状态。

> **要点** — 恢复后的Redis只是一份候选状态；能否使用取决于状态权威性、持久化窗口、复制回退风险与源版本验证。
