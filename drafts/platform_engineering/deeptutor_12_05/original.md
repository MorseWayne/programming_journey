以IM的gateway、transfer、db、migration为线索，从状态责任、流量入口和故障替换三个维度选择Kubernetes对象，而非按名称套模板。

### 先按状态责任划分四类角色

### 先按状态责任划分四类角色

不要先问“网关该用 Deployment 还是 Service”，而要先问：**进程被替换后，哪些状态必须保留，哪些状态可以丢失或重建？**

- **gateway**：负责 HTTP/WebSocket 入口、鉴权、参数校验和路由。它应尽量无状态；实例重启后，连接可重连、请求可重试。当前 S2/v1 中，`200` 仅表示“已在内存中受理”，不能误解为已持久化，因此 gateway 不能把内存队列当作可靠事实来源。
- **transfer**：负责消息转发、在线投递或后续异步处理。若只保存短暂缓冲、可由上游重投，则也可视为可替换工作者；若它独占某个会话、分区或顺序状态，就必须明确恢复、迁移和重复消费策略。
- **db**：保存成员关系、消息记录、幂等键等权威状态。S2/v1 的“重复返回 `409`”“非成员返回 `404`”都依赖可查询的一致事实，不能仅靠 gateway 本地缓存判断。数据库是有状态角色，替换实例不应等于丢失数据。
- **migration**：只在版本升级或初始化时执行模式变更、数据回填等有限任务。它不接收持续流量，也不应常驻；成功后留下可审计结果，失败后可控制地重试。

当前接口约束先定义了状态边界：正文按 UTF-8 计最多 `6B`，原始请求正文最多 `4096B`；这些是入口校验责任。`409` 与 `404` 是业务事实判断责任，最终应由可共享、可恢复的状态支撑。R9 仍待审时，更应避免把未定的持久化语义偷偷固化进某个实例内存。

### 无状态网关与消费者采用Deployment

### 无状态网关与消费者采用 Deployment

`gateway` 负责接收客户端 HTTP/WebSocket 请求、鉴权、参数校验与路由；`transfer` 负责消费队列中的消息、执行转发或投递。两者的共同点是：实例应当可以横向扩容，任一 Pod 被删除、重建或漂移到其他节点后，不应依赖本地磁盘或进程内状态恢复业务。

因此通常使用 `Deployment`：

- 通过 `replicas` 提供多副本与滚动更新；
- 通过 `readinessProbe` 避免未就绪的新 Pod 接收流量；
- 通过 `livenessProbe` 让卡死实例被替换；
- 通过 `Service` 将请求分发到健康的 gateway Pod；
- transfer 可按消费积压、CPU 或自定义指标扩容副本数。

但“无状态”不等于“业务没有状态”。S2/v1 中，`200` 只表示请求已被当前进程的内存队列受理，并不表示已持久化、已转发或已送达。若 gateway Pod 在返回 `200` 后立刻被替换，尚未落库或转交给可靠队列的数据可能丢失；这必须写入接口语义，而不能假装 Deployment 会自动保证可靠性。

同样，重复请求返回 `409`、非成员会话返回 `404`，不能仅靠单个 Pod 的内存缓存判断：请求可能被负载均衡到不同副本，Pod 重启后缓存也会消失。若这些语义需要跨副本、跨重启保持一致，判断依据应放在共享的权威状态中，例如数据库、可靠消息系统或具备明确一致性约束的去重存储。

transfer 的消费进度也不应只记录在 Pod 内存中。Deployment 可以替换消费者，但前提是消息系统或数据库能够在替换后恢复消费位置，并允许按业务要求处理至少一次投递、重复投递与幂等。Deployment 解决的是“实例可替换”，不是“业务天然不丢、不重”。

### StatefulSet提供身份，不保证数据库一致性

### StatefulSet提供身份，不保证数据库一致性

对 IM 的 `db` 角色，StatefulSet 的价值是为每个副本提供可预测、可恢复的“成员身份”：

- Pod 名称稳定，如 `db-0`、`db-1`；
- 可通过无头 Service 获得稳定地址，如 `db-0.db`；
- 可为每个副本绑定独立 PVC，`db-0` 重建后仍可挂回原来的数据卷；
- 创建、删除和滚动更新可按序进行，便于数据库集群逐个加入或退出。

这解决的是**节点身份与存储归属**，不是“数据库已经高可用”。例如 `db-0` 的 PVC 还在，并不表示其中的数据一定最新；`db-1`、`db-2` 同时运行，也不意味着它们已完成复制，更不意味着发生故障时能安全选出唯一主库。

真正的一致性责任仍属于数据库系统及其运维方案：

- **数据复制**：确定同步或异步复制、复制延迟与追赶策略；
- **选主与脑裂防护**：保证任一时刻只有一个可写主节点；
- **事务语义**：由数据库保证提交、回滚、隔离级别和日志恢复；
- **备份恢复**：备份应与数据库日志、时间点恢复机制配合，而非仅复制 PVC；
- **故障切换**：明确主库失联、PVC 不可挂载、节点网络分区时的写入策略。

因此，不能因为 IM 当前 S2 只要求 `200` 表示“仅内存受理”，就把数据库设计简化为“部署一个 StatefulSet”。S3 即使仍限制 6B 正文，`gateway` 何时把消息视为持久化成功、`transfer` 如何重试、数据库主从切换期间是否拒写，都必须先定义。StatefulSet 只提供稳定的容器外壳；一致性由数据库协议、配置和恢复演练共同实现。

### 迁移任务用Job，并为重复执行设计幂等

### 迁移任务用Job，并为重复执行设计幂等

数据库迁移的目标不是持续对外提供请求，而是在有限时间内把数据库从版本 $v_n$ 推进到 $v_{n+1}$；完成后应退出。因此它适合用 `Job`，而不是 `Deployment`。`Job` 关心“直到成功完成”，可在迁移进程异常退出、节点故障或 Pod 被驱逐后创建新的 Pod 重试。

但“Pod 重试”不等于“迁移未执行”。控制器、节点和数据库之间存在观察延迟：迁移脚本可能已经提交了 `ALTER TABLE`，随后 Pod 在上报成功前崩溃；`Job` 看到失败后重试，新 Pod 就会再次执行同一迁移。网络超时也可能让脚本不知道事务究竟是否已提交。

因此迁移必须按“至少执行一次”设计，而非假设“恰好一次”：

- 建立迁移版本表，以唯一版本号记录已完成迁移；
- 每次运行先检查版本，再在事务中写入结构变更与版本记录；
- 使用可安全重复的操作，例如条件创建、唯一约束和显式状态检查；
- 不把“Pod 日志显示成功”当作数据库已完成的唯一依据；
- 为 `Job` 设置合理的重试次数与超时，失败后保留足够日志供人工判断。

例如迁移 `20250308_add_message_index` 已写入版本表时，重试实例应直接退出成功，而不是再次创建索引。

这也约束后续 S3 的数据库提议：即使数据落入 DB，当前协议的静态正文仍是 `6 UTF8B`，原始请求正文仍不超过 `4096B`。不能借“新增数据库字段”偷偷放宽消息载荷或改变既有 `409` 重复、`404` 非成员语义；迁移只演进存储结构，接口契约仍须单独审查。

### 沿Service、DNS与Ingress追踪请求路径

### 沿 Service、DNS 与 Ingress 追踪请求路径

以 `gateway` 为例，一次客户端 `POST /v1/messages` 通常经过：

`客户端 → Ingress → gateway Service → EndpointSlice → gateway Pod`

Ingress 负责七层 HTTP 路由：例如按域名 `im.example.com` 和路径 `/v1/` 转发到 `gateway-svc:8080`。它不直接“找到某个 Pod”，而是引用 Service。Service 再用 `selector`，如 `app: gateway`，筛选匹配标签且就绪的 Pod；控制器据此维护 `EndpointSlice`，其中记录可接收流量的 Pod IP 与端口。

因此，排障应按链路逐段检查：

- Ingress 规则是否匹配域名、路径和后端端口；
- Service 的 `selector` 是否与 Pod 标签完全一致；
- EndpointSlice 是否存在地址，且端点为就绪状态；
- Pod 是否监听 Service 所指向的 `targetPort`。

集群内的 `transfer` 可通过 DNS 名称访问 gateway，例如：

`http://gateway-svc.default.svc.cluster.local:8080`

通常同命名空间内写 `http://gateway-svc:8080` 即可。DNS 返回的是 Service 的稳定虚拟地址；Pod 被替换、IP 改变时，调用方不应缓存旧 Pod IP。

Ingress 并非“所有入口”的同义词。它主要处理 HTTP/HTTPS；若未来传输协议是任意 TCP，例如自定义长连接或数据库复制流，应使用负载均衡型 Service、网关控制器的 TCP 能力，或专用四层代理，而不是硬套 HTTP 路径规则。

验证替换时，可先持续请求 gateway，再删除一个 Pod。预期是 EndpointSlice 移除旧端点、加入新端点，Service 名称和 DNS 不变；少量连接中断或重试可接受，但 S2/v1 的重复提交仍应返回 `409`，不能因 Pod 替换而重复内存受理。

> **要点** — 控制器选择取决于状态与生命周期；Service负责发现，Ingress主要处理HTTP，业务正确性仍须由应用保证。

IM 网关和转发消费者可以横向扩容，但 Pod 可替换不代表连接、身份与处理进度会自动延续。

### 先按状态责任拆分网关与消费者

### 先按状态责任拆分网关与消费者

判断网关或转发消费者能否用 `Deployment`，关键不在于“有没有状态”，而在于状态由谁负责、Pod 消失后能否恢复。

- **进程本地状态**：如 TCP/WebSocket 连接对象、心跳计时器、内存会话表、正在执行的请求。这些状态随 Pod 终止而丢失，属于可接受的短暂状态；客户端应能感知断连并重连、重新鉴权和恢复订阅。
- **可重建缓存**：如用户路由缓存、房间成员快照、热点消息索引。可放本地内存以降低延迟，但必须允许失效；新 Pod 应能从 Redis、注册中心、数据库或事件流重新加载。
- **必须外置的业务状态**：如用户身份与权限、会话归属、消息确认位点、消费 checkpoint、幂等键、投递记录、订单或任务状态。这些不能只存在 Pod 内存中，否则滚动发布、扩缩容或故障迁移都会造成重复处理、漏处理或归属丢失。

因此，“无状态”更准确地说是：**Pod 不承担不可替代的业务状态责任**，并非系统没有业务状态。网关可以维护本地连接，但连接身份、路由归属和恢复依据应可查询或重建；消费者可以由 `Deployment` 扩容，但 checkpoint、分片归属与幂等判定必须由外部系统或可靠协调机制承担。

即使状态已外置，顺序语义仍需单独设计：按用户、会话或订单选择分区键，并限制同一键的并发消费者。外置 checkpoint 解决的是“从哪里继续”，不能自动保证“绝不乱序”或“绝不重复”。

### 网关多副本：Deployment 配合 Service

### 网关多副本：Deployment 配合 Service

IM 网关通常适合用 `Deployment` 管理多个副本，再用 `Service` 提供稳定入口。网关进程本身可以被替换、重建和横向扩容；客户端不应依赖某个 Pod 的地址，而应访问域名、负载均衡地址或 `Service` 暴露的端口。

`Deployment` 负责维持期望副本数，并支持滚动更新：新版本 Pod 先启动，通过 `readinessProbe` 后才加入可转发流量的后端集合；旧 Pod 则应先进入摘流状态，再等待已有请求完成或在宽限期后退出。扩容时，新就绪 Pod 自动成为后端；Pod 故障、节点驱逐或发布替换时，控制器会创建新 Pod，`Service` 将新连接导向健康副本。

但这里的“健康”必须由应用定义。网关仅仅进程存活，不等于能够认证用户、访问会话存储、连接消息系统或向下游投递。因此应将这些依赖纳入就绪检查，而不是只检查 HTTP 端口是否监听。

需要特别区分：`Service` 只负责把**新的入站连接**分发到可用 Pod，不会迁移既有 TCP/WebSocket 连接。某个网关 Pod 在滚动更新或故障时退出，其上的 WebSocket 通常会断开；客户端必须具备重连、重新认证和必要的消息补偿能力。可在终止前停止接收新连接，并配合 `preStop`、`terminationGracePeriodSeconds` 给长连接排空窗口，但不能假设连接会自动无缝转移。

### WebSocket 连接断开后不会自动迁移

### WebSocket 连接断开后不会自动迁移

WebSocket 是一条已建立的长连接：四层连接、HTTP 升级状态、心跳计时器、未发送缓冲区以及连接对象，都属于某个具体 Pod 的进程内存。`Deployment + Service` 能在 Pod 故障或滚动发布后提供新的后端实例，却不能把旧 Pod 上的 TCP/WebSocket 连接“搬运”到新 Pod。

因此，Pod 被驱逐、进程崩溃、发布终止或负载均衡链路超时后，客户端通常会观察到连接关闭、读写失败或长时间无响应。即使 Service 的地址不变，新连接也只会被转发到某个存活 Pod；它不知道旧连接属于谁，更不会复制该连接对应的内存会话、订阅列表、待确认消息或在线状态。

客户端应把断线视为常态，并设计明确的恢复流程：

1. 以指数退避加随机抖动重连，避免大量客户端同时重连形成尖峰。
2. 每次重连重新完成鉴权，携带可验证的访问令牌；不要把“来自同一条连接”当作身份依据。
3. 使用稳定的用户标识、设备标识和会话标识恢复业务上下文，而非依赖 Pod 内存中的连接 ID。
4. 客户端携带最后已确认的消息序号或游标，服务端据此补发缺失消息，或明确告知需要全量同步。
5. 对重连后的重复投递实施幂等处理；“至少一次补发”往往比“恰好一次送达”更可实现。

若需要跨 Pod 查询在线连接、恢复订阅或续接消息进度，应将必要状态放入外部系统，如 Redis、数据库或消息日志，并规定状态的过期、抢占和一致性规则。这样做并不意味着连接本身可迁移：新 Pod 只能建立一条新连接，再根据外部状态恢复业务会话。

### 消费者可部署，但顺序与进度需另管

### 消费者可部署，但顺序与进度需另管

转发消费者通常可以使用 `Deployment`：Pod 被替换、扩容或滚动更新时，新的实例重新加入消费组即可继续工作。但这一结论的前提不是“消费者没有状态”，而是其**可恢复的处理状态、分区归属和去重依据**不能只留在旧 Pod 内。

| 状态位置 | Pod 重启后的表现 | 适用性与风险 |
|---|---|---|
| 本地 checkpoint（文件、内存、临时盘） | checkpoint 随 Pod 消失；新实例可能从较早位置重放，或无从判断已处理位置 | 仅适合可接受全量重放、下游具备强幂等能力的场景 |
| 本地分区归属 | Pod 消失后归属信息失效；多个实例可能短暂争抢同一分区 | 不应作为唯一协调依据，需要消费组协议、租约或外部协调组件 |
| 外部进度存储 | 新 Pod 可读取已确认 offset、watermark 或任务游标并恢复 | 是使用 `Deployment` 的常见前提，但仍需处理提交时机与重复消费 |

例如，消费者处理消息后先写数据库、再提交 offset，若在两步之间崩溃，消息会被再次投递；因此数据库写入应以消息 ID、业务键或唯一约束实现幂等。反过来，若先提交 offset 再写业务结果，则崩溃可能造成消息永久丢失。

分区消费还要区分“可恢复”与“有序”。外部 checkpoint 只能说明从何处继续，不能保证扩缩容期间绝不重叠处理。若业务要求同一会话、订单或用户严格有序，应让同一业务键稳定映射到同一分区，并在分区再均衡时停止旧 owner、确认租约转移后再启动新 owner。跨分区全局顺序通常不能由 `Deployment` 自然提供，往往需要单独的串行协调或改变业务语义。

因此，更准确的表述是：消费者的**计算实例**可以是可替换的 `Deployment` Pod；业务处理进度、分区所有权、重复处理控制和顺序约束，则必须由消息系统、外部存储及幂等协议共同承担。

### 用替换演练验证可用性与一致性

### 用替换演练验证可用性与一致性

不要只验证“Pod 被删后副本数恢复”。应在预发环境构造真实会话与消息流，再主动删除运行中的网关或转发消费者 Pod：

1. **网关替换**：让客户端保持 WebSocket 长连接，持续发送带唯一 `message_id` 的消息。删除承载该连接的网关 Pod，记录断连时间、重连耗时、鉴权是否重新完成，以及重连后是否回到正确会话。预期通常是连接中断后由客户端重连；若业务要求消息不丢，客户端应能依据确认号或 `message_id` 补发。

2. **消费者替换**：持续向队列写入有序编号消息，在消费者处理到一半时删除 Pod。检查新 Pod 是否从外部 checkpoint、消费组位点或任务归属记录恢复，而非从头处理或跳过未确认消息。

3. **核对结果**：按消息编号比对生产端、队列、处理结果和最终存储，分别统计遗漏、重复、乱序与恢复延迟。重复并不必然是故障：至少一次投递下应验证幂等键、去重表或条件写入是否生效；若要求顺序，还要确认分区键、单分区并发度与重试路径未破坏顺序。

演练结论应写成可验收条件，例如：“网关重连在 5 秒内完成；消费者恢复后无遗漏；重复处理不产生重复账务”。这比笼统宣称“服务无状态、可随时替换”更可靠。

> **要点** — Deployment 解决副本替换与扩容；连接、身份、进度、顺序和幂等必须由协议与外部状态机制共同保障。

StatefulSet解决的是有状态实例的身份与存储绑定，不等于替应用承担数据库正确性与运维责任。

### 先按状态责任判断是否需要StatefulSet

### 先按状态责任判断是否需要 StatefulSet

判断是否使用 StatefulSet，先问：**某个实例被替换后，应用是否仍把它视为同一个成员？** 若答案是否定的，通常应优先选择 Deployment。

适合 StatefulSet 的典型信号包括：

- 实例持有不能随意丢弃或迁移的本地数据，例如分片数据、日志段、索引或数据库数据目录；
- 集群协议要求固定成员身份，如 `db-0`、`db-1`，成员以稳定名称加入复制组、选主组或仲裁组；
- 每个副本需要独立且可持续绑定的存储卷，例如 `db-0` 对应自己的 PVC，而不是所有副本共享一块可写磁盘；
- 扩缩容、启动和终止需要按序进行，以避免成员同时加入、离开或重建造成协议混乱。

StatefulSet 会为 Pod 提供稳定序号、稳定网络名和按副本创建的 PVC 关联。例如 Pod 重建后仍可作为 `db-0` 挂载原来的数据卷。这解决的是**身份与存储归属**，不是数据库高可用本身。

反过来，若服务实例是无状态的：请求可由任意副本处理，缓存可重建，数据已在对象存储、消息系统或外部数据库中持久化，副本名称也不参与业务协议，那么 Deployment 更简单、更适合弹性扩缩。

尤其不要因为“数据库需要磁盘”就自动选择 StatefulSet。PV/PVC 不会自动配置复制拓扑、故障仲裁、备份恢复、事务日志一致性或崩溃后的数据校验；这些仍由数据库软件及其运维流程负责。对于团队缺少相应能力的场景，使用外部托管或独立运行的数据库也可能更合适。

### 序号、稳定名称与无头服务如何协同

### 序号、稳定名称与无头服务如何协同

`StatefulSet` 会为每个 Pod 分配从 `0` 起递增的序号，并把序号写入稳定名称。例如名为 `db`、副本数为 `3` 的 StatefulSet，成员通常是：

- `db-0`
- `db-1`
- `db-2`

与 Deployment 中可替换、名称随机的 Pod 不同，`db-0` 即使因节点故障被重建，仍会尝试以同一名称恢复；若同时使用 `volumeClaimTemplates`，它还会重新绑定自己的 PVC。于是“第 0 个成员”不只是一次运行中的容器，而是可被应用识别的逻辑成员身份。

稳定名称需要无头 Service 才能转换为可解析的集群 DNS 记录。设无头 Service 名为 `db-headless`、命名空间为 `prod`，则每个成员可使用类似地址：

`db-0.db-headless.prod.svc.cluster.local`

无头 Service 的关键是 `clusterIP: None`：它不提供一个统一的虚拟 IP 来负载均衡请求，而是让 DNS 返回后端 Pod 的实际地址。因此，数据库进程可以依据固定成员列表发现彼此，例如由 `db-0` 主动连接 `db-1`、`db-2`，或将这些名称写入副本集、集群种子节点配置。

这组机制提供的是成员发现的基础：

$$
\text{逻辑成员序号} \rightarrow \text{稳定 Pod 名} \rightarrow \text{稳定 DNS 名} \rightarrow \text{可连接地址}
$$

但 DNS 只回答“某个名字当前指向哪里”，并不判断该成员是否已完成恢复、是否适合选主、是否拥有最新数据。数据库仍须自行处理启动顺序、健康检查、复制拓扑、仲裁与脑裂；StatefulSet 和无头 Service 不会替它们达成一致性。

### PVC绑定解决持久化，不解决数据库语义

### PVC 绑定解决持久化，不解决数据库语义

`PersistentVolumeClaim（PVC）` 的核心价值是：让 Pod 即使被重建、漂移到其他节点后，仍能重新挂载同一份持久卷数据。配合 StatefulSet，`db-0` 可以稳定地关联其 PVC，例如 `data-db-0`；Pod 名称和数据目录不会因一次调度失败而随机变化。

但这只保障了“数据卷如何存活和被重新挂载”，不保障“数据库如何正确运行”。两类责任必须分开看：

| 层次 | PVC / 存储层负责 | 数据库层仍需负责 |
|---|---|---|
| 数据存在 | 卷不随 Pod 删除而立即丢失（取决于回收策略） | 哪些数据已经提交、哪些日志可恢复 |
| 实例身份 | `db-0` 可绑定固定卷 | 节点是否是主库、是否允许写入 |
| 多副本 | 每个副本可有独立卷 | 复制协议、延迟处理、冲突与一致性 |
| 故障切换 | 新 Pod 可挂回旧卷 | 选主、仲裁、防止双主写入 |
| 数据保护 | 可提供快照或底层冗余 | 备份校验、时间点恢复、恢复演练 |

例如，`db-0` 所在节点故障后，控制器可能在其他节点重建 `db-0` 并挂载原 PVC；这不意味着它已经知道当前集群是否存在健康主库，也不意味着可以安全地自动提升该实例。若网络分区使两个节点都认为自己可写，PVC 不会阻止“双主”；若数据库写入尚未刷盘或复制尚未确认，PVC 也不能替它判定事务是否应提交、回滚或重放。

因此，使用 StatefulSet 自管数据库时，应把 PVC 视为数据库运行的必要基础设施，而非高可用方案本身。仍需依据具体数据库设计复制、仲裁、选主、备份、恢复与监控机制；在这些能力难以可靠维护时，外部托管数据库也可能更合适。

### 用自管数据库故障场景检验误解

### 用自管数据库故障场景检验误解

假设一个三副本数据库运行在 `db-0`、`db-1`、`db-2` 上，每个 Pod 通过 StatefulSet 获得稳定名称，并绑定各自的 PVC。它们解决的是“谁是谁、数据盘通常跟谁走”，而不是“数据一定正确”。

- **Pod 被替换**：`db-1` 因探针失败重建后，仍叫 `db-1`，也会重新挂载原 PVC；但重启前未刷盘的日志、损坏的本地状态、错误的成员配置不会因此自动修复。若数据库需要恢复流程、日志回放或人工确认，Kubernetes 不会替它完成。
- **节点故障**：节点宕机时，PVC 能否在其他节点重新挂载取决于存储类型和访问模式；即使成功挂载，也必须保证旧节点已失去写入能力。否则原节点“复活”后继续写盘，可能形成双主或数据损坏。
- **网络分区**：`db-0` 与其余副本失联时，三者的 Pod 名和 PVC 都仍然稳定，但系统必须自行判断谁拥有多数派、谁可继续接受写入、隔离副本如何追赶数据。稳定 DNS 不提供仲裁，更不等于一致性协议。
- **误删与逻辑错误**：应用执行一次错误 `DELETE`，复制会把错误同步到所有副本；PVC 保留的是当前磁盘状态，不是可验证的时间点备份。恢复仍依赖备份、日志与演练。

因此，StatefulSet 是部署数据库实例的基础设施工具；复制、选主、脑裂防护、备份恢复和事务正确性，仍是数据库软件及其运维流程的责任。

### 自管与外部数据库的选择边界

### 自管与外部数据库的选择边界

是否把数据库放进 Kubernetes，不应由“已经有集群”决定，而应由团队能否持续满足数据可靠性目标决定。StatefulSet、稳定 Pod 名、PV/PVC 只能提供实例身份与存储绑定；它们不会自动完成复制拓扑、主从切换、仲裁、备份校验、跨区域容灾、权限审计或崩溃后的事务恢复。

优先评估外部数据库的典型信号包括：

- 团队缺少数据库专职运维能力，无法处理升级、慢查询、容量规划和故障演练。
- 恢复点目标（RPO）和恢复时间目标（RTO）严格，且需要可验证的备份、时间点恢复或异地容灾。
- 业务需要高可用，但无法接受自行维护副本、故障检测与切主流程的复杂度。
- 数据库生命周期独立于应用集群：应用可以频繁发布、扩缩容或重建，数据层却应保持更强的隔离与变更控制。
- 平台已有可用的托管能力，能够明确提供版本维护、监控告警、备份恢复和服务等级承诺。

集群内自管更适合数据库规模较小、依赖低延迟本地网络、具备明确运维负责人，且团队已经将备份恢复、复制与故障处置自动化并定期演练的场景。此时 StatefulSet 是部署基础设施的一部分，而不是数据库高可用方案本身。

决策时应先写清楚“数据丢失多久可接受、服务中断多久可接受、谁在凌晨处理故障”，再比较自管与外部能力是否真正覆盖这些要求。

> **要点** — StatefulSet提供稳定身份和存储关联；数据库一致性、可用性与恢复仍须由数据库机制和运维方案负责。

历史回填和未来模式迁移都可由 Job 执行，但“任务完成”只说明进程按退出条件结束，不能替代数据对账、幂等设计与权限控制。

### 先按任务边界判断是否使用 Job

### 先按任务边界判断是否使用 Job

是否使用 Job，先看“工作何时自然结束”，而不是看它是否会读写数据库。

- **一次性、边界明确的批处理**适合 Job。例如按指定时间范围回填历史数据、把某批旧格式记录迁移到新结构、重建某个索引分片。任务输入应可描述为稳定集合，如“处理 `2024-01-01` 至 `2024-03-31` 的订单”，并在处理完毕后退出。此时 Job 的成功状态表示工作进程已按设计结束，但仍应另行核对处理数量、成功数、失败数与目标数据一致性。

- **持续消费、没有自然终点的工作**不应伪装成 Job。例如持续订阅消息队列、监听对象存储事件、长期执行同步循环。这类程序即使暂时没有消息，也不代表任务完成；应使用长期运行的服务工作负载，并配合健康检查、扩缩容与重启策略。

- **影响不可逆或需要业务裁决的数据修复**通常不宜直接全自动执行 Job。例如批量删除异常账目、合并重复客户、修正已结算金额。可以由 Job 执行已审批的确定性步骤，但应先生成修复计划、抽样验证和人工确认记录；将“找出候选项”与“实际写入修复”分离。

Job 的边界还应体现在参数和权限上：限定数据范围，使用最小权限身份，并为每条处理对象建立幂等键、检查点或事务。即使设为 `parallelism: 1`、`completions: 1`，失败重试、节点故障或人工重建仍可能使程序再次运行；因此不能把“只启动一次”当作正确性的保证。

### 完成状态不等于数据已正确回填

### 完成状态不等于数据已正确回填

Kubernetes Job 显示 `Complete`，通常只表示：控制器观察到足够数量的 Pod 以退出码 `0` 结束。它证明的是**进程完成了自己的退出路径**，而不是“所有历史记录都已正确迁移”。

例如，回填程序可能在以下情况下仍以成功状态退出：

- 分页游标计算错误，只扫描到前 90% 的数据；
- 某些记录解析失败后仅打印日志并跳过；
- 写入目标库超时，程序未等待异步请求真正落盘；
- 批量写入部分成功、部分失败，却把异常吞掉；
- 查询副本存在延迟，任务扫描时尚未看见应处理的旧数据；
- 任务依据“已发送请求数”退出，却没有确认“已提交且可读取数”。

因此，`status.succeeded=1` 不是数据质量指标。即使 `parallelism: 1`、`completions: 1`，也只能减少并发协调问题，不能自动保证覆盖完整性或写入正确性；Pod 重试、节点故障或控制器重建仍可能让同一逻辑再次执行。

可靠回填应把“完成”拆成可验证的条件：

1. **覆盖性**：记录源端扫描范围、分片边界或高水位线，确认没有遗漏区间。
2. **提交性**：每批数据在目标端获得事务提交、持久化确认或可重试的写入结果。
3. **幂等性**：为每条记录使用稳定业务键、迁移版本或去重键，使重复运行不会重复扣费、重复建资源或覆盖新数据。
4. **可恢复性**：保存检查点；失败后从最后一个已确认位置继续，而非盲目从头或直接跳过。
5. **对账性**：比较源端与目标端的数量、校验和、状态分布及抽样内容，必要时生成未匹配清单。

可以把 Job 的成功状态视为“回填程序已停止”，而把对账报告视为“回填结果已被证明”。只有二者同时满足，迁移才能进入下一阶段。

### 单并发任务仍可能重复运行

### 单并发任务仍可能重复运行

`parallelism=1`、`completions=1` 只约束“控制器期望一个成功完成”，并不保证某段业务逻辑在物理世界中只执行一次。Job 的语义更接近**至少执行一次直到观察到成功**，而不是精确一次。

典型时序如下：

1. Pod 已启动并写入一批历史数据，随后进程崩溃、Pod 被驱逐或节点失联；控制器尚未得到成功状态，会创建新的 Pod 重试。新 Pod 若从头处理，就会重复写入。
2. 任务实际上已完成并提交结果，但节点故障或网络中断导致 Job 控制器未及时观察到 Pod 的 `Succeeded` 状态；控制器可能先判断原执行不可用并补建 Pod。
3. 程序先完成外部副作用，例如调用支付、写对象存储、发送消息；再尝试上报完成。若上报前退出，重试实例无法知道副作用是否已经发生。
4. 人工删除 Pod、镜像拉取失败、存活环境异常等，也会触发新的执行尝试；单并发只意味着这些尝试通常不并行，不意味着不会先后发生。

因此，不能把“只有一个 Pod”当作防重机制。每条回填记录应携带稳定的幂等身份，例如源表主键、业务事件 ID 或 `(任务批次, 记录键)`；目标写入采用唯一约束、条件更新或幂等 API。处理进度应通过检查点或事务持久化：先安全提交数据与进度，再允许任务退出。

还要区分两件事：Job 成功表示控制器观察到一次成功退出；数据完成则需要按预期范围对账，例如比较源、目标计数，核验缺失键与重复键。对于跨系统副作用，使用事务性写入、去重表或可靠消息模式，并让 Job 的服务账号仅拥有完成该任务所需的最小权限。

### 用幂等键、检查点和事务收敛副作用

### 用幂等键、检查点和事务收敛副作用

回填 Job 的最小单位不应是“第几次运行”，而应是可稳定重建的业务记录。为每条待处理数据定义幂等键，例如：

`迁移版本 + 源表主键 + 源记录版本`，或 `回填批次 + 租户 + 业务对象ID`

目标表以该键建立唯一约束；写入时使用条件写入或 `upsert`：不存在则创建，已存在且版本相同则视为成功，已存在但版本更新则按明确的版本规则覆盖或拒绝。这样即使 Pod 重启、Job 被重复调度，第二次执行也不会制造重复副作用。

进度检查点应记录“已提交的边界”，而非“已读取的位置”。例如按主键范围扫描时保存最后成功提交的 `last_id`；按时间扫描时同时保存时间戳和主键作为复合游标，避免相同时间戳下跳过记录。检查点至少包含：

- 回填批次、分片编号与输入范围；
- 已提交游标、处理数量、失败数量；
- 程序版本、规则版本与更新时间；
- 状态：`运行中`、`完成`、`需人工处理`。

关键原则是：**目标写入与检查点推进必须处于同一事务边界**。若先写数据再更新检查点，崩溃后会重放，因此写入必须幂等；若先推进检查点再写数据，崩溃后会永久漏数。关系型数据库中可将“写目标记录、写处理流水、更新检查点”放入一个事务；跨库或调用外部接口时，通常无法获得全局事务，应采用本地事务加发件箱模式，由独立投递器按幂等键重试外部副作用。

完成前还应以输入范围、成功流水和目标聚合结果做对账。`Job Complete` 只表示所有容器已按退出条件结束；只有检查点封口、失败项归零或进入显式补偿队列，并且对账通过，才可宣布该批回填完成。权限上，Job 仅应拥有读取源数据、写入指定目标表与更新自身检查点的最小权限。

### 把权限与对账作为回填的最后闸门

### 把权限与对账作为回填的最后闸门

例如，需要用历史订单消息回填新建的分析索引。该 Job 不应获得“读取全部消息、写入全部数据库”的宽泛权限，而应被限制为：

- 仅能读取指定主题、指定消费者组或明确的时间区间，例如 `orders` 中 `2024-01-01` 至 `2024-01-31` 的分区偏移范围；
- 仅能向目标索引的指定前缀或目标表的指定分区写入，例如 `order_analytics_backfill_v2`；
- 仅能读取必要的密钥、模式定义和检查点位置，不能修改生产者、删除源消息或调整其他消费组偏移；
- 使用独立服务账号，并记录 Job 镜像版本、操作者、审批单号、起止偏移、写入条数与失败明细。

回填应按可重试的小批次推进，而不是一次处理全部历史。例如每批覆盖固定偏移区间，在提交目标数据时同时写入检查点：

`批次完成 = 目标写入事务提交 + 检查点提交`

记录的幂等键可为 `(订单ID, 事件版本)`，或 `(主题, 分区, 偏移量)`；重复运行同一批次时，写入操作必须成为更新、去重插入或条件写入，而不能产生重复聚合结果。

Job 显示 `Complete` 后，还要进行业务对账。至少比较源端与目标端的消息数、唯一订单数、金额汇总、状态分布及异常记录数；对每个批次校验：

$$\text{源端可处理记录数}=\text{目标成功记录数}+\text{明确隔离的失败记录数}$$

隔离记录必须带有原因、原始位置和处置责任人，不能因“跳过坏数据”而悄悄丢失。只有检查点连续、权限审计完整、批次校验通过，并且业务口径对账通过后，才应将回填标记为真正完成。

> **要点** — Job 负责运行到退出，不负责证明数据正确；可重试任务必须以幂等、检查点、事务、权限和对账共同保证结果。

Service用稳定名称连接一组可替换的Pod，但它解决的是发现与转发，不是副本同步、请求去重或连接迁移。

### 从标签到稳定服务地址

### 从标签到稳定服务地址

Service 的核心作用是：用一条稳定的访问入口，代表一组会变化的 Pod。创建 Service 时，通常写入标签选择器，例如：

`app=orders`、`tier=backend`

控制平面持续查找匹配这些标签的 Pod，并将可作为后端的地址记录到 EndpointSlice。Pod 因滚动更新、扩缩容、故障重建而获得新 IP 时，客户端不必改配置；Service 对外的名称和虚拟地址保持不变，后端列表则随之更新。

例如，`orders` Service 选择带有 `app=orders` 标签的 Pod。集群内其他工作负载访问：

`http://orders:8080`

DNS 会将同一命名空间中的短名 `orders` 解析到该 Service 的稳定地址。跨命名空间访问时，应显式带上命名空间：

`orders.payments`

完整名称通常形如：

`orders.payments.svc.cluster.local`

其中 `cluster.local` 是常见默认集群域，但可由集群配置修改，不能在程序中硬编码。

需要区分“稳定入口”和“稳定连接”：Service 可以把**新建连接**转发到当前后端，却不会把已有的长连接从旧 Pod 无缝迁移到新 Pod。旧 Pod 终止、连接被关闭或网络路径失效后，客户端仍需依靠超时、重连和幂等设计恢复请求。Service 也不会复制多个后端的状态，更不保证请求只执行一次。

### EndpointSlice中的可用后端

### EndpointSlice中的可用后端

Service 的 `selector` 不直接保存某个固定 Pod IP，而是持续匹配带有相应标签的 Pod。控制器据此生成或更新 `EndpointSlice`：其中每个 endpoint 通常包含后端地址、端口、所在节点，以及反映生命周期的条件。Pod 被删除、重建或扩缩容时，IP 可以变化；Service 名称保持不变，但其可转发后端会随 EndpointSlice 更新。

关键条件可这样理解：

- `ready`：该地址是否应接收普通 Service 流量。通常与 Pod 的就绪探针和 `Ready` 状态相关；`ready: true` 表示可作为常规负载均衡后端。
- `serving`：该端点上的应用是否仍在提供服务。它可在终止过程中继续为真，表示应用可能仍在处理已有请求或允许优雅关闭。
- `terminating`：该 Pod 是否已进入终止流程。`true` 意味着它不应再被视为普通的新连接目标，但实现可以结合 `serving` 做连接排空。

因此，典型的健康运行端点是：

`ready: true, serving: true, terminating: false`

而一个正在优雅终止的端点可能是：

`ready: false, serving: true, terminating: true`

这表达的不是“立刻不可达”，而是“停止分配新流量，同时让仍存活的服务完成收尾”。具体数据平面如何处理既有连接取决于 kube-proxy、负载均衡器和应用协议；Kubernetes 不会把已有长连接透明地迁移到新 Pod。

### DNS名称的作用域与写法

### DNS名称的作用域与写法

设即时通信网关 `im-gateway` 需要调用消息消费者 `message-consumer`，并访问数据库代理 `db-proxy`。Service 的 DNS 名称通常按以下层级解析：

- **同一命名空间：使用短名即可。**  
  若网关与消费者都在 `chat` 命名空间，网关可连接：

  `http://message-consumer:8080`

  Kubernetes 会将短名补全并在当前命名空间中查找对应 Service。数据库代理也可写为：

  `db-proxy:5432`

- **跨命名空间：显式写出命名空间。**  
  若数据库代理位于共享基础设施命名空间 `data`，而网关仍在 `chat`，应使用：

  `db-proxy.data:5432`

  这避免当前命名空间恰好也存在同名 `db-proxy` 时发生误连。消费者若位于 `worker` 命名空间，则写作：

  `message-consumer.worker:8080`

- **完整域名：用于跨集群配置、排障或需要明确解析边界时。**  
  Service 的完整名称通常是：

  `服务名.命名空间.svc.集群域名`

  例如：

  `db-proxy.data.svc.cluster.local:5432`

  其中 `cluster.local` 只是常见默认值，实际集群域名可以配置，不能把它硬编码为不可变事实。应用配置中若必须使用完整域名，应以集群部署参数注入。

DNS 解析到的是 Service 的稳定入口，而非某个固定 Pod IP。消费者 Pod 被滚动替换后，其 IP 可变化；网关重新建连时仍应通过 Service 名称访问。已有长连接不会因为 DNS 或 EndpointSlice 更新而自动迁移到新 Pod，因此连接重试、超时和优雅下线仍需由应用与网关策略处理。

### Pod替换后的连接边界

### Pod替换后的连接边界

当后端 Pod 被删除、驱逐或重建时，新的 Pod 通常获得新的 IP。Service 名称不变，`selector` 会重新匹配 Pod，控制面随后更新 EndpointSlice：旧端点被标记为不再接收流量，新端点在通过就绪探针后才进入可选后端集合。

这对**新连接**和**已有长连接**的影响不同：

- **新连接**：客户端仍访问同一个 Service DNS 名称或 ClusterIP。转发规则会依据更新后的 EndpointSlice 选择新的 `ready` 后端，因此通常会落到新 Pod。
- **已有连接**：连接建立后，数据包已由连接跟踪状态绑定到某个具体 Pod IP。EndpointSlice 更新不会把这条 TCP、WebSocket、gRPC 流或数据库连接“迁移”到新 Pod；旧 Pod 退出、进程关闭或节点网络消失时，连接仍会中断、超时或收到重置。
- **终止中的 Pod**：端点可能同时体现 `ready`、`serving`、`terminating` 等条件。应用应在收到终止信号后停止接受新请求，同时保留短暂的优雅退出窗口，尽量完成正在处理的请求。

因此，Service 提供的是“后端可替换时的新请求发现与转发”，不是连接连续性保证。应用层应为长连接设计重连、退避、幂等请求标识和必要的会话恢复；对可重试操作，还要区分“请求未送达”与“服务端可能已经执行但响应丢失”，避免重连后产生重复写入。

### Service不承诺的事情

### Service不承诺的事情

Service 的职责是：用标签选择一组 Pod，为它们提供稳定的访问入口，并把流量转发到当前可用的后端。它解决“该连谁、入口地址是否稳定”的问题，但不替代应用协议、数据复制或会话管理。

| 能力 | Service 提供 | Service 不提供 |
|---|---|---|
| 后端发现 | 根据 `label selector` 找到 Pod，并通过 DNS 暴露稳定名称 | 保证每次请求都落到同一个 Pod |
| 流量转发 | 将新连接或请求转发到 EndpointSlice 中可用的端点 | 复制副本间的数据、状态或缓存 |
| 副本替换 | Pod 重建后更新后端 IP 列表 | 保持旧 Pod IP 不变，或迁移既有连接 |
| 健康参与 | 依据 `ready`、`serving`、`terminating` 等状态决定端点可用性 | 保证业务请求一定成功、一定幂等 |
| DNS 入口 | 提供如 `api`、`api.payments` 的稳定名称 | 保证 DNS 查询结果永久不变或立即刷新 |

例如，三个副本都匹配 `app=orders`，并不意味着它们天然共享内存、文件或数据库事务。若请求 A 写入副本 1 的本地内存，随后请求 B 被转发到副本 2，副本 2 不会自动看到该状态；共享状态必须交给数据库、缓存、消息系统或应用复制协议。

同样，Service 不保证 HTTP `409 Conflict`。`409` 是应用根据资源版本、唯一约束或并发更新规则产生的业务响应；Service 只转发请求，不理解“订单是否重复提交”或“版本是否冲突”。

长连接尤其需要显式设计。Pod 被替换时，其 IP 会变化，EndpointSlice 也会更新；但已经建立的 TCP、WebSocket 或 gRPC 流不会被 Service “透明搬迁”到新 Pod。应用应结合优雅终止、连接排空、客户端重连、请求幂等与断点恢复，处理后端退出和重连后的状态一致性。

> **要点** — Service以标签和DNS稳定发现可用后端；Pod可替换，但连接连续性与业务一致性必须由应用自行设计。

本节追踪两条流量路径：外部 HTTP(S) 如何经 Ingress 到达网关，内部业务请求又如何发现数据库服务。

### 从外部域名到网关 Pod 的请求链路

### 从外部域名到网关 Pod 的请求链路

一次面向外部域名的 HTTP(S) 请求，可抽象为：

`客户端 A → 负载均衡/IP → Ingress Controller → Ingress 规则 → gateway Service → Ready gateway Pod`

各层并不重复，而是分别承担不同责任：

1. **客户端 A**  
   访问如 `https://api.example.com/orders`。DNS 将域名解析为集群入口暴露的公网 IP、负载均衡地址或节点地址；TLS 握手也通常在入口处终止，具体取决于 Ingress Controller 配置。

2. **Ingress Controller**  
   Ingress 只是声明 `host`、`path`、后端 Service、TLS 等规则的 Kubernetes API 对象；真正监听流量、解析 HTTP(S) 并执行转发的是 Controller，例如 NGINX Ingress、Traefik 或云厂商控制器。没有 Controller，Ingress 规则不会产生实际流量路径。

3. **Ingress 路由规则**  
   Controller 根据请求的 `Host: api.example.com` 与路径 `/orders` 匹配规则，例如：

   `api.example.com + / → gateway Service:80`

   因而 Ingress 的核心语义是 HTTP(S) 的域名与路径路由，不应将其视为任意 TCP 协议的通用四层代理。

4. **gateway Service**  
   Controller 将请求发送给 `gateway` Service。Service 提供稳定的虚拟访问点和标签选择器，不直接等同于某个固定 Pod；其后端来自与选择器匹配的 EndpointSlice。

5. **Ready gateway Pod**  
   只有通过就绪探针、处于 `Ready` 状态的 gateway Pod，通常才会进入 Service 的可用后端集合。请求最终由其中一个 Ready Pod 接收并处理；Pod 重建、扩缩容或迁移时，Service 后端会随之更新，入口域名与 Ingress 规则无需改变。

因此，排障应按链路逐层检查：DNS/入口可达性、Controller 状态与日志、Ingress 的 host/path 匹配、Service 端口与选择器，以及目标 Pod 是否真正 Ready。

### Ingress 只定义 HTTP(S) 路由规则

### Ingress 只定义 HTTP(S) 路由规则

Ingress 是面向 HTTP(S) 的第七层入口规则：它把客户端请求中的 `Host` 与 URL `Path`，映射到集群内某个 `Service` 的端口，而不是直接选中某个 Pod。

例如，外部请求可按如下关系匹配：

- `https://api.example.com/` → `gateway` Service 的 `8080` 端口；
- `https://api.example.com/v1/` → `gateway` Service 的 `8080` 端口；
- `https://web.example.com/` → `frontend` Service 的 `80` 端口。

匹配后，实际链路是：

`客户端 → Ingress Controller → gateway Service → Ready Pod`

其中，`host` 用于区分域名，`path` 用于区分同一域名下的业务前缀。若采用 `Prefix` 路径类型，`/v1` 通常可匹配 `/v1/orders`；若采用 `Exact`，则只匹配完全相同的路径。具体边界行为仍应以所用控制器的实现和配置为准。

关键点是：Ingress 资源本身只是声明规则，不会自行监听端口、申请负载均衡器或转发流量。必须有 Ingress Controller 监视该资源，并将规则落实为 NGINX、云负载均衡器、Traefik 等实际代理配置。没有 Controller，Ingress 只是一个不会生效的对象。

它也不是任意 TCP 协议的通用入口抽象；数据库、消息队列等 TCP 流量通常应通过 `Service`、控制器专用 TCP 配置或其他网关能力暴露。

### Service、EndpointSlice 与就绪状态如何决定后端

### Service、EndpointSlice 与就绪状态如何决定后端

网关通常暴露为一个 `Service`。客户端或 Ingress 不需要知道具体 Pod IP，而是访问稳定的服务名或虚拟 IP：

`Ingress → gateway Service → EndpointSlice 中的 Ready Pod`

`Service` 的 `selector` 选中带有匹配标签的 Pod，例如 `app=gateway`。控制平面随后根据这些 Pod 的 IP、端口和就绪状态维护 `EndpointSlice`；它是“此刻哪些实例可作为后端”的实际清单。

DNS 的作用是把诸如 `gateway.default.svc.cluster.local` 解析为 Service 的访问地址，而不是直接替代健康检查。请求进入 Service 后，`kube-proxy` 或相应数据平面再依据 EndpointSlice 将流量转发给具体后端。

关键在于 `Ready` 条件：

- Pod 尚未通过 `readinessProbe`，通常不会作为可用端点加入常规流量后端。
- Pod 关闭时应先变为未就绪，再等待连接排空，最后退出；这样新请求不会继续进入该实例。
- 进程“已启动”不等于“能接流量”。网关可能仍在加载配置、建立上游连接或恢复缓存，因此应以就绪探针表达真实可服务状态。
- 若 selector 标签错误，Service 可能没有任何 EndpointSlice 后端；若探针过宽松，则请求会被送往表面存活、实际尚未准备好的 Pod。

因此，Service 提供稳定入口，DNS 提供稳定发现名称，EndpointSlice 提供动态后端集合，而就绪状态决定该集合中哪些 Pod 应真正承接网关流量。

### WebSocket、长连接与非 HTTP 流量的边界

### WebSocket、长连接与非 HTTP 流量的边界

WebSocket 的握手起点仍是 HTTP(S)：客户端先发送带 `Upgrade: websocket` 的 HTTP 请求，Ingress 可按 `host`、`path` 将其路由至 `gateway Service`，再由 Service 选择一个 `Ready Pod`。握手成功后，连接升级为长期双向字节流；它能否稳定工作，不只取决于规则匹配，还取决于具体 Ingress Controller 是否正确透传升级头、支持所选 TLS 配置，并允许足够长的空闲时间。

可将外部路径理解为：

`客户端 A → Ingress/Controller → gateway Service → Ready gateway Pod`

但不要把这条路径泛化为“Ingress 能代理所有端口和协议”。标准 Ingress 的通用语义主要是 HTTP(S) 的主机名与路径路由；任意 TCP、UDP 或自定义二进制协议通常需要 Controller 提供额外配置、专用资源，或改用 `Service` 的 `LoadBalancer`、`NodePort` 等暴露方式。不同 Controller 对四层转发的配置入口和能力并不一致。

长连接还必须验证三类行为：

- **超时**：负载均衡器、Controller、上游代理与应用的读写/空闲超时是否一致；必要时设计心跳。
- **连接迁移**：Pod 滚动更新、失去 Ready 状态或节点故障时，既有 WebSocket 通常不会自动迁移到新 Pod；应用应支持断线重连、会话恢复或幂等重放。
- **协议链路**：若前端使用 HTTP/2、TLS 终止或多层代理，应确认 Upgrade、转发头和后端协议版本均被实际支持。

相对地，内部数据库访问通常是：

`transfer Pod → db Service → Ready db Pod`

它依赖 Service 的服务发现与端口转发，不经过 HTTP Ingress；数据库协议、连接池和故障重连应按其自身客户端语义设计。

### 网关访问数据库的内部发现路径

### 网关访问数据库的内部发现路径

网关处理外部请求后，业务组件 `transfer` 不应直接记忆某个数据库 Pod 的 IP，而应通过稳定的 `db` Service 发现数据库：

`transfer Pod → db Service 的 DNS 名称 → Service 虚拟地址 → 就绪的数据库 Pod`

例如，`transfer` 使用 `db`、`db.命名空间` 或完整集群域名访问数据库。集群 DNS 将名称解析为 Service 地址；随后由 Service 依据选择器关联的 EndpointSlice，把连接转发到标记为 `Ready` 的数据库 Pod。数据库重建、扩缩容或 Pod IP 变化时，只要标签和就绪状态正确，调用方通常无需修改连接目标。

这条链路与外部入口不同：

- **Ingress 入口链路**：`客户端 → Ingress → gateway Service → Ready gateway Pod`。它面向集群外 HTTP(S)，按 `host`、`path` 等七层规则选择后端，并依赖具体 Ingress Controller 实现。
- **内部发现链路**：`transfer → db Service → Ready db Pod`。它面向集群内服务调用，核心职责是名称发现、稳定访问点和后端端点选择，而不是 HTTP 路由。

因此，Ingress 解决“外部请求怎样进入网关”，`db` Service 解决“网关内部业务怎样持续找到数据库”。若数据库使用长连接，还应验证连接池、故障重连与 Pod 切换期间的应用行为。

> **要点** — Ingress 负责 HTTP(S) 入口规则，不等于通用四层代理；实际可达后端由 Controller、Service 与 Ready Endpoint 共同决定。

本节用四个“看似正常、实际失效”的反例，建立从平台信号到业务验收与回退决策的验证框架。

### 先分清源码事实与平台事实

### 先分清源码事实与平台事实

OpenIM 源码中的两处实现证据，最多回答“应用**意图如何工作**”：例如会话如何建立、消息如何去重、任务如何重试、配置项会被怎样读取。它们不能直接证明 Kubernetes 中的工作负载、存储与网络已经按该意图正确落地。

应把证据分为两层：

- **源码事实**：某服务使用本地内存保存去重状态；某组件依赖数据库持久化；某任务可能重试；客户端会复用长连接。
- **平台事实**：该服务实际有多少副本；副本是否共享状态；PVC 是否绑定到预期卷；数据库是否具备复制与故障切换；Service 后端端点是否更新；连接断开后客户端能否重连。

例如，源码出现“重复消息返回 `409`”并不等于跨 Pod 去重成立：若 S2 去重表在本地内存，多个副本各自独立，重复请求仍可能被不同 Pod 分别接受。源码显示数据库写入成功，也不等于 StatefulSet 已实现高可用：PV 存在只证明存储挂载，不能证明主从复制、日志同步或故障恢复。Job 的重试逻辑同样不能证明幂等；重跑时是否双写，取决于唯一约束、事务边界和补偿机制。

因此，每个结论都应补齐三类验证：

1. **平台证据**：`Deployment`、`StatefulSet`、`Job`、PVC、Service、EndpointSlice 与事件记录。
2. **业务验收**：跨 Pod 重复提交、主库切换、Job 重跑、旧 TCP 连接后端变更等真实场景。
3. **回退路径**：缩容到单副本、暂停任务、切回旧数据库实例或摘除异常端点。

源码是排查起点，不是 Kubernetes 配置正确性的证明。

### Ready不代表跨Pod去重正确

### Ready不代表跨Pod去重正确

设 S2 服务有两个副本。每个 Pod 都通过就绪探针，`Service` 也有正常后端；但去重键只保存在 Pod 本地内存：

`request_id -> 已处理结果`

第一次请求到达 Pod A，A 完成创建并记录 `request_id=r1`。客户端因超时重试、网关重连或负载均衡切换，第二次请求落到 Pod B。B 不知道 A 已处理过 `r1`，于是再次执行业务写入；若下游存在唯一约束，最终可能返回 `409 冲突`。此时 Kubernetes 的视角仍是“全部 Ready”，但业务语义已经从“幂等重试”退化为“重复处理或冲突失败”。

需要区分三层信号：

- **就绪探针**：只能说明该 Pod 当前可接收流量，例如端口可达、依赖未明显失效；它不证明多个 Pod 共享去重状态。
- **会话路由**：粘性会话可暂时提高同一请求落回原 Pod 的概率，但缩容、滚动更新、连接迁移和网关重试都会打破这一假设，不能作为幂等保证。
- **分布式业务状态**：去重记录必须进入所有副本可共同读取、可原子竞争的存储，例如数据库唯一键、Redis 原子写入或专用幂等表。

平台证据应记录：两个 Pod 均为 `Ready`、Service 后端列表正常、同一 `request_id` 的访问日志分别命中不同 Pod。业务验收则应主动制造“首请求后切换 Pod”的重试：结果必须只产生一条业务记录，后续请求返回首次结果或明确的幂等响应，而非新增写入或 `409`。

若验证失败，回退不应只是增加探针或强制粘性路由；应先停止扩容与滚动发布，将 S2 恢复为单副本或固定路由作为短期止损，再把去重状态迁移到共享存储，并以跨 Pod 重试测试作为发布门禁。

### PV存在不等于数据库已复制

### PV存在不等于数据库已复制

`StatefulSet` 能提供稳定的 Pod 名称、顺序启动语义和每副本独立的 `PVC`，例如 `db-0` 始终挂载自己的数据卷。`PVC` 在 Pod 重建后仍存在，也只能说明“某个节点曾持有并保留过本地数据”；它不证明 `db-0` 与 `db-1` 之间已经建立复制链路，更不证明故障时可安全提升从库。

| 看似成立的平台信号 | 仍可能缺失的业务事实 |
|---|---|
| StatefulSet `Ready=3/3` | 三个实例可能都是独立初始化的数据集 |
| PVC 均为 `Bound` | 卷内数据可能陈旧、损坏或落后于主库 |
| Headless Service 可解析 `db-0`、`db-1` | DNS 只提供寻址，不配置复制拓扑 |
| Pod 重建后数据仍在 | 保留的是旧盘，不是已确认复制的数据 |

验证应分三层进行。**平台证据**：检查 `StatefulSet` 副本、PVC 绑定、反亲和与存储访问模式；这只能确认身份和持久化路径。**复制证据**：从主库查看副本连接、复制延迟、日志位点或事务序号；从每个副本确认其上游、只读状态及已追平的位点。**业务验收**：向主库写入带唯一标识的记录，等待复制确认后在副本读取；再模拟主库不可用，执行受控提升，并验证新主库包含确认写入且旧主恢复后不会形成双主。

故障切换尤其不能只依赖 Pod 调度。若主库网络隔离但进程仍可写，自动提升另一个副本会产生脑裂；若复制为异步模式，最近提交的数据可能尚未到达候选主库。应明确可接受的恢复点目标：要求零丢失时，需要同步确认、仲裁或围栏；允许有限丢失时，也要记录最大可接受复制延迟。

回退前先停止写流量并冻结自动切换，保留各卷与复制日志作为证据；确认权威主库后，让其他实例以重新追随或重建副本的方式加入，不能把旧 PVC 直接当作可信主库启动。OpenIM 的源码实现至多说明应用如何连接数据库，不能替代 Kubernetes 存储、复制、切换与一致性的运行时验证。

### Job重跑为何会造成双写

### Job重跑为何会造成双写

`Job` 的成功语义是“某个 Pod 最终成功完成”，不是“业务动作恰好执行一次”。Pod 失败、节点中断、容器退出码异常、控制器观察延迟，都会触发重试；更棘手的是：第一次执行可能已提交数据库事务，但 Pod 尚未来得及上报成功便被终止。控制器据此创建新 Pod，第二次执行便可能再次扣款、再次发券或再次写入消息。

因此，不能用 `Job Complete=1` 证明业务只执行一次。应把重复执行视为默认故障模型，并在业务边界建立幂等性：

- 为每次业务请求生成稳定的幂等键，如 `订单号 + 操作类型`；重跑必须复用该键，而非每次生成新的随机 ID。
- 在数据库中对幂等键建立唯一约束，并将“检查是否已处理”和“写入业务结果”放入同一事务。仅在应用内先查后写，仍可能被两个重跑实例并发穿透。
- 若同时写数据库和调用外部系统，不要假设跨系统事务存在。可先持久化待投递事件，再由可靠投递者执行；外部接口也应接收幂等键。
- `backoffLimit` 只限制重试次数，不能消除已提交后重跑；降低重试次数只是缩小风险窗口，不是正确性保证。

平台证据应记录 Job、Pod 重建次数、失败原因和每次执行携带的幂等键；业务验收则应验证：人为在“数据库已提交、Pod 未上报成功”的窗口终止 Pod 后，最终仅产生一条订单流水、一笔扣款和一条下游事件。

回退也必须可执行：发现重复写入时，应暂停 Job 创建或缩容其触发来源，依据幂等键定位重复记录，执行可审计的补偿事务；不能直接删除 Job 或手工删数据，否则会丢失已完成与待补偿之间的证据链。

### DNS稳定不保证旧连接可用

### DNS稳定不保证旧连接可用

`Service` 提供的是稳定的虚拟访问入口，而不是“已有 TCP 连接永不中断”的承诺。Pod 被滚动更新、驱逐或节点故障时，客户端即使始终使用同一个服务域名，旧连接仍可能被关闭、超时或落到已失效的后端。

应沿流量链路验证，而非只检查 `nslookup` 成功：

1. **选择器**：确认 `Service.selector` 仍匹配新旧 Pod 的标签；标签漂移会使服务存在但后端为空。
2. **EndpointSlice**：观察新 Pod 是否加入、旧 Pod 是否进入 `terminating` 或被移除。DNS 名称不变，但可转发端点已经变化。
3. **DNS 解析**：ClusterIP 类型 Service 通常解析为稳定的 ClusterIP；它证明入口稳定，不证明连接后的 Pod 稳定。
4. **连接行为**：在长连接客户端持续发送请求，同时替换后端 Pod，记录旧 TCP 是否收到 `FIN`、`RST` 或请求超时，以及客户端是否按退避策略重连。

平台证据可包括 Service、EndpointSlice、Pod 终止事件与连接日志；业务验收则应明确：替换期间允许中断多久、单次请求是否可重试、消息是否重复提交、重连后会话如何恢复。仅凭 OpenIM 源码中的服务名或 Kubernetes 资源清单，不能证明上述行为已经成立。

Ingress 还存在协议边界：HTTP/1.1 请求可由代理重试或重新建连，但 WebSocket、gRPC 流和其他长 TCP 会话通常必须由客户端感知断连并恢复。若验收失败，回退应先暂停发布或恢复旧副本，再检查 `preStop`、`terminationGracePeriodSeconds`、就绪探针摘流时机，以及客户端重连与幂等设计。

> **要点** — 平台对象可用只是起点；每个反例都必须同时验证平台证据、业务结果与可执行回退。

以虚构 IM 系统为线索，先按状态与生命周期选控制器，再沿流量、名称解析与连接状态定位故障边界。

### 先按状态责任选择工作负载

### 先按状态责任选择工作负载

不要先问“这个程序要几个副本”，而要先问：**实例消失后，谁负责恢复它的状态，恢复时是否需要固定身份或只执行一次？**

- **无状态网关**：HTTP API、IM 长连接入口、鉴权与路由层通常使用 `Deployment`。请求状态应放在 Redis、数据库或令牌中；任一 Pod 被替换后，新实例应能立刻接流量。配合 `Service` 提供稳定入口，只有 `ready` 的 Pod 才应进入后端端点。
- **后台消费者**：消息队列消费者多数也适合 `Deployment`。消费者可横向扩容，进度由 Kafka、RabbitMQ 或业务库保存，而非依赖某个 Pod 的本地磁盘。必须把消费设计为幂等：消息可能因超时、重平衡或重试被重复投递。
- **数据库**：需要稳定网络身份、固定启动顺序、持久卷绑定的数据库通常使用 `StatefulSet`。其 Pod 名称如 `mysql-0`、`mysql-1` 可用于成员发现与主从配置；每个副本可绑定独立 PVC。但 **PVC 只保证存储持久化，不保证数据库复制一致性、主从切换正确性或事务语义**。
- **一次性回填任务**：历史消息重算、索引回填、数据迁移适合 `Job`。它以“任务成功完成”为目标，而非持续提供服务。`Job` 失败会重试，因此回填写入必须支持去重、检查点或幂等更新；不能假定同一分片只会执行一次。

简化判断是：持续服务且无本地身份用 `Deployment`；持续服务且身份、顺序、磁盘归属重要用 `StatefulSet`；完成即退出的有限工作用 `Job`。控制器解决的是生命周期，不会自动解决业务状态一致性。

### StatefulSet 与 PVC 不保证数据库一致性

### StatefulSet 与 PVC 不保证数据库一致性

`StatefulSet` 解决的是**运行实例身份与存储绑定**，不是数据库协议。它为 Pod 提供稳定名称和序号，例如 `im-db-0`、`im-db-1`；重建后同一序号通常仍绑定同一份 `PVC`，并可按序创建、终止。这适合数据库成员、消息队列节点等需要可预测身份的工作负载。

但 `PVC` 只保证卷的申请、挂载与数据持久化语义，不能保证：

- 多副本数据已经复制完成；
- 主库故障时不会丢失最后几次写入；
- 同一逻辑主节点不会在网络分区时被两个实例同时写入；
- 重建 Pod 后数据库日志、元数据和副本状态一定可自动恢复；
- 存储系统的“已写入”与客户端看到的“已确认”完全等价。

以 IM 消息库为例，客户端收到“发送成功”前，系统必须明确确认级别。仅主库本地落盘可称为较弱确认；等待至少两个副本确认可记为 `S2`；等待三个副本或跨故障域确认可记为 `S3`。副本数越高，丢失窗口越小，但延迟和可用性要求更高。若业务要求“设备确认”，则还需等待目标设备真正接收或持久化消息，这已超出数据库复制范围。

故障恢复还需要数据库自身处理选主、复制日志、仲裁与防脑裂。`StatefulSet` 的序号不是主从角色，`im-db-0` 宕机后重新出现，也不应天然认定为主库。应结合数据库选举机制、`PodDisruptionBudget`、反亲和与备份恢复策略；否则即使 PVC 完好，也可能出现旧副本回归、重复写入或数据分叉。

### Job 重试、重复执行与幂等回填

### Job 重试、重复执行与幂等回填

`Job` 的目标是“成功完成若干次”，不是“某段业务代码恰好执行一次”。因此应从失败链路推导重复：Pod 执行中崩溃，Job 控制器会按 `backoffLimit` 创建新 Pod；节点失联或控制面未及时观察到结果时，也可能出现旧实例实际上已完成、但新实例已启动的重叠执行。

更隐蔽的是“结果已写入、上报未确认”：

1. 回填任务向消息库写入一批离线消息；
2. 写入成功后，Pod 在更新任务状态前被终止；
3. Job 认为本次失败并重试；
4. 新 Pod 再次回填同一批消息。

所以，不能把“Job 成功状态”当作业务去重依据。应为每次回填定义稳定的去重键，例如：

`dedup_key = 会话ID + 原消息ID + 接收设备ID + 回填类型`

数据库以该键建立唯一约束，写入采用“存在则忽略”或“存在则更新”的幂等语义；批处理还应保存可重放游标，而非只依赖内存进度。

对多设备 IM，回填完成不等于用户已收到。S2 可表示服务端已持久化，S3 可表示设备确认；设备确认应携带 `消息ID + 设备ID`，并允许重复上报。这样即使 Job 重跑、网络重连或确认包重复，消息记录仍只保留一份，投递状态则单调推进：`待投递 → 已持久化 → 已设备确认`。

### 从 Service 到 DNS 追踪请求去向

### 从 Service 到 DNS 追踪请求去向

IM 网关访问 `chat-api` 时，请求并不是“发给某个 Pod”，而是沿着一条可验证的链路前进：

`客户端 → Service 虚拟地址 → EndpointSlice → 就绪 Pod`

先检查 Service 的 `selector`。它必须与目标 Pod 的标签完全匹配；例如 Service 选择 `app: chat-api`，而 Deployment 模板实际写成 `app: chat-server`，Service 仍会存在，却没有任何后端。可用 `kubectl get pods --show-labels` 与 `kubectl describe svc chat-api` 对照确认。

随后看 EndpointSlice，而不只看 Pod 是否“正在运行”：

`kubectl get endpointslice -l kubernetes.io/service-name=chat-api`

只有同时满足标签匹配、未终止且通过就绪探针的 Pod，通常才会以可转发端点出现。Pod 处于 `Running` 不等于可接流量；若 `readinessProbe` 失败，EndpointSlice 中可能标记为 `ready: false`，表现为网关连接超时、`503` 或“无可用后端”。

同命名空间内可使用短名：

`http://chat-api:8080`

跨命名空间时，短名会优先在调用方命名空间解析，容易误指向同名 Service。应显式写为：

`http://chat-api.backend.svc.cluster.local:8080`

其中 `backend` 是命名空间，`svc` 表示 Service 域。若 DNS 解析失败，先区分是名称写错、Service 不存在，还是 CoreDNS 异常；若能解析出 ClusterIP 但请求失败，则继续检查 EndpointSlice、端口名与 `targetPort`。

注意 Service 只负责将新连接分配到后端。WebSocket 建立后若后端 Pod 重建、节点故障或连接被中断，既有长连接不会因 Service 自动迁移；客户端仍需实现重连、会话恢复与必要的消息确认。

### 入口路由与连接替换验证

### 入口路由与连接替换验证

Ingress 的核心能力是按 HTTP/HTTPS 请求的主机名、路径和请求头路由，例如将 `im.example.com/api` 转给 API Service、`/ws` 转给网关 Service。它通常还能负责 TLS 终止、重定向、限流等；但“能通过 Ingress 访问”不等于“任意 TCP 协议都能转发”。

若网关承载 WebSocket，握手阶段仍是 HTTP，因此可经 Ingress 路由；但需确认控制器支持连接升级、足够长的读取/发送超时，以及后端协议配置正确。若业务使用原始 TCP、私有长连接协议，或需要四层直通，应选择负载均衡器、支持 TCP 的网关配置，或专门的四层代理，而非假定普通 Ingress 路径规则可用。

验证连接替换时，可执行滚动更新或删除一个网关 Pod，观察：

- 已建立 WebSocket 是否断开；断开本身常是预期现象，关键在客户端是否按退避策略重连。
- Service 的 `selector` 是否仍匹配新 Pod，且只有 `Ready` 的端点才接收新连接。新 Pod 未就绪时不应过早摘除旧端点。
- 重连后会话是否从 S2/S3 恢复：例如会话令牌、未确认消息游标、订阅关系应可重建，而不能依赖被删除 Pod 的内存。
- 客户端设备确认是否幂等：重复登录、重复确认、重放确认包不能造成消息重复消费或确认状态倒退。
- 若网关跨命名空间访问服务，名称应写为 `service.namespace` 或完整集群域名；仅写服务名会解析到当前命名空间，可能把重连流量送往错误目标。

PVC 只能提供持久卷，不自动提供数据库事务、一致性或故障切换；会话恢复的正确性仍取决于存储模型与确认协议。

> **要点** — 控制器管理生命周期，Service 管理可达后端；持久卷不等于一致性，重试与断线必须由业务协议兜底。
