## 教学重组

- 先区分“10 人群 80 ms vs 10000 人群 300 ms”是问题发现，不是优化收益对照；纸上候选 300→230 ms、约 23.3% 只演示算法，错误、队列、CPU 和内存数据全部标待未来实测。
- 按症状选择 CPU on-CPU、heap `alloc_space/inuse_space`、mutex 争用制造者、block 同步等待点、execution trace 运行时事件和跨进程请求 Trace；每项同时列盲区。
- 使用 Go 官方诊断文档说明采样互扰、CPU `flat/cum`、heap 采样、mutex 在临界区结束位置归因、block 在等待栈归因。22 道题逐项反馈。

## 技术修订

- 原稿在多个段落引入 300→240、P95 420→700、420→300 等不同纸上数值，读者难以区分发现问题与优化对照。正式页只用 10→10000 的 80→300 背景和同 10000 目标 300→230 算式。
- 原稿有 block profile 覆盖“网络轮询或外部 I/O 阻塞点”的直接断言。Go `runtime/pprof` 官方文档把 block profile 主要定义为 Go **同步原语**阻塞；正式页不把所有网络、数据库或设备等待都算进去，需转向 runtime trace/请求 Trace/下游证据。
- 原稿部分固定“预热 30 秒、采样 5 分钟”等操作值。正式页要求对照窗口、版本和负载一致，不把这些未经本章验证的数值当通用门槛。
- `alloc_space` 是累计分配热点，`inuse_space` 是采样时在用堆对象；两者均是采样，不能当精确 RSS。CPU profile 是运行态样本，不等于一条请求壁钟耗时或等待时长。
- mutex profile 累计他人等待并归因持锁结束位置，block profile 显示同步等待位置；execution trace 与跨服务请求 Trace 分层，均不自动证明设备展示或业务正确。
- 采集工具本身可能改变 CPU、分配、调度和尾延迟；正式页要求单独记录扰动，并以同负载无采样结果校准优化结论。
