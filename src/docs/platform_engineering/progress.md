## 一次学习记录

```text
日期、阶段与课号：
业务问题及要保护的规则：
前置概念与当前解释：
实验前的输入、时序和结果预测：
实际步骤、命令与输出（未执行则明确注明）：
预测与观察有什么差异：
证据能证明什么，不能证明什么：
独立变式和业务迁移：
解释 / 预测 / 实验 / 迁移自评：
尚未解决的问题与下一次复习：
```

复习可以安排在次日、一周后和一个月后，根据遗忘与实际时间调整。第一次合上笔记解释机制；第二次改变输入或故障点；第三次迁移到不同业务。

## 七次阶段验收

| 阶段 | 核心任务 | 通过时应能回答 |
|---|---|---|
| 一 | 顺序模型与共享关系 | 成功和失败怎样改变状态，谁有修改权 |
| 二 | 有界并发与性能证据 | 为什么排队，在哪等待，如何控制资源 |
| 三 | 持久事务与恢复 | 数据以谁为准，哪些变化一起提交 |
| 四 | 跨进程故障时间线 | 结果未知怎样恢复，旧 owner 怎样被拒绝 |
| 五 | 指标、发布与兼容 | 用户是否成功，新旧系统怎样共存 |
| 六 | 检索与工具原型 | 证据是否充分，效果是否重复，改进怎样测量 |
| 七 | 需求与综合方案 | 每项机制对应什么需求，约束变化时怎样调整 |

具体要求见各[阶段导读](./README.md)。未执行的数据库、集群或真实模型实验单独标记；理论理解可以继续推进，但相关实践保证保持待验证。

## 把错误转成下一轮问题

例如：“同一 ID 重试已正确，但新 ID 重领仍能多领”应回到领域身份；“返回 200 但用户仍失败”应回到业务完成点；“检索到文档但回答缺少前提”应回到证据充分性。

每轮只选一两个最影响当前业务的薄弱点深入，并保存原问题、改进和新证据。这样课程可以随工作中的真实问题持续深化。
