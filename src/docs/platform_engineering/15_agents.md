## 本课问题与前置

Agent 已经创建工单，保存“已完成”之前进程崩溃。恢复后会不会再创建一次？前置：第 6、8、13–14 课。建议用时 4 小时。

目标：定义工具边界、持久状态、授权与幂等身份，验证恢复后的副作用数量。

## 把决策与执行分开

工作流按预定义步骤推进；Agent 可以让模型参与选择下一步，但选择不等于执行权限。执行层必须验证工具名称、参数、租户、预算和批准状态。

一个最小流程是：

```text
接收请求 → 校验与授权 → 保存待执行状态 → 调用工具 → 保存工具结果 → 标记完成
```

**checkpoint**是用于恢复的状态记录。它告诉系统走到了哪里，但不自动修复“工具已成功、checkpoint 未保存”的窗口。

## 重用后端中的正确性方法

工具调用需要稳定 operation_id，下游收到同 ID 时能返回原结果。若同 ID 改变参数，应报冲突。批准应该绑定具体动作和参数，不能让模型一句“用户同意了”替代可信授权。

课程 Workflow 用 SQLite 的 runs 保存执行状态，tool_effects 模拟一个支持幂等的工具服务。它们使用分开的提交边界，故意保留工具成功后、本地状态更新前的崩溃窗口。

```bash
cd labs/platform_path
python3 ai/agent_lab.py workflow-demo
python3 -m unittest discover -s ai -v
```

预期 demo 输出 ticket_id 为 game-a/op-1，effects_after_resume 为 1。演示先注入崩溃，再新建对象重新打开同一数据库，重试后复用原工具结果。

## 明确模拟范围

本实验没有让模型自主决策，也没有访问外部工单系统。它证明：在工具侧保存幂等结果、工作流保存状态的条件下，重放可以避免重复效果。真实工具如果不支持幂等，需要查询已执行结果、补偿，或人工处理不确定状态。

SQLite 的两次事务也不是跨数据库分布式事务。它只是将两个提交点变得可观察。

<details>
<summary>练习：删除工具侧去重，只保留 runs，会怎样？</summary>

在工具成功、本地 runs 仍为 pending 的窗口崩溃，恢复时会再次创建工单。重试逻辑完全按本地状态执行也可能出错；正确性取决于副作用边界，而不只是流程框架。

</details>

独立练习：给工具增加次数预算；超过预算停止并输出原因。再增加“批准后参数改变”的测试，确认不能沿用旧批准。最后区分只读查询、可撤销写入、不可撤销写入的执行策略。

## 从手写模型迁移到框架

完成实验后阅读 [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)，对照 checkpoint、状态和恢复机制。框架替你保存流程状态，但业务工具仍需相应的副作用约定。

达标证据：一次真实文件重开后的恢复结果、权限拒绝测试、参数冲突测试。下一课：[评测与上线](./16_evaluation.md)。
