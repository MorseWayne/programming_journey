## 需求场景：助手已经创建工单，却再次执行

助手从排障资料中发现需要跟进的问题，经用户同意创建工单。工具执行成功之后、工作流保存完成状态之前，进程崩溃。恢复后，本地只看得到“待执行”。

这是C08 课副作用与确认之间的窗口在 AI 工程中的再次出现。本课从工具、状态机和权限讲起，推导怎样恢复并限制重复效果。

## 基础理论：模型、工作流与执行系统

**工作流**按预先定义的步骤和条件推进；**Agent**可以让模型参与选择下一步动作或工具。两者都需要一个实际执行系统来处理外部效果。这种划分可对照 [Anthropic 的工作流与 Agent 说明](https://www.anthropic.com/engineering/building-effective-agents)。

模型输出工具名称和参数，只表达一个建议。执行系统还要判断名称是否允许、参数是否合法、身份有无权限、预算是否足够、是否需要可信批准。

| 层面 | 回答的问题 | 应由谁保证 |
|---|---|---|
| 决策 | 当前目标下建议做什么 | 规则或模型，接受评测与约束 |
| 授权 | 当前调用者是否有权执行 | 可信身份与权限系统 |
| 执行 | 如何调用、超时与重试 | 工具适配与执行代码 |
| 状态 | 已到哪一步、恢复依据是什么 | 持久状态与恢复协议 |
| 结果 | 业务效果是否真的发生 | 工具回执、查询与业务验证 |

把一段提示词写成“务必小心”不能取代这些职责。应让每项保证落到可以检查的边界。

## 工具契约：输入输出之外还有效果

一个创建工单工具至少需要定义：租户与调用者、稳定 operation_id、工单内容、返回身份、错误分类，以及重复调用时的行为。

参数看起来结构正确，也可能不满足业务条件。例如 summary 是字符串但只有空格，或目标项目属于另一个租户。类型、语义与权限要分别验证。

操作可按效果区分：只读查询、可撤销写入、难以撤销的写入。越难恢复，越需要在执行前确认具体动作，并在结果未知时谨慎处理。

批准应绑定可信主体、工具、租户与确切参数；参数改变后不能继续沿用旧批准。模型生成的“用户同意了”不是可信授权记录。

## 状态机基础：把执行进度变成明确数据

一个实际系统可以包含：等待授权、待执行、执行中、结果未知、已完成、明确失败等状态。每个状态都应有允许的下一步，以及支持这个状态的证据。

```text
已验证并获授权 → 保存待执行 → 调用工具
  → 明确成功：保存结果 → 完成
  → 明确拒绝：记录失败
  → 超时或崩溃：查询或用原身份恢复
```

**checkpoint**保存恢复所需状态。它可以告诉你流程停在哪里，但无法独立判断一个远程副作用是否已经生效。

状态越多不一定越安全。如果没有确定的转移条件，“执行中”长期停留也只是换一种方式记录未知。需要超时处理、查询和人工核对的入口。

## 机制推导：两次提交之间怎么恢复

课程 Workflow 使用 runs 表保存本地流程，用 tool_effects 模拟支持幂等的工具端。两边采用不同提交点，保留真实系统会遇到的原子性缺口。

| 步骤 | runs | tool_effects | 此时崩溃后的判断 |
|---|---|---|---|
| 保存请求 | pending | 无 | 可以使用原操作身份继续 |
| 工具提交 | pending | 已有结果 | 重试应复用已有结果 |
| 保存完成 | complete | 已有结果 | 返回已记录结果 |

工具端将效果与幂等记录放在同一提交边界，重复 operation_id、相同参数返回原结果；改变参数则冲突。本地工作流不必假装拥有跨服务事务，但必须依赖明确的工具契约。

如果外部工具不支持幂等，先查询是否已完成、采用可验证的业务唯一标识、设计补偿或让人工处理未知状态，都是需要评估的路径。无限重试不能消除这个缺口。

## 学习实验：观察真实文件重开后的结果

以下是学习时执行的步骤：

```bash
cd labs/platform_path
python3 ai/agent_lab.py workflow-demo
python3 -m unittest discover -s ai -v
```

预期 demo 返回 ticket_id 为 team-a/op-1，effects_after_resume 为 1。程序先在工具提交后注入异常，再创建新对象重新打开同一 SQLite 文件，恢复时复用原工具结果。

这里用异常模拟崩溃窗口，没有杀死操作系统进程；文件重开验证持久状态的读取。它也没有模型自主规划或真实外部工单服务，不应据此声称完整 Agent 已通过生产验证。

### 当前实现与业务设计的边界

当前模型仅保存 pending/complete，`approved` 是实验调用传入的布尔值。它用于展示授权检查位置，不构成真实批准系统。正式应用需要可信身份、批准记录、参数绑定、有效期和审计。

SQLite 内两次独立事务用于演示分开的提交点；将其换成真正远程工具时，还要重新验证网络超时和下游查询能力。

## 预算、终止与重复规划

模型可能反复选择相同工具，也可能不断拆分任务。系统需要总时间、工具次数、成本和最大步骤预算，以及达到目标、证据不足、权限拒绝时的终止条件。

预算应覆盖整个用户任务。每次失败都生成新的工作流 ID，会让“每次最多执行三次”的限制失去意义，正如请求重试重新生成 ID 会绕过去重。

长流程还需要定义恢复后是否重新调用模型。模型版本或资料变化可能产生不同决策，因此已批准动作、已有结果与新的规划应该有清晰关系。

## 独立练习与反馈

第一层：重复同一操作，再改变 summary，分别解释为什么返回原结果或冲突。

第二层：在工具成功后、本地保存前注入失败，画出重启前后的状态。再在工具执行前失败，对比恢复路径。

第三层：设计“批准后参数改变”和“工具调用预算耗尽”的案例，写出执行层必须拒绝的条件。先完成契约与状态表，再修改自己的练习副本。

## 业务应用：让助手逐步承担责任

先交付只读资料检索，让用户核对依据；再提供工单草稿；当权限、幂等、审计和恢复都可验证时，再增加实际创建。每增加一类工具，都重新列出失败成本与结果确认方式。

需要迁移到框架时，对照 [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)中的状态与恢复机制，检查框架保存了什么、业务工具还需保证什么。

验收证据：状态转移表、文件重开后的恢复记录、参数冲突和权限拒绝案例，以及未完成保证的清单。下一课：[评测与交付](./16_evaluation.md)。
