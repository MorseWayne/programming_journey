## 本课问题与前置

所有进程都存活，玩家仍然收不到邮件。应该看进程指标，还是检查完整业务结果？前置：第 4、8 课。建议用时 3–4 小时。

目标：从用户动作定义指标，区分日志、指标与 Trace，设计能够回答故障问题的证据。

## 三种信息各做什么

日志记录离散事件，例如一次发奖提交失败；指标把事件聚合成计数、速率或分布；Trace 关联一次操作经过的多个环节。一个 UUID 能帮助查日志，但只有各段正确传递关联信息，才能拼出跨服务关系。[OpenTelemetry 上下文传播](https://opentelemetry.io/docs/concepts/context-propagation/)解释了这种关联。

异步事件需要显式携带必要关联信息，不能假定 goroutine 或消息通道会自动传播。业务请求 ID、事件 ID、trace ID 的生命周期也不完全相同。

## 从用户结果定义 SLI 与 SLO

**SLI**是测量指标，例如有效发奖请求中成功保存回执的比例。**SLO**是目标，例如某个时间窗内达标比例。错误预算表达距离目标还容许多少失败。

先定义分子、分母、时间窗和排除条件，再选图表。对于邮件，“HTTP 200”与“用户能拉到正确内容”可能是不同指标。排除所有超时会让指标好看，却遗漏用户失败。[Google SRE 的 SLO 实践](https://sre.google/workbook/implementing-slos/)以用户结果组织目标。

指标标签应保持有限集合，例如服务、操作和状态。把每个用户 ID、请求 ID 作为标签会产生大量时间序列，详细身份更适合放日志或追踪。

## 实验：平均值与尾部

```bash
cd labs/platform_path
go run ./cmd/latency
```

程序使用明确标注的合成数据：990 个 5ms、9 个 500ms、1 个 5,000ms。预期均值为 14.45ms，按 nearest-rank 定义的 P99 为 5ms，最大值为 5,000ms，100ms 内完成比例为 99%。

这不是测量线上服务。它展示：即使 P99 很小，仍可能有用户等待五秒；分位数定义、样本量和阈值指标都要说明。

独立练习：把最慢样本扩成 20 个，再观察 P99。将两个副本的 P99 直接取平均，能否得到全局 P99？构造一个小副本很慢、大副本很快的反例。

## 设计一份故障证据表

| 怀疑的问题 | 首先查看 | 如何进一步验证 |
|---|---|---|
| 请求在排队 | 队列长度与等待时间 | 固定处理速度，改变到达速率 |
| 重试放大 | 单业务请求对应尝试数 | 模拟下游超时并限制重试预算 |
| 存储慢 | 下游时延和连接池等待 | 区分连接等待与查询执行 |
| 消息卡住 | outbox 最老未发送年龄 | 重启发送器，观察是否追平 |

这些实验只在隔离环境执行。每次只改变一个因素，保留基线和恢复后的结果。
