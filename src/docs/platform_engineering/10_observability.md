## 需求场景：进程都活着，玩家却收不到邮件

监控显示 CPU 正常、服务存活、接口大多返回 200，运营仍收到“奖励没有到账”的反馈。可能是 outbox 堵塞、通知丢失、客户端未补拉，也可能只是观测口径没有覆盖真正结果。

本课从用户动作定义可观察成功，再选择日志、指标和追踪。目标是能写出指标的分子分母，解释尾延迟与错误预算，并用证据缩小故障范围。

## 基础理论：监控什么才有意义

**可观测性**关心能否从外部信号推断系统内部状态。信号数量多不等于问题更容易回答；关键是信号与需要判断的状态有关。

对于奖励，至少可以区分请求已接收、余额已提交、事件已发送、接收者已处理、客户端已展示。每个阶段成功率都可能不同。

先确定产品承诺的终点。若接口返回“处理中”，可以把提交成功和最终完成分别测量；若接口承诺“奖励已到账”，只统计排入内存队列会高估成功。

## 三种信号怎样配合

| 信号 | 记录什么 | 适合回答什么 |
|---|---|---|
| 日志 | 一次离散事件的上下文 | 某次失败的请求和原因是什么 |
| 指标 | 聚合的数量、速率和分布 | 从什么时候开始、大约影响多少 |
| Trace | 一次操作经过的关联片段 | 时间消耗在哪个服务或等待阶段 |

Counter 累积计数，例如请求次数；Gauge 表示当前值，例如队列长度；Histogram 用桶累计观测分布，例如延迟。选择错误的数据类型会使后续查询含义混乱。

把 user_id、request_id 作为指标标签，会随用户与请求数量产生大量序列。聚合指标使用有限类别，详细身份放入合适的日志和追踪，并按业务控制敏感内容。

### 三种 ID 不应混用

request_id 用来识别业务操作，重试时可能不变；event_id 用来识别异步事件；trace_id 用来关联一次执行观察。一次业务重试可能产生新的 trace，但仍复用原操作身份。

上下文需要穿过 RPC、消息和异步任务边界。仅生成 UUID 而没有传播和关联约定，不能自动得到端到端追踪。参考 [OpenTelemetry 上下文传播](https://opentelemetry.io/docs/concepts/context-propagation/)。

## SLI、SLO 与错误预算

**SLI**是服务表现的测量方式，**SLO**是在时间窗内希望达到的目标。先定义测量，再讨论目标数值。

```text
示例 SLI = 在 2 秒内获得持久结果的有效领取操作数 / 有效领取操作总数
```

其中“有效”“操作”“持久结果”“2 秒起点”都需要定义。按用户操作计数和按网络尝试计数不同；五次重试不能把一个失败用户算成五个不同用户。

假设教学目标为 30 天内 99.9% 达标，100 万个符合分母条件的操作，对应允许 1,000 个不达标操作。这个目标不是通用行业标准，应由用户价值、失败成本和维护能力决定。

**错误预算**帮助团队讨论可靠性投入与发布风险，但不能允许忽略数据错乱、越权等另有硬性规则的问题。SLO 达标也可能掩盖少数租户长时间故障，需要按重要业务维度检查。

## 统计基础：平均值与分位数

平均值容易被极端值拉高，也可能掩盖群体差异。分位数描述排序位置，但不同算法在小样本时可能给出不同值。报告要写明样本量与定义。

### 实验：同一批数据的不同视角

```bash
cd labs/platform_path
go run ./cmd/latency
```

合成数据为 990 个 5ms、9 个 500ms、1 个 5,000ms。均值 14.45ms；nearest-rank 的 P99 取第 990 个样本，为 5ms；100ms 内完成比例为 99%；最慢请求仍需 5 秒。

这说明即使 P99 看起来很小，最慢的一部分请求也值得根据业务影响单独分析。这里的数字用于理解统计，不代表真实服务测量。

独立变式：将慢请求增加到 20 个，重新观察 P99。再构造一个只有少量请求的慢副本与一个高流量快副本，判断直接平均二者 P99 是否正确。

## 机制推导：从报警到验证假设

“队列长”描述症状的一部分。队列可能来自流量增加、处理变慢、worker 丢失或重试放大，需要组合证据。

| 假设 | 支持或反驳它的观察 | 隔离实验 |
|---|---|---|
| 入口流量增加 | 接收速率提高，单任务耗时稳定 | 固定处理速度，改变到达量 |
| 下游变慢 | 下游延迟、在途数与超时一起上升 | 在本地依赖中注入固定延迟 |
| 重试放大 | 每个业务 ID 的尝试数增长 | 限制总预算，比较输入与效果 |
| 发送器停止 | outbox 最老年龄持续增长 | 恢复发送器，观察追平速度 |

故障演练也要有停止条件与恢复验证。一次只改变一个因素，能让观察更容易解释；演练结论仅覆盖实际运行的条件。

## 业务应用：邮件群发的指标合同

为群发邮件设计三组指标：投放任务是否生成、目标玩家能否拉到内容、附件领取是否正确。提醒送达率可作为中间链路指标，但不能取代最终业务验证。

告警要说明触发后能采取什么行动。积压超过目标时间时，可以检查发送器、依赖与处理能力；单次日志错误如果已自动恢复且没有业务影响，未必适合直接唤醒值班人员。
