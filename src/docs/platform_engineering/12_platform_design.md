## 本课问题与前置

两个游戏共用服务，一个升级客户端、另一个保持旧版本。怎样让两者继续工作？前置：第 1、6、11 课。建议用时 4 小时。

目标：明确服务边界，验证租户身份，设计兼容升级与配置演进。

## 先区分三种边界

**模块边界**组织代码；**服务边界**增加进程与网络；**业务边界**定义独立变化的概念与责任。把包拆成服务会引入部署、故障和事务成本，必须有清晰收益，例如独立扩缩容、不同团队节奏或隔离资源。

公共库适合复用稳定机制；业务策略经常变化时，可以保留在业务模块或通过明确接口传入。一个塞满所有项目特例的 common 包，很难同时保持兼容与可理解性。

## 身份来源比字段存在更重要

namespace 进入数据库键只是隔离的一部分。服务还需确认调用者有权使用它。客户端自己填 `namespace=game-b`，不能凭该字段获得 game-b 的权限。

Arena 的教学 HTTP API 用固定实验 token 映射租户，拒绝与身份不一致的请求体。它是身份绑定的最小模型；真实系统还需可信凭据验证、轮换、权限和审计。

```bash
cd labs/platform_path
go test -run '^TestHTTPIsolationAndDrain$' -v
```

预期缺凭据为 401，跨租户为 403，参数冲突为 409。练习：加入 game-b 同 ID 的合法请求，证明它和 game-a 各自产生独立业务结果。

## 兼容性要覆盖新旧组合

| 调用方 | 服务端 | 必须检查 |
|---|---|---|
| 旧 | 旧 | 原行为仍成立 |
| 旧 | 新 | 默认值与旧语义 |
| 新 | 旧 | 未知能力的降级 |
| 新 | 新 | 新功能与失败行为 |

Protobuf 中字段编号是线上的身份；删除后应保留编号，不能用于不相关含义。新增字段也可能改变业务语义，二进制可解析不代表语义兼容。[Protobuf 实践](https://protobuf.dev/best-practices/dos-donts/)

Arena 使用严格 JSON 解析，未知字段会被拒绝。这是有意选择的教学契约，不应未经分析就移植到需要前向兼容的公开接口。

## 配置也有版本和状态

完整校验新配置后再发布，比逐字段修改共享配置更容易维持一致视图。对外记录版本，保留回滚路径，说明配置变更是只影响新请求还是也改变运行对象。

把“业务 namespace”“部署 namespace”“配置版本”“owner token”写成不同概念，避免字符串都叫 namespace 就混用。
