## 需求场景：两个团队以不同速度升级

团队 A 希望奖励增加到期时间，团队 B 一个月后才能更新客户端。两个团队使用同一平台，又有不同流量和权限。公共能力需要支持这种差异，并让故障影响范围可控。

本课从职责与变化来源理解平台边界，再讨论可信身份、接口兼容和配置。目标是能解释一个拆分或复用决定，验证租户隔离，并写出新旧版本都能执行的协议。

## 基础理论：模块、服务与业务边界

模块组织代码依赖；服务引入独立进程、部署与网络边界；业务边界表达某组规则由谁负责。三者不必一一对应。

一个模块拆成远程服务，会增加超时、重试、独立发布和数据协作成本。收益可能是独立扩缩容、资源隔离或团队自主交付。先确定需要的收益，再判断是否值得承担这些成本。

**内聚**意味着相互关联的规则放在容易一起理解和修改的位置；**耦合**描述一处变化会怎样影响其他位置。把所有业务特例塞进 common 包，可能减少重复代码，却扩大变化影响。

### 稳定机制与变化策略

认证上下文、日志格式、连接管理等机制可能适合复用；不同团队的奖励资格、匹配规则和邮件投放策略可能更适合通过清晰接口组合。

接口抽象应来自已经出现或明确需要的差异。例如按某个规则选人可以抽成策略；为尚不存在的十种数据库提前建立复杂插件系统，则需要证明其价值。

## 租户基础：身份、数据、资源和运行

多租户隔离至少包含四个维度：谁可访问、数据如何区分、共享资源如何分配、故障如何限制影响。把 namespace 加进主键只覆盖其中一部分。

| 层面 | 必须回答的问题 |
|---|---|
| 身份 | ns 来自可信认证结果，还是请求体任意填写 |
| 数据 | 表、缓存、事件和查询是否都带正确范围 |
| 资源 | 一个团队能否占满线程、连接池或队列 |
| 运维 | 灰度、告警和配置能否按租户定位 |

业务 namespace、Kubernetes namespace、配置版本和 owner 代次表达不同概念，应避免同名字符串在调用中被混用。

## 实验：让身份决定租户

教学 HTTP API 将固定 token 映射到 team-a 或 team-b，若请求体提供了不一致的 namespace，就拒绝执行。

```bash
cd labs/platform_path
go test -run '^TestHTTPIsolationAndDrain$' -v
```

预期缺凭据返回 401，跨租户尝试返回 403，重用请求 ID 但改变参数返回 409。这些错误分别对应身份、权限与业务冲突，不应全部映射为可立即重试的服务器错误。

固定 token 只是演示信任边界。生产服务还需实际凭据验证、撤销、轮换和授权规则。下游应沿用经过确认的租户上下文，不能重新信任未经校验的请求字段。

独立变式：用 team-b 的凭据和相同 user/request_id 合法发奖，再查询两者结果，证明隔离没有误伤合法操作。

## 契约兼容：能解析与语义正确不同

接口契约包括字段类型、默认值、错误、操作身份、时间单位和业务效果。新增字段也可能破坏语义，例如旧服务端忽略 `expires_at`，却继续发放本应过期的奖励。

| 调用方 / 服务端 | 必须验证的行为 |
|---|---|
| 旧 / 旧 | 现有业务基线 |
| 旧 / 新 | 缺失新字段时默认语义仍成立 |
| 新 / 旧 | 新能力能否安全降级，或明确拒绝 |
| 新 / 新 | 新规则及失败路径 |

Protobuf 是一种描述与编码结构化消息的机制，通常在 .proto 文件中写出消息类型、字段类型和编号。通信双方依据同一模式解释字节，编号用于标识传输中的字段。

Protobuf 的字段编号属于线上身份，删除后应保留编号，避免赋予不相关的新含义，见 [Protobuf 实践](https://protobuf.dev/best-practices/dos-donts/)。即使编码兼容，业务规则仍需独立验收。

当前教学 API 使用严格 JSON 解析，未知字段被拒绝。它有利于发现输入错误，也意味着新增字段向旧服务端发送时可能失败；这应进入兼容矩阵，而不能假定所有 JSON API 都会忽略未知字段。

## 机制推导：为奖励增加到期规则

先确定时间含义：是领取必须在某时刻之前，还是到账后积分会失效？由谁提供时钟？正在处理的请求跨过截止时间怎么办？同一 request_id 重试时是否沿用首次判断？

假设规则是“新领取在指定时刻前被服务端接受”。可以先部署理解新字段的服务端；旧请求缺省保持原约定；确认全部相关路由支持后再启用新调用方。若旧节点仍存在，不能让它悄悄忽略约束，应进行能力协商或定向路由。

对业务不可安全降级的字段，应明确失败，而不是为了兼容而放宽规则。兼容性是一套版本间行为协议。

## 配置是另一种可演进状态

逐字段修改共享配置，可能让请求读到“新阈值加旧策略”的混合视图。可以先构造并完整校验新配置，原子发布新快照，随后保持不可变；引用中的子对象同样要遵守约定。

还需决定新配置影响新请求、全部运行对象，还是等下一轮活动生效。对长时间任务流程，执行到一半切换规则可能破坏公平性，应记录或绑定配置版本。

配置回滚也不必然恢复旧行为：新配置可能已经触发发奖、删除或迁移，相关效果需要按业务单独处理。

## 业务实践与验收

选择一个实际公共能力，画出调用方、规则归属、权威数据和变更影响。以“新增一个团队”为变式，检查新增的是配置、策略实现还是跨服务改造，并解释为什么。

提交一份到期规则升级方案，包含兼容矩阵、身份传播、配置生效范围、灰度对象、观测指标和回滚后数据解释。
