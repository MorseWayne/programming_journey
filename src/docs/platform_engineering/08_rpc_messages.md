## 需求场景：已发奖，却显示“请求失败”

资产服务提交成功，响应在网络中丢失。调用方等待超时后需要决定怎样向玩家解释、是否重试、是否触发补偿。与此同时，邮件系统可能收到重复通知。

跨进程后，系统可以出现一部分成功、一部分失败的状态。本课用时间线分析这些状态，再推导重试、outbox 和消费幂等。

## 基础理论：远程调用比本地调用多了什么

本地函数共享进程的执行环境；远程调用经过编码、传输、排队、执行、提交和响应返回。调用双方独立运行，网络也可以单独失败。

调用者看到超时，至少可能对应四种情况：请求尚未发出；已送达但未执行；执行中；已成功但响应没回来。除非协议提供更多证据，不能从超时推断“服务端一定没有做”。

**部分失败**意味着某些组件继续正常运行，而另一些组件失联或暂停。失联不是确认崩溃，恢复通信也不代表双方状态自动一致。

### 用状态表达结果未知

业务接口可以区分成功、明确拒绝、处理中与结果待查询。结果未知需要稳定查询依据，例如 request_id。把所有异常翻译成“领取失败，请重新领取”，可能促使客户端生成新身份，从而绕过去重。

超时后是否重试，由操作语义决定。只读查询通常较容易重试；写操作需要证明重复执行不会产生不可接受的效果。

## 重试基础：次数、预算与退避

假设网关、业务服务、SDK 各最多尝试 3 次，嵌套情况下一个用户动作最坏可能触发 27 次底层尝试。系统已过载时，这种放大会进一步减少处理正常请求的能力。

合理重试需要：确定可重试错误、稳定身份、总时间预算、次数上限、退避与随机抖动，并让调用链共同承担预算。参数非法、授权拒绝等错误通常需要修正请求，不应立即重复发送。

**截止时间**表示整次调用愿意等待到的时点。上游总预算 500ms，已经消耗 200ms，下游可用预算就应考虑剩余时间和返回开销；每一跳重新给 500ms 会扩大端到端等待。

[gRPC Deadline 指南](https://grpc.io/docs/guides/deadlines/)说明了截止时间与取消。应用自行启动的工作仍需响应取消，取消信号不能撤销已经提交的事务。

## 机制推导：写库和发消息的两个窗口

先保存奖励再发通知：数据库成功后进程崩溃，通知可能永远没有发送。先发通知再保存奖励：接收者可能观察到一个尚未成立的业务事实。

若两者无法放进同一个原子提交范围，可以先把“未来需要发的事件”作为数据库事实保存。第 6 课把业务状态、回执和 outbox 一起提交，保证成功奖励有对应待发记录。

发送器随后扫描 outbox，送达后记录确认。这又产生另一个窗口：接收者已经执行，发送器却没保存确认。恢复后同一事件会重发。

| 故障位置 | 权威状态 | 恢复动作 |
|---|---|---|
| 业务事务提交前 | 没有成功业务事实 | 按请求身份重新尝试 |
| 已提交但未发送 | 业务与待发记录存在 | 继续扫描和发送 |
| 接收成功但未标记 | 接收效果可能存在，发送方仍认为待发 | 重发，由接收方识别重复 |
| 标记发送完成后 | 本次交付已确认 | 保留适当审计与业务查询能力 |

outbox 将“忘记发”的风险转成可以持续尝试的记录，但仍依赖扫描器运行、失败告警和保留策略。它不会自动保证外部系统永远接受请求。

## 交付语义与业务效果

**至多一次**限制重复，但可能丢失；**至少一次**通过重试争取送达，但允许重复。讨论“恰好一次”必须指定范围和故障假设，例如单数据库内的状态变化，或某个协议范围内的消息处理。

外部发奖、发送邮件、创建工单等副作用，各自有独立边界。消息已被 broker 确认、消息已被消费者取走、业务效果已提交，是三个不同的完成点。

顺序同样需要限定范围。一个分区的发送顺序，不一定等于多个 worker 的完成顺序；全局顺序通常比按玩家或房间顺序更昂贵。

## 实验：发送成功但确认尚未保存

```bash
cd labs/platform_path
go test -run '^TestOutboxCrashWindow$' -v
```

测试先让 Sink 应用事件，然后故意省略 MarkSent；再次扫描得到同一事件，重放后效果数仍为 1，最后标记发送完成。

这里没有真的终止进程，Ledger 与 Sink 都是内存模型。它稳定重现的是提交点之间的顺序；真实重启后能否恢复，需要持久存储与新的集成实验。第 18 课会要求连接 SQL 与 HTTP 完成这一步。

### 为什么消费记录与效果也要一起保护

先记“已处理”再执行效果，可能在中间崩溃，恢复时跳过从未做过的操作。先执行效果再记，则可能恢复后重复执行。

若效果与去重记录属于同一数据库，可在同一事务内提交。若效果在外部服务，通常需要下游支持稳定幂等身份、查询已执行结果，或明确补偿与人工核对流程。

补偿是新的业务操作，未必能完全撤销已经发生的事情。例如已发出的通知无法从用户记忆中收回；系统应明确补偿后的可接受状态。

## 独立练习：逐个改变故障条件

1. 同一事件 ID 改变金额，验证接收端拒绝参数冲突。
2. 在首次发送前失败，与发送后未确认失败分别重放，记录效果数。
3. 加入两个生产者，解释各自从 1 开始的事件 ID 为什么可能碰撞。提出稳定的生产者与事件身份组合。
4. 设计一次消息积压告警，说明最老待发年龄为什么能补充队列长度。

## 业务应用：邮件补拉与奖励发放

邮件提醒可设计成“有新邮件”的可重建信号，真实邮件通过游标查询补齐。奖励命令则必须保护资产效果，不能把丢弃重试当成降低负载的通用方法。

为一条实际链路写出正常、超时、重复、恢复四条时间线，标出谁拥有权威状态、请求身份如何传播、用户看到什么结果。下一课：[节点归属与 fencing](./09_distributed_state.md)。
