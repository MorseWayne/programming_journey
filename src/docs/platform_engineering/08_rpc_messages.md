## 本课问题与前置

数据库提交成功，响应在网络中丢失，客户端看到超时。应该重试、回滚还是告诉用户失败？前置：第 3、6–7 课。建议用时 4 小时。

目标：区分结果未知与执行失败，解释 outbox 的交付边界，验证消费者去重。

## 超时描述的是等待结果

**RPC**让程序跨进程请求服务，语法看起来像调用函数，故障语义却不同。超时可能发生在请求发出前、执行中、提交后、响应途中。客户端常常无法区分。

因此重试需要稳定请求 ID、可识别错误、总预算、次数上限与退避。重试还会增加负载；系统已过载时，立即重试可能形成放大。

**截止时间**是整个调用愿意等待到的时点。下游预算应扣除上游已消耗时间，而不是每一跳重新获得完整五秒。服务端启动的任务也必须响应取消。[gRPC Deadline 指南](https://grpc.io/docs/guides/deadlines/)说明了调用与应用任务的边界。

## 写库与发消息之间的缺口

先写库后发消息，可能在两步之间崩溃；先发消息后写库，可能通知了不存在的业务事实。第 6 课把业务数据和 outbox 写入同一数据库事务，先保证“业务成功就有待发事件”。

随后发送器读取 outbox，发送成功再标记。若接收方成功后发送器崩溃，事件会再次投递。因此这个方案仍然需要接收方幂等。

| 崩溃位置 | 恢复后行为 |
|---|---|
| 事务提交前 | 不应留下已提交业务效果 |
| 提交后、发送前 | 扫描 outbox 继续发送 |
| 接收成功、标记前 | 可能重复投递 |
| 标记后 | 已完成本次发送，后续仍需保留适当审计信息 |

## 实验：发送成功后崩溃

```bash
cd labs/platform_path
go test -run '^TestOutboxCrashWindow$' -v
```

测试故意先调用 Sink，再省略 MarkSent，模拟发送器没来得及保存确认。重放后，Sink 的效果次数仍为 1，最后 outbox 清空。

这里 Ledger、Sink 都只存在内存中，测试验证的是交付时间线。它没有证明重启后的持久性。SQL 实验的 outbox 是持久表，但当前 HTTP 服务没有连接该表；把它们连接起来是综合项目的任务。

## 传输语义与业务效果

至少一次交付允许重复；至多一次可能丢失。讨论“恰好一次”时，必须说明范围：消息系统内部、单数据库事务，还是跨多个外部工具的实际效果。

Core NATS 与 JetStream 的能力不同。JetStream 消费确认、重投等机制需要具体配置和消费者处理，不能仅凭用了 NATS 就认定持久可靠。[NATS 消费者说明](https://docs.nats.io/nats-concepts/jetstream/consumers)用于对照机制。

<details>
<summary>练习反馈：为什么“先记已处理，再执行效果”不够？</summary>

记完后崩溃，会跳过从未完成的效果；先效果后记，又可能重做。消费者的记录与业务效果如果能放在同一事务，就能缩小该缺口；如果效果是外部调用，需要下游支持幂等身份，或明确补偿与人工处理。

</details>

独立练习：重放同一事件 ID 但把金额改成 20，增加测试验证参数冲突。再解释多生产者、进程重启后如何保证事件 ID 不碰撞。本课内存模型的自增 ID 只在单个 Ledger 生命周期内唯一。
