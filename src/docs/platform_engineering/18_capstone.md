## 从一个具体业务问题开始

本章是学习者的综合实践说明。选择一条有清晰使用方、状态变化和失败代价的业务链路，把各阶段学到的原理组合起来。教学参考代码是帮助验证机制的材料，完整集成由学习者在实践时完成。

推荐主线是“邮件附件领取与结果查询”，因为它自然连接资格、身份、资产、事务、重试和通知。也可选择协作空间接管、聊天过载治理或知识助手，但需要保留所选场景对应的正确性与恢复验收。

## 需求示例：邮件附件领取

用户希望领取已满足投放条件的邮件附件，超时后能确认结果；运营希望同一附件只产生一次资产效果；客服希望能依据回执解释失败或成功。

本示例作如下教学约定：

- 附件以整数积分表示，领取资格由可信服务端规则判断。
- 同一 `(租户, 用户, 邮件, 附件)` 最多领取一次。
- 客户端重试复用 request_id；即使换了 request_id，领域唯一性仍不能被绕过。
- 成功结果在约定的持久提交点之后返回；响应丢失时可查询或安全重试。
- 通知可延迟，领取事实必须可查询，通知失败不能抹去已提交领取。
- 不同租户的同名用户、邮件和请求相互独立。

资格规则、有效期、撤销、数据保留和容量目标，应在个人方案中进一步写清。文中的数值与对象为虚构设定，不代表生产系统要求。

## 第一层：需求与顺序模型

先写出领取前、领取后、非法和已领取四类情况，再实现一个不含网络与数据库的顺序模型。明确余额、领取记录和输出各表达什么。

对应B01、C01–C02 课。验收不是只跑参考 Account，而是能解释你增加的领域状态，并验证失败不改变任何受保护状态。

产物：需求表、状态转换、正常与非法案例、所有权说明。

## 第二层：并发与持久提交

让多个执行者并发领取同一附件，以及同一用户领取不同附件。前者只产生一次效果，后者应按合法规则累加。

对应C03、C05–C07 课。将领取事实、资产结果、回执和必要的待发记录放进明确提交边界。若资产由独立服务维护，应清楚转入下一层跨服务设计，而不能假装本地 SQL 包含远程调用。

产物：表与索引、身份约束、并发与冲突案例、回滚和重启恢复说明。缺少数据库环境时可先完成设计推导，持久化实践保留为待验证。

### 连接参考 HTTP 与 SQL 时注意什么

现有 Go HTTP 使用内存 Ledger，SQL 过程独立演示事务；二者尚未相连。学习者可以先定义业务所需接口，再增加 SQL 适配，不要把 HTTP 细节塞进事务逻辑。

```go
// 设计示例，具体存储实现和领取领域规则由学习者完成。
type RewardStore interface {
    Grant(ctx context.Context, request RewardRequest) (Result, error)
}
```

context 传到数据库调用，错误区分参数、权限、冲突、依赖失败与结果未知。SQL 驱动与版本需在自己的实践中记录；课程现有标准库模型没有预装它。

## 第三层：跨服务交付与故障恢复

引入结果通知或独立资产服务，明确每一处请求身份和确认点。分别分析提交前、提交后未发送、接收成功未确认、重复接收等故障。

对应C08–C09 课。不是每个场景都需要 owner 与 fencing：若只是共享数据库的无状态处理，先说明数据库如何协调；若引入协作空间内存归属，再补充接管协议。

产物：正常、失败、恢复三条时间线，重放规则，权威来源，以及接收端效果去重证据。

## 第四层：面向多个团队运行

补充可信身份、业务指标、发布与版本变化。以“邮件增加领取期限”为升级任务，说明旧调用方、新服务端及灰度期间分别怎样执行。

对应C10–C12 课。先完成本机请求和退出的学习实验，再按个人环境选择 Kubernetes。集群实验独立验收，不应成为理解状态与契约的前置门槛。

产物：SLI 定义、错误与延迟口径、兼容矩阵、发布停止条件、回滚后的数据解释。

## 第五层：知识助手作为独立交付

围绕上述业务写一组虚构运维文档，覆盖重试、领取冲突、通知积压、版本变化和租户隔离。让助手提供资料证据，并在可信授权后创建工单。

对应D01–D04 课。先完成词项检索与可恢复工具模型，再按需要加入真实生成。分别报告检索质量、答案支持程度和任务副作用；模型调用为零时，明确交付的是确定性原型。

产物：至少 12 条独立评测样本、失败分析、来源与权限说明、工具故障恢复记录。

## 核心验收矩阵

| 输入或故障 | 预期业务结果 | 需要的证据 |
|---|---|---|
| 同 request_id、同参数并发提交 | 返回同一操作结果，效果一次 | 余额、领取事实、回执和事件 |
| 同 request_id、参数改变 | 拒绝冲突 | 原状态不变 |
| 新 request_id 重领同一附件 | 领域规则仍阻止重复领取 | 领域唯一约束或等价协议 |
| 相同 ID 属于不同租户 | 两者独立且无越权 | 身份与数据范围 |
| 事务中途失败 | 没有半份领取效果 | 回滚前后数据 |
| 提交成功但响应丢失 | 查询或重试得到可解释结果 | 持久回执与客户端行为 |
| 通知执行后确认前失败 | 重放不重复产生受保护效果 | 接收端结果与次数 |
| 服务重启 | 已承诺持久的数据可恢复 | 重启前后比较 |
| 新旧版本并存 | 按兼容约定执行或明确拒绝 | 版本组合案例 |
| 助手证据不足或无权查看 | 不把无依据内容当成确定事实 | 检索、拒答与权限案例 |

验收表中的条件需要真正执行后才记为通过。设计推导、已有参考测试与完整业务集成是不同证据，分别记录。

## 从其他业务选择等价项目

| 选择 | 核心不变量 | 必须加入的失败场景 |
|---|---|---|
| 协作空间接管 | 新状态不被旧 owner 覆盖 | 暂停、接管、迟到写、恢复版本 |
| 聊天过载治理 | 承诺的顺序与交付可解释，资源受控 | 慢消费者、队列满、断线重连 |
| 邮件投放与补拉 | 符合条件的邮件最终可查询 | 通知丢失、游标重放、分页变化 |
| 名字注册与搜索 | 名字唯一性正确，索引可追平 | 并发注册、同步失败、重建 |

改变业务时也要重写需求和验收，不能只替换函数名称。

## 最终提交与答辩

提交一份可阅读的成果包：需求与约束、状态与数据模型、核心实现、实验步骤和记录、故障恢复、设计取舍及尚未完成的范围。所有例子使用公开或虚构数据。

建议按五个维度检查：需求与边界 20 分，正确性 25 分，可观察与恢复 20 分，解释与评测 20 分，可复现性 15 分。至少 80 分作为课程自检参考；越权、重复资产或迟到覆盖等核心错误不能被其他分数抵消。该评分是学习规则，不是职业能力认证。

答辩依次回答：

1. 这个系统帮助谁完成什么，最不能接受哪类失败？
2. 每项业务承诺由哪种机制负责，证据在哪里？
3. 哪个故障点最难恢复，为什么？
4. 流量增加十倍，首先需要测量什么？
5. 团队只剩两人维护，哪些复杂度可以减少？
6. 哪项结论目前只是推导，还缺实际验证？

将尚不能解释的问题放回[进度与复习](./progress.md)。下一轮学习从这些具体问题出发，选择存储、分布式、性能或 AI 的深化材料。
