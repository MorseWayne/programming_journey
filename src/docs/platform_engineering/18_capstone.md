## 项目目标与边界

完成一个面向虚构游戏的奖励服务与运维知识助手。建议用 3–4 周，每周 6–8 小时。

现有代码是参考模型：Go HTTP 使用内存 Ledger；SQL 单独验证持久事务；Python 单独验证检索与可恢复工具。综合项目要求连接相关能力，分别通过的测试不能直接证明完整系统成立。

## 分层验收

基础结课完成 A、B；具备数据库环境再完成 C；真实模型与集群属于扩展 D。明确报告实际完成哪一层。

### A：解释与验证现有模型

运行全部 Go 和 Python 测试，增加至少一个未覆盖反例，解释内存状态、工具幂等、租户隔离的保证范围。仅复述答案不算完成。

### B：交付一个可演示的助手

扩展虚构文档，建立至少 12 条独立评测样本，覆盖可回答、证据不足、租户隔离、错误参数和重复工具执行。展示一次崩溃恢复，不重复创建工单。

无模型版本交付检索与工作流原型，并标为确定性原型。有模型版本另行检查答案质量、引用和成本。

### C：连接持久奖励服务

为 Go 服务增加存储接口与 SQL 实现，使 HTTP 使用第 6 课的事务。可选成熟的 MySQL Go 驱动，固定版本并说明来源；现有标准库实验未预装该依赖。

必须通过以下验收：

1. 同请求重复和并发提交，奖励效果一次。
2. 同请求 ID 参数不同，返回冲突。
3. 不同租户的同用户、同请求 ID 互不影响。
4. 服务重启后，回执和余额保留。
5. 投递成功但标记失败后，重放不重复产生消费效果。
6. 依赖失败时，有明确状态与恢复行为。

### D：条件扩展

在个人测试账户接入真实模型，在个人本地集群验证发布；或增加只读网页。选择与目标方向相关的一项，明确额外环境与验收。

## 实现步骤

先写接口与测试，再实现存储。HTTP 层处理身份、输入和错误映射；业务层定义请求语义；存储层保护事务。发送器独立处理 outbox，共享事件契约。

```go
// 设计片段，具体实现由学习者完成。
type RewardStore interface {
    Grant(ctx context.Context, request RewardRequest) (Result, error)
}
```

context 从 HTTP 传到数据库操作，避免无限等待。超时后结果可能未知，客户端使用原请求 ID 重试。

助手先提供只读检索，再接入需批准的工单工具。执行层验证参数与租户，不让模型任意选择数据库连接或执行 SQL。

<details>
<summary>参考方案检查</summary>

- 余额、回执、outbox 在同一事务提交。
- 身份校验后的 namespace 不能被下游覆盖。
- 多副本去重依赖共享持久约束，不只靠各自内存。
- 消费幂等记录覆盖副作用提交窗口；不支持幂等的工具有明确降级。
- 检索权限在材料进入模型上下文前应用。
- 回滚说明数据兼容，不只是重新发布旧镜像。
