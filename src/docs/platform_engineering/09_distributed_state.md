## 本课问题与前置

匹配房间被分配给节点 A；A 暂停，锁过期后 B 接管；随后 A 恢复，把旧状态写回数据库。路由与锁分别解决了什么，还缺什么？

前置：第 2、6、8 课。建议用时 4–5 小时。目标：分清路由、持有权与存储写入校验，验证旧 owner 的迟到写被拒绝。

## 三个问题不能合并

**路由**决定请求发给谁。一致性哈希根据节点集合与 key 选择目标，旨在节点变化时减少迁移，但不同客户端看到不同节点集合时可能选出不同目标。

**持有权**决定谁被允许处理对象。租约通过续期与过期表达一段时间内的持有关系；进程暂停或网络分区后，持有者不一定及时知道自己已失去资格。

**写入保护**决定接收端是否接受某次修改。仅在客户端“先查锁再写库”仍有检查与写入之间的窗口。

Etcd 的 lease 过期会删除关联 key，但不会把旧进程的 CPU 指令撤销。相关行为见 [Etcd API](https://etcd.io/docs/v3.6/learning/api/)。

## 用递增代次标识所有者

**fencing token**是有顺序的代次标识。新 owner 获得更高代次，存储端原子地比较代次并决定是否写入。单靠在日志中打印 token 没有保护作用。

```text
A 持有 token=1 → 接管安装 token=2 → B 写入新值 → A 携 token=1 迟到 → 存储拒绝
```

本课 `FencedStore.Activate` 在同一接收端原子安装新代次；Write 仅接受当前代次。这比某些只记录“已见最大 token”的实现更强：后一种在尚未见到新 token 的写入前，仍可能接受旧值。解释安全性时必须说明 token 在什么时候被接收端认识。

## 实验：固定顺序验证迟到写

```bash
cd labs/platform_path
go test -race -run '^TestFencing$' -v
```

预期：新 owner 写入 new，旧 token 写 late 得到 ErrStale，最终仍为 new。测试使用明确顺序，避免用概率性的 sleep 假装模拟网络。

独立练习：去掉 token 比较，预测哪个断言失败。再添加两个 key，证明一个房间切换不影响另一个房间。思考代次计数重启归零、备份恢复回退和整数耗尽时会破坏什么。

模型只验证“接收端校验与写入原子化”的必要性。它是单进程 map，不会解决共识、持久化、选主和跨机网络问题。实际系统需要可信的代次分配、持久记录以及所有写入路径遵循校验。

同一 owner 的并发修改还可能需要对象版本 CAS。owner 代次回答“谁有资格”，对象版本回答“我修改的是否仍是看到的那个版本”，两者不能互相替代。

## 如何评估有状态扩缩容

先列出停止接入、排空在途、安装新归属、恢复状态、重新接流量之间的约束，再考虑实现顺序。存在网络分区时，还要明确是否暂时拒绝服务以避免错误写入。

Raft 等共识算法可以帮助节点对日志或元数据达成一致，但不会自动定义应用的请求幂等与数据库事务。建议先完成当前故障实验，再选择 MIT 6.5840 的相关阅读深化。
