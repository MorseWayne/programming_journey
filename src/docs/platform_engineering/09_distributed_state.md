## 需求场景：协作空间被两个节点同时修改

协作空间最初由 A 处理。A 长时间暂停，租约过期后 B 接管并推进了状态。随后 A 恢复，把暂停前的旧状态写回，覆盖了 B 的结果。

我们希望利用局部串行简化协作空间逻辑，同时允许故障后接管。要做到这一点，必须分别解释路由、处理资格、写入保护与恢复。

## 基础理论：有状态服务为何需要归属

无状态处理也会访问数据库，但自身通常不持有无法随意迁移的业务运行态。有状态对象可能在内存中保存协作空间成员、匹配进度、队列和定时器，由一个执行者按序推进。

这种安排减少同一对象内部的并发交错，但增加了归属问题：谁处理、状态在哪里、节点失效时谁接替。一个 key 能定位节点，不代表该节点持有最新状态。

### 三个问题对应三种机制

| 问题 | 常见机制 | 单靠它尚不能保证什么 |
|---|---|---|
| 请求发到哪里 | 服务发现、路由、一致性哈希 | 不保证目标拥有合法写入资格 |
| 谁可以处理对象 | 锁、租约、所有权协议 | 不能让失联旧进程立刻停止执行 |
| 哪次写入可被接受 | 存储端版本检查、fencing | 不自动完成状态恢复和业务重放 |

它们需要协作，不能用一个“分布式锁”名称替代全部解释。

## 路由基础：从取模到一致性哈希

key 是对象的标识，hash 函数把标识映射为一个数值；取余可以将它归入有限编号。简单 `hash(key) % N` 可以把对象分给 N 个节点。N 变化时，许多 key 的结果会变化。一致性哈希将节点和 key 映射到一个有序空间，节点变化时主要迁移相邻范围，减少重映射。

虚拟节点可以改善分布，但不会消除业务热点。如果一个协作空间占用了大部分请求，即使其他协作空间均匀分布，这个协作空间仍可能成为单点瓶颈。

路由需要节点列表。服务发现的更新传播到不同客户端需要时间，它们可能暂时看见不同列表，对同一 key 选择不同目标。正确性不能只建立在“大家通常看到同一份路由”上。

## 租约基础：超时不是强制停止

租约用有限有效期表达处理资格，通过续期保持有效。网络分区或进程暂停时，持有者可能无法及时续约，也可能无法及时知道自己已经失去资格。

即使它在写入前检查锁，检查成功后仍可能暂停，等锁过期并被别人接管后才继续写入。这是检查与使用之间的窗口。

Etcd lease 失效会影响其关联键，并不会撤销旧进程接下来执行的 CPU 指令。相关语义可核对 [Etcd API](https://etcd.io/docs/v3.6/learning/api/)。

## 机制推导：让接收端识别旧主人

**fencing token**是有顺序的所有者代次。A 持有 1，B 接管获得 2。存储端在真正接受修改时检查代次，才能拒绝旧 owner 的迟到写入。

```text
A 获得代次 1，写 old
  → A 暂停
  → 接收端安装新代次 2
  → B 携 2 写 new
  → A 携 1 写 late，被接收端拒绝
```

检查和写入需要在同一个原子边界中完成。先在客户端查 token，再发普通写请求，仍然保留竞态。遗漏校验的旁路写入也会破坏保证。

### 安全性与继续服务

安全性强调不发生错误，例如旧 owner 不覆盖新状态；活性强调系统最终能继续推进。拒绝无法确认归属的写入，可以保护安全，却可能暂时降低可用性。

当网络分区发生时，系统无法同时凭空获得通信、确定最新状态并无限制接受所有写入。需要依据业务决定何时等待、拒绝或降级。不能用泛化口号替代具体失败条件。

## 实验：按固定顺序验证旧写拒绝

```bash
cd labs/platform_path
go test -race -run '^TestFencing$' -v
```

`FencedStore.Activate` 在同一接收端原子安装新代次，Write 只接受当前代次。预期 B 写入 new 后，A 写 late 返回 ErrStale，最终仍为 new。

这比某些仅保存“已经看见的最大 token”的方式更明确：如果新代次尚未到达存储，后者可能还接受旧 token。因此，解释安全性时要说明新 owner 的资格在什么时候被存储知道。

本模型是单进程 map，不提供持久化、共识或跨机租约。它证明接收端校验的作用，不能直接等同于生产分布式锁实现。

## 所有者代次与对象版本

同一 owner 内部也可能发生并发更新。owner token 回答“谁有资格写”，对象版本回答“我修改的状态是否仍然是刚才读取的版本”。

例如两个请求都读到协作空间 version=10，即使 token 都合法，也可能互相覆盖。可以在更新中检查预期版本，并成功后递增，或由单一执行者串行处理。

CAS 是“比较并交换”：在同一个原子操作里检查当前值是否仍等于预期值，相等才更新。例如只在 version=10 时写入新状态并改为 11；若已经是 11，则当前操作应失败或重新读取。

数据库 CAS、唯一约束、事务与 fencing 保护不同规则。先写出不变量，才知道需要哪些机制组合。

## 从接管继续推导恢复

新 owner 获得资格后，还需要加载状态、恢复定时器、重放已持久接收的操作、拒绝重复并最终接流量。获得锁并不意味着对象内容已准备好。

一条可能的交接流程是：限制新请求 → 处理或记录在途状态 → 确立新代次 → 恢复状态 → 校验版本 → 开放新流量。具体步骤必须与存储语义协调，尤其要防止在旧写仍可进入时加载不稳定快照。

共识算法可以帮助多个节点对日志或元数据达成一致；应用仍需定义请求身份、事务边界和外部副作用。可在掌握本课后阅读 MIT 分布式课程，继续研究复制状态机。

## 独立练习与业务应用

1. 在练习副本中去掉 token 检查，预测哪个断言失败，再验证。
2. 增加两个协作空间，证明一个协作空间接管不影响另一个。
3. 模拟 A 在 B 写入前、但新代次安装后尝试写入，检查是否仍被拒绝。
4. 解释计数重启归零、备份恢复回退和代次耗尽会破坏什么。

移动对象之前应测量状态大小、恢复耗时和在途操作。迁移大量冷对象可能很快，但一个热点协作空间仍会拖慢切换。可以分批迁移、限制同时恢复数量，并监控新旧路由拒绝和重试。

如果存储只能做到某个行范围内原子检查，应明确对象是否全部落在同一范围；多行更新的部分成功需要额外设计，不能从单行 fencing 推断完整对象原子性。
