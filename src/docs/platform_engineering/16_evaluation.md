## 需求场景：演示答对三个问题，能否交给团队使用

演示里的问题与文档措辞很接近，实际用户却会省略背景、混用术语、查旧版本，或询问无权查看的项目。一个总分无法告诉我们系统在这些条件下怎样失败。

本课先建立评测单位、标签和分母，再组织一次可解释的改进。目标是区分检索、回答和执行的结果，并根据业务代价制定上线条件。

## 基础理论：评测对象和真值

**评测样本**是输入、适用条件和预期行为的组合。输入相同但用户权限、文档版本或业务状态不同，预期结果也可能不同。

检索任务可以标注相关来源，回答任务还需要判断断言是否有证据、问题是否完整回答。工具任务需要检查实际效果与次数。模型自己说“执行成功”不能作为效果真值。

标签有歧义时应先澄清。两个评审对同一问题理解不同，可能说明需求未定义，而不仅是模型得分不好。

## 指标基础：不同分母回答不同问题

| 指标 | 分子 / 分母 | 能说明什么 |
|---|---|---|
| hit@k | 前 k 条命中至少一个相关来源的查询 / 可回答查询 | 是否找到了至少一份相关材料 |
| recall@k | 检出的相关文档 / 应检出的相关文档 | 相关材料覆盖程度，需定义逐查询聚合方式 |
| precision@k | 返回的相关文档 / 返回文档 | 候选中有多少噪声 |
| 正确拒答率 | 正确拒答 / 应拒答样本 | 对无依据或无权限请求的处理 |
| 错误拒答率 | 错误拒答 / 可回答样本 | 正常问题被拒绝的代价 |
| 任务成功率 | 满足效果验收的任务 / 全部目标任务 | 用户最终完成情况 |

检索命中不等于完整回答。一个问题需要两个条件，命中其中一份材料就可能让 hit@k 得分，却仍无法支撑结论。

回答质量可以逐条检查断言支持、引用正确性、完整性和过期信息。人工核对与确定性断言适合承担关键验收；模型裁判也存在偏差，应抽查其判断。

## 小样本与数据泄漏

八条题全对，只说明在这八条已知输入上满足检查。若反复按这些题修改代码，测试集逐渐变成调试材料，很难代表新问题。

保留开发集用于调整，再留一组未参与调整的验证样本。文档、查询、标注、模型和提示都应有版本，否则今天与昨天的分数可能不在同一口径。

生成具有波动时，对关键样本重复测量并记录结果分布。没有观察到失败，不代表失败概率为零；样本不足时应限制结论范围。

## 学习实验：先理解现有八条样本

```bash
cd labs/platform_path
python3 ai/agent_lab.py evaluate
```

预期有 8 条样本，4 条可回答、4 条应拒答；固定样本上的 hit_at_2 与 correct_refusal_rate 均为 1，model_calls 为 0。

这个脚本只评估词项检索与拒答规则，没有执行生成，也不验证答案忠实性、工具效果或真实模型成本。false_accepts 表示应拒答却发现候选证据的案例数，不能直接当作实际数据泄漏事件数。

### 扩充自己的案例

复制到自己的练习文件再修改：

```bash
cp ai/cases.jsonl /tmp/arena-my-cases.jsonl
python3 ai/agent_lab.py evaluate --cases /tmp/arena-my-cases.jsonl
```

每行使用 id、tenant、query、expected_sources、should_refuse。新增样本应先标注预期，再看系统输出。

```json
{"id":"partial-evidence","tenant":"game-a","query":"timeout dragon","expected_sources":[],"should_refuse":true}
```

这个例子故意超出资料能够回答的范围，当前基线可能失败。它用于揭示“有重合词就接受”的缺陷，不应为了维持 100% 而把预期改成通过。

## 从失败类别决定改进方向

| 失败 | 先检查什么 | 一种可验证的变化 |
|---|---|---|
| 同义词查不到 | 词项与文档表达差异 | 同义词、向量或混合检索的对照 |
| 中文没有结果 | 当前分词仅保留英文数字 | 增加适合数据的分词并检查回归 |
| 命中旧规则 | 元数据与过滤 | 按适用版本筛选并保留旧版查询 |
| 回答超出证据 | 上下文与生成断言 | 改变生成约束并人工检查支持关系 |
| 工具重复执行 | 操作身份与提交点 | 注入故障，检查实际副作用数 |

一次只改变主要因素，保存基线、改动与回归。若同时换模型、资料和检索方法，结果改善后也很难知道原因。

## 业务成本：为什么不能只优化准确率

知识助手答错一条普通术语、泄露其他租户资料、重复创建一张工单，后果不同。根据业务定义硬性条件与可接受退化，再决定综合取舍。

延迟应测用户从提交到得到可用结果的时间；成本应包含检索、重排、模型、工具调用与重试。按成功任务统计单位成本，比只看单次模型请求价格更接近业务价值。

允许人工确认的工单草稿工具，与自动执行不可撤销操作的工具，需要不同验收强度。先把功能责任讲清楚，才能设置合理门槛。

```text
业务目标与适用用户：

哪些样本参与过调试：
基线结果及失败类别：
本次改变与预期收益：
同口径结果、回归与波动：
权限、副作用、延迟和成本：

```

独立任务：增加至少 12 条未出现在参考集里的案例，覆盖同义、中文、半相关、过期、矛盾与跨租户条件。工具恢复另外建立效果验收，不把它混入检索脚本分数。

离线评测可重复，适合发现已知错误；小范围试用能发现未想到的需求和表达，但样本受使用者选择影响。两者应结合，并保留反馈、异常案例与版本信息。

回滚时不仅保存旧模型名，还应能恢复提示、检索配置和相关索引版本。工具已经产生的效果要按业务处理，不能靠切回旧版本抹去。
