## 需求场景：CPU 不高，玩家仍然说慢

聊天请求偶尔要等两秒，进程 CPU 却只有 30%。同时，长连接接入偶尔解析失败，而发送方确认自己写入了完整消息。

这两个问题都要求沿着真实执行路径分析。本课先建立网络与运行时的基础，再讨论如何测量。完成后应能区分计算、排队和 I/O 等待，解释字节流边界，并提交有明确范围的性能证据。

## 基础理论：一次请求经过哪些层

```text
客户端编码 → 网络传输 → 服务端读取/解码
  → 排队 → 业务计算 → 数据库或其他服务
  → 编码响应 → 网络传输 → 客户端读取
```

端到端耗时包含整条链路。服务端某个函数执行 2ms，并不意味着用户 2ms 就能看到结果。连接建立、上游排队、数据库连接池等待和返回传输也会占用时间。

### 从字节到业务消息

对象在内存中有结构，网络上传送的是字节。编码把字段变成约定格式，解码把字节恢复为可解释的数据。双方还要约定版本、边界、长度和错误行为。

TCP 为应用提供有序字节流。它不保留应用一次 Write 的消息边界；读取可能得到半条消息，也可能得到多条消息的一部分。重传和流量控制也不会替你判断一条业务操作是否已提交。

HTTP、gRPC 等应用协议在传输之上定义请求、响应及消息组织方式。使用框架减少了手工协议工作，仍然需要理解超时、大小限制与调用语义。

## 机制推导：用长度明确消息边界

一种简单协议是四字节大端长度加正文：

```text
[长度 N：4 字节][正文：N 字节][长度 M：4 字节][正文：M 字节]
```

读取流程为：累计读满头部 → 解析长度 → 验证长度上限 → 分配正文空间 → 累计读满正文。`io.ReadFull` 能处理底层一次只返回部分字节的情况。

必须先验证长度再分配。否则一个非常大的长度声明就可能消耗大量内存。还要考虑合法长度但一直不发完的连接，它需要读取期限与资源预算。

### 实验一：每次只返回一个字节

```bash
cd labs/platform_path
go test -run '^TestFrame' -v
```

`TestFrame` 把两条消息连起来，并通过 oneByteReader 每次提供一个字节，仍应正确解析 hello 与 world。边界测试检查截断正文和超大长度。

先预测：零字节头部、两字节头部、完整头部但不完整正文分别会怎样？在完全读不到任何头部字节时可以遇到 `io.EOF`，读到一部分后结束则通常是 `io.ErrUnexpectedEOF`。含义影响你把它解释为正常结束还是半条消息。

独立增加零长度正文和连接恰好在两帧之间结束的测试。当前实验使用内存 reader，验证解码行为；真实 socket 的截止时间、连接数和慢客户端仍需另测。

## 运行时基础：CPU、调度与垃圾回收

操作系统调度线程，Go 运行时把 goroutine 的执行安排到线程上。可运行任务多于可用执行资源时就会等待。一个 goroutine 阻塞在锁或 I/O，不代表它一直使用 CPU。

理解 Go 的调度时，可以把 G 看作 goroutine，M 看作操作系统线程，P 看作执行 Go 代码所需的运行时资源。第一轮需要掌握的是：任务数量、可执行资源和阻塞原因是三个不同维度。具体调度实现属于深化，不能靠术语数量替代测量。

程序创建对象会产生分配工作。垃圾回收追踪仍然可达的对象，并回收不再需要的空间；业务上“用完了”但仍被全局 map 引用的对象，仍可能保持可达。大量短命分配和大量长期存活对象，会以不同方式影响运行成本。

调 GC 参数前，先确定是分配率高、存活数据多、缓存无限增长，还是请求积压导致对象无法释放。单看进程内存高，无法判定是泄漏。

## 测量基础：延迟、吞吐与在途数量

**吞吐**是单位时间完成的操作数量；**延迟**是一次操作从定义的起点到终点经历的时间。P99 表示按约定计算后，约 99% 样本不超过的值；它不是最大值，也不代表每个用户的体验。

在稳定、边界一致的系统中，Little 定律描述长期平均关系：

```text
平均在途数量 L = 平均到达速率 λ × 平均停留时间 W
```

每秒 1,000 个请求、平均停留 0.05 秒，对应约 50 个在途请求。必须用均值，不能直接将 P99 代入；在持续增长的过载队列中，也不能把短暂观测套成稳定容量结论。

### 负载模型会影响结果

固定并发客户端往往在收到响应后才发下一次请求。服务变慢时，输入速率也可能下降，从而掩盖过载。固定到达速率模型更能观察外部流量持续进入时的排队，但也要记录实际是否达到了目标输入。

比较两次测量前说明输入大小、请求分布、成功/失败是否计入、并发数、预热、运行时长和依赖环境。测试条件改变时，数字不能直接归因于代码优化。

## 从假设选择工具

| 观察 | 可能原因 | 首先收集什么 |
|---|---|---|
| CPU 高 | 编码、压缩、算法或忙循环 | CPU profile 与请求分布 |
| CPU 低但延迟高 | 锁、队列、网络、连接池等待 | 等待指标、block/mutex profile、Trace |
| 内存持续增长 | 状态保留、积压、分配或泄漏 | heap、对象数量、队列和时间趋势 |
| 吞吐不随 worker 增长 | 串行临界区或共享下游瓶颈 | 锁等待、数据库等待与阶段耗时 |

[Go 官方诊断指南](https://go.dev/doc/diagnostics)介绍各类 profile 和 execution trace 的用途。CPU profile 主要观察实际占用 CPU 的栈，不能完整代表等待时间。采样工具也有开销，应记录采集条件。

## 实验二：建立可以解释的基准

从 `labs/platform_path` 运行：

```bash
go test -run '^$' -bench BenchmarkGrant -benchmem -count=3
go test -run '^$' -bench BenchmarkGrant -benchtime=2s -cpuprofile /tmp/arena-cpu.pprof
go tool pprof -top /tmp/arena-cpu.pprof
```

`ns/op` 是每次基准操作耗时，`B/op` 和 `allocs/op` 是平均分配量与次数。具体数值受环境影响。

当前 BenchmarkGrant 在初始化时写入一次奖励，随后重复查询同一回执。它测的是内存重复请求路径，并发操作还会竞争同一个 Ledger 锁。这个结果不能代表首次创建奖励、真实数据库提交或网络容量。

独立练习：另写不同请求 ID 的基准。每次新 ID 会积累回执和事件，运行时间越长数据越大；应记录对象数量，说明你是否希望把增长成本纳入测量。不能通过无限预分配获得一个无法解释的最好数字。

## 业务应用：把“优化了”写成证据

以聊天网关为例，先确定目标动作是发送到服务端、服务端持久保存，还是接收方收到。然后为排队、业务处理和下游调用分别计时，找出最值得验证的假设。

一份最小报告包含：

```text
业务动作与目标：
负载、数据、版本和机器条件：
修改前的吞吐、延迟、错误与资源：
瓶颈假设及支持证据：
一次只改变的因素：
修改后的同口径结果与波动：
没有覆盖的场景：
```
