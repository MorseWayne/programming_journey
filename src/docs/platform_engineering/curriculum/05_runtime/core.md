## 先区分三种“程序看起来没问题”

并发程序可能测试时没有崩溃，但仍有数据竞争；也可能没有数据竞争，却违反业务顺序；还可能结果正确，但一直保留不再需要的任务和内存。

先修：[B06 同步](../../backend_basics/06_goroutines_mutex.md)、[B07 取消](../../backend_basics/07_channels_context.md)、[系统卷讲义](../03_systems/core.md)。本讲分别追踪可见性、生命周期与资源，而不把它们混成“用了锁就安全”。

## 一、执行先后需要由同步关系支持

两个 goroutine 访问同一变量，不能仅凭“这段代码通常先执行”判断另一个能看到结果。语言内存模型规定哪些同步动作建立先行关系。

```go
// 片段：放在 main 内并引入 fmt。
var message string
done := make(chan struct{})
go func() {
    message = "ready"
    close(done)
}()
<-done
fmt.Println(message)
```

写 message 在关闭 done 之前；观察到通道关闭的接收与该关闭建立相应同步；随后读取 message。这条关系支持结果为 ready。

把通道替换成普通 bool，并让另一 goroutine 无同步地反复检查，不提供同样保证。缓存、编译器和执行交错不需要按照人的直觉安排。

Mutex、channel、原子操作等有各自的同步规则。选择它们时先说明谁发布数据、谁观察完成、哪些访问都必须遵循同一规则。

## 二、没有 data race 仍可能丢失业务更新

假设 Get 和 Set 都分别加锁：

```text
A Get=0 → B Get=0 → A Set(10) → B Set(10)
```

每次内存访问都受保护，但两次独立增加只留下 10。受保护的是单次读写，没有保护完整的读改写。

解决方式可以是一个覆盖完整动作的临界区、数据库条件更新，或者一个拥有状态的执行者。关键是哪个边界能够维持不变量，而不是把某个原语放进代码就结束。

### 原子操作的范围

atomic Add 可以原子更新一个数值；CAS 可以在当前值等于预期时替换。若规则同时涉及余额、领取记录和事件，单个数值原子化并不能让三份状态一起成功。

无锁算法还可能有重试、自旋、ABA 等需要证明的问题。应先确认有相应性能需要与验证能力，才能承担更复杂的实现。

## 三、发布快照时，发布与修改权都要设计

配置快照可以先在局部完整构造，再通过同步机制让读取者看到。发布之后保持不可变，会让读者看到一致的配置组合。

但如果快照里含 map，而更新者还持有该 map 并继续修改，就破坏了不可变约定。原子替换顶层指针并不递归冻结所有子对象。

可以在发布前复制必要数据，发布后只读；更新时构造新版本。还需决定一次长任务绑定哪个版本，避免执行中混用新旧规则。

练习：为配置中的限额 map 画出所有引用，指出哪些路径可以修改。只有所有路径都符合约定，才能依赖不可变设计。

## 四、goroutine 的退出必须有人负责

每个后台任务都应有完成条件、取消入口、错误接收者与资源释放者。否则它可能永远等待一个不会再发生的发送或接收。

| 阻塞位置 | 谁可能提前退出 | 需要的安排 |
|---|---|---|
| 生产者发送任务 | 消费者 | 同时等待投递与取消 |
| 消费者等待任务 | 生产者 | 关闭协议或取消信号 |
| 等待外部 I/O | 调用方 | 有支持取消的 I/O 或明确期限 |
| 返回错误给上层 | 上层已结束 | 避免无人接收导致永久阻塞 |

context 表达取消意图，WaitGroup 等待执行者退出，channel 组织通信。它们分别负责不同部分。

取消之后，已经提交的数据库效果不会自动撤销。函数收到取消要返回什么，应与事务状态和查询机制一致。

## 五、并发上限不是全部内存上限

一个工作池只有十个 worker，却可能预先读入百万项任务，每个任务再携带大对象。正在执行的任务有限，输入源与等待对象仍然可能占满内存。

需要同时约束任务产生、队列、执行和结果保留。结果消费慢也可能把已经完成的对象长期留在内存中。

如果一个任务平均持有 1MB，数万在途任务就会形成很大存活集。GC 不能回收仍然可达的对象，解决方向可能是背压和生命周期，而非调小某个 GC 参数。

## 六、从分配、存活与保留看 GC

分配率描述单位时间创建多少新内存，存活集描述仍需保留的对象。短命分配多会增加回收工作；长期引用大对象则使回收后仍然很大。

标准 Go 工具链使用追踪式垃圾回收，根据可达关系识别存活对象。调整目标会影响 CPU 与内存之间的权衡，但不能让仍被业务引用的数据消失。具体实现与参数应结合工具链版本核对 [Go GC Guide](https://go.dev/doc/gc-guide)。

因此先看 heap 中保留了什么、由谁引用，再讨论池化、预分配或参数。池化减少一部分分配，也可能延长对象存活和增加并发管理成本。

### 逃逸分析不是固定口诀

返回地址不必靠“函数局部变量会消失”猜测安全性，Go 会安排相应存储。是否放在堆上取决于使用情形与编译器分析，不应把某次编译结果当成永久语言规则。

性能报告应记录编译器、输入与运行条件。优化前后的分配变化，需要结合实际路径解释。

## 七、如何把运行时观察与业务问题关联

CPU profile 观察执行中的计算栈，heap 关注分配或存活，mutex/block 关注特定等待，trace 帮助看调度与事件。工具视角不同，没有一个数字能够独立回答全部问题。

例如高延迟与大量 goroutine 同时出现，可能是下游等待导致任务积累；先限制新任务与改善依赖，再看 goroutine 和内存是否随之变化，才能验证因果方向。

### 分层练习

1. 写出通道发布示例的先行关系，替换为 Mutex 后再次解释。
2. 构造无 data race 的丢失更新，说明为什么 race 检测无法证明业务正确。
3. 对一个处理流程标记生产、排队、执行、结果四类资源。
4. 设计固定调度信号来触发取消，不用随机 sleep 猜测时序。
5. 给高内存列出高分配、高存活、运行时保留和系统视角四个解释，分别需要什么证据。
