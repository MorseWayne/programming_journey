## 三份看似相同的数据为何不一致

任务已经完成，数据库显示 done，缓存仍显示 pending，通知服务尚未推送。这三种观察不一定都由同一种错误产生，先要明确每份数据的职责与允许的延迟。

先修：[数据库讲义](../06_databases/core.md)、[B07 通信与取消](../../backend_basics/07_channels_context.md)。本讲先分清数据角色，再推导更新与恢复。

## 一、权威事实决定争议怎样裁决

权威数据用于判断业务事实，缓存和搜索索引可能是为了特定访问方式生成的派生数据。消息可以传递命令，也可以通知已经发生的事实。

| 数据 | 一个可能的职责 | 失效后怎样恢复 |
|---|---|---|
| 领取记录 | 谁已经获得过这份奖励 | 从持久记录与恢复日志重建 |
| 展示余额缓存 | 快速显示近期结果 | 重新读取权威余额 |
| 通知队列 | 继续尝试交付消息 | 保留未完成任务并重放 |
| 搜索索引 | 按关键词发现任务 | 从原始文档与变化记录重建 |

组件名字不能决定角色。Redis 可以存缓存，也可以承载唯一任务状态；后一种需要独立讨论持久性与丢失范围。

## 二、缓存命中率不是正确性指标

cache-aside 通常先读缓存，未命中再读数据库并回填。读取变快的同时，多个执行者可能产生新的交错。

```text
A 缓存未命中，读到旧值 100
B 提交新值 110，删除缓存
A 迟到回填 100
```

缓存现在存在但已陈旧。这个时间线说明“写库后删缓存”需要额外假设，不能独立证明强一致。

TTL 为某次缓存写入设置存活期限；如果旧读者很晚才回填，陈旧窗口也会重新开始。因此关键读是否允许走缓存，应由业务决定。

对资格判断和资产操作，可能直接读取权威状态；对允许短暂滞后的展示，可通过 TTL、失效重试和版本校验满足明确承诺。

## 三、从访问方式选择缓存结构

一个大 JSON 值便于整体读取，但只修改一个字段也可能需要整个读改写，增加网络与并发协调成本。哈希结构适合某些字段访问，有序集合适合按分数取范围，列表与流则有不同消费语义。

选择时先写操作组合：是否需要按字段更新、按顺序遍历、去重、限长或原子条件修改。不能因为某个命令简单，就忽略其他访问的成本。

大 key 与热 key 也不同。大 key 主要涉及单项大小和操作耗时；热 key 涉及访问集中。一个很小的 key 同样可以成为热点。

## 四、缓存失效会改变下游负载

假设每秒 10,000 次查询原先有 99% 命中，数据库约承受其中 100 次。缓存整体不可用时，数据库可能突然承受接近全部请求，远超过平时观察到的负载。

这不是容量自动增加，而是请求路径变化。恢复方案可以包含限流、关键数据优先、合并加载、分散到期和可接受的旧值读取，但都需要说明业务边界。

singleflight 可以合并某个进程里同 key 的同时加载；它不自动限制所有不同 key，也不自动协调所有副本。负缓存要区分确实不存在与依赖暂时失败。

## 五、消息有至少三种不同抽象

队列常用于分配工作，发布订阅用于向订阅者传播，日志保留有序记录供不同消费者按位置读取。具体产品可能组合这些能力，使用前仍需核对持久化、保留与确认。

| 业务问题 | 更关注的属性 |
|---|---|
| 告诉在线用户“有新内容” | 低延迟，丢失后可补查 |
| 后台处理一项必须完成的任务 | 持久接收、重试、状态查询 |
| 为搜索重建完整变化 | 保留、回放、位置与版本 |

实时通知无法补发时，业务可能要靠权威数据和游标恢复；日志被保留也不自动保证消费者处理效果正确。

## 六、确认点决定谁负责继续尝试

发送调用返回、消息系统持久接受、消费者收到、消费者提交业务效果，是不同事件。每次确认都要定义其承诺。

如果消费者先确认再修改业务，修改失败可能导致任务不再重投；如果先修改再确认，确认丢失可能触发重复。因此需要把去重记录与受保护效果放进同一提交边界，或让下游接受稳定操作身份。

同一事件 ID 改变参数时应该被识别为冲突，否则去重会掩盖不同业务操作。事件身份还需在多生产者和重启后保持适当唯一性。

## 七、outbox 的正确性与运行责任

业务数据与 outbox 同一事务提交，保证已成立事实留下继续交付的记录。发送器扫描并发送，成功后更新发送状态。

这仍可能重复发送。多发送器还需要协调领取与重试，避免一项永久失败事件让整个队列停滞。运行中应观察最老待发年龄、失败分类、重试次数和追平能力。

“发送器稍后会重试”只有在它确实运行、记录未丢失且失败可处理时，才是一项有效恢复策略。

## 八、顺序、事件时间与派生视图

消费位置表示读取进度，不一定等于事实发生时间。网络延迟、重试和多分区可能让较早发生的事件较晚被处理。

搜索更新如果不检查版本，旧事件可能覆盖新文档。可以让派生视图比较业务版本或采用能正确重放的规则；若操作顺序不可交换，需要保留相应的顺序范围。

水位等概念用于表达对时间进展的判断，仍依赖迟到策略和故障假设。不能把一个观测到的时间自动当成“更早事件永远不会再来”。

### 分层练习

1. 为任务事实、展示缓存、通知与搜索写出权威来源和允许延迟。
2. 复现迟到回填，并说明 TTL 能保证的范围。
3. 在收到消息、提交效果、发送确认之间分别安排失败。
4. 让同一个任务先产生新版本，再让旧事件迟到，设计拒绝覆盖规则。
5. 估算缓存失效和重放同时发生时的负载，设置恢复速率。
