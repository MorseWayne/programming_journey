## 接口能返回 JSON，只是开始

任务领取接口收到用户、任务和请求 ID。真正需要回答的是：调用者是谁、任务是否属于他、是否满足资格、是否已经领取、失败时留下什么、响应丢失后怎样查询。

先修：[B03 HTTP](../../backend_basics/03_http.md)、[数据库讲义](../06_databases/core.md)、[C01 契约](../../01_contracts.md)。本讲将应用设计与安全放进同一条业务链路。

## 一、为接口建立明确完成点

POST /claims 可以表示提交领取请求，但要定义成功响应究竟意味着已接收、已持久保存还是资产已完成。如果处理异步，应提供状态身份与查询方式。

客户端重复点击和网络重试也不同。同一个 request_id 帮助识别传输重复；同一任务奖励最多一次，需要领域身份保护。

```text
可信身份 → 参数解析 → 资源权限与业务资格
  → 领域唯一性 → 事务效果与回执 → 明确响应
```

这些步骤可能由不同层承担，但职责不能因为分层而消失。

## 二、把身份来源与请求字段分开

请求体里填写 user_id，并不证明调用者就是该用户。服务端应从可信认证结果得到主体，再判断主体是否有权操作目标资源。

认证回答“是谁”，授权回答“能做什么”，业务资格回答“这一次是否满足领取条件”。三者不能只靠一个 Validate 函数名暗示已经全部完成。

查询时携带 tenant 或 team 范围也不够，范围本身必须与可信身份一致。下游不能重新采用未经验证的请求体字段覆盖已确认上下文。

### 会话与 token 还需要生命周期

凭据可能过期、撤销或被替换。只验证格式正确，无法确认当前仍有效。实际策略还要考虑访问范围、有效期与撤销需求。

口令通常应使用专门的口令哈希机制与合适参数保存，而不是可逆加密后随时取回原文。算法与参数应跟随可信安全资料和所用库维护，不自行设计密码学方案。

## 三、输入校验按使用位置设计

类型校验检查字段类型，业务校验检查范围与关系，安全处理检查数据将进入什么解释环境。

| 数据去向 | 关键边界 |
|---|---|
| SQL | 参数绑定，不能把输入拼成可执行语句 |
| HTML 页面 | 按输出上下文编码，防止输入成为页面代码 |
| 文件路径 | 限定允许位置和访问能力，避免任意路径选择 |
| 外部 URL | 检查允许访问的目标与重定向等路径 |
| 日志 | 避免记录凭据与不必要的敏感内容 |

“过滤几个特殊字符”无法成为所有上下文的通用方案。相同文本在数据库参数、HTML 属性和 URL 中有不同规则。

请求大小、字段长度和集合数量同样是接口契约。解析器能解析一个超大输入，不意味着服务应该接受它。

## 四、浏览器为什么带来额外边界

浏览器可能自动携带相应 Cookie，因此某个跨站请求即使由其他页面发起，也可能带上已有会话。CSRF 关注这类请求是否违背用户实际授权。

CORS 主要参与浏览器对跨源访问响应的限制，不等于服务端业务授权。不能因为配置了允许来源，就允许任意用户操作资源。

XSS 让不应作为程序执行的数据进入页面执行环境，可能进一步影响用户会话与操作。模板、编码与信任边界需要一起设计。

初学 API 时可以先使用明确的测试客户端；进入浏览器应用后，再逐项补充这些机制，不能把客户端换成浏览器而保持所有假设不变。

## 五、应用分层要让规则保持集中

handler 负责协议转换与响应；业务层表达领取规则；存储层负责与数据库交互并提供约定保证。配置、日志和上下文在清晰入口传入。

分层的收益在于变化更容易定位。例如将命令行换成 HTTP，不必复制领取规则；用测试存储替换数据库，可以先验证领域分支。

但是“业务层调用了两个独立存储方法”不自动形成一个事务。接口设计必须表达需要一起提交的动作，不能让抽象层隐藏关键边界。

## 六、响应之前和之后的失败

参数非法可明确拒绝；事务冲突需要保留原状态；提交过程中连接中断可能留下结果未知。后者需要按操作身份查询或重试，不能无依据地报告“肯定未执行”。

响应开始发送后，不能假设随时重写状态码和完整正文。处理链应尽可能在确定状态后再提交响应，并保留写响应失败的运行记录。

上游取消也不会撤销已提交效果。错误分类要让客户端知道应该修正输入、重新授权、稍后查询还是有界重试。

## 七、中间件顺序影响信任与观察

日志、追踪、认证、授权、限流与恢复可以组成处理链。它们的执行顺序决定能否获得身份、哪些请求计入指标、错误由谁转换。

例如按用户限流需要先确认可信用户；否则攻击者可随意更换未验证字段。panic 恢复可以保护进程边界，但必须记录失败，不能把未知状态包装成成功。

为每层写出输入、输出和失败行为，比单纯堆叠中间件更容易审查。

## 八、验收应同时包含合法与拒绝场景

仅测试非法访问全部被拒绝，可能得到一个谁也不能用的系统。还需要证明合法用户能完成目标，而且别的用户、团队或版本不会被误伤。

| 场景 | 应检查 |
|---|---|
| 合法新领取 | 资格、余额、领取事实与回执 |
| 同一操作重试 | 原结果与效果次数 |
| 新 ID 重领同一奖励 | 领域唯一性 |
| 跨用户或跨团队 | 权限和数据范围 |
| 过期或撤销凭据 | 身份生命周期 |
| 提交后响应丢失 | 可查询与可解释的恢复 |

### 业务练习

写一份接口说明，明确状态码、错误类别、请求身份、资格来源、资源限制、成功完成点和查询方式。然后沿每条失败路径标出谁负责验证。
