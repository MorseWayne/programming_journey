## 为什么程序“已经写了”还可能恢复失败

虚构任务服务更新配置：写入文件后返回成功，随后机器异常重启，文件却可能缺失或不完整。要分析这个问题，需要分清程序、运行时、内核、文件系统和设备承担什么职责。

先修：[B01 进程与状态](../../00_system_model.md)、[A10 文件](../../beginner/10_files_json.md)。操作系统的三条主线是资源虚拟化、执行协调和持久保存；本讲把它们放在同一条路径中。

## 一、地址不是物理内存位置的直接承诺

进程看到的是自己的虚拟地址空间。操作系统与硬件把地址映射到实际内存页，并检查相应访问权限。不同进程可以看到相同数值的地址，却访问不同内容。

**页**是内存管理的一种固定大小单位，**页表**保存映射信息，**TLB**缓存常用地址转换结果。它们解决的是内存访问，不是数据库里的业务行定位。

申请了大段地址空间，也不一定立刻让每一页都驻留在物理内存。实际访问时可能触发缺页处理，才建立或调入对应内容。

### 为什么几个内存数字不相等

Go heap 统计语言运行时管理的对象，进程 RSS 统计实际驻留的内存视角；此外还可能有线程栈、映射文件、运行时保留空间和其他区域。

因此“业务对象减少了”与“RSS 立即下降”不是同一事件。先弄清指标对应的层，再判断是不是泄漏。

## 二、系统调用是一条职责边界

普通 Go 函数可以只在用户态计算。打开文件、读取 socket 等操作需要请求内核服务，称为系统调用。

内核负责资源访问、权限检查、阻塞与唤醒等。程序可能在等待 I/O 时不使用 CPU；看到 CPU 低不能推断它有很大剩余处理能力。

```text
业务函数
  → Go 标准库与运行时
  → 系统调用
  → 内核文件/网络与缓存管理
  → 设备或远端
```

一次逻辑操作不一定对应一次系统调用。缓冲可能把多个小写合并，也可能让一次读取先从已有缓冲中取得数据。

## 三、文件名、文件对象与描述符

文件名是目录中寻找对象的入口。打开文件后，进程获得文件描述符，用来引用内核维护的打开文件状态，例如当前偏移和访问方式。

在典型 Linux 文件语义下，删除目录里的名字，不一定立即让仍被打开的文件内容消失。只要相应引用仍存在，数据与空间可能继续保留。

这解释了一个常见现象：日志路径已经删除，磁盘占用却没有下降。问题需要沿“谁仍打开它”查找，重复删除文件名未必有帮助。

### 偏移为何影响并发读取

读取后，文件偏移可能向后移动。共享同一个打开文件状态的操作，需要清楚其偏移关系；按明确偏移读取与依赖当前位置读取是不同契约。

程序还应处理短读短写。请求读取 4KB，只得到部分字节，不一定说明数据格式损坏；需要结合返回数量、错误与协议判断。

## 四、页缓存让快与稳成为不同问题

文件数据可能先进入用户态缓冲，再进入内核页缓存，最后由系统安排写到设备。缓存能减少频繁小 I/O，但会产生不同层次的完成点。

| 观察到的事件 | 通常可以说明什么 | 不能直接推出什么 |
|---|---|---|
| 应用缓冲接受数据 | 数据进入当前缓冲 | 内核或设备已接受 |
| write 返回成功 | 按接口约定接受了写入 | 所有故障下都可恢复 |
| 完成相应同步操作 | 按文件系统与设备约定推进持久性 | 远端副本或整个业务事务完成 |
| 数据库 COMMIT 确认 | 满足该数据库配置下的提交协议 | 任意外部通知同时生效 |

同步需要明确对象和语义。文件内容与目录项是不同状态；恢复保证还受到文件系统、设备和配置影响。

## 五、推导一次配置替换

直接打开旧配置并截断，再逐段写新内容，崩溃可能留下空文件或半份文件。一个常见设计方向是先写同一文件系统中的临时文件，完成内容校验与必要同步，再替换名字，并按要求同步目录状态。

```text
旧版本可读
  → 写临时新版本
  → 校验完整性
  → 满足内容同步条件
  → 原子替换名称
  → 满足目录持久化条件
```

“名字替换是原子的”不等于“整个流程在所有机器故障下已经持久”。原子性关注观察是否看到半次替换，持久性关注确认后经历故障还能否恢复。

这个流程也不是跨多个文件的通用事务。多个文件需要一起更新时，应设计版本目录、清单或其他一致的切换依据。

## 六、调度、阻塞与 Go 的关系

操作系统线程可能处于运行、可运行但尚未被安排、或阻塞等状态。上下文切换使不同工作共享 CPU；过多竞争会增加等待和管理成本。

Go 的 goroutine 在运行时层组织执行。网络等待、系统调用和 CPU 计算会与线程及运行时调度发生不同交互，所以 goroutine 数量不能直接换算为 CPU 利用率。

需要同时区分：没有工作、等待锁、等待网络、等待被调度、受资源配额限制。这些情况都可能表现为某些请求很慢，但修复手段不同。

## 七、容器为什么改变观察视角

namespace 改变进程看到的某些资源范围，cgroup 管理资源用量和限制。容器可以看到自己的进程与网络视图，也可能受到独立 CPU 或内存限制。

宿主机还有空闲 CPU，而容器已达到配额，两者可以同时成立。容器内存超限与主机总体内存用尽也不是同一条件。

不要因为程序跑在容器里，就跳过进程、文件和信号知识。退出信号能否到达实际业务进程，数据路径是否挂载到保留存储，都需要具体确认。

## 八、把诊断写成可反驳的假设

假设“磁盘满导致写入失败”，应观察空间与写入错误；假设“进程泄漏描述符”，应观察打开数量与增长；假设“调度受限”，应比较可运行等待与资源限额。

工具名称是入口，不是结论。proc、进程列表、内存和 I/O 统计都需要说明时间窗、单位与进程/主机视角。

### 分层练习

1. 画出变量、文件描述符、页缓存与磁盘数据之间的关系。
2. 为配置替换的每个步骤标记一次崩溃，写出恢复时可能看见的版本。
3. 解释日志路径消失但磁盘不释放，指出应查哪个持有者。
4. 给低 CPU 高延迟列出三个不同原因，以及各自能推翻它的证据。
