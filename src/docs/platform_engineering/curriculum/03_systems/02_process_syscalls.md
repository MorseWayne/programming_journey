# 03.02 进程与系统调用：本地 IM 工具怎样运行在操作系统上

> DeepTutor 初稿经技术和教学审阅后的静态课程。进程图、调用时间线、命令与输出均为按条件推导的教学预期；本次没有运行 Go 程序、Linux 观察命令、系统实验、站点构建或 IM 服务。

## 本章从哪里开始

03.01 已让你区分位、字节、地址、内存与磁盘；01.01–01.12 已让你从 Go 源码走到一个虚构本地 IM 历史工具。你可以写出 `imhistory check -file history-c-a.json`，但仍可能疑惑：**磁盘上的程序怎样变成正在运行的进程？Go 的 `os.Open` 为什么能读文件？失败由哪一层产生，最后怎样变成命令退出码？** 本章沿这一条实际任务逐层回答。

`c-a` 会话、`u-a` 用户和 `m-a` 消息均为虚构数据。本工具仍只读写本机版本 1 JSON，默认最多读取 1 MiB；本地 `check` 成功只说明文件满足课程格式和字段规则，不意味着服务端受理、跨设备同步、消息送达或已读。一次操作系统调用成功，也不能自动推出上层业务成功。

| 第一次阅读 | 第二次阅读 | 个人练习留下什么 |
|---|---|---|
| 程序/进程、启动退出、用户态与内核态 | 地址空间、文件句柄、错误边界与阻塞 | 一张分层时间线和三种失败路径 |

先修只要求理解函数、返回值、`error`、文件读取和 03.01 的字节/地址。03.03 将详细讨论 PID、环境、信号、文件描述符与权限；03.04 讲线程调度；03.05 讲地址转换；03.07–03.08 讲文件内部结构与持久性。这里先建立必须的直觉，不把后续机制当成已掌握。

## 一、一个程序文件，可以启动多个进程

**源码**是人写的 Go 文件，例如 `cmd/imhistory/main.go`。**可执行文件**是构建后供操作系统装载的程序文件，存放在文件系统中；仅仅有这个文件，不表示它正在处理消息。**进程**是程序的一次运行实例：它有正在执行的状态、自己的虚拟地址空间、打开的资源和操作系统为它记录的信息。对同一个可执行文件连续启动两次，可以得到两个不同的进程实例；一个实例退出，程序文件仍可留在磁盘上。

```text
磁盘：同一份 imhistory 程序文件
          │ 启动第一次           │ 启动第二次
          ▼                      ▼
     进程 A：自己的状态      进程 B：自己的状态
     读取 history-c-a.json   读取另一个教学文件
```

“进程”与“程序”不能互换。程序文件可以被复制、删除、替换或留在磁盘；进程关心一次运行时刻的状态。进程 A 与 B 即使使用同一份程序代码，也不能直接把 A 的普通 Go 变量当作 B 的变量访问。未来的两个客户端若要交换消息，需要明确的进程间通信或网络边界，不能把本地 `map` 当作共享权威历史。

先把另外两个常见词放在正确位置：**线程**是进程内的执行单位，多个线程可共享同一进程的一些资源；**goroutine** 是 Go 运行时管理的并发任务，并不等于一个操作系统线程，更不等于一个进程。Go 运行时可能使用多个线程承载多个 goroutine，具体调度留到 05 卷。这里不根据“源码里有一个 `main` 函数”推断系统中只有一个线程，也不根据“有两个 goroutine”推断有两个进程。

| 对象 | 放在哪里或由谁管理 | 这门课里先记住什么 |
|---|---|---|
| Go 源文件 | 项目目录 | 供工具链编译，不是正在运行的状态 |
| 可执行程序文件 | 文件系统 | 可以多次启动 |
| 进程 | 操作系统管理的运行实例 | 有独立状态与资源归属 |
| 线程 | 进程中的执行单位 | 与进程共享部分资源，调度细节后学 |
| goroutine | Go 运行时管理的任务 | 不是进程或线程的一一别名 |

**停下来推演：** 进程 A 在内存里追加了 `m-a`，进程 B 会因程序文件相同而立刻看见吗？不会。两者要共享结果，需要经过文件或后续的通信系统；即使都读同一文件，也还要定义读写时机与一致性，不能从“文件名相同”推断同步完成。

## 二、从命令输入到退出：谁依次接手

以教学 CLI 的成功路径为例。shell 读到命令行，解释参数并请求操作系统启动外部程序。操作系统准备一个新的运行实例和进程资源，装载程序所需内容；Go 运行时初始化后调用 `main.main`。`main` 再把参数、`stdout` 和 `stderr` 交给 `run`。这是一张**概念时间线**：不同操作系统、shell、Go 版本的具体启动系统调用与装载步骤会不同，本章不把它固定为某一条 `fork` 或 `exec` 路径。

```text
用户输入命令
→ shell 解析参数并请求启动外部程序
→ 操作系统建立进程执行环境
→ Go 运行时初始化、调用 main
→ run 解析 check/-file
→ 打开并限量读取本地文件
→ 在进程内解码 JSON 和核对领域规则
→ 关闭文件，形成摘要或错误
→ main 给出进程退出状态
→ shell 或调用脚本观察状态及输出
```

这里至少有三种“返回”，不要混为一谈：`run` 可在 Go 内返回整数状态码；底层文件操作可返回 `error` 给 Go 调用方；进程结束后，shell 才观察最终退出状态。01.12 给 `imhistory` 自定 0/2/3/4/5，数字含义是**课程 CLI 合同**，不是 Linux 内核对 JSON 或 IM 消息的通用分类。

01.12 的入口片段可概括为：

```go
func main() {
	os.Exit(run(os.Args[1:], os.Stdout, os.Stderr))
}
```

这是 `package main` 中的教学片段，实际文件需要导入 `os`。`run` 返回之前，内层函数的 `defer` 已有机会执行；`os.Exit` 调用本身**不运行尚未执行的 `defer`**。因此打开文件、登记关闭、检查写入与关闭错误的责任应留在 `run` 或其下层。`os.Exit(0)` 也只表示进程按约定报告成功，不能证明硬盘抗崩溃、远端服务受理或收件设备显示消息。

进程可以在执行中被信号或其他条件终止，实际结束方式未必都是这条正常路径。03.03 再学信号、父子进程和环境；此处先把“正常返回的教学退出码”与“所有可能终止原因”分开。

## 三、虚拟地址空间：地址是进程看到的位置

03.01 的地址是访问数据的位置编号。进程运行时看到的是自己的**虚拟地址空间**：程序代码、全局数据、调用时的栈与动态分配对象所使用的地址区域，都在一个由操作系统管理的地址视图中。下图只表达角色，不表达固定地址、固定上下顺序或真实物理内存排布：

```text
进程 A 的虚拟地址视图（示意）
┌──────────────────────┐
│ 程序代码与只读数据     │
│ 全局/静态数据          │
│ 动态分配的数据          │
│ 各执行任务使用的栈等    │
└──────────────────────┘

进程 B 也有自己的虚拟地址视图。
同一个数值的虚拟地址，不保证指向同一份数据。
```

Go 运行时管理堆对象、goroutine 栈和其他内部结构，不能把传统教科书的一张“代码—数据—堆—栈”矩形图直接当成每台机器的精确内存布局。一个切片值指向进程地址空间中的数据，不是直接指向文件中第几个字节；文件偏移与内存地址是不同概念。读取 JSON 后得到的 `History` 是内存中的解码结果，原始文件仍是另一份由文件系统管理的字节序列。

“虚拟”不等于“假的”或“免费”。进程可以持有大地址范围，但实际触碰、映射、驻留和页表成本要另算。03.05 将解释地址转换、页和缺页；03.06 才比较 Go 对象、分配器和系统内存统计。当前只能从这里推出**有隔离的地址视图**，不能推出某个 `map` 恰好占多少物理内存，也不能说进程 A 的所有字节都常驻内存。

为什么要有这样的视图？其一，程序可用地址访问自己的数据，而不必在每一行 Go 代码中直接管理物理内存位置；其二，操作系统可以控制进程可访问的映射与权限，降低进程任意改写其他进程数据的可能。具体隔离机制和例外条件需要后续章节说明；这里不把虚拟地址空间当作能抵御所有攻击的绝对安全承诺。

## 四、普通代码怎样请求内核服务

普通进程中的 Go 代码通常运行在**用户态**，不能直接把任意物理设备或内核资源当自己的变量修改。**内核态**是操作系统内核执行具有更高权限操作时的模式。系统调用是应用向内核请求服务的基本接口：应用准备参数，经过受控入口进入内核，内核按接口检查和处理，再把结果或失败信息返回调用方。这里的“进入”和“返回”是权限边界变化，不是新开一个 IM 网络请求。

```text
用户态：run → os.Open(path)
                 │ 标准库/运行时封装
                 ▼
受控系统调用入口：请求内核打开文件
                 ▼
内核态：核对路径、权限和资源；返回结果或错误
                 │
                 ▼
用户态：Go 收到 *os.File 或 error，继续业务判断
```

这是一张**概念图**，不是对 Go 当前某个平台源码逐指令的追踪。Linux 可用 `open`/`openat` 等接口完成文件打开；Go `os.Open` 在不同平台和版本的实现细节、实际调用次数可以不同。一个 Go 标准库调用不必严格对应一个系统调用：它可能先做用户态检查，也可能为一个任务请求多次内核服务；普通 `len(body)`、map 查询或 JSON 字段判断一般是进程内计算，不能把“调用了函数”直接写成“进入了内核”。

系统调用与**普通函数调用**的差别是权限边界和内核服务；与将来学习的**RPC**差别是后者跨进程或网络协议边界。库函数也可能包装系统调用，所以读到 `os.Open` 时先说“它需要操作系统文件服务”，再查文档或实际环境确认具体内核接口。不要把概念图当作每次运行都逐项发生的跟踪日志。

内核核对路径能否打开、是否有访问许可和资源是否可用；它不负责判断 JSON 版本是否为 1、`messages:null` 是否非法、正文是否超过课程规则。后者是本地工具在读到字节之后进行的格式和领域判断。内核文件权限也不等于 IM 的会话成员权限：即使进程能打开本地文件，线上谁有权查看会话仍需后续身份和授权设计。

## 五、沿 `check` 追踪一次受控文件读取

现在把前四节放回一个用户任务：`imhistory check -file history-c-a.json`。假设文件存在、进程有读取权限，且字节数不超过课程默认的 1 MiB，即 1,048,576 B。01.12 约定输入为版本 1 JSON，顶层含 `version`、`conversation_id`、`messages`；空数组 `[]` 合法，缺失或 `null` 不合法。每条消息还有必需字段与会话内重复 ID 规则。这些是工具自己的**格式与业务合同**，不是 Linux 文件系统的规则。

| 步骤 | 谁主要负责 | 得到什么或失败什么 | 到此为止还不能推出 |
|---:|---|---|---|
| 1 | shell/操作系统 | 启动一次进程，传入参数 | 文件内容合法 |
| 2 | Go 命令入口 | `flag.FlagSet` 解析 `check`、`-file` | 路径确实存在 |
| 3 | Go `os` 与内核文件服务 | `os.Open` 返回 `*os.File` 或错误 | JSON 可解码 |
| 4 | Go 文件适配器与内核 I/O | 限量读取最多 `maxBytes+1`，判定是否超限 | 读取到的字节满足 v1 |
| 5 | Go 解码与领域代码 | 严格 JSON、版本、字段、时间、重复 ID | 服务端保存过消息 |
| 6 | Go 资源代码 | 完成需要的关闭并处理应报告的错误 | 崩溃后必然耐久 |
| 7 | Go 命令入口/进程 | 成功摘要写 `stdout` 并退出 0 | 设备已接收或用户已读 |

`os.Open` 返回的 `*os.File` 是 Go 对打开文件的句柄；在 Linux 模型中，它关联进程可使用的**文件描述符**，通常是一个整数编号。描述符不是“文件的字节本体”，也不是 JSON 对象；它是进程请求内核继续操作打开资源时使用的标识。描述符编号、内核打开文件状态、目录项和数据之间的详细关系将在 03.07 讲。本章只需要知道：**打开成功后，进程拥有一项需要管理生命周期的资源**。

以下是 01.08–01.12 已讲过的读取思路的教学摘要，不是本项目新增的软件：

```go
f, err := os.Open(path)
if err != nil {
	return nil, fmt.Errorf("open history: %w", err)
}
defer f.Close() // 简化片段；完整实现须按职责检查需报告的 Close 错误。

data, err := io.ReadAll(io.LimitReader(f, maxBytes+1))
if err != nil {
	return nil, fmt.Errorf("read history: %w", err)
}
if int64(len(data)) > maxBytes {
	return nil, ErrInvalidHistory
}
// 后续再严格解码 JSON 和检查 v1 领域规则。
```

片段假定 `path`、正数 `maxBytes`、`ErrInvalidHistory` 已由所在文件适配器定义，实际文件需导入 `fmt`、`io`、`os`。`maxBytes+1` 多读一个字节是为了区分“恰好达到上限”与“原文件超过上限”；它不增加可接受的文件大小。此处的 `defer f.Close()` 演示打开后登记关闭；01.12 的完整导出路径还要处理写入与关闭失败，不能从一个短片段推断所有资源错误已覆盖。

从概念上看，读取文件要经过用户代码与内核文件服务；但是 `io.ReadAll` 如何分批请求数据、Go 如何缓冲、底层具体调用哪个 Linux 接口，都取决于实现和环境。不能对着这六行 Go 代码声称“正好发生六次系统调用”。反过来，`json.Decoder` 和 `history.ValidateMessage` 主要在进程里处理已经拿到的字节，也不能把它们简单叫做系统调用。

### 字节从哪里到哪里

本地文件保存的是字节。内核的文件服务把请求到的数据提供给进程；Go 用 `[]byte` 读入进程可访问的内存，然后解码成结构体、切片和字符串。若文件本身在缓存中，读取可能不必每次都访问物理磁盘；若需要等待底层 I/O，调用可暂时不能继续完成。这里先记**请求和等待**的区别；页缓存、短读、偏移、设备和刷盘在 03.07–03.09 展开。

同一份 JSON 可产生几个不同结论：`os.Open` 成功说明路径在当前条件下可以打开；限量读取成功说明读到了可供解码的字节；JSON 解码成功说明语法可解释；版本与领域校验成功说明满足当前教学合同。**每一步只扩大一点证据范围**。例如内核完全可以成功读出 `{"version":99}`，工具随后仍须拒绝未知版本。

## 六、错误从哪一层来，怎样变为退出码

01.12 为这个本地工具约定：0 成功或显式帮助；2 用法错误；3 输入历史无效；4 文件 I/O 失败或导出目标冲突；5 其他未预期错误。判断错误时要沿原始原因和 `%w` 包装识别身份，不能比较 `err.Error()` 文字，因为文字可能附加路径、语言或平台说明。常见系统原因可用 `errors.Is(err, os.ErrNotExist)`、`errors.Is(err, os.ErrPermission)` 等判断；在教学 CLI 中，它们都属于 I/O 类别 4，诊断再给出合适上下文。

| 场景 | 第一个失败边界 | 课程 CLI 类别 | 对调用方的承诺 |
|---|---|---:|---|
| `-max-bytes=0` | 参数校验，尚未读文件 | 2 | 提示用法，不把它当空文件 |
| 路径不存在 | 打开文件 | 4 | `stderr` 诊断，不输出成功摘要 |
| 进程没有读取许可 | 打开或读取文件 | 4 | 错误上下文中可说明访问失败，不假称 JSON 坏 |
| 读到一半出现 I/O 错误 | 文件读取 | 4 | 不交付部分历史作为成功结果 |
| 超过允许字节数 | 本地输入资源规则 | 3 | 拒绝整份输入，不静默截断 |
| JSON 语法损坏、版本不支持 | 格式校验 | 3 | 不返回半份有效历史 |
| `messages` 缺失/`null`、消息 ID 重复 | 领域/格式校验 | 3 | 明确拒绝；`messages:[]` 仍可合法 |

文件打开失败未必都表示“不存在”：路径错误、权限、描述符资源耗尽等会给出不同底层原因；03.03 和 03.12 再深入资源故障。权限报错也不一定能由应用猜出“用户没有会话权限”。操作系统许可与 IM 身份授权是两个不同层次的规则，不能把一个替代另一个。

成功路径把摘要写到 `stdout`；错误路径把诊断写到 `stderr` 并返回非零退出状态。`list` 要整份校验后才输出第一行，避免坏记录留下部分列表。默认列表只显示消息 ID 与时间，不输出完整正文。调用脚本可以读退出码判断类别，也可以按合同读取两条输出流；只看屏幕上有没有一行文字，无法可靠区分成功与失败。

关闭也属于资源责任：对只读输入文件，关闭失败怎样报告应由文件适配器的合同决定；对 `export` 的目标文件，写入成功但关闭失败不能报告导出成功。`os.Exit` 如果放在打开文件的内层函数，尚未执行的 `defer` 会被跳过，所以 01.12 把它放在最外层 `main`。这不是说 `defer` 能修复写入中断，也不是说返回错误就保证目标文件原样不变；部分写入与耐久性由 03.08 继续讨论。

## 七、五个反例：把层次混淆会得出什么错结论

1. **“一个 goroutine 就是一个进程。”** 错。goroutine 由 Go 运行时管理，多个 goroutine 可属于同一进程，拥有不同任务却共享该进程的许多资源。并发数据归属和调度后学。
2. **“调用任意 Go 函数都会切换到内核态。”** 错。`len(body)`、字符串比较和大部分 JSON 规则是进程内计算；文件、网络等操作可能请求内核服务，但一个高层函数也不一定只对应一次系统调用。
3. **“在内存中得到一个 `History`，原文件就已更新。”** 错。读取与解码在内存中构造对象，不会自动改写磁盘字节；只有明确的写入路径才可能修改文件。
4. **“`os.Open` 成功表示历史消息完整可信。”** 错。它只提供当前文件访问的结果。损坏 JSON、重复 ID、权限问题和远端真实性分别属于不同检查。
5. **“退出码 0 表示用户已经收到消息。”** 错。本地 `check` 的 0 仅表示本工具按当前合同接受文件；线上受理、投递与已读需要其他系统和确认点。

还有一个面向将来 IM 网关的现象：服务进程可能拥有很多连接，却不是每一刻都占满 CPU；等待 I/O、就绪通知、线程调度和应用处理各有不同原因。此处只能提出“进程在等待什么”的问题，不能仅凭连接数或 CPU 百分比下结论。03.04、03.09 会给出调度与事件模型，04 卷再讲连接和协议。

进程结束时，它的普通内存状态不再作为原进程继续运行；若业务数据只放在内存 `map` 里，下次启动不能自动找回。若写过文件，也不能从 `Write` 返回成功直接推出断电后必然能恢复。03.08 会区分用户态缓冲、内核缓存、同步、原子替换与崩溃恢复；本章不提前承诺本地历史的耐久等级。

### 一张故障定位表

| 观察到的现象 | 先查哪一层 | 还应避免的推断 |
|---|---|---|
| 命令提示“未知选项” | CLI 参数解析 | 不说“内核拒绝 JSON” |
| 提示“无法打开路径” | 文件访问条件与错误身份 | 不说“消息内容无效” |
| 文件可打开但版本 99 被拒 | 本地格式合同 | 不说“磁盘坏了” |
| 正常退出却看不到另一端消息 | 当前工具仅本地检查 | 不说“网络偶发丢包” |
| 进程退出后内存消息消失 | 进程生命周期和持久化设计 | 不说“Go GC 擦掉了磁盘” |

## 八、完整时间线与分层练习

以合法 `history-c-a.json` 中含虚构 `m-a` 为前提，尝试在纸上逐步回答：

```text
1  shell 收到 imhistory check -file history-c-a.json
2  操作系统建立一次程序运行实例
3  Go 运行时进入 main，main 调用 run
4  run 解析子命令和 -file（用户态规则）
5  os.Open 请求文件服务；内核返回可用资源或错误
6  进程通过该资源限量读取最多 maxBytes+1 字节
7  若超限则按本地输入规则拒绝
8  解码 JSON，检查 v1、数组形状、字段和重复 ID
9  完成资源关闭，决定是否有需报告的错误
10  成功才向 stdout 写版本、会话与消息数摘要
11 run 返回课程约定状态 0；main 结束进程
12 shell 或脚本读取退出状态并区分 stdout/stderr
```

把第 5 步改成“文件不存在”，流程在文件边界转向 I/O 诊断与退出 4；把第 6 步改成“超 1 字节”，流程在资源规则转向无效历史与退出 3；把第 8 步改成“`messages:null`”，仍能打开和读完文件，但在 v1 规则处退出 3。每次失败都不要先写出成功摘要。`maxBytes` 的默认 1 MiB 是整份文件上限，不是 10.01 的单条正文 6 字节教学规则。

### 分层练习：先回答，再看反馈

<details><summary>1. 可执行文件与进程是一回事吗？</summary>

不是。前者是磁盘上的程序文件；后者是一次运行实例及其状态。</details>

<details><summary>2. 同一份程序能同时有两个进程吗？</summary>

能。两次启动可得到各自的运行状态与资源。</details>

<details><summary>3. 进程 A 的普通 Go 变量会自动变成进程 B 的变量吗？</summary>

不会。要交换状态须使用明确的文件、进程间通信或网络机制。</details>

<details><summary>4. goroutine 是一个操作系统进程吗？</summary>

不是。它是 Go 运行时管理的并发任务，和进程、线程不一一对应。</details>

<details><summary>5. 只看 `main` 一个函数能推断进程只有一个线程吗？</summary>

不能。Go 运行时可能使用多个线程，源码函数数目不是线程数。</details>

<details><summary>6. 进程里的虚拟地址一定是物理内存位置吗？</summary>

不是。它属于进程看到的地址视图，实际转换与驻留在 03.05 深化。</details>

<details><summary>7. 内存地址等于文件偏移吗？</summary>

不等于。前者定位进程地址空间中的数据，后者定位文件字节序列中的位置。</details>

<details><summary>8. `len(body)` 一定要通过系统调用吗？</summary>

不必。它可由进程内已有数据完成，不应把每个 Go 函数都叫系统调用。</details>

<details><summary>9. 系统调用和远端 IM RPC 相同吗？</summary>

不同。系统调用跨应用与本机内核的权限边界；RPC 还涉及进程或网络协议边界。</details>

<details><summary>10. `os.Open` 在所有平台都对应同名 `open` 系统调用一次吗？</summary>

不能这样保证。Go 标准库封装和各平台实现细节可能不同。</details>

<details><summary>11. `*os.File` 就是 JSON 内容吗？</summary>

不是。它是 Go 对打开文件资源的句柄，读取后才得到字节。</details>

<details><summary>12. 为什么限量读取用 `maxBytes+1`？</summary>

多读一个字节才能区分恰好达到上限与实际超限；可接受上限不变。</details>

<details><summary>13. 打开成功但 JSON 语法坏了，是哪个层次拒绝？</summary>

内核允许读取；本地工具的解码规则拒绝，属于输入历史无效。</details>

<details><summary>14. 文件不存在和 `messages:null` 使用相同退出类别吗？</summary>

不相同。前者是 I/O 类别 4；后者是 v1 内容无效类别 3。</details>

<details><summary>15. `messages:[]` 在本课程 v1 中合法吗？</summary>

合法；它明确表达空消息数组。缺失字段或 `null` 不合法。</details>

<details><summary>16. 操作系统允许打开文件就证明有 IM 会话权限吗？</summary>

不能。文件权限与线上会话成员授权属于不同层次。</details>

<details><summary>17. 为什么 `os.Exit` 放在资源处理函数外层？</summary>

它不会运行尚未执行的 `defer`；先让内层完成关闭并返回，再由入口退出。</details>

<details><summary>18. `check` 退出 0 证明文件一定能抗断电恢复吗？</summary>

不能。它是当前进程接受本地文件的结果；崩溃耐久要另行设计和验证。</details>

<details><summary>19. 读文件时等待 I/O，必然让整个机器 CPU 很忙吗？</summary>

不能推断。等待与占用 CPU 是不同状态，调度和 I/O 模型后续学习。</details>

<details><summary>20. `os.Open` 失败时能直接写“JSON 无效”吗？</summary>

不能。还没读到 JSON，先保留打开文件的 I/O 错误身份和上下文。</details>

<details><summary>21. 若 `list` 第三条记录损坏，能先输出前两条再返回错误吗？</summary>

不符合 01.12 合同。先完整校验，再输出第一行，避免部分列表被误当成功。</details>

<details><summary>22. 进程退出后找不到内存消息，能直接归因于 Go GC 吗？</summary>

不能。进程生命周期和是否设计持久化才是首要问题。</details>
