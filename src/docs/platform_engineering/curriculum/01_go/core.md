## 从一个数据丢失问题开始

任务导入器读出一批任务，传给校验函数，随后发现原数据也被修改。开发者说“Go 是传值”，却无法解释这个结果。理解一句语言规则还不够，需要知道被传递的值中究竟保存了什么。

先修：[A04 函数](../../beginner/04_functions.md)、[A05 集合](../../beginner/05_collections.md)、[A06 方法](../../beginner/06_structs_pointers.md)。本讲深入值语义、接口与 I/O 边界，其他语言专题按[本卷分章设计](./README.md)继续展开。

## 一、区分值复制与可访问数据

可以把每次赋值理解为“复制当前类型所定义的值”。整数值本身包含数值；指针值包含地址；切片值描述一段底层数组；map 值允许访问映射结构。

```go
// 片段：放入 main 并引入 fmt。
original := []int{10, 20, 30}
view := original
view[0] = 99
fmt.Println(original) // [99 20 30]
```

这里发生了复制，但复制后的描述仍指向同一数组。函数接收 `[]int` 时也遵循这条规则。

再改变长度：

```go
func extend(values []int) {
    values = append(values, 40)
}
```

调用后原切片变量的长度不会自动更新，因为函数只是把新的描述赋给自己的参数。底层数组是否复用则受容量影响。于是“能观察到元素变化”和“能观察到长度变化”具有不同原因。

### 用图追踪两个层次

```text
调用方切片描述 ──┐
                 ├── 同一底层数组
函数参数描述 ────┘
```

如果需要返回扩展后的序列，函数应返回新切片，并由调用者接收。如果希望调用者不能修改内部数据，返回前应根据可变引用层级复制。

### 复制还可能改变内存成本

从一个很大的数组中保留小切片，底层数组仍可能保持可达。程序只关心几十个元素，却可能因此保留整个大对象。复制小片段可以减少长期保留，但增加一次复制和分配。

所以所有权、生命周期和性能需要一起分析。先问谁在未来还会访问数据，再决定复制、共享不可变对象或同步访问。

## 二、方法集与接口赋值

方法接收者分为值和指针。普通方法调用有时允许编译器对可寻址值自动取地址；接口赋值检查的是类型具备的方法集合。

```go
type Counter struct { n int }
func (c *Counter) Add(n int) { c.n += n }
type Adder interface { Add(int) }
```

`*Counter` 满足 Adder；Counter 值本身不因为“平时能写 c.Add”就自动满足相同接口。为接口选择值还是指针，取决于修改能力与方法集合，不能只凭对象大小判断。

接口让调用者依赖必要能力。比如输入源只需 Read，不必要求它同时支持 Close；只有拥有资源并负责结束生命周期的代码才应要求关闭能力。

把所有接口都定义成十几个方法，会扩大实现和测试负担。先从调用者真实需要的最小行为出发，再随着需求演进。

## 三、接口中的 nil 与错误身份

接口可以理解为同时携带动态类型与动态值。只有没有动态类型和值时，接口才是 nil。一个值为 nil 的具体指针进入接口后，仍保留具体类型。

```go
// 片段：类型和函数放在 main 外。
type InputError struct { Field string }
func (e *InputError) Error() string { return "invalid input" }
func misleadingError() error {
    var problem *InputError
    return problem
}
// 在 main 中打印 misleadingError() == nil，预期 false。
```

这解释了“没有创建错误对象，为什么 err != nil”。正常成功路径应明确返回 nil，而不是返回某个恰好为 nil 的错误指针。

`errors.Is` 适合识别约定错误及包装关系；`errors.As` 适合取得某类错误提供的额外信息。字符串只是说明，不应承担稳定协议身份。

业务需要区分输入错误、冲突、暂时失败与结果未知。若所有错误都包装成一句“failed”，调用者就丢失恢复所需信息。

## 四、I/O 的结果不只有成功或失败

Reader 的 `Read(p)` 返回实际读入数量 n 和错误。可能同时出现 n>0 与结束或错误，因此手工读取时要明确已得到的字节如何处理。

一个业务消息可能跨越多次 Read；一次 Read 成功也不意味着完整消息已经到达。读取“恰好 N 字节”与“直到输入结束”是不同契约。

| 需求 | 可以采用的机制 | 仍需考虑 |
|---|---|---|
| 固定长度头部 | 累积读取或 io.ReadFull | 截断与长度合法性 |
| 文件复制 | io.Copy | 已写入部分与目标关闭错误 |
| 限制请求大小 | 上限检查与有界读取 | 到达上限是合法结束还是被截断 |
| 处理慢输入 | deadline 或协作取消 | 资源所有者怎样退出 |

只读 N 字节并不能证明输入最多 N 字节，可能只是截断了更大的输入。需要拒绝超长时，要设计超限检测或使用提供相应语义的接口。

文件写入成功后，Close 仍可能报告需要处理的错误；持久性还涉及同步与底层存储。资源释放与业务提交不能混为同一个动作。

## 五、泛型解决哪一类重复

当算法结构相同，只是元素类型不同时，类型参数可以保留静态检查并复用逻辑：

```go
func Contains[T comparable](items []T, target T) bool {
    for _, item := range items {
        if item == target {
            return true
        }
    }
    return false
}
```

T 是类型参数，comparable 约束允许使用相等比较。调用时可以由实参推断类型，例如 `Contains([]int{1,2}, 2)`。

接口更适合表达行为差异，例如不同对象怎样 Read；泛型更适合相同算法在一组类型上的复用。两者可以协作，不需要强行用同一种形式表达全部设计。

约束只说明允许的操作，不等于业务等价关系。浮点 NaN 等值的比较规则就可能不符合“元素一定能找到自己”的直觉。应根据业务选择数据表示和判断方式。

## 六、从语言规则迁移到包设计

假设导入器包含读取文件、解析、校验、索引和输出。把纯规则与 I/O 分开，能分别替换输入源、测试非法数据，并在失败时说明哪一步留下了效果。

公开 API 应回答：是否修改参数、谁关闭资源、返回值能否修改、是否支持并发、失败后状态怎样。缺少这些说明时，即使函数名漂亮，调用者仍只能猜测。

### 独立练习

1. 给 Task 增加 map 字段，说明浅复制会保留哪些共享。
2. 让导入函数接收 Reader，返回有效任务和错误，定义部分成功是否允许。
3. 为公开接口补充修改权、关闭权和并发约定。
4. 比较类型参数、行为接口与两个简单函数，说明各自维护代价。
