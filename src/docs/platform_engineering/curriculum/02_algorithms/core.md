## 先把输入规模说清楚

一个程序从任务列表找到指定 ID。列表只有十项时，顺序扫描很直观；达到百万项后，查询频率和数据分布就决定它是否合适。

先修：[A04 函数](../../beginner/04_functions.md)、[A05 集合](../../beginner/05_collections.md)。本讲从成本模型开始，不要求已经会复杂度符号。

## 一、用操作次数比较增长趋势

令 N 为任务数量。顺序扫描最坏检查 N 项；两个嵌套循环如果分别走 N 次，可能检查 N×N 个组合。常数成本会影响实际时间，但增长方式决定规模扩大后的压力。

O 记号描述增长的渐近上界，不是精确运行时长。例如 `2N+10` 在足够大的 N 上可以由一个常数倍的 N 界定。说 O(N) 并没有说明机器速度、数据大小或缓存命中率。

| 处理方式 | 一次典型工作量 | 数量翻倍时的趋势 |
|---|---|---|
| 按固定位置读取 | 常数次定位 | 基本不随 N 增长 |
| 顺序扫描 | 最多 N 次判断 | 工作量约翻倍 |
| 每轮缩小一半 | 约 log₂N 轮 | 通常只增加约一轮 |
| 检查所有二元组合 | 与 N² 同量级 | 工作量可能约四倍 |

最坏情况、平均情况和摊还情况也不同。动态数组扩容可能使某一次 append 很贵，但在适当扩容策略下，一串操作的平均扩容成本可以较低。不能把“通常很快”写成“每次都恒定”。

## 二、先证明二分查找，再谈快

对已排序整数序列，寻找第一个不小于 target 的位置。使用左闭右开区间 `[lo, hi)`：lo 包含，hi 不包含。

```go
func LowerBound(values []int, target int) int {
    lo, hi := 0, len(values)
    for lo < hi {
        mid := lo + (hi-lo)/2
        if values[mid] < target {
            lo = mid + 1
        } else {
            hi = mid
        }
    }
    return lo
}
```

这段放入自己的包中，再按 A09 添加测试。函数可以返回 len(values)，表示没有任何元素满足条件。

### 为什么边界更新正确

循环保持两个已知区域：lo 之前的元素都小于 target；hi 及之后的元素都不小于 target。中间区域还需检查。

若 values[mid] 小于 target，mid 及之前已可排除，所以 lo=mid+1；否则 mid 仍可能是答案，让 hi=mid 保留它作为边界。每一步都缩小未确定区间，最终 lo=hi。

| 输入 | target | 预期位置 |
|---|---:|---:|
| 空序列 | 4 | 0 |
| 2,4,4,9 | 4 | 1 |
| 2,4,4,9 | 3 | 1 |
| 2,4,4,9 | 10 | 4 |

若数据没有排序，上面的排除推理就不成立。算法前置条件应成为调用契约，而不只是写在注释里的愿望。

## 三、查找结构必须与操作组合匹配

map 适合按键定位，通常提供较好的平均查找成本；维护排序数组则有利于范围和顺序读取，但插入可能需要搬移。

例如一百万条 `int64` 的数值本体大约需要八百万字节，尚未计算容器、键和分配开销。若为每个元素创建对象和多层指针，局部性与额外内存可能抵消部分理论优势。

因此选择时同时列出：查询类型、修改频率、是否需要排序、数据规模、内存与最坏情况。单独背诵“O(1) 比 O(log N) 好”无法决定真实方案。

### 哈希冲突意味着什么

哈希函数把键映射为有限范围，不同键可能映射到同一位置。实现需要解决冲突并在必要时扩容，最终仍要确认键相等。

把 hash 值直接当成唯一身份会引入碰撞错误。业务需要可靠去重时，应保留足够的原始身份或碰撞判断。

## 四、只需要前 K 名时为什么用堆

任务列表不断到来，只保留最大 K 个分数。每次完整排序全部历史任务会保留越来越多数据，也会做不必要工作。

使用容量 K 的最小堆：堆顶是当前保留结果中最小的分数。新值不大于堆顶时可以排除；大于堆顶时替换并恢复堆性质。

```text
已保留 K 个候选 → 与最小候选比较
  → 不可能进入前 K：忽略
  → 可以进入前 K：替换并调整堆
```

在相应实现下，总体约为 O(N log K) 工作量和 O(K) 保存空间。还需定义分数相同时的顺序，以及元素是否允许更新或撤回。

堆不是完整排序数组。除堆顶外，不能把内部数组位置当成最终名次。

## 五、任务依赖为什么需要图

任务 B 依赖 A，C 又依赖 A 和 B。把任务当作节点、依赖当作有向边，就能表达哪些任务可以先执行。

拓扑处理的一种方法是记录每个节点尚未满足的依赖数。先选择计数为零的节点，完成后减少后继计数；所有节点处理完则存在合法顺序。

如果还有节点却没有可处理入口，可能有环。例如 A 等 B、B 等 A。需要报告依赖问题，而不是无限等待。

算法中的“取出节点”与业务中的“任务成功完成”必须区分。实际调度器要在成功或明确处理失败之后，按规则释放后继任务；不能仅因为开始执行就当作依赖已经满足。

## 六、从算法性质到验证

除了几个固定结果，还可以检查关系：LowerBound 返回前面的值都小于目标，后面的值都不小于目标；拓扑顺序中的每条依赖都应先于依赖者；Top-K 不应遗漏任何严格更大的未选元素。

这些性质来自问题定义，通常比复刻实现步骤更能发现错误。随机数据或模糊测试可以扩大输入覆盖，但预期性质必须正确。

### 分层练习

- 基础：手算四个二分案例，每轮记录 lo、hi、mid。
- 机制：去掉排序前提，构造反例；改变一个边界更新，检查是否无限循环或漏元素。
- 工程：给任务依赖加入失败与重试，说明调度状态与图算法如何配合。
- 进阶：比较排序数组、map 和堆在不同查询组合下的成本，记录估算假设。
