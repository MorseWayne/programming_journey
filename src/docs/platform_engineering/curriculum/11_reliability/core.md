## 先把“慢”变成可以观察的问题

用户反馈任务领取变慢。服务 CPU 不高，接口平均延迟似乎正常，却有一部分人反复超时。这里可能同时存在统计口径、排队和依赖问题。

先修：[算法成本](../02_algorithms/core.md)、[系统资源](../03_systems/core.md)、[网络路径](../04_networks/core.md)、[C10 指标](../../10_observability.md)。本讲建立从症状、假设到验证的完整过程。

## 一、业务动作定义测量边界

先确定“完成”是请求已接收、奖励已提交，还是用户已经能查询结果。如果只是测 handler 开始到返回的时间，就会遗漏入口排队和客户端重试。

分母也必须明确。一个用户操作产生五次网络尝试，可以按操作成功率观察体验，也可以按尝试失败率观察链路，但不能混着比较。

记录时间窗、样本量、输入大小、版本、错误是否计入和重试关系，让不同测量具有可比性。

## 二、平均值与分位数各说明什么

平均值表达总耗时除以数量，容易被极端值影响；分位数表达排序位置，也会受样本量和计算方式影响。

假设副本 A 的 1,000 个请求都是 1ms，副本 B 的 10 个请求都是 1,000ms。直接平均两个 P99 得到 500.5ms，而合并样本按 nearest-rank 计算的 P99 为 1ms。

两种结果差异说明分位数不能直接平均。全局 P99 又可能掩盖小流量群体的糟糕体验，因此还需按有意义的业务范围观察。

直方图可以聚合分桶计数，但精度受桶边界影响。不能把估计分位数描述成毫无误差的原始结果。

## 三、排队把局部变慢放大到整个服务

教学模型有 20 个 worker，每个任务平均耗时 50ms，理想处理能力约 400 个/秒。若某依赖让耗时升到 200ms，能力降为约 100 个/秒。

入口仍以 300 个/秒到达，净积压约 200 个/秒。容量 1,000 的空队列在简化模型中约五秒填满。此时 CPU 可以不高，因为任务大量等待依赖。

扩大队列只推迟拒绝并增加等待。需要决定入口接收、超时、重试和业务恢复策略，不能只依据内存还没用满继续排队。

### Little 定律的使用条件

在相应稳定边界下，长期平均在途数等于到达率乘平均停留时间。它要求口径一致，使用均值，不能将不断增长的队列强行视为稳态，也不能把 P99 当均值代入。

## 四、从资源维度形成假设

可以按利用程度、饱和与错误检查每种资源：是否正在使用、是否出现等待、是否报告失败。CPU、内存、磁盘、网络和连接池都应有合适观察。

| 假设 | 支持证据 | 可能推翻它的观察 |
|---|---|---|
| CPU 计算不足 | 持续饱和、热点栈与排队 | CPU 空闲且时间主要在外部等待 |
| 连接池不足 | 获取连接耗时与等待数 | 等待很少，查询本身很慢 |
| 锁竞争 | 锁等待与热点临界区 | 大部分延迟发生在无锁路径 |
| 内存保留 | 存活对象与引用增长 | 业务 heap 稳定但其他区域增长 |

工具用于收集证据。一次 profile 抓到热点，不说明它就是用户失败的根因；还需要关联同一时段和负载。

## 五、压测模型可能掩盖过载

固定并发客户端常在完成后才发下一次请求。服务越慢，实际输入速率可能越低，让系统看起来不再积压。固定到达模型则尝试保持外部输入，但也要记录压测端是否真正发出了目标流量。

每次比较应保持数据、版本和负载条件相当。预热、短时峰值、长稳、缓存失效和依赖故障，是不同测试目标。

只选一次最好成绩会低估波动。报告应同时记录吞吐、延迟、错误与资源，以及未覆盖的持续时间和故障条件。

## 六、SLO 把运行目标接到业务

假设教学目标为一个窗口内 99.9% 有效操作满足承诺，10 万个操作对应最多 100 个不达标操作。这个目标由业务决定，不能因为别的服务用了相同数字就照搬。

错误预算帮助判断当前可靠性是否仍在允许范围内。若短期错误率为 2%，相对 0.1% 的允许比例，消耗速度约为 20 倍；推断完整窗口何时耗尽还需考虑实际流量分布和持续时间。

越权、数据损坏和重复资产通常有独立约束，不能因为成功率尚达标就忽略。

## 七、告警要连接行动

一个告警应说明用户受到什么影响、为什么需要现在处理、接下来首先看什么。短暂自动恢复且未影响业务的事件，未必适合直接打断值班人员。

可以从业务结果报警，再用队列、依赖、版本与资源信号定位。也要考虑低流量下样本不足、无数据与零错误不是同一状态。

## 八、事故处理先止损，再建立完整解释

处理事故时，需要明确负责人、沟通渠道、当前影响、正在采取的操作与恢复标准。恢复不是“进程起来了”，而是关键业务结果重新满足约定，积压和错误状态得到处理。

复盘记录触发条件、促成因素和失效防线。只归咎于某个人，无法说明为什么系统允许一个错误扩大成事故。

行动项应有验证方式。例如“增加告警”还需说明测什么、何时触发、谁响应，以及怎样确认不会造成新噪声。

### 分层练习

1. 对同一数据分别计算平均值、分位数和阈值成功率。
2. 用 worker 数与耗时估算能力变化，再列出模型忽略的因素。
3. 给一个低 CPU 高延迟问题写三个可反驳假设。
4. 写出业务 SLI 的分子分母及重试处理方式。
5. 完成一份虚构事故时间线，分别列出止损、恢复与长期改进。
