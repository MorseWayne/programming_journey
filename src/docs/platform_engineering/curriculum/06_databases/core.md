## 一个查询背后不只有 SQL 文本

任务平台需要查用户最近任务、记录领取、修改余额并在重启后恢复。相同 SQL 在不同数据量和并发条件下，可能经历完全不同的成本与等待。

先修：[B05 SQL](../../backend_basics/05_sql.md)、[算法卷讲义](../02_algorithms/core.md)、[系统卷讲义](../03_systems/core.md)。本讲先建立数据库各层的关系，再深入一个领取场景。

## 一、把不同事实放在合适的位置

用户资料、当前余额、一次领取事实和一次网络操作结果不是同一种身份。若把它们塞进同一行并反复覆盖，可能无法回答“哪项任务已经领取”和“这个旧请求当时返回什么”。

可以区分用户、任务、领取和回执。用户名字若重复保存在所有领取记录中，改名时就面临更新多处的困难；保留历史显示名又可能是有意记录当时事实。是否冗余要由时间含义决定。

**函数依赖**描述一组属性能否决定另一组属性，例如稳定用户 ID 决定当前用户资料。规范化帮助减少某些更新异常；历史快照与派生视图则需要明确为何保留冗余。

## 二、查询结果与访问代价分开分析

查询最近 50 个任务，需要明确用户范围、排序字段和并列规则。主键或复合索引的列顺序，影响数据库如何缩小扫描范围。

假设索引按 `(team_id, user_id, created_at, task_id)` 排列：先找到团队与用户，再沿时间与 ID 扫描，有机会减少无关记录。若只按 user_id 查询，是否仍有高效入口要看计划与数据分布。

### 页与缓冲池

磁盘上的数据通常按页组织，内存缓冲池保留最近或常用页。业务查询一行可能涉及多页，也可能完全命中已有缓存。

脏页表示内存中的内容已经改变而尚未按协议写回相应位置。缓冲池不只是“放一个 map”，还要管理替换、并发访问、页状态与持久化顺序。

数据库索引使用树形结构时，分支帮助定位页，叶子提供记录或定位信息。高扇出可以减少层数，但实际成本还取决于范围大小、回表和缓存。

## 三、从算子理解执行计划

SQL 描述想要什么，数据库选择如何执行。过滤、扫描、排序、聚合和连接是不同算子，会形成执行路径。

嵌套循环连接可能为外层每一行查找内层；有合适索引时很有效，缺乏合适入口时可能产生大量重复扫描。哈希连接会先为一侧组织查找结构，再匹配另一侧；需要考虑内存与数据分布。

优化器依据统计信息估计行数和成本。估计偏差可能导致它选择不适合实际数据的计划，例如某个团队特别热门，却被平均分布掩盖。

| 观察 | 继续追问 |
|---|---|
| 使用了索引 | 实际扫描了多少范围，是否仍大量回表 |
| 估计返回很少 | 实际行数是否接近，统计信息是否反映倾斜 |
| 有排序 | 索引顺序能否满足，是否需要外部存储 |
| 执行很慢 | 时间在计算、I/O、锁还是连接池等待 |

所以“EXPLAIN 显示 key 不为空”不能结束性能分析。

## 四、事务为什么需要同时讨论多种异常

原子性保护一组操作的共同提交，隔离性规定并发观察与冲突方式。把多个 SQL 放入事务，并不能替你定义所有跨行规则。

以两个执行者各增加 10 为例，先读再在应用中计算新余额，可能互相覆盖。让数据库在受保护的更新里计算增量，或使用适当锁定，才能维护这条规则。

再看“至少一个任务处理节点保持启用”的跨行约束：A 看到 B 启用，于是关闭 A；B 看到 A 启用，于是关闭 B。两边各改不同一行，最终却可能全部关闭。这类写偏斜需要保护共同约束，而非只保护单行。

可能的方向包括协调同一条守卫记录、锁定必要集合或采用满足要求的更强隔离；具体方式要结合数据库实现验证。

## 五、MVCC 让读者看到哪个版本

多版本机制保留数据的不同版本，让某些读取按快照判断可见性。快照不是“永远最新”，而是一个明确观察规则。

教学时间线：A 开始一次快照读取，看到余额 100；B 更新并提交 110；A 再读时是否仍是 100，取决于隔离级别与读取类型。

普通一致性读、锁定读和更新所依赖的当前状态，不能都用同一种直觉解释。MySQL InnoDB 中相关行为要结合事务隔离与具体 SQL 核对，见 [锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

长事务还可能使旧版本长期需要保留，影响回收与存储成本。即使它很少占 CPU，也可能给系统带来压力。

## 六、日志先行怎样帮助崩溃恢复

业务更新可能先改变缓冲页。若页面只写回了一部分就崩溃，数据库需要持久日志判断哪些变化应该重做、哪些操作未提交，以及怎样恢复一致状态。

WAL 的核心是相应日志先满足持久协议，再允许依赖它的数据变化按规则落盘。redo、undo、提交记录和检查点各自帮助解决不同问题，具体实现不应仅从名字类比。

```text
事务操作 → 日志与页变化 → 提交确认
                          ↓ 崩溃后
               依据日志与检查点恢复状态
```

实际确认是否等待日志同步、是否包含副本，以及设备故障范围，取决于配置与系统设计。备份还需要恢复演练；副本也不能自动代替防止误删传播的备份。

## 七、Go 连接池也是排队系统

database/sql 的 DB 对象管理连接使用，通常不是一条固定连接。连接数量有限时，请求可能先等待可用连接，再执行查询。

若把远程 HTTP 调用放进一个持有数据库事务的长过程，会占用连接和锁，让后续请求排队。SQL 执行本身很快，也可能因为连接等待让用户觉得很慢。

需要明确事务边界、Rows 关闭、context、错误分类和提交结果未知。把 pool 大小不断调大，可能只是把更多竞争推给数据库。

## 八、回到任务领取

建立领域唯一性 `(team,user,task,reward_kind)`，再用 request_id 识别同一次网络操作。两种身份保护不同规则。

在同一事务中检查或建立领取事实，更新积分，记录结果和待通知事件。若资产由另一个服务负责，本地事务无法直接包住远端效果，需要跨服务恢复协议。

### 分层练习

1. 画出任务查询经过的索引、页、缓冲与结果路径。
2. 比较两种索引在查询、排序和写入维护上的成本。
3. 为丢失更新和写偏斜分别构造时间线，说明保护范围。
4. 在提交前后安排崩溃，判断恢复所需记录。
5. 区分连接池等待、锁等待和 SQL 计算，并选择对应证据。
