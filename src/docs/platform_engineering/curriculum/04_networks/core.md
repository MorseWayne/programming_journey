## 同一个“请求失败”可能发生在哪里

客户端查询任务，可能在名称解析、建立连接、握手、发送、服务端排队、业务处理或读取响应时失败。只知道一次调用抛出错误，无法决定应该重试、换节点还是修改请求。

先修：[B02 网络基础](../../backend_basics/02_network.md)、[B03 HTTP](../../backend_basics/03_http.md)、[A10 字节与时间](../../beginner/10_files_json.md)。本讲按请求路径逐层推导。

## 一、先定义应用想交换什么

应用协议规定任务查询的路径、方法、输入、状态和正文。客户端知道 GET /tasks 返回任务集合，才能解释收到的字节。

DNS 帮助从名称获得地址，但名称解析完成并不代表地址上存在可用服务。连接建立成功也只说明通信条件的一部分，不说明任务已经查到。

```text
URL 与名称 → 地址 → 连接 → 安全握手 → HTTP 请求
  → 服务端接入与排队 → 数据查询 → HTTP 响应 → 解析结果
```

使用连接池时，某些步骤可能被复用。比较请求耗时时，应说明是新连接还是已有连接，不能把两种样本不加区分地当作同一过程。

## 二、字节流为何需要消息边界

TCP 传送有序字节流。发送方一次写入十个字节，接收方可能分几次读取；多条业务消息也可能在同一段可读数据中连续出现。

协议必须定义怎样知道一条消息结束，例如长度头、分隔规则或 HTTP 自身的消息组织。不能把一次 Read 的返回当作一条消息。

长度头还需要规定字节顺序与最大值。解析出长度以后再盲目分配，可能让一个长度声明消耗过量内存。合法长度也可能迟迟传不完整，仍需等待预算。

流控和重传可以帮助传输推进，不会自动替应用校验字段或业务权限。

## 三、可靠传输怎样面对丢失

发送端需要知道哪些数据已经被对方确认；未确认部分可能因丢包或确认丢失而重传。序列信息帮助接收方处理重复与顺序。

确认可能在网络中丢失，因此发送端重传不意味着接收端先前完全没有收到。这个思想与业务重试相似，但保护边界不同：传输层确认字节，业务层确认具体操作效果。

客户端收到 TCP 层进展，不能直接推出数据库已经 COMMIT；客户端没有收到 HTTP 响应，也不能推出数据库一定没有执行。

### 窗口有两个不同压力来源

接收方处理慢，会限制自己愿意接收的数据量；网络拥塞则要求发送方控制注入网络的速度。两者都可能限制发送，但原因不同。

仅增加服务端应用缓冲，未必解决网络拥塞；仅增加连接数，也可能使下游数据库和服务端队列更拥挤。

## 四、用单位推导带宽与等待

带宽描述每秒能运送多少数据，RTT 描述一次往返的时间。想让链路持续有数据在途，需要考虑带宽时延积。

教学例：100 Mbit/s 的速率与 40ms RTT，对应约 4 Mbit，也就是 0.5MB 的在途数据量。这里使用十进制单位，且只是简化模型，不是某个 socket 缓冲的通用推荐值。

这说明“每次只等一个小块确认后再发下一块”，即使链路带宽高，也可能利用不足。流水线能同时保留多个在途数据，但还需控制丢失、缓冲和公平性。

单位错误会导致数量级错误：bit 与 byte 相差八倍，毫秒与秒相差一千倍。容量计算应把单位写在每个数旁边。

## 五、连接的建立与结束也是协议

TCP 建立连接时需要双方交换状态，结束时又要分别处理不再发送、剩余数据与确认。一个方向停止发送，不必然意味着另一个方向已经没有数据。

大量短连接会重复支付建立和结束成本，连接复用能减少部分开销，但会增加池管理、闲置过期和故障连接识别问题。

TIME_WAIT 等状态与连接生命周期有关，不能只看到数量多就立刻修改系统参数。应先看连接创建速率、复用方式和实际资源影响。

## 六、TLS 保护的边界

TLS 为通信提供机密性与完整性，并通过证书等机制参与对端身份验证。客户端仍需按协议检查信任链、名称和有效条件。

应用授权是另一层：连接到了真实服务，也不代表当前用户有权查询另一个团队的数据。加密只能保护传输，不能修正服务端选择了错误租户的查询。

证书过期、名称不符、信任配置不同与 HTTP 业务拒绝，应作为不同错误报告。把它们都转换成“稍后再试”，会掩盖需要配置修正的问题。

## 七、超时预算怎样贯穿调用链

一个用户请求总预算 800ms，进入服务前已用掉 200ms，服务还要留出返回和整理结果的时间。下游不应每跳重新获得完整的 800ms。

```text
总预算 = 已消耗 + 剩余依赖预算 + 返回余量
```

并行依赖的时间不能简单全部相加，关键路径才决定最终等待。失败重试又会占用剩余预算，因此必须同时约束次数和总时间。

取消通常是协作信号。服务端可能已经提交了业务状态，客户端停止等待并不会撤销它。对于写操作，需要稳定身份与结果查询，见 C08 的故障时间线。

## 八、HTTP 版本和 RPC 怎样放回这个模型

HTTP/2 在连接上组织多个流，能够减少某些应用层串行等待，但底层传输与流控仍有自己的限制。HTTP/3 使用不同传输机制，需要根据实际环境分析，不能仅凭版本数字判断所有请求更快。

gRPC 在协议之上组织方法、消息模式、状态与流。字段兼容、截止时间和业务幂等仍需要应用约定。选择框架不会消除网络中的部分失败。

### 分层练习

1. 为一次新连接查询划分阶段，再和复用连接的查询比较。
2. 让发送方写两条消息，接收方每次只读一个字节，推演解码状态。
3. 为名称解析失败、连接拒绝、TLS 错误、HTTP 403 和业务超时各提出一个最先检查的证据。
4. 设计三跳调用的预算，加入一次重试后检查是否超过用户期限。
