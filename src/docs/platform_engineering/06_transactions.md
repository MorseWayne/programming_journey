## 需求场景：邮件附件被重复领取

玩家点击领取附件后没有收到响应，又点了一次。两个请求都可能到达服务端；同时，程序还可能在“余额增加”之后、“写领取记录”之前崩溃。

业务要求是同一份奖励只产生一次效果，成功后可查询结果，失败时不留下半份状态。本课将分别解决两件事：用事务保护一组数据变化，用稳定身份识别同一操作。

## 基础理论：事务保护什么

事务把一组数据库操作放进提交单位。它的经典性质 ACID 可以放到发奖业务中理解：

| 性质 | 在本例中的含义 | 容易误解的地方 |
|---|---|---|
| 原子性 | 余额、回执和待发事件一起提交，或一起回滚 | 不会自动覆盖任意 HTTP 调用 |
| 一致性 | 合法转换应维持余额、身份和结果等规则 | 数据库不会替你定义所有业务规则 |
| 隔离性 | 并发事务按一定规则观察和影响彼此 | 不同级别不提供完全相同的保证 |
| 持久性 | 按配置与故障范围保留已确认提交 | 不等于无需备份或永不丢数据 |

事务的一致性与分布式系统中“不同副本看见什么”的一致性不是同一个讨论层面。前者强调约束维持，后者还涉及可见性、顺序和传播。

### BEGIN、COMMIT 与 ROLLBACK

开始事务后，执行若干查询与更新；成功时 COMMIT，遇到需要放弃的错误时 ROLLBACK。应用应确认提交结果后再承诺成功。

单条语句在自动提交模式下可以是自己的事务。多条语句连续执行却没有明确事务边界，不代表它们会一起失败或成功。课程存储过程显式开启事务，并在 SQL 异常处理器中回滚后重新报告错误。

数据库已经提交而响应丢失时，调用者仍可能不知道结果。事务保护了数据，不能消除网络上的结果未知，这正是幂等需要参与的原因。

## 并发基础：从丢失更新到隔离

两个请求都先 SELECT 余额 100，然后各在应用中算出 110 并 UPDATE 为 110，可能丢一次更新。解决方式应保护完整业务判断，而不仅是每条 SQL 的语法正确。

对于简单增量，`UPDATE wallets SET balance=balance+10 ...` 让数据库在更新时基于受保护的当前行计算。若还要根据余额判断资格，再改多行，需要更完整的锁定或条件更新设计。

**MVCC**用数据版本支持某些一致性读取，减少读取与写入之间的直接阻塞。**锁定读取**如 `SELECT ... FOR UPDATE` 则参与协调后续修改。普通快照读与锁定读看到的数据、持锁行为可能不同。

### 隔离级别要配合访问方式理解

较弱隔离可能允许重复读取看到变化；快照提供某种稳定视图，但不自动保护由多行共同表达的所有条件。两笔事务各检查“还有另一个人值班”，再分别取消自己的值班，可能共同破坏“至少一人值班”的规则。

这种业务约束需要考虑所有相关行的协调或更强隔离。不能仅说“用了事务，所以不会冲突”。本课固定 InnoDB 和课程 SQL 路径，重点验证具体行为；[事务模型](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-model.html)与[锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)用于核对实现条件。

## 机制推导：幂等身份与结果

这里约定同一 `(namespace, request_id)`、相同参数的重试只产生一次业务效果，并返回第一次结果。同 ID 改了玩家或积分，应返回冲突。

| 收到的操作 | 处理方式 |
|---|---|
| 新 ID | 执行并记录首次结果 |
| 同 ID、同参数 | 返回已保存的结果 |
| 同 ID、不同参数 | 拒绝冲突 |
| 超出记录保留期 | 按事先约定处理，不能假装历史仍可识别 |

请求 ID 应在重试前确定并持续复用。如果每次点击都生成新 ID，系统就会认为是不同命令。对“同一封邮件只能领一次”的领域规则，还应约束 `(ns, uid, mail_id, attachment)`，不能只信任客户端生成的 ID。

幂等讨论的是可观察效果。重复请求可以产生新的访问日志，但不能重复发放同一笔奖励。必须说清哪些效果被保护。

## 为什么“先查是否存在，再写入”不够

两个事务都可能查到不存在，然后同时尝试创建。正确性应由唯一约束和事务协调保障，而不是依赖检查与写入之间足够快。

课程的顺序是：

```text
开启事务
  → 插入或锁定请求回执
  → 核对玩家与金额是否一致
  → 已完成则返回历史结果
  → 更新余额
  → 写待发送事件
  → 保存首次结果
提交
```

唯一主键使同一请求并发进入时发生数据库协调。对回执的锁定读取让后续检查有相应保护；余额更新也通过数据库写锁协调。同一个玩家的不同奖励仍需保护余额更新。

outbox 是事务里保存的待发送事件。这里先学习“业务成功时一定有待发记录”，第 8 课继续处理记录怎样送达外部。

## 实验一：重复、冲突、并发与回滚

完成环境初始化后运行：

```bash
cd labs/platform_path
bash sql/check.sh
```

脚本每次用独立虚构租户，预期主动制造的冲突会显示错误，最终输出 PASS。正常序列中，r1 增加 10；重复 r1 保持 10；两个并发 r2 请求各要求加 7，但该操作只生效一次，余额为 17，待发事件两条。

最后预置冲突 outbox 行，让新事务在已经更新余额后插入事件失败。应回滚余额和回执：余额仍为 17，失败请求的回执不存在。故障注入用于证明原子边界，不代表正常业务数据。

再运行内存模型对照：

```bash
go test -race -run '^Test(ConcurrentDuplicate|ConflictAndTenant|ReceiptIsOriginalResult)$' -v
```

它们验证类似业务语义，但 Mutex 只保护当前进程，SQL 的共享约束则由数据库负责。两种测试的保证范围不同。

## 实验二：亲眼观察锁等待

初始化 schema 会确保 game-a/u1 已存在。打开两个连接到 `journey_lab` 的 MySQL 客户端：

```sql
-- A：保持事务打开。
START TRANSACTION;
SELECT balance FROM wallets WHERE ns='game-a' AND uid='u1' FOR UPDATE;
```

```sql
-- B：尝试修改 A 锁住的同一行。
START TRANSACTION;
UPDATE wallets SET balance=balance+1 WHERE ns='game-a' AND uid='u1';
```

B 通常等待。在 A 执行 ROLLBACK 后，B 可继续；最后在 B 也执行 ROLLBACK，保留原值。若等待超时，记录实际错误和持续时间。

单向等待与死锁不同。死锁需要形成循环依赖，例如两笔事务以相反顺序锁两个账户。数据库可能选择一个事务回滚；应用应按有界策略重试整个业务事务，并复用操作身份。

## 业务迁移：附件领取的提交边界

假设附件记录与玩家资产在同一事务数据库中，可以把“验证未领取、更新资产、记录领取、保存通知”放进同一事务。若资产由另一服务管理，则本地事务无法直接包住对方状态，需要第 8 课的幂等调用、恢复和明确中间状态。

独立练习：同一个 ID 改成给 u2 发奖，应拒绝；两个不同 ID 给同一玩家发奖，应累加；一笔新请求使累计余额溢出，应失败并完整回滚。

保存时间需要覆盖客户端允许重试的窗口和消息重放窗口。删除回执后，同一历史请求可能被当作新请求。可以限制重试有效期、保留领域唯一性记录，或明确长期操作查询机制。

保存“处理中”记录还涉及崩溃后如何恢复。在本课程 SQL 过程里 pending 与 complete 位于同一事务，新操作失败时 pending 也会回滚；不要把这点套用到先单独提交 pending 的异步工作流。
