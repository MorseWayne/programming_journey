## 本课问题与前置

客户端没收到发奖结果，又点了一次。服务端怎样判断是同一奖励重试，还是一笔新奖励？前置：第 2、5 课。建议用时 4–5 小时。

目标：定义幂等身份，把余额、回执和待发送事件纳入同一提交边界，并验证并发重复。

## 先定义重复的含义

**幂等**在本课表示：同一身份与参数重复执行，业务效果只产生一次，并能返回首次结果。Arena 的身份是 `(namespace,request_id)`；参数包括玩家和积分。

同 ID、同参数返回原回执；同 ID、不同参数返回冲突。若每次重试生成新 ID，服务端会认为它们是新操作。去重记录保留多久、业务允许多久后重试，也必须协商。

## 为什么需要事务

**事务**把多条数据库操作放进一个提交单位。成功提交后才对外承诺成功；中途失败回滚。它不能直接覆盖任意远程 HTTP 请求。

Arena 一次事务包含：

1. 插入或锁定回执行。
2. 核对重复身份的参数。
3. 更新余额。
4. 写入 outbox 待发送事件。
5. 保存结果并提交。

在 `sql/procedures.sql` 中，唯一主键使相同请求的并发插入发生协调；`FOR UPDATE` 用锁定读取核对回执。新请求更新余额时也持有相应写锁。同一玩家的不同奖励通过数据库更新串行化。

**隔离级别**规定并发事务能看到哪些变化，不等于自动修正任何业务逻辑。MVCC 通过版本帮助读取；锁定读取又有自己的规则。先验证当前访问方式，再研究更复杂隔离级别。[MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)是本课的核对资料。

## 实验 A：重复、冲突与租户

```bash
cd labs/platform_path
bash sql/check.sh
```

脚本为每次运行创建不同的虚构租户，不清理已有练习数据。预期出现参数冲突和 outbox 唯一键冲突错误，这是主动测试；脚本最终输出 PASS。

首次 r1 增加 10，重试仍为 10；两个并发客户端提交 r2，各增加 7 的请求最终只生效一次，余额为 17，outbox 两行；另一个租户独立记账。

最后脚本故意在该次虚构租户里预置一条冲突 outbox，再尝试发奖。余额更新后遇到唯一键错误，事务应回滚：余额仍是 17，失败请求的回执不存在。预置冲突行仅供故障实验，不代表合法业务事件。

脚本会重新安装实验存储过程，范围只限 `journey_lab`。不要在生产数据库执行。

## 实验 B：亲眼观察锁等待

打开两个 MySQL 客户端，均连接实验库：

```sql
-- 会话 A
START TRANSACTION;
SELECT balance FROM wallets WHERE ns='game-a' AND uid='u1' FOR UPDATE;
-- 保持事务打开，暂时不要提交。
```

```sql
-- 会话 B
START TRANSACTION;
UPDATE wallets SET balance=balance+1 WHERE ns='game-a' AND uid='u1';
-- 通常在这里等待 A 释放锁。
```

在 A 中执行 `ROLLBACK`，B 应继续；最后在 B 中执行 `ROLLBACK` 保留原数据。锁等待也可能达到超时，记录真实现象。死锁是事务依赖形成环，与单向等待不同；捕获死锁后通常需要按明确策略重试整个事务。

<details>
<summary>为什么不先 SELECT 看是否存在，再 INSERT？</summary>

两个客户端可能都看到“不存在”。正确性必须依靠数据库约束和事务协调，不能依靠检查发生得足够快。捕获重复键也不意味着直接返回成功，还要核对参数和保存结果。

</details>

## 独立练习与反馈

练习：同一个 r1 改成给 u2 发奖，应该得到什么？再模拟 outbox 插入失败，余额应该怎样？

参考：前者是参数冲突，不应把 u1 的回执当 u2 的成功。后者应回滚余额和回执；如果只有余额成功，就破坏了事务边界。可以在独立副本中制造唯一键冲突验证回滚。
