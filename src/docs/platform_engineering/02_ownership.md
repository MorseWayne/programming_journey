前置：[请求与契约](./01_contracts.md)、切片与结构体。建议用时 3 小时。目标：识别别名、确定修改权限、给完整状态转换选择同步边界。

## 值被复制，底层数据仍可能共享

Go 赋值复制值。整数和只包含值字段的结构体复制后各自独立。切片值包含对底层数组的引用，两个切片可能看到同一批元素。

```go
events := []string{"u1", "u2"}
view := events
view[0] = "u9"
// events[0] 也是 "u9"
```

`view` 是原数据的一个**别名**。如果服务希望调用者只能查看，就不应直接交出可变内部存储。**所有权**是设计约定：谁能修改、谁负责保护、数据能活多久；Go 类型系统不会自动强制全部约定。

Arena 的 `Pending()` 创建新切片，逐个复制事件。事件只包含整数、布尔和字符串，当前模型下修改返回字段不会影响内部事件。若以后增加 `[]byte` 或 map 字段，只复制外层结构体就不够。

## 同步需要保护完整动作

**goroutine**是由 Go 运行时调度的执行单元。**临界区**是一段需要相互排斥执行的操作。

余额增加包含“读旧值—计算新值—写回”。即使每个 map 操作分别加锁，两次增加仍可能都读到 0，再各写入 10，最终少发一次。

| 顺序 | A | B |
|---|---|---|
| 1 | 读到 0 | |
| 2 | | 读到 0 |
| 3 | 写入 10 | |
| 4 | | 写入 10 |

Arena 的 `Grant` 用同一个 `sync.Mutex` 保护检查回执、计算余额、写余额、写回执、创建事件的整个过程。`Lock` 获取锁，`Unlock` 释放锁；`defer` 确保函数返回前释放。同步与可见性的语言保证见 [Go 内存模型](https://go.dev/ref/mem)。

粗粒度锁便于证明正确性。是否拆锁由性能证据决定；多锁还需处理获取顺序和跨对象操作。

## 实验：分别检查封装与并发

```bash
cd labs/platform_path
go test -run '^TestOwnership$' -v
go test -race -run '^TestConcurrentDuplicate$' -count=10
```

第一条验证返回切片不能修改内部状态。第二条并发提交同一请求 100 次，预期余额为 10、事件只有一条。重复请求的业务语义将在第 6 课解释。

`-race` 检查本次运行中观察到的数据竞争；通过不等于业务逻辑正确，也不等于覆盖了所有调度。
