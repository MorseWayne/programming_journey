## 需求场景：读取接口为什么改坏了内部数据

邮件服务返回待通知玩家列表。调用者为了排序或做标记，修改了返回值，服务内部的列表也发生变化。另一个场景里，两次奖励各加 10，最终却只增加 10。

前一个问题关乎数据共享，后一个关乎执行顺序。本课先理解值与别名，再推导同步范围。完成后应能判断“谁能修改这份数据”，并区分数据竞争与业务竞争。

## 基础理论：赋值究竟复制什么

### 值、地址和别名

Go 赋值复制值，但值里可以包含访问其他数据的引用。整数副本相互独立；指针副本保存相同地址，因此能访问同一对象。

```go
x := 10
y := x
y = 20 // x 仍为 10

p := &x
q := p
*q = 30 // x 变为 30
```

`p` 和 `q` 是同一对象的两条访问路径，可称为别名。理解共享时应该画“变量指向哪里”，而不是只数变量名。

### 切片为什么容易共享

切片描述底层数组中的一段元素。赋值会复制切片描述，底层数组可能仍然是同一份。

```go
events := []string{"u1", "u2"}
view := events
view[0] = "u9"
// events 变为 [u9 u2]
```

`len` 表示当前可访问的元素数量，`cap` 表示从切片起点到可扩展范围的容量。`append` 容量足够时可能继续使用同一数组，容量不足时会分配新数组；不能依赖某次 append 恰好扩容来形成隔离。

字符串不可通过索引直接修改，字符串值共享底层表示通常不造成这种可变别名问题。但 `[]byte` 是可变切片，语义不同。

### map 与嵌套对象

map 赋值后，两边访问的是同一映射。结构体值复制也不会自动递归复制其中的 map、切片或指针字段。

```go
type Message struct {
    Text string
    Tags map[string]string
}
a := Message{Text: "hello", Tags: map[string]string{"room": "1"}}
b := a
b.Tags["room"] = "2" // a.Tags 也变了
```

所以“返回一个结构体副本”只有在字段的共享行为符合约定时才足够。复制到哪一层，应由可变性和修改权限决定。

## 机制推导：谁拥有修改权

**所有权**在本课程中是一组设计约定：谁可修改、哪些读取允许并发、何时交接、生命周期由谁负责。Go 不会自动替你证明这些约定。

常用策略有三种：

| 策略 | 如何保持可理解性 | 代价与限制 |
|---|---|---|
| 返回副本 | 调用者只修改自己的数据 | 复制时间与内存；嵌套引用要检查 |
| 发布不可变快照 | 发布后只读取，新版本另建对象 | 发布需要同步；子对象也要遵守不可变约定 |
| 共享并同步 | 所有访问遵守相同的锁或协议 | 锁竞争、阻塞及遗漏访问路径的风险 |

配置热更新适合用新快照替换旧快照；频繁变化的玩家状态可能更适合由固定执行者管理。选择前先确定访问模式。

发送指针或切片到 channel 也不会自动深拷贝。若发送后生产者继续修改同一底层数据，消费者仍可能受到影响。

## 从顺序正确到并发错误

余额增加包含读取、计算、写回。两个执行者可以按以下顺序交错：

| 步骤 | A | B | 当前余额 |
|---|---|---|---:|
| 1 | 读取 0 | | 0 |
| 2 | | 读取 0 | 0 |
| 3 | 写回 0+10 | | 10 |
| 4 | | 写回 0+10 | 10 |

两笔独立奖励总共应该增加 20，却丢了一次更新。即使每个读取和写入分别用锁保护，这个交错仍然可能出现。

**数据竞争**指多个执行者对同一内存位置存在未按同步规则协调的访问，且至少一个是写。**业务竞争**则是交错破坏了业务规则；它可能发生在每次内存访问都有同步的程序中。

基础命令的最后一行用顺序代码重放上述交错，所以它没有真正的数据竞争，却能展示业务结果错误。不能用 race 检测通过替代业务断言。

## 基础理论：互斥、可见性与临界区

`sync.Mutex` 让遵循同一把锁的临界区互斥执行，还通过语言内存模型建立可见性关系。某次解锁与之后成功加锁之间的同步，允许后者观察前者在临界区内完成的写入。具体保证可核对 [Go 内存模型](https://go.dev/ref/mem)。

本例应把完整的“读旧值 → 检查上限 → 更新”放在同一临界区。只保护最终赋值，会使检查依据过时。

```go
// 设计片段：所有 Balance/Credit 访问都要遵守同一把锁。
type SafeAccount struct {
    mu      sync.Mutex
    balance int64
}

func (a *SafeAccount) Credit(amount int64) error {
    a.mu.Lock()
    defer a.mu.Unlock()
    if amount <= 0 || amount > math.MaxInt64-a.balance {
        return ErrAmount
    }
    a.balance += amount
    return nil
}
```

这是学习者接下来可以实现的并发版本，不要给顺序 Account 的实例直接并发调用。含有已使用 Mutex 的对象也不应随意按值复制，因为不同锁可能保护到同一份引用数据。

### 保护范围如何决定

保护范围取决于需要一起维持的不变量。只更新一个余额，就保护其检查与变化；若还要求创建回执和事件，则相关状态也要纳入同一个逻辑动作。第 6 课再把这一思想迁移到事务。

持锁期间调用慢网络请求，会让其他操作等待。不能简单把网络调用移出锁后就宣称安全：需要重新判断状态是否变化，并设计版本检查或拆分状态机。

<details>
<summary>工程深化：粗锁、细锁与死锁</summary>

粗锁容易建立正确性，但会串行化不相关对象。按账户拆锁可以扩大并行度；一次操作若涉及两个账户，还要定义锁的获取顺序。A 持有甲等待乙、B 持有乙等待甲，会形成循环等待。

因此，锁越细不一定越好。先证明当前瓶颈来自锁竞争，再考虑分片、固定顺序或让一个执行者拥有状态。锁只在当前进程内生效，多个服务副本不会共享这把 Mutex。

</details>
