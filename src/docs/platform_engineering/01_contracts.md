## 本课问题与前置

玩家点击一次“领取奖励”，系统给余额增加 10。要把这句话变成可维护的程序，必须先定义：谁领取、属于哪个游戏、奖励是多少、失败时发生什么。本课只分析单次、顺序调用。

前置：Go 变量、函数、结构体、`if` 和 `error`。不熟悉时先读[Go 基础](../language/go/basic/README.md)。建议用时 2–3 小时。

完成后应能写出输入约束、状态变化和失败承诺，并用测试验证它们。

## 从业务句子到数据

**状态**是系统某时刻保存的信息，例如玩家余额。**请求**表示希望系统做什么。**契约**是调用双方约定的输入、结果和错误。

教学项目 Arena 使用四个字段：

| 字段 | 含义 | 例子 |
|---|---|---|
| namespace | 游戏或租户的逻辑范围 | game-a |
| user | 该范围内的玩家 | u1 |
| request_id | 同一个业务操作的身份 | reward-001 |
| amount | 增加的整数积分 | 10 |

请求身份与玩家身份不同：一个玩家可以有许多奖励请求。本课保留请求身份，第 6 课再解释重复提交。

```go
// 调用片段：放在 main 内，需导入 fmt 和课程模块。
r := platformpath.RewardRequest{
    Namespace: "game-a", User: "u1",
    RequestID: "reward-001", Amount: 10,
}
fmt.Println(r.Validate()) // <nil>，表示验证通过
```

完整可运行的调用见 `labs/platform_path/models_test.go` 中的 `TestContract`。`Validate` 是结构体的方法，只判断输入是否合法，不修改余额。

## 用不变量约束实现

**不变量**指操作前后必须成立的条件。本课约定：身份字段非空；积分增量为正整数；非法请求不改变状态；同一租户中不同玩家独立记账。

整数避免浮点金额比较的问题，但整数也有上限。代码在相加前检查 `math.MaxInt64-old`，避免溢出后得到错误余额。这是输入合法与计算安全之间的区别。

成功结果说明本次操作产生的余额和事件编号。失败通过 `error` 返回，调用者必须处理。不能把空结构体当作成功凭证。

```text
验证请求 → 读取旧状态 → 检查约束 → 更新状态 → 返回结果
```

先认识这条顺序。源码里的锁、事件和回执会在后续逐项解释，首次阅读先看 `RewardRequest.Validate` 与 `TestContract`。

## 实验：非法请求会不会改变余额

```bash
cd labs/platform_path
go test -run '^TestContract$' -v
```

预期测试通过。它验证缺失字段、零值、负数和正常请求；通过只说明列出的输入满足断言。

独立练习：增加三个案例——只有空格的 namespace、空玩家 ID、极大增量。先写预期，再运行。检查失败后余额和事件数是否保持原样。

<details>
<summary>提示：怎样验证“没有改变”</summary>

调用前记录 `Balance` 和 `len(Pending())`，调用后比较。验证错误类型用 `errors.Is(err, platformpath.ErrInvalid)`。极大增量第一次可能合法；先发一笔小奖励，再测试累计余额溢出的请求。

</details>

<details>
<summary>参考解释</summary>

一次增量小于整数上限，不代表它与余额相加仍合法。只有比较增量与剩余可用范围才能保护这一步。当前余额初始为零且只增不减；若以后允许扣减，必须重新定义下界、错误与并发行为。

</details>

## 检查掌握情况

1. namespace 为什么要进入数据身份？
2. 返回错误与返回正常空结果有什么区别？
3. “没有报错”和“业务结果正确”有什么区别？

迁移题：把发奖励换成创建匹配报名，写三个必须保持的条件。参考方向：重复报名、跨游戏混队、报名成功后的可观察状态。暂不设计分布式实现。

达标证据：新增失败测试、不变量说明、失败时状态未变化的断言。下一课：[数据所有权](./02_ownership.md)。

阅读：[Go 错误处理](https://go.dev/blog/error-handling-and-go)。业务模型与练习为原创。
