## 需求场景：运营说“完成任务就发奖”

这句话还有很多未确定之处：谁判断任务完成？奖励发到哪个账户？负数能否表示撤销？操作失败后余额是否变化？本课先把需求缩小为一个可以验证的承诺：**单个账户顺序接收已获业务授权的积分增量，合法时增加，非法时保持原状态。**

资格判断是上游业务的责任；账户负责数值和状态规则。这样分工让每一层都能准确说明自己检查了什么。后续扩展重试、数据库和多租户时，再增加相应边界。

本课目标：从自然语言写出输入、前置条件、状态转换、输出与失败承诺，并用测试验证边界。核心练习只阅读 `foundations/account.go`，暂不需要理解完整 Ledger。

## 基础理论：把需求写成可以判断的规则

### 1. 功能、质量和约束

**功能需求**描述系统做什么，例如给账户增加积分。**质量要求**描述做得怎样，例如在给定负载下 99% 请求在某个期限内完成。**约束**限制可以采用的方案，例如只能使用已有数据库、旧调用方一个月内无法升级。

| 自然语言 | 需要补充的判断依据 |
|---|---|
| 发奖要正确 | 输入合法、结果符合规则、失败不留下半成品 |
| 接口要快 | 哪条路径、多少流量、什么分位数、是否包含错误 |
| 数据不能丢 | 哪个确认点之后、容忍什么故障、怎样验证恢复 |
| 不能重复领 | 同一业务奖励怎样识别、重试和新领取怎样区分 |

这些问题不必第一天全部实现，但必须明确当前版本承诺哪部分。课程先处理第一行，其余分别在后续阶段落实。

### 2. 状态转换

设余额为 B，输入增量为 A。成功操作要求：

```text
前置条件：B >= 0，A > 0，A <= MaxInt64 - B
状态转换：B' = B + A
后置条件：新余额为 B'，且 B' >= B
失败承诺：任何检查不通过时，B' = B
```

**前置条件**是在执行前必须成立的条件；**后置条件**是成功执行后应成立的条件；**不变量**是所有合法状态中都应成立的规则，例如余额始终非负。

不是所有规则都只看最终结果。例如“失败时不能创建待发送通知”要求多个状态一起保持一致。现在只有一个余额，之后再扩展多个状态。

### 3. 输入是否合法与调用者是否有资格

`amount > 0` 说明数值在允许范围内，不能证明某个玩家真的完成任务。身份认证说明调用者是谁，授权说明它有权做什么，业务资格说明这次行为是否满足业务条件。

把它们都写成一个 `Validate()` 名称，容易误以为所有检查都完成了。本课的 `Credit` 只保护账户数值。第 12 课处理可信身份，第 18 课补充奖励来源与领取资格。

## 机制推导：为什么先验证，再改变状态

考虑一个错误实现：

```go
// 错误示意：先修改，再检查。
a.balance += amount
if amount <= 0 {
    return ErrAmount
}
```

返回了错误，但状态已经改变。调用者可能以为失败请求没有效果，随后重试或补偿，造成新的错误。

正确的顺序是：先读出需要验证的状态，完成全部必要检查，再提交状态变化。顺序模型可直接写成：

```go
func (a *Account) Credit(amount int64) error {
    if amount <= 0 || amount > math.MaxInt64-a.balance {
        return ErrAmount
    }
    a.balance += amount
    return nil
}
```

这段来自基础实验的完整实现。`math.MaxInt64-a.balance` 表示剩余可增加范围，因为余额已经保证非负，减法自身不会越界。若先计算 `balance+amount` 再比较，计算本身可能已经溢出。

`nil` 表示本方法没有报告错误。它的成功范围是当前账户内存已更新，尚未承诺持久保存。

### 方法接收者也影响状态

`(a *Account)` 接收账户地址，方法能改变调用者的账户。如果改成 `(a Account)`，方法操作的是值副本；本模型字段只有整数，修改不会写回原对象。

这并不意味着所有值接收者都不会影响外部数据。结构体中如果含有切片或 map，副本仍可能引用共享数据。下一课专门拆解这一点。

## 实验：用输入类别覆盖规则

|---:|---:|---|---:|
| 0 | 10 | 无 | 10 |
| 10 | 7 | 无 | 17 |
| 17 | 0 | ErrAmount | 17 |
| 17 | -1 | ErrAmount | 17 |
| 17 | MaxInt64 | ErrAmount | 17 |

```bash
cd labs/platform_path

```

预期测试通过。阅读测试时注意，它既检查错误，也检查失败前后的余额。只检查“报错了”不足以证明失败没有副作用。

### 从规则推导测试，而不是凑输入

正常、边界和非法三类输入对应不同风险。边界通常包括零、允许的最小值、最大值，以及刚刚超过边界的值。

测试还应检查关系。例如一次增加 10 再增加 7，结果应与顺序增加 17 相同；这条关系只适用于当前没有手续费、上限分段或其他规则的模型。规则改变时，关系可能不再成立。

**单元测试**检查一个较小边界内的行为，**集成测试**检查多个组件协作，**端到端测试**检查从使用入口到最终结果。第一阶段的单元测试证明不了数据库提交或真实 HTTP 链路。

## 独立练习：把需求变成可执行证据

1. 新建一个账户，增加 `MaxInt64` 应成功，再增加 1 应失败；检查失败后余额。
2. 创建两个账户，分别增加不同数量，证明一个账户变化不会影响另一个。
3. 写出“每天最多获得 100 积分”的新契约，列明按哪个时区计算一天、跨天请求和已发积分如何处理。先完成需求表，不急着实现。

<details>
<summary>提示与反馈</summary>

第一题同时验证“到边界合法”和“越过边界拒绝”，不能只测一个巨大数字。第三题引入了日期与累计记录，已经超出单余额模型；如果只限制单次 amount，无法限制多次小额领取。

如果修改后出现失败，先回答失败的是哪条承诺，再定位实现。不要通过删断言让结果通过。

## 业务应用：从账户迁移到匹配报名

“玩家加入匹配队列”也可以描述为状态转换：未报名 → 已报名。输入需要玩家、游戏、匹配模式等身份；前置条件可能包括未在其他房间、队伍人数合法；失败后不得留下半支队伍。

报名成功的输出可能是报名 ID，尚不代表匹配完成。把“已接收”和“已完成”分成不同状态，可以避免调用方把中间进度当成最终结果。

为你熟悉的一项业务填写：

```text
业务动作与使用方：
当前状态与输入：
谁负责身份、资格与参数检查：
成功后成立的条件：
失败后必须保持的状态：
本版本尚未覆盖的故障：
对应的测试案例：
```

验收时应能解释一次非法操作为何不改变状态，并指出测试没有证明哪些东西。下一课：[数据所有权与同步](./02_ownership.md)。
