## 本课问题与前置

每秒进入 1,200 个任务，系统每秒只能处理 1,000 个。多创建 goroutine 或增加缓冲，能一直稳定吗？

前置：[所有权与同步](./02_ownership.md)。建议用时 3–4 小时。目标：解释排队增长、制定过载策略、实现能停止的工作池。

## 从任务到工作池

任务互不依赖时，可由几个 worker 并行处理。**channel**传递值；带缓冲 channel 暂存有限元素。

```text
生产者 → 容量为 B 的队列 → N 个 worker → 结果或错误
```

持续到达速率超过处理能力时，积压增长。粗略模型中，每秒净积压为到达量减完成量。容量 2,000 的空队列、每秒净增长 200，约 10 秒填满；真实系统还受突发、耗时分布和重试影响。

**背压**让下游繁忙影响上游，例如阻塞提交、返回过载、限制入口速率。丢弃也是策略，但要符合业务约定：可重建的状态提醒与不可丢失的奖励事件要求不同。

## 取消是一种协议

`context.Context` 传递取消信号和截止时间。`ctx.Done()` 在取消时可被接收，但不会强行终止 goroutine。阻塞点与处理函数都需要配合。

阅读 `pipeline.go`：生产者用 `select` 同时等待投递和取消；生产者负责关闭队列；worker 用 `ok` 判断关闭；`WaitGroup` 等所有参与者退出；首次错误触发取消。

多个分支同时就绪时，`select` 不保证取消优先。源码取到任务后再次检查，但不能承诺“取消瞬间后绝对没有工作开始”。协作式退出与业务副作用提交是两个边界。

## 实验与观察

```bash
cd labs/platform_path
go test -race -run '^TestPipeline' -v
```

三个测试验证有限任务全部完成、阻塞任务收到取消后退出、首个错误被返回。预期全部通过。取消测试中的两秒是失败上限，不是性能指标。

练习 A：扩为 100 个任务，记录同时执行数量峰值，证明不超过 worker 数。计数本身也要同步。

练习 B：让第 3 个任务失败。分别说明已完成、正在执行、尚未开始的任务如何处理。

工作池限制正在执行的任务数与排队 ID，但调用者提供的 jobs 切片已经在内存里，处理函数还可能大量分配。因此队列有界不意味着整个服务内存有界。取消不会撤销已完成效果，重试业务需要独立请求身份。

## 顺序保证的边界

多个 worker 消费同一队列，完成顺序不保证与提交一致。同一会话保序可按 key 分片到固定 worker；哈希冲突使不同 key 相互等待，重启和扩缩容还会改变归属。这些将在第 9 课深入。

达标证据：并发上限测试、过载约定、取消时任务状态表。阅读 [Go Pipelines 与取消](https://go.dev/blog/pipelines)，核对发送方退出与接收方提前停止的关系。下一课：[性能与网络](./04_performance.md)。
