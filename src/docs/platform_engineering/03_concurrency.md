## 需求场景：开服活动让任务越积越多

一个公共服务每秒收到 1,200 个任务，当前每秒只能处理 1,000 个。运营希望奖励不丢，玩家希望尽快知道结果，运维希望内存不会持续上涨。三个目标需要一起考虑。

本课先研究有限处理能力与排队，再实现可控制的并发和退出。目标是能算出积压趋势，按业务选择过载策略，并解释任务在取消之后处于什么状态。

## 基础理论：并发怎样提高处理能力

### 并发与并行

当一个任务等待网络时，另一个任务可以继续运行，并发能够利用等待间隙。若任务都在消耗 CPU，可同时计算的能力最终受 CPU、容器配额和其他资源限制。

把一个任务拆成多个 goroutine，还会引入调度、同步、内存和结果合并成本。如果总工作量没有减少，增加执行者并不保证响应更快。

设一个 worker 平均处理任务需要 20ms，理想情况下每秒完成约 50 个任务；10 个相互独立的 worker 约为 500 个/秒。这个估算要求下游没有共享瓶颈、处理时间稳定、调度开销可忽略。若所有 worker 最终争抢一把锁或同一数据库行，增加 worker 可能只增加等待。

### 同时执行、等待与输入来源

一个工作池可以画成：

```text
任务来源 → 提交策略 → 有限队列 → 固定数量 worker → 结果
```

至少有三个数量需要分别限制：正在执行的任务、排队任务、上游尚未提交却已经占用内存的数据。只给 channel 设置容量，无法限制调用者预先创建的百万个任务对象。

还应检查每个任务的资源，例如单任务读取文件大小、响应体大小和对外连接数。数量有界但单任务大小无限，内存仍可能失控。

## 机制推导：队列能够吸收突发，不能制造产能

令到达速率为 λ，处理能力为 μ，单位都是任务/秒。在持续过载且队列尚未满时：

```text
每秒新增积压 ≈ λ - μ
从空队列到填满的时间 ≈ 队列容量 / (λ - μ)
```

本例差额为 200 个/秒，容量 2,000 的队列大约 10 秒填满。把容量扩成 20,000，大约能撑 100 秒，但并没有解决持续过载。

队列还会增加等待。在稳定处理速率近似为 1,000 个/秒时，排在 2,000 个任务之后的任务可能需要约 2 秒才开始执行。这个估算忽略任务差异、优先级和并发调度，只用于理解容量与等待的关系。

真实系统在平均到达量低于处理能力时，也可能因为突发和耗时波动出现长队。保留余量的目的，是让系统能消化波动，而不仅是让平均值看起来平衡。

## 从业务要求选择背压

**背压**把下游无法及时处理的事实传给上游。可以阻塞提交、限制入口速率、返回过载，也可以把任务可靠保存后稍后处理。策略取决于任务能否等待、重试、丢弃或重建。

| 场景 | 可能的选择 | 必须解释的后果 |
|---|---|---|
| 在线状态刷新 | 合并同一对象的最新值 | 中间变化不保留，最终状态如何收敛 |
| 聊天发送 | 限制用户速率，队列满时返回可见错误 | 用户是否重试、如何避免重复 |
| 奖励确认 | 持久接收或明确拒绝 | 不能在返回已接收后静默丢弃 |
| 日志上传 | 有界缓冲、按等级采样或落本地 | 哪些日志可能丢、如何观测丢弃量 |

限流控制进入速度，并发限制控制同时执行量，队列限制控制等待量。三者作用不同。例如每秒 100 个请求若各执行一分钟，仍可能累积大量在途任务。

## Go 基础：channel 是通信与同步机制

无缓冲 channel 的发送需要接收者配合；带缓冲 channel 允许有限积压，缓冲满时发送会等待。关闭 channel 表示不再有新值，接收者可读完剩余缓冲后观察关闭。

向已关闭 channel 发送会 panic。通常由能够确定“所有发送都结束”的一方负责关闭；多个生产者时需要额外协调。消费者不能因为自己想退出，就随意关闭仍有生产者使用的队列。

`select` 等待多个通信条件之一；多个分支同时就绪时，不应假定按照代码书写顺序优先执行。nil channel 的通信不会就绪，可用于动态禁用分支，也可能导致永远等待。

## 取消是双方协作的协议

`context.Context` 携带截止时间和取消信号。取消不会强行终止 goroutine，也不会自动撤销已完成的业务效果。发送方、接收方、处理函数和下游 I/O 都要决定怎样响应。

```go
select {
case queue <- job:
    // 成功提交给队列。
case <-ctx.Done():
    return ctx.Err()
}
```

若只写 `queue <- job`，当消费者已经退出且队列满了，生产者可能永远阻塞。反过来，worker 取到任务后还应检查是否已经取消，并把 context 传给处理函数。

“检查取消”和“开始副作用”之间仍可能出现状态变化。需要强业务保证时，要在提交边界使用明确协议；不能把一次 `ctx.Err()` 检查解释为取消之后绝不会有操作生效。

### 阅读工作池的顺序

阅读 `pipeline.go` 时按责任追踪：生产者创建并关闭队列；worker 读取与处理；首次处理错误记录原因并发出取消；WaitGroup 等参与者退出；最后返回处理错误或 context 错误。

这里的任务集合有限。长期运行的服务还需要处理新任务接入、资源释放、监控和退出期间的交付状态。

## 实验：成功、取消和失败分别观察

```bash
cd labs/platform_path
go test -race -run '^TestPipeline' -v
```

预期三个测试通过：有限任务全部执行、阻塞任务响应取消、首个处理错误被返回。取消测试中的两秒是避免测试无限等待的失败上限，不代表业务延迟目标。

按下面的表解释一次中途失败：

| 任务状态 | 取消能做什么 | 恢复需要什么 |
|---|---|---|
| 尚未入队 | 停止继续提交 | 保留来源或重新生成 |
| 已入队未执行 | 可以停止消费 | 明确是否重新排队 |
| 正在执行 | 请求协作停止 | 判断副作用是否发生 |
| 已完成 | 不会自动撤销 | 需要时用业务补偿 |

## 独立练习与反馈

第一步：把任务增加到 100，记录同时执行数量的峰值，证明不超过 worker 数。计数本身也要同步，不能为了观察并发而引入数据竞争。

第二步：用 channel 控制某个任务何时开始、何时允许结束，在它开始后发出取消，解释剩余任务状态。尽量用明确的通信协调，而不是依赖短暂 sleep 猜测调度。

第三步：把任务改为“向外部发奖”，解释取消后哪些状态必须查询。此时你会发现需要稳定操作身份，这将连接到第 6、8 课。
