## 需求场景：读得快，重启后还要对

活动列表访问频繁，希望减少数据库压力；玩家积分却不能因为服务重启丢失。匹配对象保存在内存中，每隔一段时间写入存储，运营需要知道故障时会影响哪些操作。

本课把缓存性能与恢复正确性放在一起讨论。完成后应能为每类状态指定权威来源，解释陈旧数据怎样产生，并定义能验证的丢失范围和恢复时间。

## 基础理论：权威状态与派生状态

**权威状态**是发生争议时用来裁决业务事实的数据；**派生状态**可依据它重新生成。例如数据库中的领取记录是权威事实，搜索索引与展示缓存可以是它的派生结果。

组件名称不能决定角色。Redis 可以存缓存，也可以存任务、会话和协调状态。某份数据只存在 Redis 中且无法重建时，它承担的就不仅是缓存职责。

| 状态 | 可能的权威来源 | 派生内容 | 需要确认的业务约定 |
|---|---|---|---|
| 奖励与回执 | 事务数据库 | 展示余额缓存 | 成功后是否要求立即读到新值 |
| 邮件正文 | 持久邮件存储 | 未读数、提醒 | 提醒丢失能否补拉 |
| 在线会话 | 活跃连接与会话协议 | 在线拓扑索引 | 重连如何恢复、过期怎样判断 |
| 搜索结果 | 原始业务记录 | 搜索索引 | 可以落后多久、如何重建 |
| 房间运行态 | 日志、检查点或当前 owner | 本地读取副本 | 故障后允许丢哪些操作 |

缓存被淘汰后可以重建，并不代表重建没有成本。冷启动可能让大量请求同时访问数据库，引起恢复期间的二次过载。

## 缓存基础：命中、未命中与失效

cache-aside 的基本过程是：先读缓存，未命中再读权威数据库，然后回填缓存。写入时更新数据库，并按策略使缓存失效。

**命中率**只是性能维度之一。命中了错误或过期的数据，对业务可能更糟。还要定义陈旧窗口、权威读取路径和失效失败时的处理。

TTL 表示过期机制；容量淘汰表示资源不足时删除缓存项。两者触发原因不同，都不能直接当作业务事实被删除。例如邮件缓存过期不代表邮件本身过期。

## 机制推导：写库后删缓存仍有竞态

按照明确顺序观察两个执行者：

| 步骤 | 读者 A | 写者 B | 数据库 / 缓存 |
|---|---|---|---|
| 1 | 缓存未命中，读到余额 100 | | 100 / 空 |
| 2 | 暂停，尚未回填 | 提交余额 110 | 110 / 空 |
| 3 | | 删除缓存 | 110 / 空 |
| 4 | 恢复，把刚才读到的 100 回填 | | 110 / 100 |

B 确实按“先写库、再删缓存”执行，最终仍可能出现旧缓存。问题来自读者的迟到回填。

TTL 可以限制某次回填后的存活时间，但不是“距权威更新最多陈旧这么久”的完整证明：暂停很久的旧读者可能在更新很久后才回填。还需检查回填时机、并发更新、时钟和失效链路的假设。

## 实验一：实际复现迟到回填

完成 MySQL/Redis 环境初始化后运行：

```bash
cd labs/platform_path
bash sql/cache_race.sh
```

预期输出包含：

```text
database=110 cache=100
PASS: stale fill reproduced; synthetic cache key expires in 60 seconds.
```

脚本先把 A 的查询结果保存在变量，再执行 B 的提交与删除，最后让 A 回填。这个顺序与并发中的一种合法交错相同，因而能稳定复现，无需依赖 sleep 碰运气。

每次实验使用独立虚构租户，保留其数据库行；缓存键 60 秒过期。它验证陈旧回填的可能性，不模拟真实网络时延或验证某种自动修复策略。

### 如何从需求选择修复方向

活动说明允许短暂旧值，可以采用明确 TTL、失效重试与监控。领取资格和资产扣减需要权威判断，可以绕过展示缓存。版本化缓存或有序更新可以拒绝部分旧写，但要求版本来源可信，且比较与写入原子执行。

singleflight 能合并当前进程里同一 key 的并发加载，减轻击穿；它不自动提供跨进程协调，也不解决所有写入竞态。负缓存需要区分确实不存在与依赖临时失败，否则可能把故障结果长时间缓存。

## 持久化基础：为什么需要日志

如果只在内存更新，崩溃就可能丢失状态。每次把整个对象写回磁盘又可能成本很高，而且写到一半还会出现不完整状态。

**预写日志（WAL）**先保存足以恢复变化的记录，再按协议更新数据页。恢复时结合日志和提交信息重做已确认变化，或处理未完成操作。具体系统还可能用 undo 支持回滚与历史版本，用检查点减少需要扫描的日志范围。

这些机制相互配合。只把一行文本 append 到文件，尚未解决记录完整性、同步刷盘、提交标记、重放幂等、损坏与截断恢复。

### 检查点与周期保存

检查点保存某个时刻的状态；日志记录之后的变化。若只每 5 秒保存一次且没有可重放记录，异常退出可能丢失尚未保存的操作。实际丢失窗口还受保存耗时与失败影响，不能直接保证绝不超过 5 秒。

优雅退出可以增加最后一次保存机会，但断电、强杀和机器丢失不会保证执行退出逻辑。正常退出路径与故障恢复路径需要独立设计。

## 恢复目标：允许丢多少，多久恢复

**RPO**表达可接受的数据恢复点差距，**RTO**表达恢复服务的目标时长。教学例子可以设“已确认奖励不允许丢，服务允许暂停恢复”；匹配运行态可能允许从检查点重建并让玩家重新排队。

这两个指标需要明确故障范围。进程崩溃、本机磁盘丢失和整个区域故障，恢复手段不同。备份也需要恢复演练，仅证明备份文件存在并不能证明可以重建业务状态。

写出恢复顺序：确定权威版本 → 加载检查点 → 重放后续记录 → 校验不变量 → 恢复接流量。若先接收新请求再重放旧日志，要额外处理交错与重复。

## 业务应用：邮件提醒与游标补拉

持久邮件存在后，实时通知可以告诉玩家“有新内容”。通知丢失时，客户端根据已保存的游标继续拉取。这里可靠性来自邮件存储、查询协议和游标推进规则。

游标应在相应数据处理成功后推进。先更新游标再处理，崩溃后可能跳过未处理内容；后更新则可能重复拉取，需要处理端能识别重复。

Redis Pub/Sub 提供实时发布订阅，不能自动当成持久可回放的事件日志，见 [Redis Pub/Sub 交付语义](https://redis.io/docs/latest/develop/pubsub/)。选型时先问需要实时提醒、持久队列还是可重放日志。
